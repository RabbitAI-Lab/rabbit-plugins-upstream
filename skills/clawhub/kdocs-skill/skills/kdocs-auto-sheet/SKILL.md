# 自动化流程（工具路由索引）

本文件包含金山文档「自动化流程」的查询与校验说明。

**适用范围**：支持查询自动化上下文与可用动作，以及流程的查询、读取、校验、保存、启停、删除，运行记录与节点结果查询。

**不适用范围**：常规文档内容编辑、文件管理及自动化流程以外的表格操作。遇到上述域外需求、需要借助其他组件定位文件或准备外部资源，或无法判断请求应由哪个组件处理时，[返回主 Skill](../../SKILL.md)安排，不自行切换子 Skill。

以下工具不可逆，调用前必须向用户确认；参数与边界以 `kdocs-cli help <tool>` 的工具卡 为准：

`auto_sheet.save_flow`、`auto_sheet.delete_flow`

自动化流程 = **触发器** + **一串节点**。触发器决定流程什么时候跑，节点决定跑起来做什么。
查询、校验、创建、修改、启停、删除都已开放；写操作遵循**先读后写、先草稿后启用**。

## 执行入口（先读这一节；以下是分主题细则）

> **本手册的分工**：**入口、顺序、判据、红线、话术**在下面 §0–§9（手写，不随平台变）；
> **动作总表与验证级别**来自生成子册 **[actions-catalog.md](references/auto_sheet/actions-catalog.md)**
> （块内由构建从平台抓取生成，勿手改）；**平台事实与踩坑**见
> **[platform-facts.md](references/auto_sheet/platform-facts.md)**（手写，直接维护）。不要在本手册里另抄一份。

### 0 前置：任何自动化任务的第一步

1. `auto_sheet.get_context` —— 拿到 `file_id`、`automate_type`（`db_sheet`/`et_sheet`）、
   工作表与字段（**名称 ↔ id**）、已有流程、可用触发器类型与字段要求、容量上限。
2. **拿不到就不猜**：表名、字段名、流程名一律用接口回传的；不要拿用户口语或记忆直接写进去。
3. 改已有流程前先 `auto_sheet.get_flow` —— **读出来的 DSL 就是唯一事实**，
   不要凭"我记得这个流程是……"动手。

### 1 任务分型（先分清，再动手）

| 任务 | 链路 | 出口（完成条件） |
|------|------|------------------|
| 新建流程 | `get_context` → `list_actions` → `save_flow(dry_run)` → **用户确认** → `save_flow` →（需要才）`set_trigger_status` | 回读一致 + 启用状态**明确告知** |
| 修改现有流程 | `get_flow` → 只改要改的 → `save_flow` | 回读一致；`enabled` 未显式传 = **沿用** |
| 排错 | `get_flow` / `validate_flow` → 定位 → 改 | 校验零 `errors` + `set_trigger_status(check_only)`（真机运行仅用户要求时） |
| 批量 | `list_flows` → 逐个处理 | 逐条回读；**不要并发写同一文件** |

### 2 主线：新建流程（按顺序，每步都有判据）

1. `get_context` —— 判据：拿到表/字段清单与 `automate_type`。
2. `list_actions`（只查要用的动作）—— 判据：参数名/必填/取值形式**照抄接口**，不凭记忆。
3. 组 `flow = { name, func_desc?, trigger, steps[] }` —— 判据：节点 `key` 唯一；引用只指向**前序**节点。
4. `save_flow(dry_run=true)` —— 判据：零 `errors`；有 `warnings` 要逐条判断能不能接受。
5. **复述给用户并等确认**（话术见 §6）—— 判据：用户明确同意写入；危险写/启用另见 §4。
6. `save_flow`（正式写入）—— 判据：回读 `verified=true`。
7. 要跑才 `set_trigger_status(enabled=true, confirm=true)` —— 判据：用户明确要求"直接生效"。
8. 真机验收（**仅当用户明确要求**，如「帮我跑通 / 真机验收」）—— 判据：节点 `exec_status=1` **且回读到业务结果**。
   默认交付到第 6/7 步就结束，并把「怎么验收」告诉用户（改哪条记录、改成什么、预期收到什么）；
   用户触发一次后，用 `auto_sheet.list_runs` 核对节点状态与正文（不需要打开浏览器）。
9. 清理 —— 判据：验证用的探针流程/记录都删干净。

### 3 决策点（几句话说完）

- **触发器**：先 `manual` 跑通，再换 `cron` / `db_event`；事件触发要写 `event.type` + 工作表 + 字段。
- **动作**：用能覆盖意图的**最少节点**；消息类节点必须核对"发出去了几条"。
- **参数形态**：字面量 / `{"$var":…}` / `{"$template":…}` / `{"$sheet":…}` `{"$field":…}` / `{"$raw":…}`（白名单）。
- **表相关**：引用"某表某字段"一律走接口给的 id（见「`$var` 的点后段必须是**列 id**」）。

### 4 安全红线与授权（判据化，不靠感觉）

- **不默认运行**：新建/修改只交付"已保存"；`enabled=true` 必须用户明确要求 + `confirm=true`。
- **删除类**：先 `list_flows` 确认候选并把**流程名回显**给用户；`delete_flow` 必须 `confirm=true`。
  已授权判据：**用户点名了对象且不追问就能唯一确定"删什么、删多少"** → 直接执行；否则先问。
- **危险写动作**（清空整表 / 批量删）必须限定范围，否则编译期硬拦（见「危险写动作必须限定范围」）。
- **脚本节点 = 影响面未知**：脚本内容不在我们可控范围；交付按"已配置"说，不按"已执行成功"说。
- **探针与回滚**：只回滚**本轮自己新建、尚未交付**的资源；用户既有数据一律不动。

### 5 失败处理 playbook

- **`code=400001`**：平台校验未过 → 按 `errors[].kind`（配合 `step_id`）定位到具体节点/参数（见「校验失败」节）；
  **不要拿同一份配置改参重试**。
- **保存/校验失败**：先**简化到最小版**（单个触发器 + 单个合法动作）存草稿，通过后再逐步加；
  仍失败就输出原始错误摘要 + 未完成项，**不要 `print(err)` 之后当成功结束**。
- **预检优先**：表/字段/选项的存在性在保存前查（三层闸门），**不要用保存失败反推配置缺口**。
- **不确定参数支不支持**：选**副作用最小**的一条先跑，用真实回读代替反复权衡；失败一次再换。
- **有浏览器时，交付前可抽查一眼画布与右侧「配置参数」面板**（渲染抽查，不是验收依据）：
  三层闸门全绿也可能渲染是空的（节点入参少一条 / 分支形状不对都会这样，见「配置参数面板空白」类条目）。
  面板整片空白先怀疑 **入参面与模板声明面没有逐条对齐**，别只看 `verified=true`；没有浏览器就按
  「验收标准：三层闸门」执行。

### 6 交付话术契约

| 情形 | 可以说 | **不能**说 |
|------|--------|-----------|
| 写入成功但未启用 | 已保存（草稿） | "已经自动运行了" |
| 已启用 | 已保存并启用 | "会自动执行成功" |
| 真机跑过且回读到结果 | 已真机验证：节点成功 + 结果值 | 泛化成"所有场景都验证过" |
| 动作级别是"仅形状" | 形状已对齐、未真机验证 | "已验证" |

### 7 能力边界（不做 / 换路）

- 脚本**内容**不能通过接口新建/编辑（平台没有这个接口）→ 让用户在界面建好，我们只引用 `script_id`。
- 表格（ET）侧目录与真机**都已核对**（不再只是"形状"级）：ET 专属动作 `write_data` / `filter_rows` /
  `create_sheet` 在 prod 真机跑通（「已将 [2] 行 [2] 列数据写入到 [Sheet1]」「获取 [1] 行 [1] 列数据」
  「已创建工作表 […]」）。ET 的结构型参数（`info` / `data`）**必须落成平台结构体**
  （`FileRangeInfo` / `DataFrame`），落成标量会在运行前报 `10001`。
- **ET 的动作面比界面窄**：白名单只有 6 个（`write_data` / `filter_rows` / `create_sheet` /
  发送WPS协作消息（`send_woa_message_v9`）/ 延迟 / 飞书群机器人）。界面上还有
  MySQL / SQLServer / PostgreSQL / Oracle / 公众号 / 快手 / 巨量千川 等，**都不在目录内**；
  **ET 侧没有 notify 系**（既无 `notify_v3` 也无 `notify_v4`，公众号/文档消息只在多维表格可用）——
  用户点名这些动作时按"形状带回"，不要承诺可用。
- 触发器**按文件类型分家**（界面实测）：表格（ET）只有 3 类（修改表格时 / 定时触发 / 手动触发，
  对应 DSL 的 `event` / `cron` / `manual`）；多维表格 7 类（`manual` / `cron` / `db_event` /
  `webhook` / `button` / `wps_approval_create` / `wps_approval_change_status`）。
  `auto_sheet.get_context` 的 `triggers` 会按文件类型裁剪，每条另带 `applies_to` 标明适用类型 ——
  不要拿另一类文件的触发器去套。
- 未知/未登记动作：只做**形状带回**，不校验语义。
- **不要手写 canonical**；形状以界面产物为准（见「形状金标准」）。

### 8 推理与调用预算（省轮次，不影响正确性）

- 探查结果**不要在推理里复述** —— 直接引用字段名/结论。
- **不在推理里起草流程 DSL 正文** —— 只在工具调用里写一遍。
- 同类改动**一次改完**（例如给多个节点加同一个参数），不要一个节点一轮往返。
- 系统限制类问题用**一次试探**代替枚举猜测；试探仅限**非破坏**操作（读 / 校验 / `dry_run`）。

## 查找内容里的时间条件（真机实测）

「采购日期早于当前 N 天」这类**相对时间条件，查找节点（`db_search_rows` 的 `search_range.filter`）表达不了**。
2026-09-24 真机四形状对照：

| 筛选值写法 | 真机结果 |
|---|---|
| `{"$var":"var_time_recent_day.7"}`（编译成 `__exp_kind__:variable`） | ❌ 查找节点**运行期** `内核错误: E_INVALIDARG` |
| `{"type":"Text","value":"$var_time_recent_day.7 "}`（变量串当字面量） | ⚠️ **不报错、条件被静默忽略**，命中全表 |
| `{"type":"Text","value":"2026-09-17"}`（字面量日期） | ✅ 正常命中 |
| `{"type":"DynamicSimple","dynamicType":"Last7Days"}` + `NotIntersected`（平台自己的相对日期） | ❌ `E_FAIL` |

（真机验证的是 **Date** 字段；`CreatedTime` / `LastModifiedTime` 属同类，编译器一并告警，但未单独真机验证。）

- **静默忽略那一行最坑**：流程能存、能启用、运行日志写着「成功」，只是过滤条件形同不存在 ——
  会把**全表**记录都当成命中行去发通知。真机那一跑「查找到 [21] 条」正是全表。
- 所以「早于当前 N 天还没入库 → 提醒提交人」这类需求**不要**用查找筛选写，三条可走的路：
  1. **字面量日期**（把某一天写死，适合一次性排查）；
  2. **在表里加一列公式**，把「是否超期」算成可筛选的值（如按天差判断），再用**字面量**条件筛 ——
     动态性来自公式列，不来自筛选值（公式列做条件的注意事项见 `trigger-snapshot-formula-column-lags`）；
  3. **改用「执行脚本」节点**：脚本里自己算日期、自己筛、自己发消息。
- 这类需求还要先想清楚**去重**：查找 + 发消息的写法**每次运行都会重发**（同一条超期记录天天提醒），
  用户没说「每天提醒」时要在计划里提出来。
- 保存期我们会对「时间类字段 + 动态取值」给出 **warning**。
  看到这条 warning 就必须改写法 —— 它在运行期一定会出问题（报错或静默失效）。

## 按条件只在特定状态变更时通知（真机验证的最佳做法）

「某字段变成某个值时才通知」这类需求有**三种做法，优先级从高到低**（都经真机检验）：

| 优先级 | 做法 | 代价 | 实测结论 |
|---|---|---|---|
| ①（正解） | **触发器筛选**：`event.filter_result`（如 状态 ∈ [已入库]）+ 动作直接引用 `${trigger_dataframe.<列>}` | 零查找、零分支，一次变更发一条 | ✅ 可用：把**界面形状**的 `filter_result` + `queryRanges` **原样透传**给 `save_flow`（工具没有可读 DSL 糖，照抄界面产物即可）。⚠️ 筛选判的是**改后**值 ⇒ 条件写**目标态**：要「改成已入库就通知」就写 `∈ [已入库]`，**写成改前值就是把方向写反**（见下面纪律） |
| ②（**已证伪**） | 查找节点 + `search_range.ever_result = {"$var":"trigger_dataframe"}` | —— | ❌ **运行失败**：保存/dry_run/开启都能过，运行期不成立。`ever_result` 的语义是"沿用**上游查找**结果"，不是"绑触发记录"。**不要再推荐** |
| ③（最后选择） | 条件分支（`branch`/`sub_branch`） | 结构节点形状讲究、开启期校验严格 | ⚠️ 形状差异未修完 |

**用 ① 时必须一起定「监听字段」（`event.field_ids`）—— 它决定「改哪些列会触发」，筛选替代不了**（平台事实 `trigger-field-ids-vs-filter-are-orthogonal`）。
三条纪律：

1. **条件用到的列一定要写进监听字段**（如「采购单价 ≥ 1000」⇒ `field_ids` 必须含 `采购单价`），否则「改这一列」根本不会触发；
2. **不要默认全选**：type=7 的新增路径语义是「以下字段**全部非空**」，全选 6 列几乎不可能同时非空 ⇒ 等于放弃「新增就通知」（平台事实 `trigger-watch-fields-default-select-all`）；
3. 要保住新增路径，就**裁到「新增时必然同时填写的那几列」**（如 采购数量 / 采购日期 / 采购单价，表单必填）—— 这也是裁剪后仍覆盖「修改」的常用集合。

**正文可以引用任意列，不必把列塞进 `queryRanges`**：2026-10-08 真机（`queryRanges` 只写了 5 列）运行日志里触发行仍带**整表 14 列**
（含未被监听、也未被引用的 备注说明 / 入库通过）⇒ `${trigger_dataframe.<任意列>|each,plain}` 都能渲染；`queryRanges` 照抄界面形状即可，别为它纠结。

### 查找 + 条件（②）的写法（2026-10-08 真机更正）

⚠️ **`search_range` 是单选**：`filter.criteria` 与（非空）`ever_result` **只能给一个** —— 编辑器里「设置查找范围」就是**同一格 cascader**
（要么「按条件筛选」、要么「选某个步骤的结果」）。两个都给时保存 / `dry_run` / 回读**全部成功**，但流程跑到该节点**必失败**「流程配置存在错误」
（真机单变量：同一节点带 `ever_result={"$var":"trigger_dataframe"}` ⇒ `exec_status=2`；**摘掉它、其余逐字节相同** ⇒ `exec_status=1`「查找到 [1] 条记录」）。
⇒ **不要再写 `ever_result`**（这也解释了 `ever-result-trigger-binding-fails`）；平台事实 `search-range-modes-are-exclusive`。

正确形状（真机端到端通过：改一条记录 → 企微群收到消息，正文渲染出真实值）：

```jsonc
{ "trigger": { "type": "db_event", "event": {
      "type": 7, "sheet_id": {"$sheet": "采购入库"},
      "field_ids": [{"$field": "采购入库.状态"}] } },
  "steps": [
    // 判【公式列】时必须在最前面插一个延迟（见下）：{"key":"s0","action":"delay","params":{"delay_time":10}}  单位=秒
    { "key": "s1", "action": "db_search_rows", "params": {
        "sheet_id": {"$sheet": "采购入库"},
        "search_range": { "filter_type": "filter",
                          "filter": { "mode": "AND",
                                      "criteria": [{"field": "状态", "op": "eq", "value": "已入库"}] } },
        // 未命中就终止：避免"不达标的记录也发一条消息"
        "on_not_found": "exit",
        "fields": ["采购记录", "采购数量", "状态", "采购总金额"] } },
    { "key": "s2", "action": "send_wecom_robot_message_v6", "params": {
        "webhook": "<用户提供的 webhook>", "message_type": "text",
        "message_content": {"$template": "已入库：${s1.采购记录|each,plain} ${s1.采购数量|each,plain}"} } }
  ] }
```

- `on_not_found`：`continue`（默认，继续执行）/ `exit`（终止；在分支中只终止当前分支）—— 取值来自平台自己的参数模板。
- 查找是**全表条件查**，命中多行时正文 `|each` 会逐行渲染 ⇒ **发几条消息由命中行数决定**；触发器里能表达条件时优先用 ①。

⚠️ **判公式列（如 `采购总金额`）必须多一步「延迟」**：公式列是**异步重算**的（真机实测，门店销售表 `销售总额=[@零售价]*[@销售数量]`）——
改「销售数量 462→599（总额 78078→101231）」后，**+0s** 跑查找（条件 `销售总额>100000`）⇒ **查找到 [0] 条记录**；**+2s / +3s / +5s / +10s** ⇒ **全部 [1] 条**；
同一跑里把条件换成**非公式列**（`销售数量>590`）⇒ **立刻**命中 [2] 条。变更触发是**写入瞬间**触发的，所以「改完立刻查公式列」永远慢一拍。
⇒ 形状：`事件触发 → 延迟(≥3s，平台限 1~60 秒) → 查找(条件判公式列) → 消息`。

**「那用触发器筛选（红框里的『同时满足以下条件』）行不行？」—— 不行，判公式列时它必漏掉你要的那一次**。
2026-10-08 真机对照（同表同时刻，两个 type=7 流程，监听字段都是 `销售数量`、动作都只是一步「延迟 3 秒」）：

| 触发器筛选 | 写入① 数量 462→600（总额 78078→101400，**由下穿上**阈值） | 写入② 600→601（本就在阈值上） |
|---|---|---|
| A：`销售总额 > 100000`（**公式列**） | **runs 0→0（不触发）** ❌ | runs 0→1（触发） |
| B：`销售数量 > 590`（**非公式列**） | runs 0→1（立刻触发） ✅ | runs 1→2 |

⇒ 判**公式列**时触发器筛选**只认「改动前」的公式值**，「把不达标的记录改成达标」那一次**必然漏掉**（恰恰是需求要的那一次）；
只有「本来就在阈值上」的记录再改才会触发 ⇒ **别指望用它代替「延迟」**。判**非公式列**时它完全正常 —— 那才是 ① 正解，优先用它。
**两个都不能用 `ever_result` 绕**（与 `filter` 互斥，运行必失败）。

**「那用条件算 `零售价 × 销售数量` 呢？」—— 平台的条件算不了乘法**。三处判定都只有「字段 + 比较操作符 + 字面量」：
触发器筛选 `filterFields[{field, op, values}]`、查找筛选 `search_range.filter.criteria[{field, op, value}]`（最终下发 `dbsheet.ListRecordsByFilter`，左值只能是字段 id、右值只能是字面量 ——
值类型只有 `Text` / `DynamicSimple` 两种，写变量/表达式会被**静默忽略**成全表命中）、分支条件 `{operate1, operator, operate2}`（操作符全集是**比较类**：`Greater/GreaterOrEqual/Less/LessOrEqual/Equal/In/NotEqual/Empty/NotEmpty`，没有算术）。
⇒ 「销售总额 > 10万」只能落在公式列上。**唯一能算乘法的是脚本节点**（`airscript_v2` / `run_python_script_v2`，入参可用 `${trigger_dataframe.销售数量}`；非公式列当场就是新值），
但要自备脚本、且 `零售价` 在 DataFrame 里是带格式的货币文本（`￥169.00`）需自行解析，未真机验证 ⇒ 不作为推荐，仍以「延迟 + 查找」为准。

数值条件（如「单价>50 且 数量>100」）的形状**有坑**（真机验证）：

```jsonc
"filter_result": {
  "filterFields": [
    { "fieldType": "Number", "id": "H", "name": "采购数量", "numberFormat": "0_ ",
      "op": "Greater", "sheetStId": 3, "isHidden": false, "isNoPermission": false,
      "values": [{"type": "Text", "value": "100"}] },        // ← 数值也用 Text + 字符串
    { "fieldType": "Currency", "id": "K", "name": "采购单价", "numberFormat": "￥#,##0.00;￥-#,##0.00",
      "op": "Greater", "sheetStId": 3, "isHidden": false, "isNoPermission": false,
      "values": [{"type": "Text", "value": "50"}] }
  ],
  "opType": "And",            // 多个条件用 And/Or
  "sheetId": 3                // ← 顶层还有它，别漏
}
```

- `numberFormat` 用**字段自己的格式串**（`get_context` 的 `fields[].numberFormat` 已返回，别再手写 `"0"`/`"0.00"`）；
- `op` 用平台枚举（`Greater` / `Less` / `GreaterEqu` / `LessEqu` / `Intersected` …），组合 `opType: And`；
- `field_ids` 写"哪些字段变化时触发"（本例 `["H","I","J","K"]`）。

纪律：

- **不要默认用分支**：先问"触发器能不能表达这个条件"（①），不行就"查找+筛选条件"（②，**不要写 `ever_result`**；判公式列再加「延迟」节点）；分支留给"同一触发下要分流做不同事"的场景。
- 触发器**没有**筛选、流程里靠查找过滤时，注意范围：查找是**全表**查 → 会把历史命中的行**逐条**发一遍；要"只针对本次改动的那条记录"，用 ① 触发器筛选。
- **默认不做真机验收**：这类流程的触发就是真实执行（改用户数据、发不可撤回的消息）。默认只做配置级验收
  （`dry_run` / 回读 `verified=true` / `set_trigger_status(check_only)`），并把验收协议写给用户——
  改哪条记录、把哪列改成什么、预期收到什么。**只有用户明确要求**（"帮我跑通/验收"）才改真实记录、发真实消息，
  且要先问清动哪条记录、用完还原。用户触发之后的事后核对交给 `auto_sheet.list_runs`（只读）：
  列表看「跑没跑、成功吗」，传 `task_id` 看节点状态与正文——这一步不改数据、也不需要浏览器。
- **「某字段改成 X 就通知」→ 筛选写【目标态】X**（平台事实 `trigger-filter-judges-post-change-value`）；
  筛选判的是**改后**值，消息正文与分支条件里的变量同样取新值。
  ⚠️ 写成**改前值**是常见错法 —— 真机反例（采购入库，监听字段=状态，筛选 `状态 ∈ [未入库]`）：
  「未入库→已入库」**runs 不变（需求那一跳永不命中）**，反而在「改成未入库」时触发；
  type=7 的新增路径（新增时状态=未入库）还会误报一条，正文出现「已变更为已入库…当前状态：未入库」自相矛盾。
  平台不给旧值 ⇒ **表达不了严格的「从 A 改到 B」**（分支条件同样吃新值），要严格只能加一列「上次状态」由流程自己回写。
- **公式列才是「改动前」的快照**（平台事实 `trigger-snapshot-formula-column-lags`）：**修改路径慢一拍**、**新增路径取 0**，
  **消息正文里打出的公式列数字也是旧的** —— 曾实测正文出现「采购数量：123 / 采购总金额：136800」这种自相矛盾的组合（123×456 应为 56088）。
  ⇒「把不达标的记录**改成**达标」在**以公式列为条件**时**不会**提醒（只有本来就在阈值上的记录再改才会）；
  需求若这么写必须补边界说明，或把条件改用公式的**输入列**。
- ⚠️ 因此用公式列做条件的流程，若做真机验收则**必须两拍写入**：先把公式**预热**到目标值（写一次不相关的列），
  再用**非公式列**触发第二次，两次都看运行日志。直接一次写入会让「快照是旧值」看起来像「分支没命中」。
  条件里做不了乘法，所以公式列是表达「金额 > N」的唯一办法 —— 不能靠改写条件绕开，只能把边界讲清楚。

## 两类自动化，动作集不通用

| 文件类型 | `automate_type` | 节点动作 |
|----------|-----------------|----------|
| 多维表格（.dbt） | `db_sheet` | `db_search_rows` / `db_insert_rows` / `db_update_rows` / `db_delete_rows` 等 |
| 表格（.xlsx / .ksheet） | `et_sheet` | `write_data` / `filter_rows` / `create_sheet` 等 |

两类都支持的动作只有 `delay` 与 `send_woa_message_v9`（个人消息）；`notify_v4`（公众号/文档消息）、
HTTP 请求、执行脚本、日程/邮件等只适用于多维表格；群机器人渠道两边各支持一部分（多维表格：企微/钉钉；
表格：飞书）。**名称以 `db_` 开头的动作只能用于多维表格**，
`write_data` / `filter_rows` 等只能用于表格——放错类型会在校验时报 `type_mismatch`。

`automate_type` 通常不必手填：服务端读文件元信息的 `office_type` 自动判定，
并在响应的 `automate_type_source` 里回传判定来源，便于核对。
