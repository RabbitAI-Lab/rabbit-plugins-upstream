# 章节写作工作流

从接到"写第 X 章 / 某小节"到交稿的步骤。每一步都服务于"读者读得懂、由浅入深"。

## 第 1 步:明确读者与前置知识

动笔前确认(不清楚就问用户):
- **读者是谁**:本科生?转行工程师?有经验的开发者想补概念?
- **已经会什么**:这决定"锚点"设在哪(原则 2)、哪些术语要解释、哪些可假设已知。
- **篇幅与深度**:一节还是整章?要不要代码/习题?要覆盖到什么程度。
- **这一章在全书的位置**:前面讲过什么(可以引用),后面会讲什么(可以推迟,原则 6)。

> 读者画像错了,后面全错:给专家写会啰嗦,给新手写会跳步。这一步别省。

## 第 2 步:定一句话"核心问题"

写下这一章要回答的**一个**核心问题,和读者读完应建立的心智模型。
- 例:"只有少量物理 CPU,OS 如何制造出近乎无限 CPU 的假象?"
- 例:"为什么需要 Kubernetes,它到底在管什么?"
- 如果一章有多个核心问题,考虑是不是该拆成多节,每节一个问题。

## 第 3 步:设计叙事弧线

在写正文前先列大纲,骨架通常是:

```
动机(为什么要学这个,原则1)
 → 锚点/类比(挂到已知,原则2)
 → 具体例子或现象(原则3;可用意外制造好奇,原则4)
 → 抽象出原理/概念(此时命名术语,原则5)
 → 逐层加细节(螺旋上升,原则6)
 → 闭环收尾(小结+回扣+预告,原则7)
```

技术章节可借两种成熟结构:
- **OSTEP 式**(讲原理/机制):关键问题 → 简化方案 → 暴露问题 → 加限制 → 再暴露 → 再补。
  用"问题链"牵着读者走,每解决一步就亮出下一个问题。
- **K8s 式**(讲工具/实操):原理介绍 → 上手实战。先建立心智模型,再给命令/YAML 落地。

## 第 4 步:由浅入深填充

按大纲写正文,边写边守两条铁律:
- **每引入一个概念前,先给它的动机**——问自己"读者到这里会不会觉得莫名其妙?"
- **每个抽象前,先有一个具体的锚**——代码、图、真实输出或生活场景。
- 控制新术语密度(一段 1~2 个),首现即解释。
- 遇到复杂细节,判断:是主线必需?否则明确推迟到后文,不要打断当前逻辑。

## 第 5 步:加深度分层

回头给正文加"框"和旁白,把主线之外的信息分流出去:
- 核心问题 → **关键问题框**
- 可迁移的通用原则 → **提示/设计原则框**
- 满足好奇的旁支(历史、命名、八卦) → **补充框或脚注**
- 留给读者思考的开放问题 → **思考题**
- (可选)整章开头用一段**对话/预告**降低陌生感,像 OSTEP 的师生对话或 K8s 的"本章分两部分"。

## 第 6 步:闭环收尾

- 小结:用两三句重述本章要点(可换个说法,重要的事讲第二遍)。
- 回扣:回到第 2 步那个核心问题,确认已经回答。
- 预告:告诉读者下一章/下一节会解决哪个新冒出来的问题,形成向前的牵引。

## 第 7 步:对照清单打磨(自检)

用 checklist.md 逐条自检。特别检查:有没有哪个术语没解释就用了?有没有哪段是
"定义先行"而非"动机先行"?有没有一次性堆太多细节?深度是否达到 SKILL.md 的深度基线?

> **到这里只是"可送审的草稿",不是成品。** 教材靠迭代打磨出来,单遍自检抓不到
> "作者以为讲清楚了、读者其实没懂"的盲区。进入下面的迭代阶段。

## 第 8 步:多角色盲审(详见 review-loop.md)

把草稿落成独立文件(不含作者思路),并行派三个互不接触编写上下文的子 agent 审阅:
- **基础薄弱学生**:测"读得懂吗、够不够详细";
- **进阶/研究生**:测"够不够严谨、够不够深、有无独到见解";
- **授课教师**:测"能不能直接拿去教、例题习题实验够不够"。

## 第 9 步:综合反馈并修订(含全局取舍)

把三份报告合成一张修订清单,标共识/冲突/优先级;冲突处用"分层满足"化解(主线给
学生,旁注框/附录给进阶生,习题与教辅件给教师)。

**全局取舍(必做):** 三份反馈以孤立视角要求本章讲透"一切",但章节不是孤岛。
对每条"补充解释/展开"类反馈,必须判断:是本章核心,还是其他章节(前置/后续)应
承担?后者不在此展开,改为**显式引用**("详见第 X 章"),避免全书臃肿冗余。

逐条落实,产出新版。**重复 8~9 共 1~2 轮**至收敛(判据见 review-loop.md)。

## 第 10 步:验收(不可跳过)

对照 review-loop.md 的验收门槛 + checklist.md 全表逐条核验(含全局取舍类),
给出验收结论与变更摘要。未过则打回继续迭代。
