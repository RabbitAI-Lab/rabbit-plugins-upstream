# foreman · Chapter 2 · Acceptance

Precondition: the changes are merged into the integration branch and `integration_sha` is written into `.foreman/batch.json`. **Acceptance runs against the integrated state only, never per-worktree** — each branch being green on its own proves nothing about the merge. If the integration SHA or the batch membership changes, every prior acceptance result is void and gets re-run.

## 1. Dynamic acceptance (only for apps that can actually be booted)

This step needs a **dynamic checker**: something that boots the app, exercises it, and writes structured findings to disk. Point foreman at yours by setting `FOREMAN_HARDENING_CMD` — any tool works as long as it satisfies the three rules below. Playwright/Puppeteer smoke suites, a homegrown boot-and-crawl harness, or a commercial scanner are all fine.

```bash
RUN_DIR=$(mktemp -d)
$FOREMAN_HARDENING_CMD <repo> --run-dir "$RUN_DIR"   # exact flags depend on your tool
```

The three rules that make this step trustworthy, and which matter far more than the tool you pick:

- **Output must go into a brand-new run directory.** Reusing a directory means a crashed run can be judged against the previous run's artifacts — a false green that looks identical to a real one.
- **Ignore the exit code.** Checkers of this kind routinely exit 0 whatever they found. Judge only on artifacts that *this* run newly generated: count the P0 findings, check that boot succeeded.
- **It is a negative gate only.** A clean report proves the app is not broken. It never proves the requested work was done — that is section 2's job.

Pure libraries, CLIs, and backend services: **skip this section entirely.** Acceptance for them = section 2 plus a static review pass. No dynamic checker configured is a valid state, not a failure; foreman degrades to section 2 and says so.

## 2. Task-level verification (mandatory for every repo; equal weight to P0)

- Re-run each work order's verification commands, one order at a time. In the integrated state you can run the full versions including the ones with side effects, once.
- **Any single order failing = acceptance failed.**
- This is the section that proves the requirement was actually met. Section 1 only proves nothing visibly broke.

## 3. Repair loop

- P0 > 0, or any task-level verification failing: build a repair package that carries **only the finding delta** — three lists: newly appeared, now fixed, still outstanding. History does not go back into the main session's context. Redispatch to the same batch per `dispatch.md` §3 and increment `total_rounds`.
- Second occurrence of the same fingerprint, or `total_rounds` ≥ 4 → circuit-break, report to the user with the manifest attached, and stop auto-cycling.

## 4. Release and the CI final word

Everything green locally is only a **preflight**. Once the PR is open, CI is the final authority:

- **CI that can run a browser**: run the dynamic checker itself (fresh run-scoped directory + manifest must be newly generated by this run + P0 == 0 + boot ok), plus re-run every `persistent` verification command. Template: `<skill-dir>/ci-gate.yml`.
- **CI that can't run a browser** (an explicitly accepted degradation): the dynamic check becomes a non-blocking preflight and the gate becomes the task-level verification commands.
- **First time using foreman in a given repo**: copy `ci-gate.yml` into `.github/workflows/`, adjust the start command for that repo, and add `.foreman/` to `.gitignore`.
- Lifecycle: `one_shot` commands are archived and retired after merge; `persistent` commands become named regression tests that stay in CI. This is what keeps a workflow file from rotting into 18 months of accumulated cruft.

## 5. Wrap-up

- Set `batch.json` status to done; archive the task state files into `.foreman/archive/`.
- Monthly calibration data: how many times the clock forced a dispatch that had been exempted, versus how many small tasks came back perfect in one round (`handoff list` + `.foreman/archive/`). Whichever count is higher, move the 30-minute threshold one notch that way.
