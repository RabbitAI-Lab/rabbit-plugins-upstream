# PRD 结构清单与诊断方法

本文件定义"产品原型与需求说明"型 PRD 的标准章节结构，以及诊断缺失章节、补全内容的实用方法。适用于把产品方案整理成可评审、可交付的需求文档。

## 一、标准章节（建议顺序）

1. **概览 / Hero** — 标题、一句话定位、版本号、作者、最后更新日期。
2. **背景与目标** — 为什么做、解决什么痛点、业务目标。
3. **范围** — In scope / Out scope，明确边界，避免范围蔓延。
4. **关键指标 / KPI / 成功标准** — 量化目标与硬性时间节点。
5. **非功能性需求（NFR）** — 性能、安全、可用性、兼容性、合规。
6. **角色与权限** — 涉及的角色、各角色能做什么。
7. **核心流程与闭环** — 主流程 + 异常/逆向流程（如下单→支付→退货取消）。
8. **接口与数据契约** — 与外部系统的接口、字段、状态机。
9. **页面 / 功能原型** — 可交互 HTML 原型（骨架见 `assets/prd-template.html`）。
10. **上线与运营计划** — 节奏、时间节点、灰度、回滚。
11. **风险与开放问题** — 未决项、依赖、假设。
12. **术语表** — 缩写、专有名词。

## 二、诊断"还缺什么"（仅诊断、先不改）

拿到 PRD 草稿时逐项对照上表，标记缺失 / 薄弱项并给优先级：

- 缺失关键章节（无范围、无 KPI、无异常流程）→ **高优先级**
- 章节存在但空泛（如"提升用户体验"无量化）→ **中优先级**，建议补量化目标
- 缺少闭环（只有正向流程，无退货 / 取消 / 失败处理）→ **高优先级**
- 缺少时间卡点（项目有硬 deadline 却无里程碑）→ **中优先级**
- 术语未定义、字段名前后不一致 → **低优先级**但易补

## 三、KPI / 成功指标写法（常见坑）

- 避免用"试点门店覆盖 X 家"这类指标：当门店基数本就不大时该指标无意义且显不专业。
- 优先用**时间节点式硬性指标**：如"8 月 17 日开启联调""12 月 1 日必须上线"。时间卡点是项目真实约束，比覆盖率更有说服力。
- 量化指标遵循 SMART；区分"业务指标"与"交付指标"。

## 四、补全章节的写法要点

- **目标**：用"动词 + 对象 + 结果"句式，避免形容词堆砌。
- **范围**：用表格列出 In / Out，评审时双方确认。
- **接口契约**：列字段名、类型、是否必填、示例值；状态机用 `available → locked → consumed/unlocked` 这类明确迁移。
- **异常闭环**：每个正向操作都配"如果失败 / 用户取消"的处理路径。

## 五、与可交互原型的关系

- 原型不是 PRD 的替代，而是第 9 章的具象化。PRD 文字定义"做什么"，原型展示"长什么样、怎么走"。
- 原型数据应与原型前序页面联动（如商品选择页 → 交易完成页的金额 / 优惠实时计算），保证演示自洽。
- 视觉遵循"大厂简约"：拒绝滥用渐变、紧凑间距、自然缓动、统一圆角（卡片 14px / 面板 16px）。
