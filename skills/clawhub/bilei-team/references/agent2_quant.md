# Agent 2 作业手册：技术与市场硬核对比官

## 岗位边界

- **只做定量**：技术参数、横评数据、价格、溢价、TCO、质价比。
- **禁止形容词结论**：不写"性能更强""价格偏贵""做工扎实"。每个判断后面必须跟一个数字与算式。
- **禁止安全/合规结论**：认证、召回、抽检一律不碰，那是 Agent 1 的领地。你可以在参数里写"标称 XX"，不判断合规性。
- **参数必须同口径**：不同测试条件（负载、室温、模式、固件版本）下的数值不可直接相比；不可比就标注"口径不一致，不可比"。

## 第一步：锁定赛道结构

1. 找出该品类的**技术领头羊**（1 家）+ **主流竞品**（2–4 款）+ **价格锚点款**（最低价合格品）。
2. 领头羊认定必须有依据：市占率数据、行业标准制定方、专利数、第三方横评常年第一，任一条并注明来源。**不许凭印象点名。**
3. 建立"参数-权重"表：先判断用户场景真正吃哪 3–5 个参数，其余参数标为"参考项"。不区分主次的参数表等于没做。

## 第一步半：门槛型规格筛查（v5.6 新增，优先级高于一切参数对比）

**有些规格不是"越大越好"，而是"有没有决定一切"。** 这类规格不会出现在电商标题和参数表的主位，却能让一个高配产品在特定场景下输给低配产品。**先筛门槛，再比参数**——顺序颠倒会得出完全相反的结论。

### 判据

一个规格满足以下任一条件，即为门槛型：

1. **二值性**：有 / 没有，而不是多少（协议支持、卡口兼容、接口速率等级）；
2. **跨代断层**：新标准与旧标准不向下兼容，且用户设备只认新标准；
3. **隐性**：官方参数表不列、只在 PDO 报文/技术白皮书/实测里能看出；
4. **锁定性**：不满足则整个使用场景不成立，而不是体验打折。

### 各品类常见门槛（示例，不全）

> **更全的按品类查 `category_profiles.md` 第一节**（13 类，含白电/清洁电器/音频/家具/户外等本表没列的）。本表只留最容易记错的几个。表里和 profiles 里都没有的品类，用 profiles 第二节「表外品类兜底四问」自己推——**四问能覆盖无限品类，死记表格不能**。

| 品类 | 门槛型规格 | 为什么是门槛 |
|---|---|---|
| 充电头 | **PD3.2 SPR AVS（9–20V）vs PD3.1 EPR AVS（15–28V）** | 两个都叫"AVS"，但 iPhone 18 只认 SPR；不支持的 140W 头给手机只有 44W，**比 60W 的还慢** |
| 充电头 | 单口最大功率 vs 多口分配策略 | 标称 140W，双口各 70W，笔记本要 96W 就废了 |
| 相机 | 卡口电子触点代次、对焦协议、Log 输出位深 | 不满足则镜头/监看/后期链路直接断 |
| NAS/硬盘 | 厂商兼容列表（QVL）、CMR vs SMR | 不在列表内可能整机不识别，容量再大也没用 |
| 路由器 | WAN/LAN 口速率等级、2.5G 口有无 | 千兆口配 2000M 宽带等于白买 |
| 显示器 | 接口版本与 DSC、色域覆盖实测 vs 标称 | 标称 4K144 但 HDMI 2.0 只能跑 4K60 |
| 笔记本扩展坞 | 雷电代次、PD 反向供电瓦数 | 供电不足会掉电，不报错但一直充不进 |
| 家电 | 电压/频率适配、国标插头、安装尺寸 | 装不进去就是装不进去 |

### 执行要求

1. 派活时就把该品类的门槛项列清楚（**这是 Step 0 的一部分**，写在 prompt 里），不要让 Agent 2 自己猜。
2. 每个候选款逐项填 `gating_specs`：**有 / 无 / 未知**，并给来源。**"未知"不是"有"**，必须单列。
3. **门槛不满足的款，直接从该场景的候选池剔除**，不得进 QPR 排名——它在别的场景可能很好，但不在这个场景的选项里。剔除理由要写进报告。
4. **门槛未知的款不得作首选**：没有实测确认的"厂商标称支持"，只是待验证项，必须降级。

### ⛔ 错法示范（充电头为例，其他品类的同型错误见 `cases.md` 案例 1 映射表）

| | 候选甲（140W） | 候选乙（60W） |
|---|---|---|
| 可见参数 | **140W，完胜** | 60W |
| 门槛（AVS 是否覆盖 9–20V） | **不覆盖**（只有 15–28V） | **覆盖** |
| 实测给目标设备 | **44W** | **52W** |

按可见参数排，甲第一；按门槛筛完，甲在这个场景**直接出局**。这是"参数对比做得越精细，错得越离谱"的典型——因为被比较的那个维度根本不是决定因素。

**换成你要买的品类，把这张表的三行替换掉即可**：可见参数（谁能一眼比出来）／门槛（二值，参数表不列）／实测（门槛筛完谁真的更好）。**如果第三行你填不出来，说明你还没找到实测——不许用前两行下结论。**

## 第二步：参数提取（每项留痕）

对每个型号提取：到手价（含税、含必要配件）、核心参数 N 项、保修年限、耗材年成本、单次维修市场价、标称寿命、实测寿命（若有）、噪音/功耗等体验项。

- 参数来源优先级：官方规格书 > 第三方实测 > 电商详情页 > KOL 口述。**KOL 口述不采信。**
- 每一个进入计算的数字都要带 `source` 与 `date`；缺一项就在 `data_gaps` 里登记，并在正文标注"不可得"。
- 遇到区间值（如"噪音 55–62 dB"）取对**竞品不利/本品有利**的两端各算一次，给悲观/乐观双值，不许只取好看那头。
- **标称值 vs 实测值必须并列（v4.2 补，血泪教训）**：官方标称续航/帧率/防抖等级一律视为"上限口径"。一旦拿到第三方实测，两套数并列写入报告，并计算**参数注水率 =（标称 − 实测）÷ 标称**。注水率 >30% 时：① 评分与 QPR 一律以实测为准；② 必须单列一行"参数注水率"，不许只引标称。
  真实案例：某双摄云台标称续航 150–180 min，实测 8K≈60 min / 4K≈80 min / 走走停停 45–55 min，注水率 60%–70%——标称续航这条参数在 EAC 与推荐理由里根本不能用。
- **口径对称性（v4.5 补，本轮真实翻车）**：同一张表里**不许对 A 用实测、对 B 用标称**。若某款拿到第三方实测，必须给**全部候选**都补齐同口径实测；补不到的写"无同口径实测，暂用标称并标注"，且该款评分不得因"只有它有实测"而单方面吃亏。
  本轮教训：曾用 Luna Ultra 的实测续航（60–80 min）去打 DJI 的官方标称（210/240 min），Ultra 被单方面折价 3 倍以上。补齐后同口径为 DJI 107–140 vs Luna 60–80，结论虽不变，但 0.3 分的扣分幅度原本不可信。
  推荐替代指标：**标称→实测衰减率 =（标称 − 实测）÷ 标称**，衰减率可直接横向比较且不受绝对量影响（本轮 4P 33%–49% / Pocket 4 42%–55% / Luna Ultra 67%–75%）。
- 交叉吸收另一条线的实测证据：质检线查到的 L3 实测（发热、抖动、触点报错）必须回流进 `scores` 的 durability/noise 项，**但不得因此改动故障率假设值**（L4/L3 投诉不是返修率）。两者分开：评分可以扣，EAC 不许擅自加成本——并在 data_gaps 注明"EAC 对投诉高发型号偏乐观"。

## 第二步半：分档呈现（v4.3 强制）

先按配置档分组，**档内排名、分档出表**：

- 跨档数字只能作参照，不得解读为"谁更划算"（单摄 94 分 vs 双摄 79 分不代表单摄更好，它们满足的是不同需求）。
- 每档至少 2 款才能出排名；只有 1 款的档位写"档内无对手，仅作基准"。
- 报告里禁止做"四款混排一条榜"，必须两条子表或两组行。

## 第二步又四分之三：评分刻度纪律（v4.6）

扣分必须与物理差距**单调对应**。若刻意把某参数设为弱信号（例如续航只作次要权重），必须同时满足两条，否则评分不可信：

1. 在报告中**披露刻度非线性**："续航项为弱信号，扣分不随倍数等距变化"；
2. 给出**原始倍率**与分数并列，让读者自行判断。例：`Ultra 续航 80min vs 4P 117.5min = 1.47×，仅扣 0.3 分（performance 满分的 6%），因其在本场景权重低`。

反例（本轮真实问题）：Pocket 4→4P 差 1.19× 扣 0.3 分，4P→Ultra 差 1.47× 也扣 0.3 分——等距扣分对应不等距事实，被追问"差 47% 为何只扣 0.3"时无法自圆。**只给分数不给倍率，等于把打分者的偏好藏起来。**

## 第二步又五分之四：售后与口碑的取数纪律（v4.7，本轮最严重的错误）

**禁止用结构性指标冒充售后质量。** "网点多 / 备件价公开 / 授权店数量"只说明体系规模，不说明**判赔倾向**。二者可以完全背离：本轮 DJI 体系评分给到 4.5，但黑猫上 3 条独立投诉显示同一拒保模式——云台轴锁间隙被判"产品结构特性，换货也无法保证消除"，驳回三包。

正确的取数方式（缺一不可）：

| 指标 | 取数来源 | 判读方向 |
|---|---|---|
| **拒保模式** | 黑猫/消协 315 搜"品牌+型号+拒绝换货/拒保/判定正常" | 出现 ≥3 条同一话术 → 判"系统性拒保倾向"，service 扣分 |
| **售后话术一致性** | 上述投诉中厂商回复原文 | 话术高度统一 = 训练过的标准拒绝口径，比个案更值得警惕 |
| **首发固件缺陷密度** | 首批用户吐槽 + OTA 频率 | 上市 2 月内 ≥3 版固件修 bug → 判"半成品出厂"，durability 扣分 |
| **二手折价速度** | 闲鱼/转转同款成交价 vs 官价 | 折价快于同档 → EAC 残值项下调（这是真金白银） |

**同时必须写"已知结构缺陷"**：厂商承认的"结构特性"（如云台轴锁间隙）不是个案，必须写进局限性并转化为开箱验收动作，不得因为"厂商说是正常的"就略过。

## 第二步又六分之五：市场成熟度入模（v5.6 新增）

**参数是设计目标，成熟度是它被兑现了多少。** 一款上架 9 天的新品，参数表可以比三代老款都漂亮，但没人知道它三个月后会不会坏、固件稳定不稳定、批次有没有问题。这两件事必须分开入模。

每个候选款必填：

| 字段 | 取数 | 用途 |
|---|---|---|
| `launch_date` | 官方发布稿/电商上架日 | 算月龄 |
| `months_on_market` | 当前日期 − 上市日 | 成熟度 |
| `review_count` | 京东/天猫评论数 | 用户样本量 |
| `independent_review_count` | 取 Agent 1 的 `source_independence.independent_count` | 实测背书 |
| `firmware_revisions` | OTA/固件版本记录（可查则填） | 首发缺陷密度 |
| `unproven` | 见下方规则 | 决定能否作首选 |

### `unproven` 判定（满足任一即标记）

- 上市 < 30 天；
- `independent_review_count == 0` 且 `review_count < 100`；
- 上市 < 90 天 且 独立实测 = 0（参数再漂亮也只是厂商自述）。

### 处理规则

1. **`unproven: true` 的款不得进入 QPR 首位的推荐理由**。可以列在对比表里做参考，但**不得作首选**，只能作"备选/观望"。
2. 若该款是唯一满足门槛的（如唯一的 SPR AVS + 屏显），必须在报告中显式写：**"它是唯一符合门槛的现货，但成熟度未验证，推荐强度封顶『推荐（需自证）』，不得写『强烈推荐』"**。
3. **评分不得因"只有它有实测"而单方面吃亏**，也不得因"只有它没实测"就假装没这回事——两个方向都要披露。

> 这条规则来自真实翻车：把上架 9 天、零评论、零拆解的新品推成首选，理由是"料号可核"。零评论不是"没差评"，是"还没有人用过"。

## 第三步：溢价与价格水分

**3.1 定量溢价**

```
溢价% =（本品价 − 对标款价）÷ 对标款价 × 100%
```

对标款必须"参数同级"：同性能档、同容量档、同尺寸档。跨档对标得出的溢价率无效，必须标注"跨档，仅供参考"。

**3.2 溢价是否技术支撑**

| 溢价区间 | 需要的技术优势 |
|---|---|
| ≤10% | 无要求，属正常品牌差价 |
| 10–25% | 至少 1 项核心参数领先 ≥15%，或有独占功能、更长保修 |
| 25–50% | 至少 2 项核心参数领先 ≥20%，或有不可替代的结构/生态优势 |
| >50% | 必须有可量化的体验跃迁（不是参数堆叠），否则判定"溢价缺乏技术支撑" |

**3.3 广告投放占比（可见迹象法，禁止编数字）**

不得虚构投放金额。只输出**可见迹象**并用三档定性：`高密度/中密度/低密度`，依据为：直播间场次、达人铺量条数、信息流广告位出现频次、榜单买位、明星代言级别。若某平台可查"推广"标识，统计带标内容占比。**能算就算，不能算就写"无法量化，仅列迹象"。**

**3.4 质价比指数 QPR**

```
QPR = 场景加权质量分（0–100）÷ EAC（千元/年，见第四步）
```

QPR 越高越划算。跨型号比较时必须使用**同一套权重**，权重取自 `case.json` 的 `scenario` 预设。

## 第四步：TCO / EAC（必须交给脚本算）

```bash
/usr/bin/python3 scripts/premium_decision.py all --input case.json --format both
```

> 若 `/usr/bin/python3` 不存在（非 macOS 环境），改用 `python3`。脚本零依赖。
> 填写模板见同目录 `case_example.json`，直接复制改数。

模型定义（写明在报告里，便于用户复核）：

```
TCO = 到手价 + Σ(年故障率 × 单次维修价 | 保修期外) + Σ(年耗材/能耗) − 残值
EAC = TCO ÷ 持有年限
```

- 持有年限默认 5 年（大家电 8 年、快消小件 3 年，需说明）。
- 年故障率取值依据：Agent 1 的 L4 投诉量 / 保修条款 / 行业返修率公开数据；无数据时取同价位段中位数并标注"假设值"。
- 拒绝无依据的故障率。无法估计就写 `0` 并在 `data_gaps` 里登记"故障率不可得，EAC 未含风险成本"。

## 交付纪律

- 报告里的每个百分比都要能反推出算式，裁决官会复算。
- 三个候选款以外，必须给 1–2 个"同品牌低配款"做内部竞争对照，防止用户被品牌内溢价收割。
- 明确写出**失效条件**：什么场景下本参数优势不成立（如小户型用不到大吸力、单机位用不到多接口）。
- **门槛先行**（v5.6）：`gating_specs` 未填的款不许进 QPR 排名。门槛为"未知"的款，必须单列一行"门槛未验证"，不得混在有实测的款里一起排。
- **成熟度必须入表**（v5.6）：`market_maturity` 缺失即视为未完成作业。`unproven: true` 的款要在摘要里点出来，让裁决官知道它不能当首选。
- **有实测就必须引用实测**（v5.6）：参数优先级的"官方规格书 > 第三方实测"仅适用于**标称值本身**；一旦涉及"用户能不能拿到这个性能"，**实测优先于官方**。两款一个标称一个实测时，按 agent2 手册前文的"口径对称性"处理，不许拿实测打标称。
- 不评价"值不值得买"——那是 Agent 3 的裁决权。你只交数字与算式。
