# MVP Builder — MVP 三段式构建

> 不要花 6 个月构建没人用的产品。用三段式方法论：先手动做 → 再流程化 → 最后自动化。每一步都有真实客户和真实收入验证。

## 能力

- 识别可手动交付的最小价值单元
- 将人工流程文档化为可复制 SOP
- 判断何时从手动转向自动化
- 用四问法控制范围：周末能上线吗？客户受益了吗？愿意付钱吗？能快速获取反馈吗？
- 避免过度构建——只做已验证需要的东西

## 使用方式

```
/mvp-builder 帮我设计一个 AI 客服工具的第一版 MVP
/mvp-builder 我现在在手动做客户入驻，怎么判断何时该自动化
/mvp-builder 我的 MVP 范围太大了，帮我砍到能周末上线的程度
```

## 工作流

1. **定义最小价值** — 客户愿意付钱的最简单交付物是什么？
2. **手动交付（Stage 1）** — 你亲自做每一步，记录所有操作
3. **流程化（Stage 2）** — 写出 SOP，别人也能照着做
4. **产品化（Stage 3）** — 自动化已验证的步骤，现在才写代码
5. **范围控制** — 每个阶段都用四问法检验

## 三段式方法论

### Stage 1: 手动（自己做）
- 为每个客户手工解决问题
- 你就是产品。你同时是客服、交付和工程
- 写下每一步操作——这将成为你的流程文档
- 案例：Gumroad 起步时，Sahil 手动收集 PayPal 信息、一个个付钱给创作者

### Stage 2: 流程化（系统化）
- 把你的流程写在纸上，任何人都能照着做
- 如果你去度假，别人能接手
- 你建立了高效服务每个客户的系统
- 这就是你的「魔法纸张」

### Stage 3: 产品化（自动化）
- 把每个经过验证的任务自动化
- 客户不需要你也能使用产品
- 这才是真正写软件的时候
- 只构建你已验证过的事情

## 四问法（每个阶段必问）

1. **周末能上线吗？** — 不能就砍范围
2. **让客户的生活变好了一点吗？** — 这是 MVP 的及格线
3. **客户愿意为此付钱吗？** — 从第一天开始盈利
4. **能快速获得反馈吗？** — 反馈越快，迭代越快

## 适用场景

- 准备开始构建第一个产品版本
- 产品开发 3 个月还没上线，需要砍范围
- 不确定 MVP 应该包含哪些功能
- 从服务型业务向产品型业务转型

## 限制

- 不适用于硬件/深度技术产品（物理原型无法「手动交付」）
- 高度监管行业（医疗、金融）可能需要先满足合规要求
- 三段式不是线性的——你可能需要多次回到 Stage 1
- 需要创始人愿意亲自做「低端」工作
