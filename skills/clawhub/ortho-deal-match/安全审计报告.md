## 四、上轮 P1 整改复核（逐项判定）

> 复核方法：**读代码确认实现** + **现场核对产物痕迹**，不采信说明文档本身。

### P1-1　破坏性重建：数据库与审计链可被一键清空 —— **✅ 已关闭**

上轮位置：`init_db.py` 原 `os.remove` 直删、`demo.py` 原 `open(...,"w")` 截断审计链。

复核结果（代码层）：
- `scripts/init_db.py:143-153`：`--reset` 命中旧库时，先 `os.replace(core.DB_PATH, bak)` 将旧库**备份为同名加时间戳后缀**，再建新库；已无任何 `os.remove` / `unlink` 调用。
- `scripts/demo.py:98-109`：对 registry/blocklist/audit 三个文件，先**整体拷贝进 `audit/archive/<原文件名>.<时间戳>`**，随后才截断原文件重建——历史留痕被归档保留，不再是「抹除」。
- 危险删除类原语（`os.remove` / `shutil.rmtree` / `os.unlink`）全文**已清零**；唯一的破坏性替换点是 `init_db.py:147` 的 `os.replace`，语义为「移动到备份名」，目标仅为技能自身 `data/match.db`。

复核结果（现场层）：`data/` 下存在 `.bak-` 时间戳后缀的旧库备份文件，`audit/archive/` 下存在对应时间戳的归档文件，与代码路径、demo 流程顺序吻合——整改真实生效。

**判定：关闭。** 重置动作显式确认（`--reset` / `--yes`）、目标限定技能自身数据目录、历史先归档后重建，破坏性操作可回溯。

### P1-2　运行时产物随包外发风险 —— **✅ 已关闭（打包阶段动作，见打包清单）**

上轮位置：`data/` `registry/` `audit/` 运行目录与代码未分离。

复核结果：
- 代码层无可改项：产物由运行时自然产生，排除机制本就在打包环节。
- 本轮确认目录当前非空且 `scripts/__pycache__/` 已出现编译缓存（整改验证运行所致）；内容为虚构演示数据（见 I-3）。
- 发布时**必须**由打包白名单显式排除以下路径，包内即无运行时产物：`data/`、`registry/`、`audit/`（含子目录 `archive/`）、`scripts/__pycache__/`、任何 `.bak-*` / `*.pyc` 文件。
- 姊妹技能 `ortho-expo-contacts` 的 `SKILL.md` 已写明同类红线（`data/ registry/ audit/` 整个排除），本技能建议在 `SKILL.md` 中补充同样表述，作为文档侧收口（不阻塞发布）。

**判定：关闭（由打包清单执行）。** 属打包阶段动作而非代码缺陷，按约定在本报告注明。

### P1-3　文档中硬编码本机绝对路径（含系统账户名） —— **✅ 已关闭**

上轮位置：`SKILL.md` 将本机解释器绝对路径（含系统账户名）写入 `PY=`。

复核结果：
- `SKILL.md:34` 现为 `PY="python"` 占位写法，注释仅为「Windows 用 Python 环境里 python.exe 的完整路径」中性说明，无具体路径、无账户名、无盘符。
- 全目录关键字扫（盘符绝对路径、家目录绝对路径、账户名、应用数据目录）在全部源码/文档中**零命中**；同段 `cd ~/.workbuddy/skills/ortho-deal-match` 为波浪号相对写法，中性可保留。
- `references/WORKFLOW.md` 与其余脚本 docstring 亦无绝对路径。

**判定：关闭。** 配套加固（demo 演示邮箱运行时拼接、公司名中性化）复核属实：demo.py 演示数据全部邮箱为运行时「用户名 + 保留示例域名」拼接生成，源码与文档中不含任何字面邮箱地址；登记主体名已中性化（「示例医疗科技」等占位）。
