# 音画同步优化

## 问题从哪来

配音是按字幕的**起始时间**投放的，但中文朗读时长常常超过那段字幕的时槽。超出部分会盖到下一条字幕的时间区间里，造成轻微串音，听感上就是"中文解说比画面慢半拍"。

这不是 bug，是 TTS 方案的固有短板。真实数据：

```
166 条字幕，超时占比约 30–40%
最严重的一条：配音 5616ms，字幕槽只有 2480ms（2.3 倍）
```

## 先量化，再优化

别猜。跑一次带报告的脚本，拿到真实分布：

```bash
"<PY>" "<SKILL>/scripts/synthesize.py" --report
```

输出里每条会带一行 `语音 xxxms / 字幕槽 yyyms = n.nn`，末尾还有汇总：

```
溢出统计: 中位占比 1.35，超过 1.1 倍的 58/166 条
```

看两个数字：

- **中位占比**：反映整体偏长多少。1.0 是刚好填满，1.3 意味着普遍超出三成
- **溢出条数**：超过 1.1 倍记为溢出

## 三档解法，按性价比排序

### 第一档：给 TTS 加速（一个参数）

```bash
"<PY>" "<SKILL>/scripts/synthesize.py" --rate "+15%"
```

`rate` 取值 `-50%` 到 `+100%`，`+15%` 几乎听不出处理痕迹，却能压掉大部分溢出。溢出率在两成以内时，这一招通常就够。省事且不用重翻译。

### 第二档：翻译时控字数（最治本，但要重做步骤 2）

中文朗读约 **4–5 字/秒**。一条 N 毫秒的字幕槽，容得下的字数是：

```
字数上限 ≈ N / 1000 × 4.5
```

举例：

| 字幕槽 | 字数上限 |
| --- | --- |
| 1.0 秒 | 4 字 |
| 2.5 秒 | 11 字 |
| 4.0 秒 | 18 字 |
| 6.0 秒 | 27 字 |

把它当成翻译时的硬约束：**英文长句要提炼，不要逐字对译**。lost in translation 在所难免，宁可丢信息也不要丢节奏。

这一步要与 `input.srt` 的时间轴配合——翻译前先把每条的槽宽算出来，长句狠心砍。

### 第三档：事后变速（兜底）

对仍然溢出的个别片段，用 ffmpeg 变速不变调：

```bash
ffmpeg -y -i seg.mp3 -filter:a "atempo=1.25" seg_fast.mp3
```

`atempo` 范围 0.5–2.0，只改时长不改音高，1.25 倍以内基本无损。适合手工修补少数几条。

## 什么时候该组合使用

用户明确要求"配音要跟画面/口型严丝合缝"时：**第一档 + 第二档一起用**，即 `--rate "+15%"` 配上按 4.5 字/秒控字数的译文。第三档留给抽检查出来的个别顽固条目。

## 一个反直觉的点

不要指望把 rate 拉得很高来补救糟糕的译文。`rate="+50%"` 以上会出现明显的机械感，字句粘连。与其事后拉速，不如翻译时就把句子写短——这是唯一既保质又保节奏的路。
