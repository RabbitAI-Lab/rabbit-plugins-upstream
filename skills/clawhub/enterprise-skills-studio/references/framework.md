# 技术框架参考

来源：Anthropic 官方《Skills for enterprise》、Atlan《What Are Enterprise Skills》、主文章，及"企业为什么不敢用"。本文件供企业技能工程台在生成技能时按需读取。

## 一、Agent Skill 的定义与定位

一个 Skill 是包含 `SKILL.md`、可选脚本/参考/资源的标准化文件夹。核心设计理念是**渐进式披露（Progressive Disclosure / Loading）**：启动时只加载名称+描述，任务匹配后才按需加载完整指令、脚本、参考，节省上下文、支持无限专家知识低摩擦接入。

**企业级的本质 = 治理信封（governance envelope）**：Anthropic 企业规范大量篇幅在评审、评估、生命周期，而非功能本身。让一个 skill 成为"企业级"的是治理（评审/审计/版本/作用域），不是它能干多少活。

## 二、Tools vs MCP vs Skills 分类（Atlan taxonomy）

| 维度 | Tools（函数调用） | MCP servers | Agent skills |
|------|-----------------|-------------|--------------|
| 做什么 | 单个离散动作 | 标准化能力访问（含 auth） | 教代理怎么做工作流 |
| 层级 | 执行 | 能力与协议 | 流程 |
| 鉴权 | 调用者上下文 | 原生 OAuth | 继承代理 auth 上下文 |
| 格式 | 含 schema 的函数 | 含 tools/resources/prompts 的服务器 | 含 SKILL.md+可选脚本的文件夹 |
| 最佳场景 | 单 API 调用 | 跨系统治理访问 | 可重复多步工作流 |
| 企业风险 | 权限误用 | token 管理复杂 | 触发冲突、恶意脚本、未治数据触达 |

关系：MCP 给代理"手"（能力），Skills 给"判断力"（流程），二者同架构不同层、互补而非竞争。

## 三、三级加载机制

1. **元数据层（常驻）**：name + description，用于判断是否调用。
2. **指令层（触发时）**：主指令、Quick start、操作规则。
3. **资源层（按需）**：脚本、参考文档、模板，沙箱执行。

## 四、SKILL.md 字段规则（硬性）

- `name`：≤64 字符；小写字母/数字/连字符；见名知意；组织内统一命名规范
- `description`：≤1024 字符；必须写清"功能 + 何时调用"；这是触发准确率的命根子
  - 触发词须**具体且带边界**，避免"升级一下""处理一下"等过于宽泛、易与日常对话重叠的短语；涉及**写文件 / 自修改 / 网络拉取**的技能，描述中应显式声明"需用户确认后才执行"，防止被无意或注入触发。
- 正文：祈使句（动词开头），客观指令，避免第二人称
- 大段参考/模板放 `references/` 或 `assets/`，保持 SKILL.md 精简（<5k 词）
- 参考 Anthropic 官方 best-practices 与 naming conventions

## 五、四层结构（每个企业技能都应覆盖）

| 层 | 作用 | 内容示例 |
|----|------|----------|
| 指令层 | 语气、格式、决策优先级 | 输出模板、禁止项、优先级规则 |
| 知识层 | 领域知识、规则、案例 | 产品文档、品牌规范、合规要求、历史案例 |
| 工具层 | 外部能力接口声明 | API、数据库、SaaS（仅声明，不写实现细节） |
| 示例层 | 输入输出标准示范 | 3–5 个 good/bad 示例，决定质量上限 |

> 关键：示例层最影响质量。无标准示范 → Agent 自由发挥、输出漂移。

## 六、技术层 vs 规则层（需求拆解两分法）

构建技能时把需求拆为两层（来自"企业为什么不敢用"）：
- **技术层**：怎么做（PDF 表格提取、财务 Excel 生成、ERP 对接）→ 软件工程活，工程团队落地
- **规则层**：按什么标准做（payment-rule 预付款≤30%、penalty-rule 违约金≤20%、compliance-check 必含保密条款）→ 基本不写代码，业务人员可写
- 组织协同：业务梳理 SOP → 拆为能力/规则两类 → 技术做能力、业务写规则 → 平台编排组合成完整智能体
- **陷阱**：不要让业务人员直接创建技术能力型 skill；设立 AI 产品经理作业务↔技术桥梁

## 七、设计原则（SkillsBench 等实证）

- **聚焦优于全面**：2–3 个专注技能通过率 +18.6 分；单体大全反降 2.9 分
- **脚本执行 > 临时写码**：确定性任务用 `scripts/`，省上下文、可复现
- **单一职责**：一个技能解决一类问题

## 八、召回边界（注意口径差异）

- 不同来源上限不同：Anthropic 官方称 API 每次最多 **20** 个；部分平台/文章以 **8** 为界。保守做法：按角色包控制在 **8 以内**更稳，超出则合并或按任务路由不同 skill 集
- 从窄到宽合并：`formatting-sales-reports` 等 → `sales-operations`（需 eval 确认等效）
- 命名即检索：描述写清触发时机，比堆功能更有效
