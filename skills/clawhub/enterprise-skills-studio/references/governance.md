# 治理参考

来源：Anthropic 官方企业规范、Sidbharath 部署指南、Cloud Security Alliance（CISO 5 风险）、aigenticlab 分层治理、人人都是产品经理、主文章。企业模式专用。

## 一、企业采用的四项前提（来自"企业为什么不敢用"）

1. **作用域隔离**：多租户/项目级/角色级隔离；敏感能力不混跑；不同角色只调指定技能集
2. **技能审计**：谁触发、何时、哪个、产出、是否越权——日志+链路+回滚
3. **技能自定义**：通用技能最多解决三成，七成是自家规则；把内部 SOP/口径/合规拆进 skill
4. **成本控制**：配额、缓存、成本分摊到部门，才能从试点切全域

## 二、三层治理体系

| 层级 | 来源 | 治理强度 |
|------|------|----------|
| 底层 | 平台内置 Skill | 平台把关，组织不可改 |
| 中层 | 平台市场 Skill | 管理员审核 |
| 顶层 | 企业自建 Skill | 私有逻辑，治理最严（本技能主要产出层） |

## 三、生命周期（六阶段 + Atlan 第7步"Ground in context"）

1. **Plan**：映射重复/易错流程到角色，窄于广
2. **Create**：写 SKILL.md，禁硬编码凭证/不可信网络/多余脚本
3. **Security review**：沙箱验脚本、扫指令操纵、查 SSRF；**作者不自审**（职责分离）
4. **Evaluation**：每技能 3–5（企业 10–20）条查询，隔离+共存测试，降召回则阻部署
5. **Ground in context**：数据触达类技能经治理上下文层（MCP 指治理源），避免"跑对但触未治数据"
6. **Deploy & version-pin**：API 上传、生产锁版本、留回滚
7. **Monitor & iterate**：用量追踪、周期重评、弃用失败技能

## 四、安全审查清单（8 项，发布前必过，已为多源交叉验证）

1. 全量审阅 SKILL.md 与脚本（目录列出 ≠ 安全评审）
2. 沙箱验脚本（隔离执行，确认无破坏）
3. 排查对抗指令（忽略安全规则、隐藏操作、按特定输入变行为）
4. 核查网络调用（未声明外联、SSRF）
5. 校验凭据（密钥不硬编码，用环境变量/凭证库）
6. 梳理工具范围（只访问必要资源）
7. 确认外跳转（重定向目标为预期域名）
8. 排查数据外泄（含经对话响应传出；敏感数据不出域）

> 背景数据：26.1% 公开 Skills 含至少一项漏洞（大规模分析 42,447 个）；36.82% 审计发现安全问题；OWASP 于 2026-03 形式化为 Agentic Skills Top 10 (AST10)。**不可信来源 skill 未经全审计禁止部署**（严苛度等同生产软件安装）。

## 五、CISO 五大风险（映射到 OWASP AST10，来自 CSA）

| # | 风险 | 关键机制 | AST 编号 |
|---|------|----------|----------|
| 1 | 无治理的技能蔓延（Sprawl） | 静默安装、无中央注册表、无 SIEM 事件 | AST09 |
| 2 | 供应链投毒 | 开放注册、零审查、无签名；克隆即触发执行/凭据外泄 | AST01/02 |
| 3 | 过度授权执行 | skill 继承代理全部运行时权限，无 per-skill 边界（"同意缺口"） | AST03/06 |
| 4 | 隐形载荷：Markdown 即攻击向量 | 自然语言指令即可外泄 `~/.ssh/id_rsa`；动态上下文命令加载即执行绕过安全推理 | AST04/08 |
| 5 | 跨平台可移植性 | SKILL.md 跨平台传播，安全元数据丢失，恶意更新静默扩散 | AST10 |

防护要点：技能库存（inventory）是一切控制前提；per-skill 最小权限；不可信源不装；版本 pin + 签名溯源。

## 六、风险等级评估（Anthropic risk tier）

| 指标 | 关注点 | 等级 |
|------|--------|------|
| 代码执行 | 目录内 `*.py/*.sh/*.js` | 高 |
| 指令操纵 | 忽略安全规则、隐藏操作 | 高 |
| MCP 引用 | `ServerName:tool_name` | 高 |
| 网络访问 | URL、`fetch`/`curl` | 高（数据外泄） |
| 硬编码凭据 | 文件内密钥/令牌 | 高（泄露） |
| 文件系统范围 | 目录外路径 `../` | 中 |
| 工具调用 | bash/文件操作指示 | 中 |

## 七、质量评估（5 维度）

1. 触发准确率（应触发都触发）
2. 共存冲突（与其他 skill 误召回/打架）
3. 输出质量（符合指令层与示例层）
4. 边界处理（模糊场景不漂移）
5. 资源效率（上下文占用合理）

测试：3–5（企业 10–20）条查询，覆盖 应触发 / 不应触发 / 模糊边界。

## 八、按组织规模的分层治理（aigenticlab）

- **初创**：伙伴审批（触客户数据需合伙人批）、开审计日志、Notion 集中登记；只自动化每周≥10次/单次>30min/年成本>£5k 且步骤一致的工作流
- **中小企业**：指定"技能负责人"（ops 兼任）；新 skill 需业务案例+ROI+安全审查+4 周试点；8 周未达 ROI 即淘汰；纵向用例聚焦
- **企业（五大支柱）**：①审批工作流（IT/安全签字）②数据分级策略③最小权限④审计轨迹（用户/时间/数据）⑤回滚程序（季度演练）。合规前置（金融/医疗生产前过审）

## 九、分发机制（Sidbharath 六法）

1. **全员统一下发**：组织设置 > Skills 上传 ZIP，默认启用可关
2. **按团队/部门定向**：Plugin+企业组，偏好 Required/Installed by default/Available/Not available（多组最宽松生效，敏感插件须隐藏+授组）
3. **同事直接共享**：Skill sharing → Shared with you 手动启用
4. **内部目录自发安装**：Share with org，只读副本自动同步（应关此开关走 intake 审批）
5. **代码仓库下发**：放 `.claude/skills/` 提交版本控制，项目成员自动获得
6. **API 应用内**：Skills API + Messages API，单包≤30MB，生产 pin 版本

> 跨表面不自动同步（管理界面↔Code↔API 各自独立），以 Git 为单一真源，多表面须自建同步。

## 十、版本 / 权限 / 审计硬规范

- **版本**：生产 pin 特定版本；省略 version 则请求用最新（任何人上传即改变生产行为）；保留上一版兜底回滚；校验和 + 签名提交；每次更新视作新部署须全量审查
- **权限**：最小特权，不继承用户全部权限；数据分级约束；仅用可信源；EU/EFTA/UK 用 Microsoft Copilot 时 Claude 作子处理器需显式 opt-in
- **审计**：开审计日志；调用级追踪（用户+时间戳+访问数据）；上线前安全测（注入/混淆/外泄）；月度 evidence-based 复审与弃用

## 十一、命名规范 / 角色捆绑 / 注册表

- 命名：`{领域}-{动作}` 或 `{角色}-{场景}`（如 `sales-proposal-generator`、`hr-offboarding-checklist`）
- 角色捆绑：销售=CRM+报表+提案；工程=审查+部署+事件；财务=报告+校验+审计
- 注册表条目：

```
| 技能名 | 领域 | 所有者 | 版本 | 依赖 | 评估状态 | 复审周期 |
|--------|------|--------|------|------|----------|----------|
|        |      |        | v0.1 |      | 待审     | 季度     |
```

注册表选型 6 标准：漏洞扫描、签名溯源、版本回滚、角色配置、评估门、上下文层集成。
