# 设计原则：厚技能 + 薄 harness

来源：用户反复强调的工程规则，结合 Atlan"三保证"、SkillsBench 实证。本文件是本技能的**最高设计准则**，贯穿构建/审查/升级全流程。

## 一、定义

- **厚技能（Thick Skill）**：把尽可能多的"智能"封装进技能本身——显式步骤、可执行脚本、参考文档、模板、校验/自检逻辑、决策树、标准输入输出示例。让宿主 Agent 少"思考"、多"执行"。
- **薄 harness（Thin Harness）**：编排/运行时层（Agent 的系统提示、调用外壳、胶水代码）保持最小。不要用复杂的 harness 提示工程去补偿一个单薄的技能。**技能自带智能，harness 只负责发现与调用**。

> 本技能自身也遵循该原则：方法论固化在 `references/` 与 `scripts/`，SKILL.md 只做调度，不堆长文。

## 二、为什么（对企业级尤其关键）

- **稳定**：确定性输出，同输入同结果（Atlan 三保证之一）
- **高效**：脚本执行 > 临时写码，省上下文、可复现
- **快速**：减少模型推理与试错，token 占用低
- **好用**：业务人员按模板/脚本即可复用，不依赖个人 prompt 水平
- **安全**：逻辑固化在技能内，行为可审计、可回滚

## 三、实操规则

1. 确定性任务用 `scripts/`：跑脚本返回结果，而非每次重新生成代码
2. 把校验/约束写进技能（schema、检查项），不赌模型"记得"
3. 用显式控制流替代"尽力而为"的指令
4. harness 只负责：发现 + 调用 + 基础路由；其余都在技能里
5. 示例层 = 质量上限：给足 应触发 / 不应触发 / 边界 示例
6. 聚焦单一职责，避免大而全的薄技能
7. 资源按需加载：大段参考放 `references/`，不撑大 SKILL.md

## 四、厚技能体检清单（审查时用）

- [ ] 是否有可复用的 `scripts/` 处理确定性步骤？
- [ ] 关键输出是否有 schema/模板约束？
- [ ] 是否给了 should / should-not / boundary 示例？
- [ ] 是否有自检/校验逻辑（格式校验、必填项检查）？
- [ ] harness 是否只需"调用"而非"指导怎么做"？
- [ ] 是否避免把复杂流程寄托于模型自由发挥？
