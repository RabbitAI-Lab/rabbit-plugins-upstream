# API 设计规范（全栈通用，架构师起草契约、前后端实现、测试验证共用）

## 1. 风格与版本

- 默认 REST；GraphQL / WebSocket 仅在 ADR 论证后采用。
- 路径版本化：`/api/v1/...`；不兼容变更升 `v2`，旧版本至少保留一个迭代。
- 资源名用复数名词、kebab-case：`/api/v1/purchase-orders/{id}/items`。
- 路径里只有资源与标识，过滤/排序/分页全走查询参数。

## 2. 方法语义与状态码

| 方法 | 语义 | 成功码 | 幂等 |
|---|---|---|---|
| GET | 读取 | 200 | 是 |
| POST | 创建/触发 | 201（创建）/202（异步受理） | 否 |
| PUT | 全量替换 | 200/204 | 是 |
| PATCH | 部分更新 | 200 | 否 |
| DELETE | 删除 | 204 | 是 |

错误状态码只用标准集：400 参数错误 / 401 未认证 / 403 无权限 / 404 不存在 /
409 冲突 / 422 业务校验失败 / 429 限流 / 500 服务端错误。禁止用 200 包错误体。

## 3. 统一响应与错误结构

成功：直接返回资源或 `{ "data": ..., "meta": ... }`（列表用 meta 放分页）。
错误（所有非 2xx 统一结构）：

```json
{
  "code": "ORDER_STATUS_INVALID",
  "message": "订单当前状态不允许支付",
  "details": [{ "field": "status", "issue": "当前为 CANCELLED" }],
  "traceId": "..."
}
```

- `code`：稳定机器码，大写蛇形，禁止直接暴露框架内部异常名。
- `message`：可直接展示给用户的可读文案。
- `details`：字段级校验错误数组，无则省略。
- `traceId`：与日志关联，可追踪。

## 4. 分页、排序、过滤

- 分页：`?page=1&pageSize=20`（或游标 `?cursor=...`，大数据集用游标）；
  响应 meta：`{ "page": 1, "pageSize": 20, "total": 123 }`；`pageSize` 上限 100。
- 排序：`?sortBy=createdAt&order=desc`，白名单字段。
- 过滤：`?status=PAID&createdFrom=2026-01-01`；时间用 ISO 8601 UTC。

## 5. 认证与安全约定

- 默认 Bearer Token（JWT 或 opaque）；开放接口显式列入契约并注明"公开"。
- Token 不放 URL、不打日志；刷新端点独立（`/api/v1/auth/refresh`）。
- 越权防护是契约的一部分：资源 ID 属主校验由服务端执行，前端隐藏按钮不算防护。
- 写操作默认要求防重放/幂等键：`Idempotency-Key` 头（支付/下单类强制）。

## 6. 契约冻结与变更流程

1. 架构师起草 → 前后端确认 → 冻结（版本号 + 日期记入契约文档头部）。
2. 实现期变更请求一律经总指挥 → 架构师裁决 → 更新契约并同步所有角色。
3. 冻结版契约是联调、测试、审查三方的唯一裁决依据。
