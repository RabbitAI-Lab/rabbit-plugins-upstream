# 调度协议（总指挥必读）

本文件定义总指挥的**分诊逻辑、阶段裁剪、并行策略与失败处理**。所有调度决策以本文件为唯一真值源。

## 1. 栈指纹探测（接单后第一步，先于一切分析）

对现有代码库，按以下顺序探测技术栈，命中即锁定"延续既有栈"原则：

| 优先级 | 探测文件 | 判定 |
|---|---|---|
| 1 | `pom.xml` / `build.gradle*` | Java 栈：Spring Boot 或 **Quarkus**（看依赖/插件） |
| 2 | `package.json` | Node 栈（NestJS 看依赖）、React/Vue，或 **Next.js**（`next` 依赖） |
| 3 | `requirements.txt` / `pyproject.toml` | Python 栈（FastAPI/Django 看依赖） |
| 4 | `go.mod` / `Cargo.toml` / `composer.json` | Go / Rust / PHP 栈 |
| 5 | `build-profile.json5` / `oh-package.json5` | HarmonyOS ArkTS 栈 |
| 6 | `docker-compose.yml` / `Dockerfile` | 补充判定数据库、中间件、端口拓扑 |
| 7 | `*.graphql` / schema 文件 | GraphQL 与 REST 并存（走 api-graphql.md 纪律） |

空目录 / 新项目 → 进入选型决策树（`stack-routing.md`）。

## 2. 任务类型路由表

| 任务类型 | 识别信号 | 启用角色（按序） |
|---|---|---|
| 从零建全栈项目 | 空目录、用户说"从零/新建/搭建" | 需求 → 架构 → UI/UX + DBA → 前端 ∥ 后端 → 测试 + 审查 + 安全 → DevOps → 文档（管理后台任务时前后端替换为管理端双角色；涉外部系统参考时逆向融合工程师前置） |
| 从零建管理后台 | "管理后台/中后台/admin/运营平台/控制台" + 从零搭建 | 需求 → 架构(轻量) → **管理端后端 ∥ 管理端前端** → 测试 → 审查 → (部署) → 文档 |
| 管理后台功能开发（既有） | 管理端任务，栈已存在 | 需求(轻量) → 架构(轻量) → **管理端后端 ∥ 管理端前端** → 测试 → 审查 |
| 逆向融合/复刻/兼容 | "复刻 xx UI/兼容 xx 协议/融合竞品能力/搞懂未知代码库/先摸清现状再重构" | **逆向融合工程师（ORRI）** → 按场景子路由移交（见下方逆向融合路由规则）→ 实现 → 测试 → 审查 |
| 新功能开发（既有项目） | "增加/实现 xx 功能"，栈已存在 | 需求 → 架构(轻量) → DBA(涉数据) → 前端+后端 → 测试 → 审查 |
| 疑难缺陷排查 | "报错/不工作/bug/异常" + 报错信息 | 定位(总指挥读日志锚点) → 对应 dev 修复 → 测试回归 |
| 系统重构 | "重构/优化结构/技术债" | 架构 → 审查(现状盘点) → 前端+后端 → 测试 → 审查 |
| 性能优化 | "慢/卡顿/并发上不去/OOM" | 架构(瓶颈定位) → DBA(涉 SQL) + 对应 dev → 测试(压测) |
| 代码审查 | "看看代码/审查/review" | 审查 → （发现问题）对应 dev → 测试 |
| API 设计/对接 | "设计 API/接口文档/联调" | 架构 → 后端 → 审查 |
| 数据库设计/迁移 | "建表/改表/数据迁移" | 需求(轻量) → DBA → 审查 |
| 技术文档 | "写文档/README/部署手册" | 文档工程师单角色直办 |
| CI/CD 与部署 | "部署/上线/流水线/容器化" | DevOps（+安全工程师审查部署配置） |

不在此表中的任务：总指挥按最接近的类型归类并向用户确认后再调度，不自行发明流程。

### 管理后台路由规则（角色替换原则）

- 识别信号：任务描述命中 `管理后台/中后台/admin/admin console/运营平台/控制台/dashboard 管理`
  任一关键词，或目标系统本身是面向内部运营人员的后台。
- **角色替换**：管理域的实现由 `admin-frontend-dev` 与 `admin-backend-dev` 承担，
  **替换**（不是叠加）通用的 `frontend-dev` / `backend-dev`——管理端角色是同栈之上的
  管理域专才（RBAC、审计、CRUD 三件套），复用同一份契约与后端栈规范。
- **混合任务**（C 端 + 管理端同时存在）：管理端归管理端角色，C 端归通用角色，
  契约由架构师统一起草、拆分为 C 端与管理端两组端点；并行策略下两组可并行实现。
- 管理端默认栈：前端 **React 18 + Ant Design 5**（架构师 ADR 可改 shadcn/ui + Tailwind）；
  后端继承总栈（Spring Boot / Quarkus / NestJS / Go 均可承载），不因"是管理端"另起炉灶。
- 安全工程师对管理端任务**强制启用**（管理端是越权与入侵高发面）。

### 逆向融合路由规则（ORRI 入口）

- 识别信号：任务目标指向**外部系统或未知系统**的能力/协议/架构/UI 提取与融合——
  复刻、兼容协议、融合竞品能力、学习陌生代码库、重构前现状摸底。
- **入口唯一**：这类任务一律先由 `reverse-fusion-dev` 按 ORRI（观察→逆向→重建→创新）
  完成观察与逆向，产出 `docs/reverse-analysis.md` 与场景规格；**任何下游角色不得跳过
  逆向阶段直接凭印象"参考竞品"实现**。
- **场景子路由**（O/R 产出移交方向，详见 agents/reverse-fusion-dev.md 第 2 节）：
  能力清单 → 需求分析师转 FR；协议规格 → 架构师入契约（后端实现附协议对照测试）；
  as-is 架构画像 → 架构师出 to-be；代码库画像 → 直接交付或支撑后续任务；
  UI 规格还原 → UI/UX 设计师校对 → 前端实现；架构画像 → 架构师评估采纳。
- **合法性门禁前置**：逆向融合工程师的合法性声明不通过时，总指挥立即终止该任务，
  不允许"换个方式偷偷做"；合规疑点呈报用户裁决。
- **置信度传递**：移交下游的逆向结论必须携带置信度标注；低置信结论进入规格前
  必须先完成探测实验升级置信度，或作为假设显式标注。
- 纯协议/工具类重建可由逆向融合工程师亲自实现（等价性测试为门禁）；
  落入本栈业务实现的重建按正常实现阶段路由到对应 dev 角色。

## 3. 阶段裁剪规则

- **涉数据库改动才启用 DBA**：纯前端 / 纯静态页面任务跳过 DBA。
- **涉用户界面才启用 UI/UX 设计师**：纯后端 / 纯脚本任务跳过。
- **安全工程师贯穿启用**：任何任务涉及鉴权、支付、隐私数据、公网暴露面时强制启用；
  其余任务由代码审查员代行基础安全检查（OWASP Top 10 清单）。
- **测试工程师介入深度**：新项目/重构/核心逻辑改动 = 全量（计划+用例+执行）；
  一般功能 = 用例 + 执行；小修小补 = 回归验证即可。
- **裁剪必须留痕**：被裁剪的角色在交付摘要"角色启用表"中标注"未启用 + 原因"。

## 4. 并行策略

- 阶段③实现期：前端 / 后端 / DBA **可并行**，但以架构师的模块划分和 API 契约为共同前提——
  因此**架构阶段必须先产出 API 契约草案**，前端按契约 Mock 开发，后端按契约实现，联调以契约为准。
- 管理后台任务：`admin-backend-dev` 先交 RBAC 权限码清单与菜单树数据，
  `admin-frontend-dev` 据此搭权限路由骨架——两端点契约齐全后即并行推进 CRUD 页面与端点。
- 模式 A（subagent）下：能并行的角色用并行委派（同一消息多个 Task 调用）。
- 模式 B（换装）下：无法真并行，按"后端 → DBA → 前端"顺序串行换装，避免上下文来回切换超过 3 次；
  大任务（全流水线 ≥8 角色）建议用户启用模式 A，或由总指挥激进裁剪角色，防止上下文膨胀失焦。
- **冲突回写**：并行实现期任何一方需要修改 API 契约，必须回到总指挥，由总指挥通知架构师裁决，
  裁决后同步给所有并行方——禁止两个角色私下协商改动契约。

## 5. 质量门禁（每阶段退出条件）

| 阶段 | 门禁 |
|---|---|
| ⓪ 逆向（可前置） | 合法性声明通过；观察档案零推测；逆向结论挂证据编号与置信度；亲自重建时等价性测试通过 |
| ① 需求 | 需求规格含可测的验收标准；用户未确认的假设已列为"待确认清单" |
| ② 设计 | ADR 记录了选型理由与被否方案；API 契约覆盖全部需求条目；涉库改动有 Schema 草案 |
| ③ 实现 | 代码可编译/构建通过；静态检查无 ERROR；按契约自测通过；无 TODO 遗留关键路径 |
| ④ 质保 | 测试用例全执行，P0/P1 缺陷清零；审查无阻塞级问题；安全无高危项 |
| ⑤ 交付 | 部署演练成功（至少本地/容器级）；回滚方案明确 |
| ⑥ 文档 | README 能让新人 15 分钟内跑起项目 |

**门禁判定人不通过时**：打回该阶段角色重做并附明确的问题清单；同一阶段最多打回 2 次，
第 3 次失败停止流水线，向用户呈现分歧双方论据。

## 6. 失败与降级处理

- **构建/运行环境不可用**：对应 dev 角色产出代码 + 自测说明，交付摘要标注"未经真机验证"及原因。
- **需求严重模糊**（连目标用户/核心场景都无法判断）：需求阶段最多 2 轮澄清提问，
  仍不明确则请用户在 2-3 个备选方向中选择，禁止带着臆测走完全程。
- **外部依赖不可达**（镜像源、私有仓库、付费 API）：报告用户并请求替代源或降级方案，不静默换依赖。
- **角色间产出矛盾**（如测试与开发对"正确行为"理解不一致）：以需求规格的验收标准为最终裁决依据；
  规格未覆盖的，由架构师补充决策并回写需求规格。
