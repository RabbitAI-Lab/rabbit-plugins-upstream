# Диета контекста агента: почему собственные скиллы агента съедают ваш бюджет

*Версия пакета: **1.0.1** (24 сентября 2026). Проверено: регрессионные тесты `scripts/test_split_skills.py`, ревью SkillQA (B, 0 провалов).*

**Проблема.** У CLI-агента (Hermes, OpenClaw и подобных) есть «скиллы» — текстовые инструкции,
которые подгружаются в контекст, когда задача подходит под их триггер. Со временем они растут:
скилл на 100–150 КБ — это ~25–38 тыс. токенов, и он попадает в контекст **целиком, каждый раз**.
Ни сжатие истории, ни кэш не спасают: скилл приходит последним сообщением (по устройству вне
сжатия), а перечитывание одного и того же скилла в сессии — это повторные полные дампы.

**Что измерено (наш случай, 24 сентября 2026).** Поставлен read-only счётчик на живой трафик:

| Показатель | Значение |
|---|---|
| Доля выводов инструментов в объёме запроса | **88,2 %** (109 запросов) |
| Медианный запрос | **568 188 символов ≈ 142 тыс. токенов** (при делении на 4) |
| Тяжелейшие блоки — дампы скиллов | **90–98 тыс. символов ≈ 23–24 тыс. токенов** |
| Один и тот же скилл за сессию | **до 10 раз за сессию** |
| Повторы внутри одного запроса (дедуп) | **0 символов из 1,86 млн** — на этом трафике дедуп внутри запроса ничего не даёт |
| Пять скиллов-монолитов | 152 КБ, 138 КБ, 109 КБ, 109 КБ, 105 КБ |

Следствие: сессия упиралась в окно, срабатывала компакция (сжатие истории) — а это уже прямые
потери работы: агент теряет нить, переспрашивает, дублирует действия.

**Решение.** SKILL.md остаётся коротким (≤ 20 000 символов), тяжёлые разделы переезжают
в `references/*.md` и грузятся **по требованию**. Разрез — механический, дословный:
ничего не переписывается, содержимое только меняет место, поэтому риск потери **текста** нулевой (переезд дословный); смысл страдает только при неверном разрезе — например, если резать вручную по `grep '^## '` без учёта код-фенсов.

**Как это сделать у себя (Python 3.9+, зависимостей нет):**

```bash
SKILLS_DIR="${SKILLS_DIR:-$HOME/.hermes/skills}"
# 1. Посмотреть, что и куда поедет (ничего не меняется)
python3 scripts/split_skills.py --root "$SKILLS_DIR"

# 2. Записать (бэкапы исходников — в каталог --backup-dir, по умолчанию $HOME/.skill-split-backups)
python3 scripts/split_skills.py --root "$SKILLS_DIR" --apply

# 3. Проверить: ни один заголовок раздела не потерян
python3 scripts/split_skills.py --root "$SKILLS_DIR" --verify-only
```

Для OpenClaw каталог скиллов указывается тем же `--root` (например
`--root /home/openclaw/.openclaw/skills`), механизм тот же.

**Результат на нашем парке:** 20 скиллов разрезаны: суммарный SKILL.md **973 659 → 379 091 символ
(−61 %)** (в байтах 1 256 160 → 478 508), тяжёлые дампы стали меньше на ~80 %
(один дамп: ~23–24 тыс. токенов → ~5 тыс.). Проверка: **0 потерянных разделов**,
живая загрузка скиллов отработала.

**Правила, чтобы не выросло заново**

1. SKILL.md ≤ 20 000 символов; всё длиннее — в `references/`.
2. Не перечитывать скилл, который уже в контексте.
3. Один скилл — один класс задач; 30 разделов в одном файле — это 2–3 скилла.
4. Новый материал дописывается в `references/`, в SKILL.md — одна строка указателя.
5. После каждого разреза — проверка целостности и живая загрузка.

**Пилот для второго агента.** Скопировать папку скилла целиком в его каталог скиллов,
прогнать сухой прогон, показать список, записать, проверить `--verify-only` и загрузить
один скилл живой задачей.

Состав пакета: `SKILL.md` (инструкция для агента), `scripts/split_skills.py` (разрезатель
с самопроверкой), `references/measurement-recipe.md` (как поставить замер).
