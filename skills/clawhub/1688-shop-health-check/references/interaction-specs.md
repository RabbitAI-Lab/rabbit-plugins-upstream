# 交互组件详细规范

本文档定义 1688-shop-health-check Skill 中所有交互组件的具体数据结构与映射规则。

## 1. confirm_execution_plan（Card 组件）

### 组件类型

`type: card`，`selectionType: requirement`

### 业务场景

用户提出店铺健康检查请求后，Agent 输出默认执行计划（含输出形式：总结性结论 + HTML 网页数据报告、时间周期、覆盖店铺），并通过该卡片提供 **8 个可选项**让用户选择要诊断的维度：前 7 项为七维度名称（流量、询盘、成交、商品、客户、广告、风险），第 8 项为"全面诊断（七维度）"。卡片**允许多选**。

> **触发条件（免确认短路）**：本卡片仅在**未命中免确认条件**时触发。用户已明确指定具体维度、明确要求全面体检/全面诊断、或明确要求直接开始（含定时任务触发的请求——其 query 即任务执行内容，逐字含七维度名）时，**跳过本卡片**直接进入诊断取数。

### 数据槽位定义

- **`questions`**:
  - 类型: `Array<Object>`
  - 说明: 问题列表，仅含一项必填多选项。
    - `question` (string): 引导用户选择诊断维度的问题文案
    - `options` (Array<string>): 固定 8 项 —— 前 7 项为七维度名称（`"流量"`、`"询盘"`、`"成交"`、`"商品"`、`"客户"`、`"广告"`、`"风险"`），第 8 项为 `"全面诊断（七维度）"`
    - `allowMultiple` (bool): 固定 `true`
    - `required` (bool): 固定 `true`（至少选择 1 项）
  - 卡片默认提供"确认"与"取消"按钮

### 完整数据示例

```json
{
  "type": "card",
  "selectionType": "requirement",
  "questions": [
    {
      "question": "请选择要诊断的维度（可多选），或选择\"全面诊断（七维度）\"执行全部：",
      "options": ["流量", "询盘", "成交", "商品", "客户", "广告", "风险", "全面诊断（七维度）"],
      "allowMultiple": true,
      "required": true
    }
  ]
}
```

### 用户选择结果处理

| 用户操作 | Agent 行为 |
|----------|-----------|
| 勾选一个或多个维度并点击"确认" | 仅按所选维度执行诊断，按「三、全面诊断维度与数据获取」对所选维度并行取数 |
| 勾选"全面诊断（七维度）"并点击"确认" | 覆盖个体选择，执行全部七维度诊断 |
| 点击"取消" / 返回空结果 / 无人作答 / 不勾选任何项 | 统一终止流程，不执行任何诊断，不输出报告，一律以「未收到有效的维度选择，本次体检未执行」口径如实收尾，**严禁表述为"用户取消"**；此为符合平台语义的正常终止而非失败，**终止后不得重试、不得自行重新弹卡或重新发起体检**，用户若需体检由其主动重新请求 |

> 勾选"全面诊断（七维度）"时优先级最高，会覆盖同时勾选的个别维度。若最终未识别到任何有效维度，按「未收到有效的维度选择」口径终止流程，**不得表述为用户取消**（取消回包形态无法与无人作答可靠区分，不做猜测）。

## 2. select_action_items（Card 组件）

### 组件类型

`type: card`，`selectionType: requirement`

### 业务场景

在总结性结论与 HTML 报告输出后，将体检流程**内部已定稿**的最多 3 条优先行动建议直接渲染为可多选行动项，并在行动项之后按条件追加一个「设置定时任务」选项，用户确认后 Agent 直接按选中项继续执行对应优化动作或为用户设置并开启定时体检任务。

> **🤫 静默约束（最高优先级）**：行动项已在体检流程内部完成挑选与排序，构造本卡片时 Agent 唯一需要做的内部判断是「定时任务去重」：调用 `Schedule`（action=list）后**立即按结果渲卡，中间不得输出任何正文**。对用户**只**呈现：最终的 `select_action_items` 卡片、以及用户选择后真实执行的结果与确认语。尤其**禁止**输出「让我先检查定时任务」「根据 Schedule 列表我看到…」「既然定时任务已启用，我不应该追加这个选项」之类的判断过程，也禁止泄露任何内部字段与判据（`id`、`enabled`、`schedule`、`cron`、技能名、触发语等）。用户勾选后的执行环节同理：直接调用对应技能，不要输出「让我看看哪个技能能处理」「行动项映射：xxx → 某技能」之类的匹配过程。

### 数据槽位定义

- **`questions`**:
  - 类型: `Array<Object>`
  - 说明: 问题列表，仅含一项，字段如下：
    - `question` (string): 引导用户选择下一步执行哪些行动项
    - `options` (Array<string>): 选项文本数组。前若干条为行动项（最多 3 条，按优先级从高到低排列，每条包含行动概要、所属店铺简称及紧急程度）；**最后按条件追加一条定时任务选项**，文案固定为 `⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务`（追加条件见「定时任务推荐选项」）
    - `allowMultiple` (bool): 固定 `true`，表示可多选
    - `required` (bool): 固定 `true`，表示至少选择 1 项
  - 卡片默认提供"确认"与"取消"按钮
  - **定时任务选项为条件型（must-check）**：构造卡片前必须先 `Schedule list` 并按「去重匹配规则」判断，未命中或命中但已停用（enabled:false）才追加该选项；即使本次体检没有可执行的行动项，也应触发该卡片并仅展示该定时任务选项（仍需先按规则判断是否展示）

### 定时任务推荐选项（条件型，非行动项驱动）

除由「优先行动建议」生成的行动项外，还需按以下规则判断是否追加「⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务」选项。该选项**不由行动项驱动**，而是根据店铺体检定时任务的存在状态判断：

1. **检查时机（重要）**：定时任务状态检查必须在**总结性结论与 HTML 报告输出之后**、构造卡片时才进行，**绝不可放在输出前**，以免阻塞诊断结论与报告的输出。
2. **必须先查（must-check）**：构造卡片前**必须先调用 `Schedule`（action=list）拉取全部定时任务**，按下方「去重匹配规则」判断是否已存在店铺体检定时任务，再决定是否追加选项。**不得跳过检查直接追加**。
3. **去重匹配规则（name / description 双键 OR 命中）**：对 list 返回的每条任务，满足以下任一即视为「已存在店铺体检定时任务」——
   - `name` 精确等于 `店铺健康检查`；**或**
   - `description` 精确等于固定执行内容 `自动进行 1688 店铺全面体检，覆盖流量、询盘、成交、商品、客户、广告、风险七大维度，生成体检报告并给出异常提醒和经营建议`。
   比对前先 `trim` 并将连续空白折叠为单空格再做**精确比对**；**禁止**用 `includes('体检')` 之类子串粗匹配（会误伤日报等其他任务）。
4. **展示 / 动作决策**：
   - **未命中**（无匹配任务）→ **追加**选项；用户确认后**新建**（create）。
   - **命中且 `enabled:true`**（已开启）→ **不追加**选项，按第 6 点措辞护栏处理。
   - **命中但 `enabled:false`**（已存在但停用）→ **追加**选项；用户确认后走 **`update` 重新启用**该任务，**禁止 create 新建**。
   - **`list` 调用报错 / 确实无法执行**（fail-open 兜底，仅此一种）→ **追加**选项；用户确认后新建。
5. **位置与文案**：作为附加选项排在所有行动项之后（最后一个），不参与优先级排序，不计入 3 条行动项上限；文案固定为 `⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务`。
6. **已存在（enabled:true）时的措辞（必须静默）**：当**确实查到已存在且已开启、决定不追加**该选项时，该选项**不追加**，且**绝对不要向用户输出任何与定时任务相关的文案**：
   - **尤其禁止输出「已为您设置/已为您开启『店铺健康检查』定时任务…」这类确认语**——此时用户既没有该选项、也没有勾选，任何定时任务提示都是凭空出现的误导；
   - **同样禁止输出任何内部判断过程或技术字段**（如 `id`、`enabled=true`、`schedule`、`cron`、“因此不需要追加定时任务选项”之类的话）。

### 完整数据示例

```json
{
  "type": "card",
  "selectionType": "requirement",
  "questions": [
    {
      "question": "已为您筛选出本次体检最关键的 3 项行动建议，请选择要立即执行的行动项：",
      "options": [
        "优化阿里巴巴的搜索进店商品详情页与主图，提升转化率（高）",
        "补充阿里巴巴的推荐/活动流量渠道，降低对搜索的依赖（中）",
        "建立新客专属权益，改善新老客结构（低）",
        "⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务"
      ],
      "allowMultiple": true,
      "required": true
    }
  ]
}
```

### 用户选择结果处理

| 用户操作 | Agent 行为 |
|----------|-----------|
| 勾选行动项并点击"确认" | 对勾选的每一项在当前会话可用技能中现场寻找能承接的技能并真实执行；若某项确实无技能可承接，直接给出具体的人工操作建议并明确告知用户 |
| 勾选「⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务」并点击"确认" | 若该选项因「未命中」而展示 → 以**完整定时任务规格新建**；若因「命中但 `enabled:false`」而展示 → 走 **`update` 重新启用**已有任务，**不新建**。新建时由客户端弹出「设置定时任务」确认卡片（含执行时间、执行内容、修改任务/立即执行按钮），待用户点击「立即执行」后再创建，不可直接建任务。规格：**任务名「店铺健康检查」**；**执行时间「每天 09:30」**；**执行内容「自动进行 1688 店铺全面体检，覆盖流量、询盘、成交、商品、客户、广告、风险七大维度，生成体检报告并给出异常提醒和经营建议」**。设置成功后向用户确认已开启（如「已为您开启『店铺健康检查』每日定时任务，每天 09:30 自动生成体检报告」）。**仅当用户确实勾选了该选项并成功设置后才输出确认；未勾选或该选项本就未追加时，禁止输出任何定时任务文案** |
| 点击"取消"或不勾选任何项 | 结束本次体检流程，不执行后续动作 |

> **只展示一次（收尾约束）**：`select_action_items` 卡片在整轮体检中只展示一次。用户完成勾选并触发对应技能（或点击"取消"/"跳过"、不勾选任何项）后，体检流程即结束；**触发的下游技能返回后，不得再次渲染该卡片**，用户如需继续优化应主动发起新请求，Agent 不得自行重弹。

### 选项生成规则

1. 行动项由体检流程内部生成并定稿（已从「优先行动建议」中按 **高 > 中 > 低** 挑选、最多 3 条），Agent 拿到后**逐条原样作为选项**，不得增删、改写、重排，也不得再按「是否有技能承接」二次筛选。
2. 行动项生成时已遵循：每条 **40 字以内**，包含「动作对象 + 核心动作 + 紧急程度（高/中/低）」，多店铺场景含所属店铺简称；同等紧急程度下优先选择更可能被自动化能力承接的行动项（软约束，不保证每条都有技能承接）。
3. 用户勾选后，Agent 在当前会话可用技能中**现场寻找**能承接的技能并真实执行；**若某项确实没有技能可承接，直接给出具体的人工操作建议并明确告知用户**，不得静默忽略。
4. 若体检流程未产出任何行动项，卡片仍需触发，仅展示下方按条件追加的定时任务选项。
5. **定时任务选项（条件型 / must-check）**：在行动项之后按「定时任务推荐选项」规则处理——先 `Schedule list` + name/description 双键 OR 命中判断，文案固定为 `⏰ 需要我自动帮你的店铺全面体检嘛？点击设置定时任务`，不参与优先级排序，不计入 3 条行动项上限；**仅当确实查到已存在且已开启（enabled:true）的店铺体检定时任务时才不追加**，命中但已停用（enabled:false）仍追加（确认后重新启用）。

## 3. 已废弃的交互（不再使用）

以下交互组件属于旧两阶段流程，当前版本已废弃：

- `select_analysis_direction`
- `select_abnormal_action`
- `input_offer_for_optimize`

当前版本采用**单阶段完整诊断**，不再在诊断过程中让用户选择深入方向，也不再输出异常商品下一步操作卡片。所有诊断结果通过总结性结论 + HTML 网页数据报告一次性交付。
