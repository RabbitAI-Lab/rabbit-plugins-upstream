# 风险编号机制

## 概览
风险编号用于唯一标识每个风险项，便于在修改、补充或追踪时快速定位。

## 编号格式

```
{场景缩写}-{序号}-{版本}
```

### 各部分说明

#### 1. 场景缩写
- 取业务场景的中文拼音首字母，大写
- 长度建议 3-6 个字符，确保可读性
- 示例：
  - 新产品量产 → XCPCL
  - 设备改造 → SBGZ
  - 供应商变更 → GYSBG
  - 质量事故处理 → ZLSGCL

#### 2. 序号
- 3 位数字，从 001 开始递增
- 每个场景独立编号
- 示例：001, 002, 003, ..., 010, 011, ...

#### 3. 版本
- 格式：V + 数字（V1, V2, V3, ...）
- 初次识别为 V1
- 每次修改后版本号递增

## 完整示例

| 场景 | 场景缩写 | 风险描述 | 编号示例 |
|------|----------|----------|----------|
| 新产品量产 | XCPCL | 新工人不熟练导致产品不良 | XCPCL-001-V1 |
| 新产品量产 | XCPCL | 设备调试不稳定 | XCPCL-002-V1 |
| 设备改造 | SBGZ | 改造期间停机影响产能 | SBGZ-001-V1 |
| 设备改造 | SBGZ | 新设备兼容性问题 | SBGZ-002-V1 |
| 供应商变更 | GYSBG | 新供应商质量不稳定 | GYSBG-001-V1 |

## 版本管理

### 版本递增规则
- 初次识别风险：V1
- 修改风险描述：V1 → V2
- 修改评分：V1 → V2
- 修改控制措施：V1 → V2
- 删除风险后重新添加：新编号（如 XCPCL-004-V1）

### 版本记录
每次修改风险时，建议记录：
- 修改时间
- 修改内容
- 修改原因
- 修改人（如适用）

## 使用场景

### 场景1：用户需要修改已识别的风险
```
用户：风险 XCPCL-001-V1 的描述需要调整
系统：确认修改 XCPCL-001-V1 → XCPCL-001-V2，请问新描述是？
```

### 场景2：用户需要补充风险
```
用户：还想加一个风险
系统：当前最大编号是 XCPCL-005-V1，新风险编号为 XCPCL-006-V1，请描述
```

### 场景3：追踪风险演变
```
用户：风险 XCPCL-003-V1 和 XCPCL-003-V2 有什么区别？
系统：V1版本描述为...，V2版本修改为...，修改原因是...
```

## 注意事项
- 场景缩写应保持一致，同一场景的所有风险使用相同的缩写
- 序号连续递增，不跳号（删除风险后，序号不重新排列）
- 版本号只针对单个风险，不影响其他风险的版本
- 编号应在风险识别阶段立即分配，便于后续引用
