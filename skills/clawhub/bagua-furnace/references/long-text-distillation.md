# 长文本提炼 SOP（八卦炉 · 长原料专章）

> 适用：单份原料 **≥3 万字** 或抽取要点 **≥80 条**——整本书、长课程、多年群聊导出、长录音稿、长播客转写。
> 短料（单篇文章、一次群聊）走主流程即可，不必上这套。

配套：`references/method-card-schema.md`（成丹字段规范 v2）｜`references/extraction-lenses.md`（辨体透镜）

---

## 一、为什么长文本必须走专门流程

两个直觉做法都是错的，而且错得很贵：

| 做法 | 后果 |
|------|------|
| **A. 整篇塞给模型** | 超上下文被拒，或勉强塞进后中间部分"迷失"（lost in the middle），后 2/3 内容等于没读 |
| **B. 截断后喂给小模型** | 更隐蔽、更致命。按字符预算 `if 超预算: break` 是**顺序截断**，取材永远只来自开头几章 |

**B 的实测代价**（八卦炉 HarborLibrary 批次，35 本书）：

- 每本实际要点 **100–150 条 / 8000–9700 字**，截断后只喂进去 **26–35 条** → **信息保留率 28.6%**
- 后果：可用率仅 **16.7%**（通过 6 / 可疑 17 / **不合格 13**），命中率普遍 0.2–0.5
- 更讽刺的是：sys_p 里写了"要点重复要合并"，模型**根本执行不了**——它看不到后面的要点

**结论：蒸馏质量的瓶颈是喂进去的信息量，不是模型聪明程度。**

## 二、四段式标准打法

### 第 1 段：分块抽取要点（可并行）

把长原料切成块，逐块抽取"要点 + 原文原句 + 溯源锚点"，落成结构化中间产物（如 `points/<slug>.json`）：

```json
{"post": "提炼后的要点", "quote": "原文原句，逐字", "type": "原则/步骤/反模式/案例/检查清单",
 "domain": "领域标签", "_chapter": "第三章", "_page": 128}
```

要点：
- **`quote` 必须逐字照抄原文**——后续成丹的"原文原句"和机器审计的命中率都依赖它，改写一步就全废
- **溯源锚点（章节/页码/时间戳）在抽取阶段就要留**，后面补不回来（实测：源文本本身无章节标记的书，溯源行永远无法标注，只能标"未标注"）
- 每块产出条数不设上限，有多少抽多少

### 第 2 段：长上下文通读全量要点后淬炼

**这是质量的分水岭。** 用长上下文模型**通读全部要点**（不是抽样、不是摘要的摘要），再淬炼成卡。

批量处理时分批并行（每批 3–5 份原料，独立上下文，互不污染）：

| 参数 | 建议值 | 说明 |
|------|--------|------|
| 每批原料数 | 3–5 份 | 太多会拖长单批耗时；太少则批次管理成本高 |
| 每份成卡数 | 3 张 | 取最有跨场景迁移价值、原料原词最密集的 |
| 并行批次数 | 3–4 路 | 视 API 并发余量 |
| 单批耗时 | 2–4 分钟 | 含读全量要点 + 成丹 + 自校验 |

给每个执行者的指令必须包含（缺一必掉质量）：

1. **通读全部要点**，明确禁止只读前面部分
2. **先读一张 gold standard 范例卡**，照它的结构、字段、文风写（比纯文字规则有效得多）
3. `# 【名称】` 标题行**必须每个方法块都有**
4. 方法名与关键概念**用原料原词**
5. 原文原句**逐字完整抄录**，不得改写/截断
6. 严禁引入原料没有的概念、方法名、案例、数据

### 第 3 段：机器审计（质量闸门，不可跳过）

成丹后必须跑独立审计，而不是靠执行者自报"成功"。四个维度：

| 维度 | 判据 |
|------|------|
| 结构合规 | 方法块是否都有 `# 【名称】` 标题行、字段是否齐全 |
| 溯源可定位 | 溯源行标注的章节/页码能否在原文中核验 |
| 概念落地率 | 卡内关键概念用 n-gram 对齐原文的命中率 |
| 幻觉 | 是否引入原文没有的东西 |

**审计口径提示**：若 `可用率 = 仅"通过"本 / 总数`，这个口径很严——"可疑"里常有内容其实满分、只是溯源缺锚点的卡。看懂分布再下结论，别被单一数字误导。

### 第 4 段：落盘核验（防静默失败）

**执行者回报"成功"不等于文件真的写好了。** 必须独立核验：

```bash
# 1) 按修改时间倒序，确认每份都真的更新了
ls -lt --time-style=+"%m-%d %H:%M" harbor_*.md | head -40
# 2) 查空文件/过小文件（<3000 字节即异常）
ls -la harbor_*.md | awk '$5<3000 {print "异常:",$9,$5"字节"}'
```

## 三、方法名命名原则（直接决定命中率）

审计用 n-gram 把卡对齐原文算"概念落地率"。**用原料原词 vs 用现代术语，命中率是 1.0 和 0.3 的差别。**

| ✅ 用原料原词 | ❌ 换成现代术语 |
|---|---|
| 恒常会合 | 相关性推断 |
| 断言、重复和传染 | 信息级联传播策略 |
| 词语和套话 | フレーミング/框架化话语 |
| 悬挂假设 | 元认知暂停 |
| 理念型 | 理想化模型 |

**规则**：方法名 = 原料原词 + 必要的动作/边界补充。原词承载"可溯源"，补充承载"可操作"。

## 四、五个已踩过的坑（按代价排序）

1. **顺序截断**（代价：可用率 16.7%）——见第一节。永远不要用 `if 超预算: break`。
2. **写成了 0 字节空文件**（代价：该份原料完全丢失）——执行者回报"成功"但文件是空的。**必须跑第 4 段的核验。**
3. **批次实际没发出**（代价：4 份原料静默漏做）——并行批次里某一路调用返回为空，误以为已下发。**以落盘时间戳为准，不以调用返回为准。**
4. **索引只收录了每份原料的第一个方法**（代价：2/3 的方法搜不到）——按"只取首个路由头"实现的索引，会让每份原料后两个方法永远进不去。要确保索引**收录全部方法块**。
5. **索引规则假定路由头一定在文件第一行**（代价：索引生成 0 条）——卡顶若有标题行，锚定开头的匹配会直接失败。匹配规则不应做这个假定。

## 五、校验清单（收工前逐条打勾）

- [ ] 每份原料的要点是**全量**抽取的，没有按预算截断
- [ ] 每张卡的方法块都**有 `# 【名称】` 标题行**
- [ ] 方法名用的是**原料原词**，不是外部术语
- [ ] 每条"原文原句"与中间产物的 `quote` **逐字一致**（可脚本比对）
- [ ] 溯源行标注了章节/页码；源文本确实无锚点的，诚实标注"未标注"，**不编造**
- [ ] 已跑机器审计，且看懂了"通过/可疑/不合格"的分布与成因
- [ ] **按落盘时间戳 + 文件大小核验过每一份**（无遗漏、无空文件）
- [ ] 索引包含**全部**方法块（条数 = 份数 × 每份卡数），不是只取了第一个
- [ ] 改动前已整体备份，可回退

## 六、实测对照（同一批原料、同一套校验口径）

一次 35 本书的实测，按四项校验：结构完整性 / 溯源可定位 / 原文可命中 / 有无编造。

| 喂料方式 | 达标 | 待确认 | 不达标 | 达标率 |
|------|------|------|--------|--------|
| 小模型 + 截断喂料 | 6 | 17 | **13** | **16.7%** |
| **长上下文 + 全量要点** | **32** | 4 | **0** | **88.9%** |

Δ 达标率 **+72.2 个百分点**，不达标 **13 → 0**。

> **"待确认"不等于质量差**：若某几份内容完整、原句可溯源、无编造，只因源文本本身没有章节标记而无法标注溯源位置，那是**源数据的限制，不是提炼的问题**——不必强求，如实标注即可。
