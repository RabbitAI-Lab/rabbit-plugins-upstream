# 场景：invoice-issue（发票开具编排）

## 触发关键词

发票开具,开具发票,开票

## 场景说明

本场景为顺序编排流程，目标是在真正调用开票接口前完成字段识别、脚本侧字段自动补全、预览确认，并在开票完成后通过状态接口轮询结果，返回摘要、原件链接与 PDF 附件。

当前检查链路中的自动补全顺序固定为：先补销售方必填上下文；若购买方名称非空且不是 18 位统一社会信用代码，或购买方名称/购买方税号本身是 18 位统一社会信用代码，则通过独立企业搜索能力查询购买方企业；仅当返回 1 个候选时才默认选择并补齐购买方名称/税号，返回多个候选时必须要求用户选择正确企业，不得取首条；再按项目名称自动补商品编码；在已拿到商品编码后，若用户未提供税率，则优先根据纳税人类型和商品字典自动匹配参考税率，并取最低税率回填；随后再按金额与税率关系反算明细金额、税额、单价，并生成整票汇总金额。若税率自动匹配失败，才转为待补充项，要求用户直接提供税率，或补充纳税人类型后重新匹配。

自动补全的触发点是“开票信息检查命令”，不是正式开票提交命令。Agent 将用户输入整理为顶层 `invoices[]` 的 input JSON 后，必须先执行 [invoice-issue-batch-invoice-info-check](batch-invoice-info-check.md) 对应的二进制命令；该命令在创建任务状态 JSON 和写入 `check_result` 的过程中完成 `areaCode`、`personalAccount`、销售方信息、购买方名称/税号、商品编码、税率、金额税额及整票汇总等补全。正式开票 `issue-from-output` 只消费已通过检查和预览确认的 `check_result.invoice_payload_json`，不得被当作自动补全入口。

因此，除煤炭类前置字段、明确冲突或无法无歧义提取的核心信息外，Agent 不应因为销售方信息、购买方企业名称/税号、商品编码、税率、税额、汇总金额等字段缺失而在执行检查命令前反复追问；应先保持缺失进入 check 阶段，再依据 `check_result.missing_fields_by_module`、`check_result.tax_rate_validation`、`check_result.purchaser_autofill` 和预览内容决定是否一次性向用户补问。

开票任务开始前进行参数校验时，若缺失的是非必填参数，或缺失项属于销售方上下文、购买方企业名称/税号、商品编码、税率、金额税额、整票汇总等可由脚本、配置、接口或字典自动补齐的参数，不得判定为中止条件；应继续进入开票信息检查链路，由检查结果决定是否需要后续补问。只有缺失原始输入阶段必填参数、存在明确冲突/歧义，或检查后确认无法自动补齐的前置必填参数时，才允许暂停流程并一次性向用户补问。

除非用户特殊说明，本场景中用户输入的金额、单价默认按含税口径识别与校验；不得自行改判为不含税金额或不含税单价。

若用户是通过图片、截图、扫描件、PDF、Word、Excel、压缩包内清单或其他文件来表达“按这个内容开票”，Agent 不得跳过字段提取直接构造 input JSON；必须先从文件中提取出可落位的开票关键信息，整理成等价的文字版开票内容，再按本场景规则转换为 `invoices[]` 输入。若文件提取结果存在识别不清、字段缺失、票与票边界不明确、税率/金额/购方等核心要素无法无歧义确认，必须先向用户展示已识别结果并说明缺失项，必要时建议用户直接改用文字输入，或手动补充缺失的关键信息后再继续开票。

本场景同时支持单张开票与批量开票，前置检查统一走批量检查链路：

1. 当用户只提供 1 张发票，或明确表达为“单张/一张/这一张”时，也必须整理为仅包含 1 个元素的 `invoices[]` 数组，再走批量检查子场景；
2. 当用户明确表达“批量开票”，或当前输入中存在 2 条及以上开票对象时，同样统一走批量检查子场景；若用户未直接说“批量开票”，但使用 `1.`、`2.`、`3.`、换行分段、分号分段等方式连续列出多组“商品/金额/税率/发票类型/购方”等开票要素，也应视为存在多张待开票对象，触发批量开票；
3. 主编排层统一复用批量检查命令与同一正式开票提交命令。

批量识别补充规则：

1. 若输入中出现多个编号段落，且每个段落都可独立形成一张发票所需的核心要素，应按“每个段落 1 张发票”识别，不得因为购方相同就合并成单张。
2. 若同一条消息中连续出现多次“商品 + 金额 + 税率/免税/0税率 + 发票类型”等组合，即使未显式写出 `info[]`，也应优先按批量开票处理。
3. 例如“给购方：测试 开具以下发票：1. 商品：苹果 金额：1 免税 普通发票 2. 商品：李子 金额：1 0税率 普通发票 3. 梨 金额1 税率1% 苹果 金额2 税率1% 普通发票”中，前两段各为 1 张发票，第 3 段为另一张发票，总计应识别为 3 张发票并触发批量场景。

执行顺序如下：

1. 无论当前输入是单张还是批量，均调用 [invoice-issue-batch-invoice-info-check](batch-invoice-info-check.md)；由 Skill 先将发票信息整理到 `invoices[]` 数组，再调用二进制命令生成统一任务状态 JSON；
2. 读取当前任务状态 JSON 中的 `check_result`；若脚本已自动补全商品编码或税率，则直接采用补全结果；其中税率补全发生在商品编码补全之后，并按“纳税人类型 + 商品编码字典”取最低参考税率；
3. 若 `check_result.purchaser_autofill.needs_user_selection=true`，必须展示 `check_result.purchaser_autofill.candidates` 候选企业并让用户选择；用户选定后将对应购买方名称和税号写回 input JSON，重新执行批量检查命令，不得取第一个候选继续；
4. 仅当 `check_result.validation_passed=true` 且 `check_result.invoice_preview_markdown_generated=true` 时，读取任务状态 JSON 中的 `check_result.invoice_preview_markdown_path`，按该本地 Markdown 文件路径读取预览内容后原样展示给用户；同时保留 `check_result.invoice_preview_markdown` 作为脚本产出的原始内容校验字段。展示时必须明确提示用户核对发票内容并回复“确认开票”；未收到该明确确认前，流程必须停留在预览阶段。Agent 认为自己已完成预览 Markdown 原样展示后，必须立即自检：核对发票明细是否完整输出，且“预览发票票样链接”对应内容是否完整输出；若任一缺失、截断或遗漏，必须先重新完整展示，再继续后续流程；
5. 用户确认后，调用 `.\bin\windows-amd64\invoice-assistant_windows_amd64.exe issue-from-output --pretty` 基于当前任务状态 JSON 发起正式开票；
6. 脚本调用 `/invoice-issue/issue-status` 轮询申报结果，首次查询从开票后 2 秒开始，最多 10 次，并支持指数退避；
7. 脚本将结果写回任务状态 JSON，并同步落地开票结果 Markdown 文件；编排层必须优先读取 `issue_result.issue_result_markdown_path` 指向的本地 Markdown 文件并原样展示给用户，同时保留 `issue_result.issue_result_markdown` 作为脚本产出的原始内容校验字段；不得自行修改 Markdown 内容，如需补充额外说明，必须放在 Markdown 之外。

预览生成命令契约：

1. 正常开票流程不得单独调用 `issue-invoice-preview-generator` 生成给用户看的预览；预览 HTML 与预览 Markdown 由 `issue-batch-invoice-info-check --input <临时输入文件>.json --pretty` 在校验通过后自动写入任务状态 JSON。
2. `issue-invoice-preview-generator` 只接受 `--input <input.json>` 和 `--output <preview.html>`，不支持 `--task-file` 或 `--pretty`；它只生成 HTML 文件，不会写入任务状态 JSON，也不会生成 `check_result.invoice_preview_markdown_path`。
3. 若 `check_result.validation_passed=false` 或任务状态为 `check_failed`，`invoice_preview_markdown_path` 为空是预期结果；此时必须根据 `missing_fields_by_module`、`validation_errors`、`tax_rate_validation`、`purchaser_autofill` 等字段补齐或确认信息后重新执行检查命令，不得改用预览生成器试错。
4. 若 `validation_passed=true` 但 `invoice_preview_markdown_generated=false`，必须优先查看 `check_result.invoice_preview_error` 或重新执行检查命令；不得手动拼装预览 Markdown，也不得直接进入正式开票。

## 新任务与继续当前任务的判定规则

为避免把历史 task JSON 误当成当前用户这一次要开的发票，编排层必须先判断当前请求究竟是“新任务”还是“继续同一任务”，并严格按以下规则执行：

1. 只要用户当前输入重新提供了新的开票内容，或重新描述了购方、商品、金额、税率、票种、明细等任一开票要素，即判定为“新任务”；不得先读取历史 task JSON 并直接复用旧的 `check_result`、旧预览或旧开票结果。
2. 只有当用户明确表达是在继续刚才那一次任务时，才允许复用当前任务指针；例如“确认开票”“继续刚才那张”“查看刚才开票结果”“继续上一条预览”这类明显承接同一任务的指令。
3. 若当前输入同时出现新的开票内容，又带有“继续”“确认”之类词语，仍应优先判定为“新任务”；必须先重新生成 input JSON 并重新执行检查命令，而不是复用旧 task。
4. 对“新任务”，第一动作必须是重新整理本次用户输入并调用批量检查命令创建新的任务状态 JSON；只有命令返回并刷新 `CURRENT_ISSUE_TASK_POINTER_PATH` 后，才允许读取该新任务 JSON。
5. 对“继续当前任务”，只允许读取本轮会话中最近一次、且已明确与当前用户请求对应的任务状态 JSON；不得因为目录里存在更早的已完成任务文件，就直接输出历史开票结果。
6. 如果无法确定当前请求是“继续旧任务”还是“发起新任务”，默认按“新任务”处理；宁可重新建新 task 做一次检查，也不能直接拿历史已开票结果回复用户。

预览 Markdown 补充要求：

1. 预览阶段的 Markdown 正文中必须包含“本次将开具 X 张发票”的提示，其中 `X` 取自当前标准化 payload 中的发票数量。
2. 单张场景显示 `1`，批量场景显示实际张数；不得省略该提示。

## 强制展示规则（新增）

发票开具链路会产出两段 Markdown 内容，Agent 在执行过程中必须完整展示给用户，不得省略、不允许只做摘要：

1. 预览阶段：`check_result.invoice_preview_markdown_path` 指向的本地 Markdown 文件内容
2. 开具结果阶段：`issue_result.issue_result_markdown_path` 指向的本地 Markdown 文件内容

执行要求：

1. 只要对应 Markdown 内容非空，必须原样展示。
2. 不得以“已生成/详见任务文件/已保存”替代正文展示。
3. 不得截断为节选或仅保留标题。
4. 展示发票预览时，必须先读取 `check_result.invoice_preview_markdown_path` 指向的本地 Markdown 文件，再将文件内容直接原样输出；不得先行二次总结、改写、精简或重新拼装一版预览文案。
5. 展示开票结果时，必须先读取 `issue_result.issue_result_markdown_path` 指向的本地 Markdown 文件，再将文件内容直接原样输出；不得先行二次总结、改写、精简或重新拼装一版结果文案。
6. 如需附加说明，必须放在 Markdown 之外，且不得改写 Markdown 原文。
7. 若字段为空或缺失，必须明确告知“未生成对应 Markdown 内容”，并给出下一步处理（重试脚本或排查失败原因）。
8. Agent 在展示发票预览 Markdown 后，必须立即自检对话框中的实际输出是否完整覆盖以下关键内容：
   - 所有发票明细条目；
   - “预览发票票样链接”标题及其对应链接内容。
     若发现任一部分缺失、截断、漏行或仅输出部分正文，必须在进入下一步前重新完整输出预览 Markdown。
9. Agent 在展示开票结果 Markdown 后，必须立即自检对话框中的实际输出是否完整覆盖该结果 Markdown 的全部正文；若发现任一标题、编号项、列表项、链接或段落缺失、截断、漏行或仅输出部分正文，必须在结束流程前重新完整输出开票结果 Markdown。

## 参数规格

说明：

- 编排场景参数是底层开票接口的统一入口。
- 商品编码补全结果由检查脚本产出；编排层负责展示补全结果、预览确认与正式提交。
- 用户当前请求阶段只强制要求提供 `uscc`；`areaCode` 与 `personalAccount` 由脚本在 input JSON 转 task JSON 阶段按 `uscc` 从 `.invoice-config/workspace-config.json` 的 `companyInfo[uscc]` 中补齐，并写入任务状态 JSON 的 `raw_input_json`。若配置文件不存在，会在首次读取时自动创建默认配置文件。
- 如用户已知纳税人类型，也可在原始 input JSON 顶层额外提供 `taxpayerType`，支持值：`一般纳税人`、`小规模纳税人`；该字段仅用于税率自动匹配，不进入正式开票 payload。
- 当用户未明确指定发票类型时，不得仅因票种缺失在 input JSON 阶段中止追问；检查脚本会查询销方企业画像，若销方为小规模纳税人，则默认补为“普通发票”。若用户明确指定“普票/专票”等票种，则必须以用户指定为准。

| 参数名          | 类型          | 必填 | 说明                           | 来源               |
| --------------- | ------------- | ---- | ------------------------------ | ------------------ |
| uscc            | string        | Y    | 销售方税号                     | 用户输入           |
| areaCode        | integer       | Y    | 地区编码                       | 按 uscc 从配置匹配 |
| personalAccount | string        | Y    | 居民身份证/手机号/用户名       | 按 uscc 从配置匹配 |
| taxpayerType    | string        | N    | 纳税人类型，仅用于税率自动匹配 | 用户输入/脚本查询  |
| invoices[]      | array<object> | Y    | 发票原始输入数组，至少 1 条    | 用户输入           |

## 用户输入到 Input JSON 的强制映射规则

开票场景下，Skill 在将用户自然语言整理为原始输入对象时，必须统一使用顶层 `invoices[]` 数组承载发票信息；即使只有 1 张发票，也不得改用其他单张结构。每张发票的明细字段统一落到 `invoices[].details[]` 层级，涉及金额、单价、税率、税额等字段时不得改写到其他原始输入路径，避免 `0税率`、`免税`、`不征税` 被写入错误字段后影响后续自动补全。脚本输出标准化 payload 时，仍会落到 `info[]`。

特别注意：本节描述的是 `issue-batch-invoice-info-check --input` 的原始 input JSON，不是正式开票接口 payload。正常开票不得把 [issue.md](issue.md) 的 `info[]` / `invoiceDetail.data[]` 结构、任务状态里的 `check_result.invoice_payload_json`，或 `params.info[]`、`params.goods[]`、`params.purchaserName`、`params.projectName` 等包装/扁平结构当作检查命令入参。正式 payload 只能由检查脚本从 `invoices[].details[]` 标准化生成。

原始 input JSON 的键名与层级必须严格限定在“本编排文档已定义的原始输入结构 + [issue.md](issue.md) 中可一一映射的接口字段语义”范围内。对非关键字段，若当前场景没有额外说明，Agent 只能使用已定义、可被脚本识别的原始输入键承载用户明确提供、或已从文件/图片中无歧义识别出的信息；仅对用户未提供、且当前也未稳定识别出的字段，才允许保持缺失。不得自行创造同义键、别名键、过渡键、包装层或调试字段，例如 `items`、`invoiceDetails`、`buyerName`、`taxAmount`、`previewData`、`extra`、`metadata` 等，以免后续脚本无法识别或映射失败。若用户明确提供“备注”，必须写入对应发票的 `noteInfo.note`；不得改写为 `remark`、`remarks`、`memo` 等别名，也不得放到顶层或单张发票对象顶层。

执行边界补充：

1. 在“用户输入 -> input JSON”阶段，Agent 只需要整理用户已明确提供、或已从文件/图片中无歧义提取出、且当前能够无歧义落位的字段；这些字段即使属于非必填，也必须写入 input JSON。典型包括：购方税号、购方地址、购方电话、购方开户行及账号、备注、已明确给出的税额、折扣比例、折扣金额等。对非必填字段，仅当用户未提供、文件/图片也未稳定识别出时，才允许保持缺失，不需要在这一阶段反复追问。
2. 对销售方上下文字段，Agent 在 input JSON 阶段只需确保顶层 `uscc` 已写入；`areaCode` 与 `personalAccount` 由脚本后续按 `uscc` 从配置文件补齐，不要求用户在本轮再次重复提供。
3. 对“备注”字段，原始 input JSON 的唯一受支持落位是对应发票下的 `noteInfo.note`。不得写成 `remark`、`remarks`、`memo` 等别名，也不得写到批量顶层或发票对象顶层。
4. 只有以下情况，才允许在 input JSON 阶段立即追问：字段本身属于原始输入阶段的必填项、当前存在明确冲突或歧义、或该字段虽为接口可选但在当前特定业务场景下属于前置必填（例如煤炭类明细的 `mtzlDm` 与 `unit`）。
5. 若发票类型缺失，Agent 应保留票种缺失并进入 check 阶段；检查脚本查询销方企业画像后，只有在销方为小规模纳税人时才自动补“普通发票”，其他情况仍按缺失项返回并由 Agent 一次性追问。
6. 对其余可选字段，Agent 应先进入 check 阶段；若脚本在 `check_result` 中明确返回缺失项、冲突项或校验失败原因，再一次性向用户确认。
7. 若用户提供的是图片或文件而非直接文字描述，Agent 必须先完成“文件内容 -> 文字版开票字段”的提取与整理，再进入 input JSON 映射；不得把未提取、未核对的原文件内容直接当作结构化字段使用。
8. 对图片或文件中提取出的字段，只要当前能够无歧义落位，就必须写入 input JSON，即使该字段在接口层属于非必填也不得遗漏；例如文件中已明确识别出购方地址、购方电话、开户行账号、备注、折扣金额、税额等，都应按受支持键名原样落位。识别置信度不足、版式混乱、同名字段含义不清、或多张发票边界不明确时，才必须保留缺失并向用户确认，不得自行猜测补全。
9. 若图片或文件提取效果不佳，导致无法稳定得到购方、商品、金额、税率等核心字段，Agent 必须明确建议用户直接用文字提供开票信息，或手动补充缺失关键信息；不得在低置信度提取结果上继续推进正式开票流程。若仅票种缺失，应先交由 check 脚本按销方企业画像处理。
10. 若某个非关键字段在 [issue.md](issue.md) 的“请求参数说明”里已有明确字段名、嵌套层级或值语义，则该表应视为字段转换主参照；原始 input JSON 只能落到本场景已约定的对应原始键上，再由脚本标准化；不得把正式 payload 的其他层级原样搬进原始 input JSON，也不得为方便表达而发明脚本未声明支持的新键。

### 金额与单价映射

1. 用户只说“金额”“项目金额”“含税金额”“价税合计金额”时，默认按含税金额识别，应优先写入 `invoices[].details[].taxInclusiveAmount`。
2. 只有当用户明确说“不含税金额”“税前金额”时，才允许写入 `invoices[].details[].amount`。
3. 用户只说“单价”“含税单价”时，默认按含税单价识别，应优先写入 `invoices[].details[].taxInclusivePrice`。
4. 只有当用户明确说“不含税单价”“税前单价”时，才允许写入 `invoices[].details[].price`。
5. 用户明确给出“税额”时，应写入 `invoices[].details[].tax`；若未明确给出，则保持缺失并由脚本按金额与税率关系自动补全。
6. 若用户仅提供“金额”或“单价”，但未明确说明为不含税口径，Skill 不得擅自写入 `amount` 或 `price`。

### 税率映射

1. 只有当用户明确说出税率语义时，才允许在原始 input JSON 阶段写入 `invoices[].details[].taxRate`；可接受的显式输入包括“税率”“征收率”“1%”“3%”“13%”“0税率”“0%”“0”“免税”“不征税”。若用户没有说明税率，或当前仅能识别到商品、金额、票种等其他字段，则不得自行识别、推断或补写 `taxRate`，必须保持缺失，交由后续脚本自动匹配。
2. `taxRate` 字段承担税率原始语义输入；Skill 不得把普通税率直接写入 `xsyhzcbz` 或 `zzstsgl`。
3. 对 `0税率`、`0%`，以及明确输入为 `0` 的情况，应按普通零税率处理，写入 `taxRate`；不得自动改写为“免税”或“不征税”。
4. 若用户未明确提供税率，原始 input JSON 阶段必须保持 `invoices[].details[].taxRate` 缺失；检查脚本会在商品编码补全完成后，优先按纳税人类型与商品字典自动匹配参考税率，并取最低税率回填。
5. 纳税人类型用于税率自动匹配时，优先级为：用户显式提供的 `taxpayerType` -> 按 `uscc + areaCode + personalAccount` 查询识别；仅当两者都无法得到明确结果时，才转为待补充项并追问用户。
6. 若自动匹配仍失败，必须一次性提示用户“请直接提供税率，或补充纳税人类型（一般纳税人/小规模纳税人）后重新匹配”；不得在 input JSON 阶段因为税率缺失而直接中止其他可继续的补全步骤。

### 免税、不征税的特殊落地规则

1. 当用户明确说“免税”时，Skill 在原始输入阶段应将 `免税` 原样写入 `invoices[].details[].taxRate`，由后续脚本标准化处理；不得在 input JSON 阶段先改写为 `0`、`0%` 或其他数值税率，也不得跳过 `taxRate` 直接只写 `zzstsgl`。
2. 当用户明确说“不征税”时，Skill 在原始输入阶段应将 `不征税` 原样写入 `invoices[].details[].taxRate`，由后续脚本补齐特殊政策字段；不得在 input JSON 阶段先改写为 `0`、`0%` 或其他数值税率，也不得只写 `xsyhzcbz`、`zzstsgl` 而缺少 `taxRate`。
3. `免税` 与 `不征税` 在脚本标准化后，都会把 `taxRate` 归一为 `0%`，并进一步区分：
   - `免税`：`xsyhzcbz=Y`，`zzstsgl=03`
   - `不征税`：`xsyhzcbz=Y`，`zzstsgl=04`
4. `0税率` 与 `0%` 不属于上述两类特殊政策，不得自动补写 `zzstsgl=03/04`。

### 折扣信息映射

1. 当用户明确提供“折扣”“折扣比例”时，原始输入阶段应先写入 `invoices[].details[].discountInfo.discount`，且该值必须先归一化为百分比数值；例如 `0.5 -> 50`、`50% -> 50`、`88折 -> 88`、`12.5% -> 12.5`。
2. 当用户明确提供“折扣金额”“优惠金额”时，原始输入阶段应先写入 `invoices[].details[].discountInfo.discountAmount`。
3. 原始输入阶段不得主动补写 `discountInfo.discountMode`、`discountInfo.discountTax`；这两个字段由后续脚本基于已归一化的折扣比例或折扣金额统一换算与标准化。
4. 若用户已经明确表达当前明细存在折扣，但只说“有折扣”“打了折”“有优惠”而未给出折扣比例或折扣金额，必须保留缺失并追问，不得在 input JSON 阶段省略该折扣信息。
5. 若用户同时提供折扣比例和折扣金额，可先按已归一化后的百分比数值写入 `discountInfo.discount`，并按原值写入 `discountInfo.discountAmount`，由后续脚本校验与标准化；若两者明显冲突，则必须追问确认。

### 防错要求

1. 若用户表达仅能确认“这是零税负相关语义”，但无法确认是 `0税率`、`免税` 还是 `不征税`，必须保留缺失并追问，不得擅自三选一。
2. 若用户同时给出“免税/不征税”和数值税率，视为冲突输入，必须中止自动落位并追问确认。
3. 若用户明确提到存在折扣，但未提供可计算的折扣比例或折扣金额，必须把折扣信息列入缺失项并追问，不得直接忽略该折扣语义。
4. 若用户提供的折扣比例不是可直接落入 input JSON 的百分比数值，Skill 必须先完成归一化；例如 `0.5 -> 50`、`50% -> 50`、`88折 -> 88`。无法确定时必须追问，不得把 `50%`、`88折`、`八折` 等原始文本直接写入 `discountInfo.discount`。
5. 购方名称属于必填信息；购方税号 `invoices[].purchaserInfo.uscc` 在普通发票场景下不属于原始输入阶段的强制必填字段，只有用户明确提供时才写入，未提供时必须保持缺失，不得为凑齐字段而补造、猜测或复用其他编号，也不应在 input JSON 阶段因其缺失而单独反复追问。若用户把购买方名称或统一社会信用代码写在购方名称位置，应原样写入 `purchaserInfo.name` 并进入检查命令；脚本会调用独立企业搜索能力，返回 1 个候选时自动补齐/修正购买方名称与税号，返回多个候选时由用户选择，不得默认取首条。
6. 若用户未指定票种，也应进入检查命令，由脚本基于销方企业画像判断是否默认“普通发票”；票种默认与购方纳税人性质无关，不得因为购方是小规模纳税人而默认普通发票。
7. 若发票类型为“增值税专用发票”，则购方名称与购方税号都属于强制必填字段；缺少任一项都必须中止并追问，不得继续进入检查通过、预览或正式开票流程。
8. Skill 在准备原始输入时，不得为通过后续脚本校验而主动补写 `tax`、`xsyhzcbz`、`zzstsgl`、`discountInfo.discountMode`、`discountInfo.discountTax` 等派生字段，除非这些值就是用户明确输入。
9. Skill 在生成原始 input JSON 时，不得输出任何未在本场景原始结构中声明、且无法稳定映射到 [issue.md](issue.md) 请求字段说明的 key；一旦发现某个字段只能通过“自造 key”才能表达，必须保持缺失或改为向用户追问，而不是继续产出脚本无法识别的结构。
10. 当税率缺失时，编排层不得擅自拍脑袋补一个常见税率，也不得因为商品类型、历史经验或零税负联想而把 `taxRate` 识别成“免税”“不征税”或其他具体税率；只能走“保持缺失 -> 纳税人类型识别 -> 字典匹配最低税率 -> 匹配失败后追问”的固定流程。

### 普通税率示例

当用户输入的是普通税率场景时，原始 input JSON 可按下面方式组织：

```json
{
  "uscc": "91440300MA5FXXXXXX",
  "invoices": [
    {
      "invoiceType": "普通发票",
      "purchaserInfo": {
        "name": "深圳市测试贸易有限公司",
        "uscc": "91440300MA6HXXXXXX"
      },
      "details": [
        {
          "projectName": "苹果",
          "taxInclusiveAmount": 113,
          "taxInclusivePrice": 11.3,
          "quantity": "10",
          "taxRate": "13%",
          "tax": 13
        }
      ]
    }
  ]
}
```

这个示例对应的落位含义是：

1. 顶层统一使用 `invoices[]`，即使只有 1 张发票也不例外。
2. 明细统一写在 `details[]`，不在原始输入阶段写 `invoiceDetail.data[]`。
3. `113` 按含税金额落到 `taxInclusiveAmount`。
4. `11.3` 按含税单价落到 `taxInclusivePrice`。
5. 普通税率 `13%` 直接写入 `taxRate`。
6. 若用户已经明确给出税额，可直接写入 `tax`；若未明确给出，则保持缺失，由脚本自动补全。

## 接口调用顺序

1. 无论当前输入数量为 1 还是多张，均调用 [invoice-issue-batch-invoice-info-check](batch-invoice-info-check.md)；由 Skill 将每张发票整理到顶层 `invoices[]` 数组后，再由二进制命令创建任务状态 JSON，并更新当前任务路径常量指针。
2. 读取任务状态 JSON 中的 `check_result.validation_passed`、`check_result.missing_fields_by_module` 和 `check_result.invoice_payload_json`。
3. 在编排层完成必要的编码转换与完整性复核；除用户明确输入可识别字段外，编排层不得自行推理并补写其他开票字段，缺失字段必须依赖脚本补全与校验结果。
4. 若脚本返回结果中仍存在缺失的 `spbm` 或缺失且无法自动匹配的 `taxRate`，则中止后续流程并向用户追问；若脚本已自动补全，或返回的缺失项仅为非必填参数，则直接采用补全结果并继续后续流程。批量场景下商品编码需按“第几张发票 + 项目名称 + 商品编码”逐条回显。
5. 仅当 `check_result.validation_passed=true` 且 `check_result.invoice_preview_markdown_generated=true` 时，读取任务状态 JSON 中的 `check_result.invoice_preview_markdown_path`，按该路径读取本地 Markdown 文件并原样渲染，不得自行修改；等待用户明确确认“确认开票”后，将任务状态 JSON 中 `check_result.invoice_preview_confirmed` 标记为 `true`。若 `validation_passed=false`，不得尝试调用 `issue-invoice-preview-generator` 补救，必须先处理缺失项或待确认项并重新执行检查命令。
6. 调用 `.\bin\windows-amd64\invoice-assistant_windows_amd64.exe issue-from-output --pretty` 提交正式开票请求；二进制命令在第一次调用开票接口前，必须先在任务状态 JSON 的 `issue_result` 中写入防重复提交标记。
7. 若 Agent 或脚本发生重复调用，必须先检查任务状态 JSON 中首次正式开票时记录的 `taskID`：
   - 若已记录 `taskID`，不得再次调用开票接口，必须直接基于该 `taskID` 调用 `/invoice-issue/issue-status` 查询开具结果；
   - 若已经存在“已发起正式开票”的标记但未记录到 `taskID`，必须停止重试，并明确告知用户“获取发票开具结果异常，为防止重复开票，请前往税局确认”。
8. 正式开票命令内部继续调用 `/invoice-issue/issue-status` 查询申报结果，首次查询等待 2 秒，后续按指数退避继续轮询，最多 10 次；状态查询请求体固定为 `taskID + uscc + isAuth=true`，其中 `taskID` 来自首次开票接口响应或任务状态 JSON 中已记录的 `taskID`，`uscc` 来自销售方税号。若状态查询返回 `data.status != -1`，即使当前单票结果里出现失败原因文案，也仍应继续重试，不能立即判定失败。
9. 根据任务状态 JSON 中的 `issue_result` 输出成功摘要、原件链接、PDF 下载链接或失败原因；其中展示开票结果时，必须优先读取 `issue_result.issue_result_markdown_path` 指向的本地 Markdown 文件并原样展示给用户，同时保留 `issue_result.issue_result_markdown` 作为校验字段。

## 编排执行规则

1. 必须先执行前置检查：统一走批量检查命令；即使只有 1 张发票，也必须放入顶层 `invoices[]` 数组后再执行检查。必填参数缺失时，一次性列出所有缺失项，不得直接调用底层接口。
2. 当用户当前消息包含新的开票内容时，编排层不得在检查前先读取旧任务状态 JSON 判断“是否已开票完成”；必须先把当前输入整理成新的 input JSON，并重新调用批量检查命令创建新任务。
3. 对原始输入阶段允许缺失的非必填字段，编排层不应在调用检查命令前反复确认；应先以保持缺失的 input JSON 进入 check 阶段，再根据脚本返回的 `check_result.missing_fields_by_module` 或其他校验结果一次性追问。
4. 若任一明细缺少 `spbm` 但已提供 `projectName`，必须先依赖检查命令执行自动赋码；若脚本仍未补全成功，则不得进入预览阶段。
5. 在商品编码确定后，若明细仍缺少 `taxRate`，必须继续依赖检查命令按纳税人类型与商品字典自动匹配最低税率；只有自动匹配失败时，才允许转为待补充项向用户追问。
6. 对脚本已自动补全的商品编码，必须把项目名称与补全后的商品编码逐条展示给用户，避免静默改写。
7. 调用底层接口前必须读取并展示任务状态 JSON 中 `check_result.invoice_preview_markdown_path` 指向的预览 Markdown 文件；如需补充摘要，也必须放在 Markdown 之外，不得自行重新拼装另一版预览文案。若该字段为空，必须先排查检查未通过或预览生成失败原因，不得手动构造预览内容。
8. 预览阶段必须等待用户明确确认；未确认前不得发起正式开票，且任务状态 JSON 中 `check_result.invoice_preview_confirmed` 必须保持为 `false`。
9. 展示预览 Markdown 后，必须先完成完整性自检，重点检查发票明细与“预览发票票样链接”是否已经在对话框中完整输出；未通过自检前不得进入正式开票步骤。
10. 第一次正式提交开票前，必须先在任务状态 JSON 中写入“已发起正式开票”的防重标记；一旦首次开票响应返回 `taskID`，必须立即写回任务状态 JSON。
11. 若检测到当前任务已存在首次正式开票记录，则不得再次调用开票接口；应优先复用已记录的 `taskID` 查询开具结果。
12. 若检测到已存在首次正式开票标记但缺少已记录的 `taskID`，必须中止流程并告知用户：“获取发票开具结果异常，为防止重复开票，请前往税局确认”。
13. `isIncludeTax` 当前固定为 `true`；若用户要求改成不含税，应直接说明当前接口不支持。
14. 金额校验不通过时必须在编排层中止，提示用户修正后再继续。
15. 开票完成后，必须优先展示任务状态 JSON 中 `issue_result.issue_result_markdown_path` 指向的开票结果 Markdown 文件内容；若仅返回部分结果，应明确说明缺失部分。
16. 发票开具完整流程中，`check_result.invoice_preview_markdown_path` 指向的预览 Markdown 文件内容与 `issue_result.issue_result_markdown_path` 指向的开票结果 Markdown 文件内容均为强制回显内容，任一非空即必须展示，不得省略。
17. 正式开票提交成功并不等于最终开票成功；必须以 `/invoice-issue/issue-status` 的轮询结果为准。
18. 编排层不得为了满足后续步骤而补写用户未明确提供的业务字段；若 `projectName`、`purchaserInfo.name` 等字段存在歧义，必须保留缺失并向用户追问，不得把同一原始值复用到多个字段。
19. 批量场景下，缺失项应按“第几张发票 + 模块”汇总，而不是把多张发票的缺失项合并成一组无索引提示。
20. 正常对话输出中，**不得**主动展示当前任务状态、任务状态 JSON 文件路径、预览文件路径、预览 Markdown 文件路径、开票结果 Markdown 文件路径或标准化后的开票 JSON；这些内容仅用于内部编排和脚本串联，只有在用户明确要求查看时才可展示。
21. 开票场景中，用户输入的金额与单价默认按“含税金额”“含税单价”口径识别；不得自动改判为不含税金额或不含税单价参与校验。
22. 涉及煤炭相关项目时，Skill 必须在“用户输入 -> input JSON”阶段就识别并写出 `mtzlDm`；可接受用户直接提供代码，或提供可唯一映射的标准名称后由 Skill 按煤炭种类字典转换。当前允许的标准映射为：`政府保供煤 -> 0100`、`市场煤 -> 0300`、`长协煤-协议期不足半年 -> 0201`、`长协煤-协议期在半年至一年之间 -> 0202`、`长协煤-协议期在一年至两年之间 -> 0203`、`长协煤-协议期在两年以上 -> 0204`。同时，煤炭类明细的 `unit` 不得为空，且仅允许 `吨`、`千克（公斤）`。若用户仅提供“长协煤”“普通煤”“常见煤种”等无法唯一映射的描述，或未提供合法单位，必须中止并追问，不得延后到后续步骤再确定。
23. 对单张开票与批量开票，除用户输入中可明确识别的字段外，Agent 不得自行推理新增其他开票字段；所有缺失字段必须由检查脚本自动补全并执行完整性校验。原始输入阶段，所有发票对象都必须归入顶层 `invoices[]` 数组。
24. 若开票失败原因包含“请先扫码验证获取开票权限”，必须先提示用户需进行人脸验证以延长开票权限；在用户明确确认“需要延长开票权限”后，转入 [invoice-issue-auth-extend](invoice-issue-auth-extend.md) 场景，并沿用当前已识别的 `uscc`、`areaCode`、`personalAccount` 参数继续执行。
25. 用户也可以直接主动触发 [invoice-issue-auth-extend](invoice-issue-auth-extend.md) 场景发起开票权限认证；此时若不存在可复用的当前开票任务，则由用户补齐 `uscc`、`areaCode`、`personalAccount` 后再执行。
26. 开票权限认证统一通过 `.\bin\windows-amd64\invoice-assistant_windows_amd64.exe issue-auth-workflow --action start|verify --pretty` 执行；二进制命令必须把二维码阶段与校验阶段分别写入本地 Markdown 文件，并将 Markdown 路径与原文写回当前开票任务 JSON 的 `issue_auth_result`，由 Agent 读取相应 Markdown 原样与用户沟通。
27. 若本次开票请求来源于图片或文件，编排层必须先把文件提取结果整理为可读的文字版开票内容并据此生成 input JSON；若文字化结果仍无法支撑无歧义映射，必须停留在补充信息阶段，不得直接调用检查命令或正式开票命令。

## 分支与异常处理

### 成功分支

- 条件：参数完整，商品编码已由脚本补全或用户明确提供，用户已确认，且底层接口返回 `code=0` 且 `data.status=1`。
- 动作：输出开票成功摘要、发票流水号、PDF 附件信息。

### 等待分支

- 条件：缺少参数、脚本自动赋码后仍缺少商品编码、图片/文件提取后仍缺少关键字段或存在歧义、待用户确认预览、或接口返回处理中状态。
- 动作：输出当前待办事项或处理中状态，并告知用户下一步操作；若问题来自图片/文件提取不完整，应明确提示用户补充文字版关键信息，必要时建议直接改用文字输入。

### 失败分支

- 条件：参数校验失败、商品赋码失败、金额关系不一致、用户输入转 input JSON 阶段仍无法确定煤炭种类代码、煤炭类商品单位缺失或不合法、底层接口返回失败。
- 动作：停止流程，输出失败原因、失败节点与可执行修正建议。

### 权限认证分支（开票权限不足）

- 条件：开票失败原因包含“请先扫码验证获取开票权限”。
- 动作：提示用户需进行人脸验证以延长开票权限；用户确认后，立即转入 [invoice-issue-auth-extend](invoice-issue-auth-extend.md) 场景执行二维码获取、扫码状态确认与认证状态查询。
