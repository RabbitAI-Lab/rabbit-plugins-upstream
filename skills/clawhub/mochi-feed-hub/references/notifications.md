# Host scheduling and delivery

These scripts keep state and queues; Python by itself does not create a timer. For a user-requested recurring reminder, use the installed OpenClaw scheduler, inspect its current help, and create a job for THIS agent/workspace and the requested chat/account only. Get the timezone, frequency and recipient from the user's request; ask only for missing details. Verify the returned job ID and next run. Never reuse another agent's mailbox credentials or destination.

The job runs poll (email: sync) with the same private profile and workspace. If there are no pending notices, finish quietly. Deliver pending notices through the host's configured messaging tool. After each successful delivery, call ack with only its noticeId. If delivery fails, leave it pending. Maintain the noticeId in the host delivery ledger to avoid duplicate delivery after a retry; this is at-least-once delivery, not a cross-service transaction. Never acknowledge before sending. Manual tests should create a near-term sample and confirm the actual received message before describing alerts as working.

For a scheduler running as a service, configure the credential environment for that service account, not just an interactive shell. Profile/token files must be accessible only to that user; do not place secrets directly in cron prompts. Use a single scheduled polling job per mailbox/feed/rule set; avoid overlapping jobs. Scripts preserve pending notices across process restarts. See the host's official scheduling guide: https://docs.openclaw.ai/automation/cron-jobs .
