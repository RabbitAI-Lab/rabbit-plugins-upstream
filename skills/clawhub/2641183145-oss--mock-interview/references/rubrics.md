# 评分标准

5 个维度,每维 1-5 分整数。打分时**必须引用用户原话**当证据 —— 不能引用的分数就是编的。

给分偏严:3 分是"能过但不出彩",不是"还不错"。5 分要罕见。

---

## Substance 实质(证据质量)

| 分 | 标准 | 例 |
|---|---|---|
| 1 | 空泛断言,零证据 | "我协作能力很强" |
| 2 | 模糊主张,支撑很弱 | "我优化了流程,大家反馈不错" |
| 3 | 有具体动作,但没量化 | "我重构了缓存层,查询变快了" |
| 4 | 有量化和上下文,但没讲清备选方案 | "重构缓存层,p99 从 800ms 降到 120ms" |
| 5 | 量化 + 权衡过备选 + 讲清决策依据 + 结果可验证 | "测了本地缓存、Redis、多级缓存三种。选 Redis 是因为订单服务有 4 个实例,本地缓存一致性搞不定。p99 800→120ms,压测 5000 QPS 验证过" |

**卡在 1-2 分的根因:**
- 没做反思功课 —— 知道发生了什么,但没提取出什么是重要的
- 回避冲突 —— 把张力、风险、难度全抹掉了,证据也跟着消失
- 冒名顶替感 —— 觉得功劳不该算自己的,主动缩小真实影响

**卡在 3 分的根因:**
- "差不多就行" —— 有细节但停在量化之前,觉得报数字像吹牛
- 没想过备选方案 —— 知道自己做了什么,不知道为什么不选别的
- 缺"所以呢" —— 有证据,但没接到业务影响上

---

## Structure 结构(叙述清晰度)

| 分 | 标准 |
|---|---|
| 1 | 意识流,没有落点,听的人跟丢了 |
| 2 | 埋结论,绕到最后才说清重点 |
| 3 | 结构在,但段落之间生硬,STAR 打得机械 |
| 4 | 结构完整流畅,有一两处小跑题 |
| 5 | 铺垫 → 冲突 → 解决 → 影响,每句都在推进,收尾有明确落点 |

**卡在 1-2 分的根因:**
- 叙事囤积 —— 什么都想塞进一个回答,怕漏掉重要的
- 没有故事结构的心理模型 —— 从没被教过按"铺垫→冲突→解决→影响"组织
- 焦虑驱动的意识流 —— 紧张把原本想好的结构冲散了

**卡在 3 分的根因:**
- 知道 STAR 但套得机械,过渡是硬拼的
- 没在不同时长下练过 —— 能讲 3 分钟版,压不到 1 分钟

---

## Relevance 相关性(是否答在点上)

| 分 | 标准 |
|---|---|
| 1 | 答的完全是另一个问题,或背了一段无关的准备好的料 |
| 2 | 沾边,但没回应问题真正问的那个点 |
| 3 | 答了,但要听的人自己去连"所以这回答了什么" |
| 4 | 直接回应了问题,覆盖了主要考察点 |
| 5 | 命中问题背后真正想考的东西,并且主动补上了面试官下一句会追问的部分 |

**卡在 1-2 分的根因:**
- 只听关键词就往准备好的故事上挂 —— 听到"团队"就背协作故事,没听清问的是冲突
- 没有可用的素材,只能拿手头有的硬套
- 没解码问题 —— 不知道"讲一次失败"考的是反思能力,不是失败本身

**卡在 3 分的根因:**
- 素材对,但没做最后那步"所以这说明我具备什么"
- 埋了正确答案,但没显式说出来

---

## Credibility 可信度(是否经得起追问)

| 分 | 标准 |
|---|---|
| 1 | 有明显夸大或前后矛盾,一追就穿 |
| 2 | 只有结论没有过程,像背的,细节一问就空 |
| 3 | 基本可信,但个人贡献和团队贡献混着说 |
| 4 | 细节扎实,贡献边界清楚,承认了局限 |
| 5 | 主动交代了权衡的代价和做得不够的地方,反而更可信;技术细节经得起深挖 |

**卡在 1-2 分的根因:**
- 简历注水,自己也讲不出细节
- 把"团队做的"说成"我做的",一问具体实现就露
- 只准备了成功叙事,没准备"哪里做得不好"

**卡在 3 分的根因:**
- 习惯说"我们",没意识到面试官需要知道你一个人做了什么
- 不敢承认局限,怕暴露弱点 —— 实际效果相反

---

## Differentiation 差异化(是否只有你能给出这个回答)

| 分 | 标准 |
|---|---|
| 1 | 换任何一个同岗位候选人都能说出一样的话 |
| 2 | 有个人经历,但讲法完全模板化 |
| 3 | 有独特细节,但没提炼成"我的判断" |
| 4 | 呈现了别人不会有的视角或经验教训 |
| 5 | 有"挣来的秘密" —— 只有真正做过这件事的人才会知道的洞察 |

> **挣来的秘密(earned secret):** 亲手做过才会知道、外人看文档看不出来的东西。比如"文档说这个接口幂等,但并发下补偿逻辑会重复触发,我们踩了才知道"。这是最强的可信度和差异化信号,评分和出题都优先抓它。

**卡在 1-2 分的根因:**
- 以为面试要的是"标准答案",主动把自己的判断抹平
- 有独特经历但觉得"这没什么好说的"
- 从没被问过"你的看法是什么",不习惯给判断

**卡在 3 分的根因:**
- 细节有了,但停在"做了什么",没走到"我因此认为什么"
- 没识别出自己手里的挣来的秘密

---

## 出分

- `per_question.scores` — 每题 5 维,整数
- `overall` — 各维跨题均值,一位小数
- **`bottleneck` 只报一个**:取均值最低的维度。并列时取"根因更可操作"的那个(Substance / Differentiation 优先于 Relevance)

---

# 写点评(重点)

分数只是索引,**用户真正要看的是点评**。一句"你没有量化"没用 —— 他不知道该在哪句话后面加什么数字。

每道题的点评要包含四块:**好在哪、差在哪、怎么改写、下次怎么做**。全部**引用用户原话**。

## 1. strengths — 好在哪(1-2 条)

每条给 `quote` + `why`:

```json
"strengths": [
  {
    "quote": "测了本地缓存、Redis、多级缓存三种方案",
    "why": "这句直接把 Substance 从 3 分拉到 4 分 —— 面试官要的就是「你知道还有别的路」。多数候选人只说自己最后做了什么,不说排除过什么。"
  }
]
```

`quote` **必须是原话片段**,能在 `answers[].text` 里搜到。不要改写、不要润色。

`why` 要说清**这句话为什么值钱**,而不是"很好,继续保持"。哪怕整题很差也要找出一条 —— 全是批评的报告用户看不完。

## 2. weaknesses — 差在哪(1-3 条)

每条给 `quote` + `problem` + `dimension`:

```json
"weaknesses": [
  {
    "quote": "效果挺明显的,查询快了很多",
    "problem": "「快了很多」是感受,不是证据。面试官下一句一定问「多少」,你如果当场答不上来,他会怀疑前面说的数字也是估的。这句话把你自己架到了一个需要临场编数字的位置。",
    "dimension": "substance"
  }
]
```

`problem` 不要只说"缺量化",要说清**这个毛病会导致什么后果** —— 面试官会怎么想、下一句会怎么追、为什么这么答对你不利。这是用户改变行为的动力来源。

引用**最该改的那一句**,不要引一整段。

## 3. rewrite — 改写示范(每题一个)

**这块最有用,不能省。** 挑用户最该改的一句,写出改后的版本:

```json
"rewrite": {
  "before": "效果挺明显的,查询快了很多",
  "after": "p99 从 800ms 降到 120ms,压测 5000 QPS 打了十分钟,上线后又跟了一周真实流量确认没回弹。",
  "what_changed": "把「很多」换成了具体数字,并补上了口径(压测环境 + 时长 + 线上验证)。数字本身不重要,重要的是你**知道自己在用什么方式衡量** —— 这才是面试官在 Substance 上真正想看的。"
}
```

`after` 里的事实**只能用用户自己说过的**。他没提过压测,就不能替他编一个 —— 这种情况写成占位:"p99 从 ___ 降到 ___(填你实际的数字)",并在 `what_changed` 里说明"这个数你应该记住,面试前查出来"。

## 4. fix — 下次怎么做(2-3 句)

不是"注意量化"这种废话。要给**可执行的动作**:

> 面试前把这个项目的三个数字写在纸上背下来:改造前的 p99、改造后的 p99、压测的 QPS。答这类题时先说数字再说做法 —— 你现在的顺序是先铺垫再给结论,面试官在你铺垫的时候就已经在怀疑有没有数据了。

## 5. summary — 全局总结(顶层,3-5 句)

五道题看完的整体判断。要有**跨题的观察**,这是逐题点评给不了的:

> 你五道题里有三道都在同一个地方掉分:讲得清「做了什么」,讲不清「为什么这么选」。q1 的方案权衡是唯一一次例外,那题也是你分数最高的 —— 说明你不是不会,是没意识到面试官在等这个。另外你的语音回答(q1/q3/q5)平均比打字长 40%,但结构分反而低 0.7 —— 说话时容易顺着想到的往下说,建议开口前先在心里定三段。

有 `input_mode` / `duration_sec` 数据时,**跨题对比语音和打字的差异** —— 这是这个系统独有的观察,别的模拟面试给不了。

## 6. bottleneck — 短板(顶层,只一个)

除了 `root_cause`,还要给:

- `evidence_across_questions` — 至少两道题的原话引用,证明这不是偶然
- `improvement_plan` — **3 步**,每步是具体动作,不是"多练"

```json
"bottleneck": {
  "dimension": "differentiation",
  "root_cause": "你五道题都停在「我做了什么」,没有一道走到「我因此认为什么」。q5 那个「已支付又变回待支付」其实是挣来的秘密 —— 只有真踩过的人才说得出,但你把它当现象描述,而不是当洞察端出来。",
  "evidence_across_questions": [
    { "qid": "q2", "quote": "5000 QPS 打了十分钟,用 wrk", "note": "口径清楚,但任何做过压测的人都会这么答" },
    { "qid": "q5", "quote": "已支付又变回待支付", "note": "这是你手里最强的差异化素材,却只用了半句话" }
  ],
  "improvement_plan": [
    "把 q5 那个时序问题写成完整的三句话:现象、根因、你因此形成的判断。这是你目前最有价值的素材,现在被浪费了。",
    "回去翻这两段实习,找出三个「文档上不会写、只有做过才知道」的点,每个写成两句话备用。",
    "下次答题时,每道题结尾加一句「我从这件事上得出的判断是……」。先刻意加,习惯了再自然去掉。"
  ]
}
```

## 硬约束

**只用用户实际说过的话。** 用户没提的经历不能拿来扣分,也不能替他补充。所有 `quote` 必须能在 `answers[].text` 里搜到。

**给分要有区分度。** 五题全 3 分的报告没有信息量。确实差别不大时,也要在点评里指出相对强弱。

**每题至少一条 strength。** 哪怕整题 2 分,也要找出一句相对好的。

**`rewrite.after` 不许编事实。** 用户没给的数字用 `___(填你实际的数字)` 占位。

**别写"多练习""注意结构"这类空话。** 每一条建议都要能在下次面试里被执行。
