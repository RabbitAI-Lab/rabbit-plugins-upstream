# H 框架详解（通用骨架）

> 本文件是**逻辑层**的静态参考，通篇通用，不含任何具体框架名。

## 一、总定义

- **Agent = 模型 + Harness**。
- **Harness = 六层功能 + 架构范式 P**。

六层功能：E 执行循环、T 工具注册、C 上下文管理、S 状态存储、L 生命周期钩子、V 评估接口。
P：架构范式，指这个 Harness 以什么风格组织起来。

## 二、六层详解

### E 执行循环（Execution Loop）

管"任务怎么拆、怎么跑、怎么停"。内部构成三块：

| 模块 | 职责 |
|---|---|
| 策略选择器 | 看任务类型，决定用哪种执行方式 |
| 策略库 | 装着可用的执行模式 |
| 运行时引擎 | 真正跑起来，管轮次上限、Token 预算、什么时候停 |

**通用设计问题**：终止条件谁说了算？如何防止跑飞？任务结构清晰时用静态模式还是动态脚本？

### T 工具注册（Tool Registration）

管"Agent 能用什么、怎么用"。

**通用设计问题**：工具如何接入？接口是否标准化？是否按需筛选子集（而不是全量暴露）？

### C 上下文管理（Context Management）

管"什么信息进模型窗口"。

**通用设计问题**：窗口预算多少？用多少比例后质量开始下降？何时 reset / 摘要？如何让 Agent 尽量留在干净上下文里？

### S 状态存储（State Storage）

管"跨轮次持久化与恢复"。

**通用设计问题**：存什么结构（JSON/KV/数据库）？写操作要不要经过治理（Agent 不能直接篡改）？失败后如何重新加载状态（可审计、可恢复）？

### L 生命周期钩子（Lifecycle Hooks）

pre-invocation / post-invocation 的拦截点。

**通用设计问题**：哪些动作需要拦截（鉴权、审计、策略执行、安全监控）？拦截点能不能被 Agent 绕过或修改？（"安检门"不能被绕过）

### V 评估接口（Evaluation Interface）

管"你怎么知道做对了"。

**通用设计问题**：谁独立验证？Agent 说"成功"算不算数？用什么客观手段验证？

## 三、策略库里的执行模式

### ① 六种静态模式（直接使用）

1. **分类与执行** —— 先判断类型，再路由给对应处理。
2. **分叉与综合** —— 拆成多个子任务并行跑，最后合并结果。
3. **对抗性验证** —— 派一个专门挑错的 Agent 去审核结果。
4. **生成与过滤** —— 批量出方案，再筛选打分。
5. **锦标赛** —— 多个 Agent 竞争同一任务，两两 PK 选最优。
6. **循环直到完成** —— 不设固定轮数，跑到条件满足为止。

### ② 动态脚本模式（临时写）

任务结构不清晰时，主 Agent 自己写一段编排脚本，交给运行时执行。脚本可用三个基础命令：

1. 派一个子 Agent 去干活。
2. 并行派多个子 Agent，等全部做完再继续。
3. 串行流水线，一步接一步处理。

## 四、终止条件怎么定

不管用哪种模式，最后能不能停，由 **V（评估接口）** 说了算——"我说做完了不算，Harness 验证通过才算"。

同时设两道保险：**最大轮数上限 + Token 预算上限**，防止跑飞。

## 五、架构范式 P（开放决策，非封闭枚举）

P 是**开放的、多维的**架构决策集，至少含以下正交子维度（可扩展）：

| 子维度 | 两端 | 说明 |
|---|---|---|
| 扩展方式 | 插件化 ↔ 嵌入式 | 能力是否可随意增删替换 |
| 配置方式 | 声明式 ↔ 命令式 | 用配置描述，还是写代码 |
| 部署拓扑 | 单机 ↔ 分布式 | 子 Agent 是否可派到远程 |
| 编排模式 | 中心化 ↔ 去中心化 | 谁在调度 |

**范式 P 如何影响 E 层**：

- 插件化 → 执行模式可随意增删替换，甚至可发明新模式。
- 嵌入式 → E 层固定成一两种模式，用户只能调参数、不能改结构。
- 声明式 → 用户写一份描述任务流程的配置，E 层照着执行。
- 分布式 → 子 Agent 可派到远程机器，状态跨节点同步。

> 重要提醒：这四个子维度只是**常见参考样例**，标注"非完备、可自定义"。真正的架构区分度（如"无特权内核"这类深度）不在标签能表达的范围内，需在设计中通过追问挖掘出来。

## 六、范式全空间选择判据（第一性原理，先于案例类比）

> **为什么要有这一节**：知识库案例并非均匀覆盖 P 的每个象限（现有案例偏「插件化 + 中心化」）。**范式选型必须从下面的判据出发，案例只作"选定后的对照印证"，不能反过来用"案例长什么样"决定选型**——否则会把案例库的偏见当成架构真理。每条选型都要在设计文档里写出"为什么选这端、对端为什么被否"。

**① 扩展方式：插件化 ↔ 嵌入式**
- 选**插件化**：确有"第三方/用户要自由增删替换能力"的真实需求；能力集开放且持续增长；要做生态/市场；团队扛得住"薄内核 + 能力注入 + 可逆注册"的复杂度（见 `pattern-dependency-injection`、`pattern-reversible-computation` 的代价）。
- 选**嵌入式**：工具/能力集小且稳定；追求极简、可一眼看懂、低维护（`mini-swe-agent` 的立场：约 100 行、只有 bash）；内部/一次性工具；没有"随便加插件"的需求。
- **默认倾向**：从嵌入式起步，等出现**真实**可扩展需求再演进到插件化（YAGNI）。"能插件化"≠"该插件化"。

**② 配置方式：声明式 ↔ 命令式**
- 选**声明式**：流程可预先描述、要可 diff/版本化/审计、非开发者也要能配、需覆盖默认行为而不 fork 源码。
- 选**命令式**：行为高度动态、每次逻辑都不同、配置 DSL 会比写代码更难；原型期。
- **代价提醒**：声明式有表达力天花板——复杂逻辑塞不进配置会逼出"配置里的图灵完备 DSL"，反而更难维护（见 `pattern-declarative-configuration` 的"何时不用"）。

**③ 部署拓扑：单机 ↔ 分布式**
- 选**单机**：单用户/单任务、状态规模可控、无横向扩展需求。**绝大多数场景先单机。**
- 选**分布式**：需横向扩展、跨节点派子代理、多租户隔离、高可用。
- **代价提醒**：分布式 = 网络分区 / 一致性 / 可观测 / 部署复杂度骤增。不要为"还不存在的规模"提前分布式。

**④ 编排模式：中心化 ↔ 去中心化**
- 选**中心化**：有一个 lead/控制器统一调度（Claude Code、Codex、多数 harness）；流程能被单一协调者掌握；调试与一致性更容易。
- 选**去中心化/对等**：多个自治 agent 点对点协作、无单点调度；适合信任域/地理分散、各自独立演化与容错（`pattern-actor-model`）。
- **诚实约束**：去中心化在本库**无 verified runtime 案例**（见 `framework-inbox.md`），主流方案（AutoGen 分布式 actor、Fetch.ai uAgents）多为**库层**、按概念边界被排除。命中该象限时**从第一性原理 + actor-model 推演**，并在设计文档显式标注"无成熟 harness 案例背书"。
- **代价提醒**：去中心化 = 最终一致、调试难、无全局视图、消息时序坑（见 `pattern-actor-model` 的"何时不用"）。

## 七、症状 → 处方决策矩阵（快速三角定位）

> 用法：拿用户需求的**信号**去下面的表里定位，得到"优先考虑的处方 + 反过度设计警示"。**每条处方都要回到对应 pattern 的"何时不用/代价"再过一遍**，确认不是无脑套用。矩阵是起点，不是结论。

| 症状 / 问题信号 | 层 | 优先考虑的处方 | 反过度设计警示 |
|---|---|---|---|
| 任务结构固定、步骤可枚举 | E | 静态执行模式 / 声明式流程配置 | 别给固定管线套动态编排或状态机 |
| 任务开放、需试错探索 | E | 循环直到完成 + 动态脚本编排 | 别把不可枚举的流程硬塞进预定义图 |
| 工具集小且稳定 | T | 固定少量工具 / 单通用工具（mini-swe-agent 单 bash） | 别为"不会来的第三方"建插件市场 |
| 能力需第三方自由增删 | T/P | 插件化 + 依赖注入（可逆注册） | 先确认"真要插"，否则走嵌入式 |
| 需审计 / 回放 / 时移 / fork | S/V | 事件溯源（append-only，`pattern-event-sourcing`） | 无此需求别上：回放慢、存储涨、schema 演化难 |
| 多轮 / 跨会话记忆 | S | 落库的记忆分层（Letta 式 core/archival/recall） | 内存态 = 单次请求，撑不起多轮追问 |
| 长上下文逼近窗口 | C | 分层 + 压缩/分页（MemGPT 式）或子代理隔离 | 阈值必须绑定度量空间（cosine/l2/ip），换 embedding 要重标定 |
| 子任务会污染主上下文 | E/C | subagent 隔离（Claude Code） | 隔离边界要划清，也别过度拆分 |
| 面向真实用户 / 高危操作 | L | 确定性 hook 拦截 + 鉴权协议（JWT/SSO/OIDC）+ 纵深防御 | 用真实 API 挂载、别虚构；别只写一句"校验身份" |
| 外部输入 / 被注入风险 | L/T | 结构层强制最小权限（OpenClaw Reader/Actor）+ 严格 schema 通信 | prompt 提示挡不住注入，要结构兜底 |
| 需被外部程序嵌入 | P/E | 协议化运行时（Codex app-server，turn 生命周期归属清楚） | 想清楚：被命令行驱动还是被协议驱动 |
| 无 ground truth 的主观任务 | V | 只评客观可验部分，其余如实标未知区 | 别让模型给自己判卷（循环论证）；别假装能自动评分 |
| "做完了"谁说了算 | E/V | 由 V（确定性校验）定终止，加轮数 + token 双保险 | 防跑飞三道：轮数上限 + token 预算 + 每节点超时 |
| 要极简 / 可维护 / 少黑盒 | P | 嵌入式单循环（mini-swe-agent） | 抵制"复杂 = 高级"的冲动 |
