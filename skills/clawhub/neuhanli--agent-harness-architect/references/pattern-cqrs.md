## 核心思想

把"写"（命令，改变状态）和"读"（查询，读取状态）分成两条路径、两套模型。写路径保证一致性，读路径为查询优化，各自独立演化。

## 可迁移到 harness 的哪一层

S（状态存储）、V（评估）

## 典型应用案例

Hermes Agent 的自修复验证（执行路径与校验路径分离）；多数 harness 的"执行日志（写）"与"评估/回放（读）"天然分离。

## 何时不用 / 代价（架构师的克制）

- **代价**：读写两套模型 → 引入最终一致性（读模型可能滞后）、双份存储与同步管道、运维复杂度上升；小系统里是明显的过度工程。
- **何时不用**：读写模型本就一致且不复杂；不需要读侧独立扩展或独立数据源；要求"读到刚写入"的强一致读。

## 对照问题（抛给用户，而非答案）

你的"执行"和"验证/评估"是同一套路径还是分离的？如果评估需要独立的、不被执行污染的数据源，读写分离能带来什么？
