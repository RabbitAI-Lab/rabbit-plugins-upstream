# 网站迁移助手（Website Migration Orchestrator）

本 Skill 是一条**端到端整站迁移流水线编排器**：它以一个**强制前置「阶段 0 · 依赖安装与自检」**开场（先按 §1.1 装好 3 个依赖 skill 并输出《依赖安装清单》），随后把一次完整的「老站 → 新站」迁移拆成 19 个有序阶段。**所有对目标站（新站）的写操作（基础数据迁移、新网站生成、上线）都必须在依赖就绪 + 目标站 MCP 连接确认之后进行**（即「依赖 skill 与 MCP 必须放在新网站生成之前处理」）。读老站的阶段（网站地图 → 内容结构化）只做分析、不触碰新站，复用建站助手 / SEO / GEO 三个专家 skill 完成生成与体检。

> 设计原则：先**盘点老站**（网站地图 / 页面 / 栏目 / 产品 / 新闻 / 图片 / 表单 / SEO），再**结构化**成迁移规格，然后**生成新站**并**承接 SEO 权重**（URL Mapping + 301），最后**体检**（SEO / GEO）与**上线**。迁移的核心目标是「内容不丢、权重不降」。

## 0. 触发场景

- 用户说"搬站""迁移""把老站迁到新站""整站搬家""保留 SEO 权重迁移"。
- 用户直接给出下方 §4 的迁移流水线。
- 用户手里有一个老站（任意平台），想要一套在新站点上、内容对齐且 SEO 权重承接的新站。

### 2.1 版权合规确认（原样迁移 / 1:1 复制模式强制，开工前门禁）

> **风险提示**：1:1 复制（复刻）老站 UI 涉及对网页 HTML/CSS、图片、字体、商标、文案等作品的复制，可能触发第三方版权 / 商标侵权风险。**本 skill 仅在用户明确作出权利声明与免责承诺后，方可执行原样迁移的抓取与复制动作。**

- **触发条件**：《迁移需求收集表单》「迁移方式」= **原样迁移（1:1 复制 UI）** 时，必须呈现本声明表单并经用户确认（第 3 项外包提示亦必读）；「重新设计」模式虽不复制 UI，但仍需用户对其迁移的内容（产品 / 新闻 / 文案）拥有合法权利，故同样建议展示、但不强制作为冻结门禁。
- **呈现方式**：通过《版权合规确认表单》（字段定义见 `references/migration-templates.md` §13.5）一次性收集，含 4 个声明项，均为「必读 + 勾选确认」：
  1. **权利承诺（必勾，硬性门禁）**：用户勾选承诺——本人是**网页全部著作权、素材、商标的合法权利人，有权授权本工具复刻，不存在第三方版权**。
  2. **免责提示（必读确认）**：工具仅提供技术能力，**版权真实性由用户自行承担，用户承诺承担全部侵权赔偿责任**。
  3. **外包合同提示（必读确认）**：如网页系外包制作，用户须自行确认外包合同是否已把网页著作权**完整转让**给站长；未确认转让前，不得据第 1 项主张权利承诺（表单应回退要求先澄清，或改走「重新设计」模式）。
  4. **投诉冻结授权（必读确认）**：用户知悉并接受——收到第三方版权投诉后，本工具将**立即冻结该站点的复制（复刻）能力**，直至权利争议澄清。
- **表单逻辑**：第 1 项（权利承诺）为硬性门禁，未勾选不得进入阶段 2 抓取与任何复制动作；第 3 项若用户选择「网页系外包制作且未确认转让」，应回退表单要求先澄清，或改走「重新设计」模式。
- **硬约束**：原样迁移模式未通过《版权合规确认表单》前，**不得进入阶段 2 抓取 / 阶段 13 复制生成**；若阶段 2 抓取已完成但声明缺失，暂停并补全声明后再继续。

### 2.2 源站所有权验证（所有迁移模式强制，开工前门禁）

> **安全原则**：在执行任何**源站（老站）数据读取、快照、解析、内容搬运**操作之前，必须先证明调用方对该源域名拥有合法控制权，防止误迁、劫持他人站点或越权抓取。核心机制：**下发随机令牌 → 用户在源站控制权层面证明持有 → Skill 自动核对**。具体验证逻辑（生成令牌 / 三种方式流程 / 超时退避 / 清洁化）详见 `references/source-site-ownership-verification.md`。

- **触发条件**：无论「原样迁移」还是「重新设计」，只要进入阶段 2 对老站做读取 / 抓取 / 解析，都**必须先通过源站所有权验证**。这是**全网关注门禁**，不区分迁移方式，位于版权合规确认（§2.1）之后、网站地图（阶段 2）之前。
- **呈现与流程**（通过《源站所有权验证表单》，字段定义见 references §13.6）：
  1. **生成令牌**：Skill 生成密码学安全的随机 `verify_token`（绑定本次迁移任务，有过期窗口 24–72 小时，禁止复用固定密钥；全程可审计，记录方式 / token 摘要 / 时间戳 / 结果）。
  2. **选择验证方式**（表单单选，默认推荐 DNS TXT）：
     - **方式一 DNS TXT 记录验证（推荐首选）**：在源域名 DNS 添加平台生成的唯一 TXT 记录，Skill 经公共 DNS 查询比对；不依赖源站 Web 在线，抗篡改性强，最适合自动化。
     - **方式二 根目录验证文件（HTTP 文件校验，备选）**：在源站网站根目录放置 `migrate-verify-<token>.txt`，Skill 经 HTTP GET 比对（仅用 HTTP，不校验证书），适合有服务器 / 主机权限、无 DNS 权限者。
     - **方式三 HTML Meta 标签验证（兜底）**：在源站首页 `<head>` 插入 `<meta name="site-migrate-verify" content="<token>">`，Skill 抓取解析校验；可靠性最低，仅作兜底。
  3. **下发操作说明**：按所选方式给用户清晰、可照做的放置步骤（TXT 记录内容 / 文件路径与内容 / meta 标签写法），引用 `references/source-site-ownership-verification.md` 对应章节。
  4. **等待用户明确告知"已准备好"**：展示说明后**暂停校验流程，不主动发起任何轮询 / 请求**；必须等用户在《源站所有权验证表单》勾选"我已按说明放置好验证材料，可以开始验证"并提交后，Skill 才启动相应校验。未收到该确认前，绝不发起任何校验请求。
  5. **启动校验**（按所选方式核对 token）：
     - DNS TXT：轮询公共 DNS（建议间隔 30s，总超时 30–60 分钟），命中匹配 token 即通过；超时提示重试或换方式。
     - 文件：请求 `http://<domain>/migrate-verify-<token>.txt`（仅 HTTP，不校验证书），比对响应体一致即通过。
     - Meta：抓取首页解析 meta `content`，一致即通过。
  6. **结果处理**：
     - 通过 → 记录 `ownership_verified=true` + 时间戳 + 验证方式 + `verify_token` 摘要，写入审计日志；并**在后续迁移执行前（阶段 12 / 13 写前）轻量复检** token 仍有效（防验证后域名被转交）。
     - 失败 / 超时 → 提示用户重试（重放说明）或**更换验证方式**；**不得进入阶段 2 及任何源站读取动作**，直至通过。
- **硬约束**：源站所有权验证未通过前，**不得执行任何老站读取 / 抓取 / 解析 / 快照动作**（阶段 2–10 全部受阻）；验证通过后，提示用户在搬迁完成后清理 TXT 记录 / 验证文件 / Meta 标签。

## 3. 迁移策略摘要（Discovery，最早产出，反复引用）

无论用户给多少资料，先落盘一份 **《迁移策略摘要》**（300 字内），作为后续识别与生成依据：

1. **迁移目标**：[原样迁移(1:1复制) / 重新设计]？核心 KPI（内容零丢失、SEO 权重零流失、关键转化路径不中断）。
2. **老站画像**：行业、核心业务、规模（页面数 / 产品数 / 新闻数）、语言、目标市场。
3. **内容与权重边界**：必须保留的页面 / 产品 / 新闻 / 表单；可合并或丢弃的；必须做 301 承接的高权重 URL 清单。
4. **新站落地约束**：目标平台、视觉调性、信息架构是否重构、公共头尾策略。

模板见 `references/migration-templates.md`。

### 阶段 0 · 依赖安装与自检（强制前置，最先执行）
- **目的**：确保本 skill 依赖的 3 个外部 skill 已安装并可被调用，避免后续阶段因依赖缺失而中断或误用未安装名。
- **动作**：严格按 §1.1 依赖安装协议，依次确认 / 安装 `DEP_JIANZHAN` / `DEP_SEO` / `DEP_GEO` 三个依赖；已可用则跳过安装、仅做校验与登记（幂等）。
- **产出**：《依赖安装清单》（角色 → 调用名 → 状态 → 来源），作为后续所有 `Skill` 调用的唯一依据。
- **硬约束**：《依赖安装清单》未产出前，不得进入阶段 1 及任何调用外部 skill 的阶段。

### 阶段 1 · 老网站
- **目的**：锁定迁移对象（内容来源），拿到可分析的真实材料。
- **动作**：记录老站 URL（来自《迁移需求收集表单》）作为内容来源与抓取入口。老站所有内容均通过逐 URL 抓取获取，无需询问可访问性或要求另提供导出包 / 材料。列出已知要保留的页面、产品、新闻、表单、高权重 URL。明确老站**不经本 skill MCP 改写**，仅作分析与内容来源。

### 阶段 2 · 网站地图（sitemap）
- **目的**：拿到老站全量 URL 清单，作为后续识别与 URL Mapping 的基底；原样迁移时同时抓取每页渲染 HTML + CSS 作为 1:1 复制基准。
- **动作**：
  - 优先读取老站 `sitemap.xml`（含子 sitemap）；无 sitemap 则用爬虫 BFS 枚举（遵守 robots.txt，相邻请求间隔 ≥2 秒，不抓登录后/隐私内容），或基于用户提供的导出包枚举。输出《老站 URL 清单》（URL / 状态码 / 类型推测 / 大致内容体积）。
  - **原样迁移模式（1:1 复制，强制）**：对《老站 URL 清单》逐页，调用浏览器自动化能力（Playwright / agent-browser 等当前环境可用工具）抓取**渲染后的完整 HTML 源码 + 页面关联的全部 CSS + 页面关联的全部 JS交互代码**（内联 `<style>`、`<link>` 外链样式表、关键背景图 / 字体、内联及外链`<script>`），按页存为源文件包（每页一份，含渲染 HTML 源码 + 关联全部 CSS + 关联全部 JS 交互代码 + 资源引用）。这是后续阶段 13（新网站生成）1:1 还原 UI 时的唯一基准；抓取遵守 robots.txt、不抓登录后/隐私内容、相邻请求间隔 ≥2 秒。
- **产出**：《老站 URL 清单》+ 抓取 manifest（供阶段 9 SEO、阶段 14 URL Mapping 复用）；原样迁移额外产出《老站页面源文件包》（HTML+CSS+JS，供阶段 3 / 10 / 13（新网站生成）1:1 复制参考）。

### 阶段 3 · 页面识别
- **目的**：把 URL 清单逐页归类，明确"有哪些页面、各是什么类型"。
- **动作**：对《老站 URL 清单》逐页识别页面类型：首页 / 关于我们 / 产品列表 / 产品详情 / 新闻列表 / 新闻详情 / 联系我们 / 表单页 / 单页落地 / 其他。结合 URL 模式、标题、内容结构判定。输出《页面识别表》（URL → 类型 → 关键内容摘要 → 是否保留）。模板见 `references/migration-templates.md`。

### 阶段 4 · 栏目识别
- **目的**：还原老站信息架构（导航 / 栏目 / 分类），确定新站栏目骨架。
- **动作**：从导航、面包屑、URL 路径、sitemap 分组识别栏目（一级 / 二级 / 详情体系）。重新设计时据此设计新 IA；原样迁移时尽量 1:1 对齐。输出《栏目识别表》（老栏目 → 新栏目 / 分类映射 → 归属页面）。模板见 `references/migration-templates.md`。

### 阶段 5 · 产品识别
- **目的**：抽取老站全部产品，作为新站产品库入库依据。
- **动作**：从产品列表 / 详情页 / 结构化数据（Product schema）抽取产品：名称、型号、描述、参数、价格（如有）、主图、分类、SEO 字段（SeoTitle/Desc/Keyword）。记录老 URL 以便 301。输出《产品识别表》（老产品 URL → 字段 → 新分类归属）。模板见 `references/migration-templates.md`。

### 阶段 6 · 新闻识别
- **目的**：抽取老站全部新闻 / 文章，作为新站文章库入库依据。
- **动作**：从新闻列表 / 详情页抽取：标题、正文、作者、发布时间、缩略图、分类、SEO 字段。记录老 URL 以便 301。输出《新闻识别表》（老文章 URL → 字段 → 新分类归属）。模板见 `references/migration-templates.md`。

### 阶段 7 · 静态资产识别（图片 / CSS / JS）
- **目的**：盘点老站全部静态资产（图片、CSS、JS），确定哪些需迁移到新站、归属到哪，形成可执行的统一上传依据；并**跨页按内容去重**，避免同一资产被重复上传或各页引用到不同副本。
- **动作**：扫描各页面 / 产品 / 新闻引用的图片、样式表（CSS）、脚本（JS），**按内容 SHA256 去重**并归属性标注。资产类型与归属：图片（页头页尾 / 产品主图 / 新闻缩略图 / 内容配图 / 背景图 / 字体）、CSS（全局样式 / 页面样式）、JS（公共库 / 页面交互脚本）。标记需下载重传的（外链 / 老平台图床 / 老站域名下的所有图片与 CSS/JS）；记录老 URL、内容 hash、归属。输出《静态资产清单》（老 URL → 内容 hash → 类型 → 归属 → 是否需重传 → 新站相对 URL 占位 → 是否已上传）。**去重规则**：内容 hash 相同的多份引用（如缩放图 `logo-200x200.jpg` 与 `logo.jpg`、带 `?v=` 缓存串的同一文件、`/static/` 与 `/img/` 别名）合并为**一条资产、只传一次**，并跨页记录其全部引用点，供阶段 12 / 13 统一回填到同一新 URL。模板见 `references/migration-templates.md`。
- **硬约束（静态资产上传唯一依据）**：《静态资产清单》是后续所有图片 / CSS / JS 上传与页面资源回填的**唯一依据**——清单中每张标记"需重传"的资产，必须进入阶段 12（图片）/ 阶段 13（CSS/JS）的上传队列并实际上传（**每资产仅传一次**），不得跳过重传、不得"识别完即视为完成"；上传后必须回填真实 URL，并在阶段 13 生成页面时替换 HTML/CSS 中全部对应引用（含 `img src` / `background-image` / `url()` / `<link href>` / `<script src>`）。任何页面渲染不得残留 `old.com` / 老图床 / CDN 域名等老站资源地址。**产品主图（归属=产品主图）按产品逐条保留、不参与跨产品合并**（避免破坏主图随产品的绑定）；logo / 图标 / 全局 CSS / 公共 JS 库等共享资源才走全局去重、一次上传多页复用。

### 阶段 8 · 表单识别
- **目的**：识别老站表单及其字段，决定新站表单方案（复用系统动态表单）。
- **动作**：识别联系 / 询盘 / 自定义表单，记录字段（姓名/电话/邮箱/留言/文件等）、提交方式、是否带校验/验证码。新站优先复用建站助手系统动态表单（`list_custom_form` → 用户选 → `FnGetCustomForm`）；询盘表单只能「修改 / 不动」，不得新建询盘表单（复用系统既有询盘能力）。输出《表单识别表》（老表单 → 类型 → 字段 → 新站方案）。模板见 `references/migration-templates.md`。

### 阶段 9 · SEO 识别（老站 SEO 要素提取）
- **目的**：提取老站 SEO 资产，作为新站 TDK / 结构化数据 / 301 承接依据，避免权重流失。
- **动作**：逐页抽取 TDK（title/description/keywords）、Heading 结构（唯一 H1 / 层级）、canonical、JSON-LD（Organization/Product/Article/BreadcrumbList 等）、内链、robots/sitemap 状态。高权重页（有排名 / 有外链）单独标注，必须进入 301 承接清单。输出《老站 SEO 要素表》+《高权重 URL 承接清单》。模板见 `references/migration-templates.md`。

### 阶段 10 · 内容结构化（产出《迁移内容规格》）
- **目的**：把前 9 阶段识别结果合并成一份可执行的"旧 → 新"迁移规格，作为「新网站生成」的唯一输入。
- **动作**：汇总《页面识别表》《栏目识别表》《产品识别表》《新闻识别表》《静态资产清单》《表单识别表》《老站 SEO 要素表》，生成：
  1. **新站信息架构**（栏目 / 页面树 / URL 规划）；
  2. **数据入库清单**（分类映射、产品入库、新闻入库、图片上传、表单方案）；
  3. **页面生成清单**（每页目标、板块、所需动态数据、TDK 草稿、CTA、JSON-LD 类型）；
  4. **旧 → 新 内容映射总表**（供阶段 14 URL Mapping 直接消费）。
- **产出**：《迁移内容规格》（落盘，作为阶段 12–13 输入）。模板见 `references/migration-templates.md`。

### 阶段 11 · 连接目标站 MCP（写入新站前，必须完成）
- **目的**：在**写入新站之前**，先拿到新站 MCP 凭据，经 MCP 读取目标站点信息并交用户确认「是否操作此站」，确保后续所有写操作都作用在正确的**新站（目标站）**上。本步骤是「依赖 skill 与 MCP 放在新网站生成前处理」要求的落点。
- **动作**（本步骤位于「新网站生成」之前，即写入新站前的站点确认关）：
  1. **呈现《目标站 MCP 信息表单》（见 references §13.2）**：通过表单收集「MCP 完整地址」+「Bearer Token」两项（表单输入框，提交后仅用于 MCP 客户端 `Authorization: Bearer` 头，**不回显、不落文件、不让用户把 Token 打在聊天里**）。若 Agent 已持有该站 MCP 凭据，可预填地址、仅请用户确认 / 重填 Token。表单已含站点标识，无需另问新站信息。
  2. **验证连通性**：经 MCP 调 `test` 验证连通性（遇 `401`/`Unauthorized` 请用户重给 Token，不回显旧 Token）。
  3. **读取并确认站点信息**：用已验证的 MCP 拉取目标站点信息（站点名称 / 页面列表 / 已有页面等），将站点信息**展示给用户确认「是否操作此站？」**；确认是则继续；确认不是则请用户重新提供正确的新站 MCP 信息，再用新凭据 `test` + 复核后继续。
- **注意**：本步骤确立的 MCP 凭据将贯穿 新网站生成 → 上线 全部写操作；本 skill 不得假设或复用其它站点凭据。Token 仅由 MCP 客户端放入 `Authorization: Bearer` 请求头，不回显、不落文件。
- **硬约束**：阶段 11 未获得 MCP 凭据、未读取出站点信息、且未经用户确认「操作此站」前，不得进入阶段 12（基础数据迁移）。

### 阶段 12 · 基础数据迁移 ✅ 调用「建站助手」/MCP（写入新站的"数据底座"，必须在"新网站生成"之前）

- **目的**：在生成页面之前，先用 MCP 把老站的底层业务数据落到新站——公司信息、分类、产品、文章、表单、素材——使后续「新网站生成」阶段生成的页面能直接绑定真实数据。本阶段是"写入新站"的第一步写操作。
- **动作**：**调用《依赖安装清单》登记的 `DEP_JIANZHAN`（建站助手）skill**（`Skill` 工具，`skill=$DEP_JIANZHAN`，调用名以登记为准），复用阶段 11 已确认的 MCP，按以下顺序执行（具体参数 / 工具名以建站助手实际提供为准）：
  1. **基础信息**：`edit_company_info` 保存企业基本信息（名称 / 联系 / 语言）。
  2. **分类映射**：`list_product_class` / `list_news_class` 映射老栏目 → 新分类；缺失经确认后 `add_product_class` / `add_news_class` 建立。
  3. **素材上传（静态资产上传子流程，强制闭环）**：遍历《静态资产清单》（阶段 7）中标记"需重传"的资产，**按内容 hash 唯一项逐条上传（同 hash 只传一次）**，按以下顺序执行，禁止遗漏：
     - 下载源资源（阶段 2 已抓取的源文件包优先；外链资源按原 URL 下载，遵守 robots / 版权声明）。图片用 `upload_file`（内容配图 / 背景图 / 页头页尾图 / 字体等通用素材）或 `upload_product_image`（产品主图，返回 `fileName`+`SmallFileName` 原样传入）；CSS / JS 用 MCP `upload_file` 上传到新站。
     - 取回服务器返回的相对 URL，填入《静态资产清单》该 hash 对应行（及所有同 hash 引用行）的"新站相对 URL（已上传填入）"列（占位 → 真实 URL），并将"是否已上传"标记为是；
     - **回填原则**：产品主图在 `add_product` 时引用返回文件名；页面内容配图 / 背景图 / 头尾图 / CSS / JS 在阶段 13 生成页面时由 HTML/CSS 引用回填后的同一新站相对 URL（同 hash 资产所有引用点共用一个 URL）。
     - 原样迁移时优先复用阶段 2 抓取的源站资源；清单外的新站资源一律不得指向老图床。
  4. **内容入库**：`add_product` / `add_news`（保留原 HTML / 分类 / 作者 / SEO；未要求发布用 `status=0` 草稿）。禁止盲目覆盖既有数据；入库前必须 `list_*` 核对，若发现同名 / 既有记录冲突，经《写入确认表单》（见 references §13.3 · 阶段 12 数据冲突分支）呈现「覆盖 / 跳过 / 改名」选项由用户选择，不擅自决定。**必须记录每条写入实际返回的 ID（productId / newsId）——这是阶段 14 URL Mapping 拼 `XXX-detail.html?id=<id>` 新 URL 的唯一依据。**
  5. **表单**：按阶段 8 方案，优先系统动态表单（`list_custom_form` → 用户选 → `FnGetCustomForm`）；询盘表单只改不动、不新建。
- **产出**：《基础数据迁移结果》（公司信息 / 分类映射 / 产品数 / 文章数 / 表单 / 素材相对 URL 映射），作为阶段 13 页面生成的入参。
- **硬约束**：本阶段是"写入新站"的数据底座，**必须在阶段 13（新网站生成）之前完成**；每项写入前必须 `list_*` 核对，冲突经表单处理，不擅自覆盖。

### 阶段 13 · 新网站生成 ✅ 调用「建站助手」skill（页面生成，绑定已迁移数据）

- **目的**：按《迁移内容规格》把已入库数据渲染成可上线页面。本阶段是"写入新站"的第二步写操作。
- **生成策略（按 §2 迁移方式分支）**：
  - **原样迁移（1:1 复制）**：以阶段 2 抓取的《老站页面源文件包》（HTML+CSS+JS）为基准，逐页还原老站 UI——保留布局 / 配色 / 字体 / 间距 / 组件形态，仅做平台模板语法适配（把静态内容替换为系统动态标签、把 CSS/JS 迁为平台兼容写法），做到视觉逐像素对齐，源站的css/js可以调用MCP上传文件接口上传到服务器并取回服务器css/js地址以便应用到新页面，此模式下不要使用公共的页头页尾。
  - **重新设计**：按《迁移内容规格》的新视觉方向（深色奢华 / 科技 / 简约等）重新实现页面，不要求 1:1。
- **动作**：**调用《依赖安装清单》登记的 `DEP_JIANZHAN`（建站助手）skill**（`Skill` 工具，`skill=$DEP_JIANZHAN`，调用名以登记为准），复用阶段 11 已确认的 MCP，按以下顺序执行（具体参数 / 工具名以建站助手实际提供为准）：
  1. **公共头尾（仅「重新设计」模式）**：仅在「重新设计」模式下制作 `common_top` / `common_foot` 公共片段（自包含 `<style>`+`<script>`），用 `{{FnInclude}}` 嵌入各页。**原样迁移（1:1 复制）模式按本阶段生成策略——整页复制、CSS 经 MCP 上传应用、不使用公共头尾**，跳过此步骤。
  2. **生成页面（含图片 / 资源 URL 替换）**：按《迁移内容规格》的页面生成清单，`save_ai_page` 生成各页。
     - **图片 / 资源回填（强制）**：生成每页前，必须将页面 HTML/CSS 中所有老站图片 / 背景图 / 字体 / CSS / JS 引用（老域名、老图床、CDN 域名，含 `img src` / `background-image` / `url()` / `<link href>` / `<script src>`）替换为《静态资产清单》（阶段 7）中对应 hash 行**已上传**的新站相对 URL（同 hash 资产所有引用点共用一个 URL）；产品主图引用阶段 12 上传返回的文件名。原样迁移尤其如此——直接拷贝阶段 2 的 HTML 时务必替换全部 `img src` / `background-image` / `url()` / `<link>` / `<script src>` 中的老图床地址，禁止页面上线后仍指向老站。
     - 原样迁移：基于阶段 2 抓取的 HTML+CSS+JS 还原结构，保留老站布局与样式，仅把可由系统获取的业务内容（已落在阶段 12 的产品 / 文章 / 表单等）替换为动态标签（`DataTag.sys` / `FnGet*`），并把 CSS/JS 按《静态资产清单》（阶段 7）唯一项经 MCP 上传后引用服务器 CSS/JS 地址（**同 hash 资产只传一次、全页共用同一 URL**），不重写视觉。
     - 重新设计：按新视觉方向实现，内容用系统标签绑定阶段 12 已入库数据，不在页面硬编码可由系统获取的业务内容。
     - 两类均每页加 JSON-LD（类型按页面匹配，企业信息用 `DataTag.sys`）。
  3. **写前确认 + 配图完整性校验**：用 `list_page` 拉最新列表，判断新建 / 更新，以《写入确认表单》（见 references §13.3 · 阶段 13 页面写前确认分支）逐页呈现「名称 / 友好 URL / 是否覆盖 / 是否首页 / 涉及表单 + 确认勾选」，用户勾选确认后再写；**不要逐页在聊天追问**。
     - **配图 / 资源完整性门禁**：写前回读已生成页面源码，确认《静态资产清单》标记"需重传"的资产均已上传并替换、页面中**无残留老站图片 / 背景图 / 字体 / CSS / JS URL**（无 `old.com` / 老图床 / CDN 域名引用，含 `img src` / `background-image` / `url()` / `<link>` / `<script src>`）。若仍残留老站资源地址，先回到步骤 2 完成资源回填，不进入写前确认；此校验未通过不得上线（见阶段 18 回读）。
- **时序说明**：阶段 12 数据已落库、图片已上传回填清单，本阶段页面预览即可拉取真实数据与已上传图片；「重新设计」模式下公共头尾（步骤 1）在页面生成（步骤 2）之前，使各页可统一引用头尾片段；「原样迁移」模式跳过步骤 1、直接整页复制（步骤 2 含图片 / 资源 URL 替换）。

### 阶段 14 · URL Mapping
- **目的**：建立旧 URL → 新 URL 的一一映射，是 301 承接与 SEO 检查的直接输入。
- **新站 URL 形式（重要，必读）**：新站的 URL 分两类，映射时**新 URL 必须取平台真实形态**，不得臆造：
  - **产品 / 文章等详情页**：由平台按内容 ID 自动生成，形式为 `XXX-detail.html?id=XXX`（前缀 `XXX` 为内容类型，如 `product-detail.html?id=<productId>`、`news-detail.html?id=<newsId>`）。其中的 `id` 来自**阶段 12 基础数据迁移**写入时 `add_product` / `add_news` 实际返回的 ID，**不是**自定义友好 URL，不能用 `set_page_friendlyurl` 改写。
  - **自定义页面（栏目页 / 单页 / 首页等）**：由 `save_ai_page` 生成、可用 `set_page_friendlyurl` 对齐的友好 URL（如 `https://new.com/about.html`）。
- **动作**：基于《迁移内容规格》的"旧 → 新 内容映射总表" + 阶段 13 生成后的真实新 URL（自定义页取 `list_page` / `set_page_friendlyurl` 确认值；详情页取阶段 12 写回的 `id` 拼成 `XXX-detail.html?id=<id>`），逐条产出《URL Mapping 表》（旧 URL → 新 URL → 映射类型：1:1 / 合并 / 丢弃）。高权重 URL（阶段 9 标出）必须 1:1 或语义最近映射。模板见 `references/migration-templates.md`。

### 阶段 15 · 301 Mapping
- **目的**：用 301 永久重定向承接老站 SEO 权重，避免迁移后流量 / 排名断崖。
- **动作**：基于《URL Mapping 表》生成 301 重定向规则：
  - 1:1 映射：旧 URL → 新 URL 精确 301。
  - 合并映射：多个旧 URL → 一个新版块页 301。
  - 丢弃 URL：无对应新页的旧 URL，尽量 301 到最相关栏目页（不要 404；确实无相关页再考虑 410）。
  - **实现方式**：若目标平台支持重定向 / `set_page_friendlyurl` / 后台重定向配置，经建站助手确认工具与参数后落地（写前展示影响并取得确认）；若平台不支持自助 301，输出《301 重定向规则表》交用户 / 运维在域名解析或服务器层（Nginx / CDN）配置。模板见 `references/migration-templates.md`。
- **硬约束**：凡阶段 9 标出的高权重 URL，必须有 301 承接，禁止直接 404。

### 阶段 16 · SEO 检查 → 调用「SEO skill」（yun-zhi-seo）
- **目的**：保证新站可被搜索引擎正确收录与排名，验证 301 / 可索引性 / TDK / 结构化数据。
- **动作**：调用「SEO skill」（`Skill` 工具，`skill=$DEP_SEO`，调用名以《依赖安装清单》登记为准，来源见 §1.1 第三方 skill 平台发布地址 `https://skillhub.cn/skills/org-b0bh4w8c/seo-skill`）。建议：① 对新站已发布 URL 跑体检（`audit` 或经 MCP 离线 `page --file`）；② 重点核对 indexability 维度——301 是否生效、无 noindex 误伤、canonical 正确、sitemap 含新页；③ 核对 TDK / Heading / Schema 与阶段 9 老站 SEO 要素的承接度；④ 输出《新站 SEO 体检报告》+ 待修复项。

### 阶段 17 · GEO 检查 → 调用「GEO skill」（yun-zhi-geo）

- **动作**：调用「GEO skill」（`Skill` 工具，`skill=$DEP_GEO`，调用名以《依赖安装清单》登记为准，来源见 §1.1 第三方 skill 平台发布地址 `https://skillhub.cn/skills/org-b0bh4w8c/geo-tools`）。建议：① 对新站跑 `crawl`+`analyze` 或单页 `analyze`；② 核对实体识别（企业 / 品牌 / 产品 / 服务）、知识覆盖、内容可信度、结构化数据、FAQ、Citation；③ 对可自动落地项产出 JSON-LD / FAQ 片段（经建站助手 `save_ai_page` 追加，严禁改动 `{{}}`/`{%%}` 数据标签）；④ 输出《新站 GEO 体检报告》+ GEO Score + 待修复项。
