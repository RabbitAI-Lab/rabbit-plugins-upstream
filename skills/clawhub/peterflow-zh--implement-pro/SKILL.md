# 分单元实施

按 Phase（阶段）→ Task（任务）接续，Phase 就是独立执行单元；已有 U001 等单元沿用原编号、任务与证据，不强制改名。主执行者负责调度、裁决和验收；每个 Phase 的实现、评审和测试环节分别使用新的执行者。所有必要职责都在本 Skill 内。

## 绑定范围

读取工作区项目规则、.peterflow/standards/ 中有关规范，以及目标、方案、单元任务和已有证据。用户指定其他资料目录时沿用。输入不限定文件名或生成工具，只需能确定：

- 公共上下文：工作区、资料路径、目标、适用规范、授权范围及验证条件。
- Phase / 单元：稳定编号、阶段目标、需求依据、直接依赖、阅读入口、写入范围、验收方法和所属 Task。
- 状态与证据：哪些已完成、未完成、未验证或受阻；最后哪个单元验证累计功能。

缺少少量信息就在原清单补足；范围或设计不明时指出具体缺口，继续可独立推进的工作。无需为了格式重建全部任务或调用其他 Skill。

## 执行边界

1. 检查当前 Git 状态、暂存区及已有修改。沿用当前授权的工作区，不自动暂存、提交、推送、创建 PR，也不为建立比较基线创建提交。
2. 任务清单是唯一进度源，主执行者统一维护。简短结果回填原任务，独立评审、测试或验收记录可按阶段保存，如 `verification/P001.md`。已有路径沿用。只记录事实、命令、评审结论与恢复信息，不另建任务清单。
3. 每个实现、修复、评审和测试环节使用新 Agent，仅传必要任务包，不继承整个聊天记录；若宿主支持，使用空历史方式创建。实现、修复、测试串行写入；评审只读，期间冻结相关内容。等待中的执行者及其后台进程也计入写入者。
4. 宿主不能创建独立执行者时，保留已有成果，给出当前阶段的最小新会话任务包及剩余步骤，报告能力受阻。不能以同一会话换角色冒充独立上下文，也不擅自创建用户侧聊天。

## 单元循环

按单元获准的路径写入产物。新增的详细设计放 `design/`，参考资料放 `references/`，交付实施的文件放 `delivery/`，多方共用的契约放 `contracts/`。各目录随第一份实际材料创建，派工只传所需路径。

按依赖选择就绪 Phase，Task 需同时满足所属 Phase 前置和自身依赖。用户只指定一个阶段时沿用该范围。已完成且证据仍适用的单元直接保留，前置只写了完成标记时先核实。按[角色协议](references/roles.md)准备本角色的必要材料，包括适用的现行条款和例外。已安装 `context-handoff` 时，可用它把这些材料附到本次派工消息中。

涉及新增抽象、依赖、配置、兜底、文档或测试设施时，把[最小改动对照](references/minimal-change.md)中命中的条目随任务交给对应角色。实现者用它选改法，评审者用它核实具体代价，测试者用它判断已有用例缺哪条断言。

1. **实现**：保存有关路径的进入状态与必要内容快照，派新实现者完成指定任务及相关编译、现有回归。返回实际修改路径、命令结果、偏差和未完成项。用进入快照区分本单元改动与前序成果，文件在允许范围内也要逐项核对改动用途。
2. **评审**：实现者和后台写入结束后，按[评审回执约定](references/roles.md#评审回执与接续)冻结本单元变化及相关需求、规范，记录工作目录和受评输入。派新只读评审者分别检查规范符合性和需求实现；保存执行者标识、实际范围和两项结论。一名独立评审者可覆盖两方面，两名可并行只读。只裁定本单元范围。
3. **裁决与修复**：主执行者逐项记录采纳、驳回或待确认及依据。采纳项交新实现者修复，重审受影响部分；影响行为的待确认项未解决时不能验收通过。
4. **测试**：依据验收和实际风险明确输入、操作及预期，派新测试者运行已有测试，并在确有缺口时补测试。测试者报告真实失败，不降低断言或自行修改生产代码求绿。生产缺陷回到修复与受影响评审，再做必要回归。
5. **验收**：核对测试断言经过目标逻辑、实际执行结果及适用输入。实现、评审裁决和必需测试全部成立后，才将单元置为已完成。代码已有但未测为未验证；缺环境或能力为受阻并写解除条件；已知失败保留未完成工作和失败证据。

**范围变化由主执行者处理。** 轻微噪声或多余机制只派修本单元可归属的差异，按原验收复核。修复跨出写入边界时，先查第一处失败和调用关系；必要适配在已有授权内重新派工，越过用户边界才请用户决定。“只改 X”时先叫停受影响的写入者，确认停写后再按 X 派工；用户叫停整个任务时，停止派工和本任务的在途写入，核对现场后回报。

测试顺序服从用户和项目要求；需要测试先行时将测试者前置设计、编写测试，实现后仍由独立测试者验证。不固定要求 TDD 或生产代码先行。纯文档单元使用适用的实际检查，并说明为何无需程序测试。

## 比较、恢复与收尾

- 暂停时在原任务写清最后已核实的环节、回执位置、待处理发现和下一步。接手时先确认上次写入者已经退出，打开原任务及阶段证据，找到上次实现、评审、测试各自的执行者和实际输入。核对裁决和覆盖范围。项目已有等价证据可直接使用；标准回执可运行[随包检查](scripts/check_review.py)。回执缺失或身份、输入无法核实时，从最早缺证的环节继续。
- 评审仍适用且只缺测试，直接派新测试者。受评代码变化时比较原快照，保留不受影响的结论，给新评审者受影响的差异。已采纳问题待修就先修复、重审；待决定项阻止相关阶段关闭。仅测试环境或验收输入变化时，核对影响，再补相应测试。只更新进度和回执不应让已核实的业务输入过期。
- 同一文件含前序未提交成果时，用本单元进入与退出内容比较；无 HEAD 时也使用内容快照。已有暂存、未暂存与新文件分别核对，不把所有 dirty 文件当成本次改动。快照缺失就明确评审范围并补充检查，不捏造前态。
- 证据记录执行时间、工作目录、命令或操作、结果、行为覆盖和所用输入。Git HEAD 单独不足以识别未提交修改；用有关文件摘要或保留快照判断是否变化。
- 代码、契约、测试或环境变化后只撤销受影响的验收，保留已完成实现和历史证据，恢复下一未完成环节。修复的前置是所需实现产物，不机械依赖失败验收。更新后继和最终单元的补验范围。
- 最后一个单元检查累计需求及跨模块行为，不只检查最后一段差异，也不把各单元勾选或静态检查当成累计测试。必要验证未运行，整体就仍有未验证或受阻项。

完成时确认所有执行者和后台进程退出，报告单元状态、两方面评审裁决、实际测试、未运行项、证据位置及 Git 状态。按原档位继续剩余工作，不重新规划已经完成的全部功能。
