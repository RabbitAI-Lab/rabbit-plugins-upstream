# 最小改动对照

提炼自 `moyu` 的改动对照和纠偏方法。以下问题由执行者自己判断。用户要求的重构、文档、完整错误处理和测试，以及项目规范规定的交付，都计入范围。确有两种可行改法，且选择会改变对外行为或部署约定时，说清各自影响，把需要决定的取舍交给用户。

| 想做的改动 | 动手前先问 | 在当前任务里怎么做 |
| --- | --- | --- |
| 顺手改邻近代码 | 保留它会让哪个入口继续出错？ | 沿实际调用链修到目标行为成立。保留无关命名、导入顺序、格式和旧代码。归属不明的改动留在原处。 |
| 拆文件、提公共函数、建接口或工厂 | 哪个现有调用方需要替换实现？两处相似代码是否真的受同一条规则约束？ | 只有一个实现时先直接实现。单处逻辑放在使用点。找到共同规则或项目已有接口约定，再决定是否抽取。 |
| 加依赖、配置或模式开关 | 项目现有实现或标准库缺哪项能力？今天谁需要第二个取值？ | 读 JSON、比较时间先找项目已有用法。固定值就近定义。新依赖确有必要时，说明它解决的缺口及对构建或部署的影响。 |
| 加校验、捕获异常或返回默认值 | 哪个真实输入能触发？到这一层还能怎样恢复？ | 在系统边界解析外部输入，内部信任已建立的类型约束。能恢复时处理具体错误，其余沿原错误路径上报。内部约定被打破时直接暴露，避免用空值把错误伪装成成功。 |
| 补注释、类型标注或说明文档 | 下一位读者从代码里还看不出什么？ | 优先沿用项目命名和类型推断。保留解释业务原因的注释、公开接口所需的契约和明确要求的文档。代码已说清的操作无需逐句复述。 |
| 加测试套件或脚手架 | 原缺陷重现时，已有哪条断言会失败？ | 先用现有入口验证。确有遗漏，就在最近的测试中补能区分正确与错误行为的用例。一个回归用例足够时，沿用现有测试设施。 |

### 发现已经做多了

- **混入少量无关差异时**，对照进入任务时的状态，只撤掉自己顺手带入的差异。同一文件中用户已有的改动保留。
- **简单修改变成一套新机制时**，暂停扩展，用原始输入和验收试一次直接改法。它能满足要求，就收掉多出的包装、配置或依赖，用同一验收复核。
- **修 A 引出 B、C 连锁修改时**，回到第一处失败，查清是本次改动引入的回归、必要的调用方适配，还是独立问题。若修 B 又破坏 A，暂停试改，用能同时检验两者的用例重新选方案。确需突破明确边界时，交代哪个行为受阻、最小还要改哪里。归属不明时不整文件回退。
- **听到“只改 X”**，就按 X 重审剩余工作。听到“停下”，立即停止写入，说明已动的部分并等待。“撤回”只处理用户指定且能确认归属的差异。

交付前用两个问题核对本轮 diff。每处变更对应哪项行为、规范或验收？拿掉哪一处，交付仍然完整？保留下来的必要改动，用实际结果说明。文件数、行数和评审耗时不设硬门槛。
