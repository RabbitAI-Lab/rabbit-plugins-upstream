# Phase 角色协议

主执行者为每次派工填写下列共用信息，然后只附本次角色段落。任务包和证据属于当前功能资料，不构成另一个 Skill 或任务账本。

## 共用任务包

- 本次角色、Phase（执行单元）编号与所属 Task 编号；已有单元编号沿用。
- 工作区、任务文件、有关目标和方案、适用规则的实际路径。
- 本次目标、验收、最少阅读入口、直接依赖产物及必要恢复事实。
- 允许写入的路径；只读评审没有写入权限。
- 已有改动的归属、用户约束、执行位置和验证条件。
- 比较依据（评审时）：本单元进入前态、冻结后态或差异的实际位置，说明前序未提交成果；没有前态时写清现状审查范围与归属限制。
- 回执要求：实际修改路径、运行命令或操作、结果、未运行项、偏差及证据位置。

执行者只处理本次实现、修复、评审或测试环节，不领取后继，不更新主任务状态，不操作 Git 暂存或提交。需要扩大范围时先返回原因，由主执行者在已有授权内决定。

## 实现者

从现有代码和直接依赖开始完成指定行为，保护已有改动。运行有关编译或现有回归，返回实际结果。需要新决定或无法完成时保留成果，指出剩余工作与原因。修复派工同时提供已采纳的问题及其依据。

先找能复用的实现和标准库能力。准备加层、加库或整段重写时，问：“更直接的局部修改会漏掉本 Task 的哪条验收或约束？”固定取值先放在使用点；输入只在边界解析，错误只在能恢复处处理。遇到具体取舍，用任务包所附的对照条目。回报前检查自己的 diff，清理无关格式、改名及顺手重构。若需越过派工范围，交回第一处失败、调用关系和最小追加改动。

## 评审者

只读检查冻结的本单元变化、相关调用方及适用规范和验收，分别报告：

1. **规范符合性**：指出违反的具体规则与代码位置；没有适用共享规范时如实说明，仍检查项目规则，不发明新规范。
2. **需求实现**：指出行为、契约、边界和本单元验收的冲突或遗漏。遇到疑似多余的改动，问：“去掉这一处会破坏哪条要求？”结合调用方、规范和验收核实。指出可以省去的具体差异及其额外影响，例如只需修正解析逻辑却新增了一项要长期维护的配置。待后续单元完成的工作不算当前缺陷。

同样核对删减的后果。例如，内部重复判空可以省，外部输入仍要按契约解析；需求明确要求迁移指南或两种实现时，保留对应文档或接口。以受评差异的归属和行为作判断，已有代码的风格偏好留在本次评审之外。

每项发现包含位置、可触发条件、实际影响、依据和建议。没有发现就明确写无发现并说明检查范围；无需为了报告凑问题。测试未运行不能当作通过，也不能仅因后置测试尚未编写就断定生产逻辑错误。将实际缺陷与待验证风险分开。

## 测试者

依据目标和主执行者给出的验收场景检验实际行为。运行已有适用测试；缺少关键断言时在授权路径补充。记录环境、输入、命令、退出结果及观察到的行为，成功日志要能对应本次内容。

准备新增测试设施时，先问：“把原缺陷放回来，现有断言会在哪个入口失败？”已有用例覆盖就复用；关键行为漏验时，就近补一个能区分修复前后的用例。任务明确要求的完整测试范围仍须逐项覆盖。

可以修正测试自身的错误，保持原需求预期；生产缺陷携复现证据交回主执行者，不自行改业务代码。外部环境未就绪就记未运行或受阻。纯静态检查只报告其证明范围。

## 评审回执与接续

主执行者在实施者退出后保留进入前态和受评后态，交给独立评审者核对。工作区有未提交代码时可用 `python3 <本技能目录>/scripts/check_review.py inputs 相对源码路径 相对契约路径` 在当时记录摘要，评审返回时再比一次。按实际范围加入测试或配置。新增、删除、未登记的文件及环境变化还要对照工作区差异。任务或证据文件会回填进度时，单独保留受评条款或快照。

一个阶段可沿用原证据目录保存下面的回执，`inputs` 填实际输出。原始角色回执或其位置也要保留。主执行者对照实际派工确认实现、评审、测试来自不同上下文。

```json
{"phase":"P002","reviewer":"实际执行者标识","standards":"适用规则与结论","requirements":"目标、入口与结论","inputs":{"相对路径":"评审时的 SHA-256"},"findings":[]}
```

有发现时逐项写 `issue`、`decision` 和依据 `reason`。待裁决、待决定、采纳待修都要留在原回执。驳回须有依据。采纳项修复后，保留旧回执，交新评审者按原发现复核并产生新回执。

中断后从工作区根目录执行 `python3 <本技能目录>/scripts/check_review.py check 回执.json --phase P002`。比对失败时按具体原因处理。比对通过只说明已登记输入和裁决可接续，仍需核对实际改动范围、独立性和测试证据。测试者回报所测版本、用户入口、输入、预期、实际结果和未运行项；主执行者据此更新原 Task 和 Phase。
