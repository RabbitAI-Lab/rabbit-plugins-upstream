# 追平功能决定

输入为原决定、新决定、当前产物及本次授权。输出是授权范围内一致的新状态、逐层证据和可核查的恢复资料。讨论或评审本技能本身，不触发变更流程。

任务进度仍在原计划或 Phase / Task 清单；`RECONCILIATION.md` 只保存本轮决定、授权边界、同步水位、恢复日志及验收依据，是变更控制记录，不是第二份任务账本。关闭后保留恢复包，用户明确要求时才能撤销。

纯影响评估可直接阅读现有材料，在会话中完成，无需 Python。核验已有活动契约、实施变更或恢复文件时，需要 Python 3.9+ 运行随包的 [contract.py](scripts/contract.py)，仅用标准库。

## 1. 定位与评估

按用户指定位置、项目入口及实际引用关系确定唯一权威主题，按需读取适用的 .peterflow/standards/。已有资料原位续接；确需新主题才使用 .peterflow/specs/主题/，保留已有文件。

先查有关主题是否已有 `RECONCILIATION.md`。若有，读取原确认，用 `status` 查看轮次状态、用 `verify` 核验日志与当前文件。核验通过后沿同一轮次接续，保留仍有效的成果。核验失败时报告实际失败，保留原轮次。重叠变更先厘清归属。

Python 或工具不可用时，仍可报告从材料确认的影响，明确标注“契约状态与日志一致性未核验”。保留现场和原记录，依赖核验的续写、关闭或恢复等待工具可用。不自动安装环境，也不用临时备份代替日志核验。

按 [评估约定](references/assessment.md) 核对变更断言、影响链、工作根、当前修改、删除候选、副作用和基线检查。区分本次执行上限 `target_stage` 与整轮闭环终点 `completion_stage`；已实现功能只先改设计，仍有待追平代码，不能因此缩短整轮终点。

只请求评估时只报告。用户已明确确认决定和范围时，完成必要核对后直接执行，不重复询问或强制结束一轮。仅对缺失的关键产品决定、实质范围扩张及未覆盖的副作用确认；事实不明时先保留有关内容。

## 2. 建立或续接变更记录

写入前读取 [控制记录与恢复协议](references/contract-schema.md)。使用随包 [契约模板](assets/RECONCILIATION.md) 对应脚本初始化，补全已确认内容及其来源，不把建议写成授权：

```sh
python3 <skill-dir>/scripts/contract.py init <主题目录> \
  --target-stage <本次上限> --completion-stage <整轮终点> \
  --version-control <git|none> --writable-root <已授权工作根>
```

默认嵌入保存真实文件前态，不依赖提交；有 Git 但没有 HEAD 也能运行。只有已有适合的提交且确需 Git 恢复来源时才传 `--baseline-ref`，不为建立基线创建提交。已有契约用 `scope` 记录新增授权，保留 round_id、原始日志与证据。

新建后补全确认内容与基线，再运行 `verify`；机械校验通过才开始目标文件写入。初始化成功或控制文件存在本身不算检查通过。

## 3. 逐层追平并验收

按照 [阶段门槛](references/stage-gates.md) 核对需求、设计、任务、实现和验证的受影响链。它们是产物职责，可合在同一文件，不要求补齐五份文档；也不是任务清单中的 Phase。当前层通过才沿该链推进，下游暴露上游问题时回流并重验受影响部分。

每次修改、创建或删除目标文件前后执行写前协议：

```sh
python3 <skill-dir>/scripts/contract.py prepare <契约> --path <目标文件>
# 执行已授权的该次编辑
python3 <skill-dir>/scripts/contract.py applied <契约> --path <目标文件>
```

同一文件多次修改逐次记录，原始前态不覆盖。新增路径先核对是否仍在既有授权内；已确认闭包内的补充直接登记，实质范围扩张先确认。外部系统和数据变更不能用文件恢复日志代替恢复方案。

涉及任务时按 [任务追平规则](references/task-rebuild.md) 保留有效的 Phase、Task、编号和成果，重建已失效部分及依赖，剩余工作仍回原清单。每层记录实际检查、输入、结果和未运行项；源码、测试、契约或环境变化后，旧验收只在仍适用的范围内有效。

## 4. 核对残留与停止位置

运行项目适用检查，并核对词法和行为残留。每个旧语义命中必须说明已替换、明确历史、与本轮无关或有当前要求明确保留；关键词零命中不能证明旧分支或旧断言消失。失败区分本轮相关、已有且有证据无关、无法归因；必要检查未运行或未知归因时不能记通过。

运行 `verify` 核对日志链、文件、权限和恢复载荷。只完成本次执行上限时，在原资料注明同步水位、下游陈旧与下一授权需求，设置 `paused` 并保留同一契约。遇到未解决失败或授权边界，设置 `blocked`，说明解除条件；不自动回滚，不降低闭环终点以求关闭。

## 5. 关闭与明确授权的撤销

关闭前读取 [关闭证据](references/closure-evidence.md)，逐项重新核对新决定、当前产物、实际验证和剩余工作。`valid: true` 只证明机械一致，不是功能完成；只有整轮终点及必要门槛通过、剩余工作为零，才准备独立的关闭证据：

```sh
python3 <skill-dir>/scripts/contract.py verify <契约> --mark-ready --evidence <关闭证据.json>
python3 <skill-dir>/scripts/contract.py close <契约> --archive <恢复包.json>
```

恢复包保存在已授权且未占用的位置，父目录按需准备。脚本复核后保存私有恢复包，再关闭活动契约；失败则保留现场，不能用删除文件绕过。恢复包是静态恢复资料，不是活动任务或已执行成功的证明。

撤销必须有当前明确授权。活动轮次直接使用 `restore`，包括已标记 `ready_to_close` 但尚未关闭的轮次。已关闭轮次先 `inspect-recovery` 核对恢复包身份和路径，再按恢复协议 `reopen`、`restore`。脚本拒绝漂移或越界，不覆盖后续修改；恢复后仍须实际复验基线与引用，再用 `outcome=restored` 的证据关闭，保留原恢复包。

收尾报告已追平层级、原 Phase / Task 的剩余工作、实际验证与未验证范围、残留分类、契约或恢复包位置、Git 状态。不得自动暂存、提交、推送、清理用户资料或修改全局配置。遇到分段推进、旧资料或误关闭边界时，可参考 [校准案例](references/case-catalog.md)。
