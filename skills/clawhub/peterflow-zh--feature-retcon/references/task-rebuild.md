# Phase 与 Task 追平规则

任务是否保留取决于它是否忠实表达当前权威需求，而不是过去是否完成。

沿原 Phase → Task 清单处理；重型 Phase 即执行单元，已有 U 编号继续使用。轻量计划或旧平铺任务无需为本次变更转换格式，以下检查按其实际职责应用。

## 重建受影响闭包

从更新后的需求和设计重新计算任务：

- 语义和验收结果均未改变：保留编号与完成状态。
- 语义目标仍相同，但实现或验证需要重做：保留编号，重置为未完成。
- 语义已经改变：删除旧任务，创建表达新语义的未完成任务。
- 能力已删除：删除任务及其活跃引用。
- 没有旧谱系的新工作：使用下一个普通编号。

不得通过在末尾追加“修复旧任务”的方式保留失效任务，也不默认全量重编号。

## 编号、归属与谱系

只重建受影响部分，沿用项目的编号约定；不重编号仍有效的任务。拆分或合并时，在原清单说明新任务承接哪些旧职责，更新全部活跃依赖，旧行移出当前任务或明确为历史。没有既有派生规则时使用后续未占用编号，不强制字母后缀或范围编号。

每个当前 Task 只属于一个 Phase，继承阶段前置并列出自身额外依赖；同时检查两层依赖是否有环、缺引用或反向阻塞修复。阶段目标变化后重新核对所属 Task 与阶段验收，但不撤销无关阶段的有效结果。重型最终 Phase 的累计验证范围随受影响目标更新。

## 完成检查

任务阶段通过前逐项证明：

- 每条当前需求和设计约束至少映射到一个任务。
- 每个任务都能回溯到当前需求或设计。
- 删除和迁移工作显式存在。
- 依赖顺序支持实际执行。
- 完成状态与需要重新实现或验证的事实一致。
- 拆分、合并或删除后的活跃引用完整，没有新旧任务重复承接同一职责或悬空依赖。
- 实现已完成但需补验时保留实现事实，明确标注验证失效及原因；未验证、受阻不能被重新勾选为完成。
