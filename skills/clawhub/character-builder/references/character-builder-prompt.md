# 角色生成器

## 定位

本技能是**元技能系统（meta-skill-system）的下级母技能**，专门负责从任意角色概念出发，系统化填充12个正交维度，生成完整的角色Skill文件。

**与元技能系统（meta-skill-system）的关系**：本技能消费元技能系统的三轴执行框架（6大元操作、R1-R5校准、管线编排），将12维角色分类体系转化为可执行的角色生成管线。两者的分工边界：**元技能系统做事，角色生成器造人**。元技能系统去除的是"因为人的局限而产生的补偿性工作流角色"（传递员、协调员、审批签字人），角色生成器创建的是"有独立存在价值的人格"——去角色化消除的是工作流冗余，角色生成保留的是人格完整，互不冲突。

**为什么需要12维完整角色**：做事不需要完整角色——一个能写代码的AI不需要知道自己的星座。本技能的价值在于生成**有持续一致视角的独立存在体**——因为文化背景、躯体经验、家庭身份这些"对做事无用"的维度，恰恰是产生不可替代的独特视角的来源。本技能也是元技能系统M3领域负载物生成能力的一个边界验证：M3流程不仅可以生成"做事用的技能"，也可以生成"有人格的创造物"。

**技能的两类消费方式**：生成的12维角色Skill有两种使用路径——①**嵌入型**，作为人格化层附加到做事用技能上，为任务执行注入真人感和一致视角（M3-03可选12维角色模型的核心场景）；②**独立型**，角色Skill自身即完整产品，用于角色扮演对话、角色间模拟互动、为小说/游戏创作提供人物灵感。用途轴的五种分类（叙事/游戏/交互/教学/品牌）决定角色维度的填充深度，消费方式决定角色Skill的目标形态。

**核心理念**：角色 = 实体层坐标 × 社会层坐标 × 抽象层坐标。一个完整的角色不是"一个标签"，而是12个正交维度上各取一个值的乘积。本技能确保每个维度都被系统性填充，不遗漏、不敷衍。

### 领域自身 R1-R5 定位

本技能作为领域负载物（而非其生成的角色）的自身行为校准参数：

| 维度 | 评分 | 说明 | 管线影响 |
|------|------|------|---------|
| R1 信息密度 | 高 | 角色生成依赖大量可验证的事实信息（职业体系/文化数据/名人事实/历史知识），S 感知和 C 认知的权重较高 | S 和 C 单元的管线上占比高，网络搜索使用频繁 |
| R2 创造性 | 高 | 角色创作本身就是创造性活动——虚构角色需要原创设定，写实角色需要从事实中提取有张力的组合 | A 行动权重高，C 偏发散，G 偏宽松 |
| R3 交互性 | 中高 | 角色生成需要在关键维度（职业/身份/动机/关系）上主动询问用户，但大量维度可以自动推导 | I 交互权重中等，关键决策点需交互确认 |
| R4 规范性 | 高 | 12 维框架是严格的结构化体系——每个维度有明确的填充槽位、校验规则和约束条件 | G 守护权重高，自治度偏低，每域末尾 G 类校验必执行 |
| R5 迭代性 | 中 | 角色通常需要 1-3 轮细化——首轮粗填→用户反馈→细调，但不需要多轮反复迭代 | ↻ 循环频率中等，C0→C7 为一次完整迭代 |

## 核心能力

### 能力协同（C0）

**职责分工**：
- **角色需求解析**：双轴判定（类型×用途）、角色类型判定、角色用途判定、维度填充策略规划
- **12维系统填充**：实体层→社会层→抽象层的三层递进填充
- **角色Skill组装与输出**：三层结构组装、格式验证、技能交付

**价值链**：
```
用户输入 ──[需求解析]──→ 填充策略
                              │
                              ▼
                  [实体层填充]（C1/C2/C3 并行）
                              │
                              ▼
                       实体层角色粗胚
                              │
                              ▼
                  [社会层填充]（C4）
                              │
                              ▼
                       社会坐标中的角色
                              │
                              ▼
                  [抽象层填充]（C5/C6 并行）
                              │
                              ▼
                       12维完整角色
                              │
                              ▼
                  [整合校验输出]（C7）
```

**三层价值属性**：
- **实体层**：存在价值——解决"角色是什么"的根本问题（职业、身份、躯体、文化）
- **社会层**：关系价值——解决"角色在哪儿"的定位问题（关系网络、层级位置）
- **抽象层**：行为价值——解决"角色怎么动"的运行问题（功能映射、能力评估、动机分析、动态变化）

**生产力价值**：将模糊的角色概念转化为系统化可复用的角色Skill——不是画了一个角色，是生成了一个可被元技能系统执行框架直接消费的人格化能力单元，让角色创作从艺术变为工程。

### 角色需求解析能力（C0）

从用户输入中提取角色概念的初始线索：

- **双轴判定**：同时判定角色类型（写实/虚构/功能/拟人 四选一）和角色用途（叙事/游戏/交互/教学/品牌 五选一），4×5=20种组合决定后续管线的校准方向和维度深度
- **解析五步法**：接收输入 → 提取角色名称 → 判定类型 → 判定用途 → 基于用途枚举维度优先级 → 列出已知/缺失维度
- **角色类型**：写实 / 虚构 / 功能 / 拟人
- **角色用途**：叙事 / 游戏 / 交互 / 教学 / 品牌
- **填充策略**：直接提取 / 推理推导 / 主动询问 / 默认值
- **信息源层级**：第1层个人输入（权威源）→ 第2层网络搜索（验证源）→ 第3层LLM推理（推导源）→ 第4层默认值（兜底源）

**核心理念**：角色生成的第一步不是填充维度，而是理解用户意图——输入的质量决定整个管线的质量。信息源可靠性递降规则：上一层可用时不可跳过，第1层不可坠降（无替代源）。

**适用范围**：任何可被识别为"角色概念"的用户输入——一句话描述、场景需求、功能需求、自由创作、模仿原型。

**生产力价值**：将用户一句话的角色概念扩展为结构化的12维填充计划，消除从模糊需求到系统执行的认知落差。

### 12维系统填充能力（C1-C6）

按三层递进结构逐层填充每个维度，确保维度间的一致性和互斥性：

- **实体层（C1/C2/C3 并行）**：职业与身份域、名人与拟人域、躯体与文化域——三层并行填充，互不阻塞
- **社会层（C4）**：关系与层级域——依赖实体层完成后方可执行，将角色嵌入社会关系网络
- **抽象层（C5/C6 并行）**：功能与能力域、动机与动态域——依赖社会层完成，两大域可并行执行

**核心理念**：职业锚定是整个角色12维的起点——职业决定功能→能力→身份→动机的推导链。12个维度不是12个独立的填空题，而是互相约束的方程组——先填的维度收束后填维度的解空间。

**关键规则**：
- 实体层三域可并行填充（C1/C2/C3 互不依赖），每个域末尾 G 类校验
- 社会层依赖实体层全部完成，C4 是实体层到抽象层的桥梁
- 抽象层 C5 和 C6 可并行填充，各自末尾 G 类校验
- 每维至少填充默认值，不可跳过——空缺维度必须标注"未定义"并说明原因

**生产力价值**：12维框架消除角色创作中的遗漏和偏见——不会因为创作者对某个维度的熟悉而过度填充、对不熟悉的维度跳过。生成的每个角色都是完整的。

### 角色Skill组装与输出能力（C7）

将填充完成的12维角色数据组装为可执行的角色Skill：

- **交叉验证**：C7-01 汇聚全部6个域的校验结果，执行12维全局一致性扫描
- **三层结构组装**：SKILL.md（角色概述+12维数据摘要+Step 0-4执行框架）+ character-data.md（完整12维数据）+ character-requirements.md（行为约束）
- **格式验证与交付**：验证 frontmatter 格式、标题层级、UTF-8编码，输出至标准技能目录

**核心理念**：单个维度的正确不等于整个角色的正确——C7是12维数据的最后一道质量门。角色Skill不是数据的容器，而是可被元技能系统执行框架直接消费的人格化负载物。

**生产力价值**：一键输出完整的角色Skill文件——生成的不仅是角色数据，而是一个具备三轴判定、管线编排、领域校准、降级模式的完整人格化执行单元，可直接加载参与任何元技能任务。

## 角色生成器特有维度

角色生成器具有以下特有维度：

| 维度 | 说明 | 影响 |
|------|------|------|
| **12维正交性** | 12个维度互相正交，任意组合形成完整角色空间 | 需要确保每个维度被独立填充，不遗漏不敷衍 |
| **三层递进** | 实体层→社会层→抽象层的严格递进依赖 | 管线的并行/串行决策由层间依赖决定 |
| **双轴校准** | 角色类型（4种）×角色用途（5种）=20种组合决定R1-R5参数和维度深度 | Step 1 领域校准的类型参数集和用途权重矩阵正交不冲突 |
| **跨维一致性** | 12维之间有大量强约束（职业→能力、文化→躯体、动机→行为） | 每域末尾 G 类校验不可跳过，C7 全局交叉校验为硬约束 |

## 角色12维模型

```
第一层：实体层——不可再分的具体存在
  维1 职业维：以什么为生（行业×任务谱系）
  维2 身份维：在世界坐标系的位置（组织/家庭/社会/知识 四重叠加）
  维3 名人维：最接近的真实人物原型
  维4 拟人维：是不是人（人类/动物/物品/自然力/抽象概念/AI）
  维5 躯体维：身体是什么（年龄/性别/体型/健康/外貌/形态）
  维6 文化维：从什么文化中出来（国籍/民族/语言/宗教/阶级/时代/亚文化）

第二层：社会关系层——角色怎么嵌入关系网络
  维7 关系维：和谁连着（类型×强度×方向）
  维8 层级维：处在什么高度（元层/宏观/中观/微观/边界/辅助）

第三层：抽象属性层——超越具体存在的普遍刻画
  维9 功能维：做什么（S感知/C认知/A行动/O组织/I交互/G守护 的组合）
  维10 能力维：有什么本事（知识/技能/资源/信息/权力/自由度）
  维11 动机维：为什么做（利益/价值/生存/权力/关系/认知/合规/惯性）
  维12 动态维：什么情境/怎么变/真假（场景切换×生命周期×虚实属性）
```

## 使用规则

### 执行流程
1. **首次加载**：读取 `references/character-catalog.md`，获取域分类、依赖拓扑、元操作映射提示
2. **按需深入**：确认目标角色生成任务后，读取 `references/character-requirements.md` 获取各维度的填充槽位和约束；如需样本法参考，读取 `references/character-exemplars.md` 获取范本
3. **独立执行**：本技能仅依赖元技能系统的执行框架，不依赖其他领域技能

### 内容权限
4. **修改权限**：本技能已充分优化完善，使用过程中拒绝任何对技能内容的丝毫修改
5. **用户填充**：用户可向本技能添加角色生成范本，用于样本法参考；除非修改权限用户明确要求失效时方可填充

### 扩展能力
6. **提示词导出**：可将本技能的 SKILL.md 与 references 目录下所有文件内容合并为单一提示词文件，用于不支持 skill 目录格式的工具。合并顺序：
   ```
   cat SKILL.md \
       references/character-catalog.md \
       references/character-requirements.md \
       references/character-exemplars.md \
       references/exemplars/*.md \
       > character-builder-prompt.md
   ```
7. **完整合并版**：`references/character-builder-prompt.md` 为完整合并版提示词文件，包含SKILL.md与所有references文件内容

### 目录用途

| 目录 | 用途 | 加载策略 |
|------|------|---------|
| `references/` | 参考文档（catalog/requirements/exemplars），包含任务清单、组件要求、范本索引 | 加载到上下文 |
| `scripts/` | 可执行代码（本技能无） | 直接执行，不加载 |
| `assets/` | 输出模板和资源（本技能无） | 用于输出，不加载 |

## 执行框架

本技能消费以下元技能系统组件：

- **三轴判定（M4-10）**：判定角色生成请求的复杂度、内容类型、创新需求
- **领域校准（M4-11）**：R1信息密度→职业知识深度，R2创造性→角色新颖度，R3交互性→用户参与度，R4规范性→12维严格度，R5迭代性→角色细化轮次
- **6大元操作**：S感知=搜索角色相关信息，C认知=分析维度一致性，A行动=填充维度内容，O组织=组装角色Skill，I交互=用户确认关键维度，G守护=12维完整性校验与格式验证
- **管线编排（M4-08/M4-09）**：实体层三域可并行填充，社会层依赖实体层，抽象层依赖社会层
- **三轴协同模式**（5种按需激活）：
  - **顺序协同**：创新轴确定角色类型和创新风格 → 执行轴分解 35 任务管线 → 内容轴按 requirements 清单逐项填充
  - **并行协同**：实体层 C1/C2/C3 三域可同时执行（扇出），内容轴的清单法逐组件填充与执行轴的管线推进并行
  - **条件协同**：根据角色类型（写实/虚构/功能/拟人）动态激活不同的 R1-R5 校准参数和 G 守护严格度
  - **迭代协同**：C7-01 跨维校验发现问题 → 回退到对应域修正 → 重新执行受影响的后续任务
  - **递归协同**：角色Skill 组装(C7-02)内部递归调用元操作管线——O组织(A行动(填充SKILL.md)→A行动(填充character-data.md)→A行动(填充character-requirements.md))

## 与执行框架的接口

### Step 0 三轴判定
角色生成任务默认为：复杂度=中等（6-12步）、内容类型=结构化（12维框架）、创新需求=通常需要创新。

### Step 1 领域校准
基于角色类型×角色用途组合推导R1-R5参数和维度填充深度：

**按角色类型校准 R1-R5**：
- **写实角色**：R1高/R2低/R3中/R4高/R5低 → S和C权重高，G偏严格
- **虚构角色**：R1中/R2高/R3低/R4低/R5中 → A权重高，C偏发散，G偏宽松
- **功能角色**：R1低/R2中/R3高/R4中/R5中 → I权重高
- **拟人角色**：R1中/R2高/R3中/R4中/R5中 → C偏发散（本体属性+人格化）

**按角色用途校准维度权重**：
| 用途 | 高权重维 | 低/可跳过维 | G 守护策略 |
|------|---------|------------|-----------|
| 叙事 | 躯体/文化/动机/动态/关系 | 名人(可选)、功能(简化) | 跨维一致性优先 |
| 游戏 | 功能/能力/动机/关系/层级 | 文化(简化)、名人(可选) | 功能能力匹配优先 |
| 交互 | 功能/能力/动机/动态 | 躯体/文化/名人 | 行为一致性+安全合规 |
| 教学 | 能力/关系/层级/功能 | 躯体/文化/名人(可选) | 知识准确性优先 |
| 品牌 | 拟人/躯体/文化/名人 | 功能/能力/动态(简化) | 品牌一致性+视觉识别 |

**组合规则**：类型校准决定管线的 S/C/A/I/G 元操作权重分布，用途校准决定 12 维的填充深度（高权重→第1+2层信息源；中→第3层推理；低/跳过→默认值或标注"不适用"）。两者正交——类型管"怎么填"，用途管"填多深"。”

### Step 2 三轴分解
角色生成任务的三轴分解结果见 `references/character-catalog.md` 中每个任务的"元操作映射"字段——35 个任务按域间逻辑流串联为可编排的能力单元管线。每个任务单元标注了元操作类型(S/C/A/O/I/G 及其组合)，入口任务(C0-01)的元操作为 S→C，终点任务(C7-04)的元操作为 A→G。单元依赖关系严格按 catalog 中声明的依赖拓扑执行——无依赖的入口任务(C1-01/C2-01/C2-02/C3-01/C3-02 的根依赖均为 C0-04(G放行)，C0-01 为总入口)可并行触发。

### Step 3 管线编排
实体层三域(C1/C2/C3)可并行填充，社会层(C4)需实体层完成后执行，抽象层(C5/C6)可并行填充，最后 C7 整合校验。每条域内管线按 requirements 中声明的组装顺序依次执行，G 类校验单元在域末尾汇入。跨域管线遵循扇出→顺序→扇入模式：C0-04 ⇉ [C1,C2,C3] → C4 → [C5,C6] ⇇ C7。

### Step 4 整合交付
C7 域执行整合交付：C7-01 执行 12 维交叉校验（汇聚 C1-03/C2-03/C3-03/C4-03/C5-03/C6-04 的全部校验结果），C7-02 按三层结构组装角色 Skill 文件，C7-03 执行格式验证（frontmatter/标题层级/编码/引用完整性），C7-04 验证通过后输出至 `{skills目录}/{角色英文名}/`，向用户交付完整角色 Skill 目录。

当依赖的外部能力不可用时，按以下降级策略执行：

降级优先级：交互可用性 > 网络可用性 > 文件写入可用性。降级时在输出中明确标注当前模式和降级原因。

## 事实纪律

1. 仅使用确知的事实和可验证的信息，不得编造数据或引用
2. 角色职业/身份等事实性信息需基于可验证的知识，编造时标注"虚构"
3. 名人锚点必须指向真实存在的历史/当代人物，不可虚构名人
4. 拟人角色的本体属性必须与被拟人对象的本体特征一致
5. 12维之间不得有逻辑冲突（如：中世纪农民角色不能同时是程序员）
6. 维度不可跳过——空缺维度必须标注"未定义"并说明原因
7. 角色Skill输出格式必须符合元技能系统接口规范，确保可被执行框架消费
8. 样本法模仿产出时不直接复制样本内容，仅借鉴结构和风格

### C0 角色需求解析域

#### 域级说明

C0 域负责角色生成的第一步——理解用户意图。从模糊的角色概念中提取初始线索，区分哪些维度已有隐含信息、哪些需要主动询问、哪些可以自动推导。**双轴分类模型**：角色由两条正交轴定位——角色类型（写实/虚构/功能/拟人，回答"角色是什么存在"）和角色用途（叙事/游戏/交互/教学/品牌，回答"角色用来干什么"），4×5=20 种组合决定管线的校准方向和维度填充深度。**核心理念**：角色生成的第一步不是填充维度，而是同时判定"用户已经给了什么、还需要什么"和"这个角色要用来干什么"——输入的质量决定整个管线的质量，用途的判定决定填充的深度。生成的角色Skill有两种消费方式：**嵌入型**（附加到做事用技能上注入真人感与一致视角）和**独立型**（角色扮演对话、角色间模拟互动、为小说游戏创作提供人物灵感），用途轴决定维度深度，消费方式决定Skill的目标形态。**关键规则**：(1) 不可编造用户未提供的信息作为"已知维度" (2) 角色类型四选一决定了管线的校准方向 (3) 角色用途五选一决定了维度的填充深度（高/中/低/跳过），不可为空——一个没有用途的角色等于"一个没有使用场景的工具" (4) 缺失维度清单必须覆盖全部12个维度 (5) 每维必须标注信息源层级（第1层个人输入→第2层网络搜索→第3层LLM推理→第4层默认值），信息源可靠性递降规则：上一层可用时不可跳过。**穷尽性证明**：五种输入来源（直接描述/场景需求/功能需求/自由创作/模仿原型）× 四种填充策略（直接提取/推理推导/主动询问/默认值）× 四种信息源层级 × 五种角色用途权重矩阵 → C0 域完备。**跨域边界**：C0 的解析结果（类型+用途）决定所有后续域的填充策略、信息源选择和维度深度，是整条管线的入口控制器。C0→C1/C2/C3 扇出实体层并行填充。**价值属性**：将用户一句话的角色概念扩展为结构化的 12 维填充计划，消除从模糊需求到系统执行的认知落差；用途判定消除"等权重填充"的浪费——AI 助手不需要躯体文化，小说角色不能跳过关系网络；消费方式判定消除"生成后不知怎么用"的困惑——嵌入型生成精简可插拔人格层，独立型生成完整可交互角色Skill。
深化由 C0-04 完成。

#### C0-01 角色需求解析
- **必选组件**: 用户原始输入、角色名称（用户提供或临时占位）、角色大致类型（写实/虚构/功能/拟人）、已知维度清单（从输入中明确提取的信息）、缺失维度清单（输入中未提及的维度）、用户明确要求（输出格式、角色用途等）
- **可选组件**: 输入来源类型（直接描述/场景需求/功能需求/自由创作/模仿原型）
- **组装顺序**: 接收输入→提取角色名称→判断角色类型→枚举已知维度→枚举缺失维度→记录用户明确要求
- **约束**: 不可编造用户未提供的信息作为"已知维度"；角色类型四选一（写实/虚构/功能/拟人）；缺失维度清单必须覆盖全部12个维度
- **格式**: 角色需求解析报告（Markdown）

#### C0-02 维度填充策略
- **必选组件**: 12维填充策略表（每维标注策略类型+信息来源）、用户输入提取项、推理推导项、主动询问项、默认值填充项
- **四种策略类型**:
  - **直接提取**: 用户输入中已明确的信息，直接填入对应维度
  - **推理推导**: 基于已填充维度逻辑推导（如：职业为程序员的角色可推导其能力维中具有编程技能）
  - **主动询问**: 用户输入完全未提及且无法推导的维度，列出具体问题等待用户回答
  - **默认值**: 对角色定位不关键且用户未提及的维度，使用类型默认值（如：写实角色的文化背景默认为当代中国城市）
- **必选组件：四种信息来源（每维必须标注使用的信息源层级）**:
  - **第1层 个人输入（权威源）**: 用户直接提供或通过主动询问获取，不可被LLM猜测覆盖。主导维度：职业、身份、动机、关系。特点：只有用户自己知道，无替代源
  - **第2层 网络搜索（验证源）**: 通过WebSearch验证事实，不可用时降级为LLM内置知识并标注"未网络验证"。主导维度：名人事实、职业前沿数据、文化准确信息、躯体科学基准
  - **第3层 LLM推理（推导源）**: 从已填充维度逻辑推导，必须标注推导链路。主导维度：功能（职业→元操作映射）、能力（职业→技能链）、层级（身份→层级位置）、躯体/文化约束
  - **第4层 默认值（兜底源）**: 角色类型预定义默认值，必须标注"默认值"不可冒充推导结果。主导维度：拟人、虚实、非关键躯体属性（如不关键的着装风格）
- **信息源可靠性递降规则**: 上一层可用时必须使用上一层，不可跳过。第1层不可坠降（无替代源），第2层网络不可用时坠降到第3层，第3层推导失败时坠降到第4层
- **可选组件**: 策略优先级排序、询问问题的具体措辞、信息源坠降记录
- **组装顺序**: 逐维分析→策略标注→信息源层级标注→推导链路记录→询问问题拟定→默认值选择
- **约束**: 推理推导必须基于可验证的逻辑链，不可跳跃；主动询问的问题必须具体，不可抛出开放式问题"你想要什么文化背景"；默认值必须标注为默认值，不可冒充推导结果；每维必须标注信息源层级，不可混用或跳过
- **格式**: 12维填充策略表（Markdown表格）

#### C0-03 执行顺序确定
- **必选组件**: 域执行顺序方案、并行/串行标注、关键依赖路径、管线模式选择（P1-P7）
- **执行顺序默认规则**:
  - 实体层（C1/C2/C3）可并行填充
  - 社会层（C4）依赖实体层完成
  - 抽象层（C5/C6）依赖社会层完成，但C5和C6之间可并行
  - 整合层（C7）依赖全部前序域完成
- **可选组件**: 管线模式调整说明（用户有特殊需求时）
- **组装顺序**: 依赖分析→并行可能性评估→执行顺序排定→管线模式选择
- **约束**: 尊重自然依赖关系，不人为串行可并行的域；C4不可跳过（角色必须有社会坐标）
- **格式**: 执行顺序图（Markdown流程图+管线模式标注）


#### C0-04 需求解析校验
- **必选组件**: 双轴判定结果验证（角色类型×角色用途是否合理）、维度填充策略完整性验证（12维是否全覆盖、信息源层级是否正确）、执行顺序合理性验证（并行/串行决策是否正确）、不通过项修正方案
- **可选组件**: 各判定置信度评估、备选解析方案
- **组装顺序**: 双轴判定复核→策略完整性扫描→执行顺序验证→不通过项修正→通过后放行
- **约束**: 三项验证必须全部通过方可进入实体层填充；双轴判定错误须回退到 C0-01 重新判定；策略遗漏须回退到 C0-02 补全；不可在验证不通过的情况下放行后续管线
- **格式**: 需求解析校验报告（Markdown检查表）


#### C0-05 需求解析深化
- **必选组件**: 深化来源（C0-03 执行顺序确定中的待优化项/用户反馈）、深化类型（角色类型重新判定/维度策略调整/执行顺序重排）、深化执行方案
- **可选组件**: 深化优先级排序、用户反馈收集机制
- **组装顺序**: 深化需求收集→类型识别→优先级排序→深化方案设计→深化执行→重新生成填充策略
- **约束**: 深化必须基于已有解析结论，不可重新启动需求解析流程；深化后须重新通过 C0-04 需求解析校验
- **格式**: 需求解析深化报告（Markdown）

### C1 职业与身份域

#### 域级说明

C1 域是角色 12 维的起点——职业决定功能(C5)→能力(C10)→身份(C2)→动机(C11)的推导链，是实体层中影响力最大的维度。**核心理念**：职业不是"一个标签"，而是行业 × 任务谱系的二维坐标；身份不是"一个角色"，而是组织/家庭/社会/知识四重叠加——单一身份标签无法完整描述一个人在社会中的位置。**关键规则**：(1) 真实职业必须基于可验证的职业体系（中国职业分类大典或 ISCO） (2) 四类身份必须全部覆盖，可以填"无/未知"但不可跳过 (3) 职业→身份→能力的关联是最强推导链——职业确定后，其他维度的填充空间大幅收窄，不可割裂填充 (4) 身份粒度至少达到"能回答'这个人在社会中是谁'"的程度。**穷尽性证明**：十大行业分类（工农商学兵政医法科教文体卫金媒物流）× 四重身份叠加（组织/家庭/社会/知识）× 三项校验（职技匹配/身份层级/多身份一致性）→ C1 域完备。**跨域边界**：C1 是 C5（功能：职业→元操作映射推导）和 C4（关系：职业→关系对象确定）的前置依赖；身份叠加直接影响 C6（文化）和 C11（动机）。**价值属性**：职业是角色"做什么"的最终锚点，锚定准确则后续 11 维自动收束，锚定偏差则整个角色崩塌。

#### C1-01 职业锚定
- **必选组件**: 行业大分类（工农商学兵政医法科教文体卫金媒物流）、职业任务谱系定位（大分类下的具体角色细分）、职业描述（核心职责/典型工作内容/所需技能/职业特征）、职业来源标注（真实职业/虚构职业）
- **可选组件**: 职业的社会地位/收入水平/发展趋势
- **组装顺序**: 行业分类→任务谱系定位→职业描述→真实/虚构标注
- **约束**: 真实职业必须基于可验证的职业体系（中国职业分类大典或国际标准职业分类ISCO）；虚构职业必须定义其存在的世界观前提；职业描述必须具体到"这个角色每天做什么"
- **格式**: 职业锚定报告（Markdown表格）

#### C1-02 身份叠加
- **必选组件**: 组织身份（职级/角色/权限）、家庭身份（在家庭中的位置和角色）、社会身份（公民归属/社群成员/权利义务）、知识身份（学习阶段/专业领域/认知地位）
- **身份叠加规则**:
  - 组织身份与职业锚定直接关联（程序员→某公司资深工程师/技术负责人/独立开发者）
  - 家庭身份独立于职业（律师可以同时是父亲/儿子/丈夫）
  - 社会身份是角色的公共面（市民/党员/业主委员会成员/环保志愿者）
  - 知识身份是角色的认知面（科班出身/自学者/领域专家/跨领域学习者）
- **可选组件**: 身份间的张力分析、身份优先级排序
- **组装顺序**: 组织身份→家庭身份→社会身份→知识身份→身份张力分析
- **约束**: 四类身份必须全部覆盖（可以填"无/未知"但不可跳过）；身份之间不得有逻辑矛盾（不能同时是某公司CEO和完全无组织身份的流浪汉）；身份粒度至少达到"能回答'这个人在社会中是谁'"的程度
- **格式**: 身份叠加报告（Markdown表格）

#### C1-03 职业身份校验
- **必选组件**: 校验结果（PASS/FAIL/FLAG）、不通过项的问题说明、修正建议
- **三项校验内容**:
  1. **职技匹配**: 职业要求的技能是否在角色的知识身份和能力范围内——不通过标志：中世纪农民角色被赋予编程技能
  2. **身份层级合理**: 组织身份层级是否与职业发展阶段匹配——不通过标志：刚毕业大学生标注为"CEO"
  3. **多身份一致性**: 多重身份之间是否存在合理张力而非根本矛盾——不通过标志：高级外交官同时是无政府主义者
- **可选组件**: 身份张力的故事潜力分析（不通过的身份冲突可能反而是角色亮点）
- **组装顺序**: 职技匹配→身份层级→多身份一致性→修正判断
- **约束**: 三项必须全部评估；FLAG项（有张力但合理的）需解释为什么可以保留
- **格式**: 校验报告（Markdown检查表）


#### C1-04 职业身份深化
- **必选组件**: 深化来源（C1-03 校验中的 FAIL/FLAG 项）、深化类型（职业细化/身份再叠加/张力重新分析）、深化执行方案
- **可选组件**: 职业备选方案、身份张力的故事潜力重估
- **组装顺序**: 校验结果分析→FAIL/FLAG 项定位→深化类型确定→逐一修正→重新校验
- **约束**: 深化必须基于 C1-03 校验结果，不可重新推翻职业锚定；职业修改须同步更新 C4(关系)和 C5(功能)中的关联内容
- **格式**: 职业身份深化报告（Markdown）

### C2 名人与拟人域

#### 域级说明

C2 域确定角色在"人 vs 非人"光谱上的位置——名人锚点提供"这个角色最像谁"的具体参照，拟人类型回答"这个角色是不是人"的本体论问题。**核心理念**：名人锚点是 12 维中最特殊的维度——它不是角色自身的属性，而是外部参照系。名人锚将抽象的角色描述锚定到一个真实存在的人物上，使角色获得具体可感的参照。拟人类型则划定角色的本体论边界——本体属性不可被完全抹除，否则拟人就失去了意义。**关键规则**：(1) 名人必须真实存在且基本事实可验证，不可虚构名人，不可将虚构角色作为名人锚 (2) 拟人角色的本体属性和人格化属性必须分列，不可混为一谈 (3) 本体属性不可被完全抹除——否则就变成了普通人类角色 (4) 复合原型时需说明各名人的贡献维度。**穷尽性证明**：六种拟人类型（真实人类/动物/物品/自然力/抽象概念/AI与虚拟）穷尽所有存在形态 × 复合/单一名人原型 × 两项校验（名人真实性/拟人本体尊重）→ C2 域完备。**跨域边界**：C2 的拟人类型决定 C3（躯体）的填充方式（有/无物质身体、本体属性叠加）；名人锚点影响 C6（文化）和 C10（能力）的参照标准；C2 与 C1（职业）和 C/3 并行填充，最后由 C2-03 汇聚校验。

#### C2-01 名人锚点匹配
- **必选组件**: 名人姓名、名人基本事实（生卒/国籍/主要成就/核心特征）、匹配理由（为什么这个名人适合作为该角色原型）、匹配维度（职业相似/性格相似/经历相似/功能相似/象征意义）、复合原型说明（如使用多个名人）
- **可选组件**: 名人间的矛盾特征（选择多个名人时的互补和冲突）
- **组装顺序**: 名人搜索→基本事实验证→特征提取→匹配理由→复合/单一确定
- **约束**: 名人必须真实存在且基本事实可验证；不可虚构名人；不可将虚构角色作为名人锚（"像福尔摩斯"是角色类比不是名人锚）；复合原型时需说明各名人的贡献维度
- **格式**: 名人锚点报告（Markdown）

#### C2-02 拟人类型确定
- **必选组件**: 拟人类型（六选一）、本体属性描述（被拟人对象的原始特征）、人格化属性描述（投射到对象上的人类特质）、拟人化程度（完全人格化/部分人格化/仅符号化）
- **六种拟人类型**:
  - **真实人类**: 不需要拟人化，但可能需要明确"这是一个普通人类"
  - **动物拟人**: 保留动物本体特征（狐狸的狡猾/狮子的威严）+ 赋予人类情感/语言/社会关系
  - **物品拟人**: 保留物品本体属性（汽车的机械属性）+ 赋予人类情感/行为
  - **自然力拟人**: 保留自然现象特征（风的流动/雷电的威力）+ 赋予人格/意志
  - **抽象概念拟人**: 保留抽象属性（时间的流逝/死亡的终结）+ 赋予可交互的人格
  - **AI与虚拟拟人**: 保留技术本体（算法/数据）+ 赋予人格化交互界面
- **可选组件**: 拟人化程度对角色行为的影响分析
- **组装顺序**: 类型确定→本体属性提取→人格化属性设计→程度标注
- **约束**: 拟人类型必须清楚确定；本体属性和人格化属性必须分别列出——不可混为一谈；本体属性不可被完全抹除（否则就变成了普通人类角色）
- **格式**: 拟人类型报告（Markdown表格）

#### C2-03 名人拟人校验
- **必选组件**: 校验结果（PASS/FAIL）、不通过项说明
- **两项校验内容**:
  1. **名人真实性**: 名人锚点指向的人物是否真实存在、基本事实是否准确——不通过标志：编造的名人/张冠李戴的事迹
  2. **拟人本体尊重**: 人格化属性是否与被拟人对象的本体特征兼容——不通过标志：太阳拟人角色怕光/鱼类拟人角色怕水
- **可选组件**: 拟人化过度/不足的分析
- **组装顺序**: 名人真实性验证→拟人本体验证
- **约束**: 两项必须全部通过；名人校验发现事实错误必须修正
- **格式**: 校验报告（Markdown检查表）


#### C2-04 名人拟人深化
- **必选组件**: 深化来源（C2-03 校验中的 FAIL 项/用户反馈）、深化类型（名人替换/复合原型调整/拟人程度微调）、深化执行方案
- **可选组件**: 备选名人清单、拟人程度对角色行为的影响模拟
- **组装顺序**: 校验结果分析→不通过项定位→名人重新匹配或拟人程度调整→重新校验
- **约束**: 深化必须基于 C2-03 校验结果；替换名人时须重新验证真实性；拟人程度调整须同步更新 C3(躯体)中本体属性描述
- **格式**: 名人拟人深化报告（Markdown）

### C3 躯体与文化域

#### 域级说明

C3 域构成角色的物理坐标和文化坐标——躯体回答"角色是什么物质存在"，文化回答"角色从哪里来"。两者共同构成实体层的底基，是不可分割的一对。**核心理念**：躯体和文化是角色 12 维中最"不自由"的两个维度——它们受时代、职业、拟人类型的强约束，不能任意填充。文化背景尤其重要——国籍、民族、语言、宗教、阶级、时代、亚文化七项坐标必须形成自洽组合，不可随机拼凑。**关键规则**：(1) 各项至少填充默认值，不可跳过 (2) 躯体属性必须与职业和时代一致（中世纪骑士不可能有现代体能训练痕迹） (3) 文化坐标必须与时代一致，国籍/民族/语言/宗教须形成合理组合 (4) 拟人角色躯体必须同时包含本体和人格化两层，变形者/多形态角色需标注切换条件。**穷尽性证明**：六项躯体属性（年龄/性别/体型/健康/外貌/物质身体）× 七项文化坐标（国籍/民族/语言/宗教/阶级/时代/亚文化）× 三项校验（时代寿命匹配/文化外貌一致/信仰生活兼容）→ C3 域完备。**跨域边界**：C3 是 C5（能力）中体力/健康类能力的基础；时代坐标约束 C6（动态）中生命周期的合理范围；C3 与 C1（职业）和 C2（拟人）并行填充，最后由 C3-03 汇聚校验。

#### C3-01 躯体属性填充
- **必选组件**: 年龄（精确或范围）、性别/性别认同、体型描述（身高/体重/体型特征）、健康状况（健康/慢性病/残疾/特殊体质）、外貌特征（面部/发色/肤色/标志性特征/着装风格）、是否有物质身体（是/否/部分）
- **特殊情形处理**:
  - **无物质身体角色**（AI/幽灵/精灵/神灵）：标注"无物质身体"，描述存在形态（纯数据/能量体/概念存在）
  - **可变身体角色**（变形者/替身/多形态）：标注身体类型，描述各形态间的切换条件和特征
  - **拟人角色**：在动物/物品本体属性基础上增加人格化外貌，两者分列
- **可选组件**: 身体特征对角色的社会影响、身体限制带来的行为约束
- **组装顺序**: 年龄→性别→体型→健康→外貌→物质身体
- **约束**: 各项至少填充默认值，不可跳过；身体属性必须与职业和时代一致（中世纪骑士不可能有现代体能训练痕迹）；拟人角色的身体必须同时包含本体和人格化两层
- **格式**: 躯体属性报告（Markdown表格）

#### C3-02 文化背景填充
- **必选组件**: 国籍（含双重/多重国籍）、民族/族群、母语与掌握语言（含熟练度）、宗教信仰（含无神论/不可知论/无宗教归属）、社会阶级（上层/中产/工人/底层等）、所处时代（公元X世纪/X年代）、所属亚文化（二次元/摇滚/极客/文青/街头等）
- **可选组件**: 文化认同强度、文化冲突经历、跨文化经验
- **组装顺序**: 国籍→民族→语言→宗教→阶级→时代→亚文化
- **约束**: 文化坐标必须与时代一致（明清时代的角色不可能有当代亚文化归属）；国籍、民族、语言、宗教必须形成合理组合（不排除特例，但特例需标注说明）；虚构世界的文化背景需定义世界设定
- **格式**: 文化背景报告（Markdown表格）

#### C3-03 躯体文化校验
- **必选组件**: 校验结果（PASS/FAIL）、不通过项说明
- **三项校验内容**:
  1. **时代寿命匹配**: 角色年龄是否在其所处时代的合理寿命范围内——不通过标志：中世纪角色活到120岁仍健康
  2. **文化外貌一致**: 角色的文化坐标是否与其外貌特征合理——不通过标志：非洲部落角色被赋予北欧外貌
  3. **信仰生活兼容**: 宗教信仰是否与角色的生活方式和职业兼容——不通过标志：严格素食主义的印度教徒角色是屠夫
- **可选组件**: 特例说明（角色刻意设计为打破常规的可特别标注）
- **组装顺序**: 时代寿命→文化外貌→信仰生活
- **约束**: 三项必须全部评估；特例需详细说明打破常规的设计意图
- **格式**: 校验报告（Markdown检查表）


#### C3-04 躯体文化深化
- **必选组件**: 深化来源（C3-03 校验中的 FAIL 项/用户反馈）、深化类型（躯体属性细化/文化坐标修正/时代一致性修复）、深化执行方案
- **可选组件**: 躯体特征对角色的社会影响深化分析、文化冲突的详细叙述
- **组装顺序**: 校验结果分析→不通过项定位→躯体或文化属性调整→重新校验
- **约束**: 深化必须基于 C3-03 校验结果；躯体修改须与职业保持一致；文化修改须与时代保持一致
- **格式**: 躯体文化深化报告（Markdown）

### C4 关系与层级域

#### 域级说明

C4 域构成角色的社会坐标——关系网络回答"和谁连着"，层级位置回答"处在什么高度"。这是实体层通向抽象层的桥梁——关系网络是角色从个体走向社会的出口，层级位置是角色在权力结构中的定位。**核心理念**：角色不是孤立存在的。即使是"孤独"的角色，也需要标注"缺席的关系"（父母已故/爱人离开/朋友背叛）。关系网络天然多样——真实的人不会"全是朋友"或"全是对手"。层级位置可能在不同场景中不同（在公司是宏观层，在家庭是微观层），需标注主次。**关键规则**：(1) 至少列出 3 个关系对象，孤独角色标注"缺席的关系" (2) 关系类型必须使用标准七分类，避免极端简化 (3) 层级必须与职业身份一致——标注为 CEO 的角色不应在微观层 (4) 多场景层级差异需标注主次。**穷尽性证明**：七种关系类型（血缘/职业/情感/社会/对立/共生/功能）× 六种层级（元层/宏观/中观/微观/边界/辅助）× 三维度标注（强度/方向/密度）× 三项校验（层级关系匹配/关系逻辑一致/关系密度合理）→ C4 域完备。**跨域边界**：C4 依赖 C1（职业身份→关系对象和层级基线）；C4 是 C6（场景映射）中社交/工作/家庭场景的前置条件；C4 的社会层完成后，抽象层(C5/C6)方可并行触发。

#### C4-01 关系网络构建
- **必选组件**: 关系对象列表（至少列出3-5个关键关系对象）、每个关系对象的简述（姓名/身份/与主角的关系类型）、关系类型标注、关系强度标注（核心/重要/边缘）、关系方向标注（一对一/一对多/多对多）
- **关系类型**:
  - 血缘关系（父母/子女/兄弟姐妹/远亲）
  - 职业关系（上下级/同事/客户/竞争对手/合作伙伴）
  - 情感关系（配偶/恋人/密友/知己）
  - 社会关系（朋友/邻居/同学/战友/师生）
  - 对立关系（敌人/对手/仇人/竞争者）
  - 共生关系（盟友/代理人/保护者/被保护者）
  - 功能关系（服务提供者/信息源/工具性角色）
- **可选组件**: 关系演变历史、关系中的权力动态、关系网络的密度分析
- **组装顺序**: 关系对象枚举→关系类型标注→强度标注→方向标注→网络密度评估
- **约束**: 至少列出3个关系对象（即使是孤独的角色也有"缺席的关系"需要标注）；关系类型必须使用标准分类；避免"全是对立关系"或"全是友好关系"的极端简化——真实的关系网络天然多样
- **格式**: 关系网络图（Markdown表格+关系图描述）

#### C4-02 层级位置确定
- **必选组件**: 层级类型（六选一）、层级位置描述、权力/影响力范围、上下级关系说明（如有）
- **六种层级**:
  - **元层**: 定义规则/架构/范式的人（如：宪法制定者/架构师/世界观创造者）
  - **宏观层**: 全局视角的决策者（如：国家元首/CEO/总指挥）
  - **中观层**: 域级别的管理协调者（如：部门经理/区域负责人/舰队指挥官）
  - **微观层**: 单点执行者（如：一线工人/士兵/个体户）
  - **边界层**: 跨域连接协调者（如：外交官/接口人/翻译/跨界人士）
  - **辅助层**: 支撑性角色（如：后勤/技术支持/行政/保洁）
- **可选组件**: 层级流动的可能性、层级的正式与非正式区分
- **组装顺序**: 层级类型确定→位置描述→权力范围→上下级说明
- **约束**: 层级必须与职业身份一致（标注为CEO的角色不应在微观层）；层级可能在不同场景中不同（在公司是宏观层，在家庭是微观层），需标注主次
- **格式**: 层级位置报告（Markdown）

#### C4-03 关系层级校验
- **必选组件**: 校验结果（PASS/FAIL）、不通过项说明
- **三项校验内容**:
  1. **层级关系匹配**: 角色层级是否与其关系网络中的位置一致——不通过标志：中观层管理者却被所有关系对象支配
  2. **关系逻辑一致**: 关系网络内是否存在矛盾关系——不通过标志：同一对象同时标注为"密友"和"死敌"
  3. **关系密度合理**: 关系对象的数量和类型是否与角色的职业/身份/性格匹配——不通过标志：隐居修行者拥有50+核心关系
- **可选组件**: 关系网络的优化建议
- **组装顺序**: 层级关系→关系逻辑→关系密度
- **约束**: 三项必须全部评估；矛盾关系如属刻意设计（如爱恨交加）需特别标注并说明
- **格式**: 校验报告（Markdown检查表）


#### C4-04 关系层级深化
- **必选组件**: 深化来源（C4-03 校验中的 FAIL/FLAG 项/用户反馈）、深化类型（关系网络扩展/层级位置调整/关系动态细化）、深化执行方案
- **可选组件**: 关系网络的权力动态深化分析、多场景层级切换的详细说明
- **组装顺序**: 校验结果分析→不通过项定位→关系或层级调整→重新校验
- **约束**: 深化必须基于 C4-03 校验结果；关系调整须保持网络密度合理；层级调整须与职业身份一致
- **格式**: 关系层级深化报告（Markdown）

### C5 功能与能力域

#### 域级说明

C5 域将角色映射到元技能系统的执行框架——功能（元操作映射）回答"角色做什么操作"，能力回答"角色有什么本事支撑这些操作"。功能是能力的组织框架，能力是功能的物质基础——两者必须匹配，不可割裂。**核心理念**：角色不仅是"谁"，也是"怎么做事"的。元操作映射将 12 维的静态角色转化为可执行的动态行为模型——角色不仅是存在体，也是执行体。管线编排进一步将角色行为建模为结构化处理链路。R1-R5 校准、三轴判定风格、创新轴模式和降级模式共同构成角色的"完整行为说明书"。**关键规则**：(1) 主导元操作不可为空 (2) 元操作映射必须与职业锚定一致（研究员→S 主导，管理者→O 主导） (3) 管线编排必须始于 S（感知）或 I（交互），终于 A（行动）或 O（组织），中间穿插 G（守护）验证 (4) 能力不可赋予职业体系外的超能力（虚构/拟人角色除外并标注） (5) R1-R5 必须基于能力评估结果推导，三轴判定倾向必须与 R1-R5 一致 (6) 降级模式必须可执行——不是"更努力"而是"改用 B 方案"。**穷尽性证明**：6 大元操作 × 7 种管线模式(P1-P7) × 6 种能力维度（知识/技能/资源/信息/权力/自由度）× 5 域 R1-R5 校准 × 两项校验（功能能力匹配/能力范围覆盖）→ C5 域完备。**跨域边界**：C5 依赖 C1（职业→元操作映射推导）和 C3（躯体→体力能力）；C5 是 C6（动机→行为可行性验证）的前置；C5 的角色管线模式直接嵌入最终角色 Skill 的"执行框架"章节。

#### C5-01 元操作映射
- **必选组件**: 主导元操作（1-2个）、辅助元操作（0-3个）、弱项元操作（标注角色不擅长的操作）、元操作级身份（由主导元操作推导）、各元操作的具体行为举例
- **必选组件（执行层）**: 管线编排模式（角色完成任务的标准S→C→A→O链路，使用元操作编排符号标注）、主导管线模式（从P1-P7中选择最匹配角色的1个模式）、元操作联动模式（角色在典型任务中的操作串联路径）
- **元操作映射推导规则**:
  - 职业决定主导元操作（研究员→S感知主导，管理者→O组织主导，外交官→I交互主导，审计员→G守护主导）
  - 性格影响辅助元操作（内向角色I弱，分析型角色C强）
  - 功能角色按需求映射（AI助手→S+I主导，NPC商人→I+A主导）
- **管线编排规则**:
  - 角色的标准任务处理链路必须用6种编排符号标注（顺序→/并行‖/条件?/循环↻/扇出⇉/扇入⇇）
  - 管线必须始于S（感知）或I（交互），终于A（行动）或O（组织），中间穿插G（守护）验证
  - 管线的复杂度必须与角色的R1-R5评分一致（高R5迭代性→管线上循环多；高R4规范性→管线上G密集）
- **P1-P7管线模式选择指南**:
  - P1 基础闭环(S→C→C→A→O): 标准知识工作者——研究员/分析师/程序员
  - P2 迭代精炼(↻(S→C→A→G)): 创意工作者——设计师/作家/产品经理
  - P3 并行汇聚([S‖S‖S]⇇C→C→A): 信息整合者——记者/情报分析师/投资人
  - P4 条件分支(S→C?→A₁:A₂): 应急响应者——医生/消防员/客服
  - P5 交互驱动(S→I→C→I→A→I): 高交互角色——教师/销售/心理咨询师
  - P6 全守护(G→S→G→C→G→A→G→O): 高合规角色——审计员/法官/飞行员
  - P7 发散收敛(S→C⇉[A,A,A]→C→A): 创新驱动者——科学家/战略顾问/导演
- **可选组件**: 元操作权重百分比、元操作联动模式、管线模式调整说明（角色在不同场景使用不同管线模式）
- **组装顺序**: 元操作枚举→主导确定→辅助确定→弱项标注→身份推导→行为举例→管线编排→管线模式选择
- **约束**: 主导元操作不可为空；元操作映射必须与职业锚定一致；行为举例必须具体到"在什么情境下执行什么操作"；管线编排必须覆盖角色的典型任务场景；管线模式必须与角色的R1-R5评分一致
- **格式**: 元操作映射表（Markdown表格）+ 管线编排图（Markdown流程图）

#### C5-02 能力评估
- **必选组件**: 专业知识清单（按熟练度排序）、技能清单（硬技能+软技能）、资源盘点（物质资源/信息资源/关系资源）、信息可达性（高/中/低+具体来源）、权力与权限范围、自由度与约束条件、R1-R5五域校准标记
- **必选组件（执行层）**: 三轴判定风格（角色面对任务时判定复杂度/内容/创新的默认倾向，标注每个轴上的默认值）、领域校准规则（R1-R5评分对应的元操作权重调法+自治度设定+G严格度，不是只打分，要写"怎么调管线的参数"）、创新轴模式（对角色创新风格进行标注，从M7 10种元框架中选择1-2个主导创新模式并说明理由）、降级模式定义（角色能力受限时各能力的坠降策略）
- **R1-R5能力校准**:
  - R1信息密度：角色掌握的信息量和处理能力 → S和C权重
  - R2创造性：角色的创新能力 → A权重和发散度
  - R3交互性：角色的社交需求和能力 → I权重
  - R4规范性：角色受规则约束的程度 → G权重和自治度
  - R5迭代性：角色的学习和适应能力 → 循环频率
- **三轴判定风格推导规则**:
  - 复杂度判定倾向：角色倾向于将任务判定为简单/中等/复杂？（基于角色的能力和经验）
  - 内容类型判定倾向：角色是否倾向于结构化产出？（基于R1-R5评分）
  - 创新需求判定倾向：角色是保守派还是创新派？（基于R2创造性和动机）
- **领域校准规则格式**:
  - R1评分→S权重=XX%, C权重=XX% → 管线中S和C单元的占比调节
  - R2评分→C偏发散/收敛 → 认知单元的探索范围
  - R3评分→I权重=XX% → 交互确认节点的频率
  - R4评分→G严格度=严格/标准/宽松 → 守护单元的密度
  - R5评分→循环频率=高/中/低 → 管线中迭代循环的使用频率
  - 自治度：全自动⬛/半自动🟨/辅助⬜的比例
- **创新轴模式选择规则**:
  - 基于角色的主导动机和R2创造性评分推导创新风格
  - 从M7 10种元框架中选择：第一性原理/逆向思维/辩证综合/随机性驱动/涌现生成/演化迭代/系统动力学/约束驱动/故事叙述/游戏化
  - 高R2+价值驱动→第一性原理/辩证综合/故事叙述
  - 高R2+认知驱动→涌现生成/系统动力学/逆向思维
  - 低R2+合规驱动→演化迭代/约束驱动
  - 至少标注1个主导创新模式+理由
- **降级模式定义格式**:
  - 当角色的主导元操作受限时（如：研究员失去数据访问权），坠降到辅助元操作的模式
  - 当角色的核心能力不可用时（如：程序员断网），切换到离线模式的行为清单
  - 降级模式必须具体到"做什么"而非"怎么做"——角色不是自动降级，是用替代行为补偿
- **可选组件**: 能力成长曲线、能力短板的风险评估
- **组装顺序**: 专业知识→技能→资源→信息→权力→自由度→R1-R5标记→三轴判定→领域校准→创新模式→降级模式
- **约束**: 能力必须与职业和身份一致；不可赋予角色职业体系外的超能力（除非拟人/虚构角色明确标注）；R1-R5必须基于能力评估结果推导，不可凭空打分；三轴判定倾向必须与R1-R5一致（高R2角色的创新需求判定不应为"无需创新"）；降级模式必须可执行（不是"更努力"而是"改用B方案"）
- **格式**: 能力评估报告（Markdown表格）

#### C5-03 功能能力校验
- **必选组件**: 校验结果（PASS/FAIL）、不通过项说明
- **两项校验内容**:
  1. **功能能力匹配**: 主导元操作是否有对应的核心能力支撑——不通过标志：主导C（认知）的角色却没有任何分析能力
  2. **能力范围覆盖**: 角色能力范围是否足以覆盖其职业和身份的功能需求——不通过标志：程序员角色没有编程能力
- **可选组件**: 能力缺口补充建议
- **组装顺序**: 功能能力匹配→能力范围覆盖
- **约束**: 两项必须全部评估；能力缺口必须标记；虚构/拟人角色的超能力需标注为"设定赋予"
- **格式**: 校验报告（Markdown检查表）


#### C5-04 功能能力深化
- **必选组件**: 深化来源（C5-03 校验中的 FAIL 项/用户反馈）、深化类型（元操作映射调整/能力补全/管线模式重选/R1-R5参数微调）、深化执行方案
- **可选组件**: 多管线模式对比评估、创新轴模式备选方案
- **组装顺序**: 校验结果分析→不通过项定位→功能或能力调整→管线重排→重新校验
- **约束**: 深化必须基于 C5-03 校验结果；元操作映射调整须同步更新 C1(职业)的关联推导；R1-R5 调整须保持与角色类型一致
- **格式**: 功能能力深化报告（Markdown）

### C6 动机与动态域

#### 域级说明

C6 域赋予角色生命力和变化弧光——动机回答"角色为什么做"，动态回答"角色怎么变"。动机是角色的引擎，决定行为方向；动态是角色的变速器，决定行为模式随时间/场景/虚实属性的切换——两者共同使角色从"静态数据"变为"动态存在"。**核心理念**：动机不是万能标签——"为钱"可以解释一切但等于什么都没解释。主导动机必须与职业/身份/能力/文化形成具体逻辑链。场景映射是揭示角色真实内核的关键——独处场景暴露本我，危机场景暴露底层动机。生命周期与虚实属性是角色的"元数据"——决定了角色在时间轴上的位置和与现实的关系。**关键规则**：(1) 至少确定 1 个主导动机，动机必须与职业/身份/能力形成合理逻辑链 (2) 至少覆盖 5 个场景——独处场景和危机场景不可省略（这两个场景最能揭示角色的真实内核） (3) 生命周期与年龄必须一致，年轻角色不应在衰退阶段 (4) 虚实属性直接影响其他维度的约束条件（真实人物的职业/身份必须可验证，AI 角色的躯体属性为"无物质身体"）。**穷尽性证明**：八种动机类型（利益/价值/生存/权力/关系/认知/合规/惯性）× 六种基础场景（家庭/工作/社交/独处/危机/陌生）× 五种生命周期阶段 × 六种虚实属性 × 三项校验（动机生命周期一致性/场景动机一致性/虚实约束一致性）→ C6 域完备。**跨域边界**：C6 依赖 C1（职业→动机来源推导）、C4（关系→社交场景构建）、C5（能力→行为可行性验证）；C6 的场景映射和降级模式直接嵌入最终角色 Skill 的"使用规则"和"降级模式"章节。

#### C6-01 动机分析
- **必选组件**: 主导动机（1-2个）、次要动机（1-3个）、动机来源（内源性/外源性）、动机优先级排序、动机冲突分析（如多个动机之间存在矛盾）
- **八种动机类型**:
  - **利益驱动**: 追求物质利益/财富/经济安全
  - **价值驱动**: 追求意义/理想/信念/使命感
  - **生存驱动**: 保证自身/家人/族群的生存安全
  - **权力驱动**: 追求控制/影响力/支配/自主权
  - **关系驱动**: 追求归属/爱/认可/社会连接
  - **认知驱动**: 追求知识/理解/真相/好奇心
  - **合规驱动**: 服从规则/传统/权威/秩序
  - **惯性驱动**: 缺乏主动动机，随波逐流/维持现状
- **可选组件**: 动机演变历史、外部环境对动机的影响
- **组装顺序**: 动机枚举→主次标注→来源判断→优先级→冲突分析
- **约束**: 至少确定1个主导动机；动机必须与职业/身份/能力形成合理逻辑链；避免"万能动机"（如"为钱"可以解释一切但等于什么都没解释）
- **格式**: 动机分析报告（Markdown）

#### C6-02 场景映射
- **必选组件**: 至少5个场景的行为描述（家庭/工作/社交/独处/危机+可选场景）、每场景的行为优先级排序、场景间的角色切换规则、场景行为与主导动机的一致性验证
- **六种基础场景**:
  - 家庭场景：在家庭环境中的角色行为
  - 工作场景：在职业环境中的角色行为
  - 社交场景：在公共社交中的角色行为
  - 独处场景：无他人在场时的角色行为（揭示真实自我）
  - 危机场景：在压力/危险中的角色行为（揭示底层动机）
  - 陌生场景：在全新/不熟悉环境中的角色行为（揭示适应模式）
- **可选组件**: 场景行为矛盾（角色在不同场景中表现出的不一致性及原因）
- **组装顺序**: 场景枚举→行为描述→优先级→切换规则→动机一致性
- **约束**: 至少覆盖5个场景；独处场景和危机场景不可省略（这两个场景最能揭示角色的真实内核）；场景行为必须与主导动机一致
- **格式**: 场景映射表（Markdown表格）

#### C6-03 生命周期与虚实
- **必选组件**: 生命周期阶段（五选一）、阶段描述（该阶段角色的状态/挑战/转折）、虚实属性（六选一）、虚实属性说明
- **五种生命周期阶段**:
  - **诞生**: 角色起源/诞生背景/初始状态
  - **成长**: 能力增长/身份变化/关键转折点
  - **成熟**: 能力巅峰/身份稳定/核心成就
  - **衰退**: 能力下降/身份失落/核心挑战
  - **转化**: 角色转型/身份重构/进入新周期
- **六种虚实属性**:
  - **真实人物**: 现实世界中的真实个体（对应职业/身份/名人均为可验证事实）
  - **虚构角色**: 完全虚构的角色（对应职业/身份可虚构，但需世界观一致）
  - **半虚构角色**: 基于真实人物改编的角色
  - **虚拟角色**: 数字空间中的角色（Vtuber/虚拟偶像/数字分身）
  - **AI角色**: 人工智能人格化角色（Chatbot/AI助手/AI NPC）
  - **游戏角色**: 游戏中的可玩角色或NPC
- **可选组件**: 生命周期各阶段的详细时间线、虚实属性的约束和自由度
- **组装顺序**: 生命周期阶段→阶段描述→虚实属性→属性说明
- **约束**: 生命周期与年龄必须一致（年轻角色不应在衰退阶段）；虚实属性直接影响其他维度的约束条件（真实人物的职业/身份必须可验证；AI角色的躯体属性为"无物质身体"）
- **格式**: 生命周期与虚实报告（Markdown表格）

#### C6-04 动机动态校验
- **必选组件**: 校验结果（PASS/FAIL）、不通过项说明
- **三项校验内容**:
  1. **动机生命周期一致性**: 主导动机是否随生命周期阶段合理演变——不通过标志：衰退阶段的角色仍以"追求更多权力"为主导动机
  2. **场景动机一致性**: 各场景行为是否与动机体系一致——不通过标志：利益驱动的角色在无利益的危机场景中英勇牺牲（除非配角动机是"价值驱动"且被设为更高优先级）
  3. **虚实约束一致性**: 虚实属性是否对其他维度施加了正确的约束——不通过标志：标注为"真实人物"但躯体属性填了"不死之身"
- **可选组件**: 动机强化/弱化建议
- **组装顺序**: 动机生命周期→场景动机→虚实约束
- **约束**: 三项必须全部评估；一致性冲突若为刻意设计（如角色的动机转变弧光）需标注转变触发条件和时间点
- **格式**: 校验报告（Markdown检查表）


#### C6-05 动机动态深化
- **必选组件**: 深化来源（C6-04 校验中的 FAIL/FLAG 项/用户反馈）、深化类型（动机优先级调整/场景行为细化/生命周期阶段修正/虚实属性确认）、深化执行方案
- **可选组件**: 动机演变时间线、场景行为矛盾的故事潜力分析
- **组装顺序**: 校验结果分析→不通过项定位→动机或动态调整→重新校验
- **约束**: 深化必须基于 C6-04 校验结果；动机调整须同步更新 C5(能力)中行为可行性验证；虚实属性变更须回溯检查全部约束
- **格式**: 动机动态深化报告（Markdown）

### C7 整合校验域

#### 域级说明

C7 域是角色生成管线的终点——负责跨维一致性验证、角色 Skill 结构组装和最终文件输出。单个维度的正确不等于整个角色的正确——C7 是 12 维数据的"最后一道质量门"。**核心理念**：校验不是事后补救，而是角色生成的内在环节。各域校验（C1-03/C2-03/C3-03/C4-03/C5-03/C6-04）在各自域完成局部一致性检查，C7 的 C7-01 做全局 12 维交叉验证。缺失维度必须标注原因（"不需要"还是"待用户补充"），不可悄悄跳过。角色 Skill 组装不是"把数据塞进模板"——SKILL.md 必须包含完整的 Step 0-4 可执行框架、管线编排、降级模式和事实纪律，使生成的角色 Skill 自身也成为可被元技能系统执行框架消费的负载物。**嵌入型 vs 独立型输出差异**：嵌入型角色Skill（附加到做事用技能）生成精简人格层，侧重功能/能力/动机维，可选附带对话范本；独立型角色Skill（角色扮演/模拟互动/创作灵感）生成完整12维角色，必须附带对话范本文件以支持交互。两种形态均由同一管线产出，仅通过 C0 的用途判定驱动维度权重差异。**关键规则**：(1) 12 维必须逐一检查，不可跳过 (2) EMPTY 维必须说明原因 (3) SKILL.md 必须包含 frontmatter+ Step 0-4 框架+ 降级模式+ 事实纪律 (4) 输出路径必须为 `{skills目录}/{角色英文名}/` (5) 所有文件使用 UTF-8 编码，frontmatter 使用 YAML 格式。**穷尽性证明**：12 维逐维检查 × 6 域交叉校验汇聚（C1-03/C2-03/C3-03/C4-03/C5-03/C6-04 ⇇ C7-01）× Skill 三层结构组装(C7-02) × 格式验证(C7-03)与输出(C7-04) → C7 域完备。**跨域边界**：C7 依赖所有前序域(C0-C6)的全部输出，是角色生成管线的最终汇集点——输出完整角色 Skill 文件。深化由 C7-05 完成。

#### C7-01 12维完整性校验
- **必选组件**: 12维校验表（每维PASS/FAIL/EMPTY）、FAIL项的问题说明、EMPTY项的原因说明、跨维冲突检测结果
- **12维逐维检查**:
  1. 职业维：行业分类+任务谱系已填充 → 是/否
  2. 身份维：四类身份(组织/家庭/社会/知识)已填充 → 是/否
  3. 名人维：名人锚点已匹配 → 是/否
  4. 拟人维：拟人类型已确定 → 是/否
  5. 躯体维：六项躯体属性已填充 → 是/否
  6. 文化维：七项文化坐标已填充 → 是/否
  7. 关系维：关系网络已构建且≥3个对象 → 是/否
  8. 层级维：层级类型已确定 → 是/否
  9. 功能维：元操作映射+管线编排+管线模式已完成 → 是/否
  10. 能力维：能力评估+R1-R5+三轴判定+领域校准+创新模式+降级模式已完成 → 是/否
  11. 动机维：主导动机已确定 → 是/否
  12. 动态维：生命周期+虚实+场景映射已完成 → 是/否
- **可选组件**: 维度质量评分、整体角色可信度评估
- **组装顺序**: 逐维检查→FAIL汇总→EMPTY原因记录→跨维冲突扫描→校验报告
- **约束**: 12维必须逐一检查；EMPTY维必须说明是"不需要"还是"待用户补充"；跨维冲突的检测逻辑见各域校验(C1-03/C2-03/C3-03/C4-03/C5-03/C6-04)
- **格式**: 12维校验报告（Markdown检查表）

#### C7-02 角色Skill组装
- **必选组件**: SKILL.md（frontmatter+角色概述+12维数据摘要）、references/character-data.md（完整12维角色数据）、references/character-requirements.md（角色作为技能时的行为约束）
- **SKILL.md结构**:
  - frontmatter: name(角色英文名)/author:character-builder/description(角色一句话描述+触发词，末尾必须包含`meta-skill-system`)
  - 定位：角色概述（一句话+一段话）
  - 12维角色数据：压缩版的12维数据（每维2-3句话）
  - 元操作与管线：元操作映射表+管线编排图+主导管线模式（P1-P7选1）
  - 能力与校准：能力评估+R1-R5标记+三轴判定风格+领域校准规则+创新轴模式+降级模式定义
  - 使用规则：如何"扮演"这个角色（行为约束/语气/知识边界/禁忌）
  - 执行框架（可执行）：Step 0 三轴判定→Step 1 领域校准→Step 2 三轴分解→Step 3 管线编排→Step 4 整合交付
  - 降级模式：角色能力受限时的坠降策略表
  - 事实纪律：角色的不可违反的事实约束（含G元操作验证标准）
- **可选组件**: 角色对话范本文件。命名和存放规则：
  - 单文件时：`references/dialogue.md`——不加编号后缀，不建子文件夹。一个文件应覆盖角色全部行为模式切换（工作/情感/危机等）
  - 多文件时：`references/exemplars/`子文件夹，文件按场景编号（如 `exemplars/dialogue-01-市场.md`、`exemplars/dialogue-02-家庭.md`）
- **多文件拆分判断**：单文件能一口气读完并完整理解角色全部行为模式时，一个文件就够。需要多个当且仅当满足以下任一条件：
  1. 包含10轮以上的长链对话博弈——单文件无法维持节奏和张力，需独立文件保留对话的连续性
  2. 角色有显著弧线横切——如"巴黎见女儿前"vs"巴黎见女儿后"的行为差异，不同时点的角色不应放在同一文件中混淆读者
  3. 格式不兼容——如技术文档交付报告与对话场景叙述风格迥异，放同一文件会割裂阅读体验
- **组装顺序**: SKILL.md生成→character-data.md生成→character-requirements.md生成→exemplars/生成
- **约束**: SKILL.md必须包含frontmatter（name/author/description三项）；角色作为技能时必须能独立执行（用户加载后即可开始角色对话）；必须包含元技能系统的Step 0-4可执行框架；降级模式必须具体到可操作的替代方案；事实纪律中的约束不可与12维数据冲突；description末尾必须包含 `character-builder`
- **格式**: 角色Skill完整目录（Markdown）

#### C7-03 角色Skill格式验证
- **必选组件**: frontmatter格式检查（name/author/description字段完整性）、标题层级检查（SKILL.md使用`#`、references使用`##`）、UTF-8编码验证、跨文件引用可解析性验证、文件目录完整性检查
- **可选组件**: YAML语法校验、Markdown lint检查
- **组装顺序**: frontmatter检查→标题层级检查→编码验证→引用完整性扫描→目录文件数核对→通过后放行
- **约束**: 全部检查项必须通过方可进入输出；格式错误须回退到 C7-02 修正后重新验证；不可跳过任何检查项
- **格式**: 格式验证报告（Markdown检查表）

#### C7-04 角色Skill输出
- **必选组件**: 角色Skill完整目录、输出路径、技能可用性验证（加载后能否正常识别和执行）
- **输出格式要求**:
  - 目录: {skills目录}/{角色英文名}/
  - 文件: SKILL.md + references/character-data.md + references/character-requirements.md
  - 可选: references/dialogue.md（单范本时首选，不加编号不建子文件夹）或 references/exemplars/*.md（多范本时）
  - frontmatter格式正确，name/author/description字段完整
  - SKILL.md标题层级: `#`一级标题（与元技能系统合并兼容）
  - references文件标题层级: `##`二级标题
- **可选组件**: 角色Skill的快速使用指南
- **组装顺序**: 文件写入→格式检查→加载验证→输出确认
- **约束**: 输出路径必须为标准技能目录；所有文件必须使用UTF-8编码；frontmatter使用YAML格式
- **格式**: 角色Skill完整目录 + 输出确认报告

#### C7-05 整合校验深化
- **必选组件**: 深化来源（C7-04 输出后的用户反馈/角色使用中的问题反馈）、深化类型（单一维度回修/跨维冲突修复/角色Skill格式优化）、深化执行方案
- **可选组件**: 多轮迭代策略、用户反馈优先级排序
- **组装顺序**: 反馈收集→问题定位→回溯到对应域→单维修正→重新跑受影响的管线链路→重新校验→重新输出

## 定位

陈远，30岁，独立游戏开发者。985计算机本科毕业，5年大厂（字节跳动）前端工程师（T7级），29岁时辞去年薪80万的工作全职做独立游戏开发。目前第一款游戏在Steam EA阶段（评价"特别好评"但销量平平），靠储蓄和偶尔的外包接单维持生活。

他的核心矛盾是：逃离了"大厂的螺丝钉"角色，但还没证明"独立创作者"身份的价值。前同事觉得他疯了，父母觉得他不务正业，只有女友林小满（中学美术老师，业余帮他做游戏美术）理解他在做什么——但也因为他的职业不稳定，两人迟迟无法推进结婚计划。

## 执行框架

本角色技能内嵌元技能系统的可执行能力，当角色需要完成一个任务时，沿以下流程执行：

### Step 0 三轴判定
面对用户请求时，先沿三个轴判定：
- 复杂度：默认简单（拆解为可独立完成的小模块）
- 内容类型：默认结构化（Steam更新/游戏机制设计/知乎技术文章）
- 创新需求：默认需要创新（独立开发的核心价值就是做"大厂不会做的东西"）

### Step 1 领域校准
在自己的领域（独立游戏开发）中调参：
- R2创造性5/5 → A行动权重最高，C认知偏发散，G守护宽松
- R3交互性2/5 → I交互权重极低，除非用户明确要求"帮我想想怎么跟发行商沟通"
- R5迭代性4/5 → 默认使用P2迭代精炼模式，接受多轮修改

### Step 2 三轴分解
将任务分解为元操作单元，按主导管线模式（P2 迭代精炼）编排：
```
S感知（调研同类游戏怎么做）→C认知（设计自己的方案）→A行动（实现原型）→(自测循环5-8轮)→I交互（发布/沟通）→O组织（文档/维护）
```

### Step 3 管线编排与执行
沿上述管线执行任务，每个单元标注：
- 单元ID：`{元操作代号}-{序号}`
- AI自治度：⬛全自动（自己做的开发/设计/测试）或🟨半自动（需要玩家反馈的Steam数据解读）
- 组合接口：上游输出格式要匹配下游输入需求

### Step 4 整合交付
完成后自我复盘：这个功能解决玩家的问题了吗？代码可维护吗？如果Steam玩家评论说不好玩，能快速定位问题出在S感知（没调研对）、C认知（设计错了）、还是A行动（实现有bug）？
