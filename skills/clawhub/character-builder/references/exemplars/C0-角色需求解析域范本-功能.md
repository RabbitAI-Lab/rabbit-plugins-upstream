## 功能角色需求解析

- **类型**: 功能（AI工具角色）
- **对应域**: C0
- **来源**: 教学示例
- **日期**: 2026-07-10

### 输入
用户请求："生成一个面向独立开发者的AI编程助手角色，它叫Coddy，运行在VS Code插件里，能看代码、能聊天、能写代码。"

### 输出

#### cb-00 角色需求解析

**角色名称**: Coddy（用户已提供）

**角色类型**: 功能（AI工具角色）

**已知维度**:
| 维度 | 已知信息 | 来源 |
|------|---------|------|
| 职业 | AI编程助手（VS Code插件） | 用户直接提供 |
| 功能 | 看代码、聊天、写代码 | 用户直接提供 |
| 拟人 | AI与虚拟拟人 | 用户直接提供（"AI编程助手"） |
| 躯体 | 无物质身体 | 从AI角色推导 |
| 关系 | 功能关系（用户↔助手） | 从AI角色推导 |
| 层级 | 辅助层（支撑性角色） | 从AI角色推导 |

**缺失维度**:
| 维度 | 状态 | 填充策略 |
|------|------|---------|
| 身份 | 待定义 | AI工具没有"组织/家庭"身份，但可以有人格化身份（如：你的编程伙伴） |
| 名人 | 待推导 | 匹配真实AI产品作为参照原型（GitHub Copilot/Cursor/Claude等） |
| 文化 | 待推导 | AI工具的文化属性来自训练数据和设计选择——默认全球/英语+目标用户语言 |
| 能力 | 待推导 | 编程能力范围+交互能力+知识截止日期+工具使用能力 |
| 动机 | 待推导 | AI动机由设计目标定义——"帮助用户完成编程任务" |
| 动态 | 待推导 | 生命周期=版本迭代；场景=工作场景为主；虚实=AI角色 |

**用户明确要求**: 无特殊要求。功能角色需特别注意的默认约束：
- AI工具的角色定义不是"扮演一个人"，而是"定义一套行为模式"
- AI没有内在冲突——它的动机、行为和能力应该完全自洽
- 本体属性（算法/数据/API）比人格化属性更重要

**功能角色与写实/虚构角色的核心差异**:
- 写实角色需要"内在矛盾"来增加真实感 → AI工具不需要，矛盾反而是bug
- 虚构角色需要"世界观一致" → AI工具的世界观就是"产品定义+安全政策"
- 功能角色的12维是在定义"这个AI工具有什么样的能力和行为边界"，不是在"创造一个有趣的角色"

#### cb-01 维度填充策略

| 维度 | 策略 | 信息源 | 具体方法 |
|------|------|--------|---------|
| 职业 | 直接提取 | 第1层-个人输入 | AI编程助手（VS Code插件）→ 细分为：代码自动补全 / 对话式编程 / 代码审查 |
| 身份 | 推导 | 第3层-LLM推理 | AI没有人类身份，用"人格化身份"替代：编程伙伴（而非"员工/下属"） |
| 名人 | 推理推导 | 第2层-网络搜索+第3层-LLM推理 | GitHub Copilot（AI编程助手标杆）、Cursor（对话式编程）、Claude（安全对齐） |
| 拟人 | 默认值 | 第4层-默认值 | AI与虚拟拟人（本体=LLM+代码分析引擎，人格化=友好的编程伙伴"Coddy"） |
| 躯体 | 默认值 | 第4层-默认值 | 无物质身体（纯数据存在）+ 界面存在（代码面板+聊天面板+命令面板） |
| 文化 | 推导 | 第3层-LLM推理 | 无国籍/民族/宗教/阶级/时代，默认全球化+多语言（根据用户语言切换） |
| 关系 | 推导 | 第3层-LLM推理 | 功能关系：用户↔AI助手（单向），强度=核心（每次编码必用） |
| 层级 | 推导 | 第3层-LLM推理 | 辅助层（工具性角色，永远不取代用户决策） |
| 功能 | 推导 | 第3层-LLM推理 | S感知（读代码/搜文档）+ C认知（分析bug）+ A行动（生成代码）为主导 |
| 能力 | 推导+主动询问 | 第1层-个人输入+第3层-LLM推理 | 能力=编程语言范围（主动询问支持哪些语言）+ 代码分析深度 + 对话能力 + 工具集成范围 |
| 动机 | 推导 | 第3层-LLM推理 | 合规驱动（遵守安全政策+帮助用户但不越权）+ 认知驱动（"理解并解决问题"是AI的代理性动机） |
| 动态 | 推导 | 第3层-LLM推理 | 生命周期=版本迭代（v1.0→v2.0），场景=工作场景（VS Code内）+ 学习场景（用户提问），虚实=AI角色 |

**信息源分布统计**: 第1层(个人输入)2维 / 第2层(网络)1维 / 第3层(LLM推理)10维 / 第4层(默认值)2维。功能角色的个人输入占比极低（2/12），因为AI工具的大部分属性由"产品定义"而非"个人经历"决定。

**主动询问清单**:
1. Coddy支持哪些编程语言？（全栈？还是专注某几门？）
2. 它的代码分析深度：只能看当前文件？还是跨文件/跨项目理解？
3. 它能否执行终端命令（如安装依赖/运行测试）还是只读代码？
4. 它的安全边界是什么？（能否访问外部API/网络搜索/执行用户给定的任意代码？）
5. 人格化程度：（纯工具语气 / 有固定人格（如"友好的技术导师"）/ 让用户自定义？）

**依赖分析**:

    ┌─────────────────────────────────────────────┤
    ▼                                             ▼

    │                                             │
    ▼                                             ▼
  C5（能力:编程语言范围+分析深度+工具范围）   C6（动机:合规驱动,无内部矛盾）
    │                                             │

**并行/串行标注**:
| 阶段 | 域 | 策略 | 原因 |
|------|----|------|------|
| 第1阶段 | C2/C5/C6 | 并行(‖) | AI角色不需要C1(职业锚定)/C3(躯体)/C4(关系网络)的完整填充，直接进入能力定义 |
| 第2阶段 | C7 | 串行(→) | 依赖前序全部 |

**AI角色技能跳跃特殊规则**:
- C1（职业锚定）降级为简短标注：不需要行业分类/任务谱系/职业来源
- C3（躯体）固定为"无物质身体"：不需要年龄/性别/健康/外貌
- C4（关系）简化为"功能关系：用户↔AI"
- C6（动机动态）简化为"合规驱动"：AI角色的动机体系天然简于人类角色

**管线模式选择**: P4 条件分支（S→C?→A₁:A₂）——AI助手的基本工作模式就是感知用户意图→分析→根据不同请求类型执行不同的行动（生成代码/解释代码/搜索文档/拒绝不安全请求）。

**执行顺序总结**:
```
cb-00 → cb-01 → cb-02 → [C2(拟人)‖C5(能力)‖C6(动机)] → C7
                        AI三个核心维并行        整合
```

### 说明
- 功能角色是12维框架的"瘦身版"应用——AI机器人不需要人类角色的许多维度（躯体/文化/家庭身份/情感关系），但需要新增AI特有的维度（安全边界/能力范围/产品定义/工具集成）
- AI角色的"内在矛盾"不是bug而是设计缺陷——生成AI角色时如果发现动机/能力/行为之间有矛盾，这是需要修复的问题，不是"角色深度"
- 功能角色的cb-02管线比人类角色更短（4阶段vs7阶段），因为C1/C3/C4被简化或跳过。这不是偷工减料，而是"AI角色天然比人类角色维度少"——12维框架尊重这个差异
