# 评审标准手册

## 概述

本手册定义PRD文档评审的详细检查项和评分标准，为评审提供统一、可量化的依据。基于大师傅餐饮系统14+1章节结构和5大核心框架原则设计，包含9大评审维度，完全聚焦于产品能力本身的质量评审。

---

## 核心框架原则（评审前提）

### 必须遵循的产品定位边界（一票否决项）
任何PRD设计违反以下定位边界原则，直接判定为不合格：
- ❌ **不是SaaS平台** - 不得设计租用服务、按月付费、多租户管理功能
- ❌ **不是多租户系统** - 一套部署=一个商户，不得设计跨租户数据隔离机制
- ❌ **不是云端强制** - 必须支持本地/私有云/公有云部署，不得强制云端
- ✅ **是开源商户系统** - 数据自主、自由部署，不得设计锁定用户的机制

### 单租户三种形态适配原则
- **单店模式**：隐藏所有组织相关功能，UI极简
- **连锁模式**：显示总部视角，支持统一配置下发
- **集团模式**：完整多级组织架构，品牌间数据隔离/打通

### 组织层级模型原则
- **四级架构**：集团(Group) → 品牌(Brand) → 区域(Region) → 门店(Store)
- **统一数据模型**：三种形态使用同一套数据模型，只是UI显示和功能开放不同
- **形态自动判断**：基于 `brand_count` + `store_count` 自动判断商户形态

### 渐进式复杂度管理框架（四层决策矩阵）
| 层级 | 决策原则 | 时间维度 |
|------|---------|---------|
| 数据模型 | 按最复杂场景建模 | 未来12个月有需求就建 |
| API层 | 接口先留着，按权限过滤 | 未来6个月可能调用就留 |
| UI层 | 按商户模式动态显隐 | 当前模式用户需要才显示 |
| MVP实现 | 按成熟度而非能力开放 | 有明确客户才实现 |
- **决策口诀**：建模必做，API预留，UI裁剪，MVP看客户

### 复杂度阈值规则
- 部分功能不按模式自动解锁，而是按实际业务规模阈值开放（如：≥3店开放批量操作）

## 维度1：章节结构完整性（权重12%）

### 1.1 14+1章节完整性检查

| 检查项 | 评分标准 | 分值 |
|-------|---------|------|
| 第1章 总览 | 模块范围 + 核心设计原则 + 版本规划完整清晰，明确遵循产品定位边界 | 1分 |
| 第2章 名词解释 | 所有专业术语有明确定义，包含三种形态的定义说明 | 0.5分 |
| 第3章 用户角色与用户故事 | 角色定义清晰，用户故事完整，覆盖三种形态的典型用户 | 1分 |
| 第4章 详细需求（P0/P1/P2） | 按优先级分级，需求清单完整，明确各形态的功能差异 | 1分 |
| 第5章 非功能性需求 | 性能、安全、兼容性等要求明确，支持本地部署场景 | 0.5分 |
| 第6章 交互流程设计 | 流程图和说明完整，包含不同形态的流程差异 | 1分 |
| 第7章 商户归属模式差异化 | 多业态适配策略清晰，明确三种形态的功能裁剪规则 | 0.5分 |
| 第8章 渐进式复杂度管理框架 | 功能准入、阈值规则、降级方案完整，遵循四层决策矩阵 | 0.5分 |
| 第9章 业务规则 | 判断逻辑、计算规则、状态流转完整，考虑不同形态的规则差异 | 1分 |
| 第10章 与已有模块的关系 | 依赖关系、影响范围明确，符合统一数据模型原则 | 0.5分 |
| 第11章 未解决问题 + 风险 | 问题清单和风险应对完整 | 0.5分 |
| 第12章 API设计规范 | 接口定义、参数、返回值清晰，遵循API预留原则 | 0.5分 |
| 第13章 数据导入导出规范 | 格式、字段映射、校验规则完整，支持本地数据自主 | 0.5分 |
| 第14章 补充需求 | 其他补充说明完整 | 0.5分 |
| 附录 数据模型设计 | 表结构、字段说明、ER图完整，按最复杂场景建模 | 1分 |
| 竞品对标分析章节 | 每个核心功能模块都有独立的竞品对标分析章节 | 0.5分 |
| 章节编号规范 | 编号连续、层级清晰 | 0.5分 |

**评分细则**:
- **优秀(11-12分)**: 14+1章节完整，所有章节内容详尽清晰，核心框架原则体现充分
- **良好(8-10分)**: 章节基本完整，少数章节细节待补充，框架原则基本遵循
- **一般(5-7分)**: 关键章节缺失，需要重点补充，框架原则体现不足
- **不足(<5分)**: 章节结构严重不完整，无法用于开发

## 维度9：竞品对标与优势提炼（权重10%）

### 核心评审目标
确保PRD是"博各家之长，避各家之短"的产物，而不是闭门造车的结果。对标分析只在内部评审版本中保留，最终交付版本需转化为独立设计。

### 9.1 竞品覆盖完整性（2分）

| 检查项 | 评分标准 | 分值 |
|-------|---------|------|
| 主流竞品覆盖 | 已覆盖行业主流竞品（美团商家、企迈、客如云、天财商龙等） | 1分 |
| 对标深度 | 每个核心功能点有至少3家竞品的对标分析 | 1分 |

### 9.2 产品能力对标分析（3分）

| 检查项 | 评分标准 | 分值 |
|-------|---------|------|
| 实现方式对比 | 对于每个核心功能，列出了竞品的实现方式 | 1分 |
| 优缺点分析 | 对比了不同竞品的优缺点 | 1分 |
| 取舍决策明确 | 明确了"取什么"和"弃什么" | 1分 |

### 9.3 优势提炼与差异化设计（3分）

| 检查项 | 评分标准 | 分值 |
|-------|---------|------|
| 亮点提炼 | 明确提炼了各家竞品的设计亮点 | 1分 |
| 短板规避 | 明确规避了竞品的明显短板和槽点 | 1分 |
| 差异化设计 | 有超越竞品的差异化设计（不仅仅是复制） | 1分 |

### 9.4 证据与标注规范（2分）

| 检查项 | 评分标准 | 分值 |
|-------|---------|------|
| 截图证据 | 关键对标点有对应竞品截图作为依据 | 1分 |
| 标注规范 | 标注了截图编号（如："参考美团-123号截图"），有版本/时间信息 | 1分 |

### 检查要求
- **必须做的**：每个核心功能模块都要有"竞品对标分析"章节
- **推荐做的**：以表格形式列出"竞品-实现方式-优缺点-我们的方案"
- **禁止的**：只说"参考竞品"但不说具体参考哪家、参考什么、怎么改进

### 与文档合规性的关系
- 评审过程中会使用竞品截图作为对标依据
- 但最终交付的CLEAN版本中**不能包含**任何竞品信息
- 对标分析的成果要转化为"独立设计"，而不是直接引用竞品

**评分细则**:
- **优秀(9-10分)**: 对标充分，优势提炼清晰，有明确的差异化设计
- **良好(7-8分)**: 有对标分析，但差异化设计不够明确
- **一般(5-6分)**: 对标覆盖不全，仅覆盖部分功能
- **不足(<5分)**: 缺少竞品对标分析，或对标不深入

**竞品对标红线**:
- 🚨 P0级问题：核心功能完全没有对标分析，闭门造车
- 🚨 P0级问题：只说"参考竞品"但无具体内容，无法评审
- ⚠️ P1级问题：对标覆盖不足，主流竞品未覆盖
- ⚠️ P1级问题：只有复制，没有差异化设计和改进

### 维度权重汇总

| 评审维度 | 权重 | 满分 |
|---------|------|------|
| 维度1：章节结构完整性 | 12% | 12分 |
| 维度2：需求质量 | 22% | 22分 |
| 维度3：交互与流程 | 13% | 13分 |
| 维度4：架构与设计 | 13% | 13分 |
| 维度5：餐饮SaaS专项 | 10% | 10分 |
| 维度6：渐进式复杂度 | 5% | 5分 |
| 维度7：文档合规性 | 10% | 10分 |
| 维度8：可交付性 | 5% | 5分 |
| 维度9：竞品对标与优势提炼 | 10% | 10分 |
| **总计** | **100%** | **100分** |

### 综合评级标准

| 等级 | 分数区间 | 决策建议 | 说明 |
|-----|---------|---------|------|
| **S级** | 90-100分 | ✅ Green Light | 优秀，可直接进入开发 |
| **A级** | 80-89分 | ✅ Green Light | 良好，小问题修正后通过 |
| **B级** | 70-79分 | ⚠️ Conditional Pass | 一般，需针对性优化后再审 |
| **C级** | 60-69分 | ❌ Red Light | 不足，重大问题需重新设计 |
| **D级** | <60分 | ❌ Red Light | 不合格，打回重写 |

### 一票否决机制

出现以下任一情况，直接判定为D级（不合格）：
1. **违反产品定位边界原则**：设计了SaaS租用、多租户管理、强制云端依赖等功能
2. **文档合规性维度存在P0级问题**：CLEAN版本中包含竞品信息
3. **需求质量维度存在P0级问题**：核心需求严重缺失，验收标准严重不足
4. **竞品对标维度存在P0级问题**：核心功能完全没有对标分析，闭门造车
5. **餐饮SaaS专项存在P0级问题**：品牌数据隔离风险、统一数据模型原则被违反
