# 行业适配规则

## 概述

不同行业的产品有不同的监管要求、业务特点和用户期望。本手册定义各行业专项评审规则，确保评审时充分考虑行业特性。特别针对餐饮SaaS行业进行了深度增强，覆盖组织架构验证、多业态差异化设计、渐进式复杂度管理等核心领域。

---

## 一、金融行业适配规则

### 1.1 合规要求（权重提升至20%）

#### 必查项
- ✅ **监管合规**
  - 是否符合人民银行、银保监会等监管要求
  - 跨境业务是否符合外汇管理规定
  - 新产品是否需要监管审批或备案

- ✅ **资金安全**
  - 资金流向是否可追溯
  - 对账机制是否完善
  - 差错处理和资金追回机制
  - 清算结算的时序正确性

- ✅ **反洗钱**
  - KYC（了解你的客户）流程完整性
  - 大额交易和可疑交易报告机制
  - 制裁名单筛查机制

### 1.2 数据安全（权重提升至15%）

#### 必查项
- ✅ **敏感数据保护**
  - 银行卡号、身份证号等脱敏展示
  - 传输和存储的加密强度
  - 数据访问的最小权限原则

- ✅ **操作审计**
  - 所有关键操作的完整日志
  - 日志的不可篡改性
  - 审计日志的保存期限

### 1.3 系统稳定性（权重提升至15%）

#### 必查项
- ✅ **高可用设计**
  - 单节点故障不影响服务
  - 异地多活架构
  - 故障切换的RTO/RPO指标

- ✅ **限流降级**
  - 突发流量的限流策略
  - 非核心功能的降级方案
  - 熔断机制的触发条件

### 1.4 典型P0级问题

- 🚨 缺少必要的合规审批流程
- 🚨 资金安全存在逻辑漏洞
- 🚨 敏感数据明文存储或传输
- 🚨 缺少关键操作的审计日志

## 二、电商行业适配规则

### 2.1 交易系统（权重提升至18%）

#### 必查项
- ✅ **订单状态流转**
  - 订单状态机完整性
  - 并发下单的幂等性
  - 取消/退款/退货流程

- ✅ **库存管理**
  - 超卖预防机制
  - 库存扣减时机
  - 预占库存释放机制

- ✅ **价格系统**
  - 价格计算逻辑正确性
  - 优惠叠加规则
  - 价格变更的影响范围

### 2.2 支付与结算（权重提升至15%）

#### 必查项
- ✅ **支付渠道**
  - 多渠道支付支持
  - 支付失败的重试机制
  - 支付状态的异步通知

- ✅ **结算规则**
  - 分账规则的清晰度
  - 结算周期和触发条件
  - 异常订单的结算处理

### 2.3 营销系统（权重提升至12%）

#### 必查项
- ✅ **活动规则**
  - 活动规则的可理解性
  - 防刷防作弊机制
  - 活动预算控制

- ✅ **优惠券/红包**
  - 发放和使用规则
  - 核销和过期机制
  - 退款时的处理逻辑

### 2.4 典型高风险场景

- 🚨 超卖：并发场景下库存扣减不正确
- 🚨 资损：优惠叠加导致价格异常
- 🚨 薅羊毛：活动规则存在漏洞
- 🚨 用户投诉：发货/售后流程体验差

## 五、餐饮SaaS行业适配规则（深度增强版）【新增】

### 5.1 行业概述与特点

餐饮SaaS行业具有以下显著特点，评审时需重点关注：

**业务复杂性**:
- 门店数量多、分布广，从单店到连锁到集团
- 业务场景多样：堂食、外卖、扫码点餐、排队叫号、会员营销等
- 交易高频：高峰期并发量大，系统稳定性要求高

**组织层级复杂性**:
- 典型的四级架构：集团 → 品牌 → 区域 → 门店
- 不同层级的权限控制和数据隔离要求严格
- 跨层级的数据汇总和分析需求复杂

**业态多样性**:
- 单店版：功能精简、操作简单、成本低
- 连锁版：多店管理、统一运营、数据汇总
- 集团版：多品牌管理、战略分析、决策支持

**国际化需求**:
- 多语言支持：满足跨国经营需求
- 多货币支持：不同国家/地区的货币结算
- 多时区支持：跨时区的时间展示和处理
- 多税务支持：不同国家/地区的税务规则

---

### 5.2 组织层级模型验证（核心评审项）

#### 5.2.1 四级组织架构完整性检查

| 架构层级 | 必查项 | 检查要点 | 严重等级 |
|---------|--------|---------|----------|
| **集团层级** | ✅ 集团基本信息管理 | 集团名称、统一社会信用代码、联系信息 | P1 |
| | ✅ 集团级参数配置 | 全局参数、默认配置、全局开关 | P1 |
| | ✅ 跨品牌数据汇总 | 销售汇总、会员汇总、库存汇总 | P2 |
| | ✅ 集团级运营分析 | 全局报表、经营分析、决策支持 | P2 |
| **品牌层级** | ✅ 品牌基本信息管理 | 品牌名称、品牌标识、品牌介绍 | P1 |
| | ✅ 品牌级参数配置 | 品牌特有配置、品牌级开关 | P1 |
| | ✅ 品牌数据隔离 | 品牌间数据严格隔离、禁止越权访问 | **P0** |
| | ✅ 品牌内门店管理 | 门店增删改查、门店分组 | P1 |
| **区域层级** | ✅ 区域信息管理 | 区域划分、区域负责人、区域范围 | P2 |
| | ✅ 区域级数据汇总 | 区域销售、区域会员、区域分析 | P2 |
| | ✅ 区域级权限控制 | 区域管理员权限范围 | P2 |
| **门店层级** | ✅ 门店基本信息 | 门店名称、地址、电话、营业时间 | P1 |
| | ✅ 门店配置管理 | 门店特有参数、门店功能开关 | P1 |
| | ✅ 门店数据权限 | 门店员工只能访问本店数据 | P1 |

#### 5.2.2 权限控制矩阵设计验证

```
权限控制原则：
├── 纵向隔离：不同层级数据严格隔离
│   ├── 集团管理员：查看所有品牌数据
│   ├── 品牌管理员：只能查看本品牌数据
│   ├── 区域管理员：只能查看本区域数据
│   └── 门店管理员：只能查看本门店数据
│
├── 横向隔离：不同功能模块权限分离
│   ├── 运营权限：营销活动、会员管理
│   ├── 财务权限：对账、结算、报表
│   ├── 管理权限：人员、组织、配置
│   └── 只读权限：查看报表、不允许修改
│
└── 权限继承机制：
    ├── 上级权限自动包含下级权限范围
    ├── 下级权限不能超越上级权限范围
    └── 权限变更需要审批流程
```

#### 5.2.3 组织架构变更流程验证

| 变更类型 | 必查项 | 检查要点 | 严重等级 |
|---------|--------|---------|----------|
| **新增组织** | ✅ 新增审批流程 | 谁可以申请、谁审批、什么条件 | P2 |
| | ✅ 数据初始化 | 默认配置、初始数据、模板设置 | P2 |
| | ✅ 权限分配 | 默认角色、初始管理员设置 | P2 |
| **组织迁移** | ✅ 门店从A品牌迁移到B品牌 | 数据迁移规则、历史数据处理 | P1 |
| | ✅ 会员数据归属 | 会员归属品牌、跨品牌消费处理 | P1 |
| | ✅ 历史订单处理 | 历史订单归属、统计口径一致性 | P1 |
| **组织停用** | ✅ 停用条件检查 | 是否有未完成订单、未结算款项 | P2 |
| | ✅ 数据归档 | 历史数据归档、备份策略 | P2 |
| | ✅ 权限回收 | 相关人员权限自动回收 | P2 |

#### 5.2.4 典型组织架构问题

| 问题类型 | 问题描述 | 严重等级 | 改进建议 |
|---------|---------|----------|---------|
| **数据泄露风险** | 品牌A管理员可以查看品牌B的数据 | **P0** | 必须严格按品牌ID进行数据过滤 |
| **权限越权** | 门店员工可以修改集团配置 | P1 | 建立完善的权限控制矩阵 |
| **架构不完整** | 缺少区域层级，无法支持区域化运营 | P1 | 补充完整的四级组织架构设计 |
| **迁移风险** | 门店迁移时历史数据丢失或错乱 | P1 | 设计完善的数据迁移和校验机制 |

### 5.3 三种商户形态差异化设计验证

#### 5.3.1 单店版（Single Store）适配验证

**单店版特点**：
- 用户：独立小店老板、夫妻店、个体户
- 需求：功能简单、上手快、成本低
- 典型场景：小型餐馆、咖啡店、奶茶店

| 功能模块 | 单店版检查要点 | 严重等级 | 说明 |
|---------|--------------|----------|------|
| **功能裁剪** | ✅ 去除复杂的多级组织管理 | P1 | 单店不需要集团/品牌层级 |
| | ✅ 简化权限管理，只保留"老板/员工"两种角色 | P2 | 角色过多增加学习成本 |
| | ✅ 去除跨店数据汇总和分析功能 | P2 | 单店不需要跨店分析 |
| **操作简化** | ✅ 默认配置充分，减少用户设置 | P1 | 降低上手门槛 |
| | ✅ 常用功能入口明显，减少操作步骤 | P2 | 提升使用效率 |
| | ✅ 提供引导式设置流程 | P2 | 新用户友好 |
| **成本控制** | ✅ 避免依赖高成本的基础设施 | P2 | 降低客户使用成本 |
| | ✅ 支持轻量化部署 | P2 | 部署成本低 |

#### 5.3.2 连锁版（Chain Store）适配验证

**连锁版特点**：
- 用户：区域连锁、多门店经营的餐饮品牌
- 需求：统一管理、标准化运营、规模效应
- 典型场景：区域连锁品牌、几十到上百家门店

| 功能模块 | 连锁版检查要点 | 严重等级 | 说明 |
|---------|--------------|----------|------|
| **多店管理** | ✅ 门店批量导入和管理 | P1 | 大量门店快速录入 |
| | ✅ 门店分组/标签管理 | P2 | 便于门店分类管理 |
| | ✅ 门店状态管理（营业/休息/停用） | P2 | 灵活的门店生命周期管理 |
| **统一运营** | ✅ 统一的菜品库/商品库管理 | P1 | 标准化菜品管理 |
| | ✅ 统一的营销活动下发 | P1 | 活动一键同步到所有门店 |
| | ✅ 统一的会员体系 | P1 | 会员跨店通用 |
| **数据汇总** | ✅ 门店销售数据实时汇总 | P1 | 总部实时掌握经营情况 |
| | ✅ 门店排行榜、对比分析 | P2 | 横向对比，发现问题 |
| | ✅ 异常门店自动预警 | P2 | 及时发现经营异常 |
| **标准化管控** | ✅ 总部统一下发配置 | P1 | 保证品牌一致性 |
| | ✅ 门店可配置项范围可控 | P2 | 避免门店随意修改破坏标准 |
| | ✅ 重要变更需要总部审批 | P2 | 风险可控 |

#### 5.3.3 集团版（Group）适配验证

**集团版特点**：
- 用户：大型餐饮集团、多品牌经营企业
- 需求：战略决策支持、多品牌协同、精细化管理
- 典型场景：大型餐饮集团、旗下多个品牌、数百家到数千家门店

| 功能模块 | 集团版检查要点 | 严重等级 | 说明 |
|---------|--------------|----------|------|
| **多品牌管理** | ✅ 品牌独立运营，数据隔离 | **P0** | 品牌间数据安全 |
| | ✅ 品牌间可以设置不同的功能开关 | P1 | 不同品牌差异化运营 |
| | ✅ 集团层面可以查看所有品牌汇总数据 | P1 | 集团决策支持 |
| **战略分析** | ✅ 品牌间横向对比分析 | P2 | 发现优势品牌和问题品牌 |
| | ✅ 整体经营健康度评估 | P2 | 集团整体运营情况 |
| | ✅ 市场趋势预测和预警 | P2 | 战略决策参考 |
| **精细化管理** | ✅ 多维数据分析（时间/区域/业态/品类） | P2 | 深入洞察经营情况 |
| | ✅ 成本分析和利润核算 | P2 | 精细化成本控制 |
| | ✅ 人员绩效评估体系 | P2 | 团队绩效管理 |
| **系统集成** | ✅ 与ERP、财务系统对接 | P2 | 业财一体化 |
| | ✅ 与供应链系统对接 | P2 | 采购、库存一体化 |
| | ✅ 与HR系统对接 | P2 | 人员管理一体化 |

#### 5.3.4 形态切换平滑性验证

| 切换方向 | 必查项 | 检查要点 | 严重等级 |
|---------|--------|---------|----------|
| **单店 → 连锁** | ✅ 数据平滑迁移 | 历史订单、会员、设置等完整迁移 | P1 |
| | ✅ 功能平滑升级 | 原有功能保留，新增功能逐步引导 | P2 |
| | ✅ 权限平滑过渡 | 原老板自动升级为连锁管理员 | P2 |
| **连锁 → 集团** | ✅ 品牌数据隔离 | 原连锁数据成为集团下的一个品牌 | P1 |
| | ✅ 集团功能解锁 | 集团功能模块可用 | P2 |
| | ✅ 历史数据完整性 | 历史统计数据口径一致 | P2 |
| **降级支持** | ✅ 高版本降级到低版本 | 功能降级、数据保留 | P2 |
| | ✅ 降级数据处理策略 | 超出低版本范围的数据如何处理 | P2 |

#### 5.3.5 典型业态差异化问题

| 问题类型 | 问题描述 | 严重等级 | 改进建议 |
|---------|---------|----------|---------|
| **功能冗余** | 单店版也有复杂的多组织管理功能 | P1 | 根据业态裁剪不必要的功能 |
| **体验不佳** | 连锁版缺少批量操作功能，门店管理效率低 | P1 | 增加批量导入、批量操作功能 |
| **数据安全** | 集团版品牌间数据未做隔离，存在数据泄露风险 | **P0** | 严格按品牌ID进行数据过滤 |
| **切换风险** | 单店升级连锁时数据丢失或错乱 | P1 | 完善的数据迁移和校验机制 |

### 5.4 渐进式复杂度管理框架验证

#### 5.4.1 原则性描述 vs 硬性数值

**渐进式复杂度原则**：
> 在需求描述中，使用原则性语言而非写死具体数字阈值，为后续优化和扩展留有余地。

| 不良实践（❌） | 良好实践（✅） | 说明 |
|---------------|---------------|------|
| "支持1000并发" | "支持高并发场景，通过性能优化确保系统稳定" | 避免技术限制，留有优化空间 |

#### 5.4.3 灰度发布和降级方案验证

**灰度发布机制**：
```
新功能发布流程：
1. 开发环境测试 → 功能验证通过
2. 测试环境测试 → 集成测试通过
3. 灰度发布 → 选择部分门店/品牌试用
   ├── 1% 门店 → 观察基础功能
   ├── 10% 门店 → 观察性能和稳定性
   ├── 50% 门店 → 大规模验证
   └── 100% 全量 → 全面上线
4. 问题回滚 → 发现问题快速回滚到稳定版本
```

**降级方案**：
```
高峰期降级策略：
├── Level 1（轻度）：关闭实时统计计算，使用缓存数据
├── Level 2（中度）：关闭非核心功能，如营销活动弹窗
├── Level 3（重度）：只保留核心交易功能，其他全部降级
└── 自动降级：根据系统负载自动触发降级
```

#### 5.4.4 典型渐进式复杂度问题

| 问题类型 | 问题描述 | 严重等级 | 改进建议 |
|---------|---------|----------|---------|
| **硬编码限制** | 需求中写死"最多支持100个门店" | P2 | 改为原则性描述，留有扩展空间 |
| **缺少配置化** | 业务规则硬编码在代码中，无法灵活调整 | P2 | 关键业务规则参数化、可配置 |
| **无灰度方案** | 新功能一刀切全量发布，风险高 | P2 | 设计完善的灰度发布机制 |
| **无降级方案** | 高峰期系统压力大时没有降级预案 | P2 | 设计分级降级策略 |

#### 5.5.2 数据打通授权机制验证

```
数据打通场景：
├── 场景1：集团旗下多个品牌，会员可以跨品牌消费
│   ├── 需求：会员在品牌A消费，积分可以在品牌B使用
│   ├── 方案：建立集团统一的会员中心，品牌会员映射
│   └── 权限：必须经过集团授权才能打通数据
│
├── 场景2：同一品牌下，门店间库存调拨
│   ├── 需求：门店A缺货，从门店B调货
│   ├── 方案：建立调拨流程，记录调拨记录
│   └── 权限：需要双方门店确认
│
└── 场景3：集团层面的数据分析
    ├── 需求：集团想看所有品牌的汇总数据
    ├── 方案：数据汇总到集团分析库
    └── 权限：只允许集团指定角色查看
```

#### 5.5.3 跨品牌数据查询限制
