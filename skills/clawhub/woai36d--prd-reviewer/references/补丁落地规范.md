# PRD补丁落地规范

## 概述

补丁落地是评审闭环的最后一步：将评审发现的问题转化为PRD文档的具体修改，精准落地到文档中。遵循"严苛但建设性"原则，只改需要改的，不改好的。

---

## 补丁类型分类

| 类型 | 适用场景 | 典型修改内容 |
|------|---------|------------|
| **A-结构补丁** | 章节缺失、编号不规范 | 补充章节、调整编号、补充目录 |
| **B-需求补丁** | 需求描述不完整、边界模糊 | 补充需求细节、明确边界条件、增加形态差异化说明 |
| **C-验收补丁** | 缺少Given-When-Then | 为每个REQ补充3-5条AC，覆盖正常/边界/异常路径 |
| **D-数据补丁** | 数据模型遗漏 | 补充表结构、字段说明、ER图、索引设计 |
| **E-API补丁** | 接口定义不完整 | 补充端点清单、参数规范、响应格式、错误码 |
| **F-规则补丁** | 业务规则冲突或缺失 | 补充状态流转、审批链、数据隔离规则 |
| **G-对标补丁** | 竞品对标不足 | 补充对标表格、差异化设计说明 |
| **H-合规补丁** | CLEAN版本问题 | 清除竞品信息、标注版本区分、补充内部评审版标记 |
| **I-性能补丁** | 大数据量无方案 | 补充虚拟滚动、分页、异步执行、分区策略 |
| **J-安全补丁** | 强制操作无兜底 | 补充二次验证、审计日志、数据加密说明 |

---

## 补丁落地流程

### Step 1: 生成补丁清单

评审完成后，基于问题清单自动生成补丁清单：

```
每条问题 → 判断是否需要补丁 → 生成补丁项 → 关联问题ID
```

**不需要补丁的情况**：
- P3建议级问题（仅记录，不修改文档）
- 涉及技术预研的功能（建议另开技术文档）
- 需要产品决策的问题（标注"待产品决策"）

### Step 2: 用户确认

**确认流程**：

1. **展示补丁摘要**（按优先级排序）
   ```
   即将落地 [N] 个补丁：
   🔴 P0: [N] 个（必须解决）
   🟠 P1: [N] 个（建议解决）
   🟡 P2: [N] 个（可选优化）
   ```

2. **展示关键补丁详情**（前3个P0）
   - 问题描述（1句话）
   - 修改位置（章节/REQ编号）
   - 修改性质（补充/修正/删除）

3. **征求确认**
   - ✅ 算：确认/是的/提交/发/可以/好/行/同意
   - ❌ 不算：嗯/哦/看看/再说吧/考虑一下/沉默/模糊表态

4. **分批执行确认**（P0全部必须确认，P1/P2可选）

### Step 3: 精准落地

**落地原则**：

| 原则 | 说明 |
|------|------|
| **精准修改** | 仅修改问题关联的段落，不全文重写 |
| **最小改动** | 能补一句就不补一段，能改一行就不改一节 |
| **标注关联** | 每个补丁标注关联的问题ID（如"关联 P0-003"） |
| **版本递增** | 修改后版本号+0.1（如v1.0→v1.1），更新变更日志 |
| **验收自洽** | 补丁后检查文档内部逻辑一致性 |

**落地顺序**：
1. 先A-结构补丁（影响编号体系）
2. 再B/C/D/E/F-内容补丁（按章节顺序）
3. 最后G/H/I/J-专项补丁

### Step 4: 验证与汇报

**验证清单**：
- [ ] 章节编号连续，无跳号/重号
- [ ] 所有REQ有对应AC（Given-When-Then）
- [ ] 数据模型与需求描述一致
- [ ] API列表与需求功能一一对应
- [ ] 竞品信息已清除（CLEAN版本）
- [ ] 版本号和变更日志已更新

**汇报格式**：
```
补丁落地完成：
- 总计落地 [N] 个补丁
- P0: [N] 个 ✅ | P1: [N] 个 ✅ | P2: [N] 个 ✅
- 文档版本: vX.X → vX.X+1
- 待确认: [N] 项（需产品决策）
```

## 补丁示例

### 示例1: C-验收补丁（补充Given-When-Then）

**问题**: REQ-ORG-001 "创建门店" 缺少验收标准

**补丁位置**: 第4章 REQ-ORG-001 下方

**补丁内容**:
```markdown
**验收标准**：
- **AC1-正常路径**: Given 连锁管理员已登录，When 填写完整门店信息并提交，Then 系统创建门店成功，返回门店ID，状态为"筹备中"
- **AC2-边界路径**: Given 必填字段为空，When 提交表单，Then 系统提示"[字段名]不能为空"，禁止提交
- **AC3-异常路径**: Given 门店编号已存在，When 提交表单，Then 系统提示"门店编号重复"，建议自动生成唯一编号
```

### 示例2: F-规则补丁（补充状态流转）

**问题**: 门店状态流转缺少异常分支

**补丁位置**: 第9章 业务规则 → 门店状态流转

**补丁内容**:
```markdown
**门店状态流转补充**：
| 当前状态 | 目标状态 | 触发条件 | 限制条件 | 异常处理 |
|---------|---------|---------|---------|---------|
| 筹备中 | 营业中 | 完成所有筹备项 | 需品牌管理员审批 | 超时30天自动提醒 |
| 营业中 | 暂停营业 | 管理员手动操作 | 需确认无进行中订单 | 有进行订单时禁止，提示先处理 |
| 营业中 | 停业 | 手动/合规触发 | 需二次确认 | 强制停业需记录原因+操作人 |
| 暂停营业 | 营业中 | 管理员手动恢复 | 无需审批 | 恢复时检查配置有效性 |
```

### 示例3: D-数据补丁（补充辅助表）

**问题**: 缺少操作审计日志表

**补丁位置**: 附录 数据模型设计

**补丁内容**:
```markdown
#### 表: operation_audit_log（操作审计日志）
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | BIGINT PK | Y | 自增主键 |
| user_id | BIGINT FK | Y | 操作用户ID |
| action | VARCHAR(64) | Y | 操作类型：CREATE/UPDATE/DELETE/LOGIN |
| target_type | VARCHAR(32) | Y | 操作对象类型：store/brand/user/role |
| target_id | BIGINT | Y | 操作对象ID |
| old_value | JSON | N | 修改前数据快照 |
| new_value | JSON | N | 修改后数据快照 |
| ip_address | VARCHAR(64) | N | 操作IP |
| user_agent | VARCHAR(512) | N | 客户端信息 |
| created_at | DATETIME | Y | 操作时间 |

**索引**: idx_user_id, idx_target_type_id, idx_created_at
**保留策略**: 保留180天，超期归档到冷存储
```

## 禁忌清单

**禁止行为**：
- ❌ 未经用户确认直接修改文档
- ❌ 补丁后不回读验证文档自洽性
- ❌ 将P3建议级问题强行升级为P0以推动修改
- ❌ 修改与评审问题无关的内容（夹带私货）
- ❌ 删除用户原有设计意图（只补充，不替换设计理念）

## 与 prd-prototype-review 的协作边界

| 场景 | 使用 prd-reviewer | 使用 prd-prototype-review |
|------|------------------|------------------------|
| 纯PRD评审 | ✅ 餐饮SaaS专版，9维度评分 | ❌ |
| PRD+原型双评审 | ✅ PRD部分 | ✅ 原型部分 |
| 补丁落地 | ✅ PRD文档补丁 | ✅ 原型文档补丁 |
| 通用产品（非餐饮） | ❌ | ✅ |

**协作原则**：两者可以独立使用，也可以组合使用。组合使用时，prd-reviewer 负责PRD的9维度评分和补丁，prd-prototype-review 负责原型的10分制评分和补丁。
