# RAG 检索管线

> 把"能找到、能验证"的上下文，稳定地交给生成模型——而不是靠模型记忆硬编。

## 能力

- 设计分块策略（按结构边界 / 重叠 / 元数据安全），决定哪些文本可被检索到。
- 选择 Embedding 模型与向量库，落实文档与查询的同质编码。
- 实现混合检索：词法（BM25/全文）与语义（向量）用 RRF 融合，覆盖术语与语义两类召回。
- 用交叉编码器对候选重排，把 top-50 收束到 top-10，提升精读精度。
- 搭建检索评测：用代表性问题集测 Recall@K / MRR，用数据驱动阈值而非拍脑袋。
- 衔接 LLM 生成：带编号引用 `[1]` 的上下文装配与"仅用检索内容作答"的约束。

## 使用方式

```text
/rag-retrieval 为这份技术文档库设计 RAG 检索管线，给出分块与混合检索方案
/rag-retrieval 我们的问答召回很差，帮我做检索评测并定位是分块还是重排的问题
```

执行前读取 `../../references/rag-retrieval-playbook.md`。若你的语料本身已是一个 LLM Wiki（raw/wiki 双层的 Markdown 知识库），先读 `../../references/retrieval-and-synthesis-playbook.md` 判断能否用索引 + 全文检索解决——简单检索优先，只有评测证明召回不足才上向量。

## 工作流

1. **判定是否要 RAG**：语料小、术语稳定、要精确字段匹配 → 先用索引/全文；页面多、表达漂移大、有 30–50 条评测问题 → 才上 Embedding。
2. **分块**：目标 256–1024 token（典型 512），重叠 10–20%，在标题/段落边界切，每块带 title/source/section 元数据。
3. **编码**：文档与查询用同一模型；查询侧批处理 + 缓存，控制 Embedding 吞吐。
4. **检索**：先各取 top-3×k（如 top-30），BM25 与向量分别召回，再 RRF（k=60）融合；融合后再做元数据 boosting。
5. **重排**：取融合后 50 候选，交叉编码器重排到 10；截断到 200–400 字符提升效率。
6. **评测**：用黄金问题集算 Recall@K、MRR、引用正确率；定发版门槛（如 P@10≥0.70、R@10≥0.85、MRR≥0.65）。
7. **装配生成**：上下文带 `[1]…[n]` 编号与 Source，系统提示强制"仅用上下文作答，无则拒答"。

## 关键决策（经验值，需按自身语料重测）

| 决策点 | 推荐 |
|--------|------|
| 嵌入模型 | text-embedding-3-small / voyage-3.5（查询与文档同模型） |
| 块大小 | 256–1024 token（512 甜点） |
| 混合权重 | 先 RRF 融合（参数无关），再按语料 eval 调元数据 boosting |
| Top-k | 召回 3×k，重排后 3–10 |
| 温度 | 0.1–0.3（事实任务） |
| 重排 | 候选 50 → 10 |
| 向量索引 | HNSW / IVFFlat |
| 延迟预算 | 端到端 p95 < 500ms（嵌/搜/排/装分别设断言） |

## 适用场景

- 给客服 / 文档问答 / 代码助手搭建独立检索后端。
- 已有向量库但召回差，需要混合检索 + 重排调优。
- 上线前做检索质量门禁，防止"Demo 好看、线上漏召回"。
- 多概念查询需要分解后并行检索再 RRF 融合。

## 常见误区

- 不跟踪引用：答案无法溯源、易幻觉。
- 上下文过大：塞满 top-k 反而稀释关键证据。
- 单一检索：只用向量会漏精确术语，只用 BM25 会漏语义。
- 不分块或固定大小硬切：边界切断语义，检索质量崩。
- 查询/文档用不同模型：相似度计算失准。
- 不缓存 Embedding：重复查询浪费吞吐。
- Agentic RAG 无回退：检索失败就无限重写。

## 限制

- 不替代知识库的内容治理（冲突/过期裁决仍属 `wiki-maintenance`）。
- 融合权重、块大小是语料属性，必须按自身评测重推，不能直接照搬默认值。
- 权限过滤在检索前执行，不把私有片段召回后再遮盖。
