# 信息架构与页面模型手册

## 1. 先从问题设计，不从目录设计

先收集用户会真实提出的问题，再决定页面类型。一个好 Wiki 的最小输入包括：10–30 个代表性问题、目标受众、回答时效和必须排除的敏感范围。

| 问题模式 | 推荐页面 | 示例 |
|----------|----------|------|
| “X 是什么，为什么重要？” | `concept` | 工具调用协议 |
| “谁/什么系统负责 X？” | `entity` | Runtime Controller |
| “这份材料贡献了什么？” | `source-summary` | 某论文摘要 |
| “如何完成 X？” | `how-to` | 新增 Provider |
| “字段/命令的准确含义？” | `reference` | 配置项字典 |
| “为什么这样设计？” | `explanation` | 权限模型原理 |
| “团队决定了什么？” | `decision` | 采用 Markdown-first |
| “旧方案发生了什么？” | `archive` | 已弃用索引器 |

Diátaxis 的 tutorial/how-to/reference/explanation 适合任务型文档；concept/entity/source-summary/decision 补足知识图谱与溯源。不要强迫所有 Wiki 使用全部类型。

## 2. 页面边界决策树

```text
内容是否回答同一个稳定问题？
├─ 否 → 拆页
└─ 是 → 是否拥有独立生命周期或责任人？
   ├─ 是 → 拆页并互链
   └─ 否 → 是否小到无法形成可引用结论？
      ├─ 是 → 合并到上位概念
      └─ 否 → 保持独立页面
```

拆页信号：超过约 1,500–2,000 字仍有多个主问题、不同部分更新频率显著不同、来源和责任人完全不同。合并信号：页面只有定义、没有独立来源、搜索时总与另一页共同出现。

## 3. 页面契约

每个活动页面至少具有：

```yaml
---
id: concept-tool-protocol
type: concept
title: 工具调用协议
status: active
updated: 2026-08-14
owner: runtime-team
sources:
  - ../../raw/articles/tool-protocol.md
---
```

正文建议按“摘要 → 核心主张 → 证据 → 冲突/限制 → 相关页面”组织。精确事实在主张附近给相对来源链接，而不是只在文末堆参考资料。

`id` 是稳定身份，不随标题润色变化；文件名用于人类导航，可以重命名，但需更新 Manifest 和入链。

## 4. 命名规范

- 文件名使用小写 ASCII kebab-case：`tool-call-protocol.md`。
- 标题使用读者语言，可包含中文和专有名词。
- 不使用 `misc`、`notes-2`、`new-page` 等无语义名称。
- 来源摘要带来源稳定标识，不用当天序号冒充身份。
- 决策页可用 `YYYY-MM-DD-short-decision.md`，但 `id` 仍保持稳定。

## 5. 导航结构

`wiki/index.md` 是人类入口，不是文件清单转储。它包含：Wiki 介绍、按任务或主题组织的导航、关键实体、最新决策和状态说明。

三层以内通常足够：

```text
wiki/
├── index.md
├── concepts/
├── entities/
├── summaries/
├── how-to/
├── reference/
├── explanations/
├── decisions/
└── archive/
```

当页面少于 20 个时，可以只创建用到的目录；空目录不是成熟度。超过约 200 页后，优先增加主题索引页和 Manifest 字段，而不是继续加深目录。

## 6. 链接语义

链接应解释关系：

```markdown
该调度器执行 [权限策略](../concepts/permission-policy.md)，其采用原因见
[权限模型决策](../decisions/2026-08-14-permission-model.md)。
```

“相关链接”列表只是兜底。正文中的语义链接更能帮助读者和检索器理解关系。对于改名页面，优先更新所有入链；需要长期兼容时保留一页简短 redirect。

## 7. 标签与分类

目录表达主要归属，frontmatter 表达可组合属性。标签只保留可用于过滤或治理的维度，如产品域、成熟度、访问级别；不要把正文里的每个名词都变成标签。

当两个分类维度竞争时，选择更新更稳定的一项作为目录，另一项作为元数据。例如页面类型通常比组织架构稳定，因此使用 `concepts/` 目录和 `owner: runtime-team` 字段。

## 8. 常见失败

- 一来源一页面：形成材料仓库，不形成知识网络。
- 一概念一个巨大页面：召回命中但难以定位和更新。
- 只建文件夹不建索引：用户需要猜路径。
- 标题承担身份：重命名导致引用和外部链接失效。
- 教程、参考、解释混在一起：读者无法判断阅读路径。
- 自动生成大量双向链接：链接数量上升，语义密度下降。

## 9. 设计检查表

- [ ] 页面类型直接服务代表性问题
- [ ] `id` 稳定，文件名和标题各司其职
- [ ] 每页只有一个主要知识边界
- [ ] 索引按用户任务或主题导航，而不是简单列目录
- [ ] 页面类型、状态、日期、责任人、来源字段一致
- [ ] 链接在正文中表达关系
- [ ] 分类深度与当前规模匹配，没有预建空架构
