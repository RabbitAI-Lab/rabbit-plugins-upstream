# 标书查重检测规则参考

> 本文件是 **`SKILL.md` Step 4 的补充参考**，并非独立权威。Step 4 内联的字段清单、定级标准与输出 Schema 为唯一权威；两者冲突时以 Step 4 为准。

本文件定义检测字段、风险等级、相似度定性锚点、招标基线剔除规则与报告结构，供分析阶段按需查阅。阈值与字段清单的权威定义以 Step 4 为准；本文件仅作字段级说明与示例。

---

## 1. 敏感字段清单（关键信息交叉检测）

用于跨文档比对「雷同即高风险」的字段：

| 字段 | 说明 | 提取方式 |
|------|------|----------|
| 公司名称 | 投标单位全称 | NER / 正则（含「公司」「集团」「有限公司」等） |
| 公司简称 | 文中出现的缩写指代 | NER / 上下文推断 |
| 联系电话 | 固定电话 / 手机 | 正则（`0\d{2,3}-\d{7,8}`、`1[3-9]\d{9}`） |
| 项目经理 | 项目负责人姓名 | NER（人名）+ 关键词「项目经理」 |
| 造价师 | 造价工程师姓名 | NER（人名）+ 关键词「造价师」 |
| 法人 / 授权代表 | 法定代表人或授权人 | NER + 关键词 |
| 开户行 / 账号 | 银行信息 | 正则 + 关键词 |
| 邮箱 | 联系人邮箱 | 正则 `[\w.]+@[\w.]+` |

> 若用户提供自定义字段或白名单，以用户配置为准（第二阶段能力）。

## 2. 风险等级定义

| 等级 | 图标 | 触发条件 |
|------|------|----------|
| 高 | 🔴 | 不同投标文件中出现相同公司名称、电话、项目经理、法人等核心身份字段；或作者/公司元数据相同；或文本相似度 ≥ 70% |
| 中 | 🟡 | 同义改写导致语义相似；最后作者相同、创建时间高度接近；表格结构相似；文本相似度 50%–70% |
| 低 | 🟢 | 其他属性异常、非核心字段雷同、文本相似度 < 50% |

---

## 3. 文本语义相似度定级（定性锚定，替代"感觉分数"）

> 大模型没有内置余弦相似度计算器，纯数值分数往往是"感觉"，缺乏一致性。因此改以
> **定性特征** 判定等级，`score` 仅作为该等级的代表值用于报告展示。判定以「段落语义
> 是否表达同一内容」为准，而非字面重合率；同义改写、换序、增删修饰词均应识别为相似。

| 等级 | 代表 score | 定性特征（满足任一即判定） | 示例 |
|------|-----------|--------------------------|------|
| 高 | 0.90 | 连续 50 字以上完全相同；或仅替换公司名称其余逐字一致；或核心句子相同且多个关键数据（单价/工期/编号）完全一致 | 技术方案整段逐字复制 |
| 中 | 0.60 | 表述逻辑/结构一致但句式与用词有明显调整（同义改写）；或表格结构一致但数据有细微变化；或最后作者相同/创建时间高度接近 | "具有10年经验" vs "拥有十年工作经验" |
| 低 | 0.30 | 仅个别通用术语或招标原文重合；非核心字段雷同 | 行业套话"根据招标文件要求" |

场景修正规则：
- 技术方案章节：整体下调一档（行业术语趋同属正常）。
- 商务报价章节：整体上调一档（报价格式趋同属正常）。
- 通用条款 / 法律法规引用：直接标记 `低`，不计入风险。

输出要求：每条 `text_similarity` 必须含 `level`、`score`（取上表代表值）、`reason`（解释定性依据）、`type`（直接复制 / 同义改写 / 结构相似）。

## 4. 招标基线剔除规则

当用户提供招标文件（`--bidding`）时：

- 将招标文件中的通用描述（招标范围、技术规格、资质要求、合同条款、投标人须知等）
  作为「基线语料」。
- 在两份投标文件互比时，剔除双方都引用自招标文件的相同段落，避免「大家都照抄招标书」造成误报。
- 仅在投标文件中**独有**的雷同才计为风险。
- 若未提供招标文件，则直接互比，并在报告中标注「未启用基线剔除，存在基线误报可能」。

---

## 5. 文档属性预警规则

读取 docx/pdf 元数据（作者、最后作者、公司、标题、创建/修改时间等）：

- 🔴 高：两份不同投标文件的**作者**或**公司**相同。
- 🟡 中：最后作者相同；或创建/修改时间高度接近（如同一分钟内）。
- 🟢 低：其他异常（如标题雷同、备注含他人信息）。

## 6. 报告结构（findings JSON → 渲染）

> **权威声明**：以下 schema 与 `SKILL.md` Step 4 的内联 Schema 完全一致，二者为同一份。
> 以 `SKILL.md` Step 4 为准；本文件仅作字段级说明。字段名必须与 `build_report.py` 期望
> 一致，请勿随意改名，否则报告渲染会丢字段或报错。

`build_report.py` 依据以下 schema 渲染 docx / markdown（新增可选字段 `reason` / `type` /
`limitations`，渲染脚本已向后兼容）：

```json
{
  "overview": {
    "file_count": 2,
    "risk_total": 5,
    "high_risk_count": 2,
    "avg_similarity": 0.42,
    "summary": "一句话概述"
  },
  "key_info_collisions": [
    {"field":"公司名称","value":"XX公司","files":["a.docx"],
     "locations":["a.docx 第3段"],"level":"高","reason":"两家投标文件单位全称相同"}
  ],
  "text_similarity": [
    {"file_a":"a.docx","file_b":"b.docx","score":0.90,"level":"高",
     "type":"直接复制",
     "reason":"连续三段落结构完全一致且关键数据相同",
     "segments":[{"text":"...","location":"a.docx 第X段 / b.docx 第Y段"}]}
  ],
  "attribute_warnings": [
    {"file":"a.docx","level":"高","fields":{"author":"张三","company":"XX"},
     "detail":"作者/公司相同","reason":"不同投标方文档作者元数据相同"}
  ],
  "table_similarity": [
    {"file_a":"a.docx","file_b":"b.docx","level":"中",
     "detail":"表格结构相似","reason":"报价表行列结构一致仅单价尾数不同"}
  ],
  "diff": [
    {"type":"add|delete|change","file_a":"a.docx","file_b":"b.docx","content":"..."}
  ],
  "limitations": ["文档 c.txt 含扫描页未提取文字，覆盖率不完整"],
  "baseline_note": "已使用招标文件做基线剔除" | null,
  "conclusion": "综合建议文本"
}
```

字段约束：
- `level` 仅取 `高` / `中` / `低`。
- `score` 取 §3 对应等级代表值（高 0.90 / 中 0.60 / 低 0.30）。
- 无风险的部分必须输出空数组 `[]`，不得省略字段。
- 每条 finding 必须含 `reason`；`text_similarity` 额外含 `type`。
- `limitations` 记录解析失败 / 扫描件未识别等覆盖缺口。

章节顺序：检测概览 → 一、关键信息碰撞 → 二、文本语义相似度 → 三、文档属性预警
→ 四、表格内容相似度 → 五、差异比对 → 六、综合结论与建议 →（附）限制与免责声明。

## 7. 准确性与免责声明（必须写入报告或对话）

- 本 Skill 基于大模型语义理解，定位为**初筛/辅助**工具，不替代专业查重系统或法律判定。
- 高利害场景（废标、投诉、行政处罚）须由专业人员人工复核，并参考专业围串标检测产品。
- 不承诺「100% 检出」或「绝对判定围串标」。
