# Data schemas

Three JSON inputs. Two of them you generate; one of them — the product data —
comes from **the user's own system of record**.

---

## 1. Product data (`--products`)

Everything the customs declaration says about a product. The skill never
invents these values.

```json
{
  "products": {
    "<product_key>": {
      "name_zh": "Chinese product name as declared",
      "name_en": "English product name as declared",
      "hs_code": "<10-digit HS code from the user's own data>",
      "declared_unit_price": 0.00,
      "material": "<materials, in both languages if the forwarder wants both>",
      "use": "<what it is for, in both languages if the forwarder wants both>",
      "has_battery": false,
      "has_magnet": false
    }
  }
}
```

`<product_key>` is whatever you key your catalogue by — ASIN, MSKU, internal
SKU. It only has to match `product_key` in the shipment file and the image
filename in the cache.

### Where this comes from — ask the user

**Do not fabricate HS codes, declared values, materials or battery flags.** A
wrong HS code is a customs problem; a wrong battery flag is a safety
declaration problem. At the start of a run, ask the user:

> Where does your product master data live — HS code, declared unit price,
> Chinese/English names, material, use, battery and magnet flags? An ERP, a
> database, a spreadsheet, an existing JSON file?

Then connect to it. Typical shapes:

| The user has | What to do |
|---|---|
| An ERP or internal API | Ask for endpoint + credentials, pull and map fields into the schema above |
| A database | Ask for connection details and the table/columns, query and export to JSON |
| A spreadsheet | Read it, map columns, export to JSON; confirm the mapping with the user |
| A JSON file already | Ask for the path, map keys if they differ |
| Nothing structured | Build the JSON together, product by product, and **have the user or their customs broker confirm every HS code and declared value before the first upload**. Save it so the next batch is cheap. |

Either way the product data file is the user's asset — it lives in their
project, not in this skill, and it should be version-controlled so that what
was declared last time is auditable.

### Declared unit price

The user's call, subject to their customs broker's advice and the destination's
de-minimis and duty rules. Ask; don't pick a number. Note that whatever is
declared should be consistent across batches for the same product — a price
that moves around between shipments invites questions.

### Battery and magnet flags

These drive the whole-shipment "contains batteries / contains magnets"
declaration and can change which channels will even accept the freight.

Electronics — anything with an LCD, a beeper, a light — very often ship with a
button cell installed even when the listing does not say so. **Get written
confirmation from the supplier and keep it.** If a product does contain a cell,
ask the forwarder whether the booked channel accepts it before shipping.

Declaring accurately is far cheaper than being found out: an under-declared
battery can mean the whole consignment held at customs for weeks, forced return
or destruction, demurrage billed back by the forwarder, everyone else's cargo in
the same consolidated container held with yours, and a mark against the customs
broker.

## 2. Shipment file (one per FBA shipment)

Generated by `build_shipments.py` from the inbound-plan result, or written by
hand.

```json
{
  "ticket": {
    "label": "FBA1XXXXXXXX_ABC1",
    "channel": "<freight channel name the forwarder uses>",
    "dest_country": "US",
    "customs_type": "<declaration type the forwarder uses>"
  },
  "boxes": [
    {
      "box_seq": 1,
      "fba_shipment_id": "FBA1XXXXXXXX",
      "reference_id": "<Amazon reference id>",
      "box_code": "FBA1XXXXXXXXU000001",
      "warehouse_code": "ABC1",
      "items": [
        {"product_key": "<key into product data>", "qty": 14}
      ]
    }
  ]
}
```

`qty` is **the quantity in this box**, not the shipment total. `box_code` must
be the `boxId` the inbound API returned, verbatim — `U` plus six digits.

## 3. Image map (`fetch_images.py`)

```json
{
  "<product_key>": "https://…/main-image.jpg",
  "<product_key2>": "/local/path/to/photo.png"
}
```

Produces `<product_key>.bmp` in the per-user cache directory, 48×48, 96 DPI,
letterboxed onto white. `generate_invoice.py` picks them up from there by key.
