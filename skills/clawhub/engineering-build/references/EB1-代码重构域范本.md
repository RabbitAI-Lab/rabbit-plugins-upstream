## EB1 代码重构域范本

### 一、领域知识要点

- 重构手法（Fowler）：提取函数、内联、搬移、重命名、以多态替代条件、引入参数对象
- 坏味道识别：重复代码、过长函数、过大类、过长参数列、发散式变化、霰弹式修改、依恋情结、数据泥团
- 架构分层：表现层、应用层、领域层、基础设施层；依赖倒置
- SOLID 原则：单一职责、开闭、里氏替换、接口隔离、依赖倒置
- 安全重构前提：有测试网或可对比的行为快照
- 重构 vs 重写：重构保行为、小步走；重写换行为、风险高

### 二、判定标准

- 外部行为不得改变，除非显式声明为行为变更
- 每步须可运行且可回滚
- 不得在同一提交中混合重构与功能改动
- 重构前后须有可对比的验证

### 三、范本结构

1. 现状与问题清单
2. 重构目标与边界
3. 分步计划
4. 每步改动与验证
5. 回归结果
6. 遗留问题

### 四、常见失范

- 无测试网直接大改
- 重构同时改功能导致无法归因
- 过度抽象增加理解成本
- 为设计模式而设计模式

### 七、执行卡（以「架构与现状分析」为例）

**开工前备齐**：模块图、调用链、数据流、依赖清单、坏味道清单

**可选补充**：运行日志、文档、提交历史

**按序执行**：

1. 读入口
2. 追调用链
3. 画数据流
4. 列依赖
5. 标坏味道

**交付前核对**：须基于实际代码而非文档；耦合点须给文件行号

**成品须符合**：架构现状报告

按「架构现状报告」交付。复制下面骨架，节标题即该节须给出的结论，不要改成中性标题。

```markdown
## 1. 现状与问题清单

## 3. 分步计划
## 4. 每步改动与验证
## 5. 回归结果

```

**齐备要求**：必选组件「模块图、调用链、数据流、依赖清单、坏味道清单」须全部落位；约束「须基于实际代码而非文档；耦合点须给文件行号」须逐条成立；可选「运行日志、文档、提交历史」按需补充。
