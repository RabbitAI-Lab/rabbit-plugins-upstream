## 工程构建任务要求清单

工程构建每种任务类型的零件清单——必选组件、可选组件、组装顺序、领域约束。按清单逐项产出。

### EB1 代码重构

#### 域级说明

**域定位**：在不改变外部行为的前提下改善内部结构，降低改动成本。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 现状→边界→分步→回归 |
| 独立成域的理由 | 以外部行为不变为硬约束，验收靠回归测试，与其他产物的验收方式不同构 |
| 穷尽性 | 5 个任务覆盖「现状→边界→分步→回归」的 4 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 重构手法（Fowler）：提取函数、内联、搬移、重命名、以多态替代条件、引入参数对象；坏味道识别：重复代码、过长函数、过大类、过长参数列、发散式变化、霰弹式修改、依恋情结、数据泥团；架构分层：表现层、应用层、领域层、基础设施层；依赖倒置；SOLID 原则：单一职责、开闭、里氏替换、接口隔离、依赖倒置；安全重构前提：有测试网或可对比的行为快照；重构 vs 重写：重构保行为、小步走；重写换行为、风险高 |
| 判定标准 | 外部行为不得改变，除非显式声明为行为变更；每步须可运行且可回滚；不得在同一提交中混合重构与功能改动；重构前后须有可对比的验证 |
| 常见失范 | 无测试网直接大改；重构同时改功能导致无法归因；过度抽象增加理解成本；为设计模式而设计模式 |
| 范本结构 | 现状与问题清单 → 重构目标与边界 → 分步计划 → 每步改动与验证 → 回归结果 → 遗留问题 |

#### EB1-01 架构与现状分析
- **必选组件**: 模块图、调用链、数据流、依赖清单、坏味道清单
- **可选组件**: 运行日志、文档、提交历史
- **组装顺序**: 读入口→追调用链→画数据流→列依赖→标坏味道
- **约束**: 须基于实际代码而非文档；耦合点须给文件行号
- **格式**: 架构现状报告

#### EB1-02 重构方案设计
- **必选组件**: 重构目标、边界、分步计划、验证手段、回滚点
- **可选组件**: 测试覆盖情况
- **组装顺序**: 定目标→划边界→拆步骤→配验证→设回滚
- **约束**: 每步须可独立验证；不得一次性大爆炸
- **格式**: 重构方案

#### EB1-03 代码简化与去重
- **必选组件**: 简化后代码、重复消除说明、复杂度对比
- **可选组件**: 静态分析报告
- **组装顺序**: 识重复→提公共逻辑→替换→简化控制流→回归
- **约束**: 行为不得改变；复杂度须有可量化改善
- **格式**: 简化提交

#### EB1-04 整洁代码改造
- **必选组件**: 改造后代码、命名对照表、职责划分说明
- **可选组件**: 项目规范、评审意见
- **组装顺序**: 统一命名→拆职责→收边界→补注释→评审
- **约束**: 须遵循项目既有规范；不得引入新风格
- **格式**: 改造提交+说明

#### EB1-05 架构演进与迁移设计
- **必选组件**: 目标架构、迁移步骤、兼容策略、数据迁移方案、回滚预案
- **可选组件**: 业务节奏、团队产能
- **组装顺序**: 定目标态→差距分析→分期迁移→定兼容→写回滚
- **约束**: 须有兼容期；数据迁移须可校验
- **格式**: 架构演进方案

### EB2 测试工程

#### 域级说明

**域定位**：建立可回归的验证网，让改动风险可被度量。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 策略→用例→自动化→执行 |
| 独立成域的理由 | 以可重复执行为验收点，覆盖率与稳定性是度量，产物本身不对外 |
| 穷尽性 | 5 个任务覆盖「策略→用例→自动化→执行」的 4 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 测试金字塔：单元（多）→ 集成（中）→ E2E（少）；用例设计方法：等价类划分、边界值、判定表、状态迁移、正交实验、错误猜测；TDD 循环：红（写失败测试）→ 绿（最小实现）→ 重构；E2E 稳定性：显式等待、稳定选择器、测试数据隔离、失败重试与截图；API 测试：契约测试、状态码、幂等性、鉴权、异常路径；性能测试：负载/压力/稳定性/尖峰；指标（P95/P99、TPS、错误率） |
| 判定标准 | 用例须覆盖正常流、异常流与边界；测试须可重复、无外部随机依赖；E2E 不得依赖固定等待时间；性能测试须给指标阈值与基线 |
| 常见失范 | 只测正常路径；用例相互依赖导致顺序敏感；用 sleep 等待导致不稳定；测试数据污染生产 |
| 范本结构 | 测试范围与策略 → 用例清单（含优先级） → 测试数据与夹具 → 自动化脚本 → 执行结果与覆盖 → 缺陷清单 |

#### EB2-01 测试策略与用例设计
- **必选组件**: 测试策略、用例清单（步骤/预期/优先级）、覆盖矩阵
- **可选组件**: 需求文档、接口定义
- **组装顺序**: 定范围→分层策略→设计用例→排优先级→建矩阵
- **约束**: 须覆盖异常与边界；用例须可独立执行
- **格式**: 测试用例集

#### EB2-02 单元测试与 TDD
- **必选组件**: 失败测试、最小实现、重构后代码、覆盖率报告
- **可选组件**: 代码结构、依赖注入方式
- **组装顺序**: 写失败测试→实现→重构→补边界→覆盖率
- **约束**: 测试须快且隔离；不得依赖网络与数据库
- **格式**: 单元测试套件

#### EB2-03 E2E 与集成测试
- **必选组件**: 场景清单、自动化脚本、稳定选择器、测试数据
- **可选组件**: 运行环境、测试账号
- **组装顺序**: 选关键路径→写脚本→稳选择器→隔离数据→跑通
- **约束**: 须显式等待；不得依赖固定 sleep
- **格式**: E2E 测试套件

#### EB2-04 API 接口测试
- **必选组件**: 接口清单、请求样例、断言、异常用例、契约校验
- **可选组件**: OpenAPI 定义、鉴权方式
- **组装顺序**: 列接口→写正向用例→写异常用例→验契约→自动化
- **约束**: 须覆盖鉴权失败与参数越界；须验幂等
- **格式**: 接口测试报告

#### EB2-05 性能测试与调优
- **必选组件**: 场景设计、压测脚本、指标结果（P95/P99/TPS）、瓶颈分析
- **可选组件**: 容量目标、监控数据
- **组装顺序**: 定目标→设场景→压测→看指标→定位瓶颈→建议
- **约束**: 须给基线对比；瓶颈须有证据（火焰图/慢查询）
- **格式**: 性能测试报告

### EB3 云与部署

#### 域级说明

**域定位**：把应用部署到云上并保持可运维，覆盖资源、存储、域名、AI 能力与发布。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 规划→配置→部署→监控 |
| 独立成域的理由 | 以可回滚与可运维为验收点，验收发生在发布之后而非交付之时 |
| 穷尽性 | 5 个任务覆盖「规划→配置→部署→监控」的 4 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 云计算基本对象：计算实例、对象存储、CDN、负载均衡、私有网络、安全组（各家命名不同，能力对应）；无服务器：云函数、静态托管、托管数据库、对象存储；DNS：A/CNAME/MX/TXT 记录、TTL、解析生效与缓存；AI 能力接入：OCR、ASR、TTS；鉴权多用 AK/SK 签名或临时凭证，具体字段以厂商文档为准；部署形态：静态托管、容器、函数、传统服务器；灰度与回滚；可运维性：日志、监控、告警、备份、成本 |
| 判定标准 | 资源规格须匹配预估负载并给扩容路径；密钥须用环境变量或密钥管理，禁止硬编码；部署须可回滚；须给成本估算与告警配置 |
| 常见失范 | 密钥写进代码或前端；未配安全组导致端口裸奔；无备份直接上生产；未设告警导致故障后知后觉 |
| 范本结构 | 资源清单与规格 → 网络与安全配置 → 部署步骤 → 环境变量与密钥管理 → 监控告警 → 回滚方案 → 成本估算 |

#### EB3-01 云资源规划与开通
- **必选组件**: 资源清单（类型/规格/数量）、网络拓扑、安全组规则、扩容路径
- **可选组件**: 访问量预估、预算
- **组装顺序**: 估负载→选规格→画拓扑→配安全组→开通
- **约束**: 须最小权限开放端口；须给扩容触发条件
- **格式**: 资源规划表

#### EB3-02 对象存储与 CDN 配置
- **必选组件**: 存储桶策略、目录结构、CDN 域名与缓存规则、生命周期
- **可选组件**: 访问模式、合规要求
- **组装顺序**: 建桶→设权限→定目录→配CDN→设生命周期
- **约束**: 存储桶不得公开可写；须设防盗链
- **格式**: 存储与CDN配置

#### EB3-03 域名与 DNS 配置
- **必选组件**: 解析记录表、TTL、证书状态、备案信息
- **可选组件**: 域名归属、服务商
- **组装顺序**: 加记录→设TTL→配证书→验解析→备案核对
- **约束**: 须核对备案；TTL 变更须说明生效延迟
- **格式**: DNS 配置表

#### EB3-04 云 AI 能力接入
- **必选组件**: 接口选型、鉴权实现、调用封装、限流重试、错误码映射
- **可选组件**: 业务场景、调用量
- **组装顺序**: 选接口→实现鉴权→封装调用→加限流重试→测通
- **约束**: 密钥须服务端持有；须处理配额与超时
- **格式**: 能力接入模块

#### EB3-05 部署发布与运维
- **必选组件**: 部署脚本、环境变量清单、监控指标、告警规则、回滚步骤
- **可选组件**: CI/CD 配置、SLA 要求
- **组装顺序**: 备环境→配变量→部署→验健康→配监控→留回滚
- **约束**: 须有健康检查；须验证回滚路径
- **格式**: 部署与运维手册

### EB4 应用开发

#### 域级说明

**域定位**：把需求或设计稿落成能跑起来的应用。这一步的价值不在代码优雅，而在跑通、可回滚、可交接。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 搭工程→实现→接数据→自测 |
| 独立成域的理由 | 以可运行与可回滚为交付标准，验收靠自测与回归 |
| 穷尽性 | 4 个任务覆盖「搭工程→实现→接数据→自测」的 4 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 小程序：页面生命周期、组件化、平台 API、分包、审核规范；Web 前端：组件化、状态管理、响应式布局、构建工具；后端接口：RESTful 设计、鉴权（JWT/Session）、参数校验、错误码、事务；工程结构：分层（表现/应用/领域/基础设施）、依赖注入、环境变量；性能：首屏优化、懒加载、缓存策略；可访问性：语义化标签、键盘可达、对比度 4.5:1 |
| 判定标准 | 接口须有参数校验与统一错误码；须处理空态、错误态与无网络；小程序须符合平台审核规范；须给运行说明与依赖清单 |
| 常见失范 | 接口无参数校验；硬编码数据源与密钥；只做正常态不做错误态；无运行说明导致无法复现 |
| 范本结构 | 功能范围与技术选型 → 目录结构 → 关键实现说明 → 接口约定 → 自测清单 → 运行与部署说明 |

#### EB4-01 小程序开发
- **必选组件**: 页面结构、组件清单、API 调用、云函数、审核自查
- **可选组件**: 设计稿、PRD、平台规范
- **组装顺序**: 读设计→搭骨架→写页面→接数据→自测→审核自查
- **约束**: 须符合平台规范；须处理无网络与空态
- **格式**: 小程序工程

#### EB4-02 Web 前端开发
- **必选组件**: 组件结构、路由、状态管理、样式方案、构建配置
- **可选组件**: 设计稿、设计系统
- **组装顺序**: 搭工程→拆组件→写样式→接数据→适配→构建
- **约束**: 须响应式与暗色适配；须语义化标签
- **格式**: 前端工程

#### EB4-03 后端接口开发
- **必选组件**: 接口清单、参数校验、鉴权、错误码、数据模型
- **可选组件**: 数据库结构、业务规则
- **组装顺序**: 定模型→写接口→加校验→加鉴权→自测
- **约束**: 须参数校验与统一错误码；须防注入
- **格式**: 后端服务

#### EB4-04 设计稿转代码
- **必选组件**: 还原页面、样式变量、组件抽取说明、差异清单
- **可选组件**: 设计稿、标注、切图
- **组装顺序**: 读标注→抽变量→搭结构→写样式→比对→修差异
- **约束**: 还原度须可比对；间距字号须取自标注
- **格式**: 还原页面+差异说明

### EB5 交互设计

#### 域级说明

**域定位**：研究用户与场景，设计流程与交互规则，保证可用与可及。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 研究→旅程→架构→交互→审计 |
| 独立成域的理由 | 以任务完成率与可用性问题数为验收点，产物是规则而非像素 |
| 穷尽性 | 5 个任务覆盖「研究→旅程→架构→交互→审计」的 5 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 用户研究：访谈、问卷、可用性测试、日志分析、A/B；用户旅程地图：阶段、触点、行为、情绪、痛点、机会；信息架构：卡片分类、树测试、导航层级（不超过三级）；交互规则：即时反馈、容错、撤销、渐进披露、状态可见；可用性启发式（Nielsen 十条）：系统状态可见、贴近真实世界、用户控制与自由、一致性与标准、防错、识别优于回忆、灵活高效、美观简约、帮助识别诊断恢复、帮助文档；无障碍（WCAG）：对比度、键盘可达、语义化、替代文本 |
| 判定标准 | 每个流程须标异常与空态；交互须有明确反馈与可撤销路径；对比度须达 4.5:1；关键路径步数不得多于必要 |
| 常见失范 | 只画正常流不画异常；导航层级过深；用颜色单独传达信息；忽略键盘操作 |
| 范本结构 | 研究结论 → 用户画像与场景 → 旅程地图 → 信息架构 → 关键流程与状态 → 交互规则 → 可用性检查 |

#### EB5-01 用户研究与画像
- **必选组件**: 用户画像、需求清单（含证据）、优先级
- **可选组件**: 访谈记录、行为数据
- **组装顺序**: 定研究问题→访谈→归纳→建画像→排需求
- **约束**: 画像须有证据；不得凭想象设定人群
- **格式**: 用户研究报告

#### EB5-02 用户旅程与流程设计
- **必选组件**: 旅程地图、流程图（含异常/空态）、痛点清单、机会点
- **可选组件**: 现有流程、客服反馈
- **组装顺序**: 分阶段→标触点→记情绪→找痛点→设计新流程
- **约束**: 须覆盖异常与空态；须标关键决策点
- **格式**: 旅程地图+流程图

#### EB5-03 信息架构与导航设计
- **必选组件**: 站点地图、导航结构（≤3级）、命名规范、卡片分类结果
- **可选组件**: 内容清单、用户心智模型
- **组装顺序**: 列内容→卡片分类→建层级→定命名→验可达
- **约束**: 层级不超过三级；命名须用用户语言
- **格式**: 信息架构图

#### EB5-04 可用性审计
- **必选组件**: 审计表（原则×问题×严重度）、截图标注、整改建议
- **可选组件**: 截图、交互稿
- **组装顺序**: 逐原则检查→记录问题→定严重度→给建议
- **约束**: 严重度须分级；建议须可执行
- **格式**: 可用性审计报告

#### EB5-05 无障碍设计与改造
- **必选组件**: 对比度检查表、语义化改造、键盘路径、替代文本
- **可选组件**: WCAG 条目、截图
- **组装顺序**: 查对比度→改语义→补键盘→加替代文本→复测

| 价值链形态 | 幂等设计→处理→校验→调度→监控 |
| 独立成域的理由 | 与其他产物不同构：脚本与管道的验收标准是"可重复执行且结果一致"，而非界面或观感。 |
| 穷尽性 | 5 个任务覆盖「幂等设计→处理→校验→调度→监控」的 5 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 幂等与可重入：同一输入重复执行结果不变；断点续跑与失败重试；数据管道：抽取-清洗-转换-加载；增量与全量的取舍；数据质量五维：完整性、唯一性、及时性、一致性、有效性；脚本工程：参数化、日志分级、退出码、干跑（dry-run）模式；调度与监控：定时触发、依赖编排、超时与告警；凭据与权限：环境变量注入、最小权限、审计留痕 |
| 判定标准 | 脚本须可重复执行且幂等；须有失败重试与断点续跑；数据须过五维质量校验；不得硬编码路径与凭据 |
| 常见失范 | 一次性脚本不敢跑第二遍；无日志导致失败无迹可寻；全量重跑覆盖了正确数据；凭据写死在脚本里 |
| 范本结构 | 任务目标与触发方式 → 输入输出与幂等设计 → 处理流程与异常分支 → 数据质量校验 → 日志与告警 → 退出码与集成方式 → 运行与回滚说明 |

#### EB11-01 自动化脚本设计
- **必选组件**: 任务目标、输入输出、参数清单、质量统计口径、幂等策略、异常分支与退出码
- **可选组件**: 现有手工流程、运行环境
- **组装顺序**: 定目标→定输入输出与质量口径→设计幂等→列异常分支与退出码→写运行说明
- **约束**: 须幂等且可 dry-run；不得硬编码路径与凭据；退出码须分级
- **格式**: 自动化脚本+说明

#### EB11-02 数据管道搭建
- **必选组件**: 数据源清单、字段映射、清洗规则、增量策略、目标表结构
- **可选组件**: 数据字典、调度条件
- **组装顺序**: 定源→定映射→写清洗→定增量→加载→验证
- **约束**: 增量策略须说明去重与迟到数据处理
- **格式**: 数据管道

#### EB11-03 数据质量校验
- **必选组件**: 校验规则表（维度/规则/阈值）、异常清单、阻断策略
- **可选组件**: 历史数据分布
- **组装顺序**: 定规则→跑校验→标异常→定阻断阈值→出报告
- **约束**: 五维须全覆盖；阻断规则须与下游约定
- **格式**: 数据质量报告

#### EB11-04 定时调度与监控
- **必选组件**: 调度配置、依赖拓扑、超时与重试策略、告警规则
- **可选组件**: 运行时资源、值班安排
- **组装顺序**: 定频率→排依赖→设超时重试→配告警→验一次
- **约束**: 须有超时与告警；失败须可定位
- **格式**: 调度与监控配置

#### EB11-05 批处理性能优化
- **必选组件**: 耗时分布、瓶颈定位、优化方案、优化前后对比
- **可选组件**: 运行日志、资源监控
- **组装顺序**: 测耗时→找瓶颈→改实现→比对→回归
- **约束**: 优化须附前后对比；不得牺牲正确性
- **格式**: 性能优化报告

### EB12 安全与可观测性

#### 域级说明

**域定位**：让系统在坏的情况下也知道自己在坏。防不住是常态，看不见才是事故。

| 维度 | 内容 |
|------|------|
| 价值链形态 | 建模→加固→观测→告警→响应 |
| 独立成域的理由 | 与其他产物不同构：验收标准是"出事前能防、出事时能看见、出事后能查清"，而非功能是否可用。 |
| 穷尽性 | 5 个任务覆盖「建模→加固→观测→告警→响应」的 5 个环节；按输入物、失败模式、验收标准三条判据互不重叠，无未覆盖环节 |
| 知识要点 | 威胁建模：资产-威胁-脆弱性-对策；STRIDE 六类（仿冒、篡改、否认、泄露、拒绝服务、越权）；权限与密钥：最小权限、职责分离、密钥轮换、临时凭证优先于长期 AK；可观测性三支柱：日志（发生了什么）、指标（趋势如何）、链路追踪（慢在哪一跳）；告警设计：症状告警优于原因告警；同因合并；避免告警疲劳导致集体无视；应急响应五步：发现-遏制-根除-恢复-复盘；每步须有明确责任人 |
| 判定标准 | 关键资产须有威胁建模，不得只做漏洞扫描；密钥不得硬编码且须可轮换；每条告警须可执行，无对应动作的告警不得上线；须有应急响应流程与责任人 |
| 常见失范 | 只跑扫描器不做威胁建模；告警太多，最终无人查看；日志无保留策略，出事时已被轮转；密钥写进代码或配置仓库 |
| 范本结构 | 资产与威胁清单 → 防护措施 → 权限与密钥方案 → 可观测性设计 → 告警规则 → 应急响应预案 |

#### EB12-01 威胁建模与安全加固
- **必选组件**: 资产清单、威胁清单（STRIDE 分类）、脆弱性、加固措施
- **可选组件**: 架构图、数据流向、历史事件
- **组装顺序**: 列资产→画数据流→套 STRIDE→列威胁→定加固
- **约束**: 须覆盖越权与数据泄露；不得用扫描替代建模
- **格式**: 威胁模型与加固方案

#### EB12-02 权限与密钥治理
- **必选组件**: 权限矩阵、角色定义、密钥清单、轮换周期、审计留痕
- **可选组件**: 账号体系、现有密钥
- **组装顺序**: 定角色→定权限→最小化→定轮换→留审计
- **约束**: 须职责分离；密钥不得明文；须可轮换
- **格式**: 权限与密钥方案

#### EB12-03 日志指标链路体系
- **必选组件**: 日志规范（级别/字段/保留期）、核心指标集、追踪埋点方案
- **可选组件**: 现有监控、业务关键路径
- **组装顺序**: 定规范→定指标→定埋点→定保留→定查询
- **约束**: 须覆盖关键路径；日志须结构化；保留期须满足审计
- **格式**: 可观测性设计

#### EB12-04 告警规则设计
- **必选组件**: 告警清单（指标/阈值/级别/动作/责任人）、抑制规则、值班表
- **可选组件**: 历史告警记录、SLA
- **组装顺序**: 选症状→定阈值→定级别→配动作→设抑制
- **约束**: 每条告警须有动作与责任人；须设抑制与聚合
- **格式**: 告警规则表

#### EB12-05 应急响应预案
- **必选组件**: 分级标准、响应流程、角色分工、通报路径、复盘模板
- **可选组件**: 历史事故、组织值班
- **组装顺序**: 定分级→定流程→定分工→定通报→定复盘
- **约束**: 须含对外通报口径；复盘须产出改进项
- **格式**: 应急响应预案
