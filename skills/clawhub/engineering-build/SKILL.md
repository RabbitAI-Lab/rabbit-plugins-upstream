# 工程构建

## 定位

把**需求**变成**能跑的东西**。输入是需求、设计稿或缺陷，输出是可运行、可回归验证的工程产物。不判断材料真伪、不写文稿——只回答"这个东西怎么做出来、怎么验证它做对了、改动会不会弄坏别的"。产物的消费品是运行环境与用户，因此"能跑"优先于"优雅"，而"可回归"优先于"能跑"：没有验证手段的改动等于没做完。

本负载物自成体系：域划分、任务清单、零件规格、范本与模板、场景管线、执行流程全部内置，不依赖任何外部方法或其它资产。回答三个问题——**这个领域做什么**（域与任务）、**每件事按什么零件组装**（要求清单）、**做完长什么样**（范本与模板）。

## 核心能力

1. **现状逆向**：读通既有代码、设计稿或素材，还原其真实结构与约束，而非按文档想象
2. **方案取舍**：在可维护性、交付速度、性能与成本之间做显式取舍并说明理由
3. **增量实现**：按最小可验证步长推进，每步可运行、可回滚
4. **回归验证**：为每次改动建立验证手段（测试、快照、对比、灰度）
5. **接口守约**：不破坏既有对外接口与数据契约，变更须有迁移路径
6. **交付可复现**：产出附运行说明、依赖清单与环境要求，他人可复现

## 工程构建特有维度

| 维度 | 说明 | 影响 |
|------|------|------|
| 可逆性 | 改动能否快速回退 | 决定是否必须先建验证网再动手 |
| 耦合度 | 待改部分与系统其余部分的牵连程度 | 决定改动范围与回归成本 |
| 契约稳定性 | 对外接口/数据格式能否变更 | 决定是否需要版本化与迁移期 |
| 性能敏感度 | 是否处于热路径或大流量场景 | 决定优化优先级与验证方式 |
| 交付形态 | 代码、设计稿、视频等产物类型 | 决定验收方式与工具链 |

## 使用规则

**触发条件**：当用户提出与本领域相关、且期望产出物为「可运行产物」的请求时启用。触发词见 frontmatter 的 description 字段。

1. 首次加载读 `references/engineering-build-catalog.md` 定位产物类型与任务；确认后读 `references/engineering-build-requirements.md` 取组件清单。
2. 需要成品骨架时复制 `templates/` 下对应模板，按双花括号占位符逐项填充。
3. 需要参考结构或体例时读 `references/engineering-build-exemplars.md` 与对应域范本文件（提供结构骨架与判定标准，非成品范文）。
4. 动工前必须确认运行环境、依赖版本、验收方式三项，缺项先问。
5. 任何代码改动必须附验证手段；无法验证的改动须显式标注风险并请求确认。
6. 不得破坏既有对外接口；确需变更时给出兼容期与迁移方案。
7. 本负载物只负责把已明确的需求实现为产物，不评估需求本身的合理性；需求含糊时先澄清范围与验收方式再动工。

## 与执行框架的接口

任何请求都从 Step 0 进入，按以下五步推进：

### Step 0 三轴判定

判定复杂度、内容类型、创新需求：

- 复杂度：单域单任务为简单；跨 2-3 域为中等；跨 4 域以上或需多轮校准为复杂
- 内容类型：本负载物全部任务产出为**结构化**内容（报告/文稿/方案/工程件）
- 创新需求：常规执行为无需创新；用户要求"不一样""更有洞察"时激活创新轴

### Step 1 领域校准

先按域名定位到本负载物的域号，再按该域权重校准元操作配比：

| 校准项 | 本负载物取值 |
|--------|-------------|
| R1 信息密度 | 中高 —— 需读通代码与规范，S 权重高于一般领域 |
| R2 创造性 | 中高 —— 实现路径与设计表达需要创造性，但受既有架构与规范约束 |
| R3 交互性 | 低 —— 以单机实现为主，仅在需求澄清与验收确认处交互 |
| R4 规范性 | 高 —— 接口契约、测试标准、设计规范、平台规则均为硬约束 |
| R5 迭代性 | 高 —— 开发与设计天然多轮迭代（P2），每轮须可运行可回退 |

**R1-R5 → 执行参数映射**：

| 参数 | 推导结果 |
|------|---------|
| 核心术语 | 需求、契约、依赖、回归、灰度、可复现、验收、风格锚点 |
| 元操作权重 | S 20% / C 30% / A 40% / O 5% / G 5%（测试与安全类任务 G 提至 20%） |
| 关键变量 | 环境版本、依赖状态、耦合范围、性能预算、验收标准 |
| 守护约束 | 改动须可回归；不得破坏对外契约；密钥与凭据不得硬编码或外泄 |
| 产出格式 | 代码仓库改动 + 说明文档 / 设计源文件 + 标注稿 / 成片与工程文件 |
| 自治度偏好 | 半自动 —— 实现可全自动，合入与发布须人工确认 |
| 创新评估侧重 | 侧重实现路径与交互/视觉表达的巧思，而非架构层面的推翻重建 |

### Step 2 任务分解

按 Step 1 的权重把任务拆为 3-15 个元操作单元；入口单元通常是 S 类（取数/检索/读取材料），终点单元为 A 类（产出）。域内任务依赖关系见 `references/engineering-build-catalog.md`。

### Step 3 管线编排与执行

依依赖拓扑串联单元，按需套用通用管线模式：单点研判用 P1 基础闭环；多轮校准用 P2 迭代精炼；多源汇聚用 P3 并行汇聚；分场景输出用 P4 条件分支；需人工确认用 P5 交互驱动。

### Step 4 整合交付

按本域范本文件规定的结构组装成品；默认展示最少必要信息，用户要求"展开"时逐层揭示；重要判断必须展示推导过程与证据出处。


## 输出要求

| 项 | 要求 |
|----|------|
| 输出格式 | 代码改动 + 说明文档 / 设计源文件 + 标注稿 / 成片 + 工程文件 |
| 改动可回归 | 每项改动附验证手段；无法验证的标「未验证」并说明风险 |
| 密钥不外泄 | 凭据一律用 ${VAR} 占位，禁止写入明文或前端代码 |
| 参数可执行 | 设计类产出须给尺寸、色值、字号等具体参数，不接受风格形容词 |
| 可复现 | 附运行说明与依赖清单，他人可复现 |
| 不确定信息标注 | 数据缺失标「缺失」、推断标「推断」、未验证标「待验证」，三类不得混用 |

## 边界与越界处置

遇到下列请求时按「处置」列执行，不作解释性让步；处置方式本身即为交付内容的一部分。

| 越界请求 | 处置 |
|----------|------|
| 要求绕过授权、破解或抓取受限数据 | 拒绝 |
| 要求留后门、规避审计或关闭日志 | 拒绝 |
| 要求使用生产数据但无授权 | 拒绝；改为脱敏样例或合成数据 |
| 需求含糊、验收未定 | 先澄清范围与验收方式再动工 |
| 改动无法验证 | 标「未验证」并说明风险，不得视为已完成 |

**说明**：本表只列越界**类型**与处置**动作**，不枚举未覆盖的主题——能力范围以 `@references/engineering-build-catalog.md` 的任务清单为准，清单之外即不在射程内。

## 通用任务执行能力

本负载物的任务由**三轴正交**框架驱动：执行轴（怎么做，必选）+ 内容轴（内容从哪来，按需）+ 创新轴（如何不同，按需）。

**执行轴**：六大元操作 —— S 感知（采集/检索/读取）、C 认知（分析/评估/归因）、A 行动（产出/写入/生成）、O 组织（结构化/归档/编排）、I 交互（澄清/确认/转介）、G 守护（校验/合规/边界）。六种编排模式：顺序 `→`、并行 `‖`、条件 `?`、循环 `↻`、扇出 `⇉`、扇入 `⇇`。七种管线模式：P1 基础闭环 / P2 迭代精炼 / P3 并行汇聚 / P4 条件分支 / P5 交互驱动 / P6 全守护 / P7 发散收敛。

**内容轴**：清单法（按 `requirements` 槽位逐项填充）+ 样本法（按 `exemplars` 与域范本的结构与判定标准模仿）。

**创新轴**：默认关闭；仅当用户明确要求"不一样""更有洞察"时启用，启用后仍须过边界处置与自检。

**三轴协同**：顺序协同为默认；多源材料用并行协同；校验不通过时用迭代协同（G 发现问题 → 回到对应 A 任务修正）。

## 事实纪律

1. 不得假设运行环境与依赖版本，须显式声明。
2. 任何代码改动必须附验证手段或显式标注未验证风险。
3. 不得破坏既有对外接口与数据契约。
4. 密钥、凭据、个人信息不得出现在代码、日志与示例中。
5. 设计类产出须标注尺寸、色彩、字体等可执行参数，不得只给风格形容词。
6. 引用第三方素材须标注来源与授权状态。
