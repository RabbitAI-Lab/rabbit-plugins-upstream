# agentbus

> 让两个（或多个）AI agent 靠一个共享文件夹交接任务，每一步都留痕可查。

一个零依赖的 Python 单文件。没有 broker、没有 socket、没有数据库、没有常驻进程。
拷走这个文件夹，整个系统就搬走了。

**v0.2 已经能跑**：`agentbus.py` 1377 行、只用标准库、27 条自测全过（Python 3.13 与 3.9 各跑一遍）。
协议层不认识任何具体产品——代码、队列、台账里没有出现任何一个 agent 名字。

---

## 先说什么时候不用它

省你五分钟：

- **你只有一个 agent。** 不用。自己跟自己交接没有意义。
- **你的活是"问一句、答一句"。** 不用。总线的价值在跨会话、跨天、跨人。
- **你想要两个 agent 实时对话、互相商量。** 不用。这里只有"派出去、交回来"，中间是黑盒。
- **你不想敲命令。** 不用。没有 GUI，也不会做。
- **你只是想让 AI 干得更快。** 它不会让任何事变快。它让事变得**可追查**，代价是每次多两步。

它只解决一个问题：**你让 agent 干的活，过几天需要证明"谁干的、干完没、结果可不可信"。**

如果你没这个需求，直接关掉这一页。

## 30 秒看懂

```
派单方                                    执行方
  │                                         │
  ├─ dispatch  建任务包 → queue/pending/     │
  │                                         ├─ claim   原子领取，拿租约
  │                                         ├─ 干活
  │                                         ├─ 写回执（结论码独占一行）
  └─ 核对证据 ← queue/completed/ ←─────────── complete
                    ↓
              共享台账追加一行
              月度复盘自动记一条
```

跑起来是这样（下面是从真机复制的输出，不是手写的）：

```
$ agentbus dispatch --title "示例：核对一份清单" --goal "逐项核对，给出差异"
{"status": "QUEUED", "id": "T-20261128-001", "package": ".../tasks/T-20261128-001/任务包.md"}

$ agentbus claim --worker worker-a
{"status": "IN_PROGRESS", "attempt": 1, "lease_expires_at": "2026-11-28T03:31:32+08:00", ...}

$ agentbus complete --id T-20261128-001
{"status": "COMPLETED", "result": "COMPLETED", "worker": "worker-a",
 "receipt_sha256": "7e62e2e3...", "ledger": "updated", "review": ".../2026-11.md"}
```

台账里多出这一行：

```
| 2026-11-28 | `T-20261128-001` | 示例：核对一份清单 | worker-a | `COMPLETED` | 回执：.../回执包.md | 2026-11 |
```

## 四条命令起步

```bash
curl -O https://raw.githubusercontent.com/lisong2003-lgtm/agentbus/main/agentbus.py

python3 agentbus.py demo              # 临时目录真跑一遍完整流程，0.3 秒，不碰你的真实数据
python3 agentbus.py init --wizard     # 回答三个问题，生成 CONTRACT.md
python3 agentbus.py dispatch --title "..." --goal "..."
```

`init --wizard` 会生成一份 `CONTRACT.md`。它是唯一需要你手写的东西，也是唯一需要你动脑子的地方。

装到本机默认位置（之后任何目录、任何 shell 都不用再带 `--root`）：

```bash
python3 agentbus.py init --set-default
```

## 契约长什么样

```markdown
# CONTRACT

- 总线：`/Users/you/agentbus`

## 参与者
- main — 派单、排优先级、终审、出结论码
- worker-a — 可执行物（代码、脚本、配置、构建）
- worker-b — 可读物（报告、表格、清单、图示）

## 归属
- 可执行物 → worker-a
- 可读物 → worker-b
- 验证 → main，即使对象是 worker-b 的产出

## 规则
- worker 不自判 PASS，只写自己执行的那一半记录。
- 结论码只有三个：COMPLETED / FAIL / PARTIAL（PASS 视作 COMPLETED）。
- 回执里结论码必须独占一行，例如 `结论：COMPLETED`。
- 冲突顺序：用户当场指令 > 派单方 > worker 自选。
```

**所有 agent 的接入片段都只有一句话：开工前读 `<绝对路径>/CONTRACT.md`。**

路径只写一次。换机器改一行。加第三个 agent 加一段。代码里不认识任何具体产品。

生成片段（默认只打印，不替你改别人的配置文件）：

```bash
python3 agentbus.py adapter codex          # 也可用 claude-code / cursor / generic
python3 agentbus.py adapter codex --write ~/.codex/AGENTS.md --force
```

## 它真的跑过

2026-11-28 凌晨，用它的前身（0.1.6 专用版）跑了一次真实任务：

| 环节 | 实际时间 | 结果 |
|---|---|---|
| dispatch | 02:07:46 | 队列 `pending` |
| claim | 02:07:48 | 租约 1800 秒 |
| 交付 | 02:25 | 149 行核查报告，SHA-256 记账 |
| complete | 02:26 | `ledger: updated`，复盘自动追加 |

那次任务的内容是核查一台机器上的插件与配置基线。**报告推翻了执行方前一天口头给出的一个结论**——当时说"4 个插件被禁用，与基线不符"，实际保护脚本里有豁免表，那 4 个关闭是合规的。

如果没有"每项差异必须附实测命令与原始输出"这条约束，这个错误会一直留在记录里。

这就是它唯一的价值：**不是让 AI 更聪明，是让 AI 的错误留下痕迹。**

## 它防住了什么

这几条是 v0.2 里花力气最多的地方，也是和"拿两个文件夹传话"的区别：

| 会出的事 | 这里的处理 |
|---|---|
| 回执正文写着"本次未达到 PASS" | 只有**独占一行**的结论码才算数，句子里的一律不算 |
| 结论码写成五花八门 | 封闭词表 + 别名表（PASS→COMPLETED），其余直接拒收，不写台账 |
| 台账被手工漏记 | `complete` 发现缺行会补一行，并告警 |
| 两个人同时领取 | `flock` 跨进程互斥；进程死了锁自动释放，不靠猜文件年龄 |
| 写到一半断电/被杀 | 先写临时文件再 `os.replace`，任何时刻读到的都是完整文件 |
| 队列文件损坏后队列"永远为空" | 隔离进 `queue/corrupt/` 并留原因，不静默跳过 |
| 任务包被删了还在队列里 | `claim` 直接判失败并记账；`doctor` 也能查出来 |
| 领了不交，任务永远卡住 | 租约到期 + `requeue` 放回队列，`attempt` 累加看得出被领过几次 |

自测里专门有一条叫 `test_verdict_inside_sentence_is_not_a_verdict`——它守的就是第一条。

## 命令

| 命令 | 干什么 |
|---|---|
| `init [--wizard] [--set-default]` | 建目录、生成 CONTRACT.md、记为本机默认 |
| `dispatch` | 建任务包入队；不填 `--id` 自动编号 `T-YYYYMMDD-NNN` |
| `claim --worker <名字>` | 原子领取并拿租约；名字随便起 |
| `complete --id <编号>` | 读回执里的独占行结论，写台账与复盘 |
| `status` | 队列状态（JSON，给脚本用） |
| `doctor [--fix]` | 体检：缺包、坏文件、过期租约；`--fix` 隔离坏文件 |
| `requeue [--id]` | 过期任务放回队列；不带 `--id` 处理全部过期 |
| `heartbeat --id` | 长任务续租 |
| `adapter <name> [--write]` | 打印/追加某个 agent 的接入片段 |
| `demo` | 临时目录真跑一遍，0.3 秒，跑完清理 |

不带参数直接跑，任何错误都以 `{"status":"ERROR","error":"..."}` 打到 stderr 并返回 1，方便被脚本调用。

## 为什么不做成服务

很多人第一反应是"为什么不用 MCP / 消息队列 / SQLite"。

- **MCP** 需要双方都实现、都有进程活着。现实是两个 agent 各自在沙箱里，互相看不见。
- **消息队列** 要多一个常驻进程。多一个进程就多一个会挂的东西。
- **SQLite** 是二进制，人和 agent 都不能直接读。出了问题没法眼看手改。

文件的好处是：**任何 agent 都能读写，出问题能直接看，拷走就能搬走。** 代价是并发能力弱——只支持"一个任务一个人领"，不支持两个 agent 同时改同一份东西。这个代价是故意付的。

---

## 局限，写在前面

- **不并发。** 一个任务只能一个 worker 领。同时十个任务会串行处理。
- **不实时。** 没有推送。谁来取任务谁就干活，没人取任务就干等着。
- **不校验内容质量。** 哈希只能证明文件没变，不能证明内容对。判断质量仍然靠人。
- **租约要人管。** 长任务不续租会过期，过期任务需要 `requeue` 放回队列。
- **单机。** 共享文件夹靠你同步（iCloud、Syncthing、SMB 都行），协议本身不处理冲突。
- **v0.2 只有一种任务类型。** 原来那套"只读验收 / 隔离候选"两条路径被砍掉了，等真有第三方写队列再加回来。
