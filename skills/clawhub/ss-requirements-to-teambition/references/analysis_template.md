# AI 分析 + 任务创建模板

## ⚠️ 核心分类方法论（先读这个）

所有进入分析的会话都已被打上「HelpKnow需求」或「AI员工」标签，**标签本身就是 AI 相关性保证**。不要因为会话后半段出现了 SS 平台话题（如导出、套餐、版本）就整条判为非 AI 相关。

### 三层分类（一个会话可同时产出多类）

| 层级 | 判断标准 | 产出 | 示例 |
|------|---------|------|------|
| ✅ FAQ/已解决 | 客服给出有效答案，客户确认理解 → 该条不建单 | 过滤 | 「AI怎么发PDF？」→ 客服教了，客户说OK |
| 🐛 BUG | 功能异常、设置不生效、客服说「反馈技术排查」**或仍在排查中未解决** | 建 BUG | 人设禁止词不生效、离线AI还在发消息、AI转人工配置了但不执行 |
| 🆕 需求 | 客户要的功能不存在、客服说「不支持/没有」→ 不管后面有没有 FAQ 部分，功能缺失就是需求 | 建需求 | 「AI能主动回访吗？」→ 客服说不支持 |

**关键规则**：
- **一个会话可以同时产出 BUG + 需求**，不是二选一
- **标签保证**：有标签 → 必有 AI 相关内容，不要整条过滤
- **SS 平台讨论不覆盖 AI 需求**：客户在问 AI 功能的同时问了 SS 平台功能，不能因为后者存在就把 AI 需求也过滤掉
- **「不支持」= 需求信号**：客服回复功能不支持、做不到、没有 → 这就是产品需要补齐的能力
- **「未解决」= 必须建单**：客户描述了明确的功能异常现象（如「配置了转人工但没转」「设置了但没生效」），即使客服回复「在排查/需授权/等技术确认」，只要问题未当场解决，就必须建 BUG。客服没解决 ≠ 没问题

## 🔗 上下文会话（新增）

ctx JSON 中每个锚点会话可能带有 `context` 字段，包含同一客户在时间窗口内的相邻会话（前 2 后 1，按 `before_2`/`before_1`/`after_1` 标记）。

**分析规则**：
- **锚点会话是主数据源**：任务创建、session_id 填写均以锚点为准
- **上下文会话是辅助信息**：帮助理解客户问题的完整背景（如之前的机器人对话、初次尝试过程）
- **典型场景**：
  - 上下文是机器人接待（agent=系统）→ 客户在上下文里描述过问题，在锚点里说「还是不行」→ 合并理解，不要因为锚点里问题描述不完整就判为信息不足
  - 上下文是同客户多次转人工 → 看前面客服有没有交代背景，避免重复建单
- **上下文会话不独立建单**：只用于辅助理解锚点会话，不要在 TB 中为上下文会话单独创建任务
- **备注中引用**：如果上下文提供了关键信息（客户早期原话、尝试过的步骤），在 note 的「需求详情」中注明来源（如「客户在前序会话 [session_id] 中提到…」）

## 分析流程

1. 读取 `scripts/data/` 下最新的 JSON 文件
2. 对每个会话,先拆分出 N 个独立的 demand
3. 对每个 demand:
   - 拉取所有「未完成」TB 任务(`isDone = false`)
   - 在内存中按 `SS客户名称` 字段匹配
   - 按内容相似性判断合并/新建
   - 执行对应操作

## 🚫 强力红线(拦截机制与强制提取)

在需求拆分(第一步)和执行操作(第三步)时,必须严格执行以下红线,违反任一条禁止建单或输出:

1. **【纯答疑/已解决】严格拦截**:
   - 必须仔细分析客服的消息。如果客户只是在咨询功能原理、机制、操作方法,且客服已经给予了明确解答、客户表示理解或问题已正常解决,**严禁新建任何 Teambition 任务**。
   - **除非**满足以下任一条件:
     - 客服明确承认是功能缺陷
     - 客服承诺了未来要排期优化
     - 客服明确表示"我们去提个需求/反馈给研发"
     - **客服明确回复功能不支持/不可以/做不到/暂未开放**——功能缺失本身就是需求，不能因客服给出否定结论就拦截。这是产研需要补齐的能力。
   - **⚠️ 客户接受判定（通用拦截）**：以下情况**即使满足上述任一建单条件，也必须拦截，禁止建单**：
     - 客服承认限制后给出了**有效的变通方案**（如「可以用XX功能替代」「试试YY方式」），且客户明接受/满意（「好的谢谢」「明白了」「那也行」等）。——此类会话已闭环，无需建单。
     - 判断关键：客服是否提供了可操作的替代方案 → 客户是否认可。只有「客服说做不到且无替代方案」或「客户不接受替代方案」时才建单。
   - 咨询类问题仅在需要沉淀为文档/FAQ时，由人工手动整理，不允许自动化需求系统建单。

3. **【非 AI 相关需求禁止建单】**：
   - SaleSmartly 平台自身的功能（自动化工作流配置、通讯录/号码管理、权限角色设置、测试沙箱等），只要跟 HelpKnow AI 员工没有直接关系，**禁止在 HelpKnow 需求项目中创建任务**。
   - 判断标准：这个需求/问题是 AI 员工的行为逻辑有问题、AI 员工缺失某项能力、还是单纯是 SaleSmartly 平台的操作/功能问题？只有前者可以建单。
   - 如果客服确认平台暂时没有某个功能，但该功能与 AI 无关，也不属于可建单范围。
   - **⚠️ SS 平台功能明确排除清单**：以下 SS 平台功能即使被打上「AI员工」标签，也**必须拦截，禁止建单**：
     - **素材库**：文件夹管理、素材上传/下载/分类 → 属于 SS 平台文件管理，非 HK AI 能力
     - **话术库**（非 AI 话术部分）：话术模板编辑、话术分类 → 属于 SS 平台内容管理
     - **渠道管理**：WhatsApp/Facebook/Telegram 等渠道的接入和配置
     - **自动化规则/工作流**：非 AI 相关的自动回复、分配规则
     - **其他 SS 平台操作**：套餐升级、导出限制、权限设置、号码管理等
   - **⚠️ 混合会话处理**：当会话中同时讨论 AI 问题和非 AI 问题（如 Pro版导出限制、套餐升级），**只过滤非 AI 部分，AI 部分仍需按三层分类处理**。不要因会话后半段出现 SS 平台讨论就整条丢弃。

2. **【客服处理结论】强制提取且禁止空泛**:
   - 任何新建任务或备注追加中,`客服处理结果` **绝对禁止留空、禁止写"处理中/待跟进/排查中/未给出明确结论"等空话**。
   - **核心原则：如实记录客服做了什么、说了什么**。目的不是判断问题是否解决，而是让你看到客服的应对方式——是否有异常、是否可优化、是否可作为培训素材。即使客服给了一个很简单很短的解答（如「分配给AI员工就行了」），也必须完整记录。
   - **必须逐条引用客服的关键答复**：用「→ 客服回复："原文引用"」格式，把客服针对该问题给出的答复逐条列出。如果是FAQ式简单答疑，就如实写FAQ式答疑——不要因为没有「反馈技术排查」就觉得没结论。
   - **客户接受/拒绝状态必须记录**：客服给出方案后，客户说了「好的/明白了/谢谢」还是「还是有问题的/不行」，必须写明。这是判断客服处理质量的关键信息。
   - **必须按需求维度精确匹配客服答复**:同一会话拆出多个 demand 时,不同 demand 可能对应客服不同的答复内容。禁止把所有客服消息一股脑塞给所有任务--必须根据需求内容,定位到客服针对该具体问题给出的那一段答复。
   - 如果客服全程只发了系统消息/自动回复,未对需求进行人工回复,必须写明:"客服未针对此需求进行人工介入;客户通过系统自动回复(引用自动回复摘要)了解到相关信息。"
3. **【备注格式规范】**:所有新建任务的 note 必须严格遵循以下章节顺序:
   ```
   ## 涉及客户
   ## 客户业务场景
   ## 需求详情
   (具体条目列表,## 需求详情 后面必须空一行再写内容)
   ## 客服处理结果
   ## 用户提供的截图/文件
   ## 会话信息
   ```
   每两个 `##` 标题之间保留一个空行,内容与标题之间保留一个空行。
4. **【截图必须内嵌图片格式】**：`## 用户提供的截图/文件` 章节中的所有截图，**必须使用 `![描述](URL)` Markdown 图片语法嵌入**，禁止使用 `[文字](URL)` 链接语法、禁止用纯文字描述代替图片。
   - ✅ 正确：`![客户截图1](https://assets-cdn.salesmartly.com/...)`
   - ❌ 错误：`[截图1](https://assets-cdn.salesmartly.com/...)`
   - ❌ 错误：`4张截图（AI未回复的记录）`
   - 原始数据中客户消息的图片 URL（`sender_type=1` 且 text 以 `https://assets-cdn` 开头）和客服消息中的 `file_url`（`sender_type=2` 且 text 为 file 对象）都需要提取为 `![](url)` 格式。

## 第一步:拆分 demand

**判断维度**(满足任一即拆分):
1. 不同功能模块(批量导入 vs AI回复 vs 数据导出)
2. 同一模块的不同问题(AI回复"太慢" vs AI回复"答非所问")
3. 不同产品线
4. 客户明确说了两件不相关的事

**输出**:拆分决策 + 每个 demand 对应的客户消息

## 第二步:demand 分配

### 2.1 拉取未完成任务

```python
# 查所有未完成任务
searchProjectTasksV3(
    projectId="6959d07f4991ad9a71ca2afa",
    q="isDone = false",
    pageSize=100
)
```

### 2.2 内存过滤

从返回结果中,筛选 `SS客户名称`(cfId=`6a1422a4f4593ff6edd1ee63`)与当前会话 `customer_name` 匹配的任务。

**匹配逻辑**:字段值包含 `customer_name` 即匹配(因为该字段格式如 `HelpKnow.ai 服务群 项目ID:27828`)。

### 2.3 内容相似性判断

对匹配到的已有任务,逐个与新 demand 做内容相似性判断:

| 判断 | 条件 | 操作 |
|------|------|------|
| **同一件事** | 客户明确说「跟之前一样」/ 同一功能点 / 48h内同一操作目标且内容相关 | 追加到已有任务备注 |
| **疑似相关** | 涉及同一模块但不确定 | 新建,备注标注「疑似与 [任务标题] 相关」 |
| **完全新需求** | 新功能点 / 超过7天 / 内容无重叠 | 正常新建任务 |

## 第三步:执行操作

### A. 追加备注(合并)

1. 用 `queryTaskV3` 读取目标任务的当前 `note`
2. 拼接新内容块
3. 用 `updateTaskNoteV3` 整体写入

**追加备注格式**(接在原 note 后):
```
--更新 [时间](session: [session_id],客服:[接待客服真实姓名])--
[本次新增的需求详情]

---
[原有 note 完整保留]
```

### B. 新建任务

**标题格式**:
- 有 `ss_project_id` 时:`[{ss_project_id}] {summary}`
- `ss_project_id` 为空时:直接用 `{summary}`，不加 `[]` 前缀

**任务参数**:
- **stageId(必填):`69fed981a6333372a4b12b72`**——必须是「客户需求（AI记录）」列表
- projectId:`6959d07f4991ad9a71ca2afa`
- scenariofieldconfigId:`6959d080d242a000e6f0de59`

**自定义字段**:
- 需求orBUG(单选):`cfId=69df253e95d7ece67f2d6e94`
  - 需求→`69df253e95d7ece67f2d6e95`
  - BUG→`69df253e95d7ece67f2d6e96`
- SS客服沟通会话ID(文本):`cfId=69df25e800b8437a49b4840e`,值=`session_id`
- SS客户名称(文本):`cfId=6a1422a4f4593ff6edd1ee63`,值=`customer_name`
- ⚠️ HK项目ID(文本):`cfId=69e055b3f2ad64465068810e`——**该字段始终留空，不要填写任何值**
- ⚠️ **BUG 仅填问题分类**, cfId=`69e1cf00cedd6482fe39b0c1`（多选）
- ⚠️ **需求仅填需求方向**, cfId=`69e07ac01888a925adbc27fc`（多选）
- **这两个字段互斥，禁止同时设置！**

**note 格式**:
```
## 涉及客户
[客户名称] | SS项目ID: [ss_project_id，若为空则不写此行]

## 客户业务场景
[客户背景、当前使用情况]

## 需求详情
1. **问题一标题**:问题描述。客户原话。客服处理结果。
2. **问题二标题**:问题描述。客户原话。客服处理结果。

## 用户提供的截图/文件
![截图1](URL) —— 所有截图必须用 ![](url) 内嵌，禁止文字描述或链接

## 会话信息
- SS会话ID: [session_id]
- 接待客服: [真实姓名]
- 时间: [YYYY-MM-DD]
- 标签: [标签名]
```
