# Reconcile the original tasks

Resolve each affected task against the current authoritative goal. Keep the existing phases, unit IDs, flat list or short plan. Preserve everything outside the impact of the decision.

| What changed? | Treatment |
| --- | --- |
| Same behavior and still-valid acceptance | Retain ID and completion. |
| Same goal, implementation or verification must be redone | Reopen the original task and retain already demonstrated work. |
| Meaning replaced | Retire the obsolete active task and create a task for the new behavior. |
| Capability removed | Remove its task and active references within the authorized deletion scope. |
| New work without a predecessor | Assign the next regular ID. |

For splits and merges name the responsibilities inherited from each old task, update active references and retain prior evidence as history. New IDs follow the project's convention. Each active task has one phase and inherits its prerequisites. Check the merged dependency graph for missing nodes, cycles and repairs blocked by their own failing acceptance. Revisit cumulative verification in the final heavy phase.

Before leaving tasks, verify both directions of coverage, explicit migration/deletion work, executable dependency order, accurate status and the absence of duplicate ownership or dangling IDs. An existing implementation needing new proof stays implemented with verification marked stale.
