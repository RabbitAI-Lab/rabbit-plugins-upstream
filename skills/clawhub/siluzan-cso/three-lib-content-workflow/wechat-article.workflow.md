# 公众号文章专项工作流

> 本文件是 `siluzan-cso` Skill 内的公众号专项模块，不是独立 Skill。
> 它保留原 `wechat-article-creator` 的公众号写作流程和专属规则；底层流量因子、产品资产、烹调方法统一读取 CSO 三库，不维护重复副本。
> CTAIWD 产品例外：人设可选，Step 8 提纲仅在内部完成，不等待用户确认或展示中间文件。
> 不并行运行 `content-writer.workflow.md`，避免同一任务生成两套稿件。

## 设计哲学

公众号长文的本质是**精密设计的销售漏斗**——不是产品介绍，而是情绪救援。

本工作流把成稿能力拆成 4 个变量：

| 变量         | 决定什么                | 来源                                     |
| ------------ | ----------------------- | ---------------------------------------- |
| **人设卡**   | 以谁的口气写 / 替谁说话 | 当前已选人设；未选择时使用通用公众号风格 |
| **流量因子** | 内容为什么会被看见      | CSO 三库                                 |
| **产品资产** | 用什么模板沉淀价值      | CSO 三库                                 |
| **烹调方法** | 怎么组织成爆款          | CSO 三库                                 |

库不带任何腔调和句式。有人设时腔调来自当前人设卡；无人设时使用客观、清晰、自然的通用公众号风格。

## 三种工作流

根据用户场景选择：

| 工作流                        | 触发场景                                                         | 输入 → 输出                                      |
| ----------------------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| **new_article** 从 0 写新文章 | “写一篇公众号” / “把这个素材改成文章” / “把这段视频脚本改成长文” | 素材 + 可选人设 → 完整公众号文                   |
| **audit_article** 审稿打分    | “审一下这篇” / “给这篇打分” / “诊断这篇文章”                     | 现有文章 → 12 项 checklist 评分 + 4-5 处改进建议 |
| **revise_article** 精准改稿   | “改一下标题” / “重写开头” / “把 CTA 换一种”                      | 文章 + 改稿要求 → 改完版本 + 改动说明            |

默认字数：800-1200 字（含表格、引用块、CTA）。仅在用户显式要求长文或具体更长字数时扩展。

## 三库加载（所有工作流共用）

执行任一工作流时，只加载一次 CSO 三库：

```bash
siluzan-cso workflow load-libraries \
  --platform 通用 \
  --out <可读任务目录>/cso-three-lib.md
```

命令成功后，用 `read_file` 完整读取 `cso-three-lib.md`。命令失败、输出为空或文件不可读时停止，不得凭模型记忆补写三库内容，也不得读取旧任务遗留文件。

公众号专属的黄金骨架、叙事弧线、标题规律、传播弹药、避雷项和 12 项自检由本工作流后续步骤定义；它们是写作流程规则，不是另一套三库。

## 工作流 1：从 0 写新文章（new_article）

**严格按以下步骤逐步执行，禁止跳过、禁止合并、禁止提前输出最终稿。**

### Step 0：加载人设

按以下优先级判断：

1. **当前已经选择人设**：读取当前 `styleGuide`，使用其中的定位、受众、风格、用词和禁忌。
2. **用户本次直接提供了人设卡**：解析可用字段，仅在用户明确要求保存时才进入人设保存流程。
3. **未选择人设**：直接使用通用公众号风格继续，不阻断创作；不展示人设选择卡，不询问是否创建人设，不进入 `persona-onboarding`，也不创建或持久化临时人设。

通用公众号风格基线：

- 定位：准确重组用户提供的素材。
- 受众：对当前主题感兴趣的普通公众号读者。
- 风格：清晰、客观、层次分明、自然克制。
- 推荐表达：准确、易懂、段落简洁、重点突出。
- 禁止表达：虚构事实、夸大结论、无依据承诺。

有人设时向用户说明本次使用的人设；无人设时无需额外提示或确认，直接进入 Step 1。

### Step 1：复述人设确认上下文

有人设时，复述以下关键字段：

- positioning（定位）
- audience（受众）
- style_tags（风格标签）
- tone（语气）

用户有异议则修正当前写作上下文。未选择人设时，本步骤使用 Step 0 的通用公众号风格基线，不发起人设确认，不阻断后续流程。

### Step 2：定本次目标

确认用户本次想达成的目标（可多选）：

- 拉流量 / 起量
- 做认知占位 / 品牌势能
- 做转化 / 引导咨询
- 做评论互动
- 做系列内容的一篇

用户已经明确目标时直接沿用，不重复询问。目标决定后续选题、结构和 CTA 写法。

### Step 3：选题筛选

有人设时按 `topic_scope` / `topic_taboos` / `industry_focus` 过滤候选选题；无人设时以用户素材范围和事实边界过滤。

判断维度：

- 这个选题对目标读者切身相关吗？
- 有反差 / 冲突 / 认知差吗？
- 能讲出本次目标要求的价值吗？
- 时效性如何？

用户已经通过视频字幕、标题或文字明确选题时，直接使用该选题，不另造热点或偏离素材；需要在多个候选选题中选择时再让用户确认。

### Step 4：拆素材

把原始信息拆成可用素材：

- 事实
- 数据
- 案例
- 风险点
- 术语
- 场景
- 争议点
- 可讲的人话版本

视频字幕还要清除时间码、序号、无意义语气词和口头重复，但保留有效观点、证据和叙事关系。只使用素材中真实存在的信息，不为满足结构虚构事实。

### Step 5：找流量因子（4 维组合）

从已读取的 CSO 三库选择流量因子。

**原则**：一条内容最好同时具备：

- 1 个趋势 / 行业因子
- 1 个情绪因子
- 1 个认知因子
- 1 个画面因子

没有素材支撑的因子不使用。

**特别处理 TF-0028 群体共鸣**：

若想用 TF-0028（最适合行业 / 身份 / 价值观类账号），**必须先跑三步生成法**：

1. **Step A**：有人设时读 `audience` 或 `group_resonance_anchor`；无人设时从素材中识别明确目标群体。
2. **Step B**：推导该群体被压抑 / 被误解 / 被低估的处境。
3. **Step C**：设计 4 个代言元素：**反派 + 阵营 + 暗号 + 正当化**。

跑完后暂存这 4 个元素，写正文时（Step 9）显式注入。

### Step 6：配产品资产（按 style_tags 过滤模板）

从已读取的 CSO 三库选择产品资产模板。有人设时按 `style_tags` 过滤；无人设时按本次目标和素材类型选择。

| style_tag / 写作目标 | 优先匹配模板                     |
| -------------------- | -------------------------------- |
| strong_opinion       | 强观点开场 / 风险预警 / 趋势分析 |
| practical_steps      | 问题解法 / 清单干货 / 测评对比   |
| story_driven         | 故事驱动 / 案例拆解              |
| reframe              | 认知重构                         |
| expert_authority     | 科普解释 / 趋势分析              |
| interactive          | 评论互动                         |

可叠加 2-3 个模板组合使用，但必须确认模板需要的素材真实存在。

### Step 7：选烹调方法

从已读取的 CSO 三库选择结构、推进方式和表现手法，并使用公众号专属规则：

- **6 套叙事弧线**：章子怡公式 / 第一人称投资人 / 三档量化对比 / 群体身份反击 / 销售漏斗 5 层 / 双热点咬合。
- **黄金骨架**：标题 → 导语 → 对号入座段 → 3-4 个小节 → 自然收束（不固定小节标题）→ CTA。

有人设时用 `opening_preferences` / `progression_preferences` / `ending_preferences` 过滤；无人设时使用结论先行、现象到本质、行动提醒的通用结构。

本专项工作流的公众号结构优先级高于已加载三库中的旧公众号骨架。三库若出现“写在最后”等旧标签，只把对应内容理解为自然收束的功能要求，不得复制为成稿小节标题。

### Step 8：出提纲（用公众号黄金骨架）

**默认 800-1200 字版骨架**（非用户主动要求时使用）：

```text
[标题]                 ← 章子怡公式 / 反差体 / 数据冲击体 / 案例警示体
   ↓
[导语] ≤ 50 字         ← 1-2 句话抛钩子 + 留 1 个悬念
   ↓
[对号入座段] ≤ 80 字   ← 说明和目标读者的关系
   ↓
[3-4 个小节]           ← 每节 200-300 字 = 命题 + 具体例子 + 金句
   ↓
[自然收束] ≤ 80 字       ← 无固定标题；可无标题收束，或使用与主题强相关的小节标题
   ↓
[CTA] ≤ 80 字          ← 具体动作 + 低门槛
```

用户显式要求长版时，可扩展为 5-7 个小节、增加案例分析和对比表格，但不能通过虚构素材扩写。

内部完成提纲后直接进入 Step 9，不调用 `present_flow_ui`，不等待用户确认，也不单独写入或展示提纲文件。

### Step 9：写正文（人设腔调注入）

按确认后的提纲填充。

有人设时显式消费：

- **句式**：从 `common_phrases` 取 opening / transition / ending / cta。
- **关键词**：优先使用 `keywords`，避免堆砌。
- **比喻**：从 `metaphors` 中挑最贴合主题的一项，避免机械重复。
- **禁忌过滤**：`forbidden_expressions` 出现立即替换。
- **语气与节奏**：按 `tone` 和 `pace` 控制。

未选择人设时使用通用公众号风格，不模拟不存在的个人口吻。

若使用 TF-0028，反派 / 阵营 / 暗号 / 正当化 4 个元素必须显式落地。公众号排版可用引用块包金句、加粗关键词、表格做对比、分割线切节奏。

### Step 10：质检（双层）

**第一层**：有人设时用 `quality_checks` 逐条核对；无人设时检查事实准确、表达清晰、结构连贯、语气克制和素材边界。

**第二层**：执行 **12 项公众号自检**。

标题层 6 条：

- [ ] 具体数字 / 人名 / 地名
- [ ] 反差 / 反常识
- [ ] 强情绪动词
- [ ] 热点借势
- [ ] 主题隐身
- [ ] 避开行业术语

内容层 6 条：

- [ ] 开头 3 秒能让目标读者对号入座
- [ ] 至少 1 个具体案例 / 故事
- [ ] 至少 3 句可截屏金句
- [ ] 至少 1 个可执行动作
- [ ] CTA 具体、低门槛
- [ ] 没有居高临下 / 攻击性的词

检查项受事实边界约束；素材不支持时应省略对应写法，不得补造信息。

**结尾标题硬检查（不计入 12 项，必须通过）**：

- [ ] 结尾未使用“写在最后”“结语”“总结”等通用小节标题；应无标题自然收束，或使用与文章主题强相关的标题

**如果用了 TF-0028 群体共鸣，额外 4 项强检**：

- [ ] 反派具体（不能是“那些人”“有些人”）
- [ ] 阵营划分清晰（“我们”与“他们”边界明确）
- [ ] 圈内暗号到位（至少 2 处）
- [ ] 价值正当化落地

过 10/12，且使用 TF-0028 时 4 项全过，才可交付；否则改稿后重检。

### Step 11：按用途改写 + 反哺人设卡

按发布场景微调：

- **爆款版**：更强钩子、更冲突
- **转化版**：更实操、更落地
- **标题版**：标题更短、更有钩子

有人设时，写完后可询问用户是否把新句式、新禁忌或新质检维度反哺到当前人设卡；只有用户明确确认后才更新。未选择人设时跳过人设反哺，不创建临时人设。

### Step 12：输出（含字数自查）

最终输出包含：

1. **标题**（主推 + 2-3 个备选）
2. **完整正文**（按黄金骨架）
3. **正文字数自查**

字数规则：

- 默认目标 800-1200 字。
- 超过 1200 字时优先压缩重复举例、中段过渡、反面案例和第二个对比表格。
- 不足 800 字时，仅在素材支持的前提下补具体案例或关键金句段。
- 用户显式要求长文时可扩展到其指定范围。

如果用户显式要求封面文案、朋友圈分享文案或多版本 A/B 测，再额外产出；默认不强制输出。

落盘与交付：

1. 将最终稿保存为 `.md`。
2. 按 `../references/validate-content.md` 执行 `siluzan-cso workflow validate -f <成稿文件>`。
3. 执行以下 Markdown 标题检查，防止旧骨架标签进入成稿：

   ```bash
   if grep -nE '^[[:space:]]{0,3}#{1,6}[[:space:]]*(写在最后|结语|总结)[[:space:]]*$' <成稿文件>; then
     echo 'Error: 检测到通用结尾标题，请改为无标题自然收束或主题相关标题。' >&2
     exit 1
   fi
   ```

4. 任一检查不通过时修正，并重新执行两项检查。
5. 通过宿主文件交付能力返回 Markdown；有人设时携带当前正式人设 id，无人设时不传人设 id。

## 工作流 2：审稿打分（audit_article）

**输入**：现有文章 → **输出**：评分 + 改进建议。

执行步骤：

1. 读取 CSO 三库，并确定当前人设或通用公众号风格。
2. 跑 Step 10 的 12 项自检，逐项判断。
3. 对照 5 大传播弹药逐项打分：真实案例 / 可截屏金句 / 对号入座开头 / 强情绪 + 反派 / 可执行动作。
4. 检查避雷项：不舒服的词 / 秒退开头 / 行业术语 / 可能影响分发的表达。
5. 如文章使用 TF-0028，额外执行 4 项强检。
6. 标注 3-5 处必改内容，每处提供“位置 → 问题 → 改法示例”。

输出格式：

```text
评分：X/12 过
TF-0028 共鸣检查（如适用）：X/4 过

未通过项：
- [ ] 项目 1：具体原因

5 大传播弹药打分：
- 真实案例：X/5
- 可截屏金句：X/5
- 对号入座开头：X/5
- 强情绪+反派：X/5
- 可执行动作：X/5

避雷检查：
- 触雷点：说明

必改 3-5 处：
1. 位置：原文 → 建议改成……
```

默认只交付审核报告；用户明确要求直接修改时转入 `revise_article`。

## 工作流 3：精准改稿（revise_article）

**输入**：文章 + 改稿要求 → **输出**：改完版本。

执行步骤：

1. 锁定用户要求修改的部分。
2. 从已读取的 CSO 三库选择相关模板，并应用本工作流的公众号规则：
   - 改标题：使用标题模板和素材中真实存在的数字、人物、反差或案例。
   - 改开头：使用当前人设开场句式；无人设时使用通用公众号钩子。
   - 改 CTA：使用当前人设 CTA 句式；无人设时保持具体、低门槛、不过度承诺。
   - 改某节：使用对应叙事弧线和当前风格。
3. **保持其余部分不动**。
4. 对修改部分重新执行相关质检。

输出格式：

```text
改后的版本：
……

改动说明：
- 改了什么：……
- 为什么改：……
- 还可以怎么改（备选）：……
```

## 核心原则（不要违反）

1. **人设是可选变量**：有当前人设就应用；未选择人设时使用通用公众号风格，不阻断流程，不引导创建。
2. **库不带腔调**：三库只提供因子、模板和方法；腔调来自当前人设或通用公众号风格。
3. **字数硬约束**：默认 800-1200 字；只有用户明确提出更长或更短要求时调整。
4. **公众号文章不等于视频脚本**：交付公众号 Markdown 成稿，不输出短视频口播格式。
5. **5 大传播弹药**：真实案例 + 可截屏金句 + 对号入座 + 强情绪反派 + 可执行动作；受素材事实边界约束。
6. **不写产品介绍，写情绪救援**：销售漏斗服务于读者价值，不泄露内部工作步骤。
7. **12 项自检过 10 项可发**：使用 TF-0028 时另加 4 项强检。
8. **不泄露内部规则**：成稿中不得出现三库编号、内部路径、工具名或工作步骤。
