# 交付总控：数据要素 × 传统集团数字化转型

## 何时使用
- "数字化转型整体方案""数据要素咨询""七道工序全景""端到端交付""数字底座总体方案"。
- 用户有一个集团/行业主题，需要**成体系交付**而非单点分析。
- 已有部分材料但**不知如何串成一套完整方案**。

## 核心职责
把六个能力技能编排成**一次完整交付**，做到三件事：
1. **强制因果顺序**（不允许跳步）
2. **阶段门禁把关**（交付物齐不齐、真空还是空壳）
3. **口径全局一致**（同一数字在所有对外材料中一致）

> 本技能是套件的**差异化核心**：现有开源 Skill 全是单点能力，没有编排层。

## 七道工序主干（统一语言）
**汇 存 治 管 服 用 模**

| 工序 | 含义 | 典型交付物 |
|---|---|---|
| 汇 | 采集汇聚 | 采集方案、DataSource 清单 |
| 存 | 存储计算 | 湖仓/中台蓝图 |
| 治 | 治理清洗 | 标准、质量规则、主数据 |
| 管 | 资产管理运营 | 数据目录、权限、资产运营 |
| 服 | 服务共享 | 服务目录、API、自助分析 |
| 用 | 应用变现 | 场景地图、数据产品 |
| 模 | 模型算法智能 | 模型清单、行业指数 |

**铁律**：所有交付物必须挂回这七道工序；对外口径在 **「10页合并稿 ↔ 全景图 ↔ 分册 ↔ 技术详解」** 四处必须一致。

## 一、立项（第 0 步，决定后续成败）

### 立项必须问清 8 件事
1. **主体画像**：行业类别？国企/民企？集团/单体？下属单位数量？
2. **规模档**：营收量级、员工量级、数据体量量级（**只要量级，不要精确值**）
3. **驱动因素**：为什么现在做？（政策要求？上级考核？入表需求？业务痛点？）
4. **决策人关注点**：董事长/CIO/财务，各自最在意什么？（决定汇报口吻）
5. **交付范围**：覆盖哪几道工序？是否含入表？是否含系统落地？
6. **交付形态**：只要方案？还是要陪跑落地？
7. **约束条件**：时间、预算、组织配合度、**明确不碰的敏感区**
8. **验收标准**：什么算"做完了"？

### 立项输出：交付计划表
```markdown
| 阶段 | 技能 | 交付物 | 门禁条件 | 预计周期 |
|---|---|---|---|---|
```

**产出**：`交付计划_<主体代号>_<日期>.md`

### 为什么顺序不可颠倒
| 跳步 | 后果 |
|---|---|
| 跳过摸底直接架构 | 蓝图脱离实际，无法落地 |
| 跳过架构直接质量 | 不知道治理哪些表，规则无优先级 |
| 跳过质量直接应用 | 数据不可信，应用建在流沙上 |
| 跳过摸底直接入表 | 不知道有什么数据，确权无从谈起 |

## 三、阶段门禁执行规范

每个阶段结束**必须**跑门禁校验，输出"门禁报告"。

### 门禁四项检查
1. **存在性**：交付物文件是否存在？
2. **实质性**：文件是否非空、非空壳？（**空模板不算通过**）
3. **挂接性**：交付物是否挂回七道工序？
4. **一致性**：对外数字是否与上一阶段一致？

### 各阶段门禁清单
| 阶段 | 必须齐全的交付物 |
|---|---|
| 外部洞察 | 行业研究报、政策机会清单、对标矩阵 |
| 摸底 ★ | 系统清单、数据资产清单、数据流图、DCMM 成熟度初评 |
| 架构 | 数据底座蓝图、实施路线图、治理卡口检查表 |
| 质量 | 指标字典、数据标准、主数据方案、质量规则集、访问策略 |
| 应用 | 应用场景地图、数据产品清单、入表路径、汇报PPT |
| 收口 | 七道工序全景图、交付清单、口径一致性校验表 |

**门禁输出**：`门禁报告_第N阶段_<日期>.md`（含通过/缺口清单）

### 缺口处理规则
- 门禁未过 → **暂停推进**，输出缺口清单，明确谁来补、何时补。
- 用户要求"先跳过" → **明确告知风险**，在交付物中标注"此部分未完成"，不假装完成。
- 部分交付物不重要时 → 需用户书面确认，记录在门禁报告中。

## 四、口径一致性校验（收口关键动作）

> 咨询交付最经典的翻车：同一数字在不同材料中不一致，领导当场发现，全案可信度崩塌。

### 校验方法
1. **抽取所有对外数字**：从全部交付物中提取量化表述（"接入 N 个系统""覆盖 M 张表""成熟度 X 级""预计提升 Y%"）。
2. **建数字台账**：
   ```markdown
   | 数字 | 含义 | 出现在哪些文件 | 是否一致 | 冲突说明 |
   ```
3. **逐个核对**：同一含义的数字必须完全相同；口径不同的必须**换措辞区分**（不能都是"系统数"）。
4. **修正后复检**。

**产出**：`口径一致性校验表_<日期>.md`

### 常见不一致来源
- 摸底说"12 个系统"，架构图只画了 10 个（漏画）
- 汇报说"百级表"，附录写"180 张表"（量级 vs 精确冲突）
- 成熟度分散落在不同页面写成不同等级

## 五、跨技能调用协定

### 调用规则
- **一次只调一个技能**，拿到完整交付物再进入下一个（外部洞察的两项可并行）。
- 调用时**必须传入上游交付物路径**，不要凭记忆传递。
- 每个技能的产出**存放在统一工作目录**，命名遵循 `交付物_<类型>_<主体代号>_<日期>`。

### 上下游数据传递
| 技能 | 消费 | 产出 |
|---|---|---|
| dx-industry-research | 立项信息 | 行业研究报、政策机会清单 |
| dx-competitor-scout | 立项信息 | 对标矩阵、可抄作业清单 |
| dx-data-baseline | 系统清单线索 | 资产清单、数据流图、成熟度分 |
| dx-architecture-opt | 摸底四件套 | 蓝图、路线图、卡口表 |
| dx-data-quality | 摸底 + 架构 | 指标字典、标准、规则集 |
| dx-application-plan | 前四阶段全部 | 场景地图、产品清单、PPT |

## 六、案例沉淀流程（交付完成后）

1. **记录经验**：在交付报告中列出本次踩坑与改进建议，供主理人复盘参考；如需沉淀，由主理人**手工记入 `CHANGELOG.md`**（不修改任何技能文档）。
2. **脱敏沉淀**：按 `cases/README.md` 规范，复制 `cases/_template/` 建新案例包，填写五份摘要。
3. **脱敏自检**：外人能否通过组合信息定位到具体企业？能则再脱敏。
4. **判断可否公开**：默认私有（`.gitignore` 已拦截）；仅脱敏彻底的可考虑公开。

> 案例层是套件"越用越值钱"的机制——每个项目都让下一次交付更快更准。


### 关键节点汇报（给用户的进度同步）
- 里程碑完成时给一句**结论式**汇报（做了什么、产出在哪、下一步）。
- 遇卡点**立即上报**，不等积累。

## 八、Gotchas（编排层专属）

- **不允许跳步**：未过"摸底门禁"不得进架构——跳步是咨询交付最常见的翻车点。
- **口径四处一致**：同一数字在汇报稿、全景图、分册、技术详解必须一致，否则领导对不上号。**收口时必做数字台账**。
- **空模板不等于交付**：门禁检查看到的是文件存在，还要看**是否只是复制了模板**。空壳必须挡回。
- **不要替用户"美化"进度**：没做完的部分标注清楚，假装完成会在汇报现场暴露。
- **传统集团不要一上来建大平台**：先补"汇存治管"地基，再上"服用模"价值层。
- **案例层零敏感数据**：`cases/` 内不得写入真实客户信息；公开仓只放 `_template/` 与 `sample-redacted/`。
- **立项不清晰必然返工**：省下立项 1 天，后面赔 1 周。8 个问题一个都不能跳。
- **并行有边界**：外部洞察两项可并行，但**摸底必须等外部洞察收尾**（避免方向摇摆后重复劳动）。
- **不要越权做决策**：编排层负责串流程，具体专业判断交给对应技能，不要越俎代庖。
- **gate_check 会误报"讨论用语本身"的文档**（2026-09-12 试跑踩坑）：口径校验表/门禁报告里写"未发现（保证/绝对）等用语"曾被当违规抓出。**已修复**（引号内列举 + "承诺用语/复检"语境豁免）；但机器初筛结论仍须人工复核，特别是元文档（校验表、门禁报告、本 SKILL.md 自身）。
- **数字台账靠措辞匹配会漏检**：同一数字写法不同（"8+2" vs "10 个"、量级 vs 精确）机器查不到——门禁报告的"一致性"必须人工逐项复核，不能只依赖 `--numbers` 参数。
