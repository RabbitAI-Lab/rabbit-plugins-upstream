# 数据应用规划及呈现（七道工序：服 + 用 + 模）

## 何时使用
- "数据能干什么""规划数据产品""做应用场景地图""数据资产怎么入表""给领导做个汇报""数字底座方案"。
- 前面摸底/架构/质量已完成，需要**把能力变成价值叙事**。

## 目标
把"数据能干什么"变成三样可落地的东西：**场景地图 + 数据产品 + 入表路径**，并产出**领导看得懂的汇报**。

> 一句话原则：**先讲价值，后讲技术。** 领导要的是"省多少 / 赚多少 / 风险降多少"，不是架构图。

---

## 一、应用场景地图（二维筛选法）

### 绘制方法
以 **业务价值（纵轴）× 落地可行性（横轴）** 建四象限：

```
高价值 │  ⚠️ 战略储备        │  ★ 优先落地
       │  （价值高但难）      │  （价值高且可行）
       ├─────────────────────┼─────────────────────
低价值 │  ❌ 暂不考虑        │  ○ 快速见效
       │  （低价值且难）      │  （易做但价值有限）
       └─────────────────────┴─────────────────────
        低可行性              高可行性
```

### 象限处理策略
| 象限 | 策略 | 说明 |
|---|---|---|
| ★ 优先落地 | 立即启动 | 作为第一阶段成果，建立信心 |
| ○ 快速见效 | 批量纳入 | 低垂果实，快速铺开 |
| ⚠️ 战略储备 | 分阶段规划 | 明确前置条件，排入中远期 |
| ❌ 暂不考虑 | 明确排除 | **写进材料说明为何不做**（避免被追问） |

### 可行性评估维度
- **数据就绪度**：数据有没有？质量够不够？（引用摸底 + 质量交付物）
- **技术复杂度**：现有能力能否支撑？
- **组织接受度**：业务部门愿不愿意用？
- **合规风险**：是否涉及敏感数据/需授权？

### 每个场景必填
| 字段 | 说明 |
|---|---|
| 场景名 | 简短可懂 |
| 业务痛点 | 现在怎么难受 |
| 数据方案 | 用哪些数据、怎么用 |
| 价值类型 | 降本/增效/增收/风控 |
| 价值量化 | 尽量给数字或量级 |
| 可行性 | 高/中/低 + 理由 |
| 前置条件 | 依赖什么 |
| 归属工序 | 服/用/模 |

**产出**：`应用场景地图_<主体代号>_<日期>.md`

## 二、数据产品设计

数据产品分两类，**必须分开设计**（逻辑、客户、定价都不同）：

### 对内提效类
| 类型 | 例子 | 价值主张 |
|---|---|---|
| 经营看板 | 日报、周报自动化 | 省人工、提时效 |
| 自助分析 | 业务人员自助取数 | 减少取数排队 |
| 指标平台 | 统一口径的指标服务 | 消除口径争议 |
| 预警监控 | 异常自动告警 | 提前发现问题 |

### 对外变现类
| 类型 | 例子 | 变现方式 |
|---|---|---|
| 数据服务 | API 查询、批量数据 | 按调用/订阅收费 |
| 行业指数 | 价格指数、景气指数 | 授权/发布/影响力 |
| 分析报告 | 行业供需报告 | 售卖/引流 |
| 数据源授权 | 原始数据授权 | 一次性/分成 |

### 产品设计要点
- 每个产品写清：**目标用户、解决什么问题、数据来源、交付形态、计费方式（若对外）**
- 对外产品必须回答：**凭什么我们能做而别人不能？**（数据源独特性）
- 产品优先级按场景地图象限排，不按技术难度排

**产出**：`数据产品清单_<主体代号>_<日期>.md`

## 三、数据资产入表路径（财政部《暂行规定》口径）

> ⚠️ **核心红线：不能把"数据资源"直接当"数据资产"。** 确认条件未达不能入表。

### 第一步：概念辨析（必须讲清）
| 概念 | 定义 | 关系 |
|---|---|---|
| **数据资源** | 电子化记录、可机器读取、有使用价值的数据集合 | 基础 |
| **数据资产** | 企业拥有或控制、预期带来经济利益的资源 | 数据资源中符合条件者 |
| **数据要素** | 参与生产经营、带来效益的数据资产 | 资产中"活性"部分 |

### 第二步：入表确认条件（逐条核对）
按《企业数据资源相关会计处理暂行规定》，确认需满足：
- [ ] **合法拥有或控制**（确权清晰）
- [ ] **预期带来经济利益**（有明确应用或交易场景）
- [ ] **成本可靠计量**（采集/加工/维护成本可归集）
- [ ] **权属无争议**

### 第三步：路径选择
| 路径 | 适用情形 | 会计处理 |
|---|---|---|
| **无形资产** | 自用为主（内部提效、支撑业务） | 按无形资产准则 |
| **存货** | 用于对外交易（数据产品售卖） | 按存货准则 |

### 第四步：三阶段推进
```
确权 → 计量 → 入表
 ├─ 确权：数据来源合法性、权属界定（业务+法务+风控共同参与）
 ├─ 计量：成本归集（采集/清洗/加工/维护），分摊规则（多业务共用如何分）
 └─ 入表：财务确认、披露
```

### 关键卡点（提前预警，第四步前置）
- **确权难点**：集团是否拥有数据经营权？（尤其涉及商户/合作伙伴数据）
- **成本分摊**：多市场/多业务共用数据，成本如何分摊？
- **价值波动**：数据资产价值易变，后续计量需谨慎
- **审计口径**：需会计师事务所认可，提前沟通

**产出**：`数据资产入表路径建议_<主体代号>_<日期>.md`

## 四、价值量化（把技术翻译成钱和风险）
### 量化口径模板
| 价值类型 | 量化方式 | 注意 |
|---|---|---|
| **降本** | 减少人工工时 × 人力成本 | 说明是"年化"还是"累计" |
| **增效** | 时效提升（如 T+3 → T+1） | 时效本身也是价值 |
| **增收** | 数据产品潜在规模（量级） | **对外材料用区间/量级，避免绝对承诺** |
| **风控** | 合规风险降低、避免处罚 | 难量化时给"风险等级下降" |

### 表达规范（重要）
- **对外材料用"量级"而非"精确承诺"**："预计年化节约百万级"优于"节约 123.4 万"。
- 收益口径**必须注明时间范围**（年化/累计/首年）。
- 无法量化时，**给对比而非绝对值**（如"取数周期从 3 天缩短到 1 小时"）。

## 五、汇报呈现规范（融合 What / So What / Now What）

### 核心原则：先价值，后技术
初版汇报若以架构图开场，反馈常是"看不懂"。正确顺序：
```
① 现状困境（业务语言，不用技术词）
② 机会与价值（能省多少/赚多少/降多少风险）
③ 路径与节奏（分几步，每步给什么）
④ 保障与投入（要什么人、多少钱、多长时间）
⑤ 技术方案（放附录，需要时才展开）
```

### 汇报结构建议（约 20 页）
| 页 | 内容 |
|---|---|
| 1-3 | 现状与困境（业务语言） |
| 4-6 | 机会与价值量化（**最重要**） |
| 7-10 | 实施路径（三阶段，含里程碑） |
| 11-13 | 快速见效项（第一阶段成果预告） |
| 14-16 | 投入与保障（人/钱/时间） |
| 17-19 | 风险与应对 |
| 20 | 决策事项（明确要领导批什么） |
| 附 | 技术方案、七道工序全景图、术语表 |

### 汇报技巧
- **每页一个结论**（标题即结论）。
- **禁止术语裸奔**：出现专业词必须一句话解释。
- **准备"深挖材料"**：领导问到细节时能立刻翻到附录。
- **决策事项必须明确**：要领导批什么、批多少、什么时候批。

**产出**：`领导汇报_<主体代号>_<日期>.pptx` / `数字底座方案_<主体代号>.docx`

## Gotchas
- **先讲价值再讲技术**——初版以架构图开场会被反馈"看不懂"，改为"省多少/赚多少"开场后顺利推进。
- **入表不能把"数据资源"直接当"资产"**：确认条件未达不能入表；确权是最大卡点，需业务+法务+风控共同参与。
- **对外收益用量级/区间，不做绝对承诺**：避免后续无法兑现。
- **每个不做的事也要写清原因**（❌ 象限）——否则汇报现场必被追问"为什么这个不做"。
- **场景必须挂回七道工序的"服用模"**，与前序摸底/架构/质量口径一致。
- **数字必须与上游交付物一致**（呼应 orchestrator 的口径一致性校验）。
- **快速见效项必须有**：纯远期规划难以获得支持，第一阶段要有能立刻看到成果的项。
- **对外产品要回答"凭什么我们能做"**（数据源独特性），否则只是通用工具。
- **不要越界承诺技术可行性**：需与架构/质量阶段结论一致，不能为汇报效果夸大。
