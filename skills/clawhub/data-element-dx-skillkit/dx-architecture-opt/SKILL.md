# 数据架构优化（七道工序：存 + 治 + 管）

## 何时使用
- "设计集团数据架构""数据底座怎么建""湖仓一体/数据中台规划""数据治理平台"。
- "现有系统太多太乱，怎么整合""技术选型给个建议"。
- 已有摸底结果，需要**从现状走到蓝图**。

## 目标
基于摸底结果，给出**可落地**的数据底座蓝图 + 分阶段路线图，并守住**治理卡口**。

> 核心判断：**架构不是选型比赛，是路径设计。** 传统集团最常见的失败不是选错技术，而是**一上来建大平台**。

---

## 核心方法论

### 原则 1：先地基，后价值层

传统集团**不要一上来建大平台**。按七道工序顺序补地基：

```
第一阶段  汇 + 存     统一采集与存储（ODS → 湖/仓）      ← 地基
第二阶段  治 + 管     标准/质量/主数据 + 目录/权限/血缘   ← 主干
第三阶段  服 + 用 + 模  共享服务 → 应用变现 → 模型智能     ← 价值层
```

**为什么不能倒过来**：地基没补就上中台，中台只会变成"**数据垃圾场**"——把没治理过的脏数据集中起来，问题也被集中放大了。

### 原则 2：架构必须能追溯到资产清单
蓝图里的每一个节点，都要能回答"**对应现实中的哪张表/哪个系统**"。
画得漂亮但落不了地的架构图，是咨询交付最常见的自嗨。

### 原则 3：存量系统增量迁移，不推倒重来
老 ERP、离线 Excel 流程，**禁止一次性替换**。
做法：新数据走新链路（双跑期）→ 逐域切换 → 老链路只读 → 下线。

### 原则 4：One ID / 主数据先于应用层
没有统一标识，上层任何"打通"都是假的。**One ID 是架构的地基中的地基。**

## 执行步骤（六步）

### Step 0｜读上游（半天）
读 `dx-data-baseline` 的**系统清单 + 数据资产清单 + 数据流图 + DCMM 成熟度**。
**门禁未过不得开工**——没有资产清单就画架构图，必然返工。

### Step 1｜现状诊断（1–2 天）
把摸底结果转成架构视角的问题清单：
- **数据流断点**：哪些环节靠手工传递？（列出全部）
- **多份拷贝**：同一数据在几个系统各存一份？
- **口径冲突点**：哪些字段在不同系统定义不同？
- **技术栈碎片**：几种数据库？几种 ETL 工具？有没有人在用的冷门技术？
- **政策/合规约束**：集团有无信创、等保、数据出域要求？

**产出**：`架构现状诊断_<集团>.md`

### Step 2｜蓝图层级设计（2–4 天，核心工作量）

按七道工序设计七层，每层写清：**做什么 / 用什么 / 谁负责 / 与现状差在哪**。

| 层 | 对应工序 | 设计要点 |
|---|---|---|
| **采集层** | 汇 | 数据库直连 / CDC / API / 文件采集 / IoT；**离线 Excel 也要有采集通道** |
| **存储层** | 存 | ODS（原样落地）→ DWD（明细治理）→ DWS（主题汇总）→ ADS（应用）；冷热分层 |
| **治理层** | 治 | 标准落库 / 质量规则引擎 / 主数据管理 / 元数据 |
| **管理层** | 管 | 数据目录 / 血缘 / 权限（RBAC+RLS/CLS）/ 审计 / 资产运营 |
| **服务层** | 服 | API 网关 / 查询服务 / 自助分析工具 |
| **应用层** | 用 | 经营看板 / 数据产品 / 对外服务 |
| **模型层** | 模 | 指标计算 / 行业指数 / 算法模型 |

**技术选型要点**（不做品牌推荐，给判断标准）：
- **不要唯新技术**：团队能维护的技术才是好技术。评估团队现有技能栈。
- **湖仓 vs 中台**：数据量级小（TB 以下）优先湖仓或直接数仓，中台是组织产物不是技术产物。
- **能买不建 vs 能建不买**：通用能力（ETL/BI/目录）优先买成熟产品；核心数据资产与口径必须自建。
- **国产化约束**：国企项目先确认信创要求，再谈选型。
- **成本分级**：给"最小可用版 / 标准版 / 理想版"三档，让领导有得选。

**产出**：`数据底座蓝图_<集团>_<日期>.md`（含 mermaid 架构图）

### Step 3｜治理卡口设计（1–2 天）★不可省略

见下节「治理卡口」——这是架构能不能进生产环境的**硬约束**。

**产出**：`治理卡口检查表_<集团>.md`

### Step 4｜分阶段路线图（1–2 天）
每阶段必写五件事：**做什么 / 交付什么 / 谁负责 / 多久 / 怎么验收**。

| 阶段 | 内容 | 典型周期 |
|---|---|---|
| 一期（地基） | 采集 + 存储 + 目录雏形 | 3–6 个月 |
| 二期（主干） | 治理 + 主数据 + 权限 + 血缘 | 4–8 个月 |
| 三期（价值） | 服务 + 应用 + 模型 | 6–12 个月 |

**路线图必须挂回七道工序**，且与汇报材料的阶段划分一致（口径四处一致）。

**产出**：`实施路线图.md`

### Step 5｜口径对齐与交棒（半天）
- 架构图里的数字（系统数/表数/阶段数）必须与摸底、后续汇报材料一致。
- 交棒给 `dx-data-quality`：蓝图里的治理层需要指标字典与规则集填充。

## 治理卡口（HALT 机制，融合 des-governance-and-security）

架构不是画完就完。**每个数据集从 Silver/Gold 层提到生产前必须过治理卡口，缺证据就 HALT（停机）。**

### 七项必检
- [ ] **① 所有权**：该数据集有具名 owner 吗？（**无主不放行**）
- [ ] **② 分类分级**：敏感级别已标定？PII 列已逐列识别？
- [ ] **③ 访问策略**：RBAC + 行级/列级安全（RLS/CLS）已定义？各消费角色只能查该查的？
- [ ] **④ 隐私处理**：脱敏 / 令牌化 / 加密策略**按列**选定？
- [ ] **⑤ 保留与删除**：保留期窗口、删除流程（含被遗忘权）已文档化？
- [ ] **⑥ 审计**：查询与导出行为有审计日志？
- [ ] **⑦ 上游证据**：合规范围、数据契约、上游就绪证明齐全？

> **任一缺失即 HALT** —— 宁可挡住不完整的治理产物，也不让不合规数据进生产。
> HALT 不是惩罚，是**免责机制**：拦住问题的人有功，放过问题的人背锅。

### 卡口执行规则
1. 卡口检查在**架构设计阶段完成设计**，在**数据提生产时执行**。
2. 每项检查留**证据**（谁签的、什么时候、看的是哪份材料）。
3. HALT 后必须给出**补齐路径**（缺什么、谁补、多久），不能只说"不通过"。
4. 紧急放行需**书面例外审批**，并记录在案（有例外机制才能被真正执行）。

## Gotchas

- **不要先建大平台**：地基（汇存治管）没补，中台只会变成"数据垃圾场"。
- 架构图必须与对外口径（汇报稿/全景图/分册/技术详解）**四处一致**——领导对不上号是真实翻车点。
- 存量系统（老 ERP/Excel 流程）**禁止一次性推倒重来**，按七道工序增量迁移。
- One ID/主数据**要先于应用层建设**，否则数据服务无法打通。
- **治理卡口不可绕过**：为赶进度跳过"所有权/分级/访问策略"，生产环境必出合规事故。
- 分类分级与 PII 识别要在**架构设计阶段**完成，不能等上线前补。
- **不要唯新技术**：团队维护不了的技术 = 技术债。先看团队技能栈再选型。
- **中台是组织产物，不是技术产物**：没有统一的数据组织与流程，买什么中台都白搭。
- **架构图要能落到具体表**：画不出"这个节点对应哪张表"的架构图，落不了地。
- **信创/等保要求先确认**：国企项目后期因合规要求推翻技术选型，是常见重大返工。
- **不要给单一方案**：给"最小可用/标准/理想"三档，领导才有决策空间。
- **路线图不要给"全面推进"**：一期范围必须小而能验收，否则一年后无人能说清做了啥。
- **迁移双跑期必须留**：直接切换新老链路，业务中断风险极高。
