# 数据质量提升（七道工序：治）

## 何时使用
- "数据不准怎么办""建数据标准""主数据管理 MDM""写质量规则/DQC""数据质量评估"。
- **指标口径跨团队打架**（同一指标两个部门数字不同）← 最高频触发场景。
- **不知道哪个数据集是权威源**。
- 在把数据集开放给更广受众之前。
- 上级要做数据资产入表，需要先证明"数据可信"。

## 目标
把"数据不准"变成可治理的工程动作，最终产出**六件套**：

| # | 产出 | 一句话价值 |
|---|---|---|
| 1 | 指标字典 | 争议当场消解（最高价值） |
| 2 | 所有权与权威源清单 | 无主数据不再腐烂 |
| 3 | 数据标准 | 同名不同义不再发生 |
| 4 | 主数据方案 | 跨系统对得上 |
| 5 | 质量规则集 | 数据像代码一样被持续测试 |
| 6 | 访问策略与合规边界 | 开放但不失控 |

> **一句话原则**：**先统一口径，再谈质量；先定 owner，再谈规则。**

---

## 核心方法论

### 原则 1：从"定义"开始，不是从"政策"开始

> 治理被当成审批队列才显得官僚；做对了反而让人**不用问人就能用数据**。

**最高价值的治理产物是"指标字典"（Metric Dictionary）**，每个业务指标写清四件事：

| 要素 | 说明 | 反例 |
|---|---|---|
| 业务定义 | 算什么、**刻意排除什么** | "销售额" ← 没说排不排除退货/税/内部交易 |
| 计算口径 | 源表 + 过滤 + 时间粒度 + 时区 | "从系统里取" ← 不可复现 |
| 责任人 Owner | **一个人**，不是团队 | "数据部" ← 无人真负责 |
| 已知 Caveats | 何时误导、历史改过什么 | 留空 ← 埋雷 |

> 90% 的指标争议，在双方读完同一定义后发现"原来算的不是一回事"就自动消解——**几乎不需要政策介入**。
> 特别警惕"看起来显然"的指标：**"活跃客户""营收""注册数"每个都有半打说得通的定义**，歧义总在最糟的时刻冒出。

**只做争议最大的 10 个，不为求全而铺满。** 铺满 = 三个月交不出东西 = 治理被判定失败。

### 原则 2：所有权（Ownership）
- 每个数据集有**具名 owner**（一个人），对质量与访问负责。无主数据集会腐烂，且没人发现，直到有人基于过期数据做决策。
- **Owner 应坐在业务语义一侧**，不是管道一侧——产数据的团队懂"含义"，平台团队懂"怎么流"。
- **找不到 owner 的数据集，说明该业务域尚未就绪**——这是结论，不是待办。

### 原则 3：质量要"实测"而非"宣称"
像测代码一样持续测数据、失败即告警。**六个实测维度**：

| 维度 | 检查 | 经典故障 |
|---|---|---|
| 新鲜度 | 该到的时候到了吗 | 报表显示"最新"其实是三天前 |
| 量级 | 行数在正常区间吗 | **静默掉到 0**（最危险，无报错） |
| 唯一性 | 主键/业务键是否唯一 | 重复入账 |
| 空值率 | 关键字段空值比例 | 关键字段 30% 为空但无人知 |
| 引用完整性 | JOIN 不断链 | 孤儿外键，报表少算 |
| 分布 | 形状是否异常漂移 | 单位从"元"改"万元"，无人察觉 |

> 一个"大声失败"的管道，好过"静默产出昨天数字"的管道。

**实测的意思是：你真的跑过，有数字。** 没跑过就写"质量良好"是宣称，不是治理。

### 原则 4：访问默认开放（内部非个人数据）
- **默认开放**内部非个人数据；**默认限制会催生影子表格层，那比治理过的仓库更不安全**。
- 个人/财务/受监管数据是例外：最小权限、声明用途、定期复核。融合 des-governance-and-security：RBAC + 行级/列级安全（RLS/CLS）、PII 分级、保留期、审计日志。

### 原则 5：血缘
- 知道一个数字从哪来、喂给了谁。没有血缘，事故时答不出两个关键问题：**上游什么断了？下游什么错了？**

## 执行步骤（七步，可照做）

### Step 0｜读上游（半天）
读 `dx-data-baseline` 的资产清单与数据流图、`dx-architecture-opt` 的蓝图与治理卡口检查表。
**若上游门禁未过，先回退，不要凭空建规则。**

### Step 1｜建指标字典（2–5 天，核心工作量）
1. **先找争议**：不要从"有哪些指标"开始，要从"**哪些指标两个部门数字不一样**"开始。
   - 来源：访谈中听到的抱怨、报表对不上的地方、会议上的争执记录。
2. 列出**争议最大的 10 个指标**（宁可少，不可全）。
3. 用 `../_shared/assets/指标字典模板.md` 逐项填写，**每个必须有可跑的 SQL**。
4. 找 Owner 逐个签字确认——**签字动作本身就是治理**。
5. 重点关注易歧义清单：活跃客户 / 营收 / 注册数 / 金额类 / 数量类。

**产出**：`指标字典_<组织>.md`（附 xlsx 版便于流转）

### Step 2｜定所有权与权威源（1–2 天）
1. 每个数据集标**具名 owner**（人，不是部门）。
2. 每个主数据标**权威源**。
3. **禁止两个系统都自称同一事实的唯一真相源**——二选一，另一个降级为消费方。
4. 无主数据集单列一表，标注"业务域未就绪"。

**产出**：`数据所有权与权威源清单.md`

### Step 3｜定数据标准（1–2 天）
- **命名标准**：表名/字段名规范（统一后缀如 `_dt` 表日期、`_amt` 金额）。
- **编码标准**：组织机构/商品/地域等公共代码统一。
- **格式标准**：日期格式、金额精度、单位（元/万元**必须统一**）。
- **值域标准**：状态字段枚举值统一（同一业务状态在各系统叫法不同的，先列表再归一）。

**产出**：`数据标准_<组织>.md`

### Step 4｜主数据方案（2–4 天）
1. **先定唯一标识**，再谈质量。四个主数据域：客户/供应商/商品/组织。
2. 画出跨系统 ID 映射（同一客户在交易/会员/财务三套 ID 是常态）。
3. 定**主数据管理机制**：谁新建、谁审核、谁同步、冲突怎么裁。
4. One ID 方案要与 `dx-architecture-opt` 的架构口径一致。

**产出**：`主数据管理方案.md`

### Step 5｜写质量规则集（2–5 天）
1. 套用 `../_shared/references/数据质量规则库.md` 的五性模板。
2. 每条规则必填：编号 / 字段 / 维度 / 检查逻辑 / 阈值 / 责任人 / **业务语义**。
3. **必须可机检**——写进 Word 不算治理。
4. **优先级排序**（不铺全网）：
   - ① 高频被用的核心表（交易/价格/客户）
   - ② 对外报送与合规字段
   - ③ 沉睡表/离线文件（可后置）
5. **跑一遍拿真实数字**，把"质量良好"改成"主键非空率 99.97%"。

**产出**：`质量规则集_<组织>.xlsx`（可机检）

### Step 6｜划访问边界（1–2 天）
1. 内部非个人数据 → **默认开放**。
2. 个人/财务/受监管 → 最小权限 + 声明用途 + 定期复核。
3. 逐列标 PII 级别与处理方式（脱敏/令牌化/加密）。
4. 定义保留期与删除流程（含被遗忘权）。
5. 明确审计范围（查询与导出是否留痕）。

**产出**：`访问策略与合规边界.md`

### Step 7｜交棒（半天）
产出质量看板口径，供 `dx-application-plan` 在汇报中呈现（**"数据可信度提升"本身就是一个价值点**）。

## 输出物（门禁检查）
- [ ] `指标字典_<组织>.md` + `.xlsx`（**核心交付物**，≥10 个指标，每个有 SQL 和具名 owner）
- [ ] `数据所有权与权威源清单.md`（含无主数据集清单）
- [ ] `数据标准_<组织>.md`
- [ ] `主数据管理方案.md`
- [ ] `质量规则集_<组织>.xlsx`（可机检 + **有实测数字**）
- [ ] `访问策略与合规边界.md`

**门禁**：指标字典 + 所有权清单 + 质量规则集为必需；
**实质性检查**：质量规则集必须含实测跑出的数字，纯模板不算通过。

## 质量优先级矩阵

| | 高频使用 | 低频使用 |
|---|---|---|
| **对外/合规** | 🔴 P0 立即治 | 🟡 P1 排期 |
| **内部使用** | 🟡 P1 排期 | ⚪ P2 后置/考虑下架 |

> 不要全网铺开。**先治 P0，做出样板，再横向复制。**

## Gotchas

- **不要两个系统都当唯一真相源**——同一事实只能有一个权威源，否则永远对不上。
- **质量问题的修复位置在上游**：在报表里修，其他消费方还会再犯。
- 规则必须**绑定业务语义**且可机检；写进 Word 不算治理。
- 数据集**"看起来没人用"不等于没人用**——删之前先下架、公示、再移除，不要直接 retire。
- 主数据**先定唯一标识**再谈质量。
- 质量优先级：先治"高频被用的核心表"，不要全网铺开。
- **不要从"制定政策"开始**——会陷入审批队列，三个月出不了成果。从"解决一个具体争议指标"开始。
- **指标字典不是越全越好**：铺满 300 个指标 = 无人维护 = 三个月后全部过期。只做争议最大的 10 个。
- **Owner 必须是人**：写"数据部""IT 部门"等于没写。找不到人 = 这个域还没准备好，如实说明。
- **同名指标必须合并**：两个系统都叫"销售额"但算法不同 → 必须改名区分（如"销售额（含税）"/"销售额（净额）"），不能都叫销售额。
- **单位不统一是最隐蔽的质量问题**：元 vs 万元、吨 vs 公斤，常常无人察觉直到汇总出错。
- **不要为赶进度跳过实测**：规则集写完不跑一遍，等于没有质量数据。
- **保留期与删除流程容易漏**：涉及个人信息的数据集，没有删除流程是合规硬伤。
