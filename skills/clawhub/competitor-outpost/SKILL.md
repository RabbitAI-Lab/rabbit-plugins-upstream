# 竞品前哨 (Competitor Outpost)

把「手动翻官网刷新闻」变成「一杯咖啡时间看完当日、且每条敢直接引用的情报」。专业竞争情报（CI）的核心不是找到信息，而是**同时回答两个正交问题**：这条**有多可信**（来源可靠性），以及**有多重要**（对自家业务的影响）。据此给出可溯源、可行动的结论。

## 30 秒上手（TL;DR）
1. **复制下面任一句触发语**发给 Agent（改竞品名即可）。
2. Agent 会**复述确认**（竞品/维度/范围/去向），你回"对"或改正。
3. 收日报：每条带 可信度 P0–P3 × 影响度 I1–I3 × 发布/采集日 × 可点溯源 × 行动建议。

## 快速触发（复制即用）
- 最简：`用竞品前哨盯 火山引擎方舟、阿里云百炼，关注 定价变动，发我邮箱`
- 完整：`用竞品前哨监控 硅基流动、百度千帆，维度=产品更新/定价/融资，范围=最近7天，重点=新模型发布与降价，生成日报推到钉钉群「市场情报」`
- 定时：`每天早8点用竞品前哨跑 上述竞品，日报发我邮箱并同步飞书文档`
- 只看一眼：`用竞品前哨给我今天 火山引擎方舟 的情报，只要 P0/P1 和 I1`
- 演示：`用竞品前哨出一份示例日报看看效果`（零输入，见下）

## 零配置演示模式（开箱即看）
用户说「演示 / 示例 / 看看效果 / 先出一份样例」且**未给竞品清单**时：不要追问，直接用内置示例数据产出一份完整样例日报，并在标题与页脚显著标注「演示数据，非真实情报」。真实监控仍走 Step 0 问清单。

## 何时使用
- 用户给出若干竞品 + 关注维度，要一份当期竞品动态汇总。
- 用户要「每天/每周自动」盯竞品，并推到邮箱或 IM。
- 汇报场景需要「这个数据哪来的、要不要现在处理」的可追溯答案。

## 依赖与能力探测（工业级：缺什么、降级什么）
本 Skill 的**核心管线（采集→双轴分级→交叉验证→结构化输出）零外部依赖**，任何环境都能跑。外围能力按探测结果自动降级，绝不因缺连接器而整体失败：
| 能力 | 探测方式 | 有 | 无（降级） |
|------|----------|----|-----------|
| 联网采集 | 尝试 WebSearch/WebFetch | 真实抓取 | 仅用用户提供的自定义源/离线数据，明确标注「未联网」 |
| 邮箱推送 | 是否存在 dingtalk-mail / lark 邮件能力 | 发日报邮件 | 落盘 Markdown/HTML 文件并回传路径 |
| 钉钉 IM/待办 | 是否存在 dingtalk-chat / dingtalk-todo（dws） | 群播报/建待办 | 落盘 + 提示手动转发 |
| 飞书文档/卡片 | 是否存在 lark-docs / lark-chat 等 | 写飞书文档/卡片 | 落盘 Markdown（可粘贴进飞书） |
| 定时自动跑 | 是否支持计划任务(cron) | 建每日 job | 提示用户手动触发或改用其系统 cron |
| 在线页发布 | 是否有 QW Pages 且名额可用 | publish 同域 | 仅交付本地 HTML 文件 |
降级时**必须在输出里显式说明**哪些通道未启用、用了何种替代，不得静默吞掉。

## 输入参数（竞品列表与监控维度为硬必填、无默认值；缺失就用 AskUserQuestion 一次问全，别猜、别套示例）
| 参数 | 必填 | 说明 | 示例 |
|------|------|------|------|
| 竞品列表 | 是 | 顿号/逗号分隔；重名先按主体/官网域名消歧 | 火山引擎方舟、阿里云百炼、硅基流动、百度千帆 |
| 监控维度 | 是 | 可多选 | 产品更新、定价变动、融资新闻、招聘动态、API上新 |
| 时间范围 | 否 | 默认最近24h，以**发布日**为准 | 最近7天 |
| 重点事件 | 否 | 特别关注类型，命中项高亮 | 新模型发布、价格调整、高管变动 |
| 自家基线 | 否 | 用于影响度判定的自家对标（价格/能力/客群） | 我方 Plus 定价 0.012/千token |
| 输出格式 | 否 | 默认 Markdown 日报 | Markdown / 表格 / 卡片 / HTML |
| 分发方式 | 否 | 交付去向 | 仅回话 / 存文件 / 发邮箱 / 飞书 / 钉钉 / 定时任务 |
| 自定义数据源 | 否 | 除内置渠道外要接入的 API/RSS/Webhook，含鉴权与信源等级 | IT桔子融资 API(P2)、竞品 Changelog API(P0)、自建社媒监听(P3) |

## 处理流程

### Step 0 — 确认监控对象（先问再做，绝不套默认）
- **竞品列表与监控维度必须由用户当次给出**。若用户没明说，先用 AskUserQuestion 一次问清：要盯哪几家竞品（名称/主体）、关注哪些维度、时间范围、结果发到哪里。**问清之前不要开始任何采集。**
- **禁止**把示例或模板里的竞品（如火山引擎方舟、阿里云百炼、硅基流动、百度千帆）当作默认监控对象；它们仅用于演示输出格式，不代表用户的真实监控清单。
- 竞品重名/简称先消歧（公司主体、官网域名）；不确定就问，不要猜。
- 用户已给清单时，复述一遍确认（竞品+维度+范围+去向）再执行，避免理解偏差。

### Step 1 — 多源采集（按渠道优先级）
对每个竞品并行扫描，优先用 WebSearch / WebFetch（用当前年份做时效检索）：
- 官网首页、产品更新/Changelog、博客、文档与 API 中心（P0/P1）
- 官方公众号、官方微博、官方演讲实录（P1）
- 权威行业媒体：36氪、虎嗅、钛媒体、量子位等（P2）
- 开发者社区、GitHub、技术论坛（P2/P3）
- 招聘平台岗位变化＝业务扩张方向信号（P3 为主）
- 财报 / 投资者关系页（上市公司，P0）

**自定义数据源接入（可选）**：内置渠道之外，支持接入用户自己的源，并自动纳入分级：
- 类型：第三方数据 API（IT桔子/天眼查 融资工商、七麦 榜单、SimilarWeb 流量等）、竞品开放 API / Changelog、RSS、自建爬虫、内部 BI/CRM。
- 定级：官方一手接口→P0，官方转述→P1，第三方数据/媒体→P2，自建/社媒→P3；来源性质不明时按更低等级处理并打「待人工复核」。
- 鉴权与密钥：API Key / Token / OAuth 凭证**绝不写死在 Skill 或页面**，运行时从环境变量 / 密钥托管注入；调用失败或超时降级为「未采集到」，不编数据。
- 回推：可把结果 Webhook POST 回用户系统（BI / 工单 / IM 机器人），或反向拉取自家基线数据做对比。

**采集健壮性与边界处理（专业级必守）**：
- **去重合并**：同一竞品同一事件的多源报道合并为**一条**，`sources` 数组保留全部出处，可信度取最高等级，并标 `✓ 多源交叉验证`。
- **无结果**：某竞品某维度本期无动态时显式写「本期未检索到 X 的 Y 维度动态」，不留空、不编造。
- **受限源**：遇付费墙 / 登录墙 / 反爬，标注「受限源，未能核实全文」并按更低可信度处理，不臆测正文。
- **超时 / 限流**：单源重试一次，仍失败记「采集失败」并继续其它源，不阻塞整体。
- **软文识别**：疑似营销通稿 / 水军内容降为 P3 并标「疑似软文」。
- **时间口径**：一律以发布日判断是否本期，旧闻重炒单列（见 Step 3）。

### Step 2 — 双轴评级（本 Skill 的灵魂：可信度 × 影响度）

**轴一 · 信源可信度 P0–P3（这条信息有多可靠）**
| 等级 | 定义 | 引用规则 |
|------|------|----------|
| P0 | 竞品官方一手事实（官网公告、财报、官方文档数据） | 可直接引用 |
| P1 | 竞品官方渠道转述（官方公众号文章、官方演讲实录） | 可引用，标注来源 |
| P2 | 权威媒体报道（有审稿流程） | 需注明「媒体报道」 |
| P3 | 社媒 / 论坛 / 自媒体（未经审稿） | **必须打「待人工复核」** |

**轴二 · 情报影响度 I1–I3（这条信息对自家业务有多重要，结合「自家基线」判定）**
| 等级 | 定义 | 触发例 |
|------|------|--------|
| I1 高 | 直接冲击核心指标，需当日上报/决策 | 价格战、旗舰模型/能力跃升、大额融资、关键客户或高管变动、渠道政策突变 |
| I2 中 | 值得关注的趋势信号，纳入周度研判 | 次级功能更新、区域/行业拓展、招聘方向变化、生态合作 |
| I3 低 | 背景信息，存档备查 | 常规小更新、营销软文、与己无关动态 |

**优先级象限（两轴交叉 → 行动指引）**
| | 影响 I1/I2（重要） | 影响 I3（次要） |
|------|------------------|------------------|
| **可信 P0/P1** | 🟢【立即行动/上报】事实清楚且重要 | 🔵【记录归档】 |
| **存疑 P2/P3** | 🟠【优先核实】重要但未证实，最高优先级去查证，勿外传 | ⚪【忽略/存档】 |

### Step 3 — 交叉验证 + 日期口径（防最常见的坑）
每条情报必须附：① 可信度 + 影响度；② **发布日期**（事件发生日，非采集日）；③ 采集日期；④ 可点击溯源链接；⑤ 行动建议（由象限推导）。
- **多源同事件**：取最高可信度为准，标 `✓ 多源交叉验证`。
- **发布日 ≪ 采集日**：多为旧闻重炒，标 `↻ 旧闻回收`，不计入「本期新增」。
- **低信源独报、高信源未证实**：保留但打 `⚠ 待人工复核`，绝不写成事实。
- **信息互相矛盾**：并列两种说法 + 各自信源，打 `⚠ 待人工复核`。

### Step 4 — 结构化输出（竞品 × 维度矩阵，非时间流水账）
先产出一份符合 `templates/data-schema.json` 的结构化记录数组（供 BI/趋势/复用），再按选定格式渲染：
- **Markdown 日报**（默认）：套用 `templates/report-template.md`——`# 竞品情报日报 | YYYY-MM-DD` → 今日三件事（含影响度与行动建议）→ 每竞品分维度表格（发布/采集 · 事件 · 可信度 · 影响度 · 来源链接）→ 信源说明 + 待复核免责 + 合规声明。
- **表格 / 卡片**：同一数据压平成一张表或 IM 卡片正文。
- **HTML 可视化页**：套用 `templates/report-demo.html`（Notion 风、双轴彩色标签、发布/采集双日期、旧闻回收/交叉验证、竞品×维度矩阵、信源筛选、配置输入面板驱动整份报告实时重算、数据概览可视化含**可信度×影响度优先级象限**、术语解释折叠区）。用 Write 生成本地 index.html 后交付；需在线访问走「分发」里的 QW Pages。

## 复杂任务编排（竞品多 / 维度多 / 时间长时仍保持高质量）
- **分治并行**：竞品数 ≥3 或维度 ≥4 时，按「竞品」拆成子任务并行采集（可用子 Agent），每路独立超时与重试，单路失败不阻塞整体，失败路在报告中标「采集失败」。
- **先结构化后渲染**：一律先产出符合 `templates/data-schema.json` 的记录数组，再渲染各格式；渲染层不做判定，避免格式差异导致结论漂移。
- **去重与对齐**：跨源同事件按 (竞品, 维度, 事件语义) 归并；用稳定 id 与历史报告对齐，识别「新增 / 持续 / 旧闻回收」，避免每天重复报同一条。
- **长列表分页/截断**：单源条目 >20 时只取时间窗内前 20 并标注「已截断」，不静默丢。
- **时间盒**：整体设超时预算；超预算则先交付已完成部分 + 明确列出未完成源，绝不为了"凑满"而编造。

## 质量门禁（交付前二次校验，Critic 视角）
在 DoD 之外，再做一遍"挑刺"自检：
- **证据复核**：抽 ≥2 条 P0/P1 打开链接，确认页面真含该事件且日期吻合；不符则降级或标待复核。
- **矛盾扫描**：同事件多源结论冲突时并列呈现 + 待复核，不得择一隐瞒。
- **日期 sanity**：发布日不得晚于采集日；晚于"今天"的一律视为数据错误剔除。
- **链接活性**：抽样 HEAD/GET 确认可访问；死链替换为可达官方页或标注「链接失效」。
- **影响度复核**：I1 必须能回答"冲击我方哪个指标"，答不出降为 I2。
- 任一门禁不过 → 修正后再交付，并在报告末尾附「质检说明」。

## 模型增强（可选加速器：Jev / Muse，缺省自动回落）
本 Skill 的判定与编码子任务可外接更强/更快的模型；**均为可选**，未配置时回落到执行 Agent 自身能力，不影响主流程。密钥一律走环境变量，不写死。
- **Jev（TypeSafe AI 决策模型）**：用于**批量结构化判定**——把候选情报字段（来源类型/是否官方/是否多源/发布-采集间隔/与我方基线关系）提交 Jev，取其 70–500ms 的结构化决策作为 可信度 P0–P3、影响度 I1–I3、是否待复核 的初判，再由执行 Agent 复核兜底。配置：`JEV_API_ENDPOINT` / `JEV_API_KEY`。Jev 不生成文本，故不用于撰写摘要。
- **Muse（Meta Muse Spark / Muse Code）**：用于**代码型子任务**——生成/修补 HTML 可视化、为自定义 API/RSS 源编写抓取与字段映射适配器、生成趋势图表代码。配置：`MUSE_API_ENDPOINT` / `MUSE_API_KEY`。
- **回落顺序**：Jev/Muse 不可用或调用失败 → 执行 Agent 按本 Skill 规则自行判定/编码，并在输出中注明「未启用外部模型加速」。
- 启用外部模型不改变评级规则与合规约束；最终定级与免责仍以本 Skill 的 P0–P3 / I1–I3 与 DoD 为准。

## 错误与降级手册（出错时怎么说、怎么自救）
| 错误 | 用户可见话术 | 自动恢复 |
|------|-------------|----------|
| 源超时/限流 | 「X 源本次超时，已跳过；其余 N 源正常」 | 重试 1 次→跳过→报告标注 |
| 403/反爬/登录墙 | 「X 源受限（需登录/反爬），未抓取正文」 | 标「受限源」，不臆测正文 |
| CORS 拒绝（前端直连） | 「该源不允许浏览器跨域，需改后端/Agent 抓取」 | 提示切换 Agent 通道 |
| 无结果 | 「本期未检索到 X 的 Y 维度动态」 | 显式留痕，不编造 |
| 密钥缺失 | 「未配置 X 密钥，该源以无鉴权尝试/跳过」 | 回落或跳过并说明 |
| 连接器缺失（邮件/钉钉/飞书） | 「未检测到 X 连接器，已改为落盘文件：<路径>」 | 落盘 + 回传路径 |
| 解析失败（非 JSON/无数组） | 「X 源返回格式不符（预期数组位于 path）」 | 提示核对 path/类型 |
| 超时预算耗尽 | 「已达时间预算，先交付已完成 M/N 源」 | 部分交付 + 列未完成源 |

## 增值分析（不止罗列，给出 so-what）
- **跨期趋势**：与上期报告 diff，标「新增 / 持续 / 消退」，量化各家动态强度变化。
- **动作解读**：对每条 I1/I2 给一句"这意味着什么"（对我方价格/能力/渠道/人才的含义）。
- **预警阈值**：可配置（如"竞品降价>10% 或旗舰模型发布 → 立即@我"），命中即高优推送。
- **聚合视图**：支持周报/月报（按周/月聚合 + 趋势），不止日报。
- **对标基线**：结合「自家基线」输出差距表（我方 vs 竞品：价格/能力/节奏）。

## 分级校准示例（保证判定一致、可复现）
- 官方定价页公告降价 → P0 + I1（直接冲击价格）→ 🟢 立即上报。
- 官方公众号预告"将发布"（尚未发布）→ P1 + I2 → 🔵 记录，发布后再升级。
- 单一自媒体称"某司裁员/拆分"、无官方与权威证实 → P3 + I1 → 🟠 优先核实，勿外传。
- 两家媒体同报一笔融资、金额一致 → P2 + ✓多源 + I1 → 🟢 上报（注明媒体口径）。
- 官方招聘页新增某方向岗位 → P0（官方页）+ I2（是信号非事实变动）→ 🔵 记录研判。

## 分发（映射到真实能力，别虚构）
- **存文件 / 在线页**：Write 生成文件到 outputs；在线版用 `qwenwork_pages_publish`（static 目录，root 含 index.html）。发布后回传公开 URL。
- **邮箱推送**：用 `dingtalk-mail`（`dws mail`）发正文/附件；先用 `dingtalk-contact` 解析确认收件人再发。飞书生态用对应 lark-* skill。
- **钉钉群消息 / 待办**：群播报用 `dingtalk-chat`（`dws chat`）；「跟进某竞品动作」用 `dingtalk-todo`（`dws todo`）。DWS 命令一律用 PATH 形式 `dws ...`，作为直接命令执行，勿套管道/重定向/后台。
- **飞书文档 / 卡片**：用 `lark-docs` / `lark-bitable` / `lark-chat` 等 skill（先读其 SKILL.md）。
- **定时自动跑**：用 QW 计划任务（cron）建每日 job，payload.message 用自然语言写清「竞品=…，维度=…，自家基线=…，生成日报并发送到『某邮箱/某群』」，含 IANA 时区。定时任务在独立会话跑，务必写全参数与投递目标。
- **每日自动刷新在线页（无数据库也能"活"）**：若已有一个 static QW Page，让 cron 的 Agent 步骤在生成真实日报后，用真实数据重写页面里的 `EVENTS` 数组（或注入一段 `report.json`），再 `qwenwork_pages_publish` 到**同一目录**（同域名升版）。这样静态站每天自动换新内容，无需 dynamic+database 页。
- **平台约束提醒**：一个 QW 账号通常只有一个 Page 且 category 锁死；若该名额已被 static 演示页占用，可能无法再 provision dynamic+database 页。需要"数据库支撑的实时站"时，先确认账号名额，否则优先用上面的"Agent 生成→重刷 static 页"方案。真正的联网抓取 / API / RSS / Webhook 与语义分级一律在 Agent 层执行，页面不自己抓。

## 交付前质量自检（Definition of Done）
- [ ] 每条情报都带：可信度 + 影响度 + 发布日 + 采集日 + ≥1 个可点来源 + 行动建议。
- [ ] 无「裸事实」：任何未证实/矛盾项已打「待人工复核」。
- [ ] 去重合并完成，无同事件重复条目。
- [ ] 无动态的维度显式标注，非留空。
- [ ] I1/I2 高影响项已进入「今日三件事 / 行动建议」，低可信×高影响落入「优先核实」。
- [ ] 对外分发前已确认收件人/目标群，并附「待复核项对外前须人工确认」提示。
- [ ] 未泄露任何密钥或非公开数据；所有来源均公开合规。

## 合规与免责
- 仅采集**公开可得**信息，遵守 robots.txt / 站点 ToS / 平台规则；不绕过登录墙或付费墙抓取。
- 不采集、不存储个人敏感信息；招聘信号只看岗位类别，不看个人。
- 引用第三方数据须注明出处与日期；涉真实公司，附「基于公开信息整理，非投资/法律建议」。
- 对外发布前，所有「待人工复核」项必须经人工确认，禁止把未证实传言写进对外材料。

## Pitfalls
- 不要沿用演示/模板里的 4 家竞品当默认监控对象；每次以用户当次确认的清单为准（见 Step 0）。
- 别把「可信」和「重要」混为一谈：低价信源+高影响＝优先核实而非直接上报；官方+低影响＝记录而非打扰决策。
- 别将低信源传言当事实写；P3 与矛盾信息一律「待人工复核」。
- 日期用「发布日」判断是否本期事件，别把抓取时间当新事；旧闻重炒要标出。
- 不臆造链接或数据；抓取不到就写「未检索到」，勿填空。
- 分发前若收件人/目标群不明确，先确认再发，别群发。
- 自定义数据源的 API Key / Token / OAuth 凭证绝不写死进 Skill、页面或提交包，只走环境变量 / 密钥托管；对外分享前确认无泄露真实密钥。

## Verification
- 逐条核对 DoD 七项，缺一即返工。
- 抽 2–3 条 P0 打开链接核对事件确为当期、非旧闻、影响度评级合理。
- 矩阵/分组视图切换后计数一致（矩阵格 = 分组明细条数）。
- 若走定时任务：首次可 `run` 一次验证能出日报并成功投递到目标入口。

## 分发与上架（让别人能装、能用）
- **打包**：整个 skill 目录（含 SKILL.md + templates/）zip 即得可安装包；QwenWork 内 `.skill` 后缀 zip 可直接"保存技能"。
- **上架前隐私剥离（必做）**：`templates/report-demo.html` 分发版必须移除作者个人的二维码/头像/主页链接/昵称（替换为占位注释），只保留通用结构；作者个人版仅用于自己的展示页，不进公共包。发布前 grep 确认无个人标识、无密钥。
- **SkillHub**：`skillhub publish <目录或.zip> --version <x.y.z> --changelog "..."`（先 `skillhub auth whoami` 确认登录；`--dry-run` 本地预检 metadata+打包，不发起请求）。
- **ClawHub 等无 CLI 的平台**：导出同一 zip，按其后台"上传技能包"流程提交；包内 SKILL.md 的 YAML `name/description/version` 即元数据。
- **元数据卫生**：description 要含触发词（竞品/监控/情报日报/competitive intelligence），version 语义化递增，changelog 记录每版变更。

## FAQ（集中答疑）
- **没装钉钉/飞书连接器能用吗？** 能。自动降级为落盘 Markdown/HTML 并回传文件路径，输出中会注明未启用的通道。
- **密钥怎么给？** 一律环境变量/密钥托管注入（源鉴权、JEV_*、MUSE_*），绝不写进 Skill、页面或提交包。
- **能只看某个维度/等级吗？** 能。维度可单选；也可加"只要 P0/P1 和 I1"这类过滤语。
- **误报/旧闻怎么办？** 发布日≠采集日自动标「旧闻回收」；单源/矛盾自动标「待人工复核」，不进对外材料。
- **能接公司内部 API/BI 吗？** 能。作为自定义源（API/RSS/Webhook）接入，按来源性质自动定级。
- **日报太长？** 用过滤语收窄，或改周报/月报聚合视图。
- **如何停止定时？** 删除/禁用对应 cron job 即可；不会残留后台进程。
- **支持海外竞品/英文源吗？** 支持。源与关键词不限语言，分级规则通用。
- **和新闻聚合器有什么区别？** 双轴评级 + 交叉验证 + 发布/采集日分离 + 可溯源 + 行动建议，而非时间流水账。
- **数据存在哪？** 默认不落敏感库；在线页为静态演示，真实数据留在 Agent 会话与你指定的投递端。
