# 2.0：跨任务固定执行记录

涉及平台动作时读取本文。`scripts/execution_store.py` 提供固定执行记录入口，供 [动作网关](action-gateway-v2.md) 使用。当前只有合成验证，尚未配置真实店铺、宿主授权和生产目录。

## 报告记录与执行记录分开

报告目录内的 `run-journal.sqlite` 记录这次专家协作、报告冻结和交付。平台执行另用宿主固定配置的 `ExecutionStore`，不同报告共享这一执行记录；不能在每次报告文件夹中新建空的执行库来绕过之前的提交。

同一部署的 WorkBuddy/Codex 若允许操作同一平台账号和店铺，必须指向同一权威执行存储，而不是各自复制一份。跨设备部署不能使用彼此不同步的本地 SQLite；需后续接入共享服务，当前不宣称跨机器防重。

初始化是明确的部署动作：由用户/管理员选定尚不存在的专用目录及允许的客户、平台、账号、店铺、连接器清单，再调用 `ExecutionStore.create(directory, scopes)`。同一平台账号/店铺不能同时分给不同客户或连接器别名。scope 清单不是平台授权，不能替代凭证或动作批准。正常专家任务只可打开已配置入口，不得调用 create 自行“修复”缺失记录。

## 任务使用方式

1. 从可信宿主配置读取固定的 `execution-store.json` 绝对路径，调用 `ExecutionStore.open(profile_path)`。目录内配置与 `execution.sqlite` 的身份、路径、指纹必须匹配。缺文件、损坏、复制目录、换库时停止，不自动创建表或新数据库。
2. 使用本次真实 run_id、版本和任务类型调用 `bind_run(run_id, binding, version, task_type)`。已绑定的运行不能换客户或店铺。返回执行引用，可由任务保存进本次报告记录；引用不包含凭证。
3. 使用 `store.read_gateway(connector, binding, ...)` 创建平台只读入口，或用 `store.gateway(connector, binding, ...)` 创建动作网关。`api` 模式必须绑定 ExecutionStore，不能给它任意报告账本。原有明确 mock 测试仍可使用隔离账本。
4. 核对报告引用时，先打开宿主固定的执行存储，再调用 `check_reference(reference, run_id, client_scope)`。不能倒过来信任报告里的路径选择另一库。它返回该运行的动作状态，可供展示；仍须由真实平台回读才能获得执行完成证据。
5. 使用完关闭存储连接。每个并发调用者单独打开连接，同一数据库通过事务和唯一约束保护占用；不能跨线程共享同一个 sqlite3 连接。

本轮提供的是固定入口、范围绑定和引用校验 API。WorkBuddy/Codex 启动配置与报告产物中的自动引用接线还须在真实宿主验收时落实；不能把库函数存在当作已部署完成。

## 备份与恢复边界

`store.backup(new_directory)` 使用 SQLite 一致快照生成仅供检查的副本、原配置和 backup.json，记录数据库指纹及每个运行的事件数量、链头。目标必须不存在，不覆盖旧备份；当前连接正在写事务时直接停止，避免等待自己的锁。

`verify_backup(directory)` 校验文件指纹、SQLite 完整性、运行哈希链和存储身份。副本保留原权威路径，直接从备份目录 open 会被拒绝，不会把过去的状态变成另一套可执行记录。

安全恢复尚未实现。尤其不能拿较旧备份覆盖原路径继续执行：这样会丢失备份之后的提交记录，有重复操作风险。需要用户确认、暂停执行、核对平台当前状态和后续调用后另行恢复。当前身份/哈希校验抵御误用和普通篡改，不保证抵御有权同时改写配置与数据库的操作者，也不检测同一路径下整套旧状态被特权恢复。

测试入口：`scripts/execution_store_smoke.py`，全部使用临时目录、合成店铺、合成批准和 mock 连接器，不读取真实客户记录。
