# 工作流卡片库

> 一张卡片 = 一个**重复出现且验收稳定**的复杂任务，由一个或多个 skill **接力**完成。
> 卡片定义各 skill 的**前后连接关系、接口、参数**，Agent 照卡执行即可顺畅衔接、一次跑完，不再每次重新推理组合。

## 来源与准入

卡片只从 self-evolution 的沉淀条件产生：同类任务**重复 ≥ 2 次**、输入与验收标准稳定、失败可回退。新卡必须经教授确认后写入本目录。

## 卡片七字段

1. **目标**：这张卡一次性完成什么；
2. **触发**：何时该用（手动话术 / 自动化衔接）；
3. **步骤表**：`序号 | skill | 输入接口 | 参数 | 输出接口 | 验收`，每步一行；
4. **衔接与数据契约**：步与步之间传什么、什么格式；
5. **失败回退**：任一步失败怎么办（先重试一次，见 retry-policy；仍失败降级运行并记录）；
6. **运行记录**：上次运行时间、结果、降级情况；
7. **沉淀来源**：哪几次真实任务验证了这条组合。

## 统一数据契约：要点卡

为让任意 skill 的输出能被下一步直接消费，步骤间传递统一使用「要点卡」格式：

```markdown
## 要点卡：<步骤名>
- 结论：（一句话，结论先行）
- 要点：（3–5 条，每条带来源/依据）
- 置信与风险：（不确定项、需要教授注意的点）
```

下一步只读上一步要点卡的「结论 + 要点」，不回溯原始检索过程。

## 卡片模板

```markdown
# 工作流：<名称>
- 目标：
- 触发：
- 沉淀来源：
- 状态：active / retired

| 步 | skill | 输入接口 | 参数 | 输出接口 | 验收 |
|----|-------|----------|------|----------|------|
| 1  |       |          |      | 要点卡   |      |

## 衔接与数据契约
（逐步说明：上一步的哪个字段进入下一步的哪个参数）

## 失败回退
（每步：重试一次 → 仍失败的降级方案 → 记录）

## 运行记录
- （日期 | 结果 | 备注）
```

## 维护规则

- 上限 **10 张**；超过先淘汰最久未运行或连续降级者（`status: retired`，不删除）；
- 每季度复查一次：触发条件是否仍成立、步骤 skill 是否已退役或改名；
- 运行后必须更新「运行记录」；连续 2 次降级运行的卡片标记 `retired` 待重设计；
- 卡片里的每块积木应已登记在 [积木注册表](../skill-registry.md)；未注册的先注册再上卡。

## 编写卡片时的接口注意（2026-09-16 首次真实运行后补充）

样板卡首跑暴露的问题具有通用性，写任何新卡前先对照：

1. **skill 多数是 prompt 型**——只有 `SKILL.md`，不接收参数、不返回结构化数据。卡片里的「skill」应理解为「分析框架来源」，真正的执行者是 Agent；不要按函数调用去写接口。
2. **数据不在 skill 里**——数据一律来自连接器或 CLI（如 finance-data 链路的 `westock`）。卡片必须显式写出**取数命令与前置检查**，否则首次运行会卡在依赖缺失。
3. **原生输出 ≠ 要点卡**——各 skill 输出结构互不相同，卡片要明确「由 Agent 显式转换为要点卡」这一步，否则衔接契约落空。
4. **确认 skill 的真实边界**——写接口前先确认该 skill 到底输出什么。样板卡曾要求 `position-management` 给「个股触发价」，而它实际只做总仓位决策，导致接口错配。
5. **验收可能与 skill 输出规范冲突**——如「引用出处」vs「不注明来源机构」。冲突需在卡片里显式裁定并备案。
6. **时间语义要分两个字段**——「生成时点」与「适用交易日」，否则盘后生成的简报会被误读。
7. **取数后做常识校验**——除权日、单位（元/万元/亿元）、指数代码拼写，都曾造成误读。
