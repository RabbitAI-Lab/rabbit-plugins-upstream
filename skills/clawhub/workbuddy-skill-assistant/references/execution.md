# 执行路径：帮助用户更好使用 skill

> 主动调用和自动化触发共用本流程。自动化只读、建议、入队；涉及安装、升级、停用、写外部文件时必须等待用户确认。

## 1. 定位 skill 根目录

从当前加载的 `SKILL.md` 得到 `$SKILL_DIR`，所有脚本、状态和参考文件都用绝对路径。不要依赖 cwd，也不要写死安装目录名。

## 2. 判断用户要哪一种帮助

**判定口诀**：主语槽（skill／技能／助手／积木／工作流／自动化）+ 动作槽（用／装／推荐／选／不会／没生效／不触发／整理／固化）**同时命中即命中本 skill**；句中没有“skill”二字但上下文在说已装能力，同样算。

**不归本 skill**：动作槽是「创建／设计／改进／打分／审计」→ 交设计类或审计类 skill；只有产物槽而无 skill 语境（“帮我想个方案”）→ 直接做那件事，不硬套。

每条 = **信号 → 最小动作 → ⛔ 不要做 → ⚠ 前置检查**：

| 用户信号（判定依据） | 最小动作 | ⛔ 不要做 | ⚠ 前置检查 |
|--------------------|----------|----------|-----------|
| 说出任务目标但没点 skill（“我想把周报自动化”） | 读画像/当前任务，推 1–3 个候选 + 触发话术 | ⛔ 别先跑全量扫描 | 产出／输入／验收能从上下文推断吗？推不出再追问（**至多 2 轮**，见 `SKILL.md` §1） |
| 点名一个已装 skill，问怎么用 | 读 `skill-usage-guide.md`，给输入模板 + 示例 + 验收标准 | ⛔ 别重复介绍它是什么 | 先确认该 skill 已装（查 `skill-registry.md`） |
| 说某 skill 没生效／不触发／报错 | 按「触发词 → 安装路径 → 输入 → 权限/连接器 → skill 本身」只查一层 | ⛔ 别先重装或重置平台 | 先让用户给一次真实触发原话与预期产出 |
| 说 skill 太多／想整理／该关哪些 | 跑诊断读数量、重复、frontmatter 事实，给关闭优先级 | ⛔ 别替用户停用 | 停用属写操作 → 需用户确认 |
| 想把重复工作变成自动化／固定流程 | 先跑一次真实任务，产出稳定后再固化；复杂接力转 [工作流卡片](workflows/README.md) | ⛔ 别跳过首次真实运行直接建自动化 | 至少有一次成功产出可参照 |
| 要做全面 WorkBuddy 体检／平台治理 | 说明本 skill 不做平台治理，改用专用体检 skill | ⛔ 别用 12 条核心检查冒充全面体检 | 先分清是「单个 skill 质量」还是「平台治理」 |
| **创建／设计／改进／给 skill 打分** | 转设计类 skill（创建、改进、打分各有入口） | ⛔ 别在本 skill 内设计或改造 skill | — |
| 表外：完全不像上面任何一条 | 问一句归类问题——“你是想选 skill、排查某个 skill，还是把这事变成固定流程？”，**一轮内收敛** | ⛔ 别展开长问卷 | 一轮问不出就直接按最可能的一类做最小动作 |

命中后仍按「推荐话术三件套」（建议值 + 一句理由 + 备选 + “按建议”快捷键，权威见 `SKILL.md` §2）给方案。

## 3. 针对性读取事实

只有在用户确实需要检查时运行：

```text
python $SKILL_DIR/scripts/usage_diag.py --offline --json
```

优先读取：

- `skills.names`：已装 skill 和数量；
- `checklist`：12 条核心项的状态和证据；
- `issues` / `issue_items`：P0/P1/P2 发现；
- `tier`：只作为回答深度提示，不作为复杂流程分叉。

不要为了产出一个分数而读取全部日志、全部主题清单或全部历史报告。

## 4. 给出最小可执行方案

每项建议必须同时给：

1. 推荐的 skill 或组合；
2. 可复制的触发话术；
3. 需要准备的输入；
4. 成功验收标准；
5. 是否需要用户确认。

推荐顺序：

1. 已装且能满足目标的 skill；
2. 已装 skill 的组合；
3. 只安装一个缺失的关键 skill；
4. 最后才考虑自动化或新增连接器。

SkillHub 托管 skill 直接使用 `references/best-practices/toolbox.md` 的安装 prompt，不走市场搜索。外部调用统一遵守 `references/retry-policy.md`。

## 5. 执行与验收

用户确认后执行一个最小真实任务。执行结束后检查：

- 产出文件/消息/数据是否存在；
- 内容是否满足格式与边界；
- 是否需要补充输入；
- 是否值得沉淀为记忆、工作流或自动化。

失败时只扩大排查范围一层：触发 → 安装路径 → 输入 → 权限/连接器 → skill 本身。不要先重装全部 skill 或重置平台。

## 6. 状态与报告

只有以下信息进入 `state.md`：

- `health_score`；
- `checklist_score` / `checklist_status`；
- 生态覆盖与推荐采纳记录；
- 待用户确认的动作。

报告由 `scripts/report_builder.py` 生成，内容是：

- 事实发现；
- 12 条核心项的达标明细；
- 最多 3 条建议动作；
- 已确认事项与下一步。

如果没有新发现、没有失败项且没有用户要求，不落盘、不推送，直接返回 `SILENT`。

## 7. 自动化触发时的额外红线

- 可以运行只读诊断、生成报告、更新检查时间；
- 不可以自动安装、升级、停用 skill；
- 不可以自动写 `SOUL.md`、`USER.md`、`MEMORY.md`；
- 不可以自动创建连接器或修改用户配置；
- 所有待做变更只进入 `pending_actions`，由用户下一次确认。
