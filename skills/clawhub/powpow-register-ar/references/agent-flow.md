# مسار الإنجاز التفويضي للـ agent وعقد السكربت — powpow-register

تفاصيل تنفيذ كل خطوة من SKILL.md. كل الأوامر بالصيغة `node scripts/powpow-register.mjs <أمر فرعي> [معاملات]`،
والسكربت **بدون تبعيات** ويتطلب **Node ≥ 18**؛ وكل الطلبات تُرسل حصريًا إلى `https://global.powpow.online`.

## تصميم الأمان (لماذا صُمِّم هكذا)

| التصميم | السبب |
|---|---|
| كلمة المرور تدخل فقط عبر متغير البيئة `POWPOW_REGISTER_PASSWORD` | وسائط سطر أوامر العملية مرئية لبقية عمليات الجهاز نفسه (سطح تسرب argv)؛ أما متغير البيئة فيقرأه السكربت ويستخدمه فورًا |
| كلمة المرور **لا تُكتب أبدًا في ملف الحالة** ولا تظهر في السجلات أبدًا | ملف الحالة قد يبقى على القرص؛ وفي وضع التوليد تُعرض مرة واحدة ليحفظها المستخدم |
| ملف الحالة في مجلد النظام المؤقت (`os.tmpdir()/powpow-register-state.json`, 0600) | لا يحوي سوى الحقول الخمسة email / username / nickname / token / outTradeNo؛ و`cleanup` يمحوه بكبسة واحدة |
| الـ JWT الذي يحصل عليه الـ agent يُستبدل بـ cookie للمتصفح عبر نقطة النهاية الرسمية `me?token=` | إنه الجسر الرسمي الذي صممته المنصة لـ WebView في HarmonyOS؛ والتحقق يفحص التوقيع + مدة الصلاحية فقط دون ربط ببصمة الجهاز، فمتصفح المستخدم يصلح |
| الدفع يقتصر على create-order / query / فتح صفحة الدفع | فعل الدفع وبيانات الدفع يبقيان دائمًا بين المستخدم وصفحة دفع Alipay الرسمية؛ والـ agent لا يتدخل فيهما |

## مرجع الأوامر

| الأمر | المعاملات الرئيسية | الوظيفة / التوقيت |
|---|---|---|
| `status` | —— | الاطلاع على تقدّم المسار (يقرأ ملف الحالة)؛ بعد انقطاع المحادثة شغّله أولًا |
| `gen-password` | —— | توليد كلمة مرور قوية من 24 محرفًا (كبيرة + صغيرة + أرقام)؛ stdout يعرضها **هذه المرة فقط** |
| `prepare-suggest` | `--username --nickname --email` | تدوين المعلومات المؤكدة في ملف الحالة (فتُغني عن تمريرها مجددًا عند register) |
| `send-code` | `--email` | تفعيل إرسال المنصة لرمز تحقق من 6 أرقام (صالح 10 دقائق، تهدئة 60 ثانية) |
| `register` | `--code` (إلزامي)؛ `--username --nickname --avatar --phone` (اختيارية، تُغنى إذا وُجدت في ملف الحالة) | إنشاء حساب pending؛ كلمة المرور عبر متغير البيئة `POWPOW_REGISTER_PASSWORD`؛ وعند النجاح يُخزَّن الـ JWT تلقائيًا في ملف الحالة |
| `login-link` | `--target pending` أو `--target home` | توليد رابط دخول بنقرة واحدة (تصميم الرابط المزدوج، انظر أدناه) |
| `create-order` | `--package monthly\|quarterly\|yearly` (الافتراضي Alipay)<br>`--provider alipay\|paypal` | إنشاء طلب الدفع؛ Alipay يعيد مسار ملف صفحة الدفع + outTradeNo؛ PayPal يعيد مسار ملف صفحة التفويض + subscriptionId (يُدوَّن تلقائيًا في ملف الحالة) |
| `query` | —— | الاستعلام عن حالة الطلب/الاشتراك. Alipay: `paid / pending / closed / unknown`؛ PayPal: `ACTIVE / PENDING`؛ استعلام كل 10–15 ثانية |
| `refresh-login` | كلمة المرور عبر متغير البيئة | تسجيل دخول جديد واستبدال بـ **JWT جديد** (إقرار الاشتراك يتحول من NONE إلى ACTIVE)؛ إلزامي بعد وصول المبلغ |
| `whoami` | —— | الاستعلام بالـ token الموجود في ملف الحالة عن حالة الحساب والاشتراك (التحقق من فعالية التنشيط) |
| `cleanup` | —— | حذف ملف الحالة (إلزامي عند الختام) |

**تمرير متغير البيئة** (كلمة المرور لا تصعد إلى سطر الأوامر أبدًا):

```bash
# bash / zsh / WSL
POWPOW_REGISTER_PASSWORD='<كلمة المرور>' node scripts/powpow-register.mjs register --code 123456
# PowerShell
$env:POWPOW_REGISTER_PASSWORD = '<كلمة المرور>'; node scripts/powpow-register.mjs register --code 123456
# cmd
set POWPOW_REGISTER_PASSWORD=<كلمة المرور> && node scripts/powpow-register.mjs register --code 123456
```

## آلية الرابط المزدوج (التصميم الجوهري)

حالة الدخول في المنصة هي cookie من نوع HttpOnly، ولا يستطيع الـ agent زرع cookie في المتصفح مباشرة؛ والجسر هو نقطة النهاية الرسمية
`/api/auth/me?token=<JWT>&redirect=<مسار داخلي للموقع>`: التحقق من التوقيع → إنشاء session تلقائيًا للمستخدم
pending → `Set-Cookie: powpow_token` (HttpOnly / SameSite=Lax /
7 أيام) → التحقق من redirect (فقط مسار يبدأ بشرطة مائلة واحدة، مع منع `//` والشرطة المائلة
العكسية، وبعد التحليل يجب أن يكون من المصدر نفسه) → توجيه مؤقت 307 إلى الصفحة الهدف.

- **الرابط 1 (يُسلَّم فور نجاح التسجيل)**: `--target pending` → الهبوط في `/subscription`.
  متصفح المستخدم يدخل حالة «نصف جلسة»: صفحة الاشتراك وصفحة عودة Alipay مرئيتان وقابلتان للتشغيل؛
  أما صفحات المحتوى فلا تزال يردها جدار الدفع إلى صفحة الاشتراك (حماية ثلاثية: فحص إقرارات JWT
  عند البوابة → إعادة فحص في قاعدة البيانات → فحص في واجهات API الأساسية؛ وهذا سلوك طبيعي).
- **الرابط 2 (يُسلَّم بعد تأكيد paid)**: أولًا `refresh-login` لاستبدال JWT جديد (الدفع يحدّث قاعدة
  البيانات فقط ولا يغيّر إقرارات JWT صادر أصلًا؛ وبدون الاستبدال سيظهر الأمر كـ«دفعت وليست لديّ
  عضوية»)، ثم `--target home` → الهبوط في الصفحة الرئيسية،
  بحالة عضوية كاملة.

## التسلسل الكامل (المسار الطبيعي)

```
1.  status                          # فحص ذاتي للبيئة
2.  (الخطوة 2 تأكيد المعلومات في المحادثة، كلمة المرور بالاختيار بين خيارين؛ وضع التوليد: gen-password → ليحفظها المستخدم فورًا)
3.  prepare-suggest --username U --nickname N --email E
4.  send-code --email E             # → يذهب المستخدم إلى بريده للاطلاع على الرمز (مغادرة المحادثة الوحيدة، اللحظة ①)
5.  POWPOW_REGISTER_PASSWORD=*** register --code 123456 [--avatar pic.jpg]
6.  login-link --target pending     # → الرابط 1 يُرسل إلى المستخدم
7.  (يختار المستخدم طريقة الدفع)
    # Alipay: create-order --package monthly|quarterly|yearly
    # PayPal: create-order --provider paypal
8.  start <ملف صفحة الدفع>   # ويندوز؛ في ماك استخدم open، وفي لينكس xdg-open
     # → يتمم المستخدم الدفع/التفويض في صفحة دفع Alipay/PayPal (مغادرة المحادثة، اللحظة ②)
9.  query (كل 10–15 ثانية) حتى paid / ACTIVE
10. refresh-login                   # استبدال بـ JWT جديد بإقرار ACTIVE
11. login-link --target home        # → الرابط 2 يُرسل إلى المستخدم
12. whoami                          # تأكيد subscriptionStatus: ACTIVE (اختياري)
13. cleanup                         # تنظيف ملف الحالة
```

## مطابقة الأوامر مع واجهات المنصة

| أمر السكربت | واجهة المنصة |
|---|---|
| `send-code` | `POST /api/auth/register/send-code` |
| `register` | `POST /api/auth/register` (multipart، رفع مباشر للصورة الرمزية) |
| `login-link` | `GET /api/auth/me?token=…&redirect=…` (الرابط نفسه، يسري عند النقر في المتصفح) |
| `create-order` | `POST /api/payment/alipay/create-order` (Bearer، Alipay)<br>`GET /api/subscription/plans` + `POST /api/subscription/create` (Bearer، PayPal) |
| `query` | `GET /api/payment/alipay/query?outTradeNo=…` (Bearer، Alipay)<br>`GET /api/subscription/create` (Bearer، PayPal) |
| `refresh-login` | `POST /api/auth/login` (`{step:1, username, password}`) |
| `whoami` | `GET /api/auth/me?token=…` |

مصدر القواعد: حقول التسجيل وحدود المعدل في `registration-flow.md`؛ والباقات وسلسلة التنشيط في
`payment-and-activation.md` (وكلاهما يذكر ملفات الكود المصدري للمنصة).

## معالجة الأخطاء على مستوى السكربت

| العارضة | المعالجة |
|---|---|
| `إصدار Node منخفض جدًا` | تراجع إلى وضع الإرشاد الخالص ولا تُصرّ |
| خطأ شبكة / انتهاء مهلة | أعد المحاولة مرة واحدة؛ وإذا استمر الفشل فليفحص المستخدم الشبكة ثم يُتابع (ملف الحالة لا يزال موجودًا؛ استعد المسار من البداية بتشغيل `status`) |
| register يعيد خطأ أعمال (اسم المستخدم موجود مسبقًا ونحوه) | عالجه وفق جدول الخطوة 5 من SKILL.md، **ولا حاجة لإعادة إرسال رمز التحقق** (ما يزال صالحًا 10 دقائق) |
| register يعيد 「邮箱验证码错误或已过期」 (رمز التحقق خاطئ أو منتهي) | انقضى الوقت → أعد تشغيل `send-code` |
| أغلق المستخدم صفحة الدفع بعد `create-order` | أعد تشغيل `create-order` مباشرة (الطلب القديم يُغلق تلقائيًا بعد ساعتين؛ اشتراكات PENDING في PayPal تنتهي بعد ساعة) |
| `create-order --provider paypal` يعيد 409 | يوجد اشتراك PayPal غير مكتمل؛ انتظر ساعة حتى تنتهي صلاحيته، أو أكمل التفويض القديم في المتصفح |
| `query` يبقى pending / PENDING | ربما لم يدفع المستخدم؛ اسأله. وإذا دفع فعلًا → سِر وفق جدول المعالجة في payment-and-activation.md |
| `refresh-login` يعيد 403 `pending_payment` | المبلغ/التفويض لم يصل بعد؛ عُد إلى الخطوة 9 وتابع الاستعلام |
| ملف الحالة مفقود (حُذف سهوًا / تغيير جهاز) | يتعذر استخدام `whoami`/`refresh-login`؛ فليحدّث المستخدم صفحة الاشتراك مباشرة في المتصفح الذي فتح فيه الرابط 1 للتأكد من الحالة، أو ليسجّل الدخول من جديد (وضع الويب) |

## وضع التراجع (إرشاد خالص)

عند أيٍّ من الحالات التالية تراجع فورًا إلى الإرشاد الخالص على طريقة v1 وتوقف عن عناد السكربت:

- لا يوجد Node ≥ 18، أو فشل السكربت مرتين متتاليتين في الخطأ نفسه؛
- قال المستخدم بوضوح «سأفعلها بنفسي على صفحة الويب»؛
- سياسات الشركة/الجهاز تقيّد اتصال السكربتات بالشبكة.

بعد التراجع: أعطِ صفحة التسجيل https://global.powpow.online/register وصفحة الاشتراك
https://global.powpow.online/subscription، ورافق معالجة الأخطاء وفق قواعد `registration-flow.md`،
مع الإبقاء على النبرة نفسها، واختم كل دور بكتلة «الخطوة التالية» كالمعتاد.
