# 排错最佳实践与常见模式

## 排错思维模型

### 1. 二分法（Bisection）
最强大的排错技术之一。适用于：
- 版本间回归：`git bisect` 自动二分commit
- 配置问题：二分配置项
- 数据问题：二分输入数据集

**关键**：每次二分需要明确的pass/fail判定标准。

### 2. 排除法
逐步排除不可能的原因，缩小范围：
- 这个bug在A环境出现、B环境不出现 → 差异点是什么？
- 这个bug在v1出现、v0不出现 → v1改了什么？
- 这个bug在数据集X出现、数据集Y不出现 → X和Y的差异？

### 3. 变更追踪
"最近改了什么？"是排错的第一问：
- `git log --since="1 week ago"` — 最近的代码变更
- `git diff HEAD~5` — 最近5次提交的差异
- 部署记录、配置变更记录
- 依赖版本变更记录

### 4. 最小化复现
将bug触发条件缩到最小：
- 从完整输入中删除不影响bug的部分
- 从完整系统中移除不相关的模块
- 目标：最小的输入 + 最小的系统 = 清晰的因果链

## 常见Bug模式

### 竞态条件（Race Condition）
**特征**：偶尔出现、难以复现、与时间/顺序相关
**排查**：
1. 提高复现率：循环100-1000次
2. 添加stress：多线程并发、网络延迟
3. 使用ThreadSanitizer / race detector
4. 检查共享状态的所有访问点

### 内存问题
**特征**：运行一段时间后崩溃、内存持续增长、偶发segfault
**排查**：
1. 内存profiling：找到增长最快的分配点
2. 检查：未释放的资源、缓存无上限、循环引用
3. 工具：Valgrind / ASAN / 语言特定profiler

### 边界条件
**特征**：特定输入触发、空值/极值/大数据量
**排查**：
1. 测试空集合、单元素、极大值、极小值
2. 测试Unicode、特殊字符、超长字符串
3. 测试并发写入同一资源

### 环境差异
**特征**：开发环境正常、生产环境异常
**排查**：
1. 对比环境变量、配置文件
2. 检查OS版本、运行时版本、依赖版本
3. 检查时区、locale、文件路径分隔符
4. 检查权限、SELinux/AppArmor策略

## 性能回归排查

### 步骤
1. **建立基线** — 在已知好的版本上测量性能指标
2. **二分定位** — 找到引入退化的commit
3. **分析原因** — 是算法退化、数据量增长、还是资源竞争？
4. **量化影响** — 退化了多少？影响哪些场景？
5. **修复验证** — 修复后与基线对比

### 常见性能退化原因
| 原因 | 识别方法 |
|------|---------|
| N+1查询 | 数据库查询次数随数据量线性增长 |
| 缺少索引 | 查询计划显示全表扫描 |
| 内存泄漏 | RSS持续增长不释放 |
| 锁竞争 | 线程等待时间占比高 |
| GC压力 | GC频率/耗时增加 |
| 网络延迟 | 请求耗时主要在I/O等待 |

## 反模式（避免）

### ❌ "日志一切然后grep"
**问题**：信息过载，关键信号淹没在噪声中
**正确做法**：在区分假设的边界处打目标日志

### ❌ "一次改多处"
**问题**：无法确定哪个改动修复了bug
**正确做法**：一次改一个变量，验证后再改下一个

### ❌ "先修再说"
**问题**：没有理解根因就修复，可能引入新bug
**正确做法**：先理解根因，再针对性修复

### ❌ "在我机器上没问题"
**问题**：忽略环境差异，bug仍然存在
**正确做法**：对比环境差异，找到关键变量
