# Troubleshooting

## The skill isn't eligible / doesn't load

This skill is gated on `DANUBE_API_KEY` being set and `curl` being on `PATH`.
Check both:

```bash
test -n "$DANUBE_API_KEY" && echo "DANUBE_API_KEY is set (${#DANUBE_API_KEY} chars)"   # keys are opaque tokens, no fixed prefix
command -v curl
```

If the key lives only in `openclaw.json`, make sure it's under the skill's
entry, which is what `primaryEnv` binds to:

```json5
{ skills: { entries: { danube: { enabled: true, apiKey: "YOUR_DANUBE_API_KEY" } } } }
```

`openclaw skills list --json` shows the skill's `eligible` flag and anything `missing`.

## Danube's MCP tools don't show up in OpenClaw

```bash
openclaw mcp list                      # is "danube" saved?
openclaw mcp doctor danube --probe     # can OpenClaw connect and list tools?
openclaw mcp status
```

Common causes:

- The server was saved without `"transport":"streamable-http"` — OpenClaw then
  assumes SSE, which Danube does not serve. Re-run the `openclaw mcp set danube '{...}'`
  command from `SKILL.md`.
- The header was saved as the literal string `${DANUBE_API_KEY}` instead of
  the key value. `openclaw mcp set` stores what you type; use the actual
  key value (or switch to `"auth":"oauth"` + `openclaw mcp login danube`).
- The agent is running with the `minimal` tool profile, which hides MCP tools.
  Use `coding` or `messaging`, or check `tools.deny` for `bundle-mcp`.

Sanity-check the server and the key from the shell:

```bash
curl -s https://mcp.danubeai.com/health                      # server up? (no auth needed)
curl -s -o /dev/null -w "%{http_code}\n" "https://api.danubeai.com/v1/tools/search?query=weather" \
  -H "danube-api-key: ${DANUBE_API_KEY}"                      # 200 = key accepted, 401 = rejected
```

## Errors while executing tools

**Start with the attribution.** A failed `execute_tool` carries `error_type`, `fault` and
`retryable` — in `_meta` over MCP, at the top level of the response over REST. `fault` is
`caller` (your parameters or credentials), `upstream` (the third party failed; retrying later
may work, and this is the only class that counts against the tool's reliability score) or
`danube` (a stale catalog row or a request Danube built wrong — neither a retry nor a
`report_tool` helps). Those three fields pick the row you need below faster, and more
reliably, than matching message text.

Over MCP the text *usually* also opens with `Request error:` / `<Service> error:` / `Danube
error:` plus a line of advice, but don't match on that: `auth_required` and an insufficient
wallet balance return their own text with no prefix, and nothing is prefixed over REST. The
fields can be absent altogether when the failure never reached the execution engine — an
unresolvable `tool_id`, a `tool_name` matching nothing (no `_meta` at all over MCP), or a
refusal the REST layer turned into a real status such as `402` or `503` — so read them with
`.get()`.

| Symptom | Cause | Fix |
|---|---|---|
| A failure and you can't tell whose it is | Read `fault` before anything else: `caller`, `upstream` or `danube`, with `error_type` naming the specific class (`missing_parameters`, `auth_required`, `rate_limited`, `timeout`, `endpoint_missing`, `upstream_tool_missing`, `bad_request`, `not_found`, …) and `retryable` saying whether the identical call could succeed later | Act on the verdict rather than the prose. `retryable: false` means a bare retry cannot help — change the request, pick another tool, or tell the user. Note `error_type` is a different vocabulary from the `last_error_class` in a search result's `reliability` block, which is the reliability view's own coarser bucket |
| `fault: danube` and you want to help by filing a report | A genuine Danube-side defect is recorded for repair without you. The rest of this class isn't a defect at all: a sunset tool, a retired service and a disabled tool are deliberate catalog states | Don't `report_tool` either kind — it adds nothing in the first case and is wrong in the second. Pick another tool or tell the user what is unavailable |
| `error_type: auth_required` (`fault: caller`) | The user hasn't connected that service on Danube | Send them to the `configuration_url` in the error, or https://danubeai.com/dashboard → connect the service. For API-key services the user may hand you the key to store (confirm first) |
| A call takes ~30s and comes back `error_type: timeout` on a tool that legitimately does slow work (an Apify actor run, a crawl, a server-rendered report) | The default per-call ceiling is about 30 seconds | If the tool is served by an **MCP server**, re-run with `timeout_seconds` — 1 to 300 on `execute_tool`, or the same key beside `tool_input` on `POST /tools/call/{id}` — and don't `report_tool` something that simply needs longer. On an **`api`** service that parameter is accepted and ignored: the budget lives on the tool's own catalog row and a caller can't raise it, so narrow the request instead (fewer items, a tighter filter, the upstream's pagination) or `report_tool` it as `timeout`. Past 300 s the work belongs in an async flow either way: start it, keep the handle, poll the service's own status tool |
| `invalid_grant` / "token expired" | The service's OAuth grant was revoked or expired | User re-authorizes the service in the dashboard |
| `401 Unauthorized` from `api.danubeai.com` | Bad or revoked `DANUBE_API_KEY` | Regenerate at https://danubeai.com/dashboard/api-keys |
| `403` | The API key is scoped to specific services/tools, or the org's policy blocks this tool | Tell the user what was blocked; don't work around it |
| A service you just connected or published is missing from `list_services` | `list_services` (REST `GET /services` and `/services/public`) is served from a cache refreshed every 60 seconds | Wait up to a minute, or go straight to `search_tools` / `get_service_tools(service_id)`, which are not cached |
| `list_services` over MCP returns a JSON-RPC error — code `-32602`, "Invalid request parameters" — instead of a result | Not your parameters, despite what the message says. A page of results containing a service whose `tool_count` arrives `null` fails the MCP layer's own `Service` model, which declares that field as an `int`, and the whole page fails with it — so this belongs to the page, not to the service you were looking for. (Any field violating that model would do the same; `tool_count` is what does it today. The null comes from the keyword branch of the service search, which doesn't stamp a count, so the *same* service can carry a number on one query's page and `null` on another's.) Stable for a given query rather than a passing blip: live on 2026-09-15, `query: "Day AI"` failed five times running while `"Outreach"` and `"Coupler"` returned normally on the same connection, and still failing on 2026-09-23. The offending row is almost never the service you searched for — the same query over REST returns Day AI itself with `tool_count: 0` and the `null`s on the loosely-matched rows below it | Re-sending the identical call won't clear it, but a **different phrasing may** — it reshuffles which rows land on the page (`"Day"` and `"dayai"` both worked, both returning Day AI first). The reliable routes are `search_tools` with the capability you're after (unaffected on the same query), or `GET /v1/services?query=…` over REST, which returns those rows without complaint. Nothing to `report_tool`: this is Danube's own API, not a marketplace tool |
| `get_service_tools` says `needs_configuration: false` but calls fail with `auth_required` | The flag is true only when *every* tool of the service is `needs_credential` for this account; a service mixing credential-free and credential-bearing tools reports false. Over MCP it is derived from the tools that call *returned*, i.e. the first 50 at most — see the 50-cap row below | Read the per-tool `readiness` on each entry (or on `search_tools` results); that is the answer for the tool you are about to call |
| `get_service_tools` on a service the user just connected comes back with an empty `tools` list | Possibly "not yet" rather than "none": an MCP service's tools are registered by a first sync that runs in the background (since 2026-09-13), and registering a large server's takes tens of seconds. The response says so — `tool_sync: {"status": "running"}` plus a `message`, and over REST `needs_sync: true` as well. Note the sync starts when the user connects the service in the dashboard, or on your own first read of the tool list — your `store_credential` does not start one | Read it again in a few seconds. There is nothing for you to call: the read is what starts or restarts the sync (including one a backend restart lost). Neither `"failed"` nor a `"done"` that still lists no tools is final — a read five minutes later starts a fresh attempt, and the `message` in that case explains what went wrong. It also names `POST /services/{id}/refresh-tools`, but that one needs the service **owner** signed in to the dashboard and answers `401` to an API key, so pass it on to the user rather than calling it. Read `tool_sync` defensively — it can arrive as `{}` with no `status`. Don't report the service as empty and don't `report_tool` — no tool was called |
| `get_service_tools` listed exactly 50 tools, and the one you were looking for isn't among them | Over MCP the tool's `limit` parameter defaults to **50** and the list is cut to that length, with no total, no cursor and no truncation flag to say so — the remaining tools read as tools the service doesn't have. Not an MCP-server quirk: the cut lands before anything branches on service type, and the biggest services are `api` ones (Vercel, 407 tools). Live on 2026-09-20: Higgsfield has 101 tool rows, the default call returned 50 and `limit=200` returned all 101 (nothing clamps what you pass). The REST route takes no `limit` and returns the whole list. A count of exactly 50 is a hint, not proof — a service that really has 50 looks the same — and note `needs_configuration` is derived from the sliced list, so on a larger service it describes only the first 50 | Re-read it with a big `limit` (500 covers every service in the catalog today), or use `GET /services/{id}/tools` over REST, which is already complete. Better still for "can this service do X", `search_tools(query, service_id=…)` — the filtered search reaches the whole service rather than one truncated page (mind its own `limit`, which defaults to 10). Nothing to `report_tool` |
| `needs_configuration: true` and you don't know which fields to ask the user for | The `configuration_required` block answers this: `service_id`, `service_name`, `message`, `configuration_url`, `instructions`, and `credential_schema` | Read `credential_schema` for the field names, labels, help text and eligibility notes, and `instructions` for the list to ask for ("Ask the user for: …"). It is `null` for a service whose credential shape isn't registered — common for plain API-key services — and then it's one key, or send the user to `configuration_url`. Never invent a field name the schema doesn't list. **Check `needs_mcp_oauth` before you ask for anything**, though — see the next row |
| `needs_mcp_oauth: true` from `get_service_tools`, with an empty `tools` list | The service's own MCP server authorizes through OAuth (Coupler.io and Outreach are live examples). Over MCP this comes *with* `needs_configuration: true` and a `configuration_required` whose `credential_schema` is `null`, so it looks exactly like the plain API-key case in the row above; over REST it comes with **no `needs_configuration` key at all**, so a caller testing only that field reads it as "this service has no tools". It appears only while Danube holds no tool rows for the service at all — an OAuth service whose tools are already on record answers with the ordinary list instead (Notion does, with 44 tools and `needs_mcp_oauth: false`), each entry carrying its own per-caller `readiness`, which is the answer for your account | Send the user to `configuration_required.configuration_url` over MCP, or to `https://danubeai.com/dashboard/tools/<service_id>` composed from the `service_id` over REST, where the response carries no URL. The `authorization_endpoint` / `token_endpoint` / `registration_endpoint` in `mcp_oauth_info` are the *provider's* and the dashboard drives them, not you. Don't route around the prompt with `store_credential`: it does not refuse these services, so an improvised token is stored, sent as the connection's bearer, and stops *you* seeing this shape (the credential is per-account, so the prompt is still there for everyone else) — a service that then looks connected and fails every call. Store one only if the user hands you a token their provider actually issued. Read the tool list again after they connect: tools are discovered from the MCP server only once authorization completes, and then by the background first sync two rows above |
| A tool's `reliability.error_classes` is mostly `auth`, or `auth_failures_30d` is large | Those are *other* callers' missing or invalid credentials, which say nothing about the tool. They are left out of `calls_30d` and `success_rate_30d` entirely, so they can't push a tool over the `flagged` line, and `last_error_class` never reports `auth` at all | Not a reason to avoid the tool if *your* account has the service connected — judge it on `success_rate_30d`. That rate is `null` under 10 calls: too small a sample, not a bad tool |
| A tool has a lot of failures in `faults` or the `*_failures_30d` counters, but `success_rate_30d` still looks fine | Since 2026-09-10 the rate is scored on successes plus `upstream` failures only. `caller_failures_30d` (your side of the wire — bad values, missing credentials; `auth_failures_30d` is its credential part) and `danube_failures_30d` (a stale row, a request Danube built wrong) are reported next to the rate and excluded from it, which generalises the older rule that excluded only `auth` | The rate is not hiding anything — it is deliberately answering "does the *provider* serve this tool reliably". A large `danube_failures_30d` is a Danube bug already queued for repair, not a reason to steer the user elsewhere. `faults` gives the `caller`/`upstream`/`danube` split behind the counters |
| `fetch_result` came back shorter than the result you know was stored | The read-back has a cap of its own, defaulting to **50000 characters**: `max_response_chars` on `fetch_result`, `max_chars` on `GET /tools/executions/{id}/result`. The floor is 100 on both; the ceiling is 500000 over MCP and 2,000,000 over REST (the execute call's own ceiling). It trims like any execution response, in the same three modes — a JSON array loses whole elements off the tail (valid JSON of the same shape, simply short, which is exactly what makes it easy to read as the whole answer), plain text is cut mid-string, and an object with no array big enough to trim degrades to `_truncated_partial_json` with its own keys gone. Live on 2026-09-20 against a stored 194-element result: the default fetch returned 32 elements with `truncated: true` on both transports, and `max_response_chars: 500000` returned all 194 with `truncated: false` | Check `_meta.truncated` (top-level `truncated` over REST) before treating a fetched result as complete, then either raise the cap or narrow with `path`. Over MCP that flag is only half the signal: it carries the backend's trim, while the MCP layer silently clamps anything above 500000 to 500000 and re-shapes afterwards — so never ask for more than 500000 there; page with `path` or fetch the handle over REST instead. This is the read-back cap, not the store-time one in the row below: here the stored copy is intact and re-running the tool gains you nothing |
| You are reading a very large result back by `path` and the tail is missing | The stored copy behind an execution handle is capped at 1,000,000 serialised characters — though that cap is rarely what cut, because what gets stored is the already-shaped response: over MCP the backend's own 500000 shaping always binds first (your `max_response_chars` never reaches it), so there the 1,000,000 can never be the limit you hit. Past the cap a JSON result loses whole array elements from the tail at store time (the JSON stays valid and same-shaped, just short); a plain-text result is cut at the limit | Over REST the handle tells you: `stored_truncated: true` plus a `stored_meta` block with the original size and what was dropped. `fetch_result` over MCP does **not** carry those keys, so there you get no signal — don't read a short tail as the upstream having nothing more. Re-run the tool with a narrower request (`fields`, a filter, the upstream's own pagination) rather than paging a capped handle |
| `last_error_class` is `upstream_5xx` (or `upstream_4xx`) and you're deciding whether to retry | The classes are `validation`, `upstream_4xx`, `upstream_5xx`, `timeout` and `other`. Upstream throttling has no class of its own, so a `429` lands in one of the two upstream buckets depending on how the provider worded the message | Don't read `upstream_5xx` as proof of a server fault. Check the tool's own error text before deciding; a throttled tool is worth retrying later, a genuinely broken one is worth `report_tool` |
| `404 Tool not found` | Stale tool ID | Re-run `search_tools` — never reuse IDs from earlier sessions |

Either way it is Danube's own API, not a marketplace tool | Use `GET /v1/tools/{tool_id}/describe`, which works on every backend and needs no key at all. Both routes take a slug or a UUID. The unpaginated contract is the likely reason; the `500` itself is not explained by anything a caller can see. Sent without a key it answers `401` first, as does the bare per-tool route | Don't retry it and don't `report_tool` it. | `404 "No tool with id …"` from `POST /v1/ratings` | The `tool_id` is a well-formed UUID that names no tool — stale, or mistyped a character. Over MCP the refusal arrives flattened into a string with no status to branch on, so read the message there | Re-resolve the tool with `search_tools` / `GET /v1/tools/search` and submit against the `id` on the result. Not a `report_tool` case — no tool was called |
| `error_type: upstream_tool_missing`, with `retryable: false`, `upstream_tool` and `available_tools` (over MCP these are in `_meta` beside `isError: true`; over REST they are body fields on an ordinary `200`, not an HTTP status) | The catalog row routes to a tool its MCP server no longer offers — drift on Danube's side, not a mistake in your call and not a provider outage. ## A tool is broken or returns wrong output

Call `report_tool(tool_id, reason, description)` with `reason` one of
`broken`, `degraded`, `incorrect_output`, `timeout`, `other` — the Danube team
reads these. A rating via `submit_rating` helps other agents too.

Don't check for an existing report first: filing the same `tool_id` + `reason`
again while an earlier report is still open or acknowledged bumps that report's
occurrence count instead of creating a duplicate. Both tools also take a `source`
parameter — leave it unset. It exists to mark Danube's own internal dogfooding
traffic, and setting it on a real report tells the team to discount what you saw.

Pass the tool's UUID as `tool_id`: the MCP `report_tool` and `submit_rating`
tools reject anything else rather than guessing. Look it up with
`search_tools` — and if what you're closing out wasn't a marketplace tool call
at all, just skip the report instead of passing a tool name or a placeholder
string.

`get_my_rating` wants the UUID too, and fails one step later: it has no
client-side guard, so a slug reaches the backend and comes back as HTTP `400`.
Over REST that is the ordinary envelope, `{"error": {"code":
"validation_error", "message": "tool_id must be a tool UUID, got:
'gmail-send-email'"}}`; over MCP the same refusal is flattened into a string —
`{"error": "API request failed with status 400 (Details: {…})", "isError":
true}` — so there is no `error.code` to branch on there. Both live, 2026-09-22.

`get_recommendations` wants it as well and is the one that never complains: a
slug is queried against a UUID column inside a `try` that only logs, and the
same unresolved string is what the endpoint excludes from its own results, so
you get the generic popular list and the tool you asked about recommended back
to you. Live on 2026-09-22, `get_recommendations("supabase-execute-sql")`
returned `Supabase - Execute SQL` at the top of its own list while the UUID
call left it out. A `reason` of `Frequently used together` is a real co-usage
hit; `Popular` is what every caller gets.

Over plain REST the *report* endpoint is the one that does accept a slug —
`POST /v1/tools/{tool_id}/report` resolves either form and stores the resolved
UUID — so the same call is fine over curl and refused over MCP. Send the UUID
and both work.

## `get_tool_ratings` says `rating_count: 0`

Three different things look identical here, and only one of them is "nobody
liked it".

- **The id wasn't a tool UUID.** This endpoint validates nothing: it swallows
  the failed lookup deliberately, so that a public endpoint never `500`s on a
  bad id, and returns `{"avg_rating": null, "rating_count": 0}` for a slug, a
  tool name or a typo — byte for byte what an unrated tool returns. So a zero
  is never confirmation that your id was right.
- **The ratings that exist aren't counted.** The aggregate behind this tool
  counts only ratings whose `source` is `user`; ratings left by agents
  dogfooding Danube are excluded from it. Live on 2026-09-22, `Gmail - Send
  Email` (`6f0c4361-d0cc-45df-8ee6-87b9cc1e0d37`) returned a five-star rating
  from `get_my_rating` and `rating_count: 0` from `get_tool_ratings` on the
  same UUID.
- **It hasn't caught up yet.** It reads a materialized view on a five-minute
  refresh schedule (five minutes is the floor: a run that would overlap the
  previous one is skipped), so a rating submitted moments ago — including one
  you just submitted — is not in it.

None of these is breakage and there is nothing to `report_tool`. Judge the tool
on the `reliability` block that comes free on every search result, and read the
response's real keys, `avg_rating` and `rating_count` — not the
`average_rating` / `total_ratings` the tool's own description names.
