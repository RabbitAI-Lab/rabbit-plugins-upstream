# 项目控制塔机制（Control Tower）
> 用于「单工作空间内多会话协同 + 可追溯 + 动态管理」的约定。
> 配合「秽土转生」技能使用：秽土转生是「细胞分裂」原子操作，控制塔是「神经系统」调度层。

## 〇、存储位置（技能自包含，不依赖外部目录）
**核心原则：可复用技能不应硬编码依赖某个外部目录（如个人的中转目录约定）。跨会话追踪靠「工作空间内部文件 + 平台原生 conversation_search」完成，二者都不碰外部路径。**

- **默认存储（自包含）**：`<workspace>/.workbuddy/control-tower/`
  - `INDEX.md` —— 会话地图 + 代号血缘 + 拆分/归档审计追踪 + SHARED 共享约定（唯一事实源）
  - `handoffs/会话交接_YYYYMMDD_N_主题.md` —— 各卫星会话的交接文档
  - 该目录随工作空间走，可提交/分享，换机器也不丢。
- **跨工作空间/跨设备中转目录（导出/导入用）**：当用户要从工作空间 A 抽出某节点/子树迁到工作空间 B 独立管理（或另一台设备）时，导出的「导出包」默认落到此目录（如用户已配置的个人中转目录），再由 B 用 `导入` 生成独立子树（跨设备则先把包拷到新机器再 `导入 <路径>`）。**这不是跨设备实时同步 hub**——导出包自包含（含产物副本），拷贝即迁移；中转目录仅作 A→B 迁移暂存，不写死在技能逻辑里。
- **首次使用零配置**：新用户安装技能后，**默认即自包含可用**——`CT_DIR` 默认 `<workspace>/.workbuddy/control-tower/`，无需指定任何目录。中转目录仅在用户真正执行「导出」跨工作空间/跨设备迁移时才需要，且默认即为「用户主目录/.edo-tensei/exports」或用户当场指定；**不强制首次安装时选目录**（个人的中转目录只是本人约定，非他人必填项）。
- **新会话带入上下文的两条路（均不依赖外部目录）**：
  1. 读工作空间内的 `INDEX.md` + 自己的交接文档（本地文件，新会话立即可见）；
  2. 用平台原生 `conversation_search(query)` 从**服务端历史**直接捞回已归档父会话的深层内容（连文件都不需要）。
- **"创建新会话"是用户动作**（当前无程序化建会话工具）：技能只负责"预备交接文档 + 在 INDEX 登记"；新会话首条启动提示词负责"读取 INDEX + 交接文档，必要时 conversation_search 父会话"。

## 一、为什么需要控制塔
当一个开发会话混入了需求整理、头脑风暴、代码修改、音乐美术素材等多个子任务，上下文越滚越大：
- 单纯归档/秽土转生只能「瘦身」，不能「分诊」——多个子任务仍被笼统丢进一个后继会话；
- 拆出多个卫星会话后，缺少一个「总知/总览」来知道「现在有哪些会话、各自负责什么、谁依赖谁」；
- 原重会话归档后，若没有登记，未来的你无法追溯「这段产物当初属于哪个子任务」。

控制塔机制解决这三件事：① 分诊拆分；② 总览管理；③ 全链路追溯。

## 二、角色定义（同一工作空间内，结构不变）
1. **控制塔会话（master / 总览）**：常驻、轻量。只维护「会话管理总览」文档，不做重活、不产生大量产物。你的 `支付宝智能体` 项目里 `会话交接_…_7_会话管理总览.md` 就是这个角色。
2. **卫星会话（satellite）**：每个聚焦一个子任务（需求 / 代码 / 素材…）。
3. **归档会话（archived）**：过重或已完成的会话归档，但仍被总览引用，可随时回看。
4. **中转站**：所有交接文档、产物清单、总览文档的物理存放地（跨会话唯一权威）。沿用你已有的 `会话交接_YYYYMMDD_N_主题.md` 命名。

## 三、代号 / 血缘规则（一眼看清从哪来）
- 根会话：`R0`
- 首轮拆分：`R0-A` `R0-B` `R0-C`
- 对 R0-B 再拆分：`R0-B1` `R0-B2`
- 规则：前缀是「父代号」，后缀是「本次拆出的序号」。血缘在代号里可见。
- 实现方式：在「会话管理总览」里给每行加「代号」列；文件名仍用你的 `N_主题` 习惯，代号仅用于索引内关联。

## 四、动态管理流程
1. **建控制塔**：开一个轻量会话，产出 `会话交接_YYYYMMDD_7_会话管理总览.md`（或更高序号的总览），作为唯一事实源。
2. **分诊拆分（重会话 → 卫星）**：
   a. 在重会话里按「子任务拆分交接清单」梳理子任务边界；
   b. 为每个子任务生成独立交接文档 → 落 `中转站/会话间交接材料/`；
   c. 归档重会话；
   d. 在总览登记：新增对应行 + 拆分历史一行。
3. **卫星过重 → 就地再审拆（递归秽土转生）**：
   a. **就地拆分**：在哪个会话变重，就在哪个会话里执行 `转生`——因为它持有「拆分前的完整实时上下文」，父会话/R0 早已归档、拿不到这些新内容，控制塔会话只懂索引不懂业务细节。
   b. 拆分前先跑「路由检查」：查 INDEX 现有会话职能，能合并进现有会话的就不新建（见第十节）。
   c. 原卫星归档；新拆出的孙子会话按 `R0-B1/R0-B2` 代号登记。
   d. 回总览更新索引（状态、下游、拆分历史）。
4. **新会话启动铁律**：首条消息先读「会话管理总览」，确认自己的代号/上游/下游，再开工（见升级版启动提示词）。
5. **合并/收口**：某子任务完成 → 总览标「已完成」→ 归档；需要汇总时由控制塔拉通。

## 五、可追溯性来自哪里
- **总览里的「拆分 / 归档历史」** 是审计追踪，每一次拆分/归档都留痕（时间 + 动作 + 代号）。
- **中转站里的交接文档** 是内容溯源，每个卫星会话的来龙去脉都有文档。
- **代号血缘** 让你不看文档也能猜出关系。

## 六、与秽土转生的关系
- 秽土转生（待你实测后生成）= 原子操作：取重会话 → 抽交接 → 归档 → 生后继。
- 控制塔机制 = 编排层：决定「何时拆、拆成几个、谁来管」，并把结果登记进总览。
- 两者正交：没有控制塔，秽土转生也能用（只是容易失联）；有了控制塔，多会话项目不会散架。

## 七、何时真正需要控制塔
- 单会话 > 1 个子任务且会持续演化 → 需要。
- 只是「一次重会话瘦身后不再拆」→ 直接秽土转生即可，不必建塔。
- 经验法则：当你开始问「我上次那个代码会话现在在哪、和素材会话啥关系」时，就该建塔了。

## 八、技能打包：一个技能包「秽土转生」，5 个用户动词
不必拆成 N 个技能，做成**一个技能包「秽土转生」**，用触发词分发。为把用户感知复杂度压到最低，**只暴露 5 个动词**（转生/接管/导出/导入/设置），其余流程全部内嵌自动化（SKILL.md 用触发词分发，写操作前都有提示词交互确认边界）。

**用户主动指令（5 个，各管一件事、零重叠）：**
- **`转生` (rebirth)**：在「变重的那个会话」里唤起，做**同空间就地拆分**。技能**先产出「拆分计划草案」**——扫描子任务自然分界，**推荐 N 个候选子会话**，每个候选带「建议主题名 + 由技能统一分配的建议代号(R0-A…) + 建议依赖边 + 是否命中现有会话(命中则标『将并入 X』)」。**草案经用户确认/改写后才写盘**（可重命名、增删候选、指定「只拆出某块」、或把某候选改并入现有会话，尊重自定义节点）。确认后一次性自动：① **前置断言·确保已登记**——若工作空间无 INDEX，先**自动单会话接管**（建塔、当前会话定 R0）再拆；若 INDEX 存在但本会话未登记，先轻量登记本会话再拆（绝不要求用户先手动跑接管）；② 跑依赖检查(破死锁)；③ 跑路由检查(命中现有职能就合并投送、不新建)；④ 生成交接文档 + 启动包(各带目标节点标识、落盘 handoffs/)；⑤ 更新 INDEX(血缘+审计)；⑥ 自动对账(含归档同步)。—— 原 `init / solo / split / merge / deps / bootstrap` 全部作为内部原语吞进这一个动词。
  - **个数逻辑**：草案候选数 = 检测到的独立子任务数；若仅 1 个主题则退化为「单会话瘦身」(出 1 个后继)，不硬拆。
  - **命名逻辑**：主题名由技能据上下文拟、用户可在确认时改；代号由技能在中央仲裁下分配并立即写 INDEX，用户不发明代号（避免 G5 撞码）。最终「名字=用户确认的主题名，代号=技能分配」，二者都记进 INDEX。
- **`接管` (onboard)**：针对「已存在多个会话的工作空间」做**同空间存量纳管**——发现（`conversation_search` + 用户确认）→ 建塔并轻量登记（legacy 叶子）→ 启发式推断依赖 DAG → 进入标准管理。详见第十三节。
- **`导出` (export)**：把当前工作空间某段结构（节点+handoff+产物副本）打包成**自包含可移植包**，用于**跨工作空间 / 跨设备**迁移。支持「单节点 / 子树(默认) / 整塔」三档范围；包内**复制产物文件副本**并内嵌 `PROVENANCE.json`（记录本次导出溯源、不含技能作者名）；落盘目录三级优先级（显式指定 > `config.yaml:export_dir` > 主目录/.edo-tensei/exports）；语义**复制不移动**。
- **`导入` (import)**：把导出包在目标端落成独立子树。无参扫默认目录列包选（同设备便捷）/ `导入 <路径>`（跨设备）/ `--namespace 前缀` 自定义；产物副本落**命名空间子目录**，禁止指向/覆盖原路径，与源零污染、各自独立。详见第十四节。
- **`设置` (config)**：查看/修改技能配置，免去手工改文件。如 `设置 export_dir <路径>` 写入并持久化 `config.yaml`；`设置`（无参）打印当前配置；`设置 export_dir reset` 退回默认。

**指令两层模型（用户指令 1:N 组合内部原语）+ 权限隔离：**
- **用户指令层（唯一可输入）**：`转生` / `接管` / `导出` / `导入` / `设置`（及别名 `rebirth` / `onboard` / `export` / `import` / `config`）。
- **技能原语层（内部能力，用户不可直调）**：建塔(build_tower)、分析(analyze)、提案(plan)、依赖检查(dep_check)、路由检查(route_check)、生成交接(gen_handoff)、生成启动包(gen_bootstrap)、更新索引(update_index)、对账(reconcile)、发现(discover)、登记存量(register_legacy)、推断DAG(infer_dag)、导出包(export_package，含 collect_artifacts / write_provenance)、导入包(import_package，含 land_namespaced)、配置读写(set_config / get_config)。
- **映射（随 SKILL.md 维护）**：
  - `转生` = build_tower → analyze → plan → dep_check → route_check → gen_handoff → gen_bootstrap → update_index → reconcile
  - `接管` = discover → build_tower → register_legacy → infer_dag → dep_check → reconcile
  - `导出` = read_index → select_scope → collect_handoffs → collect_artifacts → write_provenance → export_package
  - `导入` = scan_or_read_package → build_tower(若需) → land_namespaced → register_subtree → update_index → reconcile
  - `设置` = get_config / set_config
- **权限隔离规则**：
  1. SKILL.md 触发词表**只暴露用户指令层**，不把原语名注册为可触发命令；
  2. 若用户输入原语名（误输），技能识别后**提示「请用 转生 / 接管 / 导出 / 导入 / 设置」并忽略该调用**，绝不越权写 INDEX，避免状态错乱；
  3. 原语仅由用户在跑上述动词时、由技能按既定顺序内部调用，用户无法插入/跳步；
  4. 未来增删原语只改映射与内部实现，**用户指令面不变**。

**技能内自动流程（用户不单独唤起，全部内嵌于对应动词）：**
- **建控制塔 (init)**：首次「转生 / 接管」时若工作空间还没有 INDEX，自动建好并定根代号 R0。对「从未接管、直接输转生」的会话，这一步即「自动单会话接管」——把当前会话定 R0 再进入拆分，用户无需先手动跑接管。**接管须幂等**：若 INDEX 已存在，仅在缺失处增量登记，绝不重建/覆盖。
- **依赖检查 (deps)**：「转生」内部对 INDEX 的 DAG 拓扑排序；发现环立即中止并给破环建议。
- **合并投送 / 路由 (merge)**：「转生」生成卫星前先查 INDEX——某段待拆内容若命中现有会话职能，就并入该会话（追加续接交接），不新建平行会话；防重复/防孤儿会话。
- **生成启动包 (bootstrap)**：「转生」拆出 N 个卫星后自动顺带输出 N 段自包含、读盘不挂附件的启动提示词；平台支持自动建会话时同一份 payload 直接注入。
- **产物副本与溯源 (export)**：「导出」内部 `collect_artifacts` 复制节点关联产物进包、`write_provenance` 写 PROVENANCE，确保包自包含、可跨设备、且不含技能作者名。
- **命名空间落盘 (import)**：「导入」内部 `land_namespaced` 把产物副本解到命名空间子目录，杜绝跨空间原路径直读/直写污染。
- **归档同步 (archive-sync)**：每次对账时自动比对「INDEX 登记状态」与「平台真实会话状态」——包括你用**原生归档按钮**直接归档的会话。
- **盘点对账 (reconcile)**：自动发生。每次「转生 / 接管 / 导入」后做局部对账；会话启动时若检测到 INDEX 与平台状态可能脱节（如你手动归档过），自动问「要跑一次全量对账吗？」——回车即跑、不回车跳过，零负担。

> **归档的正确姿势**：优先直接用平台「原生归档按钮」归档会话，技能在对账时自动把 INDEX 对齐——不必走专门指令。这样归档动作最顺手，地图也不会丢。

优势：用户只装一个技能、只需记 **转生 / 接管 / 导出 / 导入 / 设置** 五个动词；模式共享同一套 INDEX 与约定；升级只改一个包；内部原语全部吞进动词自动化，感知复杂度最低；用户不可直调原语，权限隔离防错乱。

### 扩展埋点（为平台演进预留，能力检测而非硬编码）
- **EXT-1 自动建会话**：检测到「创建会话+注入首条消息」工具时，`bootstrap` 由「输出文本」升级为「直接建并注入」，「转生」拆出 N 个卫星即自动建 N 个窗口；payload 两路共用。
- **EXT-2 生命周期事件**：平台暴露会话归档/删除事件钩子时，归档同步由「手动 reconcile」升级为「事件自动触发」。
- **EXT-3 平台状态 API**：平台提供会话状态/末次修改查询时，漂移检测由「手动触发」升级为「近实时」。
- **EXT-4 跨工作空间 / 跨设备导出导入**（见第三、七、十四节）：由专用 `导出`/`导入` 动词承载，包自包含、可移植，覆盖同设备跨工作空间与跨设备两种场景。
- **EXT-5 多空间聚合**：未来可在 hub 层加「根索引」，跨空间聚总览（当前单空间已自洽，留接口不实现）。
- 演进原则：只在「平台能力存在」时升级体验，绝不因平台没能力而报错；所有自动流程保留「降级到人工」退路。

## 九、防工作空间污染原则（重要）
- **技能存放位置**：用户级技能在 `~/.workbuddy/skills/`（所有工作空间可用）；项目级在 `<workspace>/.workbuddy/skills/`（仅本空间）。建议做成**用户级**（一次安装处处可用），但**操作永远只作用于「当前工作空间」**。
- **绝不硬编码跨空间路径**：INDEX / handoffs 一律用当前工作空间内的相对路径 `.workbuddy/control-tower/`，不写死到某个外部目录或别的 workspace。
- **作用域锁定**：技能被调用时，只读取/写入「当前会话所在工作空间」的文件系统；每个 workspace 自带独立 INDEX，互不串。WorkBuddy 的工具调用本就限定在当前 workspace，因此天然隔离。
- **跨工作空间中转是显式动作而非默认**：只有用户主动 `导出` → `导入` 时才跨空间；中转目录仅作 A→B 迁移暂存，默认不开启任何后台同步，确保零污染。
- **写操作前确认**：涉及归档 / 删除 / 跨文件移动，先列清单确认，不自动跨空间。
- 结论：污染风险来自「写死绝对路径 + 跨空间读写」，二者都在本设计中规避，故用户级全局安装也安全。

## 十、再拆分 / 孙子会话 / 合并路由模型（关键精修）

### 核心前提：状态在文件、不在会话
- 控制塔的「唯一事实源」是工作空间里的 `INDEX.md` 文件，**不是某个会话本身**。
- 所谓「父会话 / 控制塔会话」只是「负责维护 INDEX 的角色」；它可以被归档、甚至可以不存在——因为状态在文件里，不在会话里。
- 推论：任何会话（父、子、孙、甚至全新会话）只要读到 `INDEX.md`，就拥有了完整的「全项目会话地图 + 血缘 + 审计」。因此**孙子会话天然接入顶端管理**，无需父会话在线传话。

### Q1：再拆分时，指令在哪个会话执行？
- **规则**：在「当前正在变重的那个会话」里执行 `转生`。
- **理由**：只有该会话持有「拆分前的完整实时上下文」（它自己这几十轮的对话、产物）。父会话/R0 早就被归档了，拿不到这些新内容；控制塔会话只懂索引、不懂业务细节。
- 链路示例：
  - R0 变重 → 在 **R0** 里拆 → 出 R0-A/B/C（R0 归档）
  - 后来 R0-B 变重 → 在 **R0-B** 里拆 → 出 R0-B1/B2（R0-B 归档）
- 永远「就地拆分、就地归档」，不存在「父会话替子会话拆」。

### Q2：孙子会话怎么接入顶端管理？
- 它出生就带代号 `R0-B1`，而 `INDEX.md` 里这行写着：上游 R0-B、再上游 R0。**代号即血缘**。
- 启动提示词第 0 步强制它先读 `INDEX.md` → 立刻知道：我是谁、我爸爸是谁、我爷爷是谁、我还有哪些兄弟姐妹。
- 「顶端管理」= `INDEX.md` 这份文件，谁都能读。所以不需要一个常驻的「父会话」在线上传话——这正是「状态在文件」带来的解耦。

### Q3：拆分内容其实已有对应子会话 → 合并而非新建（转生内部自动路由投送）
- 这是最容易长「孤儿会话」的坑：R0-B 里冒出一块素材需求，结果它和已存在的 R0-C 职能重叠，若直接拆就会变成两个平行会话、内容分叉。
- **解法：拆分流程里加一道「路由检查」**：
  1. 拆分前，先从 `INDEX.md` 取出所有现有会话的「负责子任务 / 职能范围」。
  2. 对要拆出的每一块内容，判断：是否已有某现有会话覆盖该职能？
     - **是 → 路由投送（转生内部自动）**：把这块内容并入那个现有会话（追加一份「续接交接」，在 INDEX 该会话行记「续接于 YYYYMMDD」），**不新建会话**。
     - **否 → 新建**卫星/孙子会话，代号 = 当前会话代号 + 新序号。
  3. 这样就不会出现功能重叠的平行会话。
- 合并的两种情形：
  - 目标子会话仍活跃 → 直接把内容续接到它，下一个回合就在它里面继续。
  - 目标子会话已归档 → 追加一份 `会话交接_YYYYMMDD_N_主题_续接.md` 作为该会话的续篇，INDEX 里在该会话行加「续接链」，需要时从 INDEX 拉起继续；**不新建独立会话代码**。
- 此路由动作已内嵌于「转生」，不再作为独立指令（见第八节）。

### 完整决策流（伪代码）
```
某会话变重，要拆分：
  1. 在【当前会话】执行 转生
  2. 技能先读 INDEX，列出所有现有会话职能
  3. 对每块待拆内容：
       if 命中现有会话职能 → 路由投送（合并，不新建，转生内部自动）
       else → 新建卫星/孙子，代号 = 当前会话代号 + 新序号
  4. 生成交接文档（新建的落 handoffs/，合并的追加到目标会话）
  5. 归档当前会话
  6. 更新 INDEX：新增行（孙子）/ 标记续接（合并）/ 拆分历史留痕
  7. 提示用户：按新会话启动提示词开新会话；合并的回到现有会话继续
```

### 一句话收口
**就地拆分（就地归档）、状态在文件（不在会话）、拆前先路由（能合不建）。** 这三句就是「无限递归拆分也不散架、不重复、始终可追溯」的保证。

## 十一、跨会话依赖 / 状态一致性（把会话当「多应用共享数据库」来治理）

### 你的类比完全正确
多会话并行 = 多个应用同时读写同一份「项目真相」；用户 = 事务协调器 / 消息总线；INDEX.md = 那张被共享的表。脏读、游离态、脏写、死锁，本质都是**缺少并发控制与事务边界**。下面用数据库套路补齐。

### 1. 单一真相源 + 显式状态机（消灭「游离态」）
- 在 INDEX 给每个会话 / 每个交付物定义**唯一状态枚举**（不要让它停在模糊的「进行中」）：
  `待启动 / 进行中 / 已完成待验收 / 已验收 / 阻塞(等待X) / 已归档`
- 关键：`阻塞(等待X)` 是一等状态——被依赖卡住的会话不是「含糊地进行中」，而是明确写着「我在等 R0-C 的提示词」。游离态消失。
- `已验收` 才是「已落库、可被消费」的状态（见两阶段提交）。

### 2. 依赖关系 DAG（声明依赖，杜绝隐式耦合）
- INDEX 新增「依赖关系」节，显式登记边：消费方 ← 提供方（交付物）。
  ```
  R0-B ← R0-C（素材提示词.md）
  R0-A ← R0-B（assets/* 素材）
  ```
- 谁依赖谁一目了然；同级会话不必互相打听——它们只看 INDEX（控制塔只是给人看的视图，真相在文件）。

### 3. 两阶段提交（跨会话交付物的事务边界）
1. **生产方**完成交付物 → 写交付物文件 → INDEX 标记该交付物 = `已完成待验收`（已提交、未确认）。
2. **用户**复核 → 翻 `已验收`（或打回）。**只有 `已验收` 才允许被消费**——这就是「读已提交」隔离，脏读被挡在门外。
3. **消费方**启动时重读 INDEX：上游全是 `已验收` 才动手、引用交付物文件路径；否则自动转 `阻塞(等待X)`。
- 用户的搬运被压缩到最小：**只传「文件名/路径」，不传内容正文**。

### 4. 死锁检测与破环（转生内部自动跑依赖检查）
- 「转生」内部对 INDEX 的 DAG 做拓扑排序（依赖检查）。若出现环（A←B←A）→ 立即中止并建议破环（常见解：把循环部分抽成一个新的公共子会话 R0-E，让双方都依赖它，环即断）。
- 排程阶段先跑它，从架构上消灭死锁，而不是等到运行时卡死。

### 5. 就绪队列 / 下一步行动看板（让用户知道「下一步干啥」）
- 控制塔按「上游全 `已验收` 且自身 `待启动/阻塞`」推导「可启动队列」，输出看板：
  | 现在该启动 | 触发条件 | 给它什么 handoff |
  | R0-B | R0-C 已验收 | 交 `会话交接_…_提示词.md` |
- 用户照表执行即可，不必自己推理依赖。相当于调度器的 runnable queue。

### 6. 一致性对账（会话盘点，弥补「总理无法自动获取进度」）
- 会话确实不能自动轮询彼此——这是平台硬约束，用户是总线。
- **权威对账渠道**：先读 `~/.workbuddy/workbuddy.db` 的 `sessions` 表拿平台真实 `status` / `deleted_at` / `title` / `project_id`（见第十三节前置步骤），**再**用文件时间戳做交叉验证；不要只靠 handoff 文件的 mtime 猜状态。
- 补偿：总理会话跑 `会话盘点` 时，**重读所有 handoff 文件 + INDEX，重算每个会话有效状态并比对登记值**，列出「状态漂移」：
  - INDEX 记 R0-B「进行中」但交付物 3 天没改 → 提示核实；
  - R0-C 标「已验收」却找不到验收记录 → 提示脏写。
- 这是「最终一致 + 周期性对账」，把漂移在盘点时暴露，而非一直错下去。

### 7. 用户作为总线的「最小动作集」
把人的搬运降到最低，只剩两步：
1. 复核交付物，翻 `已完成待验收 → 已验收`；
2. 打开看板里「可启动」的会话，贴入 handoff 文件名。
没有大段文本来回拷贝；内容只在文件里流动，人在中间只做「确认 + 指路」。

### 收口
把会话当数据库治理：**单一真相源(INDEX) + 显式状态机(无游离态) + 依赖DAG(显式耦合) + 两阶段提交(读已提交) + 拓扑排序破死锁 + 就绪队列(调度) + 周期性对账(最终一致)**。七件套齐了，多会话并行就不会再脏读脏写、游离态、死锁——只剩「用户做确认与指路」这一道必要的人工总线。

## 十二、新会话初始化便捷化（人工建会话也能很轻）

### 现实约束
当前平台通常不提供「程序化创建会话」的工具，**新会话的创建 + 首条上下文注入是人工动作**。技能要做的，是把这个人工动作压缩到「开窗口 → 粘贴一段 → 回车」三步，而且**不需要手动挂文件、不需要重贴长文**。

### 关键设计：启动块自包含（读盘而非挂附件）
把「新会话启动提示词」从「要求用户上传交接文档」改为「指示新会话**直接从同一工作空间磁盘读取** `INDEX.md` 与自己的 `handoffs/会话交接_….md`」。因为新会话与源会话同属一个 workspace，文件天然可见——这样省掉了附件步骤，用户只需粘贴一段话。

### 转生自动输出：启动包（原 `生成启动包`）
- 在「转生」拆分/规划会话时自动输出；技能读 `INDEX.md` + 该代号的交接文档，输出一段**单块复制即用的启动提示词**，内含：
  - 项目名 + 本会话代号 + 负责子任务；
  - 上游/下游（来自 INDEX）；
  - 两条磁盘读取路径（`INDEX.md` 与自己的 handoff 文件）；
  - 约束（保持轻量、验收即归档、走两阶段提交等）。
- **用户操作（挂载 = 粘贴启动包）**：复制该块 → 新开会话 → 粘贴 → 回车。新会话自动读盘继承上下文，**零附件、零长文拷贝**。每段启动包**自带目标节点标识**（代号 + 主题名 + 磁盘路径），多新会话并发时各包自述身份、各挂各自节点，**无需用户人肉指定「挂到哪个节点」**。
- **落盘可重取**：每段启动包同时写入 `handoffs/启动包_代号.md`，若丢失或需重挂，直接复制该文件即可；**勿在既有节点重复跑「转生」**（会触发再拆分）。
- **批量模式**：「转生」拆出 N 个卫星后，自动顺带输出 N 段启动包（R0-A / R0-B / R0-C 各一块），用户开 N 个窗口依次粘贴即可。

### 自动模式（若未来工具支持）
设计上把「输出启动包」与「自动创建并注入」做成**同一份 payload 的两种消费方式**：
- 若平台开放「创建会话 + 注入首条消息」API → 「转生」在生成 handoff 后**自动调用创建会话并注入启动包**，人工只做复核；
- 若无该 API → 降级为输出启动包文本，人工粘贴。
技能逻辑无需重写，只是消费端切换。

> 配套改动：见 `会话交接模板/新会话启动提示词.md`（已升级为「读盘自包含」版本）。

## 十三、存量多会话纳管（已散落多个会话的工作空间怎么接管）

### 场景
工作空间下已经散落了多个会话（很久前裸跑、没走控制塔），现在想引入技能统一管理，而不是从头拆。

### 前置步骤（强烈建议先做）：读「权威会话台账」
WorkBuddy 桌面端的本地 SQLite 就是**平台真实会话台账**，含真实标题与状态——远比 `conversation_search` 的摘要推断可靠。**2026-09-17 实测教训：搜索工具会为同一个会话的不同话题片段各生成一条摘要，看上去像多个独立会话 → 据此推断会话结构会整段错（曾把 4 个现存会话误判为「已删除」）。**

- 库文件（跨平台）：`~/.workbuddy/workbuddy.db`（Windows 实际为 `C:\Users\<用户>\.workbuddy\workbuddy.db`）
- 表 `sessions`：`id`（＝conversation_id）/ `cwd`（所属本地目录）/ `title` + `custom_title`（侧栏真实名）/ `status`（`working`｜`completed`｜`archived`｜`error`）/ `deleted_at`（非空＝已删除）/ `project_id`（属某「项目」时非空）/ `created_at` / `last_activity_at`
- 表 `workspaces`：本机登记的工作空间目录（`path` / `last_opened_at`）——**工作空间＝本地目录，全局唯一**，与「项目」是两回事
- 只读打开、绝不写：`sqlite3.connect("file:<路径>?mode=ro", uri=True)`（WAL 未落盘时也能读；文件可能正被客户端占用）
- 用法：
  ```sql
  SELECT id, title, custom_title, status, deleted_at, project_id
  FROM sessions WHERE cwd LIKE '%<工作空间目录>%' ORDER BY last_activity_at DESC;
  ```
  这一步直接给出「真实会话名 + conv id + 平台状态 + 归属项目」，是建塔与后续 `会话盘点` 对账的**唯一权威来源**。
- 「项目（Project）」侧：`~/.workbuddy/project-resources/<project_id>/` 存该项目级资源（如 `mcp.json`）。`status='archived'` 才是平台归档；`deleted_at` 非空才是已删除，**二者别混**。
- 平台**没有**归档入口的会话（如某些项目成员会话）：经用户明确授权后可记 `已归档（标记）`，效力等同已归档，但**必须写明平台侧实际状态**，不得含糊。

### 指令：`接管`（onboard），分四步
1. **发现（Discover）**
   - **先读本地 SQLite 台账**（见上方前置步骤），拿到真实名单 / conv id / 平台状态；
   - **再用** `conversation_search(项目关键词)` 从**服务端历史**召回内容与上下文，用于补摘要（**不可用其条数推断会话个数**）；
   - 同时请用户确认/补充「还有哪些会话属于本项目」，避免漏网；
   - 技能汇总去重（**以 conv id 去重**，不以摘要主题去重），得到「待接管会话清单」。
2. **建塔 + 轻量登记（Lightweight Register）**
   - 在当前 workspace 创建 `INDEX.md`（根代号 R0）；
   - 每个已存在会话登记为一行，**代号用 `R0-1 / R0-2 …` 顺序（或用户指定语义码）**，类型标 `legacy`（存量）；
   - 状态按状态机枚举估填（多为 `进行中` / `已归档` / `阻塞`）；
   - **不强制立刻生成详细 handoff**——只填「负责子任务(摘要) + 产物路径(若已知) + 一个 `conversation_search` 检索串」。详细交接文档**懒生成**：仅当该会话之后要被归档/拆分时，才对其跑「转生」产出完整 handoff。
   - 这样接管几乎零成本：不动旧会话、不逼用户逐一轮查。
3. **关系推断（Infer DAG）**
   - 技能基于各会话主题/产物做启发式建议：哪些会话存在依赖（如「素材」类通常是「代码」类的上游），在 INDEX 依赖节给出候选边，由用户确认/修正；
   - 由「接管/转生」内部自动跑依赖检查，确认 DAG 无环。
4. **后续正常管理**
   - 接管完成后，该工作空间即进入标准控制塔状态——哪个会话变重就在哪拆、拆前先路由、跨会话交付走两阶段提交、定期 `会话盘点` 对账。

### 与「单会话增量引入」的对比
| 引入方式 | 起点 | 动作 | 旧会话命运 |
|---|---|---|---|
| 单会话增量引入 | 一个重会话 | 「转生」自动建塔 → 原会话作 R0 → 拆出卫星 → 原会话归档 | 原会话被拆分归档 |
| 存量多会话纳管 | 已有 N 个散落会话 | 「接管」把**已有会话直接登记为 R0 下的 legacy 叶子** → 补 DAG → 进入标准管理 | 原会话都不必动（已是成品/半成品），只补一层索引 |

### 用户操作步骤（以存量 A/B/C 三个会话为例）—— 直接照做

**Q：应该新开 D 在 D 里接管？还是先在 A/B/C 各自建索引再开 D？**
**A：只开一个 D（控制塔/master 会话），在 D 里一次性 `接管` 即可。** 不必在 A/B/C 里分别跑技能——接管依赖 `conversation_search` 直接从服务端历史把 A/B/C 的上下文"拉回来"建索引，是**「自上而下」的集中接管**，不是「各自先建再汇总」。

具体步骤：
1. **新开会话 D**（轻量，几乎不产生产物；它就是"控制塔会话"这个角色。注：状态在文件不在会话，所以 D 之后可归档，INDEX.md 仍持久）。
2. **在 D 调用 `接管`**：
   - 技能用 `conversation_search("项目关键词")` 召回 A/B/C 的服务端历史摘要；若召回不准，你直接告诉它 A/B/C 的代号/主题即可；
   - 列出候选清单让你确认 / 去重。
3. 技能在当前 workspace 生成 `INDEX.md`：根 R0 + `legacy` 叶子 `R0-1(A)` / `R0-2(B)` / `R0-3(C)`，填摘要 / 产物路径 / 检索串；并给出依赖候选边。
4. 你确认依赖边、由「转生/接管」内部自动跑依赖检查查环 → **接管完成**。

**Q：接管后 A/B/C 怎么办？要全归档吗？**
**A：不用全归档，也不建议立刻归档。** 纳管只是"登记建档"，不改变 A/B/C 的运行状态：
- A/B/C **继续正常工作**，只是现在有了一张"地图"可查；
- 只有当它们各自进入**终态**时才按需处理：
  - 某会话已完工 → 用平台「原生归档按钮」归档，技能对账自动同步 INDEX 标 `已归档`；
  - 某会话又变重（堆了很多产物）→ 在**那个会话里**跑 `转生` 拆分并归档它自己，INDEX 登记新卫星；
  - 有新任务 → 直接开新会话，由「转生」自动输出启动包注入，INDEX 登记新代号。
- 一句话口诀：**建档不拆家，按需再处理。**

### 收益
存量工作空间无需推倒重来，引入技能后立刻从「散沙」变「有地图、有依赖、可追溯」。之后无论是继续拆某个 legacy 会话，还是新开会话接入，都按同一套规则走。

## 十四、跨工作空间/跨设备迁移：导出/导入包（非同步 hub）

### 为什么不是「同步 hub」
G3 决议已明确：跨设备（pc-pc / pc-手机 / 云端会话）不需要实时同步——状态随文件走、接管可重建。唯一需要「在另一个工作空间取到本空间内容」的场景，是**跨工作空间迁移**（同设备下从 A 工作空间迁到 B 工作空间，或拷到另一台设备），此时 B 读不到 A 的本地 control-tower。这不能用「同步」解决，而要用**显式导出/导入**。

### 专用动词、零歧义
- `导出` = 出：把 A 的某段管理结构（节点 + handoff + 关联产物副本）打包成自包含导出包；
- `导入` = 入：把导出包在 B 落成独立子树（带命名空间前缀，绝不引用 A 原路径）。
- 高频的「同空间拆分」永远走 `转生` 裸词，`接管` 只管同空间纳管——跨空间与同空间动词彻底分离，绝不互相误触发。

### 两个子场景
1. **B 已有自己的控制塔（禁止覆盖式接入）**：默认禁止把 A 直接并进来乱掉 B。合规路径：`导出 <节点/子树>` 导出 A 的子树 → 到 B 用 `导入` 作为**带命名空间前缀的隔离子树**（如 `B-R0-A2…`），不动 B 原有节点。
2. **B 是新的（从 A 抽细分独立管理）**：`导出 <节点/子树>` → 导出包落中转目录（默认用户主目录/.edo-tensei/exports，或个人已配置的中转目录）→ 在 B 用 `导入 <包>` 生成全新独立子树。导出的包内嵌 `PROVENANCE.json` 仅作审计留痕；**导入后 A 原节点与 B 子树无实时关联，各自独立发展**。

### 导出包内容（自包含、复制不移动）
- INDEX 子树（或单个节点行）+ 其引用的 handoff 文件；
- **节点关联的产物文件副本**（复制本体进包，而非只留路径指针）——防污染关键：
  - **来源（合并去重）**：① INDEX 会话地图选中节点的「**产物清单**」列（机器可解析、分号分隔的路径，由 LLM 导出前补全登记，**主来源**）；② `--artifacts` 显式追加；③ 从 handoff 文本启发式兜底。
  - **落位规则**：workspace 之内 → 保持相对目录 `artifacts/<相对路径>`；workspace 之外（跨盘/跨目录）→ `artifacts/_external/<盘符>/<原路径>`，**杜绝跨盘 `relpath` 崩溃与 `..` 逃逸**，导入端原样还原。
  - **技能自身文件不迁移**：凡落在 `.workbuddy/skills/` 或 `.workbuddy/plugins/` 下的文件（技能靠「安装」获取，不靠迁移）一律自动跳过并提示，不会误带进包。
- `PROVENANCE.json`：skill_id / skill_version / exported_by / source_workspace / source_node / exported_at / package_content_hash / scope（仅记录本次导出事件溯源，**不含技能作者名**）；
- 物理形态：一个 zip + 中转目录，而非常驻 hub。

### 默认中转目录（三级优先级）
- ① 当场显式指定（如「导出到 D:\xxx」）；
- ② 用户个人配置 `export_dir`（由 `设置` 指令写入，落用户主目录 `~/.edo-tensei/config.yaml`，不随技能包发布；出厂 `config.yaml` 仅含默认说明）；
- ③ 零配置默认 `用户主目录/.edo-tensei/exports/`。
- **他人首次安装（共享技能）**：**无需任何配置**——默认即「用户主目录/.edo-tensei/exports」或当场指定；个人中转目录只是本人约定，不是他人必填项；技能默认自包含、零配置上手。
- 比「持续同步 hub」简单，且天然规避跨空间污染（见第九节）。

### 十四·附：导入端必须处理顶层文件（full 深度包陷阱）

#### 现象
导出 在 context_depth=full 时会在包内生成顶层 CONTEXT_DIGEST.md（它不落在 handoffs/、artifacts/、INDEX.excerpt.md 任一已知分支下）。早期 import_package.py 的 landed_of() 只认 INDEX.excerpt.md / handoffs/ / artifacts/，其余文件被静默丢弃——导致两个后果：

- full 包导入后 CONTEXT_DIGEST.md 不落盘（整段 context 摘要丢失）；
- 逐文件校验因「期望有、实得无」误报 存在差异 ✗，尽管包内容其实完整无损。

#### 修复（已落事实源）
landed_of() 改为：其余文件（含 full 深度的顶层 CONTEXT_DIGEST.md）按原名落命名空间根 `<ws>/<prefix>/`；并加安全护栏——当 `os.path.isabs(rel)` 或 `rel` 含 `..` 路径段时返回 `None`（拒绝绝对路径与 `..` 逃逸），避免包内异常/恶意路径写穿工作空间。

#### 回归判据
- full 包导入后须存在 `<prefix>/CONTEXT_DIGEST.md`，且其 sha256 与 `PROVENANCE.files["CONTEXT_DIGEST.md"]` 一致；
- 哈希校验须报 `逐文件校验全部通过 ✓`，不再误报「存在差异」。

#### 纪律联动
任何改动 `scripts/` 或 `references/` 的提交都会改变 SEAL 指纹 → 发布前必须重跑 `gen_seal.py` 并比对新旧 `package_sha256`。 （注：本坑修复后已由源空间会话重跑 `gen_seal.py`，包版本从 1.0.0 → 1.0.1，SEAL 已含该脚本新哈希；R0-B 回归核验确认 SEAL 与事实源一致。）
