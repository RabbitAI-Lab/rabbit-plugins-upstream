# 版权戳记与溯源方案（SEAL）

> 回答用户问：「技能 skill 能否添加加密戳记，作为后续有争议时（被抄袭 / 改造 / 引入商用）对代码权属的证明、方便追踪溯源？」
> 结论：**可以，且强烈建议做**。但需先澄清一个概念——

---

## 一、先澄清：「加密」≠「权属证明」

用户说的「加密戳记」，其真实诉求是 **「能证明这段代码在某一时刻归我、且被别人拿走/改了/商用了我能追到」**。

- **单纯加密（encryption）** 解决的是「别人看不到内容」，并不能证明归属，也不利于追踪（因为加密后别人根本用不了你的技能）。
- 真正能证明权属与溯源的是 **「数字指纹 + 可信时间戳 + 水印标识」** 三件套，我们统称为 **SEAL（戳记）**。
- 因此本方案**不加密技能内容**，而是：① 给每个文件算哈希指纹；② 给整包一个不可伪造的存在证明（时间戳）；③ 在 SKILL.md 埋一个随包走的水印令牌。

---

## 二、SEAL 机制设计

### 2.1 物理落点（不污染技能运行）
- `SEAL.json`：放在技能包根目录的 `provenance/` 子目录（或包根）。**不被 SKILL.md 自动加载**，仅作权属证据文件。
- 水印令牌：在 `SKILL.md` 顶部加一行 HTML 注释 `<!-- edo-seal:<skill_id> -->`——它随包走，别人复制 SKILL.md 时令牌一起被带走，便于反向溯源。

### 2.2 SEAL.json 字段（见 `SEAL.schema.json`）
```json
{
  "skill_id": "edo-tensei-1fef9b18bc9c451395d4bf85c0814afd",
  "skill_name": "秽土转生 (Multi-Session Control Tower)",
  "version": "1.0.0",
  "author_declared": "晋锡斌",
  "author_contact": "jinxibin1993@foxmail.com",
  "created_utc": "2026-09-15T08:35:05Z",
  "files": {
    "SKILL.md": { "sha256": "<哈希>", "bytes": 0 },
    "scripts/xxx.py": { "sha256": "<哈希>", "bytes": 0 }
  },
  "package_sha256": "<全文件哈希拼接后的总哈希>",
  "seal_hash": "<对上方规范化 JSON 的自签哈希>",
  "watermark_token": "edo-seal-1fef9b18bc9c451395d4bf85c0814afd",
  "tsa_timestamp": null,
  "notes": "本 SEAL 为权属溯源指纹，非加密。发布时建议另取可信时间戳（RFC3161 TSA）锚定存在时间。"
}
```

### 2.3 生成方式
- 用 `gen_seal.py <技能包目录>` 一键生成/刷新：遍历包内文件算 SHA-256 → 组装 `files` → 算 `package_sha256` → 对排除 `seal_hash` 后的规范化 JSON 算 `seal_hash` → 写回 `SEAL.json`。
- 每次发版（version 递增）重跑一次即可，哈希随内容变化，天然反映「这一版长什么样」。

---

## 三、可信时间戳（让「存在时间」不可抵赖）

`SEAL.json` 里的哈希只能证明「内容是什么」，不能证明「我在某天之前就拥有它」。要补齐这一环：

- **RFC 3161 可信时间戳（TSA）**：把 `package_sha256` 发给可信时间戳服务中心（如国内「联合信任时间戳服务中心」、或免费 TSA 如 `freetsa.org`），取回一张带权威时间签名的 `.tsr` 文件。
- 这张时间戳 = 「在 T 时刻，已存在哈希为 H 的内容」的第三方公证，**法律上可采信**。
- 用法：发布前跑 `gen_seal.py` 生成哈希 → 申请 TSA 时间戳 → 把 `.tsr` 一并打进包 / 备份腾讯文档。

> 本沙箱环境暂不便直接调用 TSA（需联网 + 证书），故 `gen_seal.py` 只产出哈希，TSA 步骤由你在本机发布时手动补；本文件已写明操作方式。

## 四、被抄袭 / 改造 / 商用的追踪思路

| 场景 | SEAL 如何应对 |
|---|---|
| **整包被原样抄袭发布** | 对方包里若带着 `SEAL.json` / 水印令牌 → 直接比对 `skill_id` 与 `package_sha256` 即可证明同源；若对方删了 SEAL，可用「文件哈希 + 腾讯文档备份 + TSA 时间戳」证明你更早拥有该内容。 |
| **被改造（改头换面）** | `files` 里逐文件哈希变化即暴露「被改」；核心逻辑若被复制，可凭「创意点清单 + 差异化分析」主张实质性相似。 |
| **被引入商用** | SEAL 的 `author_declared` + LICENSE 的「商业集成需授权」条款 + TSA 时间戳，构成「权属 + 许可条件 + 在先证据」完整链条，便于发函 / 投诉 / 诉讼。 |

> 注意：SEAL 是**证据工具**不是**技术锁**。它不能阻止抄袭，但能让抄袭「可被证明、可被追责」。真正防滥用还需配合 LICENSE 条款 + 平台投诉通道。

---

## 五、与多平台发布的关系

- 在 WorkBuddy（ClawHub / SkillHub）发布：SEAL.json 随包走，市场审核通常只看 LICENSE + author，SEAL 作为隐藏证据文件无副作用。
- 移植到 DeepSeek / 豆包 / Claude 等：这些平台无 SKILL.md 原生市场，移植成「系统提示词/专家人设」时，**务必把水印令牌与「最初于 WorkBuddy 创作」来源注明一并带过去**，否则跨平台同款技能将失去溯源锚点。
- 每个平台的发布记录统一登记到腾讯文档「技能发布视图」（平台 | 版本 | 发布日 | 来源迭代 | 状态 | 链接），与 SEAL 的 `version` 对齐，形成跨平台版本线。
