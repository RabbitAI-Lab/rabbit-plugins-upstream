# Axiom

Axiom lets the model order physical products for the user from online merchants. The model starts the order and relays progress; Axiom completes the merchant's checkout on the user's behalf through the user's Axiom account, applies the user's spending rules and approval limits, and captures the receipt. The model never handles payment details.

The Axiom MCP endpoint is `https://mcp.useaxiom.ai/mcp`.

## When to use this skill

Use Axiom when the user asks to:

- buy, order, or reorder a specific physical product with Axiom
- check which payment method Axiom has on file or whether their account is ready to order
- review recent Axiom orders, a receipt, or the status of an order in progress

Do not use it for browsing or price comparison, subscriptions or digital goods, account settings outside the tools below, or orders the user has not clearly requested.

## Authentication

For the full authentication guide, see [`references/authentication.md`](references/authentication.md).

**Quick summary:**

1. Register Axiom: `mcporter config add axiom --url https://mcp.useaxiom.ai/mcp`
2. Start auth: `mcporter auth axiom --reset --oauth-timeout 300000 --log-level info` (runs in background, prints the OAuth URL)
3. Parse the OAuth authorize URL from mcporter's log output
4. Navigate to that URL with a headless browser: `agent-browser open "<URL>"` (or `browser-use open "<URL>"`)
5. Read the **activation URL** from the rendered page: `agent-browser eval "document.querySelector('a[href*=\"activate\"]')?.href"`
6. Send the activation URL to the user to approve on their phone
7. mcporter completes the OAuth exchange automatically when the user approves
8. Verify: `mcporter call axiom.get_payment_method`

> **Important:** The OAuth authorize URL and the activation URL are different. The agent navigates to the authorize URL; the user opens the activation URL. Never send the authorize URL to the user. See the auth doc for examples of both.

To clear cached tokens: `mcporter auth axiom --reset`

Starting a purchase and answering a clarification require the `payments:write` OAuth scope; polling requires `payments:read`. If a purchase tool is rejected for insufficient scope, reset auth and reconnect so the client requests the current scope set.

## Placing an order

Axiom completes the order with the merchant on the user's behalf: cart, shipping, delivery, order confirmation, and receipt, through the user's Axiom account. The model's job is to (1) make sure the request is specific enough, (2) start the order, (3) relay each response to the user, and (4) follow `nextAction`.

When the user has clearly asked to buy a specific item, start the order. Axiom verifies the request against the user's stated intent and spending rules, and asks the user for explicit approval whenever its rules require it. When anything about the request is unclear, ask the user first.

### Step 1: Pre-flight checklist (ask first, then call)

Before calling `make_purchase`, all four must be true:

1. **Merchant known**, with an `https` URL. Prefer the product page URL when you have it; otherwise the merchant homepage. Never invent a URL.
2. **Specific product known.** "Acana Adult Recipe 25 lb" passes; "dog food" does not.
3. **Required variants known** for that product type: size and width for shoes and apparel, storage and color for electronics, flavor, size, and count for food and drink, loft and grind for golf clubs, and so on.
4. **The user actually asked to buy it** (not browse, compare, or think about it).

If any box is unchecked, ask the user one short question and wait. Do not call `make_purchase` to test a guess: every call creates a purchase attempt that counts toward the user's daily attempt limit.

Resolve from context when you can defend it: earlier turns, the user's stated preferences, memory. "My usual", "the same one again", and "buy that" are invitations to resolve from context. When the literal command is terse like that, pass `intentContext` with the evidence (the prior message or remembered preference) so Axiom can verify the resolution.

### Step 2: Call `make_purchase`

- `userCommand`: the user's words, near-verbatim. Do not paraphrase or fold resolved details into it.
- `merchant.merchantName`, `merchant.merchantURL`, `itemName`: your resolved specifics, including variants in `itemName`.
- `itemSubtotal`: only when the user stated a budget or the price is known (dollars, before shipping and tax).
- `intentContext`: only for terse or contextual commands; include concrete `evidence`.

### Step 3: Read the response the same way every time

Every purchase-flow response carries:

| Field | Meaning |
|---|---|
| `status` | Machine state (see table below) |
| `nextAction` | Exactly what to do next. Follow it literally. |
| `userMessage` | Text written for the end user. Relay it as written; you may add a short lead-in. |
| `agentInstructions` | Guidance for you. Never show it to the user. |
| `isFinal`, `safeToTellUserComplete` | Finality flags. Only `status: "completed"` with `safeToTellUserComplete: true` means the order went through. |

| `status` | `nextAction` | What you do |
|---|---|---|
| `running` | `poll_get_purchase_status` | Relay `userMessage` (it includes the tracking link). Save `browserPurchaseSessionID`. Poll `get_purchase_status`. `resumedFrom` means Axiom picked up an order it held during setup. |
| `needs_clarification` | `ask_user_then_call_make_purchase` | Ask the user the `question` (options are already listed in `userMessage`). Wait for the answer. Call `make_purchase` again with the answer folded into `itemName` or `merchant`. Never `submit_purchase_clarification`. |
| `unavailable` | `tell_user_unavailable` | Relay `userMessage`. Call `make_purchase` again only after the user picks an available option or changes the request. |
| `awaiting_approval` | `open_approval_link_then_wait_for_user` | Relay `userMessage` with the `approvalLink`. Stop polling. Poll again only after the user says they approved. |
| `awaiting_user_input` | `submit_purchase_clarification` | Ask the user `userInputRequest.question` (options are listed in `userMessage`). Then call `submit_purchase_clarification` with `browserPurchaseSessionID`, `userInputRequest.requestID`, and `selectedOptionID` and/or `userInput`. |
| `polling_too_often` | same as the parked state (`parkedStatus`) | You polled again too soon; nothing changed. Stop polling. Relay `userMessage` only if you have not already, then wait for the user to approve or answer. |
| `completed` | `tell_user_complete` | Relay `userMessage` (order number, total, receipt link). You may summarize `receipt` and `cart`. Stop polling. |
| `completed` with `safeToTellUserComplete: false` | `none` | Relay `userMessage`. Do not say the order went through. |
| `mandate_denied` | `tell_user_denied` | Relay `userMessage`. Do not retry the denied request. |
| `limit_reached` | `tell_user_limit_reached` | Relay `userMessage` exactly. Do not retry or guess a reset time. |
| `account_setup_required`, `email_verification_required` | `open_setup_link_then_wait_for_user` | Relay `userMessage` word for word, keeping its link on its own line; it already explains what Axiom needs and how to come back. Axiom holds the order (`heldPurchaseID`) for 24 hours. When the user says they're done, call `make_purchase` again with the same details; the response is `running` with `resumedFrom`. |
| `account_restricted` | `tell_user_restricted` | Relay `userMessage`. Final; do not retry. |
| `failed`, `cancelled`, `human_needed` | `tell_user_failed` | Relay `userMessage`. Normal terminal outcomes, not tool errors. Ask the user how to proceed; do not retry on your own. |

### Step 4: Poll `get_purchase_status`

Call `get_purchase_status` with the `browserPurchaseSessionID` while `status` is `running`. Each call waits up to 30 seconds for the next change and then returns. Checkouts usually take 10 to 15 minutes, so expect many rounds.

Between polls, give the user the `userMessage` only when something changed (a new `progressLabel`, a parked state, or a terminal state). Do not narrate every poll.

### Polling in an autonomous agent

Poll `get_purchase_status` in a loop while `status` is `running`; each call waits up to 30 seconds. Checkouts take 10 to 15 minutes. Report to the user only when something changes (a new `progressLabel`, a parked state, or a terminal state), and stop polling on `awaiting_approval` until the user says they approved.

### Step 5: Parked states

**Approval** (`awaiting_approval`): the order is above the user's auto-approve limit, so Axiom needs the user's explicit approval. Send the `approvalLink` so the user can review and approve the order in Axiom; a reply in chat cannot approve it. Wait for the user to say they approved, then call `get_purchase_status` again.

**Mid-checkout question** (`awaiting_user_input`): Axiom found several plausible options or a missing detail on the merchant site. Ask the user, then call `submit_purchase_clarification`. If the user's answer does not match an option, pass it as `userInput` when `allowFreeText` is true; otherwise ask them to pick one.

### Step 6: Completion

Only `status: "completed"` with `safeToTellUserComplete: true` means the merchant accepted the order. Progress labels, intermediate transaction states, and audit entries are not completion signals. Relay `userMessage`; it contains the confirmation number, total, and the Axiom receipt link (`transactionUrl`). Do not link to the merchant's order page.

### Which clarification tool?

| The question came from | You answer it with |
|---|---|
| `make_purchase` returning `needs_clarification` or `unavailable` | Ask the user, then call **`make_purchase` again** with the answer folded in. No purchase session exists yet. |
| `get_purchase_status` or `make_purchase` returning `awaiting_user_input` with a `userInputRequest` | Ask the user, then call **`submit_purchase_clarification`** with `requestID`. |

When in doubt, check `nextAction`: it names the tool.

### If you lose the session ID

Call `list_transactions`. Each in-flight transaction includes `purchaseFinality.browserPurchaseSessionID`; use it to resume polling. `get_transaction` with the `transactionID` returns the same finality block plus the receipt.

## Talking to the user

- Relay `userMessage` as written. It already includes links, questions, options, prices, and confirmation numbers. You may add a one-line lead-in; do not drop the link or the options.
- Never show `agentInstructions`, `finalityMessage`, `nextAction`, status codes, or session IDs to the user. Those fields are for you.
- Never say an order went through unless `status` is `completed` and `safeToTellUserComplete` is `true`.
- Never fabricate merchant, price, tax, shipping, receipt, or transaction details. Report only what the tools return.
- Money is in dollars everywhere in these responses (`amount`, `finalTotal`, `itemSubtotal`, option `amount`).
- When an order is waiting on the user or still running and you must end your turn, tell the user what is happening, give them the `transactionUrl`, and say you will check again when they ask.

## Safety rules

- Ask before you call: never start an order the user did not clearly request, and never call `make_purchase` with an invented merchant, URL, product, or option.
- Always surface Axiom's approval request to the user when one appears. It is how the user authorizes an order above their limit; it cannot be answered on the user's behalf.
- If `make_purchase` returns `mandate_denied`, stop and relay the reason. Do not retry the denied request.
- If `limit_reached` or `account_restricted` comes back, relay `userMessage` exactly and stop. Do not guess at limits or reset times.
- If `account_setup_required` or `email_verification_required` comes back, relay `userMessage` exactly with its link on its own line, then wait; call `make_purchase` again with the same details only after the user says they're done.
- Never share account credentials or internal identifiers.
- Treat `failed`, `cancelled`, and `human_needed` as normal outcomes: relay them, then ask the user how to proceed.

## Troubleshooting

`mcporter` (>=0.8.0) must be installed and on PATH; check with `mcporter --version`, and reset auth with `mcporter auth axiom --reset` if tokens expire. Common cases (auth expired, `account_setup_required`, repeated `needs_clarification`, `limit_reached`, `mandate_denied`, lost session ID, `isError` results) are covered in [`references/troubleshooting.md`](references/troubleshooting.md). The short version: relay `userMessage`, follow `nextAction`, and never retry a denied or limited order on your own.
