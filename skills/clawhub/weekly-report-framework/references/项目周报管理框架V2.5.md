## 一、组织架构

```
智能装备研究所（所长）
├── 机电系统研究室（ME）— 研究室经理
├── 工业视觉研究室（IV）— 研究室经理

## 二、项目编号体系

| 项目状态 | 编号格式 | 示例 |
|----------|----------|------|
| 未立项 | 年份(2位)+3位数字 | 26001, 26002, 26003... |
| 已立项 | 研究室缩写+年份(2位)+2位数字 | ME2601, ME2602, IV2601, LA2601... |

**研究室缩写**：

| 研究室缩写 | 说明 |
|------------|------|
| ME | 机电系统研究室 |
| IV | 工业视觉研究室 |
| LA | 物流与自动化研究室 |

**编号说明**：
- "26"代表2026年，便于区分不同年份的项目
- 每年1月1日起，新立项项目使用新年份编号

**规则**：
- 项目是否进入周报由研究室经理指定
- 未立项项目也进入周报
- 项目清单不自动增删，只按研究室经理指令变更
- 编号一旦分配，与项目名称绑定，不可随意变更

## 三、项目生命周期（11阶段+3特殊状态）

```
前期调研 → 风险评估 → 方案设计 → 项目立项 → 详细设计 → 采购加工 → 设备装配 → 设备调试 → 现场交付 → 项目结项 → 项目售后
```

**3个特殊状态**：暂停、终止、取消

**规则**：
- 3个特殊状态在**已立项和未立项中都会存在**
- 任何阶段都可能转为特殊状态
- 特殊状态可恢复为正常阶段

### 状态变更优先级

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1（最高） | 研究室经理直接告知 | 项目经理、状态等关键信息 |
| 2 | 群聊公告 | 美信群内公开宣布的变更 |
| 3（最低） | 文件推断 | 仅在已知项目范围内 |

### 项目结项 vs 项目售后

| 状态 | 定义 | 说明 |
|------|------|------|
| **项目结项** | 项目完成交付，**在1年质保期内** | 仍需处理质保期内的问题 |
| **项目售后** | **1年质保期结束后** | 仅处理售后遗留问题 |

**判断标准**：以项目交付日期为起点，满1年后自动从"项目结项"转为"项目售后"。

## 四、状态合法性检查

### 已立项项目合法状态
详细设计、采购加工、设备装配、设备调试、现场交付、项目结项、项目售后、暂停、终止、取消

### 未立项项目合法状态
前期调研、风险评估、方案设计、项目立项、暂停、终止、取消

**【异常检测】**：如果状态列出现不在上述列表中的名称，触发预警，等待研究室经理确认。

### 7.4 美信群聊消息抓取规则

#### 7.4.1 群聊匹配策略（模糊匹配+人工确认）

**铁律**：所有项目关联群必须由攀哥主动指定，不允许AI自动抓取或关联。

**匹配流程**：

```
1. 获取美信会话列表 → mx_message_sessions（本地接口，稳定）
2. 字符串相似度匹配 → 相似度>85%的候选群
3. 列出候选群 → 让攀哥确认哪个是对的
4. 确认后记录sId → 存入群聊关联表的sId列
5. 后续直接用sId查询 → 不再依赖搜索API
```

**匹配规则**：
1. **优先用sId**：已确认的群直接用sId查询，不再搜索
2. **模糊匹配**：攀哥给的群名和美信实际群名相似度>85%即可匹配
3. **人工确认**：匹配结果必须攀哥确认，防止关联错误
4. **永久记录**：确认后sId存入映射表，一次确认永久使用

**为什么这样做**：
| 问题 | 解决方案 |
|------|---------|
| 搜索API不稳定（HTTP 500） | 用本地会话列表，不依赖搜索API |
| 群名差几个字符匹配不上 | 模糊匹配，容错性强 |
| 容易关联错误 | 人工确认，最终攀哥拍板 |
| 每次都要搜索 | sId永久记录，后续直接用 |

#### 7.4.2 抓取流程

**抓取流程**：

```
开始
  ↓
检查存储目录是否存在md文件？
  ↓
┌─────────────┬─────────────┐
│ 不存在       │ 已存在       │
│ ↓           │ ↓           │
│ 首次抓取     │ 增量抓取     │
│ 最近3个月    │ 从last_fetch │
│ (90天)       │ _time开始    │
└─────────────┴─────────────┘
  ↓
用sId直接查询（不再搜索）
  ↓
分页抓取消息（每页100条，循环翻页）
  ↓
对每条消息处理：
  - 文字消息 → 直接记录到md
  - 图片消息 → 下载临时目录 → 视觉识别 → 记录关键信息到md → 删除临时图片
  - 文件消息 → 下载临时目录 → 读取内容 → 记录关键信息到md → 删除临时文件
  ↓
更新 last_fetch.json
  ↓
结束
```

**首次抓取规则（最近3个月）**：
- 条件：存储目录下不存在md文件
- 范围：从当前日期往前推90天（3个月）
- 示例：今天是2026-07-08，则抓取2026-04-08至今的消息
- 操作：循环翻页，每页100条，直到获取全部消息或到达3个月边界
- 输出：生成完整的md文档 + last_fetch.json
- 注意：超过3个月的历史消息不抓取，避免数据量过大

**首次抓取限流策略（防止触发美信反爬机制）**：
- **单次请求间隔**：每次API调用后随机延时1-3秒（模拟正常用户行为）
- **批次控制**：每抓取10页（1000条消息）为一个批次
- **批次间休息**：每批次完成后休息30秒
- **多群间隔**：多个群的首次抓取之间间隔5分钟
- **异常处理**：如触发限流（API返回错误或超时），立即暂停抓取，通知攀哥，等待10分钟后重试

**限流参数示例**：
```
抓取第1-10页 → 休息30秒 → 抓取第11-20页 → 休息30秒 → ...
群A抓取完成 → 等待5分钟 → 群B抓取完成 → 等待5分钟 → ...
```

**预估耗时计算**：
- 假设群消息量：10000条
- 需要翻页：100页
- 批次数量：10个批次
- 批次间休息：9次 × 30秒 = 270秒（4.5分钟）
- 请求间延时：100次 × 2秒（平均）= 200秒（3.3分钟）
- 总耗时：约8分钟/群

**首次抓取确认规则**：
- 场景：生成周报时，发现某项目存在首次抓取的群聊（md文件不存在）
- 处理流程：
  1. 提示攀哥："以下群聊需要首次全量抓取，耗时可能较长（几分钟到十几分钟）：
     - ME2601: 楼宇荆州-智研院 新月笛行管配管自动化
     - ME2603: 03-冷凝器自动焊接项目沟通群
     ..."
  2. 询问攀哥："是否现在开始抓取？"
  3. 攀哥确认"抓取" → 开始全量抓取
  4. 攀哥确认"稍后" → 跳过首次抓取，仅使用已有数据生成周报

**增量抓取规则**：
- 条件：存储目录下已存在md文件
- 范围：从last_fetch.json记录的时间戳开始
- 操作：只抓取新消息，追加到md文档
- 输出：更新md文档 + 更新last_fetch.json

**存储结构**：
```
knowledge/项目周报知识库/群聊抓取记录/
├── ME2601/
│   ├── 楼宇荆州-智研院 新月笛行管配管自动化/

- md里记录消息ID，便于追溯
- 需要原文件时 → 用消息ID去群里精准下载
- 不保存原档（节省空间），只保存关键信息

**群聊不存在/被删除处理规则**：
- 场景：按群名精确匹配时，找不到对应群聊（可能已被删除或退出）
- 处理流程：
  1. 反馈给攀哥："群聊'XXX'未找到，可能已被删除或退出"
  2. 询问攀哥是否需要从群聊关联表中移除该群
  3. 攀哥确认后，更新群聊关联表.md
- 已抓取的md记录：保留，不删除（作为历史记录）

**群消息保留策略**：
- 群聊抓取记录（md文件）：**永久保存，不删减**
- 用途：项目复盘分析、历史追溯、学习迭代
- 即使项目结项/售后，群聊记录仍保留
- 不清理、不归档、不删除

**增量抓取逻辑**：
- 首次抓取：只抓取最近3个月（90天）的消息，生成md文档
- 后续抓取：读取last_fetch.json的时间戳，只抓取新消息
- last_fetch.json格式：`{"last_fetch_time": "2026-07-07T15:00:00+08:00", "last_message_id": "xxx"}`

**按月归档**：
- md文件按月命名：`2026-07.md`
- 避免单文件过大（read工具限制50KB/2000行）
- 跨月周分别读取对应月份文件合并分析

**跨月周合并逻辑**：
- 场景：周报汇报周期跨月（如7.28周一-8.3周日）
- 处理步骤：
  1. 根据汇报周期确定涉及月份（7月+8月）
  2. 读取对应月份的md文件（2026-07.md + 2026-08.md）
  3. 合并分析（按时间排序，统一处理）
- 示例：
  ```
  汇报周期：7.28-8.3
  需要读取：
  - 2026-07.md（7.28-7.31的消息）
  - 2026-08.md（8.1-8.3的消息）
  合并后分析 → 生成周报
  ```

**消息过滤**：
- 不过度过滤，先全量抓取再分类
- 排除无关闲聊、重复消息、非工作相关内容

### 7.5 群消息分析流程

```
1. 读取群聊抓取记录（md文档）
      ↓
2. AI判断分类（成员输出/进度/计划/风险）
      ↓
3. AI智能分析（汇总提炼，生成E/F/G/H列内容）
      ↓
4. 结论多轮检查自证：
   - 是否存在矛盾？
   - 是否是上周周报的递延？
   - 数据是否自洽？
   - 结论是否有依据？
      ↓
5. 最终生成周报呈现
```

### 7.6 周报增量迭代规则

**问题背景**：
- 每次生成周报从零开始，导致两次生成内容差异大
- 攀哥修改过的内容可能丢失
- 需要版本迭代机制

**存储结构**：
```
knowledge/项目周报知识库/周报草稿/
├── ME2601/
│   ├── 20260705_latest.xlsx    ← 最新Excel（攀哥修改后更新）
│   ├── 20260705_latest.md      ← 最新md（从Excel同步）
│   ├── 20260705_v1.xlsx        ← 历史版本（自动备份）
│   └── 20260705_v1.md          ← 历史版本（自动备份）
├── ME2602/
│   └── ...
```

**增量迭代流程**：
```
生成周报时：
  ↓
检查 latest.xlsx 是否存在？
├─ 不存在 → 从零生成 → 存为 latest.xlsx + latest.md
└─ 已存在 → 读取 latest.xlsx
           ↓
         抓取群聊增量消息
           ↓
         在 latest.xlsx 基础上追加新内容
           ↓
         输出新版 → 更新 latest.xlsx + latest.md
```

**核心原则**：
- 攀哥修改过的内容 → 保留，不覆盖
- 新增群聊消息 → 追加到对应位置
- 没有新消息的群 → 原内容不动

**迭代规则**：
| 场景 | 处理方式 |
|------|----------|
| 首次生成 | 从零分析，生成V1 |
| 再次生成 | 读取上一版，对比群聊，只增减 |
| 攀哥修改后 | 以攀哥修改版为基准 |
| 新一周周报 | 新一周开始时，重新从零开始（新一周=新周期） |

**"新一周"判断逻辑**：
- 新一周 = 新的一周开始（周一00:00起）
- 判断方法：比较当前周的文件名日期（周日）与latest.xlsx的文件名日期
- 如果日期不同 → 新一周，重新从零开始
- 如果日期相同 → 同一周，增量迭代

**攀哥修改版同步流程**：
```
攀哥修改Excel → 发给我
      ↓
我读取Excel，对比差异
      ↓
告诉攀哥差异，询问"是否修改？"
      ↓
攀哥确认"修改"
      ↓
├─ 自动备份当前版本为 v1.xlsx / v1.md
├─ 更新存档的最新Excel文件（latest.xlsx）
└─ 将读取的信息更新到latest.md（E/F/G/H列摘要）
```

**latest.md更新内容**：
- 更新周报内容摘要（E/F/G/H列）
- 不是完整复制Excel，只记录关键信息
- 便于下次生成时快速读取

**历史版本保留**：
- 攀哥确认修改前，自动备份当前版本
- 命名规则：`20260705_v1.xlsx`、`20260705_v2.xlsx`...
- 保留所有历史版本，用于追溯

**数据保留策略**：
| 数据类型 | 保留策略 | 理由 |
|----------|----------|------|
| 群聊抓取记录 | 一直保存 | 项目复盘分析用 |
| 周报草稿 | 保留2周 | 第4周删除第1周草稿，只保留最新版本 |
| 周报草稿（项目结项后） | 不删除，保留 | 项目结项后仍需保留草稿 |

**周报草稿清理逻辑**：
```
每周生成周报时：
  ↓
检查草稿目录
  ↓
遍历所有草稿文件
  ↓
判断：当前周 - 草稿周 > 2周？
├─ 是 → 删除该草稿
└─ 否 → 保留
```

**示例**：
- 第1周（7.5）草稿 → 第4周（7.26）删除
- 第2周（7.12）草稿 → 第5周（8.2）删除
- 第3周（7.19）草稿 → 第6周（8.9）删除

**判断逻辑**：
```
群聊有新消息 → 追加到周报
群聊无新消息 → 保留原内容
```

### 文件名日期规则

**【铁律】日期计算必须用代码，禁止心算**：
```python
from datetime import datetime, timedelta

today = datetime.now()
weekday = today.weekday()  # 0=周一, 6=周日
sunday = today + timedelta(days=(6 - weekday))
monday = today - timedelta(days=weekday)

print(f"今天：{today.strftime('%Y-%m-%d')} 周{weekday+1}")
print(f"本周：{monday.strftime('%m.%d')}-{sunday.strftime('%m.%d')}")
print(f"文件名日期：{sunday.strftime('%Y%m%d')}")
```

**严格执行**：
- 生成前必须执行日期计算代码
- 计算结果必须打印验证

- 周二~周四：需与研究室经理确认导出上周还是本周
- 周五：默认导出本周周报

## 十一、预警机制

### 11.1 检测时机

| 时机 | 检测内容 |
|------|----------|
| 每周自动生成时 | 检查上周周报数据是否异常 |
| 收到修改版时 | 检查修改版是否引入异常 |

### 11.2 检测规则（2026-07-08 V2.5更新：增加异常检测）

| 序号 | 检测项 | 异常示例 | 级别 |
|------|--------|----------|------|
| 1 | 编号与项目名称匹配 | ME2601对应的项目名称变了 | 严重 |
| 2 | 项目经理一致性 | 项目经理突然变了 | 严重 |
| 3 | 内容位置错乱 | "本周进度"出现在"下周计划"列 | 严重 |
| 4 | 旧信息检测 | 修改版内容还是几周前的 | 严重 |
| 5 | 群名称变更 | 美信群名改了导致编号对不一 | 提示 |
| 6 | 项目消失 | 上周有这个项目，本周突然没了 | 提示 |
| 7 | 新增项目 | 突然出现新编号 | 提示 |
| 8 | **群聊无消息超2周**（V2.5新增） | 某项目关联群聊连续2周无新消息 | 提示 |
| 9 | **项目状态长期未变**（V2.5新增） | 项目状态连续4周未变化 | 提示 |

### 11.2.1 异常检测详细说明（V2.5新增）

**检测项8：群聊无消息超2周**
- **触发条件**：某项目所有关联群聊连续2周（14天）无新消息
- **检测逻辑**：
  ```python
  last_message_date = 从群聊抓取记录中获取最后一条消息的时间
  if (当前日期 - last_message_date) > 14天:
      触发预警
  ```
- **预警输出**：
  ```
  【提示】以下项目群聊无消息超过2周，请确认项目状态：
  1. ME2601 F4新月输出管自动插管焊接连续流（楼宇荆州）- 最后消息：2026-06-20
  2. 26001 电磁线圈盘绞线穿管自动化（生活顺德）- 最后消息：2026-06-15
  
  建议：如项目已暂停/终止，请更新项目状态。
  ```

**检测项9：项目状态长期未变**
- **触发条件**：项目状态连续4周（28天）未变化
- **检测逻辑**：
  ```python
  last_status_change_date = 从周报草稿中获取状态最后变化的时间
  if (当前日期 - last_status_change_date) > 28天:
      触发预警
  ```
- **预警输出**：
  ```
  【提示】以下项目状态连续4周未变化，请确认是否需要更新：
  1. ME2604 水路镀层导热及阻垢优化及设备化 - 状态"设备装配"已持续35天
  2. ME2606 多臂协同微波外漏检测 - 状态"详细设计"已持续42天
  
  建议：确认项目是否正常推进，或是否需要更新状态。
  ```

### 11.3 预警输出格式

```
【注意】周报异常检测报告

【严重】
1. ME2601 项目编号对应项目名称变更：原"XX项目" → 现"YY项目"
2. ME2602 本周工作内容与第3周完全重复，疑似未更新

【提示】
3. 美信群"链式绕线设备"群名已变更，原对应编号26001，请确认归属
4. 新增项目26005，请确认编号是否正确

请确认后回复，我将按确认结果更新。
```

### 11.4 处理原则

- **严重异常**：暂停生成，等待研究室经理确认
- **提示类**：生成周报但附带提示，研究室经理可选择忽略
- **所有异常**：记录到日志，用于学习迭代

## 十二、学习迭代逻辑

### 12.1 迭代流程（V2.4更新）

```
周五16:00 自动生成本周周报（含E/F/G/I四列初稿）
    ↓
攀哥审阅，与AI交互修正F列和H列
    ↓
多轮交互，直到攀哥满意
    ↓
攀哥线下修改后发回修改版
    ↓
【注意】AI收到修改版 → 不盲目归档
    ↓
AI先分析判断，对比差异
    ↓
AI输出问题点给攀哥确认：
"修改版与上一版有以下差异，请确认是否需要进一步修订：
 1.xxx 2.xxx 3.xxx"
    ↓
攀哥确认：
→ "需要修订xxx" → 继续交互
→ "直接归档" → 归档+更新知识库
```

### 12.2 差异对比

**对比内容**：

| 对比项 | 说明 |
|--------|------|
| 项目增删 | 研究室经理新增或删除了哪些项目 |
| 状态变更 | 研究室经理修改了哪些项目的状态 |
| 内容调整 | 研究室经理修改了哪些列的内容 |
| 格式调整 | 研究室经理调整了哪些格式 |

**对比方法**：

1. 读取AI生成的周报（原始版本）
2. 读取研究室经理修改后的周报（修改版本）
3. 逐行逐列对比，记录差异

### 12.3 学习内容

| 学习类型 | 说明 | 示例 |
|----------|------|------|
| **项目信息修正** | 项目信息的正确值 | 如：状态应该是"设备装配"而不是"设备安装" |
| **描述风格** | 研究室经理偏好的用词和表达方式 | 如：E列每条改为≤15字 |
| **信息抓取方式** | 哪些信息重要、如何提炼 | 如：某类消息不需要提取 |
| **洞察生成逻辑** | 如何生成洞察 | 如：需要增加某类分析 |
| **异常处理策略** | 如何处理异常 | 如：某类异常不需要预警 |

### 12.4 学习记录格式

```markdown
## 学习记录 - 2026-07-06

### 差异对比
- E列格式：原≤20字 → 修改为≤15字
- ME2604状态：原"设备安装" → 修改为"设备装配"

### 学习内容
1. E列每条消息总结应更简洁，控制在15字以内
2. 状态名称必须使用合法状态，"设备安装"不是合法状态

### 应用规则
- 下次生成时，E列每条≤15字
- 状态检查时，"设备安装"触发预警
```

### 12.5 学习应用

**应用时机**：每次生成周报前，读取学习记录，应用已学习的规则。

**应用优先级**：
1. 学习记录中的规则 > 框架默认规则
2. 最新学习记录 > 历史学习记录
3. 研究室经理确认的规则 > AI推测的规则

### 20.5 三种初始化方式对比

| 方式 | 适合人群 | 流程 | 优点 |
|------|----------|------|------|
| **方式1：手动填写md** | 熟悉markdown的技术用户 | 直接编辑模板文件 | 灵活 |
| **方式2：对话式填写** | 不熟悉markdown的用户 | 和AI对话，AI帮忙写入 | 友好 |
| **方式3：Excel模板填写** | 所有用户（推荐） | 下载模板→填写→上传→AI验证→确认→写入 | 高效、直观 |
