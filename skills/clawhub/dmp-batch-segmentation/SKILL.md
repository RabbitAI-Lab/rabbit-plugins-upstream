# 明日DMP批量圈包

## 概述

本技能是一个**项目级批量圈包管理工具**，专门解决大批量圈包场景下的系统限制问题。通过自动任务拆分、批次调度和进度跟踪，实现从"单次圈包"到"项目级批量圈包"的能力升级。

### 核心价值

- **突破系统限制**：自动拆分超限任务（LBS单次最多200个坐标、组合人群每组最多50个标签）
- **分批创建策略**：每批最多5个任务，**同批内逐个串行创建**（一个创建API返回成功后再创建下一个，不需要等计算完成）；**必须等上一批全部计算完成后才能创建下一批**
- **项目级管理**：一个项目生成多个人群包，统一管理和追踪
- **自动化执行**：自动生成执行计划、批次调度、进度监控
- **降低操作成本**：从手动拆分N次任务 → AI自动完成

### 适用场景

| 场景 | 描述 | 系统限制 | 解决方案 |
|------|------|----------|----------|
| **场景1：LBS批量点位圈选** | 需要圈选大量门店/网点周边用户（数量不定） | 单次最多200个坐标 | 自动拆分为N个任务（每任务200个坐标） |
| **场景2：组合人群-多规则拆分组合** | 将标签、已有人群包拆分成多个规则组合，组内OR、组间AND/NOT/OR（支持标签ID+人群包ID作为规则条件） | 每个规则最多50个标签 | 按多对一/一对多/多对多模式拆分，自动批量创建多个组合人群任务；**每批最多5个任务，同批逐个串行创建，等上一批全部计算完成后再创建下一批** |

**支持查询已有人群包**：在选择规则条件前，可通过人群列表查询接口搜索已有DMP人群包，将人群包ID作为规则条件传入，实现"已有基础人群包 + 标签过滤"或"人群包与人群包之间交并差"的批量组合。

### 脚本拦截规则（代码级硬拦截，无法跳过）

1. **上一步任务必须成功**：`status == "success"` 才能创建下一个
2. **凭证必须有效**：AK/SK 必须存在且完整
3. **鉴权技能必须安装**：`mingdata-dmp-auth` 必须存在
4. **不可重复创建**：已成功的任务不可再次创建
5. **不可超出总数**：任务索引不能大于总任务数

### cron 任务创建规范

使用 `cron` 工具创建监控任务（不是命令行）：

```python
cron(action="add", job={
    "name": f"DMP任务状态监控-{project_id}-任务{task_index}",
    "schedule": {"kind": "every", "everyMs": 60000},
    "payload": {
        "kind": "agentTurn",
        "message": f"检查DMP任务状态..."
    },
    "sessionTarget": "current",  # 必须
    "delivery": {"mode": "none"}  # 必须
})
```

**为什么不用命令行？**  
命令行无法正确设置 `sessionTarget: "current"`，会导致监控任务无法触发。

⚠️ **API参数结构说明（必须理解）：**

**关键规则：**
1. **同一个rule内的tag是OR关系**
   - `{"rule": {"tag": [15705, 34140]}}` = 女 OR 北京
   - 如果需要AND关系，必须分开成多个rule

2. **不同rule之间通过op字段定义逻辑关系**
   - `{"op": "and", "rule": {"tag": [15705]}}` + `{"op": "noop", "rule": {"tag": [34140]}}` = 女 AND 北京

3. **最后一组必须用noop**
   - 最后一个rule的op必须是"noop"

**示例对比：**

❌ 错误（女 OR 北京）：
```json
{
  "data": [
    {"op": "and", "rule": {"tag": [15699]}},
    {"op": "noop", "rule": {"tag": [15705, 34140]}}
  ]
}
// 实际：高收入 AND (女 OR 北京)
```

✅ 正确（女 AND 北京）：
```json
{
  "data": [
    {"op": "and", "rule": {"tag": [15699]}},
    {"op": "and", "rule": {"tag": [15705]}},
    {"op": "noop", "rule": {"tag": [34140]}}
  ]
}
// 实际：高收入 AND 女 AND 北京
```

**组合逻辑处理规则：**
- 用户指定AND：每个标签单独一个rule，用op="and"连接
- 用户指定OR：可以把标签放在同一个rule里（OR关系）

⚠️ **预览规则（必须遵守）：**
- ✅ 每个标签必须展示ID和名称
- ✅ 必须明确标注OR/AND关系
- ✅ 必须展示实际API参数
- ✅ 预览内容必须与实际创建参数完全一致
- ❌ 禁止使用简化描述（如"18-24岁"）
- ❌ 禁止预览和创建使用不同的数据

**第六步D：定时监控方案（强制使用cron，禁止后台exec轮询）**

🔴 **三种方式的强制约束：**

| 方式 | 是否允许 | 原因 |
|------|---------|------|
| ✅ `cron(action="add", job={...})` 工具 | **必须使用（强制）** | 绑定当前session，每60秒自动触发agent turn，完成后可自动通知用户和推进下一批；默认自动启用，不需要询问 |
| ❌ `openclaw cron add` 命令行 | **严格禁止** | 无法设置sessionTarget=current，会绑定到isolated session导致监控无法触发 |
| ❌ `exec(background=true)` + `sleep` + 手动轮询 | **严格禁止** | 后台进程在session休眠/断连后不会唤醒AI，导致任务完成后无法通知用户（已发生过此故障） |

**监控cron任务创建规范（第一批任务创建成功后必须立即执行，不需要询问用户）：**

```python
cron(action="add", job={
    "name": f"DMP任务状态监控-{project_id}",
    "schedule": {"kind": "every", "everyMs": 60000},
    "payload": {
        "kind": "agentTurn",
        "message": f"检查DMP项目{project_id}的任务状态，audienceIds={task_ids}。查询POST /audience/manage/taskList，检查每个任务audienceStatus(1=成功,0=失败,2/3=计算中)。本批全部成功后：若还有下一批则自动创建下一批并继续监控；若全部完成则汇总结果通知用户，然后调用cron(action='remove',...)删除本监控任务。若有失败按failureStrategy处理。"
    },
    "sessionTarget": "current",
    "delivery": {"mode": "none"}
})
```

**为什么不再询问用户是否启用监控：**
- 多批次任务必须依赖监控才能自动推进（批间等待计算完成）
- 不启用监控 = 无法自动创建下一批 = 项目无法完成
- cron监控是项目执行的必要环节，不是可选项

**cron任务触发时的执行流程：**
1. 查询当前所有任务的audienceStatus
2. 本批全部成功（audienceStatus=1）→ 自动创建下一批任务，继续监控
3. 全部批次完成 → 输出汇总结果、主动通知用户、调用cron(action="remove",...)删除监控任务
4. 有失败（audienceStatus=0）→ 按failureStrategy处理（pause通知用户等待指令/skip记录后继续）

**🔴 自我检查清单（每次创建第一批任务后必须逐项确认）：**
- [ ] 我是否使用了 `cron` 工具（不是exec background，不是命令行）？
- [ ] sessionTarget 是否设置为 `"current"`？
- [ ] delivery 是否设置为 `{"mode": "none"}`？
- [ ] payload.message 是否包含了项目ID、推进下一批、完成后删除cron的指令？
- [ ] 创建cron后是否向用户确认了监控已启动？

**只有在单批次（任务数≤批大小，不需要分批）且用户明确选择手动查看时，才可以不创建监控任务，但仍需提示用户后续可手动查询进度。**

**步骤7.1：判断任务总数**

🔴 **分批创建规则（仅适用于场景2）：**
- 场景2（组合人群）：每批最多**5个任务**
- **同批内逐个串行创建**：创建任务1→等API返回audienceId→创建任务2→...→创建任务5。同批内不需要等计算完成，只需等创建API返回成功即可提交下一个创建请求
- **批间必须等待全部计算完成**：一批5个任务全部创建提交后，启动监控等待这批所有任务计算完成（audienceStatus=1），**全部成功后才能创建下一批**
- 创建失败时按第六步C确认的策略处理（pause/skip）
- 场景1（LBS）：所有坐标点直接创建（受单次200坐标限制，自动拆分）

**步骤7.2：分批创建任务（每批最多5个，逐个串行创建，批间等计算完成）**

调用对应的创建脚本：
- 场景1：`python scripts/create_lbs_batch.py`
- 场景2：`python scripts/create_combine_batch.py --batch-start N --batch-end M`

**⚠️ 分批创建机制：**

场景2（组合人群）任务数 > 1 时，按每批5个分批创建：

```bash
# 第1批：逐个串行创建任务1~5
python scripts/create_combine_batch.py --batch-start 1 --batch-end 5 ...
# 脚本内部：创建1→等返回→创建2→等返回→...→创建5→等返回

# 等待第1批全部计算完成（监控audienceStatus，全部=1后继续）

# 第2批：逐个串行创建任务6~10
python scripts/create_combine_batch.py --batch-start 6 --batch-end 10 ...

# 等待第2批全部计算完成...
# ... 以此类推
```

**🔴 代码级硬拦截（场景2，任务数>1时生效）：**

脚本内置了强制约束：
```python
if total_tasks > 5 and args.batch_start is None and args.task_index is None:
    print("🔴 前置校验失败：场景2任务数>1，必须使用 --batch-start/--batch-end 分批创建（每批最多5个）")
    sys.exit(1)
```

**场景2任务数>1且未指定批次范围或单个task-index，脚本会拒绝执行。**

**🔴 严格禁止的行为（违反视为严重错误）：**

❌ **禁止在一个命令行里一次性提交超过5个任务的创建请求**

❌ **禁止同批内并发提交多个创建请求（必须逐个串行）**
```python
# 错误示例：同批内并发创建
import concurrent.futures
with concurrent.futures.ThreadPoolExecutor(5) as pool:  # ❌ 禁止并发
    pool.map(create_task, [1,2,3,4,5])
```

❌ **禁止不等上一批计算完成就创建下一批**
```python
# 错误示例：
create_batch(1,5)
# 没等计算完成就...
create_batch(6,10)  # ❌ 必须等1~5全部计算成功
```

❌ **禁止直接调用API而不通过脚本**

✅ **正确做法：同批逐个串行创建，批间等待全部计算完成**
```bash
# 第1批：逐个创建任务1~5（脚本内部串行）
python scripts/create_combine_batch.py --batch-start 1 --batch-end 5 --project-id xxx ...

# 等待第1批全部计算完成（audienceStatus全部=1）
# 然后创建第2批
python scripts/create_combine_batch.py --batch-start 6 --batch-end 10 --project-id xxx ...

# ... 以此类推
```

**为什么这样设计？**
1. **避免API限流**：同批逐个创建，不会瞬时并发过多请求触发限流
2. **批间控制**：等一批计算完再创建下一批，避免DMP平台同时排队任务过多
3. **失败可控**：一批内某个任务失败时可以暂停，不会产生大量失败任务
4. **可追溯**：每个任务的创建时间、状态、人群规模都有记录

**脚本返回结果包含：**
- `batch_start/end`: 本批任务索引范围
- `created_tasks`: 本批成功创建的任务列表（含audienceId）
- `failed_tasks`: 本批创建失败的任务列表（含错误信息）
- `pending_batches`: 剩余待创建的批次信息
- `status`: 任务状态（partial/completed/failed）

**AI助手处理流程（场景2分批创建）：**
1. 计算总任务数N，按每批5个切分：批1=[1,2,3,4,5], 批2=[6,7,8,9,10], ...
2. 调用脚本提交第1批（`--batch-start 1 --batch-end min(5,N)`），脚本内部逐个串行创建
3. 检查第1批创建结果：
   - 全部创建提交成功 → 启动监控，等待这批所有任务计算完成（audienceStatus=1）
   - 有创建失败 → 按failureStrategy.onCreateFail处理（pause暂停/skip跳过）
4. 第1批全部计算成功后，再提交第2批
5. 重复步骤2-4，直到所有批次创建并计算完成
6. 向用户汇报最终结果

**⚠️ 关键：同批逐个串行创建（不等计算），批间必须等待全部计算完成！**

```
第1批：创建1→等返回→创建2→等返回→...→创建5→等返回
    → 启动监控，等5个任务全部计算完成（audienceStatus=1）
    → 全部成功
第2批：创建6→等返回→创建7→等返回→...→创建10→等返回
    → 启动监控，等5个任务全部计算完成
    → ...
最后一批完成 → 汇总结果通知用户
```

   - **所有任务都执行成功（audienceStatus=1）后，才删除监控任务**

3. **cron任务的优势：**
   - ✅ 不需要修改openclaw.json配置文件
   - ✅ 不需要重启网关
   - ✅ 立即生效
   - ✅ 可靠性高
   - ✅ 任务完成后自动通知到当前会话
   - ✅ 可以自动清理（任务完成后删除cron）

**🔴 重要：分批创建的核心逻辑**

**⚠️ 这是最容易出错的步骤，必须严格遵守！**

**核心原则：每批最多5个任务，同批逐个串行创建（只等创建返回不等计算），批间必须等全部计算完成！**

**分批创建的完整流程：**

```
第1步：计算总任务数N
    ↓
第2步：按每批最多5个切分
    第1批：任务1~5
    第2批：任务6~10
    ...
    第k批：任务(5(k-1)+1)~min(5k, N)
    ↓
第3步：逐个串行创建第1批
    创建任务1 → 等API返回audienceId → 创建任务2 → 等API返回 → ... → 创建任务5
    ↓
第4步：启动监控，等待第1批全部计算完成（audienceStatus全部=1）
    ↓
┌─────────────────────────────────────────┐
│ 第1批全部计算成功                         │
│   → 继续创建下一批                        │
└─────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────┐
│ 有任务计算失败（audienceStatus=0）        │
│   → 按failureStrategy.onExecuteFail处理  │
│   ├─pause：停止，询问用户是否继续         │
│   └─skip：记录失败，继续下一批            │
└─────────────────────────────────────────┘
    ↓
第5步：逐个串行创建第2批（同第3步）
    ↓
等待第2批全部计算完成
    ↓
... 重复直到所有批次完成 ...
    ↓
汇总所有批次结果通知用户
```

**❌ 绝对禁止的行为：**
- ❌ 一次性提交超过5个任务的创建请求
- ❌ 同批内并发提交多个创建请求（必须逐个串行）
- ❌ 不等上一批全部计算完成就创建下一批
- ❌ 有失败任务时不询问用户直接继续（pause策略下）
- ❌ 有失败任务时不询问用户直接继续（pause策略下）

- ❌ 忽略脚本输出的 `mandatory: true` 指令
- ❌ 跳过参数确认和执行计划预览直接创建

**✅ 必须执行的行为：**

## 任务监控机制

### 触发条件（强制，第一批创建后立即启动）

第一批任务创建API返回成功后，**必须立即**使用 `cron` 工具创建监控任务（不再询问用户）。

🔴 **严格禁止：**
- ❌ `exec(background=true)` + `sleep` 轮询（session断连后AI无法被唤醒，已发生故障导致不通知用户）
- ❌ `openclaw cron add` 命令行（无法设置sessionTarget=current）
- ❌ 询问用户是否需要监控（多批次必须依赖监控才能自动推进，不是可选项）

### 监控策略

```yaml
监控配置:
  工具: 必须使用 cron(action="add", job={...}) 工具
  sessionTarget: "current"（必须）
  delivery: {"mode": "none"}（必须）
  轮询间隔: 每60秒触发一次agent turn
  创建阶段: 每批最多5个，逐个串行创建（不等计算），批间等全部计算完成
  监控阶段: cron每60秒触发一次，检查当前批任务状态
  超时阈值: 1800秒（30分钟未完成视为异常，通知用户）
  失败处理: 按第六步C确认的策略（pause等待/skip自动跳过）
  完成后: 汇总结果 → 通知用户 → cron(action="remove") 删除监控任务
```

### 监控流程

```
第一批任务创建成功（API返回audienceId）
        ↓
🔴 立即调用cron(action="add",job={...})创建监控任务（不是exec、不是命令行）
        ↓
cron每60秒触发一次agent turn
        ↓
检查当前批任务audienceStatus
├─ 本批全部成功（status=1）：
│   ├─ 还有下一批 → 创建下一批任务（同批逐个串行），继续监控
│   └─ 全部完成 → 第八步检查 → 汇总通知用户 → 删除cron任务
├─ 有失败（status=0）→ 按failureStrategy处理（pause通知用户/skip记录继续）
└─ 仍有计算中（status=2/3）→ 等待下一次cron触发
```

**创建cron定时任务标准模板（直接使用）：**

🔴 **严重警告：必须使用 `cron` 工具，禁止使用命令行和exec后台轮询！**

```python
# ✅ 正确方式：使用 cron 工具
cron(action="add", job={
    "name": f"DMP任务状态监控-{project_id}",
    "schedule": {"kind": "every", "everyMs": 60000},  # 每1分钟
    "payload": {
        "kind": "agentTurn",
        "message": f"检查DMP任务状态，项目ID: {project_id}，任务ID列表: {task_ids}。查询每个任务的状态，如果所有任务都完成，自动创建下一批并删除此cron任务。"
    },
    "sessionTarget": "current",  # 🔴 关键：必须设置为 current
    "deleteAfterRun": False
})
```

❌ **禁止使用命令行：**
```bash
# ❌ 错误方式：命令行无法正确设置 sessionTarget
openclaw cron add --name "xxx" --every 1m --message "xxx" --session current
```

**原因说明：**
- 使用 `cron` 工具可以正确设置 `sessionTarget: "current"`
- 使用命令行 `--session current` 会被错误解析为 `isolated`
- 错误的 sessionTarget 会导致监控任务无法自动触发

**cron定时任务的优势：**
- ✅ 不占用后台进程
- ✅ 不需要重启网关
- ✅ 立即生效
- ✅ 可靠性高
- ✅ 任务完成后自动通知到当前会话
- ✅ 可以自动清理（任务完成后删除cron）

- data从"条件框数组"升级为"组列表"：`data: [{ op, group: [{op, rule}, ...] }, ...]`
- 组间op支持and/or/not，从左到右计算，末组必须noop
- 组内结构与V1的data完全一致（框内OR，框间and/not，不支持or）
- 本技能所有批量圈包任务均为单组，外层包一层group即可兼容V2

**3. 标签类型扩展**
- tagType=2：明略定制标签（mz_tag source=2）
- tagType=4：自定义标签
- tagType=5：明日定制标签（mingdata_tag）
- 返回新增字段：pcAmount（PC端覆盖量级）、mbAmount（Mobile端覆盖量级）、ottAmount（OTT端覆盖量级）

**🔴 cron监控硬约束（代码级拦截）：**
- scripts/cron_helper.py - cron监控锁文件管理
  - `check`：monitor/推进下一批前检查锁文件，未设置cron则拒绝执行（exit 1/2）
  - `mark-cron-set --cron-name <名字>`：AI创建cron任务后必须调用此命令写入锁文件
  - `cleanup`：全部完成后清理锁文件，提示AI删除cron任务
  - `gen-cron-params --type combine|idlink`：生成标准cron任务参数

**cron硬拦截工作机制：**
```
第一批创建成功 → 脚本输出cron_params和mark-cron-set指令
      ↓
AI必须执行：
  1. cron(action="add", job=cron_params)  ← 创建cron
  2. cron_helper.py mark-cron-set         ← 写入锁文件
      ↓
cron每分钟触发 → 推进下一批/monitor模式
      ↓
推进前 check_cron_setup():
  ├─ 锁文件存在 → 正常推进
  └─ 锁文件不存在 → exit 2 拦截
      ↓
全部完成 → cron_helper.py cleanup → 删除cron
```
即使AI忽略提示词，脚本层面也会拦截无cron的批次推进。

## 🔴 重要提醒：监控任务创建规则

**必须使用 `cron` 工具，禁止使用 `openclaw cron add` 命令行！**

**原因：**
- 命令行的 `--session` 参数只支持 `main` 或 `isolated`
- 不支持 `current`（当前会话）
- 使用命令行创建的监控任务，`sessionTarget` 被错误设置为 `isolated`
- 导致监控任务无法正确绑定到当前会话，无法自动触发

**正确做法：**
```python
# ✅ 使用 cron 工具
cron(action="add", job={
    "name": "DMP任务状态监控-xxx",
    "schedule": {"kind": "every", "everyMs": 60000},
    "payload": {...},
    "sessionTarget": "current",  # 🔴 必须设置为 current
    "delivery": {"mode": "none"}
})
```

**错误做法：**
```bash
# ❌ 禁止使用命令行
openclaw cron add --name "xxx" --every 1m --message "xxx" --session current
```

**每次创建监控任务前，必须执行以下验证：**
1. 检查脚本输出的 `cron_instruction` 字段
2. 验证使用的是 `cron` 工具（不是命令行）
3. 验证 `sessionTarget: 'current'`
4. 验证 `delivery: {'mode': 'none'}`
5. 如果检测到使用命令行，立即更换为 `cron` 工具
