## 二、适用场景

本工作流适用于交通行业客户的数据架构（数据资源→数据湖→数据仓库→数据集市→数据服务）和技术架构（技术栈选型、平台架构、集成架构、部署架构、安全架构）的完整设计。

**1.2 交通数据域划分**

| 数据域 | 子域 | 核心数据实体 |
|-------|------|-------------|
| 基础设施域 | 路网/桥隧/场站/设备 | 路段、桥梁、隧道、收费站、服务区、摄像机、情报板 |
| 运行监测域 | 交通流/事件/环境 | 交通流量、速度、占有率、事件、天气 |
| 收费运营域 | 收费/拆分/稽查 | 通行流水、ETC交易、拆分记录、黑名单 |
| 养护管理域 | 病害/维修/材料 | 病害记录、维修单、养护计划、材料消耗 |
| 安全管理域 | 应急/风险/事故 | 应急预案、应急资源、安全事件、风险评估 |
| 出行服务域 | 出行/发布/咨询 | 路况发布、出行规划、热线工单 |
| 企业管理域 | 人事/财务/资产/工程 | 组织、人员、预算、合同、资产台账 |
| 外部数据域 | 气象/地图/舆情 | 天气预报、POI、路况舆情 |

### 步骤2：数据湖仓设计

**目标**：设计分层的数据存储和计算架构。

**输入**：数据域划分、数据量级预估、性能需求
**输出**：数据湖仓设计方案、分层模型、ETL/ELT设计

**操作指南**：

**2.1 分层设计原则**

| 分层 | 命名 | 职责 | 保留策略 |
|------|------|------|---------|
| ODS | 贴源层 | 原始数据落地，保持源结构不变 | 按需(3-12月) |
| DWD | 明细层 | 清洗、标准化、轻度汇总 | 3-5年 |
| DWS | 汇总层 | 按主题聚合、预计算 | 5-10年 |
| ADS | 应用层 | 面向应用的指标宽表 | 按需求 |
| DIM | 维度层 | 维度数据统一管理 | 长期 |

**2.2 交通行业特色数据模型**

```
交通行业核心数据模型示例:

DWD_交通流明细:
  - 路段ID、方向、车道
  - 时间(5分钟粒度)
  - 流量、速度、占有率
  - 车辆类型分布
  - 数据来源标识(微波/视频/ETC/浮动车)

DWD_事件明细:
  - 事件ID、类型(事故/拥堵/施工/天气/抛洒物)
  - 发现时间、确认时间、处置时间、恢复时间
  - 位置(路段+桩号+经纬度)
  - 发现方式(AI/人工/热线)
  - 影响范围(排队长度/延误时间)
  - 处置记录关联

DWS_路网运行日报:
  - 路段ID、日期
  - 日均流量、高峰流量、高峰时段
  - 拥堵指数、拥堵时长、拥堵里程
  - 事件总数、信息发布次数
  - 同比、环比指标

ADS_决策者驾驶舱指标:
  - 今日路网健康指数
  - 本周拥堵治理成效
  - 本月安全态势评分
```

**2.3 实时 vs 离线数据通道**

| 通道 | 技术 | 延迟 | 适用场景 |
|------|------|:---:|---------|
| 实时流 | Kafka+Flink/Spark Streaming | <1秒 | 事件告警、实时大屏、动态调度 |
| 近线 | Spark Streaming | 秒-分钟 | 态势评估、动态预测 |
| 离线批 | Spark/Hive on HDFS | 小时-天 | 日报月报、AI模型训练、数据挖掘 |

### 步骤5：集成架构详细设计

**目标**：设计系统间集成的详细技术方案。

**输入**：应用交互矩阵、现有系统接口、技术选型
**输出**：集成架构设计、接口规范、数据交换标准

**操作指南**：

**5.1 集成模式选择**

| 集成模式 | 适用场景 | 技术实现 |
|---------|---------|---------|
| API同步调用 | 实时查询/操作 | REST/gRPC + API Gateway |
| 消息异步 | 事件通告/数据同步 | Kafka/MQ |
| 文件交换 | 批量数据交换 | SFTP + 文件解析 |
| 数据库共享 | 只读数据访问 | 数据虚拟化/联邦查询 |
| ETL/ELT | 批量数据汇聚 | DataX/SeaTunnel |

**5.2 集成规范制定**

必须统一的集成规范：
- API设计规范（RESTful/命名/版本/分页/错误码）
- 消息格式规范（消息头/消息体/序列化方式）
- 接口认证规范（OAuth2.0/JWT/API Key）
- 数据格式规范（JSON Schema/XML Schema）
- 错误处理规范（重试/补偿/死信队列）
- 接口文档规范（Swagger/OpenAPI 3.0）

### 步骤6：国产化适配与合规设计

**目标**：确保技术架构满足国产化（国产化）替代要求和合规标准。

**输入**：技术选型、国产化政策、合规要求
**输出**：国产化适配方案、合规矩阵

**操作指南**：

**6.1 国产化替代推进路线**

```
国产化替代时间线:

Phase 1 (2025-2026): 办公系统 + 非核心业务系统
  - OA系统: 流式/版式/签章 → WPS/永中
  - 邮箱/会议 → 本地化方案

Phase 2 (2026-2027): 核心业务系统适配
  - 数据库 → 达梦/人大金仓/神通
  - 中间件 → 东方通/宝兰德/中创
  - OS → 麒麟/统信UOS

Phase 3 (2027-2028): 全面国产化
  - 芯片 → 鲲鹏/飞腾/海光
  - 云平台 → 华为云Stack/天翼云
  - 安全产品 → 本地化安全设备
```

**6.2 国产化适配策略**

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| 全新建设 | 新系统直接基于国产化技术栈 | 新建系统 |
| 并行替换 | 新老系统并行运行后切换 | 核心系统 |
| 改造迁移 | 将现有系统迁移到国产化平台 | 有源码的系统 |
| 容器封装 | 将现有系统容器化后部署在国产化OS上 | 短期内过渡 |

### 步骤8：架构评审与基线发布

**目标**：完成数据和技术架构的评审，建立架构基线。

## 八、常见陷阱与对策

| # | 陷阱 | 对策 |
|---|------|------|
| 1 | 技术选型追新求异 | 优先选成熟稳定、交通行业有案例的技术 |
| 2 | 数据架构不考虑存量 | 设计数据迁移和桥接方案 |
| 3 | 忽视国产化对技术选型的约束 | 早期引入国产化专家，技术选型即考虑国产化 |
| 4 | 安全后知后觉 | 安全设计融入架构设计全程，而非事后补丁 |
| 5 | 过度设计导致实施困难 | 按MVP原则，核心架构先行，能力逐步叠加 |
