## 二、适用场景

本工作流适用于在通过RFI筛选出短名单后，对候选供应商进行深度评估，包括PoC（概念验证）、综合打分、尽职调查、实地考察等环节，最终确定推荐供应商。

## 三、前置条件与输入

| 输入项 | 来源 | 说明 |
|-------|------|------|
| 供应商短名单（3-5家） | phase-04-01 | RFI筛选结果 |
| 技术需求与SOW | phase-04-01 | 项目技术需求 |
| 方案评审标准（初步） | phase-04-01 | 评分维度参考 |

## 四、详细步骤说明

---

### 步骤1：短名单确定与评估策略

**目标**：最终确认进入深度评估的供应商名单，制定评估策略。

**输入**：RFI分析报告、供应商长名单
**输出**：短名单确认、评估策略文档

**操作指南**：

**1.1 短名单组成原则**

```
短名单理想组成（3-5家）:

┌──────────────────────────────────────────┐
│ 至少1家 大型综合集成商(SI)                │
│  - 综合实力强、行业口碑好                   │
│  - 风险: 响应慢、创新不足                   │
├──────────────────────────────────────────┤
│ 至少1家 交通行业垂直领域专家               │
│  - 行业理解深、产品成熟度高                 │
│  - 风险: 市场份额小、财务可能不稳定           │
├──────────────────────────────────────────┤
│ 至少1家 技术创新的专业厂商                  │
│  - 技术领先、反应敏捷                      │
│  - 风险: 交付能力未经大规模验证              │
└──────────────────────────────────────────┘
```

**1.2 评估策略制定**

根据项目类型确定评估重点：

| 项目类型 | PoC必要性 | 考察必要性 | 评估重点 |
|---------|:---:|:---:|---------|
| AI/大数据平台 | 必须 | 推荐 | 算法效果、性能 |
| 业务应用平台 | 推荐 | 推荐 | 功能匹配、易用性 |
| 基础平台(IaaS/PaaS) | 必须 | 推荐 | 性能、稳定性 |
| 实施服务为主 | 可选 | 必须 | 团队能力、方法论 |
| 国产化替代 | 必须 | 推荐 | 国产化适配、兼容性 |

### 步骤2：PoC设计与方案

**目标**：设计公平、有针对性、可操作的PoC方案。

**输入**：技术需求、短名单
**输出**：PoC方案文档、PoC评分表

**操作指南**：

**2.1 PoC设计原则**

| 原则 | 说明 |
|------|------|
| 公平性 | 所有供应商相同的场景、数据、环境和时间 |
| 代表性 | 场景覆盖核心需求，能体现供应商能力差异 |
| 可量化 | 结果能客观评分而非主观判断 |
| 时间可控 | 每家供应商PoC执行时间1-3天 |
| 成本可控 | 供应商投入成本在合理范围（避免过高门槛） |

**2.2 交通行业PoC典型场景设计**

```
智慧高速AI视频分析PoC场景设计:

场景1: 交通事件检测（核心场景，权重40%）
  测试数据: 准备2小时真实高速监控视频（含标注）
  测试指标:
    - 停车事件检出率 > 90%
    - 逆行事件检出率 > 95%
    - 行人闯入检出率 > 85%
    - 平均检测延迟 < 5秒
    - 误报率 < 10次/路/天

场景2: 交通参数采集（权重25%）
  测试数据: 多路段多时段视频
  测试指标:
    - 流量统计准确率 > 95%
    - 车速估计误差 < 10%
    - 车型分类准确率 > 90%

场景3: 抗干扰能力（权重20%）
  测试数据: 雨雪/夜间/遮挡等恶劣条件视频
  测试指标:
    - 恶劣条件下的检出率不低于正常的60%

场景4: 平台能力（权重15%）
  测试内容: API调用、批量处理、结果可视化
  测试指标:
    - API响应时间 < 500ms
    - 并发路数支持 > 50路/GPU
```

**2.3 PoC评分表设计**

| 评分项 | 满分 | 供应商A | 供应商B | 供应商C |
|-------|:---:|:---:|:---:|:---:|
| 场景1-检出率 | 20 | | | |
| 场景1-误报率 | 10 | | | |
| 场景2-准确率 | 15 | | | |
| 场景2-覆盖性 | 10 | | | |
| 场景3-抗干扰 | 10 | | | |
| 场景4-平台能力 | 10 | | | |
| 现场表现（专业性、配合度） | 10 | | | |
| 实施建议（合理性、创新性） | 15 | | | |
| **总分** | **100** | | | |

### 步骤3：PoC准备与环境搭建

**目标**：为PoC执行做好所有准备工作。

**输入**：PoC方案
**输出**：PoC环境就绪、测试数据就绪、供应商通告

**操作指南**：

**3.1 PoC准备清单**

| 准备项 | 负责方 | 完成标准 |
|-------|-------|---------|
| 测试环境（服务器/GPU） | 我方 | 环境配置完成、供应商可远程接入 |
| 测试数据集 | 我方 | 视频/图片/文档数据集准备完成、脱敏处理 |
| 测试脚本/工具 | 我方 | 用于评测结果的标准脚本 |
| PoC方案最终确认 | 双方 | 供应商签字确认了解PoC要求 |
| 时间安排 | 我方 | 每家供应商的时间段分配 |
| NDA签署 | 双方 | 保密协议签署完成 |
| 合规审批 | 客户方 | 如果需要客户方资源 |

**3.2 数据准备要点**

- 测试数据必须**脱敏**（车牌、人脸、个人信息）
- 测试数据必须是供应商**未接触过的**新数据
- 测试数据的标注必须经过**双重校验**（两人独立标注一致）
- 准备足够的数据量（避免统计偏差）

---

### 步骤4：PoC执行与评估

**目标**：公平、规范地执行PoC并进行量化评估。

**输入**：PoC方案、环境、数据
**输出**：PoC执行记录、评分结果

**操作指南**：

**4.1 PoC执行流程**

```
单家供应商PoC执行流程:

Day 0: 环境准备
  - 供应商远程接入测试环境
  - 部署供应商系统
  - 预测试（确保环境正常）

Day 1: PoC执行
  09:00-09:30  开场说明（规则重申）
  09:30-12:00  场景1测试
  12:00-13:00  午餐
  13:00-15:00  场景2测试
  15:00-17:00  场景3测试
  17:00-18:00  平台能力演示

Day 2 (如需):
  09:00-11:00  场景4测试 + 补充测试
  11:00-12:00  供应商方案讲解（实施建议）

Day 2/3: 结果统计
  - 我方独立统计测试结果
  - 供应商确认结果
```

**4.2 PoC执行纪律**

| 纪律 | 说明 |
|------|------|
| 统一环境 | 所有供应商使用相同配置的硬件环境 |
| 统一数据 | 所有供应商用同一套测试数据 |
| 统一时间 | 每个场景给予相同的时间 |
| 不允许优化过拟合 | 禁止针对测试数据特调参数 |
| 结果保密 | 不向供应商透露其他供应商的结果 |
| 全程记录 | PoC过程全程记录（屏幕录像/shell日志） |

**4.3 PoC结果处理**

- 客观指标自动计算（脚本自动化评测）
- 主观指标至少2人独立打分后取平均
- 对供应商的反馈点（优缺点）详细记录
- 形成每家供应商的PoC评估分报告

---

### 步骤5：综合评估与打分

**目标**：整合PoC结果与其他评估维度，进行综合打分。

**输入**：PoC评分、技术方案评分、商务评估
**输出**：综合评估矩阵、排名结果

**操作指南**：

**5.1 综合评估维度**

| 评估维度 | 权重 | 数据来源 | 评分方法 |
|---------|:---:|---------|---------|
| PoC技术验证 | 30% | PoC执行结果 | 客观指标+主观评价 |
| 技术方案 | 25% | RFP技术应答 | 专家评审 |
| 行业经验 | 15% | 案例审查 | 案例评分 |
| 团队能力 | 10% | 面试/简历审查 | 面试评分 |
| 商务条件 | 15% | RFP商务应答 | 报价+商务条款 |
| 公司实力 | 5% | 资质/财务审查 | 客观事实 |

**5.2 综合得分计算**

```
综合得分 = PoC×30% + 技术方案×25% + 行业经验×15%
          + 团队×10% + 商务×15% + 公司×5%
```

**5.3 带权重的多人评分**

| 评委 | 权重 | 角色 |
|------|:---:|------|
| 技术负责人 | 30% | 技术评估主导 |
| 业务负责人 | 25% | 业务匹配度评估 |
| 项目经理 | 20% | 实施可行性评估 |
| 采购负责人 | 15% | 商务条件评估 |
| 高层代表 | 10% | 战略匹配度评估 |

---

### 步骤6：尽职调查与考察

**目标**：对排名前2-3的供应商进行尽职调查和实地考察。

**输入**：综合评估结果
**输出**：尽职调查报告、考察报告

**操作指南**：

**6.1 尽职调查清单**

| 调查维度 | 调查内容 | 方法 |
|---------|---------|------|
| 法律合规 | 营业执照、资质证书、无犯罪记录 | 天眼查/启信宝+原件核对 |
| 财务健康 | 近3年评估审查报告、纳税记录 | 财务数据审查 |
| 知识产权 | 核心产品软著/专利、开源合规 | 知识产权清单+抽查 |
| 诉讼纠纷 | 在诉案件、行政处罚 | 裁判文书网+天眼查 |
| 关联关系 | 与客户/方案评审专家有无关联 | 自查+背景调查 |
| 履约能力 | 在手合同量、交付团队规模 | 供应商提供+客户验证 |

**6.2 客户案例验证**

对供应商声称的关键案例进行验证：

| 验证步骤 | 内容 |
|---------|------|
| 1. 文件验证 | 要求提供合同关键页（可脱敏金额）、验收报告 |
| 2. 电话验证 | 致电案例客户的IT/业务负责人（需供应商同意） |
| 3. 实地考察 | 到1-2个代表性案例现场考察系统运行情况 |

**6.3 实地考察要点**

- 看真实系统而非Demo系统
- 与一线使用者而非仅管理人员交流
- 观察系统运行的健康度（BUG数量、响应速度）
- 了解售后服务的响应速度和质量

---

### 步骤7：推荐报告撰写

**目标**：撰写供应商评估推荐报告，供决策层参考。

**输入**：综合评估结果、尽职调查报告
**输出**：供应商评估推荐报告

**操作指南**：

**7.1 推荐报告结构**

```
供应商评估推荐报告:

1. 评估概述
   - 评估背景、范围、过程
   - 参与供应商列表

2. 评估方法
   - 评估维度与权重
   - 评分规则说明

3. 各供应商评估详述
   对每家供应商:
   - 综合评分
   - 竞争优势分析
   - 风险与不足
   - PoC结果
   - 案例验证结果
   - SWOT分析

4. 综合对比
   - 评分矩阵对比表
   - 核心能力对比（雷达图）
   - 关键指标对比（表格）

5. 推荐建议
   - 排名与推荐供应商
   - 推荐理由（核心优势+风险可控性）
   - 备选方案
   - 合作建议（联合体/分包建议）

6. 风险提示
   - 推荐供应商的主要风险
   - 风险缓解建议

附录
   - 详细评分明细
   - PoC测试原始数据
   - 尽职调查记录
```

---

### 步骤8：供应商最终选定

**目标**：完成供应商最终选定，进入合同谈判阶段。

**输入**：推荐报告
**输出**：供应商选定通告、下一步计划

**操作指南**：

**8.1 决策会议**

| 议程 | 内容 | 参与人 |
|------|------|-------|
| 评估过程汇报 | 评估方法和过程说明 | 项目经理 |
| 结果展示 | 各供应商评分和对比 | 技术负责人 |
| 推荐建议 | 推荐供应商及理由 | 项目经理 |
| 讨论决策 | 提问、讨论、投票 | 全体 |
| 下步计划 | 合同谈判安排 | 全体 |

**8.2 选型通告**

- 向选定供应商发出合作意向通告
- 向未选定供应商发出礼貌通告（保护关系，为未来合作留空间）
- 提供简要反馈（有助于供应商改进，维护行业关系）

## 八、常见陷阱与对策

| # | 陷阱 | 对策 |
|---|------|------|
| 1 | PoC变成"选美大赛"不看实效 | 设计严格的客观指标和自动化评测工具 |
| 2 | 供应商在PoC中造假 | 要求部署在我方环境，全程监控 |
| 3 | 评估过于侧重技术忽视实施 | 增加团队面试和交付方法论评估权重 |
| 4 | 忽视供应商的长期稳定性 | 尽职调查中必须审查财务状况和在手合同 |
| 5 | 考察只看"样板工程" | 随机抽取验证案例，联系一线用户 |
