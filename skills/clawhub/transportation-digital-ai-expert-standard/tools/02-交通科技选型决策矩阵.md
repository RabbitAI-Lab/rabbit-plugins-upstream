# 交通科技选型决策矩阵
## Transportation Technology Selection Decision Matrix

---

## 一、工具概述

本工具为交通领域科技选型提供系统性决策框架。涵盖7大评估维度、50+评价指标，包含供应商评分卡、PoC设计指南、TCO计算器、合同谈判清单等完整工具链。适用于信号控制系统、大数据平台、AI平台、综合交通运行协调中心、MaaS平台、车路协同设备、云平台、数字孪生平台等各类交通科技采购决策。

### 适用场景
- 交通科技产品/平台/解决方案选型
- 供应商评估与比选
- Make vs Buy决策分析
- 技术架构评审
- 采购决策汇报材料撰写

### 4.2 评分计算公式

```
维度得分 = SUM(该维度各指标得分 × 指标权重)
加权总分 = SUM(各维度得分 × 维度权重)
```

### 4.3 评分等级判定

| 加权总分 | 等级 | 结论 |
|----------|------|------|
| 4.0 - 5.0 | A | 强烈推荐，可作为首选供应商 |
| 3.5 - 3.9 | B+ | 推荐，适合进入谈判短名单 |
| 3.0 - 3.4 | B | 可考虑，需关注特定风险项 |
| 2.5 - 2.9 | C | 备选，需重大改进后考虑 |
| < 2.5 | D | 不推荐 |

### 4.4 雷达图对比说明

在七维度坐标轴上绘制各供应商得分，直观对比优劣势。通常规则：
- **重叠区域大** = 各供应商能力接近，价格/服务成为关键区分因素
- **某供应商在T维度突出** = 技术导向项目可优先考虑
- **F维度不足但T维度高** = 定制化项目慎选，标准化项目可考虑

## 五、PoC（概念验证）设计指南

### 5.1 PoC决策流程

```
是否需要PoC？
├── 项目投资 > 500万 → 强烈建议PoC
├── 项目投资 200-500万 → 建议PoC
├── 项目投资 100-200万 → 简化PoC（技术验证）
├── 项目投资 < 100万 → 可选
├── 技术成熟度低 / 创新性高 → 必须PoC（不管金额）
└── 已有同规模成功案例 → 可免PoC（仅做参考验证）
```

### 5.3 PoC实施时间线

## 七、合同谈判检查清单（20项）

```
============================================================
            合同谈判检查清单
============================================================

【产品/服务定义】
□ 1. 明确产品名称、版本、模块清单、license类型和数量
□ 2. 明确服务范围（实施、开发、培训、运维的边界）
□ 3. 明确功能交付标准（关键功能清单+验收标准）
□ 4. 明确排除项（哪些不在本合同范围内）

【价格与付款】
□ 5. 明确总价构成（软件/硬件/实施/培训/运维分项报价）
□ 6. 付款里程碑绑定交付成果（非单纯按时间付款）
□ 7. 明确是否包含所有第三方授权（数据库、中间件等）
□ 8. 明确后续年度维保费用及涨幅上限（建议涨幅≤5%/年）
□ 9. 明确扩容/加购的折扣率（锁定未来价格）
□ 10. 明确价格有效期

【实施与交付】
□ 11. 明确项目计划与里程碑（含关键依赖）
```

## 九、Make vs Buy 决策树

### 9.1 决策树流程

```
              ┌─── 是否为差异化核心能力？
              │
          ┌───┤
          │   └─── 是 → 是否有内部研发能力？
          │              ├── 是 → 是否有足够的研发资源（30+人团队）？
          │              │         ├── 是 → 【MAKE】（自研）
          │              │         └── 否 → 【PARTNER】（联合研发/源码购买）
          │              └── 否 → 【BUY+深度定制】（采购+需求定制）
          │
          └─── 否 → 市场上是否有成熟的商业产品？
                       ├── 是 → 产品能否满足80%+需求？
                       │         ├── 是 → 【BUY】（直接采购）
                       │         └── 否 → 【BUY+配置/低代码】（采购+轻量定制）
                       └── 否 → 是否有可靠的开源方案？
                                  ├── 是 → 【OPEN SOURCE】（开源+服务外包）
                                  └── 否 → 【MAKE/重做】（自研）

```

### 9.2 Make vs Buy 评分矩阵

| 评分维度 | 权重 | Make得分 | Buy得分 | 说明 |
|----------|------|----------|---------|------|
| 核心差异化程度 | 20% | /5 | /5 | 越核心越倾向Make |
| 内部研发能力 | 20% | /5 | /5 | 能力越强越倾向Make |
| 上市时间紧迫度 | 15% | /5 | /5 | 越紧迫越倾向Buy |
| 市场成熟度 | 15% | /5 | /5 | 越成熟越倾向Buy |
| 长期拥有成本 | 15% | /5 | /5 | |
| IP保护需求 | 10% | /5 | /5 | |
| 持续迭代需求 | 5% | /5 | /5 | |
| **加权总分** | **100%** | **____** | **____** | |

**判定规则：**
- Make得分 > Buy得分 20%以上 → 强烈建议自研
- Make得分与Buy得分接近（差距<10%）→ 建议联合研发（Buy+源码+共建）
- Buy得分 > Make得分 20%以上 → 强烈建议采购

## 十二、使用说明

1. **确定评估维度权重**：根据项目类型，使用第二节权重配置表调整权重
2. **筛选指标**：根据产品类型，从50+指标中选取30-40个关键指标
3. **供应商评分**：组织评估团队（建议5-7人）独立打分后汇总
4. **PoC验证**：对核心供应商进行PoC验证（参见第五节）
5. **参考客户调研**：至少调研2-3家已有客户（参见第六节）
6. **TCO计算**：完整计算5年总拥有成本（参见第八节）
7. **合同谈判**：按检查清单逐项确认（参见第七节）
8. **形成决策报告**：按模板撰写选型报告（参见第十一节）
