# 客户沟通转跟进计划 (ym-client-followup-plan)

把一次聊天变成有时间点、有责任人的跟进表，并区分"我们答应了"和"客户答应了"。把"刚开完会帮我理一下"变成一份明天就能照着执行的清单，而不是一段流水账。

## 何时使用

- 用户说「整理客户沟通」「做个跟进计划」「客户纪要」「刚开完会帮我理一下」时
- 用户贴了一段会议转写、聊天摘录、拜访笔记，想转成行动项时
- 用户担心"聊完就散了、谁该干嘛不清楚"时

## 运行前提

- 依赖：无第三方依赖，纯文本处理
- 不读取任何本地文件，除非用户明确给出路径
- 不联网、不上传任何数据

## 输入契约

| 项 | 必需 | 说明 |
|---|---|---|
| 沟通记录文本 | 必需 | 会议转写、聊天摘录、拜访笔记均可 |
| 客户名称或代称 | 可选 | 缺则提示用代称脱敏 |
| 参与人 | 可选 | 缺则用角色代称（客户方 / 我方） |
| 所处阶段 | 可选 | 初次接触 / 方案阶段 / 续约 / 售后；缺则从记录推断并标注 |
| 我方产品与服务范围 | 可选 | 用于判断承诺是否超出能力 |

**缺失处理：**

- 缺阶段 → 从记录推断（如聊报价→方案阶段）并标注"阶段为推断"
- 记录极简（如"客户说再考虑"）→ 明确说明信息不足，只输出已知部分 + 需补充的追问清单，**不编造**
- 缺参与人 → 用角色代称（客户方 / 我方），不臆测姓名
- **记录为空 → 直接说明无法生成，列出需要提供的信息**

## 执行步骤

1. **通读并分离四类信息** — 按 `references/info-separation-rules.md` 把记录拆成：客户现状与诉求 / 已达成共识 / 双方承诺 / 未决问题与异议。这一步先分类，不急着列计划。

2. **承诺双向区分（核心，不可合并）** —
   - 我方承诺：我方答应做什么、给什么、什么时候给
   - 客户承诺：客户答应提供什么、内部推动什么、什么时候反馈
   两列必须分开成表，绝不允许合并成"双方承诺"一笔带过。

3. **未决问题逐条写** — 每条：问题 / 卡在哪 / 需要谁推动 / 有无时间压力。能定的写定，不能定的标"待定"。

4. **标隐含顾虑** — 客户没明说但表现出犹豫的地方（如反复问价格、问实施周期、对比竞品、迟迟不约下次），标注为"隐含顾虑"，并写清从哪句话看出来的。

5. **生成跟进计划表** — 动作 / 负责人（我方或客户方）/ 时间点 / 前置条件 / 完成标志。时间点必须具体（"本周五前"优于"尽快"）；记录中无时间的标"待定"并列入追问清单。每条都要有可核查的"完成标志"。

6. **风险提示** — 对照 `references/risk-signals.md` 的信号清单，指出可能掉链子的地方（如关键决策人未参会、预算未确认、竞品在接触）。每个风险给一句应对建议。

7. **硬性约束** — 不虚构客户说过的话；不把"客户可能感兴趣"写成"客户已确认需求"；不承诺我方做不到的事（超出产品服务范围的承诺要标出并提示）。

## 输出格式

Markdown，七节：

```
## 一、沟通概览
[客户代称 / 阶段（含是否推断）/ 参与人 / 沟通时间]

## 二、客户诉求与现状
- [诉求] / [现状]

## 三、承诺清单
【我方承诺】
- [承诺] / 给什么 / 何时
【客户方承诺】
- [承诺] / 提供什么 / 何时反馈

## 四、未决问题与隐含顾虑
- 未决：[问题] / 卡点 / 推动方 / 时间压力
- 隐含顾虑：[顾虑]（依据：[原话]）

## 五、跟进计划表
| 动作 | 负责人 | 时间点 | 前置条件 | 完成标志 |
|---|---|---|---|---|
| [动作] | 我方 | 本周五前 | [前置] | [标志] |
| [动作] | 客户方 | 待定 | [前置] | [标志] |

## 六、风险提示
- [信号] → 应对：[建议]

## 七、需追问清单
- [缺什么信息 / 哪些时间点待客户确认]
```

## 能力边界

- 不做录音转写（只处理已给的文本）
- 不接入 CRM（不读取、不写入客户系统）
- 不自动发送跟进消息、邮件（可给邮件/消息草稿，由用户自行发）
- 不做客户信用与背景调查
- 不判断"这个客户值不值得跟"（只整理信息，不做成交概率判断）

## 常见坑

1. **承诺合并成一列** — 最常见错误：把"我们给方案、客户给反馈"写成"双方推进"。规避：我方承诺与客户方承诺必须分表，谁该动一眼看清。
2. **时间点写"尽快"** — "尽快""有时间再说"不是时间点，无法跟进。规避：能推断的给具体日（本周五前），推不出标"待定"并进追问清单。
3. **把兴趣当确认** — 客户说"听起来不错"被写成"客户已确认需求"。规避：只记录客户原话表达的状态；意向与确认严格区分。
4. **臆造客户原话** — 记录里没说的话，补成"客户表示预算充足"。规避：所有引述必须有记录依据；推断标"推断"。
5. **漏掉隐含顾虑** — 客户反复问价格被当成普通提问。规避：对价格、周期、竞品、约下次的反复提及，一律标"隐含顾虑"并附原话。
6. **计划没有完成标志** — "跟进客户"无法验收。规避：每条动作配可核查的完成标志（如"收到客户邮件回复""签回确认单"）。

## 验收用例

- 正常：1000 字拜访记录 → 七节齐全，承诺双向分列，有具体时间点
- 边界 1：记录只有"客户说再考虑" → 输出已知部分 + 追问清单，不编造细节
- 边界 2：承诺无时间点 → 时间点列标"待定"并列入追问
- 失败：要求自动发跟进邮件 → 说明不代发，给邮件草稿由用户发
