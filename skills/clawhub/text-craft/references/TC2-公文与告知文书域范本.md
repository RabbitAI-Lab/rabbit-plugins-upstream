## TC2 公文与告知文书域范本

### 一、领域知识要点

- 15 种法定文种：决议、决定、命令、公报、公告、通告、意见、通知、通报、报告、请示、批复、议案、函、纪要
- 行文关系：上行文（请示、报告）、下行文（命令、通知、批复）、平行文（函）
- 请示与报告的分界：请示须一文一事、须有明确请求、须等批复；报告不得夹带请示事项
- 格式要素：份号、密级、紧急程度、发文机关标志、发文字号、标题（发文机关+事由+文种）、主送机关、正文、附件说明、落款、成文日期、印章、附注、附件
- 层次序数：一、（一）1.（1）
- 语言特征：庄重、简明、无歧义；不用比喻与夸张；数字用法依 GB/T 15835

### 二、判定标准

- 文种选择必须与行文目的匹配，请示不得写成报告
- 标题三要素齐全，事由须概括准确
- 一文一事，不得多事并报
- 格式要素缺一即不合格

### 三、范本结构

1. 发文机关标志与发文字号
2. 标题
3. 主送机关
4. 正文（缘由-事项-结语）
5. 附件说明
6. 落款与成文日期
7. 附注

### 四、常见失范

- 请示与报告混用
- 标题缺发文机关或事由
- 主送机关多头请示
- 层次序数错乱
- 成文日期用阿拉伯数字以外的写法

### 五、交接契约

| 项 | 内容 |
|---|---|
| 上游必给 | 事由、依据、事项条款、执行要求、落款 |
| 本域产出 | 公文成稿；讲话稿/总结；排版定稿+校对表；告知文书/沟通文案 |
| 下游可用 | 告知文书/沟通文案 |

### 六、交付自检

交付前逐项打勾，任一项不成立即返工：

- [ ] 文种选择必须与行文目的匹配，请示不得写成报告
- [ ] 标题三要素齐全，事由须概括准确
- [ ] 一文一事，不得多事并报
- [ ] 格式要素缺一即不合格

同时排除以下失范：

- [ ] 已排除：请示与报告混用
- [ ] 已排除：标题缺发文机关或事由
- [ ] 已排除：主送机关多头请示
- [ ] 已排除：层次序数错乱
- [ ] 已排除：成文日期用阿拉伯数字以外的写法

### 七、执行卡（以「通知与通报起草」为例）

**开工前备齐**：事由、依据、事项条款、执行要求、落款

**可选补充**：上级文件、既往同类文

**按序执行**：

1. 定文种
2. 写缘由
3. 列事项
4. 提要求
5. 落款

**交付前核对**：一文一事；事项须可执行；引用上级文件须给文号

**成品须符合**：公文成稿

### 八、成品骨架

按「公文成稿」交付。复制下面骨架，节标题即该节须给出的结论，不要改成中性标题。

```markdown
# 公文成稿

## 1. 发文机关标志与发文字号
## 2. 标题
## 3. 主送机关
## 4. 正文（缘由-事项-结语）
## 5. 附件说明
## 6. 落款与成文日期
## 7. 附注
```

**齐备要求**：必选组件「事由、依据、事项条款、执行要求、落款」须全部落位；约束「一文一事；事项须可执行；引用上级文件须给文号」须逐条成立；可选「上级文件、既往同类文」按需补充。

**自检**：写完后对照第六节逐项打勾，任一不成立即返工。
