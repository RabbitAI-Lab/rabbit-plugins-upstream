# M24 — 增量唯一 ID 设计

## I — 方法论重写

**核心命题**：M14 增量同步讲"策略"（指纹缓存 / 批量写入 / 频率控制），M24 讲"标识"——如何为每条数据设计唯一且稳定的 ID，让增量抓取能区分"已抓"和"未抓"。

**5 种唯一 ID 设计策略**：

### 策略 1：URL 解析 ID（推荐，最稳定）
- **来源**：从条目 URL 中解析参数
- **示例**：`https://community.airtable.com/t/topic/12345` → `tid = "12345"`
- **优势**：天然唯一，不会变，URL 不变则 ID 不变
- **劣势**：需要 URL 规律性强

### 策略 2：API 原生 ID
- **来源**：API 响应中的原生字段
- **示例**：`{"id": "abc123", "title": "..."}` → `id = "abc123"`
- **优势**：API 自带，无需解析
- **劣势**：部分 API 不返回 ID，或 ID 不稳定（如用数组索引）

### 策略 3：字段组合哈希
- **来源**：多个字段拼接后做哈希
- **示例**：`hash(title + author + publish_time)` → `"a1b2c3d4"`
- **优势**：无原生 ID 时可用
- **劣势**：字段变更（如标题被编辑）会导致 ID 变化

### 策略 4：内容指纹
- **来源**：整条数据 JSON 序列化后做 MD5
- **示例**：`md5(json.dumps(record, sort_keys=True))` → `"e5f6g7h8"`
- **优势**：检测内容变更（同一 ID 但内容不同 = 已编辑）
- **劣势**：计算成本高，仅适合小数据量

### 策略 5：时间戳+序号
- **来源**：`publish_time + index`
- **示例**：`"20260726_001"`
- **优势**：天然有序，支持按时间增量
- **劣势**：不是真正的唯一 ID，需配合其他字段

### 选择决策树

```
有 URL？ → 用策略 1（URL 解析 ID）
  ↓ 否
API 返回 id 字段？ → 用策略 2（API 原生 ID）
  ↓ 否
有多个稳定字段？ → 用策略 3（字段组合哈希）
  ↓ 否
数据量小（<10000）？ → 用策略 4（内容指纹）
  ↓ 否
有发布时间？ → 用策略 5（时间戳+序号）+ 反问用户
  ↓ 否
→ 终止：必须有唯一 ID 才能增量，反问用户业务主键是什么
```

## A1 — 书中案例

**Airtable 社区案例**：
- 候选 1：`post_id` 字段 → API 返回但部分帖子缺失
- 候选 2：`topic_url` → 稳定但需解析
- **最终选择**：从 `topic_url` 中解析 `tid`（如 `/t/topic/12345` → `"12345"`）
- **理由**：URL 最稳定，不会变，且解析简单

**Monday 论坛案例**：
- 候选 1：`id` 字段 → API 返回，稳定
- **最终选择**：直接用 API 原生 `id` 字段
- **理由**：API 自带，无需额外解析

## E — 可执行步骤

**AI 给用户的诊断步骤**：

```
要做增量抓取，需要先设计唯一 ID。请回答：

1. 每条数据有 URL 吗？URL 规律是什么？（如 /t/topic/12345）
2. API 返回的数据里有 id 字段吗？稳定吗？
3. 有没有发布时间字段？

根据你的回答，我会推荐：
- 策略 1：URL 解析 ID（最稳定）
- 策略 2：API 原生 ID
- 策略 3：字段组合哈希
- 策略 4：内容指纹
- 策略 5：时间戳+序号
```

**AI 内部执行步骤**：

```
1. 分析 API 响应结构，识别可用作 ID 的字段
2. 按决策树选择最佳策略
3. 设计增量缓存（JSON 文件 / SQLite / 飞书多维表格）
4. 实现增量逻辑：
   - 抓取新数据
   - 对比已缓存 ID
   - 过滤掉已存在的
   - 只写入新数据
   - 更新缓存
5. 输出完整代码 + ID 设计说明
```

## B — 边界与盲点

### 适用边界
- ✅ 增量抓取场景（必须有唯一 ID）
- ✅ 去重场景（多次抓取后合并）
- ✅ 数据同步场景（与外部系统对账）
- ❌ 一次性全量抓取（不需要增量，直接抓完即可）

### 盲点与陷阱
1. **ID 不稳定**：用标题做 ID，标题被编辑后变成新数据 → 用 URL 或 API 原生 ID
2. **ID 冲突**：不同条目有相同 ID（如 API bug）→ 加前缀（`post_123` / `reply_456`）
3. **ID 泄露**：ID 含敏感信息（如用户邮箱）→ 做哈希处理
4. **缓存膨胀**：缓存所有 ID 会越来越大 → 用 LRU 淘汰或定期归档
5. **并发冲突**：多进程同时抓取 → 用 Redis 分布式锁
