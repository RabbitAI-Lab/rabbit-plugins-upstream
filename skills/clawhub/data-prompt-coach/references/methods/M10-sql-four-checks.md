# M10 SQL 4 必看点

> **核心定位**：审查 AI 生成 SQL 的 4 个必看清单。

## R (Reading) 原文引用

> "检查 SQL 的几个必看点：1. JOIN 类型对不对 2. 时间边界 3. 去重 4. 业务口径"

## I (Interpretation) 重写方法论

**4 必看清单**：

```
1. JOIN 类型
   → 该用 LEFT JOIN 的地方别用成 INNER JOIN
   → 检查：关联表是否有 NULL 值？有 NULL 必须用 LEFT

2. 时间边界
   → 是 >= 还是 >？"近30天"含不含今天？
   → 检查：跟 AI 确认时间口径

3. 去重
   → COUNT 要不要 DISTINCT？
   → 多表 JOIN 后很容易出现行数翻倍
   → 检查：跑一条样本数据看行数对不对

4. 业务口径
   → 比率类指标（续费率/转化率）的分子分母定义
   → 检查：永远要自己再确认一遍
```

**关键认知**：AI 写的 SQL "逻辑对、口径错"是最常见的坑——4 必看是最后一道防线。

## A1 (Past Application) 书中案例

小陈活跃学员 SQL（教程场景 3）：
- JOIN：4 表关联，检查是否该用 LEFT
- 时间：近30天完成 + 近7天登录，边界要对
- 去重：COUNT(DISTINCT user_id) vs COUNT(user_id)（多对多关系易翻倍）
- 口径：续费率 = 有续费订单的活跃学员 / 全部活跃学员

## A2 (Future Trigger) 何时会需要

- **用户说**：任何 AI 生成的 SQL 审查
- **场景**：场景 3 SQL 生成
- **与相邻 skill 的区分**：
  - vs M3 80/20 协作：M3 是协作姿势（分工），M10 是具体审查清单
  - vs M7 验真闭环：M7 是通用验真，M10 是 SQL 专属

## E (Execution) 可执行步骤

1. **查 JOIN 类型**：该 LEFT 是否写成了 INNER？
2. **查时间边界**：>= vs >？含不含今天？
3. **查去重**：COUNT 要不要 DISTINCT？跑样本看行数
4. **查业务口径**：比率指标的分子分母定义对不对？

## B (Boundary) 边界与盲点

**不适用于**：
- NoSQL 查询（无 JOIN 概念）
- 已审查过的存量 SQL
- 单表简单查询（无 JOIN 无比率）

**作者盲点**：教程只列了 4 个必看点，对"窗口函数边界""CTE 性能""索引使用"等进阶审查点没展开——但这些是高级 DBA 才需要关注的，对教程目标用户（数据分析师/运营/HR）4 个已够。
