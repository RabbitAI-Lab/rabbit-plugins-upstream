# M13 中间逻辑可追溯

> **核心定位**：AI 分析可信度机制——拒绝结果黑盒，任何中间步骤可追问可校验。
>
> **来源**：v3.1 教程蒸馏（不止是写代码·TRAE 数据分析 + 5 步采集到可视化）

## R (Reading) 原文引用

> "中间逻辑可追溯、可追问：拒绝'结果黑盒'，你可以针对分析过程中的任何中间步骤进行追问和校验（如：'为什么这么过滤？'），确保逻辑百分之百准确。"
> "每步输出修改内容 + 校验结果，最后输出最终表格。"

## I (Interpretation) 重写方法论

**可追溯五要素**：

```
1. 中间产物显式输出
   → 每个分析步骤输出"中间产物"：
     - 过滤条件（"筛掉了哪些行？为什么？"）
     - 聚合逻辑（"按什么字段聚合？聚合函数是？"）
     - 计算公式（"这个比率怎么算的？分子分母是？"）
   → 不只输出最终结果，还要输出推导过程

2. 可被追问
   → 用户可在任意中间步骤插入追问
   → AI 必须能解释每个中间产物的来源
   → 例："为什么这个字段被过滤掉了？"→ AI 回答过滤规则 + 具体被过滤的行数

3. 推导链完整
   → 任何结论必须附带"数据 → 处理 → 结论"的完整路径
   → 无法解释推导过程的结论不输出
   → 推导链可追溯到原始数据行

4. 拒绝结果黑盒
   → 输出"结论"时必须同时输出"这个结论怎么来的"
   → 例：✅ "Q3 销售额下降 15%，因为 A 渠道下降 30%（具体数据行 23 条），B 渠道持平"
   →    ❌ "Q3 销售额下降 15%"

5. 逻辑校验点
   → 在关键中间步骤设置校验点
   → 用户可在校验点插入验证逻辑
   → 例：在"过滤"步骤后设置校验点 → "过滤后剩多少行？是否符合预期？"
```

**关键原则**：
- 中间产物优先于最终结果——先输出过程，再输出结论
- 每个结论必须有推导链——无推导链的结论是"黑盒"，禁止输出
- 用户可在任意步骤插入追问——AI 必须能回答
- 推导链可追溯到原始数据——不只到"过滤后"为止，要能追到"原始哪几行被过滤了"

**反常识**：AI 时代的核心需求不是"更快"，而是"更可解释"——用户对 AI 结果的不信任是合理的，AI 必须主动证明自己的逻辑。

## A1 (Past Application) 书中案例

**教程 1 场景五 · 安全修改**：
```
【第一步：价格更新】
- 所有"电源设备"类别单价下调 3%
- 所有"配件"类别单价上调 2%
- 校验：确认单价均为正数，库存总值=库存数量×单价

【第二步：供应商统一】
- "思科系统" → "思科系统（中国）有限公司"
- 校验：确认无供应商名称为空的记录

【第三步：状态重算】
- 重新计算所有产品的库存状态
- 校验：确认状态与库存数量/安全库存的关系正确

【第四步：异常检测】
- 标记库存数量为负数的记录
- 标记单价异常高（>50000）或异常低（<50）的记录
- 标记安全库存>库存数量 3 倍的产品

每步输出修改内容 + 校验结果，最后输出最终表格。
```

每一步都输出"修改内容 + 校验结果"——这就是中间逻辑可追溯的典型应用。

**教程 3 · Stack Overflow 分析**：
- "为什么这么过滤？" → AI 必须能回答过滤规则
- "中间逻辑可追溯、可追问" → 任何中间步骤可校验

## A2 (Future Trigger) 何时会需要

- **用户说**："为什么这个结论""这个怎么算的""逻辑是什么""我要校验"
- **场景**：6 周报 / 7 深度报告 / 3 SQL 生成（SQL 必须可解释）
- **信号**：用户对 AI 输出的结果不放心，想验证推导过程
- **与相邻 skill 的区分**：
  - vs M2 防幻觉三招：M2 是防编造（亮证据+禁脑补），M13 是可追溯（推导链完整）
  - vs M7 验真闭环：M7 是事后抽查，M13 是过程中显式输出
  - vs M12 下钻分析：M12 是发现新维度，M13 是验证已有结论

## E (Execution) 可执行步骤

1. **显式输出中间产物**：每个分析步骤输出过滤条件/聚合逻辑/计算公式
2. **构建推导链**：从原始数据 → 处理 → 结论的完整路径
3. **设置逻辑校验点**：在关键步骤设置校验点，用户可插入验证
4. **接受追问**：用户任意时刻可问"为什么 X？"，AI 必须能回答
5. **输出校验报告**：每步输出"做了什么 + 校验结果"

**Prompt 骨架**：
```
【分析步骤】
Step 1: [过滤] 规则=[具体规则]，过滤前=[N 行]，过滤后=[M 行]
        校验：[通过/失败 + 原因]

Step 2: [聚合] 字段=[字段名]，函数=[SUM/AVG/COUNT]
        校验：[通过/失败 + 原因]

Step 3: [计算] 公式=[具体公式]，分子=[值]，分母=[值]
        校验：[通过/失败 + 原因]

【最终结论】
[结论] ← 推导链：Step 1 → Step 2 → Step 3

【可追溯性】
- 原始数据行号：[X 到 Y]
- 推导过程：见上述 Step 1-3
- 校验结果：[全部通过/部分失败]
```

## B (Boundary) 边界与盲点

**不适用于**：
- 采集/提取类任务（场景 1/2）——这些是确定性提取，无推导过程
- 简单查询（场景 3 部分）——单表 SELECT 无需推导链
- 实时性要求极高的查询——显式输出推导过程会增加响应时间

**与 M9 分步提问联动**：
- M9 的"每步结果人工检查"需要 M13 的中间产物显式输出
- M13 的"可被追问"在 M9 的分步流程中更容易实现

**与 M4 任务拆解联动**：
- M4 拆解后的每一步都应输出中间产物（M13）
- 步骤之间的数据传递需标准化（避免格式转换损失信息）

**作者盲点**：
- 教程没讨论"推导链的存储与复用"——一次分析的推导链应可保存，下次相同任务可复用
- 教程没讨论"推导链的可视化"——长推导链用文字描述难读，建议用流程图
