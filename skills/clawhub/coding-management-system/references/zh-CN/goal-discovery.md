# 目标发现

当用户只有概念、问题、方向或期望结果，但不知道软件应该如何实现时使用。

## 低负担访谈

每轮最多询问三个问题，只询问会明显改变以下内容的问题：

- 期望结果；
- 主要用户或使用场景；
- 最小有用流程；
- 法律、隐私、安全、数据、预算或环境边界；
- 可观察的成功；
- 昂贵或不可逆选择。

不要要求用户选择框架、数据库、API 风格、托管平台、测试框架或架构，除非该选择存在用户可感知的取舍。

用户回答“不知道”时：

1. 提供两到三个普通语言选项；
2. 每个选项用一句话说明实际差异；
3. 推荐一个默认选项；
4. 明确该推荐是假设，之后可以修改。

不要重复询问对话、仓库或当前项目状态已经回答的问题。

## 解释需求

使用以下结构重述：

```text
期望结果：
谁会受益：
当前问题：
最简单有用结果：
已知约束：
已确认事实：
AI 推断：
待确认事项：
```

不能把 AI 推断当作已确认事实。

## 准备度阶梯

| 状态 | 已理解内容 | 下一步 |
| --- | --- | --- |
| `Concept` | 大致想法或问题 | 明确结果与受益者 |
| `Direction` | 结果与主要使用方式 | 提出最简单有用流程 |
| `Ready for Planning` | MVP 边界和成功证据 | 评估规模 |
| `Ready for Execution` | 范围、验收、约束、权限 | 授权执行 |
| `Owner Decision Required` | 重大选择不能安全推断 | 提供选项并只等待该决定 |

不因可逆的不确定性阻塞。记录假设并采用最安全、低成本默认方案。

## Intent Brief

使用 `{baseDir}/templates/zh-CN/INTENT_BRIEF.md`。默认在聊天中生成；只有用户要求、开始规划或其他 Agent 需要交接时，才保存一份规范文件。

Brief 必须区分：

- 现在必须工作；
- 以后有用；
- 明确不在当前范围；
- 假设；
- 能证明有用的证据。

## 推荐一个下一步

最后给出一个推荐动作、为什么先做、以及应产生什么证据。只选择一个：

- 澄清一个阻塞决策；
- 观察当前工作流；
- 检查已有仓库；
- 不写代码先验证用户流程；
- 创建低成本原型；
- 定义验收示例；
- 评估目标规模；
- 创建 Active Packet；
- 开始已授权执行；
- 因价值或可行性不足而简化、暂停或拒绝。

不要给出没有优先顺序的长清单。
