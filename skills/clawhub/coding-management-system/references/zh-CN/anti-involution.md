# 反内卷 2.2

治理内卷指的是：项目持续产出看起来正确的治理产物，但产品本身停止前进。本文件定义识别信号、文档预算与退出规则。当项目文档很多而交付很少、当有人要求重基线、或当同一个风险反复出现时加载。

## 识别信号

出现以下任意两条，即判定为内卷活跃信号，并作为**结论本身**上报，而不是附注：

| 信号 | 典型表现 |
| --- | --- |
| 文档量超过代码量 | 治理文档的数量或体积超过它所描述的代码 |
| 文档增长而行为不变 | 一个汇报周期内只产出文档，没有代码改动，也没有新的已验证行为 |
| 层层作废注释 | 在生效的权威文件里出现 `Superseded`、`CURRENT OVERRIDE`、`本段作废` 之类的批注 |
| 风险反复顺延 | 同一个实质性风险连续出现在多次 `Accepted With Risk` 判定中 |
| 已验收但未发布 | 工作进入 `Accepted`，但用户侧什么都没上线 |
| 门禁需要人离开键盘 | 某个里程碑因为一项人工检查而"差一点验收"地挂上数周 |
| 状态自我覆盖 | STATUS / TARGET 文件被原地改写，而不是重基线后归档 |

## 文档预算

- 保持活跃治理文档集可以在一次阅读中读完。实务上就是：Active Packet、Loop Log、一份合并后的 Work Order、一份当前 QA 判定，再加当前基线。
- 其余全部是历史，移入 `Docs/archive/YYYY-MM.md`。是移动，不是删除。
- 新增一份文档时，必须指出它取代了哪一份。没有前任的新文件，通常是一个重复的状态归属。

## 归档纪律

正确：

```text
Docs/TARGET.md  -> git mv Docs/archive/2026-09.md/TARGET.md
newDocs/REBASELINE-2026-09-06.md  （新的当前权威）
```

错误：

```text
Docs/TARGET.md
  > 已被 2026-09-01 修订版取代。
  > CURRENT OVERRIDE：忽略以上段落。
```

错误的写法迫使未来每个读者和 Agent 去重建"哪一层才生效"，并且让冲突检测无法自动化。

## 重基线纪律

重基线是追加式的，绝不原地修改：

1. 把新基线写成 `REBASELINE-<YYYY-MM-DD>.md`（若项目已有日期化基线惯例则沿用该惯例）；
2. 在同一次改动中归档旧基线；
3. 更新 Active Packet 的 authority fingerprint；
4. 在派发新 Work Order 之前，对新基线跑一次 Alignment。

方向对齐不改写目标。重基线之后必须另起一次 Planning / Dispatch。

## Accepted With Risk 的退出条件

`Accepted With Risk` 只有在四项齐全时才成立：

1. 核心结果确实可用；
2. 剩余缺口被写成明确的解锁条件；
3. 有责任人；
4. 有日期。

缺任一项，它就不是带风险的验收，而是一个挂着绿牌的未决阻塞。同一 Program 连续三次正式 `Accepted With Risk`，在继续扩张前触发 Direction Alignment。

## 止损

治理需要预先承诺的退出条件，否则一条弱线会被沉没成本一直养着：

- 止损线在开工前设定：预算上限、时间上限或证据阈值。
- 触及上限时，默认动作是归档，不是续期。
- 已耗尽预算且只产出文档而未产出行为的项目，应连同"可复用部分清单"一起上报归档。
- 为了逃离卡点而重启同一个目标，是失败模式。正确做法是把范围砍到最小可发布增量。

## 减项闸门

当出现新方向、新功能或新项目提案时：

1. 先说明为了让出空间，将砍掉、暂停或归档什么；
2. 如果说不出来，新事项就排队等待；
3. 优先把一条"数据到用户价值"的链路做深，而不是再开一条平行的。
