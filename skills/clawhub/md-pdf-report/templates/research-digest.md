# Research Digest Template (研究消化)

消化**已有的**研究产物（提案 / 论文 / 博客 / 论坛帖 / 媒体报道）→ 结构化中文摘要 → PDF → 飞书投递。

**与 `research-report.md` 的关键区别：**

| | research-report | research-digest |
|---|---|---|
| **输出性质** | 自己的研究输出 | 消化别人的研究 |
| **批判性分析** | 可选 | **REQUIRED**（Helen 反谄媚原则） |
| **社区讨论** | 通常无 | **必出**（如源材料是论坛帖 / 有讨论） |
| **来源** | 自己整理 | **必须**带超链接、作者、日期、阅读量 |
| **一句话总结** | 建议 | **必出**（包含 价值 + 代价 + 成熟度） |

**Best for：** ethresear.ch 提案、ArXiv 论文、官方博客、媒体报道、关键论坛帖。

# 标题：<原标题中文译名>

<div class="callout">

**TL;DR：** 1-3 段把整个消化结果讲清楚，含：核心问题、提出方案、关键反例。读者只看这一段也能 get 80% 价值。

</div>

## 一、核心问题（一句话）

不要长。**问题 + 本质归类**两段就够。
例：「问题：… 本质：这就是 X 问题的另一种说法。」

## 二、传统/现有方案的处理方式 + 硬伤

讲清楚**为什么这个问题之前没解好**。
重点不是堆事实，是讲**结构性缺陷**（不是单点失败）。

## 三、原始方案的核心机制

- **用代码块/数学公式**把核心机制讲清楚（不要回避公式）
- 关键恒等式 / 不变量 / 守恒律 用 `callout` 框出来
- 机制上的"意外等价"（如「本提案本质就是标量预测市场」）单列一节
- 数学验证：分情况走一遍，证明恒等式在边界条件下也成立

## 四、怎么用 / 操作流程

- 给出最直接的使用场景
- 把「反直觉的困难」明确标出（避免读者高估方案成熟度）
- 推荐策略 / 算法 / 步骤用编号列表

## 五、与现有方案对比（**必出表格**）

至少 3-5 个对比维度，每个维度有具体判断。
**表格比段落更利于决策。**

## 六、代价 / 风险 / 局限

- 数学上的代价（漂移率 / 复杂度 / 边界条件）
- 经济上的代价（流动性 / 对手方风险 / 滑点）
- 适用边界（哪些场景适合、哪些不适合）

## 七、社区讨论 / 后续实现（**有则必出**）

如果源材料是论坛帖 / 有讨论 / 有后续实现：
- 引用关键**反对意见**和原作者回应
- 引用**已工程化**的实现（带合约地址 / commit hash / vault 地址）
- 引用**开放问题**（"待解决"项）
- 每条引用都标楼层号 + 日期

## 八、批判性分析（**REQUIRED per anti-sycophancy**）

<div class="callout">

**这一节必须有。** 不要只罗列原方案的优点。逐项找：

1. **隐含假设** — 作者默认了但未证明的前提
2. **未验证的声明** — 数字 / 比率 / 边界条件缺乏严肃推导
3. **适用边界** — 方案只在小范围有效，但在大众市场可能失败
4. **被忽视的反例** — 原作者没考虑的场景
5. **承认原作者做对的事** — 不是为了反对而反对，是**真评价**

至少 3 条**具体**反例（不是空话）。

</div>

## 九、一句话总结

> 用一句话讲清楚：**价值 + 代价 + 当前成熟度**。
>
> 模板：「X 提出用 Y 替代 Z，代价是接受 W，N 天后已被工程化（实现位置），但仅在 A 子集有效。」

- **主源：** [<标题>](URL) — 作者 / 日期
- **关键引用：** [链接1](URL) | [链接2](URL)
- **已实现代码：** 合约地址 / GitHub URL（如有）
