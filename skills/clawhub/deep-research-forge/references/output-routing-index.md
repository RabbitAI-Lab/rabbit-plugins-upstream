# Output Routing Index

Choose one main artifact for the current turn. Add appendices only when they make the artifact reusable.

Before using this index, select a method stack with `research-methodology-atlas.md` and `methodology-routing-index.md`. Then use `dynamic-output-composer.md` to add or remove modular blocks.

## `research-brief`

Use when the user wants to quickly understand a topic or decide whether deeper research is worth it.

Asset:

- `assets/research-brief-template.md`

Must include:

- research question
- one-line answer with confidence
- compact evidence base
- time, snapshot, and mechanism notes
- next verification step

## `deep-research-report`

Use when the user asks for a full study, strategic understanding, or a report that can be shared.

Asset:

- `assets/deep-research-report-template.md`

Must include:

- evidence window
- claim citation map for load-bearing claims.
- narrative time axis
- competitive / substitute snapshot
- mechanism analysis
- future scenarios
- action recommendation and monitoring gaps

## `competitive-map`

Use when comparison, substitutes, ecosystem position, or user choice is the dominant need.

Asset:

- `assets/competitive-map-template.md`

Must include:

- category definition
- direct competitors, indirect competitors, substitutes, and likely challengers
- comparison dimensions tied to user jobs
- evidence gaps for volatile claims

## `concept-lineage-timeline`

Use when the user asks for a concept, paradigm, technology, theory, or cultural phenomenon's development history, origin, evolution, or long arc.

Asset:

- `assets/concept-lineage-timeline-template.md`

Must include:

- scope choice: technical, intellectual, product / industry, policy, or mixed.
- evidence ledger with source type and reliability.
- periodized deep timeline, not just a date list.
- schools, definitions, and disputes.
- mechanism shifts across data, compute, algorithm, interface, institution, and regulation where relevant.
- current snapshot and reversal conditions.

This output can stand alone or become the lineage section inside a deep-research-report.

## `decision-brief`

Use when the user needs a go / hold / no-go style answer.

Assets:

- `assets/decision-brief-template.md`
- `references/decision-rubric.md`

Must include:

- verdict and confidence
- key assumptions
- evidence supporting and weakening the verdict
- reversal conditions
- next action

## `research-asset-pack`

Use when the user wants material that can be reused, updated, delegated, or turned into later writing.

Asset:

- `assets/research-asset-pack-template.md`

Must include:

- evidence ledger
- source map
- claim citation map for load-bearing reusable claims
- reusable timeline notes
- comparison notes
- open questions
- monitoring list
- follow-up search queries

Do not turn an asset pack into polished prose. It is a working research base.

## `parallel-research-plan`

Use when the user explicitly requests multi-agent execution or the lead-integrator needs to coordinate independent research lanes before producing the final artifact.

Asset:

- `assets/parallel-research-plan-template.md`
- `assets/sample-parallel-research-sprint.md`

Must include:

- why parallel execution is justified
- role-level tasks and source targets
- shared definitions
- specialist return contract
- merge checklist
- final synthesis owner

This is an execution scaffold, not the final research answer. Pair it with the user's requested artifact: brief, report, map, decision brief, or asset pack.

Use the sample only as a structural example. Refresh all claims, evidence IDs, dates, and confidence for real research.

## `research-retrospective`

Use when the user asks how a real research run performed or what should be improved next.

Assets:

- `references/research-retrospective-protocol.md`
- `assets/output-blocks/research-retrospective-block.md`

Must include:

- overall score with a short reason.
- scorecard across question fit, method fit, evidence traceability, formal status clarity when relevant, mechanism depth, dissent, actionability, and composition quality.
- root causes using the retrospective issue labels.
- the next highest-leverage fix.
- whether the fix belongs in execution, a rule, an asset, or an eval.
- ship / revise / rerun decision when the user asks whether the report is good enough.

Do not rewrite the whole report unless the user asks for a new version.
