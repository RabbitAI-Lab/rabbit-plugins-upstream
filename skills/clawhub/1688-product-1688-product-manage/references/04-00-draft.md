# 草稿组装、保存与交付

当前商品已有有效发布字段，且用户目标包含创建草稿时读取。

## 从文件组装

取 `category.json.categoryId` 为 `catId`，`scene` 固定 `aigc`；将五份字段文件按原结构放入 `publishData`：

```text
{
  "catId": 当前真实类目ID,
  "scene": "aigc",
  "publishData": {
    "title": title.json中的title,
    "imageList": imageList.json中的imageList,
    "catProp": catProp.json中的catProp,
    "skuTable": skuTable.json中的skuTable,
    "detail": detail.json中的detail
  }
}
```

这里表示字段映射，实际请求是合法 JSON 对象。不要把来源、任务 ID、候选结果或工具整个 dataJson 当作 publishData。

## 组装前检查

核对当前商品已被用户选中或在明确的连续执行授权内，绑定店铺一致且无未解除的终止状态，类目已按接口顺序采用，SKU 已核对且必填维度和值齐全（价格库存可空，无必填规格可无规格），产物来自本商品本次有效任务且依赖未变。标题、CPV、SKU 直接组装 [生产规则](03-00-production.md) 的已采用字段文件，不再次核对事实依据或与输入逐行比较，也不反向覆盖原始输入文件。已有创建草稿授权就继续，不把展示草稿摘要或内部整理结果作为保存前置条件。

检查必要字段与映射：五项存在、类型可组装；主展示图 1—5 张；所有实际用图均有本地对应与图片银行回执，详情中的 URL 可逐个映射；categoryId 与本次 schema/生成输入一致。不能只看域名证明图片银行来源。此处不检查三个素材工具的语义、SKU 组合/数值是否与输入相同或 CPV 各项是否有原素材依据。

可用 [本地脚本](../scripts/prepare_payload.py) 组装并检查必要字段、JSON 和详情图 URL 映射：

```sh
python3 <skill目录>/scripts/prepare_payload.py assemble --product <商品目录>
```

脚本只读文件并向标准输出给出 JSON，不访问网络、不创建草稿，也不验证真实入库或三个素材工具的内容正确性。工具回执、任务归属和图片来源仍由 Agent 核对；脚本通过不代表发品成功。将完整请求和组成文件的校验值保存至 `text/draft/request.json`，再调用 `1688_publish_product_draft_save`。

## 判断保存结果

调用前再次检查已有 `draftId` 和未知结果标记。只在未保存、未处于结果未知状态时提交；用户明确另建一份的任务另记尝试身份。

保存原始回执至本次 draft 尝试记录。先识别明确业务错误与下述 null 规则；外层成功且 `dataJson` 解析得到真实非空 `draftId` 才记“已保存”；数字 ID 转字符串时保持完整，不截断。其他未知/矛盾返回按 [恢复规则](00-02-recovery.md) 核实，不立即重提。

草稿保存接口实际返回 JSON `null`（含宿主原样呈现的文本 `null`），或明确返回的 `dataJson` 为 null/JSON 文本 `"null"` 且无其他具体业务错误时，按草稿箱已满处理。该约定仅针对草稿保存的业务结果，不包括字段缺失、`draftId:null`、空字符串、超时、断网、工具执行异常或其他接口的 null。明确权限/参数/系统错误优先按实际错误解释，不能被伴随的 null 覆盖。

真实 ID 作为查询参数安全编码后，生成：

```text
https://offer-new.1688.com/aigc/publish.htm?draftId=<真实draftId>&operator=draft2offer
```

说明.md 记录真实 ID、链接、请求与回执位置。保存成功即完成当前商品链路并交付，不再审核内容，不调用浏览器、web_fetch 或页面截图打开草稿检查。保存失败/结果未知也只依据请求、回执和已有记录说明问题，不自行转网页排查。保存成功但消息交付失败时只重发链接，不再保存一次。

## 保存报错：先识别原因，再说明下一步

查看实际请求、外层成功标识和回执中的 `errorCodes`、`message`/`errorMessage` 等实际错误字段，以及可解析的 `dataJson` 业务错误。保留原始回执与错误码；不要仅凭“执行失败”猜草稿数量超限，不把工具传输成功当保存成功。

| 回执/证据 | 判断与处理 |
|---|---|
| 上述 null 业务结果，或明确草稿容量已满 | 记录 `stopReason: DRAFT_CAPACITY_FULL`，提示“草稿箱已满，请前往 PC 端检查并清理草稿后再试。”停止当前发布及同店铺剩余发布，保留本地素材、请求、回执，不自动重试、不自动删除草稿、不宣称保存成功。回执未给容量数字就不编数字，也不误说成 SKU 库存不足 |
| 明确提示字段缺失、类型或格式错误 | 说明实际字段与要求。若是本地组装/编码导致，可在不改素材工具原始业务值的前提下修正格式后重试一次；若来自工具内容或缺少业务信息，说明原因并请求对应补充/处理，不借报错主动清洗三个工具的输出 |
| 明确未授权、无操作权限或店铺不匹配 | 请用户检查绑定/选择的店铺和授权；不索要 Token，不自行换店保存 |
| 明确限流、服务不可用或临时系统错误 | 简短说明服务暂不可用，保留状态，按回执建议稍后继续；不能断言用户资料错误或草稿箱已满 |
| 超时、连接断开、未收到业务回执，无法判断是否已保存 | 标记保存结果待核实，查已有记录或请用户核对草稿箱；核实前不重复提交，避免重复草稿；与接口实际返回 null 区分 |
| 只有通用失败文案，没有具体原因 | 如实说明“草稿暂未保存成功，接口没有返回明确原因”，给出可用错误码/请求标识供排查；不编故障原因。若提交是否落地也不明确，仍按结果待核实处理 |

只按上述业务判定做恢复；信任素材生成结果不意味着忽略保存工具的真实拒绝。对用户采用“当前状态 + 原因 + 下一步”的短句，不贴堆栈或敏感回执。容量满后，用户确认已处理并明确要求继续时才恢复，不自行定时重试。失败不套用成功四行格式，不给虚构链接；已明确保存成功则不重新创建。

## 对用户的成功格式

```text
店铺：<当前发品店铺名，无法取得则写未获取>
类目：<采用的真实类目路径>
标题：<本次保存请求中的标题>
草稿：[点击编辑草稿](<基于真实draftId的链接>)
```

上面代码块只解释格式，实际回复不要放在代码块中；四项各占一行，使用 Markdown 硬换行或空行确保分行，草稿链接必须可点击。不把参考商品店铺当成发品店铺。

四行简短结果外可加一两句自然引导，例如“商品草稿已保存，打开链接即可继续编辑。还有其他商品要发布吗？”不附文件目录、生成过程、完整 SKU、价格库存表或逐字段解释，尤其不透出修改、纠正、删除了什么及其内部理由。必要实质问题在处理该问题时说明，不在正常成功结果里复盘。保存草稿不能说成正式上架，没有 draftId 不能给链接或计入成功。

批量默认交付当前商品后问一句“接下来发哪款？”可列剩余商品简称，不再展示全批缺口问卷。用户已指定下一件或明确授权全部顺序执行时不重复问，串行推进并保留已交付状态；收尾仅简短汇总成功/待处理数量，未交付的成功项按四行格式补齐，失败只说明必要原因和下一步，不重复堆全部过程。
