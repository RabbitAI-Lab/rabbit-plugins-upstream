# S5 · 贡献计量与分配设计器

## R — 原文 (Reading)

> 这套"贡献即确权、确权即分配、分配可追溯"的价值治理新范式改变了"资本主导分配"传统逻辑……智能合约将"按劳动分配""按贡献分配"的规则以代码自动执行分配给个体、机构，体现其在生产、协作、服务等环节的贡献所得。

## I — 方法论骨架 (Interpretation)

这套范式的核心，是把"谁该分多少"从拍脑袋变成可计算的事。它走四步：

1. **确权**：把每个人的行为、资源、关系、时间、知识等贡献先上链，变成不可抵赖的原始记录——这一步解决"贡献说不清"的问题。
2. **计量**：用通证当"贡献刻度尺"。通证在这里不是炒的标的，而是三合一的计量工具——记账凭据（记下了多少劳动）、权利凭据（对应多少收益/治理权）、结算凭据（预言机捕获事件后自动清算）。
3. **分配**：把这些规则写进智能合约，按约定比例把收益自动打给贡献者，跳过中心化平台"先抽成、再主观裁量"的老路。
4. **可追溯**：从贡献发生到分润到账全链路留痕，任何人可查、不可篡改。

它的真正颠覆不在技术，而在生产关系：用"行为贡献代码化分配"替换"按出资/股权分配"，让资本不再天然主导。但注意——四步里"计量"与"写入合约"是关键落点，也是最容易翻车的地方（见 B 段）。

## A1 — 书中的应用 (Past Application)

### 案例 1: IP STORY 可编程版权分润（第一章 全球演进案例1）
- **问题**：独立音乐人依赖中心化平台，收益被中介层层抽走，流媒体收入不足 15%，原创者拿不到应得的份额。
- **方法论的使用**：把作品信息上链确权（确权）→ 智能合约记录创作、演奏、传播各方贡献（计量）→ 按约定比例实时自动分润，如 Justin Bieber《Peaches》全球版税实时分配（分配+可追溯）。
- **结论**：创作者 / 合作者 / 传播节点按贡献自动获激励，形成多方共赢，而非平台独吞。
- **结果**：已在多领域落地，验证了"行为上链 + 自动化分润"的闭环可行。

### 案例 2: OORT 去中心化 AI 数据云（第一章 全球演进案例2）
- **问题**：AI 训练算力/存储成本高（AWS/Google Cloud 昂贵），分散在全球的闲置算力无法被可信整合与结算。
- **方法论的使用**：以区块链为激励层聚合全球算力，用"贡献激励 + PoH（算力证明）"验证每个节点贡献（计量+确权），智能合约自动调度与结算（分配+可追溯）。
- **结论**：分散资源被可信整合，贡献"可追溯、结果可验证"。
- **结果**：成员遍布 130+ 国家、超 35 万人；中国实践 DataHub 助云天励飞计算时间缩短约 35%、成本降低约 50%。

### 案例 3: 海数交（海南）RDA 服务平台（第一章 中国大陆案例19）
- **问题**：数据加工贸易中，模块化任务协同、工作量计量与分账缺乏可信自动化机制。
- **方法论的使用**：搭建联盟链 + 价值凭据 HAI + 工作量证明 POW + 智能合约分账；共建者以 POW 计工作量、HAI 计价结算（计量→分配），RDA 上架流通（可追溯）。
- **结论**：社会力量可买入 RDA 份额支持实体数智化，按社区模型智能合约自动分账。
- **结果**：建成海南数据流通基础设施，支持"来数加工"形成收入并自动分账。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计社区/平台分润机制，想替代平台抽成、按贡献而非按出资分配。
2. 想让多方（创作者/合作者/传播者/共建者）公平分钱，但苦于没有可信计量。
3. 设计通证经济模型或积分激励体系，担心分配不公、分配不可信、规则被少数人操纵。
4. 搭建共建社区，需要把"消费即投资、行动贡献即投资"落成可计量、可分配的权益。
5. 需要把"贡献即确权"从口号落成可审计、可回溯的自动化规则（写入合约）。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么让多方按贡献公平分润 / 公平分钱？"
- "不想让平台抽成，想按贡献分配。"
- "怎么设计通证 / 积分的分配规则？比例怎么定？"
- "怎么把用户贡献计量出来、自动发奖励？"
- "贡献即确权 / 确权即分配 怎么落地成代码？"

### 与相邻 skill 的区分

- 与 **S6 共建社区运营框架**（p20 主）的区别：S6 偏"如何搭建与运营事业共同体、用四融转化资源、设计黏性工具"，是组织与运营视角；S5 偏"把多元贡献可信计量并公平分润的可代码化经济模型"，是分配机制设计与合约落地视角。用户问"怎么让社区活跃/怎么拉共建者"用 S6；问"贡献怎么计量、收益怎么分、规则怎么写进合约"用 S5。
- 与 **S1 通证/代币化概念辨析器**（rwa01/f11/f10）的区别：S1 解决"某说法属于哪一层通证、是否触碰金融属性"的定性合规判定；S5 解决"拿到通证工具后怎么设计分配规则与计量模型"。S1 是"定性"，S5 是"定量设计"。
- 与 **S8 RWA 落地流程与路径设计器** 的区别：S8 是端到端十环节作业手册；S5 聚焦其中"经济模型设计 + 分配上链"这一子环节，可作为 S8 的分配模块调用。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **枚举可计量贡献类型**
   - 完成标准：列出本社区/平台的全部贡献维度（资本、劳动、资源、关系、时间、知识、数据、传播等），并明确区分"可客观计量"（如算力、订单、数据量、消费额）与"难客观计量"（如创意、声誉、关系）两类，输出一张贡献清单表。

2. **设计通证计量与分配规则**
   - 完成标准：产出经济模型草案——每种贡献 → 通证计量口径（记账凭据）→ 权益映射（权利凭据）→ 分配比例（结算凭据）；同时标注各项是商品/治理型（非金融、境内可探索）还是债权/股权型（需境外合规通道）。
   - 判停条件：若任一关键贡献无法客观计量（如创意、声誉），则跳转步骤 3 先做社区协商与抽检机制，不强行代码化。

3. **社区确认后写入智能合约并设可追溯**
   - 完成标准：分配规则经创始团队与共建者商议、社区确认，写入经形式化验证的智能合约自动执行；全程链上可追溯，并预置多源预言机 + 应急开关（kill switch）与责任边界条款。
   - 判停条件：若涉及境内发行代币化融资或面向零售募资，则必须先触发 S2 合规红线检查 + S10 跨境备案路径，本步不可直接执行。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 仅把"发个币/积分"当营销噱头、并无真实贡献计量意图 → 应先做 S1 概念辨析或 S6 社区运营，而非用 S5 严谨设计经济模型。
- 只做概念科普/定性讨论 → 用 S1 概念辨析器。
- 项目处纯融资导向（链改-资产支持型融资）且面向境内零售 → 必须先做 S2 合规红线检查，本 skill 的分配设计不可绕过备案。

### 作者在书中警告的失败模式

- **智能合约代码偏差与预言机喂价错误的责任真空（ce04）**：链上自动执行但链下责任主体不明（开发者、发行人、预言机商、托管方责任划分不清），损失无追责通道。须用多源预言机 + 形式化验证 + 应急开关约束。
- **错误输入被"不可篡改+自动执行"放大（ce05）**：预言机/合约被攻击或数据源错误，触发错误清算形成死亡螺旋，本金永久性、不可逆损失。
- **"伪 RWA"借"贡献即确权"叙事行集资之实（ce18）**：历史上大量项目以"赋能实体/贡献分配"为包装实为变相融资盘或代币炒作；若缺乏强监管，"贡献即确权"易被操作为新型集资工具，普通参与者风险极高。

### 作者的盲点 / 时代局限

- **"代码化分配必然更公平"未证**：假设智能合约分配天然优于人工，却忽略规则本身由少数人定义，存在"代码即法律"的寡头风险。
- **"贡献可被通证精准计量"未证**：现实中部份贡献（创意、关系、声誉）难以客观度量，强行量化会失真。
- **立场局限**：编写组含项目方与服务商，对失败案例/落地难度的披露可能选择性弱化，对本 skill 的"可代码化"乐观预期需打折。

### 容易混淆的邻近方法论

- 与 **S6 共建社区**（组织运营 vs 分配机制设计）、**S1 概念辨析**（定性 vs 定量）、**S8 RWA 路径**（全链路 vs 分配子模块）的区别见 A2。
