# 团队一图流数据架构

当用户说“团队情况一图流”“团队看板”“一张图了解团队”“A4 概览”“团队概况升级版”时，使用本参考。

目标：在一张 A4 纵向图里呈现团队管理者最需要的态势判断，并提供同构 Markdown 文字版。图版用于快速决策，文字版用于弱智能体兜底、复制和追溯。

## 固定数据包

先运行：

```bash
python3 scripts/team-dashboard.py --format all
```

脚本会写入 `data/insights/team-dashboard-YYYYMMDD.svg`、`.md`、`.json`。三种输出必须来自同一个数据包，不要让图版和文字版使用不同结构。

数据包结构：

1. `meta`: 生成时间、观察窗口、主库路径。
2. `kpis`: 团队健康、证据覆盖、控制压力、势能差。
3. `summary`: 管理结论、亮点/机会、关键注意、需关注成员。
4. `coverage`: 成员数、近窗事件数、相关方反馈、活跃/高优先/逾期/等待/沉默待办、高频类别。
5. `members`: 成员状态、近期信号、正向/关注事件、活跃待办、最新证据、下一步管理动作。
6. `actions`: 未来 7 天动作、未来 30 天动作。
7. `context`: `team-memory-overview.md`、`upward/expectations.md`、`company/strategy.md` 摘录。
8. `evidence`: 最近证据索引，保留日期、事件 ID、对象、摘要、来源文件。

## 管理视角

输出时优先回答四个问题：

1. 当前团队是“稳定进攻、可控需跟进、压力偏高、优先止血”中的哪一类。
2. 最大管理杠杆是什么：授权放大、风险闭环、协作修复、证据补齐、目标对齐。
3. 哪些成员需要本周动作，哪些成员值得给更高挑战或沉淀方法。
4. 哪些判断只是线索，不能直接用于绩效、晋升或处罚。

不要只罗列记录。要把信息压缩成“结论 -> 数据 -> 人员 -> 风险 -> 动作 -> 证据”的顺序。

## A4 图版布局

使用 `scripts/team-dashboard.py` 生成的 SVG 作为默认图版。不要临场发明新的版式，除非用户明确要求重设计。

版式分区：

1. 页眉：标题、日期窗口、输出说明。
2. KPI 条：团队健康、证据覆盖、控制压力、势能差。
3. 管理结论：一句总体判断 + 2-3 个机会。
4. 关键注意点：风险、待办、证据盲区和相关方问题。
5. 人员雷达：优先显示风险最高或最值得关注的成员。
6. 未来动作：7 天动作和 30 天动作分开。
7. 数据控制台：事件、待办、相关方、类别分布。
8. 证据索引：最近关键证据，保留事件 ID。

文字必须短。图版每个要点尽量不超过 28 个汉字；成员动作尽量是一句话。不要把一图流变成报告截图。

## Markdown 兜底

如果环境不能展示图片，直接返回脚本生成的 Markdown，结构必须保持：

1. 管理结论
2. 关键数据
3. 人员雷达
4. 7 天动作
5. 30 天动作
6. 背景摘录
7. 证据索引

Markdown 版可以比图版略详细，但不要超过一屏半；需要深挖时再追溯成员 `timeline.md`、相关方 `timeline.md` 或 `tasks.md`。

## 判断边界

- 图版中的健康分和势能差是管理启发指标，不是绩效评分。
- 线索级、未核实反馈只能放在“注意点/待核实”，不能写成成员结论。
- 绩效、晋升、处罚类判断必须回到具体日期、事件 ID、证据等级和原文。
- 记录覆盖不足时，要明确写“证据盲区”，不要用沉默推断表现。
- 团队级结论要同时参考 `upward/expectations.md` 和 `company/strategy.md`；没有这两类文件时，要提示补齐背景。
