# Decision Rules

## 事实判断

将信息拆为三类：

| 类型 | 定义 | 输出要求 |
|---|---|---|
| 已确认事实 | 用户明确提供、资料明确存在或人工确认的信息 | 可以写入“已确认事实” |
| 用户判断 | 用户对原因、责任、影响或可能结果的判断 | 标为“用户判断”或转为待验证 |
| 待确认信息 | 缺少来源、尚未确认、时间或结果未定的信息 | 标为“待确认”，不得写成事实 |

## 承诺判断

出现以下情况时必须提醒：

1. 未经相关部门确认就承诺时间。
2. 未经评估就承诺结果。
3. 将预计时间表达为确定时间。
4. 将内部讨论方案表达为最终方案。
5. 将他人建议表达为正式结论。

稳妥表达：

- “目前还不能确认最终时间。”
- “需要先完成评估后再同步可执行安排。”
- “建议先对外表达为正在确认，并约定下一次更新时间。”

## 推责风险判断

出现以下表达时必须改写：

1. 指责某部门动作慢。
2. 暗示某个人失职。
3. 暴露内部协调混乱。
4. 用情绪化语言催促。
5. 把复杂问题简化为单一责任人问题。

改写原则：

1. 先描述事实。
2. 再说明影响。
3. 最后提出具体请求。

## 推进判断

一条合格的协同内容至少包含：

1. 当前状态
2. 待确认事项
3. 责任角色
4. 下一步动作
5. 期望反馈时间
6. 无法按时反馈时的更新方式

## 信息不足判断

关键信息不足时，不生成看似完整的结论。优先输出：

1. 当前可以确认的内容
2. 待确认事项
3. 建议向内部补充确认的问题
4. 可暂时使用的保守沟通版本
