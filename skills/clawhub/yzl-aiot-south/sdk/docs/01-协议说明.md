# 01 · 南向接口协议说明

本文是实现依据，也是 SDK 的行为说明。内容来自平台“开放接口 / API 文档”页面，并在 2026-11-04 用测试设备对 `ciot.yzlkj.com` 做了抓包验证。平台后续可能调整字段，遇到不一致时以平台文档和实际报文为准。原始报文摘录见 [08-实测报文.md](08-实测报文.md)。

---

## 1. 环境与端点

| 环境 | 设备服务器 | TCP | UDP | MQTT |
|---|---|---:|---:|---:|
| 测试 / 教学 | `ciot.yzlkj.com` | 41032 | 40501 | 1883 |
| 正式生产 | `siot.yzlkj.com` | 41032 | 40501 | 1883 |
| 农污控制器（旧） | 同上 | 40032 | — | — |

- Web/开放 API 统一走 `https://aiot.yzlkj.com`，但**设备南向连接不走 443**，而是上面这些端口。
- 设备属于哪个环境由平台设备记录决定。测试设备连 `siot` 会提示设备不存在/认证失败；反之亦然。
- 41032/40501/1883 均为明文，无 TLS。

## 2. 通用报文

所有上行功能共用同一个 JSON 信封：

```json
{
  "top": "func",
  "ter": "WANCD1-0000000007",
  "data": [
    {
      "func": "facs",
      "args": ["wd", "25.3"],
      "fid": "F1"
    }
  ],
  "ack": "12345"
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `top` | TCP/UDP 必填 | `func`=上行功能；`order`=下行指令；`result`=平台回执 |
| `ter` | 必填 | 终端 ID，即平台设备 ID |
| `data` | 必填 | 功能数组，可一次携带多个功能 |
| `func` | 上行必填 | 功能名，见第 6 节 |
| `args` | 视功能 | 参数数组 |
| `fid` | 可选 | 帧序号，平台回执原样带回，用于请求/响应配对 |
| `ack` | UDP 推荐 | UDP 消息号，平台回执原样带回，用于丢包判断 |

MQTT 的 **上行 payload 省略 `top`**（平台文档示例如此），只保留 `ter` / `data`：

```json
{"ter":"WANCD2-0000001008","data":[{"func":"facs","args":["kk1","1"],"fid":"F1"}]}
```

MQTT 下行 `down/order` 仍带 `"top":"order"`。

### 返回码（`result.code`）

| code | 含义 | 设备侧处理 |
|---:|---|---|
| 0 | 成功 | — |
| 1 | 参数错误（缺必填/格式不对） | 检查 args、时间戳、单包点数 |
| 2 | 对象不存在（设备/固件/指令） | 检查设备 ID、固件 ID、指令 tra |
| 3 | 认证失败（密码错误） | 检查设备密码；不要重试到封禁 |
| 4 | 未登录（TCP 未 lgn / UDP 未先 lgn_facs） | 先登录/唤醒，再发业务 |
| 9 | 未知函数 / 服务器内部错误 | 检查 func 拼写；稍后重试 |

> TCP 回执里还会带 `"ack":""`（即使请求没有 ack）。这是平台行为，解析时忽略即可。

## 3. TCP 长连接（41032）

### 3.1 连接与登录

```text
TCP connect ciot.yzlkj.com:41032
  → {"top":"func","ter":"DEV","data":[{"func":"lgn","args":["PASSWORD"],"fid":"L1"}]}\n
  ← {"top":"result","ter":"DEV","data":[{"func":"lgn","code":0,"result":"SESSION_TOKEN","fid":"L1"}],"ack":""}\n
```

- 明文 JSON，**一行一帧**，以 `\n` 结尾；平台回执也带 `\n`。
- 连接建立后第一件事必须是 `lgn`；未登录就发 `facs` 会返回 `code=4`。
- `lgn` 成功返回会话 token。当前平台**不强制**后续报文带 token，SDK 不保存/不回传。
- 默认密码规则是“型号 ID 小写 + 2026”，但设备详情页可能显示独立“认证密钥”；以设备详情页为准。

### 3.2 一次请求、多条回执

一个 `data` 数组里放多个功能时，平台会**每个功能返回一行**。例如：

```text
→ {"top":"func","ter":"DEV","data":[
     {"func":"order_conf","args":["T1"],"fid":"C1"},
     {"func":"facs_reply","args":["T1","DEV","sw","1"],"fid":"F2"}
   ]}\n
← {"top":"result","ter":"DEV","data":[{"func":"order_conf","code":0,"result":null,"fid":"C1"}],"ack":""}\n
← {"top":"result","ter":"DEV","data":[{"func":"facs_reply","code":0,"result":null,"fid":"F2"}],"ack":""}\n
```

因此 SDK 的 RX 必须按行拆分；`aiot_client_rx()` 可以一次喂任意长度，内部会处理半包/粘包。

### 3.3 下行指令

平台主动推送：

```json
{"top":"order","ter":"DEV","data":[{"cmd":"set","args":["DEV","sw","1"],"tra":"a1b2c3d4"}],"ack":"3724261884"}
```

- `cmd`：`set` / `get` / `upfs`
- `args`：`[设备ID, 设施键, 目标值]`（set）或 `[设备ID, 设施键]`（get）
- `tra`：事务 ID，回执时必须原样带回
- 设备应先回 `order_conf`（已收到），执行后再回 `facs_reply`（执行结果 + 实际值）。

### 3.4 心跳

```json
{"top":"func","ter":"DEV","data":[{"func":"hear","args":[],"fid":"H1"}]}
```

- 周期应小于型号的 `keepalive_sec`（默认 300 秒）。SDK 默认 60 秒发一次。
- 心跳只刷新 `last_seen`/在线状态，不携带数据。
- 平台对长时间无数据的连接会断开；SDK 在 `keepalive_sec × 2` 无任何回执时上报 `AIOT_EV_TIMEOUT`。

## 4. UDP 低功耗（40501）

### 4.1 唤醒 + 数据一体上报（免登录）

```json
{"top":"func","ter":"YZLSTM1-0000000018","data":[
  {"func":"lgn_facs","args":["PASSWORD","YZLSTM1-0000000018","wd","28.5","sf","60.1"],"fid":"L1"}
],"ack":"12345"}
```

```json
{"top":"result","ter":"YZLSTM1-0000000018","data":[
  {"func":"lgn_facs","code":0,"result":null,"fid":"L1"}
],"ack":"12345"}
```

- 每个 UDP 数据报就是一个完整 JSON；平台按数据报回复。
- `args[0]` 是密码，`args[1]` 是设备 ID，之后是键值对。
- `ack` 原样回传；设备可用它判断丢包/匹配响应。
- **不要连续 pipeline**：先发 `lgn_facs`，等它的回执后再发 `get_order`/`get_time`。实测连续发送时，`get_order` 可能先被处理而返回 `code=4 未登录`。

### 4.2 拉取挂起指令

```json
{"top":"func","ter":"DEV","data":[{"func":"get_order","args":[],"fid":"G1"}],"ack":"67890"}
```

有指令时：

```json
{"top":"result","ter":"DEV","data":[{"func":"get_order","code":0,
  "result":{"cmd":"set","args":["DEV","kk1","1"],"tra":"895ab2c9"},"fid":"G1"}],"ack":"67890"}
```

无指令时 `result=null`。设备执行后仍需 `facs_reply`。

### 4.3 校时

```json
{"top":"func","ter":"DEV","data":[{"func":"get_time","args":["1"],"fid":"T1"}],"ack":"12347"}
```

平台文档写 `"1"` 返回 Unix 时间戳，但实测测试环境返回的是格式化字符串：

```json
{"func":"get_time","code":0,"result":"2026-11-04 01:05:14","fid":"T1"}
```

SDK 不做假设，`result_text` 原样给出；设备侧应同时兼容“数字时间戳”和“格式化字符串”。

## 5. MQTT（1883）

### 5.1 连接认证

| 参数 | 值 |
|---|---|
| Broker | `ciot.yzlkj.com:1883`（测试）/ `siot.yzlkj.com:1883`（生产） |
| Client ID | 设备 ID，例如 `AIOTMQ-0001` |
| Username | 设备 ID（与 Client ID 相同） |
| Password | 设备密码 |
| 协议 | MQTT 3.1.1 |
| TLS | 平台未提供 8883；当前为明文 |

实测：匿名连接返回 `Not authorized`；用“设备ID + 设备密码”可成功 CONNACK。

### 5.2 Topic

| 方向 | Topic | QoS | 说明 |
|---|---|---:|---|
| 设备 → 平台 | `south/{product}/{device}/up` | 1 | 设备上报主通道 |
| 平台 → 设备 | `south/{product}/{device}/down/order` | 1 | 下行指令 |
| 平台 → 设备 | `south/{product}/{device}/down/result` | 1 | OTA 等请求的平台回复 |
| 第三方订阅 | `north/{product}/{device}/data` | — | 北向实时数据（只读） |

设备必须订阅两个 `down` topic。`{product}` 是型号 ID，`{device}` 是设备 ID。

### 5.3 上行/下行 payload

上行（省略 `top`）：

```json
{"ter":"DEV","data":[{"func":"facs","args":["temp","24.5"],"fid":"F1"}]}
```

下行 `down/order`（带 `top`）：

```json
{"top":"order","ter":"DEV","data":[{"cmd":"set","args":["DEV","sw","1"],"tra":"f9e6b5133a9827e4"}],"ack":"..."}
```

设备回执同样发到 `up`：

```json
{"ter":"DEV","data":[
  {"func":"order_conf","args":["f9e6b5133a9827e4"]},
  {"func":"facs_reply","args":["f9e6b5133a9827e4","DEV","sw","1"]}
]}
```

MQTT 平台**不回**普通 `facs` 的 result（与 TCP 不同）；写入结果通过北向 topic 或业务 API 查看。`get_time` 在 MQTT 下也不保证有回执，设备应尽量用 TCP/UDP，或依赖本地 RTC。

## 6. 上行功能

### 6.1 `facs` 实时数据

```json
{"top":"func","ter":"DEV","data":[
  {"func":"facs","args":["dc","4.49","kk1","0","fv","V12-260612"],"fid":"F1"}
]}
```

- `args` 是扁平键值对：`[k1,v1,k2,v2,...]`
- 键必须在型号设施定义内；未定义键在 `autoAddMetrics=0` 时会被丢弃
- 值建议用字符串（平台按 `dataType` 转换）。实测 `"25.5"`、`"60"`、`"1"` 均可正确写入 decimal/int/enum
- 平台按**收到时间**入库，并刷新在线状态、参与告警

### 6.2 `facs_his` 历史补传

```json
{"top":"func","ter":"DEV","data":[
  {"func":"facs_his","args":[
    1792714948,"kk1","11","vot","221.5",
    1792716748,"kk1","12",
    1792718548,"kk1","13"
  ],"fid":"H1"}
]}
```

- 时间戳必须是**数字**（Unix 秒），不能是日期字符串
- 遇到下一个数字即开始下一时间点
- 单包 ≤ 1000 个数据点；超出整包拒绝
- 时间范围：> 2000-01-01，且 ≤ 当前时间 + 60 秒
- 补传不刷新在线状态、不触发告警、不推北向实时流
- 同一时间点重复补传是幂等覆盖

### 6.3 `lgn_facs` UDP 唤醒

见 4.1。`aiot_udp_wakeup()` 与 UDP 模式下的 `aiot_report()` 都会生成它。

### 6.4 `hear` 心跳

```json
{"top":"func","ter":"DEV","data":[{"func":"hear","args":[],"fid":"H1"}]}
```

### 6.5 `facs_reply` 指令执行结果

```json
{"top":"func","ter":"DEV","data":[
  {"func":"facs_reply","args":["a1b2c3d4","DEV","kk1","1"],"fid":"F2"}
]}
```

`args[0]` 是原 `tra`；`args[1]` 是设备 ID（平台文档说可选，SDK 固定带上）；之后是执行后的实际键值对。

### 6.6 `order_conf` 收到确认

```json
{"top":"func","ter":"DEV","data":[{"func":"order_conf","args":["a1b2c3d4"],"fid":"C1"}]}
```

平台把指令状态从 `pending` 推进到“已送达”；执行完再发 `facs_reply` 推进到 `succeeded`。SDK 默认在收到 order 时自动发送。

### 6.7 `get_time` 校时

```json
{"top":"func","ter":"DEV","data":[{"func":"get_time","args":["1"],"fid":"T1"}]}
```

### 6.8 `gfinfo` / `gfcet` OTA

```json
{"func":"gfinfo","args":["fw_1a2b3c"],"fid":"I1"}
{"func":"gfcet","args":["fw_1a2b3c",1],"fid":"I2"}
```

`gfinfo` 返回版本、总包数、单包大小、总字节数、整包 CRC；`gfcet` 返回 `{"fmid","no","pro","data"}`，`data` 是大写 hex 字符串。

平台也可能通过下行 `upfs` 主动推分片：

```json
{"cmd":"upfs","args":["0","4","512","A8FF3C..."],"tra":"fw000001"}
```

## 7. 下行指令

### 7.1 `set`

```json
{"top":"order","ter":"DEV","data":[
  {"cmd":"set","args":["DEV","kk1","1"],"tra":"a1b2c3d4"}
]}
```

执行后：

```json
{"top":"func","ter":"DEV","data":[
  {"func":"facs_reply","args":["a1b2c3d4","DEV","kk1","1"],"fid":"F2"}
]}
```

### 7.2 `get`

```json
{"top":"order","ter":"DEV","data":[
  {"cmd":"get","args":["DEV","wd"],"tra":"895ab2c9"}
]}
```

执行后：

```json
{"top":"func","ter":"DEV","data":[
  {"func":"facs_reply","args":["895ab2c9","DEV","wd","28.5"],"fid":"F3"}
]}
```

### 7.3 `upfs`

```json
{"top":"order","ter":"DEV","data":[
  {"cmd":"upfs","args":["0","4","512","A8FF3C..."],"tra":"fw000001"}
]}
```

设备回 `order_conf` 即可；需要可靠确认时再逐包 `facs_reply`。

## 8. 实测中发现的坑

1. **TCP 回执可能一次读到多行**：必须按 `\n` 拆，不能假设一次 `recv` 一帧。
2. **`get_time` 返回类型和文档不一致**：测试环境返回 `"2026-11-04 01:05:14"` 而不是数字。设备侧兼容两种。
3. **UDP 不能把 `lgn_facs` 和 `get_order` 立刻连着发**：会出现 `get_order` 先到、返回 `code=4`。先等 `lgn_facs` 回执。
4. **TCP 未登录发业务返回 `code=4`**：SDK 在 `AIOT_STATE_WAIT_LOGIN` 会拒绝业务发送，避免浪费配额。
5. **MQTT 匿名必失败**：必须 `clientId=设备ID`、`username=设备ID`、`password=设备密码`。
6. **MQTT 普通上报没有回执**：不要等 `facs` 的 result；用 TCP/UDP 做需要确认的场景。
7. **测试/生产环境域名不同**：`ciot` vs `siot`，设备记录决定环境。
8. **下行 `tra` 必须原样回传**：否则平台无法把指令关联到 `succeeded`，会超时。
9. **`facs_his` 时间戳必须数字**：写成 `"2026-11-04 01:00:00"` 会整包参数错误。
10. **UDP 数据报不要超过 MTU 太多**：建议单包 < 1200 字节，避免分片丢包；大量补传用 TCP。

## 9. 安全

- 三个南向端口都是明文。生产环境应在设备侧使用 APN/VPN，或在网关做 TLS 终结。
- 设备密码是长期凭证；不要硬编码在公开固件/仓库。建议一机一密 + 安全存储。
- 平台用户账号（Web 登录）和 API Key 不应下发到设备；设备只用设备密码。
- 如果设备被克隆，平台侧只能看到同一个设备 ID；建议在业务层加入设备指纹/序列号校验。
