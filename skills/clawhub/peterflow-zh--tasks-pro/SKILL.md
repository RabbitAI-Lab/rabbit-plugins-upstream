# 拆分执行单元

输入是已有目标、设计、验收及当前实现；文档名称和来源不限。产物仍是一份 tasks.md，按 Phase（阶段）→ Task（任务）分组。每个 Phase 就是独立执行单元，不再增加一层单元，也不建立第二份任务账本。

## 定位输入

确定工作区及唯一资料目录，读取适用项目规则、.peterflow/standards/ 的有关规范、需求、计划、现有任务和验证。已有其他资料根目录则沿用。不要求 constitution、外部 Skill、Issue 平台或通用初始化。

方案不足时只补影响切分的决定，标明受影响单元和解除条件；不凭空替用户确定产品语义。给单元列出新材料的写入路径时，详细设计归 `design/`，参考资料归 `references/`，验证记录归 `verification/`，实施交付物归 `delivery/`，跨团队或跨系统契约归 `contracts/`。由写入者在保存第一份实际文件时创建相应目录。保留现有资料，同名非目录或符号链接冲突先说明。拆任务不需要创建分支、暂存或提交。

## 切分与覆盖

1. 列出范围内目标、接口契约及必要验证，沿用编号或稳定章节引用，先理清依赖再切单元。
2. 每个单元交付一个可观察的结果。按行为切分；共享前置确实阻塞其他工作时才独立成单元，并给出自身验收。
3. 为每个 Phase 写清目标、需求依据、直接依赖、所属 Task 和验收。单列实施者获准修改或新建的产物路径。实施者只改列出的产物并回报结果；只有主执行者在原任务清单勾选 Task、更新 Phase 状态和证据位置。交接时区分现在能读的输入、前置阶段将交出的产物和本阶段才创建的输出。写清下一位执行者从哪个目录、用哪个入口消费前置产物，去哪里找其验收证据。交接前实际打开必读资料，已有其他位置直接沿用。
4. 容量包括阅读、实现、排错、评审和测试，不用行数或固定 token 保证一次能做完。涉及多个未知系统时先安排有明确产物的调查，或继续拆小。
5. 最终 Phase 直接或间接依赖其余必要阶段。给跨阶段接通指定具体 Task，写出用户入口、经过的前置产物和可观察结果。分别运行各模块测试只能证明各自的行为。

## 写入与恢复约定

新建可用 [阶段任务模板](assets/tasks.md)，示例编号为 P001、T001；Task 编号在整份清单中唯一，每个任务只归属一个 Phase。现有 U001 等单元可直接作为 Phase 续接，沿用原编号体系、任务和证据路径，不为命名重排已完成工作。公共上下文保存影响所有阶段的范围、授权、项目规则及验证条件。

单元状态用以下语义；现有同义标记无需为格式迁移：

| 状态 | 含义 |
| --- | --- |
| 未完成 | 有实现、评审或验证工作待做 |
| 未验证 | 实现已有，必要验证未完成或旧证据失效 |
| 受阻 | 缺明确的决定、环境或执行能力，记录解除条件 |
| 已完成 | 全部任务、内部评审和必要测试成立，有当前有效证据 |

实际运行失败要记录失败现象和后续修复，不能写成已通过。任务勾选描述已做工作，单元状态描述整体是否验收；二者不互相替代。

更新时保留已有编号、完成事实和历史证据，重排或拆走剩余工作不会使旧结果自动通过。新增缺口放回相应单元，补齐真实前置关系，更新最终单元的覆盖；受影响的旧验收标为未验证并说明原因。避免让修复工作依赖正在等待它修复的失败验收。

标准模板交付前运行 `python3 <本技能目录>/scripts/check_dependencies.py --require-final <任务文件>`。[随包检查](scripts/check_dependencies.py) 核对编号、任务依赖环及最终阶段的依赖覆盖。跨阶段引用 Task 时，按该 Task 所属的 Phase 检查阶段之间能否排出执行顺序。再逐条核对跨阶段行为是否真有接通与验收。旧 U 编号、平铺清单或自定义字段继续按原格式核对，注明工具覆盖范围。交付时给出首个可执行单元、前置产物和阻塞项。
