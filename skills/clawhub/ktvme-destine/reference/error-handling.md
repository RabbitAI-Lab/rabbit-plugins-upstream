# 错误处理指南

> 📖 **通用约束**：详见 [api-overview.md](./api-overview.md)

---

## 接口调用错误处理

### 网络相关错误

| 错误类型 | 处理策略                                             |
| -------- | ---------------------------------------------------- |
| 网络超时 | 等待1秒后重试，最多3次                               |
| 连接失败 | 检查网络，向用户提示"网络连接失败，请检查网络后重试" |
| searchCompany 超时 | 等待3-5秒后重试，最多3次（该接口首次调用偶尔超时）|

### 业务逻辑错误

| 错误类型     | 处理策略                                           |
| ------------ | -------------------------------------------------- |
| 时段已被预订 | 向用户说明情况，询问是否更换时段或包厢             |
| 包厢不存在   | 重新调用 queryRoomAvailability 查询可用包厢       |
| 门店不存在   | 重新调用 searchCompany 查询门店                    |
| 活动不存在   | 重新调用 queryRoomAvailability 获取活动            |

### 查询返回空结果

| 场景 | 可能原因 | 处理策略 |
| ---- | -------- | -------- |
| queryRoomAvailability 返回 `hour_packages: []` | 未传 `begintime`/`endtime` | **加上时间参数重试**（最常见原因）|
| queryRoomAvailability 仍返回空（已传时间参数） | 门店未发布该日期的可预订资源 | 尝试不同日期；建议致电门店 |
| 所有查询均返回空 | 门店未在系统发布线上房态 | 提供门店电话，建议致电预订 |


### 登录状态错误

| 错误类型           | 处理策略                          |
| ------------------ | --------------------------------- |
| status=0（未登录） | 调用 subflow-login 完成登录后重试 |
| 会话过期           | 同上                              |

### "当前未选择操作门店" 提示

km-bot 输出中可能包含此提示，这是工具层面的预检查信息，**不影响实际 API 调用结果**。

**判断方法**：查看响应中的 `status` 字段，若为 `"success"` 则调用成功，可忽略此提示。

### 支付相关错误

> 💳 支付信息（`payment_link` / `qr_code` / `expire_time`）由 `roomHourCreateOrder` 直接返回，无独立支付接口。

| 场景                           | 处理策略                                                                                |
| ------------------------------ | --------------------------------------------------------------------------------------- |
| 二维码/链接无法打开            | 引导用户点击打开 `payment_link`扫码支付；仍不行则按下方「超时」处理                  |
| 超过 `expire_time` 未支付      | ⚠️ **禁止直接重新下单**；重新 `queryRoomAvailability` 查时段 → 用户重选 → 下新单        |
| `roomHourCreateOrder` 时段已被预订 | 向用户说明，重新 `queryRoomAvailability` 查询其他可选时段                            |
| 用户询问支付状态               | 引导用户以支付页面/收银台提示为准，或联系门店确认                                       |

## 场景化错误处理

### 场景1：用户要求换店

```
用户：在哪家店来着？换一家吧
处理：
1. 调用 searchCompany 查询新门店（如需要，注意可能超时需重试）
2. 调用 switchCompany(company_code="xxx") 切换上下文
3. 清空所有之前收集的预订信息
4. 从 queryRoomAvailability 重新开始（记得传 begintime/endtime）
```

### 场景2：用户要求换包厢/时段

```
用户：换一个包厢 / 换一个时间段
处理：
1. 清空时段相关信息
2. 重新展示可用选项供用户选择
```

### 场景3：验证码发送失败

```
用户收不到验证码：
1. 检查手机号格式是否正确
2. 检查是否在60秒冷却期内（需等待）
3. 检查是否已达24小时5次上限（需次日再试）
4. 建议稍后重试或联系客服
```

### 场景4：用户想调整时段

```
用户：太贵了，能便宜点吗？/ 能再延长/缩短时间吗？
处理：
1. 清空当前选定项
2. 重新调用 queryRoomAvailability 使用新的时间段
3. 展示新的可预订时段供用户确认
```

### 场景5：订单创建失败

```
订单创建接口返回错误：
1. 根据错误信息判断原因（如：时段已被预订）
2. 向用户说明具体情况
3. 提供解决方案建议（更换时段/包厢等）
```

### 场景6：支付超时/二维码过期

```
用户：支付链接打不开/过期了/二维码失效了
处理：
1. ⚠️ 禁止直接调用 roomHourCreateOrder 重新下单（原时段可能已被他人预订）
2. 重新调用 queryRoomAvailability 查询当前可选时段
3. 按展示规范重新展示可预订时段供用户选择
4. 用户选定后调用 roomHourCreateOrder 创建新订单（返回新的 payment_link/qr_code/expire_time）
5. 展示新的支付二维码，提醒新的有效期 expire_time
```

> ⚠️ **原因**：`expire_time` 既是锁定包厢时间也是支付时间，过期后包厢锁定解除，原时段可能已被他人预订或状态变化，必须重新查询确认当前可用时段。

## 错误恢复检查清单

当遇到错误时，按以下顺序检查：

```
1. 网络问题？
   → 等待重试或检查网络连接
   → searchCompany 超时？等待 3-5 秒重试，最多 3 次

2. 参数问题？
   → queryRoomAvailability 是否传了 begintime + endtime？（不传返回空！）
   → 检查 api-overview.md 中的字段要求
   → 检查 api-*.md 中的参数格式

3. 返回空结果？
   → 确认时间参数已正确传入
   → 尝试到点时间延后半小时查询

4. 登录状态问题？
   → 调用 sessionInfo 检查 status
   → status=0 则先完成登录

5. 业务逻辑问题？
   → 查看具体错误信息
   → 按场景化处理指引操作

6. 系统问题？
   → 提示用户稍后重试
   → 如持续失败，建议联系客服
```
