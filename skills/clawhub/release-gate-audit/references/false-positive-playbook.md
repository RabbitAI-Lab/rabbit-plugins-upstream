# 误报判定手册 — 让高召回变得可用

## 为什么必须人工判定

任何基于正则的敏感信息扫描，都只能做到**高召回、低精度**：宁可多报，不能漏报。
这是正确的取舍——漏一个真凭证的代价远高于多看十条误报。

但代价是：**工具的输出不是结论，是线索。**

两种偷懒方式都会出事：

|偷懒方式 | 后果 |
|---------|------|
| 看到 P0 数量不为 0 就判"不可发布" | 告警疲劳，团队开始整体忽略扫描结果 |
| 为了让扫描通过而放宽规则/扩大忽略 | 把真问题一起藏起来，下一个 clone 的人照样拿到 |

正确做法只有一个：**逐条读上下文**。本手册就是判定时的对照表。

## 判定四问

对每一条 P0/P1，依次问：

### 问题一：这个值是真的吗？

| 信号 | 判定 |
|------|------|
| 厂商官方文档里的示例串| **误报**。如 AWS 的 `AKIAIOSFODNN7EXAMPLE`（这串就是 AWS 文档专用示例） |
| 含 `example` / `dummy` / `changeme` / `your_` / `xxx` | 大概率误报 |
| `${VAR}` / `{{ }}` / `<placeholder>` 插值语法 | **误报**，是模板不是字面值 |
| 长度、字符集符合真实格式，且无占位符特征 | **重点怀疑**，进入问题二 |
| 高熵随机串 | **重点怀疑** |

### 问题二：它在什么位置？

位置往往比内容更能说明性质。

| 位置 | 判定倾向 |
|------|---------|
| `test/` `tests/` `__tests__/` `spec/` `fixtures/` `mocks/` | 大概率是测试固定装置 |
| `*.test.*` `*.spec.*` `test_*` | 同上 |
| `examples/` `demo/` `docs/` | 大概率是示例 |
| `.env.example` `.env.template` `*.sample` | **设计上就该是假值** |
| CI 配置里配`localhost` / service container | CI 本地凭证，非真实 |
| **生产代码路径** | **重点怀疑** |
| **commit 历史（且当前文件已无）** | **重点怀疑**——这是典型事故形态 |

> 本工具已自动标注这两类信号（内容特征 + 路径性质），输出里带
> `<- 疑似误报，需读上下文` 标记。**但标记只是提示，不是结论。**

### 问题三：暴露面有多大？

| 暴露面 | 紧急度 |
|-------|-------|
| 公开仓库的已追踪文件 | **最高**，且要假设已被爬取 |
| 公开仓库的 git 历史 | **同样最高**——clone 即可得|
| 私有仓库 | 仍需轮换（内部人员风险 + 未来可能开源） |
| 未追踪 / 已 gitignore 的本地文件 | 未泄露，但要确认 gitignore 生效 |

### 问题四：这个凭证现在还有效吗？

到对应服务控制台查。**如果有效 → 立即吊销，不要先讨论。**

## 常见误报速查

| 命中内容 | 为何是误报 |
|---------|-----------|
| `AKIAIOSFODNN7EXAMPLE` | AWS 官方文档的固定示例 Access Key |
| `AIzaSyExample...` | Google 文档示例格式 |
| `sk_test_...` | Stripe **测试**密钥，与生产环境隔离（但仍不该硬编码） |
| `postgres://user:pass@localhost:5432/db` | 本地/CI 数据库，host 是 localhost |
| `postgres://a:${PG_PASS}@db:5432/x` | 变量插值，非字面密码 |
| `apiKey: "secret-token"` 配 `mockFetch` | 单测假值，不发真实请求 |
| `password: "changeme"` in `.env.example` | 模板占位符，设计上就是假的 |
| `-----BEGIN CERTIFICATE-----` | **公钥/证书**不是私钥，公开无害 |
| `test@example.com` | RFC 2606 保留域名，标准占位符 |
| UUID 格式串 | 很多 UUID 不是凭证；需看赋值给了什么变量 |
| lockfile 里的 integrity hash | 内容校验哈希，非密钥 |

## 容易被误判为误报的真问题（反向清单）

这一类更危险——它们**看起来像测试数据，实际是真的**：

| 情况 | 为什么危险 |
|------|-----------|
| 测试文件里用了**真实**的沙箱/测试环境凭证 | 沙箱凭证依然是凭证，可能关联真实账号 |
| `.env.example` 里作者**手滑填了真值** | 极其常见。必须逐字核对，不能因为文件名就放过 |
| 注释掉的代码里的密钥 | 注释不影响它在仓库里是明文 |
| 「反正是内部私有仓库」 | 内部人员风险 + 仓库可能未来开源 |
| 「这个 key 已经不用了」 | 未吊销的废弃 key 依然可用 |
| 文档/教程里的"示例"其实是从真环境复制的 | 写文档时最容易发生 |

**判定原则：文件名和目录只能降低怀疑度，不能直接免检。**

## 基线机制的正确用法

确认为误报的命中，写入基线文件，而**不是**放宽正则或扩大忽略目录。

```bash
# 生成报告
python3 scripts/release_gate.py <repo> --format json > report.json

# 人工判定后，把确认为误报的项写入基线
# 基线格式：{"accepted": [[category, location, line, desc], ...]}

# 后续扫描带上基线
python3 scripts/release_gate.py <repo> --baseline baseline.json
```

### 为什么用基线而不是放宽规则

| 做法 | 问题 |
|------|------|
| 放宽正则 | 同类型的**真**泄露以后也检不出来了 |
| 把 `test/` 整个加入忽略 | 测试目录里的真凭证从此隐形 |
| **写入基线** | 只豁免"这一条已判定过的命中"，规则强度不变 |

基线是**逐条问责**的：每一条都对应一次人工判定。规则放宽是**批量免责**的。

### 基线维护纪律

- 每条基线项应有判定理由（建议在 JSON 里加注释字段或维护配套说明）
- 代码变动后基线可能失效（内容变了指纹就变），这是**特性**：它会重新提示你判定
- 定期回顾基线，删掉已不存在的条目——否则基线会变成"忽略一切"的垃圾场

## 判定记录模板

审查报告里应当逐条留痕，而不是只给一个总数：

```markdown
## P0 命中判定（共 N 项）

| # | 位置 | 内容摘要 | 判定 | 依据 |
|---|------|---------|------|------|
| 1 | `test/redact.test.mjs:20` | `AKIAIOSFODNN7EXAMPLE` | 误报 | AWS 官方文档示例串，且位于脱敏功能的单测中 |
| 2 | `ci.yml:145` | `postgres://a:a@localhost` | 误报 | CI service container 本地凭证，host 为 localhost |
| 3 | `src/client.py:88` | `sk-xxxx...`（真实格式） | **真泄露** | 生产代码路径，无占位符特征，控制台确认仍有效 → 已吊销 |
```

>「0 findings」且无证据的报告是无效的。
> 「6 项 P0，逐条核实全部为测试固定装置，附每条依据」才是一次审计。
