# Multi-day construction-log progression reconstruction

Use when a user supplies a last known daily log, one or more later construction milestones, and an undated *current* status, and requests a **working-use** day-by-day schedule in C01-8 form. This is materially different from the §3 single-day T−1/T+1 bracket: over a long gap, no given milestone proves the exact day on which intermediate work occurred. Never represent such dates as verified site facts or certify the resulting files as contemporaneous original records.

## Two-ended schedule check

1. Inventory the full month tree recursively, including draft subfolders, before writing; do not overwrite existing canonical logs. Read the last 2–3 authentic files and the user's later milestone files separately. Label each input as contemporaneous source, user-confirmed milestone, or previously inferred file. Do not treat a prior agent-created draft as independent corroboration.
2. Build an internal matrix with columns `date / supported ongoing work / necessary predecessor / possible parallel work / precipitation / provenance`. From the older record **forward**, carry only unfinished items and expected successor stages. From each dated milestone **backward**, check necessary predecessors: earthwork/base preparation → cushion → waterproofing and protection → reinforcement and embeds/formwork → concrete; curing follows concrete. Stage start/end dates inside a long gap are assumptions, not derived facts.
3. A user's undated “current status” is an **upper endpoint**, not a historical measurement: don't write its percentages into earlier dates. A current 50% cushion says neither when work started nor what percentage was complete at any older date. Avoid invented headcounts, machine counts, concrete quantities, acceptance decisions and precise completion percentages. Avoid placing waterproof paving on sustained rainy days; use weather as a feasibility check, not proof of attendance, work, or stoppage.
4. For normal-layout working copies, keep Row 4/5 concise and in the established C01-8 template, rather than filling every sentence with “拟核对”. If the user asks to omit draft labels *inside* the Word files, provenance must still be plainly stated in the delivery message; if intended for statutory/archival use, ask for daily field evidence before representing the records as original logs.
5. Verify each actual output by opening its absolute path with python-docx: expected date, weekday, formula page number, title + 6-row table + sectPr, Row 4/5 one paragraph each, 11pt 宋体 on all nonempty runs, and no unsupported numbers or acceptance claims. If files live under nested directories, a month-root-only verifier reporting `MISSING` has checked **zero** of them; inspect those paths directly. Verify ZIP member names/count and archive CRC as a separate step.

## Lessons from a September–October working reconstruction

An existing September log identified early waterproofing, earthwork, and completed pile-cap cushion; later user milestones dated two slab pours in October. A separate “current status” included undated percentages for other zones. The sound constraint is to use the pour dates only to order their own predecessors, advance the existing earthwork/workface activities, and place other zones in plausible **predecessor phases** without prematurely backdating today's percentages. Deliver the logical progression as working-use schedule, not as verified attendance, inspections or daily measurements. In one case, rain data were fetched for the entire date range from Open-Meteo's archive endpoint; wet days were used to avoid incompatible exposed waterproof operations, not to assert actual site shutdowns.
