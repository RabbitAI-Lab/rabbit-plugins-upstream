# Actual-milestone corrections in construction-log collections

Use when a user supplies actual pour dates, concrete specification and volume, then asks to align earlier reinforcement entries. This is a **targeted revision of sourced records**, not permission to invent a new daily history.

## 1. Resolve the active edition

- Inventory current directories and available manifests. The newest valid edition may be a separate reconciled collection, not the original month folder or first matching filename.
- Read the two or three adjacent records and scan earlier occurrences of the affected zone and component. Inspect scene, materials and quality/safety, not only the first scene sentence.
- Record source paths, dates, hashes, page numbering and font scope before changes. Avoid scanning generated revision folders back into the source set.

## 2. Build a small change matrix

For each candidate entry record `date / zone / component / activity / source / status / proposed edit`.

Evidence order for this task:
1. Explicit new user-confirmed **actual** date/specification/quantity.
2. Day-specific monitoring record, subject to explicit source conflicts being reported rather than silently repaired.
3. Existing date-specific user facts.
4. Master or detailed plan.
5. Earlier assistant reconstruction.

A later pour constrains its own reinforcement to precede that pour. It does **not** establish when tying began, how much was complete on any earlier date, or that earlier partial tying was impossible. Waterproofing and tying can coexist on different workfaces. Do not remove dated monitoring evidence merely to make an aesthetically simple timeline.

Distinguish slab, pile cap, wall/column inserts, rear-pour strip and support-replacement strip. A strip pour is not necessarily the whole slab pour; later wall reinforcement is not contradictory slab reinforcement.

## 3. Apply bounded changes

- Put the actual pour **completion** on the user-confirmed date, with exact concrete strength/impermeability notation and cubic-metre volume.
- Use the same quantity consistently in scene and materials. Those repeated descriptions refer to one pour, not two volumes to sum.
- Remove or revise stale estimates and clearly unsupported conflicting reconstruction only within the requested scope.
- Keep sourced tying dates. If a closing/preparation day is needed but not supplied, either ask when it matters or identify the working-use arrangement briefly in chat; never manufacture an inspection/acceptance result.
- After pouring, avoid ongoing bottom-slab tying for the same completed extent; use curing/protection as requirements or documented activity, not invented inspection success.
- Newly created dates should not automatically carry every earlier zone's percentages or claim unchanged progress. Record what is supplied and conservative relevant requirements.

## 4. Preserve format and edition integrity

- Keep the user's C01-8 layout and intentional font variant: scene content and quality/safety body in 华文行楷, fixed headers and signature/date in 宋体, original approved size unless the user changes it.
- Retain the active edition's page scheme. A collection intentionally renumbered in date order must continue that sequence; do not revert only newly added dates to a different historic base-date formula.
- Copy the complete active collection into a new edition. Unaffected DOCX files must be byte-identical. Check source hashes again after all rendering/export work.
- Build one full ZIP and optionally one delta ZIP, with filenames/counts derived from actual manifests rather than hard-coded expectations. Exclude stale drafts, previews, instructions and audit files unless requested.
- For a revised attachment, use a new descriptive filename. If the user reports old contents, inspect ZIP members and rebuild under a distinct name; caching is only a possible explanation, not a verified cause.

## 5. Verification gates

1. Exact date, zone, C-grade/P-grade and volume in each new event.
2. No premature completion, false acceptance, invented percentages or unscoped edits.
3. Correct date/weekday, page sequence, six-row table and one paragraph per body cell.
4. Explicit font attributes on new runs; body/signature font split preserved.
5. All unaffected files match source bytes; all source hashes unchanged.
6. ZIP unique-member count, CRC and entry hashes equal generated outputs.
7. Real Word read-only export of the new/changed dates: volume and specification present, weather fully visible, final signature not clipped. Page-count changes are disclosed, not silently fixed by shrinking text.

## Delivery

Lead with actual events updated, then changed/new-file counts and full/delta links. One short sentence identifies any inferred reinforcement timing. Do not repeat the whole workflow or put drafting/provenance commentary into the construction-log body.
