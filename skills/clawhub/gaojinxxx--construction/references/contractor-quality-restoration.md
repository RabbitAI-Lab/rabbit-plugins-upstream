# 施工单位原质量恢复：逐日JSON决策

## 适用范围

输入为按日期隔离的施工对照 `construction`、旧现场 `old_scene`、未污染旧质量 `old_quality`；任务是修复施工日志而非重写监理日志。仅使用指定字段，不为丰富质量措辞再读取监理其他栏。调用方指定的字段、数量及交付格式优先于其他审核合同。

```json
{"date":"YYYY-MM-DD","scene":["去掉条目编号后的工序"],"quality_mode":"restore","controls":[],"notes":[]}
```

## 逐日决策

1. 完整扫描旧现场所有章节，包括材料、机械、人员之后追加的现场作业，不只截取第一个标题下面。
2. 按部位＋构件＋工序拆出事实。以旧施工为底，对照来源逐项记录为保留、补充、冲突替代或重复合并。监理未提不等于未施工。
3. 同一塔号、同一基础已安装后的安装前开挖准备属于阶段冲突；不同塔号、不同部位或未指明塔号不能仅凭日期临近强行合并。排水沟、消防水池、坡面、构筑物破除可与主工序并行。
4. 冲突统计采用授权优先来源。分项口径不同不得直接相加；原来源自身的日数与累计不一致时保留原值并记notes，不能反推一个新数。后续试打、浇筑或安装节点仅用于检测真实冲突，不是编造早期开工日的依据。
5. 用户授权简化时，删去冗长套话及明确属于助手无据估算的百分比、人数等，不扩大为删除所有原规格。保留非冲突的材料等级、钢筋规格、真实部位及明确节点。估算值与真实原始值须区分，不能只因含“约”便自动判伪。
6. 判定全日质量模式：
   - **restore**：原质量对应最终保留工序。`controls=[]`，父流程从原件恢复，不让子流程转述损失原文。
   - **controls**：有具体证据表明原质量工种、部位或阶段不符，或该日没有原质量。写2—4句过程控制要求，与当天工序对应。
   - 对照新增了其他工序，并不自动否定原质量；不因“覆盖不够丰富”就重写全日质量。
7. controls采用施工单位口吻，如“控制…、检查…、保持…、作业区设置…”，不用监理/旁站/见证/通知，不将要求改写成已验收合格、已完成整改闭环。来源冲突和编写解释只入notes，不进入scene或controls。

## 状态锚点、时点与停工判例

- **推排不是当天实录：** 用户指定旧推排不确定的时段时，不把旧连续性扩写全叠到监理实际工序后面。优先保留有独立现场证据的原工序，其他旧推排仅记处置说明，避免同一天出现一长串未经证实的超前阶段。只有缺记、没有反证时，说明是未获当天证据，不写成监理证实未施工。
- **完成与施工中先比范围和时点：** 用户报5区绑筋完成，监理同日记绑筋施工，不能凭动词差异便删除完成状态，也不能臆造“上午施工、下午完成”。按用户反馈时点保留已完成，notes保留监理状态与时点未知的边界。未发生的预计次日浇筑仍是计划，不能升级为实际浇筑。
- **缺失字段不等于冲突：** 用户报承台垫层、预制板和底板垫层分别完成不同比例，而监理只记“垫层放样”，缺少构件、区段和时点，不能据此归零全部比例。监理未列某区，也不否定用户明确的该区比例、剩余量或未开工状态。
- **实际阶段优于旧超前安排：** 同一底板仍在防水涂膜或卷材施工时，不叠加旧推排的该底板全面绑筋；比较前先核实是否同一构件、同一施工段。承台钢筋与底板防水不能仅因区号相同便判冲突。主体底板已浇筑后保留养护，后浇带背包及换撑带浇筑不等于底板整体再次浇筑。
- **整日停工与阶段停工不同：** 施工栏先记塔吊、围墙、排水沟等加固，再记收到台风响应后停工，应保留停工前作业和之后人员转移，不用旧“场内无施工作业”覆盖全天。相反，施工栏仅有台风后排查、维保、监测，不足以认定正常施工作业已全面恢复。
- **controls与restore分开验证：** 替代质量用“注意／应／做好”等施工方控制要求，不生成实际整改验收结论；原质量即使含旧表述，restore也不能被统一禁词清洗器悄悄改写。工序新增而原质量仍匹配时，保留restore，不追求覆盖齐全而整日重写。

## 覆盖与重读验证

- 写前读取源文件哈希，写后验证未改源文件。
- 从磁盘重新读取源JSON与输出JSON，断言数量、唯一日期数和**日期序列完全相等**；不能只验首尾日期，也不自动补齐日历中的缺日。
- 验证精确字段、数组类型、`quality_mode`枚举；restore的controls必须为空，controls模式必须有2—4条。
- 对每个非空construction条目建立覆盖检查：规范化空白、条目编号、明显标点后，应找到原条目或明确的合并映射。重复工序合并也要有映射，不能以“去重”为名丢轴线、区块或施工部位。
- 同样复核旧现场独立工序保留情况。监理覆盖率为100%并不能证明旧施工未被误删；两路来源分别检查。
- 扫描scene/controls是否出现制作旁白；仅对新写controls执行监理措辞与虚构闭环措辞禁词检查。restore原文不应被此扫描顺便改写。
- 用程序统计restore/controls数量，按用户要求交付；若只要路径、总数及模式计数，不附长篇正文。

## 去编号的关键陷阱

`^\d+[、.．]`既会识别“1、工序”，也可能误判“3、5、6区块”开头的真实区块列表。仅检查有无该正则匹配会把正确数据当错误；盲目替换则会丢掉首个区块。

- 优先在仍有原始条目结构时识别编号，再提取正文。
- 区别“1、3、5、6塔吊基础…”中的条目编号与真正的塔号列表，不凭一个字符决定。
- 验证至少覆盖：`1、排水沟砌筑`应去编号；`3、5、6区块土方开挖`、`1#、4#塔吊`、`18-31轴`必须保持实体编号。
- `(?!\d)`可避免部分连续数字列表的误报，但不是通用中文编号解析器；正文上下文与原条目结构仍是决定依据。

## 质量验证边界

结构、数量和来源覆盖通过只证明输出合同与覆盖检查通过，不证明每个历史工程事实已被独立核实。不要把一次成功的JSON验证升级为对全部旧估算、部位映射或真实验收结果的确认。
