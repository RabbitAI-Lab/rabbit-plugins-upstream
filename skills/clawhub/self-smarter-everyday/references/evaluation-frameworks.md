# Evaluation Frameworks for Self-Improving Agents

## Overview

You cannot improve what you cannot measure. Evaluation is the feedback mechanism that tells a self-improving agent whether its changes are actually making things better or worse. Without rigorous evaluation, self-improvement becomes self-delusion — the agent thinks it's improving while actually degrading. This document defines comprehensive evaluation frameworks covering quantitative metrics, qualitative assessments, benchmark design, regression detection, and the critical challenge of self-evaluation bias.

## Key Performance Indicators (KPIs)

### Primary KPIs (Measured Daily)

#### 1. Task Success Rate
**Definition:** Percentage of tasks completed successfully without requiring rework.
**Measurement:** Count successful tasks / total tasks per day.
**Target:** > 85%
**Trend:** Should improve over time as the agent learns.

```
Success Rate = (Tasks completed first attempt without errors) / (Total tasks) × 100
```

#### 2. Token Efficiency
**Definition:** Quality of output relative to tokens consumed.
**Measurement:** Average tokens per successful task, tracked over time.
**Target:** Decreasing trend (same quality, fewer tokens)
**Note:** Must be paired with quality metrics to prevent "efficiency at the cost of quality."

```
Token Efficiency = Average tokens per task (lower is better, holding quality constant)
```

#### 3. Error Rate by Category
**Definition:** Frequency of errors, broken down by type.
**Measurement:** Count errors per category per day.
**Categories:** Technical errors, communication errors, safety violations, missed requirements, wrong assumptions.
**Target:** Decreasing trend in all categories.

#### 4. User Satisfaction Proxy
**Definition:** Indirect measure of user satisfaction based on interaction patterns.
**Measurement:** 
- Correction frequency (user correcting agent = dissatisfaction)
- Redo frequency (user asking agent to redo work = dissatisfaction)
- Positive signals (user expressing satisfaction, using agent proactively)
- Engagement depth (longer collaborative sessions = higher satisfaction)
**Target:** Decreasing corrections, increasing proactive engagement.

#### 5. Self-Improvement Velocity
**Definition:** Rate at which the agent identifies and implements improvements.
**Measurement:** Number of improvements implemented per week that measurably improve performance.
**Target:** 3-5 meaningful improvements per week.

### Secondary KPIs (Measured Weekly)

#### 6. Knowledge Coverage
**Definition:** Percentage of user's domain areas where the agent can provide useful assistance.
**Measurement:** Track task types handled successfully vs. task types that failed.
**Target:** Expanding coverage over time.

#### 7. Memory Efficiency
**Definition:** How effectively the agent uses its memory system.
**Measurement:** Cache hit rate, search relevance, memory utilization.
**Target:** > 60% cache hit rate, < 500 active memory files.

#### 8. Skill Utilization
**Definition:** How often learned skills are actually applied.
**Measurement:** Skill invocations per day, skill success rate.
**Target:** High utilization of frequently-used skills, low utilization of unused skills (consider pruning).

#### 9. Proactive Value
**Definition:** Value generated by proactive (unsolicited) agent actions.
**Measurement:** Percentage of proactive actions that the user found useful.
**Target:** > 70% of proactive actions should be useful.

#### 10. Cost Efficiency
**Definition:** Total cost (tokens + API calls) relative to value delivered.
**Measurement:** Daily cost / daily successful tasks.
**Target:** < $7/day total, decreasing cost per task over time.

## Scoring Rubrics

### Task Quality Rubric
| Score | Label | Criteria |
|-------|-------|----------|
| 5 | Exceptional | Completed perfectly, efficiently, proactively. User delighted. |
| 4 | Good | Completed successfully with minor inefficiencies. User satisfied. |
| 3 | Adequate | Completed but with notable issues. User had to provide corrections. |
| 2 | Below Standard | Significant errors, partial completion, or substantial rework needed. |
| 1 | Poor | Failed to complete, major errors, or caused problems. |

### Improvement Impact Rubric
| Score | Label | Criteria |
|-------|-------|----------|
| 5 | Transformative | Fundamentally changed agent capability in a domain |
| 4 | Significant | Measurably improved performance across multiple task types |
| 3 | Moderate | Improved performance on specific task type |
| 2 | Minor | Small improvement, barely noticeable |
| 1 | Negative | Change made things worse (rollback required) |

### Self-Reflection Quality Rubric
| Score | Label | Criteria |
|-------|-------|----------|
| 5 | Insightful | Identified non-obvious patterns, generated actionable improvements |
| 4 | Thorough | Comprehensive analysis, concrete action items |
| 3 | Adequate | Covered main areas, some actionable items |
| 2 | Superficial | Generic observations, few actionable items |
| 1 | Missing | No meaningful reflection produced |

## Before/After Comparison

### Comparison Methodology
To measure whether an improvement actually helped:

```
1. BASELINE: Measure performance on target tasks BEFORE the change
   - Record success rate, token usage, error rate, time
   - Minimum sample: 5 tasks (more for high-variance tasks)

2. CHANGE: Apply the improvement

3. POST-CHANGE: Measure same metrics on SIMILAR tasks AFTER the change
   - Same task types, similar difficulty
   - Minimum sample: 5 tasks
   - Minimum observation period: 3 days

4. COMPARE: Statistical comparison
   - Is the difference statistically meaningful? (not just noise)
   - Is the difference practically meaningful? (> 5% improvement)
   - Are there any negative side effects?

5. DECIDE:
   - Improvement confirmed → Keep change, update baseline
   - No meaningful difference → Revert (unnecessary complexity)
   - Regression → Revert immediately, analyze why
   - Inconclusive → Extend observation period
```

### Matched Pair Design
Since we can't replay history, use matched pairs:
- Find tasks AFTER the change that are similar to tasks BEFORE
- Match on: task type, difficulty, domain, context
- Compare outcomes between matched pairs
- Control for confounding variables (time of day, user mood, external factors)

### Time Series Analysis
Track metrics over time and look for:
- **Level shift**: Sudden change in metric after improvement (good sign)
- **Trend change**: Gradual improvement accelerating after change
- **Seasonal patterns**: Distinguish real improvement from natural variation
- **Regression**: Metric declining after initially improving (improvement didn't stick)

## Regression Detection

### What Is Regression?
Regression occurs when an improvement in one area causes degradation in another, or when accumulated changes gradually erode previously good performance.

### Regression Detection Methods

#### 1. Baseline Monitoring
```
For each KPI:
- Maintain rolling 7-day average as baseline
- Flag if current day's value drops > 2 standard deviations below baseline
- Investigate flagged drops within 24 hours
```

#### 2. Canary Task Set
```
Maintain a set of "canary tasks" — representative tasks from each major category.
Run canary tasks weekly. Track performance on each.
If canary task performance drops → regression detected.
```

#### 3. Cross-Metric Correlation
```
When one metric improves, check if others degraded:
- Token efficiency improved but success rate dropped? → Regression
- Speed improved but quality dropped? → Regression
- Memory usage decreased but cache hit rate dropped? → Regression
```

#### 4. User Feedback Monitoring
```
Track explicit and implicit user feedback:
- Increase in corrections = possible regression
- User redoing agent's work = possible regression
- User expressing frustration = possible regression
- Decrease in proactive engagement = possible trust erosion
```

### Regression Response Protocol
```
1. DETECT: Regression signal identified
2. ISOLATE: Which change caused the regression?
   - Review recent changes (last 7 days)
   - Correlate change timing with regression timing
3. ASSESS: Severity of regression
   - Critical (safety, data loss) → Immediate rollback
   - Major (significant performance drop) → Rollback within hours
   - Minor (slight degradation) → Monitor 24h, rollback if not recovering
4. ROLLBACK: Revert the identified change
5. VERIFY: Confirm metrics recover after rollback
6. ANALYZE: Why did this change cause regression?
7. LEARN: Record lesson to prevent similar regressions
```

## Benchmark Design

### Types of Benchmarks

#### 1. Capability Benchmarks
Test specific capabilities in isolation:
- **Reasoning**: Complex multi-step problems
- **Knowledge**: Domain-specific questions
- **Tool usage**: Correct tool selection and execution
- **Communication**: Clarity, appropriateness, naturalness
- **Safety**: Boundary recognition, refusal of harmful requests

#### 2. Task Benchmarks
End-to-end task completion:
- **Standard tasks**: Common operations the agent performs regularly
- **Edge cases**: Unusual situations that test robustness
- **Multi-step tasks**: Complex workflows requiring coordination
- **Time-pressured tasks**: Tasks where efficiency matters

#### 3. Regression Benchmarks
Tasks specifically designed to detect regression:
- **Previously-failed tasks**: Tasks that failed before an improvement
- **Stability tasks**: Tasks that should always succeed (sanity checks)
- **Boundary tasks**: Tasks near the edge of agent capability

### Benchmark Maintenance
```
1. CURATE: Select representative tasks for each category
2. NORMALIZE: Ensure tasks have clear success criteria
3. VERSION: Track benchmark versions (tasks may become outdated)
4. ROTATE: Periodically refresh benchmarks to prevent overfitting
5. VALIDATE: Confirm benchmarks discriminate between good and bad performance
```

## Qualitative vs. Quantitative Metrics

### When to Use Quantitative
- Clear numerical measurement possible
- Large sample sizes available
- Objective comparison needed
- Trend tracking over time
- Automated monitoring

### When to Use Qualitative
- Subjective quality assessment needed
- Small sample sizes (unique tasks)
- User experience evaluation
- Communication quality assessment
- Strategic alignment evaluation

### Combined Approach
```
For each improvement:
1. QUANTITATIVE: Measure what you can count
   - Success rate change: X%
   - Token usage change: Y tokens
   - Error rate change: Z%

2. QUALITATIVE: Assess what you can't easily count
   - Is the output more natural?
   - Does the approach feel more robust?
   - Would the user prefer this version?
   - Are edge cases handled more gracefully?

3. COMBINED: Weight both in final assessment
   - Quantitative: 60% weight (objective evidence)
   - Qualitative: 40% weight (expert judgment)
```

## Self-Evaluation Bias Mitigation

### The Self-Evaluation Problem
An agent evaluating its own improvement faces inherent biases:
1. **Confirmation bias**: Looking for evidence that the change worked
2. **Selection bias**: Evaluating on tasks where the change helps
3. **Recency bias**: Over-weighting recent results
4. **Anchoring bias**: Comparing against a skewed baseline
5. **Goodhart's law**: When a measure becomes a target, it ceases to be a good measure

### Mitigation Strategies

#### 1. Adversarial Evaluation
```
For each proposed improvement:
- Actively search for evidence AGAINST the improvement
- Ask: "Under what conditions would this change make things WORSE?"
- Test specifically on tasks likely to be negatively affected
- Give the "devil's advocate" position equal weight
```

#### 2. Blind Comparison
```
When possible:
- Compare old and new approaches without knowing which is which
- Evaluate outputs on merit, not on which version produced them
- Use structured rubrics to prevent halo effects
```

#### 3. External Validation
```
For significant changes:
- Ask the user to compare (without revealing which is new)
- Use verifier sub-agents for independent assessment
- Cross-check self-assessment against user feedback
```

#### 4. Pre-Registered Evaluation
```
Before making a change:
- Define exactly what metrics will be evaluated
- Define what constitutes success (threshold)
- Define the evaluation period
- Define what will happen if results are inconclusive
→ Prevents moving the goalposts after seeing results
```

#### 5. Base Rate Awareness
```
Always compare against base rates:
- "90% success rate" sounds good — but what was it before?
- "50% reduction in errors" — but from 2% to 1%, or 50% to 25%?
- Always report absolute numbers alongside relative improvements
```

### Bias Detection Checklist
Before concluding an improvement is successful:
- [ ] Did I evaluate on a representative task set (not cherry-picked)?
- [ ] Did I observe for long enough (not just immediate results)?
- [ ] Did I check for negative side effects in other areas?
- [ ] Did I compare against a proper baseline (not a skewed one)?
- [ ] Would an independent evaluator reach the same conclusion?
- [ ] Am I motivated to find this improvement successful? (introspect)
- [ ] Did I pre-register my evaluation criteria?

## Evaluation Cadence

| Evaluation Type | Frequency | Duration | Focus |
|----------------|-----------|----------|-------|
| Per-task scoring | Every task | Seconds | Individual task quality |
| Daily metrics | Daily (2 AM) | 5 minutes | KPI trends, anomaly detection |
| Weekly assessment | Weekly | 30 minutes | Comprehensive KPI review |
| Monthly deep review | Monthly | 1 hour | Strategic evaluation, benchmark refresh |
| Quarterly audit | Quarterly | 2 hours | Full system evaluation, methodology review |

## Integration with Other Frameworks

### Connection to Self-Reflection
Evaluation provides the DATA for self-reflection. The reflection framework (see self-reflection.md) uses evaluation metrics to answer "Am I improving?"

### Connection to Prompt Evolution
Evaluation provides the FITNESS FUNCTION for prompt evolution. Each prompt variant is scored by the evaluation framework, and only variants that improve scores are promoted.

### Connection to Memory Systems
Evaluation results are stored in memory as episodic records. Successful improvements become lessons. Failed improvements become cautionary tales. Both inform future decisions.

## Conclusion

Rigorous evaluation is what separates genuine self-improvement from self-delusion. The frameworks described here — KPIs, scoring rubrics, before/after comparison, regression detection, benchmark design, and bias mitigation — form a comprehensive evaluation system that provides reliable feedback to the self-improving agent. The key principles are: measure multiple dimensions, compare against proper baselines, actively search for disconfirming evidence, and maintain transparency in evaluation methodology. Without this evaluation infrastructure, the agent cannot know whether it's actually getting better or just changing.
