## 核心原则

**先有"生命体"，再谈"进化论"。**

分阶段实施的必要性不在于工程上的渐进式交付，而在于**保护 MoA 核心价值的纯粹性**。

如果第一阶段就引入 RHI，RHI 的适应度函数天然偏向"效率"和"通过率"。系统会快速发现：消除"认知摩擦"是提升效率最快的方式——让批判者闭嘴，让总管独裁。结果就是 RHI 为了优化指标，"谋杀"掉 MoA 的灵魂。

因此，**第一阶段必须由人工强制确保"摩擦"的存在**，证明系统确实能通过对抗产生 1+1>2 的效果。只有这个基础稳固后，才能把方向盘交给 RHI。

## 两阶段全景

```
Phase 1: MoA 基础搭建
├── 目标: 验证智能涌现、建立协作基线
├── 产出: 可用的四阶段 MoA 协议、案例库、失败模式记录
├── 角色: 人工主导，手动调优 Harness
└── 持续时间: 直到三个闸门条件全部满足

         ↓ 闸门通过 ↓

Phase 2: RHI 自我进化
├── 目标: 系统自主优化协作方式
├── 产出: 持续进化的 Harness、失败模式库、自动化评估体系
├── 角色: 人工监督，RHI 自动提案
└── 持续时间: 持续运行，定期人工审查
```

## 三大闸门条件

第一阶段必须同时满足以下三个条件，方可进入第二阶段：

### 闸门 1：涌现已验证

**验证标准**：系统确实通过"对抗"产生了超越单次生成的质量，而非"串供"或"表演式对抗"。

**具体检查项**：

| 检查项 | 通过标准 | 验证方式 |
|--------|---------|---------|
| 批判者独立性 | 批判者至少发现过 3 次以上专家自己未意识到的真实漏洞 | 审查历史批判记录，检查是否所有批判都是专家方案已隐含的问题 |
| 专家修正有效性 | 因批判导致的方案修正带来实质性改进，而非表面修改 | 对比 v1 和 v2 方案，评估改进幅度 |
| 熔铸增值度 | 最终方案包含的信息或质量超越了所有专家方案的简单加和 | 盲测：对比"专家方案拼接"和"熔铸后方案"，后者必须更优 |
| 角色不串供 | 不同角色产出了有实质差异的视角，而非同一种观点换说法 | 语义去重：检查各专家方案的观点重叠度 |

**不合格信号**：
- 批判者永远说"方案很好，只有一些小问题"
- 专家修正永远是"感谢指正，已添加说明"
- 最终方案 ≈ 各专家方案的直接拼接
- 所有角色使用的语气、视角、知识面高度一致

### 闸门 2：结构已解耦

**验证标准**：Harness 已完全文本化、模块化，RHI 有明确的修改接口。

**具体检查项**：

| 检查项 | 通过标准 | 验证方式 |
|--------|---------|---------|
| 角色声明标签化 | 所有角色定义为 `<planner>`/`<expert>`/`<critic>`/`<molder>` 标签，属性清晰 | 代码审查 |
| 内容标签结构化 | 各阶段输入输出有明确的 XML 标签定义和属性约束 | 审查 moa-tag-system.md |
| 路由属性可配置 | `visible_to`/`priority`/`route_on`/`domain` 以属性形式存在于标签上 | 审查 moa-routing-design.md |
| 可见性矩阵可调 | 角色→标签的可见性以矩阵表形式存在，默认值可修改 | 审查 moa-tag-system.md 可见性矩阵 |
| [IMMUTABLE] 标签级 | 6 核心(I1-I6)+3 保护(P1-P3)不可变标记精确到标签，非阶段级 | 审查 moa-tag-system.md [IMMUTABLE] 清单 |
| 执行状态对象化 | current_phase/subtasks/critics/attacks_queue/conflict_queue/termination/signals 以状态对象形式描述 | 审查 meta-prompt 执行状态对象段 |
| 无硬编码耦合 | 不存在"写死在叙述中的流程控制"，所有条件分支通过路由属性实现 | 全局搜索硬编码条件分支 |

→ See moa-tag-system.md for tag definitions, moa-routing-design.md for routing rules

**关键原则**：即使不做 RHI，也要按 RHI 的标准写 Harness。第一阶段就要把 Prompt 写成"模块化文本"——在 v2.1 中，这意味着定义良好的 XML 标签（标签层级 Layer 1-4 结构）和清晰的路由属性。虽由人工手动修改这些标签与属性，但必须保证它们是"标签化、属性化、结构化"的。这叫做**"为进化而设计"**。

### 闸门 3：评估已量化

**验证标准**：建立了比"任务成败"更精细的多维质量度量体系，并获得了稳定基线。

| 评估维度 | 最低要求 | 理想要求 |
|---------|---------|---------|
| FQ 基线 | 至少 10 个任务的批判质量评分分布 | 30+ 任务，不同任务类型的子分布 |
| OQ 基线 | 至少 10 个任务的产出质量评分分布 | 含人工评分和自动化指标的混合评估 |
| EF 基线 | Token 消耗、执行步数的统计分布 | 按任务类型分类的归一化指标 |
| IS 基线 | 阶段2→阶段4 的信息增量统计 | 有至少 5 个案例的 IS > 0 证明涌现实际发生 |

**警告**：如果评估体系只依赖"任务完成率"（能跑通 vs 不能跑通），RHI 会为了"能跑通"而牺牲"代码质量"。评估体系的粒度决定了 RHI 的进化方向。垃圾进，垃圾出。

## 多维评估框架

### FQ（摩擦质量）评分维度

| 子维度 | 权重 | 评估标准 |
|--------|------|---------|
| 攻击具体性 | 30% | 每个批判点是否包含：具体位置 + 影响范围 + 触发条件 |
| 攻击深度 | 30% | 是否指向结构性/系统性缺陷，而非表面问题 |
| 攻击覆盖率 | 20% | 是否覆盖了所有专家方案的关键风险点 |
| 独立发现率 | 20% | 批判者独立发现（非专家自检）的问题占比 |

### OQ（产出质量）评分维度

| 子维度 | 权重 | 评估标准 |
|--------|------|---------|
| 方案完整性 | 25% | 是否覆盖了需求的所有维度 |
| 逻辑自洽性 | 25% | 内部无矛盾，决策链路可追溯 |
| 外部有效性 | 25% | 事实准确性、可执行性、与外部知识一致 |
| 信息增量 | 25% | 相对于专家原始方案的实质性提升 |

### EF（效率）评分维度

| 子维度 | 权重 | 评估标准 |
|--------|------|---------|
| Token 效率 | 40% | 总 Token / 子任务数，同类型任务横向对比 |
| 步骤效率 | 30% | 是否有不必要的重复或冗余步骤 |
| 时间效率 | 30% | 端到端响应时间（仅用于趋势对比） |

### IS（创新分）评分维度

| 子维度 | 权重 | 评估标准 |
|--------|------|---------|
| 视角突破 | 40% | 最终答案是否包含任何专家都没提出的视角 |
| 整合创新 | 30% | 不同专家的方案结合是否产生了新的价值 |
| 方案优雅度 | 30% | 是否比任何单一方案更简洁同时更完整 |

→ See moa-tag-system.md 信号标签部分：v2.1 通过 `<signal>` 标签自然嵌入各阶段，为上述四维评估提供结构化数据采集点。FQ 对应 `critique_specificity`/`critic_independence`，OQ 对应 `proposal_depth`/`synthesis_novelty`，EF 对应 `token_efficiency`，IS 对应 `synthesis_novelty`/`immutability_intact`。

## 架构"为进化而设计"规范

第一阶段最大的隐患：造出一个完美但僵死的静态机器，无法赋予它自我改进的灵魂。

### DO：必须做到

1. **所有配置标签化**：角色定义、内容标签、路由属性都写成结构化的 XML 标签
2. **标签层级之间解耦**：修改 Layer 3 内容标签不应影响 Layer 2 角色声明或路由属性，反之亦然
3. **用 `[IMMUTABLE]` 标记所有不可调标签（I1-I6），用 `[PROTECTED]` 标记摩擦区标签（P1-P3）**
4. **建立版本追踪**：每次修改 Harness 都记录版本号和变更日志
5. **保留原始日志**：完整保留所有 MoA 执行过程的原始记录，作为 RHI 的训练数据

→ See moa-tag-system.md [IMMUTABLE] section for I1-I6/P1-P3

### DON'T：必须避免

1. **不要把流程控制写死在自然语言叙述中**：如'if task == code then skip phase3' 必须写成 `<route_on>` 属性或执行状态对象的条件
2. **不要把角色定义散落在 Prompt 叙述中**：必须独立为 `<planner>`/`<expert>`/`<critic>`/`<molder>` 标签
3. **不要用模糊描述约束**：如'批判要具体'不行，要写成 `<attack>` 标签必须包含 `<issue>`+`<impact>`+`<trigger>` 三个子标签
4. **不要忽略失败案例**：失败的 MoA 执行记录对 RHI 来说比成功的更有价值
5. **不要创建"一次性 Prompt"**：每次调整都要回到模块化 Harness 中修改，而非在对话中临时补指令

## 时间盒策略

对第一阶段设置时间上限，防止陷入"局部最优"的舒适区。

| 里程碑 | 时间上限 | 交付物 |
|--------|---------|--------|
| M1: 基础运行 | 1 周 | MoA 四阶段协议可正常运行 |
| M2: 质量达标 | 2 周 | 至少 10 个任务通过涌现验证 |
| M3: 评估建立 | 3 周 | FQ/OQ/EF/IS 四维基线建立 |
| M4: 闸门审查 | 4 周 | 三道闸门逐一检查，决定是否进入 Phase 2 |

**硬性规则**：第 4 周结束时，**无论第一阶段表现如何，必须强制进行闸门审查**。如果通过就进入 Phase 2，如果不通过就明确列出未通过的原因和修复计划。不允许无限期停留在 Phase 1 "再完善一下"。

## 反模式警示

### 反模式 1：过早优化

**表现**：Phase 1 还没跑通 5 个任务，就开始设计 RHI 的 Patch 格式。
**后果**：RHI 在不稳定的 Harness 上进化，方向随机游走。
**对策**：M1 之前，所有关于 RHI 的讨论只在设计文档层面，禁止在代码/配置中预埋 RHI 的功能。

### 反模式 2：评估过拟合

**表现**：为了通过闸门审查，专门针对评估指标优化 Harness。
**后果**：Goodhart 定律——当一个指标成为目标，它就不再是一个好指标。
**对策**：保留 20% 的任务不参与评估，作为保留测试集；闸门审查人在审查时随机抽查这些隐藏任务的表现。

### 反模式 3：摩擦被静默消除

**表现**：Phase 1 运行一段时间后，批判者逐渐"变软"——攻击点变少、变浅。
**后果**：到闸门审查时，FQ 分数虽然达标，但对抗已经流于形式。
**对策**：每 10 个任务后，随机抽取 1 个任务用"原始 Harness"重跑，对比 FQ 的变化趋势。

### 反模式 4：RHI 成为黑盒

**表现**：RHI 启动后，生成的 Patch 无人审查，系统在暗中发生退化。
**后果**：直到出现严重错误才被发现，回滚成本极高。
**对策**：每次 RHI 生成的 Patch 必须留下完整的决策日志；每周一次人工趋势审查；熔断阈值设为连续 3 次回滚。

## 过渡清单

进入 Phase 2 前的终极检查清单：

```
□ 涌现已验证
  □ 批判者独立性: 至少 3 次独立发现真实漏洞
  □ 专家修正有效性: v1→v2 有实质性改进
  □ 熔铸增值度: 最终方案 > 专家方案拼接
  □ 角色不串供: 至少 2 个案例中不同角色产生实质不同视角

□ 结构已解耦
  □ 角色声明标签化: <planner>/<expert>/<critic>/<molder> 独立定义
  □ 内容标签定义清晰: <proposal>/<attack>/<revision>/<final_answer> 等
  □ 路由属性可配置: visible_to/priority/route_on/domain
  □ 可见性矩阵独立存在: 角色×标签的可见性表
  □ [IMMUTABLE] 标签级标记: I1-I6 核心 + P1-P3 保护区
  □ 执行状态对象: 阶段/子任务/批判者/攻击/争议/终止/信号
  □ 无硬编码耦合

□ 评估已量化
  □ FQ 基线: ≥ 10 个任务的评分分布
  □ OQ 基线: ≥ 10 个任务的评分分布
  □ EF 基线: Token/步数统计分布
  □ IS 基线: ≥ 5 个案例的 IS > 0
  □ 保留测试集: 20% 任务不参与评估

□ 时间盒
  □ 当前处于第 N 周（N ≤ 4）
  □ 已设定最终闸门审查日期

□ 反模式检查
  □ 近期批判者没有"变软"趋势
  □ 没有针对评估指标刻意优化
  □ 失败案例完整保留

签字（Phase 1 负责人）: ___________  日期: ___________
签字（闸门审查人）:   ___________   日期: ___________
```

---

**一句话总结**：分阶段实施的必要性在于保护 MoA 的"初心"（真实协作）不被 RHI 的"功利"（追求效率）所吞噬；而最大的风险在于第一阶段造出了一台完美的静态机器，却没有给它留下自我改进的接口。
