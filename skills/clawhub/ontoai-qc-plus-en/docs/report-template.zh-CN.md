# 质检报告模板与输出契约

版本 1.3.0 ｜ 2026-10-11

---

## 输出契约（四条，缺一不可）

借鉴 detect-only 模式的四要素，每条问题必须包含：

| # | 要素 | 要求 |
|:--:|---|---|
| 1 | **点名规则** | 必须引用本技能内已命名的规则代号（如 RZ-01、D2.4、C1）。**不命名的模糊指责无效** |
| 2 | **引用原文** | 必须给出具体位置（页码/行号/章节）+ 原文片段 |
| 3 | **给出修法** | 写明怎么改（或写"需用户补充"） |
| 4 | **不改的后果** | 必改项专有。写不出后果 = 不该进必改区 |

**三条硬禁令**：

- ❌ **不改写** —— 报告阶段不动原文，改需用户确认
- ❌ **不猜作者** —— 不判断"这是不是 AI 写的"，只判断"能不能交付"
- ❌ **不编造** —— 不补数字、不补引语、不补案例

---

## ★ 报告格式三条新规（v1.2 起强制执行）

> 逐条平铺的报告，用户要读 15 次才知道全貌。**先给全貌，再给细节。**

| # | 新规 | 说明 |
|:--:|---|---|
| **1** | **同级归类** | 同一分层的问题**归为一类、放在一张表里**，不得一条一条平铺。🔴 一个表、🟡 一个表、⚪ 一个表、✅ 一个表 |
| **2** | **先给计数** | 报告**第一屏**必须给出各分层的**数量**，以及按维度的分布。用户不看细节也能知道"有多少问题、集中在哪" |
| **3** | **表格优先** | 明细一律用**表格**，一行一条。只有必改项允许在表格下方追加"不改的后果"说明 |

**条形图（纯文本，任何 Markdown 环境都能渲染）**：

```
条形长度 = round(该层数量 / 各层最大数量 × 12)，最少 1 个 █
```

例：必改 2 / 可改 4 / 存疑 1 → 最大 4 → 必改 `██████`（6）、可改 `████████████`（12）、存疑 `███`（3）

> **⚠️ 落到 HTML / PDF 时不要照抄 `█` 和 emoji**（本轮踩过的坑）：
> - `█` 字符条在 HTML→PDF 打印链路里会变成**实心黑块**（尤其当某层数量远超基准、条被拉长时）；HTML/PDF 版一律改用 **CSS 画条**：`<span class="bar"><i style="width:…%"></i></span>`。
> - emoji（🔴🟡⚪✅）在 PDF 里会退化成**位图字形**、放大发糊；改用 **CSS 画彩点**（`dotEmoji()` 生成 `<span>` 圆点）。
> - **禁止对宋体/黑体/仿宋这类"无真粗体"的字体用 `font-weight:700`**：浏览器会"合成粗体"并把它存成 **Type3 位图** → 整段发糊。强调要么换有真粗体的字体（Microsoft YaHei），要么用彩色/加边框代替加粗。
> - 以上均已内置在 `assets/report.html`，改模板时勿回退；校验：PDF 里 **位图 Type3 计数必须为 0**。

## 版式与交付形态（HTML 版 / PDF 版）

当用户**明确要求**"出一份报告文件 / 给我看图表 / 导出报告 / 出 PDF"，或产物较复杂
（**问题 ≥ 8 条、多模态、批量文件**）时，生成报告文件。

### 四种版式（同一份 DATA，改一个字段即切换）

**模板只有一个**：`assets/report.html`。四套版式的 CSS 与渲染函数都在文件内，
由 `DATA.style` 字段选择，不需要维护四份文件。

| 版式 | `DATA.style` | 气质 | 适用 |
|---|---|---|---|
| **A · 官方检验报告** | `"a"`（默认） | 公文版式：宋体正文、红头线、检验结论框、印章位、编制/审核/批准签署栏、声明条款 | 正式对外、递交甲方、归档留痕 |
| **B · 第三方检测机构** | `"b"` | 实验室风：深蓝表头、结论徽章、编号小节、声明条款 | 委托检验、需体现机构中立性 |
| **C · 现代图表** | `"c"` | SaaS 风：卡片计数、条形图、环形图 | 屏幕阅读、内部快速过目 |
| **D · 学术 / 出版** | `"d"` | 期刊风：衬线、三线表、表题与注释、摘要段 | 书稿、论文、出版物审校 |

**切换方式**（优先级从高到低）：

1. URL 参数：`report.html?style=b`（临时预览用，不动文件）
2. `DATA.style` 字段（正式出报告时改这里）
3. **快捷切换条（默认）**：双击打开 HTML，左上角即悬浮款式切换条——4 个款式按钮 + 收起按钮（收起即恢复干净正式外观），点击即换款，无需输入任何参数
4. 全量对比：`report.html?picker=1`（带标题、各款描述与打印提示的完整对比条，可选）
5. 干净正式交付：`report.html?formal=1`（隐藏全部外壳，收件人看到的即纯报告）

切换条不会出现在打印/PDF 输出里（`@media print` 剥离全部外壳元素），因此"双击预览"与"正式交付"共用同一文件互不干扰。

**默认策略**：Markdown 报告为主交付物；要文件时——**屏幕阅读给 C 款，打印/PDF 给 A 款**
（A 款为 A4 公文版式，最稳，也最符合"官方、严谨"的对外气质）。

**四款落成样例**：`evals/samples/`（各含 .html 与 .pdf，直接用浏览器打开即可对比）。
改动 `report.html` 后，用 `node assets/gen-samples.js` 一键重生成四份 HTML+PDF（脚本会先删旧 PDF 再打印，避免误判到上一次的旧文件）。

### 两个交付形态

| 形态 | 说明 |
|---|---|
| **HTML 版** | 单文件、无外部依赖、离线可用。图表全部由原生 CSS 渲染，不引外部图表库 |
| **PDF 版** | 由 HTML 版打印生成，用于归档、发送、盖章。HTML 内已内置 `@page A4` 与背景色保留规则 |

**PDF 生成**：`node assets/make-pdf.js <输入.html> [输出.pdf]`
调用本机 Edge / Chrome 的无头打印能力，**不依赖 puppeteer / wkhtmltopdf**，离线可用。
未安装浏览器时的备用方案：浏览器打开 HTML → Ctrl+P → 目标「另存为 PDF」→ 勾选「背景图形」。

> **硬约束**：HTML / PDF / Markdown 三版**内容必须一致**。版式只是呈现层，不得增删问题条目。

### 语言切换（DATA.lang = zh / en）

报告 UI 支持中文 / 英文外壳切换，由 `DATA.lang` 控制（`"zh"` 默认，`"en"` 切英文外壳）。

- **作用范围**：仅切换报告自身的 **UI 标签**——含页面标题、版式大标题、各区块标题、表格列头（位置/问题/规则/原文/维度/结果/数量/分布/分层/含义/处置…）、四档图例短语（不改就别发 / 改了更好，不改也能发 / 我判断不了，请你确认 / 已检查、无问题…）、声明条款、签署栏、排版符号（`。「」｜` 等，分别转 `"` `.` `|`），以及 B 款的通过率英文文案，**约 120 处**。**受检产物正文、引用原文（`quote`）、规则代号（RZ-xx / RZE-xx）、维度名均保持原文**——中文产物报中文、英文产物报英文，不做翻译迁移（避免引入新事实 / 改变原意）。
- **实现方式**：`assets/report.html` 采用「先渲染、后本地化」模式——4 套皮肤渲染函数保持不动，组装出的 HTML 字符串在 `show()` 内过一道 `localize()` 做最长匹配替换（`ZH2EN` 字典 + 排序后 `split/join`），零风险、不重写皮肤逻辑。
- **字体切换**：`en` 模式下 `<html>` 挂 `.lang-en` 类——标题 / 强调字走 **Arial / Georgia**（均有真粗体，避免合成粗体 Type3 位图退化）；正文西文走 Arial，并保留 `Songti SC / SimSun` 中文回退，防止嵌含中文时乱码。
- **PDF 校验（英文模式额外硬约束）**：英文拉丁字体须为**矢量 Type0（嵌入子集）**，不得回退到合成粗体的 Type3 位图；校验须确认英文 PDF 中 **位图 Type3 计数 = 0**、且 **UI 标签无残留中文**（受检产物 → Product Inspected、检验结论 → Inspection Conclusion、合计 → Total、必改 → Must Fix…）。
- **英文样例**：`evals/samples/style-a-en.html` / `.pdf`（A 款官方检验报告 · 英文 UI），由 `node assets/gen-samples.js` 一并生成。

## 报告写作的负面清单

| ❌ 禁止 | 原因 | ✅ 替代 |
|---|---|---|
| 逐条平铺（【1】【2】【3】…） | 读 15 次才知道全貌 | 同级归入一张表，一行一条 |
| 只给明细不给计数 | 用户不知道有多少问题 | 第一屏给总览表 + 分布表 |
| "AI 味很重" | 无法指导修改 | "第 3 段存在三连排比（RZ-16），建议合并" |
| "读起来不像人写的" | 主观、不可执行 | 指出具体片段与规则代号 |
| "建议润色一下" | 无信息量 | 给出具体位置与改法 |
| "可能有问题" | 不确定 | 进存疑项，写明核不动的原因 |
| "整体质量不错，但…" | 客套话 | 直接给裁定与条目 |
| 自评分、"AI 含量 73%" | 伪装精度 | 用影响分与规则代号，不用百分含量 |
| 20 条必改项 | 用户不会看 | 超过 5 条改判「建议重做」 |

**报告的价值 = 用户扫一眼就知道有多少问题、集中在哪、该做什么。** 做不到这点的报告不如不给。
