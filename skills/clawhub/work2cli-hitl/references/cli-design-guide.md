# CLI 设计规范（从日常工作到命令行的逐条标准）

> 本文件是 SKILL.md Phase 2 的展开。给用户设计每个 CLI 时逐条对照，来自实战踩坑沉淀，语言与平台无关（示例文件名仅作示意）。

## 1. 领域拆分

- **一个外部系统一个 CLI**：订单系统一个、代码平台一个、工单系统一个。不做一个万能 CLI——各系统认证方式、状态枚举、迭代节奏都不同，混在一起改一个崩三个。
- **公共能力沉到独立模块**：`_common`（请求/签名/错误信封）、`_token_cache`（token 缓存）、`_write_guard`（审批流程）、`_feishu_gateway`（lark-cli 唯一出口）。**守卫和网关必须独立成模块，且测试可整体 mock**。
- **测试目录跟随**：守卫类逻辑必须离线可测（mock 外部依赖），覆盖批准/拒绝/超时/哈希不一致/网关故障五种路径。

## 2. 命令设计

- **子命令 = 工作流步骤**，命名用动词：`list`（列表）、`detail <id>`（详情）、`report <id>`（聚合报告）、`export <id>`（导出本地）、`pull`（一站式拉取+下载）、`apply <id>`（写回）。
- **高频多步操作做聚合命令**：如果 agent 干一件事要连调 4 个单点接口，就做一个 `report` 类命令一次拉齐。判断标准：同一会话里两个以上命令总是成串出现。
- **列表命令默认自动翻页**（`--all`），并提供 `--format jsonl` 流式输出处理大数据量。
- **过滤参数在客户端做**（`--status` `--level` `--keyword`），并在回显里带 `filtered_*` 字段说明过滤生效；同时回传 `status_breakdown` 类统计字段，让使用者一眼看全分布。
- **中英文/数字参数等价**：`--status done` = `--status 已完成` = `--status 4`，人记哪个用哪个。状态枚举必须和系统前端源码逐一核对后在 skill 里列表固化，并写「常见误读提醒」（中间态 ≠ 终态）。

## 3. 输出规范

```
stdout = 纯数据（agent 解析的根基，永远不要往里混人类提示语）
stderr = 错误/进度/提示
```

- 默认 JSON；`--format table` 人读表格；`--fields f1,f2` 按需取字段；`--jq .data[].id` 简易过滤。全局选项放命令前后均可（CLI 内部提升到最前）。
- **注意不同命令的返回结构差异并在 skill 里写明**：列表命令是 `{"data": [...], "count": n}` 信封，详情命令字段在顶层——agent 解析时别套错模板。
- 错误输出 JSON 信封：`{"type":"auth_invalid","code":401,"hint":"token 已过期，已尝试刷新"}`，hint 里写下一步该干什么。

## 4. exit code 表（全 CLI 统一）

| code | 含义 |
|------|------|
| 0 | 成功 |
| 1 | 参数错误 |
| 2 | 认证失败（token 拿不到/过期且刷新失败） |
| 3 | 限流；或写操作未获授权（靠 stdout 的 `{"approved": false}` 区分） |
| 4 | API 错误（远端返回异常） |
| 5 | 网络错误 |
| 6 | 未找到 |

## 5. 认证规范（无硬编码凭据）

token 获取优先级，逐级降级，全失败 exit 2 并打印手动获取指引：

1. 显式覆盖：`--token` 参数 / 环境变量（如 `XXX_TOKEN`）
2. 本地缓存：`~/.config/<tool>/token.json`（记录获取时间，过期与否以服务端 401 为准——收到 401 自动作废缓存重取）
3. shell 配置文件兜底：环境变量为空时，自动从 `~/.zshenv`/`~/.zshrc`/`~/.zprofile` 解析 `export XXX_TOKEN=` 行（用户把 token 写进 shell 配置后，CLI 免 export 直接可用——非交互 shell 也能吃到）
4. 自动获取：**用浏览器的登录态取**（agent 的浏览器操作能力从已登录会话里拿 cookie/token）
5. 全失败：exit 2，stderr 打印手动获取步骤（开发者工具 → 网络 → 复制 token）

skill 里写明：「token 一般无需设置，CLI 自动走 缓存→浏览器 链路；仅自动失败时才需要问用户」——agent 就不会上来就跟用户要 token。

## 6. 写命令规范

- **必须支持 `--dry-run`**：构造完整 payload 打印到 stdout（含参数哈希、提交后状态走向的 `result_label` 标注），不发请求。
- **守卫是常驻服务，不是随命令生死的一次性逻辑**：收飞书按钮回调的守护进程由 CLI 按需拉起并复用，决定走本地 spool；同参数在途卡片要复用，不重发。实现要点见 `write-guard-hitl.md` §2.5——这块最容易做错成「第一次能批、第二次没反应」。
- **执行后自动回读验证**：写成功后立刻回读目标对象，输出 `verified_*` 字段确认状态已流转，省掉手动复查。
- **不可逆操作在输出里标警示**：帮助文本和 dry-run 输出都写「不可逆/需先人工确认 XX」。
- **不可逆状态回写必须绑定外部事实**（实战教训）：终态回写（如「已打款」「已发布」「已关闭」）只能在外部事实发生后执行（财务回执/上线记录），**不能因流程到这一步就超前标记**——标早了下游会收到假通知。skill 里把「状态机 + 每步前置事实」写成硬规则。
- **参数语义陷阱单独成节写进 skill**：同一系统里同类资源常有双标识（数据库主键 `id` vs 业务单号 `orderNo`），写命令用错一个会改到别的对象。在命令帮助和 skill 里显式写「这个参数是哪个 id、从哪个命令的哪个字段拿」。
- **批量参数用逗号分隔**（`--id 29,28,24`），并回写每个 id 的处理结果；后端无批量接口时客户端封装循环 + 汇总「N/M 成功」。

## 7. 落地顺序建议

1. 先做**只读**命令跑通认证（连通性最快验证，也能立刻产生价值）
2. 再做聚合命令（`report`/`pull`），把 agent 的多步查询收拢
3. 最后做**写**命令：dry-run → 接守卫（Phase 4）→ 离线测试 → 真机演练
4. 每做完一个领域就补 skill + README 典型场景（真实用法 > 抽象描述）

## 8. 上下文保护：渐进式读取（给 agent 用的 CLI 特有）

Agent 的上下文窗口是稀缺资源，一个命令的输出就可能把它撑爆。大文件/大列表类命令必须做**三段式渐进**（实战验证的完整形态）：

```bash
<cli> file <id> <path> --meta-only              # 第一段：只看元数据（size/行数估算），不下载内容
<cli> file <id> <path> --head 50                # 第二段：分块读（--start-line/--end-line/--head/--tail）
<cli> file <id> <path> --grep "keyword"         # 第三段：CLI 内置 grep 定位（输出命中行号+上下文），再精读
```

- **大文件保护**：超过阈值（如 500KB）默认只给元数据 + 前 50 行预览 + 提示用分块参数；`--force` 显式绕过。错误信封带 `hint` 指路（如 `{"type":"file_too_large","hint":"用 --start-line/--end-line 或 --force"}`，此场景可加 exit 7）。
- **所有读取模式统一返回带真实行号的 `lines`**（`[{line, content}]`），agent 拿到就能引用，不用再写脚本补行号。
- 列表类大结果同理：`--all` 自动翻页 + `--format jsonl` 流式 + `--fields` 瘦身，别让人一个命令拉回全量字段的全量数据。

## 9. 服务端缺啥，客户端补（就地补偿模式）

内部系统的 API 常有缺陷，别硬吃——在 CLI 层补偿，并把补偿写进 skill：

| 服务端缺陷 | 客户端补偿 |
|-----------|-----------|
| 搜索不支持正则 alternation（`a\|b` 零结果） | `--keywords a,b` 逗号 OR，客户端合并去重 |
| 搜索无正则/过滤能力 | `--filter "regex"` 客户端对命中行二次过滤 |
| 无路径过滤，monorepo 搜索被无关服务淹没 | `--path` 客户端过滤（glob/子串） |
| blame/明细 API 不支持行范围 | 全量取回后客户端按行号裁剪 |
| 无批量接口 | 客户端封装循环 + 逐条结果 + 汇总统计 |

原则：**补偿是 CLI 的职责**（agent 每次都手搓就等于没沉淀），补偿行为写进命令帮助和 skill。

## 10. 跨系统关联映射

多系统工作台的核心杠杆：**一个系统的输出直接喂另一个系统**。把系统间的 ID/URL 映射关系固化进 skill（这是勘察阶段最值钱的发现之一）：

- 例：A 平台工单里业务填的修复链接是 `https://ep.example.com/scm/repo/<id>/mr/<iid>`——**`<id>` 直接就是 B 平台（GitLab）的 project id**，不需要任何转换就能 `mr-changes <id> <iid>` 拉修复 diff。
- 注册表条目里单列「跨系统关联」节：映射规则、验证方法、联动命令示例。
- 有了映射，「审核 A 平台的工单 → 直接核对 B 平台的代码 → 回写 A 平台结论」这种跨系统工作流才能一键化，否则每次都要人工换算。

## 11. 产物落地规范

批处理类命令（pull/export/payout）的输出是后续步骤的输入，落地结构必须确定：

- **输出目录结构固定**：如 `<outdir>/vulns.json + <id>_<uuid8>/`（每个对象一个目录：正文 md + `images/` + `attachments/`（自动解压）+ `messages/`），并输出一份处理后的完整 JSON 供下游直接读。
- **`--outdir` 必须指定为工作区内的绝对路径，禁用 /tmp 等临时目录**——产物是要被后续阶段和下次会话引用的。
- 附件自动解压时清理 `__MACOSX`/`.DS_Store` 垃圾；内嵌图片下载后把正文里的引用改写为本地路径。
- 引用产物的命令参数都用绝对路径，agent 跨会话也能续上。
