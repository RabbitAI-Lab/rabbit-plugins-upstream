# write-guard：写操作飞书 HITL 设计规范（完整版）

> SKILL.md Phase 4 的展开。指导实现一个「写命令执行前必须本人飞书批准」的极简 HITL 守卫。**规范与语言无关**（Python / Node / Go / Shell 均可实现）；文中出现的模块名与代码片段只是示意，不是必须照搬的结构。
>
> **前置假设**：环境已装好 `lark-cli` 并完成登录（`lark-cli auth login`），登录用户本人就是审批人。其余不假设。
>
> **定位（先读）**：这是**软控**，防的是「agent 偶尔判断错」和「agent 干太快没人来得及看一眼」，给人一次人工点头的安心感。**它不防「被明确指示绕过」的执行者**——本机运行的守卫，执行者（人或 agent）随时可以改守卫代码、绕过 guard 直接调底层 API、或手工构造请求。审批强度 = 遵守约定的意愿，对协作的 AI 有效，对对抗的场景无效。要硬控必须把控制点移出执行者权限（服务端只在审批后下发短期写凭据 / 远端 RBAC / 凭据与执行环境分离），见 SKILL.md「定位与边界」。

## 0. 一句话机制

CLI 的写/改/删类命令执行前，把操作摘要做成飞书交互卡片（含参数 SHA256 前 8 位），以 bot 身份发给**当前登录用户本人**；本人点卡片按钮（或文本回复 `ok <hash8>`）批准后才真正执行；10 分钟超时按拒绝。**任何环节失败都不放行（fail-closed）。**

**三条运行形态硬要求（自己用过踩出来的，实现时别省）：**

1. **收按钮回调的进程必须常驻**，不能随某次命令生死——否则批完这一次，下一次按钮就没人收了。
2. **同参数的在途卡片要复用**——同一个写操作重试/重跑时，老卡片没点就继续用它等，不要重发一张新的刷屏。
3. **事件订阅要短切片强制重建**——长连接会静默掉线变「聋」（进程活着、无报错、永远收不到事件），到点主动重连把丢失窗口压到常数分钟。

详见 §2.5。

## 1. 参与方与前提

| 参与方 | 说明 |
|--------|------|
| 写命令 | CLI 里变更远端状态的子命令（如 apply / close / update-status / send-message） |
| write-guard | 审批流程：算哈希 → 发/复用卡片 → 等决定 → 比对 → 放行/拒绝 → 审计 |
| **回调守护进程** | **常驻**收 `card.action.trigger` 按钮回调，把决定落到本地 spool；由 CLI 按需拉起、崩溃自动重启（见 §2.5） |
| feishu-gateway | lark-cli 调用的**唯一出口**，收窄成 6 个动作（whoami / 发文本 / 发卡片 / 拉消息 / 消费按钮回调 / 更新卡片），测试可整体 mock |
| lark-cli | 本机飞书 CLI，`lark-cli auth login` 登录态即凭据，**一人一应用**，无共享配置 |
| 审批人 | 操作者本人（卡片接收人固定为 `whoami` 的 `onBehalfOf.openId`） |

**不拦截**：全部只读命令；写命令的 `--dry-run`（只打印 payload，本来就不变更状态）。

## 2. 审批流程状态机

```
写命令被调用
  → 规范化参数（sort_keys 紧凑 JSON）→ SHA256 前 8 位 = hash8
  → 查本地在途记录：已有「同 hash8 且未决定」的卡片？
       ├─ 有 → 复用该卡片（不重发），直接进入等待
       └─ 无 → lark-cli whoami 取本人 open_id
              → bot 发交互卡片：工具/操作/目标/完整参数(截断800字符)/hash8/两按钮
              → 登记在途记录（hash8 → 卡片消息ID/chat_id/发起时间）
  → 确保回调守护进程在跑（pid 文件 + 锁；没跑就拉起，跑着就复用）
  → 等待决定（守护进程从 card.action.trigger 收按钮回调落 spool；
     或兜底 5 秒轮询会话消息找文本回复）
  → 决定 = 拒绝 / 10 分钟超时 → 不执行，exit 3，
       stdout 末行 {"approved": false, "reason": "..."}，卡片原位置为「未批准」终态
  → 决定 = 批准（⭐ 从 spool 领取，领取即标记 consumed——同 hash 的第二个等待者拿不到）
  → ⭐ 重算实际执行参数的哈希，与批准哈希比对
       ├─ 不一致 → 拒绝执行（fail-closed），审计记录 reason=hash_mismatch
       └─ 一致 → 执行原命令（行为与 exit code 完全不变）
  → 执行结果写回 spool（result 文件）→ 守护进程用它持有的 token
     把卡片原位刷成「执行结果」终态（预算按成功 1 次设计；
     刷失败/300040 → 静默回退发一条文本，不重试）
  → 清掉在途记录，audit.jsonl 追加一行（含 result_channel）
```

### 2.5 运行形态：全局单例守护进程 + 决定 spool + 卡片复用（⭐自己用踩出来的坑）

**架构总纲：全机只部署一个守卫守护进程，服务所有系统的所有 CLI。** 这不是优化项，是事件总线性质的必然结论——`lark-cli event consume card.action.trigger` 独占一个应用的事件总线（第二个消费者报 `another event bus is already connected`），两个进程抢 = 互相踢下线。所以：

- **一个登录应用 ↔ 一个常驻守护进程**，机器上所有产品的 CLI（订单系统、工单系统、代码平台……）都通过**同一份守卫客户端**（`cli/_guard/`，全机共享不复制）接入它；
- 守护进程不关心业务：它只按 **spool 里的 `<tool>/<hash8>` 命名空间**转发决定——哪个 CLI 的写命令在等哪个哈希，守护进程不用知道；
- CLI 按需拉起：检查 pid 文件 + 进程存活，没跑就拉起（守护进程内部自己抢文件锁，双开互斥），跑着就复用；崩溃自动重启（服务化）或由下一次任意 CLI 调用重新拉起；
- **CLI 自己绝不直接 `event consume`**——那是守护进程的专属活。

**spool 目录布局（按工具命名空间隔离，防跨系统哈希碰撞）：**

```
~/.config/work2cli-hitl-guard/
├── daemon.pid / daemon.lock        # 单例锁
├── inflight/<tool>/<hash8>.json    # 在途审批（卡片 message_id/chat_id/发起时间，供复用）
├── decisions/<tool>/<hash8>.json   # 守护进程落：{"decision":"approved|rejected","operator","message_id","time"}（领取即 consumed）
├── results/<tool>/<hash8>.json     # CLI 落：执行结果（守护进程读到后统一刷卡片，预算 1 次）
└── audit.jsonl                     # 审计（所有工具共用一个文件，按 tool 字段区分）
```

**决定流（按钮通道）**：守护进程收到回调 → 解析 `action_value.hash` + `operator_open_id` → 在 `inflight/` 里反查归属工具 → 把决定写进 `decisions/<tool>/<hash8>.json` → 对应 CLI 每 5 秒轮询领取（领取即标记 consumed；同 hash 第二个等待者拿不到，exit 3 reason=`decision_consumed`，防同一操作执行两次）。

**结果流（卡片刷新）**：CLI 执行完写 `results/<tool>/<hash8>.json` → 守护进程监听到 → 用自己持有的回调 token 把卡片原位刷成「执行结果」终态（预算按成功 1 次设计，见 §3）→ 刷成功/失败都记 `result_channel`。**刷新只由守护进程做**，CLI 不碰卡片更新。

**兜底通道不变**：守护进程不在/死了，CLI 的文本轮询照常工作（用户回 `ok <hash8>` 一样能批）；两条通道都不可用才 fail-closed。

**坑 A（历史教训）：回调消费者随命令生死 → 第二次审批永远收不到。** 守卫 CLI 每次执行写命令时自己起一个消费者、命令结束就退出，事件总线跟着退出。修法即上面的全局单例 + CLI 按需拉起。

**坑 B：同参数重复执行时重发卡片刷屏。** 重试、重跑、批量里多条同参数操作很常见——参数一样，审批意义也一样：

- 发新卡前先查 `inflight/<tool>/<hash8>.json`（未决定且未过期）→ 命中就**复用老卡片**，直接进入等待，不重发；
- 在途记录有寿命：超过等待上限的 2 倍（或卡片已明显过期）就作废重发；
- 复用卡片的刷新配额可能已被前一次用掉——反正刷新归守护进程统一管，记账判断即可，超了退化文本汇报；
- 审计记 `card_reused: true/false`。

**坑 C：结果刷新报 300040——回调 token 实测只能成功刷一次。** 旧的「刷两次（已批准+执行结果）」假设不成立。修法：刷新职责归守护进程，CLI 把执行结果写 `results/` 由它统一刷，预算只留给「执行结果」；300040 静默回退文本、不重试。细节见 §3「结果回写」。

**坑 D（⭐最阴险）：卡片「发出」≠「注册」——接入方漏注册，点击被静默丢弃。**

现象：用户点按钮没反应、卡片不刷新、**全链路无一处报错**（用户侧最多看到飞书弹「目标回调服务未在线」），而文本兜底通道一直是好的。根因形态：守卫客户端有个可选的集成参数（如「注册进共享 spool 的路径」），新 CLI 接入时照抄旧代码漏传了——卡片照发、审批照等、exit code 正常，**唯独卡片没进 inflight**，守护进程收到回调按卡片消息 ID 反查不到归属，只能静默丢弃。可选参数不传不报错，这是 HITL 接入里最坏的失效形态：三条通道看起来都活着，唯独最关键的一条断了。

修法（按优先级）：

1. **API 设计上消灭它**：守卫客户端把「注册」并进「发卡」动作内部，不提供可绕过的开关；
2. **等待前自检**：进入等待循环前校验「本卡片已注册且归属本工具」，未注册直接 fail-closed 报错，绝不带病等 10 分钟；
3. **接入验收硬规则**：新 CLI 接守卫，**验收标准 = 真人点一次按钮、看到卡片原位变成「已批准」终态且命令真正执行**。「卡片发出来了」「审批流程走完了」都不算接入成功。

**坑 E：常驻消费者也会「聋」——长连接静默掉线，进程活着但永远收不到事件。**

现象：守护进程在跑、consume 子进程在跑、无任何错误日志，按钮点击就是收不到（平台不排队、不补投，这条事件等于丢了）。根因：长连接被网络抖动/服务端掐断后，消费侧进程不退出也不报错——**「进程在」不等于「连接健康」**。

修法（把最坏丢失窗口从「直到进程重启」压到常数分钟）：

- **短切片强制重建**：一次事件订阅别超过几分钟（实测 1800s 太长，改 300s），到点主动断开重连——聋连接最多聋一个切片；
- **CLI 本进程兜底消费同理**：检测到消费子进程退出且**无错误输出**（EOF 但无 channel_error）就自动重建通道（带冷却间隔，防紧转）；此前一旦断线就聋到审批超时；
- **区分两种失败**：通道级报错（如总线被占，见 §7）→ 退避重试（30s 级）；静默 EOF → 立即重建。混淆处理要么紧转刷日志、要么带病等待。

> 守护进程从哪来：写守卫落地时一并交付（参考骨架见 [../../demo/guard/feishu_guard_daemon.py](../../demo/guard/feishu_guard_daemon.py)），并写进 README 自检清单——`守护进程在跑吗 / 杀掉后能自动拉起吗 / 两个不同 CLI 连续审批都能收到吗`。这三问过不了，按钮审批就是「一次性的」，形同虚设。

### 关键细节（都来自实测）

- **哈希算法**：把参数规范化成 keys 排序、无多余空格的紧凑 JSON（`sort_keys=True`、`separators=(",",":")`、保留非 ASCII），取 `sha256(canonical.encode("utf-8")).hexdigest()[:8]`。摘要与执行校验必须用**同一函数**。
- **文本回复解析**：`^no$` → 拒绝；`^ok\s+([0-9a-f]{8})$` → 哈希匹配才批准，**不匹配的 ok 视为无关消息忽略**（可能是对另一个待审批操作的回复）；一律先 `strip().strip("`'\"").lower()` 再匹配。
- **只认请求消息之后的消息**：轮询会话消息时按 `message_position` 排序，只看我们那张卡片**之后**、`sender_type == "user"` 且未删除的消息，最后一条匹配指令生效。卡片消息找不到时保守视为尚无决定。
- **倒计时不静默**：等待期间每 30 秒在 stdout 打一行倒计时状态，让调用方（人和 agent）都知道在等审批。
- **等待上限 600 秒**，超时 = 拒绝。

### 排障视图：「点了没反应」四道闸门（⭐）

一次按钮点击要落到「命令真正执行」，中间有**四道闸门**，任何一道断掉，用户看到的现象几乎一样：点了、卡片不动、没报错。排查时按依赖方向逐道确认，别跳步：

```
用户点按钮
  → ① 平台投递：要求该应用此刻有在线消费者；没有时事件直接丢
       （不排队、不补投），用户侧弹「目标回调服务未在线」
  → ② consume 子进程收到：WS 会静默掉线「聋掉」（坑 E），进程在 ≠ 连接健康
  → ③ 按卡片消息 ID 反查归属：卡片必须注册在 inflight 里（坑 D），查无此卡即静默丢弃
  → ④ CLI 领取决定 + 哈希比对执行：决定可能已被同 hash 的另一个等待者领走
```

| 断点 | 特征信号 | 查什么 |
|------|---------|--------|
| ① | 飞书弹「目标回调服务未在线」 | 守护进程活着吗（pid 文件 + 进程在）？消费子进程在吗？ |
| ② | 全在跑但点击收不到、无错误日志 | 子进程跑了多久了？接近切片上限就等重建；立即要通就重启守护进程 |
| ③ | 进程全在、事件也到了、卡片不刷新 | 卡片注册进 inflight 了吗？——调用方漏传注册参数（坑 D），查接入代码 |
| ④ | 卡片刷成「未批准」或 reason 异常 | 看审计 jsonl 的 result 与 reason |

通用排障命令序列（按 ①→④ 顺序跑）：

```bash
pgrep -fl "<guard-daemon>"                          # ① 守护进程活着吗
ps aux | grep "<lark-cli>.*event consume" | grep -v grep   # ② 消费子进程恰好一组？
ls ~/.config/<guard>/inflight/<tool>/               # ③ 在等的卡片注册了吗（找本次 hash8）
tail -5 ~/.config/<guard>/audit.jsonl               # ④ 最近一次审批的 result/reason
```

**总线串台提醒**：自检或测试 `event consume` 必须用守卫**专用 profile**——默认应用可能挂着别的常驻系统（值班机器人、门禁类服务，甚至可能在别的机器上）的远程事件连接，撞 `another event bus is already connected` 不代表守卫坏了；反过来，守卫也绝不能寄生在共享应用上（§7 方案 B 的适用场景）。

## 3. 卡片与消息规范

**审批卡片文案**（文本兜底消息同内容）：

```
🔐 [write-guard] 写操作审批
工具: order_cli
操作: apply
目标: 订单 27127
参数:
{ ...完整参数，截断至 800 字符... }
参数哈希: a1b2c3d4

回复「ok a1b2c3d4」批准；回复「no」拒绝。
10 分钟内未回复视为拒绝。
```

交互卡片另带两个按钮：value 里放 `{"hash": "a1b2c3d4"}`，回调事件里三重匹配：**卡片消息ID + 点击人 open_id（必须等于本人）+ action_value 里的哈希**。

### 卡片可读性：审批卡片是给人审的（⭐）

**uuid 串和 JSON 墙没有可审性。** 人看不懂的卡片，点「批准」只是仪式——HITL 的全部价值都在「人看清了要干什么」这一眼上。批量改状态类操作尤其严重：目标一多，原始参数区就是一堵 `id+uuid` 的墙。

守卫客户端支持可选 `detail`（markdown 明细）：**给出时替代参数 JSON 区**，不传保持旧行为（已有 CLI 零影响）。批量改状态类操作的推荐模板（业务字段按需自定，模板只定结构）：

```
操作: update-status (<对象状态> -> <目标状态>)
目标: <N> 单 → <目标状态>（#<id>、#<id>、#<id>）
参数哈希: a1b2c3d4

共 <N> 单 → <目标状态>
- **#<id>** <当前状态> → <目标状态> ｜ <对象名称/一句话标识>
- **#<id>** <当前状态> → <目标状态> ｜ <对象名称/一句话标识>
```

三条实现规则：

1. **同源硬规则**：`detail` 纯展示，执行校验仍绑定机器参数（params）的哈希；detail 必须与 params **在同一处代码从同一份数据生成**——「人批的是 A、执行的是 B」比 JSON 墙更危险，可读性不能引入新的漂移面。
2. **名称来路要只读**：人类可读标识（对象名/标题）在发起审批前按目标补查，每个目标 ≤1 次只读请求（批量 ≤5 时开销可忽略）；查不到降级为仅编号，绝不阻塞审批。
3. **批次人审工程学：一次审批卡片 ≤5 个目标**——CLI 做成硬约束（超限报错，显式旗标才能越过）。卡片太长看不过来 = 没审；真有大批量需求就拆批发卡，审批次数多一点是特性不是缺陷。

### 文本兜底指令要「一键可复制」（⭐）

按钮通道退化到文本回复时（卡片点不动/事件通道坏了），用户要手打 `ok <hash8>`——这个哈希**别埋在散文里**。卡片上的兜底指令单独给一个代码块元素，移动端/桌面端都能一键复制：

> 批准或拒绝可直接复制回复：
> ```
> ok a1b2c3d4
> ```
> （拒绝则回复 no）10 分钟内有效，超时视为拒绝

反面教材：`也可回复「ok a1b2c3d4」/「no」` 这种嵌在句子里的写法，手机上把引号里的哈希选干净非常费劲——兜底通道本来就处在「出事了」的语境，别再叠加复制摩擦。文本兜底消息同理：`ok <hash8>` 独占一行。

**结果回写（⭐预算按「成功 1 次」设计，别依赖 2 次）：**

- **实测结论**：按钮回调返回的卡片更新 token，实际只能**成功刷新一次**（第二次报飞书 `300040 update token invalid`）——「已批准态 + 执行结果态刷两次」的旧假设不成立。谁先刷谁拿走预算：守护进程刷完「已批准」后，CLI 再刷「执行结果」必然失败，只能回退单独发文本（审批/执行/审计不受影响，纯体验问题）。
- **推荐方案（守护进程统一负责刷新）**：CLI 执行完把结果写回 spool（`pending/<hash8>.result.json`：exit code、成功/失败、输出尾部 600 字符）；守护进程监听到结果文件后，用它持有的 token **一次性**把卡片原位刷成「执行结果」终态——预算让给用户最关心的「执行结果」，「已批准」态不再单独刷（点按钮本身有交互反馈）。
- **降级方案（无守护进程模式）**：CLI 自己持有 token 时，直接把这次刷新用在「执行结果」上；「已批准」态省掉。
- **300040 处理**：捕获该错误码，**静默回退发一条文本消息汇报结果，不重试**（重试必然还是 300040）；审计里记 `result_channel: card | text_fallback`，复盘时能看出结果回写的实际到达方式。

## 4. 结果语义（对调用方/agent 的契约）

| 场景 | 行为 |
|------|------|
| 批准且执行 | 原命令行为与 exit code 完全不变（审批对成功路径零侵入） |
| 拒绝 / 超时 / 哈希不一致 / lark-cli 不可用 | **不执行**，exit code = 3，stdout 最后一行 `{"approved": false, "reason": "..."}` |

> 注意与限流共用 exit 3 的 CLI：靠 stdout 的 `approved:false` 区分，agent 判断「未获授权」必须同时看 exit code 和 stdout。

## 5. 审计日志

每次授权事件追加一行 JSON 到 `~/.config/<项目名>-write-guard/audit.jsonl`：

```json
{"time": "2026-09-19T10:30:00+08:00", "tool": "order_cli", "op": "apply", "target": "订单 27127", "hash": "a1b2c3d4", "result": "approved|rejected|timeout|hash_mismatch|gateway_error", "reason": "..."}
```

追写文件（append），从不覆盖；事后可复盘「谁在什么时候批了什么」。

## 6. lark-cli 约定（实现网关时照抄，已在 lark-cli 1.0.79 实测）

| 能力 | 调用 | 要点 |
|------|------|------|
| 身份 | `lark-cli whoami` | `onBehalfOf.openId` = 当前登录用户本人 |
| 发消息 | `lark-cli im +messages-send --as bot --user-id <open_id> [--msg-type interactive]` | 响应 data 里直接带 `chat_id`/`message_id`；bot 无法列 p2p 会话，轮询用的 chat_id 必须从发送响应里拿 |
| 拉消息 | `lark-cli im +chat-messages-list --as bot --chat-id <chat_id>` | `sender.sender_type` 区分 user/app（bot 自己是 app）；排序用 `message_position`（create_time 只有分钟精度） |
| 按钮回调 | `lark-cli event consume card.action.trigger --as bot` | 输出扁平 JSON：`message_id`/`operator_id`/`action_value`/`token`（30 分钟内可原位更新）；需在开发平台控制台为应用订阅该事件（长连接模式）。**事件总线独占：这个消费者只能由常驻守护进程持有**，CLI 或其他进程再起一个会把守护进程踢下线（报 `another event bus is already connected`） |
| 原位更新 | card/update（bot 身份，卡片 1.0 需带 open_ids） | 受频控 30 分钟 2 次 |

- 二进制定位：PATH 找不到时回退 `~/.local/bin/lark-cli`。
- profile：支持专用 profile（名字自取，如 `<项目>-guard`），取值顺序 = 显式传入 > 环境变量（如 `WRITE_GUARD_LARK_PROFILE`）> 自动检测（`profile list` 里存在同名 profile 就用）> 默认。所有调用统一加 `--profile`。
- 版本差异：以上命令依据 lark-cli 1.0.79；换版本先跑一遍 `--help` 核对子命令名与参数。
- **未登录/调用失败/二进制不存在 → 一律按拒绝处理，绝不放行。**

## 7. 接入方式（团队/个人）

- 写命令在谁的机器上跑，就用谁自己的 lark-cli 登录态——一人一应用，事件总线互不冲突，无共享凭据。
- 首次初始化二选一：**A. 用默认应用**（零配置，按钮点不动时按 stderr 提示打开订阅直达链接一次）；**B. 新建专用应用** `lark-cli config init --new --name <项目>-guard`（默认应用事件总线被占用时报 `another event bus is already connected` 时用）。
- 自检五项：`whoami` 有 openId → `profile list` 看专用 profile → 守护进程在跑（pid 存活）→ `event consume card.action.trigger --timeout 5s --quiet` 无输出即通道干净（**注意：这条会抢总线，自检时先停守护进程，查完再拉起**）→ 目标应用 `whoami`（open_id 按应用隔离）。

## 8. 测试清单（全部离线，mock 网关）

| 用例 | 期望 |
|------|------|
| 卡片按钮批准 | 执行原命令，exit code 不变，卡片刷新结果，审计 approved |
| 文本 `ok <hash8>` 批准 | 同上 |
| 文本 `no` / 点拒绝 | 不执行，exit 3，stdout 末行 approved:false，审计 rejected |
| 600 秒无回复 | 不执行，exit 3，审计 timeout |
| 批准后参数被改（哈希不一致） | 拒绝执行，审计 hash_mismatch |
| 哈希不符的 ok（别操作的回复） | 忽略，继续等 |
| 网关故障/未登录/二进制缺失 | 不执行，exit 3，审计 gateway_error（fail-closed 验证核心用例） |
| **守护进程不在 → CLI 自动拉起** | pid 文件 + 锁正确，拉起后按钮决定可达 spool |
| **守护进程被杀 → 再来一次写命令** | 重新拉起成功，第二次审批按钮仍然生效（「一次性审批」回归测试） |
| **同参数重复执行（老卡未决定）** | 复用在途卡片，不重发；审计 card_reused=true |
| **同 hash 两个等待进程** | 决定只被第一个领取并执行；第二个 exit 3 reason=decision_consumed，不重复执行 |
| **在途记录过期** | 作废重发新卡；复用卡片刷新超频控时退化为文本消息 |
| **执行结果回写（守护进程模式）** | CLI 写 result 文件 → 守护进程统一刷卡片成「执行结果」终态，卡片只刷这一次 |
| **刷新报 300040** | 静默回退发文本汇报结果，不重试；审计 result_channel=text_fallback |
| **新 CLI 接入验收（集成）** | 真人点一次按钮 → 卡片原位变「已批准」终态且命令真正执行；这是接入成功的唯一标准（「卡片发出了」不算） |
| **消费连接静默退出（聋连接回归）** | 消费子进程 EOF 且无错误输出 → 自动重建通道，重建后的点击仍可达 |
| **卡片可读性/可复制** | 传 detail 时卡片显示明细而非 JSON 墙；`ok <hash8>` 有独立代码块可一键复制 |

## 9. agent 协作要点（写给会调用带守卫 CLI 的 agent）

- 看到命令卡住且 stdout 有倒计时 → 是在等飞书审批，**如实转告用户去飞书点按钮**，不要杀进程、不要绕过。
- 看到 exit 3 + `{"approved": false}` → 本次写操作被拒/超时，向用户复述 reason，等用户明确指示后再重试（重试会重新走审批）。
- 不要把守卫说成「安全边界」——它是**软控**。如实描述：「执行前会请你本人在飞书确认一次，防手滑和 AI 判断失误」。agent 自己也不该尝试 mock/跳过守卫：那等于背着用户改变了约定，破坏了这次协作的信任基础（技术上做得到，但性质是越界，不是「机智」）。
- 若用户明确要求绕过守卫（如「别审批了直接执行」）→ 停下来说明：走守卫是为了让他本人有决定权，然后问是要**这次单独放行**（临时 `--no-guard` 类开关，需用户显式确认）还是**改规则**（改 md/代码），不要默默跳过。
