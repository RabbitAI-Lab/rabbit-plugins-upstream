# 自主勘察：从一个网址到 API 全貌（不问用户）

> SKILL.md Phase 1 的展开。用户只给一个网站地址，agent 自己摸清系统、判读写、炼 CLI。手法提炼自实战（前端单页应用 + 自定义签名 + 状态机复杂的内部平台），对绝大多数 Web 系统有效。**前提：agent 具备浏览器操作能力**（打开页面、读页面、执行页面脚本、观察网络请求）。

## 0. 勘察顺序总览

```
① 进得去吗（登录态）→ ② 页面上有哪些功能（信息架构）
→ ③ 每个功能调什么 API（网络请求观察 / 页面脚本源码）
→ ④ 哪些是写（HTTP 方法 + 语义信号 + 前端二次确认弹窗）
→ ⑤ 枚举/状态机语义（前端源码核对，别猜）
→ ⑥ 签名/加密算法（从页面脚本里逆出来）
→ ⑦ 产出《勘察报告》给用户拍板
```

## 1. 进系统（认证自发现）

- **优先复用已有登录态**：用户日常在用的系统，浏览器里多半已登录。用浏览器操作能力直接带登录态操作；cookie/token 从已登录会话的请求里自动取，**不问用户要 token**。
- 需要登录时：一句话「浏览器里登录一下 XX，好了说一声」，然后自动从登录后的请求里提取凭据。只在自动化手段全失败时才让用户手动复制 token，并给出精确步骤（开发者工具 → 网络 → 任意 API 请求 → 请求头的哪个字段）。
- 有现成 API 文档/OpenAPI/已有脚本的：直接读，跳过网络勘察的大半工作。

## 2. 摸 API 面

两条腿一起走，交叉验证：

**A. 动态观察（真实操作）**：跟随用户/自己在页面上的真实操作（列表页、详情页、筛选、导出……），记录每个操作触发的请求：URL、方法、请求体、响应结构、鉴权头。这是**行为 → 接口**的映射，最可靠。

**B. 静态挖脚本（前端源码）**：动态操作只能覆盖走过的路径，页面加载的脚本里有全部：

```bash
# 从网络请求里拿真实的 chunk/脚本 URL（静态猜 webpack hash 命名几乎必 404）
# 下载后挖接口路径与枚举
grep -oE '"/api/[a-z0-9_/]+' app.*.js | sort -u          # API 路径全表
grep -oE '(status|state)[=:][0-9]' app.*.js               # 状态码使用点
grep -oE '[a-zA-Z_]+:(["'"'"']?[a-z_]+)["'"'"']?,' app.*.js  # 枚举名
```

静态挖到的每个接口都要在动态侧找到对应行为（或确认是废弃代码）才可信。

## 3. 读写分型（核心：写操作识别信号）

对每个接口按下表打分判定，**拿不准的一律按写对待**（宁可守卫多拦，不可 HITL 漏拦）：

| 信号 | 判定 |
|------|------|
| GET / HEAD，无副作用语义 | 只读（但仍需排除「GET 带副作用」的烂设计——看前端调用场景是否伴随状态变更提示） |
| POST/PUT/PATCH/DELETE | **按写对待**，除非路径和响应明确是查询（如 `POST /search`） |
| 路径动词：create/add/update/edit/delete/remove/apply/close/submit/approve/reject/send/reply/revoke/transfer/order | 写 |
| 前端对该操作弹「确认执行吗」二次确认框 | 写，且大概率不可逆 → 记入不可逆档 |
| 操作后页面状态流转（列表行状态变化、按钮消失） | 写 |
| 操作结果发通知/消息/邮件 | 写（有外部副作用） |

**绝不允许在勘察阶段真实调用写接口来验证**——写操作的验证靠 dry-run 思维：前端点「确认」前停下，把构造好的 payload 记录下来即可；语义拿不准就标「待确认」进报告，让用户拍板。这也是整个流程里 HITL 思想的第一次落地。

## 4. 枚举与状态机（从源码核对，别猜）

- 状态枚举（如 待处理/进行中/已完成/已驳回）以**前端渲染源码为准**：找到列表/详情页把状态码映射成标签的那段代码，逐一核对后固化成表格写进 skill，并附「常见误读提醒」——**注意区分中间态和终态**（踩过的坑：把「待确认/待复核」这类中间态当成了终态，把还在流转的对象当成可收尾的）。
- 筛选参数支持中文名/英文/数字多种写法等价，CLI 层做归一。
- 后端「预留状态」（前端无渲染、实测查不到数据）标注出来，别让 CLI 支持一个永远没结果的值。

## 5. 签名/加密算法（有就逆，逆不动就带原请求头重放）

- 从前端脚本定位签名函数（搜 `sign`、`md5`、`sha256`、`hmac`、请求拦截器里的 header 组装逻辑），逆出算法后在 CLI 里复现，并用抓到的真实请求**逐字节验证**（同输入必同输出才算过关）。
- 逆不动或算法混淆严重的降级方案：CLI 支持透传「从浏览器复制的完整请求头」模式，但要在报告里注明这是降级、有 token 过期问题。
- sign 覆盖范围要确认：只签 query？还是签 JSON body？**别信文档，以抓包逐字节验证为准**（踩过的坑：文档没写的 body 签名，靠抓包才确认下来）。
- 注意时间戳/nonce 类参数：确认是否有有效期窗口，CLI 复现时要现取现算，不能缓存。

### ⭐ sign 枚举比对：钉死写接口的 body 契约（无需反复真实写入）

写接口的请求 body 契约常常拿不准（表单字段多、字段名不直观、文档缺失），又不能拿生产数据反复试写。手法：

1. **一次真实点击拿基准**：让用户（或测试环境）在页面上真实执行一次该写操作，抓包拿到请求的 `sign` 和能观察到的部分参数；
2. **候选假设枚举**：结合前端脚本里该请求的提交处理函数（组装 body 的代码）列候选 payload——完整表单版、精简字段版、字段类型变体（数字 vs 字符串），通常不超过几个；
3. **对每个候选算 sign，与抓包基准比对**：sign 是 body 的确定性函数——**算出的 sign 与基准一致，就证明候选 payload 与真实请求参与签名的字段、名称、取值完全一致**（哈希碰撞除外）；
4. 命中的那个假设就是 body 契约，CLI 直接复现，之后不需要再点平台。

要点：候选里「缺字段」和「字段为空」在规范化签名串里可能是等价的（部分实现会跳过 null/空值），确认 CLI 的取舍与服务端语义一致即可。无签名接口不适用此法，改用「写后回查」验证（写完立刻 list/get 核对字段值）。

## 6. 产出《勘察报告》（唯一找用户的确认点）

格式：

```
## 平台勘察报告：<系统名/网址>
### 1. 认证方式（自动拿到 / 需登录一次 / 需手动 token）
### 2. API 清单与读写分型
| 接口 | 方法 | 判定 | 依据 | 对应页面功能 | 建议 CLI 命令 |
|------|------|------|------|------------|--------------|
### 3. 状态机/枚举表（含常见误读提醒）
### 4. 签名机制（复现方案 / 降级方案）
### 5. 待确认项（语义拿不准的接口 + 我的猜测，请拍板）
### 6. 建议的 CLI 命令面（list/detail/report/... 哪些先做）
```

**写操作判定必须醒目汇总**（漏判一个 = 绕过 HITL）。用户拍板后直接进 Phase 2 开写，过程中不再逐条问；勘察阶段拿不准的新问题，攒着在下一次确认点一起问。
