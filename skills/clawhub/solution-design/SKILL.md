# 方案设计

## 定位

把**目标**变成**路径**。输入是想要达成的结果与现实现约，输出是分步可执行、资源可核算、结果可验收的方案。不判断材料真伪、不写成稿文本——只回答"要达成这个目标该走哪几步、每步谁做、做到什么程度算完成、什么情况下这套方案会失效"。方案的消费品是执行，因此模糊的形容词是方案的头号敌人：每一步都必须有动词、责任人与验收标准。

本负载物自成体系：域划分、任务清单、零件规格、范本与模板、场景管线、执行流程全部内置，不依赖任何外部方法或其它资产。回答三个问题——**这个领域做什么**（域与任务）、**每件事按什么零件组装**（要求清单）、**做完长什么样**（范本与模板）。

## 核心能力

1. **目标可测量化**：把"提升体验""加强管理"等模糊诉求转成可测量的目标与验收标准
2. **约束显式化**：把预算、人力、周期、合规、技术条件摆上台面，作为方案边界而非事后借口
3. **路径分解**：把目标拆成有依赖关系的阶段与动作，标出关键路径与可并行项
4. **资源核算**：估算每步所需人力、时间、预算与外部依赖，给出总量与峰值
5. **风险与预案**：识别关键假设与失败模式，为高影响风险预置备选路径
6. **验收与复盘设计**：定义验收指标、数据来源、复盘节点与调整触发条件

## 方案设计特有维度

| 维度 | 说明 | 影响 |
|------|------|------|
| 约束强度 | 预算、人力、时间、合规四类约束的刚性程度 | 决定方案是"理想型"还是"底线型"，影响路径取舍 |
| 执行主体 | 方案由谁执行（个人/团队/外部供应商） | 决定颗粒度与交接设计 |
| 可逆性 | 执行后回退的成本 | 决定是否需要分阶段试点与灰度 |
| 验收客观性 | 结果能否用数据客观判定 | 决定验收标准是量化指标还是评审清单 |
| 失效条件 | 方案在什么条件下不再成立 | 决定预案设计的必要性与触发阈值 |

## 使用规则

**触发条件**：当用户提出与本领域相关、且期望产出物为「可执行方案」的请求时启用。触发词见 frontmatter 的 description 字段。

1. 首次加载读 `references/solution-design-catalog.md` 定位场景与任务；确认后读 `references/solution-design-requirements.md` 取组件清单。
2. 需要成品骨架时复制 `templates/` 下对应模板，按双花括号占位符逐项填充。
3. 需要参考结构或体例时读 `references/solution-design-exemplars.md` 与对应域范本文件（提供结构骨架与判定标准，非成品范文）。
4. 动笔前必须确认目标、约束、执行主体、周期四项，缺项先问，不得自行假设预算与人力。
5. 每个动作必须有动词、责任人、时限与验收标准，四缺一即视为未完成。
6. 涉及医疗、法律、教学的方案必须附专业复核提示；不得替代持证专业人员判断。
7. 本负载物只负责路径与验收设计，不判定结论真伪，也不做文字润色；方案所依赖的判断与数据须由使用者提供或确认。

## 与执行框架的接口

任何请求都从 Step 0 进入，按以下五步推进：

### Step 0 三轴判定

判定复杂度、内容类型、创新需求：

- 复杂度：单域单任务为简单；跨 2-3 域为中等；跨 4 域以上或需多轮校准为复杂
- 内容类型：本负载物全部任务产出为**结构化**内容（报告/文稿/方案/工程件）
- 创新需求：常规执行为无需创新；用户要求"不一样""更有洞察"时激活创新轴

### Step 1 领域校准

先按域名定位到本负载物的域号，再按该域权重校准元操作配比：

| 校准项 | 本负载物取值 |
|--------|-------------|
| R1 信息密度 | 中 —— 需先吃透约束与既有资料，但重心在路径设计 |
| R2 创造性 | 中高 —— 路径设计需要创造性，但必须服从约束与可执行性 |
| R3 交互性 | 中 —— 目标与约束确认、方案评审两处需要交互 |
| R4 规范性 | 中 —— 教学与医疗类方案受课标与临床规范约束，G 权重提升 |
| R5 迭代性 | 高 —— 方案天然需要按周期迭代（P2 循环），尤其是训练、增长与投放 |

**R1-R5 → 执行参数映射**：

| 参数 | 推导结果 |
|------|---------|
| 核心术语 | 目标、约束、里程碑、关键路径、验收标准、假设、预案、颗粒度 |
| 元操作权重 | S 20% / C 35% / A 30% / O 5% / G 10%（医疗与教学域 G 提至 15%） |
| 关键变量 | 目标清晰度、约束刚性、周期长度、执行主体能力、外部依赖 |
| 守护约束 | 不得假设未确认的预算与人力；医疗法律方案强制专业复核提示；安全类方案必须含风险预案 |
| 产出格式 | 方案文档（目标 → 约束 → 路径与里程碑 → 资源 → 验收 → 风险预案） |
| 自治度偏好 | 半自动 —— 路径可全自动设计，资源承诺与优先级须人工确认 |
| 创新评估侧重 | 侧重路径创新（用更少资源达成同一目标），而非目标本身的颠覆 |

### Step 2 任务分解

按 Step 1 的权重把任务拆为 3-15 个元操作单元；入口单元通常是 S 类（取数/检索/读取材料），终点单元为 A 类（产出）。域内任务依赖关系见 `references/solution-design-catalog.md`。

### Step 3 管线编排与执行

依依赖拓扑串联单元，按需套用通用管线模式：单点研判用 P1 基础闭环；多轮校准用 P2 迭代精炼；多源汇聚用 P3 并行汇聚；分场景输出用 P4 条件分支；需人工确认用 P5 交互驱动。

### Step 4 整合交付

按本域范本文件规定的结构组装成品；默认展示最少必要信息，用户要求"展开"时逐层揭示；重要判断必须展示推导过程与证据出处。


## 输出要求

| 项 | 要求 |
|----|------|
| 输出格式 | 方案文档（目标 → 约束 → 路径与里程碑 → 资源 → 验收 → 风险预案） |
| 动作四要素 | 每个动作须含动词、责任人、时限、验收标准，缺一视为未完成 |
| 约束先声明 | 预算、人力、周期三项未确认须标「待确认」，不得自行假设 |
| 验收可判 | 验收标准须客观可判，禁止「体验良好」类表述 |
| 专业复核 | 医疗、法律、教学类方案附专业复核提示 |
| 不确定信息标注 | 数据缺失标「缺失」、推断标「推断」、未验证标「待验证」，三类不得混用 |

## 边界与越界处置

遇到下列请求时按「处置」列执行，不作解释性让步；处置方式本身即为交付内容的一部分。

| 越界请求 | 处置 |
|----------|------|
| 要求承诺治愈、录取、胜诉或收益 | 拒绝承诺结果；改为给前提条件、概率区间与风险 |
| 要求设计规避监管或规避审计的方案 | 拒绝；指出合规风险并给替代路径 |
| 预算、人力、周期未确认 | 标「待确认」，不得自行假设数额 |
| 医疗、法律、教学类方案 | 附专业复核提示，不替代持证人员判断 |
| 要求把口号写成方案步骤 | 拒绝；改为「动作＋责任人＋时限＋验收标准」 |

**说明**：本表只列越界**类型**与处置**动作**，不枚举未覆盖的主题——能力范围以 `@references/solution-design-catalog.md` 的任务清单为准，清单之外即不在射程内。

## 通用任务执行能力

本负载物的任务由**三轴正交**框架驱动：执行轴（怎么做，必选）+ 内容轴（内容从哪来，按需）+ 创新轴（如何不同，按需）。

**执行轴**：六大元操作 —— S 感知（采集/检索/读取）、C 认知（分析/评估/归因）、A 行动（产出/写入/生成）、O 组织（结构化/归档/编排）、I 交互（澄清/确认/转介）、G 守护（校验/合规/边界）。六种编排模式：顺序 `→`、并行 `‖`、条件 `?`、循环 `↻`、扇出 `⇉`、扇入 `⇇`。七种管线模式：P1 基础闭环 / P2 迭代精炼 / P3 并行汇聚 / P4 条件分支 / P5 交互驱动 / P6 全守护 / P7 发散收敛。

**内容轴**：清单法（按 `requirements` 槽位逐项填充）+ 样本法（按 `exemplars` 与域范本的结构与判定标准模仿）。

**创新轴**：默认关闭；仅当用户明确要求"不一样""更有洞察"时启用，启用后仍须过边界处置与自检。

**三轴协同**：顺序协同为默认；多源材料用并行协同；校验不通过时用迭代协同（G 发现问题 → 回到对应 A 任务修正）。

## 事实纪律

1. 不得假设未确认的预算、人力与时间约束。
2. 每个动作须有动词、责任人、时限与验收标准。
3. 涉及医疗、法律、教学的方案须标注专业复核要求。
4. 不得用"加强""优化""提升"等无动词表述充当方案步骤。
5. 关键假设必须显式列出，并给出失效条件。
6. 引用外部数据与标准须标注来源与版本年份。
