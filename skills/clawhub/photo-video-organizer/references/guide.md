# 大量照片/视频整理规范（从混乱到有序的可复现流程）

> 本文档基于一次真实的 2.5 万+ 照片 / 1500+ 视频（跨 13 年、6+ 来源、网盘多次重下导致元数据错乱）的整理实践提炼而成，并经多轮追加实践（深度二次去重、GPS 来源审计、年份归档、动态照片拆分）持续修订。目标是让任何人照着做，就能把自己的海量照片视频梳理成"时间正确、画质完整、重复较少、结构清楚、能安全导入手机/云盘"的长期资料库。
>
> 文档里出现的脚本名、命令是参考实现（Python + exiftool + OpenCV + CLIP），可替换为等价工具。核心是**方法论和顺序**，不是某个具体脚本。
>
> **地区适配**：本方法论全球通用；与地区相关的差异（坐标系、行程表数据源、云盘生态、传输渠道、时区）统一收在 `region_cn.md`（中国大陆）和 `region_global.md`（海外）两份地区档案里，开始整理前先确定用户地区并加载对应档案。本文档中的示例若写有"北京时间"等字样，仅为中国区默认值。

---

## 0. 一句话总纲

> **先备份，再去重；先隔离，不真删；先修时间，再导入图库；照片和视频分开处理；软件负责辅助，人工负责最终判断。**

目标不是把数量降到最低，而是：**时间正确、画质完整、重复较少、结构清楚、能安全导入苹果和华为的长期资料库**。

---

## 1. 核心原则（贯穿全程，违反必踩坑）

1. **先备份再去重**：动手前至少保留一份完全未处理的原始备份。绝不动：苹果照片图库内部文件、网盘唯一副本、无人机原始素材。
2. **先隔离，不真删**：所有"删除"都是**可逆地移入子文件夹**（保留 mtime、附回滚脚本），确认无误后才考虑真删。绝不直接 `rm`。
3. **先修时间，再导入图库**：导入手机/图库前必须把拍摄时间修对；导入后再改外部原文件无效。
4. **照片和视频分开处理**：两者的时间存储方式、GPS 写入、去重逻辑都不同，分开流水线。
5. **软件辅助，人工终判**：去重/相似由算法给出候选，**人工在对比图上核定**后才移动。算法会误判，人工不核定就批量删 = 灾难。
6. **元数据是硬要求**：传输/备份照片必须保留 EXIF 时间/GPS；禁用会剥离元数据的渠道（微信/QQ/WhatsApp/社交平台压缩传输）。
7. **绝不做不可逆操作覆盖原始**：不重新编码损画质、不剥离 GPS/相机型号、不改图库内部文件、导入图库后不再改外部原文件。

## 2. 元数据与文件名的可信度规则（决定时间怎么修）

整理网盘重下/多源汇合的库，最大的坑是"时间不可信"。先建立判据：

### 2.1 文件名时间戳可信度
| 文件名形态 | 是否含拍摄时间 | 说明 |
|---|---|---|
| `IMG_YYYYMMDD_HHMMSS.*`（华为/安卓） | ✅ 可信 | 直接解析 |
| `VID_YYYYMMDD_HHMMSS.*` | ✅ 可信 | 视频录制开始时间 |
| `YYYYMMDD_HHMMSS` / 17 位 `YYYYMMDDHHMMSSmmm` | ✅ 可信 | 可解析 |
| 13 位纯数字 | ✅ Unix 毫秒时间戳 | 可解，但需标注来源 |
| **19/20 位纯数字（微信服务器 ID）** | ❌ 不含时间 | 是随机 uint64，**禁止反推时间**（实测与真实时间无关） |
| 32 位 hex | ❌ MD5，不可解 | |
| `mmexport<ms1>_<ms2>_...` 多时间戳 | ⚠️ 取最早的 | 多次转发/另存叠加，最早的最接近快门 |

### 2.2 拍摄时间来源优先级
> **原生 EXIF（DateTimeOriginal）> 13/17 位文件名时间戳 > 其他**。**绝不用文件 mtime**——网盘下载会把 mtime 污染成下载日。

### 2.3 "保存时间 ≠ 拍摄时间"
微信/转发另存的"保存时间"与真实拍摄时间**仅约 1/4 完全一致，约 16% 跨日，最大滞后可达 36 小时**。按"保存时间"推城市写 GPS 会写错。务必以 EXIF/文件名时间戳为准。

### 2.4 传输渠道元数据保留
| 渠道 | 是否保留 EXIF 时间/GPS |
|---|---|
| AirDrop / 访达数据线同步 / Files / USB | ✅ 保留 |
| 百度网盘（电脑客户端 + 文件区 + 原图） | ✅ 保留 |
| 微信 / QQ / WhatsApp / 社交平台传输 | ❌ 压缩并剥离 |
| 网盘"在线预览/转存" | ⚠️ 可能丢 |

## 3. 准备阶段

### 3.1 工具准备
- **exiftool**（13.x）：读写 EXIF/视频元数据。读用 `-T -n -m`，写 GPS 用 `-GPSLatitude/-GPSLongitude/-UserData:GPSCoordinates -P -api LargeFileSupport=1`。
- **Python 3.10+** + 虚拟环境，装：`opencv-python`(cv2)、`pillow`、`pillow-heif`(读 HEIC)、`numpy`、`openai-clip`(语义嵌入)、`torch`。
- 可选：`ffmpeg/ffprobe`（视频信息，本文档方案用 OpenCV 替代，无需 ffmpeg）。
- 外置盘/大容量空间（去重和移动需要空间余量）。

### 3.2 备份策略
- 保留**至少一份完全未处理的原始备份**（不动手改的那份）。
- 绝不动：苹果"照片"图库内部文件、网盘唯一副本、无人机原始素材（LRF/DNG）。
- 整理过程中所有"删除"都是可逆移动，附回滚脚本。

### 3.3 收集到 Mac 普通文件夹（先别导入图库）
把分散来源（手机/网盘/微信收发图/华为/大疆/多版本复制导出/截图连拍）集中到 Mac 的**普通文件夹**，不要急着导入"照片"App。建议结构：
```
01_原始文件备份/        # 完全不动的那份
02_待整理/              # 平铺后待处理
03_待去重候选/          # 算法标记的候选删除（先别真删）
04_时间待修复/
05_视频单独处理/
06_无人机原始素材/
07_最终保留/            # 去重完+时间对+画质元数据保
08_准备导入苹果/
09_准备导入华为/
```

## 4. 梳理顺序（从前到后）

> 照片和视频是两条平行流水线，顺序相同但实现不同。下面先讲通用阶段，再分别讲照片/视频的差异。

```
Phase 0    盘点与平铺
Phase 1    拍摄时间修复
Phase 1.5  前置任务：构建多年行程表（每日所在城市，独立任务）
Phase 2    拍摄 GPS 写入（依赖 Phase 1.5 行程表）
Phase 3    文件名统一
Phase 4    完全相同去重（字节级）
Phase 5    相似去重（语义级）
Phase 6    低质量/模糊隔离（可选）
Phase 7    哈希校验清单
Phase 8    导入手机 / 上传网盘
```

### Phase 0　盘点与平铺
- **做什么**：把各子文件夹里的媒体**平铺到一层**（解散嵌套），统计总数/格式/大小分布。视频单独分出。
- **怎么做**：脚本 `os.walk` 收集，按扩展名分类（jpg/jpeg/heic/png/livp/mp4/mov/avi/mkv/m4v...），输出 CSV 清单。
- **坑**：`.DS_Store`、`.baiduyun.uploading.cfg` 等垃圾文件要排除；网盘残留的 `.bdcache` 别误算。
- **阶段性成果**：一份媒体清单 CSV（路径/大小/mtime/扩展名），知道总盘子有多大。

### Phase 1　拍摄时间修复（最关键）
- **做什么**：让每个文件都有正确的 `DateTimeOriginal`（照片）/ `CreateDate`（视频）。
- **照片**：优先读 EXIF；无 EXIF 则从文件名时间戳解析后写入（标注 `INFERRED-FILENAME`）。**不用 mtime**。
- **视频**：见 §5（视频时间存储有 UTC 偏移坑）。
- **坑**：
  - exiftool 对上万个文件单次调用会超 macOS `ARG_MAX` → **每批 ≤400 个**传参。
  - exiftool `-T` 返回列数因文件类型不同 → 校验列数，别写死。
  - 19/20 位微信 ID 不能当时间（§2.1）。
  - 网盘下载污染 mtime → 绝不用 mtime 推时间。
- **阶段性成果**：100% 文件有正确拍摄时间；缺时间的少数移入 `无法恢复拍摄时间/` 子文件夹单独处理。

### Phase 1.5　前置任务：构建多年行程表（每日所在城市）—— GPS 写入的先决条件

Phase 2 要按"日期→城市"给无 GPS 的照片/视频补坐标，前提是先有一张**覆盖全部年份**的"每日所在城市"行程表。这本身是一个**独立的梳理任务**，建议在 Phase 1（时间修复）之后、Phase 2 之前完成。多数人手里没有现成的行程表，需要从消费/出行记录里反推。

**目标产物**：一张 CSV，每行一天：
`日期, 主城市, 当日全部城市, 数据来源, 备注`
（例：`2015-02-08, 防城港, 南宁/防城港/东兴, 火车票+消费, 自驾途经`）

**数据来源（多源交叉，越全越准；国内源与海外源清单见地区档案 `region_cn.md` §2 / `region_global.md` §2）**：

**构建方法**：
1. 把上述各源导出为表格，统一提取 `日期 + 城市`。
2. **按日聚合**：同一天有多条记录，取出现最多的城市为"主城市"，其余记入"当日全部城市"。
3. **冲突仲裁**：火车/飞机当天跨越多城市（出发地→目的地），按"白天在出发地、晚上在目的地"，或以消费记录时间为准；无法定的标"在途"。
4. **补空段**：某天无任何记录，看前后日推断（短途不出城则同前日）；推断的标注 `INFERRED-ADJACENT`，**宁缺毋错**（写错 GPS 比不写更糟）。
5. **细分到县级**：尽量到区县（如"西藏/山南"而非只"西藏"），坐标更准。
6. 保留"数据来源"列，便于追溯某天为何定这个城市。

**坑**：
- **不要用照片的"保存时间"反推城市**（§2.3，跨日 16%）—— 行程表必须独立从交通/消费记录建，再反向匹配照片。
- **微信/支付宝账单的城市字段**可能是商家注册地而非消费地（连锁店/网购），优先用线下餐饮/交通/酒店等本地消费来定城市。
- **跨年/跨时区**：红眼航班、出国时差，注意日期边界。
- **宁缺毋错**：存疑的日子留空，不强行写——GPS 写错比不写更难发现。

**配套：城市→坐标字典**：维护一份 `城市名 → (纬度, 经度)` 字典（含区县，如 `山南 → (29.236, 91.766)`）。Phase 2 用它把"主城市"转坐标写入。坐标精度到 0.001°（约 100m）即可，不必精确到门牌。

**阶段性成果**：`每日所在城市_逐日明细.csv`（覆盖全部年份）+ `城市坐标字典`。这两个是 Phase 2 的输入。

### Phase 2　拍摄 GPS 写入
- **做什么**：给无 GPS 的文件按"行程表"（日期→城市→坐标）补写 GPS。**前置**：先完成 Phase 1.5 的行程表。
- **怎么做**：用 exiftool 写 `-GPSLatitude/-GPSLongitude`（+视频的 `-UserData:GPSCoordinates`）。对每个无 GPS 的文件，按其拍摄日期查行程表得"主城市"，再用城市坐标字典转成经纬度写入。标注来源 `INFERRED-ITINERARY`。
- **坐标系（写前必查，地区档案 §1）**：EXIF 要求 **WGS-84**。中国大陆地图服务取的坐标是 GCJ-02（百度为 BD-09），**必须先转 WGS-84 再写**（用 `scripts/datum_convert.py`，转换后做往返校验，偏差应为 0）；海外坐标无需转换，直接写。坐标来源和转换方式记入审计日志（见 §13）。
- **坑**：
  - **不要无脑按"保存时间"推城市**（§2.3，跨日会写错）；必须用**拍摄时间**（Phase 1 已修好）去查行程表。
  - **保留已存在的真实 GPS**——很多人有真实行程（泰国/上海/湖北等），别用行程表覆盖；先识别"真无 GPS"再补。
  - **AVI/RIFF 容器写不进 GPS**（格式硬限制），跳过即可，别死磕。
  - exiftool `-r` 递归会漏读大疆 `UserData` 里的 GPS → 用**单文件直扫或分批直接传参**。
  - 大文件重写若中断会留 `*_exiftool_tmp` 残留挡路 → 先清残留再重跑。
- **阶段性成果**：GPS 覆盖率报告（如 99.5%），仅个别格式限制的留空；行程表覆盖不到的少数日子留空。

### Phase 3　文件名统一
- **做什么**：统一命名为 `YYYYMMDD_HHMMSS_设备.扩展名`（视频加 `video` 前缀：`videoYYYYMMDD_HHMMSS_设备.ext`）。
- **设备后缀**来源：EXIF Model 直映 > 文件名前缀按时期推断（如华为 IMG_/VID_ 按年份分 p20/mate40/mate80）> 微信 `_weixin` > 大疆 `_dji·action6` > 富士 `_fujifilm·s8600` > 苹果 `_iphone`。
- **同秒冲突**：自动加 `_2`/`_3`。
- **坑**：
  - 设备推断要按"当时主力机"分时期，不能一刀切。
  - 中间点 `·`（U+00B7）在 macOS 文件名合法，可用。
  - **务必保留 mtime**（`os.utime` 还原），改名别改时间。
- **阶段性成果**：①改名映射 CSV（old→new+mtime+method）②回滚脚本。**这两个必须随库保留**，是追溯和回滚的唯一凭证。

### Phase 4　完全相同去重（字节级，Tier A）
- **做什么**：找字节级完全相同的文件，每组留最优，冗余移入 `待删除（重复副本）/`。
- **怎么做**：先算"大小 + 头部 2MB MD5 + 尾部 2MB MD5"指纹（只读 4MB/文件，与总大小无关），指纹相同的组再全量 MD5 确认。留优优先级：有 GPS > 拍摄时间早 > 文件大 > 干净名 > 原图格式（HEIC/DNG > 微信 jpg）。
- **坑**：
  - **LIVP（华为动态照片=ZIP(JPG+MOV)）只比封面会误判**——必须封面+视频都相同才算整包重复；封面同视频不同的要保留。
  - **静态 JPG/PNG/HEIC 与 LIVP 即使封面相同也不判重复**（动态照片价值不同）。
  - 全量 MD5 别同时把多个大文件读进内存（OOM）→ 流式分块、读完即释放。
- **阶段性成果**：完全相同组清单 CSV + 可逆移动 + 回滚脚本。

### Phase 5　相似去重（语义级，Tier B）—— 重点
- **做什么**：找"画面相似但不字节相同"的（连拍、同场景、重新编码副本），同组择优保留，其余移入 `待删除（相似副本）/`。
- **核心方法**：**CLIP 语义嵌入 + 拍摄日期分组对比**。**禁止单纯用感知哈希**（pHash 会把无关照片误判相似）。
- **照片流程**：
  1. 每张照片 CLIP(ViT-B/32) 嵌入 → 512 维向量。
  2. **按拍摄日期分组**，组内用余弦相似聚类（阈值如 0.94）。
  3. **大组递归细分**：成员 >N（如 20）时用更高阈值（0.96）拆子场景，避免把同地点不同构图压成几张。
  4. 同组择优保留，客观代理指标：分辨率·文件大小·清晰度·EXIF·GPS·原图格式；主观指标：构图/表情/主体/光线（人工定）。
  5. **多轮递进**：第一轮后对剩余库再做**深度轮**（全局重新聚类，阈值降到 0.88 + 大组 0.96 拆分），通常还能再筛出 30–40% 冗余；每轮独立留移动日志，独立可回滚（详见 §12）。
  6. **特殊主题组单独调阈值**：宠物/纯色背景/重复构图主题（如同一只猫的 31 连拍）默认阈值会误拆，用更高阈值（0.98）单独重聚，保留率可从 ~20% 提到 60–85%（详见 §12）。
  7. **同姿势跨景别**：同一姿势的近/中/远景属于"相似"，应归同组由人工定去留；**最佳照片评分可纳入水平/垂直对齐（level/plumb）**——地平线歪斜的照片除非内容独特否则降权。
  8. 宠物/特殊组可用更高阈值（0.98）单独拆，提高保留率。
- **保留规则**：每组保留约 **20–30%（取中值 25%），上限 5、下限 1**——不是只留 1 张。
- **视频流程**：见 §5。
- **坑**：
  - **必须结合"拍摄日期"一起判**——纯全局 CLIP 聚类会把不同时间相似画面乱归。
  - **大组太粗** → 多级递归细分（0.94→0.96→0.98 逐级拆到 ≤4）。
  - **每组只留 1 个太激进**（大组如 30 个删 29 不合理）→ 用 25% 规则。
  - 聚类脚本里"组内最高相似度"别初始化成 1.0（会全显示 1.0，初始化 0.0）。
  - **去重前先排除已移走的文件**（`os.path.exists` 过滤），避免重复出现在新结果里。
- **阶段性成果**：相似组清单 CSV + **可交互对比 HTML**（每组成员缩略图，绿保留/红移除）+ 人工核定后的移动日志 + 回滚脚本。

### Phase 6　低质量/模糊隔离（可选）
- **做什么**：把明显模糊/低分辨率/压缩渣的移入 `待删除（画面模糊）/`。
- **怎么做**：综合"全局清晰度 rank（全库百分位）+ 边缘强度 + 文件大小"三因子评分，取最低 1–2% 为候选。**必须抽样人工核验**——实测中蓝天/雪景/夜景等低对比正常照片容易被误伤，抽样通过后才移动。
- **阶段性成果**：模糊候选清单 + 可逆移动。

### Phase 6.5　覆盖度分析（可选，导入前查漏）
- **月份断档检查**：按拍摄时间统计每月文件数，找出"全库零照片"的断档月。断档月说明该月照片散落在别处（旧手机/他人设备/未导出的云相册），**无法从库内补齐**，需外部来源——把断档月清单交给用户，由用户决定是否去其他渠道找回，不要凭空造数据。
- **年份归档**：按 EXIF 拍摄年份建 `YYYY/` 子文件夹归档（生成 old→new 移动清单 + 回滚脚本）。归档前必须先修完时间（Phase 1），否则按错时间归档会放错年份。

### Phase 7　哈希校验清单
- **做什么**：对最终保留的库算 MD5+SHA1，生成校验清单 CSV（relative_path, filename, ext, size, md5, sha1, mtime_iso）。
- **用途**：上传网盘/导入手机**前后**比对，任何字节变动（尤其 GPS 丢失）立刻现形。
- **怎么做**：多进程并行，单遍读同时喂两个 hash，流式 4MB 分块（应对大文件）。**断点续传**（边算边写、跳过已算），大库（几百 GB）才跑得完。
- **坑**：一次性把全库哈希写内存会被回收无产出 → 边算边落盘 + 断点续传。
- **阶段性成果**：`哈希校验清单.csv`（照片）+ `视频哈希校验清单.csv`。

### Phase 8　导入手机 / 上传网盘
> 具体到"哪台手机走哪条路、哪家云盘怎么传"，**按地区档案执行**：`region_cn.md` §4/§6（华为星河互联、百度网盘/阿里云盘）、`region_global.md` §4/§6（iCloud/Google Photos/OneDrive）。以下只写跨地区通用要点。
- **上传网盘（保元数据通用原则）**：用**电脑客户端** + **"文件区"**（不是相册备份功能）+ **原图**上传；别用"在线预览/转存"或压缩模式。
- **导入 iPhone（可不开 iCloud，全球通用）**：关两端 iCloud 照片 → 数据线连 Mac → 访达「照片」标签页勾选同步（含视频）→ 应用 → iPhone 按拍摄时间/GPS 本地归位 → 插电联网等索引跑完出"回忆/精选"。注意：访达同步进来的照片不能在 iPhone 单张删，只能回 Mac 取消同步。
- **LIVP 动态照片**：iPhone 不认 .livp，传 iPhone 前需处理（转 Live Photo 或抽 JPG 静态）。Apple Live Photo 传非苹果设备同理需转换。

## 5. 视频处理的特殊差异（与照片不同处）

视频的元数据存储和去重都和照片不一样，单独说明：

### 5.1 拍摄时间
- 视频 `CreateDate` 对 **mp4/mov 存的是 UTC**，写入时用"拍摄地本地时间 − 该地时区偏移"算 UTC 再写。**时区不是固定的**：中国库默认 UTC+8（北京时间减 8h）；海外库或含出境游的库要按拍摄地时区换算（泰国 UTC+7、日本 UTC+9、美国西部 UTC−8/−7 等），有 GPS 的文件可用"坐标→时区"交叉验证。对 **AVI 存的是本地**，别一刀切。
- 写时间要同时写 `CreateDate/TrackCreateDate/MediaCreateDate` 三字段（`-AllDates` 只更新影片头，漏 Track/Media）。
- **部分华为设备的视频 `CreateDate` 系统性偏 +1 小时**：先抽样已知拍摄时间的文件比对，确认偏移后按设备批次还原，不要假设全库一致。

### 5.2 GPS
- 写 `-GPSLatitude/-GPSLongitude` + `-UserData:GPSCoordinates`（大疆私有 GPS 在 UserData）。
- **AVI/RIFF 容器写不进 GPS**（格式硬限制），跳过。
- exiftool `-r` 递归漏读大疆 UserData → 单文件直扫。

### 5.3 文件名
- 加 `video` 前缀：`videoYYYYMMDD_HHMMSS_设备.ext`。设备推断同照片但视频有自己的前缀（VID_/DJI_/dji_mimo/IMG_.MOV 等）。
- 大疆 `dji_mimo` 文件名里的 13 位毫秒是**导出时间不是录制时间** → 用内层 MP4 录制时间。

### 5.4 去重
- **完全相同**：同 §Phase 4（头尾指纹 + 全量 MD5）。
- **相似**：抽关键帧 → CLIP 嵌入 → 聚类。关键点：
  - **按"拍摄日期 + 地理位置 + 主题"分组对比**，不全局两两比（O(n²) 不可行）。
  - **整段理解 vs 抽帧**：抽 N 帧覆盖头/中/尾。**OpenCV 深跳转 `cap.set(POS_FRAMES)` 在多数编码会从头解码到目标位置 → 长视频极慢**，必须**顺序读**到目标帧。
  - **大文件（如 ≥500MB）整段解码不现实**（16GB 文件要数小时）→ 只抽**前 ~13 秒、硬上限 400 帧**，耗时恒定。代价：只覆盖开头，核对时留意"开头像但中段不同"。
  - `CAP_PROP_FRAME_COUNT` 对部分视频误报巨大值会导致死循环 → **必须 clamp 到合理上限**。
  - 保留规则同照片（25%，上限 5 下限 1）+ 大组递归细分。

### 5.5 动态照片 / Live Photo（易踩坑）
- **华为 LIVP = ZIP(JPG+MOV)，自包含动态照片**，别拆开；去重时封面+视频都同才算整包重复。
- **Apple Live Photo = HEIC + MOV 配对**，靠 `ContentIdentifier` UUID 关联，不是文件名。注意：用 exiftool 写 GPS/时间可能**破坏 ContentIdentifier**导致配对失效，操作前确认是否需要保留 Live 关系。
- **千万别把动态照片的配对视频单独移走**，否则静态图变静态。整理前先识别动态照片配对，整体处理。

## 6. 坑汇总（按发生频率排序）

| 坑 | 规避 |
|---|---|
| 用 mtime 推拍摄时间 | 网盘下载污染 mtime，**绝不用**；用 EXIF/文件名时间戳 |
| 19/20 位微信 ID 当时间 | 是随机 ID，不含时间，**禁止反推** |
| 保存时间当拍摄时间 | 16% 跨日，会写错 GPS；以 EXIF/文件名为准 |
| exiftool 一次传上万个文件 | 超 ARG_MAX，**每批 ≤400** |
| exiftool `-r` 漏读大疆 GPS | 单文件直扫或分批直接传参 |
| AVI 写 GPS | RIFF 容器硬限制，跳过 |
| 视频时间不换 UTC | mp4/mov 的 CreateDate 是 UTC，北京时间减 8h |
| 感知哈希判相似 | 误判多，**禁用**，用 CLIP + 日期 |
| OpenCV 深跳转抽帧 | 长视频极慢，**顺序读**到目标帧 |
| `CAP_PROP_FRAME_COUNT` 误报 | 死循环，**clamp 上限** |
| 大文件整段解码 | 不现实，抽前段（如前 13s/400 帧） |
| LIVP 只比封面 | 必须封面+视频都同才算重复 |
| 静态图与 LIVP 比重复 | 价值不同，不判重复 |
| 聚类 sim_max 初始化 1.0 | 全显示 1.0，初始化 0.0 |
| 每组只留 1 个 | 大组太激进，用 25%（上限 5 下限 1） |
| 大组太粗 | 多级递归细分（0.94→0.96→0.98） |
| 后台长任务静默中断 | 环境会回收，**断点续传 + 分批 + 巡检** |
| 一次性写大库哈希 | 被回收无产出，**边算边落盘 + 续传** |
| 直接 rm 删除 | 不可逆，**一律可逆移子文件夹 + 回滚脚本** |
| 导入图库后改外部原文件 | 无效，**先整理完再导入** |
| 微信/QQ 传图保元数据 | 会剥离压缩，禁用；用 AirDrop/Finder/网盘客户端 |
| GCJ-02 直接写进 EXIF | 国内地图坐标必须先转 WGS-84（datum_convert.py + 往返校验），否则地图上偏 300–600 米 |
| 海外坐标做 GCJ 转换 | 境外无偏移，转了反而引入 300–600 米假偏移 |
| 华为视频 CreateDate 偏 +1h | 硬件批次坑，抽样已知时间文件确认后按批还原 |
| 动态照片拆分后散放 | 华为 livp 拆出的封面/视频要成对管理；拆分静态封面归位时按分类对应 |
| 一次迁移漏依赖 | 迁移/复用脚本前先 grep 完所有路径引用（含兄弟目录、写死的输出路径） |

## 9. 推荐"可交互核定"做法（强烈建议）

相似去重这一步，**别让算法直接移动**，做成可交互对比 HTML：

- 这样人工能在几分钟内核定几百组，算法误判由人兜底。**这一步是"软件辅助、人工终判"原则的关键落地。**

## 12. 多轮递进去重（Tier B 一轮不够）

第一轮"同日 0.94"只能抓明显的连拍/同场景。实战中对 1.5 万张剩余库再做**深度轮**，又筛出约 35% 冗余：

**深度轮做法**：
1. 对第一轮后的剩余库**全局重新聚类**（不再限同日？不——仍按日期约束，但阈值降到 **0.88**），抓"同场景跨小时"的相似（早上拍的和傍晚拍的同一座桥）。
2. 大组（>20 张）用 0.96 递归拆子场景，防把同地点不同构图压扁。
3. 保留规则同前：单张组 100% 保留；2–4 张 ~41%；5–9 张 ~28%；每组 `ceil(n×25%)` 上限 5 下限 1。
4. **每轮独立产物**：独立清单 CSV、独立 `待删除（深度相似副本）/`、独立移动日志与回滚脚本——绝不在第一轮日志里混记，否则回滚颗粒度错乱。
5. 何时停：再跑一轮新增候选 < 剩余量的 5% 时停，边际收益消失。

**特殊主题组**：宠物（同一只猫/狗的连拍）、纯色背景证件照、重复构图主题，默认阈值会把"同只猫不同天"也聚一起或把"同天不同姿势"误拆。识别出这类组后**单独用 0.98 重聚**，保留率可从 20% 提到 60–85%。识别方式：先按默认阈值聚类，看"组内拍摄日期跨度 > 30 天"或"组内画面主体极单一"的组，标记为主题组。

**同姿势跨景别**：CLIP 对"同一姿势的近景/中景/远景"相似度天然偏高（0.9+），这正合理——它们同组，人工从中挑构图最好的 1–2 张。**最佳照片评分可加水平/垂直对齐项**：地平线/竖直线明显歪斜的降权（除非内容独特）。

## 13. GPS 来源审计（写完不是结束，要能回答"哪些是真的"）

行程表补写的 GPS 是"城市中心盖章"，与真实拍摄点有差距。整库必须能区分：

1. **写入时打标**：真实 GPS（原带）不动不打标；行程表补写的在审计清单里记 `INFERRED-ITINERARY` + 坐标来源（城市字典条目 + 是否做过坐标系转换）。
2. **审计方法**：取所有有 GPS 的文件，坐标与城市字典中心点**完全相等**的 = 盖章写入；其余 = 真实 GPS。输出"各年月 真实/盖章 数量分布"报告。
3. **校验**：报告总数必须等于库内有 GPS 文件总数（diff=0 才算过）。
4. **用途**：后续若拿到更精确的地点记录，只覆盖盖章的，不碰真实的。

## 14. 受限/沙箱环境执行注意（WorkBuddy 等托管环境实测）

在受限沙箱里跑批量脚本，这些系统调用会**静默失败**（退出码 1 且无 stderr）：
- `mkdir`（含项目下建隐藏目录）→ 改用 Python `os.makedirs`
- `cp` → 改用 `shutil.copyfile` / `copy2`（保留 mtime 用 copy2）
- heredoc（`cat > f <<EOF`）→ 直接用写文件工具
- `chmod`/`touch` → 改用 `os.chmod` / `os.utime`
- 任何 `rm` → 改用系统废纸篓机制或干脆只做可逆移动

**排查手法**：单条命令 + 显式 `echo "RC=$?"`；管道 `| tail` 会吞退出码；重定向到日志再查。

## 15. 阶段进度记录纪律（跨会话不失忆的关键）

长任务每完成一个阶段，**先往产物同目录的 `阶段进度记录.md` 追加一条，再结束本轮**。每条必须含：
- **完成度标记**：✅ 完成 / 🟡 部分完成 / ❌ 未做
- **验证数字**：多少文件、多少成功/失败、校验差值（如"移动 9962 个，前后文件数守恒 diff=0"）
- **遗留问题**：什么没做、为什么、下一步

这份文件是跨会话/跨轮对话的**唯一可信源**。没有它，下次会话只能靠考古或重做——两者都不可接受。阶段记录的同时写"回滚清单"（old→new 路径 + mtime），任何移动都可逆。
