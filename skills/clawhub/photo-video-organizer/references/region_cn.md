# 地区档案：中国大陆（region profile: cn）

> 本档案是 `photo-video-organizer` skill 的地区适配层之一。
> SKILL.md 在 Phase 0 会判定用户地区并加载对应档案；本文件覆盖**所有与"中国大陆使用环境"相关的差异点**。
> 核心方法论（备份/可逆/先修时间/人工终判）在 `references/guide.md`，全球通用，此处只写差异。

---

## 1. 坐标系（最重要的地区差异，写 GPS 前必读）

中国大陆地图采用 **GCJ-02**（国测局加密坐标，俗称"火星坐标"），而 **EXIF 标准要求 WGS-84**：

| 坐标来源 | 坐标系 | 能否直接写入 EXIF |
|---|---|---|
| 腾讯地图 / 高德地图 取点 | GCJ-02 | ❌ 必须先转 WGS-84 |
| 百度地图 取点 | BD-09（GCJ-02 二次加密） | ❌ 先转 GCJ-02 再转 WGS-84 |
| 照片里已有的真实 GPS（手机在国外拍的除外） | WGS-84 | ✅ 直接保留 |
| 手机在国外/海外拍的照片 | WGS-84 | ✅ 直接保留 |

**规则**：
1. 从国内任何地图服务取到的城市/地点坐标，写 EXIF 前**必须转成 WGS-84**（用 `scripts/datum_convert.py`，离线算法，无需联网）。
2. 转换后建议做**往返校验**：把算出的 WGS-84 再转回 GCJ-02，与原始坐标比对，偏差应为 0（防止参数顺序写反——这是实测踩过的坑，写反会偏移数百米到 1 公里）。
3. 国内城市坐标精度到 0.001°（约 100 米）即可；用地图选点工具（腾讯地图坐标拾取器等）获取 GCJ-02 值。
4. 苹果"照片"App、Google 地图显示 EXIF GPS 时按 WGS-84 解读——如果误把 GCJ-02 写进去，照片在地图上会**整体偏移约 300–600 米**。

## 2. 行程表数据源（Phase 1.5 的"每日所在城市"从哪来）

国内可用的多源交叉记录（按可靠性排序）：
1. **12306 火车票**：APP 订单/电子票根/购票短信 → 出发到达站+日期。
2. **机票行程单**：航司 APP / 携程 / 飞猪 / 值机短信。
3. **微信账单**：我 → 服务 → 钱包 → 账单 → 常见问题 → 下载账单（含交易时间+商家城市）。
4. **支付宝账单**：我的 → 账单 → 开具交易流水证明（含时间+交易地点）。
5. **补充源**：高德/百度地图出行轨迹、美团/大众点评消费、酒店订单、打车发票、ETC 记录、过路费短信。

**坑（国内特有）**：
- 微信/支付宝账单的"城市"可能是**商家注册地**而非消费地（连锁店/网购），优先用线下餐饮/交通/酒店等本地消费定城市。
- 12306 车票可能是"到达站"为县级市但实际住市区——坐标字典尽量建到**区县级**。
- 每日所在城市最终产出 `每日所在城市_逐日明细.csv` + 城市坐标字典（坐标先存 GCJ-02，写入 EXIF 时统一转 WGS-84）。

## 3. 传输渠道与元数据

| 渠道 | EXIF 时间/GPS | 说明 |
|---|---|---|
| AirDrop / 访达数据线 / USB | ✅ 保留 | 首选 |
| 百度网盘 / 阿里云盘（**电脑客户端 + 文件区 + 原图**） | ✅ 保留 | 别用"在线预览/转存" |
| 微信 / QQ | ❌ 压缩并剥离 | 禁用于传原件；且"保存时间≠拍摄时间"（约 16% 跨日） |
| 网盘"相册备份"功能 | ⚠️ 可能重压缩 | 用"文件区"不用"相册区" |

**微信文件名判读**（高频场景）：
- `IMG_` + **19/20 位纯数字** = 微信服务器随机 ID，**不含任何时间信息，禁止反推**。
- `mmexport<13位ms>_<13位ms>_...` = 多次转发/另存叠加的毫秒时间戳，**取最早的**最接近快门。
- `image_<13位ms>.jpg` = 保存/导出时间，可作兜底但须标注 `INFERRED-FILENAME`。

## 4. 设备生态

- **华为（纯血鸿蒙）**：Mac 导入用「鸿蒙星河互联」；**USB/HiSuite/adb/PTP 在纯血鸿蒙+Mac 上不可用**（实测多次失败，别浪费时间）。华为动态照片 `.livp = ZIP(JPG+MOV)` 自包含，别拆开散放。
- **华为硬件时钟坑**：部分华为设备导出的视频 `CreateDate` 系统性偏 +1 小时，需按设备批次还原（先抽样比对已知时间的文件再定偏移量）。
- **大疆**：`dji_mimo` 文件名 13 位毫秒是**导出时间非录制时间**，用内层 MP4 的录制时间；大疆私有 GPS 在 `UserData:GPSCoordinates`。

## 5. 视频时间与时区

- 国内库默认统一**北京时间（UTC+8）**：mp4/mov 的 `CreateDate` 存 UTC，写入时用北京时间 **减 8h** 再写，且要同时写 `CreateDate/TrackCreateDate/MediaCreateDate` 三字段。
- 如果库里有**海外旅行**拍的视频（泰国/日本/欧美等），文件名的本地时间与 EXIF UTC 的差不再是固定 8 小时——按拍摄地时区换算（泰国 UTC+7、日本 UTC+9 等）。有 GPS 的文件可用"GPS 坐标 → 时区"交叉验证。

## 6. 云相册 / 导入目标

| 目标 | 方法 | 注意 |
|---|---|---|
| iPhone/iPad | 关两端 iCloud 照片 → 数据线 → 访达「照片」同步 | 可不开 iCloud，本地仍能生成"回忆/精选/旅程"；访达同步的照片不能在手机单张删 |
| 华为 | 鸿蒙星河互联 | 见 §4 |
| 百度网盘/阿里云盘 | 电脑客户端 + 文件区 + 原图 | 上传前后跑哈希清单比对 |
| 一刻相册等 | 客户端原图上传 | 同上 |

## 7. 国内示例场景（验证用例）

**用户画像**：深圳，华为 Mate 60 + iPhone 双机，微信收发图多，百度网盘重下过整库，2014–2026 跨 12 年。

走法：
1. Phase 0 平铺后约 2.5 万文件，微信来源 `IMG_<19位ID>.jpg` 占三成 → 按 §3 规则标记"文件名不可解"。
2. Phase 1 时间修复：EXIF 优先；微信图按 `mmexport` 最早时间戳兜底；绝不用 mtime（网盘重下污染为下载日）。
3. Phase 1.5 行程表：12306 + 微信/支付宝账单反推每日城市，建到区县；产出 GCJ-02 城市字典。
4. Phase 2 GPS：按拍摄日期查行程表 → **GCJ-02 转 WGS-84（datum_convert.py + 往返校验）** → 写 EXIF；已有真实 GPS（出境游）不覆盖。
5. Phase 4/5 去重：LIVP 整包（封面+视频都同）才算重复；CLIP 同日 0.94 → 深度轮 0.88；宠物组单独 0.98。
6. Phase 8 导入：华为走星河互联，iPhone 走访达同步，百度网盘走客户端文件区。
