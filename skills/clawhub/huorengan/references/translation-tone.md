# Translation tone | 翻译腔（中文特有）

> 中文特有的 AI 味：英文思维直译到中文的痕迹。引擎里有 4 个 zh-only 检测类型，
> 本文件是它们的人读说明 + 不可正则化的判断补充。

这些形态在母语中文里不存在，是 LLM（英文语料训练为主）写中文时的典型痕迹。
没有英文对应——这是 zh-only 类型（见 [CATEGORIES.md](../detector/CATEGORIES.md) lang=zh）。

## 1. 被动语态堆砌（zh-passive-stack）

引擎检测：「被」字在一句话里密集出现（3+ 被-从句）。

```
❌ 系统被优化后，性能被显著提升，用户体验被大幅改善，整体被全面重构。
✅ 我们优化了数据库查询，页面加载从 3 秒降到 0.8 秒。
```

判断补充：学术/实验语体里的常规被动（"实验由 MIT 团队完成"）可保留。
引擎的 3+ 阈值已经避开了单个被动，但密集被动在技术描述里也可能是合理的——
按场景判断。

## 2. 长定语结构（zh-long-attributive）

引擎检测：4+ 个「的」字链式修饰。

```
❌ 这是一个由多个相互关联的、复杂的、高度耦合的子系统构成的架构。
✅ 这个架构有几个耦合的子系统。
```

判断补充：法律/正式文体里的长定语有时是必要的。密度阈值（4+）已过滤掉
正常使用，但接近阈值的要按可读性判断。

## 3. 「基于…」开头（zh-translation-opener）

引擎检测：句子以「基于 + 名词」开头。

```
❌ 基于上述分析，我们可以得出结论……
✅ 上面分析了，结论是……
```

判断补充：「基于实测数据」「基于 RFC 7231」这类有具体依据的开头是合理的——
引擎只匹配句首形式，是否空洞要看宾语。

## 4. 「通过…来…」结构（zh-via-to）

引擎检测：「通过 X 来 Y」句式。

```
❌ 通过优化算法来提升性能，通过减少请求来降低延迟。
✅ 优化算法提升性能；少发请求降延迟。
```

判断补充：技术文档里「通过 API 来调用」有时是准确的（强调手段），不一定要改。
判断标准：删掉「通过…来」后句子是否更清楚。

## 不可正则化的翻译腔（留 SKILL.md 判断）

- 「对于…而言」 filler（引擎检测，但该不该删看上下文）
- 「在…方面」 filler（同上）
- 整体「英译中」腔：主语冗长、动词后置、定语堆砌——需要重写，不是替换

## 和 protected spans 的关系

翻译腔检测**不动**：

- 命令、代码、接口名（即使含「的」「被」）
- 报错原文（"Error: 资源已被占用"里的「被」是原文）
- 引用块里的翻译原文

引擎的指纹检测（ai-citation-markup 等）和 protected-spans 判断在翻译腔之前
跑，确保不误伤。
