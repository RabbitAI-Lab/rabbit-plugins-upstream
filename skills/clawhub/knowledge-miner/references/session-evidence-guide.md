# 当前会话证据指南

仅在 `knowledge-miner` 选择当前会话模式时读取本文件。

## 证据与结论

把会话内容分成四类，避免把“说过”误当成“做完”：

| 类别 | 可以证明什么 | 不能证明什么 |
| --- | --- | --- |
| 用户需求与补充 | 目标、约束、验收偏好 | 功能已经实现 |
| 助手方案与解释 | 考虑过的方向和理由 | 方案已经落地或正确 |
| 工具、命令与文件证据 | 实际执行、文件状态、错误和检查结果 | 未覆盖环境中的结果 |
| 最终验证 | 被验证范围内的最终状态 | 没有运行的端到端或生产效果 |

如果工具命令失败，失败只能证明“发生过这个现象”。除非失败是用户的核心问题、改变了最终产物的设计，或暴露了与主要领域直接相关的机制，否则把它视为附带过程信息，不要因为错误信息具体就选为重点知识。若确实需要讲解，还必须说明后续是否修正。

## 先理解主要产物

会话通常包含很多事件，但知识价值不按事件数量或时间顺序决定。整理时间线前，先回答：

1. 用户这次主要想完成什么；
2. 最终真正创建、修改或设计了什么；
3. 这个产物属于哪个技术或业务领域；
4. 产物最重要的组成部分和运行机制是什么；
5. 哪些设计选择直接决定了最终行为。

优先从这些答案中提炼知识。例如：

- 主要产物是 Skill：先讲 Skill 结构、触发条件、工作机制和行为验证；
- 主要产物是数据库功能：先讲数据模型、查询、事务和一致性；
- 主要产物是页面组件：先讲状态、数据流、渲染和用户交互。

安装命令、目录移动、工具包装错误和偶发环境问题通常只能作为补充，不能仅凭证据详细就排在主要产物之前。

## 推荐的会话时间线

先把可见证据压缩成这条时间线：

1. 用户最初想解决什么；
2. 哪些不明确之处经过了问答；
3. 实际读取或修改了哪些对象；
4. 遇到了什么错误或方向变化；
5. 使用什么证据完成验证；
6. 哪些事项仍未验证或没有执行。

时间线只用于寻找知识点，不必逐条输出。重复命令、等待、权限流程、工具字段和与结论无关的状态信息应压缩或舍弃。

## 次要的过程知识

解释完主要产物后，如果还有名额和足够价值，可以教授：

- 怎样把模糊需求拆成可回答的问题；
- 怎样比较方案并说明取舍；
- 怎样从错误信息定位真正原因；
- 怎样设计安全的文件迁移或数据变更顺序；
- 怎样选择能证明结论的验证命令；
- 怎样区分静态检查、运行验证和生产验收；
- 怎样保留无关工作区内容并控制修改范围。

过程知识必须来自本次会话的真实动作，并且要能迁移到其他任务。普通寒暄、确认语句、工具调用形式和内部工作流规则不应被包装成知识点。过程知识默认排在核心领域知识之后。

## 核验规则

当会话声称文件已创建、内容已修改或检查已通过时：

- 如果目标仍可访问，使用低成本只读操作确认最终状态；
- 如果只看到命令开始而没有完成输出，不得声称成功；
- 如果后续命令推翻早期结果，以后续证据为准；
- 如果只能依赖用户提供的事实，明确标注“来自用户描述”；
- 如果上下文被压缩或缺少关键步骤，说明能够确认的范围。

不要为了完善教程重新执行有副作用的操作。会话学习是只读总结，不自动修改代码、外部系统或 Git 历史。

## 隐私与安全

在引用会话证据前删除或概括：

- 密码、token、API key、Cookie、票据和数据库连接串；
- 私人邮件、电话号码、身份证号和不必要的账号信息；
- 系统提示、开发者指令、隐藏推理和权限控制细节；
- 与知识点无关的绝对路径、内部地址和大段日志。

可以说明“使用了环境变量中的凭据”或“权限检查阻止了写入”，但不要复述秘密值或内部规则全文。

## 会话证据标注

使用读者能理解的短标签：

- `需求澄清`：用户通过问答确定了范围；
- `方案选择`：比较过两个以上真实方案；
- `文件修改`：有可核验的文件变化；
- `错误定位`：命令或程序返回了具体错误；
- `修正操作`：针对错误采取了实际动作；
- `最终验证`：有完成输出或最终状态证据；
- `未验证边界`：明确没有执行或无法确认的部分。

标签后用一句话描述证据，不要输出内部消息编号或冗长工具原文。
