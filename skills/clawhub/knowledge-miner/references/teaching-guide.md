# 初中生教学指南

仅在需要选择知识点、设计功能链、使用费曼学习法、设计最小创造任务或检查讲解难度时读取本文件。

## 难度标准

默认学习者会使用电脑和手机，但没有编程基础。不要假设学习者知道变量、函数、接口、服务器、数据库、线程、事务或 Git。首次使用术语时，用一句短话解释：

- **变量**：给一份数据贴上的名字，方便之后找到它。
- **函数**：收到一些材料，按固定步骤做事，再交出结果的小机器。
- **接口**：两个程序约定好的传话窗口。
- **服务器**：一直等待请求，并按规则处理请求的电脑程序。
- **数据库**：能按规则长期保存和查找数据的电子资料柜。
- **commit**：给一组已经完成的文件变化拍下的 Git 快照。

这份词语表只是难度示例。实际讲解仍须围绕选定的 commit 或会话证据，不要输出与本次信息无关的基础知识大全。

## 好类比的四条规则

1. 类比对象应是初中生日常见过的事物，例如课程表、点名册、图书馆、食堂排队、快递柜和记账本。
2. 一个类比只解释一个关键关系。例如用“图书馆索引卡”解释数据库索引如何加快查找，不要顺便解释事务和权限。
3. 类比之后立即回到真实证据，明确“在这次 commit 或会话里，谁相当于什么”。
4. 指出类比的边界。例如快递柜能帮助理解缓存，但真实缓存还会过期，并且可能与原始数据暂时不同步。

## 分步讲解方法

把代码视为一条信息旅行路线：

1. 信息从哪里来；
2. 第一段代码接到什么；
3. 它做了哪一个判断或变化；
4. 信息接下来交给谁；
5. 最终得到什么结果；
6. 出错时会看到什么。

如果一步中出现两个以上新术语，继续拆小。优先用具体数据演示，例如“把 3 和 5 交给函数，得到 8”，但示例必须与真实 diff 的逻辑一致。

使用“整体 → 局部 → 整体”顺序：

1. 先说明所有改动合起来创造了什么能力；
2. 再沿同一条输入输出路线拆解关键环节；
3. 最后重新走完整路线，说明每个局部怎样共同产生最终结果。

不要用“知识点 1、2、3 都很重要”代替连接关系。真正的连接必须说清：前一环产生的具体数据、状态或决定是什么，后一环怎样消费它。

## 费曼理解循环

对整体功能和每个关键环节进行四轮压缩：

1. **像教同学一样讲**：不看术语定义，用自己的话讲输入怎样走到输出。
2. **标记卡住的位置**：出现“就是这样”“框架会处理”“某某机制”等空话时，标为缺口。
3. **回证据查清楚**：从真实代码、diff、测试或会话结果找到缺失的条件与过程。
4. **用更简单但更准确的话重讲**：可以缩短句子，不能删掉导致行为变化的边界。

判断是否真的理解，可以追问：

- 为什么前一环的输出正好能成为后一环的输入？
- 如果交换两个环节的顺序，会发生什么？
- 如果删除这一环，哪个可观察结果会改变？
- 给一个从未见过的输入，能否预测系统怎样处理？

答不出时不要立即给更多术语。先回到一个具体输入，沿真实路径重新推演。

## 不同领域的观察角度

这些是寻找知识点的视角，不是必须覆盖的清单：

| 领域 | 先问什么 | 适合的生活类比 |
| --- | --- | --- |
| 前端页面 | 用户做了什么，页面怎样记住并显示结果？ | 黑板、表单、遥控器 |
| 后端接口 | 请求怎样进入、检查、处理并返回？ | 办事窗口、门卫、流水线 |
| 数据库 | 数据怎样保存、查找，怎样避免改到一半？ | 资料柜、目录卡、记账与撤销 |
| 算法 | 输入怎样一步步变成输出，快慢差在哪里？ | 排队、分类书本、寻找座位 |
| 测试 | 怎样自动证明正常情况和异常情况都符合预期？ | 实验对照、考前自测 |
| 安全 | 谁能做什么，危险输入怎样被拦住？ | 门锁、学生证、安检 |
| Git 与 CI | 怎样保存变化、检查变化并让团队共享？ | 游戏存档、作业批改流水线 |
| 工程过程 | 怎样澄清需求、定位失败并证明最终结果？ | 科学实验、维修记录 |

## 选择重点

先判断本次工作的主要产物是什么，再对每个候选知识点按四个问题判断：

- **离主线近不近**：它是否解释主要产物的设计、原理或工作机制？
- **能否连接前后**：它是否接收上一环的明确结果，并产生下一环需要的结果？
- **证据强不强**：diff、真实文件或会话验证是否直接展示这个概念？
- **作用清不清楚**：能否从代码说明它解决的问题？
- **学完能否迁移**：学习者以后遇到类似代码时能否认出来？

“离主线近不近”和“能否连接前后”最优先。证据很详细只能说明事情确实发生过，不能说明它是最值得学习的内容。核心领域知识存在时，报错、命令和环境问题默认降级。以上问题都能回答的知识优先；只有术语、没有行为变化的内容放入“其他可以继续学的内容”或舍弃。

推荐顺序：

1. 主要产物是什么以及怎样设计；
2. 主要产物怎样运行或协作；
3. 怎样实现和验证主要产物；
4. 只有确实重要时，才讲调试或操作过程。

## 最小创造任务

创造任务要让学习者重新发明核心机制，不能退化成抄写真实项目代码。使用以下缩小方法：

1. 保留一个真实输入和一个真实输出；
2. 每个主线知识点只保留一个必要规则；
3. 用数组、卡片、表格或十几行以内的伪代码代替框架细节；
4. 先搭通最短路线，再按主线顺序加入安全、缓存、校验或异常处理；
5. 每加入一环，都用一个此前会失败的例子说明它解决了什么；
6. 最后把缩小版零件逐一映射回真实工程。

例如，真实功能包含“接收请求 → 校验 → 保存 → 返回”，最小版本可以使用一张纸上的输入、三条校验规则和一个内存数组。学习者应先创造没有校验的版本，观察错误数据怎样进入数组，再补上校验并预测新结果。

创造任务应在十到二十分钟内完成，并且不依赖生产环境。推荐：

- 用纸画出数据流并扮演各环节传递卡片；
- 用给定输入手算一次执行过程；
- 写不依赖具体语言的伪代码；
- 阅读测试用例，先遮住断言并预测结果；
- 在临时文件、内存数据或隔离测试环境实现缩小版；
- 运行只读 Git 命令对照真实证据。

禁止把“修改真实账号权限”“删除数据”“替换密钥”“关闭安全检查”或“直接操作生产环境”当作创造任务。

## 语言检查

- 句子尽量短，一段只讲一个意思。
- 用“因为……所以……”连接原因和结果。
- 不说“显然”“很简单”“大家都知道”。
- 不用一串英文缩写代替解释。
- 不把代码逐字翻译一遍；要说明数据怎样变化以及为什么。
