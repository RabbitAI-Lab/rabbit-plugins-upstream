# Networking — HTTP Stack, TLS, and Connectivity

The request that works from your laptop and fails on the device is failing for one of five reasons, and they are checkable in order.

## Diagnose in Order

| Check | Symptom if this is it |
|---|---|
| 1. Cleartext policy | Immediate failure on an `http://` URL, with a cleartext-not-permitted message; works over `https` |
| 2. DNS / host reachability | Unknown host, or works on WiFi and not on cellular (split-horizon DNS on a corporate network) |
| 3. TLS trust | Handshake failure, certificate path not trusted — a self-signed or corporate-proxy certificate, or an expired one |
| 4. Pinning | Handshake succeeds against the same server in a browser and fails only in the app |
| 5. Timeouts | The request eventually fails after a suspiciously round number of seconds |

Do them in that order. Steps 1 and 2 account for most "works with curl" reports, and both are configuration, not code.

## Cleartext and Network Security Config

- From targetSdk 28, plain HTTP is blocked by default. The message names the host, which is often a third-party analytics or ad endpoint you did not know was unencrypted.
- The fix is a network security configuration XML referenced from the manifest, allowing cleartext **per domain** — never a global `usesCleartextTraffic="true"`, which turns the protection off for every host including the ones you do not control.
- Debug-only trust (a local server's self-signed certificate, a proxy's CA) belongs in a `debug-overrides` block in the same configuration, which the platform ignores in non-debuggable builds. Putting a custom trust manager in code is how a debug-only bypass ships to production.
- From API 24 the app does not trust user-installed CA certificates by default. That is why an interception proxy that works in a browser shows nothing from the app until the configuration opts in for debug builds (→ Inspecting Traffic).

## Reaching a Local Server

- From the standard emulator, the host machine's loopback is a specific alias address rather than `localhost` — inside the emulator, `localhost` is the emulated device itself. This single fact accounts for a large share of "the API is down" reports during development.
- From a physical device on the same network, use the host's LAN address, and check that the host firewall allows the port and that the server binds to all interfaces rather than to loopback only.
- Port forwarding over ADB (`adb reverse`) maps a device port to a host port and works on physical devices over USB — cleaner than a LAN address, and it survives the network changing.
- Local HTTPS with a self-signed certificate needs the debug-overrides route above; plain HTTP to a local host needs a cleartext exemption for that host in the debug configuration.

## Timeouts and Retries

- OkHttp's defaults: connect, read and write timeouts of 10 seconds each, and **no overall call timeout**. A response that trickles bytes forever never trips a read timeout, so a request can hang indefinitely without `callTimeout` set. Set it explicitly to the longest a user should ever wait.
- Timeout budget rule: the sum of connect + all retries must stay below the UI's own patience. If the screen shows a spinner and the user gives up at 10 seconds, a 30-second call timeout with two retries is a design that never reports failure in time to be useful.
- Retry only idempotent operations and only for transient failures: connection resets, 5xx, 429 with a retry-after. Never retry a 4xx — it will fail identically, and a retried non-idempotent POST duplicates the user's order.
- Exponential backoff with jitter, capped. Without jitter, every device that lost connectivity at the same moment retries at the same moment when it returns, and your backend gets a synchronized wave.
- Non-idempotent writes carry an idempotency key generated by the client, so a retry after an ambiguous failure is safe (`architecture.md`).

## Certificate Pinning

- Pinning binds the app to a specific certificate or public key. The moment the server rotates to an unpinned key, every installed copy of the app stops working, and the fix requires an app update the users have not installed yet.
- If you pin: pin to the **public key** rather than the leaf certificate, include at least one backup pin for the next key, set an expiry date on the pin set, and keep a server-side kill switch that can disable pinning remotely before it bricks the install base.
- Pin hashes are public information and belong in the config; the private keys obviously do not exist in the app at all.
- For most apps, pinning is not the right control: it defends against a compromised or coerced certificate authority, at the price of an outage risk you carry forever. Decide it deliberately, write the decision and the rotation plan in `artifacts/`, and put the rotation date in the `## Due` table (`memory-template.md`).

## Connectivity and Metered Networks

- "Connected" is not "has internet". The correct check asks for a network with validated internet capability — a captive portal reports a connection and drops your requests.
- Register a network callback rather than polling; the callback also reports capability changes (WiFi to cellular, metered to unmetered) that should change what the app does.
- Respect metered networks and data saver: large downloads and prefetching wait for unmetered, expressed as a WorkManager constraint rather than as an in-app check (`background.md`).
- Network changes mid-request are normal. The stack retries a new connection on some failures and not others; the app still needs an explicit "you are offline" state and a retry affordance rather than an error string.
- Offline-first removes most of this: the UI reads the database, the network fills it, and connectivity becomes a sync-status indicator rather than an error path (`architecture.md`).

## Serialization

- One JSON library, chosen once. A reflective mapper needs R8 keep rules for every model class, and the failure mode is empty fields in the release build only (`release.md`). A compiler-plugin serializer generates code and needs no keep rules, which removes that entire class of bug.
- Server nulls and missing fields are different things and both happen. Model optional fields as nullable with defaults, and fail loudly in debug when a required field is missing rather than defaulting silently.
- Never let API models be your domain models. A field rename on the server should break one mapper, not every screen.
- Dates: transport as an unambiguous instant, parse once at the boundary. Timestamps that arrive as local-time strings without an offset are a bug that surfaces only for users in another timezone.

## Caching and Bandwidth

- HTTP caching works if the server sends the headers; an OkHttp cache with a size budget gives conditional requests and 304s for free. Without server headers, an app-level cache in the database is the honest alternative.
- Images are the bandwidth budget for most apps: request the size you will display, use a modern format, and let the image library handle memory and disk caching. Decoding a full-resolution photo to fill a thumbnail is both a bandwidth and a memory bug (`performance.md`).
- Batch small requests. Ten sequential round trips at 200 ms each is two seconds of screen-blocking latency that one endpoint would remove.
- Compress request bodies for uploads over cellular, and measure — compression that costs more CPU than it saves radio time is a battery regression.

## Inspecting Traffic

- The straightforward route: an in-app HTTP logging interceptor at body level, **debug builds only**, added conditionally with a debug-only dependency so it cannot ship. Log bodies contain tokens and personal data.
- The thorough route: an interception proxy on the host, with the device's proxy set to it and the proxy's CA trusted via the debug-overrides block. Only debuggable builds can trust it, which is the intended limit.
- On-device inspectors in the IDE show requests without a proxy for the common cases.
- Whatever the route: **captured traffic is not a paste to store.** If a captured request or response has to be kept, strip every header and body value that authenticates or identifies before writing it anywhere (`memory-template.md`).

## Networking Traps

| Trap | Why it fails | Do instead |
|------|-------------|------------|
| `usesCleartextTraffic="true"` to fix one endpoint | Disables the protection for every host | Per-domain exemption in the network security config |
| A custom trust manager that accepts everything | Ships to production and disables TLS for all users | `debug-overrides` in the configuration, which cannot ship |
| `localhost` from the emulator | Resolves to the emulator itself | The host loopback alias, or `adb reverse` |
| Relying on OkHttp's defaults | No overall call timeout means a request can hang forever | Set `callTimeout` explicitly |
| Retrying every failure | Duplicates writes and hammers a failing backend | Idempotent operations, transient failures, backoff with jitter |
| Pinning without backup pins | The next key rotation bricks every installed app | Backup pins, expiry, kill switch — or no pinning |
| Checking "is connected" | Captive portals report connected | Ask for validated internet capability |
| Reflective JSON without keep rules | Fields silently empty in release only | Keep rules, or a code-generating serializer |
| Body-level logging left in release | Tokens and personal data in logcat, readable by anyone with a debug bridge | Debug-only dependency and a debug-only interceptor |
| API models used as domain models | One server rename breaks every screen | Map at the boundary |

## Write Down What It Was

- **Base URLs per environment and any proxy or corporate-CA requirement** go to `## App Context` in `~/Clawic/data/android/memory.md` — never a token, only the pointer (`memory-template.md`).
- **A pinning decision, its pin set source and its rotation plan** is `artifacts/<kebab-name>.md` with its `## Boxes` line, plus a `## Due` row for the rotation date. A pinning decision that lives only in code is an outage waiting for a calendar.
- **A network failure whose cause was environmental** — split DNS, a captive portal, an OEM VPN, an MTU problem — is a line in `## Pain Points`, because it will be reported again by the same user.
