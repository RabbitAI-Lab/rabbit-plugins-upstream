# Insight Challenge

Adversarial review of code quality findings: challenge insights with counter-evidence, verify claims against source code, and produce structured verdicts.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  Insight Challenge (SKILL.md) — Adversarial Review          │
│  → Parse finding → Read source → Challenge → Verdict        │
└─────────────────────────────────────────────────────────────┘
                           │
    ┌──────────┬───────────┼───────────┬──────────┐
    ↓          ↓           ↓           ↓          │
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐      │
│Phase 1 │ │Phase 2 │ │Phase 3 │ │Phase 4 │      │
│ Parse  │ │ Source │ │Challenge│ │Verdict │      │
│Finding │ │ Review │ │Analysis │ │Report  │      │
└───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘      │
    │          │          │          │             │
 finding    source     counter-   structured      │
 parsed     code       evidence   verdict         │
```

## Key Design Principles

1. **Adversarial by Default**: Assume findings may be incorrect; seek counter-evidence first
2. **Source-Code Anchored**: All claims must be verified against actual code, not assumptions
3. **Structured Output**: Verdicts follow a fixed schema for downstream consumption
4. **Fair Challenge**: If evidence supports the finding, confirm it; don't manufacture doubt
5. **Transparent Reasoning**: Show the chain of evidence and reasoning

## Finding Input Format

Findings can be provided as JSON or structured text. Field requirements:

| Field | Required | Notes |
|-------|----------|-------|
| `id` | Required for JSON input; generated by the skill for inline input | Finding identifier |
| `title` or `claim` | Yes (either) | Finding title or verifiable claim |
| `file` or inline evidence | Yes (either) | Source file reference, or evidence text provided directly |
| `severity` | No | Original severity |
| `line` | No | Line number |
| `description` / `evidence` / `suggestion` / `design_ref` | No | Supplementary notes and design references |

When required fields are missing, list them per IC-E05 and ask for completion; never proceed on guesses.

```json
{
  "id": "HIGH-01",
  "title": "Knowledge edge types resolves/documents not declared in types.ts",
  "severity": "high",
  "file": "src/graph/kg/db/types.ts",
  "line": 58,
  "description": "issue-extractor uses 'resolves' edge type...",
  "evidence": "types.ts KnowledgeEdgeKind: defines, constrains...",
  "suggestion": "Add missing edge type declarations",
  "design_ref": "Gap 2 — 12 CodeEdgeKind + 9 KnowledgeEdgeKind"
}
```

Or structured text:
```
HIGH-01: Knowledge edge types resolves/documents not declared in types.ts
Severity: high
File: src/graph/kg/db/types.ts:58
Claim: issue-extractor uses 'resolves' edge type but it's not declared in the type system
Evidence: types.ts KnowledgeEdgeKind list is missing 'resolves'
```

## Execution Flow

Execute in four phases: Parse Finding → Source Review → Challenge Analysis → Verdict Report.

### Phase 1: Parse Finding

1. Extract finding ID, title, severity, file reference, and claims.
2. Identify all verifiable assertions:
   - File existence claims
   - Code structure claims (types, functions, variables)
   - Behavioral claims (usage patterns, dependencies)
   - Design conformance claims
3. Create a verification checklist.

### Phase 2: Source Review

1. Read the referenced file(s) at the specified lines.
2. Search for related code using Grep/Glob.
3. Document the actual state of the code:
   - What types/functions actually exist
   - What values are actually declared
   - What the actual implementation looks like
4. Compare claims against reality.

### Phase 3: Challenge Analysis

For each claim in the finding:

1. **Seek confirming evidence**: Does the source code support this claim?
2. **Seek disconfirming evidence**: Does the source code contradict this claim?
3. **Check for misinterpretation**: Could the claim be based on outdated code or misunderstanding?
4. **Verify design references**: Are cited design docs accurate?

Challenge strategies:
- **Direct contradiction**: Source code explicitly shows the opposite
- **Context omission**: The finding omitted relevant context that changes the interpretation
- **Stale reference**: The finding references code that has been updated
- **Miscounted**: A numeric claim (missing N types) is incorrect
- **Scope error**: The finding applies the wrong scope (e.g., confusing edge types with language types)

### Phase 4: Verdict Report

Produce structured output:

```json
{
  "finding_id": "HIGH-01",
  "challenge_result": "overturned|weakened|confirmed",
  "confidence": 95,
  "reasoning": "Detailed explanation of why the finding was challenged or confirmed",
  "counter_evidence": [
    "Source file line 64: 'resolves' IS declared in KnowledgeEdgeKind",
    "Design doc specifies 20 edge types, not 28"
  ],
  "supporting_evidence": [],
  "adjusted_severity": "none|critical|high|medium|low",
  "recommendation": "Dismiss this finding; the claimed gap does not exist"
}
```

After producing the verdict, run the validator (supported input forms: a JSON file, a stdin pipe, or a markdown report; the JSON itself can be a single verdict, a batch verdicts object, or a top-level array; see README.en.md):

```bash
node scripts/validate-verdict.mjs <verdict.json>   # or report.md, or - to read stdin
```

If it fails, fix the verdict per the reported errors and re-validate (see IC-E06).

## Verdict Definitions

| Verdict | Meaning | When to Use |
|---------|---------|-------------|
| **overturned** | Finding is factually incorrect | Source code directly contradicts the claim |
| **weakened** | Finding is partially correct but overstated | Some evidence supports it, but severity/scope is wrong |
| **confirmed** | Finding is accurate | Source code supports all claims |

## Challenge Patterns

### Pattern 1: Type Declaration Check
```
Claim: "Type X is not declared"
Challenge: Read the type file → check if X exists in type union/enum
Counter: "Line N shows X IS declared in the type definition"
```

### Pattern 2: Design Reference Verification
```
Claim: "Design requires N items, implementation has M"
Challenge: Read design doc → verify the claimed requirement
Counter: "Design doc actually specifies K items, not N"
```

### Pattern 3: Usage Verification
```
Claim: "Code uses type X but X is not defined"
Challenge: Check both usage site AND definition site
Counter: "X is defined at line N in file Y"
```

### Pattern 4: Scope Confusion
```
Claim: "Missing 7 edge types (total should be 28)"
Challenge: Check what the "28" actually refers to
Counter: "The 28 refers to language types, not edge types; edge types are 21"
```

## Error Handling

| Code | Scenario | Resolution & Recovery |
|------|----------|-----------------------|
| IC-E01 | Referenced file not found | Report file missing; verdict = weakened (potentially stale) |
| IC-E02 | Line number out of range | Relocate via Grep on the claimed content; adjust the line reference |
| IC-E03 | Design doc not found | Skip design verification; note in report |
| IC-E04 | Ambiguous evidence | Present both sides; drop confidence below 70 and explain |
| IC-E05 | Required input fields missing | List missing fields and ask for completion; never proceed on guesses |
| IC-E06 | Verdict fails the validator | Fix the verdict per validator errors and re-validate |
| — | Multiple findings batch | Process each independently; produce per-finding verdicts |

## Stability Guarantees

- **Idempotent**: verdicts are determined solely by source evidence — challenging the same finding against the same codebase twice yields the same verdict.
- **Read retry**: on Read failure, retry once via Grep content search; if that fails, degrade per IC-E01 without retry loops.
- **Context cap**: expand call chains at most 2 levels deep; stop when confidence stops rising with further evidence.
- **Batch isolation**: a single failed finding never blocks the rest of the batch; each finding gets its own verdict.

## Scope & Limitations

This skill is for **adversarial review of code-quality findings against source code**. It is **not** suitable for:

- Security-only audits or vulnerability scanning as tasks themselves (use a dedicated security review tool); **specific findings** produced by a security scan can still be adversarially verified as input.
- Generic code review of a full MR/PR without specific findings to challenge.
- Findings that cannot be verified against accessible source code, design docs, or runtime evidence — in that case output `weakened` with a note that evidence is unavailable.
- Style-only or preference-based findings with no factual claim to verify.

## FAQ

**Q: What if the source file doesn't exist?**
A: Output `weakened` with confidence lowered. Note the missing file as the reason; do not guess the finding is wrong.

**Q: What if multiple findings contradict each other?**
A: Challenge each independently. If one finding's evidence overturns another, note the conflict in the `reasoning` field.

**Q: Can I confirm a finding without reading the source?**
A: No. Always verify against the source. If the source is inaccessible, lower confidence and say so.

**Q: How is `confidence` decided?**
A: 90–100 = source directly proves the verdict; 70–89 = strong evidence with minor gaps; below 70 = evidence is partial or ambiguous. Never fabricate confidence — justify it with the evidence collected.
