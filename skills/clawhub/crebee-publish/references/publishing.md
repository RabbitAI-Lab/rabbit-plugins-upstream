# 内容发布

## 业务流程与表达边界

所有发布都遵循同一业务路径：

```text
选账号 → 登记目标 → 填参数 → 参数校验 → 用户确认 → 提交 → 跟踪终态
                          ↑ 校验失败只回到对应平台/账号
```

CLI 内部使用 `runId`、`taskId`、`planHash`、参数 JSON、平台表单和状态轮询完成编排。这些都是内部协议，正常对话中禁止向用户展示或解释。用户侧只使用以下说法：

- 提交前：本次发布、发布计划、准备发布。
- 提交后：发布中、已发布、发布失败。
- 只有技术支持确实需要定位时，才把 `runId` 称为“发布批次编号”，不要说 run。

不要向用户展示或主动提及：`run/runId`、`taskId`、`planHash`、`common-form.json`、目标登记文件、平台参数文件、平台表单、schema、validate、submit、发布队列、轮询、SSE、trace、本地记录、缓存命中、发布预占或释放、项目 memory。不要专门解释“本地提交不等于平台成功”；内部正确跟踪结果即可。

## 固定职责

主 Agent 始终负责：

- 确认账号、公共内容、推荐范围和发布时间。
- 初始化本次发布并登记权威目标账号集合。
- 收集所有平台的查询计划，向用户展示一次 BC 总预计。
- 收齐平台结果后执行全体校验，展示最终发布计划并取得确认。全体校验由 CLI 自动聚合各平台已保存的表单，主 Agent 不读取、复制或合并任何 CLI 产物文件。
- 唯一一次正式提交、按返回的恢复指令轮询发布状态、有限自动纠错和最终汇报。

平台参数处理可以由主 Agent 或平台 Sub Agent 执行，但交付协议不变：

- 一到两个目标平台：主 Agent 默认按平台串行完成。
- 三个及以上目标平台：推荐一个平台一个 Sub Agent 并行；一个 Sub Agent 负责该平台全部目标账号。
- 平台执行者只做三件事：读取本平台 schema → 按计划查询动态字段 → 写一份本平台账号级覆盖参数文件并执行平台校验。
- 平台执行者把校验通过或字段级错误的结果交回主 Agent 即可，不回传任何产物路径或规范化参数，也不执行全体校验和提交。
- 用户的转载来源、固定话题、平台文案偏好等自由意图由主 Agent 写进平台任务提示；串行处理时主 Agent 把同样的意图作为该平台的填写依据。不为此新增专门字段。
- 用户指定串行或并行时服从用户；宿主不支持 Sub Agent 时由主 Agent 串行。
- 即使主 Agent 串行，也是一个平台一个参数文件分别校验。

平台隔离是硬约束，Sub Agent 只是规模较大时的执行优化。

## 对话入口

### 账号与素材

用户未给准确账号 ID 时，先运行：

```text
crebee accounts list --status connected
```

账号名称有多个候选时让用户选择。优先索取或定位绝对路径素材和目标账号，不要机械要求用户按“标题、正文、视频、封面”格式填写。

- 能理解素材时，主动生成可编辑标题和文案；不要把建议说成用户已提供的事实。
- 不能可靠理解时，只补问主题、目的或重点等最少信息。
- 多个视频或文章文件是多个独立作品，每个作品独立走一次发布。
- 多张图片只有明确属于同一组时才组成一篇图文；否则先确认分组。
- 视频没有自定义封面时运行 `media cover --video "/absolute/video.mp4"`，使用 `artifacts.cover`，不要自行安装 ffmpeg。

### 推荐范围

确认目标账号后，只问一次：

> 除了标题和描述/正文，是否还需要我根据素材推荐话题、合集、配乐等发布参数？这会增加一些 CreBee API 调用次数。

- 用户只要标题和正文：只处理必填动态字段和用户明确指定字段。
- 用户需要推荐：按 schema 的 `recommendationPolicy` 制定计划；发布前展示一次总预计后直接执行，不逐字段再次询问。
- 用户尚未选择时等待回答，不默认开启推荐。

BC 仅表示 CreBee API 调用次数。用户全程只看到三段 BC，各段措辞固定：

1. **查询前（总预计）**：在账号和推荐查询范围确定后展示一次“预计共 N 次调用（M 次参数查询 + K 次发布）”。
2. **计划确认时（已消耗 + 待消耗）**：查询已经发生、不可退回，禁止再说“预计”。直接使用全体校验结果里的 `bcPlan` 照抄：“本次已消耗 X 次（参数查询）；确认发布将再消耗 Y 次；合计 Z 次。若取消发布，已消耗的查询次数不返还。”
3. **终态后（总实际）**：所有自动纠错结束后报告 `bcActual.totalConsumed` 一次。

发布中途用户询问消耗时，用 `publish status` 返回的 `bcSnapshot.consumed` 回答“目前已消耗 N 次”，不表述为最终总量。任何阶段都不要展示平台拆分、参数查询拆分、缓存、预占、释放或失败账号结算公式。

### 版权与转载来源

版权属性不是固定表单问题。先结合用户表述、文件名和可见素材判断是否存在转载或二创信号，只在有必要时询问：

- 用户明确说明是自己拍摄或自己制作：采用用户事实，不再重复询问。
- 用户明确说明转载、搬运、二创或给出外部来源：采用该意图；平台需要来源时使用用户给出的来源。
- 文件名包含下载器常见后缀、来源平台或作者标识，画面包含第三方水印、频道名、账号名、字幕来源等明显信号：认为存在转载可能，简短询问原创、转载或二创；如果是转载，再询问缺失的来源。例如：“这个视频看起来可能来自其他平台。它是你自己制作的、转载的，还是二次创作的？如果是转载，也请告诉我来源。”
- 没有明显转载信号，且目标平台没有必填版权字段：不增加固定问题，也不擅自填写转载、原创或 AIGC 声明。
- 平台没有来源/转载声明字段（如快手的 declareInfo 只有 AI、演绎、个人观点）时，不追问来源，也不伪造声明；仅在最终预览的备注里说明“未填写来源”。
- 目标平台版权字段必填，而现有信息不足以确定取值：必须询问，不能默认原创。
- “没有水印”不能单独作为原创证据。

转载来源采用用户输入，不做内容真实性和具体性审核，不主动打开来源核验：

- 平台允许文本来源时，用户给出的站点、作者或频道信息可直接使用。
- 平台要求 URL 时，完整 URL 直接使用；`www.youtube.com`、`youtube.com/channel/...` 等可识别域名补成 HTTPS 后使用。
- 不要求用户把站点域名补成具体频道或作品链接，除非平台 schema 明确需要更具体结构。
- 空值、“网上找的”“不知道”“朋友手机里偷的”等无法满足平台格式要求的输入必须补问。
- 不得自行编造来源，也不能为了通过校验悄悄改成原创。

使用 Sub Agent 时，主 Agent 把已经得出的版权判断和用户补充内容写进对应平台任务提示。

### 素材路径

用户给出的绝对路径是第一搜索参考，不保证永远正确，也不允许仅凭风险猜测提前复制素材：

1. 对用户给出的绝对路径正确引用并检查文件是否存在。
2. 文件存在时原样使用；空格、中文、emoji 或较长文件名本身不是复制和重命名的理由。
3. 文件不存在时，以原目录和文件名为锚点做最小修复：引号、路径分隔符、盘符大小写、Unicode 规范化，以及在原目录附近寻找唯一明显匹配项。
4. 只有一个确定匹配项时可以自动采用修正后的真实路径。
5. 出现多个候选，或候选差异可能代表不同素材时，询问用户选择。
6. 文件确实存在，但 CLI 或平台明确返回路径编码、文件名或上传兼容错误时，才允许复制到安全的临时工作路径后重试；不得覆盖或移动用户原文件。

## 内部执行流程

以下命令和文件只用于 Agent 执行，不复制到用户回答中。

### 1. 初始化公共内容

写一个临时请求 JSON，只包含内容类型和公共内容，不包含账号：

```json
{
  "contentType": "video",
  "commonForm": {
    "title": "公共标题",
    "desc": "公共文案",
    "videoPath": "/absolute/video.mp4",
    "coverPath": "/absolute/cover.jpg",
    "timing": 0
  }
}
```

- `contentType`：`video`、`image` 或 `article`。
- 视频：`title`、`desc`、`videoPath`、`coverPath`；图文：`desc`、`images`；文章：正文直接放 `content`，可带 `title`、`covers`。
- 素材使用真实绝对路径；`videoPath`、`coverPath` 和图文 `images` 也接受 http(s) 远程 URL，CreBee 会在发布前自动下载本地化。远程视频无法用 `media cover` 本地截帧，未提供封面时需用户给出封面或先下载视频。文章封面 `covers` 仍要求本地绝对路径。
- 公共标题和文案只是每个账号的初值；平台限制更严时在账号参数中单独适配。

运行：

```text
crebee publish create --request "/absolute/request.json"
```

保存返回的 `runId` 供后续内部命令使用，不告诉用户。提交前用户增减账号时，在内部重新登记目标账号集合并重校验受影响的平台，不解释内部状态。提交后新增账号时告诉用户：“前面的账号已开始发布，新增账号需要单独再发布一次。”

### 2. 登记目标账号

用户确认目标账号后，写一个只含平台与账号标识的登记文件：

```json
{
  "targets": [
    { "platform": "douyin", "accountId": "account-1" },
    { "platform": "douyin", "accountId": "account-2" },
    { "platform": "xiaohongshu", "accountId": "account-3" }
  ]
}
```

运行：

```text
crebee publish targets --run "<runId>" --request "/absolute/targets.json"
```

- 纯本地命令，不查询平台接口、不消耗 BC。
- 只写平台和账号 ID，不写 `taskId`；账号的内部任务号由 CLI 分配，目标不变时保持稳定。
- 登记是整体替换，不是增量追加；必须一次写入用户确认的全部账号。
- 任一账号增减都会使旧的确认计划失效；目标发生变化的平台需要重新执行平台校验。
- 提交后目标集合冻结，新增账号属于另一次发布。

### 3. 逐平台读取字段清单

每个目标平台执行：

```text
crebee schema --run "<runId>" --platform douyin
```

独立查看能力时可用：

```text
crebee schema --platform douyin --type video
```

读取 `summary.fields`：

- `requirement`：`required`、`conditional`、`optional`。
- `recommendationPolicy`：`required`、`recommended`、`contextual`、`explicit_only`。
- `options`、`defaultValue`、`constraints`、`agentPrompt`：静态填写依据。
- `remote.queryUnits`、`requiresKeyword`、`reusePolicy`、`queryCommand`：动态查询依据。

推荐模式下：

- `required` 必须处理。
- `recommended` 主动查询并尝试匹配，典型是话题、合集、配乐、活动和热点。
- `contextual` 只在素材存在可靠人物、账号或地点信号时查询，典型是 @ 和位置。
- `explicit_only` 只在用户明确要求或业务条件明确触发时处理，典型是商品、权限和商业字段。

“主动尝试”不等于强行填写：无候选、账号没有可用值或关联明显牵强时省略。不要在最终预览中列出所有省略字段。

### 4. 汇总一次 BC 总预计

先让所有平台完成 schema 和查询计划，再向用户展示一次总预计，随后执行查询。不要边查边问或边查边播报。

计算方式：

```text
总预计 = 唯一计划查询的 remote.queryUnits 之和 + 目标账号数
```

按去重后的计划查询把 `queryUnits` 机械加总即可，不做其他折算或预留。
- `requiresKeyword` 的字段按**每个关键词一次查询**计费：同一字段查两个关键词就是 2 次 `queryUnits`（实测口径）。

动态字段的 `remote.reusePolicy` 决定去重：

- `scope=none`：不复用。
- `scope=account`：同平台每个账号单独计算，合集、好友、商品通常属于此类。
- `scope=platform`：同一次发布中，相同平台、字段、规范化关键词和请求依赖只计算一次，话题等平台公共候选可以给该平台多个账号使用。
- `maxAgeSeconds`：超过有效期必须重新查询。

实际调用 `field query` 时始终带一个目标账号用于平台鉴权；平台级复用不代表查询接口不需要账号。

用户侧只需表达，例如：“这次发布到 6 个账号，预计共使用 11 次 CreBee API 调用。要按这个计划发布吗？”不要列每个平台花多少，也不要提缓存。

### 5. 查询动态字段

按计划执行：

```text
crebee field query --run "<runId>" --platform douyin --field topics --account "<accountId>" --keyword "AI 工具"
```

- `--run`、`--platform`、`--field`、`--account` 必填；需要关键词时必须给 `--keyword`。
- 正常流程不传 `--task`。
- 从 `summary.candidates` 选中完整 `value` 原样写入参数；不得只抄 ID、手拼对象或直接调用底层 HTTP API。
- `scope=platform` 且复用键仍有效时，只查询一次；其他账号使用同一候选值即可通过校验。
- `scope=account` 的候选只能给对应账号使用。
- 候选永远不能跨平台或跨本次发布使用。
- 中间 `bcActual` 是内部累计，不向用户播报。

### 6. 逐平台填写覆盖参数并校验

一个平台一个文件，一个文件包含该平台全部目标账号。`params` 只写相对公共内容的账号级覆盖项，不写 `taskId`：

```json
{
  "platform": "douyin",
  "targets": [
    {
      "accountId": "account-1",
      "params": {
        "title": "平台限制下的适配标题",
        "topics": []
      }
    },
    {
      "accountId": "account-2",
      "params": {
        "collection": {}
      }
    }
  ]
}
```

- 公共内容（标题、文案、素材路径、发布时间等）和平台默认值由 CLI 自动继承合并，账号覆盖优先；不要在文件里逐账号复制公共参数。
- 需要平台适配时只写差异项，例如更严限制下的短标题、清空某字段或账号专属话题。
- 文件必须精确覆盖登记的本平台全部账号，缺失、重复或额外账号都会被拒绝。

运行：

```text
crebee publish validate --run "<runId>" --scope platform --platform douyin --params "/absolute/platform-params.json"
```

校验通过后 CLI 直接保存该平台最新表单，平台执行者把结果交回主 Agent 即可，不回传文件路径或规范化参数。校验失败时读取字段级错误，只修改失败账号并重跑本平台校验；已通过账号不返工。平台级候选可以按 schema 声明复用，账号级候选跨账号使用会被拒绝。

### 7. 全体校验

所有平台都通过平台校验后，主 Agent 执行一次：

```text
crebee publish validate --run "<runId>" --scope all
```

- 全体校验不传任何参数文件：CLI 从登记的目标账号集合和各平台最新已保存表单自动聚合，主 Agent 不读取、复制或合并任何 CLI 产物文件。
- CLI 会核对结果精确覆盖用户选择的全部账号，没有遗漏或多出账号，并在通过后给出内部确认摘要。
- 任一平台尚未通过校验、目标或平台输入在校验后发生变化，或公共素材中途失效，全体校验都会失败；按错误回到对应平台的填写与校验，不向用户解释内部文件或状态。

### 8. 用户预览与提交

最终预览只展示：

- 内容标题和简短文案摘要。
- 目标平台与账号。
- 实际选中的话题、合集、配乐、活动、位置等有意义的平台参数。
- 立即或定时发布。
- 本次 BC 总预计。

禁止增加“关键风险”“明确省略项”“本地提交”等技术栏目。标题或文案可以修改，只需在最后自然补一句：“如果标题或文案还要调整，告诉我即可；没问题我就按这个计划发布。”

用户明确确认后，主 Agent 内部执行一次：

```text
crebee publish submit --run "<runId>" --confirm "<planHash>"
```

- 一个内部 Run 只提交一次。提交只把任务交给发布队列并立即返回，不等待发布结果，也不使用等待参数。
- 提交结果不确定时禁止重提，只能用 `publish status` 恢复。
- 提交后按返回的 `nextAction` 重复执行 `publish status --run "<runId>"`：建议间隔为返回的 `retryAfterSeconds`（5 秒），最长轮询 10 分钟。
- 轮询超过 10 分钟仍有账号未到终态时，如实告诉用户“仍在发布”，不判失败、不重提；之后用户询问时可以继续查询。
- 全部账号到达终态后才展示一次实际 BC，并先按下一节的自动纠错条件处理失败账号。
- 立即发布和定时发布使用同一成功口径：平台发布接口正常接受即为发布成功。定时只是发布方式，不需要等到计划时间，也不因为定时而额外查询状态。
- `publish status` 是本地任务状态查询，不是云端作品审核查询。用户没有明确要求时，不额外查询云端审核记录，也不说“审核成功”。

## 确定性失败的有限自动纠错

用户确认发布后，视为同时授权一次不会改变核心意图的机械纠错。取得明确失败终态后，逐个失败账号判断。

可以不再询问、直接自动修正并只重试失败账号一次，必须同时满足：

1. 失败是明确终态，不是超时、未知或仍在发布中。
2. 平台消息明确指出具体字段和具体约束。
3. 修正可机械完成，不改变账号、素材、发布时间、版权归属或核心表达。
4. 不增加发布预览之外的新推荐字段；需要的既有动态字段按原查询计划重新取得。
5. 该账号在这次用户发布意图中尚未自动纠错过。

典型可纠错场景：`标题最多 50 字`、`描述不能超过 1000 字`。把对应文本压缩到明确限制内，在内部为失败账号单独完成参数校验和发布；已成功账号绝不重复发布。

内部纠错执行仍复用本文固定流程，但目标集合只包含失败账号：以原公共内容初始化新的内部发布 → 登记只含失败账号的目标集合 → 读取该平台 schema → 只重新取得原计划确实需要的动态候选 → 写入修正后的账号覆盖参数 → 平台校验与全体校验 → 直接提交并轮询到终态。用户对原发布计划的确认已经覆盖这次有限纠错，不再发起确认题。最终实际 BC 必须把初次发布和纠错发布的 `totalConsumed` 相加后只报总数。

以下情况不自动重试：

- 只有通用错误码，无法定位具体字段。
- 认证、账号权限、平台风控、版权、素材格式、上传或网络错误。
- 修正需要替换素材、改变版权声明、增加新字段查询或明显改变用户表达。
- 同一账号已经自动纠错一次，或重试再次出现相同错误。

视频号 `300002 request failed` 只表示“发布参数未通过平台校验”。没有进一步字段证据时不得猜测 `link`、`objectType`、权限或素材，也不得盲目重试；按 troubleshooting 在内部排查，向用户只说“视频号参数未通过平台校验”。

自动纠错成功后，最终备注一句即可，例如：“首次标题过长，已缩短后发布成功。”不要告诉用户内部重新创建了发布流程。自动纠错失败或不符合条件时，再向用户给出可理解原因和下一步选择。

## 最终结果与 BC

所有初次任务和允许的一次自动纠错都结束后再汇报。推荐格式：

```text
已发布到 6 个账号：5 个成功，1 个失败。实际使用 11 次 CreBee API 调用。

| 平台 | 账号 | 发布方式 | 结果 | 备注 |
|---|---|---|---|---|
| 百家号 | 示例账号 | 立即发布 | 已发布 | 首次标题过长，已缩短后发布成功 |
| 视频号 | 示例账号 | 定时发布：9 月 3 日 20:00 | 发布失败 | 发布参数未通过平台校验 |
```

- BC 只给所有内部发布与纠错合计后的 `totalConsumed` 总数，不解释参数查询、成功账号、缓存、失败扣费或节省来源。
- 同时包含立即与定时任务时，表格必须展示发布方式和定时时间；纯文本汇报也可以分为“立即发布”和“定时发布”两段。
- 原始平台错误码默认不展示；用户明确要求技术细节时才附带。
- 不声称写入了 memory、项目文档或内部记录，除非用户要求这样做。
- 只要有账号发布成功，在结果末尾自然补一句“平台审核或展示可能需要一些时间。”不要展开 CreBee 提交、平台接口和内容审核的内部层级；用户之后明确要求查审核状态时再单独查询。

## 取消与兼容

用户要求取消仍可取消的发布时，在内部使用：

```text
crebee publish cancel --run "<runId>"
crebee publish cancel --run "<runId>" --tasks "taskId1,taskId2"
```

取消失败通常表示任务已执行或不存在，不自动重复取消。

旧版 Skill 创建的旧发布继续按其创建时的命令完成。新发布一律使用本文流程；不要手工改写旧状态，也不要把旧内部兼容细节告诉普通用户。
