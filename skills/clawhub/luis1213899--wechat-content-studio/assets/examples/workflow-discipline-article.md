# 我被一键发布教育了一次

前两天，我做了一件看起来特别小的事。

我写了一篇测试文章。

然后顺手把它发进了公众号草稿箱。

如果只看结果，这件事挺顺。

文章有了。

草稿也有了。

脚本还跑通了。

但我回头一想，心里其实有点不踏实。

因为那个过程里，有一个动作很危险。

我把「试一下」听成了「可以先绕开正式流程」。

坦率的讲，这个毛病太常见了。

我们做自动化的时候，很容易被一个词骗过去。

试试。

随便跑跑。

先看看链路通不通。

听起来都很轻。

但内容发布不是本地打印一行日志。

它一旦真的撞到平台接口，就不是玩具动作了。

草稿箱里会多一篇文章。

素材库里会多一张图片。

日志里会多一个 Media ID。

微信后台会记住你这次请求。

如果你没有把这些东西当成正式动作，它们就会反过来教育你。

我这次就是这样。

一开始，我的想法很简单。

先写一篇短稿，证明发布链路能跑。

于是我直接写了 Markdown。

用了旧封面。

跑了预检。

再推到草稿箱。

流程确实跑通了。

但这件事有个问题。

它证明了脚本能跑，却没有证明工作流是对的。

这两个东西完全不一样。

脚本能跑，只说明机器执行了一串命令。

工作流是对的，说明这串命令前后的人、内容、素材、校验和平台状态都被照顾到了。

差别就在这里。

一个是能不能动。

一个是该不该动。

## 最容易出事的地方，是大家都觉得没事

我以前很喜欢一键按钮。

尤其是那种看起来很潇洒的按钮。

点一下。

封面上传。

正文渲染。

草稿创建。

验证完成。

控制台一片绿色。

说真的，这种感觉很爽。

但现在我有点警惕这种爽感。

因为一键按钮如果没有门禁，它就不是效率工具。

它只是一个很快的风险放大器。

公众号发布尤其明显。

它不像本地构建失败了，删掉缓存重来就行。

它连着微信接口。

连着素材上传。

连着草稿箱。

连着 IP 白名单。

也连着你对读者的第一印象。

你以为自己只是在跑测试。

平台那边可不会这么理解。

它只知道你发起了一次真实请求。

所以我现在越来越觉得，内容工作流里最重要的不是自动化。

最重要的是停顿。

该停的时候能停下来。

发现 IP 不对，就别继续。

发现封面还没确认，就别继续。

发现正文没排版校验，就别继续。

发现草稿已经存在，就别继续。

这些停顿看起来会让流程变慢。

但它们其实是在帮你省掉后面更贵的返工。

## 写作也不能被当成占位符

这次还有一个问题更隐蔽。

我把文章当成了测试材料。

只要能发出去，好像就够了。

但公众号文章不是接口请求体。

它不是随便塞进去的一段字符串。

它有标题，有开头，有情绪，有节奏，也有读者打开以后那几秒钟的判断。

读者不会管你是不是在试流程。

他只会觉得，这篇东西值不值得继续看。

这也是为什么写文章本身必须进工作流。

选题要先过一遍。

它有没有好奇心。

有没有信息量。

有没有共鸣。

这篇文章的题材，其实就是一次很小的翻车复盘。

Happy 不算强，但它有一点反差。

明明是为了验证自动化，却暴露出自动化不能乱用。

Knowledge 是有的。

它能把写作、封面、排版、发布和验证之间的关系讲清楚。

Resonance 也有。

因为很多人都踩过这种坑。

嘴上说只是试试，手上却已经动了正式环境。

所以它至少是一个及格选题。

文章原型也很明确。

它不是教程。

不是工具清单。

更像是一次方法论分享。

我把自己刚踩到的坑拿出来，拆给你看。

不是为了证明流程有多复杂。

而是为了说明，为什么有些复杂是必要的。

我有时候觉得，成熟的工作流都有一点反人性。

人性想省事。

工作流偏要你确认。

人性想先跑了再说。

工作流偏要你先检查。

人性觉得这次只是测试。

工作流偏要把测试也当成正式动作的一部分。

这听起来有点烦。

但也正是这种烦，让系统开始可靠。

## 封面不是装饰，它是发布流程的一部分

封面这件事也一样。

很多时候，我们会觉得封面只是配图。

临时找一张能用的图，先把流程跑通就行。

但公众号里，封面就是入口。

它不是正文的附属品。

它是读者看到文章前的第一块信息。

所以这个项目里才把封面单独拎出来。

不用旧图凑合。

不用别的模型降级。

也不把 API key 写进脚本。

先出提示词草稿。

人确认以后，再调用中转站的 gpt-image-2。

这个确认动作不是形式主义。

它是在问一件很朴素的事。

这张图，真的代表这篇文章吗。

如果文章讲的是工作流纪律，封面就不该是一张随便的科技背景。

它应该让人一眼看出，里面有发布、有门禁、有检查、有从混乱到秩序的过程。

不要文字。

不要 logo。

不要乱七八糟的界面。

画面要像一次编辑部里的发布前复盘。

桌面上有稿纸，有检查清单，有草稿箱的隐喻，有一盏灯。

这比直接拿旧封面靠谱得多。

因为素材也在表达。

素材不能只负责填空。

## 排版校验，是给公众号编辑器准备的安全带

正文排版也不是可有可无。

Markdown 看起来很干净。

但微信公众号编辑器不是 Markdown 编辑器。

它吃进去的是富文本。

很多样式如果没有按平台脾气写，粘贴进去就会丢。

有些标签会被过滤。

有些属性会被剥掉。

有些半角标点在正文里看着也很突兀。

所以 gzh-design 那一步不能跳。

它要把文章变成可粘贴的 HTML。

所有样式内联。

所有文字节点包进 span leaf。

再跑校验脚本。

ERROR 清零。

正文半角标点 WARNING 清零。

然后再生成带复制按钮的预览页。

这一步听着很工程。

但它服务的其实是阅读体验。

排版不是为了好看而好看。

它是在帮读者分层。

哪里是主线。

哪里是提醒。

哪里是结论。

哪里只是过渡。

如果没有这一步，文章可能也能发出去。

但读起来会散。

尤其是这种讲流程的文章，如果排版没有层次，读者很快就会觉得自己在看说明书。

我不想让它变成说明书。

我想让它像一个人坐下来，把刚刚踩到的坑讲清楚。

## 真正的一键，是前面每一步都不偷懒

再往后说发布。

发布脚本本身现在已经更稳了。

它会先看本机出口 IP。

如果本机不在白名单，就切到服务器出口。

它会检查凭证是不是占位符。

它会查上一条草稿还在不在。

如果草稿已经存在，就短路，不重复发布。

这些都是好设计。

但好设计也怕人绕开。

人一旦说「这次就算了」，流程就开始漏水。

所以这次要把规则写死。

写文章要走写作工作流。

封面要走 image2 确认式工作流。

正文要走 gzh-design 排版和校验。

发布要走预检和草稿验证。

哪怕只是测试稿，也一样。

测试稿可以短。

但不能假。

测试流程可以快。

但不能跳。

我现在对一键发布的理解也变了。

一键不是前面什么都不管，临门按一下。

一键是前面每一步都被清楚地定义过，所以收束时那一下才值得信任。

没有这些定义，一键只是碰运气。

有了这些定义，一键才像工具。

这大概就是我被这次发布流程教育到的地方。

不是自动化不好。

恰恰相反，我很喜欢自动化。

但越是喜欢自动化，越要承认一件事。

机器可以跑得很快。

人必须把边界画清楚。

如果边界没画清楚，机器只会很快地把错误送到更远的地方。

如果边界画清楚了，机器才会稳稳地把表达送出去。

这次重新来一遍，我想验证的就不是脚本能不能跑。

而是我们能不能认真对待一整条工作流。

写作认真。

封面认真。

排版认真。

校验认真。

发布也认真。

只有这样，草稿箱里多出来的那篇文章，才不只是一次测试记录。

它才算是一篇真正准备给人看的公众号文章。
