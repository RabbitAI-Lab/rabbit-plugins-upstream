# 任务接力规程

> 本文件是 handoff 运行时协议本体。在安装包内它只是待搬运的载荷，不会被加载或执行；
> 只有被安装到目标仓库的 `.agents/skills/handoff/` 之后才生效，且安装需经用户确认。
> 下面的规程面向**已安装该协议的仓库**里的日常工作。


本仓库的接力状态全部存放在 `.agents/tasks/current.md`（下称「任务棒」）。
接力不依赖任何会话历史——任务棒是唯一的状态来源。

## 接棒（会话开始时）

1. 读 `.agents/tasks/current.md`。文件不存在时，视为无进行中任务，正常开工。`status: done` 时先看
   `Next` 是否已清空（`- (none)` 也算清空）、现场是否有新的未提交改动——都没有才视为无进行中任务，
   正常开工；否则按下面「异常情况」里对应的行处理。`status: draft` 时不要直接往下走 2-5 步——
   按「异常情况」里对应的行处理，先经用户确认再继续。
2. 在**第一段回复**里用自己的话复述 **Intent** 与 **Next 第一条**。不要复制原文——复述的意义
   在于让人一眼看出你有没有跑偏。
3. **把这句复述同时写进 frontmatter 的 `ack` 字段**，一到两句，压成一行。
   对话输出会被截断、压缩、或在非交互模式下被调用方丢弃，写进任务棒才留得下痕、进得了 git、
   事后能和 Intent 对照。只说在回复里等于没说。
4. 校验 Next 第一条的前置条件。不成立就往 **Open questions** 追加一条并告知用户，不要硬上。
5. 把 frontmatter 的 `owner` **覆盖**成你自己的标识，然后开工。

> **`owner` 记录的是「谁持有这根棒」，不是对你的身份指派。**
> 你的标识由你是哪个 agent 决定（`claude-code` / `codex` / `zcode` / `kimicode`），
> **永远不要从 `owner`、`ack`、Decisions 或 commit 历史里读取自己的身份**。
> 接棒时 `owner` 里已有别人的值，是要你覆盖掉，不是要你冒名。
> commit trailer 的 `Agent:` 同理——填你自己是谁，不是抄任务棒里写的谁。

## 交接（结束工作时）

按顺序更新任务棒：

1. **Done** —— 把本轮完成的项从 `Next` 挪过来，每项附产物路径。已完成的条目**只能**出现在
   `Done` 里，不要留在 `Next` 里用 `- [x]` 之类的标记打钩——这样 `Next` 是否还有活，只看这个
   小节下面还有没有列表行就行，不用逐条判断状态。**空 `Next` 按规格要求写成 `- (none)`，判断
   清空时把这一行也算作没有活，不要因为它本身是列表项就误判成还有活。** Done 超过十条时，
   把陈旧的压缩成一句摘要。
2. **Next** —— 改写成下一棒该做的事。第一条必须自包含：写清产物路径与验收条件，
   不要只给「见某文档某节」这类指针。可以附参考链接，但删掉链接后这一条仍要能照做。
   **如果改写后这里已经没有条目了（或者只剩 `- (none)`），先确认 Intent 和验收条件是否也已
   达成、`Open questions` 有没有遗留阻塞项——都确认过了才转去走下面的「完成任务」。只是暂时
   想不出下一步但目标还没达成，说明 Next 漏写了，应该补上，不能当成任务已经完成。**
3. **Decisions** —— 追加本轮做出的判断，格式 `**选择** —— 理由。已考虑并排除：…（日期, 你的标识）`。
   **只追加不覆盖。** 推翻旧决策时追加新条目说明原因，不要删旧的。
4. **Open questions** / **Do not** —— 有变化就更新。
5. frontmatter —— `hop` 加一，`owner` 置空，`ack` 置空，`updated` 改为当前时间。
   `ack` 属于接棒时的瞬时状态，交给下一棒重新填；**最终交棒 commit 里的 `owner:` 与 `ack:` 必须
   都是空字段，不得为了保留本轮复述而留下 `ack` 内容。**

**先改完 frontmatter 再提交**，且 trailer 里的 `Hop` 必须**照抄 frontmatter 的 `hop`**，
不要凭记忆填。两处一旦漂移，`tools/ledger.sh` 的 hop 序列就不再对应任务棒的真实状态。
提交前可以核对：

    grep '^hop:' .agents/tasks/current.md
    grep -Eq '^owner:[[:space:]]*$' .agents/tasks/current.md
    grep -Eq '^ack:[[:space:]]*$' .agents/tasks/current.md

后两条任一失败都说明交棒尚未完成，先清空字段再提交。

然后提交。三个 trailer 必须写在**同一个 `-m` 参数里、彼此换行**——git 只把 message 的最后一个
段落识别为 trailer 块，拆成多个 `-m` 会让前面的降级成正文，`git log --format='%(trailers:...)'`
取不到：

    git commit -m "<英文单行总结>" -m "Task-Id: <task>
    Hop: <hop>
    Agent: <claude-code | codex | zcode | kimicode>"

用 `sh tools/ledger.sh <task>` 可以核对本任务的全部 hop 是否连续。

## 完成任务

**改 `status` 为 `done` 之前，先确认 `Next` 里没有未完成项**——还有的话要么做完，要么明确拆成新任务棒，
不要在 `Next` 有遗留的情况下把 `status` 标成 `done`。`status` 只是粗粒度开关，`Next` 才是任务是否
真做完的依据，两者一旦不一致，下一棒会不知道该信哪个。

确认完 `Next` 之后，`status` 改为 `done`，然后归档并提交。**顺序不能变**（归档必须在合并回主干之前完成）：

    git add .agents/tasks/current.md
    git mv .agents/tasks/current.md .agents/tasks/archive/<task>.md
    git commit -m "archive completed task <task>"
    git show --stat HEAD

**为什么必须先 `git add`**：`git mv` 只把「重命名」这个动作写进索引，工作树里未暂存的内容改动
（也就是你刚改的 `status: done`）不会被一并带上。跳过 `git add` 的结果是归档 commit 变成
0 insertions / 0 deletions 的纯 rename，`status` 仍是旧值，账本上看不出这个棒到底完没完成。

最后那条 `git show --stat HEAD` 是核对：输出里应当有内容改动的行数，只显示重命名就是踩坑了。

归档之后才能合并回主干。此时 `current.md` 已经 `git mv` 进 `archive/`，主干上不会出现它，
另一条任务分支也就不会在合并时和你撞车（实测：归档后合并零冲突，未归档合并必得
`CONFLICT (add/add)`）。

## 反面清单

- **不要**把整段对话复制进任务棒。任务棒记状态，不记过程。
- **不要**写「继续之前的工作」这类 Next。接棒者看不到「之前」。
- **不要**删除旧的 Decisions。它们记录的是为什么不走另一条路，删了下一棒会重走弯路。
- **不要**把探索中的死胡同写进 Done。写进 Decisions 的「已考虑并排除」。
- **不要**跳过复述直接动手。复述是本协议唯一的纠偏点。

## 异常情况

| 情况 | 怎么做 |
| --- | --- |
| `current.md` 不存在 | 视为无进行中任务，正常开工。若用户描述的是延续性工作，提示先建任务棒 |
| `status: done` 且 `Next` 已清空（含 `- (none)`） | 忽略，提示可以归档 |
| `status: done` 但 `Next` 仍有未完成项 | 不默认信任 `status`——`Next` 才是任务是否做完的实际依据。向用户说明这处不一致，由用户决定是接着做完 `Next` 剩余项，还是当作新任务重新登记 |
| `status: done` 但现场有新的未提交改动，且改动就是 `current.md` 自己 | 大概率是「完成任务」流程在 `git add` 之前中断——不要当成新任务，提示用户接着走完剩余的 `git add` / `git mv` / `commit` |
| `status: done` 但现场有新的未提交改动，且改动在其他文件里 | 不要替用户判断这些改动和旧任务的关系——展示 diff，请用户确认是旧任务收尾还是独立新任务，再决定是否走「起第一根任务棒」 |
| `status: done` 且以上任意一种「新改动」情况与「`Next` 未清空」同时成立 | 不要自己判断改动归属——把 `Next` 遗留项和新改动的 diff 一起摆给用户，由用户说明关系，不要只按其中一行处理 |
| `status: draft` | 建棒尚未经人确认——先按「起第一根任务棒」一节的确认步骤处理，用户确认前不要复述、写 `ack`、覆盖 `owner` 或开工 |
| frontmatter 缺字段或小节缺失 | 按现有内容尽力接手，同时往 Open questions 追加一条指出缺了什么 |
| 复述与 Intent 对不上 | 停下来向用户确认，不要开始动手 |
| `owner` 非空且不是你 | 提示「该任务显示由 X 持有」，由用户决定是否抢占。若决定接手，把 `owner` **覆盖**成你自己的标识 —— 不要沿用 |
| 你不确定自己该用哪个标识 | 用你所属 CLI 的名字，四选一。**不要**去任务棒或 git 历史里找答案 |
| 你想援引一条协议规则 | 先在 `AGENTS.md` 或本文件里搜到原文再援引。搜不到就是不存在，不要凭印象立规矩 |
| `current.md` 与代码现状明显不符 | 说明上一棒没交接完（崩溃或遗忘）。走下面的抢救流程 |

## 起第一根任务棒

仓库里还没有 `.agents/tasks/current.md`，要建第一根。

**不需要先判断这是新项目还是老项目。** 下面的取证步骤在全新仓库上会自然返回空——没有未提交
改动、没有分支独有提交、没有项目文档——跑完直接落到最后的提问环节，而那正是新项目本来就该做的
事。**同一套流程，只是产出多寡不同。**

之所以不做新旧之分，是因为判错的代价不对称：把老项目当成新的，agent 会不取证就凭空写任务棒，
人得从头供全部信息，还可能拿到一份看着权威的错 Intent；把新项目当成老的，只是多跑四条 git
命令、五秒、返回空。

真正需要判断的也不是项目新旧，而是「**有没有一件正在做的事，而它不在任何任务棒里**」——
这个问题只有人答得了，所以它在下面的提问环节里。

本节和「抢救」不是一回事：抢救的源头是上一个会话的日志，这里的源头是 git 历史、工作区和**人**。

### 取证：找最近的代码变动

只看一件事——**这个仓库最近被改了什么**。变动藏在三个位置：

```bash
git status --porcelain                       # 未提交改动
git diff --stat                              # 改了哪些文件、改了多少
git log --oneline -20                        # 最近提交
git stash list --date=iso --format='%gd %ai %gs'   # 暂存起来的活
```

**stash 要和其它两处比时间。** 一小时前的 stash 多半就是正在做的事；三个月前的是历史垃圾。
拿它的日期对比最近提交的日期和工作区文件的修改时间，明显更旧就忽略，不要写进任务棒。

不关心改动是谁提交的——只看仓库变成了什么样。

不携带意图的提交（merge、format/lint、依赖升级、版本号 bump、`chore:` 收尾）**视同没捞到**：
它们是最近的，但不说明在做什么。

空仓库上 `git log` 会以 `fatal: your current branch 'main' does not have any commits yet`
退出，这是正常的，不是出错。

### 捞不到就问，不要推测

三个位置都没有有意义的代码变动时，**不要试图从项目结构或文档推测一个 Intent**——
一个看着合理的错 Intent 比没有任务棒更危险。

直接告诉人：「我没在最近的代码变动里发现进行中的工作，请说明现在要做什么。」
然后走下面的提问环节。事情可能确实没有，也可能是调研、评审、排查这类不产生代码改动的活——
两种情况的处理是一样的，都由人来补充，不需要区分。

### 捞到多件不相关的事时，让人选

工作区改的是 A、分支上的提交是 B，这种情况下**不要合并成一个 Intent**——合并出来的会同时
不满足两件事。把发现的几件事列给人，问「现在要做哪件」，其余的不写进这根棒。

其余那几件事的去处是**各起一条分支**：任务棒随分支走，每条分支自己的 `current.md`，互不干扰。
合并回主干前必须先归档（`current.md` 已 `git mv` 进 `archive/`），否则第二条分支合并时会撞上
`CONFLICT (add/add)`。因此**主干上不应存在 `current.md`**。

### `Constraints` 另有来源

`Constraints` 不来自最近的变动，来自**项目自己的规则文件**——目标仓库的 `AGENTS.md`、`CLAUDE.md`
及其引用的文档。那里写着这个项目长期有效的硬约束，照抄进来即可，不需要推测。

### 硬规则：`Intent` 和 `Do not` 必须由人确认

git 只能告诉你**做了什么**，`Intent` 问的是**要达成什么**——两者不等价。从提交历史反推出来的
Intent 看起来很权威，一旦偏了，比没有任务棒更危险：接棒者会朝错误方向全速前进。
`Do not`（拒收标准）在 git 里更是零痕迹。

所以取完证之后**必须向人提这三个问题**：

1. 这件事要达成什么？（一句话，不要背景）
2. 哪些已经做完了、哪些还没有？
3. 有什么是绝对不能碰的？

拿到回答再改写 `Intent` / `Done` / `Next` / `Do not`。

### 格式硬要求（最容易踩的四条）

- **`task` 必须是 `t-<YYYY-MM-DD>-<短名>`**，短名用小写英文加连字符。它是账本的检索键，
  `tools/ledger.sh` 靠 `git log --grep "Task-Id: <id>"` 过滤——带空格或中文会让整根棒查不出来。
  **不要把任务描述写进 id**，描述是 `Intent` 的活。
  正确：`t-2026-08-27-deep-research-next`；错误：`"确认 Deep Research 后续任务"`。
- **`Done` 只填已经完成的工作**，每项附产物路径。「工作区无未提交改动」「当前分支是 X」
  这类是**取证结果**不是完成项，该进 `Decisions` 或直接丢掉。
- **`updated` 用完整 ISO8601 带时区偏移**（`2026-08-27T15:30:00+08:00`）。
  只写日期的话，同一天多次交接就分不出先后。
- **`hop` 在 draft 期间填 `0`**，表示尚未被任何人接过；转 `in_progress` 时置 `1`。

### 落盘

**先起分支，再落盘。** 任务棒只活在任务分支上：

    git checkout -b <任务分支名>

主干上不应存在 `current.md`——它一旦落到主干，第二个任务就无处安放，而且合并时会撞上
`CONFLICT (add/add)`。规则见「完成任务」一节。

草稿**直接写进 `.agents/tasks/current.md`**，但：

- `status` 填 `draft`，不是 `in_progress`
- `owner` 与 `ack` 留空——这是建棒，不是接棒
- **Open questions 必须记一条**：`- 本棒由 git 历史建立，Done 可能不全，Intent 待确认`

写成文件而不是只在对话里给人看：对话输出会丢，文件不会；`status: draft` 本身就是「未经确认」
的信号——接棒者读到 draft 状态应当先向人确认，而不是直接开工。

人确认之后把 `status` 改成 `in_progress`，删掉那条 Open question。

## 抢救：上一棒没留交接

任务棒缺失或明显陈旧时，上一段工作只存在于那个会话的历史里。

**这条路径要读仓库之外的数据，动手前必须先问。** 会话历史里可能有与本任务无关的东西——别的项目、
凭据、私人对话——而任务棒会被提交进 git 历史，写进去就跟着仓库走，事后难以抹除。

1. 先告诉用户你打算读哪个会话文件、用什么工具读，**取得明确同意再读**。用户不同意就停在这里，
   改走「起第一根任务棒」直接问人，不要碰 session 文件。
2. 用现成的 session 读取工具（如 `catchup`、`cli-continues`）导出对话。
3. **整理成任务棒格式**——只提取 Intent / 已完成 / 待办 / 做过的判断，不要整段粘贴，
   与本仓库无关的内容一律不带入。
4. 把整理结果给用户过目，**经确认后**再写入 `.agents/tasks/current.md`。
5. 在 Open questions 记一条「本棒由会话历史抢救重建，可能有遗漏」。
6. 回到正常接棒流程。

本仓库**不实现** session 文件解析：四家格式各异且随版本变动，而这只是灾后路径，不是主路径。
