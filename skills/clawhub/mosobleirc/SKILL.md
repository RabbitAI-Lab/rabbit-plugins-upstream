# МосОблЕИРЦ

Это консервативный workflow для настроенных объектов и водосчётчиков.
OpenClaw ведёт диалог, Gemini используется только как vision/extraction,
детерминированный Python решает правила, настроенный transport выполняет запросы,
а МосОблЕИРЦ остаётся source of truth.

Никогда не вызывай МосОблЕИРЦ напрямую из shell, Python, браузера или произвольного HTTP.
Работай только через `{baseDir}/scripts/mosobleirc.py` и transport, настроенный во внешнем runtime-конфиге; допустимы configured direct helper и private Yandex relay. Direct внутри helper разрешён; bypass HTTP запрещён.
Не обходи helper ради удобства и не делай функцию public.

## Локальный статус

```bash
python3 {baseDir}/scripts/mosobleirc.py status
```

`status` полностью локальный: `provider_contacted=false`.
Не используй live-команды для health-check, фонового мониторинга или проверки токена.
Не создавай cron для портала.

## Фото без текста и локальная маршрутизация

Фото без текста сначала обрабатывай как обычное изображение. Не считай любое фото запросом к МосОблЕИРЦ.
Если на фото не водосчётчик — веди себя как при обычной работе с фото и не запускай этот workflow дальше.
Если это водосчётчик, сначала прочитай на фото именно напечатанный заводской/серийный номер прибора. Не используй показание, бренд, количество фотографий, список missing/pending references или визуальное сходство с reference как доказательство квартиры.

Прочитанный serial обязательно проверь локально:
```bash
python3 {baseDir}/scripts/mosobleirc.py local identify --serial <serial>
```
Только статус MATCHED однозначно определяет meter_id, квартиру и адрес. Если serial не читается или identify вернул REVIEW — не угадывай квартиру; коротко попроси владельца указать квартиру/прибор. Явная привязка владельца к конкретному прибору также допустима. К МосОблЕИРЦ на этом этапе не обращайся.

После однозначной привязки читай табло прямо в текущем turn основной мультимодальной моделью. Не запускай вложенные OpenClaw agent, headless-agent, openclaw agent, sessions_spawn или отдельные vision-сессии ради OCR.

Передавай в детерминированный helper именно группы цифр с табло, сохраняя ведущие нули и физическую границу между чёрными целыми и красными дробными цифрами. Команда: python3 {baseDir}/scripts/deep_read.py --meter-id <id> --black-digits <digits> --red-digits <digits> [--ambiguous].

Не передавай helper готовое десятичное число: запятую ставит Python по профилю конкретного счётчика. Например 00008 + 611 всегда означает 8.611, а не 86.11.

Если читаешь табло уверенно, не делай второй model-pass. Если сомневаешься хотя бы в одной цифре, добавь --ambiguous; helper вернёт REVIEW, и ты человеческим языком попросишь владельца подтвердить или исправить конкретное показание. Не запускай автоматические повторные OCR-pass, locator/crop recovery и не проси пользователя перекалибровывать layout/reference.

GREEN означает, что значение можно использовать для локального local analyze. REVIEW — нормальный диалоговый исход: покажи предполагаемое значение и последнее подтверждённое значение, затем попроси владельца подтвердить или исправить. Подтверждение значения при REVIEW уточняет только OCR и не является разрешением обращаться в МосОблЕИРЦ. После подтверждения сделай локальный анализ расхода и отдельно спроси, отправлять ли показание.

Сам факт получения фото или подтверждения OCR не является согласием на live-read или отправку. До VERIFIED ничего из нового фото не сохраняй в readings/provider_history и не обновляй last-provider snapshot. Candidate живёт только в текущем turn/операции.

Если у одного объекта несколько счётчиков, расход и статистику считай по каждому прибору отдельно.
Не суммируй разные приборы для проверки нормы: у них могут быть разные профили потребления.

Локальные команды не обращаются к провайдеру:
```bash
python3 {baseDir}/scripts/mosobleirc.py local analyze --meter-id <id> --value <value> --observed-at <iso-date>
python3 {baseDir}/scripts/mosobleirc.py local history --meter-id <id>
```

## Эталонные фотографии

Эталоны не участвуют в выборе квартиры. `reference pending` показывает только техническую полноту базы и никогда не является подсказкой, к какой квартире относятся новые фото.

Сохраняй reference только когда связь фото ↔ конкретный прибор уже доказана точным serial либо владелец явно подтвердил эту связь. Автоматически заполнять отсутствующие references входящими фото запрещено.

При совпавшем serial:
```bash
python3 {baseDir}/scripts/mosobleirc.py reference add <meter_id> "<AttachmentPath>" --observed-serial <serial>
```
При явной ручной привязке владельцем, когда serial не читается:
```bash
python3 {baseDir}/scripts/mosobleirc.py reference add <meter_id> "<AttachmentPath>" --confirmed-by-user
```
Без одного из этих доказательств CLI обязан отказать.

Reference images хранятся отдельно от skill в `~/.local/share/mosobleirc/reference-images/`.
`meter.db` и вся изменяемая история также находятся в `~/.local/share/mosobleirc`.
Обновление skill не должно удалять или заменять эти данные.

## Распознавание и проверка

Основная модель ассистента сама видит фотографию в текущем turn. Не создавай отдельную модельную сессию для чтения того же изображения. Python helper не вызывает Gemini и не имеет сетевого OCR: он только проверяет группы цифр, восстанавливает десятичную границу по профилю прибора и сравнивает целую часть с последним подтверждённым значением.

Для OCR действуют два пользовательских состояния:
- GREEN: табло прочитано уверенно и локальные физические проверки не обнаружили противоречия;
- REVIEW: сомнение в цифре, неправильная длина группы, уменьшение относительно последнего подтверждённого значения или подозрительно большой скачок. Покажи владельцу понятное предполагаемое значение и попроси владельца подтвердить или исправить.

Не показывай владельцу внутренние коды vision_ambiguous, digit_layout_mismatch и т.п., если он сам не попросил диагностику. Жёсткие блокировки остаются внутри `send readings`: подтверждённое значение не может быть меньше актуального ЕИРЦ, запись запрещена вне окна/при уже переданном периоде, а POST считается успешным только после совпадающего read-back.

Первые 2–3 месяца каждое распознанное значение требует подтверждения пользователя,
даже если validator вернул GREEN. Только после накопления успешной истории на конкретном счётчике
можно отдельно проектировать auto-submit.

## Передача показаний через настроенный transport

Не обращайся в МосОблЕИРЦ при получении или анализе фотографии. После того как ты показал владельцу распознанные значения и он одним отдельным сообщением явно сказал «отправляй»/«передавай», этого одного подтверждения достаточно для write-flow.

Выполни одну команду для всех подтверждённых приборов:
```bash
python3 {baseDir}/scripts/mosobleirc.py send readings \
  --reading <meter_id>:<whole>:<full-reading> \
  [--reading <meter_id>:<whole>:<full-reading> ...] \
  --observed-at <iso-date> --confirmed-by-user
```

В `--reading` второе число — целое значение, которое реально уйдёт в ЕИРЦ, третье — физический photo reading с фотографии. В обычном случае `<whole>` равен целой части `<full-reading>`. При явном ручном override владельца меняй только второе число и не заменяй photo reading: например, если на фото `615.302`, а владелец велел передать `616`, используй `<meter_id>:616:615.302`.

В итоговом ответе различай «на фото» и «передано в ЕИРЦ». Дробная часть у этих счётчиков вспомогательная и провайдер хранит целое значение; расход/дельту ЕИРЦ считай по реально переданному целому значению. Полный photo reading сохраняется локально отдельно.

Не создавай и не выбирай `operation_id`, не вызывай `send prepare`, `send execute` или `send reconcile` вручную. Команда `send readings` сама последовательно выполняет допустимый следующий шаг для каждого прибора: свежий read-only GET, проверку окна/монотонности/уже переданного периода, максимум один POST и обязательный read-back. Если обнаружена старая неопределённая операция, helper сначала сверяет её с провайдером. При достаточном proof она становится `VERIFIED`; если результат по-прежнему неоднозначен, она остаётся `UNCERTAIN_NO_RETRY` и новый POST блокируется. Слепого повторного POST нет.

`UNCERTAIN_NO_RETRY` нельзя автоматически превращать в `NOT_APPLIED` только по одному отрицательному GET: у провайдера возможна eventual consistency. Если после повторной проверки значение так и не появилось, попроси владельца самостоятельно проверить личный кабинет МосОблЕИРЦ. Только после его отдельного явного подтверждения, что показание отсутствует, допускается операторская recovery-команда `send resolve-not-applied --operation-id <id> --confirmed-not-applied-by-user`. Она делает ещё один fresh read-only GET и никогда не выполняет POST. Если provider уже доказывает исходную запись, операция принудительно закрывается как `VERIFIED`; при `WAITING`/`ACCEPTED`, занятом текущем периоде, сетевой ошибке или неоднозначном ответе manual resolution запрещён. Для нового счётчика отсутствие `lastValue` допустимо только вместе с явным `isValueSentForCurrentPeriod=false` и отдельным подтверждением владельца; пустой/сломанный `lastValue` считается неоднозначным. После подтверждённого `NOT_APPLIED` новая отправка выполняется отдельной обычной командой `send readings` с новым `operation_id` и новым preflight.

Для нескольких приборов передавай все значения одной командой. Helper работает последовательно, concurrency=1, и возвращает одну сводку по каждому прибору: `VERIFIED`, `ALREADY_SENT`, `BLOCKED`, `UNCERTAIN_NO_RETRY` или ошибка доступа. Если один прибор уже принят с тем же значением, повторный POST не выполняется. Если значение уменьшилось, окно закрыто или провайдер запрещает запись, блокируется только этот прибор.

Получение фото и подтверждение OCR никогда не дают согласия на POST. До явного «отправляй» live-read и write запрещены. Только VERIFIED/VERIFIED_AFTER_UNCERTAIN_RESPONSE с совпадающим read-back позволяет сохранить photo reading, provider history и новый last-provider snapshot. Не делай дополнительный GET после relay read-back.

401/403 означает `AUTH_REQUIRED`: не повторяй запрос и не запускай SMS/login/refresh без реального `AUTH_REQUIRED`. Timeout/5xx не означает, что POST нужно повторить: helper возвращает фактический статус и останавливается без слепого retry. Не запрашивай YANDEX_API_KEY или provider token через secrets tool. Не открывай gateway config, не исследуй proxy/egress и не делай direct HTTP при обычной передаче. При relay network error остановись на фактическом результате helper и не придумывай обходной сценарий или будущую проверку. Если helper уже вернул частичные результаты по нескольким приборам, перечисли их по каждому прибору; не утверждай, что «состояние не изменилось», если часть операций уже VERIFIED/ALREADY_SENT.

Никогда не вызывай relay `submit` напрямую и не делай обходной HTTP-вызов.
Не печатай Yandex API key, `MOSOBLEIRC_TOKEN`, Authorization headers и содержимое secret-файлов.
