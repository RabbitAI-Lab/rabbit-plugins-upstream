# 投递记录 & 面试复盘方法论

## 核心逻辑

不做定时提醒，只做记录和查询。用户问到「上次那个面试面了什么」时能查到。

## 记录内容

每次用户说「投了 XX 公司」或「面了 XX 公司」，记录以下信息：

### 投递记录

| 字段 | 说明 | 必填 |
|------|------|------|
| 公司全称 | | ✅ |
| 岗位名称 | | ✅ |
| JD 原文 | 或链接 | 可选 |
| 投递时间 | | ✅ |
| 投递渠道 | 官网/内推/猎头/Boss | ✅ |
| 面试结果预期时间 | 用户说的「大概 X 天通知」 | 可选 |
| 状态 | 待面试 / 已面试 / 已拒 / 已过 / 已 offer | ✅ |

### 面试记录

| 字段 | 说明 | 必填 |
|------|------|------|
| 面试时间 | | ✅ |
| 面试类型 | 一面/二面/终面 | ✅ |
| 面试官风格 | 技术导向 / 业务导向 / 压力面 | 可选 |
| 答得好的点 | 用户自评 | 可选 |
| 答得不好的点 | 用户自评 + Javis 评估 | 可选 |
| 核心教训 | 这次面试最重要的收获是什么 | ✅ |
| 行动项 | 下次面试前需要补什么 | ✅ |

## 输出格式

投递 + 面试信息合并存储，一条投递可关联多条面试记录。

```
## 投递日志

### 1. XX公司 — YY岗位 — 2026-07-12投递 — 【已面】
- 渠道：Boss 直聘
- 预期通知：3 天内

#### 一面 | 2026-07-15
- 面试官：技术负责人，喜欢追问底层原理
- 答得好：数据治理经验较扎实
- 答不好：对行业理解偏浅，容易被问住
- 教训：行业知识需要提前做功课
- 行动项：花 2 天时间补充行业基础知识

#### 二面 | 2026-07-20
- 面试官：业务负责人，更关注实际产出
- 答得好：项目贡献度清晰
- 答不好：薪资期望表述不够清楚
- 教训：准备好期望薪资的逻辑
- 行动项：梳理市场行情和自己的底线

### 2. ZZ公司 — XX岗位 — 2026-07-13投递 — 【待面试】
- 渠道：内推
- 预期通知：一周内
```

## 查询场景

用户可能的提问：
- 「帮我看看我投了哪些公司」→ 列出所有投递，标注状态
- 「上次 XX 公司的面试说了什么」→ 查对应面试记录
- 「这次面试有什么要注意的」→ 查最后一次面试的教训 + 行动项
- 「我最近面了哪几家」→ 按时间倒序列出最近面试

## 不做的事

- ❌ 不主动发消息提醒「该跟进 XX 公司的面试结果了」
- ❌ 不分析投递转化率、响应率等统计
- ❌ 不给用户排面试优先级

## 存储方式

投递日志存储在用户会话上下文中，格式为扁平 Markdown。

如果 Agent 框架支持持久化存储，可考虑写入独立的文档：
- 每次新增记录时追加到文档尾部
- 用户查询时读取整个文档
- 不修改历史记录（除非用户要求修改状态）
