# فرایند انجام‌کار توسط ایجنت و قرارداد اسکریپت — powpow-register

جزئیات اجرای هر گام SKILL.md. همه فرمان‌ها به قالب `node scripts/powpow-register.mjs <زیرفرمان> [آرگومان‌ها]` هستند، اسکریپت **بدون وابستگی** است، به **Node ≥ 18** نیاز دارد و همه درخواست‌ها فقط به `https://global.powpow.online` می‌روند.

## طراحی امنیتی (چرا این‌طور طراحی شده)

| طراحی | دلیل |
|---|---|
| رمز عبور فقط از متغیر محیطی `POWPOW_REGISTER_PASSWORD` وارد می‌شود | آرگومان‌های خط فرمان پروسه برای دیگر پروسه‌های همان ماشین قابل مشاهده‌اند (سطح نشت argv)، متغیر محیطی را اسکریپت می‌خواند و همان لحظه استفاده می‌کند |
| رمز عبور **هرگز در فایل وضعیت نوشته نمی‌شود**، در لاگ‌ها هم نمی‌آید | فایل وضعیت ممکن است روی دیسک بماند؛ نمایش یک‌باره در حالت تولیدِ داخل گفتگو برای ذخیره‌کردن توسط کاربر است |
| فایل وضعیت در پوشه موقت سیستم (`os.tmpdir()/powpow-register-state.json`, 0600) | فقط پنج فیلد دارد: email / username / nickname / token / outTradeNo، با `cleanup` با یک فرمان پاک می‌شود |
| JWT ایجنت از طریق نقطه پایانی رسمی `me?token=` به کوکی مرورگر تبدیل می‌شود | پل رسمی پلتفرم برای WebView هارمونی است؛ راستی‌آزمایی فقط امضا + مدت اعتبار را می‌گیرد، به اثر انگشت دستگاه وصل نمی‌شود، در مرورگر کاربر کار می‌کند |
| پرداخت فقط create-order / query / باز کردن صفحه پرداخت | کنش پرداخت و اعتبارنامه‌های پرداخت همیشه بین کاربر و صفحه پرداخت رسمی علی‌پی می‌مانند، از دست ایجنت نمی‌گذرند |

## مرجع فرمان‌ها

| فرمان | آرگومان‌های کلیدی | کار / زمان |
|---|---|---|
| `status` | —— | دیدن پیشرفت فرایند (خواندن فایل وضعیت)؛ بعد از قطع شدن گفتگو اول این را اجرا کنید |
| `gen-password` | —— | ساخت رمز عبور قوی ۲۴ نویسه‌ای (با حروف بزرگ+کوچک+اعداد)، روی stdout **فقط همین یک بار** نشان می‌دهد |
| `prepare-suggest` | `--username --nickname --email` | ثبت اطلاعات تأییدشده در فایل وضعیت (بعداً در register لازم نیست دوباره داده شود) |
| `send-code` | `--email` | تریگر کردن پلتفرم برای فرستادن کد تأیید ۶ رقمی (۱۰ دقیقه اعتبار، فاصله 60s) |
| `register` | `--code` (اجباری)؛ `--username --nickname --avatar --phone` (اختیاری، اگر در فایل وضعیت باشد لازم نیست داده شود) | ساخت اکانت pending؛ رمز عبور از متغیر محیطی `POWPOW_REGISTER_PASSWORD`؛ بعد از موفقیت JWT خودکار در فایل وضعیت ذخیره می‌شود |
| `login-link` | `--target pending` یا `--target home` | تولید لینک لاگین یک‌کلیکی (طراحی لینک دوگانه، پایین را ببینید) |
| `create-order` | `--package monthly\|quarterly\|yearly` | ساخت سفارش علی‌پی؛ مسیر فایل صفحه پرداخت + outTradeNo را برمی‌گرداند (خودکار در فایل وضعیت ثبت می‌شود) |
| `query` | —— | بررسی وضعیت سفارش `paid / pending / closed / unknown` (outTradeNo از فایل وضعیت)، پولینگ هر ۱۰ تا ۱۵ ثانیه |
| `refresh-login` | رمز عبور از متغیر محیطی | ورود مجدد برای گرفتن **JWT جدید** (ادعای اشتراک از NONE به ACTIVE)، بعد از رسیدن پرداخت حتماً اجرا شود |
| `whoami` | —— | بررسی وضعیت اکانت و اشتراک با token فایل وضعیت (بررسی مؤثر بودن فعال‌سازی) |
| `cleanup` | —— | حذف فایل وضعیت (در پایان حتماً اجرا شود) |

**ارسال از طریق متغیر محیطی** (رمز عبور هرگز به خط فرمان نمی‌رود):

```bash
# bash / zsh / WSL
POWPOW_REGISTER_PASSWORD='<رمز عبور>' node scripts/powpow-register.mjs register --code 123456
# PowerShell
$env:POWPOW_REGISTER_PASSWORD = '<رمز عبور>'; node scripts/powpow-register.mjs register --code 123456
# cmd
set POWPOW_REGISTER_PASSWORD=<رمز عبور> && node scripts/powpow-register.mjs register --code 123456
```

## سازوکار لینک دوگانه (طراحی اصلی)

وضعیت لاگین پلتفرم کوکی HttpOnly است، ایجنت نمی‌تواند مستقیم برای مرورگر کوکی بکارد؛ پل، نقطه پایانی رسمی
`/api/auth/me?token=<JWT>&redirect=<مسیر داخل سایت>` است: راستی‌آزمایی → ساخت خودکار نشست برای کاربر pending →
`Set-Cookie: powpow_token` (HttpOnly / SameSite=Lax / ۷ روز) → بررسی redirect (فقط شروع با یک اسلش، `//` و بک‌اسلش ممنوع،
بعد از تجزیه باید هم‌مبدأ باشد) → تغییر مسیر موقت 307 به صفحه هدف.

- **لینک ۱ (بلافاصله بعد از موفقیت ثبت‌نام بدهید)**: `--target pending` → فرود روی `/subscription`.
  مرورگر کاربر وارد وضعیت «نیمه‌لاگین» می‌شود: صفحه اشتراک و صفحه بازگشت علی‌پی دیده و قابل کار می‌شوند؛ صفحات محتوا هنوز توسط دیوار پرداخت
  به صفحه اشتراک برمی‌گردند (سه لایه محافظت: بررسی claims در JWT توسط دروازه → بررسی مجدد DB → بررسی API اصلی، رفتار عادی است).
- **لینک ۲ (بعد از تأیید paid بدهید)**: اول با `refresh-login` یک JWT جدید بگیرید (پرداخت فقط DB را به‌روز می‌کند، claims مربوط به
  JWT صادرشده قبلی را عوض نمی‌کند؛ اگر جدید نگرفته نشود «پرداخت کرده ولی عضویت ندارد» نشان می‌دهد)، بعد `--target home` → فرود روی صفحه اصلی،
  با وضعیت کامل عضویت.

## ترتیب کامل (مسیر عادی)

```
1.  status                          # خودآزمایی محیط
2.  (در گام ۲ تأیید اطلاعات در گفتگو، رمز عبور یکی از دو حالت؛ حالت تولید: gen-password → کاربر فوراً ذخیره کند)
3.  prepare-suggest --username U --nickname N --email E
4.  send-code --email E             # → کاربر به ایمیل برود و کد را ببیند (تنها بخش خروج از گفتگو ①)
5.  POWPOW_REGISTER_PASSWORD=*** register --code 123456 [--avatar pic.jpg]
6.  login-link --target pending     # → لینک ۱ برای کاربر فرستاده شود
7.  (کاربر بسته را انتخاب کند) create-order --package monthly
8.  start <فایل صفحه پرداخت>         # Windows؛ در macOS از open، در Linux از xdg-open
    # → کاربر در صفحه پرداخت علی‌پی پرداخت می‌کند (بخش خروج از گفتگو ②)
9.  query (هر ۱۰ تا ۱۵ ثانیه) تا paid
10. refresh-login                   # JWT جدید با ادعای ACTIVE
11. login-link --target home        # → لینک ۲ برای کاربر فرستاده شود
12. whoami                          # تأیید subscriptionStatus: ACTIVE (اختیاری)
13. cleanup                         # پاک‌سازی فایل وضعیت
```

## نگاشت فرمان → API پلتفرم

| فرمان اسکریپت | نقطه پایانی پلتفرم |
|---|---|
| `send-code` | `POST /api/auth/register/send-code` |
| `register` | `POST /api/auth/register` (multipart، آپلود مستقیم عکس پروفایل) |
| `login-link` | `GET /api/auth/me?token=…&redirect=…` (خودِ لینک؛ با کلیک در مرورگر اثر می‌کند) |
| `create-order` | `POST /api/payment/alipay/create-order` (Bearer) |
| `query` | `GET /api/payment/alipay/query?outTradeNo=…` (Bearer) |
| `refresh-login` | `POST /api/auth/login` (`{step:1, username, password}`) |
| `whoami` | `GET /api/auth/me?token=…` |

منبع قوانین: فیلدها و محدودیت‌های ثبت‌نام در `registration-flow.md`؛ بسته‌ها و زنجیره فعال‌سازی در
`payment-and-activation.md` (هر دو با ذکر فایل سورس پلتفرم).

## رسیدگی به خطاهای سطح اسکریپت

| نشانه | چه کنیم |
|---|---|
| `Node 版本过低` (نسخه Node خیلی قدیمی) | به حالت راهنمای خالص برگردید، به‌زور امتحان نکنید |
| خطای شبکه / پایان زمان انتظار | یک بار دوباره امتحان کنید؛ باز هم ناموفق بود از کاربر بخواهید شبکه‌اش را چک کند و ادامه دهید (فایل وضعیت هست، اجرای `status` از اول بازیابی می‌کند) |
| خطای بیزینسی register (用户名已存在 و غیره) | طبق جدول گام ۵ در SKILL.md رسیدگی کنید، **کد تأیید دوباره فرستاده نشود** (تا ۱۰ دقیقه هنوز معتبر است) |
| register با「邮箱验证码错误或已过期」 (کد تأیید ایمیل اشتباه یا منقضی) | پایان زمان → دوباره `send-code` |
| بعد از `create-order` کاربر صفحه پرداخت را بست | مستقیم دوباره `create-order` (سفارش قبلی تا 2h خودکار بسته می‌شود) |
| `query` مدام pending | احتمالاً کاربر پرداخت نکرده؛ یک بار بپرسید. واقعاً پرداخت کرده → طبق جدول عیب‌یابی payment-and-activation.md بروید |
| `refresh-login` با 403 `pending_payment` | پول هنوز نرسیده، به گام ۹ برگردید و پولینگ را ادامه دهید |
| گم شدن فایل وضعیت (اشتباهی حذف شد / ماشین عوض شد) | `whoami`/`refresh-login` کار نمی‌کنند؛ از کاربر بخواهید در همان مرورگری که لینک ۱ را باز کرده بود صفحه اشتراک را رفرش کند و وضعیت را ببیند، یا دوباره لاگین کند (حالت وب) |

## حالت جایگزین (راهنمای خالص)

در هر یک از موارد زیر فوراً به راهنمای خالصِ سبک v1 برگردید و دیگر با اسکریپت کلنجار نروید:

- Node ≥ 18 نباشد یا اسکریپت دو بار پشت‌سرهم شکست هم‌نوع بدهد؛
- کاربر صریح بگوید «خودم در وب انجام می‌دهم»؛
- سیاست شرکت/دستگاه شبکه اسکریپت را محدود کند.

بعد از برگشت: صفحه ثبت‌نام https://global.powpow.online/register و صفحه اشتراک
https://global.powpow.online/subscription را بدهید، طبق قوانین `registration-flow.md` همراه کاربر پیش بروید،
لحن همان می‌ماند و هر نوبت باز هم با بلوک «قدم بعدی» جمع‌بندی می‌شود.
