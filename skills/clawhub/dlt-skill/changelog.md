## 随机性检验灵敏度升级（2026-08-08，NIST SP 800-22）

**新增密码学级随机性检验模块 `dlt_nist_sts.py`，作为既有卡方电池的"位级"灵敏度压力测试。**

用户要求"全网搜集信息和技能，对大乐透四体系统进行升级"。调研 NIST SP 800-22（密码学级随机性测试套件）后，新增本模块，从"位级"进一步探测极微弱非随机结构（连号机 / 伪随机生成器瑕疵），强化项目诚实框架（no_edge / 无可利用模式）。

- **新增 `dlt_nist_sts.py`**：纯标准库实现（无 numpy/scipy），含 6 项检验——
  Monobit / Block Frequency / Runs / Longest Run / Discrete Fourier(Spectral) / Approximate Entropy。
  自实现 radix-2 迭代 FFT（零填充到 2 的幂）与正则化不完全 Gamma Q(a,x)（级数+连分式，Numerical Recipes）。
- **编码方案（关键）**：每球取 1 个奇偶比特，先全部前区后全部后区（扁平化），去除"每期 5+2=7 位帧"的 1/7 频谱假象与"一球多位"同球依赖假象。
- **诚实定位（防误读）**：NIST 为 i.i.d. Bernoulli(0.5) RNG 校准。彩票号码不是位流，其二进制展开天然携带两项"非随机"特征——
  (1) 号码轻微频率非均匀（χ² 已量化 KNOWN_BIAS）；(2) 位编码固有特性（前区奇偶边际≈0.514 / 无放回抽样 / 前-后区阶跃）。
  因此个别项"未通过"是**预期且良性**，与"均匀随机开奖穿过同一编码也会同样未通过"对照一致 → 证明是编码/偏差假象，非开奖机缺陷。
- **实质结论（2906 期 → 20342 位）**：2 项 PASS / 3 项 KNOWN_BIAS / 1 项 N/A（Runs 因 1 比例略偏离 0.5 按 NIST 预处理条件不适用）/ **0 项 ANOMALY**。
  完整性闸门：位流 1 比例 0.5165 ∈ [0.45,0.57] ✅ 且 0 ANOMALY ✅ → 数据源一致，无可利用结构。
- **自检（self_test）**：用 `random.getrandbits` 生成真随机 i.i.d. 位流，验证 FFT 与朴素 DFT 一致、各检验通过率 0.992（落入 NIST 推荐置信区间 [0.90,1.06]），证明算法实现正确。
- **集成**：`dlt_randomness_test.py` 的 `randomness_battery()` 末尾新增"密码学级随机性(NIST SP 800-22)"一节（非硬闸门；NIST 个别项"未通过"已被证明是编码/偏差假象，不纳入硬闸门）。`dlt_healthcheck_all.py` 第 17 项描述同步更新。
- **文档**：`references/methodology.md` 新增 §4.5（NIST 灵敏度升级），并把全文"2904 期"更新为当前"2906 期"。
- **验证**：`build_dist.py --full` 四体重建 + 22 项护栏体检 **22/22 全绿**；包内 0 SkillHub 违禁词；根↔SKILL 数据与产物一致。

## 2.1.24（2026-08-05）

**护栏并行化加速：串行 155s → 并行 56s（加速 2.75 倍）。**

v2.1.23 修复了排程超时问题后，用户反馈"运行有点慢、等待有点久"。分析发现护栏 22 项检查
中有 10 个重型子进程（交叉验证/ECI回测/方法发现/随机性检验/未定义名/5套反诈骗）**串行执行**，
合计占护栏总耗时 ~80%。

**优化方案**：在 `main()` 开头用 `subprocess.Popen` 一次性预启动全部 10 个重型脚本，让它们
在后台并行执行；各检查函数到点只需等自己的那个完成（`_wait_prelaunched()`）。由于这些是
独立子进程（非线程），可真正利用多核并行。

**效果**：
- 普通会话：155s → 56s（2.75 倍加速）
- SYSTEM 语境（预估）：600s → ~150s（3-4 倍加速）
- 22/22 全绿不变，RC=0

**设计要点**：
- 预启动失败不阻断（后续 check 函数会自己 `subprocess.run` 兜底）
- `_wait_prelaunched()` 返回与 `subprocess.run` 兼容的结果对象（returncode/stdout/stderr）
- 超时处理：`communicate(timeout=...)` 超时则 `kill()` + `wait()`
- 输出顺序不变：重型脚本并行跑，但结果按原有顺序处理
