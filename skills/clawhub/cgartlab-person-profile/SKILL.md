# Person Profile / 人物档案

一个独立的、通用的、可脱离特定知识库使用的**人物档案 skill**。

用于 AI agent 结构化地创建、维护、验证人物档案。核心承诺：**每条事实可核验、每条判断可反驳、每份档案可自我证伪**。

## When to Use

**触发场景**：
- 老板要新增人物档案到某个知识库
- 老板要"统一档案格式"、"对齐模板"、"所有档案检查一下"
- 老板要补齐档案之间的关系网络双向链
- 老板说"同规格呈现"、"高质量"、"事实核查"

**不用于**：
- 单个档案的搜索与证据分级（本 skill 聚焦建档流程，不处理搜索本身）
- 长段落论述字段的写作（用 `quill`）
- 概念去重与合并（本 skill 只处理人物档案）
- 公司 / 产品 / 技术档案（本 skill 只处理人物）

---

## 前置依赖

- **模板**：`templates/person-archive.md`（11 节完整模板，本 skill 内置）
- **方法论**：`references/` 下有 8 份深度方法论（按需加载）
- **校验脚本**：`scripts/` 下 5 份 Python 脚本（可直接运行）
- **标杆样本**：`benchmarks/` 下 3 份高质量档案作为质量锚点

> **模板与校验器的关系**：`templates/person-archive.md` 是 11 节完整骨架，每节带 HTML 注释说明（落盘前删除）；`templates/person-archive-lite.md` 是 6 节精简子集，用于快速建档；`templates/person-fragment.md` 提供补链 / 补章节的单节片段。三者都是**起点模板**，不要求自身通过 `validate_library.py` 全量校验（精简版缺章节属预期）。校验器以 `tests/fixtures/` 为 CI 基准（正例必须通过、反例必须被检出），不是以模板为基准。

**知识库路径参数**：`--library-root` 参数指定档案库根目录。默认当前工作目录。

## 知识库集成（Obsidian / PARA）

本 skill 默认对接 `cgartlab-obsidian` 知识库，也可替换 frontmatter 规范用于其他环境。

| 项目 | 默认值 |
|---|---|
| 档案目录 | `03-资源/人物/` |
| 索引文件 | `03-资源/人物/人物-README.md` |
| frontmatter type | `reference` |
| frontmatter tags | `资源/人物` |
| 必填字段 | `title`、`type`、`description`、`tags`、`created`、`updated` |
| 知识库校验 | `node scripts/check-frontmatter.mjs`（管 type / tags / 日期） |
| skill 校验 | `python scripts/validate_archive.py`（管 11 节 + 写作纪律） |

**两套校验分工**：
- 知识库自带 `check-frontmatter.mjs` 校验 `type` 是否在允许枚举、`tags` 前缀是否为 `资源/`、`created/updated` 是否为合法日期。它**不检查章节结构**。
- 本 skill 的 `validate_archive.py` 校验 11 节齐全、顺序、标题级别、禁词、破折号、`author: ChatGPT` 残留。它**不重复校验 type/tags**。
- 两者都要通过，档案才算完工。

**读写方式**：
- 读取现有档案：`obsidian read path="03-资源/人物/某人.md"` 或直接读文件。
- 新建档案：先落盘到 `03-资源/人物/`，再跑两套校验。
- 补链：直接在对方档案的「关系网络」章节追加，格式见 `templates/person-fragment.md`。

**若用于非 Obsidian 环境**：把 frontmatter 的 `type` / `tags` 改为目标系统约定值，或直接删除；校验时用默认的 `--profile generic`（不强制 frontmatter 字段），其余 11 节结构与写作纪律不变。档案文件可放在任意普通文件夹，脚本从任何工作目录用绝对路径调用均可。

## 核心工作流（7 步）

```
[1] 立项澄清   → 必答 3 问，不澄清不开工
[2] 前置研究   → 委派 3-5 路并行搜索
[3] 起草       → 严格按模板 11 节 + 写作纪律
[4] 补双向链   → 扫描全库，按类型追加条目
[5] 更新索引   → 目录 README 计数与分类更新
[6] 格式统一   → 全库校验，全通过才算完成
[7] 交付       → Conventional Commits + 验收清单
```

### [1] 立项澄清（必答 3 问）

**任何新增档案前，必须向老板澄清 3 个问题。不问就开工是违规**。

| 问 | 目的 | 常见答案 |
|---|---|---|
| **1. 档案定位** | 主线是什么？（1 句话） | "自媒体创作" / "技术写作" / "产品方法论" |
| **2. 信息源范围** | 挖多深？ | "全网" / "只用官方" / "含第三方批评" |
| **3. 交付形态** | 新建还是补现有？ | "同规格新增" / "补入已有" |

**为什么必问**：阮一峰档案起草前，任务起点给的"2007 年创建博客 / 2014 年创刊周刊"全是错的（实际是 2003-12 和 2018-04-23）。不问定位就开工，起点错一步、下游全错。

### [2] 前置研究（并行委派）

委派 3-5 路并行研究子任务（用当前 harness 的 subagent / 委派工具）：

| 子任务 | 目标 | 输出 |
|---|---|---|
| 生平与教育履历 | 出生、教育、职业转折、居住地 | 事实清单 + URL + 访问日期 |
| 商业化与争议 | 变现方式、立场演变、争议事件 | 争议时间线 + 各方立场 |
| 传播与内容策略 | 平台覆盖、粉丝规模、传播路径 | 硬数字 + 一手 URL |
| 时间线与主要作品 | 出版物、里程碑言论、代表作 | 按时间排序的作品清单 |

**关键约束**：
- 每条事实必须附**可点开核验的 URL** + 访问日期
- 抓不到就标「未取得」，**绝不凭记忆构造 URL**
- 5 级证据身份分级（详见 `references/evidence-grading.md`）
- 机构自述不能当事实用；来源冲突时**两说并列**，不择一

### [3] 起草（严格 11 节 + 写作纪律）

**11 节固定结构（顺序不可变）**：

1. 执行摘要
2. 关系网络
3. 时间线与主要作品/言论
4. 核心价值观
5. 思维模式
6. 方法论
7. 创作如何变成影响
8. 争议与风险点
9. 可信度与信息差异
10. 可操作建议
11. 主要参考来源

**章节标题必须 `##` 级别**，不能用 `#` 或 `###`。

**15 条硬规矩**（写作时逐条对，详见 `references/writing-style.md`）：

结构类：
1. 一级章节固定 11 个，名称与顺序不可增删改
2. 关系网络必须双向

标点与句式：
3. 禁破折号（`——`、`—`、`–`）；年份区间用半角连字符
4. 提示性冒号只用于引出人物直接原话
5. 禁翻案腔「不是 A 而是 B」
6. 禁商业黑话（闭环 / 赋能 / 抓手 / 底层逻辑 / 复利 / 范式 等）
7. 禁模型路标词（值得注意的是 / 本质上 / 由此可见 / 总之）
8. 禁借喻清单（仓库 / 抽屉 / 温度 / 坍塌 / 浪潮 / 钥匙 / 底座）

证据纪律：
9. 每条事实可点开核验；抓不到写「未取得」，不构造 URL
10. 查不到的东西标「待核实」+ 同句写清原因
11. 证据身份 5 级分级写进可信度章节
12. 引号内一个字都不能动

判断纪律：
13. 核心价值观至少 1 条具体、可被反驳的判断
14. 判断写完做反例审查；反例**只能取自档案已有材料**
15. 关系可查 ≠ 影响双向；单向影响如实标注

**长度参考**：
- **质量底线**：≥ 300 行（不含 frontmatter）
- **标杆样本**：`benchmarks/dan-koe.md`（278 行）、`benchmarks/ruanyifeng.md`（294 行）、`benchmarks/esor-huang.md`（289 行）
- **不设上限**：超过 350 行考虑合并同类信息

### [4] 补双向链

新增档案 A 后，扫描全库找需要链到 A 的档案。

**6 类关系**（固定）：
- **真实事件**：有具体事件可核实
- **合作**：有具体合作产出
- **争议对照**：彼此公开评论或对立
- **同期**：同一时代但无交集
- **概念对照**：方法 / 立场可并置（**必须写清「无事实交集」**）
- **无可核实交集**：明确否定结论，防止日后被误传

**补链操作规范**：
1. 在对方档案「关系网络」章节末尾追加条目
2. 格式：`- **[[A]]｜类型（说明）。** 一段说明文字`
3. 对方档案如果没有「关系网络」章节，新建完整章节
4. **不能凭空制造合作或影响关系**——查不到就写「无可核实交集」

**判断补链规则**：
- **必须链**：真事件 / 合作 / 争议对照
- **可以链**：概念对照 / 同期 / 无可核实交集
- **不链**：完全无关的人物

### [5] 更新索引

- 找到知识库的目录 README（如 `人物-README.md`）
- 更新档案计数（24 → 25）
- 在对应分类下追加条目（格式：`- [[人名]]｜一句话主线`）

### [6] 格式统一校验

**每次新增档案都要跑一次全库校验**。使用内置脚本：

```bash
python scripts/validate_library.py <library-root>
```

校验项：
- 11 节是否齐（缺一即不通过）
- 章节顺序是否与模板一致
- 标题级别是否全为 `##`
- frontmatter 是否有 `author: ChatGPT` 残留
- 是否有非模板章节
- 是否有禁词与破折号

**批量修改规则**：
1. 先 dry-run 报告所有偏差
2. 得到老板明确许可后再执行
3. 执行后再跑校验确认 100% 通过
4. 最后人工 spot-check 3-5 份

### [7] 交付

**Conventional Commits**：

```
docs(人物): 新增 XXX 档案 + 统一标题级别为 ## + 补关系网络双向链

- 新增：XXX.md（N 行 / M KB）
- 格式统一：X 份档案 Y 处标题从 # 改为 ##
- 补双向链：A / B / C / D 各补 [[XXX]] 条目
- 索引更新：人物-README.md 从 N 份更新为 N+1 份

所有档案现严格符合 11 节结构、无 AI 残留、无非模板章节。
```

**分支命名**：
- 新增档案：`feat/人物-XXX`
- 格式统一：`chore/unify-person-archives`
- 补双向链：`chore/backfill-links-person`
- 组合：`docs/人物-XXX-and-unify`

- [ ] 时间线 ≥ 20 条事件，每条附 URL + 访问日期

## 特殊场景

### 主档特殊情况（作者本人档案）

- 一手来源是作者自己的公开作品（博客、GitHub、官网）
- 公开来源天然是作者自述，机构自述比例必然高
- 冲突数据以老板确认为准，但**保留原页面冲突记录**到可信度章节作为「已知问题」
- 内部记忆 / 私人笔记可以作一手，但**必须显式标注**

### 关系网络章节不存在

历史原因，部分老档案可能没有「关系网络」章节。

处理：
1. 按模板格式新建整节
2. 先补 A 档案相关人物的双向链
3. 再补其他「同赛道」人物的概念对照链（至少 3-5 条）

### 模板 HTML 注释

- 模板文件包含「11 条硬规矩」HTML 注释块
- **成稿档案不保留这些注释**——起草期可保留，落盘前删除

## Pitfalls（历史踩坑清单）

1. **不问定位就开工** → 起点数据错误，返工成本高
2. **只搜正面不搜反面** → 档案变宣传稿，争议章节空洞
3. **抓不到就写"不存在"** → 应该写"本次抓取失败"或"未取得"
4. **来源冲突替老板选** → 两说并列，不择一
5. **凭印象写 GitHub 数字** → 必须走 API 拉，README 声明与 API 返回不一致时都列
6. **补链凭空制造合作** → 查不到就写"无可核实交集"，否定结论要写
7. **批量改格式没跑校验** → 改完必须再校验一次，全部通过才算
8. **合并到 main 未确认** → 老板未明确许可不合并
9. **模板注释留在成稿** → 起草期可保留，落盘前删
10. **frontmatter 残留 author: ChatGPT** → 模板红线禁止，逐份扫
11. **章节顺序靠记忆** → 用 required_sections 列表按模板顺序校验
12. **关系网络标题级别和正文其他章节不一致** → 全档案必须 `##`
