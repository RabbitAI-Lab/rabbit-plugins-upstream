# 应用深度标准详解：系统架构设计师（架构）

架构是本技能的**默认资格**，其深度标准散落在 `SKILL.md`（技术深度要求、论文七问）与 `writing-principles.md`（专业视角）中。本文档将其汇总为可对照的清单，说明架构论文"维度二·应用深度"的评分要点与常见写法。

---

## 一、架构设计要素对照

阅卷关注是否完成"设计→决策→验证"，而非技术名词堆砌。论文应覆盖以下要素：

| 要素 | 论文中可体现的内容 |
|------|-------------------|
| 架构风格/模式 | 层次式、微服务、事件驱动、CQRS、管道-过滤器等，并说明为何选它 |
| 质量属性 | 性能/可用性/安全性/可修改性/可扩展性，用"刺激-响应-度量"场景描述 |
| 架构视图 | 逻辑视图（分层/构件）、运行视图（进程/并发）、部署视图（节点/网络）、开发视图 |
| 构件与连接件 | 构件职责、接口契约、连接方式（REST/gRPC/MQ）、同步与异步的划分 |
| 数据架构 | 分库分表、读写分离、缓存一致性、数据分布与复制 |
| 架构评估 | 场景走查/ATAM 式的权衡点、敏感点、风险点识别 |
| 演化与技术债 | 单体→微服务的演进路径、遗留系统兼容、债务偿还计划 |

## 二、高分写法

### 架构选型（对应七问 Q2）
- 错误："本系统采用微服务架构"
- 正确："业务变更频繁且 6 个团队并行交付，单体架构的发布耦合已成为瓶颈；因此按业务边界拆分为 8 个微服务，代价是引入分布式事务，随后用 Saga 补偿应对"

### 架构描述（对应七问 Q3）
- 错误：罗列功能模块清单
- 正确："接入层（SLB + WAF）→ 网关层（鉴权/限流）→ 服务层（8 个业务服务）→ 数据层（MySQL 主从 + Redis 集群 + ES）；服务间用 MQ 异步解耦，同步调用仅保留在强一致链路"

### 落地实践（对应七问 Q4）
- 错误：介绍框架或中间件用法
- 正确："库存扣减与订单创建拆为本地事务 + MQ 事件，热点商品走 Redis 预扣减，大促峰值 QPS 10 万下库存超卖为 0"

### 取舍表述（对应七问 Q0，架构论文的硬指标）
- 每篇至少一处**明确的取舍**：为达成某质量属性牺牲了什么
- 示例："为保证可用性采用同城双活，代价是写入需跨中心同步，核心链路 RTT 由 1ms 增至 2ms"

## 三、权衡与评估（高分关键）

| 权衡维度 | 典型取舍 |
|---------|---------|
| 一致性 vs 性能/可用性 | CAP 取舍；TCC / Saga / 本地消息表的选择依据 |
| 拆分粒度 vs 运维复杂度 | 服务数与团队规模匹配，避免"分布式单体" |
| 自研 vs 成熟组件 | 团队熟悉度、社区活跃度、可控性 |
| 成本 vs 扩展性 | 预留容量 vs 按需弹性伸缩 |
| 演进性 | 为未来 2-3 年业务预留扩展点，避免过度设计 |

---

## 四、量化指标清单（建议准备）

- 峰值 QPS/TPS、响应时间（P99）、并发用户数
- 可用性（99.9% / 99.99%）、RTO/RPO
- 部署节点数、服务数、接口数、数据日增量
- 缓存命中率、数据库查询耗时下降比例
- 故障恢复时间、发布频率（如由月度发布提升至周发布）
