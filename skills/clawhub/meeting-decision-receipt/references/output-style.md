## 产品语气

默认语气清楚、克制、方便行动：少讲过程，先给结论和下一步。

- 开场：`整理好了。`
- 判词：`2 项已确认，1 项暂定，1 人明确接下，2 件事待确认。`
- 结尾：`这条确认消息可以直接发群，发送前核对人名和时间。`

普通业务会议可以使用“接活”等常见说法，但不对任何个人做玩笑。敏感会议统一改用“责任确认、待确认事项”。

## 首屏信息层级

按以下顺序渲染：

1. 会议标题与日期。
2. 一句计数判词。
3. 已确认。
4. 暂定 / 条件决定。
5. 谁接下、谁未确认、谁仅表达意向。
6. 还有什么待确认。
7. 会后确认消息。

提议、延后、被排除的备选细节和被覆盖项默认放在证据层。首屏每区最多 3 项；超出时显示总数与最高影响项，完整内容放证据层。

open loop 超过 3 项时，首屏只保留前三个最高影响项，并追加“另有 N 项待确认，见判断依据”。禁止为了显得完整把每条决定再复制成一条无人负责事项。

## 状态文案

### 决策

- `confirmed`：已确认
- `provisional`：暂定
- `conditional`：条件成立后执行
- `proposed`：仅为提议
- `deferred`：延后再议
- `rejected`：已排除
- `superseded`：已被后续结论覆盖

### 承诺

- `explicit_commitment`：明确接下
- `accepted_assignment`：已确认接下
- `unacknowledged_assignment`：被点名，未确认
- `implied_assignment`：会议语言指向，未确认
- `tentative_intent`：仅表达意向
- `conditional_commitment`：条件满足后执行
- `unowned`：没人接

不要把内部枚举直接暴露给普通用户。

## 缺失字段文案

将机器字段翻成具体问题：

- `owner` → 明确负责人
- `due` → 截止时间
- `dependencies` → 前置条件或条件负责人
- `acceptance_criteria` → 交付标准 / 版本要求
- `confirmation` → 被指派方确认

示例：`预算表仍缺截止时间、版本要求和被指派方确认。`

## 会后确认消息

默认格式：

```text
为避免会后理解偏差，把今天的结论对一下：
1. [当前明确决定]
2. [暂定结论，保留范围]
3. [明确承诺，保留负责人和时间]
4. [未确认指派，明确写待确认]
5. [悬空事项]
请相关同学直接回复“确认”，或补充需要修正的内容。
```

约束：

- 不写入提议当结论。
- 不把表达意向写成承诺。
- 不省略否定、范围与条件。
- 不添加来源没有给出的姓名或日期。
- 不在文本里嵌入密钥、联系方式或原始长引文。
- 不使用指责性语言。

## 双版本会议纪要

结论与待办清单承担语义判断，纪要只从验证通过的结构化 JSON 派生。不得为了补足篇幅重新读取原文自由发挥。

### 自用执行纪要

用于个人推进和会后核对，允许 1–2 屏：

1. 当前结论：确认、暂定、条件决定和排除项，保留范围与条件。
2. 执行清单：全部承诺类型，明确标出“责任已确认、未确认指派、仅表达意向、无人负责”。
3. 待确认事项：保留缺失字段与风险说明。
4. 讨论留档：提议、延后和被覆盖项。
5. 会后确认消息。
6. 折叠判断依据。

用户未明确提供本人身份时，使用“执行清单”，不得生成“我的任务”归属。

### 飞书管理层会议纪要

用于向上汇报，正文可直接复制到飞书文档，控制在一屏左右：

1. 以“会议名｜管理层会议纪要”为一级标题。
2. 写明会议日期与整理状态。
3. 用一个短段落概括当前结论与待协调数量。
4. 当前有效的核心结论，最多展示 3 项；超出部分汇总到结论与待办清单。
5. 已确认责任：只纳入 `explicit_commitment`、`accepted_assignment` 和证据充分的 `conditional_commitment`。
6. 待协调事项：使用 open loop 的主题与缺失字段，默认不带会议对话原句。
7. 待明确确认权：仅纳入明确缺 `decision` 或 `final_approver` 的事项；与普通待协调事项互斥，避免同一问题重复出现。没有相关事项时省略整节。
8. 下个节点：只使用已有截止时间、明确条件或已明确延后再议的节点。

向上版不得写入来源外的业务影响、优先级、执行进度、负责人姓名或日期。“回头看看”等个人对话原句只留在自用版依据层。

飞书复制兼容规则：

- 只使用一级 / 二级标题、普通段落、加粗、编号列表和分隔线。
- 不使用 Markdown 表格、代码块、HTML 标签、折叠块、复选框、脚注或嵌套列表。
- 正文不放结论清单、自用纪要等内部相对链接，不展示文件名或生成命令。
- 每个列表项表达一件事；保留否定、范围、条件与原始时间。
- 宿主支持可复制文档块时，仅把成稿正文放入文档块，解释与验证信息留在文档块外。
- HTML 预览把飞书正文放进独立复制区；复制动作同时提供富文本与纯文本，便于直接粘贴。

当前 Schema 记录承诺状态，不记录任务完成状态。“责任已确认”只表示有人明确认领或接受，禁止改写成“工作已完成、已闭环、进展正常、交付合格”；来源明确报告完成结果时，也需先扩展结构化契约再展示。

### 一键 bundle

同一条命令生成六个文件：

```text
receipt.md
receipt.html
minutes-personal.md
minutes-personal.html
minutes-executive.md
minutes-executive.html
```

结论清单与 HTML 预览通过轻量导航互相连接；飞书管理层 Markdown 保持独立成稿，不夹带导航链接，也不把两份纪要正文继续堆在同一长页底部。

## 中性模式

当 `safety.neutral_language_mode=true`：

- 证据或来源中的“接活”等口语统一改为“责任确认”。
- 界面只使用“待确认事项”，不使用“还欠”或“挂账”。
- “整理好了”改为“审计结果已整理”。
- 页脚改为“发送前请核对相关人员、时间与适用范围”。
- 删除玩笑、图标和拟人化评价。

## HTML 图卡

- 视觉采用低饱和纸张 / 项目清单语汇，避免咨询公司式长表格。
- 默认宽度 1080px，内容容器最大宽度 920px。
- 标题区保持紧凑，首条决策尽量在常见笔记本视口内出现。
- 计数判词使用四格数字带，避免长句在首屏占据两行以上。
- 已确认、责任、待确认使用轻微色差与边框，不依赖颜色单独传达状态。
- open loop 按“主题 / 缺失标签 / 一句说明”分层，避免大段文字墙。
- 会后确认消息使用有序列表，保持复制后的阅读顺序。
- 证据层在浏览器中可展开；截图首屏默认收起。
- 支持长中文自动换行、打印与窄屏。
- 页脚固定文案：`会开完，把下一步说清楚。`

## 纯文本降级

HTML 不可用时仍输出完整 Markdown。宿主不支持折叠时，使用“判断依据”小节，并将证据放在正文末尾。
