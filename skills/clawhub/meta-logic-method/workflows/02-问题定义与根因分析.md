# W-2 问题定义与根因分析流程

> 输入：一个模糊的"问题感觉"或明确的故障现象。
> 输出：问题定义书 + 已验证的根因链。
> 调度：S-2 溯因推理（主）+ S-8 系统思维（结构定位）+ M-P 系列（概念与前提）+ S-3（检验）。
> 场景：bug 排查、业绩下滑归因、顽疾复发、"总是这样"类问题。

---

## W-2.1 问题陈述规范化【强制】

把"问题感觉"写成规范定义（M-2）：

```
现状：（可观察的事实，量化优先）
期望：（标准 / 目标，来源注明）
差距：现状 − 期望
约束：时间 / 资源 / 不可动项
影响：这个差距造成了什么损失（决定问题优先级）
```

【禁止】把解决方案写进问题定义（"问题是缺少一个监控平台"——监控平台是方案，"故障发现晚于用户上报"才是问题）；此为"方案入题"，会锁死后续方案空间。

## W-2.2 概念明晰【强制】

问题陈述中的关键词过 M-P1 三查（定义 / 边界 / 反例）："性能差"的"差"指延迟还是吞吐？"用户流失"的口径是登录频次还是付费中止？——归因分析前概念必须钉死，否则根因链会在错误的地基上生长。

## W-2.3 溯因链构建【强制】

执行 S-2 完整流程：

1. 现象固定（S-2.1）：区分事实与解读
2. 候选解释 ≥ 3（S-2.2，含平凡解释）
3. 逐层追问 Why（5 Whys 实践约定：问到**可采取行动**的层级即停，通常 3~5 层）
4. 每层候选解释均须列齐再下钻，【禁止】单线直下（5 Whys 的最大陷阱：第一层选错解释，后面五层全错）

## W-2.4 系统结构定位【强制】

根因链的顶层接 S-8 回答："**什么结构让这个原因反复出现？**"

- 识别维持顽疾的回路（S-8.2）：哪个增强 / 调节回路在给这个根因供能？
- 区分**一次性诱因**（这次的具体触发）与**结构性根因**（让触发必然发生的结构）——只修诱因，问题必然复发

## W-2.5 根因验证【强制】

候选根因必须过三关才可输出（M-9）：

1. **复现关**：按根因推演，现象应能复现 / 解释全部已知现象（覆盖度，S-2.3）
2. **消除关**：若根因被消除，现象应消失或显著减弱——设计可执行的检验（能做干预实验最优，S-2.4）
3. **反证关**：主动找"根因在但现象未发生"的反例；反例存在 → 根因降级为"相关因素"，回 W-2.3

三关未过 → 标注为"当前最优假说 + 置信度"，【禁止】以确定语气输出。

## W-2.6 输出：问题定义书 + 根因链【强制】

按 `reference/cot-templates.md` R-2 模板输出：规范问题定义（W-2.1）、根因链（诱因 → 结构性根因，分层）、验证状态与置信度（W-2.5）、结构性建议入口（接 W-3 做方案）。

## 反模式

- 【禁止】方案入题（W-2.1）
- 【禁止】把"人为失误"当终点根因——失误背后必有让它发生且未拦截的结构（S-8.2 追问）
- 归因于"人不行 / 环境如此"后停止：这类归因不可行动，等于放弃分析（M-2：不可行动的"根因"只是抱怨的升格）

## 示例（微型）

现象：线上故障平均发现时间 45 分钟，皆由用户上报先于监控告警（现状），期望 ≤ 5 分钟。
概念（W-2.2）："发现"= 任一渠道确认异常的时刻（钉死口径）。
溯因（W-2.3）：候选 = 告警规则缺漏 / 阈值过高 / 告警通道失灵 / 错误未打日志。逐层下钻定位：错误码未纳入监控采集（诱因）← 新服务接入监控靠人工 checklist，无强制卡点（结构性根因）。
系统定位（W-2.4）：人工 checklist + 发布压力大 = 漏配必然反复发生（R 回路）。
验证（W-2.5）：复现关 ✓（漏配服务均在故障名单）；消除关：试点接入自动校验后两月零漏配；反证关：全量复核未发现"已配置但未告警"反例。
输出：根因 = 监控接入无强制卡点（已验证，置信度高）；结构性建议入口 → W-3。
