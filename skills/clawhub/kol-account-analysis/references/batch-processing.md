# 批量处理协议 — 运行时 token 经济性

> 专家审计补充（v1.2，推断）：近 2000 条评论若全量交给 LLM 分类，token 成本高且计数不稳定。生产执行原则：**能计算的绝不让 LLM 数，LLM 只做判断与解读。**

## 分工边界

| 任务 | 执行者 | 说明 |
|------|--------|------|
| 计数、去重、占比、高赞集中度、参与结构比率 | 脚本（Python / 表格处理工具） | 确定性统计，零幻觉 |
| 评论七维分类、代表性摘录筛选 | LLM 分批处理 | 每批 ≤ 200 条，输出「维度标签 × 置信度」 |
| 小数字核查、掩盖信号解读、五问结论 | LLM | 基于统计结果做判断 |

## 评论清洗规则（统计前置）

1. 去重：完全重复 + 复读型（仅表情/「哈哈哈哈」类）合并计数
2. 活动型评论（直播时间/抽奖口令/求链接/价格问询）单独标记，不参与内容认同类占比的分母
3. 计数口径写入采集说明：原始条数 / 去重后条数 / 进入分类的条数

## 分层抽样降级协议

评论量超出预算时（建议阈值 > 3000 条）：

| 层 | 抽取 | 用途 |
|----|------|------|
| 高赞层 | 按赞数排序 Top 200 | 代表性观点（高赞权重最高） |
| 随机层 | 随机 500 条 | 结构占比估计 |
| 关键词层 | 含品牌/商品关键词的全量 | 小数字核查（不许抽样） |

- 结构占比按随机层估计并标注「抽样口径」
- **关键小数字必须全量核查**——"只出现 2 次"这类结论抽不得样
- **信任资产信号（记忆残留/自来水安利/商单记忆反应）同样全量核查**——数量稀少，抽样必然漏检（见 comments-analysis.md）

## 作品层数据处理

- 数据分布（最低/中位/最高）、月度趋势、异常样本剔除：全部由脚本计算，LLM 只做母题归纳与解读
- 母题归纳按作品逐条进行（作品条数 ≤ 40，可直接处理）

## 失败降级

- 脚本不可用时：LLM 分批处理但每批完成后输出批次计数校验和，汇总时人工核对总数
- 任一批次分类失败：重试一次，仍失败则该批降级为「未分类」，占比分母相应调整并标注缺口
