# 自进化机制 | Self-Evolution

Code Spec Guardian 是活的规范系统，在每次对话中持续学习、提炼、进化。

## 触发条件

| 信号 | 示例 | 处理 |
|------|------|------|
| 用户明确给出规范 | "我们项目用 2 空格缩进" | 直接写入对应模块 |
| 用户纠正生成代码 | "不要用 var，用 const" | 提取为命名规范条目 |
| 用户偏好表达 | "API 返回用下划线命名" | 写入 api-spec.md |
| 代码中体现新约定 | 生成的代码遵循了项目既有模式 | 自动识别并记录 |
| 用户否定规范 | "这个不用遵循" | 标记为 deprecated |

## 增量更新流程

```
对话内容 → 信号识别 → 分类到模块 → 读取现有规范 → 对比差异 → 增量写入
```

1. **信号识别** — 从对话中识别潜在规范信息
2. **模块归类** — 匹配到对应模块
3. **差异对比** — 读现有规范，判断新增/修改/冲突
4. **写入策略**：
   - 新增：追加到文件末尾，标注 `[auto: YYYY-MM-DD]`
   - 修改：更新内容，旧条目保留为注释标记 `[deprecated: YYYY-MM-DD]`
   - 冲突：不自动覆盖，标记 `[pending-review]`，提示用户
5. **元数据更新** — 更新 `skill-meta.json`

## 重大变更确认

以下变更必须向用户确认后才写入：
- 删除或废弃已有规范条目
- 修改核心架构约定（如更换状态管理方案）
- 修改 UI 体系（如更换组件库、主题色）
- 单次更新涉及 3 个以上模块

确认方式：展示简洁变更摘要 diff。

## 信号优先级

1. **用户显式指令** — 最高优先级
2. **用户纠正反馈** — 对 AI 生成代码的修改意见
3. **代码模式推断** — 从项目代码中自动识别
4. **隐式偏好** — 用户多轮对话中一致的偏好

## 进化示例

```
Day 1: 首次分析 → 生成 6 模块，42 条规范
Day 2: 用户纠正引号 → code-style.md +1 条
Day 3: API 偏好表达 → api-spec.md +1 条
Day 5: 更换工具库 → 重大变更，确认后更新
Day 7: 积累 58 条，AI 写代码越来越贴合项目
```
