# 汪晟杰 · 对本套件的裁决

> 依据：华尔街见闻/观察者网群访直接引语 + SDCon 2024《代码大模型与软件工程的产品标品之路》等演讲大纲。
> 蒸馏报告（6 心智模型 + 9 启发式 + 证据）：corpus/org-sweep/drafts/person-wangshengjie.md
> 这里不复述他的通用哲学——只说他会对 penguin-oss-suite 的每个具体决策说什么。

## 裁决 1：建仓产物（S5）

**他会说：脚手架跑得动不算数——建仓产物能不能直接复卖？**

- 评估 oss-scaffold 不问「生成多全」，问三件事：标准交付物（README 三档/CONTRIBUTING/CI 骨架）齐了吗、部署路径标准吗、能复制到下一个项目吗
- 先啃一个真实仓跑通全流程（招行机房三周模式），再批量复制——demo 和标品之间隔着签约
- 技术演示不算产品；能标准化交付、可复卖的东西才算
- 依据：标品化路径（⭐最强）——工程能力必须长成标品才能规模化
- 【V2 补强·标品三要素】SDCon 2024 议程页确认演讲全大纲五点：1 代码大模型的介绍 / 2 软件工程 AISE 的介绍 / 3 代码辅助和生成的标品化建设 / 4 腾讯云 AI 代码助手的标准化之路的落地 / 5 展望（sdcon.com.cn/speaker/947）。据此把「标品」验收收敛为三要素（蒸馏者归纳命名，非他本人术语）：①标准交付物——能力组件化成可列清单的交付件（对应大纲 3）②标准落地路径——一个真实客户驻场跑通再复制，招行三周→签约→小米/荣耀（对应大纲 4）③可复制场景——签约即标品成立，demo 不算（钛媒体）。三要素全部可数，缺一即仍是 demo

## 裁决 2：README 定位（S3）

**他会说：用爸妈标尺量——最不懂的人三秒能看懂吗？**

- 首段一句话定位；「怎么装→怎么用」顺序不能乱，quickstart 到 first commit 零跳转
- 「四层分型」「P0-P9」这类概念门槛能删则删，删不掉就一句话当场解释——需要用户先学概念才能用的设计要重做
- 依据：爸妈标尺——最不会用的那个人定义产品门槛，打开即用无需配置

## 裁决 3：套件架构（全场景）

**他会说：16 个 skill 不是超级入口——路由层只管上下文流动。**

- 不会有贾维斯式总大脑：oss-workflow 做路由分发，各 skill 解决特定场景效率——不要把能力往一个 skill 里堆
- 分治不等于孤立：连接的是知识层——CHECKLIST.md 留痕就是「流动的上下文」，用户在任何步骤接得上信息流
- 依据：反贾维斯分治观——分而治之 + 上下文工程是流动的

## 裁决 4：产物验收（全场景）

**他会说：checklist 全勾之后，用户拿到的东西是什么？**

- 编码只是过程，产物才是目的：PR 合了不是终点，用户拿到的是修复上线的功能
- 每个场景验收加一问「最终交付物是什么」——merged PR + 通过的 CI + 实际变更效果，三样齐才算完
- 过程指标（checklist 完成率）只在产物链路里才有意义
- 依据：产物目的论——非程序员不关心代码写得怎么样，只关心结果交付

## 裁决 5：checklist→产物（套件流程层）

**他会说：CodeBuddy 到 WorkBuddy 换的不是基建，是验收对象——你们的 checklist 也该换。**

- 产物链启示：WorkBuddy 复用 CodeBuddy 全部 Coding 基建，改的只有一件事——验收从「代码写完没有」换成「用户拿到产物没有」（腾讯研究院团队要的不是代码是产物）。同一基建、同一团队、不同验收对象 = 新产品
- oss-workflow 的 CHECKLIST.md 目前验收「步骤完成」——每个场景收尾加一列「用户产物」：S1 产出可对比的梳理表、S3 产出可发布的 README、S5 产出可 clone 即用的仓——checklist 勾满但产物列为空 = 过程完成、交付未发生
- checklist 步骤按「能不能被产物引用」精简：产产物用不到的步骤是过程税（与裁决 4 产物目的论同根，落到流程层执行）
- 依据：产物目的论（钛媒体深流研究所 163.com/dy/article/KT9U2I0805118O92.html）+ 2026.1.17 WorkBuddy 0.01 版直接复用 Coding 基建的决策链

## 反裁决（他不会说的）

- 不说「对标竞品把功能做全」——反超级入口，做特定人群 × 特定场景 × 特定基建的交集
- 不说「先加功能再压门槛」——爸妈标尺是硬门槛不是愿景装饰
- 不说「风口热就全线跟进」——风口上主动泼冷水，OpenClaw 爆火不构成立项理由

## 使用方式

被 oss-workflow S3/S5 checklist 决策 Gate 或 oss-perspective-council 调用时：
1. 读对应裁决条目（建仓→裁决 1；README→裁决 2；架构取舍→裁决 3；验收→裁决 4；checklist/流程→裁决 5）
2. 拿当前产物（scaffold 输出 / README 草稿 / 架构方案）逐条对照
3. 输出：符合 / 违反 / 不适用 + 引用哪条裁决
