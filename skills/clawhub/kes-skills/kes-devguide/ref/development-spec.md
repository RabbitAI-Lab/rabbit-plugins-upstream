# 应用设计规范

## 概述

最优的系统性能从设计阶段开始，并贯穿系统生命周期。在初始设计阶段考虑性能问题为后续生产调优奠定坚实基础。

## 性能规划 6 步流程

1. **定义应用工作负载特性和性能目标** — 确定数据规模、用户并发度、事务类型、响应时间和吞吐量目标
2. **使用启发式原则确定软件部署架构** — 选择合适的架构模式
3. **估算硬件资源需求** — 基于工作负载和架构评估硬件配置
4. **设计并开发应用** — 遵循应用设计原则
5. **通过模拟或真实负载测试测量资源消耗** — 工作负载测试
6. **验证目标是否达成** — 未达标则重复步骤 3-5

## 系统架构考量

### 硬件组件

| 组件 | 关键因素 |
|------|---------|
| CPU | 架构（X86 > ARM/MIPS 每核性能）、核心数（更多核心=更多并发，受内存带宽限制）、主频 |
| 内存 | 等主频下容量越大越好，缓存数据减少磁盘 I/O |
| I/O 子系统 | SSD > HDD；磁盘数 = I/O 线性扩展；转速影响 HDD IOPS（5400/7200/15000） |
| 网络 | 带宽（容量）和延迟（响应时间）是两个关键指标 |

### 软件组件

- **用户界面**：展示、输入收集、状态管理
- **业务逻辑**：数据模型到关系表映射、约束、业务流程
- **资源管理**：数据库连接管理、SQL 执行效率、客户端状态管理、负载均衡、任务队列
- **数据和事务**：锁管理、索引、内存缓存、容错、约束执行

### 架构设计关键问题

- 多少用户？（单用户 / 中大型企业 / 大规模分布式互联网用户）
- 用户交互方式？
- 用户分布和网络速度？
- 数据量和只读比例？
- 响应时间要求？
- 是否需要 7×24 可用性？
- 实时变更需求？
- 数据库规模（更大数据库需要更多 CPU 维护操作）？

### 部署架构选项

- 应用与数据库服务器同机部署
- 应用与数据服务分离部署
- 缓存技术优化性能
- 应用服务器集群
- 数据库读写分离
- 分布式数据库架构
- NoSQL 数据库和搜索引擎
- 业务逻辑拆分

## 应用设计原则

### 简洁性原则

- 如果表设计复杂到无法理解，那就是不良设计
- 如果 SQL 长到优化器无法处理，说明存在设计问题
- 同一列上的重复索引表示索引设计不当
- 查询响应缓慢可能反映不良的 UI 或事务设计
- 通过过多层过度抽象数据库调用是不良实践

### 表与索引设计

- 规范化到 3NF 保证灵活性，关键表选择性反规范化提升性能
- 索引设计是迭代过程：从 PK 和基础索引开始，测试阶段逐步优化

### 索引类型选择

| 索引类型 | 适用场景 |
|---------|---------|
| B-tree | 标准 PK 和频繁查询，适合 JOIN |
| Bitmap | 小空间、快速查找；适合低基数列（1-10000）且无更新 |
| 函数索引 | 派生值查询（如 `(price-discount)*quantity`、`upper()` 大小写不敏感搜索） |
| 分区索引 | 启用分区裁剪，减少 I/O |
| 反向索引 | 消除写入热点，但不能做范围扫描 |

### 索引代价估算

在已索引键上的 INSERT/DELETE/UPDATE 代价约为实际 DML 的 3 倍。3 个索引时写入速度降至无索引表的约 1/10。

### SQL 执行效率

**连接管理**：最小化并发连接，复用连接。

**游标管理**：使用绑定变量启用软解析和 SQL 共享。

```sql
-- 字符串字面量（每次硬解析）
SELECT * FROM employees WHERE first_name LIKE 'KING';

-- 绑定变量（启用软解析）
PREPARE em_plan(VARCHAR) AS SELECT * FROM employees WHERE first_name LIKE $1;
EXECUTE em_plan('KING');
```

### 实现指南（8 条规则）

1. 选择支持性能设计的开发环境
2. 专注于实现组件自身功能，不越界实现其他组件功能
3. 不忽略任何特性 — 数据归档和清理是最常被忽视的
4. 用过程语言（C、Java、PL/SQL）处理流程逻辑；用 SQL 处理数据访问。避免在 SQL 中嵌入过程逻辑（如 `DECODE`、多个 `OR` 谓词）
5. 缓存高频访问、低频变更的数据（当前日期、用户名、税率、折扣率等）
6. 优化组件间接口
7. 使用数据库外键约束而非应用层强制引用完整性
8. 配置操作名和模块标识以便端到端追踪

## 工作负载测试

### 确定数据规模

- 对变长数据保持谨慎；键长度可能随数据量增长
- 监控每个对象的空间分配；升序键写入后左侧删除会浪费空间
- DBA 应持续监控空间分配，识别失控对象

### 估算工作负载

- **从相似系统推断**：基于经验调整规格。风险：如果规模相差一个数量级，组件可能超出设计限制
- **基准测试**：资源密集且耗时。适合确定实际 I/O 需求和验证恢复流程

### 测试规则（6 条）

1. **使用真实数据量和分布** — 用满表测试、生产级数据基数、所有生产索引和准确的模式统计信息
2. **测试单用户性能** — 如果单用户在空闲系统上无法可接受地执行，多用户在生产环境更不行
3. **捕获并记录所有 SQL 执行计划** — 验证优化器决策；通过 CPU 时间和物理 I/O 理解相对代价
4. **尝试多用户测试** — 测试 DML 操作中的锁冲突和串行化问题
5. **使用正确的硬件配置** — 匹配生产的网络延迟、I/O 带宽和处理器类型/速度
6. **测量稳态性能** — 基准测试中包含暖机（数据进入缓存、一次性解析完成）和冷却期

## 容量估算方法

### 硬件资源估算

基于以下参数估算：

- 数据总量和日增量
- 并发用户数和连接数
- 事务类型比例（读/写）
- 响应时间要求
- 备份和归档需求

### 存储估算

```
总存储 = 数据量 + WAL 量 + 归档量 + 备份量 + 预留空间

数据量 = 表数据 + 索引数据 + TOAST 数据
WAL 量 ≈ 根据写入频率和 max_wal_size
归档量 ≈ 根据保留策略
备份量 ≈ 根据备份频率（全量/增量）
预留空间 ≈ 数据量的 20-30%
```

### 内存估算

```
shared_buffers = 物理内存的 1/4 ~ 1/3
effective_cache_size = 物理内存的 3/4 ~ 1 倍
work_mem = 根据排序/哈希操作规模
maintenance_work_mem = 维护操作内存
操作系统预留 = 物理内存的 10-20%
```
