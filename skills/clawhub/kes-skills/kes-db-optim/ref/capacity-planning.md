# KingbaseES 容量规划指南

## 性能指标体系

### 响应时间

响应时间衡量从发出数据库请求到接收全部结果数据的时间间隔。由 CPU 处理时间加上非空闲等待时间（如 IO 时间、锁等待时间）组成。对于在线系统，响应时间要求通常严格——例如用户按回车后 0.5 秒内必须显示结果。

### 吞吐量

吞吐量衡量数据库单位时间内可处理的请求数。与响应时间的关系：

```
单会话最大吞吐量 = 1 / 响应时间
N 会话最大吞吐量 = N / 响应时间
```

此公式假设会话间无相互等待，且硬件资源充足。任一资源的最大吞吐量 = 资源处理能力 / 单次请求资源消耗。

### 数据库时间模型

数据库性能分析的核心公式：

```
DB Time = CPU 时间 + 非空闲等待时间
```

DB Time 量化数据库处理用户请求的总时间，不包含应用层、网络或中间件消耗的时间。性能调优的目标是降低 DB Time——通过减少 CPU 占用或等待时间，进而提升吞吐量。

## 可扩展性

可扩展性指系统资源增长时有效处理增加负载的能力。理想情况下负载加倍只需双倍资源。实际上内部竞争和冲突导致资源消耗超过线性预期。

### 限制可扩展性的因素

**应用设计问题：**
- 模式设计不当：关键 SQL 未优化，无法利用系统资源
- 事务设计不合理：锁竞争和串行化问题限制扩展
- 连接管理不当：响应时间增加，系统可靠性下降

**物理实现问题：**
- 生产环境 IO 策略不当
- 生产与测试环境执行计划差异
- 内存密集型应用缺少运行时内存释放机制
- 内存利用率低或内存泄漏对虚拟内存子系统造成压力

**硬件配置：**
- 资源超配或欠配都会影响负载下的可扩展性

**软件与硬件限制：**
- 所有软件组件（应用服务器、数据库）都有性能边界
- 多 CPU 扩展在超过某一阈值后不再线性——增加 CPU 可能无法同比提升性能，甚至导致性能下降

### 互联网应用特征

通过互联网访问的应用面临更复杂的可扩展性要求：
- 需要 7×24 可用性
- 并发用户数不可预测
- 容量规划困难
- 多层架构
- 无状态中间件
- 开发和测试周期短

研究表明，互联网用户等待响应超过 7 秒后注意力永久流失。系统重新设计和迁移的成本通常远超一开始构建稳定系统的成本。

## 性能问题产生模型

性能问题源于资源竞争或资源耗尽。当系统资源达到处理极限，系统无法继续扩展。

根本原因：
1. **资源使用效率低**——SQL 不佳、缺少索引、配置不当
2. **资源容量不足**——硬件无法满足负载需求

数据库所依赖的资源包括 CPU、IO、内存、网络和锁。常见瓶颈症状：

- CPU 利用率接近 100%
- IO 利用率接近 100%
- 内存耗尽，开始使用 swap
- 网络带宽饱和，传输错误增多
- 数据库内长时间等待状态

调优时 DBA 的首要目标是识别并解决资源使用效率低下的问题。若不存在效率问题，则资源容量不足，需评估硬件升级。

## 性能管理方式

### 被动式性能管理

事后应对——性能问题出现后才处理。表明被动管理的常见表述：

- "先做出来看看性能如何"
- "先赶进度，性能之后再调"
- "性能是 V2 的事"

风险：预算超支、交付延期、项目失败。

### 主动式性能管理

事前预防——在开发生命周期早期预见潜在性能问题并处理。主动管理涵盖整个软件开发生命周期，包括容量规划、架构设计、应用开发原则、负载测试和验证。

## 6 步容量规划流程

1. **定义应用负载特征和性能目标**

   明确数据量、并发用户数、操作类型（事务特征）、响应时间和吞吐量目标。

2. **确定软件部署架构**

   基于同类项目经验选择合适架构：

   - 应用与数据库同机部署
   - 应用与数据服务分离
   - 缓存层优化
   - 应用服务器集群
   - 数据库读写分离
   - 分布式数据库架构
   - NoSQL 数据库和搜索引擎
   - 业务逻辑拆分

3. **估算硬件资源需求**

   基于负载特征和系统架构。参见下文硬件和软件部分。

4. **设计与开发应用**

   遵循应用设计原则：数据建模、表/索引设计、SQL 效率、连接管理、游标使用。

5. **通过负载测试测量资源消耗**

   使用模拟或实际负载测试。参见下文负载测试部分。

6. **验证是否达到目标**

   若未达标，重复步骤 3、4、5 直到满足性能要求。

## 硬件资源估算

### CPU

- 架构优先级：X86 > ARM/MIPS（单核性能）
- 核心数：更多核心支持更高并发，受内存带宽限制
- 主频：影响单线程性能

### 内存

```
shared_buffers = 物理内存的 1/4 ~ 1/3
effective_cache_size = 物理内存的 3/4 ~ 1 倍
work_mem = 根据排序/哈希操作规模设置
maintenance_work_mem = 维护操作内存
OS 预留 = 物理内存的 10%~20%
```

### 存储

```
总存储 = 数据量 + WAL 量 + 归档量 + 备份量 + 预留空间

数据量 = 表数据 + 索引数据 + TOAST 数据
WAL 量 = 取决于写入频率和 max_wal_size
归档量 = 取决于保留策略
备份量 = 取决于备份频率（全量/增量）
预留空间 = 数据量的 20%~30%
```

- SSD > HDD（IOPS 和带宽）
- 磁盘数量 = IO 性能线性扩展

### 网络

- 带宽（传输能力）和延迟（响应时间）是关键指标
- 读写分离场景需评估主备同步带宽

## 系统架构

### 硬件组件

**CPU：** 考虑架构类型（X86、MIPS、ARM）、核心数和主频。架构影响效率——X86 通常在相同核心数下性能更优。

**内存：** 相同频率下容量越大越好。数据库和应用服务器需要大量内存用于数据缓存。

**IO 子系统：** 受多因素影响：
- 磁盘类型：SSD 比 HDD 提供更高 IOPS 和带宽
- 转速：HDD 的 RPM 越高理论 IOPS 越高（5400、7200、15000 RPM）
- 磁盘数量：IO 性能随磁盘数量线性扩展

**网络：** 两个关键指标——带宽（传输能力）和延迟（数据传输时间）。

### 软件组件

大多数应用包含：

1. **用户界面**——向用户展示信息、收集输入、控制应用状态
2. **业务逻辑**——将数据模型转换为关系表、定义约束、实现业务规则
3. **资源管理**——数据库连接管理、高效 SQL 执行（游标和 SQL 共享）、客户端状态管理、负载均衡、持久任务队列
4. **数据与事务管理**——通过锁和事务语义控制并发数据访问，通过索引和内存缓存优化访问，通过变更日志实现故障恢复，规则强制执行

### 架构配置考量

引导架构设计的关键问题：

| 问题 | 影响 |
|------|------|
| 系统需支持多少用户 | 决定部署模式：单机、中等规模共享或互联网级分布式 |
| 用户交互方式 | 浏览器、自定义客户端、API、批处理 |
| 用户分布 | 影响网络延迟处理、高峰时段调度 |
| 网络速度 | 决定 UI 与后端通信模式 |
| 用户需要多少数据；多少是只读 | 读密集型负载受益于复制和本地缓存 |
| 响应时间要求 | 高管决策支持需要高精确度；数据录入需求较低 |
| 是否需要 7×24 可用 | 决定维护窗口策略 |
| 变更是否需要立即生效 | 同步与异步事务处理 |
| 数据库规模要求 | 大数据量需要更多 CPU 执行维护操作，与负载无关 |

## 应用设计原则

### 简洁性

- 如果表太复杂难以理解，说明设计有问题
- 如果 SQL 过长导致优化器无法有效优化，说明语句、事务或表设计有缺陷
- 同一列上的重复索引说明索引设计有问题
- 在线用户查询缓慢说明 UI 或事务设计不佳
- 通过软件层过度抽象数据库调用说明开发实践不当

### 数据建模

- 对受业务事务影响最频繁的实体建模
- 避免过度关注非核心数据元素，延长开发周期
- 使用建模工具快速生成模式和原型

### 表与索引设计

**表设计**在灵活性与性能之间平衡。为灵活性和未知负载规范化到第三范式。对业务关键表选择性反规范化以提升性能。

**索引设计**是迭代过程。从主键约束和已知访问模式的索引开始，随着测试发现问题逐步优化。

**索引类型：**

| 索引类型 | 使用场景 |
|---------|---------|
| B-tree | 主键、频繁查询列、JOIN 操作的标准索引 |
| 位图 | 低基数列（1~10000 个不同值），只读数据 |
| 函数索引 | 派生值、不区分大小写搜索、计算表达式 |
| 分区索引 | 范围或列表分区，用于分区裁剪，减少 IO |
| 反向索引 | 消除写入密集型应用的索引热块；不支持范围扫描 |

**索引成本估算：** 维护一个索引约消耗表 DML 操作 3 倍资源。对有 3 个索引的表写入数据的速度约为无索引表的 1/10。

**索引列排序：**
- 按选择频率排序（最常用方法）
- 按数据分组排序，减少范围扫描的 IO

### 视图

视图通过屏蔽数据模型复杂性来简化应用设计。但嵌套视图或参与 JOIN 操作的视图可能导致次优执行计划。直接访问表通常更优。

### SQL 执行效率

**连接管理：** 建立数据库连接是资源密集型操作，不可扩展。尽量减少并发连接数；尽量在应用初始化时建立连接。在多层架构中共享连接，避免每次请求都建立连接。

**游标管理：** 解析操作分类：

- **硬解析**——SQL 首次提交且共享池中无匹配项时执行。资源消耗最大、最不可扩展的操作。
- **软解析**——SQL 与共享池中已有条目匹配时执行。仍需语法和安全检查。

性能影响（4 CPU 机器 OLTP 测试）：

```
无解析（所有语句）         支持 270 用户
全部软解析               支持 150 用户
全部硬解析               支持 60 用户
每事务重新连接           支持 30 用户
```

使用绑定变量实现 SQL 共享：

```sql
-- 使用字符串字面量：不可共享
SELECT * FROM employees WHERE first_name LIKE 'KING';

-- 使用绑定变量：可共享
PREPARE em_plan(VARCHAR) AS SELECT * FROM employees WHERE first_name LIKE $1;
EXECUTE em_plan('KING');
```

**实现规则：**
1. 选择支持性能设计的开发环境
2. 每个软件组件专注自身功能
3. 设计和测试阶段不可忽视实现细节
4. 过程逻辑使用过程语言（C、Java、PL/SQL），数据访问和 DML 使用 SQL
5. 在本地缓存频繁访问、极少变更的数据（如当前日期、用户名、税率）
6. 优化组件间接口
7. 使用数据库外键约束，而非应用层强制引用完整性
8. 配置操作名和模块标识，实现端到端追踪

## 内存管理

KingbaseES 仅支持手动内存管理。需要管理的内存结构是系统全局区（SGA）和进程全局区（PGA）。

### SGA（系统全局区）

共享内存结构，包含数据库实例的数据和控制信息，由所有服务器进程和后台进程共享。

**数据块缓存（`shared_buffers`）：**
```sql
ALTER SYSTEM SET shared_buffers = '1GB';
SHOW shared_buffers;
```
缓存越大，内存中的数据页越多，减少磁盘读写。推荐配置为操作系统总内存的一半左右，根据需求调整，但一般不超过 OS 内存的 80%。需要重启数据库。

**日志缓冲区（`wal_buffers`）：**
```sql
ALTER SYSTEM SET wal_buffers = '4MB';
SHOW wal_buffers;
```
存储重做日志内容，在日志写入器刷盘前暂存。如果事务修改的数据量过大导致缓冲区频繁提前刷盘，应增大此值。值设得过大也无益，因为日志始终在提交和检查点时刷盘。需要重启数据库。

**锁缓存：** 大小由数据库内部决定。参数 `max_locks_per_transaction`（默认 64）影响锁缓存大小。值越大消耗越多内存。锁缓存很少成为瓶颈，通常不需要手动配置。

### PGA（进程全局区）

非共享内存，包含单个服务进程的数据和控制信息。进程启动时创建，仅该进程可访问。

**临时缓冲区（`temp_buffers`）：**
```sql
ALTER SYSTEM SET temp_buffers = '8MB';
SHOW temp_buffers;
```
在进程私有内存中缓存临时表数据页。需要重启数据库。

**工作内存（`work_mem`）：**
```sql
ALTER SYSTEM SET work_mem = '4MB';
SHOW work_mem;
```
用于服务进程内的排序和哈希连接操作。仅在活跃的排序/哈希操作期间分配，操作结束后释放。work_mem 不足会导致操作溢出到磁盘临时文件。需要重启数据库。

**维护工作内存（`maintenance_work_mem`）：**
```sql
ALTER SYSTEM SET maintenance_work_mem = '64MB';
SHOW maintenance_work_mem;
```
维护操作（VACUUM、CREATE INDEX、ALTER TABLE ADD FOREIGN KEY 等）的最大内存。默认 64MB。值越大清理和数据恢复速度越快。需要重启数据库。

**动态分配内存：** SQL 执行期间用于临时控制信息和数据。在内存上下文管理下动态分配和释放。大小不可配置。

## 负载测试

### 数据量估算

注意变长数据。键长度可能随数据增长而显著增加，改变列大小假设。持续监控每个对象的空间分配。索引空间增长的最坏情况：使用升序键写入然后从左侧删除大部分行，留下碎片化的空闲空间。熟悉此类场景的在线索引重建工具。

### 负载估算方法

**从同类系统推断：** 专家驱动方法，以现有系统为参考。根据已知差异调整规格。同规模系统效果良好，但参考系统差异一个数量级时可能失效。

**基准测试：** 资源消耗大但有效，可确定实际 IO 需求并在全负载下验证恢复流程。强调对所有系统组件的压力测试。需要丰富的经验才能提取最大价值。

**应用建模：** 数学或启发式估算。未考虑应用低效（SQL 不佳、索引设计不合理、游标管理不当）。容量规划工程师应为潜在低效预留余量；性能工程师应识别并消除低效。

### 测试规则

1. **使用真实数据量和分布**——所有测试必须在完全填充的表上运行，数据具有生产代表性，包括数据量和表基数字段。建立所有生产索引并正确填充模式统计信息。

2. **测试单用户性能**——在空闲或轻负载数据库上验证可接受的性能。如果单用户在理想条件下无法达到可接受性能，多用户在真实条件下也无法成功。

3. **捕获并记录所有 SQL 的执行计划**——获取每条 SQL 的执行计划。验证优化器选择了最优计划，并通过 CPU 时间和物理 IO 揭示相对成本。

4. **尝试多用户测试**——在事务中执行 DML 语句，测试锁竞争或串行化问题。

5. **使用正确的硬件配置**——在尽可能接近生产的配置上测试，特别是网络延迟、IO 子系统带宽、处理器类型和速度。

6. **测量稳态性能**——每次基准测试运行应包括预热阶段（用户连接、逐步开始工作、数据初始化到缓存、一次性操作完成）和冷却阶段（系统释放资源、用户停止工作、断开连接）。

## 部署架构选项

| 架构 | 使用场景 |
|------|---------|
| 应用与数据库同机 | 小规模、开发/测试环境 |
| 应用与数据分离 | 标准生产配置 |
| 缓存层优化 | 读多写少场景 |
| 应用服务器集群 | 高并发 Web 应用 |
| 读写分离 | 读压力远超写入 |
| 分布式数据库 | 超大规模数据 |
