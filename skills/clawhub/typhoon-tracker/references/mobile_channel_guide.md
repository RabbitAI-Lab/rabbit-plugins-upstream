# Typhoon Tracker - 移动端/消息通道适配指南

当部署环境通过消息通道（飞书、微信、钉钉、Web Chat 等）接收和发送响应时，输出受限于纯文本、长度限制和无文件预览。加载此文件获取完整的适配策略。

## 通道能力判断

首先确认当前消息通道的能力：

| 能力 | WorkBuddy飞书 | OpenClaw飞书 | OpenClaw微信 | Hermes/网关 | Web Chat |
|------|-------------|------------|------------|------------|----------|
| 文件生成(Write) | ✅ | ✅ | ✅ | 取决于配置 | ✅ |
| 文件展示(present_files) | ❌ | ❌ | ❌ | ❌ | ✅ |
| 表格渲染 | ⚠️ 差 | ⚠️ 差 | ⚠️ 差 | ⚠️ 差 | ✅ |
| 单条消息长度上限 | ~20KB | ~20KB | ~2KB | 取决于网关 | ~无限制 |
| Markdown支持 | ✅ 基础 | ✅ 基础 | ⚠️ 有限 | ✅ 基础 | ✅ |
| 交互卡片 | ✅ | ✅ | ❌ | 取决于网关 | ✅ |

## 适配原则

1. **结论先行**：前1-3行必须是关键发现，让用户在消息预览就能看到
2. **表格→文字列表**：表格在消息通道中渲染差。将表格改为`[字段]: [值]`格式的键值对列表
3. **单条消息≤500字**：超出则拆分为多条。每条消息自包含（假定用户可能不按顺序阅读）
4. **不引用文件路径**：移动端无法打开文件。需要完整报告时，将核心内容直接嵌入消息
5. **行动导向**：以明确的行动建议结尾（而非"详见报告"）
6. **紧急标记**：如风力或将登陆时间在12h内，消息开头加 `⚠️` 标记

## 表情符号与排版规范（重要——移动端可读性）

**核心原则：减少装饰性 emoji，用序号/符号列表保证清晰。** 移动端页面每行都有 emoji 会显得杂乱，大幅降低可读性。

### 允许使用的符号（白名单）

| 符号 | 用途 |
|------|------|
| `✅` / `❌` / `⚠️` | 状态判断（可行/不可行/注意） |
| `🔴 🟠 🟡 🟢` | 风险等级四级（仅在城市影响、风险等级处使用） |
| `1. 2. 3.` / `-` / `•` | 有序/无序列表序号 |
| `**加粗**` | 关键数字、结论强调 |
| `---` | 段落分隔（可选） |

### 禁止使用的符号（黑名单）

- ❌ 装饰性气象 emoji：`🌪️ 🌧️ ⛈️ 💨 🌀` 
- ❌ 图标类 emoji：`📍 📍 🧭 🎯 🌆 🚦 🔁 ⏰ 🗓️` 
- ❌ 其他装饰：`✨ 🎉 👍 👌` 等

### 排版规则

1. **标题不用 emoji 前缀**：直接写 `台风晨报·白海豚（2613）— 8月6日20时`，不要 `🌪️ 台风晨报...`
2. **段落小标题必须加粗**：每个信息块的字段名用 `**加粗**` 与内容区分，格式 `**位置**：26.6°N...`。这是提高可读性的关键——不加粗会让所有段落连成一片。示例：
   ```
   **位置**：26.6°N、132.0°E（温州偏东约1130km）
   **强度**：强台风级，42m/s（14级）/ 955hPa
   **移动**：西偏北 15-20km/h
   **登陆预测**（置信度：中-高）：9日下午-10日早晨登陆浙江沿海
   **预警**：中央气象台台风黄色预警
   **城市影响**：
   1. 温州（🔴）：...
   **交通状态**：
   - 高铁/航班暂无停运公告
   **行动建议**：
   1. ...
   **下次复查**：8/7白天
   ```
3. **换行用真实换行**：使用 Markdown 真实换行（段落间空行），**禁止输出字面 `\n` 字符串**——飞书会把 `\n` 显示为乱码字符
4. **列表用序号，且同层级统一**：多城市影响用 `1. 2. 3.` 有序序号逐条列出；同层级列表**只使用一种标记**——要么全用有序（`1.`），要么全用无序（`-`），禁止在同一段落中混用。**字段名本身（位置/强度/城市影响/行动建议）不作为列表项，而是作为加粗标题行**
5. **风险等级符号放在文本后**：如 `杭州：9日大到暴雨（🟠）`，不要 `🟠 杭州：...`（首字符 emoji 会占用预览空间）
6. **"度"符号用文本**：经纬度/角度统一用 `°`（标准度符号），不要用其他相似字符；如发现输出乱码，改用文字"度"或直接写 `42m/s`

### 速报模板示例（符合规范）

```
台风晚报·白海豚（2613）— 8月6日20时

**位置**：约26.7°N、131.7°E（温州偏东约1150-1200km）
**强度**：强台风级，42m/s（14级）/ 955hPa
**移动**：西北西 15-20km/h，7日白天进入东海

**登陆预测**（置信度：中-高）：9日晚-10日白天登陆浙江沿海，概率70-75%

**城市影响**：
1. 温州（🔴）：9日12-14级，可能为登陆点附近
2. 宁波（🟠）：9-10日沿海9-11级
3. 杭州西湖/滨江（🟠）：9日大到暴雨、阵风7-9级
4. 上海嘉定南翔（🟠）：7日起持续大风
5. 安徽淮北/淮南（🟡）：10-12日残涡强降雨风险

**交通状态**：
- 高铁/航班暂无停运公告，上海局停运计划窗口预计明日（8/7）开启
- 已停：舟山水上航线、南麂岛转移1764人

**行动建议**：
1. 8/7可出行（选早班）；8/8不建议长途；8/9-10不安排出行
2. 今明两天关注12306邮件，收到停运通知立即退票
3. 杭州西部山区居民提前防范山洪滑坡

**下次复查**：8/7白天（进东海实况 + 停运计划窗口）
```

## 多城市速报

当用户询问多城市时，每条消息一个城市，避免信息混杂。

## 详细报告替代方案

当用户通过移动端要求详细报告，但无法生成和发送文件时：

1. 执行完整分析（三层搜索+判断阶段），将 .md 报告写入可用存储
2. 在消息中回复：核心结论 + 关键数据摘要（≤500字） + 报告已保存的位置提示
3. 如部署环境无文件系统（纯消息通道），将报告拆分为3-4条消息逐条发送：
   - 消息1：核心结论 + 台风实况
   - 消息2：路径预报 + 主要城市影响
   - 消息3：交通评估 + 行动建议 + 复查计划

## 上下文恢复

移动端消息是无状态通道——每条消息独立处理，不自动保留上下文。

**恢复策略（按部署环境选择）**：

| 部署环境 | 恢复方式 |
|---------|---------|
| WorkBuddy | 读workspace `.workbuddy/memory/YYYY-MM-DD.md` + 最近的报告 .md 文件 |
| OpenClaw | 读skill目录 `references/[name]_[编号]_case_data.md` 中的最新数据 |
| Hermes/网关 | 无文件系统时，依赖用户消息中显式引用，通过搜索重建上下文 |
| 通用回退 | 在回复末尾附加简短的数据快照（位置+强度+时间戳），方便下次引用 |

**用户发送"更新"/"继续"/"最新情况"时的处理流程**：

1. 尝试读取存储的最新分析数据（按部署环境选择恢复方式）
2. 如无法恢复上下文：搜索当前台风最新数据，重新生成完整速报
3. 与上次分析对比，仅报告变化
4. 若首次查询或无法对比：明确告知"首次分析，无对比基准"

## 紧急推送通知（选配，需定时任务支持）

| 触发条件 | 推送内容 |
|---------|---------|
| 登陆时间提前>6h | `⚠️ [台风名] 登陆时间提前至 [新时间]，距登陆仅 [X] 小时` |
| 登陆强度升级≥2级 | `⚠️ [台风名] 强度升级至 [新等级]，预计登陆强度 [X] 级` |
| 路径重大变化（>200km） | `⚠️ [台风名] 路径重大变化：从 [旧路径] → [新路径]，[城市] 风险 [上升/下降]` |
| 应急响应升至I级 | `🔴 [城市] 防台风 I 级应急响应！五停措施执行中，立即避险` |
