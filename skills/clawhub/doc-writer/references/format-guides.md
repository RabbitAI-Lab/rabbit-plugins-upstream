# 格式指南：各文档类型的成熟工程经验

本文沉淀各类型的强制性格式经验。编写对应文档前必读对应章节。

## ADR：五种状态管理

### 状态机

```
                 ┌────────────── rejected（已拒绝，存档保留）
proposed ────────┤
（提议中）        └────────────── accepted（已接受，生效约束）
                                  │
                        ┌─────────┴─────────┐
                        ▼                   ▼
                 deprecated            superseded
                 （已废弃）            （已被取代）
                        └─────────┬─────────┘
                                  ▼
                          （新的 accepted ADR 取代它）
```

### 五种状态定义

| 状态 | 含义 | 约束 |
|---|---|---|
| `proposed` | 起草完成，开放讨论 | 应设定决策时限（如两周），到期必须转入 accepted/rejected，不允许永久 proposed |
| `accepted` | 决策生效 | 成为当前有效约束；后续实现必须遵守 |
| `rejected` | 经讨论被否决 | **不删除**。必须保留否决原因，防止重复论证同一条路线 |
| `deprecated` | 曾生效，现不推荐新场景使用 | 必须说明：仍适用的存量范围、新场景的替代方案、退出计划 |
| `superseded` | 被后续 ADR 取代 | 必须在后继 ADR 与本 ADR 双向链接（`supersedes` / `superseded-by`） |

### 强制规则

1. **一决策一篇**：一个 ADR 只记录一个决策。两个选型纠结在一起 → 拆两篇。
2. **不可变原则**：进入 accepted 及之后的状态，正文永不修改；只允许更新状态行、日期与后继链接。想改决策 = 写新 ADR 取代旧的。
3. **rejected 与 accepted 同等重要**：没有"失败的 ADR"这种概念——记录被否决的方案及其否决原因，正是 ADR 防止团队（和 AI）重蹈覆辙的机制。
4. **编号只增不减**：NNNN 递增，不复用已删除 ADR 的编号。
5. **命名**：`NNNN-kebab-case-title.md`，如 `0007-use-event-driven-messaging.md`。

### 状态查询语义（供人类与 AI 检索）

- "当前必须遵守的约束" → 查询 `status: accepted` + `status: deprecated`（后者看存量范围）
- "我们考虑过哪些路线" → 查询全部 ADR（含 rejected/superseded）
- "这个决策的最新版本" → 沿 `superseded-by` 链条找到链尾

## DESIGN：arc42 骨架 + C4 视图

### arc42 章节（模板骨架）

1. 引言与质量目标（质量目标必须是可验证的，如"P99 < 200ms"）
2. 架构约束（技术、组织、法规、标准层面的硬约束，与 ADR 区分：约束是"没得选"，决策是"选了"）
3. 系统范围与上下文 —— 对应 **C4-L1 上下文图**
4. 解决方案策略（总体思路：分层？事件驱动？单体优先？）
5. 构建块视图 —— 对应 **C4-L2 容器图**（第一级）/ **C4-L3 组件图**（第二级）
6. 运行视图（关键场景的运行时行为：时序/通信）
7. 部署视图（节点、环境、部署形态）
8. 横切概念（贯穿全局的机制：日志、鉴权、错误处理、幂等）
9. 架构决策（**ADR 索引**：不复制内容，只列 `ADR-NNNN + 标题 + 状态`）
10. 质量要求（按场景写：负载、性能、可用性、安全）
11. 风险与技术债务（每项附缓解思路与追踪出处）
12. 词汇表（只收本篇高频且易歧义术语；通用术语不收，项目专属黑话必收）

### C4 分级取舍（防止过度画图）

| 级别 | 画什么 | 何时必画 | 何时可不画 |
|---|---|---|---|
| L1 上下文 | 系统 + 外部用户/系统 | 永远 | — |
| L2 容器 | 服务/进程/存储/网关 | 容器数 ≥ 2 或预期会拆分 | 纯单体单进程且短期不拆 |
| L3 组件 | 某容器内部组件 | 容器内部复杂（>7 个模块或多人分工） | 容器内部可自明 |
| L4 代码 | 类/函数 | **不进文档**，由代码表达 | — |

### 图的机器友好写法

- 每个图旁附 Mermaid 源码（AI 可解析），不要只放截图。
- 图中每个元素在图下方的表格中登记：名称、职责、技术栈、对应代码路径。
- 箭头/连线标注协议与数据（HTTP/JSON、gRPC、事件名）。

### doc-class 迁移

- 设计定稿未实现：`doc-class: to-be`，章节以目标架构为主体。
- 实现验收通过：改 `doc-class: as-is`，补 `last-verified`；此后架构变更先改文档再改代码，或同 PR 更新。

## PERSONA：四阶段用户旅程分析框架

### 画像基础

- 背景：角色、职责、技能水平、工作环境、工具链。
- 痛点：与产品相关的前 3-5 个痛点，每个痛点给出场景证据（访谈/数据/工单），**无证据的痛点标注"假设待验证"**。
- 目标：用户想完成什么（任务目标）与想成为什么（情感/成长目标）。

### 四阶段旅程（每阶段必填五要素）

| 阶段 | 回答的问题 | 五要素 |
|---|---|---|
| **1. 认知/发现** | 用户如何意识到问题与解决方案的存在？ | 场景、行为、触点、情绪、机会点 |
| **2. 评估/决策** | 用户如何比较、试用并决定采用？ | 同上 |
| **3. 使用/实施** | 用户如何上手并进入日常使用？关键卡点在哪？ | 同上 |
| **4. 沉淀/传播** | 用户如何获得价值、留存、复用并推荐他人？ | 同上 |

- **触点**：用户与产品/团队接触的具体渠道（搜索、文档、CLI、群聊、告警）。
- **情绪**：该阶段的典型情绪（挫败/好奇/满意/流失风险），标注情绪低谷——那是设计机会。
- **机会点**：产品/文档/流程可改进处，逐条链接到 PRD 需求或 ROADMAP 条目。

### 纪律

- 一个 PERSONA 文档只写一个画像；多画像拆多篇。
- 旅程必须按时间顺序完整走完四阶段，禁止只写"使用"阶段。
- 每条结论可追溯到证据；AI 生成的画像同样遵守——标注哪些是推断。

## RUNBOOK：强制四段式

| 段 | 内容要求 |
|---|---|
| **1. 前提条件** | 权限/角色要求；工具与版本；环境变量与配置；备份状态；影响范围与需通知的人；预估时长 |
| **2. 操作步骤** | 原子化编号步骤；命令可直接复制执行；占位符用 `{{尖括号}}` 显式标注；破坏性操作（删除/覆盖/停服）加 `⚠ 危险操作` 标记与确认点 |
| **3. 验证** | 每个关键步骤后的期望输出；整体完成判据（怎么知道成功了）；验证命令同样可直接执行 |
| **4. 故障排查** | 按"症状 → 可能原因 → 处置手段"组织；含回滚方案；常见错误码/报错文案 |

### 强制规则

- Runbook 是 as-is 文档：描述**现有**系统的操作；流程变更时同步更新，旧流程不保留在同篇中（历史进 PROGRESS）。
- 步骤必须经过至少一次实际执行验证后才能标记 `status: active`；未验证的标 `draft`。
- 每个命令写清"在哪执行"（本地/跳板机/容器内/某命名空间）。

## ROADMAP：当前迭代与待办强制分离

### 双区结构（+第三区）

1. **当前迭代 Current**：已承诺事项。每项含：目标、完成标准、关联（PRD 条目/RETRO 行动项）、跟踪（PROGRESS 链接）、负责人。**进入即承诺**，事项有 WIP 约束（建议 ≤ 5）。
2. **待办 Backlog**：按优先级排序的候选池。每项标注**来源**（PRD-xxx / RETRO 行动项 / 战略目标）与价值/成本粗估。**待办不是承诺**。
3. **Later / 已拒绝**：暂缓事项与明确不做的事项；拒绝的保留原因（同 rejected ADR 逻辑）。

### 流转规则

- 待办 → 当前迭代：移动时建立 PROGRESS 跟踪，这是"承诺"动作的全部含义。
- 当前迭代完成 → 事实落在 PROGRESS/RETRO，ROADMAP 只保留状态标记，不复述过程。
- 迭代结束时：未完成事项明确去向（留续 / 回 Backlog / 拒绝），不允许"永远差一点"的僵尸条目。

## PRD：补充要点

- 需求 ID 规范：功能需求 `FR-NNN`，非功能需求 `NFR-NNN`；ID 一经分配不复用。
- 验收标准（Given-When-Then）归 REQ-SPEC（`docs/project/req-spec.md`，唯一真值源）：Given（前置状态）When（动作/事件）Then（可观察结果）；PRD 不复制 GWT，只保留需求摘要并链接对应 FR 条目。
- 成功指标表列：指标名、定义与测量方式、基线、目标值、测量来源。缺基线时写"待建立基线"并进入当前迭代。
- 需求边界三件套缺一不可：in-scope、out-of-scope、non-goals（明确不追求的价值，防止范围蔓延的"我不做"声明）。

## PROGRESS / RETRO / TECH：补充要点

- **PROGRESS**：按日期倒序或正序**固定一种**；每条含"做了什么/产出链接/临时决策/阻塞"；当天记录，不攒批。
- **RETRO**：行动项格式 `行动 → 去处 → 责任人`；去处必须是 ADR/ROADMAP/TECH/RUNBOOK 之一；全部外发后 RETRO 才能标记关闭。
- **TECH**：一主题一篇；标题即结论（"在 X 场景下应使用 Y 而非 Z，因为 Z 会导致 W"优于"关于 X 和 Y 的笔记"）；必须写"适用范围与限制"——没有边界说明的知识是隐患。
