# 试运行指南

## 试运行的目的

不是"测试 Skill 能不能跑"，而是"测试 Skill 跑出来的东西对不对"。

## 试运行样本选择

**选择标准：**
- **真实任务** — 不是编造的测试用例，是用户真正要做的事
- **中等复杂度** — 不是最简单的（测不出问题），也不是最复杂的（太慢）
- **覆盖主要分支** — 至少走到一条主要路径

**反模式：**
- ❌ 用最简单的用例试运行 → 测不出边界问题
- ❌ 用编造的数据试运行 → 和真实场景脱节
- ❌ 一次测所有分支 → 太慢，且问题难以定位

## 试运行清单

```markdown
## 试运行报告 — [Skill 名称]

**样本：** [描述使用的测试样本]

### 阶段检查

- [ ] Phase 0：触发是否正确？
- [ ] Phase 1：输入标准化是否完整？有无信息丢失？
- [ ] Checkpoint 1：确认项是否完整？人类是否能理解？
- [ ] Phase 2：构建是否顺利？产出是否符合预期？
- [ ] Phase 2+：质检是否发现了真问题？
- [ ] Checkpoint 3：交付流程是否完整？
- [ ] 状态文件：中断后能否恢复？
- [ ] 文件结构：是否清晰有序？

### 发现的问题

| # | 阶段 | 问题 | 严重程度 | 修复方案 |
|---|---|---|---|---|
| 1 | [阶段] | [问题描述] | 高/中/低 | [方案] |

### 修复记录

| # | 问题 | 修复内容 | 验证结果 |
|---|---|---|---|
| 1 | [问题] | [改了什么] | PASS/FAIL |
```

## 迭代原则

1. **每次只修一个问题** — 不要一次性改所有东西
2. **修 bug 而不是重设计** — 除非发现根本性设计缺陷
3. **修完必须重新跑** — 验证修复是否生效
4. **记录所有问题** — 即使已修复，也要记录到试运行报告
