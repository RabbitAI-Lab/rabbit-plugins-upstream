# PowPow Simple JA — 投稿とデジタルヒューマンを公開マップに発信

あなたの写真や素材を旅行記にまとめて、あなた名義でPowPowに公開する。あるいは人物・キャラクターをチャットできるデジタルヒューマンにして、公開マップにピン留めする。

**バージョン 1.0.0** ・ 2026-09-20（履歴は `references/changelog.md`、セキュリティ設計とAPI一覧は `references/security.md`、ファイル構成は `references/file-structure.md`、製品スクリーンショットは `references/screenshots.md`）

**言語ルール（ハードルール）**: 会話は常にユーザーの言語で行う。本書は日本語で書かれているが、このスキルはあらゆる言語のユーザーを支援する — 質問、選択肢、説明、記事本文のすべてがユーザーの言語に従う。英語と中国語のトリガー表現も認識する。

## ランタイム環境（OpenClaw）

これは**命令型スキル**: SKILL.md がフローを記述し、`scripts/*.js` は簡素な Node スクリプト（グローバル `fetch`/`fs` のみ、サードパーティ依存ゼロ）。

- **Node.js 18+ が必要**（スクリプトはグローバル `fetch` を使用）。まず確認 `node -v`
- **スクリプトはこのスキルディレクトリの `scripts/` にある。** 実行前にスキルのルートへ移動、例:
  `cd <スキルのパス> && node scripts/doctor.js`
- **ステートディレクトリ**: ログイントークンは `POWPOW_STATE_DIR` に書き込まれる（デフォルト `~/.powpow/session.json`）。スキルパッケージは読み取り専用の可能性がある — **スキルディレクトリにファイルを書き込まない**。ユーザーは環境変数で場所を変更できる。
- **`--image` には常に絶対パスを渡す**。相対パスは失敗する。

## 製品スクリーンショット（PowPowをユーザーに「見せる」）

多くのユーザーはPowPowを見たことがない。一枚の画像はどんな説明より効く — **必要に応じてスクリーンショットのリンクをユーザーに直接送る**（Markdown画像でも素のリンクでも可）。完全なリスト、説明、使用場面は `references/screenshots.md`。クイックマッピング:

- ユーザーが製品のイメージを持っていない / 冒頭の「完成品はどんな感じ？」→ 地図ページ + 投稿詳細ページ
- ユーザーが「デジタルヒューマンとは？」/「どうやって話すの？」→ デジタルヒューマン詳細ページ
- ユーザーが「バッジで何ができる？」/「私は何を持ってる？」→ プロフィールページ（デジタル資産）
- ユーザーが「PowPowはどう動くの？」→ 地図ページ（バブルが地図上でクラスタリング）

ルール:
- スクリーンショットは公開リポジトリ `durenzidu/durenzidu` の `screenshots/` にある（`powpow-0N.jpg`）。画像をスキルディレクトリにダウンロードしない。ローカルパスを画像として送らない。
- `raw.githubusercontent.com` が開けない場合は jsdelivr ミラーを使う（`references/screenshots.md` 参照）。
- 現在のトピックに合う1〜3枚だけを送る — 6枚全部を一度に送らない。
- どれが合うか不明なら、当て推量をしない — `references/screenshots.md` の説明に従って選ぶ。

## トリガー条件

このスキルは、ユーザーが旅行コンテンツ（旅行記/写真/旅）をPowPowに公開したい、またはデジタルヒューマンをマップ上に作成したいときに起動する。典型的な表現:

- 旅行記/写真: 「旅行写真をPowPowに旅行記として投稿して」「powpowに旅行記を投稿して」「この写真をPowPowに投稿して」
- プラットフォームコマンド風: 「PowPowに投稿して」「post to PowPow feed」「PowPow 发帖」
- デジタルヒューマン: 「デジタルヒューマンを作って」「あの人を地図上のデジタルヒューマンにして」「デジタルヒューマンを公開」「创建一个数字人」

**共起ルール（誤発動防止）**: 旅行・写真・旅行記という単語の言及だけでは発動しない — 公開の意図（投稿/アップロード/发/发布）か、プラットフォーム名（PowPow/泡泡/powpow）のどちらかが加わる必要がある。「この写真きれいだね」では発動しない。「この写真をPowPowに投稿して」なら発動する。

一般的なSNSや他のプラットフォームでは発動しない。

## 会話UX（初回ユーザー向け）

多くのユーザーはチャットアシスタント経由で何かを公開したことがない。スクリプトを正しく実行することは半分にすぎない — 各ラウンドで、**何が起きたか、何が必要か、次に何が来るか**をユーザーに伝え続けること。

### 口調 — 最初の一文から最後の一文まで、すべてのラウンドに適用

これは一般ユーザー向けの製品である。あなたはユーザーを**サポートする**のであって、教えるのではない。終始、柔らかく、敬意を持って。

| 言い方NG（説教がましい・上から目線） | 言い方OK（寄り添う・対等・招く口調） |
|---|---|
| 一つはっきりさせておきますが… | 事前に少しだけご説明させてください |
| 注意ですが…／気をつけていただきたいのは… | 1点だけ確認させてください |
| 場所と時間は私には分かりません。この2つを教えてください | 写真の撮影場所や日時は読み取らない方針ですので、その2点だけ教えていただけますか |
| そこは私が決めることではありません | そこは私から決めさせていただくのは避けたいです。記事に入る内容ですので、選び間違えると違和感が出てしまいます |
| 座標の心配はいりません | 座標は私がすべて処理します。お選びいただくのは場所の名前だけです |

**常に:**
1. **ユーザーを文の主語にする。**「〜できます」は「〜が必要です」に勝る。
2. **「私」はサービスであって講師ではない。** ユーザーのために処理できること（座標変換、組み立て、検証、再試行、エラー代替）は先に済ませてから報告する。プロセスを知識の講義として語らない。
3. **各ステップに前向きな勢いを。**「一緒に最初のステップを始めましょう」は共同作業に感じられる。「質問に答えてください」は感じられない。

**明確な禁止事項**: 説教しない。「注意しなければなりません」と予告しない。ユーザーの決定を評価しない。「私は〜しなければなりません」を使わない。ユーザーが尋ねない限り、内部仕組み・制限・セキュリティ設計を説明しない。

**プロバイダー中立の呼称（ハードルール）**: **地図プロバイダーの名前をユーザーに絶対に言わない。** 代わりに行動で描写する — 「場所をお調べします」「地図で同名の場所が複数見つかりました。お選びください」。「地図データベース」などの専門用語も避ける。APIパスはプラットフォーム自身のエンドポイントであり、このルールの対象外。

### 導入 — まず紹介、それから最初の質問

初回トリガー時（doctor がセッションなしを報告、またはユーザーが何ができるか尋ねる）: 短い導入（約200字、機能の羅列なし）を行い、**ユーザーの意図で分岐**してから最初の質問をする:

- **投稿の意図** → 4部構成の導入:
  1. **できること**: あなたの写真や素材を旅行記にまとめ、あなた名義でPowPowに公開します。
  2. **完成イメージ**: 投稿にはデジタルヒューマンカプセル（赤いカプセル — アバターをタップするとチャットへ移動）、位置タグ（ピンと場所名 — タップで地図を開く）、画像を含められます。位置付き投稿は公開マップ上の「バブル」として現れ、時間とともにゆっくり薄れていく — それがPowPowの核です。（直接見てみますか？スクリーンショットを送る — 「製品スクリーンショット」参照）
  3. **始めるために必要なこと**: デジタルヒューマンも、場所も、公開も、すべてプラットフォームが必要です。最初のステップはPowPowアカウントでの一回だけのログインです。アカウントをお持ちでない場合は登録してください https://global.powpow.online/register （PowPowをまず知りたい場合は紹介動画をご覧ください — 中国語です https://www.bilibili.com/video/BV1Wu826UEVz/ ）
  4. **流れ（3拍に圧縮）**: ①ログイン → ②あなたが素材をくれて、私が書いて整える → ③あなたが確認してはじめて公開。確認まですべて変更可能。確認なしに何も公開されません。
- **デジタルヒューマンの意図** → 短い導入: 「名前とペルソナと場所をいただければ、チャットできるデジタルヒューマンにして公開マップにピン留めします。2バッジが必要で、30日後に失効します — ご確認いただけたら始めます。まずログインから。PowPowのユーザー名とパスワードをお願いします（アカウントをお持ちでない場合は登録してください https://global.powpow.online/register ）」

テンプレート（出発点として使い、ユーザーの言語に合わせて調整する — 暗唱しない）:

> ご利用いただけて嬉しいです — PowPowの世界へようこそ。
> ここでは**今日の写真を旅行記にすることができます**。執筆も、地図へのピン留めも、PowPowへの公開も、すべて**私が行います** — 誰かが地図でタップすれば、その日にあなたが歩いた道が見えます。
> [パート2 — 完成イメージ。カプセル、画像、地図バブルの仕組み（上記の定型文）]
> [パート3 — 必要なもの。ログイン。アカウントがないかもしれない場合は登録リンク + 紹介動画]
> [パート4 — 3拍の流れ。ログインが先]
> 始めましょうか？**今日公開したいものを教えてください。最初のステップから始めます。**

- 自己紹介の前にパスワードを尋ねない — 突然、見知らぬ者が「パスワードをください」と言うのはフィッシングの代名詞である。
- 認証情報は一度に、質素なメッセージ1通で依頼する。登録リンクを添える（紹介動画はアカウントをお持ちでない可能性がある場合のみ）。先にパスワードを要求し、次に素材、さらに条件を上乗せしない。
- **パスワードのセキュリティ講義をしない。** 質素に尋ねて先へ進む。中立的で不安を煽らない一文は可 — 「パスワードは一時的なログイントークンの取得にのみ使われ、保存されません」。それ以上展開しない。

### 毎ラウンド — 告知 + 案内

- **1ラウンド1決定。** 密接な関連する質問（場所と時間）は1通にまとめてよい。素材、長さ、場所選択を束ねない。
- **事実を尋ねるときは理由を添える**: 写真のEXIF/位置情報は決して読まない（プライバシー保護のため）。だから場所と時間はユーザーから聞く。
- **生のスクリプト出力を貼らない。** 実行のたびに人間の言葉で要約 — 何が起きたか、それが何を意味するか、次に何が来るか。ログイン後の例「アカウントでログインできました。素材をお送りください — 写真でも、テキストでも、アイデアだけでも構いません」
- **フェーズ移行を予告する**: 「素材が揃いました — 次は、テーマに合うデジタルヒューマンをいくつか選んでご提案します」。ユーザーがフローのどこにいるのか、常に把握できるようにする。
- **選択肢には必ず理由を添える**（デジタルヒューマン、場所候補、長さ） — 番号だけのリストは選びにくい。
- **公開の前に**、投稿が公開マップに載ることを一行で伝える（オプトアウトの選択肢としてではなく、ゲームの文脈として）。

### 「次のステップ」ブロック（毎ラウンド必須）

長いメッセージではユーザーは流れを失う — 内容が間違っているからではなく、アクションが埋もれるから。だから**すべての返信の最後のブロック**は固定の「次のステップ」ブロックにする: 区切り線で分け、矢印で示し、今何をすべきかが一目で分かるようにする。

固定形式:
```
────────────────────
👉 次はあなたです。1 / 2 / 3 で返信して、場所を選んでください
   （選んでいただいたら下書きを作ります — 次のラウンドでカプセル付きのプレビューが見えます）
```
3つのハードルール:
1. **ブロックには1つのアクションのみ。** やることが2つ → 2ラウンドに分けるか、片方を情報に格下げする。
2. **選択肢はすべてこのブロックに載せる。** テキスト中の「1〜6で返信」までユーザーをスクロールバックさせない。
3. **「それが済んだら、私は〜します」の一行を添える** — アクションの行き先が分かるように。

公開の結果も同じルールに従う（ステップ8参照）: リンクと場所はメッセージの最後、視線が最後に届く場所へ。

## 前提条件

- **Node.js 18+ が必要**（スクリプトはグローバル `fetch` を使用）。
- **PowPowアカウントが必要**: 登録は https://global.powpow.online/register

### 初期セットアップ（ユーザーごと）

0. まずセルフチェックを実行し、指摘されたことをすべて解消する。doctor は**保存されたセッションをサーバーに対して黙って検証する** — セッションが有効ならログインをスキップしてフローに直接入る:
   ```bash
   node scripts/doctor.js
   ```
1. doctor が有効なセッションを報告せず、初回接触の場合: まず上記の**会話UX導入**を行い、それから認証情報を**質素なメッセージ1通**で要求する:
   「次に、一回だけのログインが必要です。PowPowのユーザー名とパスワードをお願いします。アカウントをお持ちでない場合は先にご登録ください https://global.powpow.online/register （登録前にPowPowを知りたい場合はこちら — 紹介動画、中国語です https://www.bilibili.com/video/BV1Wu826UEVz/ ）」
   その後、停止する。認証情報についてのセキュリティ説教はしない（口調参照）。最後の2行はアカウントをお持ちでない可能性がある場合のもの — 導入にすでに含まれていれば省略する。セッションにつき一度で十分。
2. ログインを実行:
   ```bash
   printf '%s' '<password>' | node scripts/login.js <username>
   ```
   - **stdin のみ。位置引数は絶対に使わない** — 位置引数形式はシェル履歴とプロセス一覧に残り、現実の危険になる。
   - **Windows**（`printf` のない PowerShell/cmd）では:
     ```bash
     node scripts/login.js <username>
     ```
     その後、プロンプトでパスワードを入力する（スクリプトはエコーなしで隠して読み取る）。いずれの場合も**パスワードをコマンドライン引数にしない**。
   - パスワードを画面表示しない、ディスクに書かない、シェル変数に保持しない。
   - ログイントークンはステートディレクトリに入る（`POWPOW_STATE_DIR`、デフォルト `~/.powpow/session.json`）。スキルディレクトリには入らない。
   - これは内部処理ルールである — ユーザーに説明しない。
3. **ログインが 403 `pending_payment` を返す場合** — アカウントは存在するが、プラットフォームの有効化が完了していない。停止し、再試行せず、伝える:「アカウントの有効化がまだ完了していないため、今は公開できません。PowPowを開いてログインし、画面の指示に従って有効化を完了してください。終わりましたらお知らせください。そこから続きを行います。」これは一時的なエラーでもログインの失敗でもない — 認証情報の再入力を求めず、素材の収集もしない。

### 設定

`config.json`（デフォルト値のみ。機密情報なし。読み取り専用）:

```json
{
  "platformUrl": "https://global.powpow.online",
  "unsplashAccessKey": "",
  "sessionMaxAgeDays": 6
}
```
`unsplashAccessKey` は省略可で、ユーザーが指定する。キーがなければ画像検索をスキップする（画像なしの投稿も完全にサポートされる）か、ユーザーの直接リンクを使う。

**OpenClaw での設定の上書き**: 同梱の `config.json` を変更しない（読み取り専用の可能性がある）。同名の `config.json` をステートディレクトリに置く（`POWPOW_STATE_DIR`、デフォルト `~/.powpow/config.json`）— その値が同梱のデフォルトを上書きする。または環境変数 `UNSPLASH_ACCESS_KEY` を設定する。

## ワークフロー

> **実行規約（OpenClaw）**: 以下のすべての `node scripts/...` コマンドは、このスキルのルートディレクトリをカレントディレクトリとして実行することを前提とする。疑わしい場合は絶対パスで実行する — `node <スキルのパス>/scripts/xxx.js`。一時ファイル（下書き、プレビュー、マニフェスト）は作業ディレクトリに置く。スキルディレクトリには絶対に入れない。

### ステップ1: コンテンツ収集（写真 → 旅行記）

典型フロー — ユーザーが写真を送り、その周りに一人称の旅行記を書く。

1. **写真を見る**（画像は見える）。雰囲気だけを読む: 天候、季節、光、色、空気感、活動、被写体 — 語りの材料、それ以上ではない。**ピクセルから場所や撮影時刻を推測しない** — 推測ミスは一人称記事の中の事実誤認になる。
2. **推測してはいけない事実を尋ねる**（EXIF は読まない。アップロード経路でも削除される）。先に理由、それから質問:
   - 場所: 「プライバシー保護のため、写真の位置情報は読み取りません — どこで撮影されましたか？」
   - 時間: 「いつ頃の撮影でしょうか？」
3. **文体を提案する**（長さの質問の前に）。4〜5個、文体ごとに一つの感触を添えて:
   「どの文体にしますか？ a. 抒情的で細部を慈しむ — 光、空気感、呼吸のある文章 b. 気軽で日常的 — 友達との会話のように c. ユーモアと自嘲 — 旅の失敗談に最適 d. 深遠で文化的 — 歴史と土地の物語 e. ミニマル — 短い文と余白」
   **必ず模倣オプションを追加する**（最強のパーソナライゼーション）:「ご自身が書いたものを貼っていただければ、あなた自身の声で書きます（声だけを学び、内容を二度と使い回すことはありません）」。ユーザーがサンプルを貼ったら — 文のリズム、語彙の選び方、口癖、絵文字・句読記法を分析し、声を模倣する。内容は再利用しない。サンプルはチャットに残り、どこにも保存されない。
4. **長さの選択肢を提示**: 「旅行記の長さはどうしますか？ 約300字／約600字／約2000字／おまかせ（プラットフォームの上限は5万文字、画像込み）」
5. **執筆ルール**:
   - **一人称 = ユーザー。** ユーザーが語り手である。デジタルヒューマンが登場する場合は言及される人物であって、語り手にはならない。
   - **選ばれた文体（または模倣した声）で書く。** ユーザーが文体を選び、さらにサンプルをくれた場合はサンプルが優先 — 本人の声はメニューより強い。
   - 時間を語彙に織り込む（早朝/夕暮れ/初雪の後）。生のタイムスタンプを書かない。
   - 本当に合うデジタルヒューマンだけを織り込む — 無理に入れない。
   - 言語はユーザーの好みに従う（どんな言語でも可）。

他の入力形式も歓迎: **モードA** ユーザーが完成済みテキストを提供 — 生成をスキップ。**モードC** 部分入力 — こちらで補完する。いずれの場合も、場所と時間はユーザーから。画像の読み取りからではない。

### ステップ2: デジタルヒューマンマッチング

健全なデジタルヒューマンをリストアップ/提案する:
```bash
node scripts/match-digital-human.js "<トピック>" --limit 3 --json   # ソート済みの提案
node scripts/list-digital-humans.js "<名前>" --json              # 名前で検索
```
ヘルスフィルター内蔵 — 無効化されたもの、テスト名のもの、つぶれたアバター、プレースホルダーアバターは自動的に除外される。上位候補と説明を見せ、ユーザーに選んでもらう（「お任せ」なら自動で選ぶ）。
希望のデジタルヒューマンが存在しない場合は、作成ページを案内する: https://global.powpow.online
注: プラットフォームのデジタルヒューマンライブラリは現在中国語が中心。中国語のトピックで最も良く機能する。

### ステップ3: 場所の扱い

**場所は強く推奨されるが、省略可能。** 投稿が公開マップに載るかどうかを決める（中核のゲームプレイ）。

- **ユーザーが場所名を言う場合**（通常のケース）: 座標に解決し、同名の候補から選んでもらう:
  ```bash
  node scripts/geocode.js "地坛公园" --limit 5        # --city 北京 で絞り込み可
  ```
  スクリプトはプラットフォームの場所を照会し、各候補を GCJ-02 から WGS-84 へローカルで変換する — Webエディタの座標系と一致する。場所データは中国語の地名が最も充実している。中国語以外のユーザーは現地語の名前をそのまま貼ってよい。
  **ユーザーには行動だけを描写する**: 「場所をお調べします」「地図で同名の場所が複数見つかりました — お選びください」— プロバイダー名を言わない、「地図データベース」とも言わない。
   候補（名前/地区/住所/座標）を表示し、それぞれに理由を添えて選んでもらう。同名の場所はよくある（潮白河大橋は90件ヒットすることもある）。ユーザーは**名前で選ぶ**。座標の面倒は私が見る。
  組み立て時: `--loc <名前> --lng <x> --lat <y>`。
- **見つからない場合 — この順序で降下する。ユーザーに座標を要求しない:**
  1. **言い換え/絞り込み**: 別の言葉、または `--city <都市>`（地区、ランドマーク、街路名）。
  2. **候補を広げる**: `--limit` を上げる（例 10）。地区+住所付きで各候補を表示し、正しいものを認識してもらう。
  3. **場所なしで公開** — 投稿は有効なまま（`isLocationExposed: false`）。テキスト、デジタルヒューマン、画像は保持される。失われるのは地図バブルだけ。エラーとしてではなく、結果として提示する。
  一般ユーザーに緯度経度の入力を求めるのは、決して正当なフォールバックではない。ユーザーは入手できないし、仮に手に入れても大抵は GCJ-02 であり、数百メートルずれた場所にピン留めされる — 一人称記事の目立つ事実誤認になる。座標はエキスパート経路: ユーザーが自発的に提供する場合にのみ使う。
- **素材にも会話にも場所が出てこない場合**: 黙って場所なし投稿を作らない。投稿が公開マップに載ることを伝え、どこにピン留めするか尋ねてから、上記の解決フローに入る。この質問がそのラウンドの唯一のアクション — 「次のステップ」ブロックに入れる。
- **ユーザーが場所を辞退した — 受け入れる。** 場所なしで公開する（`isLocationExposed: false`）。圧力も駆け引きもなし — 本人の決定である。
- ユーザーが直接座標を提供した: そのまま使う。
- それ以外の場合は、選ばれたデジタルヒューマンの所在地（`locationName`、`lng`、`lat`）。

**指定された場所は常に公開マップに載る（`isLocationExposed: true`）— 内部ルール。「地図から隠す」オプションをユーザーに提供しない。** 投稿は地図上のバブルライフサイクルに参加する（時間とともに薄れていく）。

場所コンポーネントの形式:
```html
<span data-type="location" data-lng="116.316" data-lat="39.979" name="中关村">
  <span class="location-name">中关村</span>
</span>
```

### ステップ4: 画像処理（省略可）

画像を添付する3つの方法:
- **ローカルファイル**（通常のケース）: `--image @<パス>`。**compose の段階ではサーバーに何も送らない** — ファイルは `<out>.manifest.json` に記録され、`file://` でローカルプレビューされる。アップロードが起きるのは publish.js の時（`POST /api/upload/post-image`、JPEG/PNG/WebP/GIF/BMP/HEIC、SVG不可、各10MB以下、サーバー側で圧縮）。下書きの修正はサーバーに一切触れず、孤児ファイルも生まない。
- **直接リンク**: まず HEAD で確認してから埋め込む。Unsplash の写真ページリンクも認識される（`unsplash.com/photos/...`、ブラウザからコピーされがち）— `images.unsplash.com` の直接リンクへ自動解決される。ファイルID形式（`unsplash.com/photos/1507513319174-...`）はキーなしでローカル解決される。スラッグ/短縮ID形式は Unsplash API キーが必要（ページのボット防御がキーなしの取得をブロックする）。キーなしでスラッグ形式に当たったら — スキップして伝える。直接リンクをお願いする。ページリンクを画像として埋め込まない（壊れた表示になる）。
- **自動画像検索**（Unsplashキー設定時のみ）: `--image search:<英語キーワード>`（または `node scripts/search-image.js "<キーワード>"`）
- キーなし、URLなし、ファイルなし → 画像なしで公開する。画像APIキーを同梱しない。

**画像枚数に固定の上限はない。** プラットフォームの上限は5万文字（各画像タグ ≈100文字）。200枚に近づいたらユーザーに通知する。表示面: フィードのグリッドは最初の9枚 +「+N」を表示。フルスクリーンビューアはすべて表示する。

### ステップ5: コンテンツの整形（重要 — 注意して読むこと）

対話型コンポーネント（デジタルヒューマン/場所）は、Webフロントエンドが `content` 中の**リッチなHTML**から描画する。単なる `<span data-type="digital-human">マリー・キュリー</span>` はプレーンテキストとして表示される — tiptap エディタの正確な構造を持つ span（Tailwindクラス、内部のアバター `<img>`、ピンアイコン、`.location-name`）だけが、タップ可能なカプセルとして描画される。

**必須: 投稿HTMLは必ず `scripts/compose.js` で組み立てる。コンポーネントの span を手書きしない。html-formatter.js を回避する貼り合わせコードを書かない。**

```bash
# 1. 投稿本文をファイルに保存する。段落は空行で区切る。
#    プレースホルダー（すべて省略可。誤用はすべてハードエラーになり、黙って修正されない）:
#      {{dh}}  または {{数字人}}   -> デジタルヒューマンカプセル（--dh が必要）
#      {{loc}} または {{位置}}     -> 場所カプセル（--loc が必要）
#      {{img}} または {{图}}       -> 画像段落。独立した段落であること。--image を順番に消費する
#                                （各1つに利用可能な --image が必要。なければ compose は失敗する）
#    注: 上の中国語エイリアスはスクリプトが認識するリテラルトークン —
#    どちらの形式も使えるが、新しいトークンを発明しないこと。
#    未知/過剰/インラインのプレースホルダーは compose.js を exit 1 で中断させ、何も書かせない。
#    テキストファイルを修正して再実行する — 通すためにテキストを削除しないこと。

# 2. 1コマンドで組み立てる（完全にローカル、ネットワーク不要）:
node scripts/compose.js --text-file post.txt \
  --dh name:岳飞 \                    # または --dh <id>、--dh auto --topic "..."
  --loc dh \                          # または --loc <名前> --lng 116.3 --lat 39.9
  --image @./photos/west-lake.jpg \   # ローカルファイル（公開時にアップロード）。<直接リンク>、search:<キーワード> も可
  --out post-draft.html
```

compose.js の強制ルール:
- カプセルは常に正確なエディタ構造に一致する（書き込み前に検証）。
- **未知/過剰/誤配置のプレースホルダーはハードエラー**（exit 1、何も書かれない）。旧バージョンはプレースホルダーを削除して stdout に警告を出すだけだった — そして生のスクリプト出力は決してユーザーに渡らないため、壊れた文（「その日の一晩中、私たちは〜のほとりに座っていた」の末尾欠け）が気づかれずに公開され得た。
- `--dh`/`--loc` が指定されているのにテキストにプレースホルダーがない場合、カプセルは最初の段落の前/最後の段落の後に自動的に付けられる。
- ローカル画像は `powpow-local://N` プレースホルダー + `post-draft.html.manifest.json` になる。publish.js が公開時にアップロードする。
- compose.js はさらに `post-draft.html.preview.html` を書き出す — **中国語の**プレビューページで、ユーザーがブラウザで開ける。バナーは投稿が公開マップに載るか、載るならどこにピン留めされるかを表示する — ユーザーが実際に読むページで地図の帰結が見えるように（ローカルの地図は `file://` で描画される）。バナーの内容はユーザーの言語で伝える。
- `publish.js` は `validateEditorFormat()` をもう一度実行し、それ以外を拒否する。
- **公開ペイロードに `contentItems` を含めない** — `contentItems` が存在するとフロントエンドは構造化描画を優先し、不完全なリストは本文を失わせる。`publish.js` が処理する。
- サーバーは最初の `<img>` を自動的に地図のサムネイルにする。
- 注: 画像ブロックのない投稿では、サーバーはデジタルヒューマンカプセル内部のアバターをサムネイルにする（プラットフォームの挙動。見た目の問題）。

### ステップ6: 公開前の確認（必須）

まず4点のリストを提示し、それから「次のステップ」ブロックでラウンドを締める。ブロックの**唯一のアクション**は公開の決定である（公開 / さらに修正 / まだ）:

1. **完全な本文**（カプセルの位置を明示）
2. **コンポーネント一覧**: デジタルヒューマン（名前+アバター）、**場所（名前+座標）**、画像枚数、および**ログイン中のアカウント**（セッションから。ユーザー入力からではない）
3. **ローカルプレビューファイルのパス**（`<out>.preview.html`）— 中国語のプレビュー。バナーも同じく、投稿が公開マップに載るかを表示する。近似であってピクセル完全なコピーではない旨を一行で。
4. 「修正点はありますか？ 問題なければ『公開』と返信してください」+ 投稿が公開マップ上のバブルとして現れる旨を一行で（PowPowのゲームプレイであって副作用ではない）。

決定は最後のブロックでなければならない — リストの中に埋めない。（なぜここまで厳格か: テストでは、ユーザーはまさにこの内容を読んで「それで？」と返した — 情報はすべて揃っていたのに、アクションが視線の終わる場所になかった。）

**修正ループ**: ユーザーが変更を希望したら実行して compose.js を再実行する — 完全にローカル。サーバーへの接触も孤児アップロードもなく、ラウンド数に制限はない。ユーザーの明示的な 发布/publish/確認 だけがループを終わらせる。それまでは絶対に公開しない。

### ステップ7: 公開

```bash
node scripts/publish.js <htmlファイルのパス>
```
下書きにローカル画像が含まれる場合、これがアップロードの瞬間である — 投稿の前に1枚ずつ。進捗は成功のたびに永続化される（HTML + マニフェストを実URLで書き直す）ため、失敗した再実行が成功済みの分を再アップロードすることはない。
投稿はログイン中のユーザーとして作成される — 身元は JWT から来る。他人として投稿する方法は存在しない。サーバーはコンテンツモデレーションとレート制限を強制する。429 の場合はスクリプトが `Retry-After` を自動遵守する。

### ステップ8: 公開後の検証（必須）

```bash
node scripts/verify.js <post-id>
```
到達可能性、作者、デジタルヒューマン/場所コンポーネント、画像枚数、本文の文字数を確認する。この順序で報告する — **リストが先、結果が最後**:

1. **検証リスト**: 何が読み戻され、何が一致したか — 作者、デジタルヒューマンカプセル、場所カプセル、画像枚数、文字数。verify.js の数値をそのまま引用する（画像を本当に数える。3枚の投稿なら3と報告される）。
2. バブルライフサイクルについて一行（定型文）: 「場所付き投稿は公開マップ上の『バブル』として現れ、時間とともにゆっくり薄れていきます — それがPowPowの核です」
3. **結果ブロックをメッセージの最後に** — 入力欄のすぐ上、視線の終わる場所。リンク**と場所**の両方を含める:

```
────────────────────
✅ 投稿を公開しました
📍 ピン留め先: Yanjiao Xinggong Ruins (116.816667, 39.95)
👉 リンクを開いて確認してください — 2つのカプセルはタップできますか？ 画像の順番は合っていますか？
   （コマンドラインでは確認できません — あなたの目が最後の関門です）
🔗 https://global.powpow.online/posts/<post-id>
```

場所がない場合は同じブロックで伝える:「📍 場所なし — この投稿は公開マップには載りません」。

対話型の描画（カプセルのタップ、画像のライトボックス）は CLI では検証できない — ユーザーの目が最後の関門である。

テスト投稿の後片付け:
```bash
node scripts/delete-post.js <post-id>
```

## デジタルヒューマン作成（公開とは独立のフロー）

人物（歴史上の人物、キャラクター、ユーザー自身のアバター…）をチャットできるデジタルヒューマンに変え、公開マップにピン留めする、公開とは独立したフロー。トリガー: 「デジタルヒューマンを作って」「あの人を地図上のデジタルヒューマンにして」「デジタルヒューマンを公開」。

**コスト — 実行前に、公開の決定と同じ形式で確認する:**
- **バッジとは**: PowPowでの活動（投稿、チェックイン）で稼げる仮想リソース — お金ではなく、カードも絡まない。
- **コスト**: **作成1回につき2バッジ、返金不可**。完成したデジタルヒューマンは**30日後に失効**する。
- まず残高確認（スクリプトが自動で行い、不足なら中断する）、それからコストを「次のステップ」ブロックに書き、明示的な確認を待つ。

ユーザーから収集するもの:
1. **名前 + ペルソナ**（両方必須）: どんな人物で、どう話すか — ペルソナは2〜4文で十分。プラットフォーム内蔵のLLMが会話を担当する。
2. **場所**（必須）: その人物にとって意味のある場所 — ステップ3の解決フローを再利用し、候補を選んでもらう。推測しない。
3. **アバター** — 次の3つのうち1つ（選択肢を提示する）:
   - **AI生成**（通常のケース）: 参照画像URLが必要（`--avatar-ref`）。プラットフォームがペルソナ+参照から生成する（8〜30秒）。ローカルの参照写真も可 — まず `/api/upload/post-image` にアップロードし、その公開URLを `--avatar-ref` に渡す。
   - **ローカルアップロード**（`--avatar @<パス>`）: ユーザー自身の画像をそのまま使う。
   - **直接リンク**（`--avatar <url>`）: 画像への直接URL。

```bash
node scripts/create-digital-human.js \
  --name 史铁生 \
  --desc-file persona.txt \            # または --desc "..."
  --avatar-ref https://...jpg \        # または --avatar @./photo.jpg、--avatar <url>
  --lng 116.408195 --lat 39.952372     # ユーザーが選んだ解決結果から
```

作成後は、デジタルヒューマンID、場所、**失効日（30日）**、バッジ残高を報告し、地図へリンクする: https://global.powpow.online/map 。ユーザーはすぐに投稿で@言及できる（`compose.js --dh <id>`）し、`match-digital-human.js` の候補にもなる。

既存のものを探す: `node scripts/list-digital-humans.js --search "<名前>"`。

## エラー処理

**ハードルール: 生のスクリプト出力、nodeコマンド、エラーコード（DEVICE_MISMATCH など）をそのままユーザーに投げない。すべてのエラーを、人間の文 + 次のアクションに翻訳する。**

- **401 / セッション期限切れ（フロー中）**: これは「前回のログインの有効期限が切れた」であって「未ログイン」ではない — ユーザーにとってこの2つはまったく別物であり、期限切れを初回ログインとして扱うと、最初からやり直しだと思い込ませる。伝え方「前回のログインが期限切れのようです — もう一度アカウントを教えていただけますか。ちょうどそこから再開します」。login.js を再実行し、1回だけ再試行する。**済んだ作業はすべて残る** — 下書き、素材、選んだデジタルヒューマンと場所はローカルに残る。その地点から続きを行い、前のステップを繰り返さない。
- **429 レート制限**: サーバーは1時間あたり10投稿/ユーザーを許可する。待ち時間をユーザーに伝える。連続リトライしない。
- **400 CONTENT_BLOCKED**: コンテンツがモデレーションを通らなかった。ユーザーに伝え、どう変更したいか尋ねる。
- **403 pending_payment**: アカウントが完全に有効化されていない。ログイン必須のすべての呼び出しでハードゲートになる（デジタルヒューマン、ジオコーディング、画像アップロード、公開 — すべてブロック）。劣化モードはない — ログイン成功後、フローの途中でも出現し得る。ユーザー自身にプラットフォームで有効化を完了してもらう（登録 https://global.powpow.online/register）。再試行しない、一時的なエラーとして扱わない。
- **423 アカウントロック**: ログイン失敗が多すぎる。30分待つ。
- **認証情報の誤り（ログイン時の401）**: 再入力を依頼するか、https://global.powpow.online/login へ案内する（5回失敗すると30分のロック）。
- **公開時にローカル画像が見つからない**: 組み立て後にファイルが移動/削除された。publish.js は中断する（何も送信されない）。有効なパスで compose.js を再実行する。
- **画像検索が利用不可**: 画像なしで続けるか、直接リンクをユーザーに依頼する。
- **バッジ不足（デジタルヒューマン作成）**（スクリプトは引き落としの前に中断する）: 残高をユーザーに伝える。バッジはプラットフォームの活動（投稿、チェックイン）で稼げる。同じアカウントでそのまま再試行しない。

## 注意事項

- 公開したら必ず、投稿が本当に載っているか検証する。テスト投稿はその後削除する。
- ユーザーの明示的な確認なしには絶対に公開しない。
- ユーザーのパスワードを保存/ログに出さない。ローカルにキャッシュされるのは JWT セッションのみ。
- **パスワードの扱い（内部ルール — ユーザーに説明しない）**: stdin パイプを使う — `printf '%s' '<password>' | node scripts/login.js <username>`。位置引数形式（`login.js <user> <password>`）は絶対に使わない — シェル履歴とプロセス一覧に残る。エコーなし、ディスクへの書き込みなし、シェル変数なし。`login.js` は互換性のため位置引数形式を受け付けるが、使ってよいという意味ではない。認証情報は質素なメッセージ1通で依頼し、セキュリティ説教をしない（会話UX → 口調参照）。
- **パス規則**: ユーザーが `--text-file`/`--image` に明示的に指定したパスか、カレント作業ディレクトリで自分が作成したファイルのみを使う。マシンをスキャンしない、パスを当て推量しない — 誤ったパスはプライベートなファイルを公開してしまう。
- 写真から場所/時間を推測しない — 尋ねる。推測ミスは一人称記事の事実誤認になる。
- 指定された場所は常に公開マップに載る（内部ルール、オプトアウトなし。ステップ3参照）。
- **地図プロバイダーの名前をユーザーに言わない** — 「場所をお調べします」と言う。表現、選択肢リスト、スクリプト出力の言い換えすべてに適用（会話UX → プロバイダー中立の呼称参照）。
- **ユーザーに座標を要求しない。** フォールバックの順序: 言い換え → 候補を広げる → 場所なしで公開。
- このスキルは安全に配布できる: プラットフォームの機密情報を含まず、危険な能力（身元、レート制限、モデレーション）はすべてサーバー側で強制される。
