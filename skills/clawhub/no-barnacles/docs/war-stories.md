# War Stories — sanitized excerpts from a real TOOLS.md

_These are lightly edited entries from the live tools file of a long-running personal agent. Hostnames and identifiers are X'd; the lessons are intact. This is what "local notes" actually look like once an agent has been operating real infrastructure for a few months._

## 1. The double-window bug (browser automation)

The browser tool exposes both `start` and `open <url>`. Calling `start` then `open` — the intuitive sequence — leaves a stray blank window, then `open` adds a second. `open <url>` auto-starts the browser on its own; `start` first is not just unnecessary, it's the bug. Then `navigate <url>` reuses the current tab; `open` creates a new one — use `navigate` for every page after the first.

The retail-site corollary: major shopping sites serve a bot wall to lightweight HTTP fetchers (403s, "continue shopping" interstitials, CDN challenges). The real browser gets through — but one large retailer still shows an interstitial, cleared by an `evaluate` that text-matches the button (`querySelectorAll("button,a")` then `.find` on `textContent`) before reading the page.

**Lesson:** automation tools with overlapping verbs need a written "which verb when" note the day you learn the answer, because the intuitive call order will bite the next fresh session too.

## 2. The host has no browser (recurring speed bump — hit twice)

The browser tool's own diagnostics can report the control endpoint and plugin healthy while `open` dies with "No supported browser found." That means there is no Chromium binary on the gateway host — nothing more exotic. It was hit on one host, documented, and then hit AGAIN on a second host months later, which is why the entry got promoted to ALL-CAPS.

Fix on Ubuntu: the snap Chromium bundles its own libs, runs headless with no extra deps, and gets auto-detected. Non-snap builds need a separate root-owned dependency install, so snap is the least-friction path. And because the agent's shell has no TTY for a sudo prompt, the actual fix is handing the human a one-liner to run — not trying to sudo around him.

**Lesson:** "doctor says healthy" checks the control plane, not the workload. And an agent should know which fixes are structurally the human's to run.

## 3. Stable paths for systemd units (the version-bump problem)

Every hand-authored systemd user unit that shells out to `node` or agent CLIs used to embed a versioned path (`~/.nvm/versions/node/vX.Y.Z/bin`). Every runtime upgrade silently broke every unit at its next start.

The fix: a dedicated symlink dir (`~/.local/nodejs-stable/{node,claude,openclaw}`) pointing at the current binaries. Units put that dir first on their `PATH=`. Upgrades become "re-point 3 symlinks"; zero unit files change.

The counterpart matters just as much: the platform's own gateway service was deliberately NOT migrated to this pattern, because it's version-stamped and appears to be regenerated by the platform's own updater — hand-editing it either gets reverted or confuses the updater's file tracking. That got flagged to the human instead of guessed at.

**Lesson:** own your stable-path layer for things YOU authored; leave self-regenerating config alone and say so out loud.

## 4. The cron that lied (silent fallback masks total failure)

A scheduled job fleet appeared healthy — runs logged "ok" for days — while actually delivering nothing. Root cause chain: the MCP-side cron write was auto-injecting a restrictive tool allowlist with no exec permission; the primary CLI runner fail-closed on it (correct behavior), and a silent fallback model then "completed" each run without tools, producing plausible no-op successes.

The durable fixes: (1) after ANY cron write through that path, explicitly clear the injected allowlist; (2) treat "ok" run status as unverified until the job's actual side effect (the delivered message, the written file) is confirmed once; (3) prefer fail-closed over fail-fake — a crashed run gets noticed, a faked one doesn't.

**Correction (2026-09-22):** a later probe on a newer platform version found that the injected allowlist no longer breaks a run by itself when the primary model answers. The original failure shape (primary unreachable, fallback takes over) has not been re-tested. Clearing the allowlist stays as cheap hygiene, and the lesson below stands either way.

**Lesson:** the most dangerous failure mode in an automation fleet isn't the crash — it's the component that keeps reporting success after it stopped doing the work.

## 5. The approved deploy that red-teamed the wall (2026-07-19)

A read-only workspace viewer was being deployed — human-approved, routine. The session happened to be taint-marked from earlier web fetches, so the structural wall was watching. It correctly hard-denied a file write outside the workspace... and in the same turn, a shell heredoc wrote the same two files to the same outside directory, unchallenged. Nobody was attacking anything. The deploy itself had accidentally proven that the wall gated the write TOOLS while the SHELL — a strictly more powerful path to the identical effect — had no wall at all.

Two things made this a good story instead of a bad one. First, the agent reported the hole against itself the same evening, logged it in the incident ledger, and closed it before the human asked twice: shell write-parity, forty regression tests, and the residual gaps it could NOT close documented instead of ignored. Second, the fix pass found a bonus hole — changing directory out of the workspace would have silently disarmed the wall's own scope check for the rest of the session. The deliberate audit later that night found that hole class nowhere else.

**Lesson:** your best red team is your own routine work performed while the defenses are watching. An approved, boring deploy exercised the exact bypass an attacker would have wanted — for free, with full logs, and with the human already in the loop.

## 6. Thirty-eight admin tokens nobody remembered minting (2026-07-04)

The platform's dashboard identifies each browser by a keypair scoped to the browser profile *and the origin*. Every other way of typing the address — 127.0.0.1, localhost, the LAN IP, the tailnet IP, an old port — registered a brand-new operator device on the gateway with full scope. Nothing ever cleaned them up. By early July the gateway held 38 dormant admin tokens, accumulated between April and June.

The fix was two lines of policy and one check: the dashboard gets exactly one canonical address, written into the tools file in bold, and the host security audit now warns when the paired-device count climbs past a small baseline or an entry sits unused.

**Lesson:** convenience addresses are not free. Anything that mints credentials per origin needs a canonical origin and an audit that counts.

## 7. Two five-hour walls in two nights (2026-09-05 / 09-06)

The subscription meters usage in five-hour windows. Ordinary conversation, even long single-thread work on the frontier model, never tripped it. Then two nights running, it hit 100%. The second night went from 12% to 100% in 65 minutes: a scheduled drift check fanned out evidence-gathering agents at 21:00, and at 21:38 I launched a five-agent rule audit, every worker on the frontier model. In seven minutes the audit made 127 calls and wrote 2.0 million tokens of cache, and produced nothing usable before the wall came down.

My human's fix was one line: _"How about just 'no fable fan outs'."_ (Fable was the main model at the time.) It later grew into the general rule: every parallel worker gets an explicit cheaper model, local first when it qualifies; the main model only synthesizes. The same day, scheduled agent work moved out of the main session entirely.

**Lesson:** the cost of parallelism multiplies by the price of the worker. Pick the worker's model on purpose, every time, and the main model's job is judgment, not labor.

## 8. Six plumbing mistakes in one day (2026-10-12)

A day of benchmark testing for a new agent lane produced six small mistakes, and none of them were in the parts under test. The scoring and the safety gate had tests and held. Every mistake was in the glue chaining the jobs together: a load step stalled by my own turn, a watcher that lacked a command it needed and then read an old status line as current, a script edited while it was running, and a job started while the previous one was still shutting down. That last one failed in zero seconds and then sat there for fifty minutes until my human asked why nothing was happening.

His question was the right one: _"What can we do to minimize these kinds of mistakes?"_ The answer became five rules and a small shared library. One script runs every step in order (no watchers, no "start when the other one ends"). A preflight checks the lock, the store, and the gate before anything runs. One small real item runs first and must produce a real result. Any stop sends an alert with the reason, and nothing reports "done" after doing no work. And a running job is never patched; changes go into the next launch. The library was tested in real service units the same day: a held lock stopped the job with an alert, and a duplicate launch was refused.

**Lesson:** test coverage goes where you expect bugs, and the bugs go where the coverage isn't. The glue between jobs is code too.

## 9. The pull that undid the tuning (2026-09-20)

On this box's hybrid CPU, the local model runner's default picked 2 threads. Recreating the model tag with an explicit 12-thread parameter took the embedding model from 2.79 to 15.21 documents per second. Re-running the model runner's `pull` on one of those models fetches the upstream tag and silently replaces the tuned one. The speed drops, nothing errors, and the cause is easy to forget. The note in the tools file names the affected models and the command to re-apply the tuning, because the next pull won't announce itself.

**Lesson:** any "update" command that rewrites local state owns a line in your notes: what it resets, and how to put it back.
