# 術語表

這份文件收錄本 Skill 各檔案出現的**業界通用術語**。Agent 通常不需要讀它 —— 它的用途是讓非技術背景的成員（PM、業務、專案負責人）能讀懂這份 Skill 與它產出的規格文件。

本 Skill 自訂的詞彙（考量項目、涵蓋度、Gate、反查影響等）定義在 `SKILL.md`，不在這裡。

---

## 文件與格式

| 術語 | 說明 |
|---|---|
| **Markdown** | 純文字的排版格式，用 `#` 表示標題、`|` 表示表格。規格文件一律用這個格式 |
| **YAML** | 用縮排表示層級的資料格式，人與程式都能讀。`spec-coverage.yaml` 用的就是它 |
| **frontmatter** | 檔案最開頭、用 `---` 包起來的一段 YAML，放版本、負責人、依賴等資訊。它不會顯示在文章內容裡 |
| **anchor（錨點）** | 指向文件內特定小節的連結位置，例如 `檔名.md#業務規則` |
| **schema** | 資料的「格式規定」—— 有哪些欄位、每個欄位放什麼、哪些必填 |
| **manifest** | 索引檔。列出有哪些檔案、各自負責什麼，讓 Agent 只載入需要的部分 |
| **Mermaid** | 用純文字畫流程圖的語法。因為是文字，Agent 讀得懂、也能追蹤修改紀錄 |
| **diff** | 兩個版本之間的差異對照 |
| **deprecated** | 已廢棄但保留紀錄，不再使用 |
| **superseded** | 已被新版取代（用於 ADR） |

## 需求與規格

| 術語 | 說明 |
|---|---|
| **PRD** | Product Requirements Document，產品需求文件 |
| **FR** | Functional Requirement，功能需求 —— 系統要能做到什麼 |
| **NFR** | Non-Functional Requirement，非功能需求 —— 系統要多快、多穩、多安全 |
| **BR** | Business Rule，業務規則 —— 不能違反的商業邏輯 |
| **AC** | Acceptance Criteria，驗收標準 —— 怎樣算做完了 |
| **ADR** | Architecture Decision Record，架構決策紀錄 —— 記錄為什麼這樣選 |
| **Given / When / Then** | 描述驗收標準的固定句型：在什麼前提下、發生什麼事、應該得到什麼結果 |
| **In Scope / Out of Scope** | 這次要做的範圍／明確不做的範圍 |
| **Persona** | 典型使用者的人物側寫 |
| **User Journey** | 使用者從開始到達成目的的完整歷程 |
| **Value Proposition** | 價值主張 —— 這個產品為顧客解決什麼、憑什麼被選擇 |
| **Definition of Done** | 完成的定義 —— 團隊對「這件事做完了」的共同標準 |

## 資料

| 術語 | 說明 |
|---|---|
| **Entity** | 業務上的一個實體概念，例如「訂單」「會員」，通常對應一張資料表 |
| **ER Diagram** | 實體關聯圖 —— 畫出各資料表之間的關係 |
| **Index（索引）** | 讓查詢變快的資料結構，代價是寫入變慢、佔更多空間 |
| **Constraint（約束）** | 資料庫層級的規則，例如「這個欄位不能重複」 |
| **FK（Foreign Key）** | 外鍵 —— 指向另一張表的欄位，用來維持資料關聯的正確性 |
| **Partition** | 把一張很大的資料表切成多份儲存，改善效能 |
| **Cache（快取）** | 把常用資料暫存在快速的地方，減少對資料庫的查詢 |
| **Cache Invalidation** | 快取失效 —— 原始資料變了，要讓過期的快取作廢 |
| **Migration** | 資料庫結構的變更腳本，例如新增欄位 |
| **backfill** | 回填 —— 為既有的舊資料補上新欄位的值 |

## 介面與整合

| 術語 | 說明 |
|---|---|
| **API** | 系統對外開放的呼叫介面 |
| **REST / GraphQL** | 兩種常見的 API 設計風格 |
| **Webhook** | 反向通知 —— 對方系統發生事情時主動打過來，而非我方一直去問 |
| **Event（事件）** | 「某件事發生了」的訊息，供其他模組訂閱處理 |
| **Queue（佇列）** | 訊息排隊區，讓工作可以非同步、依序處理 |
| **Pub/Sub** | 發布／訂閱 —— 一方發出訊息，多方各自接收處理 |
| **DLQ（Dead Letter Queue）** | 死信佇列 —— 重試多次仍失敗的訊息會被丟到這裡，等待人工處理 |
| **Retry** | 重試 —— 失敗後自動再試一次 |
| **OAuth** | 一種授權標準，讓使用者不必交出密碼就能授權第三方存取 |
| **Sitemap** | 網站架構圖 —— 有哪些頁面、如何層層相連 |
| **Wireframe** | 線框稿 —— 只有版面配置、沒有視覺設計的畫面草圖 |

## 可靠性與失敗處理

| 術語 | 說明 |
|---|---|
| **冪等性（idempotency）** | 同一個操作重複執行多次，結果與只執行一次相同。是安全重試的前提 |
| **補償交易** | 已送出的操作無法撤銷時，改用一個反向操作來抵銷（例如發「取消通知」） |
| **降級（degradation）** | 部分服務不可用時，系統改用較低品質但仍可運作的方式繼續服務 |
| **部分失敗** | 多步驟流程中，前幾步成功、後面失敗的狀態 |
| **HA（High Availability）** | 高可用 —— 單一元件壞掉時系統仍能運作 |
| **Failover** | 故障切換 —— 主要系統失效時自動切到備援 |
| **RPO（Recovery Point Objective）** | 可容忍遺失多久的資料（例如「最多遺失 15 分鐘」） |
| **RTO（Recovery Time Objective）** | 可容忍多久才恢復服務（例如「4 小時內」） |
| **SLA / SLO** | 對外承諾的服務水準／內部設定的服務目標 |

## 安全與合規

| 術語 | 說明 |
|---|---|
| **Authentication（認證）** | 確認「你是誰」 |
| **Authorization（授權）** | 確認「你能做什麼」 |
| **RBAC** | Role-Based Access Control，以角色為基礎的權限控管 |
| **PII** | Personally Identifiable Information，個人可識別資訊，例如姓名、電話、地址 |
| **GDPR** | 歐盟的個人資料保護法規，涉及歐盟使用者資料時適用 |
| **OWASP** | 一份廣泛採用的網站安全風險清單，常作為安全檢查的基準 |
| **Rate Limit** | 流量限制 —— 限制單位時間內的請求次數 |
| **Secret 管理** | 密碼、金鑰等機密資訊的儲存與存取方式 |
| **Audit Log（稽核紀錄）** | 記錄誰在何時做了什麼，供事後追查 |

## 運行平台

| 術語 | 說明 |
|---|---|
| **Serverless** | 無伺服器 —— 不管理主機，程式碼被觸發時才執行、用多少算多少 |
| **Lambda** | AWS 的 serverless 運算服務，有單次執行時間上限 |
| **ECS / EKS** | AWS 的容器服務 —— 程式跑在常駐的容器裡，沒有執行時間限制 |
| **EC2** | AWS 的虛擬機器 —— 最接近傳統伺服器的形態，管得最多也最自由 |
| **Cloudflare Workers** | 在邊緣節點執行的 serverless 環境，啟動極快但可用的函式庫受限 |
| **冷啟動（cold start）** | serverless 閒置後第一次被呼叫時，需要額外時間初始化 |
| **無狀態（stateless）** | 每次請求都獨立處理，不在記憶體保留上次的資料。serverless 通常強制如此 |
| **連線池（connection pool）** | 預先建立並重複使用的資料庫連線。serverless 難以使用，是常見的架構限制 |
| **供應商鎖定（vendor lock-in）** | 過度依賴特定廠商的專有功能，導致日後難以更換 |
| **退出路徑（exit path）** | 若要更換供應商，需要改動什麼、成本多少的預先評估 |
| **資料落地（data residency）** | 資料必須儲存在特定國家或地區的法規要求 |
| **IaC** | Infrastructure as Code —— 用程式碼描述基礎設施，可版控、可重建 |

## 部署與維運

| 術語 | 說明 |
|---|---|
| **CI/CD** | 程式碼變更後自動測試與自動部署的機制 |
| **Rollback** | 回滾 —— 部署出問題時退回上一個正常版本 |
| **Feature Flag** | 功能開關 —— 程式已上線但可用開關決定是否對使用者生效 |
| **UAT** | User Acceptance Test，使用者驗收測試環境 |
| **Logging** | 記錄系統執行過程的文字紀錄 |
| **Metrics** | 可量化的數值指標，例如請求數、錯誤率、回應時間 |
| **Tracing** | 追蹤單一請求流經各個服務的完整路徑 |
| **Health Check** | 健康檢查 —— 定期確認服務是否還活著 |
| **Runbook** | 故障處理手冊 —— 出事時照著做的標準步驟 |
| **CDN** | 內容傳遞網路 —— 把靜態檔案放到離使用者近的節點以加快載入 |
| **Cron / Scheduler** | 定時排程 —— 在指定時間自動執行的工作 |

## AI 相關

| 術語 | 說明 |
|---|---|
| **LLM** | Large Language Model，大型語言模型 |
| **Prompt** | 給模型的指示文字 |
| **Token** | 模型計算文字量的單位，也是計費單位 |
| **幻覺（hallucination）** | 模型產生看似合理但實際錯誤的內容 |
| **Guardrails** | 護欄 —— 限制模型不得產出的內容或不得執行的行為 |
| **Human-in-the-loop** | 在流程中保留人工介入點，例如 AI 無法處理時轉真人 |
| **eval set** | 評測題組 —— 一組固定的測試案例，用來衡量模型表現與偵測退步 |
| **fallback** | 後備方案 —— 主要方式失效時改用的替代做法 |
| **context** | 模型單次可讀取的資訊總量。載入無關內容會排擠真正需要的資訊 |

## 工程實務

| 術語 | 說明 |
|---|---|
| **Repository（repo）** | 程式碼倉庫 |
| **Branch Strategy** | 分支策略 —— 團隊如何開分支、如何合併 |
| **Commit Convention** | 提交訊息的格式規範 |
| **Coding Style** | 程式碼撰寫風格規範 |
| **Unit / Integration / E2E Test** | 單元測試（單一函式）／整合測試（多元件協作）／端對端測試（模擬真實使用流程） |
| **Regression Test** | 回歸測試 —— 確認新改動沒有弄壞原本正常的功能 |
| **pre-commit** | 提交程式碼前自動執行的檢查 |
