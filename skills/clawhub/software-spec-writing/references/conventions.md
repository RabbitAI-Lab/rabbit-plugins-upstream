# 撰寫慣例

## 一、依賴方向

**核心規則：較早的篇不得依賴較晚的篇。**

篇的順序就是抽象層級的順序，而抽象層級高的內容不應該建立在具體實作之上。若第二篇需要第五篇的內容才能成立，那代表某個東西被放在錯誤的層級。

### 允許與禁止

| 情況 | 是否允許 |
|---|---|
| 依賴較早的篇（S25 → S06） | ✅ |
| 同一篇內互相依賴（S07 → S09） | ✅ |
| 依賴較晚的篇（S07 → S13） | ❌ |
| 同篇內形成循環（A → B 且 B → A） | ❌ 通常代表兩者該合併，或該把共用前提抽到更早的篇 |
| 第九篇（S39–S41） | 不參與排序檢查，見下方 |

### 內容依賴 vs 參考連結

`depends_on` **只宣告內容依賴** —— 上游改了，本篇內容可能失效。

純粹的閱讀導引不算依賴。S17 架構圖寫「本決策見 ADR-003」是導引，不是依賴 —— 實際方向相反：架構章節陳述決策，ADR 解釋為什麼，**ADR 依賴架構**。

沒有這個區分的話，任何一句交叉引用都會變成假違規。

### 第九篇為何不參與排序

S39 ADR、S40 開發規範、S41 參考資料是**跨層紀錄**，不是抽象層級。ADR 記的決策橫跨架構、資料、基建；開發規範同樣適用於所有層。它們可以依賴任何篇，也可以被任何篇引用（作為導引）。

### 發現地點 ≠ 歸屬地點

這是維持規則最常用的操作手法。

寫 S25 第三方整合時發現「Shopee API 每分鐘限 60 次」—— 這是外部約束，歸屬在 S06。正確做法是**把內容往上登記到 S06**，然後 S25 宣告 `depends_on: [S06]`。

錯誤做法是就地寫在 S25，然後讓 S06 或其他早篇反向引用它。

### 違規時的處理

若確實需要早篇依賴晚篇，多半是分層放錯了。**不要自行破例**，回報：

```
疑似分層錯誤
  S09 業務規則需要引用 S28 的快取失效邏輯
  建議：該內容若屬業務約束，應上移至 S09 或 S06；
        若屬實作細節，則 S09 不應依賴它，請確認需求描述是否過度具體
```

## 三、檔案結構

一篇一資料夾、一章一檔案。不要把整篇塞進單一檔案 —— Agent 每次載入都會浪費大量 context。

```
software-spec/
├── INDEX.md                      # 人看的入口：文件地圖與閱讀順序
│
│   # ↓ 以下兩個是「規格管理檔案」，不屬於任何考量項目
├── spec.manifest.yaml            # Agent 看的入口：項目 → 檔案對應
├── spec-coverage.yaml            # 涵蓋度常駐檔案
├── 01-business/
│   ├── 01-background.md          # S01
│   ├── 02-glossary.md            # S02
│   └── 06-assumptions.md         # S06
├── 02-business-design/
│   ├── 08-data-model.md          # S08
│   ├── 09-business-rules.md      # S09
│   └── 10-state-machines.md      # S10
├── 03-requirements/
│   ├── 13-requirements.md        # S13
│   ├── 14-nfr.md                 # S14
│   └── 16-platform-constraints.md # S16
├── 04-system-design/
├── 05-interface-design/
├── 06-implementation/
├── 07-infrastructure-operations/
├── 08-quality-assurance/
├── 09-records/
│   ├── adr/
│   │   ├── ADR-001-xxx.md
│   │   └── ADR-002-xxx.md
│   └── 40-engineering-standards.md
└── assets/
    └── （僅放無法用 Mermaid 表達的素材，例如 UI 截圖）
```

**ADR 一則一檔**，不要合併成大檔 —— 它們的生命週期各自獨立。

### 規格管理檔案

根目錄的兩個檔案（`spec.manifest.yaml`、`spec-coverage.yaml`）**不歸屬於任何考量項目**，也不要為它們新增代號 —— 它們描述的是規格的狀態，不是專案的規格。兩者都納入版本控制，且都不參與依賴方向檢查。

### spec.manifest.yaml

Agent 的載入索引。先讀 manifest 決定要載入哪幾個檔案，而不是全讀。

```yaml
project: <專案代號>
version: 0.4.0
items:
  - id: S09
    title: 業務規則
    file: 02-business-design/09-business-rules.md
    section: 2
    id_prefix: BR
    tags: [business, rules, validation]
    roles: [pm, backend, qa]
  - id: S13
    title: 功能需求與驗收標準
    file: 03-requirements/13-requirements.md
    section: 3
    id_prefix: [FR, AC]
    tags: [requirements, acceptance]
    roles: [pm, backend, frontend, qa]
```

`section` 讓依賴方向可以直接用數字比較。`tags` 與 `roles` 讓 Agent 依任務性質篩選：後端實作任務不需要載入 S26 UI 規劃。

## 四、檔案 frontmatter

```yaml
---
id: S09
title: 業務規則
section: 2
status: confirmed          # confirmed | draft
version: 3
owner: <負責人>
last_updated: 2026-08-17
depends_on: [S02, S06, S08]
---
```

`depends_on` 中的每一項，其 `section` 必須 ≤ 本檔案的 `section`（第九篇除外）。

`status` 只會是 `confirmed` 或 `draft` —— 其他三種狀態（`tbd` / `n/a` / `missing`）的項目根本沒有檔案，只存在於 `spec-coverage.yaml`。

**版本紀錄放在這裡，不要維護全域 Revision History。** 拆檔之後全域紀錄必然過期，而過期的版本資訊比沒有更糟。

## 五、反查影響

每次修改任一項目後，**必須**掃描該項目之後所有規格檔案的 frontmatter，找出 `depends_on` 包含被改動項目的檔案，並在回應中列出。

```
改動：S27 資料庫設計（新增 messages.status 欄位）

受影響（depends_on 包含 S27）
  S28 Cache 策略     快取鍵可能需納入新欄位
  S29 資料遷移       需補 backfill 計畫
```

**不要自動修正這些檔案。** 自動連鎖修改會失控，且會把單一決策放大成大量未經確認的變更。只列清單，由人決定。

## 六、ID 命名規範

| 前綴 | 用於 | 來源項目 |
|---|---|---|
| `S01`–`S41` | 考量項目代號 | 固定清單 |
| `BR-xxx` | 業務規則 | S09 |
| `FR-xxx` | 功能需求 | S13 |
| `AC-<FR>-<n>` | 驗收標準 | S13 |
| `NFR-xxx` | 非功能需求 | S14 |
| `API-xxx` | API 端點 | S23 |
| `ADR-xxx` | 架構決策 | S39 |

### 三條規則

1. **ID 變更需要人類授權。** 判定方式與回報要求見 `SKILL.md`〈項目代號的變更〉。未經授權不得變更任何已發出的 ID。
2. **ID 不重用。** 廢棄的項目標記為 `deprecated` 並保留條目，不要把號碼讓給新項目 —— 舊的程式碼註解、commit message、測試名稱都還指向它。

   若某個 ID 已被大量外部引用，改名後可在原位置留一行對照（`BR-004 → 已更名為 BR-011`），讓查舊代號的人就地找到答案，不必翻版控紀錄。
3. **編號連續遞增，不補洞。** 刪除 BR-004 之後，下一條仍是 BR-008，不要填回 004。

## 七、章節合併

內容都很少的相鄰項目可以合併成一章，但**項目代號不變**。合併後在 manifest 登記多個 id：

```yaml
  - id: [S17, S18]
    title: 系統架構與模組設計
    file: 04-system-design/17-architecture.md
    section: 4
```

### 只能同篇合併

**不得跨篇合併。** 跨篇合併會讓一個檔案同時橫跨兩個抽象層級，依賴方向規則立刻失效。

### 允許的合併組合

| 合併 | 篇 | 條件 |
|---|---|---|
| S03 + S04 | 一 | 尚未建立 Persona，痛點與目標的內容合計不足一頁 |
| S17 + S18 | 四 | 模組數量少於 5 個 |
| S27 + S28 | 六 | 未引入獨立快取層 |
| S30 + S31 | 六 | 批次與檔案處理共用同一套機制 |
| S33 + S34 | 七 | 單一環境、備援策略簡單 |
| S37 + S38 | 八 | AI 功能範圍小，評測併入整體測試策略 |

**不在此表的合併需要先詢問使用者。** 自由合併會導致每次產出的結構都不同，文件之間無法比較，diff 也會爆炸。

以下項目**不得與其他項目合併**，因為它們是 Agent 最常直接查詢的對象：S09 業務規則、S10 狀態機、S13 功能需求、S16 運行平台約束、S23 API 規格、S39 ADR。

## 八、內容格式

### 圖一律用 Mermaid

不要用 png / jpg / drawio 匯出圖。理由有二：Agent 讀不懂圖片；圖與文字必然不同步，而不同步的圖比沒有圖更誤導人。

`assets/` 只放真的無法用 Mermaid 表達的東西（UI 截圖、設計稿）。

### 結構化資料用表格或 YAML，不用散文

業務規則、功能需求、API、錯誤碼、狀態轉換、設定項 —— 這些都要能被逐條引用與比對，散文形式會讓 Agent 難以精確定位。

```markdown
❌ 付款成功之後才可以建立發票，另外退款每筆訂單只能執行一次。

✅
| ID | 規則 | 違反時行為 |
|---|---|---|
| BR-001 | 付款成功才能建立 Invoice | 拒絕，回傳 409 |
| BR-002 | 退款每筆訂單只能執行一次 | 拒絕，回傳 422 |
```

### 唯一歸屬原則

同一個主題只能有一個正式歸屬，其他地方只放交叉連結。

對人來說重複只是囉唆；**對 Agent 來說，兩處寫得不一樣就是矛盾指令，而它不會報錯，只會挑一個照做。**

| 主題 | 唯一歸屬 | 只能交叉引用的地方 |
|---|---|---|
| 外部給定的限制 | S06 | S16、S25 |
| 平台選型導出的限制 | S16 | S17、S21、S33 |
| Retry / DLQ | S21 | S24、S30 |
| 錯誤碼定義 | S23 | S40 |
| Audit Log 要求 | S15 | S32、S35 |
| Audit Log 實作 | S35 | — |
| 概念層資料模型 | S08 | S27 |
| 實體資料庫結構 | S27 | S28、S29 |
| 資料搬遷計畫 | S29 | S33 |
| 快取策略 | S28 | — |
| AI 元件細節 | S22 | S25、S38 |
| Role 業務定義 | S11 | S20 |
| Permission 矩陣 | S20 | — |
| 技術決策的理由 | S39 | 所有陳述該決策結論的章節 |
