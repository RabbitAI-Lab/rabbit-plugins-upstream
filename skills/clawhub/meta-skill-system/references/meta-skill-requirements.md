## 任务要求清单

每种任务类型的"零件清单"——必选/可选组件、组装顺序、领域约束。按清单逐项产出。

---

### M0 任务域协调域

#### 域级说明

M0 域负责根据任务需求选择评估(A)、重构(R)、生成(G)、执行(X)四个能力域的组合，四组件均可独立入口。**核心理念**：任何元技能任务都可以通过这四个能力域的单用或组合来完成。**路径组合**（15 条，✅ 推荐 ⚠️ 跳过逻辑推荐步骤）：

- **仅评估** ✅：判断领域是否需要存在
- **仅重构** ⚠️：跳过评估，直接重构
- **仅生成** ⚠️：跳过评估和重构，直接生成
- **仅执行** ✅：纯三轴框架执行
- **评估 + 重构** ✅：评估后重构
- **评估 + 生成** ⚠️：跳过重构
- **评估 + 执行** ⚠️：跳过重构，无负载物
- **重构 + 生成** ⚠️：跳过评估
- **重构 + 执行** ⚠️：跳过评估，无负载物
- **生成 + 执行** ⚠️：跳过评估和重构
- **评估 + 重构 + 生成** ✅：生成负载物后暂停
- **评估 + 重构 + 执行** ⚠️：跳过负载物生成
- **评估 + 生成 + 执行** ⚠️：跳过重构
- **重构 + 生成 + 执行** ⚠️：跳过评估
- **评估 + 重构 + 生成 + 执行** ✅：完整价值链

**职责分工**：领域评估（边界识别/存在理由分析/决策）→ 工作流重构（流程分析/补偿层消除/IPO重整）→ 领域负载物生成（catalog/requirements/exemplars）→ 通用任务执行（三轴框架持续执行）。**价值链**：传统领域 → [评估] → 评估结论 → [重构] → IPO基元链 → [生成] → 负载物 → [执行] 持续运行。**四层价值属性**：评估=判断价值（低频脉冲）、重构=转化价值（低频脉冲）、生成=创建价值（中频按需）、执行=运行时价值（高频持续）。**生产力价值**：将模糊任务需求转化为确定的方法论路径，消除试错成本。省掉的不是几小时会议，是一个团队每周的决策摩擦。

#### M0-01 任务路由
- **必选组件**: 任务需求分析、任务类型识别、路由目标确定（域+入口任务+深化预判）、多域组合方案
- **路由表**:
  | 任务类型 | 目标域 | 入口任务 | 深化任务 |
  |---------|--------|---------|---------|
  | 领域评估 | M1 | M1-01 | M1-06 |
  | 工作流重构 | M2 | M2-01 | M2-07 |
  | 负载物生成/修改 | M3 | M3-01 | M3-10 |
  | 任务执行 | M4 | M4-01 | M4-14 |
  | 内容产出 | M5 | M5-01/M5-02 | M5-09 |
  | 创新·直用 | M6 | M6-01~M6-04 | M6-08 |
  | 创新·改进 | M7 | M7-01 | M7-12 |
  | 创新·迁移 | M8 | M8-01~M8-04 | M8-06 |
  | 创新·构建 | M9 | M9-01 | M9-07 |
  | 跨域组合 | 多域 | M0-02 | 各域深化协同 |
- **可选组件**: 路由优先级、并行执行可能性分析、路由表
- **组装顺序**: 任务需求收集→类型识别→路由表匹配→目标域确定→多域组合设计→深化预判
- **约束**: 路由须基于任务类型；跨域组合须明确各域职责边界
- **格式**: 任务路由报告（Markdown）

#### M0-02 执行顺序确定
- **必选组件**: 任务域依赖关系分析、执行顺序方案、关键路径识别
- **可选组件**: 并行执行可能性分析
- **组装顺序**: 依赖分析→顺序确定→关键路径识别
- **约束**: 执行顺序必须尊重任务域依赖关系
- **格式**: 执行顺序图（Markdown流程图）

#### M0-03 结果整合与优化
- **必选组件**: 各任务域执行结果汇总、整合方案、优化建议
- **可选组件**: 整合效果评估
- **组装顺序**: 结果收集→整合分析→优化建议
- **约束**: 整合必须保持各任务域输出的完整性
- **格式**: 整合报告（Markdown）

### M1 领域评估域

#### 域级说明

M1 域评估一个领域是否需要存在，而不是如何优化。**核心理念**：领域存在的根本问题不是"能不能优化"，而是"需不需要存在"。**适用范围**：任何可识别为"领域"的实体——业务领域、工作流、组织部门、技术模块、知识分类、流程阶段等。**选择原则**：能消除的不重构，能重构的不保留，消除是最彻底的优化。**评估后典型决策**：消除（边界模糊、功能离散、历史遗留）、重构（边界清晰、功能内聚、消除成本高）、保留（已足够优化、外部约束不可变）。**生产力价值**：消除冗余领域，直接减少组织维护成本和协作损耗。不是优化了预算，是砍掉了一整行。深化由 M1-06 完成。

#### M1-01 领域边界识别
- **必选组件**: 领域名称、领域范围描述（包含什么、不包含什么）、与其他领域的交集列表、边界清晰度评估（清晰/模糊/高度重叠）
- **可选组件**: 领域历史演变、领域规模（人员/流程/功能点数量）
- **组装顺序**: 领域确认→范围梳理→交集识别→边界清晰度评估→数据汇总
- **约束**: 必须完整识别领域的所有边界，不可跳过"理所当然"的边界；边界清晰度必须基于客观标准，不可凭感觉
- **格式**: 领域边界图（Markdown表格+交集标注）

#### M1-02 领域存在理由分析
- **必选组件**: 领域存在的根本原因（事情本身需要 / 人的局限需要 / 历史遗留 / 外部约束）、存在理由标记（✅必要 / ❌可消除 / ⚠️待评估 / 🔒不可消除）、标记理由
- **可选组件**: 存在理由细分（组织架构/协作需要/认知局限/历史惯性/法规要求）、消除动机评估
- **组装顺序**: 追问存在理由→根本原因判定→类型标记→理由记录→汇总统计
- **约束**: 每个领域必须追问"如果组织是完全扁平的、没有部门壁垒，这个领域还需要独立存在吗？"；判定必须基于事情本身逻辑，不可因"行业惯例"保留
- **格式**: 存在理由分析表（Markdown表格）

#### M1-03 领域消除可行性评估
- **必选组件**: 消除方案（被更大领域吸收 / 功能分散到其他领域 / 直接废弃）、消除成本评估（低/中/高）、消除风险评估（低/中/高）、消除后功能覆盖度
- **可选组件**: 消除时间表、消除后需新增的协调机制、消除后需调整的依赖关系
- **组装顺序**: 消除方案设计→成本评估→风险评估→功能覆盖度验证→消除可行性判定
- **约束**: 消除方案必须具体到"功能A→领域X，功能B→领域Y"；成本评估必须基于实际数据，不可凭感觉；风险评估必须考虑最坏情况
- **格式**: 消除方案表（Markdown表格）

#### M1-04 领域独立存在必要性判断
- **必选组件**: 边界清晰度评分（1-10）、功能内聚性评分（1-10）、消除成本评分（1-10，越高越不值得消除）、独立存在必要性评分（综合评分）
- **可选组件**: 评分依据详细说明、敏感性分析（不同权重下的评分变化）
- **组装顺序**: 边界清晰度评分→功能内聚性评分→消除成本评分→综合评分→必要性判定
- **约束**: 评分必须基于客观标准，不可凭感觉；综合评分必须考虑三个维度的权重（边界清晰度30%，功能内聚性40%，消除成本30%）
- **格式**: 评分表（Markdown表格）

#### M1-05 决策输出
- **必选组件**: 五项验证结果（每项标注通过/不通过）、决策建议（消除 / 重构 / 保留）、决策理由、后续行动建议
- **五项验证内容**:
  1. **边界识别完整性**: 是否完整识别了领域的所有边界（包含/不包含/交集）
  2. **存在理由判定准确性**: 每个存在理由是否按四类正确标记（✅必要/❌可消除/⚠️待评估/🔒不可消除）
  3. **消除方案具体性**: 消除方案是否具体到"功能A→领域X"级别
  4. **独立存在评分客观性**: 评分是否基于客观标准，权重是否合理（边界30%/内聚40%/成本30%）
  5. **决策明确性**: 决策建议是否明确，消除方案/重构方向/保留理由是否完整
- **可选组件**: 决策置信度（高/中/低）、决策风险提示、决策后跟踪指标、五项验证内容
- **组装顺序**: 五项验证→评估结果汇总→决策建议→理由记录→后续行动建议
- **约束**: 五项验证必须全部通过；决策建议必须明确，不可模棱两可；如果建议消除，必须给出具体的消除方案；如果建议重构，必须说明重构方向和预期效果
- **格式**: 决策记录（Markdown）

#### M1-06 评估深化
- **必选组件**: 深化来源（M1-05 决策输出中的待深化项）、深化类型（边界细化/存在理由深化/消除方案细化）、深化执行方案
- **可选组件**: 深化优先级排序、深化资源需求评估
- **组装顺序**: 深化需求收集→类型识别→优先级排序→深化方案设计→深化执行
- **约束**: 深化必须基于已有评估结论，不可重新评估或推翻决策
- **格式**: 评估深化报告（Markdown）

### M2 工作流重构域

#### 域级说明

M2 域将复杂工作流重构为 AI 辅助一人简易完成。**核心理念**：传统工作流复杂度 = 事情本身复杂度 + 人的局限补偿层，AI 拥有广域知识+生成能力+上下文窗口，可端到端完成复杂任务。**适用范围**：不止于流程——任何产物的组装过程都是一种"工作流"。**关键规则**：基元数约束≤5，超过说明未充分消除补偿层；校准是过程中锁定方向，校验是事后检查对错，校准环节的中间产出物起纠偏锚点作用不可消除；合并判断准则——AI 能一步完成≠一步完成最好，若中间产出物起校准作用须保留为基元内分步校准点。**生产力价值**：将多角色协作流程压缩为端到端 IPO 链，降低传递损耗和协调成本。一个需要5人3天的工作流压缩为1人2小时。深化由 M2-07 完成。

#### M2-01 传统工作流识别
- **必选组件**: 目标领域名称、传统工作流全链路描述（环节→角色→文档→协作点）、环节数、参与角色数、中间文档数、协作节点数
- **可选组件**: 各环节耗时占比、传递损耗率、返工率
- **组装顺序**: 领域确认→全链路梳理→环节标注→角色标注→文档标注→协作点标注→数据汇总
- **约束**: 必须完整列出传统工作流的每个环节，不可跳过"理所当然"的步骤；量化数据缺失时标注"待测"
- **格式**: 工作流全景图（Markdown表格+流程标注）

#### M2-02 环节存在理由分析
- **必选组件**: 每个环节的存在理由（事情本身需要 / 人的局限需要）、环节类型标记（✅核心 / 🔶校准 / ❌传递 / ❌协调 / ⚡校验 / ❌格式）、标记理由
- **可选组件**: 人的局限类型细分（脑容量/传递/协作/记忆/出错）、可消除程度评估、校准价值评估（该环节的中间产出物是否起纠偏作用）
- **组装顺序**: 逐环节追问→存在理由判定→类型标记→校准价值评估→理由记录→汇总统计
- **约束**: 每个环节必须追问"如果执行者是一个拥有无限知识能力和零协作损耗的AI，这个环节还需要吗？"；判定必须基于事情本身逻辑，不可因"行业惯例"保留；对中间产出物必须追问"这个产出物是否在过程中起校准作用？"——起校准作用的标记为🔶校准
- **格式**: 环节分析表（Markdown表格）

#### M2-03 人的局限补偿层消除
- **必选组件**: 消除清单（哪些环节消除、为什么可消除）、保留清单（✅核心环节+🔶校准环节+⚡关键校验节点）、消除后的信息传递方式（IPO链自动传递）
- **可选组件**: 每个消除环节的风险评估、消除后需新增的关键校验点
- **组装顺序**: ❌标记环节逐一评估→消除决策→🔶校准环节确认→信息传递替代方案→保留环节确认→关键校验点插入→消除清单+保留清单
- **约束**: 消除传递/协调/格式环节不可犹豫——这些是人的局限产物不是事情本身需要；校验环节精简为关键节点但涉及合规的不可消除；**校准环节不可消除**——中间产出物起纠偏作用的必须保留为基元内分步校准点
- **格式**: 消除决策表（Markdown表格）

#### M2-04 重整为IPO基元链
- **必选组件**: 重构后的工作流形态（单步IPO/简短基元链/IPO+人工决策）、每个基元的I/P/O定义、基元间传递关系、基元内分步校准点（如有）、总环节数（目标≤传统工作流的30%）
- **可选组件**: 每个基元的能力需求标注、AI自动化程度评估、关键人工决策节点说明
- **组装顺序**: 保留环节排序→IPO基元划分→基元内分步校准点插入→基元I/P/O定义→传递关系确认→形态选择→能力需求标注
- **约束**: 基元数≤5（超过5说明还没充分消除）；每个基元必须可由AI辅助一人完成；合规节点必须有人工介入；🔶校准环节作为基元内分步校准点保留，不是独立基元
- **格式**: IPO基元链图（Markdown流程图+表格）

#### M2-05 重构验证
- **必选组件**: 七项验证结果（每项标注通过/不通过）、验证不通过项的修正方案
- **七项验证内容**:
  1. **事情完整性**: 重构后是否覆盖全部核心步骤
  2. **补偿层消除**: 传递/协调/格式环节是否已消除
  3. **校准不丢失**: 起纠偏作用的中间产出物是否保留为基元内分步校准点
  4. **端到端可执行**: AI辅助一人能否从头到尾完成
  5. **复杂度回归**: 流程复杂度是否回归事情本身
  6. **质量守恒**: 产出质量是否不低于传统工作流
  7. **合规不跳过**: 涉及合规的环节是否保留
- **可选组件**: 重构前后对比数据（环节数/中间文档/参与角色/耗时/传递损耗）、风险残留项、七项验证内容
- **组装顺序**: 逐项验证→记录结果→不通过项修正→二次验证→通过
- **约束**: 七项必须全部通过；"质量守恒"不可妥协——重构是简化流程不是降低质量；"合规不跳过"是硬约束；"校准不丢失"防止过度合并
- **格式**: 验证清单（Markdown检查表）

#### M2-06 执行形态选择
- **必选组件**: 选定执行形态及理由、执行方式说明、关键人工决策节点（如有）、重构前后对比（环节数/中间文档/参与角色/协作节点/耗时/传递损耗）
- **可选组件**: 形态切换条件、后续迭代方向
- **组装顺序**: 重构结果评估→三种形态适配判断→选定→理由记录
- **约束**: 选择最简形态——能单步IPO的不用基元链，能基元链的不加人工决策；人工决策节点必须标注具体决策内容和触发条件
- **格式**: 形态选择记录（Markdown）

#### M2-07 重构深化
- **必选组件**: 深化来源（M2-06 执行形态选择中的待优化项）、深化类型（环节细化/校准点优化/IPO链调整）、深化执行方案
- **可选组件**: 深化优先级排序、深化效果预估
- **组装顺序**: 深化需求收集→类型识别→方案设计→深化执行→二次验证
- **约束**: 深化必须基于已有重构结果；深化后须重新通过七项验证；基元数≤5不变
- **格式**: 重构深化报告（Markdown）

### M3 领域负载物生成域

#### 域级说明

M3 域任务以生成新领域负载物为主，同时覆盖对已生成负载物的后续修改、优化和完善。**核心理念**：本能力不依赖任何被它创建的领域技能，仅依赖通用任务执行能力、工作流重构能力和自身的references文件。**目录结构**：SKILL.md + references/（必选） + scripts/（可选） + assets/（可选）。**校验标准分层**：母技能豁免A4、B5、D1，其余25项必须通过；生成技能全部28项必须通过。无论生成还是修改，最终产出物均须通过 M3-09 接口校验。修改不得绕过校验；新增内容须转化为新增任务或融合进现有任务要求，不得直接追加文件而不纳入任务体系。**生产力价值**：将领域知识系统化为可复用的技能包，消除从零构建的重复劳动。相当于一个不用培训、不会离职、24小时待命的领域专家，一次性投入，边际成本趋零。深化由 M3-10 完成。

**校验标准分层**：母技能（执行框架本身）豁免A4、B5、D1，其余25项必须通过；生成技能全部28项必须通过。

#### M3-01 领域分析与定义
- **必选组件**: 领域英文名、域名代号前缀、R1-R5定位结果（信息密度/创造性/交互性/规范性/迭代性）
- **可选组件**: 领域分类定位说明、执行框架参数映射推导
- **组装顺序**: 领域名称规范化→领域分类定位→R评分到执行框架参数映射
- **约束**: 领域名称必须准确反映核心工作内容；域名代号前缀取英文名中最短唯一缩写（去连字符后逐字截取至无冲突，如 meta-skill-system → metaskillsystem：M → ME → MET → META → METAS → ...）；R1-R5评分必须基于客观标准
- **格式**: 领域分析报告（Markdown）

#### M3-02 域划分与任务枚举
- **必选组件**: 域数量、每个域的名称和范围、任务枚举结果（每个域的任务类型）、依赖拓扑（域间逻辑流、跨域管线链路）
- **可选组件**: 管线发现启发式说明；知识图谱（在依赖拓扑基础上扩展实体节点类型、关系边类型和推理能力）
- **组装顺序**: 价值链拆解→域数量确定→域命名→任务枚举→依赖推导→域间逻辑流→跨域管线链路
- **约束**: 域数量必须合理（5-15个）；域名必须具体且互斥；任务枚举必须覆盖领域核心工作流；依赖拓扑必须清晰；识别各域是否存在跨任务逻辑，有则标记为需域级说明；识别多个域之间是否存在共同跨域逻辑，有则标记为需多域总览
- **格式**: 域划分表（Markdown表格）+ 依赖拓扑摘要

#### M3-03 SKILL.md生成
- **必选组件**: frontmatter元数据（name/author/description三项）、技能中文名、定位、核心能力、三层结构（references/catalog + references/requirements + references/exemplars）、使用规则、通用任务执行能力（三轴正交+管线编排+5种协同模式）、事实纪律
- **可选组件**: 领域特有维度、域概览表格、完整角色定义（当负载物需要人味如客服、导师等场景时，可附加 12 维角色模型）、写作风格建议（祈使/不定式形式）、渐进披露原则（三级加载设计）、目录用途说明（references/scripts/assets/各自定位）
- **组装顺序**: frontmatter→技能中文名→定位→核心能力→领域特有维度→三层结构→使用规则→通用任务执行能力→角色定义（可选）→域概览→事实纪律
- **约束**:
  - **结构约束**：必须使用三层结构模板（references/catalog + references/requirements + references/exemplars）；必须包含完整的通用任务执行能力说明（三轴+管线+协同模式）；须包含提示词导出说明（合并为目标单一提示词文件的方法、合并顺序及完整合并版文件路径）；领域负载物的完整目录结构为 SKILL.md + references/（必选，含 catalog/requirements/exemplars）+ scripts/（可选）+ assets/（可选）
  - **元数据约束**：frontmatter使用name/author/description字段；默认author为meta-skill-system(wangjiaocheng@foxmail.com)；description中的触发词最后默认包含meta-skill-system
  - **内容一致性约束**：SKILL.md中提到的所有能力、验证清单、维度等必须在references文件中有对应定义
  - **标题层级**：SKILL.md使用`#`；catalog/requirements/exemplars及具体范本文件使用`##`；确保合并时标题层级不冲突
  - **写作风格**：采用祈使/不定式形式（verb-first），使用客观指令性语言，避免第二人称，保持一致性
  - **渐进披露**：三级加载——①元数据（始终在上下文）→ ②SKILL.md正文（<5k词）→ ③资源文件（references/加载到上下文，scripts/直接执行不加载，assets/用于输出不加载），信息优先放在 references/ 中
  - **目录用途**：`references/`——参考文档，加载到上下文；`scripts/`——可执行代码，不加载到上下文；`assets/`——输出模板和资源，不加载到上下文
  - **角色提示**：生成完成后提示用户可附加 12 维完整角色；当需人味场景时，AI 可根据负载物内容自动推导并建议角色，用户决定是否接受
- **12维角色模型**（可选附加，当负载物需要完整人设时使用）：
  ```
  第一层：实体层——不可再分的具体存在
    维1 职业维：以什么为生（行业×任务谱系）
    维2 身份维：在世界坐标系的位置（组织/家庭/社会/知识 四重叠加）
    维3 名人维：最接近的真实人物原型
    维4 拟人维：是不是人（人类/动物/物品/自然力/抽象概念/AI）
    维5 躯体维：身体是什么（年龄/性别/体型/健康/外貌/形态）
    维6 文化维：从什么文化中出来（国籍/民族/语言/宗教/阶级/时代/亚文化）

  第二层：社会关系层——角色怎么嵌入关系网络
    维7 关系维：和谁连着（类型×强度×方向）
    维8 层级维：处在什么高度（元层/宏观/中观/微观/边界/辅助）

  第三层：抽象属性层——超越具体存在的普遍刻画
    维9 功能维：做什么（S感知/C认知/A行动/O组织/I交互/G守护 的组合）
    维10 能力维：有什么本事（知识/技能/资源/信息/权力/自由度）
    维11 动机维：为什么做（利益/价值/生存/权力/关系/认知/合规/惯性）
    维12 动态维：什么情境/怎么变/真假（场景切换×生命周期×虚实属性）
  ```
- **格式**: Markdown文件（SKILL.md）

#### M3-09 接口校验
- **必选组件**: 28项校验结果（每项标注PASS/FAIL/N/A）、FAIL项修正方案
- **校验范围**：仅校验领域负载物的结构规范性，确保其可被执行框架（M4-M9）正确消费和编排。不校验负载物中具体领域知识内容的正确性或质量——领域内容校验无边界，无穷无尽，不应附加于规范层面。
- **28项校验内容**:
  - **A类：结构一致性（6项）**:
    A1. 三层结构存在：references/目录下是否有3个文件 + exemplars/子目录
    A2. SKILL.md含定位声明：是否含"定位"或"依赖声明"章节
    A3. 使用规则完整：是否有完整的使用规则
    A4. 降级模式定义：是否有只读模式的权限表
    A5. 域间逻辑流声明：catalog文件头部是否有域间逻辑流描述
    A6. 依赖拓扑摘要：catalog文件末尾是否有"依赖拓扑摘要"章节
  - **B类：任务Schema（5项）**:
    B1. 每个任务含5字段：ID/名称/说明/依赖/元操作映射
    B2. 依赖格式正确：格式为"无（入口）"或"X-XX"或"X-XX, Y-YY"
    B3. 元操作映射有效：仅允许S/C/A/O/I/G及其组合
    B4. 无孤立任务：依赖ID必须指向已定义的任务
    B5. 入口任务标识正确：入口任务数应≥1且≤总任务数的30%
  - **C类：槽位规范（5项）**:
    C1. 必选组件存在：每个任务必须有"必选组件"字段
    C2. 可选组件存在：每个任务必须有"可选组件"字段（可为空）
    C3. 组装顺序存在：每个任务必须有"组装顺序"字段
    C4. 约束字段存在：每个任务必须有约束相关字段
    C5. 格式字段存在：每个任务必须指定输出格式
  - **D类：执行框架接口（3项）**:
    D1. "与执行框架的接口"或"执行框架"章节：SKILL.md中是否存在此章节
    D2. Step 0-4覆盖：该章节是否覆盖Step 0到Step 4
    D3. Step 1领域校准具体化：是否包含R1-R5规则的领域特定推导
  - **E类：范本库（3项）**:
    E1. 范本清单表存在：`{技能英文名主体}-exemplars.md`中是否有按域分组的范本清单表格
    E2. 范本子文件存在：references/exemplars/目录下是否有.md文件
    E3. 范本模板格式存在：是否提供了子文件的标准化模板格式
  - **F类：可执行脚本（3项，可选——scripts/目录不存在时标记N/A）**:
    F1. 脚本目录结构：scripts/目录下是否存在可执行脚本文件，每个脚本是否有明确的执行方式和依赖声明
    F2. 脚本可独立执行：每个脚本是否可独立运行，是否声明了所需的环境依赖
    F3. 脚本引用一致：SKILL.md中引用的脚本路径是否可解析到scripts/下的实际文件
  - **G类：输出资源（3项，可选——assets/目录不存在时标记N/A）**:
    G1. 资源目录结构：assets/目录下是否存在资源文件，每个资源是否有用途说明和使用方式
    G2. 资源可直接使用：资源文件是否完整可用，模板类资源是否包含占位符说明
    G3. 资源引用一致：SKILL.md中引用的资源路径是否可解析到assets/下的实际文件
- **可选组件**: FAIL项修正方案、内容质量评估、校验范围说明、校验内容清单
- **组装顺序**: A类检查→B类检查→C类检查→D类检查→E类检查→F类检查→G类检查→修正FAIL项
- **约束**: A类必须6/6 PASS；B类必须5/5 PASS；C类必须5/5 PASS；D类必须3/3 PASS；E类必须≥2/3 PASS（E1必过，E2和E3有一项通过即可）；F类为可选校验——当scripts/目录存在时F1-F3必须全部PASS，不存在时全部标记N/A；G类为可选校验——当assets/目录存在时G1-G3必须全部PASS，不存在时全部标记N/A
- **格式**: 校验报告（Markdown检查表）

### M4 执行轴域

#### 域级说明

M4 域定义通用任务执行能力的三轴执行框架。执行轴（必选）提供6大元操作与管线编排，内容轴（按需）提供清单法与样本法，创新轴（按需）提供4种模式与10种元框架，三轴通过5种协同模式正交配合。**核心理念**：万物皆可单元化、单元即管线节点、领域无关方法通用、身份自适应叠加（元操作级身份+领域级身份两层正交）、管线与IPO统一（横向管线纵向IPO递归分形一致）。**核心公式**：产出 = 元操作 × 领域负载物。元操作（S/C/A/O/I/G）是领域无关的思维原语，负载物是可替换的领域知识内容，两者相乘产生最终产出。**执行公理**：仅使用确知的事实和可验证的信息，不得编造数据或引用。**生产力价值**：将任意任务转化为可编排的能力单元管线，消除临场判断的不确定性。从"怎么做"到"执行完成"之间的真空地带被管线自动填充，省掉每次任务的认知切换成本。深化由 M4-14 完成。

#### M4-01 能力单元定义
- **必选组件**: 单元ID（`{元操作代号}-{序号}`）、名称（`{功能描述}`）、元操作类型（S/C/A/O/I/G）、输入定义、输出定义、依赖列表、AI自治度（⬛全自动/🟨半自动/⬜辅助）、组合接口
- **可选组件**: 身份叠加（元操作级身份+领域级身份，可使用12维角色模型完整定义，见 M3-03）、P实现（LLM/工具/技能/人机/组合）
- **组装顺序**: 元操作类型确定→ID分配→名称定义→I/O定义→依赖标注→自治度判定→组合接口定义→身份叠加（可选）
- **约束**: 每个单元必须是一个AI可独立执行的最小操作；ID格式必须为`{元操作代号}-{序号}`；元操作类型必须为S/C/A/O/I/G之一；自治度根据AI独立完成程度判定
- **格式**: 能力单元Schema表（Markdown表格+元操作映射）
- **自适应身份叠加**:
  - **元操作级身份**: 由元操作类型自动推导(S→侦察者/C→分析师/A→执行者/O→管理者/I→协调者/G→守门人)
  - **领域级身份**: 附于名称字段括号中(如"市场分析师×数据科学家")，展示层视觉增强
  - 两层正交不冲突：元操作管"做什么操作"，领域管"哪个领域"
- **管线与IPO统一**: 管线是IPO的P的具象化，IPO是管线的展开机制。横向看是管线(6类型+6编排)，纵向看是IPO递归(I→P→O)，P递归展开时子级仍是管线结构

#### M4-02 感知元操作
- **必选组件**: 信息源描述、采集方法、监测指标、扫描范围、检索策略
- **可选组件**: 信息质量评估、采集频率、监测阈值
- **组装顺序**: 信息源识别→采集方法选择→监测指标设定→扫描范围确定→检索策略制定

#### M4-08 管线编排
- **必选组件**: 管线模式选择、单元编排顺序、依赖关系、顺序/并行/条件/循环/扇出/扇入节点标注
- **可选组件**: 管线优化说明、编排工具
- **组装顺序**: 主链路建立→依赖检查→顺序标记→并行标记→条件分支→循环设置→扇出/扇入标记→G类验证单元插入
- **约束**: 管线编排须尊重任务的自然依赖关系，不得人为制造冗余节点；编排完成后主动提示用户可要求展示任一能力单元的Schema信息、6种编排模式详情或7种通用管线模式详情；若能力单元需人味场景，主动提示用户可为该单元附加或自动推导 12 维完整角色（见 M3-03）
- **格式**: 管线图（Markdown流程图+表格）
- **6种编排模式**:
  | 模式 | 符号 | 说明 | 示例 |
  |------|------|------|------|
  | 顺序 | → | A完成后执行B | S-01 → C-01 → A-01 |
  | 并行 | ‖ | A和B同时执行 | S-01 ‖ S-02 → C-01 |
  | 条件 | ? | 满足条件X执行A，否则B | C-01 ?(通过)→ A-01 : → C-02 |
  | 循环 | ↻ | 重复执行A直到条件满足 | ↻(C-01 → A-01, 直到精度达标) |
  | 扇出 | ⇉ | A的输出同时供给B/C/D | S-01 ⇉ [C-01, C-02, C-03] |
  | 扇入 | ⇇ | B/C/D的输出汇总到E | [A-01, A-02, A-03] ⇇ O-01 |

#### M4-09 通用管线模式
- **必选组件**: 模式选择、模式适用场景、模式执行流程
- **7种通用管线模式**:
  1. **P1 基础闭环**: S→C→C→A→O（标准任务完整执行链）
  2. **P2 迭代精炼**: ↻(S→C→A→G, 达标)→O（多轮改进）
  3. **P3 并行汇聚**: [S‖S‖S]⇇C→C→A（多源信息汇聚决策）
  4. **P4 条件分支**: S→C?(条件)→A₁:A₂:A₃（分路径执行）
  5. **P5 交互驱动**: S→I→C→I→A→I（频繁人工确认）
  6. **P6 全守护**: G→S→G→C→G→A→G→O（高安全合规）
  7. **P7 发散收敛**: S→C⇉[A,A,A]→C→A（创意产出）
- **可选组件**: 模式组合方案、模式优化建议、通用管线模式明细
- **组装顺序**: 模式识别→模式选择→执行流程设计
- **约束**: 模式选择必须基于任务特征；执行流程必须符合模式规范；模式选择后主动提示用户可要求展示全部7种通用管线模式详情
- **格式**: 管线模式说明（Markdown）

#### M4-10 三轴判定
- **必选组件**: 复杂度判定（简单/中等/复杂）、内容类型判定（非结构化/结构化）、创新需求判定（无需创新/需要创新）、判定组合结果
- **判定标准**:
  - **复杂度判定**: 简单=可直接完成，中等=3-7步协调，复杂=8+步或多层嵌套
  - **内容类型判定**: 非结构化=简单答案/数据/操作结果，结构化=文档/方案/报告/代码

- **可选组件**: 判定依据说明、判定置信度
- **组装顺序**: 复杂度判定→内容类型判定→创新需求判定→组合判定

#### M4-11 领域校准
- **必选组件**: 领域识别结果、R1-R5校准参数推导、核心术语/元操作权重/关键变量/守护约束/产出格式/自治度偏好/创新评估侧重
- **R1-R5校准规则**:
  - **R1 信息密度**: 高信息密度领域（科研、金融、情报）→ S和C权重高，G偏严格
  - **R2 创造性**: 高创造性领域（设计、写作、艺术）→ A权重高，C偏发散，G偏宽松
  - **R3 交互性**: 高交互性领域（服务、教育、医疗）→ I权重高，S偏人本，G偏伦理
  - **R4 规范性**: 高规范性领域（法律、认证、监管）→ G权重高，O偏严格，自治度偏低
  - **R5 迭代性**: 高迭代性领域（软件、产品、实验）→ 循环多，S→C→A链短而频
- **可选组件**: 校准依据说明、领域特征分析
- **组装顺序**: 领域识别→R1-R5分析→校准参数推导→参数映射
- **约束**: 校准推导必须向用户展示过程和依据；R1-R5评分必须基于客观标准
- **格式**: 领域校准报告（Markdown）

#### M4-12 三轴分解
- **必选组件**: 激活轴说明、任务分解结果（元操作单元列表）、内容方法标注（如有）、创新模式标注（如有）
- **分解粒度原则**:

  - 如果一个单元需要多个不同类型的操作，继续拆分
  - 目标粒度：3-15个单元/任务（少于3合并，多于15分层）
  - 入口单元（无依赖）通常是S类或I类
  - 终点单元通常是A类（交付）或O类（归档）
- **可选组件**: 分解依据说明、单元依赖关系
- **组装顺序**: 轴激活判断→任务分解→单元标注→依赖关系确认
- **约束**: 分解必须基于任务本身的结构，不得强行套用模板；每个单元必须有明确的元操作类型
- **格式**: 三轴分解报告（Markdown表格）

#### M4-13 整合交付

- **呈现规则**:
  - 默认展示最少必要信息
  - 用户说"展开""详细"时逐层揭示
  - 重要决策点必须展示推导过程
  - 创新方案必须附创新路径说明和四维评估结果
- **工具调用策略**:
  - 优先使用专用工具（如数据查询、文件操作）
  - 专用工具不可用时，使用通用工具（如bash、python）
  - 工具调用失败时，提供降级方案或人工介入提示
- **三轴协同模式**:
  1. 顺序协同：创新轴生成方向 → 执行轴分解管线 → 内容轴确定构成方法
  2. 并行协同：执行轴和内容轴同时进行，创新轴按需插入

- **可选组件**: 交付后改进建议、用户反馈收集
- **组装顺序**: 管线复盘→成品组装→方案评估→呈现优化→用户交付
- **约束**: 呈现规则须匹配用户需求；默认展示最少必要信息，用户说"展开""详细"时逐层揭示
- **格式**: 整合交付报告（Markdown）

### M5 内容轴域

#### 域级说明

M5 域定义内容轴的两种产出方法——清单法（组件组合）和样本法（模仿产出），按需激活。**适用判断**：清单法适用于结构明确、组件清晰的成品；样本法适用于有高质量同类样本可参考的场景。**生产力价值**：将非结构化产出需求转化为结构化组装流程，消除每次从零构思的成本。一份30页的方案不再是3天的白纸苦思，而是30分钟的组装产出。深化由 M5-09 完成。

### 创新轴总览

**四模式穷尽性证明**：任何创新实例从发生学角度只有四种可能来源，四分类穷尽且互斥：

| 来源 | 对应模式 | 本质 | 完备性 |
|------|---------|------|--------|
| 已有模式，换了地方用 | M6 直用 | "这招我也能用" | 起点已知，操作不变 |
| 已有模式，做了变形 | M7 改进 | "把这招扭一下" | 起点已知，施加变换 |
| 别处的模式，搬过来 | M8 迁移 | "那招挪到这里试试" | 起点跨域，适应性移植 |
| 没有模式，从零组合 | M9 构建 | "两个不搭边的东西硬接" | 起点为零，维度矩阵生成 |

一个创新要么有已有模式作为起点（M6/M7/M8），要么没有（M9）。四分类穷尽且互斥。**完备性成立。**

**四模式关系**：M6 是最直接的应用——将已知基元嵌入处理环节；M7 在 M6 基础上对基元施加变形；M8 扩展了基元的来源域（跨领域提取）；M9 则是当所有已知基元都不适用时的从零构建方案。四者构成梯级递进的创新生成体系。**创新纪律**：创新方案引用的案例、数据必须确知真实存在，不确定的标注"待验证"。

### M6 创新轴·模式直用域

#### 域级说明

M6 域是创新轴最直接的应用——将已知基元嵌入处理环节。本质是同领域模式复用，不需抽象化。包含反常识、框架、迁移、构建四种基元运用方式 + 基元重组 + 四维评估 + 领域适配。**生产力价值**：用已知模式快速产生多变体方案，消除从零创新的时间成本。投入一份思考得到四份独立可交付成果。深化由 M6-08 完成。

#### M6-01 基元运用反常识创新
- **必选组件**: 领域描述、默认假设识别（至少3个）、假设反转方案、反转空间提取
- **执行流程**: 识别领域中被视为理所当然的默认假设→逐一反转每个假设并推到逻辑极端→从反转后的空间中提取可行的创新方案→评估每个方案的创新潜力和落地可行性
- **可选组件**: 假设验证方法、反转风险评估、执行流程
- **组装顺序**: 领域描述→默认假设识别→假设反转→反转空间提取→方案生成
- **约束**: 必须识别至少3个默认假设；每个假设必须反转并推到逻辑极端
- **格式**: 反常识创新方案（Markdown）

#### M6-02 基元运用框架创新
- **必选组件**: 领域描述、创新元框架选择（10种中选择）、框架应用方案、方案生成
- **10种创新元框架**:
  1. **第一性原理**: 归零重建器——分解到基本元素，仅从事实重建
  2. **逆向思维**: 反共识引擎——反转核心假设，推到逻辑极端
  3. **辩证综合**: 正反合引擎——全力支持正反方，创造合题
  4. **随机性驱动**: 混沌生成器——引入无关概念，强制组合
  5. **演化迭代**: 突变选择器——随机生成方案，迭代循环
  6. **涌现生成**: 规则迭代器——定义基本单位和简单规则，运行系统
  7. **系统动力学**: 反馈循环设计器——识别存量/流量/反馈/延迟
  8. **约束驱动**: 极限约束引擎——强化约束到极限，添加新约束
  9. **故事叙述**: 叙事生成器——故事化重构（英雄旅程）
  10. **游戏化**: 游戏规则设计器——转化为游戏机制
- **可选组件**: 框架组合方案、框架效果评估、创新元框架清单
- **组装顺序**: 领域描述→框架选择→框架应用→方案生成
- **约束**: 框架选择必须基于领域特征；框架应用必须深入
- **格式**: 框架创新方案（Markdown）

#### M6-03 基元运用迁移创新
- **必选组件**: 源领域描述、目标领域描述、结构模式提取（形式化：I→P→O结构+核心机制+关键变量关系）、迁移方案生成
- **迁移类型**: 机制迁移/结构迁移/方法迁移/概念迁移
- **可选组件**: 迁移可行性评估、迁移风险评估、执行流程
- **组装顺序**: 源领域描述→目标领域描述→结构模式提取→迁移方案生成
- **约束**: 源领域必须有清晰可描述的底层结构；迁移必须产生新视角
- **格式**: 迁移创新方案（Markdown）

#### M6-04 基元运用构建创新
- **必选组件**: 两个概念描述、维度解构（每个概念3-5个维度）、维度矩阵、强制连接方案
- **执行流程**: 两个概念→各解构3-5个维度→维度矩阵→随机选3-5个组合强制连接→评估逻辑距离→形成可能性集群→输出最有潜力/最激进/最被忽视的可能性
- **可选组件**: 维度组合评估、连接可行性分析、执行流程
- **组装顺序**: 概念描述→维度解构→维度矩阵建立→强制连接→方案生成
- **约束**: 每个概念必须解构为3-5个维度；必须选择3-5个看似无关的维度组合
- **格式**: 构建创新方案（Markdown）

#### M6-05 基元重组创新
- **必选组件**: 基元列表、重组方式（顺序/并行/条件/循环/扇出/扇入/嵌套）、重组方案、方案评估
- **重组方式说明**:
  - **顺序(→)**: A基元输出→B基元输入
  - **并行(‖)**: A和B同时执行
  - **条件(?)**: 满足条件X执行A，否则B
  - **循环(↻)**: 重复执行A直到条件满足
  - **扇出(⇉)**: A的输出同时供给B/C/D
  - **扇入(⇇)**: B/C/D的输出汇总到E
  - **嵌套**: 基元的P环节展开为子管线
- **可选组件**: 重组可行性分析、重组效果评估
- **组装顺序**: 基元列表确认→重组方式选择→重组方案设计→方案评估
- **约束**: 重组必须产生新的处理链条；重组方案必须可执行
- **格式**: 基元重组方案（Markdown）

#### M6-06 四维评估标准
- **必选组件**: 四维评估结果（每项标注✅/⚠️）、综合评估
- **四维评估内容**:
  1. **问题明确性**: 是否有可解决的核心问题——不通过标志：方案是领域词而非方案（如"数字化转型"而非具体方案）
  2. **可行性基础**: 是否有可依托的资源/能力/条件——不通过标志：找不到可支撑方案落地的核心资源或实现路径
  3. **范围适度**: 是否过泛或过窄——不通过标志：资源不够做/一句话就说完了
  4. **非平凡性**: 是否能产出非平庸结果——不通过标志：结果可预测或已被充分实践
- **可选组件**: 评估维度权重调整、评估结果可视化
- **组装顺序**: 问题明确性评估→可行性基础评估→范围适度评估→非平凡性评估→综合评估
- **约束**: 四个维度必须全部评估
- **格式**: 四维评估报告（Markdown表格）

#### M6-07 领域适配方法
- **必选组件**: 领域特征识别、评估侧重推导、创新风格推导
- **评估侧重推导规则**:
  - 需要落地执行（产品/商业/工程）→ 可行性基础优先
  - 需要理论论证（学术/研究/教育）→ 问题明确性优先
  - 有强约束环境（政策/法律/合规）→ 范围适度优先
  - 需要突破常规（艺术/战略/创新）→ 非平凡性优先
  - 混合型（按实际权衡）→ 取前两位侧重
- **可选组件**: 领域适配示例、适配推导过程说明
- **组装顺序**: 领域特征识别→评估侧重推导→创新风格推导→适配结果确认
- **约束**: 必须根据领域特征推导，不可查表
- **格式**: 领域适配报告（Markdown）

#### M6-08 直用深化
- **必选组件**: 深化来源（M6-06 评估待改进项/M6-07 适配待细化项）、深化类型（方案展开为执行树/路线图生成/风险扫描/原型验证设计）、深化执行方案
- **可选组件**: 多方案并行深化、二阶效应模拟
- **组装顺序**: 深化需求收集→深化方式选择→方案展开→路线图生成→风险扫描→原型设计
- **约束**: 深化须基于已有评估结果；深化方式须根据方案特征选择
- **格式**: 直用深化报告（Markdown）

### M7 创新轴·模式改进域

#### 域级说明

M7 域将已有模式施加变形操作，按变换维度分为内容、输入、结构、框架四类共十种元框架。**路由规则**：M7-01 根据方案特征定位对应变换维度和元框架。**生产力价值**：用十种系统化变形操作替代随机试错，系统性挖掘改进空间。替代的不是十次脑暴会议，是十轮挂着价格标签的外部咨询。深化由 M7-12 完成。

**十种元框架穷尽性证明**：任何对已有方案的"变形操作"，本质上是对方案的某个维度施加变换。变换只涉及四个基本维度，覆盖十种元框架：

| 变换维度 | 元框架 | 操作 | 穷尽说明 |
|---------|--------|------|---------|
| **内容** | M7-02 第一性原理 | 剥掉所有非本质，只留基石 | 消解型——对内容做减法到底 |
|  | M7-03 逆向思维 | 每个假设取反，推到极端 | 反转型——对内容取对立面 |
|  | M7-04 辩证综合 | 正反冲突不选边，向上创造新立场 | 融合型——对内容做超越性整合 |
| **输入** | M7-05 随机性驱动 | 从外部引入无关扰动，打破惯性 | 注入型——改变输入来源 |
|  | M7-06 演化迭代 | 大量变异 + 适应度筛选 + 多代循环 | 选择型——改变输入的生成与淘汰机制 |
| **结构** | M7-07 涌现生成 | 只设简单规则，不设目标，等秩序自发生长 | 自组织型——改变底层结构规则 |
|  | M7-08 系统动力学 | 找到反馈环和高杠杆干预点，撬动系统 | 反馈型——改变结构中的因果链路 |
|  | M7-09 约束驱动 | 改变约束条件（收紧/放宽/替换），在边界处穷尽 | 边界型——改变结构的限制条件 |
| **框架** | M7-10 故事叙述 | 用叙事框架重新组织同一组事实 | 叙事型——改变解释框架 |
|  | M7-11 游戏化 | 叠加挑战/反馈/奖励机制改变行为动力 | 激励型——改变动力框架 |

**为什么没有第十一个？** 四个维度——内容（方案本体）、输入（方案的生产方式）、结构（方案的底层规则）、框架（方案的解释系统）——穷尽了你能对"一个已有事物"施加的基本变换域。十个元框架穷尽了每个维度内的基本操作类型。再多一个，不是冗余（与其他重复）就是特例（是现有某个的子类型）。**十种元框架完备性成立。**

#### M7-01 改进路由选择
- **必选组件**: 方案特征分析、变换维度判定（内容/输入/结构/框架）、对应元框架路由结果
- **可选组件**: 多框架组合策略、路由优先级
- **组装顺序**: 方案特征分析→变换维度判定→元框架路由
- **约束**: 路由须基于方案特征；可组合多个框架但须明确先后顺序
- **格式**: 改进路由选择报告（Markdown）

#### M7-02 第一性原理创新
- **必选组件**: 事物描述、基本元素分解（列出该领域基本事实）、假设区分、从事实重建方案、传统方案对比
- **执行流程**: 作为归零重建器将事物分解到不可再分的基本元素→区分假设→仅从事实出发重新构建解决方案→并与传统方案对比
- **可选组件**: 重建可行性评估
- **组装顺序**: 事物描述→基本元素分解→假设区分→从事实重建→方案对比
- **约束**: 必须分解到不可再分的基本元素；必须仅从事实出发重建
- **格式**: 第一性原理创新方案（Markdown）

#### M7-03 逆向思维创新
- **必选组件**: 事物描述、核心假设识别、假设反转、逻辑极端推导、方案重建
- **执行流程**: 作为反共识引擎列出事物核心假设→反转→推到逻辑极端→重建多个可行方案→整合成为一个方案
- **可选组件**: 反转风险评估、方案可行性分析
- **组装顺序**: 事物描述→核心假设识别→假设反转→逻辑极端推导→方案重建
- **约束**: 必须列出核心假设；必须反转并推到逻辑极端
- **格式**: 逆向思维创新方案（Markdown）

#### M7-04 辩证综合创新
- **必选组件**: 事物描述、正方论证、反方论证、真理局限识别、合题方案
- **执行流程**: 作为正反合引擎对事物同时全力支持正方反方→构建最有力论证→识别各自真理局限→创造包含但超越正题反题新立场→合题发展具体方案
- **可选组件**: 正反方论证深度分析、合题可行性评估
- **组装顺序**: 事物描述→正方论证→反方论证→真理局限识别→合题方案
- **约束**: 必须同时全力支持正方反方；合题必须包含但超越正题反题
- **格式**: 辩证综合创新方案（Markdown）

#### M7-05 随机性驱动创新
- **必选组件**: 事物核心概念、无关概念引入、强制组合、有趣连接保留、方案发展
- **执行流程**: 作为混沌生成器提取事物核心概念→引入无关概念→强制组合→保留看似荒谬但有趣的连接→发展为完整方案
- **可选组件**: 连接可行性评估、方案创新性评估
- **组装顺序**: 核心概念提取→无关概念引入→强制组合→有趣连接保留→方案发展
- **约束**: 必须引入无关概念；必须保留看似荒谬但有趣的连接
- **格式**: 随机性驱动创新方案（Markdown）

#### M7-06 演化迭代创新
- **必选组件**: 事物描述、初始方案生成、迭代循环（评估→选择→交叉→变异→引入）、最优方案输出
- **执行流程**: 作为突变选择器随机生成几个事物解决方案→迭代循环（评估→选择→交叉→变异引入）→输出几个最优方案→选出一个最佳方案
- **可选组件**: 迭代参数设置、方案多样性评估
- **组装顺序**: 事物描述→初始方案生成→迭代循环→最优方案输出
- **约束**: 必须执行完整的迭代循环；必须输出几个最优方案
- **格式**: 演化迭代创新方案（Markdown）

#### M7-07 涌现生成创新
- **必选组件**: 系统描述、基本单位定义、简单规则设计、系统运行、涌现模式提取
- **执行流程**: 作为规则迭代器定义系统中基本单位→设计简单规则→设定主体互动环境→让系统运行足够步骤→记录涌现模式结构行为→提取解决方案
- **可选组件**: 系统运行参数、涌现模式评估
- **组装顺序**: 系统描述→基本单位定义→简单规则设计→系统运行→涌现模式提取
- **约束**: 必须定义基本单位和简单规则；系统必须运行足够步骤
- **格式**: 涌现生成创新方案（Markdown）

#### M7-08 系统动力学创新
- **必选组件**: 系统边界确定、存量/流量/反馈/延迟识别、高杠杆干预点分析、干预方案设计
- **执行流程**: 作为反馈循环设计器确定系统边界→识别存量流量反馈延迟→分析高杠杆干预点→设计干预→模拟二阶三阶效应
- **可选组件**: 二阶三阶效应模拟、干预效果评估
- **组装顺序**: 系统边界确定→存量/流量/反馈/延迟识别→高杠杆干预点分析→干预方案设计
- **约束**: 必须识别存量/流量/反馈/延迟；必须分析高杠杆干预点
- **格式**: 系统动力学创新方案（Markdown）

#### M7-09 约束驱动创新
- **必选组件**: 现有约束识别、约束强化到极限、新约束添加、边界内可能性穷尽、边界方案提取
- **执行流程**: 作为极限约束引擎识别现有约束→强化到极限→添加随机新约束→在约束边界内穷尽可能性→提取边界方案
- **可选组件**: 约束可行性评估、边界方案创新性评估
- **组装顺序**: 现有约束识别→约束强化→新约束添加→可能性穷尽→边界方案提取
- **约束**: 必须强化约束到极限；必须在约束边界内穷尽可能性
- **格式**: 约束驱动创新方案（Markdown）

#### M7-10 故事叙述创新
- **必选组件**: 事物描述、故事化重构（主角/欲望/障碍/导师/转变）、英雄旅程映射、方案提取
- **执行流程**: 作为叙事生成器将事物故事化重构（主角欲望障碍导师转变）→转化为三幕英雄旅程→提取解决方案→将故事元素映射回现实
- **可选组件**: 故事可行性评估、方案落地性分析
- **组装顺序**: 事物描述→故事化重构→英雄旅程映射→方案提取
- **约束**: 必须进行故事化重构；必须将故事元素映射回现实
- **格式**: 故事叙述创新方案（Markdown）

#### M7-11 游戏化创新
- **必选组件**: 事物描述、游戏机制转化（挑战/选择/反馈）、目标规则反馈循环设计、参与驱动方案
- **执行流程**: 作为游戏规则设计器将事物转化为游戏机制（挑战选择反馈）→设计目标规则反馈循环→以意义成就授权产权社交稀缺随机驱动参与→输出可立即使用的游戏化方案
- **可选组件**: 游戏化可行性评估、参与度预测
- **组装顺序**: 事物描述→游戏机制转化→目标规则反馈循环设计→参与驱动方案
- **约束**: 必须转化为游戏机制；必须设计目标规则反馈循环
- **格式**: 游戏化创新方案（Markdown）

#### M7-12 改进深化
- **必选组件**: 深化来源（M7-02~M7-11 任一框架执行后的待展开项）、深化类型（执行树/路线图/风险扫描/原型验证）、深化执行方案
- **可选组件**: 多框架交叉深化、迭代优化策略
- **组装顺序**: 深化需求收集→深化方式选择→方案展开→路线图生成→风险扫描→原型设计
- **约束**: 深化须基于已有改进方案；方式须根据方案特征选择
- **格式**: 改进深化报告（Markdown）

### M8 创新轴·模式迁移域

#### 域级说明

M8 域将异领域模式按粒度从小到大进行跨域迁移——概念（最原子）→ 机制（因果链）→ 结构（关系模式）→ 方法（复合系统）。四类穷尽且互斥。**边界规则**：M8 是异领域迁移，须先抽象化再重新定义；同领域复用走 M6，M8-05 的异质充分性检验为此把关。**生产力价值**：用已验证的异领域方案解决本领域问题，消除跨界探索的盲目性。省掉整个跨领域学习曲线的沉默成本。深化由 M8-06 完成。

**四种迁移穷尽性证明**：一个领域的可迁移要素按粒度从小到大穷尽为四类——**概念**（单个抽象思想，最原子）、**机制**（因果链条：I→P→O+关键变量）、**结构**（要素间的关系模式）、**方法**（完整操作流程系统，最复合）。四类穷尽且互斥。**完备性成立。**

**M8 vs M6 职责边界**：M8 是异领域迁移，须先抽象化再重新定义；同领域复用走 M6。M8-05 的「异质充分性」检验为此边界把关。

#### M8-01 概念迁移
- **必选组件**: 源领域概念描述、目标领域描述、概念重新定义、概念迁移方案
- **示例**: 递归→个人能力建设；熵→市场不确定性定价
- **可选组件**: 迁移可行性评估、迁移效果预测、示例
- **组装顺序**: 源领域概念描述→目标领域描述→概念重新定义→概念迁移方案
- **约束**: 源领域概念必须清晰可描述；概念重新定义必须合理
- **格式**: 概念迁移方案（Markdown）

#### M8-02 机制迁移
- **必选组件**: 源领域机制描述、目标领域描述、机制抽象化（形式化：I→P→O结构+核心机制+关键变量关系）、机制迁移方案
- **示例**: 生态系统"共生"→组织管理；免疫系统→风控架构
- **可选组件**: 迁移可行性评估、迁移效果预测、示例
- **组装顺序**: 源领域机制描述→目标领域描述→机制抽象化→机制迁移方案
- **约束**: 源领域机制必须清晰可描述；迁移必须产生新视角
- **格式**: 机制迁移方案（Markdown）

#### M8-03 结构迁移
- **必选组件**: 源领域结构描述、目标领域描述、结构抽象化、结构迁移方案
- **示例**: 编译器管线→知识转化教学法；句法树→法律条文分析
- **可选组件**: 迁移可行性评估、迁移效果预测、示例
- **组装顺序**: 源领域结构描述→目标领域描述→结构抽象化→结构迁移方案
- **约束**: 源领域结构必须清晰可描述；迁移必须产生新视角
- **格式**: 结构迁移方案（Markdown）

#### M8-04 方法迁移
- **必选组件**: 源领域方法描述、目标领域描述、方法抽象化、方法迁移方案
- **示例**: 对称性破缺→组织变革策略；遗传算法→产品迭代
- **可选组件**: 迁移可行性评估、迁移效果预测、示例
- **组装顺序**: 源领域方法描述→目标领域描述→方法抽象化→方法迁移方案
- **约束**: 源领域方法必须清晰可描述；迁移必须产生新视角
- **格式**: 方法迁移方案（Markdown）

#### M8-05 源领域质量检验
- **必选组件**: 四项检验结果（每项标注通过/不通过）、不通过时的源领域替换建议
- **四项检验内容**:
  1. **结构可提取性**: 源领域是否有清晰可描述的底层结构（非混沌态）
  2. **抽象层级匹配**: 提取的抽象模式是否在目标领域有对应物
  3. **异质充分性**: 源领域与目标领域的差异度是否足够产生新视角
  4. **可操作性**: 迁移后的方案是否可在目标领域落地
- **可选组件**: 检验结果评估、源领域替换建议、检验内容清单
- **组装顺序**: 结构可提取性检验→抽象层级匹配检验→异质充分性检验→可操作性检验
- **约束**: 四项检验必须全部通过；不通过时必须更换源领域
- **格式**: 源领域质量检验报告（Markdown）

#### M8-06 迁移深化
- **必选组件**: 深化来源（M8-05 检验通过后的待细化项）、深化类型（方案细化/适应性调整/路线图）、深化执行方案
- **可选组件**: 多源领域备选、跨领域组合迁移
- **组装顺序**: 深化需求收集→类型识别→方案设计→深化执行
- **约束**: 深化必须基于已通过质量检验的迁移方案；适应性调整保持源领域核心机制不变
- **格式**: 迁移深化报告（Markdown）

### M9 创新轴·模式构建域

#### 域级说明

M9 域是创新轴最底层的生成方式——当所有已知模式都不适用时，从零构建。通过维度矩阵强制连接两个概念，推导可能性集群，生成反常识方案。**生产力价值**：用维度矩阵穷举未知组合，消除"无路可走"的创新停滞。两个不搭边的概念强制连接，生产从未被想到的方案。深化由 M9-07 完成。

#### M9-01 概念解构
- **必选组件**: 两个概念描述、概念A维度解构（3-5个维度）、概念B维度解构（3-5个维度）
- **可选组件**: 维度重要性评估、维度独立性验证
- **组装顺序**: 概念描述→概念A维度解构→概念B维度解构
- **约束**: 每个概念必须解构为3-5个维度；维度必须基本且独立
- **格式**: 概念解构报告（Markdown表格）

#### M9-02 维度矩阵建立
- **必选组件**: 概念A维度列表、概念B维度列表、维度矩阵
- **可选组件**: 矩阵可视化、矩阵分析
- **组装顺序**: 维度列表确认→维度矩阵建立
- **约束**: 矩阵必须完整覆盖所有维度组合
- **格式**: 维度矩阵（Markdown表格）

#### M9-03 强制连接
- **必选组件**: 维度矩阵、随机选择的维度组合（3-5个）、强制连接方案
- **可选组件**: 连接可行性评估、连接创新性评估
- **组装顺序**: 维度矩阵确认→维度组合选择→强制连接
- **约束**: 必须选择看似无关的维度组合；必须执行强制连接
- **格式**: 强制连接方案（Markdown）

#### M9-04 可能性推导
- **必选组件**: 强制连接方案、可能性发展推导、可能性描述
- **可选组件**: 可能性可行性评估、可能性创新性评估
- **组装顺序**: 强制连接确认→可能性发展推导→可能性描述
- **约束**: 必须从每个强制连接推导可能性发展
- **格式**: 可能性推导报告（Markdown）

#### M9-05 可能性集群形成
- **必选组件**: 可能性列表、逻辑距离评估、可能性集群、无人探索区域识别
- **可选组件**: 集群可行性评估、集群创新性评估
- **组装顺序**: 可能性列表确认→逻辑距离评估→可能性集群形成→无人探索区域识别
- **约束**: 必须评估逻辑距离；必须形成可能性集群；必须识别无人探索区域
- **格式**: 可能性集群报告（Markdown）

#### M9-06 方案生成
- **必选组件**: 可能性集群、最有潜力/最激进/最被忽视的可能性选择、反常识方案生成
- **可选组件**: 方案可行性评估、方案创新性评估
- **组装顺序**: 可能性集群确认→可能性选择→反常识方案生成
- **约束**: 必须输出最有潜力、最激进、最被忽视的可能性；必须生成反常识方案
- **格式**: 构建创新方案（Markdown）

#### M9-07 构建深化
- **必选组件**: 深化来源（M9-06 方案生成中的待展开项）、深化类型（执行树/路线图/风险扫描/原型验证）、深化执行方案
- **可选组件**: 多方案并行深化、二阶效应模拟
- **组装顺序**: 深化需求收集→深化方式选择→方案展开→路线图生成→风险扫描→原型设计
- **约束**: 深化须基于已有构建方案；方式须根据方案特征选择
- **格式**: 构建深化报告（Markdown）
