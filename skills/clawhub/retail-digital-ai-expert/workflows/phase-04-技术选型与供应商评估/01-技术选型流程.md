# 01 — 技术选型流程

> **触发条件**：目标架构确认，需要选择具体系统/供应商
> **产出**：详细需求清单 + 自建vs采购决策 + 技术栈推荐

---

## 一、选型流程全景

```
Step 1: 需求清单 → Step 2: 自建vs采购 → Step 3: 长名单(RFI) →
Step 4: 短名单(RFP) → Step 5: 七维评分 → Step 6: PoC → Step 7: 决策
```

---

## 二、Step 1: 需求清单

### 功能需求（按MoSCoW分类）

| 分类 | 定义 | 示例 |
|:---:|------|------|
| **M**-Must 必须 | 缺了就不能用的 | POS必须有离线模式 |
| **S**-Should 应该 | 很重要但可替代 | 应该支持企微会员打通 |
| **C**-Could 可以 | 锦上添花 | 可以支持AI推荐 |
| **W**-Won't 这次不做 | 明确不做 | 本次不要求跨境能力 |

### 非功能需求

| 需求 | 标准 |
|------|------|
| 门店规模 | 支持当前__家，3年内可扩展至__家 |
| 日均交易量 | 高峰__单/秒 |
| 可用率SLA | 99.5%+ |
| 响应时间 | 收银<2秒，查询<1秒 |
| 离线能力 | 断网可收银，恢复后自动同步 |
| 数据本地化 | 数据存储在中国大陆 |
| 安全认证 | 等保二级/三级，ISO27001 |

## 三、Step 2: 自建 vs 采购决策

### 决策框架

| 判断维度 | 倾向采购(SaaS) | 倾向自建 |
|------|:---:|:---:|
| 门店数量 | <200家 | >500家 |
| 行业标准化程度 | 高（需求=行业标准） | 低（需求=竞争差异） |
| IT团队能力 | <10人 | >30人 |
| 市场方案成熟度 | 有成熟方案 | 无合适方案 |
| 时间要求 | <3个月 | >12个月 |
| 预算 | <¥50万/年 | >¥500万/年 |
| 定制化需求 | <20% | >50% |

### 决策矩阵

```
                   采购SaaS  混合（SaaS+自研）  自研
门店数 <50           ✓
门店数 50-200        ✓          ✓
门店数 200-500                  ✓               ✓
门店数 500-2000                 ✓               ✓
门店数 2000+                                     ✓（核心）+SaaS（非核心）
```

### 核心原则

> **200家店以下不碰核心系统自研（POS/ERP/WMS）**
> **核心竞争力部分（数据/AI/会员）可以考虑自研**
> **能买到的、行业标准的、不产生差异化的 → 一定用SaaS**

## 四、Step 3: 长名单筛选（RFI）

### RFI(Information)模板结构

```
1. 公司简介与需求概述
2. 供应商基本信息（成立/规模/融资/客户）
3. 产品功能覆盖度（给功能清单，让厂商标记√/×/部分）
4. 技术架构（部署方式/API/扩展性）
5. 定价模式（许可/订阅/交易费）
6. 实施能力（方法论/周期/培训）
7. 客户参考（3家类似规模/业态）
8. 服务与支持（SLA/响应时间/客服渠道）
```

### 长名单→短名单筛选标准

- RFI回复完整度
- 功能覆盖度>80%Must需求
- 至少3家同等规模/业态的客户
- 价格在预算范围的50-150%之间
- 本地有服务团队

## 六、常见陷阱

1. **厂商Demo看到什么都觉得"我们也要"** → 先确认核心需求，Demo只是验证
2. **只比价格不比TCO** → SaaS年费低但实施费高；开源免费但人力成本高
3. **忽视集成成本** → 选了个便宜的但和现有系统集成要花3倍价格
4. **没有考虑3年后的需求** → 今年够用但明年门店翻倍就撑不住
