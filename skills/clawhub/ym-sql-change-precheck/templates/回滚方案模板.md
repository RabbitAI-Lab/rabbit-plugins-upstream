# 回滚方案模板

> 配合风险报告第五节使用。原则：可逆操作给回滚 SQL；不可逆操作标注"无安全回滚，上线前必须全量备份兜底"。
> 所有回滚 SQL 同样未经执行，需 DBA 评审后使用。

```
## 回滚方案

### 1. 备份兜底（所有变更前必做）
- 全量备份涉及表：`mysqldump -u<user> -p<db> <table> > backup_<table>_<日期>.sql`
- 或快照：按所用数据库平台执行快照，记录快照 ID 便于一键恢复

### 2. 按操作类型的回滚

| 正向操作 | 可逆性 | 回滚 SQL / 动作 |
|----------|--------|-----------------|
| CREATE TABLE | 可逆 | `DROP TABLE <t>;` |
| ADD COLUMN | 可逆（未投产后） | `ALTER TABLE <t> DROP COLUMN <col>;` |
| CREATE INDEX | 可逆 | `DROP INDEX <idx> ON <t>;` |
| ALTER 改列类型 | 视情况 | 改回原类型（可能丢精度，需先备份） |
| UPDATE | 可逆（有旧值） | 上线前先 `SELECT` 记录受影响行旧值，回滚 `UPDATE ... SET col=<旧值> WHERE <条件>;` |
| INSERT | 可逆 | `DELETE FROM <t> WHERE <本次插入的标识条件>;` |
| DELETE（带条件） | 可逆（有备份） | 从备份恢复被删行 |
| DROP / TRUNCATE / 数据清理 | 不可逆 | 无安全回滚，必须依赖第 1 步全量备份恢复 |

### 3. 回滚顺序建议
- 与正向执行顺序相反回滚
- 不可逆操作出问题：停手 → 用备份恢复 → 通知 DBA，不现场拼 SQL 补救

### 4. 未提供回滚时的默认骨架
- 若用户未给回滚脚本，本技能按上表为每条正向语句生成对应回滚项
- 含 DROP/TRUNCATE/清理的，单独列出"无安全回滚，需备份兜底"并高亮
```

## 填写约束

1. 可逆操作必须给具体回滚 SQL，不能只写"反向操作"
2. DROP/TRUNCATE/清理类必须明确"无安全回滚"，指向备份兜底
3. UPDATE/DELETE 回滚依赖旧值记录，方案里写清"先 SELECT 记录旧值"
