# 从回答与材料生成可复用技能

## 生成契约与补充

从现有 brief、用户随时提供的补充和材料建立任务约定：触发范围、输入、交付物、稳定方法、关键事实边界、失败处理、依赖和可观察验收。以实际任务的输入、变换、输出、依赖、状态、质量、异常维度组织方法，领域自由描述，能力按需组合；不因领域陌生、跨领域或未命中问题库而拒绝生成或机械缩小任务。

只有无法确定可交付单元时才继续澄清目标；完整工作流明确时保留其范围。关键规则应改变具体决定，删去只有“认真、专业、优质”而没有操作含义的要求。信息足够就生成，不把普通默认、未知的可选偏好或样例数量设为确认门槛。

材料直接支持的内容记录来源；确定推导、可逆低风险默认和未验证建议按 [问答流程](interview.md) 写入 `supplements`，无需逐项请用户确认。缺少依据的事实、金额、身份、业务口径、专业结论、外部授权及不可逆选择不能编造。关键 `pending` 项只暂停依赖它的部分；可先交付清楚标注的草案，不能把关键假设写成已经成立的规则。

把关键要求与验证做简短追溯，放在制作记录，避免全部塞进技能入口：

| 规则 ID | 规则与适用条件 | 来源或补充 ID | 性质 | 验证用例 |
|---|---|---|---|---|
| R01 | 缺关键日期时保留未知 | 用户明确要求 | 已知约束 | case-missing-value |
| R02 | 输出使用用户交流语言 | S01 | 已应用可逆默认 | case-standard |
| R03 | 单位转换按给定换算率计算 | 材料 M01 与 S02 | 有依据的推导 | case-unit-conversion |

事实、偏好、推导、默认和建议必须可区分。未解决的关键冲突不转换为确定规则；记录候选分支和各自条件。覆盖台账说明维度怎样得到处理，不能代替对应行为证据。

## 文件结构与渐进读取

最小技能可以只有 `SKILL.md`；按实际需要添加资源，不要求统一的大模板。

```text
your-skill-name/
  SKILL.md
  references/       # 按条件读取的长规则与方法
  assets/           # 产出使用的模板或允许复用的素材
  scripts/          # 值得自动化且已运行验证的确定操作
```

入口使用 UTF-8，不把整个文件包在代码围栏中。名称与目录保持一致，开头采用：

```yaml
---
name: your-skill-name
description: 根据哪些输入完成什么任务；当用户提出哪些具体请求时使用。
---
```

description 写实际输入、动作和触发条件，不承诺“万能”。正文只放最短可执行主流程、完成条件、关键分支与执行边界；在容易误触发时说明相邻任务的区别。复杂工作流可保留多个互相关联的交付物和能力，不强制限制分支数。

按任务需要覆盖：输入及关键缺项、核心方法、输出约定、依赖、异常处理、验证与资源读取条件。用户明确偏好和关键边界在入口可见，长例子和罕见分支按条件下沉；引用使用目录内相对路径，并说明何时读取，不无条件加载全部资料。

## 从案例提炼可迁移方法

提炼“在什么条件下，观察哪些信号，因此做什么”，不要固化“这次的答案”。例如，记录写“计划完成”时保留计划语气，只有实际完成证据才写成成果。样例的栏目只有被指定为长期模板才固定；人物、公司、金额、日期和本机路径不能成为未来默认值。

没有独有经验时可从明确目标与验收建立最小候选，并把待积累的经验标为未知。新领域的方法由材料、可核实知识和实际工具条件支持；所需专业方法未核实时标出验证缺口，不凭空给出专业结论。

## 依赖与执行证据

- 通用方法与特定设备接入分开，依赖写明作用、必要／可选、输入输出及不可用时的处理。
- 不把本机绝对路径、用户名、凭据或会话 ID 写入可分享入口。确需绑定本机时，作为显式配置保存并说明适用环境。
- 脚本要有明确输入、输出、失败返回与依赖，新增或改变的实际逻辑需运行验证。格式检查通过不等于事实正确。
- 文件存在、生成成功、实际打开、渲染正确、可编辑性、目标工具执行和自动触发分别需要相应证据。
- 没有兼容宿主时可以显式读取入口演练，标为“显式加载实验”，不能据此声称安装后自动发现已验证。
- 创建技能本身不自动赋予发送、发布、安装或修改外部账户的权限。按用户已有授权推进，只对尚无授权的对应动作保留边界。

## 可观察验收与范围

把“结果准确、专业”改成能观察的条件，例如“数值能按明确口径复算”“引用支持相邻结论”“实际文件可编辑”“没有执行未授权发送”。从当前任务的维度与失败风险选择用例，不拿一个领域的栏目、格式或固定案例数约束其他领域。

格式与语义分别验证：引用编号可自动检查，引用是否支持结论需要核对内容；文件需要在实际产物上检查，不能只看生成说明。跨领域组合同时验证每个必要能力和它们之间的传递，例如单位、版本、引用和状态是否在交接中保留。

“全场景覆盖”落实为已声明维度、关键组合和异常路径的覆盖记录；新领域可继续扩展，没有行业白名单。有限实验只能证明列出的版本、环境和场景，不承诺穷尽所有未来输入或所有模型。

## 多轮修订与交付

用户在生成前后主动新增要求，都合并进当前 brief；无需等待那一题被问到。以当前明确要求替换旧偏好，保留变化依据，不反复要求恢复旧版本。每次规则变更递增 `revision`，在制作记录列出：

| 变更对象 | 需要检查的影响 |
|---|---|
| 输入、事实来源、业务口径 | 提取结果、推导、计算、结论及其断言 |
| 方法或输出要求 | 入口、引用、脚本、模板、已有产物和相关验收 |
| 依赖、权限或执行方式 | 工具调用、降级、外部动作、失败与恢复断言 |
| 偏好、适用范围或状态规则 | 触发用例、多轮续接、已有输出与回归预期 |

将受影响产物和断言标为“待更新／待重测”，保留旧版证据及版本指纹，不能把旧通过结果转记到新版。重做受影响案例，并覆盖必要关联回归；不相关证据可保留，但注明它对应的版本和未受影响的理由。

为每个目标技能建立自己的 `experiment-suite.json`；工坊的 `assets/experiment-suite.json` 用于测试工坊，不能原样当作所有目标技能的验收。测试包含用户目标、相关维度组合、必要异常和多轮修改，具体执行与评估见 [评估方法](evaluation.md)。

交付包括可复制技能目录及其实际引用资源、简明启动方法和依赖、去除不必要私人材料的 brief 与追溯记录，以及对应案例、证据和修订记录。简单任务可以合并文档。

标记 `candidate`（关键行为仍失败或未执行必要验证）或 `validated-in-scope`（列出的环境与场景内达到验收）。按用户要求或失败证据做聚焦修改，保留修订前后证据。默认最多连续修复 3 轮，用户可调整；预算用尽仍未达标就交付候选并列明缺口，不伪造通过。

工坊默认的 2 次实验重复和 3 个修复轮只用于制作与审计，不自动成为目标技能的日常步骤；日常检查强度由任务风险和用户要求决定。
