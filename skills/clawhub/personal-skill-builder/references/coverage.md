# 开放场景覆盖设计

“无特定场景限制”意味着根据实际任务建立维度、按需要组合能力、接纳新领域和新约束，不意味着每个生成技能要包办所有任务。领域标签是描述信息，不是准入条件。

## 先声明覆盖，再看结果

1. 将需求拆为可观察行为：输入与来源、变换、输出、依赖与授权、状态、质量、异常。按任务加入子维度，例如 output.editability、state.resume；维度名称自由定义。
2. 对适用维度分别给出正常路径与会导致错误的变化。审计工坊自身时，包含用户未被问到的主动补充、AI 主动查漏、低风险默认与关键未知的区分；评估生成的目标技能时仅选与其能力相关的项目。将不适用项及理由写入范围说明，不能事后为去掉失败而排除维度。
3. 设计少量能覆盖交互的组合案例：多能力衔接、资料冲突后澄清、续接时新材料解决旧问题、工具失败后更换输入、生成后改规则。组合数量和领域不限，但不为凑矩阵无限增加任务。
4. 将断言映射到覆盖维度，而非仅给案例贴标签。一个断言可以观察多个维度，但必须能提供各项具体证据。关键维度只有其全部计划记录均已执行、判定且通过，才标 verified。
5. 在结果揭晓前固定案例、重复次数、所用工具和验收条件。保留至少一例作者未针对其具体答案调整规则的留出案例。评测执行者只看当前用户轮和必需材料，不看未来轮次、评分断言或旧实验答案。
6. 每个案例从新上下文开始；其内部后续消息在上一轮结束后逐条投递。重新执行使用新上下文，不把同一输出复制成重复实验。
7. 结果表列出遗漏、待执行、阻塞、未判定、失败和通过。增加维度或改技能后重新绑定版本并补测，不能延用旧报告声称新范围已覆盖。

可以先用模板声明一组通用维度，但不得把模板当成穷尽列表。新工具、新产物、新领域或运行条件带来新的错误方式时扩展维度和实验。通用向导的机制验证、某个生成技能的功能验证、宿主自动触发验证分别记录。

对于计算与受限输出，按实际任务增加 `data.domain`（合法数值与跨字段关系）、`data.invalid-isolation`（未知字段不参与不可靠计算）、`output.all-paths`（自由文本等全部出口遵守展示约定）、`output.allowed-content`（允许信息仍保留）、`artifact.raw` 与 `artifact.final`（脚本原始产物和最终交付独立通过）。维度名称可自定义，未涉及的项注明不适用原因；不把禁止负数或隐藏金额设为跨领域默认。

修复的覆盖必须有旧失败、改变数值／书写形式／字段位置的留出变体和正常例。执行者不预先知道断言；独立审阅者核对实际字段，不能只采纳执行者的“全部通过”自评。普通新上下文重复、多轮状态更新、冷续接和新周期数据隔离分别记录，不能互相代替。

## 可复用的维度契约

suite 的 coverage_contract.dimensions 接受任意唯一 id、description 与 required 布尔值；断言的 dimensions 引用这些 id。缺少必测维度的断言，或全部仅规划未执行，都不构成全覆盖。category 与 domain 没有固定枚举。

逐轮输出必须来自实际执行，保存 UTF-8 原文及哈希。哈希只能证明文件未变，不能证明模型真实执行、无外部副作用或人工判定正确；这些仍依赖执行轨迹和独立核对。

报告说“本次声明的 X 个维度，在 Y 个案例、Z 次独立执行中通过”，同时写实际环境。不同模型、真实账户、远端操作、自动触发或未打开的宿主不因本地实验成功而自动获得通过结论。无需让用户为这种范围说明再次确认。
