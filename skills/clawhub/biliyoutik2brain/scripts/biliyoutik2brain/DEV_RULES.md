# BiliYouTik2Brain 开发规则

## 核心理念：让代码跑确定，提示词做不确定

这是整个项目的第一原则，所有设计决策都必须服从。

### 什么是"确定的"（代码处理）

可计算、有明确边界、可穷举的：

| 领域 | 具体 | 工具 |
|:-----|:-----|:-----|
| 资源评估 | 工作量=时长×模型复杂度，对比历史容量×0.8 | `assess_and_route()`, `record_task()` |
| 分块决策 | workload > capacity×0.8 → chunk | `transcribe()` 容量感知逻辑 |
| VAD静音检测 | ffmpeg silencedetect 找自然停顿 | `_detect_silence_points()` |
| 切分点选择 | 15min边界 ±3min窗口内找最近静音 | `_find_best_split()` |
| 资源争抢 | 文件级轻量锁 | `_acquire_lock()` / `_release_lock()` |
| 确定性替换 | 100%不会错的whisper误识别修正 | `_smart_correct()` |

### 什么是"不确定的"（prompt处理）

需要语境判断、语义理解、专业知识的：

| 领域 | 具体 | 工具 |
|:-----|:-----|:-----|
| 同音字纠错 | "主力/阻力"、"孕线/均线"等语境敏感替换 | LLM 提示词中的纠错规则 |
| 内容分析 | 提取摘要、关键词、章节划分 | LLM 结构化分析 prompt |
| 置信度判断 | 转录质量的综合评价 | LLM 输出的 confidence_score |
| 领域感知 | 交易/编程/财经等不同领域的术语优先 | 说话人知识库 + LLM 提示 |

### 为什么这么分

两条简单因果链：

```
确定性链条（代码可控）：
  时长 → 容量计算 → 是否分块 → 静音检测 → 切分点 → 各段转录 → 拼接
  ↑ 每一步都是可计算、可验证的，无需"猜测"

不确定性链条（LLM处理）：
  转录文本 → 同音字纠正 → 语义修复 → 关键词提取 → 章节划分
  ↑ 每一步都需要"理解"，只能靠大模型
```

如果把确定性的事塞给prompt（比如"按15分钟分块"），prompt会：
- 每次理解不同，行为不一致
- 浪费token重复说明规则
- 出错时难以定位是代码问题还是prompt问题

反过来，把不确定的事硬编码（比如"主力→阻力"全局替换），会导致：
- 过度纠错（把"主力吸筹"变成"阻力吸筹"）
- 规则火山（每个词都要列举上下文例外）
- 维护灾难

### 落地检查清单

每次改代码前，先问自己：

```
❓ 这个改动处理的是"确定"的事还是"不确定"的事？
  确定 → 写在代码里（函数/if/数学计算）
  不确定 → 写在提示词里（prompt/规则/例子）

❓ 如果写在代码里，有没有可能变"确定"？
  比如"根据系统负载80%做分块"——可以，因为计算是确定的

❓ 如果写在prompt里，有没有可能太快"确定"？
  比如"所有同音字替换"——不行，"主力"在两种语境下意思完全不同
```

### 历史教训

1. **v1.1.0 bug**（05-12）：`transcribe()` 硬编码 `duration_s < 30min` 判断，else 分支名字叫 "chunked" 但实际调的是 `transcribe_full_audio()`——不切片。违反"代码说真话"原则。
2. **"主力→阻力"困境**（05-12）：用全局替换的同音字修正导致"主力吸筹"被误改。这是把不确定的判断放进代码的错误。
3. **提示词膨胀**（05-11）：纠错词典 `SPEAKER_CORRECTIONS` 无限扩张，每个词都带上下文规则——这是把代码逻辑搬进了prompt的错误。

## 架构原则

### 1. 容量感知调度（v1.7.0+）

```
T × M ≤ C × 0.8
```
- T = 视频时长（分钟）
- M = 模型复杂度（base=1, tiny=0.5）
- C = 历史校准的云端容量
- 0.8 = 安全余量（留20%给系统开销和其他任务）

### 2. 分块转录策略

触发条件（满足任一）：
- workload > capacity × 0.8
- 时长 > 30分钟
- 时长 > 15分钟 且 历史容量 < 60（冷启动）

分块参数：
- 目标段长：15分钟（900秒）
- 搜索窗口：±3分钟找静音点
- 段间重叠：30秒（边界保护）

### 3. 资源争抢

使用文件锁 `~/.biliyoutik2brain_transcribe.lock`：
- 长视频分块前获取锁
- 加锁时写 PID + 时间戳
- 锁过期（>30min）自动释放
- 获取锁失败：最多等10分钟
- 超时仍失败：回退到全量转录（有风险，但比卡死好）

### 4. 版本管理

- 开发版：`~/openclaw/workspace/biliyoutik2brain/`
- 发布版：`~/.openclaw/skills/biliyoutik2brain/scripts/`
- 新功能在开发版先测，稳定后同步到发布版
- 紧急修复可直接改发布版，改完立即通知同步回开发版

## v3 改造落地案例（2026-05-21）

### L2批量化（最大收益点）
**问题**: `_llm_fix_one_word()` 每个低置信词独立一次API调用，N个词=N次调用。
**改造**: 先查确定性词典(0 LLM) → 剩余打包为1次批量调用 → 批量失败才逐词兜底。
**结果**: N次API调用 → 最多2次(N=0 或 N=1)。
**原则应用**: 确定性查表代码做，语义修复prompt做，一次做完。

### L1加"反面"
**问题**: L1只有正面确认(字幕中有=确认)，缺反面(字幕中没有怎么办)。
**改造**: 加编辑距离轻量语义匹配，高度相似(≥0.7)但不完全一致→标记需人工确认；完全不匹配→保持原置信度。不调LLM。
**原则应用**: 字符串算法是代码确定的事，不用LLM判断。

### L4 OCR接入
**问题**: `level4_ocr_frame` 是空壳 `return []`，`_match_ocr_words` 已实现但未被调用。
**改造**: 利用 `enhance_engine` 传入的 `ocr_context`，代码做匹配(OCR中有→确认)。自动启用(有OCR数据时不需手动 `enable_ocr=True`)。
**原则应用**: OCR匹配是字符比较，代码做；OCR提取是预先算好的数据。

### 代码收口层
**新增**: `_final_code_check()` 在 `enhance_and_analyze` 末尾做代码最终裁决：
1. 高置信词保护(原始≥0.9的词被修了要警告)
2. 长度变化合理性检查
3. 置信度由代码根据修正比例和原始置信度计算(不用LLM打分)
**原则应用**: LLM产出必须被代码验证，代码做终结者。

### 异常保护
**新增**: 所有批量和逐词循环都包了 try/except，单步失败不破坏整段修复。
