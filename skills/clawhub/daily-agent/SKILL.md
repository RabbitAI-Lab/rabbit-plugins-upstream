# Daily Agent — 任务调度中枢 v2.17.0

**所有对话先调用 daily-agent**，由它决定执行路径。

**职责**：任务调度中枢 — 负责任务分类、路由、技能匹配与执行监控，不直接操作工具或数据。

## 核心职责

```
用户消息 → daily-agent（第一条操作）
  ├─ Step 1: 任务分类（什么类型？）
  ├─ Step 1.5: 记忆预加载（Top 3 相关场景摘要）（v2.8 新增）
  ├─ Step 1.8: 技能自动触发（PreTask hook）（v2.9 新增）
  ├─ Step 2: 复杂度评估（短链/长链？）
  ├─ Step 3: 执行路由（主会话/spawn/cron？）
  ├─ Step 4: 技能匹配（需要哪个skill？由daily-agent决定）
  ├─ Step 4.5: 执行前读规划文件 + 2-Action Rule（v2.10 新增）
  ├─ Step 5: 委派执行与状态监控
  ├─ Step 5.5: 异常处理与降级
  └─ Step 6: 收尾检查（浏览器/学习/git/记忆/上下文摘要/规划文件更新）
```

在任务分类前，先检测是否触发内置模式：

| 模式 | 触发关键词 |
|------|-----------|

**若命中**：

## Step 0.5: Converse 意图检测（v2.5.0 新增）

> 核心原则：分离"讨论"和"执行"意图。用户在描述想法时，AI 不应立即执行，而是先进入讨论阶段。

### 三层意图检测

**Layer 1: 显式触发（直接进入 CONVERSE）**

触发词：`讨论一下` / `你觉得` / `帮我分析` / `我在想` / `聊聊` / `converse` / `分析一下` / `XX怎么样` / `XX好不好` / `可行吗` / `有没有可能`

→ 直接进入 Converse 模式，告知用户："进入讨论模式。"

**Layer 2: 隐式触发（提示用户确认）**

句式模式：
- 消息以"我在想"开头，但无后续操作指令
- 消息包含"是不是可以"但无具体操作动词
- "我想做XX"（无具体指令）

→ 提示确认："听起来你在探索一个想法——要进入讨论模式吗？还是想让我直接开始？"

**Layer 3: 上下文推断（自动进入）**

- 用户连续 2+ 条消息都是讨论性质（无明确操作动词）
- → 自动进入 Converse 模式，告知用户："检测到连续讨论，已切换到讨论模式。"

### 退出 Converse 的条件

用户说出以下任一情况 → 立即退出 CONVERSE，进入执行：

**显式退出词**：`执行` / `开始` / `做吧` / `动手` / `就这么做` / `go` / `implement` / `结束讨论` / `退出 converse`

**隐式退出**：用户给出明确操作指令（"创建文件"、"写代码"、"发送"、"帮我做"、"实现"、"部署"）

### CONVERSE 状态下的行为约束

1. **禁止写操作**：不调用 write / edit / exec(写操作) / browser(写操作) / message
2. **允许读操作**：read / web_search / web_fetch（用于支撑讨论）
3. **输出风格**：提问 > 断言，探索 > 结论，挑战假设 > 直接执行
4. **每次回复末尾**：提供推进选项
   ```
   ---
   ?? 推进选项：继续讨论 | 转为执行（说"执行"即可）| 暂停
   ```
5. **可与 grill-me/ToT 叠加**：讨论时自然会有审视和多路径探索

### 状态维护

在对话上下文中维护 Converse 状态：
```json
{
  "converse_active": true/false,
  "converse_topic": "讨论主题",
  "discussion_points": ["已讨论的要点"],
  "pending_action": "待执行的操作（用户说执行后执行）"
}
```

### 执行中暂停回退（v2.5.0 补充）

如果 AI 正在执行写操作，用户说 **"等等，讨论一下"** / **"停，先聊聊"** / **"暂停，我想讨论"**：

1. **立即暂停当前执行链**
2. **保存当前执行进度**到 `pending_action`
3. **进入 CONVERSE 状态**，回复：
   ```
   ?? 已暂停执行。
   
   当前进度：[简要说明执行到哪一步]
   待执行：[剩余操作]
   
   你想讨论哪个方面？讨论完说 **"继续执行"** 即可恢复。
   ```

### 讨论记录持久化（v2.5.0 补充）

退出 Converse 时（用户说"执行"后），将讨论摘要写入当日记忆：

```markdown
## Converse 讨论记录 [HH:MM]
- **主题**：[topic]
- **参与模式**：[Converse / Converse + grill-me / Converse + ToT]
- **讨论要点**：
  1. [要点1]
  2. [要点2]
- **结论/决策**：[最终决定]
- **后续执行**：[pending_action]
```

写入位置：`memory/YYYY-MM-DD.md`

## Step 1: 任务分类（v2.4.0 重构为三级判断）

### 第一级：触发方式判断

```
收到消息
    │
    ├─ cron/定时触发 ──→ 直接匹配 cron 专用技能
    │   （关键词：每天/每周/定时/提醒/周期）
    │
    └─ 手动/事件触发 ──→ 继续第二级
```

### 第二级：领域分类

| 领域 | 典型场景 | 特征 |
|------|---------|------|
| **通信** | 发消息、发邮件、发通知 | 匹配 mx-im/outlook 技能 |
| **记忆** | "记住XX"、更新规则、知识录入 | 匹配 self-improving/ontology |
| **文件** | 做 PPT/Word/Excel/PDF/HTML | 匹配对应文件技能 |
| **编码** | 写代码、调试、重构、测试 | 匹配编码类技能 |
| **搜索** | 搜资料、搜新闻、技术调研 | 多引擎搜索，交叉验证 |
| **查询** | 查消息、查天气、查文件、查状态 | 1-3 次工具调用，即时返回 |
| **对话** | 闲聊、问答、讨论、建议 | 无需工具调用，或 ≤2 次 |

### 第三级：复杂度评估

在领域分类后，评估任务复杂度，决定执行环境（主会话/spawn）。

### 第四级：任务模式判断（v2.17 新增）

> 借鉴游戏设计中的 Fog of War（战争迷雾）：不是所有任务都能预先规划全部步骤，有些任务需要"边走边看"。

在复杂度评估后，判断任务的执行模式：

| 模式 | 特征 | 典型场景 |
|------|------|----------|
| **确定性模式**（默认） | 路径清晰，步骤可预先枚举 | 已知功能实现、bug修复、文件生成 |
| **探索性模式** | 路径未知，需逐步探索 | 新架构设计、未知领域研究、方案对比、技术调研 |

**识别规则**：

```
任务描述
    │
    ├─ 包含以下关键词之一 → 候选探索性模式：
    │   探索 / 设计 / 研究 / 分析 / 不确定 / 未知 / 方案对比
    │   "不知道怎么做" / "需要边做边看" / "先看看" / "调研"
    │
    ├─ 任务涉及"首次接触"的技术/领域 → 探索性模式
    │
    ├─ 任务的输出不确定（不是明确的文件/代码/数据） → 探索性模式
    │
    └─ 任务路径清晰、步骤可枚举 → 确定性模式（默认）
```

**确认方式**：
- 如果判断为探索性模式，告知用户："这个任务路径不太确定，我将使用探索模式——走一步看一步，每步完成后根据新信息决定下一步。"
- 用户可覆盖判断："这个我知道怎么做" → 强制确定性模式

### 决策矩阵

| 触发方式 | 领域 | 复杂度 | 执行策略 |
|---------|------|--------|---------|
| cron | * | * | cron 专用技能 |
| manual | memory | * | memory 技能 + 主会话 |
| manual | comm | * | 通信技能 + 主会话 |
| manual | file/code/search | long | 匹配技能 + spawn |
| manual | file/code/search | short | 匹配技能 + 主会话 |
| manual | query/chat | * | 主会话直接回复 |
| **converse** | **任意** | **任意** | **主会话讨论（禁止 spawn/write）** |

### 分类优先级（当任务跨多领域时）

1. **通信** — 涉及"发送给/发到群里/通知"
2. **记忆** — 涉及"记住/记一下/更新规则"
3. **文件** — 涉及具体文件格式
4. **编码** — 涉及代码/调试/测试
5. **搜索** — 涉及"搜/查/找"
6. **查询** — 简单查询
7. **对话** — 默认

**完成条件**：已输出任务分类结果，包含四级判断（触发方式、领域、复杂度、任务模式），明确了执行策略（主会话/spawn/cron）和执行模式（确定性/探索性）。

## 探索性任务模式（v2.17 新增）

> 借鉴游戏设计中的 Fog of War（战争迷雾）：对于路径未知的任务，不预先规划所有步骤，而是用"决策地图"代替"执行计划"，每完成一步后根据新信息决定下一步。

### 确定性模式 vs 探索性模式

| 维度 | 确定性模式（默认） | 探索性模式 |
|------|-------------------|-----------|
| 规划方式 | 预先枚举所有步骤 | 只规划"当前可见"的下一步 |
| 进度追踪 | 执行计划 + checkbox | 决策地图 |
| 步骤间行为 | 按既定计划执行 | 根据新信息重新评估 |
| 适用场景 | 路径清晰、经验范围内 | 路径未知、需要探索 |
| 失败预期 | 步骤可能失败，但路径已知 | 路径本身可能需要调整 |

### 决策地图格式

探索性模式使用"决策地图"代替传统执行计划：

```markdown
## 决策地图

### 已解决
- [决策1]: [结论]
- [决策2]: [结论]

### 当前焦点
[当前正在解决的问题]

### 下一步选项
- 选项A: [描述] → 预期结果: [描述]
- 选项B: [描述] → 预期结果: [描述]

### 模糊区域（Not yet specified）
- [故意不规划的未知区域1]: 信息不足，待后续决策
- [故意不规划的未知区域2]: 依赖前面的决策结果
```

### 探索性模式执行规则

1. **不预先规划所有步骤** — 只规划当前可见的下一步
2. **每步完成后更新决策地图** — 将新发现填入"已解决"，更新"当前焦点"
3. **根据新信息决定下一步** — 不是机械执行计划，而是基于最新认知
4. **标记 Fog of War 区域** — 对"故意不规划"的区域明确标注 `Not yet specified`
5. **允许路径大幅调整** — 探索中发现新方向是正常的，不是失败

### Fog of War 标记规范

在任务输出中，对尚未明确的区域使用以下标记：

```markdown
### ? Fog of War 区域

以下区域当前信息不足，**故意不做规划**：

- **[区域名称]**: Not yet specified
  - 原因: [为什么现在无法规划]
  - 澄清条件: [什么信息出现后可以规划]
```

**标记原则**：
- Fog of War 不是"忘了规划"，而是"故意不规划"
- 每个 Fog of War 区域必须说明原因和澄清条件
- 随着探索推进，Fog of War 区域应逐渐缩小

### 模式切换

**探索性 → 确定性**：
- 触发：用户说"现在路径清晰了" / "我知道怎么做了" / 探索中所有 Fog of War 区域已消除
- 行为：将决策地图中的"已解决"和"当前焦点"转化为确定性执行计划，切换到 checkbox 追踪

**确定性 → 探索性**：
- 触发：执行中遇到意外（预期外的错误/行为/依赖） / 用户说"等等，我不确定" / 发现原计划不可行
- 行为：暂停当前执行计划，切换到决策地图模式，将意外纳入"当前焦点"

**切换时输出**：
```
?? 模式切换: [确定性/探索性] → [探索性/确定性]
原因: [为什么切换]
当前状态: [决策地图 / 执行计划]
```

## Step 1.5: 记忆预加载（v2.8 新增，渐进式披露优化）

> 借鉴 Claude-Mem 的渐进式披露设计：不一次性加载全部记忆，而是按需预加载相关场景摘要。

### 预加载策略

根据 Step 1 的任务分类结果，从 scene-navigation 中选择相关场景：

```
任务分类完成
    ↓
解析任务关键词（编码/记忆/文件/搜索...）
    ↓
从 scene-navigation 匹配相关场景（按热度排序）
    ↓
根据热度分级注入（v2.8.1 新增）
    ↓
任务执行中需要详情时 → 按需 read 完整 scene block
```

### 场景匹配规则

| 任务领域 | 优先匹配的场景关键词 |
|---------|---------------------|
| 编码 | coding-framework, skill开发, 编程任务 |
| 记忆 | 记忆系统, memory-tencentdb, ontology |
| 文件 | 文档处理, PPT, Excel, PDF |
| 搜索 | 新闻日报, 技术调研, 行业分析 |
| WCS | WCS项目, 仓储系统 |
| 焊接 | 自适应焊接, 视觉检测 |
| 巡检 | 移动巡检, VMS |

### 热度分级注入规则（v2.8.1 新增）

根据场景热度决定注入详细程度：

| 热度 | 级别 | 注入内容 | 示例 |
|------|------|----------|------|
| ≥10 | ?? 热场景 | 完整摘要（2-3行） | `### 1. {场景名}（热度: XX ??）\n{完整摘要}` |
| 5-9 | ??? 温场景 | 一行摘要 | `- {场景名}（热度: X）: {一句话摘要}` |
| <5 | ?? 冷场景 | 只注入场景名 | `- {场景名}（热度: X）` |

### 注入格式示例

```markdown
## ?? 相关记忆（预加载）

### ?? 热场景（完整摘要）
1. **coding-framework v10.9**（热度: 56 ??）
   统一编程框架，7种工作模式，8个子代理，Rubber Duck自动审查，Plan Mode，Explore侦察。

### ??? 温场景（一行摘要）
- **WCS项目**（热度: 8）: 仓储控制系统，完成度95%，剩余5%为外部集成Mock。
- **自适应焊接**（热度: 6）: 激光视觉焊缝跟踪，KNN参数调节，PoC阶段。

### ?? 冷场景（仅场景名）
- 移动巡检项目（热度: 3）
- 勒索软件事件（热度: 1）

?? 需要详情时，使用 `read` 工具加载完整 scene block。
```

### 预期效果

- 减少初始 token 消耗（从 2-3KB 降到 500-800 token）
- 热场景保留完整上下文，冷场景仅保留可检索索引
- 保持记忆可用性（按需加载）
- 避免无关场景污染上下文

**完成条件**：已输出相关记忆预加载摘要，包含热场景（≥10，完整摘要）、温场景（5-9，一行摘要）、冷场景（<5，仅场景名），总 token 消耗 ≤ 800。

## Step 1.8: 技能自动触发（v2.9 新增）

> 借鉴 Superpowers 的技能自动触发设计：任务开始前，根据任务特征自动加载相关技能上下文。

在 Step 1（任务分类）和 Step 1.5（记忆预加载）完成后，调用 PreTask hook：

### 执行流程

```
任务分类 + 记忆预加载完成
    ↓
构建 PreTask 事件数据：
  {
    "task_type": "coding",          // 从 Step 1 获取
    "files": ["src/main.py", ...],  // 从用户消息/上下文中提取
    "keywords": ["review", ...]     // 从用户消息中提取关键词
  }
    ↓
调用 hook-engine：
  bash skills/hook-engine/hooks/pre-task-check.sh
    ↓
解析返回结果：
  {
    "triggered_skills": ["python-reviewer", "code-reviewer"],
    "context_injection": "已加载 2 个技能上下文"
  }
    ↓
自动加载触发技能的上下文（read SKILL.md 前 50 行）
    ↓
继续 Step 2（复杂度评估）
```

### 触发规则

规则定义在 `skills/hook-engine/rules/skill-triggers.md`：

| 条件 | 触发技能 | 优先级 |
|------|----------|--------|
| task_type=coding + *.py | python-reviewer | 10 |
| task_type=coding + *.ts/*.js | typescript-reviewer | 10 |
| keywords=review/审查 | code-reviewer | 20 |
| keywords=security/安全 | security-auditor | 30 |
| keywords=test/测试 | test-engineer | 15 |
| keywords=architecture/架构 | architecture-critic | 25 |
| keywords=performance/性能 | performance-analyst | 25 |
| keywords=explore/侦察 | explore | 5 |

### 注意事项

- 显式调用优先：用户说"用 XX 技能"时，不自动触发
- 最多触发 3 个技能，避免 token 浪费
- 每个技能只加载 SKILL.md 前 50 行（摘要级）
- 无匹配时静默通过，不影响正常流程

## Step 2: 复杂度评估（v2.4.0 增强）

### 评估方法：加权成本计算（v2.4.0 新增）

**工具类型权重表**：

| 工具类型 | 权重 | 说明 |
|---------|------|------|
| browser | 8 | 最耗时，涉及页面渲染 |
| exec | 5 | 命令执行，可能耗时 |
| web_fetch | 4 | 网络请求 |
| web_search | 2 | API 调用，较快 |
| read | 1 | 本地文件读取 |
| write/edit | 2 | 本地文件写入 |

**复杂度评估公式**：

```
总成本 = Σ (工具类型权重 × 调用次数)

soft_limit = 20   # 预警
hard_limit = 40   # 强制 spawn

if 总成本 > hard_limit:
    → 长链，必须 spawn
elif 总成本 > soft_limit:
    → 预警，建议 spawn，但允许主会话执行
else:
    → 短链，主会话执行
```

**保留原规则作为兜底**：
- 工具调用次数 ≥ 10 → 长链
- 涉及数据源 ≥ 3 → 长链

### 短链任务

- 在主会话直接执行
- 工具调用上限：5次
- 超过5次 → 立即转spawn

### 长链任务

- 必须spawn子代理执行
- 主会话只负责：接收结果、汇报用户
- 禁止在主会话"先做几步"再spawn

## Step 3: 执行路由

根据任务类型和复杂度，选择执行方式：

| 条件 | 执行方式 | 说明 |
|------|---------|------|
| 短链 + 对话/查询 | 主会话直接回复 | 最简单路径 |
| 短链 + 搜索/文件/编码 | 主会话 + 匹配skill | 加载对应SKILL.md |
| 长链 | spawn子代理 | 后台执行，完成后汇报 |
| 定时任务 | cron | 创建/触发cron job |
| 通信任务 | mx-im/outlook | 直接调用通信技能 |

### spawn子代理时的规则

1. **必须提供完整上下文**：任务描述、输入文件、期望输出
2. **设置合理超时**：根据任务复杂度分级（见下表）
3. **可选：创建监控任务**：对于超长任务，创建一次性at监控

### runTimeoutSeconds 配置规则（v2.14.0 新增）

根据任务复杂度评估结果，设置对应的 `runTimeoutSeconds` 参数：

| 复杂度等级 | runTimeoutSeconds | 典型场景 | 判断标准 |
|-----------|-------------------|---------|---------|
| **trivial** | 30 | 简单查询、单文件读取、输出固定内容 | 1-2次工具调用，无网络请求 |
| **small** | 60 | 文件编辑+提交、简单搜索、配置修改 | 3-5次工具调用，少量网络请求 |
| **medium** | 120 | 多文件修改、报告生成、数据分析 | 6-10次工具调用，涉及文件读写+exec |
| **large** | 240 | 复杂报告、多步骤网页探索、代码审查 | 11-20次工具调用，涉及browser/web_fetch |
| **critical** | 360 | 大型项目构建、批量处理、深度分析 | 20+次工具调用，多数据源+多文件生成 |

**复杂度评估方法**：
```
工具调用次数预估：
  - read/write/edit: 1次
  - exec: 1-3次（取决于命令复杂度）
  - web_search: 1-2次
  - web_fetch: 2-5次（可能需要多次抓取）
  - browser操作: 3-10次（snapshot+act序列）

复杂度映射：
  1-2次 → trivial (30s)
  3-5次 → small (60s)
  6-10次 → medium (120s)
  11-20次 → large (240s)
  20+次 → critical (360s)
```

**spawn调用示例**：
```
sessions_spawn(
    task="任务描述",
    mode="run",
    runTimeoutSeconds=120,  // 根据复杂度评估设置
    ...
)
```

**注意事项**：
- 宁可设置偏大，避免任务因超时被截断
- 子代理实际完成时间通常远小于timeout
- 超时后子代理会被kill，已完成的文件操作不会丢失

## Step 3.5: 阶段编排 — Hat 动态切换（v2.11 新增）

> 借鉴 ralph-orchestrator 的 Hat System：大型编程任务按阶段动态切换角色，而非一次性执行。

### 触发条件

- 任务类型 = coding
- 复杂度 = large 或 critical
- 用户未明确说"直接写"

### 阶段流程

```
大型编程任务
    │
    ├─ Phase 1: Research Hat（侦察）
    │   ├─ 分析代码库结构、依赖关系、现有模式
    │   ├─ 输出：context 摘要（关键文件、架构约束、技术栈）
    │   └─ 实现：调用 coding-framework 模式7 Explore
    │
    ├─ Phase 2: Plan Hat（规划）
    │   ├─ 基于 context 生成实现计划
    │   ├─ large → PDD .specs/ 目录（requirements + design + plan）
    │   ├─ critical → PDD + 用户评审
    │   └─ 实现：调用 coding-framework 模式6 Plan Mode
    │
    ├─ Phase 3: Code Hat（编码）
    │   ├─ 按 plan 逐步实现
    │   ├─ 每步完成后运行 Backpressure 门控
    │   └─ 实现：调用 coding-framework 模式1/5
    │
    ├─ Phase 4: Review Hat（审查）
    │   ├─ 调用 code-review skill
    │   ├─ large → 标准审查（3代理）
    │   ├─ critical → 深度审查（5代理）
    │   └─ 发现问题 → 回到 Phase 3 修复
    │
    └─ Phase 5: Debug Hat（调试，按需）
        ├─ 审查发现 high/critical 问题时激活
        ├─ 分析根因 → 修复 → 重新审查
        └─ 最多 3 轮 debug → review 循环
```

### 阶段间上下文传递

每个阶段产出的文件作为下一阶段的输入：

| 阶段 | 输入 | 输出 |
|------|------|------|
| Research | 用户需求 | context 摘要（关键文件列表、架构约束） |
| Plan | context 摘要 | plan.md 或 .specs/ 目录 |
| Code | plan + context | 代码文件 |
| Review | 代码文件 | review.md（问题列表） |
| Debug | review.md | 修复后的代码 |

### 实现方式

**在 coding-framework 中**：阶段编排通过模式组合实现：
- 模式7（Explore）→ 模式6（Plan）→ 模式1/5（Code）→ code-review（Review）

**在 daily-agent 中**：Step 3 路由时，如果 task_type=coding 且 complexity=large/critical：
1. 告知用户："这是大型任务，将按 侦察→规划→编码→审查 四阶段执行"
2. 按阶段顺序调用 coding-framework 的对应模式
3. 每个阶段完成后输出进度：`[Phase 2/5] Plan ? → 进入编码阶段`

### 动态插入 Debug 阶段

```
Review 结果:
  ├─ 无 high/critical 问题 → 完成 ?
  └─ 有 high/critical 问题 → 插入 Debug 阶段
      ├─ 修复 → 重新 Review
      ├─ 仍有问题 → 再次 Debug（最多 3 轮）
      └─ 3 轮后仍有问题 → 报告用户，列出未解决问题
```

## 内置模式（轻量级，不需要加载外部skill）

### 模式A：压缩沟通（原caveman）

**触发条件**：
- 用户说"简单说"/"太长了"/"省点token"/"caveman"
- 用户连续表现出不耐烦

**行为规则**：
- 去掉：冠词(a/an/the)、填充词(just/really/basically)、客套话(sure/certainly)
- 用短句：`[东西] [动作] [原因]. [下一步].`
- 技术术语保持精确，代码块不变
- 用箭头表示因果：X -> Y

**示例**：
- 问："为什么React组件重新渲染？"
- 答："Inline obj prop -> new ref -> re-render. `useMemo`."

**退出条件**：用户说"stop caveman"/"正常说"/"normal mode"

### 模式B：全局理解（原zoom-out）

**触发条件**：
- 用户说"看看整体结构"/"这个模块是什么"/"给我个地图"
- 面对陌生代码库，需要高层次理解

**行为规则**：
- 先列出所有相关模块和调用关系
- 用项目的领域术语（参考domain glossary）
- 画架构图（ASCII或描述）
- 不深入细节，只给全景

### 模式C：方案审视（原grill-me）

**触发条件**：
- 用户提出方案/计划/设计思路
- 用户说"帮我审视一下"/"grill me"/"压力测试这个方案"

**行为规则**：
- 逐个追问方案的每个分支
- 每个问题给出推荐答案
- 一次只问一个问题
- 如果能从代码库找到答案，先查代码再问

### 模式D：多路径探索（Tree-of-Thought）

**触发条件**：
- 复杂规划/决策问题，存在多种可行路径
- 用户说"帮我分析几种方案"/"有哪些思路"/"ToT"
- 任务类型：架构设计、技术选型、方案对比、创意发散

**行为规则**：
1. **生成分支**：先提出 3 个不同思路/方案（不要雷同，要有差异化）
2. **逐分支评价**：对每个方案从可行性、成本、风险、效果四个维度打分
3. **淘汰+深入**：淘汰最弱的 1 个，对剩余 2 个深入展开（具体步骤、关键决策点）
4. **推荐**：给出最终推荐方案及理由
5. **输出格式**：

```
## 方案对比

| 维度 | 方案A | 方案B | 方案C |
|------|-------|-------|-------|
| 可行性 | ??? | ?? | ???? |
| 成本 | 中 | 低 | 高 |
| 风险 | 中 | 高 | 低 |
| 效果 | 好 | 一般 | 最好 |

## 淘汰：方案B（原因：...）

## 深入对比：A vs C
...

## 推荐：方案C（理由：...）
```

**与方案审视(grill-me)的区别**：
- grill-me：针对用户已有的方案追问漏洞
- ToT：用户还没有方案时，主动生成多路径并评估

## Step 4.5: 并行工具评估（v2.3 新增）

```

```

|------|----------|----------|

| cron_list | API | 8 |

write / edit / exec / browser — 有副作用或状态依赖

### 典型并行场景

## Step 4.8: Design Gate（v2.15 新增）

> 来源：Superpowers brainstorming 的 HARD-GATE 设计
> DS评审修正：补充执行机制 + 跳过条件需用户显式确认

### 铁律

```
NO IMPLEMENTATION WITHOUT DESIGN APPROVAL
```

在用户审批设计之前，不允许调用任何实现技能（coding-framework、frontend-design等）。

### 执行机制（DS修正版）

**技术实现**：
1. daily-agent 被调用时，在内存中设置 `design_gate_active = true`
2. 在调用任何实现技能前，**强制检查**：IF `design_gate_active` AND 无设计审批记录 THEN STOP → 进入设计阶段 → 不加载实现技能
3. 设计审批通过后，设置 `design_approved = true`，允许调用实现技能
4. 用户说"直接写代码"时，设置 `design_gate_bypassed = true`

### 门控流程

```
收到编码任务
    ↓
判断：是否有明确的设计文档/规格？
    ├─ YES → 继续执行
    └─ NO → 进入设计阶段
              ↓
         提出2-3个方案 + 权衡
              ↓
         用户选择方案
              ↓
         呈现设计（架构/组件/数据流）
              ↓
         用户审批设计
              ↓
         继续执行
```

### 何时跳过 Design Gate（DS修正版）

**可跳过条件（需满足全部）**：
1. 用户明确说"直接写代码" / "不用设计" / "just code it"
2. 任务 <= 50行代码（估算）且为单一功能

**不可跳过（即使满足条件1）**：
- 涉及数据库 schema 变更
- 涉及 API 接口变更
- 涉及外部系统集成
- 影响多个模块

**跳过时仍需告知**：
"正在跳过设计阶段（用户已确认），直接进入实现。"

## Step 5: 委派执行与状态监控（v2.4.0 重构）

**职责**：负责任务编排与监控，所有具体操作委托给子技能/代理。

### 5.1 构建委派指令

根据技能匹配结果，构建完整的委派指令：

```
委派指令包含：
- skill_name: 匹配的技能名称
- task_description: 任务描述（遵循 Agent Brief 持久性原则）
- input_context: 输入上下文（用户消息、相关文件路径等）
- expected_output: 期望输出格式
- timeout: 预估超时时间
```

### Agent Brief 持久性原则（v2.17 新增）

> 来源：Matt Pocock 的 triage skill — "持久性优于精确性——不引用文件路径/行号，只描述行为"
> 原因：spec 不会因为代码重构而失效，行为描述比路径引用更稳定。

**铁律**：生成的 task spec 和任务描述中，禁止引用具体文件路径和行号，只描述行为。

**规则**：
1. **禁止** 引用具体文件路径（如 `src/components/Button.tsx`）
2. **禁止** 引用具体行号（如 `第42行`）
3. **改为** 描述行为（如"用户登录按钮组件"、"处理支付的函数"）

**示例对比**：

| ? 错误（路径引用） | ? 正确（行为描述） |
|---|---|
| `修复 src/api/user.py 第127行的空指针异常` | `修复用户API中处理空用户ID时的空指针异常` |
| `在 components/Header.tsx 中添加导航菜单` | `在页面顶部导航区域添加菜单组件` |
| `修改 utils/auth.js 的 validateToken 函数` | `修改令牌验证函数，增加过期时间检查` |
| `第42行的循环性能问题` | `数据遍历循环中的性能瓶颈` |

**例外情况**：
- 当用户**明确要求**引用具体路径时（如"帮我看看这个文件"），对话中可以引用
- 但在生成的 task spec / 委派指令中，**始终**使用行为描述
- 子代理接收的任务描述应该是行为导向的，由子代理自行定位具体文件

**适用范围**：
- daily-agent 生成的所有委派指令
- coding-framework 生成的任务描述和计划
- PDD .specs/ 中的 requirements.md 和 implementation-plan.md
- 所有 spawn 子代理时传入的 task 描述

### 5.2 调用执行环境

根据复杂度评估结果，选择执行环境：

**短链任务（主会话执行）**：
- 按技能指引直接调用工具
- 先评估并行可能性（Step 4.5）
- 工具调用计数，接近 5 次时提醒

**长链任务（spawn 子代理）**：
- 调用 `sessions_spawn` 创建子代理
- 传入完整上下文：skill_name、task_description、input_context
- 设置合理超时：简单 300s，中等 600s，复杂 900s+

**spawn 调用格式**：
```
sessions_spawn(
    task="任务描述",
    label="daily-task-{timestamp}-{domain}",
    skill="{matched_skill}",
    timeoutSeconds=600
)
```

### 5.3 状态监控

**主会话执行**：
- 实时汇报进度（如果 >30 秒）
- 监控工具调用次数

**spawn 子代理执行**：
- 子代理后台执行

**触发条件**（必须同时满足）：
1. 任务类型为"编码"（涉及代码生成/修改）
2. 任务复杂度评估为 medium 或 large（≥3 文件修改 或 涉及安全敏感操作）

- 用户已显式要求审查（避免重复审查）

**执行方式**：
```
sessions_spawn(

         1. 安全漏洞（eval/exec/SQL拼接/硬编码凭证/路径遍历）
         2. 逻辑错误（边界条件/空值/类型不匹配/死代码）
         3. 正确性（是否实现了需求，不是'看起来对'但逻辑偏移）
         
         变更文件列表：{changed_files}
         
         输出格式（严格 JSON）：
         {\"issues\": [{\"severity\": \"high|medium|low\", \"file\": \"xxx\", \"line\": N, \"desc\": \"...\"}], \"verdict\": \"pass|fail\"}
         
         规则：
         - 只报告高置信度问题（≥80%确定）
         - 不报告风格建议
         - 无问题则返回 {\"issues\": [], \"verdict\": \"pass\"}",
  model: "sonnet",
  mode: "run",
  runTimeoutSeconds: 120
)
```

**结果处理**：
- `verdict: "pass"` → 静默通过，不通知用户
- `verdict: "fail"` → 将 issues 注入主会话，由主代理决定是否修复
- spawn 超时/失败 → 静默跳过（不阻塞主流程）

**Token 预算控制**：
- 只传入变更的文件路径和 diff（不传整个项目）
- 输出限制 500 tokens
- 超时 120 秒

### 规则3：搜索必须多引擎

- 中文搜索：web_search(bocha/baidu) → 验证
- 英文搜索：web_search(volc/ali) → 验证
- 交叉比对，标注可信度

### 规则4：不认识就先搜

- 遇到训练截止后的新名词 → 先搜索确认
- 禁止编造
- 知道系列≠知道新作品

### 规则5：浏览器智能关闭（v2.4.0 修改）

浏览器操作完成后，检查任务计划中后续是否仍有浏览器步骤：
- 若后续 2 步内无浏览器操作 → 立即关闭
- 若后续仍有浏览器操作 → 保留至当前阶段结束
- 收尾检查时，若浏览器还开着 → 强制关闭

**判断逻辑**：
```
if "browser" not in predicted_remaining_tools(next_2_steps):
    browser.stop()
```

### 规则6：任务失败要记录

- 失败/纠正 → 调用 self-improving 记录
- 写入 .learnings/ 对应文件

### 规则7：任务异常必须优雅降级（v2.4.0 新增）

- 任务异常 → 重试 3 次 → 降级策略 → 记录错误
- 不得无限重试或静默失败
- 详见 Step 5.5 异常处理与降级

### 规则8：技能匹配失败时路由至通用对话（v2.4.0 新增）

- 技能匹配失败 → 回退到通用对话能力
- 向用户确认："我需要哪个技能？"
- 禁止猜测执行高风险技能（如 exec、browser）
- 详见 Step 4 兜底策略

### 规则9：Converse 模式期间禁止写操作（v2.5.0 新增）

- CONVERSE 状态下，禁止调用 write / edit / exec(写) / message / browser(写)
- 仅允许 read / web_search / web_fetch（读操作支撑讨论）
- 用户说"执行"/"开始"/"做吧"/"动手"/"就这么做" → 退出 CONVERSE → 恢复正常执行
- 违反 = 失职

## 与子技能的关系

daily-agent是调度器，不直接执行具体工作。具体工作由对应技能执行：

| 保留的独立子技能 | 用途 | 何时加载 |
|-----------------|------|---------|
| `diagnose` | 6阶段排错方法论 | 排错/调试/bug |
| `tdd` | Red-Green-Refactor循环 | 测试驱动开发 |
| `prototype` | 原型构建规则 | 验证想法/做demo |
| `thesis-review` | 论文评审意见生成 | 论文评审 |

| 内联到daily-agent的模式 | 用途 | 触发方式 |
|------------------------|------|---------|
| 压缩沟通（caveman） | 省token回复 | 用户要求/不耐烦 |
| 全局理解（zoom-out） | 看架构/模块关系 | 用户问"整体结构" |
| 方案审视（grill-me） | 追问已有方案漏洞 | 用户提出方案 |
| 多路径探索（ToT） | 生成多方案并评估 | 复杂规划/无明确方案 |
| **讨论模式（converse）** | **分离讨论/执行意图** | **用户讨论想法/探索方案** |
