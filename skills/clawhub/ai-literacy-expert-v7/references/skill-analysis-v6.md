## 二、核心诊断：为什么 V5.5 还不是「工作流 skill」

V5.5 本质是「**高质量提示词 + 知识库**」——它告诉 AI *该怎么做*，但每一步仍需人/AI 手动串联，存在三类断点：

### 断点 1 · 流程靠「记忆清单」，无状态机
门控、备课 Phases、评估 Phases 都是散文式清单。AI 长任务中易跳步、漏步、重复问同题。**缺一个可恢复、可 checkpoint 的执行骨架。**

### 断点 2 · 验证靠「人工实测」，不可复现
§11 控件测试是质量生命线，但依赖人工逐控件点。规模一大就漏测、且不可复跑、不可 CI。

### 断点 3 · 能力之间「串联断裂」，无闭环
推荐→课件→评估→补学→再推荐 这条最有价值的链路，目前是四个独立对话，没有自动编排把「评估发现的薄弱点」回流成「下一份课件/补学路径」。

### 断点 4 · 交付止于「生成文件」，无自动分发
WorkBuddy 适配写明了 IMA/腾讯文档/设备侧用法，但执行时仍需人工记得去调用。应从「能力末尾」自动接上「原生落库 + 提醒 + 分享」。

### 断点 5 · 时间维度缺失
所有能力都是「请求-响应」。缺少「**时间触发型**」自动驾驶：4 周上手推进、每日速递、考前提醒、周报——这些靠人想起才会做。

## 三、设计目标（V6.0 工作流引擎版）

把技能从「提示词库」升级为「**可编排、自驱动、可验证、可恢复、跨时间**」的工作流引擎：

| 目标 | 含义 | 落地手段 |
|------|------|----------|
| **自动化** | 触发即编排，少问多办 | 意图分类器 + 8 阶段管线 + 自动验证闭环 |
| **智能化** | 会判断、会决策、会回流 | 自适应路由、评估→补学回路、推荐→可执行计划 |
| **闭环化** | 教-练-评-补全链路 | 评估薄弱点自动触发补学课件/路径（LEARN 阶段） |
| **可验证** | 控件全测可复跑 | `playwright-control-test-harness.js` 自动实测 |
| **可恢复** | 长任务可断点续跑 | `workflow-state-template.json` 状态持久化 |
| **跨时间** | 时间触发型运营 | `automation-ops.md`：4 周自动驾驶/速递/提醒/周报 |

## 四、8 阶段通用工作流管线（所有能力的统一骨架）

```
INTENT(意图识别) → PLAN(计划拆解) → BUILD(生成) → VERIFY(自动验证闭环)
   → ASSEMBLE(组装打包) → DELIVER(原生分发) → REPORT(报告留痕) → LEARN(回流优化)
```

| 阶段 | 输入 | 自动决策 | 完成判据 | 失败处理 |
|------|------|----------|----------|----------|
| INTENT | 用户自然语言 | 分类器命中：能力 + 模块 + 受众 + WB目标 | 结构化意图对象 | 模糊→主动澄清（仅问 1 次） |
| PLAN | 意图对象 | 选 runbook + 拆 stage + 建状态文件 | 计划可读、有 checkpoint | 缺参数→智能默认（不阻塞） |
| BUILD | 计划 | 调对应 reference 生成产物 | 产物生成、语法 OK | 生成失败→重试 1 次 |
| VERIFY | 产物 | **自动跑 Playwright 控件实测** | 第12维门控全过 | 缺陷→自动修(≤3次)→复测 |
| ASSEMBLE | 验证后产物 | 拼 README/版本/SHA256/离线清单/zip | 包完整、≤体积上限 | 缺项→补生成 |
| DELIVER | 包 | 依 WB目标自动落库/分享/提醒 | 落库确认/分享成功 | 未授权→引导授权后重试 |
| REPORT | 全流程 | 生成工作流状态报告 + 门控结果块 | 报告附交付物 | — |
| LEARN | 报告+反馈 | 评估薄弱点→补学建议/下一课件 | 回流记录写入状态 | — |

> **关键升级点**：VERIFY 阶段由「人工」变为「`playwright-control-test-harness.js` 自动实测 + 自动修复闭环」；DELIVER 阶段由「给文件」变为「WorkBuddy 原生动作自动接上」；LEARN 阶段实现「评估→补学」闭环。

## 六、结论

V5.5 已是「内容/质量双优」的技能；V6.0 的增量价值集中在**编排与闭环**：用一套 8 阶段管线把六个能力串成可恢复、可验证、跨时间的工作流，并把最贵的「控件实测」与「原生分发」自动化。详见 `workflow-orchestrator.md`。
