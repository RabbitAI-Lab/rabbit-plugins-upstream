# 逆向工程助手

## 定位

当用户需要对**已发布但没有源码的软件**（安装包、二进制、应用目录、流量记录等）做逆向分析、还原实现或复现功能时使用本技能。底层分析能力由「逆向工程助手」连接器提供；本技能负责指导 AI 走完：确认授权与目标 → 选择正确的调查入口 → 按证据工作流推进 → 输出可复核的结论。

**依赖声明**：本技能仅依赖「逆向工程助手」连接器提供的分析能力（REA 工具），不依赖其他技能；连接器不可用时可用 CLI 兜底（见「前置检查」）。对正常源码仓库的日常分析不需要本技能，使用常规代码阅读工具即可。

## 核心能力

1. **需求与授权路由（REA0）**：确认目标身份、来源与授权，对照目标路由表判定类型，规划分析入口与取证顺序。
2. **侦察与总览（REA1）**：复用已有会话与证据，打开目标并核验身份，summary-first 取得可推进的锚点。
3. **追踪与取证（REA2）**：按类型执行静态分析，沿字符串 → 引用 → 调用链 → 伪代码逐步追踪，登记证据台账与未决项；运行时观察按需且先获确认。
4. **重建与验证（REA3，按需）**：在用户项目中复现目标功能，以固定样例对拍并声明等价性范围。
5. **输出与交付（REA4）**：按「事实 / 推断 / 未知」三分撰写结论，导出证据、回访问题清单。
6. **环境与恢复（REA5）**：环境适配核验、连接与故障处置（诊断 → 修复 → 继续原任务）、更新与卸载。

## 三层结构

```
reverse-engineering-assistant/
├── SKILL.md                                          # 本文件：定位 + 路由 + 执行接口
└── references/                                       # 三层资料，与索引同级平铺
    ├── reverse-engineering-assistant-catalog.md      # 第一层：任务清单 + 依赖拓扑
    ├── reverse-engineering-assistant-requirements.md # 第二层：任务要求清单
    ├── reverse-engineering-assistant-exemplars.md    # 第三层：范本索引 + 标准格式
    └── REA0~REA5-*范本.md                            # 各域范本（6 份，按域分文件）
```

**目录约束**：Skill 包仅支持两级目录（根目录/二级目录/文件）；references/、scripts/、templates/ 内不得再建子目录，各域范本与索引文件在 references/ 下同级存放。本技能当前无 scripts/ 与 templates/（按需再建，不凑数）。

**目录用途**：`references/` 参考文档，按需加载到上下文；`scripts/` 可执行代码，直接执行不加载；`templates/` 输出模板与资源，输出时使用不加载。

**命名约定**：域与任务 ID 统一用 `REA0`~`REA5` / `REA{n}-{nn}`（`REA` = Reverse Engineering Assistant），范本文件前缀同名。此约定用于与「Step 1 领域校准」的 R1~R5 参数区分——后者是信息密度/创造性/交互性/规范性/迭代性五个校准维度，与域编号无关。

## 使用规则

### 执行流程

1. **首次加载**：读取 `references/reverse-engineering-assistant-catalog.md`，获取域分类、依赖拓扑与元操作映射提示。
2. **按需深入**：读取 `references/reverse-engineering-assistant-requirements.md` 获取目标任务的必选/可选组件与约束；需要模仿产出时读取 `references/reverse-engineering-assistant-exemplars.md` 及对应域范本。
3. **独立执行**：本技能不依赖其他技能，全部方法论与约束已内嵌；连接器不可用时按「前置检查」走 CLI 兜底。

### 内容权限

4. **修改权限**：本技能 references/ 内容按领域负载物规范维护；平台规范或 REA 版本变更时，先更新 references 对应文件，再按「事实纪律」与校验流程复检。
5. **用户补充**：用户可将脱敏后的真实任务范本（与索引同级）放入 references/ 供样本法参考。

### 降级模式

| 模式 | 权限 |
|------|------|
| 标准模式 | 读写用户指定目录、执行分析与 CLI 命令、生成报告与实现代码、导出证据 |
| 只读模式 | 仅分析与读取（含只读命令），输出结论与建议；不写入任何文件、不导出证据包 |
| 禁写模式 | 无法落盘时，将结论与证据引用以代码块形式输出，由用户自行保存 |

### 提示词导出

可将本技能合并为单一提示词文件，用于不支持 skill 目录格式的工具。合并顺序：SKILL.md → reverse-engineering-assistant-catalog.md → reverse-engineering-assistant-requirements.md → reverse-engineering-assistant-exemplars.md → references/ 下各域范本文件（REA0→REA5）。命令示例：

```bash
cat SKILL.md references/reverse-engineering-assistant-catalog.md references/reverse-engineering-assistant-requirements.md references/reverse-engineering-assistant-exemplars.md references/REA[0-5]-*范本.md > reverse-engineering-assistant-prompt.md
```

## 前置检查（每次任务开始时）

1. **确认目标与授权**：目标必须是用户拥有或已获得明确授权分析的软件。用户未说明来源时，先询问并在任务中提示合规边界；不帮助绕过任何授权保护机制。
2. **确认分析能力可用**：
   - 会话中已提供 REA 分析工具（如 `binary_session`、`analyze_javascript_application` 等）→ 直接使用，不必先跑诊断。
   - 没有 REA 工具时 → 使用 CLI 兜底：`npx -y rea-agents@6.5.0 <命令>`（需 Node.js ≥ 22.19）。目录与归档清单、静态 JS/.NET 分析不需要任何反汇编引擎；环境与恢复细节见 requirements 的 REA5 域。
   - 两条通道同源（`rea --mcp` 即以 MCP stdio 服务启动），CLI 子命令为工具名的 kebab-case 形式，目标类型覆盖一致；差异仅在会话/快照、未决项登记、调用路径构建三类，见 requirements 的 REA2-01。
3. **拆解问题**：把用户诉求整理成可回答的问题清单（要搞清哪个功能、什么行为、输入输出与边界），后续每一步都围绕它取证。

## 主工作流

按 catalog 的主链路推进（REA0→REA1→REA2→REA4，REA3 按需、REA5 支持）：

1. **目标路由**（REA0）：确认授权与目标 → 对照「目标路由表」判定类型 → 规划调查方案；从最轻的证据开始，不要一上来就全量反编译。
2. **侦察总览**（REA1）：检查并复用已有证据 → 打开目标并核验身份 → 先请求概要（summary）取得锚点；大目标必须 summary-first。
3. **追踪取证**（REA2）：按类型执行静态分析 → 沿字符串 → 交叉引用 → 调用关系 → 伪代码/汇编逐步追踪（每次只追一个未回答问题）→ 把证据与未决项登记进台账；运行时观察按需且必须先获确认。
4. **重建与验证**（REA3，按需）：用户要复现功能时，用常规开发流程实现，并以固定样例对拍、声明验证范围。
5. **输出交付**（REA4）：按「事实 / 推断 / 未知」三分撰写结论 → 导出证据、关闭会话 → 回访问题清单并归档台账。

## 高风险操作确认规则

- 运行、交互目标程序（运行时观察/场景捕获）前，先向用户说明将执行什么、以什么权限运行，并取得确认。
- 解包、提取、导出文件前，确认输出目录；不覆盖用户未同意的文件。
- 发现目标可能与用户无授权关系时，立即停止并说明。

## 合规边界（红线）

- 仅限分析用户拥有或获得授权的软件；结果用于学习研究、互操作、安全分析、软件保存和用户自己的项目。
- 不修改、不破解、不绕过目标软件的保护机制；不输出真实凭证。

## 与执行框架的接口

本技能通过以下五步接入通用任务执行框架（三轴正交），任何分析请求都从 Step 0 进入：

- **Step 0 三轴判定**：复杂度（单目标单问题=中等；多目标或多问题=复杂）；内容类型（证据 + 报告类产出）；创新需求（默认无需创新；复现实现允许常规工程创造）。
- **Step 1 领域校准**：按本领域 R1-R5 参数校准执行（见下表）。
- **Step 2 三轴分解**：执行轴按 catalog 依赖拓扑分解为 REA0→REA1→REA2→REA4 主链（REA3 按需、REA5 支持）；内容轴对台账、报告、结论等文案类组件启用清单法与范本法；创新轴默认关闭。
- **Step 3 管线编排与执行**：每完成一个任务立即对照 requirements 做分步校准；证据按 REA2-03 登记，未决问题闭环后再扩展下一个问题。
- **Step 4 整合交付**：结论三分（事实/推断/未知）→ 证据导出 → 问题清单回访与台账归档。

**Step 1 领域校准的领域特定推导**：

| 参数 | 本领域取值 | 执行影响 |
|------|-----------|---------|
| R1 信息密度 | 极高（证据、偏移、伪代码密集） | S/G 权重最高：结论前必须先读 limitations/coverage，禁止跳读证据 |
| R2 创造性 | 低（分析结论零创造；复现实现可创造） | C 权重低：不得脑补缺失细节，推断必须标注 |
| R3 交互性 | 中高（授权确认、高风险确认、问题澄清） | I 权重高：授权与高风险动作必须经用户确认 |
| R4 规范性 | 高（证据规则、合规红线、平台约束） | G 权重高：合规红线零容忍；无证据不下结论 |
| R5 迭代性 | 高（追踪→取证→回读→再追踪循环） | 迭代精炼为默认：每个未决问题闭环后再扩展 |

**自治度**：分析执行=全自动；高风险操作=需用户确认；复现实现=半自动（关键设计向用户确认）；上架与提交类动作=人工。

## 通用任务执行能力

**三轴正交**：执行轴（How，必选）+ 内容轴（What，按需）+ 创新轴（Why Different，按需）。

**执行轴**：6 大元操作 S 感知 / C 认知 / A 行动 / O 组织 / I 交互 / G 守护，按管线编排；编排模式：顺序→、并行‖、条件?、循环↻、扇出⇉、扇入⇇。本领域默认管线：P4 条件分支（目标类型判定后进入对应分析路径）嵌套 P2 迭代精炼（追踪→取证循环，直至未决问题闭环）。

**内容轴**：清单法（台账、报告、核验清单按组件清单逐项填充）+ 样本法（模仿 references/ 范本的结构与风格，不复制范本内容）。

**创新轴**：默认关闭；仅在用户对复现实现提出差异化要求时启用，启用后仍须通过对拍验证。

**五种协同模式（按需激活）**：顺序协同（判定→分解→执行→交付）/ 并行协同（互不依赖的追踪问题并行取证）/ 条件协同（按目标类型动态启用或关闭能力分支）/ 迭代协同（证据不足→调整追踪方向→复检）/ 递归协同（每个任务内部可再分解为子步骤链）。

**核心公式**：产出 = 元操作（S/C/A/O/I/G 管线）× 本负载物（references 任务要求 + 范本 + 证据规则）。

## 事实纪律

1. 仅使用确知的证据与可验证的信息，不得编造数据、偏移或引用。
2. 分析结论必须能指回证据（evidence_id / 偏移 / 代码片段）；推断必须标注依据。
3. 「未观察到」不等于「不存在」；覆盖不完整必须如实声明。
4. 静态分析结果不得表述为运行时行为。
5. 目标判定、入口选择等推导须向用户展示依据。
6. 任务分解须遵循 catalog 的自然依赖关系，不得人为添加冗余步骤。
7. 范本法模仿产出时不复制范本内容，仅借鉴结构与风格。
8. 各任务的输出格式须匹配下游任务的输入（台账 → 结论 → 回访的接口保持一致）。
