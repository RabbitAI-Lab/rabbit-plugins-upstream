## 任务要求清单

每种任务类型的"零件清单"——必选/可选组件、组装顺序、领域约束。按清单逐项产出。任务编号与 catalog 对齐（REA0-01~REA5-03，共 18 个任务、6 个域）。

---

### 多域总览

**类型定位**：本负载物属于「分析执行类」技能——把"授权范围内的软件逆向分析"从需求推进到可复核结论。域划分依据调查的自然生命周期：路由（REA0）→ 侦察（REA1）→ 取证（REA2）→ 重建（REA3，按需）→ 交付（REA4）；环境与恢复（REA5）为贯穿全程的支持域。

**跨域红线**（所有域任务均须遵守）：
1. 授权未确认不得进入 REA1 及之后任何任务；结论不得脱离证据存在。
2. 静态分析结果不得表述为运行时行为；"未观察到"不等于"不存在"。
3. 运行时观察、解包提取等有副作用的操作必须先获用户确认。
4. 任何阶段不得硬编码或输出真实凭证；不修改、不破解、不绕过目标软件的保护机制。

---

### REA0 任务路由域

#### 域级说明

入口域。全部分析任务走"授权确认 → 类型判定 → 方案规划"三步；判定对照 REA2-01 的「目标路由表」。授权是本域的第一门禁：目标来源与授权不明确时，先追问，不得带疑进入后续域。

#### REA0-01 需求与授权确认

- **必选组件**: 目标身份（哪个软件/版本/文件）、来源与授权说明、问题清单（具体到"哪个功能/什么行为"）
- **可选组件**: 材料清单（文件/目录/流量记录）、范围与时间预期
- **组装顺序**: 目标与来源确认→授权边界声明→问题拆解→缺失项追问
- **约束**: 授权不明确必须追问；发现目标可能与用户无授权关系立即停止；问题清单不得停留在"帮我看看这个软件"级别的模糊表述
- **格式**: 确认信息摘要（Markdown，含一行授权声明）

#### REA0-02 目标类型判定

- **必选组件**: 目标类型（对照「目标路由表」）、判定依据、所需能力与前置（引擎/环境）
- **可选组件**: 候选类型差异说明（类型存疑时）
- **组装顺序**: 目标特征分析→路由表匹配→能力前置核对→向用户展示判定依据
- **约束**: 判定依据必须展示给用户；类型存疑时列出差异请用户确认；优先选择不需要分析引擎的路径
- **格式**: 判定报告（Markdown）

#### REA0-03 调查方案规划

- **必选组件**: 分析入口（工具/命令）、"问题→证据类型"映射表、推进顺序
- **可选组件**: 风险项（首次下载耗时、引擎缺失、高风险操作点）
- **组装顺序**: 入口选择→问题-证据映射→顺序编排→用户确认
- **约束**: 从最轻的证据开始，不默认全量反编译；每个问题必须明确用什么证据回答；涉及运行时的必须标注高风险确认点
- **格式**: 调查方案（Markdown）

### REA1 侦察与总览域

#### 域级说明

侦察域。目标是"用最小成本取得可推进的总览"，为取证域提供锚点。禁止跳步直接全量分析；大目标必须 summary-first。

#### REA1-01 已有状态检查

- **必选组件**: 会话/快照/书签/已有证据的检索结果、可复用清单
- **可选组件**: 先前结论与未决项回顾
- **组装顺序**: 检索→目标身份比对→复用判定
- **约束**: 目标身份不一致不得复用；复用必须说明依据；不重复打开已打开的对象
- **格式**: 状态摘要（Markdown）

#### REA1-02 目标打开与身份核验

- **必选组件**: 打开结果（分析会话或快照）、身份核验记录（摘要哈希/清单/版本信息）
- **可选组件**: 快照保存（供跨会话复用）
- **组装顺序**: 打开→身份核验→（可选）保存快照
- **约束**: 路径必须是用户指定的目标，不得分析无关文件；同时只维护一个活动目标
- **格式**: 核验记录（Markdown）

#### REA1-03 概要总览

- **必选组件**: 概要结果（summary/清单/入口点）、后续问题的锚点候选（模块、node_id、函数、通道）
- **可选组件**: 覆盖与限制（limitations）阅读记录
- **组装顺序**: 概要请求→限制阅读→锚点选择
- **约束**: 大目标未取概要不得直接全量深入；限制与覆盖字段必须阅读后再决定深入方向
- **格式**: 总览摘要（Markdown）

### REA2 追踪与取证域

#### 域级说明

核心取证域：承载「目标路由表」（能力映射）、追踪方法与证据规范。REA2-04 是本域唯一的高风险任务，仅在静态证据不足且用户确认后进入。域内存在追踪-取证循环（↻）：追踪产生新证据→证据引出新问题→继续追踪，直到问题闭环。

#### REA2-01 静态分析执行

- **必选组件**: 目标路由表（下表）、执行命令或工具调用、输出证据文件（大输出重定向保存）
- **可选组件**: 聚焦选择（source_paths、指定表、类型筛选）
- **组装顺序**: 按类型取入口→执行→保存输出→初步读解
- **约束**: 不重复执行相同分析；优先"不完整解压的清单"；输出过大时先概要后分页；不需要引擎的路径不得强上引擎
- **格式**: 证据文件（JSON）+ 执行记录

**目标路由表**（按目标类型选第一个入口）：

| 目标类型 | 首个 MCP 工具 | CLI 对应命令 | 备注 |
|---|---|---|---|
| ASAR / 已解包 JS、Electron 应用目录 | `analyze_javascript_application` | `analyze-javascript-application <目录>` | 静态分析，不需要反汇编引擎 |
| 归档包（ZIP/APK/IPA/MSIX/AppX/DMG）成员清单 | `open_binary`（配合 `inspect_artifact`） | `inspect-artifact <文件>` | 可不完整解压直接生成清单 |
| 安卓 APK 代码（类/方法/引用） | `inspect_android_package`，后续用聚焦安卓工具 | `inspect-android-package` / `inspect-android-class` / `inspect-android-method` / `trace-android-references` / `decode-android-resources` | 需要自备 JADX 与 JDK；资源解码用 apktool |
| .NET 托管程序集（PE/CLI） | `inspect_managed_artifact`；成员用 `inspect_managed_members` | `inspect-managed-artifact` / `inspect-managed-members` | 只读元数据，不加载不执行 |
| 原生二进制（ELF/PE/Mach-O/macOS .app） | `open_binary` → `binary_overview` / `analyze_function` / 伪代码 | `analyze` / `search` / `function` / `decompile` / `xrefs` / `trace`（配合 `--provider`） | 深度分析需要 Ghidra 或 IDA（Windows 不支持 Hopper） |
| Go 二进制元数据 | `inspect_go_binary` | `inspect-go-binary` | 不需要引擎 |
| Rust（cargo-auditable）依赖元数据 | `inspect_rust_binary` | `inspect-rust-binary` | 不需要引擎 |
| SQLite 数据库快照 | `inspect_sqlite_database` | `inspect-sqlite-database` | 先读 Schema 再按需取行 |
| 用户已控制的浏览器页面 | `list_browser_targets` | `list-browser-targets`；页面捕获用 `capture-web-screenshot` / `capture-browser-scenario` | 被动观察，不主动改动页面 |
| 已打开的 Electron 运行时 | `list_electron_targets`；fuse 检查用 `inspect_electron_fuses` | `list-electron-targets` / `inspect-electron-fuses`；V8 目标用 `list-javascript-runtime-targets` | 检查 fuse 可判断 `--inspect` 是否可用 |
| 网页流量记录（HAR/SAZ/mitmproxy/qlog） | `inspect_web_network_capture` | `inspect-web-network-capture` | 离线读取，不回放请求 |
| 报文捕获（pcap） | `inspect_packet_fields` → `inspect_packet_capture`；摘要用 `inspect_pcap_capture` | `inspect-packet-fields` / `inspect-packet-capture` / `inspect-pcap-capture`；工具自检用 `inspect-pcap-client` | 需要 TShark；只读录制文件 |
| 固件镜像 | `inspect_firmware_regions`；提取用 `extract_firmware` | `inspect-firmware-regions` / `extract-firmware` | 提取需指定全新的输出目录 |
| WebAssembly 构件 | `inspect_wasm_artifact` | `inspect-wasm-artifact`；接口对比用 `compare-wasm-interfaces` | 需要自备 WABT |
| EVM 字节码 | `inspect_evm_interface` | `inspect-evm-interface` | 仅本地字节码，不查询链上 |
| 版本差异对比 | `compare_application_versions` / `compare_artifacts` / `compare_functions` / `find_changed_behavior` | `compare <左> <右>` | 两侧覆盖完整才可下"新增/移除"结论 |

**命令与工具名对应**：CLI 子命令即 MCP 工具名的 kebab-case 形式（`inspect_wasm_artifact` ↔ `inspect-wasm-artifact`），两条通道同源——`rea --mcp` 即以 MCP stdio 服务启动，连接器为同一引擎的外壳。上表「CLI 对应命令」按 `rea-agents@6.5.0` 实测校准（该版本共 155 个子命令），已无「仅 MCP 可用」的目标类型。

**CLI 通道缺少的三类能力**（6.5.0 实测无对应子命令，走 CLI 时须自建替代）：

- **会话与快照**：`binary_session` / `open_binary` / `close_binary` 无 CLI 对应。CLI 为一次性命令，同一目标不能跨命令保持打开状态，须把 Evidence JSON 落盘、由下条命令读入接力；大目标反复分析的开销高于连接器。
- **未决项登记**：`record_unknown` / `update_unknown` 无 CLI 对应，台账须自行以文件维护（格式沿用 REA2-03）。
- **调用路径构建**：`build_call_path` 无同名子命令，用 `trace` / `trace-application-feature` 近似替代，并向用户声明覆盖范围。

**工具与命令索引**（REA2 全域通用）：

- 会话与证据工具：`binary_session`（会话状态与工具可用性）、`open_binary` / `close_binary`（打开/关闭，支持快照）、`get_evidence_bundle` / `inspect_analysis_view`（读取已保留证据：概要/分页/单模块）、`export_evidence_bundle`（导出完整证据）、`record_unknown` / `update_unknown`（未决项登记与更新）、`trace_application_feature`（从节点/字符串/通道出发追踪）、`build_call_path` / `correlate_static_and_runtime` / `verify_reconstruction`（路径、关联、验证）。
- CLI 约定：固定 `npx -y rea-agents@6.5.0 <子命令> --format json`；大输出重定向到文件再读取；退出码 `0` 成功（可含部分证据与未决项）、`1` 无法完成；管道场景建议 `set -o pipefail`。上下文控制用 `--token-count` / `--token-limit` / `--token-offset` / `--filter-output <键路径>`，参数不确定时先 `--schema`。
- CLI 无会话，跨命令的「同一证据」须以 `evidence-export` / `evidence-import` 落盘传递，并用 `inspect-analysis-view` 复读既有证据，不得重复分析。
- 分页与复用：先 `detail: "summary"`（MCP 专有；CLI 无对应参数，改由 `inspect-analysis-view` 截取概要），再用 `inspect_analysis_view` 分页（按 `coverage.next_offset` 推进）；带 `parent_evidence_id` 时引用同一份证据，不重新分析（CLI 无此参数，以证据文件路径充当引用）；被截断的预览不得当作完整结果解析；同一路径可能有多个图角色，选择用 `node_id`。

#### REA2-02 线索追踪

- **必选组件**: 追踪种子（字符串/引用/通道/函数）、追踪结果与证据引用、与问题的对应说明
- **可选组件**: 调用路径构建、静态-运行时关联
- **组装顺序**: 选种子→单向追踪→聚焦（每次一个未决问题）→伪代码/汇编取读
- **约束**: 双向追踪必须说明理由并防止图扩散；伪代码不完整时结合汇编与调用关系复核，不得脑补缺失细节；追踪结论标注为观察或推断
- **格式**: 追踪记录（证据引用列表）

#### REA2-03 证据登记与未决项管理

- **必选组件**: 证据台账（结论 ↔ 证据 ID ↔ 置信度 ↔ 证据类型）、未决项登记（含义与所需证据）
- **可选组件**: 覆盖与限制汇总
- **组装顺序**: 登记→更新→复核
- **约束**: 结论必须可指回证据（evidence_id/偏移/片段）；"未观察到"≠"不存在"；未决项写清"还需要什么证据才能定论"；只有合格观察证据才能将未决项标记为已解决
- **格式**: 证据台账（Markdown 表）

#### REA2-04 运行时观察（按需）

- **必选组件**: 用户确认记录、观察会话与结果、副作用说明（读写/网络）
- **可选组件**: 场景定义（声明动作）
- **组装顺序**: 高风险说明→取得确认→执行→结果登记
- **约束**: 执行前必须向用户复述"将执行什么、以什么权限运行"并获确认；运行时捕获不是沙箱；静态证据能回答的不得上运行时；被动观察不主动改动目标
- **格式**: 观察记录（Markdown）

### REA3 重建与验证域（按需）

#### 域级说明

仅当用户要求"复现/重建"时进入。重建用常规开发流程实现，验证只声明已验证范围内的等价；本域产出承接 REA2-03 的证据台账。

#### REA3-01 功能重建

- **必选组件**: 目标功能的行为规格（整理自 REA2 证据）、实现代码、与原始行为的对照点
- **可选组件**: 技术选型说明、依赖清单
- **组装顺序**: 规格整理→实现→初步对照
- **约束**: 设计与观察分开陈述（哪些是目标行为、哪些是自己的设计选择）；不得整段复制目标软件的代码内容；实现放在用户指定的项目/目录
- **格式**: 实现代码 + 说明文档

#### REA3-02 对拍验证与等价性声明

- **必选组件**: 测试用例集（固定输入输出/测试向量）、一致率统计、等价性声明范围
- **可选组件**: 边界与异常用例
- **组装顺序**: 用例设计→执行→一致率统计→范围声明
- **约束**: 只声明已验证范围内的等价；对拍失败先核对输入样本而不是改算法；算法类尽量扩大用例数并写明用例数与一致率
- **格式**: 验证报告（Markdown）

### REA4 输出与交付域

#### 域级说明

交付域。三段式结论是本域的硬格式：事实（可指回证据）/ 推断（明确标注）/ 未知（如实列出）。未执行 REA3 时，REA4-01 直接承接 REA2-03 的产出。

#### REA4-01 结论撰写

- **必选组件**: 结论正文（三分结构）、证据引用、限制与覆盖说明
- **可选组件**: 复现建议（用户要重建时）
- **组装顺序**: 结论草稿→证据核对→限制补充→（按需）复现建议
- **约束**: 每条事实可指回证据；不得把静态结果写成运行时行为；未决项如实列出，不把"部分回答"写成"已答"
- **格式**: 结论文档（模板见范本）

#### REA4-02 证据导出与会话收尾

- **必选组件**: 留存判定、证据导出（如需）、会话关闭记录
- **可选组件**: 快照保存
- **组装顺序**: 判定留存→导出→关闭
- **约束**: 关闭会话前导出需保留的证据（关闭后保留引用失效）；导出路径需用户确认，不覆盖未同意的文件
- **格式**: 收尾记录（Markdown）

#### REA4-03 问题清单回访与台账归档

- **必选组件**: 问题清单逐条状态（已答/部分回答/未解决）、台账归档位置
- **可选组件**: 后续建议清单
- **组装顺序**: 回访→归档→交付
- **约束**: 逐条状态必须与证据一致；未解决问题必须给出下一步需要什么（证据/权限/环境）
- **格式**: 回访记录（Markdown）

### REA5 环境与恢复域（支持域）

#### 域级说明

支持域，任何阶段可用。故障处置顺序恒为"诊断 → 修复 → 继续原任务"，禁止反复重装、反复重跑失败命令。

#### REA5-01 环境适配核验

- **必选组件**: 运行时核验（Node ≥ 22.19 / 24.11 / 26+）、分析引擎状态（Ghidra/IDA/Hopper 按需）、无需引擎能力清单确认
- **可选组件**: 托管运行时说明（连接器已声明 Node 运行时与 npm 镜像）
- **组装顺序**: 核验清单→逐项确认→结论
- **约束**: 不需要引擎的能力不得要求安装引擎；本机 CLI 场景才检查本机 Node（连接器托管模式下无需本机安装）
- **格式**: 核验清单（Markdown）

**无需引擎即可用的能力**：JS/Electron 静态分析、.NET 静态检查、归档清单、Go/Rust 元数据、SQLite、网站观察、流量记录读取、WASM、EVM、固件区域识别。
**特定能力的额外依赖**：安卓反编译需 JADX+JDK；pcap 需 TShark；WASM 需 WABT；固件提取需 Binwalk/Unblob（以工具返回的提示为准）。

#### REA5-02 连接与故障处置

- **必选组件**: 症状定位结论、处置动作、验证结果（是否恢复）
- **可选组件**: 恢复记录与耗时
- **组装顺序**: 对照故障表→定位→处置→验证→回到原任务断点
- **约束**: 先诊断再修复；修复后继续原任务，不从头重做；不要用重装解决所有问题
- **格式**: 处置记录（Markdown）

**故障对照表**：

| 症状 | 含义 | 处置 |
|---|---|---|
| 会话里看不到 REA 工具 | MCP 未连接或未授权 | 在 WorkBuddy 连接器设置中重新连接；必要时重启后重试 |
| 首次调用超时或特别慢 | 正在下载分析引擎包（体积较大） | 等待 1～2 分钟后重试一次；之后启动为秒级 |
| 工具报告引擎不可用 | 该能力需要 Ghidra / IDA 等 | 按返回的 remediation 配置引擎，或先用无需引擎的能力回答部分问题 |
| 调用被客户端拦截 | 本地权限或审批策略 | 按 WorkBuddy 提示处理审批，不得改配置绕过 |
| CLI 报 Node 版本不符 | 本机 CLI 环境过旧 | 升级 Node ≥ 22.19（托管模式下无需本机安装） |
| 下载很慢 | 到 npm 源较慢 | 连接器已启用 npm 镜像；CLI 场景可加 `--registry https://registry.npmmirror.com` |
