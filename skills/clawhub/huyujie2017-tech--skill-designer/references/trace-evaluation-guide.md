# 五维质量门 — BR-5 蓝图就绪度（设计期）+ TRACE 自查（发布期）

> **同一套五维骨架，两套问法。** 字母键 T / R / A / C / E 是**桥接键**，两套口径共用，便于与 SkillHub 官方体系互相对话、互相换算。

---

## 〇、定位声明：两套口径，别用错

| | **设计期口径 BR-5** | **发布期口径 TRACE** |
|---|---|---|
| 学名 | Blueprint Readiness-5（蓝图就绪度五维） | SkillHub TRACE 五维评测 |
| 评价对象 | **设计蓝图**（还没开工的施工图纸） | **已落地的 skill 成品** |
| 核心问句 | 这一条**约定了吗**？ | 这一条**做到了吗**？ |
| 用在哪 | **B09 质量门（本 skill 主用）** | 准备发布 / 收到平台返评 |
| 分数含义 | 设计完备程度 | 运行实测表现 |
| 证据来源 | 蓝图对应积木格里的文字 | 实际跑一遍的结果 |
| 配套脚本 | `trace_patch.py --mode design`（补哪格） | `trace_patch.py`（默认，改哪个文件） |

> **一句话**：本 skill 是设计指南，**默认走设计期口径**。只有当用户已经把 skill 做出来、准备发布或拿到平台返评时，才切到发布期口径。

## 一、BR-5 五维速查卡（设计期）

| 键 | 中文名 | 评的是什么 | 对应积木格 | 证据去找 |
|----|--------|-----------|-----------|----------|
| **T** | 边界可信 | 权限、敏感数据、输出边界**是否做出约定** | B01 / B05 / B06 | `01-条件` 准入四问 + 边界；`05-分析` 风险；`06-决策` 输出约定四要素 |
| **R** | 失败可控 | 异常与失败路径**是否做出约定** | B05 / B06 | `05-分析` 边界字段；`06-决策` 降级路径 |
| **A** | 触发可辨 | 触发条件与生态位**是否做出约定** | B02 / B06 | `02-事实` 生态正交性；`06-决策` description 五件事 |
| **C** | 结构可解 | 目录与文档结构**是否做出约定** | B07 | `07-计划` archetype + 五段骨架 |
| **E** | 验证可证 | 交付物与验证方式**是否做出约定** | B05 / B08 | `05-分析` 输出契约；`08-行动` 验证计划 |

**与双维评分的关系**：BR-5 均分换算成外部价值分（`EVS = BR-5 均分 × 20`），蓝图完备度作为内部质量分（`IQS`），综合评分 = `IQS × EVS / 100`。详见 [blueprint-methodology.md](blueprint-methodology.md) §5.2。

> **⚡ B09 只需人工评 BR-5 五维，其余全部机器算**：
> - `IQS`（蓝图完备度）← `check_blueprint.py <蓝图目录> --write-iqs`，按 0/5/8/10 四档逐格打分（满分 100）；
> - `EVS` ← BR-5 均分 × 20 自动换算；`综合评分` ← IQS × EVS / 100 自动推出。
> 直接跑 `b09_summary.py` 也会自动补算缺失的分数。**只有 BR-5 需要人评**——"证据在哪一格"需要人判断。
> `--json` 输出里每个分数都带 `*_source` 字段标明来源（手填 / 机器算 / 由 BR-5 换算），可直接追溯。
>
> **IQS × BR-5 联动**：待补格标注它能涨哪些维度（如 `B05(涨T/R/E)`），`下一步` 优先推荐能涨最多维度的格——补一格同时涨 IQS 与多个 BR-5 维度。映射单一数据源在 `scripts/blocks.py` 的 `BR5_DIMENSIONS`。
> 修复顺序：**先补没填的格（涨 IQS，顺带涨多个 BR-5 维度），再深化设计填得浅的格（涨 BR-5）**。

## 二、逐维评分锚点（设计期，1–5 分）

> 打分原则：**证据必须在蓝图里找得到**。找不到证据的维度，最高给 2 分。

### T — 边界可信（B01 / B05 / B06）

| 分 | 判据 |
|----|------|
| **1** | 完全没提权限、敏感数据或输出去向 |
| **3** | 提了权限或输出目录，但输出「目录 / 命名 / 格式 / 错误」四要素缺两项以上 |
| **5** | 权限最小化已说明；敏感数据（密钥、个人信息）处理方式已定；输出四要素**全部**约定 |

**自检问句**：这份 skill 会碰到什么敏感东西？出问题时往哪写、写成什么样，蓝图说了吗？

### R — 失败可控（B05 / B06）

| 分 | 判据 |
|----|------|
| **1** | 只考虑顺利路径，没想过会失败 |
| **3** | 列了部分边界输入，但失败后的输出格式或降级方案没定 |
| **5** | 边界输入（空 / 超长 / 极少匹配 / 用户取消）列全；失败输出格式已约定；断点续跑或降级方案已设计 |

**自检问句**：用户中途取消、输入是空的、依赖的工具没装——这三种情况蓝图各说了一句什么？

### A — 触发可辨（B02 / B06）

| 分 | 判据 |
|----|------|
| **1** | 说不清什么时候该用它、什么时候不该 |
| **3** | description 有 WHEN 但缺 NEGATIVE，或没做生态正交性检查 |
| **5** | 正交性检查通过（不与既有 skill 张成同向）；description 的 WHEN / NEGATIVE / 中英同义覆盖已定；能力边界有明确归属页 |

**自检问句**：生态里有没有别的 skill 已经干了这件事？两个会不会同时被触发？

### C — 结构可解（B07）

| 分 | 判据 |
|----|------|
| **1** | 只有模糊想法，没画目录 |
| **3** | 画了目录骨架，但只有层级没有**具体文件名**，或五段骨架只写了个标题 |
| **5** | archetype 已选定；目录骨架含具体文件名；SKILL.md 五段骨架**逐段填出**；references 索引策略已定 |

**自检问句**：拿这份蓝图去施工的人，能不能不看我就知道该建哪些文件、每个文件里写什么？

### E — 验证可证（B05 / B08）

| 分 | 判据 |
|----|------|
| **1** | 没想过怎么验证 |
| **3** | 有验证想法但用的是空泛测试，或没安排有/无对比 |
| **5** | 输出契约可直接交付；真实场景已指定（非空泛测试）；有 / 无 skill 对比计划已排；独立审已安排 |

**自检问句**：做出来之后，拿哪个真实场景证明它有用？谁来判断？

## 三、BR-5 ↔ 积木格 ↔ TRACE 三方映射

```
B01 条件 ┐
B05 分析 ┼─→ T（边界可信）  ─→ 成品视角：权限最小、无密钥、过安全扫描
B06 决策 ┘

B05 分析 ┐
B06 决策 ┴─→ R（失败可控）  ─→ 成品视角：自动重试、错误降级、断点续跑

B02 事实 ┐
B06 决策 ┴─→ A（触发可辨）  ─→ 成品视角：不误触发、不漏触发、边界清晰

B07 计划 ──→ C（结构可解）  ─→ 成品视角：信息架构清晰、FAQ 好找

B05 分析 ┐
B08 行动 ┴─→ E（验证可证）  ─→ 成品视角：真实场景验证、输出可直接用
```

> **读法**：左边是设计期证据来源，中间是 BR-5 维度，右边是同一个字母键在成品阶段长成什么样。
> **推论**：**十格走完填实，BR-5 自然不低**——BR-5 低不是在说"分数低"，而是在说"某一格没填到位"。

## 四、设计期低分定位表（分数低 → 补哪格）

| 低分维度 | 最可能没填到位的格 | 机器辅助 |
|---------|------------------|---------|
| **T 低** | `01-条件` 缺边界与准入四问；`06-决策` 缺输出四要素 | `check_blueprint.py <蓝图目录>` |
| **R 低** | `05-分析` 缺边界输入；`06-决策` 缺失败输出与降级路径 | 同上 |
| **A 低** | `02-事实` 缺生态正交性检查；`06-决策` description 五件事不全 | 同上 |
| **C 低** | `07-计划` 目录骨架无具体文件名 / 五段骨架只写标题 | 同上 + `render_structure.py` 出结构图自检 |
| **E 低** | `05-分析` 输出契约模糊；`08-行动` 验证场景空泛 | 同上 |
| **综合分低** | 先查 `IQS`（完备度）——**多半是有格子根本没填**，而不是填得不好 | `check_blueprint.py --write-iqs`（机器算 IQS + 报待补格） |

> **修复顺序**：先补没填的格（涨 IQS，见效快），再深化设计填得浅的格（涨 BR-5，涨 EVS）。

## 五、发布期口径 TRACE（成品自查，保留降级）

> **只在准备发布 / 冲 SkillHub 高分 / 收到平台返评时使用。** 原始标准：https://skillhub.cn/tutorials#trace-evaluation

| 维度 | 一句话 | 核心问题 |
|------|--------|----------|
| **T — Trust** | 能不能放心用？ | 权限最小？泄露敏感信息？过安全扫描？ |
| **R — Reliability** | 能不能稳定用？ | 异常输入处理？失败可理解反馈？自动恢复？ |
| **A — Adaptability** | 该不该在这用？ | 触发条件明确？会误触发/漏触发？ |
| **C — Convention** | 能不能被理解和维护？ | 信息架构清晰？示例/限制/FAQ 可找到？ |
| **E — Effectiveness** | 问题真解决了吗？ | 输出完整可用？有额外判断与质量提升？ |

**简版自查清单**（详细逐条见 §四 定位表反向使用）：

- **T**：frontmatter 完整（name/description/version/tags/allowed-tools）；未硬编码密钥；不索要超需权限 → `validate_skill.py --self` §6
- **R**：脚本瞬态失败可自动重试（`retry.py` + `sd_cli.py --retries`）；失败给可执行的下一步；断点续跑可用
- **A**：description 明确 WHEN 与 NEGATIVE；触发词覆盖中英同义；与兄弟 skill 不重叠
- **C**：零技术门槛启动路径清晰；FAQ / 限制 / 案例集中且易抵达；references 采用索引机制；有 version + CHANGELOG
- **E**：真实场景验证 + 有/无对比；产出可直接发布；评分指向具体改进项

## 六、返评期低分定位表（关键词 → 改哪个文件）

| 平台返评关键词 | 最可能维度 | 优先修复动作 |
|----------------|-----------|-------------|
| "没有自动重试" / "网络问题需手动重来" | R | `retry.py` + `sd_cli.py --retries`；更新 SKILL.md Error Handling |
| "FAQ 不好找" / "文档太长找不到答案" | C | quickstart.md §FAQ；README.md 加 FAQ 标签；SKILL.md 加 FAQ 路由 |
| "触发词不够" / "不知道什么时候该用它" | A | SKILL.md description；capability-boundary.md |
| "失败没提示" / "出错直接卡死" | R | B05 边界 + B06 错误输出 + flow-recovery.md |
| "输出不能直接用了还要自己整理" | E | B05 输出契约 + B08 真实场景验证 |
| "缺版本号 / CHANGELOG" | C | frontmatter + CHANGELOG.md |
| "疑似密钥 / 外部链接" | T | `validate_skill.py --self` §6 全目录安全扫描 |

## 七、机器可消费摘要

**设计期目标**：BR-5 均分 ≥ 4.5（换算 EVS ≥ 90）；蓝图完备度 IQS ≥ 90
**发布期目标**：TRACE 五维 ≥ 4.9

**关键抓手**（按见效速度排序）：
1. **先填齐十格** —— IQS 是乘积的一侧，缺格对综合分伤害最大
2. **R 维**：边界输入 + 失败输出 + 降级路径（设计期最常漏）
3. **C 维**：目录骨架要有具体文件名，五段骨架要逐段填（不是写标题）
4. **E 维**：真实场景 + 有/无对比 + 独立审

**一句话验收**：
> 设计期——施工的人拿到蓝图，不看设计者就知道建什么文件、每个文件写什么、做完拿什么场景证明有用。
> 发布期——用户在任何正常/边界/中断场景下，都知道"能不能用我这件事"、"失败后下一步做什么"、"最终产物长什么样"。

## 八、外部返评消费流程（v3.15.0 移植姊妹分支 v4.3——返评不是终点，是补丁输入）

> 平台五维返评（如 SkillHub 评价页）到手后，按此流程闭环，不让返评停留在"读一遍"。`trace_patch.py --mode ship` 是现成消费工具，缺的只是把流程钉死。

**流程四步**：

1. **录入**：返评原文 + 五维分数（若有）存入 `outputs/`（文件名 `skillhub-review-assessment-<日期>.md`），作为证据快照；
2. **拆补丁**：`python scripts/trace_patch.py <反馈.json> --mode ship --threshold 4.5` → 生成"改哪个文件"的 P0/P1/P2 补丁清单（§六 定位表即其知识源）；
3. **逐项落实**：按 P0→P2 执行；改 description / 错误处理 → 重跑 `sd_cli evals` + 用例回归；
4. **复评对账**：修复完成后**带证据路径**重新自评，登记下次平台返评做对照；**能变成机器检查项的当天就落**（见 D-132 / lessons L10——返评结论停在文档里 = 下次照犯）。

**实例 #1（2026-09-10，SkillHub 五维评价，姊妹分支）**：
- 返评要点：流程稳、不漏项、可交接、机器质检闭环为强项；**边界定义密度不如资深设计师**（同一句短板重复两次）。
- 证据快照：`outputs/skillhub-review-assessment-2026-09-10.md`（含与 `baseline-vs-with-skill.md` 实测 11 vs 18 条的对齐分析）。
- 拆解结果：P0 边界补全机制（③固定步骤 + `check_blueprint` **C7** 门槛）；P1 Step ⑤ 施工通道（本工作空间定位为「只设计不施工」，未移植）；P2 本节流程本身。**返评→补丁→落实→本节归档**构成第一个完整闭环案例，发布期 E 维可直接引用。
