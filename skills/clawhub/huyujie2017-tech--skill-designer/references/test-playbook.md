# 测试打磨剧本（Part 4）— 闭环验证层

> 加载条件 / 核心主题 / 命中标签 / 不回答 → 见文件头 frontmatter（与 references 其余 17 份同口径）。

> 主流水线走完、蓝图/草稿产出后进入本层。回答三件事：**怎么测、测什么、怎么改**。
> 核心判断：**Skill 的评估不看结构是否干净，而看注入后 LLM 的任务完成质量是否提升。**
> "写得对不对"（静态分）与"用了真不真有效"（动态分）是两回事——分别测、分别报。

## 一、两层测试框架总览

两个正交的测试问题，**不能合并**：

| 测试 | 测什么 | 用户问题 | 判断方式 |
|------|--------|----------|----------|
| **trigger-queries** | 会不会被触发（触发率） | "这个 skill 能不能被 router 激活" | 模拟 router：只看 description 判断 YES/NO |
| **test-prompts** | 触发后输出质量 | "这个 skill 好不好用" | baseline vs with-skill 双跑，独立评分 |

> 新手往往只测功能，忘了测"description 到底能不能被激活"。两者 schema 不同、生成策略不同。

> **第三维度（性能对比）**：除触发 + 效果外，还可对同一任务分别"无 Skill / 有 Skill"各跑 5 次对比 Token 用量与完成质量，验证渐进披露的经济性——见 [engineering-practices.md](engineering-practices.md) §7.1。

### 静态自检要跑三处：安装布局不同，目录名规则就不同

`validate_skill.py --self` 的结论**依赖当前目录名**，所以同一份 skill 必须在三种布局各跑一遍，全过才算过：

| 布局 | 目录名来源 | 例 |
|------|-----------|-----|
| 源工程 | frontmatter `name` | `…/skill-designer` |
| dist 发布包 | frontmatter `name` | `…/dist/skill-designer` |
| 发布平台安装目录 | **config.json 的 `slug`**（常带 `@namespace/` 前缀） | `~/.workbuddy/skills/@ns/high-quality-skill-guidance` |

> **只在源目录 + dist 跑，仍会漏掉一整类 bug**。本项目 v2.20.6 之前 `check_name_dir` 只认「目录名 == `name`」，而发布平台安装时目录名取的是 slug（还可能带命名空间前缀）——结果是**任何用户装上后跑自检都会红第 2 项**，内容却完全合规。
> 教训：**写任何路径相关检查前，先问一句"这个 skill 还可能被装在哪个目录下"**——目录名 ≠ name 是常态，不是异常。

## 二、触发测试（trigger-queries）

### 三类查询

| 类 | 含义 | 例 |
|----|------|-----|
| `should_trigger` | 应该激活 | "帮我做张报表" |
| `should_not_trigger` | 不应激活（似是而非） | "帮我配置 npm 仓库" |
| `ambiguous` | 歧义（仅记方差不计分） | "看看这个" |

### 量化纪律

- **60/40 split**：前 60% train 用于优化反馈，后 40% test 用于"未见过的查询"评估——防 description 过拟合训练措辞。
- **只投喂 description**：真实 router 只看 description，不投 SKILL.md body。
- **N=3 重复**降方差，单次结果不可信。

### 用例模板

```json
{
  "should_trigger": ["帮我做张报表", "生成 excel", "create a skill", "把这件事教给 AI", "我想让 AI 更会写周报", "帮我把这个流程固化成能力"],
  "should_not_trigger": ["帮我配置 npm", "写一篇博客"],
  "ambiguous": ["看看这个工具"]
}
```

**失败 → 针对性调 description**：扩触发词（五维）或加显性排除（NEGATIVE BOUNDARIES），再测。

## 三、效果测试（test-prompts）

### 双测试集分工

`test-prompts` 只管触发后输出质量，与 trigger-queries 分开维护。

### 场景五分类（每类缺一不可）

| 场景 | 含义 | 典型 prompt |
|------|------|-------------|
| `happy_path` | 用户最常说的那句话（核心路径） | "帮我做 X" |
| `complex` | 多步骤/分支/上下文依赖 | "评测这 5 个 skill 排个序" |
| `edge` | 边界：空输入/极大输入/极少匹配 | 空字符串/极长文本 |
| `negative` | 反例：说了"似是而非"的话，应**不**激活 | "帮我配置 npm 仓库" |
| `error` | 异常：依赖缺失/API 失败/权限不足 | "搜索 X"（Token 未配置） |

### 功能 × 场景 覆盖矩阵 + 优先级

| 功能模块 | happy | complex | edge | negative | error | 优先级 |
|----------|:-----:|:-------:|:----:|:--------:|:-----:|:------:|
| 功能 A（核心） | ☐ | ☐ | ☐ | ☐ | ☐ | P0 |
| 功能 B（次要） | ☐ | ☐ | — | ☐ | — | P1 |
| 功能 C（附加） | ☐ | — | — | — | — | P2 |

**完整性要求**：功能覆盖率 100%、P0 场景 ≥ 95%、每条 prompt 判别力 ≥ 1 条 skill 专属 judgement。

### 判别力要求（防假测试）

**每条测试必须含 baseline 不可能命中的专属检查**——否则"通用礼貌回复也能过"。

> 例：Excel 报表 skill 的判别力 = "输出的 xlsx 里是否含 `月报-{YYYY-MM}.xlsx` 命名、Sheet1=汇总"——baseline（无 skill）答不出。

## 四、双跑与独立评分

### baseline vs with-skill 双跑

| 跑 | 加载 | 目的 |
|----|------|------|
| `with_skill` | 加载 SKILL.md | 看 skill 让结果变好多少 |
| `baseline` | 不加载 | 对照基准 |

### 独立评分（防自评偏差）

**用独立的评分者/另一个上下文评，不能"改完直接评"**——同一上下文里容易把自我说服当改进。

### 双轨独立评分 + 交叉一致性校验

静态分（结构）与动态分（实测）**分别呈现**，交叉校验（delta > 15 报警）：

| 模式 | 含义 | 处理建议 |
|------|------|----------|
| **静态高 + 动态低** | "摆设型 skill"——结构规整但实际不起作用 | 攻指令/知识增量，不要只磨静态分 |
| **静态低 + 动态高** | "干货但粗糙"——内容有价值，格式需整理 | 先补结构，不要因静态分低判 skill 没用 |

> 这是"双维度衡量（内部质量 × 外部价值）"的另一个同构实例。

## 五、打磨纪律

### 知识三分法（删什么留什么）

| 类别 | 定义 | 处理 |
|------|------|------|
| **Expert（专家知识）** | LLM 真的不知道的 | **必须保留**——skill 的核心价值 |
| **Activation（激活知识）** | LLM 知道但可能想不到的 | 简短保留——起提醒作用 |
| **Redundant（冗余知识）** | LLM 肯定知道的基础内容 | **应删除**——浪费上下文窗口 |

- **优秀基准**：Expert ≥ 70% / Activation < 20% / Redundant < 10%。
- **冗余典型来源**：角色扮演（"你是一个专业的…"）、与 scripts/ 重复的逻辑、行业标准术语的定义。
- **关键区分**：看起来像冗余但实际在构建指令的背景知识（认知型 skill），**不是**冗余；判断标准：**删掉后 LLM 任务表现是否下降**。

### 棘轮纪律（每轮只改一个维度）

- **每轮只改一个最低维度**——避免多变更无法归因；
- **只有新分严格 > 旧分才 keep**，否则回滚（git revert 防退步）；
- **体积守门**——新 SKILL.md > 原始 × 1.5 拒绝提交；
- **记录每轮**——`results.tsv: old_score / new_score / status / dimension`，跨轮可追溯。
- **反馈必须强制收集**——可选步骤永远不会被执行（chenlin 成功模式经验）：每次使用后固定问「这次产出是否可用？（可用 / 部分可用 / 不可用）+ 原因」，否则自进化机制永远没有数据。

### BUG_LOG 跨会话沉淀 + BUG 五分类

`BUG_LOG.md` 是复盘积木的实体化，跨会话持久化 BUG：

| BUG 五分类 | 含义 | 例 |
|-----------|------|-----|
| 触发问题 | description 没召回 | "说'做张表'没激活" |
| 指令缺陷 | body 指令不清/歧义 | "不知道先做什么" |
| 边界缺失 | 没处理边界输入 | "空输入报错" |
| 示例问题 | 示例与场景不符 | "示例是英文用户场景" |
| 资源问题 | 引用的文件/脚本缺失 | "references 加载不到" |

- **修复后加预防指令**：在 SKILL.md 写 `## 注意事项` 防复发（"失败 → 归纳成通用规则"的落地）。

#### 负向约束优先升级（错误台账 MISTAKES.md，来源: chenlin-skillcreator 切片）

把 BUG_LOG 从"记录打磨期 bug"升级为**运行期错误台账**机制：

- **append-only 永不删改**：运行中发现新失败模式 → 立即追加一行（`ID | 日期 | NEVER | 后果 | 改为 Y | 触发场景 | 证据`）；
- **TOP N 注入**：下次执行前读取台账，把高频/高危错误注入 SKILL.md 约束区；
- **reverse-inference 找全集**：初始化时从该领域"完整错误骨架"反推，而非凭记忆列几条（避免隐性盲区）；
- **正负配对**：每条 NEVER 尽量配一个"改为 Y"（粉红大象问题——纯否定堆砌会激活被禁行为的注意力），仅安全/合规/不可逆等二元硬边界可用纯否定。

> 详见 [design-blocks-library.md](design-blocks-library.md) D-117；产出物模板见 [blueprint-template.md](blueprint-template.md)「可选配套交付物」。

### 改进优先级

| 优先级 | 内容 |
|--------|------|
| 高 | description / 逻辑缺陷（直接影响激活与正确性） |
| 中 | 清晰度 / 示例 |
| 低 | 格式 |

## 六、静态验证清单（六步）

**自检先于评分**——链接都是断的，打分没有意义。

> **机器强制版（推荐）**：这 6 步的**硬性项**已封装为脚本 `scripts/validate_skill.py`（YAML 有效 / name 与目录一致 / 引用完整性 / 长度守门 / 安全密钥 / 无 README），跑 `python scripts/validate_skill.py <skill_dir>` 即可机器判定（`--json` 出结构化结果供 AI 解析）。**软性项（逻辑连贯、触发质量、工作流合理性）仍由 AI/人裁定**——脚本查形式不查功能（呼应"硬性交给自动化，软性留给人"）。
>
> **蓝图侧配套**：设计期蓝图本身的完整性/一致性由 `scripts/check_blueprint.py <蓝图目录>` 机器判定（逐格填空与验收 + 6 条跨格一致性规则，`--json` 结构化输出）——B09 质量门前置一道机器闸门：蓝图缺口未清零不进入施工蓝图交接。

| # | 检查 | 硬性/软性 |
|---|------|-----------|
| 1 | frontmatter YAML 有效 | 硬性（可自动判） |
| 2 | `name` 与目录名一致 | 硬性（可自动判） |
| 3 | 引用完整性：references/ 链接都能解析 | 硬性（可自动判） |
| 4 | 逻辑连贯性：流程能一步步走通 | 软性（AI/人裁定） |
| 5 | 长度检查：body < 5K（与 P11 三层渐进披露一致），不超限 | 硬性（可自动判） |
| 6 | description 五件事齐全 + 触发词覆盖五维 | 半软（可清单化） |

### 硬性检查 vs 软性判断

| 类型 | 谁判 | 例 |
|------|------|-----|
| **硬性检查** | 脚本/清单可自动判 | YAML、name 一致性、引用完整性、体积守门 |
| **软性判断** | AI/人裁定 | 语义、触发命中质量、工作流是否合理 |

> 与 SCK"查形式不查功能"的诚实定位一致：**硬性交给自动化，软性留给人/LLM**。

### 六-续、双轨审查规则库（实现后自检的进阶形态，来源: cloudbase 切片 D-101）

> **定位**：§六 静态验证是"包级体检"（YAML / 引用 / 长度 / 安全）；这里把**领域级审查规则**沉淀成可累积资产——**确定性规则给正则（秒级机器查）+ 判断性规则给 LLM 提示（语义查）+ 每条带修复指引**。适用于"实现后自检"，尤其多模块 / 高风险 skill。参见 [design-blocks-library.md](design-blocks-library.md) D-101、活样板 cloudbase-code-review。

**双层机制**：

| 层 | 方法 | 速度 | 查什么 |
|----|------|------|--------|
| **Lint（确定性）** | 正则脚本（可选） | 秒级 | 错 API 调用、缺配置、模式不匹配 |
| **LLM 审查（语义）** | 读每条规则"LLM 检查"节，语义审查 | 视复杂度 | 路由守卫逻辑、权限完整性、架构级问题 |

**规则统一格式**（每条规则一个 `.md`）：

```markdown
# RULE-ID 规则名
- **Module**: auth / database / storage / ...
- **Severity**: error | warning
- **Stage**: code-generation | deployment | config

## 正则检查 (Lint)   ← 给确定性脚本（可判定的查）
## LLM 检查          ← 给语义审查（判断性的查）
## 修复指引          ← 怎么修
```

**规则索引矩阵**：模块 × 前端类型 → 适用规则（`RULES_INDEX.md`），让"实现后该查哪些规则"可按模块 / 类型定位，不靠记忆。

**规则边界纪律（防特例污染）**：
- 单个失败或 case-specific workaround **不提升为硬规则**；
- 只有**稳定文档 / 反复失败 / 确定性运行时行为**才能进规则库；
- case-specific 观察只留归因报告、不入库——否则规则库被特例稀释、失去判别力（与 [lessons.md](lessons.md) 三问晋升检查同构，但更强调防特例污染）。

**与既有机制的关系**：
- `validate_skill.py`（§六）查**包级形式**；规则库查**领域级语义**——二者叠加 = 纵深防御；
- 规则库新增规则走本文件 §九 的召回健康检查（新 reference 必须登记）；
- 与 `BUG_LOG` / `MISTAKES.md`（§五）互补：规则库是"防再犯"的静态资产，BUG_LOG 是"运行中发现"的动态台账——新失败 → 先记 BUG_LOG → 验证为稳定模式 → 晋升为规则进库。

## 七、反馈输出：三位一体格式

打磨反馈**不用"通过/不通过"二元**，用：

```
🌟 亮点     —— 这次做对了什么（肯定）
⚠️ 需改进   —— 具体哪里要改（可操作）
💡 学习要点 —— 从中可以沉淀什么规则（教，而不只是裁判）
```

## 八、安全审查（进阶可选）

涉及脚本/网络/凭证时，按 OWASP LLM Top 10 对齐做安全审查：

**7 类风险指标**：
1. 脚本执行权限（allowed-tools 是否过宽）
2. Prompt 注入（"ignore safety rules" 类）
3. 网络调用（是否访问未知端点）
4. 硬编码凭证（密钥/token 是否在文件里）
5. 跨目录路径（能否读写预期外路径）
6. 危险操作（删除/覆盖/发消息）
7. 数据泄露（是否输出敏感信息）

**8 步审查清单**：逐项过 7 类风险 + 结论（通过 / 需修复）。

> 普通用户创建 skill 时安全易被忽略，但作为**进阶可选**值得提醒——尤其涉及脚本/网络调用时。

## 九、reference 召回健康检查（新增 / 修改 reference 必做）

> 当 skill 采用"SKILL.md 路由器 + references 分层"结构时，每个新增的 reference 都藏着一个隐蔽风险：**写得再好，若主文件导航表 / 加载条件表没把它正确召回，或召回后给不出判别力，它就是死知识**。本指南的 `engineering-practices.md` §9 已拿它自己做过完整示范——本节把那次方法沉淀为可复用清单，今后每个新增 / 修改的 reference 都照此自测。

### 架构前提：二级路由召回

**关键认知**：reference（辅助文件）**不是靠顶层 `description` 激活**的，而是靠 **SKILL.md 内部的「references 导航表」+「References 加载条件表」做二级路由**检出。因此"召回测试"必须测二级路由命中，而非复用 §二 的"一级 description 触发测试"（那一层测的是整个 skill 是否被激活）。

> 若你的 skill 结构简单（无 references 分层），则跳过本节，直接用 §二 / §三。

### 召回测试（二级路由命中）

**判定依据**：SKILL.md 导航表 + 加载条件表 + 该 reference 自身的"加载条件"段落。

**用例模板**（类比 §二 三类查询，但判定对象是"该 reference 是否被正确路由"）：

```json
{
  "should_trigger": ["指向该 reference 核心主题的口语化 query（应召回）"],
  "should_not_trigger": ["易混淆、但主召回应是其他 reference/原则的 query（不应召回）"],
  "ambiguous": ["边界 query，两边都可能命中，仅记方差不计分"]
}
```

**量化纪律**（同 §二）：60/40 split 防过拟合；N=3 重复降方差；只用主文件导航表 / 加载条件判定（不投喂 reference 正文）。

**召回率目标**：`should_trigger` ≥ 95%；`should_not_trigger` 误召回率 ≤ 10%。误召回率高 → 调主文件导航表措辞，或该 reference 的标题 / 导语（措辞精确性直接影响误召回，见下）。

### 效果测试（加载后判别力）

**同 §三 五场景矩阵**，但每条必须带"该 reference 独有的、baseline（无该文件）答不出的专属判别力"——否则测了等于没测。

| 场景 | 判定重点 |
|------|----------|
| `happy_path` | 核心主题 query，是否给出该 reference 的差异化增量（非 Activation/Redundant 知识） |
| `complex` | 多步骤 / 交叉，是否给出该 reference 独有结构（如分层决策树 / 级联白名单） |
| `edge` | 边界（接近量化阈值如 300/500 行），是否给出量化信号 |
| `negative` | 该 reference 明确"不重复、仅指向别处"的主题，是否正确不展开而指向别处 |
| `error` | 引用的子资源（其他 reference / 脚本）是否真实存在（防孤儿引用） |

### 防自评偏差与措辞精确性

- **评分独立性**（同 §四）：若本次自测为设计者自评，存在自评偏差——务必声明，并建议独立上下文交叉评分。
- **措辞精确性（关键防坑）**：reference 的**标题 / 导语用词**会直接影响二级路由命中。例如把"工具接口白名单隔离"冠以"安全实践"标题，会让 router 把"防 prompt 注入"类 query 误路由过来（与真正的安全审查主场混淆）。**边界主题用词要精确，避免与相邻 reference 的语义重叠措辞。**

### 三处触发词同步维护

若主文件用"导航表 + 加载条件表 + reference 自身加载条件"三处描述同一 reference 的触发条件，**未来调触发词须三处同步**，否则出现"语义漂移"导致召回不一致。
