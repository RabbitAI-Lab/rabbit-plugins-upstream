# 蓝图方法论（Part 1）— 积木哲学 × 技能蓝图

> **一句话命题**：技能蓝图（skill 需求规格书）= 用「条件 → 事实 → 观点 → 问题 → 分析 → 决策 → 计划 → 行动 → 结果 → 复盘」的积木链，把用户一个模糊的念头，施工成一块**可链接、可复用、可衡量、可演进的能力积木**。
> 本文是全局的方法论底座。它不产生流程步骤，而是为主流水线的每一格提供"为什么"和"在世界观坐标系中的位置"。本文件自包含，可随 skill 独立安装。

---

## 一、世界观对齐：每个 skill 都是一块可拼装的能力积木

> **大白话**：把"做一个 skill"想成"用乐高搭一个功能"——每一块乐高就是一个技能，拼起来就能组合出复杂能力；蓝图就是搭之前画的拼装说明书。下面这张表把"积木世界"和"skill 世界"一一对应，先建立直觉。**看不懂术语直接翻本文 §十「术语白话表」**。

| 积木空间概念 | 能力空间（Skill 域）对应 |
|---|---|
| 知识积木 | **能力积木（Skill）** |
| 积木空间 | 已安装的 skill 生态 |
| 积木链 | skill 之间的前置 / 后续 / 组合流程 |
| 接口向量 V_interface | **description（Tier1 召回索引）** |
| 内部向量 V_internal | SKILL.md 正文 + scripts/ + references/ + assets/ |
| 双维度衡量 | 内部质量 IQS × 外部价值 EVS |

**推论**：用积木哲学规划技能蓝图不是"套皮"，而是把 skill 放回它本来的坐标系。蓝图里的每一项，都能在积木哲学里找到对应物、约束和衡量法。其中 **IQS×EVS（内部质量 × 外部价值）是本 skill 自有的双维度质量框架**，完整权重定义见 [blueprint-template.md](blueprint-template.md)，不依赖任何外部 skill。

<details>
<summary>📐 进阶深读：为什么用"积木"比喻（数学视角，初学可跳过）</summary>

积木哲学借用了线性代数"向量空间"的框架：正如**函数空间由基本函数张成（span）**，AI 能力空间由基本 Skill 积木张成；选对"基（basis）"就能高效组合出复杂能力。接口向量 V_interface 即 description，决定 Tier1 召回；两个 skill 若张成同一向量方向（功能重叠）就不是独立基向量（这叫"正交性"）。这套数学给"先出蓝图、精简 body、避免重叠"提供了统一的理论根基——**看不懂完全不影响你写出好 skill**，照流程图走即可。

</details>

## 二、核心重构：10 型积木链 = 技能蓝图

积木哲学最有价值的一点是**"链式为主"**——蓝图不是一堆平铺字段，而是一条有因果顺序的逻辑链：

```
条件积木 → 事实积木 → 观点积木 → 问题积木 → 分析积木
                                                   ↓
                                        决策积木 → 计划积木 → 行动积木
                                                   ↓
                                              结果积木 → 复盘积木
```

| 积木链角色 | 结构公式 | 蓝图对应环节 | 具体承担 |
|---|---|---|---|
| **条件积木** | `[前提] + [背景] + [资源约束]` | 需求判断 | 该不该做、边界、前置、准入四问 |
| **事实积木** | `[时间]+[主体]+[动作]+[客体]+[结果]` | 上下文画像 | 用户 / 环境 / 已有生态 / 正交性 |
| **观点积木** | `[主体]+[判断]+[内容]+[依据]` | 设计模式处方 | 选哪个设计模式、依据是什么 |
| **问题积木** | `[问题]+[前提]+[待定]` | 需求澄清 | 未决口径、待用户确认项 |
| **分析积木** | `[输入]+[方法]+[推导]+[假设]+[结论]` | 任务分析 | 输入输出契约、口径、边界、风险 |
| **决策积木** | `[决策者]+[内容]+[理由]+[后果]` | 方案抉择 | 拆分?组合?脚本化?触发策略 |
| **计划积木** | `[目标]+[步骤]+[时间表]+[负责人]` | 施工图 | 目录骨架、脚本化清单、实施步骤 |
| **行动积木** | `[主体]+[动作]+[客体]+[状态]` | 验证执行 | 真实场景实测、有/无对比 |
| **结果积木** | `[行动]+[产出]+[影响]+[验证]` | 质量门 | 内部质量 × 外部价值双维度评分 |
| **复盘积木** | `[结果]+[验证]+[经验]+[改进]` | 双回路对抗 | 失败归纳、防 overfit、迭代 |

**关键差异**：从"七个功能模块平铺"变为"一条有因果顺序的逻辑链"。蓝图从"一份需求文档"变成"一条可走的逻辑通路"——每一步都由上一步推出，设计师沿链逐格引导用户，不漏、不跳步。

## 三、四原则 = 蓝图规划的工作引擎

> 四原则的**权威定义即本节下表**（v3.11.0 修正：此前本段指向 SKILL.md「四原则 = 工作引擎」，但 SKILL.md 并无该章节——悬空指针，已就地改为权威源）。注意与两处「四」的区别：**四原则是世界观**（蓝图为什么这样规划，SKILL.md 定位块引用的是 [lessons.md](lessons.md) L1/L2/L4/L7 四条）；**四条硬规矩是流程硬规矩**（四步流里什么不可破坏，见 SKILL.md §1）。

| 积木四原则 | 在蓝图规划中的落点 |
|---|---|
| **蓝图优先** | 先出蓝图，再进 skill-creator / 写作。蓝图是 SKILL.md 的**上游**，永不跳步 |
| **增量优于全量** | 蓝图先做 MVP 切片（最小积木链）→ 再扩展；skill 先最小可用 → 再打磨 |
| **可替换不绑定** | 蓝图各积木松耦合：description / 脚本 / 模板可独立替换，不硬编码；skill 不绑定单一 host |
| **闭环即进化** | 每轮"生成 → 验证 → 人审 → 改进"是一个闭环，推动蓝图（和 skill）演进 |

这四条同时是各环节的**验收标准**：一个环节的产出若不符合"可替换、松耦合"，说明该积木设计有问题；蓝图本身不追求一次性大而全，而是"最小闭环先跑通"。

## 四、双维结构 = 蓝图同时回答"长什么样"和"站在哪里"

### ① 上下分层 = skill 的内部架构（回答"长什么样"）

```
SKILL.md  = index.md（接口描述，决定 Tier2 加载）
├── scripts/      = 确定性子积木（V_internal：内部实现）
├── references/   = 领域知识子积木（按需取用）
└── assets/       = 模板子积木
```

这正是**渐进披露三层加载**的积木表达。蓝图要在"计划积木"环节画出这棵组合树：哪些是确定性脚本（该写成 scripts/，而非让 AI 每次重造轮子）、哪些是领域知识（放 references/）、哪些是模板资源（放 assets/）。

> **关键定位：references 的读者是 agent，不是用户。** references/ 是给 **agent 在引导时优先参考**的领域知识库（方法论、最佳实践、问题库、边界、恢复），不是让用户逐篇查阅的文档。agent 命中即用、按需加载；用户只需跟着 SKILL.md 的引导走，无需翻 references。**参考资料是 agent 的"弹药库"，数量由定位决定——高质量参考资料 → 高质量施工蓝图 → 高质量 skill。**

### ② 水平连接 = skill 的生态位（回答"站在哪里"）

```
用户需求 → [data-skill] → [excel-skill] → [slides-skill] → 交付
```

蓝图要在"事实积木"环节标出：这个 skill 与既有生态的**前置 / 后续 / 并行**关系，以及**正交性检查**——避免两个 skill 张成同一个向量方向（重叠），保证每个 skill 是独立基向量。

### ③ 接口向量 = description 的哲学解释

"接口向量 V_interface 决定对外呈现"**直接就是 description 的哲学基础**——description 是这块能力积木的接口向量，决定 Tier1 召回。触发词工程因此有了理论根基：**接口向量张得准不准**。

> **推论**：一个 skill 的 description 写不好，本质是这块能力积木的**接口向量定义错了**——张量不准，召回必失。

## 五、准入四问 + 双维度衡量 = 质量门

### 5.1 准入四问（条件积木的门）

> ☐ ① **形态合规** — 边界清晰吗？（有明确类型/形状）
> ☐ ② **非元信息** — 是可复用积木，而非一次性操作说明？
> ☐ ③ **可链接** — 能写出"关于 X 请参考 [[积木名]]"吗？
> ☐ ④ **复用检验** — 至少两个场景需要它？
> **当疑虑时，跳过。零个新积木比一堆噪音积木好。**

一个念头进蓝图前，先过四问。不通过的，引导用户转向 Rule（全局约束）、脚本/MCP（确定性能力）、或"根本不用做"。

### 5.2 双维度衡量（结果积木的评分法）

- **内部质量分 IQS = 蓝图完备度**（十格填得齐不齐）：B01–B10 每格 10 分，满分 100
  - 每格锚点：`0` 未填 / `5` 占位空壳 / `8` 已填但缺关键项 / `10` 填全且可交接
  - **⚡ 机器直接算，不用人评**：`check_blueprint.py <蓝图目录> --write-iqs` 逐格打分并回填 `09-结果.md`
  - 判定口径：拿 `blocks.py` 的模板字段逐条比对——**原样还在 = 未填，被改写或删除 = 已填**；只统计可机器判定的字段（含 `______` / `☐` / 选择题型），说明型文字与分组标题不计入，避免"判不了的字段永远扣分"
  - **B09 的「内部质量分」行由机器回填，统计时排除**，避免自己拉低自己
- **外部价值分 EVS = BR-5 就绪度换算**（每格填得深不深）：`EVS = BR-5 均分 × 20`（五维各 1–5 分 → 20–100 分）
  - BR-5 五维：T 边界可信 / R 失败可控 / A 触发可辨 / C 结构可解 / E 验证可证
  - 每维 1/3/5 分锚点与对应积木格 → [trace-evaluation-guide.md](trace-evaluation-guide.md) §二
- **综合评分 = IQS × EVS / 100**

这套数学即本 skill 自有的 IQS×EVS 双维度框架——同一个积木哲学在"知识积木"和"能力积木"两个域的两次实例化。

> **⚠️ 子项按评价对象实例化（易误解处）**：P26 原始子项（完整性/规范性/独立性/精准度/深度 × 信息价值/时间敏感性/可靠性/关联度/复杂度）是为**知识积木**设计的——其中"复杂度"对知识是加分项，对蓝图却是减分项。**蓝图场景下子项必须换成本节的实例化口径**，只有**乘积算法与 100 分量纲**是共用的。若您装有技能生态管家，两套口径靠这个共同内核打通，不会漂移。

## 六、蓝图文档形态：一块"元积木"（bundle）

既然蓝图是"规划积木的积木"，它就天然是一块 **bundle 积木**：

```
skill-blueprint/                    # 一块元积木
├── index.md                        # 蓝图接口：type: Blueprint + 一句话定位 + 接口向量
├── 01-条件.md                       # 准入四问 + 边界 + 前置
├── 02-事实.md                       # 画像 + 生态位 + 正交性
├── 03-观点.md                       # 设计模式处方
├── 04-问题.md                       # 待确认口径
├── 05-分析.md                       # 输入输出契约 + 风险
├── 06-决策.md                       # 方案抉择
├── 07-计划.md                       # 目录骨架 + 脚本化清单
├── 08-行动.md                       # 验证计划
├── 09-结果.md                       # 双维度评分
└── 10-复盘.md                       # 迭代记录
```

**断链容忍**天然适用：蓝图里可以先写"此处依赖一个尚不存在的脚本积木"，不报错，标记为待创建占位积木——**鼓励先搭骨架、再填充**，降低用户从零开始的心理门槛。

> 断链容忍在此的深层含义：**蓝图允许"指向未来的链接"**。这让用户可以先勾画完整的能力构想（哪怕是空壳），再逐格填充，符合"蓝图优先"原则。

**每张可填模板见**：[blueprint-template.md](blueprint-template.md)（bundle 实体化，含 Excel 报表 skill 实例）。

## 七、实例切片：前四格长什么样

以"Excel 报表生成 skill"为例，积木链前四格：

```markdown
## 01-条件积木
- 前提：用户每月从 CSV/JSON 生成运营/财务报表
- 背景：团队有统一报表风格，assets/templates/ 已有月报/财报模板
- 资源约束：依赖 openpyxl；缺失时降级 csv 标准库并明确告知（禁静默失败）；验证命令 `python -c "import openpyxl"`；绝不写死密钥
- 准入四问：形态合规✓ 非元信息✓ 可链接✓ 复用检验✓（月报+财报+临时分析≥3场景）

## 02-事实积木
- 时间：2026-08-16 | 主体：普通职场人，AI 中等熟练度
- 动作：已装 find-skill-skillhub、pdf-report-builder
- 结果：生态内无 Excel 报表 skill → 存在空白
- 正交性：与 pdf-report-builder（PDF 输出）不重叠，可形成前后链路

## 03-观点积木
- 判断：采用 Pattern A（流程配方）+ Pattern E（带自检）
- 依据：步骤清晰可脚本化；报表含数字，错误代价高，需验证步骤

## 04-问题积木
- 待定：是否需要图表注入？（取决于用户是否常做可视化月报）
```

## 八、与既有体系的关系

| 既有体系 | 关系 | 互补点 |
|---|---|---|
| **skill-creator** | 蓝图是它的**上游输入 brief** | skill-creator 生成草稿，蓝图提供上下文与验收标准 |
| **技能生态管家**（可选协同） | 共用 IQS×EVS **乘积算法与 100 分量纲**；子项按评价对象各自实例化（蓝图按 §5.2） | 蓝图在"创建前"把关；若装有管家，可在"创建后"管生态 |
| **Ctx2Skill 自进化框架** | 复用"红蓝对抗 + 跨时间回放"思想 | 把自博弈降维成普通人可用的"设计师挑战者 × 用户推理者"验证回路 |
| **OKF** | 提供准入四问、断链容忍、bundle 接口 | 让蓝图可交换、可 Agent 可读写 |

**定位一句话**：技能蓝图是 **skill 生产链路的"需求澄清层"**——介于用户念头与 skill-creator/写作之间，用积木哲学保证"做正确的事"（选对基），再用同一套哲学在"结果积木"环节保证"正确地做事"（双维度衡量）。

## 十、术语白话表

> 遇到听不懂的词，来这里查一行白话解释。**不需要提前背**——对话中遇到时设计师也会当场解释。

| 词 | 大白话 |
|----|--------|
| **积木链** | 把"做一个 skill"拆成 10 个有先后的步骤，一步步走完——像乐高说明书的 10 个拼装步骤 |
| **蓝图（bundle）** | 走完积木链产出的"需求规格书"——写 skill 前的施工图纸，比直接砌砖少返工 |
| **准入四问** | 动工前四道筛子：形态合规？非一次性？可链接？≥2 场景复用？漏一个就别开工 |
| **Phase 0 三问** | 出发前三确认：跑哪（平台）/ 干啥（新建还是改进）/ 花多久（轻量还是完整） |
| **诊断先行** | 改进已有 skill 时，先诊断病在哪再开药——用诊断结论填已明确的格，只对缺口格引导 |
| **我拟 / 你填** | 两种起草方式：你填=你主导填空设计师把关；我拟=设计师先出完整草稿你修改拍板 |
| **断链容忍** | 蓝图可以先留空壳（"此处还差一个脚本"），不报错，以后再填 |
| **软提示一次** | 识别到"想做 skill"意图时只建议一次先出蓝图，拒绝完全 OK、不拦截 |
| **强制阻塞** | 触发词和 skill 名必须你自己产出，设计师绝不代填（可给候选） |
| **双维评分** | B09 质量门：内部质量 IQS（十格填齐了吗）× 外部价值 EVS（每格填深了吗，由 BR-5 换算），评分必须指向具体改进项 |
| **BR-5 就绪度** | 设计期五维体检：T 边界可信 / R 失败可控 / A 触发可辨 / C 结构可解 / E 验证可证，每维问"约定了吗"而非"做到了吗" |
| **archetype（结构框架）** | B07 用的 7 套典型目录骨架范例（极简/流程/工具/知识/模板/全栈/套件），先选型再往里填内容 |
| **五段章节骨架** | SKILL.md 的五个标准段落：Workflow / Clarification Protocol / Resource Routing / Failure Handling / Validation |

> **两个"维度"别搞混**：**起草方式**（你填/我拟，谁起头）与**写法策略**（模板速填/Eval 验证，怎么写）相互独立、可叠加。
