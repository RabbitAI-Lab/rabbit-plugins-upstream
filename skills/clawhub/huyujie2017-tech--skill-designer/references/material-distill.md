# 经验蒸馏入口 — 把已发生的工作变成可设计的 skill

> **分工判据（一句话）**：**对象还是不是 skill**？
> 是一个**现有 skill** 值得学 → 走**外部样本设计切片**（见 [`example/design-blocks/README.md`](../example/design-blocks/README.md)）；
> 是**一段经验 / 一份材料**想变成 skill → 走本入口蒸馏。
>
> **在流程里的位置**：本入口是①概念讨论的**前置子流程**。走完得到「合格的候选单元」后，回到 B01 主流水线正常推演 10 格——**它不替代主干，只负责把材料筛干净再喂进去**。

---

## 一、何时走这条入口

**触发信号**（命中任一）：

- "这次项目跑通了，沉淀一下" / "把这个复盘做成 skill" / "我做了 XX，能变成 skill 吗"
- ①概念讨论时用户**一次丢入多份资料**（对话记录 / 复盘 / 日志 / 交付物）
- 用户描述里已含"我上次是这么干的""我们团队一直这么做"C10 命中且资料**含多个闭环**

**不走**（反面信号）：

- 用户只是描述一个想法、没有任何已发生经验 → 直接进主流水线
- 想学某个**现有 skill** 的优点 → 走外部样本设计切片（不进本入口）

---

## 二、Step 1 · 切经验单元

以**一个完整的「问题 → 判断 → 行动 → 验证」闭环**为单位。一份材料通常藏着 **3–7 个**候选单元。

| 规则 | 做法 |
|------|------|
| **优先选** | 经过真实运行 / 发布 / 安装 / 用户验收的经验 |
| **暂不提升** | 单次灵感、纯技术兴趣、只含内部背景的内容 |
| **合并** | 同一用户结果、共享上下文与验收的不同渠道 / 项目 → 合成一个单元 |
| **拆分** | 验收方式不同、用户结果不同 → 拆成多个单元 |

> **心法**：**别把整包资料当成一个 skill**。最常见的失败，是把三个月的项目日志一次性做成一个臃肿的 skill——边界模糊、触发词写不出来、验收无从下手。

---

## 三、Step 2 · 蒸馏五问（逐单元问）

| # | 问题 | **答不上来说明什么** |
|---|------|---------------------|
| 1 | **结果是什么？**（用用户能判断的结果表达，**不写内部工具动作**） | 还没想清楚交付什么 → **继续蒸馏** |
| 2 | **为什么有效？**（抽出稳定判断、顺序和约束，**不复述全部调试过程**） | 只是运气或一次性巧合 → **归档** |
| 3 | **哪些会变？**（渠道 / 模型 / 路径 / 品牌 / 项目名） | 可变项即**配置项**——**不要**为它们各拆一个 skill |
| 4 | **哪里会失败？**（失败信号 + 恢复路径 + 最终验收） | 说不出失败信号 → **继续蒸馏**；⚠️ **"编译成功"不等于交付成功** |
| 5 | **什么必须留在边界内？**（人名 / 客户数据 / 密钥 / 专有规则 / 作者环境） | 答不上来就默认"全部私有"，先脱敏再谈别的 |

> **与 B02「动作五问」的分工，顺序不可颠倒**：
> **先蒸馏五问**（定价值与不变量）→ **再动作五问**（挖流程具体怎么干，见 designer-guide B02）。
> 顺序颠倒会得到"流程很细但边界模糊"的 skill——那正是返工的主要来源。

---

## 四、Step 3 · 提升决策四结论

| 结论 | 判据（须全满足） | 下一步 |
|------|-----------------|--------|
| **创建** | 用户结果、边界、验收、证据**均清楚** | 回主流水线 **B01**，正常推演 10 格 |
| **继续蒸馏** | 缺真实验收 / 核心判断 / 可移植边界 | ⛔ **不出方案**。补证据后再判一次 |
| **合并** | 只是另一个渠道 / 参数 / 阶段的差异 | 进「改进已有 skill」分支（designer-guide §七诊断先行） |
| **归档** | 只能服务一次性项目上下文 | 写成项目文档，**不做 skill** |

> **「继续蒸馏」是本入口最重要的刹车**。材料不够时明确停住，比硬出一个粗版方案再返工划算得多——这与本 skill 一贯的「实证项不代填」是同一条原则。
>
> **引擎侧已接通（v3.3.0）**：`materials` 已进 `infer_design` 的信号扫描（模式 / archetype / 触发词）与 BR-5 A 维证据（有真实材料 → 触发可辨有锚定证据）。但引擎只做**关键词存在性**判定——喂入的应是蒸馏后的**匿名摘要**（Step 4 产物），别把整包原文塞进 C10，塞原文只会引入噪声信号。

## 五、Step 4 · 证据层 → 产物层（脱敏口径）

```
证据层（可回溯、留本地）              产物层（进蓝图 / 可分发）
├─ 人名、客户信息              ✗ 不进
├─ 项目代号                   ✗ 不进 → 改为「某 X 类项目」
├─ 私有路径                   ✗ 不进 → 改为 <本地参考目录>/...
├─ 访问凭据 / 密钥             ✗ 不进
├─ 临时聊天细节               ✗ 不进
└─ 经验的**匿名摘要**          ✓ 进 → 写入 01-条件 的「证据来源」字段
```

**写入格式**：`证据来源：<时间> <场景> 实测 <N> 例（成功/失败/边界），已匿名化`

这个字段有两个用处：

1. **可回溯**——事后能查到这条设计当初凭什么这么定；
2. **供 B09 打分**——BR-5 要求"每一维的证据在哪一格"（`designer-guide.md` B09 增强项），有了它就不必打分时才临时找证据。

> **为什么要有专门字段**：隐私靠**架构隔离**保证，不靠"记得不写"。给脱敏证据一个正当的存放位置，才不会有人为了留痕而把原文塞进 description。

## 六、反模式（出现即停）

1. 把每个 bug、文件名或项目名称直接命名成一个 skill
2. 聊天里的背景信息泄漏进蓝图的名称 / description / 示例
3. 只写"自动化"，没有输入、输出和验收
4. **因为技术实现复杂就拆成套件（suite），而每个阶段并没有独立用户价值**
5. 因为一次成功就忽略失败恢复与边界
