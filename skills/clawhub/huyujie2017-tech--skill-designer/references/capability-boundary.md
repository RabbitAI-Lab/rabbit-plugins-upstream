# 能力边界（Capability Boundary）— 单一权威源

> 本文件是 skill-designer 的**能力边界专页**。
> 定位：把散落在 description / 何时不使用 / Error Handling / FAQ / fix-toolbox 的边界信息**收口到一页**，其余位置只留速览 + 指向本页。

---

## 一句话总边界

> skill-designer 只做一件事：**把"创建 / 改进 skill"的念头，引导成一份可交接的施工蓝图**。落地施工交给兄弟 skill skill-creator。
> 凡"要创建 / 改进一个 skill、怎么设计它"都归它管；凡"已装 skill 的安装 / 体检 / 推荐 / 调度"都不归它管。

---

## 边界矩阵（做 / 不做 / 交别人做）

| 类别 | 场景 | 归属 |
|------|------|------|
| ✅ 做 | 从零创建 skill（需求模糊，要引导） | 本 skill |
| ✅ 做 | 改进已有 skill（诊断先行） | 本 skill |
| ✅ 做 | 要技能蓝图（需求规格书）作为下游输入 | 本 skill |
| ✅ 做 | 用 skill-creator 写/改时，要一次轻量设计把关 | 本 skill（软提示） |
| ❌ 不做 | 安装 / 推荐 / 体检 / 调度**已安装** skill | 交技能生态管家类 |
| ❌ 不做 | 一次性脚本、单点小助手（无复用价值） | 引导"不做"，转 Rule / 脚本 / MCP |
| ❌ 不做 | 闲聊 skill 概念、无创建意图 | 直接对话，不启动引导 |
| ⚠️ 灰区 | 用户说不清"要不要做成 skill" | 先跑 Phase 0 三问 + 准入四问判定 |
| ⚠️ 灰区 | 带已验证经验来，但说不清验收方式或可移植边界 | **继续蒸馏**——先补证据，**不出方案**（[material-distill.md](material-distill.md) §四） |
| ⚠️ 灰区 | 材料里只是渠道 / 参数 / 阶段的差异 | **合并**进已有 skill（走"改进"分支），不新建 |
| ❌ 不做 | 只能服务一次性项目上下文 | **归档**为项目文档（不是 skill）——给"不做"一个正当出口 |

## 边界判断决策树（核心，解决"不确定能不能用"）

```
用户表达一个念头
   │
   ▼
Q1 是不是"创建 / 改进 skill"相关？
   ├─ 否 ──────────────→ 不用本 skill（闲聊 / 管理已装 skill / 纯任务）
   └─ 是 ↓
Q2 有没有跨场景复用价值？（换个场景 / 换个人还能用吗？）
   ├─ 否 ──────────────→ 引导"不做 skill"（转 Rule / 脚本 / MCP；只服务一次性上下文 → **归档为项目文档**）
   └─ 是 ↓
Q2.5 带的是**已验证经验**吗？材料够不够？（有真实验收 + 说得出可移植边界）
   ├─ 是且够 ──────────→ 先切经验单元（[material-distill.md](material-distill.md)），合格单元 ↓
   ├─ 是但不够 ────────→ 判「继续蒸馏」：补证据后再判，⛔ **不出方案**
   └─ 否（纯想法） ────→ 直接 ↓
Q3 需求是否已清晰到能直接交给创建类 skill？
   ├─ 清晰 ────────────→ 软提示一次（可选出蓝图），不强拦
   └─ 模糊 ────────────→ 本 skill 主战场：走蓝图
Q4 是"创建新"还是"改进已有"？
   ├─ 创建 ────────────→ 主流水线 B01–B10
   └─ 改进 ────────────→ 诊断先行分支
```

## 灰色地带处理原则

> 拿不准时，**不猜**。先问一句：
> "你是想**问 skill 设计方法**，还是想**实际做一个 / 改一个 skill**？"
> 前者直接答，后者进 Phase 0。宁可多问一句，不要误启引导或漏掉把关。
