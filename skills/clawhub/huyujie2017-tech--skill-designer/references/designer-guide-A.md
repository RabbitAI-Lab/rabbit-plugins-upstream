# 引导话术库 A — Phase 0 + B01–B06

> 拼装定位：**① 想清楚（B01–B02）→ ② 定下来（B03–B04）→ ③ 画出来（B05–B06 前半）**。每格含 MVP / 增强 / 追问方向 / checklist+产物 +「拼完能决定什么」。

## 一、Phase 0 出发前确认三问

**开场**："开工前先拼第 0 块——三问对齐，跳过是最大的时间陷阱。"

| 三问 | 话术 | 说明 |
|------|------|------|
| **平台** | "这个 skill 在哪里跑？（桌面 / CLI / 某个框架 / 不确定？）" | 用"在哪里跑"反推平台，决定 allowed-tools、路径、字段差异 |
| **入口** | "创建一个新的，还是改进一个已有的？" | 从零建 vs 诊断先行，起点不同 |
| **通道** | "想要轻量 MVP（约 30 分钟）还是完整版（约 2 小时）？" | 呼应"增量优于全量"，先最小闭环可升级 |

- **增强问题**：已确定的技术栈/依赖/模板？期望今天做完还是多轮打磨？
- **追问方向**：用户说"不确定平台"→ 追问"你最常在哪用这类工具"；想改已有 skill → 切诊断先行分支（designer-guide-B §七）。
- **checklist / 产物**：☐ 三问有明确答案且用户确认（三句话小结+"对吗"）☐ 入口为"改进"时已切诊断分支 → 蓝图 index.md 头部字段（平台/入口/通道）。

**双回路注入（复盘回路·启动项，B01 之前）**：
- **内部循环**：读 [`lessons.md`](lessons.md) 经验库，取与当前任务最相关的 TOP 3 规则（按触发格+触发信号匹配），口头提示（一句话一条，不阻塞）；引导中命中某条规则的触发信号时先讲规则再继续；引导结束若某条实际影响了决策 → 引用计数 +1（**机器写回：`check_blueprint.py <蓝图目录> --tick-lesson L1,L4`**）。
- **外部循环**：同一时机读 [`design-blocks-library.md`](design-blocks-library.md) 的 B0X 聚合索引（或 [`blocks/design-blocks-b0X.md`](blocks/design-blocks-b01.md) 对应分片），按已粗判的模式/画像取命中的条目 **TOP 2**，口头提示"有个 skill 在这一点做得很好：……"（不阻塞；用户拍板是否采纳）；命中某条目的触发信号时先讲该亮点再继续。

## 二、探积木链六问（含信号翻译表）

**为什么需要**：不能问用户"你的积木链是条件还是事实"——那是类型概念。用**自然语言提问**探测结构特征，内部映射到设计模式，**不向用户暴露类型概念**。

| # | 自然提问（对用户说） | 探什么 | → 交互模式 | → 内容模式 |
|---|---------------------|--------|-----------|-----------|
| 1 | 一次干完出结果，还是分几步、中间需确认/调整？ | 流程节奏 | Pipeline | A 流程配方 |
| 2 | 主要调外部（API/文件/DB），还是靠推理判断？ | 执行性质 | Tool Wrapper | C 工具编排 |
| 3 | 产出标准化东西，还是灵活应对？ | 产出模式 | Generator | D 模板渲染 |
| 4 | 做之前先聊一圈搞清情况，还是直接跑？ | 交互模式 | Inversion | 依任务定 B/E 等 |
| 5 | 检查/评审已有东西，还是从零生成？ | 输入物 | Reviewer | E 带自检（评审侧） |
| 6 | 最复杂一步会嵌套分支吗？ | 内部分支 | Pipeline（复杂度↑） | A + 分支决策树 |

**使用原则**：用户已说清的跳过；**组合信号比单信号可靠**（Q1+Q5 = Pipeline + Reviewer；Q2+Q5 = Tool Wrapper + Reviewer；Q4+Q1 = Inversion + Pipeline）；不归约到"唯一类型"，记在心里，B03 给对应检查要点。最终处方在 B03 由设计师给出、用户拍板。

## 三、写法策略二选一 + 三层加载量化

通道确认后，进一步选"怎么写"（与「起草方式：你填/我拟」是独立维度，可叠加）：

| 写法 | 适用 | 做法 |
|------|------|------|
| **模板速填** | 已知需求、想快速产出 | 用 [blueprint-template.md](blueprint-template.md) 直接填 → 快速出草稿 |
| **Eval 验证** | 高价值、需证明有效 | 先写 eval baseline → 写最小 skill → 迭代到新分严格优于 baseline |

**三层加载量化**（说服用户"为什么要精简 body"）：Metadata ~100 token（Tier1 召回）｜ SKILL.md body < 5K（Tier2）｜ references 按需无限（Tier3）。**"经验上约 85% 的初始 context 开销可通过分层消除（经验值）"**——所以"description 写好 + body 精简"是两个最高 ROI 动作，细节拆 references，body 只留主流程。

## 四、B01–B06 逐格问题库（前半程）

> 每格 = MVP（非答不可）/ 增强（可选深挖）/ 设计师追问方向 / checklist+产物 + **拼完能决定什么**。设计师追问用自然语言，不暴露积木类型概念。

### B01 条件积木 — 该不该做

- **开场**："第 1 块，**①想清楚**——这个 skill 到底该不该做。"
- **MVP**："这个 skill 解决什么人的什么问题？" "边界在哪——它做什么、**不**做什么？"
- **增强**："如果只能解决一件事，是哪件？"（找核心）"谁会用它、多久用一次？"（复用检验）
- **追问方向**：回答太宽就追问"想象一个具体的人在什么场景打开它"；过准入四问（形态合规 / 非元信息 / 可链接 / 复用检验）。
- **checklist / 产物**：☐ 准入四问通过 ☐ 结论明确（做/不做/转向）☐ 非目标清单已确认（③ 收尾）→ blueprint-template.md `01-条件`（含**非目标清单**字段）
- **拼完能决定**：✅ 进不进主流水线；B02 画像的范围与 B07 生态位讨论的锚点。

### B02 事实积木 — 上下文画像

- **开场**："还在**①想清楚**——把用户画像和生态位摸清。"
- **MVP**："用户是谁、在什么场景下会打开它？" "生态里已经有什么 skill？会不会跟它重叠？"
- **增强**：环境/平台约束（离线/在线、权限、数据源）？依赖哪些外部工具或数据？
- **前置（带已验证经验时）**：若用户带来的是**已验证经验**（复盘 / 历史任务 / 一次丢入多份资料），**先过蒸馏五问**（见 [material-distill.md](material-distill.md) §三：结果 / 为什么有效 / 哪些会变 / 哪里会失败 / 什么留边界内），**再挖下方动作五问**。⚠️ **顺序不可颠倒**——先定价值与不变量，再定流程动作，否则会得到"流程很细但边界模糊"的 skill。
- **专家经验萃取**（完整通道 / 有领域经验可挖时，**高价值**）："能给我 **3–5 个真实案例**吗？成功的、失败的、信息不足的、边界的各来一个。" **别问"你的方法论是什么"**（会得到经验散文），改问具体动作五问：

  | 追问 | 产出喂给哪格 |
  |------|------------|
  | ① 你拿到材料**先看哪里**？ | → B07 Workflow 第一步 |
  | ② 什么信号会让你**停下来追问**？ | → B04 澄清协议 / B05 分支判断点 |
  | ③ 哪些错误是**新人常犯**的？ | → Gotchas 段 / MISTAKES.md |
  | ④ 遇到**例外**你怎么处理？ | → B07 Failure Handling |
  | ⑤ 做完后你怎么**验收**？ | → B07 Validation / golden checklist |

- **独特资产挖掘**（独特性三挖之一）："你手上有哪些**别人没有**的资料可以喂进来——现成模板、历史报告、术语表、内部规范、私有案例库？"（有 → 记入资产清单，B07 第 2 步落成具体文件名；没有 → 一句话带过，不纠缠）
- **AI 受众立场**（取自 skill-creator，D-014；自此贯穿后续所有格）："记住：skill 的最终读者是**另一个 agent 实例**，不是人。"后续每格的内容取舍都多问一句"**这条它执行时会用到吗？**"——对 AI 有益且非显然的留下，给人看但 AI 用不上的舍弃；面向人的部分（白话注释 / FAQ）与指令体分层，不混写。
- **追问方向**：正交性检查——两个 skill 张成同一方向即重叠；标前置/后续/并行链路。
- **checklist / 产物**：☐ 画像清晰 ☐ 生态位与正交性已检查 ☐ 独特资产已盘点（有则记清单） ☐（完整通道）真实案例≥3 且覆盖四类 → `02-事实`
- **拼完能决定**：✅ B03 模式处方的场景依据；B07 的生态定位与独特资产清单（哪些独门资料要落成文件）。

### B03 观点积木 — 设计模式处方

- **开场**："进入**②定下来**——给这个 skill 开模式处方。"
- **MVP**："产出是标准化结果，还是灵活应对？" "一次干完，还是分几步、中间要确认？"
- **创意确认**（独特性三挖之二，**必须先于 AI 建议三件套**）："这个 skill 有没有你想注入的独特玩法、坚持的原则或个人哲学？"（例：积木哲学、特定复盘结构、独门命名法）——用户的主张先落地，AI 建议才有挂钩处，防止"按建议"批量采纳把创意淹没成默认值；有 → 写入 `03-观点` 并作为后续所有 AI 建议的约束条件；没有 → 直接进三件套，不硬问第二遍。
- **增强**：用探积木链六问（§二）补齐信号。
- **AI 建议三件套**：据六问信号查 §二 翻译表，直接给「建议模式 + 理由 + 备选」：
  > "我建议按 **Pipeline + A 流程配方**：你说分几步、中间要确认，流程配方正好带 checkpoint。备选是单步 Generator（更快，但没法中间停下确认）。回'按建议'即可。"
- **checklist / 产物**：☐ 模式已选 ☐ 依据已给出（并让用户认同"为什么是这个模式"）→ `03-观点`
- **拼完能决定**：✅ B06 拆合判断的依据；B07 结构框架选型（archetype 映射矩阵）的输入。

### B04 问题积木 — 需求澄清 + 澄清协议

- **开场**："还在**②定下来**——把没定的口径列出来，定好'没信息时怎么问'。"
- **MVP**："现在还有哪些口径没定？（每项标注：**问谁 / 何时问 / 怎么问**）" "**信息不够时，这个 skill 该怎么问？**"（澄清协议四型，逐型判定适用条件）
- **增强**："哪些问题你自己能拍板，哪些一定要问最终用户/上级？"
- **澄清协议四型**（可组合；只写"缺信息时询问用户"是不够的）：

  | 策略 | 适用条件 | 规范写法 |
  |------|---------|---------|
  | **一次性追问**（grouped checklist） | 缺多个**独立**配置项、用户容易一次补齐 | 合并成一张清单一次问完，减少往返 |
  | **逐步澄清**（one at a time） | 需求**本身模糊**、用户可能不知道专业选项、需据首轮回答定后续 | 一次只问一个，答完再定分支 |
  | **选项式**（2–4 个） | 任何需要选择处 | 每个选项**必须说明影响**，不给开放式问题 |
  | **关键假设确认** | 覆盖 / 删除 / 迁移 / 发布 / 生产环境 | **复述即将执行的动作**，等显式确认 |

- **追问方向**：把待定项分成"设计师可代答" vs "必须用户拍板"（后者的子集进 designer-guide-B §八 决策表）；每格待定项至少指定一种提问策略。
- **GATE 门禁（skill 含写入/上传/覆盖等不可逆操作时必走，DP-001 不可逆优先门禁）**："哪些操作是不可逆的？（可逆性是唯一判据）→ 逐个编成 GATE 门：检查点 + 终止动作 + 适用范围声明（如'仅上传适用，读取不受影响'）。相似但破坏力不同的操作（新建 vs 追加）→ 配信号词三分表，模糊场景**必问并列候选**。最后加一条 ⛔ 禁止软化：用户已确认后不得重复追问。"
- **checklist / 产物**：☐ 待定项已列全并标注「问谁/何时问/怎么问」 ☐ 四型已逐型判定 ☐ 归属已分 ☐（含不可逆操作时）GATE 门禁清单已编 → `04-问题`
- **拼完能决定**：✅ B05 契约的口径（哪些输入算齐了）；§八 决策表里哪些项必须用户拍板。

### B05 分析积木 — 任务分析（IPO+B 四象限）

- **开场**："进入**③画出来**——用 IPO+B 四象限把任务契约展开（只问输入/输出会漏掉流程与边界）。"
- **MVP（四象限逐项问）**：
  - **I 输入**："用户**必须**提供什么？AI **可以自己去读**什么？缺了哪一项就**不能开始**？哪些**可以默认**、哪些**必须确认**？"
  - **P 处理**："标准执行顺序是什么？哪些地方要**分支判断**？**哪些步骤必须严格执行**、**哪些允许自由发挥**？"
  - **O 输出**："最终交付物是什么？什么格式？写到哪里？**需不需要报告 / 日志 / 摘要 / 验证结果**？有**现成模板 / 样例**要贴着做吗？（独特性三挖之三：有样例 → 样例即输出事实源，B06 四要素直接抄它；没有 → 才需要自定义格式）"
  - **B 边界**："哪些情况**不属于**这个 skill？哪些必须**暂停并询问**？哪些应该**交给另一个 skill 或工具**？"
- **增强**："做错的代价有多大？哪个环节最怕出错？"（风险）"方法：脚本 / LLM 推理 / 混合？"（决定 B06 决策 2）
- **追问方向**：P 象限的"必须严格执行 vs 允许自由发挥"是**逐步骤自由度**——B03 只定整 skill 三档，这里下沉到步骤，直接决定 B06"哪些写脚本"。数字/财务/医疗类输出强调验证步骤。
- **checklist / 产物**：☐ IPO+B 四象限已逐项填出 ☐ P 象限已标出严格/自由步骤 ☐ 风险已列出 → `05-分析`
- **拼完能决定**：✅ B06 哪些步骤写脚本 vs AI 推理；B07 Failure Handling 的分支点清单。

### B06 决策积木 — 方案抉择

- **开场**："还在**③画出来**——关键决策拍板：拆合、脚本/推理分工、触发策略。"
- **MVP**："关键决策：拆成多个 skill 还是一个？哪些逻辑写成脚本、哪些让 AI 推理？触发策略是什么？" "**会不会产出文件？** 若会 → 输出文件约定四要素（见 designer-guide-B §六）。"
  > **拆合判据（一句话）**：差异是**用户结果或核心判断** → 拆；差异只是**渠道 / 模型 / 路径 / 品牌 / 参数** → **合**，并把可变项下沉为**配置项**。
  > 反模式：**因为技术实现复杂就拆成套件**——每个阶段并没有独立用户价值，拆完谁都不能单独用（详见 [skill-archetypes.md](skill-archetypes.md) §三）。
- **增强**："有没有需要你本人拍板的决策点？"（对照 designer-guide-B §八 决策表）
- **追问方向**：明确"决策者"是谁；涉及文件产出必须声明四要素，这是新手最容易漏的。
- **checklist / 产物**：☐ 关键决策已拍板 ☐ 输出文件约定（若涉及）已声明 → `06-决策`
- **拼完能决定**：✅ B07 目录怎么搭（一个 skill 还是套件、哪些文件必须存在）、输出文件四要素是否要声明。

## 五、边界补全追问（③「边界补全」固定步骤用，v3.15.0 移植姊妹分支 v4.3）

> 非目标清单确认（四步流 ③ 步骤 4）之后、落盘 checkpoint 之前执行。先注入 design-blocks-library **边界类条目 TOP 3**（T1 主题标签），再按下表对四个边界高产格逐格追问——每格产出的条目当场写入对应蓝图文件。
> **为什么**：有/无对比实证显示自动出稿边界 11 条 vs 深度人工 18 条（评审两次点名）；本步骤 + `check_blueprint` **C7 门槛**（<15 条或无易混淆正例 → WARN）把它变成机器守的底线（见条目 D-132 的回流纪律）。

| 格 | 逐格追问（对用户说） | 条目落点 |
|----|---------------------|---------|
| B01 | "除了刚才定的非目标，**还有哪些事它明确不做**？（谁来做？转给谁？）" | `01-条件` 负例 |
| B01 | "有没有**听起来像它能管、其实归别人**的场景？反过来——**听起来超界、其实该它管**的呢？" | `01-条件` 易混淆正例（防误伤，≥1 条） |
| B02 | "哪些请求会**误触发**它？靠什么信号区分？" "与生态里相邻 skill 的**分工线**画在哪？" | `02-事实` 触发边界 |
| B05 | "**哪些输入属于边界情况**——空 / 超长 / 极少匹配 / 用户取消？各怎么处理？" | `05-分析` 边界输入 |
| B05 | "什么情况下**必须暂停并询问**？什么情况**降级处理**而不是硬做？" | `05-分析` 前提降级 |
| B06 | "失败了输出什么？写到哪里？**不写敏感信息**的约定是什么？" | `06-决策` 错误输出四要素 |

三类条目模板（照此措辞写，C7 才认得出）：
