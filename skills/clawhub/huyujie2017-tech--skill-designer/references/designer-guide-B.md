## 四（续）、B07–B10 逐格问题库（后半程）

### B07 计划积木 — 施工图（三步 + 一图）

- **开场**："**③画出来**的收尾——选框架、画目录、填五段，一张施工图。"

> 施工图 = **选框架 → 画目录 → 填五段**。只画目录树是不够的——用户拿到手仍不知道 SKILL.md 该写哪几段。

**第 1 步：选结构框架 archetype**

- 问："按刚才的模式，**它更像哪一种**？（极简 / 流程 / 工具编排 / 知识密集 / 模板产出 / 全栈工程 / **套件**——覆盖多个正交子域时）"
- **查映射矩阵**：B03 已定内容模式（A–F）× 交互模式（SCK），查 [skill-archetypes.md](skill-archetypes.md) §〇 的「模式 → 结构」映射矩阵得**推荐 archetype** + 该结构的**五段侧重段**，给用户看依据。
- **AI 建议三件套**：查矩阵得推荐后给「建议 + 依据 + 备选」（示例见 designer-guide.md §一 三件套表）。用户拍板；拿不准 → 索引命中后加载 skill-archetypes.md 的选型决策表。
- 心法：**minimal 是起点不是终点**——装不下时按「先 references → 再 scripts → 再 assets」扩容，别一次上满；毕业信号见 §四（可上可下，防过度工程）。

**第 2 步：画目录骨架（文件层）**

- "目录里具体有哪些文件？"（**建议写出具体文件名**，如 `render.py` / `style-rules.md` / `月报.xlsx`——结构图会自动把它们画成子节点）
- "哪些逻辑写脚本、哪些放 references、哪些放 assets？"（三层渐进披露，见 designer-guide-A §三）B02 挖到的**独特资产逐一对号入座**——独门资料成 references、样例成 assets、固定动作成 scripts。
- 大 reference 预案（D-073）："会有超过约 1 万词的大 reference 吗？→ 是 → 在 SKILL.md 路由条目旁**内嵌 grep 检索模式**（索引管发现，grep 管检索，不加载全文）。"

**第 3 步：填 SKILL.md 五段章节骨架（内容层，本格核心）**——逐段问、逐段填，**不能只写"见目录"**：

| 段落 | 问什么 |
|------|--------|
| `## Workflow` | "标准执行顺序是什么？（≤7 步，每步一句话，含分支与收尾）" |
| `## Clarification Protocol` | "四类提问策略各用在什么情况？"（承 B04） |
| `## Resource Routing` | "命中什么信号 → 加载哪个文件 → 产出什么？"（**强路由**：`If… load … before …`，禁止 `see xxx.md` 式弱路由）**多模块/多功能时升级三层路由表（D-004）**：① 正向决策表 ② 易混淆消歧表（"像去哪但其实不是去哪"→ 别用什么该用什么）③ 跨模块顺序表（组合任务按什么顺序读） |
| `## Failure Handling` | "四状态（Not started / In progress / **Partial success** / Failed safely）各怎么办？升级条件是什么？怎么回退？" **脚本类加双层错误分类（D-082）**：进程级（退出码/stderr）与业务级（错误码表）分开叙述，错误码表必带"建议处理"列且写**动作**不写解释（D-084）；拒绝类失败一律 fail-with-direction（D-083："不支持 + 应该用什么替代"），把死路变指路牌 |
| `## Validation` | "完成前必查什么？（产物存在 / 退出码 / 格式校验 / 报告验证命令与结果）" |

**正文组织模式**（与 archetype 正交：archetype 管目录怎么分，模式管正文章节怎么排，可混搭——取自 skill-creator，D-072）：
- 问："正文主体按哪种模式组织？**流程型**（顺序步骤体，适合单一主流程）／**任务型**（工具集合体，每节一个独立任务）／**规范型**（标准与准则体，适合评审/风格类）／**能力型**（按子系统分章，适合套件）。默认建议：流程型为主干 + 复杂操作嵌流程；给建议+依据+备选（三件套），用户拍板。"

- **增强**："批量操作怎么记录已处理/未处理？重复运行会不会重复写入（幂等）？"
- **追问方向**：按三层加载量化（designer-guide-A §三）说服"body 精简、细节下沉"；Failure Handling 的 **Partial success** 最常被漏——必须说清"完成了什么、没完成什么"；**逐段填时按映射矩阵的「侧重段」深挖**（knowledge 型的 Resource Routing 是重头、tool 型的 Failure Handling 是重头），非侧重段可简写但不可缺失。
- **可选产物（建议生成）**：`render_structure.py <蓝图目录> -o structure.svg` → **文件结构图**（目录 + 每节点内容要点 + 五段骨架），本格最直观的交付物；`visualize_blueprint.py -o blueprint.svg` → 10 格进度图（汇报 / SkillHub 介绍页）。
- **checklist / 产物**：☐ archetype 已选定 ☐ 目录骨架已画（含具体文件名）☐ 五段骨架已逐段填出 ☐ 路由全为强路由 ☐ 步骤已排 → `07-计划`（+ `structure.svg` / `blueprint.svg`）
- **拼完能决定**：✅ 施工范围（做哪些文件）与 B08 的验收对象（拿什么真实场景跑）。

### B08 行动积木 — 验证执行

- **开场**："进入**④验一遍**——拿真实场景跑一遍，别靠感觉说'应该没问题'。"
- **MVP**："用什么**真实场景**验证？"（不是空泛测试）"有 skill / 无 skill 对比做了吗？"
- **增强**："谁来独立审结果？（人亲自审，AI 不能当自己作业的唯一判官）"
- **错误验收条（DP-002 错误即修复指引）**："逐条过脚本/文档的错误消息——每条要能回答三问：原因是什么？agent 下一步做什么？有没有替代渠道？写不出任一答案的错误消息打回重写。"
- **机器验证钩子（可执行验证优先于口头承诺）**：蓝图对象若是**本 skill 自身的维护**（改 references / 改脚本），行动证据直接跑机器——`run_user_tests.py`（24 用例回归）+ `validate_skill.py --full`，把"真实场景跑过"从口头勾选变成命令输出；一般 skill 蓝图则按 [test-playbook.md](test-playbook.md) 的触发测试 + 效果测试走。
- **追问方向**：指向 [test-playbook.md](test-playbook.md) 的触发测试 + 效果测试。
- **checklist / 产物**：☐ 真实场景跑过 ☐ 对比结果在手 ☐ 错误验收条过完（含脚本时）→ `08-行动`
- **拼完能决定**：✅ B09 E 维（验证可证）的证据——"跑过 + 对比在手"直接支撑评分。

### B09 结果积木 — 质量门

- **开场**："**④验一遍**的质量门——机器算 IQS，人工只评 BR-5 五维。"
- **MVP**（**只需人工评 BR-5，其余机器全算**）："BR-5 五维各几分：**T** 边界可信 / **R** 失败可控 / **A** 触发可辨 / **C** 结构可解 / **E** 验证可证？"
  - **不要让用户报 IQS / EVS / 综合分**——`b09_summary.py` 自动补算（IQS 机器算、EVS = BR-5 均分 ×20、综合 = IQS×EVS/100），`--json` 里每个分数都标了来源。
  - 想提前摸缺口：`check_blueprint.py <蓝图目录> --write-iqs`（待补格标注能涨哪些维度，如 `B05(涨T/R/E)`）。
- **增强**："**每一维的证据在哪一格？**"（找不到证据的维度，最高只给 2 分）"如有 SkillHub TRACE 等外部返评，是否已用 `trace_patch.py` 生成 P0/P1/P2 补丁清单？"
- **追问方向**：评分必须**指向具体改进项**，不是数字。**修复顺序**（IQS × BR-5 联动）：先补**没填的格**——优先补 `check_blueprint` 推荐的那格（能涨最多维度），再深化填得浅的格。
- **口径提醒**：BR-5 问的是"**约定了吗**"（设计期），不是"做到了吗"（发布期 TRACE 口径，见 trace-evaluation-guide.md §〇）。
- **可选产物**：`b09_summary.py` 生成 `b09-summary.svg`（蓝图完备度、BR-5 五维、前三名改进项可视化）。
- **checklist / 产物**：☐ IQS 已机器算出 ☐ BR-5 五维已出（每维有证据） ☐ 改进项已列 ☐（可选）外部返评已拆补丁清单 → `09-结果`（+ 可选 `b09-summary.svg`）
- **拼完能决定**：✅ 改进优先级（补哪格涨最多维）；蓝图是否达到可交接状态（IQS ≥ 阈值）。

### B10 复盘积木 — 双回路对抗

- **开场**："最后一块——**④验一遍**收尾，把本任务的教训变成下个任务的起点。"
- **MVP**："这轮失败/不足，归纳成什么**通用规则**？"（而非加特例补丁）"下一轮迭代点是什么？"
- **两道必答项（v3.15.0，C8 机器守底线）**：
  | 必答 | 对用户说 | 判据 |
  |---|---|---|
  | **教训 → 检查项** | "这个坑能不能写成一条**机器可判定**的检查（正则/枚举/文件存在性）？能落哪就写落到哪，不能就写『不适用 + 理由』。" | 有没有一条命令能在它再次发生时**拦住它**——没有就等于没做 |
  | **能力 → 主流程** | "本轮新写的脚本能力 / 开关，**主流程调用了吗**？" | 有没有一条命令能在需要时**自动执行它** |
  写法：按「LXX → 落点」格式写（如 `L10 → validate_skill 第 15 项`），跑 `check_blueprint.py <蓝图目录> --tick-reflow` 自动登记 lessons 引用计数 + 回流落点（幂等；写**权威源** `library/lessons.json` 并重编译，md 是生成物勿手改）。零标注 → **C8 WARN**。
- **增强**："换个比喻/换思路重写，会不会优于继续堆规则？"
- **追问方向**：防 overfit；关键改动走版本号 bump + CHANGELOG。
- **checklist / 产物**：☐ 通用规则已归纳 ☐ 迭代点已定 ☐ **晋升检查已做** → `10-复盘`
- **拼完能决定**：✅ 哪些规则晋升 [lessons.md](lessons.md)（`--tick-lesson` 机器写回引用计数）——反哺下一个任务的 Phase 0 注入。

**晋升钩子（复盘回路·出口——让 B10 从终点格变成反馈回路起点）**：B10 收尾时必问用户："本任务有没有值得沉淀进经验库的规则？"候选规则走**四问**晋升检查（①跨任务可复用？②有明确触发格与信号？③有真实证据可溯？④**能落检查项吗**——能就当天加进 validate/check 脚本，不能写「不适用 + 理由」，见 [lessons.md](lessons.md) L10）——全过则写入**权威源** `library/lessons.json` 条目区（ID 递增）→ 跑 `python scripts/compile_library.py --write` 重编译 [lessons.md](lessons.md)（**该 md 是生成物，禁止手改**），并在 `10-复盘.md` 标注「已晋升 → LXX」；不过晋升标准的留在本格任务级存档。规则被后续任务实际引用时**机器写回计数**，两个入口：手动 `check_blueprint.py <蓝图目录> --tick-lesson LXX`，或**推荐**——B10 按「LXX → 落点」格式写回流标注后跑 `--tick-reflow`（自动提取 + 计数 +1 + 写回流落点，幂等）；长期无用自动降级归档。

## 五、description 环节：五件事 + 关键词覆盖五维

到 B06/B07 涉及 description 设计时，按"五件事"引导（SAP 升级版）：

| 件 | 内容 | 关键点 |
|----|------|--------|
| ① **WHAT** | 1-2 句具体功能 | 第三人称，非 "I can…" |
| ② **WHEN** | 触发场景 + 5-10 个具体说法 | "Use when…" + 触发词 |
| ③ **NEGATIVE BOUNDARIES** | 3-5 个易混场景 | "Do NOT use for: …" |
| ④ **LANGUAGE MATCH** | 主体语言匹配用户提问语言；技术术语保留英文；多语言含双语兜底 | 中文用户 + 全英文 description 实测召回降低约 30–50%（经验值） |
| ⑤ **TRIGGER WORDS 边界** | 只列**主入口动作**，不列**派生菜单动作** | 判断法：问自己"用户冷启动对话时会不会单独说这句话" |

**关键词覆盖五维**（让触发词写得更全，skill-improver）：核心词（领域主名词，"Excel 报表"）｜同义词（"电子表格 / spreadsheet"）｜场景词（"月度报表 / 财务报表"）｜口语表达（"帮我做张表"）｜中英混杂（"生成 excel"）。

**强触发句示范**（来源: chenlin-skillcreator 模板）——在 WHEN 件后加一句，提升误漏触发时的召回：

> `Make sure to use this skill whenever the user wants to <核心场景>, even if they don't explicitly say "<关键词>".`

写法注意：只加在主入口场景一句（别逐条加，会稀释）；中文用户可保留英文强触发句（触发面更广）+ 中文触发词；配合 NEGATIVE 边界防误触发。**强制阻塞**：触发词必须用户自己说，AI 不能代填，可给候选例子。

## 六、输出文件约定四要素

当 B06 决策确认**涉及文件产出**时，必须在 SKILL.md 声明 `## 输出文件约定`：

| 要素 | 问什么 | 例（Excel 报表 skill） |
|------|--------|------------------------|
| **输出目录** | 文件写到哪 | `./output/` |
| **命名** | 文件名规则 | `月报-{YYYY-MM}.xlsx` |
| **格式** | 文件格式与结构 | `.xlsx`，Sheet1=汇总，Sheet2=明细 |
| **错误输出** | 失败时产出什么 | 写 `error.log` 并返回可读错误码 |

这是新手最容易漏的一项——涉及文件产出却不说清写哪、叫什么、失败怎么办。

## 七、已有 skill 改进 → 诊断先行分支

用户入口为"改进已有 skill"时，切换诊断先行顺序（skill-improver 模式 A）：

```
加载已有 SKILL.md → 诊断（静态检查 + 画像分析）→ 输出诊断报告（🌟亮点 / ⚠️需改进 / 💡学习要点）
  → 确认改进范围（用户拍板）→ 执行：用诊断结论先填充已明确的格，
     仅对诊断发现的"缺口格"做引导对话，已达标格不重走
```

- 诊断先于动手，**先搞清楚病在哪再开药**；用 [design-blocks-library.md](design-blocks-library.md) 的"常见病症库 9 种"快速定位根因；修复后**加预防指令**（`## 注意事项`），防复发（模式 B 思想）。

## 八、决策归属：强制阻塞 + AUTO/REQUIRED 一张表

### 强制阻塞（设计师绝不代填——比"给建议"更进一步，是"用户必须自己产出"）

| 决策 | 为什么强制 | 设计师可以 |
|------|-----------|----------|
| **触发词** | 归属用户的语言直觉，AI 代填会导致召回错位 | 给例子、给方向，但字词必须用户产出 |
| **名字（name）** | 归属用户的命名权 | 三角度给候选，**用户确认** |

### AUTO / REQUIRED 统一决策表

> **决策归属**管"谁拍板"，**AUTO/REQUIRED 标记**管"要不要停下来问"。AUTO 项默默补全进草稿、小结带一句"已按经验补：……，可改"；REQUIRED 项用 AI 建议三件套问，停下等用户。

| 决策点 | 标记 | 归属 |
|--------|------|------|
| 触发词 / name | **REQUIRED** | 用户（强制阻塞） |
| 最在意做对哪一点（B5 优先级） | **REQUIRED** | 用户 |
| 流程性质（一次干完 vs 分步确认） | REQUIRED | 用户 |
| 数据源 / 依赖 | REQUIRED | 用户 |
| 输出文件约定（涉及文件产出时） | REQUIRED | 用户 |
| 非目标清单 | REQUIRED | 用户 |
| 通道（轻量/完整） | REQUIRED | 用户（Phase 0） |
| 核心原则/信念 | REQUIRED | 用户 |
| P0 修正 / 自进化采纳 | REQUIRED | 用户 |
| 通用规则（输出必填校验、Partial success 四状态、幂等防重） | **AUTO** | AI 补全（行业通用最佳实践） |
| 平台运行约束（离线/在线、权限、数据源） | AUTO | AI 先按经验默认，用户可改 |
| 目录骨架 / 工程细节（B07） | AUTO | 设计师可代劳 |
| 需求判定（B01 做/不做） | AUTO + 拍板 | 设计师建议转向 Rule·脚本·MCP，做不做用户定 |
| 设计模式处方（B03） | AUTO + 确认 | 设计师给依据 + 候选，默认"按建议" |
| 初步方案生成（我拟） | AUTO + 拍板 | 设计师起草，用户拍板/修改 |
| 验收评分（B09） | AUTO + 认可 | 设计师评（须指向改进项），用户认可 |

**用法**：提问前先扫这张表；用户喊累 / 说"你看着办" → AUTO 全采纳，REQUIRED 仍要一句确认。

## 九、起草方式与交接落地

### 起草方式选择（你填 / 我拟）

两种起草方式**都走完 B01–B10**，产物一致，区别只在"谁先起草蓝图"：

| 起草方式 | 适用用户 | 谁起草 | 体验 |
|----------|----------|--------|------|
| **你填（协作引导）** | 能说清需求、懂一些原则 | 用户主导填空，设计师追问把关 | 深度共创 |
| **我拟（主动生成）** | 说不清 / 不懂核心原则（新手） | 设计师按积木逻辑+最佳实践**先出完整方案**，用户讨论修改 | 高效降级、低门槛 |

**判断信号**：用户能答出"具体场景 + 谁用 + 打开做什么" → 你填；只会说"想做个 XX 的技能" → 我拟，并主动建议"要不要我先按经验出一份初步方案，你改？"

**我拟四步**：
1. **问核心 3–5 问**（不必全答）：解决什么？什么场景用？跑在哪？新做还是改进？最在意做对哪一点？
2. **跑 `scripts/draft_blueprint.py` 生成草稿 v1**：把回答写成 JSON 传给脚本，自动生成带 `【AI 建议】/【需用户拍板】/【待回填】` 标注的 B01–B10 蓝图文件。示例：
   ```bash
   python scripts/draft_blueprint.py ./skill-blueprint --name "月报生成" \
     --answers '{"problem":"从CSV生成标准Excel月报","scenario":"财务同事每月导CSV后快速出报表","platform":"workbuddy","entry":"create","priority":"数字准确不出错"}'
   ```
   脚本产出后逐格带用户确认：标 `【AI 建议】` 可回"按建议"批量采纳；标 `【需用户拍板】` 必须用户自己决定；标 `【待回填】` 写明触发时机。
3. **多轮流式深化设计**：每轮聚焦 1–2 格，用户改、设计师补依据，直到 B01–B10 全部有产物并写入蓝图文件。
4. **用户拍板定稿**：三句话小结 + "这份蓝图可以出施工蓝图了吗？"，确认后 `check_blueprint.py` 通过即"施工蓝图"。

### ④施工蓝图 → 交接产物 → 创建类 skill

蓝图定稿后，先跑 `scripts/export_brief.py` 生成标准化交接产物（避免人工从 11 个文件里拼装 brief），再交 skill-creator 等创建类 skill 落地。

**步骤 1**：`python scripts/export_brief.py ./skill-blueprint --output ./skill-blueprint/brief --format all`

| 产物 | 给谁看 | 用途 |
|------|--------|------|
| `brief/summary.md` | 人 | 项目小结、关键决策、验收标准、回滚约定 |
| `brief/brief.json` | 机器 / agent | 结构化摘要，供自动解析与后续流水线消费 |
| `brief/SKETCH.md` | skill-creator | 精简需求规格书，可直接作为输入 |

**步骤 2（二选一）**：
- **硬交接**：环境支持 `Skill` 调用且创建类 skill 已装时，直接 invoke skill-creator，传 `brief/SKETCH.md` + `brief/brief.json`，约定"保持蓝图设计模式与输出文件约定；触发词/name 以蓝图为准（已用户确认）；SKILL.md 正文用**指令体**（动宾开头，如'加载 X''先跑 Y'，不写'你应该'式对话体——详细施工规范归 skill-creator）；生成后进 test-playbook 闭环验证"。
- **软交接**：给用户复制粘贴段——"请用 skill-creator 依据以下施工蓝图生成 SKILL.md 与目录结构，并跑 test-playbook 验证：\<粘贴 brief/SKETCH.md 全文\> + 同上三句约定"。

**回滚约定**：蓝图是唯一事实源——创建 skill 产出偏离蓝图（改了模式、漏了输出约定）→ 回蓝图对照要求修正，不默许漂移；用户不满意 → 回对应格修订蓝图 → 重新落地，形成"蓝图 ↔ 落地"闭环。

**衔接范围**：首选 skill-creator（兄弟 skill）；改进旧 skill 可交接 skill-improver；蓝图格式中立，任何创建类 skill 都可消费。
