## §1 定位澄清：System Prompt vs Skill，与作用域

### 1.1 System Prompt 是"项目规矩"，Skill 是"可复用能力"

| 维度 | System Prompt（如 CLAUDE.md） | Skill |
|------|-------------------------------|-------|
| 定位 | 项目级全局规则、编码规范 | 特定领域能力封装 |
| 加载策略 | 会话启动**全量**加载 | 渐进式**按需**加载 |
| 生效范围 | 当前项目 | 可跨项目、跨会话（取决于作用域） |
| 上下文成本 | 恒定占用，无关任务也消耗 | 命中才加载，未命中零成本 |
| 结构化 | 单文件，扁平组织 | 多文件模块化（scripts / references / assets） |

**协同关系**：System Prompt 中规则对**所有 Skill 生效**（全局约束）；Skill 内部规则**仅在激活时叠加**（局部能力）。一个项目可同时拥有两者——System Prompt 定规矩，Skill 封装工作流。

> **设计落点**：B02 事实积木判断"在哪跑"时，应顺带厘清"哪些写进全局 System Prompt、哪些封装成 Skill"——能复用的能力优先做成 Skill，避免把领域知识塞进全量常驻的 System Prompt 撑爆上下文。

### 1.2 作用域与优先级（四级）

| 位置 | 生效范围 | 适用场景 |
|------|----------|----------|
| 企业配置中心 | 全员生效 | 强制的企业级规范与安全策略 |
| 用户主目录全局配置 | 个人所有项目 | 通用工具、个人偏好、跨项目能力 |
| 项目根目录 / `.skills/` | 仅当前项目 | 项目特定工作流、团队约定 |
| Plugin 内置资源 | Plugin 启动时 | 社区共享能力包、特定框架专用指令 |

**触发冲突优先级**：`企业策略 > 个人配置 > 项目配置 > Plugin 内置`。

**设计落点**：Phase 0 平台确认时一并确认作用域；若用户要把某个 skill 做成"公司强制规范"，应放进企业级作用域；个人通用工具放用户主目录；项目约定放项目目录。不要让项目级 skill 和企业策略打架。

## §2 Frontmatter 标准字段全集（E1）

> 这是 Agent Skills 开放规范（已被 Claude Code / Cursor / Copilot / Gemini CLI 等 40+ 产品采纳）的字段约定。本指南的自定义字段（`name-zh` / `display-name` / `stability` / `agent_created` 等）是 WorkBuddy 宿主的**扩展字段**，与标准字段**双轨并存**，互不冲突。

### 2.1 必填字段

| 字段 | 约束 | 用途 |
|------|------|------|
| `name` | ≤64 字符；小写字母 / 数字 / 连字符；不能以连字符开头或结尾；省略则用目录名 | Skill 唯一标识符，也是文件夹名 |
| `description` | ≤1024 字符，不能为空；省略则用 SKILL.md 正文首段 | 触发核心——Agent 靠它判是否激活（详见 P8 description 五件事，本文不重复） |

### 2.2 可选字段（按用途分组）

> 来源补全：对照 Claude Code 最新 frontmatter 规范（OSINT 交叉验证），在原有字段基础上补齐 `disallowed-tools` / `effort` / `paths` / `background` / `shell` / `arguments`。

| 分组 | 字段 | 类型 / 取值 | 用途 | 何时用 |
|------|------|-------------|------|--------|
| 入口提示 | `argument-hint` | 字符串，如 `[源目录] [输出格式]` | 在 `/` 菜单显示参数格式 | 需用户显式传参的 skill |
| | `arguments` | YAML 列表，按序映射 | 命名位置参数，供 `$name` 替换 | 需位置参数传入的 skill |
| 权限控制 | `disable-model-invocation` | bool | `true`=禁止模型自动触发，仅手动 | 危险 / 须用户主动调用的 skill |
| | `user-invocable` | bool | `false`=用户不能直接调，仅模型自动 | 纯后台辅助 skill |
| | `allowed-tools` | 工具名列表，如 `Read, Grep, Write, Bash(python:*)` | 工具白名单，精确控制可调用的工具与权限范围 | 所有涉及工具调用的 skill（见 §4 级联） |
| | `disallowed-tools` | 工具名列表 | 从可用池移除的工具（如自治循环禁 `AskUserQuestion`）；**不能移除 `EndConversation`** | 需禁用交互/危险工具时 |
| 运行时 | `model` | 模型名，如 `haiku`/`sonnet` | 指定该 skill 使用的模型；简单任务用 Haiku 提速度降成本 | 任务简单、想省 token |
| | `effort` | `low`/`medium`/`high`/`xhigh`/`max` | 覆盖当轮 effort 级别 | 需调节推理强度时 |
| | `context` | `fork` | 在隔离子智能体中执行，不污染主对话上下文 | 长流程 / 重上下文 skill |
| | `agent` | `Explore`/`Plan`/`general-purpose`/自定义 | 子智能体类型，配合 `context: fork` | 需要隔离执行的 skill |
| | `background` | bool | 仅配 `context: fork`；`false`=当轮等待结果而非后台运行 | fork 后台执行时（默认 `true`） |
| | `hooks` | PreToolUse / PostToolUse 等 | 生命周期事件钩子 | 需在激活期定义事件处理的 skill |
| | `shell` | `bash`（默认）/`powershell` | `!command` 与 ` ```! ` 围栏所用 shell | 用了 `!command` 动态注入时 |
| 路径 | `paths` | glob 列表，如 `["src/**/*.py"]` | 限制自动激活的文件范围 | 仅编辑特定文件时触发 |
| 版本 | `version` | semver，如 `1.0.0` | 版本控制与迭代追踪 | 所有 skill（配合 P33） |

> **触发词字段注意**：`trigger_terms` 是 SkillHub 等分发平台的**目录字段**，Claude Code **运行时不识别**——触发词应写进 `description`（核心触发）+ `when_to_use`（附加上下文 / 示例请求，追加计入预算）。运行时识别的触发载体是 `description` + `when_to_use`。

### 2.3 动态上下文注入（`!command` 语法）

Claude Code 支持在内容发送给 Claude **之前**执行命令并替换为输出（预处理，非 Claude 执行）：

- **行内**：`` 当前 git 分支：!`git branch --show-current` ``（仅行首或紧接空白后识别）
- **多行**：```` ```! `` 围栏代码块
- **性质**：预处理执行一次，输出以纯文本替换，不再二次扫描 `!command` 占位符
- **关闭**：settings 设 `disableSkillShellExecution: true`（不影响 bundled/managed skills）
- **shell 选择**：用 `shell` frontmatter 字段指定（`bash` 默认 / `powershell`）

**用途**：运行时动态获取环境信息（git 状态、文件列表、环境变量、日期），让 skill 上下文更精准、避免硬编码。

> **安全边界（P32 级联）**：`!command` 会执行命令——只应使用可信、只读、确定性的命令（如 `git status`、`date`）；禁止从外部 URL 拉取内容再执行。列入安全审查（test-playbook §八）范围。

**示例（标准 + 扩展双轨）**：

```yaml
---
name: my-skill
description: 为用户提供 XXX 能力，支持 A / B / C 操作。当用户提到 XXX、YYY 等场景时触发。
argument-hint: "[意图: 创建 / 改进 skill]"
allowed-tools: [Read, Write, Edit, Glob, Grep, Bash, Skill]
model: sonnet
version: 1.0.0
# ↓ WorkBuddy 扩展字段（标准规范之外，宿主识别）
name-zh: 我的技能
display-name: My Skill
stability: beta
agent_created: true
---
```

## §3 SKILL.md 路由器范式（E4）+ 知识分层阈值（E5）

### 3.1 SKILL.md = 路由器，不是知识仓库

**核心**：SKILL.md 正文职责是"分发任务到正确的模块"，而非包含全部业务细节。经验上限 **≤500 行**（约 2000–3000 token），这是单个 Skill 激活后合理的上下文开销。

**引用契约（强制）**：在 SKILL.md 中引用辅助文件时，不能只给路径，必须建立契约 = **触发时机 + 资源位置 + 预期产出**。

```
# ✅ 最佳实践：SKILL.md 是路由器
## 意图路由表
| 场景示例          | 路由模块   | 加载文件                       | 预期产出            |
|-------------------|-----------|-------------------------------|---------------------|
| "创建实验"        | creator   | modules/creator/creator.md    | 创建参数收集清单     |
| "实验XX调流量"    | modifier  | modules/modifier/modifier.md  | 调流量执行计划       |

## 全局安全红线
1. 禁止调用万能工具（如裸 HTTP）
2. 禁止编造数据
3. 各模块限定接口白名单（见各模块 tools.md）
```

> 这正好对应本指南"三层渐进披露（P11）"——body 精简、references 按需。本文补的是**路由表 + 契约**的具体范式。

### 3.2 知识分层阈值（经验法则 E5）

**何时拆文件**（量化信号）：
- 单个文件 **>300 行** → 拆；
- 某个 **Step 的规则 >100 行** → 拆。

文件太长不光浪费 token，还会让 Agent 的注意力在大段文本中迷失。

**如何组织（按使用频率分层）**：越频繁用到的知识离入口越近；越偶尔查阅的越往深处放。

```
trade-ab-skill/                       ← 频率决策树：这个知识每次都用？
├── SKILL.md                          ← 意图路由表 + 全局安全红线（每次激活必读 = 最高频）
├── modules/creator/creator.md        ← 创建流程 Step 编排（进入创建模块才读 = 中频）
│   ├── collect-phase.md              ← 参数填充 11 项清单（仅 Step 2 才读 = 低频）
│   ├── validate-phase.md             ← 校验规则（仅 Step 3 才读 = 低频）
│   ├── tools.md                      ← MCP 接口白名单（调接口时按需 = 最低频）
│   └── safety.md                     ← 安全约束细则（validate 阶段按需 = 最低频）
```

**分层决策树**（实践可用）：
1. 这个知识**每次激活都要用**吗？→ 放 SKILL.md 顶层（路由表 / 红线）。
2. 只在**进入某模块**才用？→ 放该模块主文件。
3. 只在**某个 Step** 才用？→ 拆成 Step 级文件。
4. 只在**调接口 / 查细节**时翻阅？→ 放 tools.md / safety.md 等末梢。

## §4 工具隔离：接口最小权限级联（E6）

> 这是工程级 Skill 最关键的**接口隔离实践**之一（注意：它管的是"工具/接口白名单隔离"，与 `test-playbook.md` §八 的"prompt 注入等安全审查"是**不同维度**，勿混淆——后者是安全审查主场，本节只讲接口最小权限）：当 Skill 涉及多模块、多 MCP 接口时，必须实施**模块级**工具隔离，遵循权限最小化级联。

**设计原则**：
1. **白名单制**：每个模块的 `tools.md` 明确列出可用接口，白名单外一律禁止。
2. **危险接口显式禁用**：万能工具（如直接 HTTP 调用）**全局禁止**。
3. **工具隔离**：不同模块用不同接口集合，防误调用。

**实践示例（trade-ab-skill）**：
- 实验**创建**接口仅在 `creator` 白名单；
- `modifier` 只能用**实验修改**接口；
- **审批 / 发布**接口在所有模块中均禁止调用；
- `modifier` 模块明确标注易混淆接口的**禁止规则**。

**与现有体系对接**：这是对 skill 级 `allowed-tools`（D-057）的**级联细化**——`allowed-tools` 管"Skill 能调哪些工具"，模块级白名单管"模块内具体能调哪些接口"。两者叠加 = 纵深防御。

## §5 脚本封装判定 + 四原则（E7）

### 5.1 何时把逻辑封装成脚本（判定标准）

> 核心理念：把**确定性计算**封装为脚本，由 Agent 调用而非自行推导。脚本是 Skill 突破 LLM 能力边界的利器。

**判定**：如果这件事让 **LLM 做有概率出错**，但让**脚本做能 100% 确定完成** → 封装成脚本。特别是——如果你发现自己在 SKILL.md 里写**公式**让 Agent 跑计算，该逻辑应挪到脚本。

| 场景 | 纯指令的局限 | 脚本的优势 |
|------|--------------|------------|
| 配置文件读写 | LLM 可能写错 JSON 格式 | 脚本保证格式正确、原子写入 |
| 环境检测 | LLM 无法可靠检测系统状态 | 脚本直接查询，返回结构化结果 |
| 日志采集 | LLM 不应直接处理网络请求 | 脚本封装 HTTP，异常自处理 |
| 复杂计算 | LLM 算术不可靠 | 脚本精确计算 |

### 5.2 脚本四原则

1. **自愈性**——脚本内部处理所有异常，始终正常退出，**绝不阻断 Skill 主流程**。
2. **结构化输出**——统一输出 JSON，方便 Agent 解析与流转。
3. **幂等性**——多次执行结果一致；预检脚本只追加缺失项，不覆盖已有配置。
4. **安全边界**——只操作指定文件，不触碰其他系统资源。

**实践示例**：`trade-ab-skill` 内置两个脚本——MCP 预检脚本（启动前自动检测 MCP 依赖是否就绪）+ 日志采集脚本（采集操作日志）。Agent 只调脚本、读 JSON，不用自己"猜"环境状态。

> **与现有体系对接**：D-113"脚本工程纪律"已讲"确定性逻辑写脚本 + 结构化输出"，本文补**完整四原则 + 封装判定**。

### 5.3 状态脚本模式（探测 + 决策一次调用，来源：tencent-docs 切片 T-A07）

> **判定**：写类操作前需要**先探查外部系统状态再分支**（读 >1 个接口才能定分支、且分支数有限）→ 把"探测 + 决策"封装成**一个状态脚本**，而不是让 agent 连调 N 个接口自己判断。

**三件套**：
1. **脚本**：单次调用完成全部探测，输出**单行机器可判定 JSON**（含 `action` + `reason` 字段）；
2. **决策表**：文档层给 `reason → 下一步` 查表，agent 按表走，不做自由发挥；
3. **上下文纪律**：明文规定"**不把原始大 JSON 写入上下文**"——agent 只消费脚本归纳后的结论。

**实例（tencent-docs `get_slide_info.sh`）**：
```json
{"action":"write_design_md","reason":"design_is_empty","slide_count":1,"w_pt":960,"h_pt":540,"design_exists":false}
```
entry.md 同时给出 reason 决策表（`ppt_is_empty → 0-1 构建` / `design_is_empty → 先写 DESIGN` / `permission_denied → 提示授权`…）。

**收益**：探测成本从"N 次接口调用 + agent 自由推理"压成"1 次脚本调用 + 查表"；分支判断从 LLM 弱项变成机器强项（呼应 §5.1 封装判定——分支判断本质是确定性逻辑）。

## §6 参数传递与动态注入（E8）

> Skill 不只是静态指令，更支持运行时参数传递与上下文预注入。多阶段之间需要可靠传递参数。

### 6.1 快照（Snapshot）机制——跨阶段参数载体

良好的参数传递应满足：**显式**（来源去向可追溯）、**可校验**（每阶段有门卡查参数完整性）、**防丢失**（关键参数在快照中持久化）。

**实践**：每个阶段将产出写入**快照**，下一阶段从快照读取；阶段**门卡**确保参数完整性（缺参不进下一步）。

### 6.2 动态注入（执行中动态获取参数）

- `businessName`：通过业务接口按当前用户工号动态查询；
- `scenarioId`：根据用户输入的业务关键词，从对照表动态匹配；
- `metricBindingBases`：固定使用指定模板展开的指标数组。

### 6.3 用户偏好持久化

成功操作后，将关键参数写入 `user-prefs.json`，下次执行时自动注入：

```json
{
  "defaultScenarioId": "<场景ID>",
  "defaultMetricTemplateId": "<模板ID>",
  "recentExperimentIds": ["<实验ID1>", "<实验ID2>"],
  "lastUsed": "2026-06-17",
  "usageCount": 2
}
```

> **与现有体系对接**：B06 决策积木的"输出文件约定四要素（P24）"定义了**产物文件**约定；本节补的是**运行期参数与用户偏好**的持久化约定。

## §7 测试第三维度 + 观测驱动迭代（E9 / E10）

### 7.1 性能对比维度（补充 test-playbook 的两层框架）

现有 test-playbook 有**触发测试**（会不会激活）+ **效果测试**（激活后质量）。本文补**第三维度——性能对比**：

> 针对同一任务，分别用"**无 Skill**"和"**有 Skill**"两种方式各跑 5 次，对比 **Token 用量**与**完成质量**。

这是验证"渐进披露经济性"的硬指标——Skill 的价值不仅在质量提升，也在"用最小上下文成本换最大知识覆盖"。

### 7.2 观测驱动迭代（E10）

> 与传统软件 bug 修复逻辑一致：发现问题 → 定位原因 → 修复文档 → 验证效果。更高效的一种迭代法是**观测驱动迭代**——通过日志埋点收集每次执行的状态（成功/失败/取消）、耗时、调用工具列表，用数据定位薄弱环节。

**实践**：`trade-ab-skill` 的日志采集采用**两阶段 traceId 配对追踪**，保障埋点可追溯。

> **与现有体系对接**：本指南已有 `BUG_LOG` 跨会话沉淀（test-playbook §五）+ 棘轮纪律（每轮只改一个维度）。本文补"**观测驱动**"思路——从埋点数据而非纯人工回顾发现薄弱环节。

### 9.3 改进点（诚实反馈，三位一体）

🌟 **亮点** —— 本文件"自身示范"闭环兑现：结构体（SKILL.md 路由器 + references 分层 + 引用契约）与它所教的一致；二级路由召回率 100%、效果判别力充分。

⚠️ **需改进** —— §4 导语称"工程级 Skill 最关键的**安全实践**之一"，该措辞可能让 router 把"防 prompt 注入"类安全 query 误路由到本文件（实则 prompt 注入防护是 `test-playbook.md` §八 OWASP 7 类的主场，§4 只讲"工具接口白名单隔离"）。建议将 §4 标题/导语改为"**工具隔离（接口最小权限级联）**"，与"安全审查"明确区分，消除误召回。

💡 **学习要点** —— 一个 reference 的"召回健康度"取决于两件事：① 二级路由的加载条件是否与主文件导航表语义对齐（本例三处表述风格不同但语义一致，属合理双受众设计，不必强改，但**未来调触发词须三处同步**）；② 边界 query（如"安全"）可能因措辞歧义导致误召回，标题用词要精确。

### 9.4 评分独立性声明

> 本次自测由本文件的**设计者**（即整合本次工程层的同一 agent）模拟 router 并评分，判定标准客观（对照加载条件表 + 每条判别力检查）。但存在**自评偏差**风险（test-playbook §四要求"独立评分防自评"）。建议：由另一独立上下文对本 §9 做一次交叉评分，尤其复核 `should_not_trigger` 中"防 prompt 注入"的误召回判定与 §4 措辞改进建议。
