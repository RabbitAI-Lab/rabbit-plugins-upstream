# 高质量 Skill 核心原则与要点（摘要汇总）

> **定位**：本文把 skill-designer 素材库中收集梳理的文章——积木哲学×技能蓝图方法论、四部分骨架、三份参考资料笔记（skill-improver / skill-creator-king / skill-assistant-pro）——中涉及**"高质量 skill"的核心原则与要点**归纳、摘要、汇总成若干条原则与概要。
> **用法**：作为 skill-designer 的"**原则速查层**"。设计师在引导/诊断/打磨时快速对照本文件判断"这条设计对不对、这个写法够不够高质量"。详细的操作话术见 [designer-guide.md](designer-guide.md)，条目库见 [design-blocks-library.md](design-blocks-library.md)，测试见 [test-playbook.md](test-playbook.md)。
> **自包含声明**：本文自包含，可随 skill 独立安装，不依赖外部链接。

## 一、核心原则（分组条目）

> 每条 = 原则名 + 一句话核心 + 落地要点。原则之间相互支撑，共同构成"高质量"的定义。

### A. 定位与价值

**P1 积木世界观** — 每一个 Skill 都是一块能力积木。
> 能力空间由 Skill 积木张成（span）；好 skill = 选对基。规划 skill 就是规划一块可链接、可复用、可衡量、可演进的能力积木。

**P2 蓝图优先** — 先出蓝图（需求规格书），再进写作。
> 蓝图是 SKILL.md 的上游，永不跳步。从模糊念头到结构化蓝图的这段"需求澄清层"是质量的根本保障。

**P3 专家知识增量** — Good Skill = 专家知识 − LLM 已知知识。
> 评估 skill 不看结构是否干净，而看注入后 LLM 的任务完成质量是否提升。只保留 LLM 不知道的专家知识、权衡、边界与决策树。

**P4 增量优于全量** — 先最小闭环跑通，再扩展。
> MVP 切片（最小积木链）→ 再扩展；轻量通道（~30min）可升级到完整通道（~2h）。

**P5 可替换不绑定** — 各积木松耦合，不硬编码。
> description / 脚本 / 模板可独立替换；skill 不绑定单一 host。产物若不符合"可替换、松耦合"，说明该积木设计有问题。

**P6 闭环即进化** — 每轮"生成 → 验证 → 人审 → 改进"是一个闭环。
> 失败案例归纳为通用规则（防 overfit）；关键改动走版本号 bump + CHANGELOG。

### B. 接口与召回

**P7 description 是接口向量** — 决定 Tier1 召回，写不好 skill 等于不存在。
> 触发词工程不只是"写得好不好看"，而是"接口向量张得准不准"。张量不准，召回必失。

**P8 description 五件事** — WHAT / WHEN / NEGATIVE BOUNDARIES / LANGUAGE MATCH / TRIGGER WORDS 边界。
> ① 具体功能（第三人称）② 触发场景 + 5-10 个说法 ③ 3-5 个易混场景（"Do NOT use for"）④ 主体语言匹配用户（中文用户+全英文 description 召回降约 30–50%，经验值）⑤ 只列主入口动作，不列派生菜单动作。

**P9 关键词覆盖五维** — 核心词 / 同义词 / 场景词 / 口语表达 / 中英混杂。
> 至少每维 1-2 个词；中文用户补中文口语词（"帮我做张表"）。

**P10 触发词是用户的** — 触发词、名字必须用户自己产出，AI 不代填（强制阻塞）。
> 归属用户的语言直觉与命名权，AI 代填会导致召回错位。

### C. 结构与组织

**P11 三层渐进披露** — SKILL.md 精简、references 按需、scripts 确定性。
> Metadata ~100 token / body <5K / references 按需无限——经验上约 85%（经验值）的初始 context 开销可通过分层消除。description 写好 + body 精简是两个最高 ROI 动作。

**P12 双维结构** — 上下分层（内部架构）+ 水平连接（生态位）。
> 上下分层回答"长什么样"（SKILL.md/scripts/references/assets）；水平连接回答"站在哪里"（前置/后续/并行链路 + 正交性检查）。

**P13 设计模式双轴** — 交互模式 × 内容模式。
> 交互结构（SCK：Tool/Generator/Reviewer/Inversion/Pipeline）× 内容组织（A-F：流程配方/领域知识包/工具编排/模板渲染/带自检/技能组合）。蓝图同时标注两轴。

**P14 五类模式 + 自由度** — 思维/导航/哲学/流程/工具，按任务脆弱度选自由度。
> 思维型重专家知识、工具型重脚本+安全；自由度三档：高（原则框架）/中（伪代码+带参脚本）/低（确定性脚本）。创意任务用死板脚本 = 自由度错配。

### D. 内容取舍

**P15 知识三分法** — Expert（保留）/ Activation（简短）/ Redundant（删除）。
> 优秀基准：Expert ≥ 70% / Activation < 20% / Redundant < 10%。判断标准：删掉后 LLM 任务表现是否下降。

**P16 Gotchas 最高 ROI** — 每条 = 症状 + 原因 + 隐含修复。
> 提前注入 Agent 自己摸索会踩的坑，省 10× 试错成本——skill 里最高价值的内容。

**P17 讲 why 不堆 must** — 少写"必须"，多解释因果。
> LLM 理解因果才能在新场景迁移；堆 must 只会机械执行。反模式"模糊警告"（"注意错误"）要改成具体的 Gotchas。

**P18 防 overfit 打磨** — 失败归纳成通用规则，而非加特例补丁。
> 换比喻/换思路重写，优于继续堆规则；每轮只改一个最低维度（棘轮纪律）。

### E. 引导与纪律

**P19 AI 助手，用户拍板** — 好用的 skill 是聊出来的，不是生成出来的。
> AI 是助手，用户拍板。每一步带着真实踩坑经验帮用户绕开陷阱。

**P20 出发前确认三问** — 平台 / 入口 / 通道。跳过是最大的时间陷阱。
> 平台（在哪跑→决定 allowed-tools）；入口（创建 vs 改进→起点不同）；通道（轻量 vs 完整→增量优于全量）。

**P21 必须用户决策清单** — 明确"哪些用户拍板、哪些设计师可代劳"。
> 名称/通道/核心原则/触发词/数据源/P0 修正/自进化采纳/输出文件约定 → 用户；设计模式/目录骨架 → 设计师建议+用户确认/可代劳。

**P22 自然语言引导（探六问）** — 不向用户暴露类型概念。
> 用自然问题探测结构（一次干完还是分步？调外部还是靠推理？标准产出还是灵活应对？先聊再跑还是直接跑？评审还是生成？有无嵌套分支？），内部映射设计模式。

**P23 小结 → 确认节奏** — 每阶段收尾三句话小结 + "对吗"。
> 全程复用，不替用户默认正确。半开放引导：固定骨架 + MVP 问题 + 增强问题 + 设计师自由追问。

**P24 输出文件约定四要素** — 涉及文件产出必须声明：输出目录 / 命名 / 格式 / 错误输出。
> 新手最容易漏的一项——写了文件却不说清写哪、叫什么、失败怎么办。

### F. 质量门与验证

**P25 准入四问** — 形态合规 / 非元信息 / 可链接 / 复用检验。
> 当疑虑时跳过，零个新积木比一堆噪音积木好。不通过 → 转向 Rule / 脚本·MCP / 根本不用做。

**P26 双维度衡量** — 内部质量（完整性/规范性/独立性/精准度/深度）× 外部价值（信息价值/时间敏感性/可靠性/关联度/复杂度）/ 100。
> 与本 skill 自有的 IQS×EVS 同构（若装有技能生态管家，口径可对齐），可打通"创建→衡量→优化"闭环。

**P27 自检先于评分** — 链接都是断的，打分没有意义。
> 交付前先过静态验证：YAML 有效 / name 一致 / 引用完整 / 逻辑连贯 / 体积守门 / description 五件事齐全。

**P28 硬性检查 vs 软性判断** — 硬性交给自动化，软性留给人/LLM。
> 硬性：YAML、name 一致性、引用完整性、体积守门（可脚本判）；软性：语义、触发命中质量、工作流合理性。诚实定位：查形式不查功能。

**P29 双测试集分工** — trigger-queries（会不会被激活）+ test-prompts（激活后好不好用）。
> 新手只测功能、忘了测触发。触发测试：should/not/ambiguous 三类 + 60/40 split + 只投喂 description + N=3 重复。效果测试：场景五分类（happy/complex/edge/negative/error）+ 功能×场景覆盖矩阵 + 判别力要求。

**P30 独立评分防自评偏差** — baseline vs with-skill 双跑 + 独立评分 + 双轨交叉校验。
> 动态分始终独立于静态分，不进主评分公式。交叉校验：静态高+动态低=摆设型（攻指令/知识增量）；静态低+动态高=干货但粗糙（先补结构）。

**P31 反馈三位一体** — 🌟亮点 / ⚠️需改进 / 💡学习要点。
> 从"挑错"变成"教学"：教用户，而不只是裁判。

### G. 安全与工程

**P32 最小化与不硬编码** — allowed-tools 最小化；密钥/token 绝不写进 skill。
> 从环境变量/配置文件读取；涉及脚本/网络/凭证时做安全审查（OWASP LLM Top 10 对齐：脚本权限/注入/网络/凭证/路径/危险操作/泄露）。

**P33 版本管理** — SemVer + CHANGELOG + stability 标记。
> 破坏性改动 bump major；新功能 bump minor；修 bug bump patch。可追溯、可回滚、供版本对比（若装有技能生态管家可自动对比）。

### G. 工程实现（来源：文章《Harness 工程之道》工程实践层）

**P34 Frontmatter 标准字段** — 采用 Agent Skills 开放规范的字段全集。
> 必填 `name`（≤64）/ `description`（≤1024）；可选 `argument-hint` / `disable-model-invocation` / `user-invocable` / `allowed-tools` / `model` / `context`(fork) / `agent` / `hooks` / `version`。宿主自定义字段（如 `name-zh` / `stability` / `agent_created`）与标准字段**双轨并存**，互不冲突。

**P35 路由器契约** — SKILL.md 是路由器不是知识仓库，正文 ≤500 行，引用辅助文件须带契约。
> 契约 = 触发时机 + 资源位置 + 预期产出。用"意图路由表"分发任务，业务细节下沉模块文件（呼应 P11 三层披露，补具体范式）。

**P36 模块级最小权限** — 权限最小化级联到模块：每模块 `tools.md` 白名单 + 危险接口全局禁用。
> skill 级 `allowed-tools` 管"能调哪些工具"，模块级白名单管"模块内具体接口"，叠加 = 纵深防御（呼应D-057）。

**P37 脚本四原则** — 确定性逻辑封装脚本；脚本遵循自愈性 / 结构化输出 / 幂等性 / 安全边界。
> 判定：LLM 做有概率出错、脚本能 100% 确定 → 封装。在 SKILL.md 写公式让 Agent 跑计算 → 挪脚本（细化D-113）。

**P38 参数快照与偏好持久化** — 长流程用 Snapshot 跨阶段传参 + 门卡校验；成功写 `user-prefs.json` 下次注入。
> 参数传递须显式 + 可校验 + 防丢失；与 P24 输出文件约定互补（P24 管产物，本节管运行期参数与偏好）。

**P39 知识分层阈值** — 文件 >300 行或单 Step >100 行即拆；按使用频率分层（频繁→近入口）。
> 频率决策树：每次必用→SKILL.md 顶层；进模块才用→模块主文件；某 Step 才用→Step 级；调接口才查→末梢。把 P11 概念补成量化阈值。

**P40 作用域优先级** — 明确 System Prompt 与 Skill 分工 + 四级作用域（企业 > 个人 > 项目 > Plugin）。
> System Prompt 全量常驻定规矩，Skill 按需加载封装能力；能复用的能力优先做 Skill，避免撑爆全局上下文。

## 二、核心要点概要（主题速查）
