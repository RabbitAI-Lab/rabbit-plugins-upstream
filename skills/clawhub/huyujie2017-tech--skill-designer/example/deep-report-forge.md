## 1. 蒸馏入口（这次不是从零开始）

### 1.1 起点：用户带来的不是想法，是一段已跑通的经验

> 用户原话：**「指定研究主题及提纲，然后细化要点，进行研究搜索，形成深度专业报告。以上任务对话过程，是一个实际例子，是私募基金税务相关的主题，可以作为例子。」**

这句话命中 skill-designer 路由表里的 **「带已验证经验来」**——入口不是 B01 概念讨论，而是 `material-distill`（经验蒸馏）。

**这一步的判据很关键**：先切**经验单元**（整段对话是 1 个完整闭环：输入提纲 → 输出可演示报告，**不拆**），再过**蒸馏五问**：

| 问 | 答 |
|---|---|
| 结果是什么 | 可直接演示/存档的深度专业报告（90KB 交互 HTML，七章 30+ 子点四层深化） |
| 为什么有效 | ①先核法规时效性 ②优先用订阅知识库 ③统一四层结构 ④骨架+分章填充 ⑤数字必复算 |
| 哪些会变 | 主题 / 提纲 / 知识库 / 口径 / 格式 → **全部抽为配置项** |
| 哪里会失败 | 检索空转、单位算错、超大写入、法规过时、盘符与授权故障 |
| 边界内留什么 | 人名、邮箱、私有路径**一律不进蓝图** |

→ **四问齐备（用户结果 / 边界 / 验收 / 证据）→ 判定「创建」**。

### 1.2 强制阻塞项：名字和触发词必须用户拍板

skill-designer 规定：**skill 名与触发词是强制阻塞项，AI 只给候选，用户拍板**。理由是 AI 代填的名字上线后可能永远触发不了。

本次用户拍板：**`deep-report-forge`** + 触发词「**按提纲出深度报告**」+ 交付默认单文件交互 HTML。

> **可复用做法**：提问时每个选项给「名称 + 为什么 + 备选」，用户回一个词即可批量采纳。

## 2. 十格蓝图定案

### 2.1 选型：为什么是 `tool` 而不是 `pipeline`

`selection_rules` 顺序匹配，**第 2 条「有外部 API/工具调用」先命中**（依赖 ima 知识库 MCP 与 WebSearch），所以 archetype = **tool**，又融合了 pipeline 的 checkpoint 与 template 的渲染特征。

| 项 | 定案 |
|---|---|
| archetype | **tool**（工具编排型），融合 pipeline checkpoint + template 渲染 |
| 内容模式 | A 流程配方 + D 模板渲染 |
| 组合形态 | Process + Reviewer（多阶段流水线，每阶段收尾自检） |
| 侧重段 | **Failure Handling 写四状态 + 降级路径** |

### 2.2 7 步 SOP 与两道硬门禁

```
1 接提纲+一次问齐 → 2 时效核实【硬门禁①】→ 3 四层细化 → 4 多路检索补料
→ 5 骨架+分章填充 → 6 可视化+交互 → 7 校验+交付【硬门禁②】
```

**两道硬门禁是本 skill 最大的增值点**，都来自真实教训：

| 门禁 | 内容 | 真实教训 |
|---|---|---|
| ① 时效核实 | 动手前核法规/标准有效期与**日落条款**；有重大变更必须改框架并在顶部置警示 | 原报告若不核，会建立在"私募证券基金价差免税"这一**已被新法推翻**的旧认知上 |
| ② 数字复算 | 数字**独立复算**（不复用生成时的心算） | 实测揪出累进税率表用"元"级门槛代入"万元"级金额的错误 |

### 2.3 四层深化硬约束（防各章深浅不一）

每个子点必须齐备：**概念 → 分析（法规/逻辑/计算）→ 具体内容（操作/风险）→ 详细案例（数字演算）**。

> 没有硬约束时的典型毛病：熟悉的章写很深、陌生的章两句话；有的章空谈概念没数字，有的章堆案例没逻辑。**四层就是深度刻度的量尺。**

## 3. 落地与回归实测

### 3.1 目录骨架（施工图 B07 的产物）

```
deep-report-forge/
├── SKILL.md                      # 131 行 / 581 词（五段骨架 + 四层约束 + 目录自述图）
├── scripts/
│   ├── outline_lint.py           # 提纲解析与子点计数（防漏点）
│   └── verify_report.py          # 8 项校验 E1–E8
└── references/                   # 5 份，均带四键元数据
    ├── README.md                 # 索引（含「N 行 / ~M 词」体量列）
    ├── retrieval-strategy.md     # 检索与时效
    ├── deepening-playbook.md     # 四层深化写法
    ├── html-report-template.md   # HTML 骨架与交互组件
    └── verification-checklist.md # 交付校验清单
```

**为什么不建 assets/**：HTML 报告内联 CSS/JS/SVG，assets 不进上下文，建了是负担。

### 3.2 两个脚本的设计取舍

| 脚本 | 承担 | 为什么交给脚本而不是 LLM |
|---|---|---|
| `outline_lint.py` | 提纲解析、子点计数、缺口提示 | 计数是**确定性逻辑**，LLM 数会飘 |
| `verify_report.py` | 占位/标签/重复 id/关键 id/四层抽查/覆盖度/外链/时效 | 结构校验**可机器判定**，比人眼可靠 |

脚本错误分类（A-408）：**进程级**（退出码 2，参数错误 → 打印用法）与**业务级**（错误码表 → 逐条给「建议处理动作」，**写动作不写解释**）分开。

### 3.3 回归实测：用原提纲真跑一遍

| 项 | 结果 |
|---|---|
| `outline_lint.py` 解析原提纲 | **7 章 / 25 子点**，与提纲实际一致 |
| `verify_report.py` 校验原报告 | **PASS 4 / FAIL 0 / WARN 0**（关键 id 齐全、四层通过、覆盖度 25=25、无外部依赖） |
| `validate_skill.py` | **12 过 / 0 警 / 0 败** |

> 覆盖度 25=25 这一步，**等于机器反证了当初那份报告确实完整覆盖了提纲**——回归不是为了走流程，是为了拿到这个证据。

### 3.4 实测抓出的三个真 bug（本案例最有价值的部分）

| Bug | 现象 | 根因 | 修法 |
|---|---|---|---|
| **Git Bash 路径失效** | 脚本报"文件不存在"，但文件在 | 原生 Python 不认 `/c/Users/...`，`os.path.exists` 恒 False | 脚本内置 `normalize_path()`：`/X/...` → `X:\...` |
| **章标题重复计为子点** | 7 章提纲多出 7 个假子点（32 vs 25） | for-else 里匹配到章标题后**没 continue**，落进"裸行"分支又加一遍 | 命中章标题立即 `continue` |
| **附录被按四层结构要求** | 校验器对"过渡规划专节"和"附录"报缺层 | 过滤器解包错误：`for i,b in blocks` 里 `b[0]` 取到正文首字符而非开标签 | 保持二元组整体取 `blk[0]`；并按 id 识别 `appx`/`trans` 跳过 |

> **教训**：这三个都不是"想出来的"，是**跑出来的**。回归实测的价值就在把隐性假设打回原形。

## 4. 发布前审计与上架

### 4.1 审计结果

`skill-publish-audit` 的 `audit_skill_publish.py`（10 维）：**P0=0 / P1=0 / P2=0**（唯一 P2 是 description 277 字 > 200，已精简到 173 字）。

**前置条件**：`PYTHONDONTWRITEBYTECODE=1` 已持久化到用户环境变量 → 无 `__pycache__` 再生风险（这是 skillhub 上传被拒的头号原因）。

### 4.2 ⚠️ 两套 frontmatter 契约（本案例最大坑）

**WorkBuddy 与 SkillHub 是两套解析器，不能复用同一份 SKILL.md**：

| 字段 | WorkBuddy（本地运行） | SkillHub（发布） |
|---|---|---|
| 标识 | `name` | `slug` + `displayName` + **`name`（服务端也要）** |
| description | 多行 `description: \|` 可读性好 | **必须单行**，且值内**不能出现英文冒号**（解析器取首个 `:` 分隔） |
| 包裹引号 | 双引号 | **单引号**（解析器不理解 `\"` 转义） |
| tags / triggers | 多行 `- item` 列表 | **行内数组** `tags: [a, b]`；多行列表会被**静默丢弃且无报错** |
| 额外 | — | 需 `summary`、`license` |

**解法**：不改源，用转换脚本生成**发布副本**（dist）。范式参考 skill-designer 的 `scripts/prepare_release.py`——**跨落点字段必须有唯一事实源，脚本常量只能当回退**（踩过：打包脚本把 displayName 写成常量，源里改完中文名一跑就被静默回滚）。

### 4.3 发布前最终安检（7 步）

1. 禁用文件类型扫描（`.pyc/.pyo/.so/.pkl/.DS_Store/.bak` → 应为 0）✅
2. 文件清单核对（应只留文本）→ 8 个纯文本文件 ✅
3. frontmatter 合规（无重复字段、版本号对）✅
4. 敏感信息 grep（私有路径 / 用户名 / 凭证）→ 无命中 ✅
5. 运行时缓存抽检 ✅
6. 脚本硬编码路径扫描 → 无 ✅
7. 文档结构完整性 ✅

### 4.4 上架

```bash
bash ~/.workbuddy/skills/skillhub-auto-publish/scripts/prep_and_publish.sh \
  "<发布副本目录>" --changelog "首次发布：..." --dry-run   # 先预检
# 去掉 --dry-run 正式发布
```

**结果**：`skillId=190678`，详情页 `https://skillhub.cn/skills/deep-report-forge`。

> ⚠️ **验证发布成功看 `stats.versions` 计数 +1，不要看 `latestVersion`**——社区发布走审核队列，后者有 2–4 分钟延迟，`status=None` 也属正常。本次验证：`versions: 1`，5 个 tags 全部正确落库（证明行内数组写法没被丢弃）。

## 5. 过程文件亮点切片

### 5.1 四层深化手册（references 的核心）

给每层配**合格判据**与**常见失败**，比只说"要写四层"有用得多：

| 层 | 合格判据 | 常见失败 |
|---|---|---|
| 概念 | 读者能复述含义 | 只贴定义不划边界 |
| 分析 | 有明确依据（文号/来源/公式） | 只有观点没有依据 |
| 具体内容 | 读者可照做或自查 | 空话套话 |
| 详细案例 | 数字可独立复算 | 数字模糊或**单位错** |

再配一份**四层齐全的真实范例子点**（含完整数字演算），比抽象规范有效。

### 5.2 强路由句式（Resource Routing）

不用弱路由（"see xxx.md"），一律写成条件 + 动作 + 产出：

> If 需要把要点展开为正文 → **load `references/deepening-playbook.md`** before 动手写章节正文 → 产出：四层齐备的章节内容。

配套**易混淆消歧表**（像「研究」但其实不是 → 转 deep-research 类），避免误触发。

### 5.3 可触线纪律要带显式数字

| 写法 | 机器判定 |
|---|---|
| 「授权失败一次性上报不重试」 | ❌ 不可触线 |
| 「授权失败**至多 1 次**上报，不重试」 | ✅ 可触线 |

同理：澄清**至多 2 轮**、回退**至多 2 次**、第 3 次转人工。

## 6. 六个可复制决策

| # | 决策 | 为什么跨领域成立 |
|---|---|---|
| 1 | **经验蒸馏优先于概念讨论** | 手上已有跑通经验时，从经验反推比从零空想更准、更快 |
| 2 | **把"最大教训"升级为硬门禁** | 本次两个门禁（时效核实、数字复算）都来自真实踩坑——skill 的价值 = 它能防住什么 |
| 3 | **确定性逻辑交给脚本** | 计数与结构校验让 LLM 做会飘，脚本做是确定的 |
| 4 | **回归实测用原始输入真跑** | 三个 bug 全是跑出来的，不是想出来的 |
| 5 | **发布副本不改源** | 两套契约冲突是硬约束，改源会破坏本地运行 |
| 6 | **发布成功看 versions 计数** | 审核队列延迟会误导判断，认准唯一可靠指标 |
