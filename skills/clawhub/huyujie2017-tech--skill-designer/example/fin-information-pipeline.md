## 1. 意图沟通（①概念讨论）

### 1.1 起点：一句需求里藏着八个动宾

> 用户原话（需求登记口径）：**「基金投资经理每日需广读国内外财经信息，要求：分类、重要度排序、分类型格式、影响分析、历史关联、归档、专题、统计。」**

一句话里 8 个动宾 = 8 个待拆解的功能承诺。**意图沟通的第一件事不是答应，是数清楚有几个承诺**——数漏了，后面每一格蓝图都会漏。

### 1.2 五问收口（这一步做完才有资格进②初步方案）

| 问 | 答 | 落点 |
|---|---|---|
| **为什么做**（痛点） | 信息散、看不出轻重、看过即忘、无法回溯 | B01 条件 |
| **为谁做** | 基金投资经理本人，每交易日高频使用 | B02 事实 |
| **怎么做**（流程骨架） | 采集 → 去重 → 分类 → 分级 → 影响分析 → 归档 → 专题 → 统计 → 简报 | B03 / B05 / B07 |
| **优先级**（只能保一个先） | ①**分级必须可信可复核**（反推：ADR-2 与用户「引擎判断逻辑透明」的明确要求）②**看过即忘必须解决**（反推：L6/L7 索引与专题页给了最大篇幅） | B06 决策 |
| **给个样例** | 「到新浪财经看一下招商银行的最新新闻」 | B08 验收 |

> **样例不是举例，是需求**。这条随口的样例后来直接催生了「入口 B 即时组合」（见 §1.5），把单入口设计改成了双入口。**意图沟通阶段一定要逼用户给一个真实句子**——那是需求里唯一不会撒谎的部分。

### 1.3 转折一：生态诊断把「从零建」改写成「升级」

沟通中发现生态里已有 `info-collector` v0.1.0（采集 + 去重 + 简报）。读完它的 SKILL.md 后判断：

- 需求本质是**同一 job 的向下游延伸**，不是另一个 job；
- 可复用：config / 去重索引 / 邮件回执 / automation 调度 → **复用率约 50%**；
- 结论：需求从「从零建一个新 skill」变成「升级旧 skill 到 V2」，工作量直接砍半。

> **可复制的动作**：改进意图下，**永远先读已有 SKILL.md 再谈设计**。这一步省下的不是时间，是「重复造轮子还造歪」的风险。已沉淀为 `references/lessons.md` 一条经验。

### 1.4 转折二：一次实搜推翻两个假设

真跑一遍采集后，两个「想当然」当场死亡：

| 原假设 | 实测 | 后果 |
|---|---|---|
| `site:x.com` 能限定 X 源 | **完全失效，零命中** | 检索策略改为弱限定 `fallback_keywords` |
| 去重可用「URL + 标题」双键 | 公众号源 5 条结果里 **2 条 URL 为空** | 去重改为三档降级（见 §2.4） |

> **可复制的动作**：涉及外部数据源/API 的 skill，**②初步方案之前必须做一次最小实证**。若按假设出施工蓝图，去重与检索两块设计全错，返工成本远大于实证成本。已沉淀为 `references/lessons.md` 一条经验。

### 1.5 转折三：用户追加需求 → 必须回蓝图改，不能只在产物上打补丁

| # | 追加需求 | 原设计 | 蓝图改动落点 |
|---|---|---|---|
| 决策 6 | 「到新浪财经看一下招商银行的最新新闻」这类**即时单查** | 只有定时全量轮询单入口 | SKILL.md 把入口 B 提为一等公民；**临时源/主题默认不写 config**，但走同一套去重评分，防归档库被污染 |
| 决策 7 | 公众号源 URL 常空导致去重失效 | URL + 标题双键 | 三档降级：①URL 非空→双键 ②URL 空→标题指纹+日期+源 ③仍无法判重→留 `raw/` 待人工确认，**不进简报** |

> **意图沟通的三条硬规矩**（本案例验证）：
> 1. **数清动宾**再谈方案——一句需求 = 几个承诺，漏一个后面全漏。
> 2. **改意图就回蓝图改**，绝不在产物上打补丁；产物偏离蓝图 → 回蓝图修正，不默许漂移。
> 3. **外部依赖先实证**，假设没有证据值。

## 2. 最终施工方案（④施工蓝图 → 落地产物）

### 2.1 设计定案

| 项 | 值 |
|---|---|
| 平台 / 入口 / 通道 | workbuddy / improve（升级既有 skill）/ full |
| **设计模式**（交互 × 内容） | Pipeline + Generator + Tool Wrapper × **A 流程配方 + D 模板渲染 + C 工具编排 + E 带自检** |
| **结构框架** | pipeline（九层流水线，每层产物落盘） |
| 版本 | 2.0.0（源自 info-collector v0.1.0 升级，非兼容变更） |
| 输出根 | `~/.workbuddy/fin-information-pipeline/output/` |

### 2.2 九层流水线（每层产物落盘，失败跳过不阻断）

| 层 | 名称 | 归属 | 产物 |
|----|------|------|------|
| L0 | 配置 | 脚本 | 读 4 份 config；缺失/损坏 → **停止并提示，不瞎猜** |
| L1 | 采集 | AI | WebSearch/WebFetch；每源 × 每词取前 10 条 |
| L2 | 去重校验 | 脚本 | `process_cards.py` 三档降级 |
| L3 | 分类 | 脚本建议 + AI 确认 | 7 类：news / policy / research / data / event / opinion / market |
| L4 | 评分 | 脚本建议 + AI 覆盖 | 五维加权 0–100 → **S ≥ 80 / A 60–79 / B 40–59 / C < 40** |
| L5 | 加工 | AI | 按类型套影响分析骨架；**S/A 级全量深加，B 级仅入索引** |
| L6 | 归档 | 脚本 | `cards/{YYYY}/{MM}/` + 四类索引 |
| L7 | 专题 | 脚本组装 | `topics/{slug}.md` 时间线 |
| L8 | 分发 | AI + 脚本 | 分级日报/周报 + agent-mail 推送（**回执验证**） |
| L9 | 查询 | 脚本 | 统计报表、专题回溯、S 级检索 |

> **归属列是本案例的骨架决策**：确定性逻辑（去重/分类建议/评分建议/索引/统计）**全部下沉脚本**，语义判断（采集/影响分析/覆盖评分）**留给 AI**。交界处用「脚本建议 + AI 覆盖写 `score_reason`」衔接。

### 2.3 双入口流程

**入口 A（定时流水线，6 步）**
1. **L0 读配置** → 缺失即停。
2. **L1 逐源逐主题检索**：web 源用 `{keyword} site:{site}`（`site_filter: false` 的源改用 `fallback_keywords` 弱限定）；**mcp 源按 `query_template` 对每个主题发自然语言问句**。源失败 → error.log + 跳过；连续 3 轮失败 → 简报提示停用。
3. **L2 写 raw 卡片 + 跑 `process_cards.py`**。**0 条新信息也继续**——发「本轮无新信息」简报，证明任务活着。
4. **L3+L4 跑 `classify_score.py`** → AI 复核：同意则沿用，覆盖则写 `score_reason:`。
5. **L5–L7 深度加工 + 归档**：S/A 级按类型骨架写影响分析（**事实区 / 推断区物理分区**）→ `build_index.py` 归档建索引回填 related。
6. **L8 组装分级简报 → agent-mail 推送**。发送后**必须确认回执**；失败重试 1 次 → 仍失败写 error.log 并**在对话中显式报告，绝不静默**。

**入口 B（即时组合，4 步）**
1. 解析句式「到/在 {源} 查看/看一下 {主题} 的最新{新闻\|公告\|动态}」→ 源与主题（**都可不在清单内**）。
2. 单源 × 单主题检索，走 L2–L5 同一套去重/评分/加工（临时源 tier=medium）。
3. 结果并入同一归档库（同一套索引，防污染）。
4. 对话中直接给分级卡片摘要；**不自动发邮件**，除非用户要求。

### 2.4 三条硬纪律

**① 评分双轨（脚本建议分 + AI 覆盖留痕）**
- 脚本按 `taxonomy.json` 规则算**建议分**（breadth / relevance / credibility 可规则化；intensity / urgency 默认中位值）。
- AI 可覆盖，但**必须在 frontmatter 写 `score_reason:`**——用户明确要求引擎判断透明、可复核。
- 周报抽检评分一致性；权重跑满 3 轮后按人工判定校准。

**② 事实 / 推断物理分区**（投资类 skill 的最高纪律）
- 凡涉及预测的产出，卡片强制分「关键事实（带出处）」「影响推断（标注）」两区；
- **推断区禁止出现原文没有的精确数字**——这一条把「AI 编数据」的门焊死了。

**③ 三档降级去重**
1. URL 非空 → URL 归一化 + 标题指纹双键
2. URL 空（公众号源常见）→ 标题指纹 + 日期 + 源三键
3. 仍无法判重 → 留 `raw/` 待确认，**不进简报**

**错误处理表**（施工方案必须逐条写明，不能只写「做好错误处理」）

| 场景 | 处理 |
|---|---|
| 配置缺失/损坏 | 停止 + 提示修复路径，不瞎猜 |
| 单源失败 | error.log（`{ISO时间} \| {层} \| {源} \| {错误} \| {动作}`）+ 跳过 |
| 某源连续 3 轮失败 | 简报提示「建议停用」，等用户决定 |
| 0 条新信息 | 仍产出并推送「本轮无新信息」简报 |
| 邮件失败 | 重试 1 次 → error.log + **对话显式报告** |
| 低质结果（标题党/广告） | 信源扣分 + exclude 过滤，不进 S/A |
| 单轮 error.log 新增 > 5 条 | 停止本轮，报告用户，不硬跑 |
| 用户说「停掉收集」 | 建议暂停对应 automation，不自行删除 |

**输出四要素**（涉及文件产出必填——新手最容易漏）

- **目录**：`~/.workbuddy/fin-information-pipeline/output/`（由 config 指定）
- **命名**：卡片 `cards/{YYYY}/{MM}/{date}-{type}-{slug}-{NN}.md`；索引 `index/{processed\|entity\|topic\|score}_index.json`；专题 `topics/{slug}.md`；日报 `briefing/briefing-{date}.md`；周报 `briefing/weekly-{YYYY-Www}.md`；月统计 `stats/stats-{YYYY-MM}.md`；错误 `error.log`
- **格式**：Markdown 卡片（frontmatter 12 字段）+ JSON 索引
- **错误输出**：一律 error.log + 当期简报末尾异常摘要；推送失败对话显式报告

# Fin Information Pipeline — 财经情报流水线

> 一句话定位：把"每日多源财经阅读"跑成确定性流水线——**采集 → 去重 → 分类 → 分级 → 影响分析 → 归档 → 专题 → 分级简报**。
> 蓝图是唯一事实源：`<workspace>/blueprints/fin-information-pipeline/`。产出偏离蓝图 → 回蓝图修正，不默许漂移。

## 双入口（先判断走哪个）

| 入口 | 触发 | 行为 |
|------|------|------|
| **A 定时流水线** | automation 触发，或用户说"跑一轮收集""积木消息助理" | 按 `config/` 预置的 源 × 主题 **全量轮询**，产出分级日报 + 归档 + 专题更新 |
| **B 即时组合** | "到新浪财经看一下招商银行的最新新闻""到浪潮信息网看一下中国石油的最新公告" | 解析**任意源 × 任意主题**（两者都可是清单外的），单次执行，结果并入同一归档库。**临时源/主题默认不写 config**，除非用户说"加进配置" |

1. **L0 读配置** → 缺失即停。
2. **L1 逐源逐主题检索**：web 源用 `{keyword} site:{site}`（`site_filter: false` 的源改用 fallback_keywords 弱限定）；**mcp 源（type:"mcp"）按 `query_template` 对每个主题发自然语言问句**（如妙想研报/公告通道）。源失败 → error.log + 跳过；连续 3 轮失败 → 简报提示停用。
3. **L2 写 raw 卡片到 `<output>/raw/`，跑 `process_cards.py`**。**0 条新信息也继续**——发"本轮无新信息"简报，证明任务活着。
4. **L3+L4 跑 `classify_score.py`** → 拿建议分类/建议分；AI 复核：同意则沿用，覆盖则写 `score_reason:`。
5. **L5–L7 深度加工 + 归档**：S/A 级按类型骨架写影响分析（**事实区/推断区物理分区**，推断区禁止出现原文没有的精确数字）→ `build_index.py` 归档建索引回填 related。
6. **L8 组装分级简报 → agent-mail 推送**。发送后**必须确认回执**；失败重试 1 次 → 仍失败写 error.log 并**在对话中显式报告，绝不静默**。

## 入口 B 流程（4 步）

1. 解析句式「到/在 {源} 查看/看一下 {主题} 的最新{新闻|公告|动态}」→ 源与主题（都可不在清单内）。
2. 单源 × 单主题检索，走 L2–L5 同一套去重/评分/加工（临时源 tier=medium）。
3. 结果并入同一归档库（同一套索引，防污染）。
4. 对话中直接给分级卡片摘要；**不自动发邮件**，除非用户要求。

## 评分双轨（硬纪律）

- 脚本按 `taxonomy.json` 规则算**建议分**（breadth/relevance/credibility 可规则化；intensity/urgency 默认中位值）。
- AI 可覆盖，但**必须在 frontmatter 写 `score_reason:`**——用户要求引擎判断透明、可复核。
- 周报抽检评分一致性；权重跑满 3 轮后按用户人工判定校准。

## 三档降级去重（源可用性实证后定稿）

1. URL 非空 → URL 归一化 + 标题指纹双键
2. URL 空（公众号源常见）→ 标题指纹 + 日期 + 源三键
3. 仍无法判重 → 留 `raw/` 待确认，**不进简报**

## 错误处理与停止条件

| 场景 | 处理 |
|------|------|
| 配置缺失/损坏 | 停止 + 提示修复路径，不瞎猜 |
| 单源失败 | error.log（`{ISO时间} \| {层} \| {源} \| {错误} \| {动作}`）+ 跳过 |
| 某源连续 3 轮失败 | 简报提示"建议停用"，等用户决定 |
| 0 条新信息 | 仍产出并推送"本轮无新信息"简报 |
| 邮件失败 | 重试 1 次 → error.log + **对话显式报告** |
| 低质结果（标题党/广告） | 信源扣分 + exclude 过滤，不进 S/A |
| 单轮 error.log 新增 > 5 条 | 停止本轮，报告用户，不硬跑 |
| 用户说"停掉收集" | 建议暂停对应 automation，不自行删除 |

### 3.2 B06 决策格 —— ADR 三行式 + 废弃方案表 + 输出四要素

**决策记录写法：结论前置 + 理由 + 后果**

> **决策 1：拆分 / 组合 → 合（升级 `info-collector` → V2）** ✅ 用户已拍板
> - 理由：复用现有 config/去重索引/邮件回执/automation 调度，省约 **50% 施工量**；需求本质是**同一 job 的向下游延伸**。
> - 后果：需同步更新旧 automation 的 prompt。
>
> **决策 4：归档底座 → 本地结构化目录为主 + 可选同步 Obsidian** ✅ 用户已拍板
> - 理由：零依赖、机器可查、统计快；只有被标记有价值的专题才同步，**避免噪音污染用户知识库**。
> - 后果：关联关系靠 JSON 索引维护，图谱能力在 Obsidian 侧获得。

> **ADR-2：评分双轨（脚本建议分 + AI 覆盖留痕）**
> - 决策：规则可算部分由脚本产出建议分，AI 覆盖须写 `score_reason`
> - 置信度：**85%**
> - 依据：纯 AI 评分跨天漂移、不可回归；纯规则无法处理语义。双轨兼顾稳定与灵活，且覆盖留痕可复核
> - 替代方案：纯 AI 评分（简单但不稳定）

## 4. 五个可复制决策

> 不是所有案例都要抄，但这五条跨领域成立。

1. **先诊断再设计** —— 发现已有 skill 后，需求从「从零建」变成「下游延伸」，省一半工作量。改进意图永远先读已有 SKILL.md。
2. **外部依赖先实证** —— 一次实搜推翻两个假设（`site:x.com` 零命中、公众号源 URL 常空），避免了去重与检索两块设计全错。
3. **评分双轨** —— 确定性逻辑下沉脚本，语义判断留 AI，交界处「脚本建议分 + AI 覆盖写 `score_reason`」。**AI 不单独决定重要事项**。
4. **事实 / 推断物理分区** —— 凡涉及预测的产出强制分区，推断区禁止出现原文没有的精确数字。投资类 skill 的最高纪律。
5. **产物即索引** —— 归档类 skill 的产物本身要能回溯历史，否则只是把「看过即忘」换了个地方忘。
