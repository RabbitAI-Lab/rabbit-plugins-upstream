# 设计蓝图（逆向拆解）：tencent-docs-1.0.41

> **来源**：腾讯文档官方 MCP 管理器（`<本地参考目录>/tencent-docs-1.0.41`，~100 文件）
> **采样日期**：2026-09-03
> **一句话**：把"多品类在线文档平台"的 agent 操作层做成了**三级渐进披露的路由器套件**——顶层 SKILL.md 只做意图路由 + 硬纪律，品类细节下沉到自治的 entry.md，长尾知识（边界场景/错误码/鉴权状态机）全部外置成按需读取的参考文档，并用"状态脚本 + 设计契约 + 强制校验"把 LLM 的自由发挥压进可验收的轨道。
> **配套文件**：亮点条目见 [`1-highlights.md`](1-highlights.md)，原文证据切片见 [`2-source-skill.md`](2-source-skill.md)。

## 一、功能架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  顶层 SKILL.md（路由器，~240 行）                              │
│  · frontmatter：触发关键词内嵌 description + 平台元数据         │
│  · 品类能力总表（9 种 doc_type + 推荐度）                       │
│  · 场景路由表（4 大意图 → 关键词 → 品类 → 首选方法 → 参考文档）   │

│  · 核心规则区（🚨 品类误用 / 批量写入阈值 / 降级路径）           │
```

**四个 MCP 服务的分工**：`tencent-docs`（通用：创建/管理/搜索/OCR/剪藏）+ `slide-mcp` / `doc-mcp` / `sheet-mcp`（各品类精细编辑）。工具名前缀命名空间化（`slide_*` / `doc.*` / `sheet.*` / `smartsheet.*`），四服务共用同一 Token 但 endpoint 独立。**跨品类误用被列为 🚨 顶格禁止项**，且错误码 400016 专门兜品类误用的底——路由规则与错误处理互相印证。

## 二、模块划分与职责

| 层 | 模块 | 职责 | 不做什么 |
|---|---|---|---|
| 路由层 | SKILL.md | 意图识别、品类路由、全局硬纪律、错误码兜底 | 不展开任何品类细节 |
| 品类层 | `*/entry.md` ×4 | 该品类完整工作流（状态探测→前置契约→执行→校验） | 不复述全局规则 |
| 组件层 | `component-*.md` ×12 | 单个 JSX 组件的语法规范 | — |
| 格式层 | `mdx_references.md` / `doc_format/` | 内容格式规范与模板 | — |
| 公共层 | `references/*.md` | 跨品类接口、鉴权、上云、遥测 | 不归属单一品类 |
| 脚本层 | 根目录脚本 | 封装易错/跨平台的确定性操作 | 不做语义判断 |

设计要点：**每一层都明确"不做什么"**。slide/entry.md 声明"DESIGN 的结构规范本文件不重复展开"；doc/entry.md 只有 60 行，纯粹是转发器。同一信息只在一处呈现，其余用链接引用——这正好是 skill-designer 的"重复收口 1 处"纪律的范本。

## 三、核心工作流（逆向）

### 3.1 主干：意图路由 → 品类执行 → 校验回复

```
用户请求
  │ ①先判主操作意图（创建/改写/文件管理/转换），混合意图按主操作归类、分步执行
  ▼
场景路由表查表 → 得到「品类 + 首选方法 + 参考文档」
  │ ②改写类：先判原始文档类型（file_id/链接前缀/query_file_info），严禁品类横跳
  ▼
读品类 entry.md（三级渐进披露的第 2 级）
  │ ③按需读组件/格式规范（第 3 级，"用到什么组件再读哪个文件，不要一次读全"）
  ▼
写类操作前置：状态探测（get_slide_info.sh 单行 JSON + reason 决策表）→ 写 DESIGN 契约
  ▼
执行（串行纪律 + 显式参数 + 批量接口 + 失败降级路径）
  ▼
完成后校验（页数/关键文本/顺序对账/残留空白页）→ 强制回复规范（给链接、只说四件事）
```

### 3.2 支线工作流（每条都有明文的降级路径）

| 工作流 | 通路 | 失败降级 |
|---|---|---|
| 网页剪藏 | scrape_url → scrape_progress 轮询（status 1/2/3）+ spawn 子会话防阻塞 | status=3 停止轮询 |
| 本地文件上云 | aipage_pack.js → import_file.sh → async_import → import_progress | 格式不支持由后端判定后再降级 |
| OCR | 公网图直调 ocr.*；本地图必须走 ocr.js | — |
| 鉴权 | setup.sh 三步状态机：check → 等用户确认 → fetch → 人工兜底 | 每个错误输出有对应话术与去向 |
| 编辑定位 | find 优先（有关键词）→ read 降级（找不到）→ 猜锚点 | UPDATE/DELETE 前必须先 read/find |

## 四、设计模式清单（可直接迁移复用）

| # | 模式 | 机制 | 收益 |
|---|---|---|---|
| P1 | **三级渐进披露** | 路由器 → 品类 entry → 组件规范 | token 成本按需发生，与 skill-designer 的 progressive disclosure 原则同构 |
| P2 | **目录自述图** | SKILL.md 内嵌文件树 + 每文件一句话职责 | agent 免 `ls` 猜测，一次读完全图 |
| P3 | **量化纪律** | "连续 ≥3 次写入必须批量接口"、"严禁并发、显式传 page_index" | 规则可判定，不是"建议尽量" |
| P4 | **状态脚本模式** | get_slide_info.sh 返回单行 JSON + `reason` 字段 → 查表决策 | "探测+决策"一次调用完成，agent 不读大 JSON |
| P5 | **设计契约模式** | 写类操作前必须先写 DESIGN（8 段必填结构 + 自检门禁，不满足重写） | 把审美/规格从"即兴发挥"变成可验收契约 |
| P6 | **读-改配对协议** | UPDATE/DELETE 的 id 必须来自 find/read 返回；readonly 块禁作锚点 | 杜绝"盲改"，编辑天然幂等 |
| P7 | **边界场景规范节** | ColumnList 删剩 1 列、空 Callout、表格 readonly……逐条"场景→操作→反例 JSON" | 长尾边界前置成文档，而非靠 agent 试错 |
| P8 | **鉴权三步状态机** | check → **⛔强制等待用户确认** → fetch → 人工兜底；明文"AI 注意：必须停止等待" | 把人机协作时序写成硬规则，防 agent 抢跑 |
| P9 | **错误码兜底表** | 7 码各带解决方案；VIP/积分错误直购链接闭环 | 失败路径唯一化，agent 不自创处理方式 |
| P10 | **外置 prompt 资源** | 3 个 prompt.txt + 5 个模板 JSON（schema 带 description/required/multiple） | 长 prompt 不塞 SKILL.md，按需读取，模板可独立迭代 |
| P11 | **模板库 + 四级匹配 + 反照搬** | 38 个 mdx 场景模板；精确>场景>分类>通用；"禁止照搬示例数据" | 输出质量下限抬高，又防内容抄袭 |
| P12 | **强制校验与回复规范** | 完成后页数/顺序对账；回复只说四件事 + 链接来源优先级 | 交付确定性：验收有清单，回复有格式 |
| P13 | **能力缺口静默遥测** | report_unsupported_feature（feature 动宾短语 / user_prompt 原话 / doc_type），无需告知用户 | 能力盲区持续回流给上游，无需打扰用户 |
| P14 | **SKILL OTA 自升级** | frontmatter version + check_skill_update 每日检查 | 官方 skill 的版本保鲜机制 |

## 五、最佳实践检查清单（设计新 skill 时逐条对照）

**结构与路由**
- [ ] 顶层只做路由 + 硬纪律，领域细节下沉（P1）
- [ ] 场景路由表带关键词 → 方法 → 参考文档；混合意图有归类规则
- [ ] 有负向路由（"严禁用 A 工具改 B"）且与错误码互相印证
- [ ] 文件目录自述图与实际结构一致（P2）

**规则与纪律**
- [ ] 硬规则带量化触发条件与强制动词（P3）
- [ ] 每条工作流有明文失败降级路径（不许"自行想办法"）
- [ ] 人机协作时序（等待用户确认）写成 ⛔ 硬规则（P8）

**工具与脚本**
- [ ] 易错/跨平台操作封装成脚本，输出单行机器可判定 JSON（P4）
- [ ] 写前探测 + 读-改配对，杜绝盲写盲改（P6）
- [ ] 复杂产出先立契约（DESIGN）再执行，契约带自检门禁（P5）

**文档与错误处理**
- [ ] 长尾边界场景独立成节，含反例 JSON（P7）
- [ ] 错误码表：每码一个解决方案，不留自由发挥空间（P9）
- [ ] 长 prompt 外置为资源文件按需读取（P10）

**交付**
- [ ] 完成后校验清单 + 强制回复格式（P12）
- [ ] 能力缺口有上报通路（P13）
- [ ] version 双落点 + 更新检查机制（P14）

## 六、对 skill-designer 的整合建议（待用户拍板）

1. **「品类模块」粒度入指引**：cloudbase 收录的 A-075 是"路由器 + N 个子 skill"的重量级 suite；本案例展示了更轻的变体——**路由器 + N 个 entry.md 品类模块**（2–8 个子域时更合适）。建议作为 suite 架构的轻量档补进 skill-archetypes 指引。
2. **「目录自述图」进 SKILL.md 模板**：低 token 高收益，且 validate 可低成本新增检查项"目录图与实际文件清单一致性"（注意做反向夹具测试）。
3. **「状态脚本 + reason 决策表」进脚本设计原则**：与既有"实证项不代填""统一 _norm()"并列——凡"探测→分支"逻辑先封装脚本，输出单行 JSON，agent 查表不走灵。
4. **「边界场景规范节」进文档模板**：凡写类/有副作用的工具文档，强制"边界场景"一节（场景→操作方式→反例）。
5. **「鉴权/前置状态机 + ⛔ 停止点」进失败处理指引**：与"自动重试只管瞬态"互补——**需要用户动作的等待必须显式声明停止点**。
6. **「量化纪律」进 best-practices**：硬规则写成"可判定条件 + 强制动词 + 违规后果"，替换一切"建议尽量"。
7. **「外置 prompt 资源」**：SKILL.md body <5K 红线之外的第三条路——不是删内容，是**把内容移到按需读取的资源文件**，路由层留一句指引即可。
