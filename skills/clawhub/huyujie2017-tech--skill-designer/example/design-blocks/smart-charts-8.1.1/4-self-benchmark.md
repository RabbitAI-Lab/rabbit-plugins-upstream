> **正向验证（benchmark）第三样本**。前两样本：westock-data（外部成品）、fin-information-pipeline（自家成品）。
> 本次特殊性：**它是三者中工程最重的**（13 py / 190KB 代码 / 1MB 资产 / 133 项端到端自检 / 8.1.1 迭代 8 次）。
> 方法：B1 立标 → B2 模拟 → B3 **四层对照**（机制/知识/闭环/**存活度**） → B4 根因归并 → B5 落点。

> **造不出它的"工程密度"，但这个差距是设计目标不同造成的，不是能力不足；真正该脸红的是三条——其中一条是「我们的纪律只存在在 AI 的记忆里」。**

## ③ 根因归并（不是罗列 3 个缺口，是 1 个根因 + 1 个例外）

### 根因：**我们把"一致性"当纪律管，它把"一致性"当架构管**

T1（单一事实来源）、T10（跨落点权威源）、T7（否定式契约）**三项指向同一件事**：

> 凡是"两处必须保持一致"的需求，我们的解法是**写一条纪律**（"改任一侧必须同步另一侧""version 双落点必同改"）；它的解法是**造一个引用关系**（抽 stats_kernels、变量取色、文案共用模块）+ **在模块头写死否定式约束**。

而纪律会漂移，引用不会。我们其实**早就知道这件事**——lessons L8 记录了 2026-09-03 的 G1 事故（init 路径与 proto 路径两套骨架不同步），但 L8 开的药方是"**改任一侧必须同步另一侧**"，**仍然停留在纪律层**。DP-204 今天才把正确药方补进来。

> **可以归并判据**：多项缺口若都表现为"靠人记住同步"，一律判**架构问题**，解法是引用/生成关系，**不写第 N 条同步纪律**。

### 例外：T4（安全 PoC）不是架构问题，是**领域缺席**

我们没有沙箱类设计，因为 skill-designer 是元 skill、不执行不可信代码。这一项**不应补**——补了就是过度设计。

### T10 单独点名：本次最狠的一条

| | smart-charts | skill-designer |
|---|---|---|
| 版本双落点纪律 | 写在 `__init__.py` 代码注释里（**意图可发现**） | **只写在 `.workbuddy/memory/MEMORY.md`** |
| 实现方式 | 声称由 regression_check 校验（**未实现，空头支票**） | **连声称都没有** |
| 机器校验 | 无 | 无（`validate_skill.py` grep `version` = **0 命中**） |

**它至少把意图写进了交付物，被后人 grep 得到、可以补实现；我们把纪律写进了 AI 的私人记忆——换个会话就丢。** 这是"知识没入库"最彻底的形态：不是知识错了，是**知识根本没进系统**。

## ④ 真实差距（机制之外的诚实部分）

| 维度 | smart-charts | 我们 |
|---|---|---|
| 迭代次数 | **8.1.1**（1 主版 + 8 迭代） | 3.8.0（但语义版本不同，不可直接比） |
| 工程密度 | 190KB 代码 / 133 自检 | 19 脚本 / 12 静态检查 / 25 端到端用例 |
| 自检性质 | **真实 CLI 子进程，非 mock** | validate 静态扫描；`run_user_tests.py` 是真跑（**本次实测 25 用例全过**）但不在 validate 链路 |
| 质量证据 | 133 项自检 + 5 个真实逃逸 PoC | 自家 validate 12/0/0 + 25 用例（**仍是自评**） |

**两个必须说清的诚实判断**：

1. **它的自检比我们硬，但我们的第 10 项比它没有。** 它 133 项里**没有一项**校验"文档写的数字 = 实际"（133 这个数字本身就写死在文档里、随时会漂）。我们 validate 第 10 项专治这个，且本次会话已连续 4 次精准抓到漂移。**这就是闭环层的价值——不在项数多少。**
2. **它的"存活度"无法评估。** 它是刚拿到的 zip 包，无运行痕迹。

### ⚠️ 关于第四层：一次自我更正

我一度以为发现了模式的"第二个盲区"——**B3.5 存活度层对外部 zip 包不可用**。复核后**这不是盲区**：`benchmark-mode.md` L58 / L106（v0.8.0）已明确要求"拿不到运行数据的一律显式标注『运行期不可验』，**不许拿设计期达标冒充整体达标**"，且切片模板第②段已要求"存活度不可验须显式声明"。**模式已覆盖，本次照做即可。**

**真实存在的只是一个轻微缺口**：模式要求"至少取 L1 + L2 两条"，但对外部包而言，agent 要**先去找运行数据、确认找不到**才能走标注分支——**样本类型的判断应在 B1 立标阶段做，而不是拖到 B3.5**。

建议（待落 benchmark-mode.md，P2）：B1 增加一步**样本分类**——
- `自家产物 / 已安装且有运行痕迹` → 立标时即抽 L1+L2 运行期特质；
- `外部包 / 只读代码` → 立标时即标 `运行期不可验（无数据）`，不浪费步骤去找。

> 记一笔自我提醒：**差点把"模式已解决的事"当成自己的新发现**。这跟我们批评别人的"空头支票"是同一类自欺——已覆盖的部分必须如实承认已覆盖。

## ⑥ 答案复述

> **造不出它的工程密度，但那不是设计能力问题，是设计目标不同**——它是给人天天用的工具，我们是给 agent 用的设计方法。
>
> 真正该改的只有一条根因：**我们把"一致性"当纪律管，它把"一致性"当架构管**。三项缺口（T1/T7/T10）都是这一个病。
>
> 而最该脸红的具体事实是：**我们有一条纪律，只存在在 AI 的记忆文件里——SKILL.md 没有、references 没有、validate 也没有。** 它至少把意图写进了交付物。
