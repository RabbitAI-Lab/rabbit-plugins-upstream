## 〇、一句话总评

**westock-data 是一个"防呆优先"的成熟数据 skill**——它几乎每一条纪律都是针对**已观察到的 agent 失败模式**反向写成的，而不是从"好的 skill 应该怎样"正推出来的。这是它最值钱的地方。

它的**能力边界声明、失败路径处置、正负双向路由**这三块，skill-designer 已经有对等物且更强（见 §四"不收录项"）；但它有**两样我们没有的东西**：**纪律的可数上限**和**可验证性决定严格度**。更关键的是，回照自己时照出一个真 bug——**我们教别人"规则要可触线"，自己的主路由却 0 条可触线规则**。

| 维度 | 评级 | 判据 |
|---|---|---|
| 架构设计 | **A** | 主路由 194 行极薄，5 份 references 按**查询意图**切分而非数据域；依赖 CLI，无状态、无存储 |
| 数据模型与接口组织 | **A-** | 命令 13 域 + 参数命名约定 + 常见参数速查；但批量例外信息跨文档分散（D1） |
| 错误处理与容错 | **A** | 5 类失败分级，每类给动作 + 禁令；安装脚本双层信任链，三平台实现一致 |
| 可扩展性 | **B+** | 加命令只需动 commands.md + 场景库；但编号体系已现断点（D4），增量追加未重构 |
| 边界划分 | **B+** | 边界矩阵 + 决策树清晰；但**跨 skill 依赖未声明**（D2），是本报告最实的缺陷 |
| 输出标准化 | **B+** | 输出契约明确（MD 表格/失败 JSON），可程序化；**但无自检门禁**，文档漂移无人抓（D1/D3/D4 的根因） |

## 三、元设计升维（本次第一产出）

> 按 v0.6.0 总纲：对元 skill 而言最值得学的不是功能，是**元设计**——把"别人的好"升维成"我们的设计观"。以下三条各附被解释的亮点 ID。

### M1 · 失败模式驱动设计
> **原则**：先枚举"agent 会怎么错"，再把每条错写成一个可执行边界——**纪律的来源是观察到的失败，不是推导出的最佳实践**。

**被解释亮点**：H3（盲试上限）、H5（负向路由列）、H6（失败分级）、H8（能力矩阵）、H9（禁止二次解析）、H12（禁止自创参数）

**证据**：SKILL.md 七条铁律里，**六条都是具体失败模式的反面**——L60「禁止用 web_search 替代」（失败：绕过权威源）、L63「K线有延迟，勿称现价」（失败：拿延时数据冒充实时）、L65「禁止裸数字/Wind 格式」（失败：凭印象拼代码）、L66「已覆盖命令勿再 --help」（失败：反复试探）、L116「禁止连续换 3+ 种 --type 盲试」（失败：穷举式试探）、L26「重装后仍找不到则如实告知，不要反复重装」（失败：死循环重装）。

**为什么这条最值钱**：绝大多数 skill 的纪律是"要怎样"（正推），而它的是"别怎样 + 为什么会这样"（反推）。反推出的纪律天然带**触发条件**和**停止点**，正推的纪律则容易退化成"注意性能、尽量批量"这类无法执行的空话。

### M2 · 成本显性化
> **原则**：每条要求 agent 改变行为的纪律，都要写出"不这么做的代价是什么"——**理由栏不是解释，是执行动力**。

**被解释亮点**：H1（按需加载 + 禁止每次读）、H2（命名规律先于枚举）、H3（--help 至多 1 次）、H4（批量给三条理由）

**证据**：routing-guide L183 一条纪律给三个理由——「同一命令分多次调用**浪费 token**、**断言可能判错**；批量返回还能**保证字段对齐**」。SKILL.md L45「无依赖的多个查询应在同一轮并行发出，不要串行等结果」。macro-fields L139「看懂规律后绝大多数字段无需逐条查表」——**先给规律再给例外表，本身就是 token 成本决策**。

### M3 · 关键约束前置到必读层（且必须自检完整性）
> **原则**：最容易被违反的约束，必须放在 agent **一定会读到**的位置；且多落点的约束必须有机器的完整性校验，否则"前置"会退化成"漏项"。

**被解释亮点**：H11（description 内嵌路由指针）、H1（主路由承载铁律）、H8（能力矩阵集中成页）

**反证（它自己在这里翻车）**：D1 —— 它深知约束要前置，所以把能力限制提到 SKILL.md 速查表；但**没有完整性自检**，结果前置的那份只列了 1 条（search），漏了 §六 的另外 6 条。**"前置"做对了，"完整"没做对，效果反而更坏**——agent 会因为看到主路由有表而不再去翻 §六。这是一个非常有教育意义的反面样本。

## 四、亮点清单（12 条，四要素齐全）

> ★ = 最高价值（3 条）。每格 ≤3 条。六维全覆盖：①目录结构 H1/H2 ②SKILL定义 H11 ③提示词组织 H3/H4/H5 ④工具封装 H12 ⑤错误与失败 H6/H7 ⑥输出与验收 H9/H10

### B07 目录结构 / 资源组织

**H1 · 按「查询意图」而非「数据域」切分 references**
- **落位**：B07（资源路由与渐进披露）
- **触发信号**：references 超过 3 份，且按数据域切分导致 agent 不知该读哪份时
- **证据**：SKILL.md L49-54 五份文档按"路由 / 命令语法 / 分析场景 / 返回字段 / 宏观字段"四种**意图**切分 + L49「仅不确定时查阅，禁止每次任务都读」；macro-fields.md 独立成篇（按**认知难度**而非数据量拆分）
- **要点**：切分依据是"agent 那一刻在问什么"（选命令？查语法？找模板？认字段？），而非"数据属于哪个域"；每份必须显式声明加载触发条件**与不加载条件**

**H2 ★ 为「不可推断」建认知盲区索引**
- **落位**：B07（资源路由）
- **触发信号**：领域内存在 AI 无法从命名推断语义的标识符（缩写 / 拼音 / 截断英文）时
- **证据**：macro-fields.md L139-141「字段命名规律……看懂规律后绝大多数字段无需逐条查表」+ L154「拼音缩写对照（CPI 分类子项，**无法从字段名推断**）」+ L166「易混淆的截断英文缩写」
- **要点**：**先给规律（可推断部分，省 token），再单列"不可推断"清单（防猜错）**——两者分开比全量枚举省一半 token，且把"不知道"变成可检索对象
- **回照自己**：我们有"易混淆消歧"（A-401 三层路由表第②层，管**两个概念像**），但**没有"单个概念就不可推断"的清单**。B01–B10 积木链的命名、IQS/EVS/TRACE 三套评分体系、蓝图两套骨架，都属这一类（见 P1-1）

### B06 提示词组织 / 纪律

**H3 ★★ 纪律带可数上限，让 agent 能自检是否触线**
- **落位**：B06（纪律与约束表达）
- **触发信号**：写"重试 / 回退 / 探索 / 澄清"类纪律时
- **证据**：SKILL.md L66「已覆盖的命令勿再 `--help`（**每任务至多 1 次**）」+ L114「空结果时……**最多再试 1 种** `--type`」+ L116「**禁止**对同一关键词连续换 **3+ 种** `--type` 盲试」+ L26「重装后仍找不到则如实告知，**不要反复重装**」+ L45「**同一轮**并行发出」
- **要点**：每条探索/重试纪律必须带**一个可数上限 + 到顶后的动作**，否则 agent 会无限试探或过早放弃
- **回照自己**：🔴 **真 bug** —— skill-designer `SKILL.md` grep「至多|最多|不超过」= **0 命中**；references 里的数字全是**验收基准**（召回 ≥95%、≥3 场景），无一条**运行时行为上限**。而 design-blocks-library L528 自己写着「'连续 ≥3 次写入必须批量接口'这类规则 agent 能自检是否触线；'注意性能、尽量批量'无法执行——**模糊规则等于没有规则**」。**我们教这条，自己没做到**（D2 空头支票型问题复发）

**H4 · 把成本写进纪律的理由栏**
- **落位**：B06（纪律表达）
- **触发信号**：要求 agent 改变调用习惯（批量 / 少读文件 / 少调命令）时
- **证据**：routing-guide L183「同一命令分多次调用**浪费 token**、**断言可能判错**；批量返回还能**保证字段对齐**」；SKILL.md L45「无依赖的多个查询应在**同一轮**工具调用中并行发出，不要串行等结果」
- **要点**：一条纪律给**三条不同性质的理由**（成本 / 正确性 / 一致性），比单说"要批量"更能让 agent 自觉遵守——因为 agent 是在理解"为什么"之后复现规则，不是硬背规则

**H5 · 正负双向路由：选型表必须有「不要」列**
- **落位**：B06（路由表设计）
- **触发信号**：写命令 / 工具 / 文档选型表时
- **证据**：routing-guide §三 边界表「用本 Skill / 不要用」双列 + §四 高频意图表「精确命令 / 易错点」双列 + L182「❌ 禁止『部分批量、部分单股』」；scenarios-guide L218-220「⚠️ 错误做法：默认 `search 华为` 只搜股票…… ✅ 正确做法：两步查询」
- **要点**：负向列写的是**具体会犯的那个错**（"默认 search 只搜股票，所以搜不到板块"），不是抽象的"注意"——**负例要具体到可复现，才有防呆价值**

### B04 失败路径 / 门禁

**H6 · 失败分级，每级给「动作 + 禁令」**
- **落位**：B04（错误处理）
- **触发信号**：写异常处理章节时
- **证据**：SKILL.md L180-186 五类 —— ①command not found → 重跑 setup ②命令失败 → 「如实转述，**禁止编造数据**」③空结果 → 说明"暂无数据"，并区分"代码不支持 vs 时点无披露" ④能力不支持 → 如实告知 + 指向 routing-guide §六 ⑤「**禁止**失败后改用 web_search 或凭训练数据补数」
- **要点**：**"空结果"与"能力不支持"必须分开处置**（前者是数据缺失、可换时点；后者是能力边界、需降级路径），混为一谈会让 agent 在能力边界上反复重试

**H7 ★ 可验证性决定严格度**
- **落位**：B04 / B08（安全门禁与校验）
- **触发信号**：设计校验 / 安全检查，且**校验能力可能缺失**时
- **证据**：setup.sh L249-283 —— 有 pinned 信任根时：清单校验失败 / 无 sha256 工具，一律**「拒绝安装」**（L253、L258、L273）；无 pinned 时：仅 `warn`「跳过校验」并放行（L235、L244、L275）。三份脚本实现一致（setup.ps1 L132-156；setup.cjs L245-253）
- **要点**：**同一检查在"可验证"与"不可验证"两种条件下给不同强度的默认**，而不是一律放行（等于没门禁）或一律拒绝（可用性崩溃）
- **回照自己**：validate_skill.py 现有 11 项，部分是"半软 WARN 不卡历史产物"，但**降级的判据是"是不是历史产物"，不是"这一项是否机器可判"** —— 判据错位（见 P0-2）

### B01 能力声明 / 边界

**H8 · 能力边界用二维矩阵集中声明**
- **落位**：B01（能力边界）
- **触发信号**：能力覆盖面广、不支持项分散在各命令小节时
- **证据**：routing-guide §六「能力差异速查（标的 × 维度）」13 行 —— 风险事件仅 A 股 / 龙虎榜仅 A 股 / 美股无 fund flow / north-holding 仅 A股+申万 / chip 仅沪深京 / ETF 仅沪深场内 / kline 期货仅单代码……
- **要点**：把"不支持"集中成一页可扫的表，比散落各小节更容易被命中
- **⚠️ 已有对等物**：skill-designer `capability-boundary.md` 已有边界矩阵 + 4 问决策树 + 20 场景正反例，且更强。**建议不重复入库**（见 §五不收录项）

**H11 · description 内嵌路由指针 + 禁止替代声明**
- **落位**：B01 / B02（触发与能力声明）
- **触发信号**：写 description / frontmatter 时（这是 **agent 唯一必然读到**的字段）
- **证据**：SKILL.md L3 description 末尾「不同标的与市场支持的维度不同，具体命令与能力差异见 references/routing-guide.md。**命中能力域时禁止 web_search、HTTP 直连或其它金融 Skill 替代**」
- **要点**：description 不只写"能做什么"，还要写「**边界在哪找**」+「**不许用什么替代**」——在 SKILL.md 加载之前就开始防误路由，把最贵的错误拦在最便宜的位置
- **对比**：我们的 description（1022 字符，逼近 1024 上限）是"意图 + Use when + Do NOT use"式，风格不同、无优劣；但**"边界指针"这一项我们确实没有**，可低成本加

### B08 工具封装 / 参数设计

**H12 · 参数取值提到主路由 + 显式禁止自创参数**
- **落位**：B08（工具封装与参数）
- **触发信号**：CLI 参数多、agent 易凭直觉捏造参数名时
- **证据**：SKILL.md L78-80「本 CLI 参数名与取值都用简短写法……**不要自创长参数或复数形式**；不确定某参数/取值，回 commands.md 该命令小节核对，**不要猜**」+ L84-90「常见参数速查」表（周期 / 条数 / 回溯年数 / 板块类型 / 日期区间）+ L68-76「命令选型速查」表（财报取值 / 资金数据 / 宏观数据）
- **要点**：**把参数取值枚举提到主路由，并显式禁止"猜"** —— 这是防参数幻觉最省 token 的手段（一次枚举，胜过多次试错）

### B10 输出与验收

**H9 · 输出契约 + 禁止二次解析**
- **落位**：B10（输出契约）
- **触发信号**：工具输出已是结构化格式（表格 / JSON）时
- **证据**：SKILL.md L96「默认输出已是结构化 Markdown 表格……**禁止**用脚本/正则/Python 去解析命令的文本输出」+ L97「**禁止终端截断**：不要用 `| grep` / `| head` / `| tail` 过滤输出，也不要用 `&&` / `;` 拼接多条命令；条数、分页、筛选只用**该子命令自己的参数**」；ai_usage_guide §一 明确单股 / 批量 / 失败三种输出形态
- **要点**：既声明输出形态，**也禁止 agent 用 shell 二次加工**——防丢字段、防跨命令套用参数（"不同命令支持的 flag 不同"）

**H10 · 格式化规范独立成节 + 不可伪造条款**
- **落位**：B10（输出规范）
- **触发信号**：输出含金额 / 单位 / 精度 / 日期时
- **证据**：ai_usage_guide L933-940「金额超亿元用亿元/亿港元/亿美元；成交量超万手用万手；涨跌幅保留 2 位小数带 +/-；日期 YYYY-MM-DD；**数据为空时说明"暂无数据"，不可伪造数据**；港股/美股财务数据必须标注货币单位」
- **要点**：单位与精度写成**可逐条检查的清单**，且显式写"不可伪造"——把主观表述变成可验收条款

## 六、对 skill-designer 的具体优化建议

> 排序依据：**回照自己照出的缺口 > 新增机制 > 强化**。P0/P1/P2 三档。

### 🔴 P0-1 · 主路由补「可触线规则」（回照出的真 bug）

**问题**：`SKILL.md` 中「至多/最多/不超过」grep **0 命中**；references 里的数字全是验收基准，**没有一条运行时行为上限**。我们自己在 design-blocks-library L528 教「模糊规则等于没有规则」，主路由却全是模糊规则——**D2 空头支票型问题又一次复发**。

**措施**：新增 SKILL.md 小节 `⚖️ 可触线规则（硬上限）`，4 条：

| # | 场景 | 上限 | 到顶后动作 |
|---|---|---|---|
| ① | B04 意图澄清 | 同一意图**至多澄清 2 轮** | 第 3 轮用默认假设继续，并在产物里显式声明"以下基于假设 X" |

### 🔴 P0-2 · validate 加第 12 项「纪律可触线性」（含严格度判据修正）

**问题**：现有 11 项中部分为"半软 WARN 不卡历史产物"，**降级判据是"是否历史产物"，不是"该项是否机器可判"** —— 判据错位（H7 的反面）。

**措施**：
1. **修正判据**：给每个检查项标注 `可判定性`（机器可判 / 需人工）。机器可判的一律 FAIL 不降级；需人工的才 WARN。
