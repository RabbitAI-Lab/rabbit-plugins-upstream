# 专利查新检索 · PatentMax

给一段技术方案描述，返回**对比文件、相似度分析与查新结论**，判断这个方案有没有被公开过、还能不能申请。异步生成，可导出 Word 报告直接交付。

数据来自 PatentMax 专利库，可将论文与公开网页一并计入现有技术。

使用问题、企业采购：访问 **ip930.com**，右下角「联系客服」。

**不需要 API Key 就能用。**

## 运行环境（必读，所有命令都适用）

部分 WorkBuddy 等环境的命令行不完整，`cat`、`ls`、`sleep`、`rm` 等可能找不到。为保证任何电脑都能跑通：

- 脚本路径一律写**绝对路径**：`$DIR/scripts/patentmax_novelty.py`（`$DIR` 是本技能所在目录），不要写 `cd ... && ...`（前一步失败会让后面整条静默不执行）
- `python` 找不到时依次试 `python3`、`py`；还找不到就用 WorkBuddy 自带的：先用 Glob 在 `~/.workbuddy/binaries/python/versions/` 下找到 `python.exe`，用它的完整路径。**下文所有 `python` 都按这条替换**
- 不要用 `cat` 读文件、不要用 `sleep` 等待：读文件用 Read 工具；等待由脚本自己完成
- 命令在**用户的工作目录**里运行，生成的 Word 会存到这个目录；也可以用 `--out-dir` 指定
- 命令超时设为 120 秒。脚本每条命令最多跑 30 秒就返回，不会卡住

## 核心原则

**技术方案描述的质量直接决定结果。** 一句「一种新型电池」查不出任何有用的东西，却照样扣费。方案少于 80 字脚本会拦下来。

**这是付费任务，执行前必须报价并取得用户确认。** 命令必须显式加 `--yes`。

**用户只想「看看有没有类似的」时不要跑这个。** 用检索加相似专利就够了，便宜得多——见「什么时候不该用」。

**判断新颖性看权利要求，不看摘要。** 摘要读着像不等于落进保护范围，要把技术特征逐条比。

**不出保证性结论。** 不写「具备新颖性」「可以申请」——见「结论纪律」。

**不重新提交。** 报告要跑几十分钟，跑得久不代表失败。只要没有报错，就继续 `wait`。**重新提交是这个技能最常见、代价最大的错误**：输入写法一变就会新建任务、重复扣费，用户还要从头再等一遍，而原来那份其实还在正常生成。

## 什么时候用

| 用户说 | 用不用 |
| --- | --- |
| 「这个想法能不能申请专利」 | ✅ 用 |
| 「有没有人做过这个方案」 | ✅ 用 |
| 「申请前帮我做个查新」 | ✅ 用 |
| 「立项前看看这个方向被占了没」 | ✅ 用 `--purpose project_screening` |
| 「要一份查新报告交给项目组」 | ✅ 用，跑完导出 DOCX |
| 「交底书 / 专利初稿写好了，看看有没有人做过」 | ✅ 用，直接 `--solution-file 交底书.docx` |
| 「先给我几个检索词 / 检索式」 | ✅ 不用提交任务，见「只要检索词或检索式」 |

## 什么时候不该用

| 用户说 | 该用什么 |
| --- | --- |
| 「查一下有没有类似的专利」 | 普通检索 + 相似专利，两次加起来便宜得多 |
| 「XX 公司在做什么技术」 | 企业情报分析 |
| 「我们下一步该往哪布局」 | 技术路线分析 |
| 「CN109761224A 是什么」 | 普通检索的单篇速览 |

**「有没有类似的」和「能不能申请」是两个问题。** 前者用检索，后者才需要查新。判断不准时问用户一句：「你是想先看看有哪些相关专利，还是要一个能不能申请的结论？」

## 执行前检查

| 检查项 | 必须确认 |
| --- | --- |
| 方案内容 | 解决什么问题、用什么手段、达到什么效果，三者缺一不可 |
| 用途 | 立项筛查、申请前查新、还是正式申请决策——决定 `--purpose` 和 `--depth` |
| 目标申请日 | 判断现有技术以公开日为准，有明确申请计划时要说清楚 |
| 地域 | 只关心国内还是要覆盖多国 |
| 文献范围 | 是否把论文和网页计入现有技术（默认计入，一般不要关） |
| 保密 | 技术方案会发送到服务端。涉及未申请的核心参数时提醒用户 |

## 技术方案怎么写

**这是整件事里最重要的一步**，详见 `references/solution-guide.md`。

至少讲清三件事：

**解决什么问题** — 现有技术卡在哪、有什么缺陷

**用什么手段** — 具体的结构、材料、步骤、参数、控制逻辑。**这块最关键**，也是最容易写空的地方

**达到什么效果** — 最好有量化指标

一份够用的描述长这样：

> 采集阀门转轴角度、启闭扭矩及前后水位，根据扭矩增量和积雪含水状态判断卡滞，并控制振动装置清理。

具体到了传感量、判据、执行动作。这种描述才查得出东西。

用户给的描述不够细时**先问，别急着跑**——问两三个问题的成本，远低于跑一次没用的查新。

## 只要检索词或检索式（不花钱）

用户只想要检索关键词或检索式、自己去别的库查时，**不提交查新任务**。按「技术对象 / 核心机制 / 区别特征」三块，各给中英文关键词和同义词，再组合成一条布尔检索式（`AND` / `OR`，短语用双引号），并标注「未实际检索」。最后问一句要不要正式查新。

## 用示例方案演示

用户说「用示例方案演示」「先试一下看看效果」，或者手上没有材料只想看看能做出什么时，用技能自带的虚构演示材料 `$DIR/references/demo-solution.md`（水渠闸门自动除冰装置）作为材料提交，命令里的文件路径换成它的绝对路径。提交前告诉用户：这是虚构的演示方案，照常收费，生成的文件仅供体验。

## 命令

```bash
# 基本用法
python "$DIR/scripts/patentmax_novelty.py" create \
  --title "阀门卡滞诊断与清理装置" \
  --solution "采集阀门转轴角度与启闭扭矩，根据扭矩增量判断卡滞并控制振动装置清理……" \
  --purpose pre_filing --depth standard \
  --yes

# 方案长的时候走文件
python "$DIR/scripts/patentmax_novelty.py" create \
  --solution-file "<绝对路径>/solution.md" --purpose novelty --yes

# 看可选值
python "$DIR/scripts/patentmax_novelty.py" options

# 接着等：每次最多 30 秒，完成时自动下载 Word
python "$DIR/scripts/patentmax_novelty.py" wait --operation-id <operation_id>

# 重新下载 Word（wait 完成时已自动下载过）
python "$DIR/scripts/patentmax_novelty.py" download --report-id <report_id>

# 不跑了
python "$DIR/scripts/patentmax_novelty.py" cancel --operation-id <operation_id>
```

**参数怎么选**

| `--purpose` | 什么场景 |
| --- | --- |
| `novelty` | 判断是否已被公开，最常用 |
| `inventiveness` | 判断创造性，比新颖性更严 |
| `pre_filing` | 申请前查新，马上要递交 |
| `project_screening` | 立项筛查，看方向有没有被占 |
| `competitor_scan` | 竞品扫描 |

`--depth` 取 `quick` / `standard` / `deep`。**正式申请决策用 `standard` 或 `deep`**，立项摸底 `quick` 够了。

`--regions` 默认 `global`，只关心国内填 `CN`，要覆盖多国用 `CN,US,EP,JP`。

`--patents-only` **一般别加**——查新的现有技术不限于专利，论文和公开产品资料同样能破坏新颖性。

`--idempotency-key` 不填会按请求内容自动生成，**同样的方案重试不会重复扣费**。

## 等待并报告进度

`create` 约 15 秒后返回。返回退出码 10 时，**先发这一句**，再发输出里的进度：

```
专利查新报告已开始生成，这类报告通常要几十分钟，进度会实时告诉你。
```

记下输出 JSON 里的 `operation_id`，后面都用它。不主动向用户展示任务编号，用户问起再给。然后运行：

```bash
python "$DIR/scripts/patentmax_novelty.py" wait --operation-id <operation_id>
```

每条 `wait` 最多 30 秒就返回。按退出码处理：

| 退出码 | 含义 | 怎么做 |
| --- | --- | --- |
| 10 | 还在生成 | 发送输出里的进度，**然后立即再运行一次 `wait`** |
| 0 | 完成了，Word 报告已自动下载 | 按「读结果」交付 |
| 1 | 出错 | 按「出错时」处理 |
| 2 | 输入有误，什么都没提交 | 按 `message` 补齐后再运行 |
| 3 | 同样的任务已经在跑 | 用输出里的 `operation_id` 运行 `wait`，**不要**换写法重新提交 |

### 进度怎么发（照原文，不改字）

把每条 `[进度] ……` / `[进度 X%] ……` 去掉方括号部分，按下表加图标后**原文发送**：

| 进度行 | 发送 |
| --- | --- |
| `[进度] 已开始生成……` | 🚀 已开始生成…… |
| `[进度] 排队中，已等待……` | 🕒 排队中，已等待…… |
| `[进度] 生成中，已用时……` | 📝 生成中，已用时…… |
| `[进度 X%] 某阶段，已用时……` | 📝 X% 某阶段，已用时…… |

例：`[进度 35%] 检索竞争对手专利，已用时 6分30秒` → 发送 `📝 35% 检索竞争对手专利，已用时 6分30秒`。

- **等待期间只发进度，不附加其它文字**；不改写进度文字，不自己估算剩余时间，不编造没出现的百分比
- **出结果之前不要结束回复。** 退出码为 10 时，发完进度立即再运行 `wait`
- 等了几十分钟还没完成 → **正常，继续 `wait`**。命令断了、对话重开了，也用同一个 `operation_id` 运行 `wait` 接着看，**不要重新 `create`**

## 读结果

退出码 0 时 Word 报告已经下载好，输出 JSON 的 `files` 里是完整路径。先发：

```
✅ 100% 专利查新报告已生成，用时 <elapsed>
📄 报告：<files 里的报告路径>
```

`quality_status` 不是 `qualified` 时，紧接着把 `quality_hint` 讲给用户。没有 Word 时（有 `docx_note`）照实说。

再根据 `summary` 用几句话讲要点，讲结论时遵守下面的「结论纪律」（不下保证性结论，交代检索边界）：

| 字段 | 怎么讲 |
| --- | --- |
| `searched` | 检索规模：找到多少篇专利、逐篇分析了多少篇、论文和网页各多少条 |
| `closest` | 最接近的几篇（按评分排）。`relevance` 是 X / Y / A：X 单篇就可能影响新颖性或创造性，Y 要和其他文献结合，A 只是背景。逐篇讲清撞在哪一点（`conclusion`） |
| `report_sections` | Word 报告里有哪几章，用户想细看时告诉他去哪章找 |

交付消息里再加「给你的下一步」（还是同一条消息，不调用工具）：

- 用一道选择题帮用户想清楚怎么补强：「你的方案在〈撞上的那个特征〉上更接近哪种？A 常规做法 → 容易被〈最接近的那篇〉命中；B ……；C 最有区分力，但需要实验数据支撑。」选项必须来自用户的方案和报告内容，不要编
- 一句提醒：「正式递交申请前，不要公开发表、参展或销售，否则会破坏新颖性。」
- 「新颖性」「创造性」第一次出现时加白话括注：新颖性（之前有没有人公开过一模一样的方案）、创造性（和已有方案比，改进是不是显而易见）

最后一句固定是：

> 在 https://api.ip930.com 控制台可以查看所有任务和余额。

- **不要打开 Word 把正文贴进对话，也不要读「完整结果」JSON 全文**：用户直接打开 Word 看。贴进来既拖长对话，又白白消耗积分
- **以上是本轮最后的输出，发完就停**：之后不再调用工具、不补表格、不写总结和建议，等用户回复。在这之后再调工具，收尾信息会被埋掉，用户看不到

用户追问细节时，再按下面几条组织回答：

**最接近的对比文件是哪几篇。** 按相似度排，重点看前三篇。

**每篇在哪一点上撞上了。** 逐条比技术特征——是解决同一个问题？用了同样的手段？还是效果相近？**看权利要求，不看摘要。**

**是不是同一篇文献公开了全部必要特征。** 这是新颖性的判断标准——**多篇结果不能拼成单篇覆盖**。多篇组合起来才覆盖的，那是创造性的问题，不是新颖性。

**结论怎么下。** 说清楚是「未检索到破坏新颖性的对比文件」还是「存在高度相似的在先专利」，别用模糊表述让用户自己猜。

**质量提示要说。** `quality_status` 不是 `qualified` 时，说明哪块数据不足、结论要打几分折扣。

## 出错时

脚本出错时输出 `{"error": true, "message": "……"}`，`message` 是写给用户看的中文说明，里面已经写明了下一步怎么办。

- **原样转述 `message`，不猜原因、不补充建议、不自己换写法重试**
- 退出码 2（输入有误：少必填项、文件读不了、方案太短）：什么都没提交、没扣费，按 `message` 补齐后再运行
- 第一次运行时输出里有「[PatentMax] 已自动领取免费试用……」：把这句话原样转告用户一次
- 出现 `"free_trial": true`：免费试用用完、过期或想用其他功能，`message` 里写着怎么办（注册 PatentMax 再送 ¥50 体验额度），原样转告
- 任务失败或取消时，预扣的费用会**全额退回**，告诉用户这一点

## 结论纪律

**禁止输出「具备新颖性」「可以申请」「全球无人做过」这类保证性结论。**

使用这个表述：

> 截至 [日期]，在 [数据库、地域、文献类型] 及所列检索范围内，未发现一篇在关键日期前公开并披露全部必要技术特征的文献。本结果不排除未公开申请、数据库缺口、非专利公开或术语差异造成的漏检。

三条必须交代：

- **18 个月公开窗口** — 专利从申请到公开约一年半，这期间的申请谁也检索不到，**这是查新最大的固有局限**
- **检索范围有边界** — 只能证明「范围内找到了什么」，不能证明「不存在」
- **正式场合需专业机构** — 查新报告可以生成，但正式的科技查新报告需要有资质的机构出具并盖章，本结果是技术参考

最后一条尤其要讲明白——**别让用户拿这份文档去当官方查新报告用**。

## 相关能力

同一把正式密钥、同一个余额（免费试用只开通本技能，其他功能要注册后用正式密钥）：

- **普通检索** — 关键词与字段式检索、单篇速览、相似专利、引证分析、15 维统计、企业画像
- **企业情报分析** — 竞争格局与对手动作
- **技术路线分析** — 下一步往哪走、专利怎么布

典型顺序：**检索摸底 → 查新确认方案 → 申请**。方向都还没定的话，先做情报分析和路线分析。
