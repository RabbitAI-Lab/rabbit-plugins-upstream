# 专利查新工作流

```
判断是不是真要查新 → 问清方案 → 便宜的方式先摸底 → 报价确认 → 跑任务 → 读结果 → 下结论
```

## 第一步：先判断是不是真要查新

**「有没有类似的」和「能不能申请」是两个问题。**

| 用户说的 | 真实需求 | 该用什么 |
| --- | --- | --- |
| 「查一下有没有类似的专利」 | 想看看有哪些相关的 | 普通检索 + 相似专利 |
| 「这个想法能不能申请」 | 要一个可专利性结论 | 查新 |
| 「立项前看看被占了没」 | 方向筛查 | 查新，`--purpose project_screening` |
| 「申请前做个查新」 | 正式决策依据 | 查新，`--depth standard` 或 `deep` |

判断不准就问一句：**「你是想先看看有哪些相关专利，还是要一个能不能申请的结论？」**

前者用检索，两次调用的成本远低于一次查新任务。**别让用户花不必要的钱**。

## 第二步：问清方案

技术方案写得不够细就先问，见 `solution-guide.md`。**最多问三个**，按缺什么挑：

1. **具体是怎么实现的？** —— 缺"手段"时问。这是最常缺的一块，也是最关键的
2. **和现有做法的区别在哪？** —— 用户自己知道区别点的话，报告会重点核这块
3. **有实测数据吗？** —— 有参数的方案比对颗粒度完全不同

用户说不出具体手段的，多半方案本身还没成型——**这种情况建议他先把方案想清楚再查**，现在查了也是白花钱。

## 第三步：便宜的方式先摸底（推荐）

正式查新之前，先用普通检索花很少的钱探一下：

```
用方案里的核心技术词跑一两次检索 → 看有没有一眼就撞上的
```

如果这一步就发现高度相似的专利，直接告诉用户——**可能根本不用跑查新**，或者要先改方案再查。

这一步不是必须的，但对用户友好，而且能提高查新的命中质量（摸底时发现的真实术语可以补进方案描述）。

## 第四步：报价并确认

付费任务，跑之前告诉用户成本并等他明确同意。脚本要求显式 `--yes`，不要替用户加。

同时定参数：

**`--purpose`** 按用途选。立项筛查用 `project_screening`，马上要递交用 `pre_filing`，纯粹判断新不新用 `novelty`，要严格看创造性用 `inventiveness`。

**`--depth`** 正式申请决策用 `standard` 或 `deep`；立项摸底 `quick` 够了。`deep` 最全但跑得久。

**`--regions`** 默认全球。只在国内申请可以填 `CN` 缩小范围，但要提醒用户：**国外的在先公开同样能破坏国内申请的新颖性**，缩范围会有漏检风险。

**`--patents-only`** 一般别加。论文和公开产品资料同样是现有技术，尤其高校和科研机构的方案，论文往往比专利早。

## 第五步：跑任务

```bash
python scripts/patentmax_novelty.py create \
  --title "..." --solution-file ./solution.md \
  --purpose pre_filing --depth standard \
  --yes
```

进度实时打到 stderr，转述给用户。

**超时不代表失败。** 这是四个任务里最容易被手滑重复提交的——等待时间长，用户容易以为没跑起来。**绝对不要重新提交**，用 `wait --operation-id <operation_id>` 继续查。

## 第六步：读结果

**最接近的对比文件是哪几篇。** 按相似度排，重点看前三篇。

**每篇撞在哪一点。** 逐条比技术特征：

- 是解决同一个问题？
- 用了同样的手段？（这一条最关键）
- 效果是否相近？

**看权利要求，不看摘要。** 摘要是概括性描述，读着像很正常；保护范围以权利要求为准。

**关键判断：是不是同一篇文献公开了全部必要特征。**

- 有一篇全覆盖 → 破坏新颖性
- 多篇组合起来才覆盖 → 那是创造性的问题，不是新颖性。**多篇结果不能拼成单篇覆盖**

这个区别要向用户讲清楚，很多人会混。

**日期要核。** 对比文件必须在关键日期**之前公开**才算现有技术。看公开日，不是申请日。

**质量分档。**

| `quality_status` | 含义 | 怎么交付 |
| --- | --- | --- |
| `qualified` | 通过校验 | 可作为查新依据 |
| `qualified_degraded` | 有数据短板 | 结论保守使用，说明哪块不足 |
| `review_required` | 需人工复核 | 不要直接当查新结论交付 |

## 第七步：下结论

**不要用模糊表述让用户自己猜。** 明确说是哪一种：

**情况 A — 未找到破坏新颖性的文献**

> 截至 [日期]，在 [数据库、地域、文献类型] 及所列检索范围内，未发现一篇在关键日期前公开并披露全部必要技术特征的文献。本结果不排除未公开申请、数据库缺口、非专利公开或术语差异造成的漏检。

**情况 B — 找到高度相似的在先文献**

直接说：`CN1234567A` 在 [日期] 公开，其权利要求 1 已记载 [具体特征]，与本方案的 [对应部分] 构成相同技术方案。建议调整方案或就 [某区别特征] 重新界定保护范围。

**情况 C — 部分特征被覆盖**

说清楚哪些特征被哪篇覆盖、哪些还没有——这种情况通常意味着**新颖性可能成立但创造性存疑**，建议找代理人评估。

三条边界每次都要讲：

- **18 个月公开窗口** — 这期间的申请谁也查不到，这是查新最大的固有局限
- **检索范围有边界** — 只能证明范围内找到了什么
- **正式场合需有资质机构** — 这份报告是技术参考，别让用户拿去当官方查新报告用

## 交付文档

```bash
python scripts/patentmax_novelty.py download --report-id <report_id> --out 查新报告.docx
```

DOCX 不额外收费。可用于立项材料、申请前自查、内部评审。**正式的科技查新报告需要有资质的查新机构出具并盖章**，这一点必须跟用户讲明白。

## 什么情况别跑

- 技术方案只有一句话，用户也说不出具体怎么实现
- 用户其实想问「有哪些相关专利」——那是检索
- 用户想知道对手在做什么——那是企业情报分析
- 用户想知道该往哪个方向走——那是技术路线分析
- 同一个方案刚跑过，用户只是想换个措辞再试——先看上次结果哪里不满意，改方案再跑
