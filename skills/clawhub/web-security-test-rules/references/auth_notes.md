# 认证与登录流程说明（通用）

> 配套 `SKILL.md` 规则 2、3、10、16 使用。
> 本文件**不含任何写死的凭据**。所有 token / 账号 / API Key 均由授权方提供，运行时通过环境变量或本地配置注入。

---

## 1. 凭据管理（规则 3、10）

- **来源**：由授权方提供，禁止从公开仓库、日志、前端代码等未授权渠道获取。
- **存储**：写入本地环境变量或配置文件（如 `.env`），**绝不写进 skill 文件、绝不提交版本库**。
- **可用必验**：使用前先验证密钥 / token 是否仍可用；不可用则替换或提示授权方（规则 10）。
- **性质确认**：确认 token 是长期有效还是短期 / 刷新式，避免测试中突然失效误判为漏洞。

### 推荐的环境变量名（示例，按需调整）

```bash
export TARGET_BASE_URL="https://api.example.com"   # 授权目标域名
export TEST_AUTH_TOKEN="<由授权方提供>"            # Bearer Token
export TEST_USER_ID="<授权方指定的测试账号标识>"     # 测试账号
```

### 典型请求头（占位，替换为真实值）

```http
Authorization: Bearer ${TEST_AUTH_TOKEN}
x-user-id: ${TEST_USER_ID}
```

> 注意：不同目标的认证头字段名可能不同（有的用 `Authorization`，有的用自定义头，有的把用户标识放在 token 之外）。测试前先抓包确认真实字段。

---

## 2. 登录 / 验证码流程梳理（通用方法）

测试前**先梳理目标登录链路**，记录关键端点与参数名差异。常见链路：

1. **获取验证码 / 挑战**：`GET /api/auth/captcha` → 返回挑战 token 与必要参数。
2. **校验挑战**：`POST /api/auth/captcha/verify` → 参数含挑战 token、位置 / 轨迹等。
   - ⚠️ 参数名可能和别处不一致（例如此处叫 `token`，登录处叫 `captcha_token`），**务必逐端点核对**。
3. **登录**：`POST /api/auth/login` → 参数含账号、密码、上一步的校验凭证等。
4. **重置密码链路**（如适用）：发验证码 → 获取新挑战 → 提交重置（含 email / 新密码 / code / 挑战凭证）。

> 记录要点：每个端点的**真实路径、HTTP 方法、参数名、返回结构、是否需要先有有效会话**。这是规则 15、16（前端资源跟踪、认证回退检测）的基础。

---

## 3. 频率限制与锁定（规则 12）

- 多数目标的限流是 **IP + 账号** 维度，**不是全局锁定**。
- 测试 IP 被限流，不代表目标存在漏洞，也不代表授权方账号失效。
- 登录失败 **1 次就停**（补充规则）：先确认凭据是否变更，不连续暴力尝试。
- 控制请求频率，避免触发告警 / 限流 / 异常通知（规则 12）。

---

## 4. 认证回退检测（规则 16）

每次测试重新验证已知端点的认证状态：

- 用**无 token 的裸请求**访问"应该需要认证"的端点。
- 若原本需认证 → 现在返回 200 / 数据，说明发生**认证回退**，必须作为漏洞报告。
- 对比上次报告记录的状态，确认是否有变化。

---

## 5. 测试账号约束（规则 2）

- 仅使用授权方指定的测试账号；记录其标识（如 user id）。
- 不冒用他人账号，不拿真实用户数据做破坏性测试。
- IDOR 类测试遵循补充规则的"先测不存在 ID → 再测他人 ID → 优先用 GET/HEAD 403 确认"的安全流程。
