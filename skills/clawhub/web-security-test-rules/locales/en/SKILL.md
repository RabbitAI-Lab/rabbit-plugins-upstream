# Website Security Testing Rules

> **Positioning**: A set of **general-purpose, responsible, minimal-impact** website / web-app security testing (authorized pentest) rules and checklists.
> **Scope**: Any target with clear, explicit authorization. This rule set is NOT bound to any specific site, account, or secret.
> **Core spirit**: Discover as many issues as possible within authorized scope, while **never harming the target, minimizing traces, always restoring after testing, and keeping standardized records**.

---

## When to Use

> 🔒 **Authorization gate (ON by default, verifiable)**: After loading this skill and before launching any test, **authorization MUST be verified first** (by default the project must provide an `AUTHORIZATION.json` authorization evidence, validating the target allowlist + validity window; if no evidence exists, a one-time interactive confirmation is required). Verification may only be skipped when the project explicitly places a `mowenfalse` marker (see "Zero, Prerequisites"). **Testing unauthorized targets is always prohibited.**

Load this skill when any of the following applies:

- The user explicitly asks to "security-test / pentest / vulnerability-scan / security-assess a certain website"
- The user mentions keywords like "security testing rules", "minimal-impact testing", "stealth testing", "vulnerability re-review", "dedup feedback"
- The user wants to validate vulnerabilities within authorized scope on a web target (injection, XSS, privilege escalation, logic flaws, etc.)

## When NOT to Use

- **Target not authorized**: asked to test a site without authorization → must refuse and confirm authorization first
- The user just wants to "look at site features / scrape public data / do normal business operations" without security testing
- The user asks for unauthorized privilege escalation on others' accounts, or asks to actually destroy / exfiltrate databases / plant backdoors

## Zero, Prerequisites: Authorization Confirmation (Highest Priority)

> Before any testing action begins, **authorization MUST be confirmed first**. Without authorization, nothing proceeds.

### Authorization Gate (ON by default: primarily signed-token verification, others are fallbacks)

> The gate is not "just talk". By default it takes the **primary path: asymmetric signed authorization token** (strongest anti-spoofing). Other mechanisms (manifest file / interactive confirmation / mowenfalse) are **fallback** downgraded paths. Any path failing blocks; unauthorized targets are always prohibited.

#### Primary Path (recommended): Signed Authorization Token

The authorizer uses a **private key** to sign an "authorization statement"; the project places an `AUTHORIZATION.json` carrying the signature and a public-key identifier; the skill verifies the signature with the corresponding **public key** before testing. Strongest anti-spoofing and tamper-resistance.

`AUTHORIZATION.json` (template in `references/authorization_template.json`) contains:

- Declaration fields: `authorized_by` / `issued_at` / `valid_from` / `valid_until` / `targets[]` / `allowed_methods[]` / `scope_note` / `scope{}` / `key_id` / `nonce`
- `scope{}`: **explicit test scope**, including `in_scope[]` (explicit targets / path prefixes), `internal_ranges[]` (internal CIDRs / hosts, e.g. `10.0.0.0/8`, `http://10.0.0.5:8080`), `include_internal` (whether internal is included), `out_of_scope[]` (explicit exclusions), `accounts[]` (authorized test accounts)
- `signed_payload`: the canonical string that was signed (generated by `scripts/sign_auth.sh`, used directly for verification)
- `signature`: RSA-SHA256 signature (base64) over `signed_payload`

Validation performed item by item before allowing:

| Check | How | On failure |
|-------|-----|------------|
| Public key trusted | find the matching public key by `key_id` in the trusted pubkey directory (`references/authorized_pubkeys/` or `auth.pubkeys`) | Block, unknown key_id |
| Signature valid | `openssl dgst -sha256 -verify <pub> -signature <sig> <(printf '%s' signed_payload)` must return `Verified OK` | Block, invalid/tampered signature |
| Target in authorized scope | the target satisfies any of: **①** domain ∈ `targets` (subdomain matching supported); **②** matches `scope.in_scope` (incl. path prefix); **③** `scope.include_internal=true` and host IP / domain falls within `scope.internal_ranges` (CIDR / host / URL matching) | Block, out-of-scope target |
| Not in exclusions | target does **not** match `scope.out_of_scope` (if provided) | Block, in explicit exclusion |
| Time window valid | current time is within `[valid_from, valid_until]` | Block, authorization expired |
| Method permitted | method ∈ `allowed_methods` (if provided) | Block, unauthorized method |
| Account permitted | account used ∈ `scope.accounts` (if provided) | Block, unauthorized account |
| Destructive op authorized | if action is destructive (DELETE / DROP / overwrite / bulk modify / reset, etc.), require `scope.destructive.allowed=true` and target matches `scope.destructive.items`; otherwise block | Block, destructive op not explicitly authorized |

All pass → allow, and record in report "signed authorization / authorizer / validity / key_id / scope summary (incl. whether internal included)".

> **Internal testing**: as long as `scope.include_internal=true` and the target falls within `scope.internal_ranges`, it is treated as authorized internal testing; when internal scope is not explicitly declared, **only public authorized domains are allowed by default**, and internal is always blocked. Internal testing also obeys all rules: minimal impact, prohibited items (A1), data minimization (A2), etc.

> See `scripts/sign_auth.sh` for key generation and signing; see `references/authorized_pubkeys/README.md` for trusted public-key management.

#### Fallback A: Authorization Manifest File (no signature, weaker)

When signature is not enforced, `AUTHORIZATION.json` declaration fields may be used alone for allowlist + validity-window validation (no signature check). Still stronger than no evidence, but **cannot prevent spoofing / tampering**; fallback only.

#### Fallback B: Interactive One-time Confirmation (when no manifest)

If the project placed no authorization manifest, the gate **does not silently pass**; instead it requires a **one-time interactive confirmation**: the agent shows the upcoming target + method + intended test window, and only proceeds after the user explicitly types a confirmation phrase (e.g. `I confirm I am authorized`). Confirmation is valid for the current session only, not persisted.

#### Fallback C: Project-level Escape Hatch (disable verification, two tiers)

> The escape hatch is a "known-risk, actively disabling the check" switch, not authorization itself.

- **Non-destructive escape hatch `mowenfalse`**: if the project is clearly authorized and wants to skip **authorization verification** (for **non-destructive testing only**), create `auth.disable` in **this skill's project directory** with content `mowenfalse` (or set env `MOWEN_AUTH_OVERRIDE=mowenfalse`). Detected → skip authorization verification; **scope constraints still apply (must not cross authorized scope, see rule 23)**.
- **Destructive escape hatch `mowenbrokentrue`**: destructive operations (rule 22) require explicit authorization + pre-backup by default. With `mowenbrokentrue` in `auth.disable` (or env `MOWEN_AUTH_OVERRIDE=mowenbrokentrue`), the **explicit-authorization requirement** for destructive ops may be skipped (destructive actions allowed without `scope.destructive.allowed=true`). **Note: `mowenbrokentrue` can only skip authorization, NOT backup** — regardless of setting, a recoverable backup MUST be made before any destructive action (rules 22, A5); backup is never waived. Note: `mowenbrokentrue` is **not** equivalent to `mowenfalse` — it does not disable authorization verification; to also disable verification, add `mowenfalse` separately (both may coexist in the file, one per line).
- **Still leave a trace after disabling**: report labels "authorization gate disabled (mowenfalse / mowenbrokentrue)" and reaffirms "for authorized targets only".
- ⚠️ The escape hatch is merely a convenience, **does not mean you may test unauthorized targets, nor that you may destroy things without backup**. Unauthorized-target testing is always prohibited; even with `mowenbrokentrue`, destructive ops **must back up first (backup not skippable)**, and scope constraints still apply (rules 22, 23).

#### Fallback D (optional enhancement): Multi-layer Combination

Stack primary + fallbacks: signed token + manifest allowlist + file SHA256 integrity + commit-audited alongside repo (`A3`). Strictest and most auditable, but highest config/maintenance cost; enable per team need.

1. **Clear authorization**: confirm this test is permitted by the target owner / authorizer, with clear scope (domains, accounts, methods).
2. **Do no harm**: testing aims to "find issues", **does not damage the target system itself** (no DB drop, no exfiltration, no backdoor, no causing unavailability).
3. **No hardcoded credentials**: test tokens / accounts / API keys are provided by the authorizer, **stored in env vars or local config, never hardcoded in this skill, never committed to VCS** (see `references/auth_notes.md`).
4. **Scope controlled**: only test authorized domains and their direct API endpoints, **do not actively scan / attack third parties or external servers**.

## One, Core Rules (19, generalized)

### 1. Authorization
Testing must have explicit authorization; do not harm the target system itself; prohibited to test unauthorized targets.

### 2. Accounts
Only use the test accounts designated by the authorizer; do not impersonate or test others' real accounts; record the account identifier used.

### 3. Methods
Under authorization and minimal-impact premises, all testing techniques (injection, XSS, privilege escalation, logic flaws, etc.) may be used.

### 4. Tools / Skills
New tools or skills may be introduced on demand, but after introduction perform a **safety & behavior check first** (confirm no malicious, no destructive scripts before use).

### 5. Restore
After each test, **record and restore** all changes (data, config, files).

### 6. Cannot Restore
Changes that cannot be restored must be **marked and explicitly reported to the authorizer**.

### 7. Verify
After each modification, use an **unauthenticated / unprivileged bare request** to verify it truly took effect (rule out cache and frontend illusions).

### 8. Dedup
Within 7 days, do **not repeat-report** the same issue (check historical reports first, see rule 14).

### 9. Report
Only report new issues; filename carries time; save to the agreed report directory (see rule 13).

### 10. Keys
First verify the key (API Key / Token) **availability**: keep if usable, otherwise replace or prompt the authorizer.

### 11. Baseline Record
Before testing, record the **original values** of target data; after testing compare to confirm whether anything truly changed.

### 12. Stealth Testing (minimize traces)
Testing must minimize traces:

- Prohibit triggering external side effects in bulk (email / SMS / push); at most **1–2** calls per single instance
- Do not modify production data; use temporary values and restore immediately after testing
- Leave no test traces; if creation is unavoidable, delete after testing
- Do not trigger alerts / rate limits / anomaly notifications
- Request rate reasonable, do not hammer interfaces
- Irreversible operations (already-sent email / notification) only call **once** when truly necessary, and record in report
- Test scope limited to authorized target domains and their direct API endpoints; do not actively scan / attack third parties or external servers

### 13. Summarize Report After Completion
- Save to a **customizable** report directory (default `reports/security/`, overridable by project config `report.path` / `report_dir` or call arguments, see rule 20)
- Filename format: `YYYY-MM-DD_findings.md`
- Content includes: test time, target, vulnerability details (id + name + severity + description + PoC + remediation), next directions
- Multiple tests on the same day **append to the same file**
- After generation, send to the authorizer via file-share / send tool
- May upload to an agreed archive location (e.g. authorized internal storage), **keep only the latest copy**

### 14. No Repeated Vectors
Within **7 days on the same target, do not repeat already-used attack vectors**:

- Read the latest report before testing, skip used methods
- Used vectors (SQLi / XSS / privilege-bypass, etc.) not repeated within 7 days
- Prioritize new methods mentioned in the last report's "next directions"
- Method records for different targets are not shared; each gets its own subfolder

### 15. Frontend Asset Change Tracking
Before each test, compare frontend JS asset names; if changed, extract new chunks and analyze newly exposed endpoints.

### 16. Auth Regression Detection
Each test re-verifies whether the auth state of known endpoints changed (**requires-auth → no-auth = auth regression, must report**).

### 17. Backup Before User-Resource Upload Tests
For upload tests involving avatars / covers / attachments etc., first capture and save the original value, restore after testing; if no restore mechanism, limit calls to **≤ 3 times**.

### 18. Irreversible-Write Endpoint Control
Endpoints writable without auth: limit test calls to **≤ 3 times**, only write harmless data, and record in report.

### 19. Vulnerability Re-review Cycle
- First re-review after 7 days → after 1 month → after 6 months → after 1 year → stop re-reviewing
- Re-review **only verifies whether fixed**, does not launch new attacks
- Re-review results appended to report, noting re-review date and outcome

### 20. Full Operation Logging + Customizable Report Location
- **Every test operation must be recorded**: maintain an "operation log" in the report, logging each test action's **timestamp, target/endpoint, method, request summary, key response result, whether as expected, whether side effects occurred**. Do not keep it only in your head and backfill from memory later.
- **Granularity**: one independent test action (one request / a group of related requests / one state-change attempt) maps to one log entry; batch or loop actions recorded as "one action + count + result summary" to avoid spam.
- **Customizable report location**: report save directory is not hardcoded; specified by user / project config (overrides default `reports/security/`). Priority: CLI / call argument > project `report.path` config > default `reports/security/<target>/`. `report_dir` in `AUTHORIZATION.json` or project config may also be a source. Custom location must be storage controllable by the authorizer (not a third-party public location).
- **Archive linkage**: reports generated per rule 13 may upload to the custom report location or agreed archive; when a custom location exists, prefer it.

### 21. Authorization Must Define Explicit Scope (internal requires explicit authorization)
- **Scope must be clear**: the authorization evidence (`AUTHORIZATION.json`) must **explicitly declare test scope** via the `scope` field — `in_scope` (targets / path prefixes), `out_of_scope` (exclusions), `accounts` (authorized accounts). When scope is ambiguous or missing, the gate should require supplementation, not default-allow.
- **Internal testing requires explicit authorization**: internal / non-public targets (internal IP, CIDR, internal domain / port) are allowed only when `scope.include_internal=true` and they fall within `scope.internal_ranges`; when internal scope is undeclared, **only public authorized domains allowed, internal always blocked**.
- Internal testing also obeys all rules: minimal impact (rule 12), prohibited items (A1), data minimization & masking (A2), operation logging (rule 20), restore after test (rule 5).

### 22. Destructive Operations: Explicit Authorization + Pre-backup + Advance Warning
- **Destructive ops need explicit authorization**: DELETE / DROP / overwrite / bulk modify / reset / large-scale status change etc. that may cause irreversible consequences, **disabled by default**. Only allowed when `scope.destructive.allowed=true` in `AUTHORIZATION.json` AND it lists the specific targets item-by-item (matching `scope.destructive.items`); vague authorization cannot sneak through.
- **Pre-backup before execution (not waivable by any switch)**: for any resource (data row, file, config, record) to be touched by a destructive action, **must back up first and confirm recoverable**, writing the backup location into the report; when `scope.destructive.backup_required=true` (default), must not execute without backup. **Note: this backup requirement is NOT affected by `mowenbrokentrue`** — `mowenbrokentrue` only skips explicit destructive authorization, never waives backup; without backup, never execute.
- **Advance warning**: clearly label in the pre-test checklist and report "this session includes destructive ops, impact scope, irreversible risk", and confirm the authorizer is aware; on accidental touch or scope overrun, immediately stop per B3 and notify.
- Backup & recovery flow for destructive ops: see `references/backup_notes.md`.
- **Destructive escape hatch `mowenbrokentrue`**: if `auth.disable` contains `mowenbrokentrue` (or env `MOWEN_AUTH_OVERRIDE=mowenbrokentrue`), the "explicit authorization + pre-backup" hard requirement of this rule may be skipped (destructive one-click). Note: ① only disables the destructive gate, not authorization verification (managed separately by `mowenfalse`); ② scope constraints still apply (rule 23, no crossing scope); ③ report labels "destructive gate disabled (mowenbrokentrue)" and reaffirms strongly suggesting backup first.

### 23. No Crossing / Leaving Authorized Scope
- **Outbound target must hit authorized scope**: any test request's target (domain / IP / port / path) must match `targets` / `scope.in_scope` / internal `internal_ranges`; must not actively send test requests outside authorized scope (see rule 96, gate checks).
- **SSRF must not use target to hit third parties**: SSRF PoCs only verify the target server's own unauthorized-access / internal-probe vulnerabilities; **must not use the target server as a springboard to access / attack external third parties or real internal systems outside authorized scope**; only verify the vulnerability itself, don't use third parties as targets (see D6).
- **Do not follow cross-domain redirects outbound**: test tools must not auto-follow cross-domain 302 / 307 redirects to sites outside authorized scope and launch tests; cross-domain jumps must first be confirmed within authorized scope.
- **Asset collection stays in scope**: subdomain enum / port scan / asset collection (e.g. amass / subfinder / httpx) outputs that exceed authorized scope — do not test them.
- **External-site attempts related to the test target also need authorization**: third parties integrated by the target (OAuth / SSO providers, payment / SMS / email services, external APIs, Webhook / callback receivers, CDNs, etc.) are "related to the tested site" but are still independent off-site systems. Any test request against them requires **that external site's own authorization**; if unobtainable, place `mowenwaitrue` in `auth.disable` (or env `MOWEN_AUTH_OVERRIDE=mowenwaitrue`) explicitly confirming "already have / awaiting corresponding external-site authorization" before attempting. External-site-related attempts without that site's authorization and without `mowenwaitrue` are always prohibited.
- **Also applies under fallback paths**: even if the gate takes Fallback B (interactive) or Fallback C (`mowenfalse` disables verification), each target must still be confirmed within authorized scope, otherwise prohibited (see gate checks and this rule).

## Two, Supplementary Rules

- **Confirm latest credentials before each test start**: do not try logging in directly with old credentials.
- **Stop after 1 login failure**: first confirm whether credentials changed, don't keep trying.
- **Default target**: when the user specifies no other target, use the agreed default target (if configured); otherwise must confirm with the target authorizer first.
- **IDOR deletion-test safety flow**:
  - First test a non-existent ID, observe the response format (404 vs 403 vs 200)
  - Then decide whether to test a real other-user ID
  - Prefer testing GET / HEAD 403 responses to confirm permission denial, **do not actually execute DELETE to success**
- **Comprehensive module coverage**: different modules' same-type endpoint protections may differ; don't assume consistent protection.
- **Business judgment principle**: endpoints with no payment / no sensitive assets are not vulnerabilities; public content with no access restriction may be a design decision. Report distinguishes **"technical vulnerability"** from **"business acceptable"**.

## Three, Authentication & Login Flow (general notes)

See `references/auth_notes.md`. Key points:

- Credentials provided by authorizer, suggested stored in env vars / local config, **never hardcoded**.
- Before testing, map the target's login / captcha / auth flow, recording key endpoints and **parameter-name differences** (e.g.: endpoint A uses `token`, endpoint B uses `captcha_token` — must distinguish).
- Rate limits are mostly per **IP + account**, not global; a test IP being limited does not mean the target has a vulnerability.

## Four, Timestamp Recording Rules

- Every record **must carry the "current" timestamp**: daily notes, reports, error records, long-term memory, test results — all records.
- **Before recording, must obtain the real current time first** (use a time tool / system command to get current time, to the second), **never fill only a date from memory or estimate time**.
- Format (mandatory): `YYYY-MM-DD HH:MM:SS` (second-level, for sorting and tracing multiple records within the same day).
- Not just daily summaries carry time — every record, every finding, every test result must have a **specific current time**.
- Reason: facilitates tracing the real discovery time, avoids mistaking historical state as ongoing, avoids inability to sort multiple same-day records.

---

## Five, Error Recording Mechanism

- **Record on error**: create a record file in the agreed error directory (default `errors/`).
- Naming format: `YYYY-MM-DD_brief-description.md`.
- Content: error description, scenario, cause, solution, preventive measures.
- **Check records first when hitting issues**: when encountering similar problems, first search the error directory.

## Six, Report Format (see references/report_template.md)

Report must at least include:

| Field | Description |
|-------|-------------|
| Test time | carries current timestamp, to the second (rule 4) |
| Target | domain / endpoint scope |
| **Operation log** | per-action record of each test action: time / endpoint / method / request summary / response result / side effects (rule 20, mandatory) |
| Vulnerability details | id + name + severity + description + PoC + remediation |
| Next directions | new methods to try next time (for rule 14) |

- **Report save path customizable**: default `reports/security/<target>/`, overridable by project config `report.path` / `report_dir` or call arguments (see rule 20). Filename remains `YYYY-MM-DD_findings.md`; same target same day appends to the same file.
- Report template in `references/report_template.md`, which already includes "Operation Log" and "Report Location Config" sections.

**Severity suggestions** (adjustable):

| Severity | Meaning |
|----------|---------|
| Critical | direct takeover, DB exfiltration, RCE |
| High | unauthorized read/write, sensitive info leak |
| Medium | exploitation requiring conditions, partial protection bypass |
| Low | info leak, config flaw |
| Info | hardening advice, not a vulnerability |

## Seven, General Principles

- **Switch tools instead of grinding**: when repeatedly failing, decisively switch alternatives.
- **Time calibration (get real current time)**: before each recording / report generation / error write, first get the current timestamp with a time tool (to the second), then write, obeying rule 4. Never fill time from memory.

## Eight, Quick Reference (Checklist)

### Before testing
- [ ] 🔒 Authorization gate verified: signed-token verification passed (or fallback: manifest allowlist / interactive confirmation / mowenfalse), target in allowlist and not expired (Zero)
- [ ] Confirm prohibited-item boundary: no DoS / social engineering / peak-hour stress test (A1)
- [ ] 🔒 Includes destructive ops? require `scope.destructive.allowed=true` and item-by-item targets, else prohibit (A5, rule 22)
- [ ] Destructive ops: related resources backed up before action and backup location recorded (rule 22, A5)
- [ ] Confirm test window / change window (A4); confirm compliance boundary (A3)
- [ ] Confirm latest credentials (don't reuse old)
- [ ] Read the target's latest report, identify vectors used within 7 days (rules 8, 14)
- [ ] Record original target data values (rule 11, baseline)
- [ ] Compare frontend JS assets, identify new endpoints (rule 15)
- [ ] Get current timestamp (to the second) and record as this session's baseline time (rule 4)
- [ ] Determine report save path (default / custom `report.path` / `report_dir`, rule 20)

### During testing
- [ ] Only use authorized test accounts (rule 2)
- [ ] Control rate (≤ 2 req/s), don't hammer interfaces, don't trigger alerts (rules 12, C4)
- [ ] External side effects ≤ 1–2 per single instance (rule 12)
- [ ] Use temporary values, don't pollute production data; don't export sensitive data, mask in report (rules 12, A2)
- [ ] Used vectors not repeated within 7 days (rule 14)
- [ ] Auth regression detection (rule 16)
- [ ] Backup user resources first (rule 17); irreversible writes ≤ 3 times (rule 18)
- [ ] Destructive ops: re-confirm backup usable before action, single-step execution with immediate logging (rules 22, A5)
- [ ] Keep request / response evidence (B1); cautious with non-idempotent requests (C2); CSRF / CORS专项 (C3)
- [ ] Write "operation log" immediately for every action (time / endpoint / method / summary / result / side effects) (rule 20)
- [ ] All outbound targets within authorized scope, don't follow cross-domain redirects off-site (rule 23)

### After testing
- [ ] Restore all changes (rule 5); destructive ops must recover from backup and verify (rule 22)
- [ ] Mark & inform if cannot restore (rule 6)
- [ ] Bare request verifies real effect (rule 7)
- [ ] Only report new issues, dedup (rules 8, 9)
- [ ] Generate `YYYY-MM-DD_findings.md` and append, "operation log" complete (rules 13, 20)
- [ ] 🔒 High (Critical / High) report immediately (B2); on accidental outage / large real-data access, stop immediately and notify (B3)
- [ ] Report only to authorized recipients (B4); distinguish self-developed / supply-chain vulnerabilities (C1)
- [ ] Errors recorded to errors/ (rule 5)

## Nine, Extended Rules (A–C, 12 total)

> 🔒 mark = directly related to "authorization / compliance boundary"; scope must be confirmed with authorizer before testing.

### A · Compliance & Boundary
- **A1 Prohibited items / scope boundary** 🔒: explicitly prohibit DoS / resource-exhaustion tests, social engineering against real employees, peak-production stress tests, unless separately authorized by the authorizer. Destructive ops see A5.
- **A2 Sensitive-data minimization & masking**: do not export / retain user PII / business data beyond what's needed to prove a vulnerability; PII in reports must be masked.
- **A3 Compliance & legal boundary** 🔒: testing must obey applicable laws/regulations (e.g. Cybersecurity Law), and retain written authorization evidence.
- **A4 Test window / change window**: test during the authorizer-agreed low-traffic / maintenance window to avoid impacting business.
- **A5 Destructive ops need explicit authorization AND pre-backup** 🔒: DELETE / DROP / overwrite / bulk modify / reset etc. destructive actions disabled by default; require `scope.destructive.allowed=true` and itemized targets, must make recoverable backup and write report before execution, and flag irreversible risk to authorizer in advance (see rule 22, ref `references/backup_notes.md`).

### B · Evidence & Reporting
- **B1 Evidence retention**: keep reproducible HTTP request / response evidence (curl / packet capture) for each finding, not just conclusions.
- **B2 High-risk immediate reporting**: Critical / High not batched to daily report; notify authorizer upon discovery.
- **B3 Stop / circuit-breaker**: on accidental outage, or unintentionally accessing large amounts of real user data, stop immediately and notify authorizer.
- **B4 Minimal report distribution**: report only to authorized recipients, no external sharing.

### C · Technical supplements
- **C1 Dependency / supply-chain annotation**: distinguish "self-developed code vulnerability" from "third-party library version vulnerability", giving CVE / upgrade advice for the latter.
- **C2 Cautious non-idempotent requests**: don't randomly fire POST / PUT / DELETE in loops / retries, avoid duplicate side effects.
- **C3 CSRF / CORS / same-origin专项**: include these common omissions in the must-test list.
- **C4 Concrete rate / concurrency limit**: give a default cap (e.g. ≤ 2 req/s), quantifying "reasonable frequency".

## Ten, Specialized Test List (new recommended rules, D class)

> Beyond the 19 core + 12 extended, supplement the following common specialties. All bound by "authorization / minimal impact / stealth".

### D · Specialized techniques
- **D1 Token & JWT weaknesses**: none algorithm, weak / brute-forceable key, no expiry check, refresh token unbounded to session, hardcoded key.
- **D2 Session & auth**: session fixation, unlimited concurrent logins, token still valid after logout, long-lived Remember-me, predictable / reusable password-reset token.
- **D3 Business logic / concurrency**: race conditions (concurrent coupon / transfer / order), negative / over-limit, duplicate submission, flow bypass (skip validation steps).
- **D4 Privilege-escalation combos**: vertical + horizontal escalation combos, IDOR bulk traversal, enumerable UUID / sequence, function-level escalation (change role param).
- **D5 Injection extensions**: command injection, XXE, SSTI, deserialization, LDAP / NoSQL injection (not limited to SQL / XSS).
- **D6 SSRF**: internal / metadata probing (e.g. `169.254.169.254`), DNS rebinding, protocol tunneling (gopher / file); probe only, don't read large sensitive data. **SSRF PoC must not point to external third-party systems outside authorized scope — must not use the target server as an attack springboard to hit off-site / real-internal third parties**.
- **D7 File upload**: type / content bypass (webshell), path traversal, decompression bomb, overwrite existing files; use harmless samples, delete after testing.
- **D8 Info leak**: `.git` / `.env` / backup exposure, unauthorized Swagger / Docs, verbose errors / stack traces, directory listing.
- **D9 Config & transport**: missing security headers (CSP / HSTS / X-Frame-Options), Cookie attributes (Secure / HttpOnly / SameSite), weak TLS config, CORS misconfig.
- **D10 Supply chain / components**: component fingerprinting + known CVE, debug endpoint exposure (actuator / phpinfo), dependency vulnerabilities.
