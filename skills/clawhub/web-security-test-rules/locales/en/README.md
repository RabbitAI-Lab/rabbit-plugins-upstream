# Website Security Testing Rules

A **general-purpose, responsible, minimal-impact** website / web-app security testing (authorized penetration testing) Skill, for AI coding assistants that support Skills such as [CodeBuddy](https://codebuddy.ai).

> This Skill only describes "how to responsibly do security testing **under authorized premises**"; it contains no attack guidance against unauthorized targets. Users must ensure they have legal authorization for the test target.

> ⚠️ **This Skill is auto-generated by AI (an AI coding assistant)**; its content serves as a security-standard example and reference. Please manually review before use and adapt to the target's actual authorization.

> 🌐 **Localization**: default **Chinese (`zh-CN`)** (i.e. the root-directory files). English under `locales/en/`; other languages per `locales/README.md`. Switch: set `MOWEN_LANG=<code>` or drop a `lang` file (content = code), then read `locales/<code>/`.

---

## Features

- **Authorization first (gate ON by default)**: primarily **asymmetric signature verification** (`AUTHORIZATION.json` + trusted-public-key check, strongest anti-spoofing / tamper-resistance); manifest allowlist, interactive confirmation, `mowenfalse` are fallback downgrade paths (see SKILL.md section Zero).
- **Minimal impact / stealth testing**: rate control, limited external side effects, no production-data pollution, always restore after testing.
- **Standardized logging**: mandatory "real current time" (to the second), structured vulnerability reports, error-recording mechanism.
- **Dedup & re-review**: same issue / already-used attack vectors not repeated within 7 days; vuln re-review at 7 days → 1 month → 6 months → 1 year.
- **Extended rules**: 12 covering compliance boundary, evidence reporting, technical supplements (A/B/C) + 10 specialized (D).

## Usage

1. **Launch a test**: tell the AI "help me test the security of https://example.com"; the Skill goes through the "authorization gate" first.
2. **Follow the checklist**: SKILL.md has built-in "before / during / after testing" checklists ensuring minimal impact and standardized logging.
3. **Generate report**: after testing, generate `YYYY-MM-DD_findings.md` with vuln id / severity / description / PoC / remediation / next directions, default `reports/security/`.
4. **Re-review**: re-review fix status on the 7-day → 1-month → 6-month → 1-year cycle, appending to the same report.

## Authorization Gate (ON by default)

To prevent misuse against unauthorized targets, this Skill **forces "verify authorization before testing" by default**.

**Primary path (recommended): Signed Authorization Token** — the authorizer signs an "authorization statement" with a private key; the project places a signed `AUTHORIZATION.json`; the Skill verifies the signature with the corresponding public key (`references/authorized_pubkeys/`), and checks target scope, validity window, accounts, etc.

**Fallback downgrade paths** (details in SKILL.md section Zero):
- Fallback A: `AUTHORIZATION.json` allowlist + validity only (no signature, weaker)
- Fallback B: one-time interactive confirmation when no manifest
- Fallback D: multi-layer combo of signature + allowlist + SHA256 + commit audit

### Three-tier switches (escape hatches; one per line in `auth.disable`, or env `MOWEN_AUTH_OVERRIDE`)

> The escape hatch is a "known-risk, actively disabling the check" switch, **not authorization itself**; disabling does not mean you may test unauthorized targets, which are always prohibited.

| Switch | Effect | Note |
|--------|--------|------|
| `mowenfalse` | skip **authorization verification** (non-destructive only) | scope constraints still apply (rule 23, no crossing scope) |
| `mowenbrokentrue` | skip the **explicit-authorization** requirement for destructive ops | **backup is NOT skippable** — regardless of setting, a recoverable backup must be made before any destructive action (rules 22, A5); not equivalent to `mowenfalse`, does not disable authorization verification |
| `mowenwaitrue` | confirm already have / awaiting authorization for external sites related to the test target | only relaxes the authorization requirement for external-site-related attempts; does not disable the gate or the destructive gate; list involved external sites in the report |

After disabling any switch, the report must label "authorization gate disabled (xxx)" and reaffirm "for authorized targets only".

### Path Cheatsheet

| Scenario | Action | Gate behavior |
|----------|--------|---------------|
| Regular authorized (recommended) | place signed `AUTHORIZATION.json` | public-key verify + allowlist + validity, pass → allow |
| Signing inconvenient | place unsigned `AUTHORIZATION.json` | allowlist + validity only (Fallback A) |
| Temporary, no file | place no file | one-time interactive confirmation (Fallback B) |
| Clearly authorized, save steps (non-destructive) | `auth.disable` with `mowenfalse` | skip verification, report labels (Fallback C) |
| Destructive, save steps | `auth.disable` with `mowenbrokentrue` | skip destructive explicit authorization (backup still mandatory), scope still constrained |
| Need to test target-related external site | obtain that site's authorization, or `auth.disable` with `mowenwaitrue` | allow external-site-related attempt (only related to this test target, see rule 23) |
