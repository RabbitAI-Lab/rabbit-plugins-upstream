# 网站改版助手（Website Redesign Orchestrator）

本 Skill 是一条**端到端改版流水线编排器**：它以一个**强制前置「阶段 0 · 依赖安装与自检」**开场（先按『依赖安装协议』装好 4 个依赖 skill 并输出《依赖安装清单》），随后把一次完整的企业网站改版拆成 18 个有序阶段（阶段 1–18），并以**阶段 0 · 依赖安装与自检**作为最先执行的强制前置：自己完成"调研—规划—策略"部分，并在**备份目标站已有页面 / 生成页面 / 迁移内容**这些写操作前先完成 MCP 连接与站点确认，在 SEO / GEO / 询盘阶段分别交给对应专家 skill。这样既保证改版有清晰的战略与结构主线，又复用成熟的建站能力落地代码与数据。

> 设计原则：先想清楚（卖什么 / 卖给谁 / 市场在哪 / 核心竞争力），再动手做（架构 / 设计 / 迁移 / 生成），最后做增长（SEO / GEO / 询盘）与交付（Preview / Publish）。

## 触发场景

- 用户说"改版""重设计""整站重构""风格升级""把旧站迁到新平台""搬站并重做视觉"。
- 用户直接给出下方『改版四问』的改版流程。
- 用户手里有一个旧站，想要一套全新的、保留 SEO 权重与转化能力的站点。

## 前置输入（开工前必须向用户确认）

> 本环节在阶段 0（依赖安装）完成后、阶段 1 之前执行；其中同一站点模式的 MCP 连接 / 确认即在此环节完成，外部网站模式则延后到阶段 10。

1. **旧站信息**：旧站 URL、是否可访问、是否需要保留域名 / 历史 URL（决定 301 映射与 SEO 权重承接）。**注意**：基于外部网站改版时，旧站 URL 为**必填**（旧站是内容来源与 301 映射依据）；基于同一站点改版时，旧站即当前经 MCP 确认的站点，无需另填旧站 URL。
2. **改版模式（必问）**：本次是「基于同一站点」改版（旧站即当前站点，产品 / 文章 / 表单等数据已存在，无需迁移上传），还是「基于外部网站」改版（旧站是另一站点 / 平台，需把数据迁移到新站点）？此决定影响「迁移内容」阶段是否执行数据上传，以及表单处理策略（见『全局约束』）。
   - **MCP 确认时机（重要）**：若选「基于同一站点」，**在确定模式的同时即进行站点 MCP 连接 / 确认**（逻辑同阶段 10）：已持有该站 MCP 则经 MCP 拉取站点信息（站点名称 / 页面列表等）列出供用户确认「是否操作此站」；未持有则此时索取 MCP 地址 + Token 并拉取站点信息复核。确认无误后再继续后续规划。若选「基于外部网站」，目标（新）站 MCP 延后到阶段 10 连接 / 确认（原外部站点仅作内容来源，不经本 MCP 操作）。
   - **旧站 URL 必填（外部网站模式）**：若选「基于外部网站」，**必须提供旧站 URL**（作为内容抓取 / 迁移来源与旧→新 URL 映射依据），未提供不得进入后续阶段；基于同一站点模式无需提供旧站 URL。
3. **目标平台**：新站（或本次改版所在站点）建在哪个建站平台？同一站点模式下即原站点所在平台。MCP 地址 + Token 的获取 / 确认时机由改版模式决定：基于同一站点在选定模式（本条）时即确认，基于外部网站则在阶段 10 确认；均无需开工前给出，MCP 信息已含站点标识，不必单独再问新站信息。
4. **改版目标**：视觉升级 / 结构重构 / 转化提升 / 全量重写？期望的规模（页面数、语言、是否多端）。
5. **品牌与调性**：品牌色、参考站、禁止项、已有 VI / Logo / 素材位置。
6. **数据与范围**：哪些产品 / 文章 / 图片 / 表单要迁移？分类如何映射？
7. **验收方式**：预览地址、上线节奏、是否保留旧 URL 的 SEO 权重。

> 缺少「改版模式 / 目标平台 / 改版目标 /（外部网站模式）旧站 URL」任一项时，先向用户追问补齐，不要直接写代码。

## 改版四问（Discovery，最先执行，产出战略摘要）

无论用户给多少资料，先回答并落盘这四问，作为后续所有决策的依据：

1. **卖什么？**（产品 / 服务 / 解决方案，越具体越好）
2. **卖给谁？**（目标客户画像：行业、角色、规模、痛点）
3. **市场在哪里？**（地域 / 渠道 / 线上还是线下 / 出海）
4. **核心竞争力？**（差异化、证据、为什么选你）

产出一份 **《改版战略摘要》**（300 字内），在「信息架构」与「设计策略」阶段被反复引用。模板见 `references/redesign-templates.md`。

### 阶段 0 · 依赖安装与自检（强制前置，最先执行）
- **目的**：确保本 skill 依赖的 4 个外部 skill 已安装并可被调用，避免后续阶段因依赖缺失而中断或误用未安装名。
- **动作**：严格按『依赖安装协议』，依次确认 / 安装 `DEP_JIANZHAN` / `DEP_SEO` / `DEP_GEO` / `DEP_LEADGEN` 四个依赖；已可用则跳过安装、仅做校验与登记（幂等）。
- **产出**：《依赖安装清单》（角色 → 调用名 → 状态 → 来源），作为后续所有 `Skill` 调用的唯一依据。
- **硬约束**：《依赖安装清单》未产出前，不得进入阶段 1 及任何调用外部 skill 的阶段。

### 阶段 1 · 旧网站
- **目的**：锁定改版对象，拿到可分析的真实材料。
- **动作**：记录旧站 URL 与可访问性；若无法访问，要求用户提供站点地图 / 截图 / 导出包。列出已知要保留的页面、产品、文章、表单。

### 阶段 2 · Audit（审计）
- **目的**：量化旧站现状，找出"该保留 / 该砍 / 该补"的内容与结构。
- **动作**：按 `references/redesign-templates.md` 的《旧站审计清单》逐项核查：技术（加载速度、移动端、可索引性）、内容（页面清单、Top 页面、死链）、SEO（TDK、外链、排名页）、视觉（配色、版式、一致性）、转化（表单、CTA、询盘路径）。
- **产出**：《旧站审计报告》+ 旧 URL → 新 URL 映射表（供 301 / 权重承接）。

### 阶段 3 · Business 理解
- **目的**：把『改版四问』的"卖什么 / 核心竞争力"落到业务模型。
- **动作**：梳理产品线、定价模式、交付方式、案例与资质、售后；标注哪些内容需要**动态数据源**（产品库 / 文章库 / 表单），哪些可以静态。

### 阶段 4 · 用户理解
- **目的**：让设计服务于真实用户，而非审美自嗨。
- **动作**：刻画 1–3 个核心用户画像（角色、目标、进入站点的场景、决策顾虑）；列出用户最关心的 3 个问题和最该被引导的下一步动作。

### 阶段 5 · 竞争对手
- **目的**：找差异化空间，避免同质化。
- **动作**：选 3–5 个竞品（含行业标杆），对比信息架构、视觉调性、内容深度、转化路径、SEO/GEO 表现；输出"我们能赢的点"。

### 阶段 6 · 信息架构（IA）
- **目的**：确定站点的"骨架"——栏目、页面层级、导航、内链关系。
- **动作**：基于 Audit + 业务 + 用户，输出站点树（主导航 / 次级导航 / 详情页体系）、URL 规划、与旧站映射关系。模板见 `references/redesign-templates.md`。

### 阶段 7 · 设计策略
- **目的**：把战略翻译成视觉与体验原则。
- **动作**：确定设计语言（深色奢华 / 科技 / 简约等）、色彩与字体系统、栅格与间距、关键交互、情绪板（moodboard）。呼应『改版四问』的核心竞争力。

### 阶段 8 · 页面规划
- **目的**：把 IA 落成一页一页的交付清单。
- **动作**：逐页面定义：目标、核心板块、所需数据（动态 / 静态）、TDK 草稿、CTA。生成《页面规划表》。模板见 `references/redesign-templates.md`。

### 阶段 9 · 组件规划
- **目的**：抽象可复用组件，保证一致性与开发效率。
- **动作**：列出组件库（页头 / 页尾 / Hero / 产品卡 / 文章卡 / 表单 / 面包屑 / 评价 / 信任徽章等），定义每个组件的 props、状态、响应式断点；明确哪些做成公共页头页尾（`FnInclude`）。模板见 `references/redesign-templates.md`。

### 阶段 10 · 连接站点（获取 / 确认 MCP）
- **目的**：确保后续所有读写都作用在正确的目标站点上。注意：基于同一站点改版时，站点 MCP 已在『前置输入』选定模式时确认（见『前置输入』中『改版模式』的 MCP 确认时机），本步骤仅作一致性核对；基于外部网站改版时，目标（新）站 MCP 在此处获取 / 确认。
- **动作**：
  1. **基于同一站点改版（MCP 已提前确认）**：复用『前置输入』已确认的 MCP 凭据；如距确认已较久或用户要求，可重新经 MCP 拉取站点信息（站点名称 / 页面列表等）复核一次。确认无误后直接进入下一阶段。
  2. **基于外部网站改版（此处确认目标站 MCP）**：
     - 若 Agent 已持有目标站 MCP 地址 + Token：先经 MCP 拉取目标站点信息（站点名称 / 页面列表等），向用户确认"是否操作此站？"；确认是则继续；确认不是则请用户重新提供**正确的目标站 MCP 信息**，再用新凭据拉取站点信息复核后继续。
     - 若 Agent 尚未持有 MCP 信息：此时向用户索取目标站的 MCP 完整地址 + Bearer Token（MCP 信息已含站点标识，无需另问新站信息），索取后拉取站点信息复核。
- **注意**：本步骤（或『前置输入』提前确认）确立的 MCP 凭据将贯穿 备份目标站已有页面 → 迁移内容 → 生成 全部写操作；本 skill 不得假设或复用其它站点凭据。

### 阶段 11 · 备份目标站已有页面（使用已确认 MCP）
- **目的**：在生成 / 重写新站之前，先对**目标站（即你拥有 MCP、即将写入的站点）即将被覆盖的现有页面**做原样留存，避免改版过程中的覆盖、删页、清缓存等误操作导致旧版不可恢复。
- **重要澄清（备份对象）**：本阶段备份的是**目标站已有页面**，不是原外部站点。基于外部网站改版时，原外部站点只是内容来源、不会经本 MCP 改写，因此**原外部站点无需也不应备份**；只有当目标站本身已有会被覆盖的页面时才需要备份。
- **动作**：
  1. **先问（必问）**：进入本阶段前，明确询问用户："是否需要先备份目标站现有页面（生成前原样留存，命名为 XX_backup）？"
  2. 若用户回答 **需要**：
     - 使用阶段 10 已确认的 MCP，经阶段 10 已确认的目标站 MCP（通过《依赖安装清单》登记的 `DEP_JIANZHAN` 建站助手所提供的 MCP 工具）（如获取页面代码的工具，工具名以建站助手实际提供为准，必要时先 `list_tools` 确认）拉取目标站各目标页面的现有代码；
     - 用同一 MCP 工具把现有代码**另存为一个新的备份页面**，页面名称按 `XX_backup` 规则命名（如 `about.html` 的备份页名为 `about_backup`、`contact` → `contact_backup`）；
     - 逐页确认另存成功，输出《目标站备份清单》（原页面 → 备份页 → 备份状态）。
  3. 若用户回答 **不需要**：跳过备份，在记录中注明"用户已确认无需备份"，直接进入「迁移内容」阶段。
- **按改版模式说明**：
  - **基于同一站点改版**：目标站即旧站，现有页面将被改版覆盖，应按上述流程备份（建议默认询问并备份）。
  - **基于外部网站改版**：原外部站点仅作内容来源、不经由本 MCP 改写，**不备份原外部站点**；目标（新）站若为空白站 / 无既有页面则无需备份，若目标站已有会被覆盖的页面则按上述流程备份。
- **注意**：备份只是原样另存，不修改内容、不覆盖原页面；MCP 凭据与写操作确认等约束遵循建站助手规则。

### 阶段 12 · 迁移内容 ✅ 调用「建站助手」skill
- **目的**：按「改版模式」把内容安全落到新站，为后续生成页面准备好真实数据源。
- **动作**：**调用《依赖安装清单》登记的 `DEP_JIANZHAN`（建站助手）skill**，依据阶段 2 确认的「改版模式」分支处理：
  - **基于同一站点改版**：产品 / 文章 / 图片等数据**已存在，无需上传入库**；仅处理本次改版需「新增 / 调整」的内容（如新栏目对应的空页面骨架），并走下方表单规则；禁止盲目覆盖既有数据。
  - **基于外部网站改版**：走建站助手的「搬站 / 参考站建设」流程：分类映射、`upload_file` / `upload_product_image` 上传素材、`add_news` / `add_product` 入库、表单复用系统动态表单、保存后核对。迁移前必须 `list_*_class` 映射并获确认，禁止盲目覆盖。
  - **表单处理（两种模式通用）**：
    - **自定义表单**：询问用户选择「新建」或「修改现有」；新建走建站助手自定义表单能力，修改则定位既有表单调整字段 / 样式。
    - **询盘表单**：只能是「修改」或「不动」——定位站点既有询盘表单进行调整，或保持原样；**不得新建询盘表单**（应复用系统既有询盘能力，而非另起）。
- **时序说明**：迁移内容（本阶段）在生成之前完成，使下一阶段生成的页面在预览时即可拉取真实数据；页面使用系统动态标签时，生成页面可直接绑定已入库的产品 / 文章 / 表单数据。

### 阶段 13 · 生成 ✅ 调用「建站助手」skill
- **目的**：把规划变成可粘贴 / 可上线的页面代码。
- **动作**：**调用 `DEP_JIANZHAN`（建站助手）skill**（`Skill` 工具，`skill=<《依赖安装清单》中 DEP_JIANZHAN 登记的真实调用名>），复用阶段 10 已确认的 MCP。把本流水线规划阶段（阶段 1–11）产出的《页面规划表》《组件规划表》《设计策略》以及阶段 12 已入库的数据作为上下文传给它，由它按建站助手规定的 Twig 模板语法、系统数据源、MCP 工具生成页面；公共头尾、结构化数据、表单均遵循建站助手强制规则。

### 阶段 14 · SEO → 调用「SEO skill」（https://skillhub.cn/skills/org-b0bh4w8c/yunzhi-seo-skill）
- **目的**：保证新站可被搜索引擎正确收录与排名，承接旧站权重。
- **动作**：调用「SEO skill」（`Skill` 工具，`skill=<《依赖安装清单》中 DEP_SEO 登记的真实调用名>，来源 https://skillhub.cn/skills/org-b0bh4w8c/yunzhi-seo-skill），基于阶段 2 的 URL 映射做 301 / 重定向校验、TDK 复核、结构化数据、内链、可索引性体检与复检。

### 阶段 15 · GEO → 调用「GEO skill」（https://skillhub.cn/skills/org-b0bh4w8c/yun-zhi-geo）
- **目的**：让新站在生成式引擎（AI 搜索 / 摘要）中可见、被引用。
- **动作**：调用「GEO skill」（`Skill` 工具，`skill=<《依赖安装清单》中 DEP_GEO 登记的真实调用名>，来源 https://skillhub.cn/skills/org-b0bh4w8c/yun-zhi-geo），做实体识别、知识覆盖、引用可信度、FAQ / Citation 优化，对齐 GEO 评分体系后复检。

### 阶段 16 · 询盘 → 调用「网站获客 skill」（https://skillhub.cn/skills/org-b0bh4w8c/yun-zhi-website-leadgen）
- **目的**：把流量转化为可跟进的询盘线索。
- **动作**：调用「网站获客 skill」（`Skill` 工具，`skill=<《依赖安装清单》中 DEP_LEADGEN 登记的真实调用名>，来源 https://skillhub.cn/skills/org-b0bh4w8c/yun-zhi-website-leadgen），按"流量入口 → Landing → 产品页 → CTA → Contact → Form → 提交 → Thank You → Lead"漏斗体检并优化表单与 CTA；表单实现优先复用建站助手的系统动态表单 / 产品询盘能力。

### 阶段 17 · Preview（预览）
- **目的**：在推送线上前让用户看到真实效果。
- **动作**：通过建站助手取得预览地址 / 渲染结果；逐页面、逐组件核对桌面端与移动端；对照《页面规划表》检查数据绑定、CTA、表单可达性。发现问题回到对应阶段迭代。

### 阶段 18 · Publish（发布）
- **目的**：安全上线。
- **动作**：经用户确认后，通过建站助手 MCP 执行 `set_home_page` / `clear_site_cache` 等上线动作；发布后回读线上页面确认；输出《上线确认清单》与后续运营建议（SEO/GEO 持续监测、询盘跟进）。

## 全局约束

- **写入前确认目标站点**：基于同一站点改版时，站点 MCP 已在『前置输入』选定模式的当下确认（已持有则列出站点信息确认，未持有则索取后复核）；基于外部网站改版时，须在进入首次写操作（备份目标站已有页面）前完成阶段 10 的目标站 MCP 获取 / 站点确认。两者共同要求：若 Agent 已持有 MCP 信息，须先经 MCP 拉取站点信息让用户确认「是否操作此站」，确认非目标站时请用户重新提供正确的目标站 MCP 信息。MCP 信息已含站点标识，无需单独再问新站信息。
- **生成前必问备份**：进入「备份目标站已有页面」阶段前，必须询问用户是否需要备份目标站现有页面；若需要，使用阶段 10 已确认的 MCP 拉取目标站现有页面代码并另存为 `XX_backup` 页面（原样另存，不修改、不覆盖原页面），输出《目标站备份清单》。注意：备份对象始终是**目标站已有页面**，原外部站点（内容来源）无需也不应备份。
- **改版模式决定迁移策略**：开工前必须确认「基于同一站点」还是「基于外部网站」。基于同一站点改版时，产品 / 文章 / 图片等既有数据不重传；自定义表单由用户选择「新建 / 修改」，询盘表单只能「修改 / 不动」，不得新建询盘表单（复用系统既有询盘能力）。
- **引用关系不可省略**：生成与迁移内容阶段必须调用「建站助手」，SEO / GEO / 询盘阶段分别调用 『依赖与引用』所列外部 skill；这些外部 skill 仅用于生成新站与后续优化，属内部实现细节。
- **依赖未就绪不得调用**：任何外部 skill 调用前，必须先在《依赖安装清单》登记其调用名（即阶段 0 已安装）；未安装则按『依赖安装协议』安装后再调用。禁止调用尚未安装 / 清单中不存在的 skill 名，也禁止假定 `jian-zhan-skill` / `seo-skill` / `geo-skill` / `website-leadgen` 等文件名即调用名——一律以该平台 skill 的 SKILL.md 的 `name` 字段为准。
- **先规划后生成**：未产出《信息架构》《页面规划表》《组件规划表》前，不进入连接站点 / 生成阶段。
- **写操作确认**：任何上线 / 删页 / 清缓存 / 覆盖动作，遵循建站助手的写操作确认规则，先展示影响再执行。
- **保留旧站 SEO 权重**：凡涉及 URL 变化的，必须产出映射表并随 SEO 阶段处理 301。
- **可复用优先**：产品 / 文章 / 表单 / 公共头尾优先用系统动态能力，不在页面硬编码可由系统获取的业务内容。
