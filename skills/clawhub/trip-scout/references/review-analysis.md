# 差评分析引擎

## 核心原则

**不是所有差评都一样重要。** 成长性差评可以忽略，本质性差评必须拉黑。

## 差评分类矩阵

| 类型 | 关键词 | 处理方式 | 信任影响 | 示例 |
|------|--------|----------|----------|------|
| 🟢 **成长性差评** | 装修味、新开业、服务响应慢、磨合期、还在调试 | **忽略** — 随时间改善 | 无 | "刚开业有点味道"、"服务还在磨合" |
| 🟡 **可接受差评** | 排队久、价格贵、停车远、位置偏、隔音一般 | **记录** — 不影响推荐 | 无 | "节假日排队1小时"、"停车费贵" |
| 🔴 **本质性差评** | 卫生问题、态度恶劣、安全隐忧、设施严重不符、欺诈、强制消费 | **拉黑** + 通知用户 | 降品牌信任 | "房间有蟑螂"、"前台态度极差"、"实际与图片严重不符" |
| ⚫ **系统性差评** | 加盟管理混乱、频繁换名、挂牌卖质、管理方频繁更换 | **拉黑** + 标记加盟风险 | 降品牌信任 | "原来是XX酒店改名的"、"管理很乱" |

## 关键词库

### 🟢 成长性关键词（可忽略）

```
装修味 / 甲醛 / 新开业 / 还在磨合 / 服务还在提升 / 还在调试
设施还在完善 / 员工培训中 / 刚开业不久 / 开业才X个月
```

### 🟡 可接受关键词（记录不拉黑）

```
排队 / 等待久 / 价格贵 / 性价比低 / 停车远 / 停车不方便
位置偏 / 交通不便 / 隔音一般 / 房间小 / 早餐一般
 wifi慢 / 空调声音大 / 水压低
```

### 🔴 本质性关键词（拉黑）

```
脏 / 卫生差 / 有虫 / 蟑螂 / 老鼠 / 异味(非装修)
态度差 / 态度恶劣 / 服务差 / 不处理 / 推诿
不安全 / 门锁坏 / 消防 / 安全隐患
图片与实际严重不符 / 欺诈 / 强制消费 / 临时涨价
设施损坏 / 热水没有 / 空调坏了 / 电视坏了
```

### ⚫ 系统性关键词（拉黑+加盟标记）

```
原来是XX酒店 / 原名XX / 改名 / 翻牌 / 换了管理方
管理混乱 / 管理方换了 / 员工流动大 / 经常换人
挂大牌卖小店 / 品牌标准不符 / 和官网图片差太多
加盟 / 个体经营
```

## 分析流程

```
收到酒店评价
  │
  ├─ 1. 提取差评内容
  │
  ├─ 2. 关键词匹配
  │   ├─ 匹配🔴本质性 → 触发拉黑流程
  │   ├─ 匹配⚫系统性 → 触发加盟识别
  │   ├─ 匹配🟢成长性 → 标记"可忽略"
  │   └─ 匹配🟡可接受 → 标记"记录"
  │
  ├─ 3. 统计各类占比
  │   └─ 成长性差评占比 > 50% → 整体评价上调
  │
  ├─ 4. 输出分析结果
  │   └─ 写入搜索结果的"差评分析"字段
  │
  └─ 5. 触发后续动作
      ├─ 本质性差评 → 写入 blacklist.md + 降品牌信任
      └─ 系统性差评 → 标记加盟风险 + 检查改名记录
```

## 携程差评量化规则(强制, 防以偏概全)

不能只凭问道摘要(代表性1-2条)下结论, 必须按以下量化标准抓取与阅读:

### 时间范围与条数

| 维度 | 规则 | 理由 |
|------|------|------|
| **时间范围** | 近 **12 个月** | 近期口碑最能预测入住体验; 一年前可能已改善/恶化, 权重低 |
| **全量评价触发(优先判断)** | 开业≤1年 **或** 评价量≤100 → 抓取**全部评价**(`--all`), 跳过下方差评专属规则 | 新店/小店差评样本过少, 差评率与分类都失真; 全量+评分分布更可信 |
| **差评条数(评价量>500, 开业>1年)** | 读差评前 **30-50 条** | 大店差评多, 取近一年最相关的前30-50条分类 |
| **差评条数(100<评价量≤500, 开业>1年)** | 读 **全部差评** | 中小店差评少, 全读避免漏 |
| **近期趋势** | 单看近 **3 个月**差评突增 | 突增=近期恶化⚠️(如新换管理/翻牌), 即使近12个月整体尚可也要警示 |

### 获取路径(按优先级)

1. **脚本抓取**(主, 推荐): `python scripts/ctrip_reviews.py <hotelId> --months 12 --pages 20`
   - **Playwright + API 双轨模式**：API优先(快) -> 浏览器降级(稳)
   - 需要先登录携程：`python scripts/ctrip_reviews.py login --show`（首次扫码，Cookie自动持久化，路径由脚本管理）
   - 检查登录态：`python scripts/ctrip_reviews.py check-login`
   - API模式：从浏览器Cookie提取后调用移动端REST API(`soa2/34308/getHotelCommentInfo`)，批量抓取速度快
   - 浏览器模式：Playwright操控真实浏览器访问携程评论页，逐页提取，稳定但较慢
   - 脚本自动分类(成长性/可接受/本质性/系统性)+统计占比+近3月趋势+踩雷风险
   - hotelId 从携程酒店详情页 URL 取(`hotelid=XXXX`)
   - ⚠️ **首次使用必须先登录**，否则API返回空结果(携程对无Cookie请求静默返回totalCount=0)

#### ⚠️ API模式 vs 浏览器模式的差评差异(实战经验, 2026-07-08验证)

**关键发现：携程"差评"的定义 ≠ 评分≤3。** 携程用自有NLP分类判定差评，API无法复现此判定。

| 模式 | 差评来源 | 准确性 | 速度 | 适用场景 |
|------|---------|--------|------|----------|
| API | 抓全部评论->用评分≤3过滤 | ❌ **严重漏差评** | 快(~10s/200条) | 差评率统计(全部评论+评分) |
| 浏览器 | 点击携程"差评"标签->抓标签下评论 | ✅ **精确** | 慢(~60s/8条) | 差评内容分析(分类/趋势) |

**实测对比（赛里木湖亚朵见野, hotelId=133232577）**:
- 携程差评标签显示: **差评(11)**
- API模式(评分≤3过滤): 仅抓到 **1条** (漏90%)
- 浏览器模式(差评标签): 抓到 **8条** (页面最大显示数)

**正确策略：双轨并用**
```
1. API模式跑一遍 -> 拿到总评论数+评分分布+差评率(粗略)
2. 浏览器模式跑一遍 -> 拿到差评标签下的精确差评(用于分类分析)
3. 以浏览器模式的差评做分类/趋势/踩雷风险判断
```

**脚本参数**:
- `python scripts/ctrip_reviews.py <hotelId>` -> 默认API优先, 失败降级浏览器
- `python scripts/ctrip_reviews.py <hotelId> --no-api` -> 强制浏览器模式(差评精确, 推荐)
- `python scripts/ctrip_reviews.py <hotelId> --pages 20` -> API模式翻20页

#### hotelId搜索正确方法(实战经验)

**❌ 错误方式**：URL拼接keyword
```
hotels.ctrip.com/hotels/list?keyword=奎屯亚朵  -> 携程默认显示"安庆"酒店(BUG)
```

**✅ 正确方式**：全局搜索框 + 下拉列表url属性
```
1. 打开 https://hotels.ctrip.com/
2. 在顶部全局搜索框 #_allSearchKeyword 输入酒店全名
3. 下拉列表项 .search_list_hotel 的 url 属性含hotelId:
   url="http://hotels.ctrip.com/hotel/132338651.html?cityid=39"
4. 正则 /hotel/(\d+)/ 提取hotelId
```

**脚本内置**：`from ctrip.reviews import search_hotel_id; search_hotel_id("酒店全名")` 自动完成上述流程。

**CLI方式（推荐）**：
```bash
# 精确搜索：输入酒店全名，返回hotelId
python scripts/ctrip_reviews.py search "乌鲁木齐城投万达锦华酒店"

# 模糊搜索：输入目的地+关键词，返回多个结果
python scripts/ctrip_reviews.py search "赛里木湖 酒店" --limit 5

# 问道说"无该店"时的兜底：用search命令验证酒店是否存在
python scripts/ctrip_reviews.py search "伊宁绿发洲际酒店"
```

**注意**：搜索时输入**酒店全名**（如"乌鲁木齐城投万达锦华酒店"），不要简写。全局搜索框不需要先输目的地城市，直接输酒店全名即可。

#### 差评数量不一致说明

携程差评标签显示的数字（如"差评(11)"）与页面实际显示的评论数（8条）可能不一致。原因：标签数字可能包含已删除/历史评论。**以实际抓取到的为准**，标签数字仅作参考。无分页器时（差评<10条），页面显示的就是全部可抓取的差评。

   - ⚠️ 问道只给代表性摘要, 可能漏差评; 会话常被锁定。
   - ⚠️ **绝不能只用问道做差评分析**--违反强制规则，必须先跑脚本
3. **美团 meituan-travel (补充, 跨平台评分交叉验证)**: `MEITUAN_RAW_JSON=1 npx --yes @meituan-travel/ht-ai@latest query --query '<酒店名 日期 房型>' --origin-query '<同>' --channel meituan-developer`
   - 返回 `{"status","data":<Markdown>}`, 从 Markdown 提取 **美团真实评分 + 起步价 + 开业时间 + AI口碑摘要**
   - ⚠️ **AI摘要, 不做差评量化依据** (无评价量/评价列表/时间分布), 定位同问道: 补充非替代
   - 价值: 携程 vs 美团评分交叉验证; 稀疏评价酒店 (开业≤1年/评价量≤100) 补第二平台信号

4. **脚本完全不可用时的降级**:
   - 登录态过期 -> 重新 `python scripts/ctrip_reviews.py login --show`
   - 被风控/验证码 -> `python scripts/ctrip_reviews.py <hotelId> --show`（显示浏览器窗口手动过验证码）
   - 全部失败 -> 只用问道摘要，**必须在输出中标注"⚠️ 未量化分析(脚本不可用)"**

### 强制执行规则(防AI偷懒)

1. **每个候选酒店的差评分析，必须先调用 `python scripts/ctrip_reviews.py`**
2. 脚本调用失败时，**必须在输出中标注原因**（如"⚠️ 未量化分析：脚本被风控/API返回空"）
3. **绝不能跳过脚本直接用问道摘要**——问道是补充，不是替代
4. 所有候选酒店的开业时间**必须逐一搜索**，不能选择性遗漏（如搜了万达文华2016但漏搜希尔顿2015）
5. 脚本返回数据为空时 → 检查登录态(`check-login`) → 重新登录 → 重试

### 两边都负面时的决策

原酒店A 和 备选B 都有负面 → **不是选负面少的, 而是选本质性差评轻的**:

```
比较 A 和 B 的:
  1. 差评类型: 成长性(可忽略) < 可接受(记录) < 本质性(拉黑) < 系统性(拉黑+加盟)
  2. 本质性+系统性差评占比(条数/总评价量)
  3. 严重度: 卫生/安全 > 服务 > 设施
  4. 时效性: 近3个月 > 近12个月 > 更早(近期权重高)
→ 选占比低、严重度轻、非近期恶化的一家
→ 若都严重 → 两家都放弃, 扩大搜索找第三家
```

## 多维度综合分析

差评分析回答"能不能住", 多维度分析回答"住得好不好"。两者并行, 不可互相替代。

### 8个评价维度

| 维度 | 说明 | 主数据源 |
|------|------|----------|
| 安静/隔音 | 房间隔音、临街噪音、空调噪音 | 携程评价 |
| 卫生 | 房间/卫生间清洁度、床品、异味 | 携程评价 |
| 设施 | 空调/热水/wifi/电视/健身房/泳池 | 携程评价 |
| 早餐 | 早餐品种/口味/含早 | 携程评价 |
| 服务 | 前台/客房服务态度与响应速度 | 携程评价 |
| 特色 | 设计风格/文化特色/独特体验 | 携程评价 |
| 位置 | 距景区/交通/通勤便利性 | 携程评价 + 高德POI |
| 周边 | 餐饮/购物/夜生活/配套 | 携程评价 + 高德POI |

### 数据获取路径(按优先级)

1. **携程全量评价**(主): `python scripts/ctrip_reviews.py <hotelId> --dimensions`
   - 抓取近 **2 年(24 个月)** 全量评价(非仅差评), 最多 **1000 条**(约 100 页, API 每页 10 条)
   - API 模式优先(快), 失败降级浏览器模式
   - 脚本自动对每条评价做 8 维度关键词命中检测, 输出各维度评分
   - 同时输出差评分析(复用现有分类引擎), 一条命令两份报告
   - hotelId 获取方式同差评分析: `python scripts/ctrip_reviews.py search "酒店全名"`
   - 首次使用需先登录: `python scripts/ctrip_reviews.py login --show`

2. **携程问道 API**(维度专项补充): 针对覆盖率低的维度专项提问
   - 示例: "赛里木湖城际酒店的隔音怎么样? 早餐如何? 周边有什么吃的?"
   - 问道摘要作为定性补充, 不做量化依据(同差评分析原则)
   - 覆盖率 < 5% 的维度(评论中很少提及), 用问道交叉补信号

3. **飞猪**(评分交叉): `flyai search-hotel --dest-name "目的地" --key-words "酒店名"`
   - 提取飞猪评分, 与携程评分交叉验证
   - 分歧 > 0.5 标注"跨平台口碑分歧"（同差评分析规则）

4. **高德地图**(位置+周边维度量化): `amap-lbs-skill poi-search`
   - 餐饮: `keyword=餐厅 radius=1000m` -> 周边餐饮数量
   - 景点: `keyword=景点 radius=3000m` -> 最近景点距离
   - 交通: `keyword=机场 radius=50000m` -> 交通便利性
   - 量化补充"位置"和"周边"维度的客观数据, 弥补评论主观偏差

5. **美团 meituan-travel**(辅助): `MEITUAN_RAW_JSON=1 npx --yes @meituan-travel/ht-ai@latest query --query '<酒店名 日期 房型>'`
   - 开业时间: 用于判断"成长性差评降权"
   - AI 口碑摘要: 定性参考, 非量化依据
   - 美团真实评分: 第三平台交叉验证

### 评分规则

#### 关键词命中检测

每条评价文本对 8 个维度分别做关键词命中检测:

- 命中**正面关键词**且不命中负面 -> 该维度正面计数 +1
- 命中**负面关键词**且不命中正面 -> 该维度负面计数 +1
- 同时命中正负面 -> 取负面(用户体验对负面更敏感)

#### 维度评分计算

```
对每个维度D:
  positive_count = 命中正面关键词的评论数
  negative_count = 命中负面关键词的评论数
  total_mentions = positive_count + negative_count
  coverage = total_mentions / total_reviews  (该维度被提及率)

  if total_mentions == 0:
      score = None  (数据不足)
      verdict = "数据不足"
  else:
      positive_rate = positive_count / total_mentions
      score = positive_rate * 10  (0-10分)
      verdict = 优秀(>=8) / 良好(>=6) / 一般(>=4) / 较差(<4)
```

## 特殊场景处理

### 新开业酒店

- **开业 ≤ 12个月: 触发全量评价抓取**(`--all`, 详见上方"全量评价触发"), 差评样本过少, 改以全部评价+评分分布为分析依据, 跳过浏览器差评专属分析
- 开业 < 6个月: 成长性差评关键词自动匹配
- 开业 < 12个月: 装修味/服务磨合类差评降权
- 开业 > 12个月: 正常分析

### 加盟翻牌店

- 发现改名记录 → 自动标记为加盟翻牌
- 检查改名前的差评 → 作为当前酒店的参考
- 用户已拉黑的翻牌店 → 同品牌同城同级别全部跳过

### 评分异常

- 同品牌不同店评分差异 > 1.0 → 标注"品控不稳"
- 携程评分 vs 美团真实评分分歧 > 0.5 → 标注"跨平台口碑分歧⚠️"
- 评价量 ≤ 100 → **触发全量评价抓取**(`--all`, 详见上方"全量评价触发"), 并标注"评价不足, 参考价值有限"
- 近30天差评突增 → 标注"近期口碑下降"
