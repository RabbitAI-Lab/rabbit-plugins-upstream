# 审稿核验器（Claim-to-Source Auditor）

## 何时使用

- 发布前对长文、报告或分析做事实核验。
- 核验已发布主张是否仍成立。
- 检查同一文章多平台版本的事实一致性。
- 审计学术引用、监管结论、财务数字、内部数据或直接引语。
- 建立回归 gold-set 以便未来修订时检查事实回归。
- 跨事件事实、平台表述与作者判断验证外部事件的归因是否正确。

## 不适用

- 风格编辑、结构批评或论证强度评估——本 Skill 只审计事实主张及其来源支撑。
- 跨材料口径/数字一致性 → 用 `cross-material-consistency-auditor`。
- 营销稿完整发布前合规 → 用本地已安装的专门合规审查 Skill。

## 架构

默认采用固定工作流、shadow 模式运行——读取输出、对比来源、产出审计表。除非用户明确要求修订，否则不修改源文章。始终将审计与编辑分离。目标：每批文章 30–50 条高风险主张。高风险指：具体数字、日期、百分比、金额、监管结论、具名个人、机构隶属、直接引语、论文细节、事件归因。

## 证据分级

| 级别 | 定义 | 示例 |
|---|---|---|
| L0 一手 | 原始、可核验、未过滤 | 法院判决、官方监管文本、公司备案、原始运营日志、作者本人社媒原帖、arXiv 预印本 |
| L1 可靠二手 | 具名来源的可靠报道 | Bloomberg、Reuters、The Register、Fortune、带 DOI 的同行评审期刊 |
| L2 补充 | 间接或未核验 | 聚合媒体摘要、引用但不引述原文的档案、论文的 LLM 生成摘要 |

- 仅当 L0 或 L1 支撑时主张才能通过。
- L2 可支撑部分通过或解释缺口，但不能单独使主张通过。
- L0 与 L1 冲突时同时呈现并标出冲突。

## 工作流

### 步骤 1：[LLM] 提取高风险主张

从正文提取属于以下任一类的主张：具体数字或百分比；日期/时间范围；具名者直接引语；金额；监管结论；论文细节；具名机构/角色/隶属；归因或归责的事件摘要。每条记录：主张文本、类别、行/节引用、事实还是作者判断。

### 步骤 2：[确定性] 收集可用证据

对每条主张识别本地可用来源（研究库、内部运营日志、既往核验报告、干净 gold-set）；需外部核验的，搜索官方判决、公司公告、监管文本、社媒原帖、可信媒体。

### 步骤 3：[LLM] 分类每条主张

五种状态：通过（L0/L1 直接支撑原文主张）；部分支持（核心事件/数字存在，但文本夸大范围、因果、精度或法律含义）；缺证（无 L0/L1，仅 L2 或无来源）；错误（L0/L1 直接矛盾）；判断（合理作者分析，单一来源无法证伪）。严重度：P0 须在下次发布前修正（错误作者、错误数字、伪造或不可引述引语、错误监管主张）；P1 应收紧或补源；P2 可接受仅附 minor 来源注。

### 步骤 4：[LLM] 跨平台核验

同一文章多语言/多平台时，逐条核对高风险主张：数字、日期、人名是否一致；来源标注是否每版都有；监管结论翻译有无增减含义。标记为 一致 / 近似 / 偏差 / 错误。

### 步骤 5：[LLM] 事故归因三层分离

描述真实事件时拆为三层：公认发生的事实；平台或相关方如何描述；作者如何解读。仅第一层可作为已核验事实，二三层不得混写为同一件事。

### 步骤 6：[确定性] 留存回归 gold-set

每次审计后将主张列表与结论存为 CSV；文章修订时重跑同一批主张检查回归。曾 通过 现失败即记为回归事件。

### 步骤 7：[LLM] 产出审计报告

含：文章名、平台、审计日期；汇总计数（总主张、各状态按严重度）；P0 清单；跨平台比对；与既往 gold-set 的回归检查；来源登记（含 URL）。

## 硬规则

1. 仅 L0/L1 可使主张通过，L2 仅补充。
2. 论文、判决、监管文本绝不静默篡改；任何转述/翻译/修正须显式标注，绝不把转述当直接引语。
3. 用户接受后已发布文章可直接修订，但对论文引用/判决/监管参考的每次改动须带标注。
4. 分离事件事实、平台/方归因与作者解读，不得压缩为一句。
5. 监管材料定义特定司法辖区要求，不得压缩为普适禁止。
6. 既往核验报告是回归 oracle，不是当前版本干净的证明；逐条历史 P0/P1 须与当前文本比对。
7. 无可核验来源的主张默认判 缺证，而非 通过。
8. 绝不编造证据填补缺口；找不到来源就报告为缺口。

## 易错点

- 不可仅因文件夹名为 `drafts` 就推断本地文件未发布；用户、CMS 记录或发布日志才是权威。
- 文章中找不到出处的直接引语即 P0，即使周围故事属实。
- 近似数字仍是不一致；源为 5817 而审计写 5810 必须标出。
- 跨平台年份高风险；一版"2024"另一版"2025"是错误而非转述。
- 监管文件存在于特定司法辖区，未查管辖文本不得写"FDA、EU MDR、中国监管都说一样"。

## 故障处理

| 场景 | 处理 |
|---|---|
| 来源付费墙或受阻 | 标 缺证，注明来源不可用 |
| 一手与二手冲突 | 同时呈现原文引述，标出冲突 |
| 涉及未来预测 | 标 判断，不作事实 |
| 外文监管文本 | 有官方译本用译本，否则标 部分支持 并注明语言限制 |
| 内部运营日志不可用 | 标 部分支持，注明缺哪份日志 |
| 既往已核验主张现失败 | 标 gold-set 回归，升级 P0 审查 |

## 核查清单

- [ ] 每个 P0 都有具体来源反驳或无法支撑该主张。
- [ ] 跨平台审计表覆盖每平台相同主张。
- [ ] gold-set CSV 干净加载且行数与当前审计一致。
- [ ] 论文作者、期刊名、案号、年份与原始来源核对，而非中介档案。
- [ ] 审计报告说明哪些主张无法核验及原因。

## 输出格式

1. **审计问题 CSV**：每主张一行，列含 claim-id、article、claim-text、status、severity、evidence-summary、required-action。
2. **审计报告**：结构化 Markdown，含汇总表、P0 清单、P1 摘要、跨平台比对、回归检查、来源登记、最终 pass/fail/conditional 结论。
3. **gold-set CSV**（可选，用于回归）：每主张一行，含最近一次审计结论。

先给结论，再给证据、边界与下一阶段动作。
