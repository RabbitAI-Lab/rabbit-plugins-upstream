# 善后与横向定损检查单

> 目的：避免“只修当前主机、不查同源风险”的常见失误。  
> 适用：Linux / Windows / 数据库 / 应用 / 云上资产。

## 1. 先回答这 5 个问题
1. 初始入口是什么（漏洞、弱口令、钓鱼、供应链、BadUSB、数据库暴露）？
2. 攻击者拿到了什么权限（普通用户、管理员、域用户、root/system）？
3. 是否发生横向移动？
4. 是否发生数据窃取或额外投递？
5. 是否建立持久化或留下攻击遗产？

## 2. 横向扩面优先清单
- 与受害资产使用**相同密码**的服务器/账号
- 部署了**相同漏洞版本/相同服务**的服务器
- 由**同一管理员/同一运维组**维护的服务器
- 与受害资产存在**互信关系**的服务器
  - SSH key
  - RDP 保存凭据
  - 域信任
  - 自动同步/备份代理
- 在受害时间段与其**高频交互**的主机
- 同业务集群、同网段、同堡垒机可达资产

## 3. 善后最低动作
- 修改高风险凭据（口令、SSH key、token、数据库口令、API key）
- 清理已知持久化（计划任务、systemd、服务、启动项、WMI、sudo/PAM、授权文件）
- 修补系统与应用漏洞
- 恢复被替换或被投毒的命令、脚本、配置、软件包
- 加固暴露面（绑定地址、边界策略、邮件/网关、MFA、最小权限）
- 重点资产补做备份和恢复演练

## 4. 需要形成的交付物
- 受害范围清单
- 关联资产扩面清单
- IOC 清单
- 时间线
- 根因与修复说明
- 仍存风险与待办项
- 新增检测规则/阻断规则

## 5. 复盘必须沉淀的问题
- 哪个日志源最关键？哪些日志缺失？
- 哪个检测最早能发现？为何没发现？
- 哪个操作最容易误伤业务？
- 哪些处置动作需要以后默认走 HITL？
- 这次事件能沉淀成哪类模式（候选，不直接合并主库）
