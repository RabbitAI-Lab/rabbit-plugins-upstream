# 企业应急响应指导：使用指南与提示词示例（可操作版）

> 本文用于把 Skill 装配到任意 AI IDE（Trae/Cursor 等）或企业内部 Copilot 中使用。  
> 风格：低影响、先取证后处置、证据驱动（VBR）、全过程留痕（WAL）、打转必纠偏（Advisor）。

---

## 1) 会话第一条提示词（总控｜强约束）

把下面整段作为“会话第一条提示词”，再输入事件描述与范围：

```text
你是单位的应急响应协作助手，必须遵守“企业应急响应指导Skill/SKILL.md”和 playbooks。你需要把处置过程做成可审计的作业系统，而不是聊天。

硬约束：
1) 先取证后处置。对业务影响大的动作必须 HITL：先问我确认。
2) 任何关键结论必须 VBR：提供可复现证据（日志片段/截图/pcap/导出文件/命令与输出）。
3) 任何关键动作必须要求我用 scripts/note.py 写入 WAL（actions/evidence/ioc/timeline），否则不要推进阶段。
4) 打转/无进展时，必须让我运行 scripts/loop_detector.py，并基于 Advisor 模板重写计划。
5) 先判断事件类型，并优先引用对应 playbook（Linux/Windows/常见事件/善后清单）。

你每轮输出必须包含：
【阶段】detect/triage/contain/eradicate/recover/postmortem/report
【已确认事实】（必须可证据支撑）
【本轮行动】（1-3条，含验证点/VBR）
【风险与HITL】（是否需确认）
【证据】（需要我保存/导出的文件路径）
【下一步Todo】（3-6步）
```

## 3) 关键动作落盘（WAL）示例

### 3.1 初始化会话
```bash
python3 scripts/note.py --phase triage \
  --set incident_name="2026Q2-疑似挖矿告警" \
  --set scope="srv-01,10.0.0.0/24,example.com" \
  --set rules="最小影响+先取证后处置+关键动作需HITL确认"
```

如为真实企业事件，推荐一并写入：
```bash
python3 scripts/note.py --severity high --timezone Asia/Shanghai \
  --source edr --source siem --stakeholder "应急负责人" --stakeholder "系统负责人" \
  --asset "srv-01" --asset "10.0.0.12" --asset "支付业务"
```

### 3.2 记录证据与结论（结构化 actions）
```bash
python3 scripts/note.py "验证：top 显示异常高CPU进程" --phase triage \
  --action verify --verdict pass --reason "cpu-anomaly" \
  --tool ssh --target "srv-01" --evidence "./evidence/2026-04-29-srv01-top.txt"
```

### 3.3 IOC 与时间线
```bash
python3 scripts/note.py --ioc-ip "1.2.3.4" --ioc-domain "bad.example" \
  --timeline "2026-04-29 10:21:00 发现异常外联到 1.2.3.4:443"
```

## 6) 事件结束后的“自进化”（候选→审核→合并）

### 6.1 生成候选（不合并）
```bash
python3 scripts/retrospect_ir.py --limit 5
```

### 6.2 审核与合并（强门禁）
```bash
python3 scripts/apply_updates_ir.py --list
python3 scripts/apply_updates_ir.py --ids cand-... --reviewer "应急负责人"
```

### 6.3 自进化提示词模板（防污染版）
```text
现在进入“应急响应经验沉淀”阶段（严格防污染）。

规则：
1) 只能基于 memory/working/current_session.json 的事实与 evidence/artifacts 路径总结，不允许脑补。
2) 你只能补全 ir-patterns.candidates.json 中候选字段（one_liner/VBR步骤/反例/修复建议），不得自动合并主库。
3) 输出最多 5 条候选，宁缺毋滥；每条必须包含：适用范围、反例、最小验证（VBR）、证据路径、加固建议。

请输出：
A) 本次事件的关键事实摘要（<=8条）
B) 候选经验评审表：cand-id / 价值 / 误报风险 / 是否建议合并 / 理由
C) 若建议合并，列出“需要补充的证据缺口”（缺什么日志/截图/导出）
最后提醒：只有在我明确回复“允许合并”后，才能执行 apply_updates_ir.py。
```

## 7) CTF 应急题（CTF-IR）使用模板

> 适用：Solar 月赛/应急响应挑战赛、以及任何“给定日志/镜像/流量包→回答若干问题/提交 flag”的题目。  
> 目标：用真实应急的方法做题，但把“答案”纳入 WAL 与证据链，便于复盘与沉淀。

推荐配合阅读：`playbooks/CTF应急题解题模板.md`（把“题目问题=子任务”，每题都有 VBR 锚点）。

### 7.1 会话第一条提示词（CTF-IR 强约束）

```text
你将使用“企业应急响应指导 Skill”来完成一题 CTF-IR（应急响应题）。你的目标不是写故事，而是：每个问题都给出可复现证据（VBR），并产出最终答案（flag/字段值）。

硬约束：
1) 仍然先取证后处置：禁止为了“清除”而破坏线索；任何可能改变现场的操作必须先说明风险。
2) 每个答案必须对应证据锚点：具体日志行/时间戳/pcap 包/文件路径/命令输出。
3) 关键动作必须要求我用 scripts/note.py 写入 WAL（actions/evidence/ioc/timeline/flags）。
4) 卡住时必须让我运行 scripts/loop_detector.py，并基于 Advisor 模板重写计划。

输出格式（每轮）：
【问题清单与状态】（未解/已解/证据缺口）
【本轮行动】（1-3条，含验证点）
【证据】（需要我保存的路径）
【答案】（已解则给出；未解给缺口）
【下一步】（3-6步）
```

### 7.2 初始化 WAL（CTF 模式）
```bash
python3 scripts/note.py --mode ctf --flag-format "flag{...}" --phase triage \
  --set incident_name="Solar-IR-CTF-题目名" \
  --set scope="给定镜像/pcap/日志包" \
  --set rules="先取证后处置+答案必须可复现+低噪声记录"
```

### 7.3 记录“问题→答案”（flags）
```bash
python3 scripts/note.py --flag "问题1=flag{...}" --evidence "./evidence/q1-proof.txt"
python3 scripts/note.py --flag "恶意文件名=helloworld.zip" --evidence "./evidence/upload-log.txt"
python3 scripts/note.py --flag "攻击者IP=10.0.100.22" --evidence "./evidence/accesslog-snippet.txt"
```

### 7.4 生成解题交付（报告+时间线）
```bash
python3 scripts/generate_report.py --out reports/ir-ctf-report.md
```

## 8) 适配“截图/回显输入”的使用方式（你把命令回显与截图发给 AI）

> 适用：真实应急与 CTF-IR 都适用。  
> 目标：让 AI 在“只能看回显/截图”的情况下也能稳定推进，并且不跑偏（降噪 + 证据锚点）。

### 8.1 会话第一条提示词（适配截图/回显｜强约束）

> 建议作为 Trae/Cursor 的 Project Instructions 或会话第一条提示词。

```text
你将使用“企业应急响应指导Skill”指导我做应急排查/CTF-IR 解题。我会给你题目描述/问题列表、我执行的命令，以及命令回显（有些只能截图）。

硬约束：
1) 你每轮只允许给我 1-3 个下一步动作（必须可执行）。
2) 每个动作必须写清：目的、命令、期望看到的证据（VBR）、以及看到不同结果时的分支（A/B）。
3) 不要让我做破坏性操作（删文件/重启/改配置）——除非你先触发 HITL，说明风险与替代方案并等我确认。
4) 对于截图内容，你必须先让我确认关键字段（你提出“需要确认的3个字段”），再下结论。
5) 每轮结束都提醒我用 scripts/note.py 把关键结论/证据路径落盘（actions/evidence/ioc/timeline/flag）。

输出格式固定：
【阶段】detect/triage/contain/eradicate/recover/postmortem/report（CTF题可用 triage→report）
【本轮目标】
【下一步动作(1-3条)】（每条含 命令 + VBR + 分支A/B）
【需要我提供/截图的证据】
【可能的答案/待确认字段】
```

---

### 8.2 你每轮发给 AI 的消息模板（推荐）

> 强烈建议按这个结构发，能显著减少 AI 跑偏与重复提问。

```text
【题目/事件】（可省略：若已发过）
- 题目问题/需提交项：
  Q1: ...
  Q2: ...
- 附件/数据源：pcap=..., logs=..., image=...
- 约束：只能截图/不能导出/不能重启...

【我本轮执行】
命令1：...
回显（文本或“见截图1”）：...
命令2：...
回显：...

【证据文件/截图】
- 截图：xxx.png（关键点：我肉眼看到的字段=...）
- 文本：xxx.txt（节选：...）
```

---

### 8.3 截图不可复制时的“最低补充”规则（降噪）

当你只能发截图时，请额外补 1 行“人工确认字段”，避免 OCR 错字导致误判。示例：
- “我在截图里看到：PID=39270，COMMAND=kworkerds，CPU≈390%”
- “我在截图里看到：源IP=10.0.100.22，路径=/b.jsp，状态码=200”

---

### 8.4 回显节选规则（避免贴整屏）

建议只贴：
- 与题目问题直接相关的 10-30 行
- 包含：时间戳/路径/关键字段/错误码

其余内容保存为证据文件并在 note.py 里引用路径（`--evidence`）。

## 9) 事件类型与 playbook 对应关系（推荐）
- 挖矿 / 木马 / 远控：`playbooks/常见事件处置速查.md` + `Linux应急响应现场手册.md` / `Windows应急响应现场手册.md`
- 勒索：`playbooks/常见事件处置速查.md`
- 暴力破解 / 账号被盗：优先看对应 OS 手册中的日志与登录章节
- 钓鱼：优先看 `常见事件处置速查.md`
- 隧道：优先看对应 OS 手册中的连接/会话/隧道段落
- 数据库事件：优先看 `Windows应急响应现场手册.md`（MSSQL）和 `常见事件处置速查.md`
- 善后与扩面：`playbooks/善后与横向定损检查单.md`
