# 断言类型目录（Assertion Catalog）

执行网页回归测试时，在每一步的预期点插入断言。下表列出支持的断言类型、适用场景与自然语言→断言的映射示例。

## 语言 / Language

- 断言类型与用户输入语言无关：用户用中文或英文描述，都映射到下表同一类断言。
- 类别中英对照（便于英文用户定位）：

  | # | 中文 | English |
  |---|------|---------|
  | 1 | 元素存在/可见 | Element exists / visible |
  | 2 | 文本内容匹配 | Text content match |
  | 3 | URL 变化 | URL change |
  | 4 | 表单字段值 | Form field value |
  | 5 | 控制台无错误 | No console errors |
  | 6 | 网络请求成功 | Network request success |
  | 7 | 形态断言 | Shape assertion (dynamic content) |
  | 8 | 列表/表格内容 | List / table content |

## 1. 元素存在 / 可见

- **用途**：验证关键 UI 元素已渲染，如按钮、表单、弹窗。
- **自然语言示例**：
  - "登录按钮出现"
  - "提交后订单详情页可见"
- **失败判定**：元素在超时内未出现在 DOM 或不可见（display:none / 不在视口且未懒加载）。

## 2. 文本内容匹配

- **用途**：验证页面文案、提示、结果是否符合预期。
- **匹配模式**：
  - 包含（contains）：如"显示'下单成功'"
  - 等于（equals）：如"标题等于'我的订单'"
  - 正则（regex）：如"订单号形如 OD\\d{8}"
- **自然语言示例**：
  - "页面出现'支付成功'"
  - "错误提示等于'手机号格式不正确'"

## 3. URL 变化

- **用途**：验证流程跳转，如登录后跳首页、下单后跳支付页。
- **自然语言示例**：
  - "登录后 URL 变为 /home"
  - "点击提交后地址包含 /order/confirm"
- **匹配模式**：精确等于 / 包含路径 / 正则。

## 4. 表单字段值

- **用途**：验证输入是否生效、回填是否正确。
- **自然语言示例**：
  - "邮箱输入框值为 test@x.com"
  - "数量框回填为 2"

## 5. 控制台无错误

- **用途**：捕获 JS 运行时错误、未处理异常。
- **自然语言示例**：
  - "整流程控制台无 error 级日志"
- **注意**：忽略网络 4xx/5xx 中的预期项（如已知 404 资源），仅报告未预期的 error。

## 6. 网络请求成功

- **用途**：验证关键接口调用成功（状态码 2xx/3xx）。
- **自然语言示例**：
  - "点击下单后 /api/order/create 返回 200"
- **匹配**：状态码区间、响应体关键字段存在。

## 7. 形态断言（用于动态内容）

- **用途**：验证码、实时价格、随机订单号等不稳定内容，不精确匹配，只验证"形态"。
- **自然语言示例**：
  - "订单号包含数字且长度大于 8"
  - "价格字段为货币格式（¥ + 数字）"

## 8. 列表 / 表格内容

- **用途**：验证搜索、筛选、分页后的结果集，是最常见的一类断言（后台 / 列表页）。
- **自然语言示例**：
  - "搜索'姜令雨'后，结果列表包含该行"
  - "结果数 ≥ 1"
  - "列表首行收件人等于'姜令雨'"
- **匹配模式**：行文本包含（contains）／首行字段等于（equals）／结果计数 ≥ N。
- **注意**：先确认结果区已渲染（等待列表容器可见），再读取行文本；空结果应断言"无数据"提示而非报错。

## 断言设计原则

- 每个关键步骤至少 1 条断言，重要流程可设多条。
- 优先"用户可感知"的断言（文本 / URL / 元素），控制台与网络作为补充。
- 断言描述写进报告，便于人工复核。
- **SPA / 客户端路由**：现代后台多为前端路由，路由切换不触发 `wait --load`。等待策略改为"目标元素可见 / 列表容器出现"，而非依赖文档 load 事件。
