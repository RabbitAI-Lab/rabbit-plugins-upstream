# 治理决策框架（拆分 / 目录模式 / 场景决策）

## 一、单文档 vs 多文档拆分

### 拆分信号（满足任一即评估拆分）

| 信号 | 说明 |
|---|---|
| 受众不同 | PM 读 PRD、工程师读 DESIGN——受众不同则文档职责不同，必拆 |
| 更新节奏不同 | 一部分每迭代更新（进展）、另一部分一年不动（架构）→ 拆，避免高频编辑扰动低频内容 |
| 生命周期不同 | 迭代级内容与长期内容共存 → 拆（过程层 vs 项目层） |
| 体积超限 | 单文档 > 500 行且存在清晰的内部边界 → 评估拆 |
| 独立引用需求 | 某章节频繁被单独引用/评审/链接 → 拆出 |
| 权限/责任不同 | 不同 owner、不同评审流程 → 拆 |

### 合并信号（满足任一则不拆或回并）

| 信号 | 说明 |
|---|---|
| 必须同读 | 两文档必须合在一起读才能理解，拆分只增加了跳转成本 → 并 |
| 高耦合同步 | 任何变更都要同时改两处，且经常漏改 → 并 |
| 子文档过薄 | 拆出的文档只剩标题加几行 → 并 |
| 无独立读者 | 没有人会单独读其中一部分 → 并 |

### 决策流程

```
1. 列出该内容的受众、更新节奏、生命周期、owner
   → 任何一项存在分裂 → 按"拆"方向评估
2. 对照合并信号排除假拆分
3. 拆分成本核算：每次拆分必须同步做三件事——
   a) 更新 docs 索引  b) 建立/更新交叉链接  c) 确定每个新文档的 owner
   三件事不做，拆分即失败（产生孤儿文档）
4. 优先沿 doc-type 边界拆（那是职责边界），不沿"长度"拆
```

### 各类型的既定拆分规则（无特殊情况不重新决策）

| 类型 | 规则 |
|---|---|
| ADR | **永远一决策一篇**，不适用本框架 |
| TECH | 一主题一篇；重复主题合并 |
| PERSONA | 一画像一篇 |
| PROGRESS / RETRO | 按迭代拆文件 |
| PRD | 单产品单 PRD；多特性且特性间边界清晰时按特性拆子 PRD + 总览 |
| DESIGN | 单服务单文档；多服务 = 1 份总览 DESIGN + 每服务子 DESIGN |
| ROADMAP | 项目级一份，不拆 |
| RUNBOOK | 一操作一篇 |

## 二、目录模式选择

| 模式 | 结构 | 适用 | 风险 |
|---|---|---|---|
| **类型优先**（默认） | `docs/<layer>/<type>/` | 中小项目；文档量 < 100 篇；AI 检索场景（按类型+层定位最稳） | 特性相关信息分散在多目录 |
| **特性优先** | `docs/feature-x/{prd,design}.md` | 单特性文档 ≥ 3 篇且特性间高度独立 | 类型级全貌（如全部 ADR）难总览——需 ADR 索引弥补 |
| **混合** | 类型为第一级、特性为第二级 | 两者都需要时的折中 | 层级易超深（>3） |

选择规则：
1. 默认类型优先；先建标准结构，不要提前设计复杂目录。
2. 某特性的文档积到 3 篇以上，再为它在类型目录下建特性子目录。
3. 任何时候目录深度 ≤ 3；超了 = 该归档或该拆子项目了。
4. **禁止按人名/日期做第一级目录**——按人和时间找文档是索引的职责，不是目录结构的职责。

## 三、场景决策表（高频治理场景）

| 场景 | 决策 |
|---|---|
| 新项目冷启动 | 只建最小集：ROADMAP + PRD 骨架 + 空 adr/ + PROGRESS；其余按触发时机增量创建 |
| 一次对话/任务中产出了需求+方案+决策 | 拆为 PRD 条目 + DESIGN + ADR 三份，按模板归位；禁止合写成一篇"方案说明" |
| 既有文档里发现了价值内容但位置错误 | 复制到正确位置 + 原位置留链接；治理动作记录在 PROGRESS（或 RETRO） |
| 两篇 TECH 主题重叠 | 合并：保留标题更"结论化"的一篇为主文档，另一篇标记 archived 并入链 |
| ADR 被新决策推翻 | 不改旧 ADR 正文：新建 ADR，双向 superseded 链接；同步更新引用了旧 ADR 的 DESIGN/规范 |
| 规范文档长期未落地 | Roadmap 建条目追踪落地；若决定不落地，转 explicit 拒绝（写明原因），不让它保持"僵尸规范"状态 |
| 迭代结束 | PROGRESS 收尾 → RETRO 行动项外发 → 两者归档 → 索引更新 → 巡检清单跑一遍 |
| 文档体系没人用 | 先查索引是否好用（人类 30 秒内能否定位到想找的文档），再查是否过度分层；治理失败最常见原因是检索成本过高，而非文档太少 |
| AI 智能体频繁读错/读漏文档 | 在索引里为 AI 补充"何时读哪个文档"的路由说明；技术事实显式化（路径/符号/版本）；检查是否混写导致新旧信息不可区分 |

## 四、人机双重视角的治理含义

人机双重视角不只是写作要求，也约束治理动作：

1. **检索路径双通道**：人类通过索引（README）浏览；AI 通过 frontmatter 过滤（doc-type/layer/status）。治理必须同时维护两条通道——索引给人看，frontmatter 给机器筛。
2. **链接即契约**：AI 会字面跟随文档中的路径与 ID。移动/重命名任何文档前，先全局检索引用并同步更新，否则每一次移动都在给 AI 制造断链陷阱。
3. **状态字段是机器的路标**：`status`、`doc-class`、`last-verified` 失真时，AI 会基于错误前提行动。巡检时把"状态字段与事实不符"按 Major 起步。
4. **一处事实一处来源**：同一事实在多文档重复展开时，指定一处为权威（source of truth），其余处只留链接——复制传播是 AI 与人共同的漂移之源。
