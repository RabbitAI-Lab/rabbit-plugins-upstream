# 跨材料口径一致性审计（Cross-Material Consistency Auditor）

对于同一主题或同一事件的多份材料，在发布前对比产品名、数字、事实表述、术语、来源标记、结构承诺和跨平台表达差异。只输出差异矩阵和统一口径建议，不自动修改原文。

## 何时使用

- 同一场发布会/活动的 PR 通稿、媒体约稿、产品稿和演讲稿之间存在数字或产品名不一致。
- 同一篇文章的中文版和英文版（微信、LinkedIn、Substack）表达、数据来源标注或重点存在差异。
- 系列文章在多篇之间的事实、术语或判断出现漂移。
- PPT、白皮书、网页和展厅物料中同一组数字或同一产品用不同名称。
- 需要生成标准化的"口径一致性核对表"供 PR/产品/编辑团队确认。

## 不适用

- 单篇文章的事实核验，由 `claim-to-source-auditor` 或 `content-compliance-reviewer` 处理。
- 单篇文章的格式、语法和客户脱敏检查。
- 选题评估，由 `editorial-topic-portfolio` 处理。
- 直接修改或重写任何原文。

## 输入

```yaml
topic_or_event:
  brief:
materials:
  - path:
    label: PR通稿 | 媒体约稿 | PPT | 网页 | 白皮书 | 微信 | LinkedIn | Substack | 演讲稿
  - path:
    label:
reference_source:  # 以哪份材料为权威源，默认第一份
scope: [numbers, product_names, fact_wording, terminology, source_attribution, structural_promises, cross_platform_drift]
read_only: true
```

## 工作流

### 步骤 1：[确定性] 加载全部材料

1. 读取全部指定材料。2. 标记每份材料的类型、日期和状态。3. 记录明显的外部引用和无法解析的内容。

### 步骤 2：[确定性] 提取主张

对每份材料提取：数字及其单位；产品正式名称和简称；事实表述；来源归属；章节级结构承诺；术语和框架名称。
产品名监测词表由使用者自备（不随 Skill 内置任何具体产品清单）：优先读环境变量 `CONSISTENCY_PRODUCT_TERMS`（逗号分隔），其次读 `scripts/product-terms.txt`（每行一个，`#` 注释）；两者都没有时退化为通用启发式（驼峰复合词 + 大写缩写）。

输出 `01-extracted-claims.json`。

### 步骤 3：[LLM] 构建差异矩阵

逐项对比，每条不一致记录：维度；材料 A 表述 vs 材料 B 表述；差异类型（绝对化 vs 稳妥、归因不同、术语混用、来源混淆、结构丢失、跨平台缩减）；严重度——**P0**：数字或法律状态错误、同客户/产品用不同名称、正文与配图关键数据不同；**P1**：来源归属不一致、跨平台核心判断表述改变、术语混用；**P2**：非关键修辞差异、跨平台深度表达不匹配、下节承诺不在；建议统一口径；是否需要在正文修订后重新对比。一致项作为正面记录，但输出中不逐条列出。

### 步骤 4：[LLM] 推荐统一口径

对每个 P0/P1 差异给出精确的统一表述：统一口径文字；引用权威源；统一理由；需要在哪些材料中修改；对系列文章，记录此表述是否需要在前后篇中也统一。

### 步骤 5：[确定性] 生成审计报告

复制 `templates/audit-report.template.md`，生成正式审计报告（含 Scope、Diff Matrix、Unified recommendations、Platform drift、Summary、Revision tracking）。

### 步骤 6：[确定性] 人工确认

审计报告输出后暂停。确认：P0/P1 处置方案；统一口径措辞；是否需要回改已发布版本；是否需要更新策划文档和元数据。确认后由用户或相应的 Writer/Editor 执行修改。本 Skill 不自动修改原文。

## 硬规则

1. 绝不修改任何原材料，只输出差异矩阵与统一口径建议。
2. 以最早或显式指定的参考源为解决冲突的权威。
3. P0 不一致阻断发布，须标出并要求解决。
4. P1 不一致需人工决策。
5. 同一主题、同一数字、同一产品名、同一术语必须在所有材料中一致。
6. 只要核心判断与关键事实保持一致，平台间的表达差异可接受。
7. 统一口径不得凭空创造，必须引用既有来源。
8. 审计报告是检查点，交付后 hands-off。

## 故障处理

| 场景 | 处理 |
|---|---|
| 仅提供一份材料 | 停止；任务至少需要两份材料 |
| 关键材料不可读 | 标记该材料，仅对比其余材料 |
| 参考源含明显错误 | 标出错误并建议修正，不传播 |
| 复杂内嵌内容（图表、带字图片） | 标记不可解析，请求文本抽取或人工检查 |
| 所有材料文本一致 | 报告"未发现不一致"并通过 |
| 已发布材料中检出 P0 | 追加严重度并建议修正 |
| 审计会话中某文件被修订 | 仅对变更文件重新提取与差异比对 |

## 输出格式

```
<run-dir>/
├── 01-extracted-claims.json
├── 02-diff-matrix.md
├── 03-audit-report.md
└── 04-unified-wording.json
```

## 核查清单

- [ ] 每对材料在所有请求维度上完成对比。
- [ ] 每个 P0/P1 不一致都有带来源的统一口径建议。
- [ ] 参考源被用作冲突仲裁。
- [ ] 报告不含任何原文修改。
- [ ] 平台漂移表覆盖所有平台。
- [ ] 任务标记完成前有人工确认记录。

## 易错点

- 比较不同发布日期的材料却不标记版本差。
- 把 PR 草稿当作事实权威，而产品规格才是真正来源。
- 推荐的统一口径引入新错误（把一个错误改成匹配另一个错误来源）。
- 忘记 PPT 与网页本就设计精度不同，不是每个四舍五入都是不一致。
- 在 PR 简报明确允许改编时，却把结构差异归咎于代笔。
- 依赖单次扫描，漏掉 PPT 内嵌图表或图片中含文本的数字。
