# 流程演示：修订一份项目汇报

> **示例，不是实测案例。** 项目名、周期与数字均为占位，不代表真实项目结果。重点展示修订模式如何限定改动范围并对账。

## 输入素材（占位）

用户提供一段项目汇报，并要求：「只把进度和风险写清楚，保留原有数字、项目名称和责任归属，不要整篇重写。」原文中有一处状态描述含混，另有一处截止日期待确认。

## 修订决策

1. 先确认本轮目标是提高进度与风险的可读性，不扩写结论。
2. 重读用户当前版本，锁定项目名、数字、责任人和范围外段落。
3. 将「基本完成」等含混状态改为原材料支持的具体动作；没有证据的完成比例不补。
4. 将待确认日期保留为待核实，不改成确定日期。

## 改前 / 改后（示例）

- 改前：`模块已基本完成，后续会尽快处理遗留问题。`
- 改后：`模块 A 的接口联调已完成。异常重试仍待验证，完成时间需项目负责人确认。`

以上仅为示意句，不来自真实项目；实际修订不得据此推断项目状态。

## 对账方式

实际任务中交付改动清单，并用 `change_list.py 改前.md 改后.md` 检查遗漏改动与数字变化。数字变化需逐条解释；`--strict-numbers` 可在发现数字变化时令脚本返回 1。本文没有真实改前/改后文件，因此没有运行或宣称通过检查。

## 边界

此例展示修订与范围保护，不展示新文档骨架；新写流程见[操作说明案例](write-sop.md)。
