# 需求优先级排序方法

## 核心原则
排优先级不是排「想做什么」，而是排「不做什么」。资源永远不够，关键是敢说不。

## 三种排序方法

### 方法一：RICE 评分模型（推荐）
适合有数据积累的产品。

**R = Reach（覆盖人数）**
- 在考核周期内，多少用户会用到这个功能？
- 评分：1-10（1=很少，10=几乎所有用户）

**I = Impact（影响力）**
- 对核心指标的影响有多大？
- 评分：0.25, 0.5, 1, 2, 3, 5（0.25=极小，5=极大）

**C = Confidence（信心程度）**
- 你对 R 和 I 的评估有多大的把握？
- 评分：20%, 50%, 80%, 100%

**E = Effort（投入估算）**
- 需要多少人月？
- 单位：人月

**RICE 分数 = (R × I × C) / E**
分数越高优先级越高。

### 方法二：价值-投入矩阵
适合早期产品，数据积累不足时使用。

```
高价值 ┼──────────────┼──────────────┐
      │   重点投入     │   优先做       │
      │  (需要计划)    │   (立即行动)    │
      ├──────────────┼──────────────┤
低价值 │   不做         │   有空再做     │
      │   (说不)      │   (等人认领)    │
      └──────────────┴──────────────┘
       高投入                      低投入
```

### 方法三：三要素法
最简单的快速排序，回答三个问题：
1. **不做会死吗？** → 是 → P0
2. **做了用户会 wow 吗？** → 是 → P1
3. **这两个都不是？** → P2 或不做

## 排序时的注意事项

### 务必考虑的因素
- **战略对齐**：这个需求在不在公司/产品今年的战略方向上？
- **技术债务**：实现这个需求是否会产生新的技术债？
- **依赖关系**：这个需求是否依赖其他团队？依赖能解决吗？
- **时机窗口**：现在做是不是最佳时机？错过会不会有损失？

### 常见错误
- 只排功能需求，忽略技术优化和 bug 修复
- 所有需求都是 P0（说明没排优先级）
- 按提需求的人的职级排优先级
- 只看价值不看投入
- 只用自己的判断，没拉研发一起评估

## 优先级对应的处理策略

| 优先级 | 含义 | 处理策略 | 时限 |
|-------|------|---------|------|
| P0 | 不做会影响核心指标或用户体验 | 当前迭代必须完成 | 本次迭代 |
| P1 | 做了有明显正向效果 | 排入下 1-2 个迭代 | 本月内 |
| P2 | 锦上添花 | 资源充裕时排期 | 本季度内 |
| P3 | 有了更好，没有也行 | 有时间再做或持续待排 | 无固定时间 |
