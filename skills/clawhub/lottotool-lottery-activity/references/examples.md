# 自然语言示例

## 查询最近和即将开奖的活动

用户：“最近我发起了哪些活动？哪些快开奖了？”

先调用 `list_my_activities({"filter":"recent"})`，再调用 `list_my_activities({"filter":"upcoming_draw","days":7})`。按实际结果列出活动名称和北京时间；“即将开奖”只覆盖未来 7 天内定时开奖的活动。没有返回活动时如实说明，不编造活动或开奖时间。

用户：“上周那个会员活动有多少人访问、多少人参与？”

先用活动列表定位；多个候选时请用户选一场。确定 `activity_id` 后调用 `get_activity_metrics`，分别报告累计 `visit_count`（访问量）和 `join_count`（参与人数）。若用户想看变化，再按返回的 `daily` 比较最近 7 天；今天尚未结束，不能直接与完整日期比较。

用户：“看看最近 7 天访问和参与有没有增长。”

确定活动后调用 `get_activity_metrics({"activity_id":"已确认编号"})`，按 `daily` 的日期顺序展示访问量和参与人数，说明起止日期。需要计算增减时仅比较工具实际返回的日期与数值；今天的数据标为截至查询时的部分数据。

## 直接导出活动数据

用户：“把刚才那场活动的参与人导出来。”

“刚才那场”已在当前对话中唯一确定时，直接调用 `export_participants({"activity_id":"已确认编号"})`。返回链接后答：“《活动名》的参与人 CSV 已生成：[下载文件](工具返回的真实链接)。”不要在对话中展示手机号、用户 ID 或逐行名单，也不声称已经把文件下载到用户设备。

用户：“导出这场活动收集的表单。”

先问：“是参与时填写的表单，还是中奖后填写的兑奖表单？”前者随 `export_participants` 的 CSV 导出，后者用 `export_form_submissions` 导出 XLSX。若用户说“中奖名单”，用 `export_winners`，并说明文件包含中奖和核销记录。

## 信息不完整时的引导

用户：

> 我想做个抽奖，但还没想好。

第一轮不要罗列所有配置项，也不要先问是否创建。先了解目的和关键限制：

> 这次抽奖主要想达到什么目的，面向哪些人？奖品或参与方式有没有必须满足的要求？

根据回答推荐玩法和参与流程，分别说明小程序能实现什么、当前专家可以自动配置什么、哪些设置需要到小程序补充。先问“这个方案能满足你的需求吗？”，用户指出缺口时继续调整。用户说“你看着配”时，可以给出推荐方案，但仍要核对是否满足需求。

用户认可方案后，再问“需要我帮你创建这个活动吗？”。如果用户选择创建，再补齐必要字段并调用预览；用简短列表标明用户要求和建议默认值，最后问“确认按这份配置创建吗？”。方案认可、创建意愿、预览后的最终确认是不同阶段。

## 定时开奖

用户：

> 建一个会员抽奖，3 天后开奖。一等奖耳机 1 份，二等奖咖啡券 10 份。

即使用户开头说“建一个”，也先确认活动目标和参与方式，解释定时开奖及奖品交付能覆盖哪些需求，再请用户确认方案是否合适。用户认可后询问是否协助创建；若用户已在看到方案后明确要求创建，不重复询问创建意愿。随后补齐领奖信息等字段，预览并取得最终确认。

关键配置：

```json
{
  "play": "classic",
  "draw": { "mode": "timed", "end_at": "3d" },
  "prizes": [
    { "name": "耳机", "count": 1, "delivery": "express" },
    { "name": "咖啡券", "count": 10, "delivery": "none" }
  ]
}
```

## 大转盘

用户：

> 做个大转盘，每人 2 次，总中奖率 30%。手办 1 份，纪念贴纸 20 份。

先核对用户要达成的效果和必要参与条件，说明大转盘属于即抽即开，以及当前专家能配置的基础规则。确认方案合适并取得创建意愿后，再预览下列配置并等待最终确认。

关键配置：

```json
{
  "play": "turntable",
  "draw": { "mode": "instant", "draws_per_user": 2, "end_at": "3d" },
  "winning_rate": 30,
  "prizes": [
    { "name": "手办", "count": 1, "delivery": "express" },
    { "name": "纪念贴纸", "count": 20, "delivery": "none" }
  ]
}
```

大转盘最多 50 个奖项。用户只需确认一个总中奖概率，服务端按数量 1:20 分摊 30%；不要追问各奖项概率，也不提交 `prizes[].probability`。

## 中奖后填写领奖信息

需要确认领奖信息时使用：

> 中奖后需要填写哪些领奖信息？
> 1. 填写姓名、手机号、地址（适合邮寄实物）
> 2. 无需填写领奖信息（适合到店领取等场景）

选项只是建议，不能代用户决定；确认后分别使用 `delivery: express` 或 `delivery: none`。

## 连续修改

1. 用户：“把一等奖改成 2 份，结束时间改到周五 20:00。”
2. 未创建时合并当前对话配置；已创建时仅按用户指定编号读取，并提示到抽奖工具内编辑。
3. 调用 `preview_lottery`，将变更后的奖品数量、结束时间回报给用户。
4. 未创建的草稿预览成功且用户确认后调用 `create_lottery`；首版不调用 `update_lottery`。

## 只写文案

用户：“帮我写群福利抽奖通知，先不要创建。”

直接交付活动名、详情和群通知；未给出的奖品数量、时间、领取方式保留明确占位符。说明“仅生成文案，尚未创建活动”，无需连接或调用写工具。

普通咖啡券、贴纸等仅描述用户自行准备的奖品，不代表已自动生成或发放优惠券。邮寄实物需用户确认“中奖后需填写姓名、手机号、地址”，线下领取可使用 `delivery: none`。

## 大转盘的参与条件与助力

用户：“大转盘还要加个入群条件，再让好友助力增加抽奖次数。”

> 小程序支持大转盘的参与条件和助力任务，当前专家暂不能自动设置。一个可行方案是先配置基础大转盘，再由你在小程序活动管理中补充这两项，具体组合以页面可用设置为准。这样的流程能满足你的需求吗？

用户认可后再询问是否协助创建基础活动。保留大转盘玩法，不要求改成经典抽奖；未在小程序内实际设置前，不写成活动已经强制要求入群或已开启助力。

## 注册小程序会员后参与

用户：“想让用户注册小程序会员后再参与抽奖，怎么设计？”

先问清会员属于哪个小程序，以及“注册后参与”是硬性门槛，还是希望通过抽奖引导更多人注册。若是硬性门槛，再确认现有会员系统能否提供名单、会员编号或其他可核验信息。介绍小程序可用的指定名单、口令等参与设置时，明确这些不等于自动识别外部小程序的注册状态；当前专家不能自动配置会员资格核验。给出与现有条件匹配的方案，请用户确认能否满足需求，然后才询问是否需要协助创建基础活动。

## 按消费金额获得抽奖机会

用户：“我想做一个满额抽奖，比如满 58 可以抽一次，满 106 可以抽两次，你这边能做到吗？”

应先准确复述需求并说明当前能力，不转成“满人开奖”或固定每人两次：

> 我理解的是按消费金额给抽奖机会：满 58 元 1 次，满 106 元 2 次。可以考虑两种做法：一是让顾客上传消费凭证，核对金额后按档位安排机会；二是您核对消费后，给符合条件的顾客发相应口令。它们都需要人工核对消费，当前专家不能自动读订单并按金额发放。您想按单笔订单还是累计消费计算？更方便让顾客传小票，还是由您发口令？

按用户选择进一步核实具体设置：上传凭证审核通过时，奖励次数由活动统一配置，审核页不能对每张凭证直接选 1 次或 2 次，需另行确认分档补发或分批处理办法；发口令时区分“口令参与”和“输入口令增加抽奖机会”，核对可兑换次数及是否允许重复兑换，不承诺发一枚参与口令就自动获得对应档位次数。说明哪些步骤需用户在小程序操作，不能仅因有“消费满额抽奖”新手方案就承诺自动计额。用户确认可行方案满足需求后，才询问是否协助创建基础活动。58 元和 106 元不是等间隔档位，不自行推导其他金额的次数。
