# 拆分任务

输入是目标、验收和足够明确的方案，可以来自任何文档或会话。产物是一份任务清单，通常是 .peterflow/specs/主题/tasks.md。

按 Phase（阶段）→ Task（任务）组织：Phase 写清阶段目标、依据、直接前置及阶段验收，下面列出完成该目标的 Task。阶段按实际可验收结果划分，不固定套用准备、开发、测试等通用阶段，也不另建阶段文件或进度表。

1. 确定工作区与本轮范围，读取有关项目规则、.peterflow/standards/ 中适用规范、需求、计划、现有任务及少量代码入口。已有清单沿用原位置；资料不必由指定 Skill 生成。
2. 将每项目标和必要验证落到具体 Task。每项写清交付什么、从哪个入口能检查；小实现和直接自检放在一起。独立验收另列时，写明开测所需的前置产物。前置任务要能凭自身产物和直接检查完成。若它的完成条件又要等下游验收，把这项验收归到下游或阶段。
3. 使用稳定编号，例如 P001、T001；Task 编号在整份清单中唯一，新项接续原编号体系。Task 继承所属 Phase 的前置依赖，只补自身额外依赖；合并两层关系检查循环和缺失编号。展示顺序不替代依赖，只有没有依赖、共享写入或接口竞争时才说明可并行。
4. 新建时可使用 [任务模板](assets/tasks.md)。已有清单可原位按目标归组，保留任务编号、完成事实和证据；已失效的验收注明原因和需要补验的内容，不能因改了组织就重新宣称通过。
5. 核对每个目标有实现与验收去向，每个 Task 有阶段归属及范围依据，依赖足以确定下一步。Phase 完成需要所属任务和阶段验收成立。重要决定未定时明确受影响工作及解除条件，其余继续。

新建或接续包内标准模板时，在交付前运行 `python3 <本技能目录>/scripts/check_dependencies.py <任务文件>`。[随包检查](scripts/check_dependencies.py) 核对编号、归属、缺失引用及两层依赖合并后的环。报错时核对原目标再修正，重跑检查。随后对照每个前置的产物与后继的开工条件，检查文字里的隐含互等。旧平铺清单、自定义格式或缺 Python 时，直接按原编号逐项核对，并说明机械检查的覆盖范围。

缺失材料时只补足影响拆分的目标、方案或验收，不强制新建 spec.md。给 Task 指定新材料的交付位置时，详细设计用 `design/`，参考资料用 `references/`，验证记录用 `verification/`，上线交付物用 `delivery/`，多方契约用 `contracts/`。清单只列需要的产物路径，等实际写文件时才建对应目录。保留已有文件，同名非目录或符号链接冲突先说明，不覆盖。已有其他资料根目录则沿用。

验证优先回填原任务；确需另存长记录时从原任务链接到验证记录，不额外安排一份重复的进度报告。

完成时报告任务文件、Phase 目标及所属 Task、依赖顺序、首个可执行任务和未决事项。此 Skill 负责拆分，不把静态清单检查当成测试通过；实际执行与验证由实现流程完成。不操作 Git 暂存、提交、推送或依赖 Issue 平台。
