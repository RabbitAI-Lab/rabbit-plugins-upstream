# task-planner：架构 → 任务清单

## 何时使用

- 用户提供（或对话中已有）架构设计方案，要求拆解开发任务
- 用户要求规划执行顺序、识别可并行任务
- 用户要求生成 Out-of-Scope 清单界定范围

**不适用**：没有架构方案时（先用 arch-designer 生成）；要求生成 Spec（用 spec-writer）；要求审计完成情况（用 audit-trace）。

## 输入

- **[必需] 架构设计方案** — 模块划分、接口定义（arch-designer 输出），或用户直接提供的设计描述

**前置依赖**：不允许跳过架构设计直接生成任务。架构设计缺失时提示用户：

> 未检测到架构设计方案。请提供架构设计文本，或使用 arch-designer 基于 Spec 生成（本 SKILL 只负责任务规划，不执行架构设计）。

**上下文完整性检查**：架构设计来自当前对话时，检查是否包含验证标记 `<!-- CONTEXT-CHECK: ... -->`；缺失或异常时提示用户"上游架构设计可能不完整，建议确认后继续"。

## 执行流程

### 1. 识别架构层次

按以下层次逐层提取模块：

```
UI 层 → 业务逻辑层 → 数据访问层 → 基础设施层
```

层内按组件/功能进一步细分。

### 2. 按拆分规则生成任务

**三种分解策略（根据项目特点选择）**：

| 策略 | 适用场景 | 方法 |
|------|---------|------|
| **Sequential（串行）** | 强依赖链、新手团队 | 按依赖顺序逐个执行 |
| **Parallel（并行）** | 弱依赖、多开发者 | 无依赖任务同步推进 |
| **Hybrid（混合）** | 大多数项目（推荐） | 按阶段串行，阶段内并行 |

**Hybrid 分解方法**：
1. 将任务按开发阶段分组（Setup → Core → Advanced → Testing）
2. 阶段间串行（前一阶段完成后才进入下一阶段）
3. 阶段内并行（无依赖关系的任务可同步推进）

**拆分依据（按优先级）**：

- **按架构层次**：每一层作为一个任务分组，层内各组件独立成任务
- **按接口/数据流**：每个 API 端点、每条数据流处理路径独立为一个任务
- **按功能点**：一个完整功能的最小可验证单元独立为任务

**双端任务编排规则**（前后端架构）：前端页面任务依赖对应后端接口任务（接口契约先定），前端任务排在后端接口任务之后；同端无依赖任务可并行，跨端任务按"后端接口 → 前端页面"顺序串行衔接。

**粒度标准**：

- 理想任务规模：独立可开发、可测试、1-2 小时完成，最长不超过 4 小时
- 超 4 小时的任务须进一步拆解
- 不足 30 分钟的任务合并到相邻任务中

**依赖识别规则**：

- 被依赖模块（数据模型、工具函数、基类等）优先拆出，排入早期任务
- 同一层次内无相互引用的组件标记为可并行执行
- 依赖链层数口径：**层数 = 任务数 − 1**（A → B → C 记 2 层），默认不超过 3 层
- 链深 > 3 时：**显式标注接受 + 理由**（如"合并将超出 4h 粒度上限"），而非机械合并中间任务；接受项在任务清单中标注"超约束，已显式接受"
- 业务固有长链（如数据平台多级数据流）属可接受场景，与可拆分场景（可合并中间任务降层）区分处理

**工作量估算标准**：

| 级别 | 时间 | 典型场景 |
|------|------|---------|
| 简单 | ≤1h | 修改变量名、配置文件、单一工具函数 |
| 中等 | 1-2h | 新增一个 CRUD 接口、一个无交互的 UI 组件 |
| 复杂 | 2-4h | 新增一个完整页面含交互、跨层联调功能 |

**验收条件要求**：

- 必须为可客观验证的描述
- ✅ "用户注册接口返回 201 且密码已加密存储"
- ❌ "注册功能正常"

**任务粒度与验收标准条数对应**：一个任务可合并多个 AC（不强制一一对应），验收条件按可验证断言编写；任务覆盖的 AC 编号在验收条件中显式列出（如"覆盖 AC-01/AC-02"），供 impl-guide 逐 AC 派生测试要求时回溯（一个任务可对应多个测试用例）。

### 3. 识别依赖关系

根据依赖规则推断依赖图，标记串行和并行关系。

### 4. 标记可并行任务

同一层次无依赖关系的任务归入同一并行批次。

### 5. INVEST 质量校验

对每个任务进行 INVEST 检查，不达标时重新拆解或合并：

| 维度 | 含义 | 检查标准 |
|------|------|----------|
| **I**ndependent | 独立 | 尽可能独立，不依赖其他任务的实现细节 |
| **N**egotiable | 可协商 | 实现方式可协商，不锁死技术方案 |
| **V**aluable | 有价值 | 单独可交付、可验证，而非"部分功能" |
| **E**stimable | 可估算 | 有足够信息估算工作量 |
| **S**mall | 小 | 1-4 小时内可完成 |
| **T**estable | 可测试 | 有明确的验收标准可验证 |

INVEST 不达标时：不够 Independent → 检查是否可调整依赖顺序；不够 Small → 进一步拆解；不够 Testable → 补充验收条件。

### 6. 为每个任务指定验收条件

按验收条件要求编写可验证断言。

### 7. 生成 Out-of-Scope 清单

明确列出本次需求**不包含**的内容：

- Spec 模糊项中被用户确认"不做"的内容
- 架构设计中明确排除的方案
- 范围边界中标注"不包含"的条目
- 开发过程中常见的隐含假设（如"不包含性能优化""不包含多语言支持"）

Out-of-Scope 清单避免后续开发中出现范围蔓延。

## 场景任务分组模板（可选参考）

架构方案含以下场景特征（或用户指定）时，按对应模板对任务预分组，再按实际模块裁剪。模板仅规定**分组模式与阶段映射**，不改变粒度、依赖识别、INVEST 校验规则。

### Web 全栈（前后端分离）

| 阶段 | 默认分组 | 典型任务 |
|------|---------|---------|
| Setup | 工程初始化 | 前端脚手架、后端脚手架、CI 与数据库初始化 |
| Core | 契约先行：接口契约 → 后端核心接口 → 前端核心页面 | 接口契约定义、用户注册/登录（接口 + 页面）、核心业务 API、核心页面 |
| Advanced | 增强功能 | P1/P2 功能、错误处理、权限细化 |
| Testing | 端到端联调 | 端到端用例、跨端联调测试 |

规则：接口契约任务排最前；前端页面任务依赖对应后端接口任务（双端编排规则），同端无依赖任务可并行。

### 纯 API 服务

| 阶段 | 默认分组 | 典型任务 |
|------|---------|---------|
| Setup | 工程初始化 | 项目脚手架、数据库 Schema、基础中间件（日志/配置） |
| Core | 按端点分组：每组的读/写接口 + 校验 | P0 端点逐组实现（每端点含接口、业务、数据访问） |
| Advanced | 横切增强 | 限流/重试、审计日志、P1/P2 端点 |
| Testing | API 测试矩阵 | 接口测试、契约测试、性能测试 |

规则：数据模型与 Repository 作为被依赖模块拆出排入 Setup 早期；同组端点无依赖时可并行。

### 小程序

| 阶段 | 默认分组 | 典型任务 |
|------|---------|---------|
| Setup | 工程初始化 | 小程序脚手架、后端脚手架（如含）、登录态基础（wx.login → session） |
| Core | 页面 + 接口配对：核心页面与其依赖接口同批 | 核心页面（列表/详情/表单）+ 对应接口 |
| Advanced | 平台能力与增强 | 订阅消息、上传下载、缓存/离线、P1/P2 页面 |
| Testing | 真机与弱网验证 | 真机验证、弱网/超时用例、平台兼容检查 |

规则：登录态任务为全局前置（多数接口依赖）；页面任务依赖对应接口任务，接口契约先行。

## 输出格式

```markdown
# 任务列表

## 任务清单
| ID | 任务 | 所属模块 | 依赖 | 预估工作量 | 验收条件 | 证据要求 |
|----|------|---------|------|-----------|---------|----------|
| T-01 | 实现用户注册 API | 用户服务 | — | 中等（2h） | POST /register 返回 201，密码已加密 | 测试通过截图或curl响应示例 |
| T-02 | 实现用户登录 API | 用户服务 | T-01 | 中等（1.5h） | POST /login 返回 JWT Token | curl响应示例含token |

## 执行顺序
- 串行依赖：T-01 → T-02 → T-03
- 可并行：T-01 和 T-04 可并行开发

## INVEST 质量校验
| 维度 | 检查结果 | 说明 |
|------|---------|------|
| Independent / Negotiable / Valuable / Estimable / Small / Testable | ✅ / ⚠️ | ... |

## Out-of-Scope（明确不包含）
| 项目 | 来源 | 说明 |
|------|------|------|
| 性能优化 | Spec 范围边界 | 不包含，后续单独处理 |
| 多语言支持 | 架构设计排除 | 当前仅支持中文 |
```

### 证据要求字段

每个任务的「证据要求」字段定义该任务完成时需要提供的实现证据（审计阶段对照检查项）：

| 证据类型 | 适用场景 | 示例 |
|---------|---------|------|
| 测试通过截图 | 有单元测试/集成测试 | 测试报告截图、CI 通过截图 |
| 测试结果文件路径 | 有可执行测试（V-03，P0-02） | `tests/report.json`（格式见 TEST-SKELETON-SPEC.md），audit-trace 自动核对 |
| API 响应示例 | 后端接口任务 | curl 请求响应截图 |
| 日志片段 | 运行时验证 | 关键流程的执行日志 |
| 性能指标 | 有性能要求的任务 | 压测结果、响应时间截图 |
| 代码截图 | 前端/UI 任务 | 界面截图、组件渲染截图 |

## 任务状态跟踪

不管理任务状态，但输出格式支持状态追踪：

- 每个任务 ID 可附加状态标记：`待开发` / `开发中` / `已完成` / `已验证`
- 用户再次要求"更新任务"时，如上下文中已有任务状态信息，仅更新未完成的任务，已完成的保留原样
- 任务清单可导出为 Markdown 表格或简单 CSV

## 任务变更与回退

当某个任务在开发中发现不可行时，可请求重新规划：

1. 标记失败任务及原因
2. 生成替代任务或调整方案
3. 重新评估受影响任务的依赖链和执行顺序
4. 标注变更原因和影响范围："任务 T-XX 因 XX 原因调整，影响下游任务 T-YY、T-ZZ"

## 输出末尾验证标记

```markdown
<!-- CONTEXT-CHECK: T-{任务数量}, M-{模块数量}, P-{可并行批次} -->
```

### 格式切换（可选）

默认输出 Markdown（以上模板）。用户明确要求 JSON / CSV 时：

- **JSON**：按产物章节结构输出 JSON 对象，字段映射如下，内容与执行方法完全一致，仅改变呈现格式
- **CSV**：任务清单、Out-of-Scope 等表格类产物以 CSV 输出，每行一条记录，列名取表头（已有"可导出 CSV"能力在此统一定义）
- **CONTEXT-CHECK 标记在任何格式下保留**（JSON 置于顶层字段 `context_check`，CSV 置于末尾注释行），供下游检查
- 格式切换不改变执行流程、判定口径与自检清单

```json
{
  "tasks": [{"id": "T-01", "name": "...", "module": "...", "deps": ["T-02"], "estimate": "中等（2h）", "acceptance": "...", "evidence": "...", "status": "待开发/开发中/已完成/已验证"}],
  "execution_order": {"serial": ["T-01 → T-02"], "parallel": [["T-01", "T-04"]]},
  "out_of_scope": [{"item": "...", "source": "...", "note": "..."}],
  "context_check": "T-{n}, M-{n}, P-{n}"
}
```

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 每个任务有可客观验证的验收条件
- [ ] 无超过 4 小时的任务（已拆解）
- [ ] 无不足 30 分钟的任务（已合并）
- [ ] 依赖链层数按"任务数 − 1"口径标注，链深 > 3 已显式标注接受及理由
- [ ] 双端架构下前端任务已排至对应后端接口任务之后
- [ ] 任务合并多个 AC 时已显式列出覆盖的 AC 编号
- [ ] INVEST 六维全部通过（或已说明调整）
- [ ] 被依赖模块已排入早期任务
- [ ] Out-of-Scope 清单已生成
- [ ] 每个任务的证据要求字段已填写
- [ ] CONTEXT-CHECK 标记已附加

## 边界与常见错误

- **不做什么**：不生成 Spec（用 spec-writer）、不做架构设计（用 arch-designer）、不编写代码实现
- **常见错误**：跳过架构设计直接生成任务；验收条件不可客观验证（"功能正常"类）；依赖链过深；遗漏 Out-of-Scope 导致范围蔓延；依赖链超约束机械合并而非显式标注；前端任务未依赖后端接口契约；多 AC 合并任务未标注覆盖范围
- **输入缺失**：架构方案缺失时提示用户提供或用 arch-designer 生成，不自行回溯补齐
