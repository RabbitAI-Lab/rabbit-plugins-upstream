# spec-writer：需求 → 结构化 Spec

## 何时使用

- 用户提供需求文档 / PRD / 功能描述，需要产出结构化 Spec
- 用户要求检查已有 Spec / proposal / 需求文档的质量（遗漏、模糊、矛盾）
- 用户回答追问后需要回填 Spec，或提供更新版 PRD 需要增量更新

**不适用**：已有完成的 Spec 且用户要求架构设计（使用 arch-designer）；仅讨论需求不产出文档（直接对话即可）。

## 输入

- 纯文本（粘贴或消息中的文字）
- 本地文件内容（读取后传入，如 `.md` / `.txt`）
- 网页内容（通过 WebFetch 抓取后传入）
- 已有 Spec / proposal（质量检查场景）
- 无输入时主动追问获取信息
- 多份文档：逐份处理，每份产出对应的独立 Spec，不合并

> **只接受文本输入**。文件读取、网页抓取、内容提取均在调用前完成。

## 前置规划（可选，Brownfield 场景）

以下场景在正式解析前先探索项目情况，将结果作为解析上下文：

1. 探索代码库 — 扫描项目目录结构、已有模块、技术栈、现有 API 风格
2. 识别相关模块 — 判断新需求涉及哪些现有模块（新增/修改）
3. 发现隐式约束 — 从现有代码中提取命名规范、目录结构、依赖版本等
4. 输出规划摘要 — 作为上下文传入三遍校验法

仅当：项目目录已有代码、需求涉及多个模块或跨系统交互、用户主动要求"先看看项目情况"。

## 执行流程：三遍校验法

### 第一遍：粗提取（广度覆盖）

通读全文，识别所有功能点和约束条件。

- 宁可多列不漏列；提取所有显式和隐式的功能需求
- 标记约束条件（技术约束、业务约束、安全约束）
- 输出：功能点清单 + 约束条件草稿

### 第二遍：细校验（精度保证）

逐段对照原文，检查第一遍的提取结果。

- 逐段扫描原始文档，对比已提取的功能点
- 补充遗漏的功能点、约束条件、业务规则
- 修正第一遍中理解偏差的条目
- **第二遍未完成前，不得输出最终结果**

### 为每个功能点生成验收标准

- 格式：Given / When / Then
- 每个功能点至少一个验收标准
- 验收标准必须是可客观验证的描述

### 第三遍：模糊检测（质量达标）

逐条检查每个功能点的表述是否明确，按以下 8 个维度检测：

| 模糊类型 | 检测方式 | 追问示例 |
|---------|---------|---------|
| **量化缺失** | 无具体数字/指标 | "快速"的具体指标是？<1s？<500ms？ |
| **主语缺失** | 谁来做？ | 前端校验还是后端校验？ |
| **条件缺失** | 什么条件？什么结果？ | 具体异常类型？提示文案/弹窗？ |
| **程度模糊** | "主流""常见"等无定义词 | "主流车型"具体指哪些？ |
| **范围模糊** | "部分""某些"无划分规则 | 划分规则是什么？按角色/标签/权限？ |
| **时态模糊** | "后续""将来"无明确版本 | 当前版本做不做？P0 还是未来规划？ |
| **参照模糊** | "类似 XX 那样"无具体指向 | 微信的哪个具体功能？交互/视觉/全部？ |
| **冲突未处理** | 多处说法不一致 | A 处说"必须登录"，B 处说"游客可用"，以哪个为准？ |

#### 矛盾检测

除单条模糊表述外，还需检测需求间的交叉矛盾：

| 矛盾类型 | 检测方式 | 追问示例 |
|---------|---------|----------|
| **功能矛盾** | 交叉对比功能点要求，检查是否有冲突 | A 要求"实时同步"，B 要求"批量处理"，以哪个为准？ |
| **约束矛盾** | 检查约束条件间是否冲突 | 技术约束要求"轻量级"，业务约束要求"支持并发1000"，是否兼容？ |
| **优先级矛盾** | 同一功能在不同段落的优先级是否一致 | 第3章说 P0，第5章说 P2，以哪个为准？ |
| **时序矛盾** | 检查依赖关系是否可行（循环依赖、不可能序列） | A 依赖 B，B 依赖 C，C 依赖 A，依赖循环如何打破？ |

矛盾检测结果纳入模糊项表格，标注矛盾类型和影响范围（涉及哪些功能点）。

- **第三遍检测出模糊项但未生成追问，不得输出最终结果**

### 分析依赖关系

- 识别功能间的依赖关系（A 依赖 B 才能运行）
- 识别功能与已有系统的依赖

## 输出格式：六要素 Spec 框架

Spec 输出包含六个核心要素，确保下游（arch-designer）拿到完整上下文：

1. **Outcomes（预期成果）** — 需求实现后的业务目标和成功指标
2. **Scope Boundaries（范围边界）** — 明确包含什么和不包含什么
3. **功能点 + 验收标准** — 结构化提取的核心内容
4. **Constraints（约束条件）** — 技术、业务、安全约束
5. **Prior Decisions（已有决策）** — 已确定的设计方向、技术选型、架构约定
6. **Open Questions（待确认项）** — 模糊项和追问清单

```markdown
# 结构化 Spec：[文档标题]

## 预期成果
- 业务目标：...
- 成功指标：...

## 范围边界
- 包含：...
- 不包含（明确排除）：...

## 功能点清单
| ID | 功能点 | 优先级 | 关联需求 |
|----|-------|--------|----------|
| F-01 | ... | P0 | ... |

## 验收标准
| ID | 功能点 | Given | When | Then |
|----|-------|-------|------|------|
| AC-01 | F-01 | ... | ... | ... |

## 约束条件
- 技术约束：...
- 业务约束：...
- 安全约束：...

## 已有决策
- 技术选型：...
- 架构约定：...
- 设计方向：...

## 模糊项
| 问题 | 建议 | 优先级 |
|------|------|--------|
| "..."未明确 | 建议确认... | 高/中/低 |

## 依赖关系
- 本功能依赖已有功能：...
- 本功能被其他功能依赖：...
```

输出末尾附加验证标记，供下游 SKILL 检查上游产物完整性：

```markdown
<!-- CONTEXT-CHECK: F-{功能点数量}, AC-{验收标准数量}, C-{约束条件数量}, Q-{模糊项数量} -->
```

## 追问回填机制

当用户回答追问清单中的问题后，将答案回填到 Spec：

1. 将答案回填到 Spec 对应的功能点描述中
2. 更新受影响的验收标准
3. 将已回填的模糊项状态从"待确认"更新为"已确认"
4. 如追问答案引发新的模糊项 → 补充到追问清单

回填完成后输出更新摘要："已回填 N 项，剩余 M 项待确认，新增 K 项追问。"

> 无需重新执行完整解析流程，直接在已有 Spec 上更新。

## 增量更新场景

当用户提供已解析过的 PRD 的更新版本时：

1. 对比新旧版本 PRD 的差异
2. 仅重新解析变更部分，更新 Spec 中对应的功能点、验收标准和约束条件
3. 保留未变更部分的原有 Spec 内容
4. 标注变更影响范围："以下 N 个功能点因 PRD 更新而变更，下游产物可能已过期"

### Delta 分类

增量更新时，每个功能点变更必须标注 Delta 类型：

- **ADDED**：新增功能点（包含完整功能点描述、验收标准）
- **MODIFIED**：修改已有功能点（包含变更说明 + 修改前文本 + 修改后文本）
- **REMOVED**：删除已有功能点（标注删除原因）

### 增量 Spec 输出格式

```markdown
# 增量 Spec 更新

## Delta 统计
- ADDED: N 个功能点
- MODIFIED: N 个功能点
- REMOVED: N 个功能点

## 变更详情

### ADDED
| ID | 功能点 | 优先级 | 关联需求 |
|----|-------|--------|----------|
| F-XX | ... | P1 | ... |

### MODIFIED
| ID | 功能点 | 变更说明 | 修改前 | 修改后 |
|----|-------|---------|-------|-------|
| F-XX | ... | 新增了XX条件 | 原文 | 新文 |

### REMOVED
| ID | 功能点 | 删除原因 |
|----|-------|----------|
```

> 增量更新仅在用户明确提供"更新版 PRD"时触发，普通新 PRD 仍走全量解析。

## Spec 摘要（长文档场景）

当 Spec 超过 500 行时，在输出开头生成摘要：

```markdown
## Spec 摘要
| 章节 | 核心内容 |
|------|----------|
| 预期成果 | ... 1-2 句话 |
| 范围边界 | ... 1-2 句话 |
| 功能点 | N 个功能点，核心：F-01, F-02, F-03 |
| 验收标准 | N 条，覆盖全部功能点 |
| 约束条件 | N 条技术约束，N 条业务约束 |
| 已有决策 | ... 1-2 句话 |
| 模糊项 | N 项待确认 |
```

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 所有功能点（含隐式的）均已提取，无遗漏
- [ ] 每个功能点至少有一条 Given/When/Then 验收标准
- [ ] 模糊项全部标记并生成追问，无"默认理解"项
- [ ] 交叉矛盾已检测并纳入模糊项表格
- [ ] 优先级（P0/P1/P2）已区分
- [ ] 六要素齐全，CONTEXT-CHECK 标记已附加
- [ ] 未修改用户原始意图，仅做结构化提取

## 边界与常见错误

- **不做什么**：不进行架构设计（用 arch-designer）、不拆解任务（用 task-planner）、不输出代码
- **常见错误**：第二遍未完成就输出；检测到模糊项但不追问；把"我认为"当作需求写入 Spec；多份文档错误合并
- **输入缺失**：无需求文本时主动追问，不凭空生成 Spec
