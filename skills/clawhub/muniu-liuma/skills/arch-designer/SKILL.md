# arch-designer：Spec → 架构设计方案

## 何时使用

- 用户提供（或对话中已有）完成的 Spec，要求架构设计
- 用户要求评估架构选型、模块划分、接口风格
- 新需求接入已有项目，需要分析架构影响

**不适用**：没有 Spec 时（先用 spec-writer 生成 Spec）；要求拆解任务（用 task-planner）；要求直接写代码（用 impl-guide）。

## 输入

- **[必需] 结构化 Spec** — 六要素框架产物（功能点、验收标准、约束、已有决策），或用户直接提供的设计描述
- **[可选] 项目现有架构上下文** — 在项目目录中收集：
  - 技术栈（语言、框架、数据库、中间件）
  - 现有模块划分及职责
  - API / 接口风格
  - 关键数据流和依赖关系
  - 已有架构文档（如有）
- 用户可补充技术栈偏好

> 无项目上下文时正常设计，输出末尾提示："未检测到项目上下文，建议在项目目录中调用以获得更好的架构一致性。"

**前置依赖**：不允许在无 Spec 的情况下进行推测性设计。Spec 缺失时提示用户：

> 未检测到 Spec 输入。请提供 Spec 文本，或使用 spec-writer 先生成 Spec（本 SKILL 只负责架构设计，不执行需求解析）。

**上下文完整性检查**：Spec 来自当前对话时，检查是否包含验证标记 `<!-- CONTEXT-CHECK: ... -->`；缺失或异常时提示用户"上游 Spec 可能不完整，建议确认后继续"。

## 项目上下文收集范围

| 收集项 | 来源示例 | 收集深度 |
|---------|---------|----------|
| 技术栈 | `package.json`、`pom.xml`、`go.mod` | 直接读取配置文件 |
| 模块划分 | 项目目录结构、`src/` 子目录 | 扫描目录层级（最深 3 层） |
| 现有 API/接口 | 路由文件、Controller 类、OpenAPI | 读取路由定义，不深入实现 |
| 已有架构文档 | `ARCHITECTURE.md`、`docs/` | 仅读取文档摘要 |
| 依赖关系 | 模块间 import/引用 | 分析顶层依赖，不做递归分析 |

> 优先读取配置文件和目录结构（成本低、信息密度高），代码分析仅作补充。项目规模较大时，可主动询问用户"项目核心模块有哪些"以替代全量扫描。

## 执行流程

### 步骤 A：交叉分析

1. 读入所有 Spec，识别 Spec 数量和功能域
2. 分析 Spec 间的关系：
   - **模块重叠检测** — 是否有多个 Spec 定义了相同或相似的模块
   - **接口依赖检测** — 是否有 Spec 的输出是另一个 Spec 的输入
   - **技术栈冲突检测** — 是否有 Spec 提出了不一致的技术选型
   - **完全不相关** — 多个 Spec 分属不同的功能域
3. 如有项目上下文，分析新设计对现有架构的影响
4. 输出关系类型：强相关 / 弱相关 / 不相关

### 步骤 B：功能交互分析

识别功能点之间的跨功能影响关系，确保架构设计不遗漏隐式依赖：

1. **交互矩阵** — 构建功能点 × 功能点矩阵，标注每对功能点间的交互类型（数据流/事件/共享状态/无）
2. **级联影响分析** — 某个功能变更时，识别可能受影响的下游功能
3. **共享资源识别** — 识别多个功能共享的资源（数据库表、缓存、配置等）

### 步骤 C：分层设计

根据关系类型选择设计策略：

| 关系 | 策略 |
|------|------|
| **强相关** | 统一设计一套架构，所有 Spec 的需求一次覆盖 |
| **弱相关** | 各自独立设计，接口定义时对齐，标注跨 Spec 边界 |
| **不相关** | 完全独立设计，互不影响 |

- 如用户提供了技术栈偏好，优先使用
- 标识可扩展点（只标记位置，不做预实现）

### 步骤 D：架构决策记录（ADR）

为每个重大架构决策生成 ADR（Architecture Decision Record）：

- **决策**：选择了什么方案
- **背景**：面临什么问题、为什么需要做决策
- **备选方案**：考虑过哪些方案（至少 2 个）
- **理由**：为什么选择当前方案
- **后果**：这个决策带来的影响和取舍

ADR 触发条件：技术选型（框架、数据库、中间件）、架构模式（单体/微服务、同步/异步）、数据模型设计（关系型/文档型）、API 风格（REST/GraphQL/gRPC）。每个需求至少 1 个 ADR，复杂需求可多个。

### 步骤 E：风险评估

评估以下维度的技术风险：

- **技术风险**：新技术/新库的成熟度、稳定性、社区活跃度
- **实现风险**：方案复杂度是否超出团队经验
- **性能风险**：关键性能指标是否可达成
- **集成风险**：与现有系统的兼容性问题

### 步骤 F：方案输出

根据关系类型选择输出形式：统一架构 / 标注边界 / 分开输出。

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 交叉分析已执行（多 Spec 时未跳过步骤 A）
- [ ] 功能交互矩阵已构建（隐式依赖未遗漏）
- [ ] 每个需求至少 1 个 ADR，备选方案 ≥ 2
- [ ] 有项目上下文时已做一致性检查，不一致项已标注
- [ ] 无项目上下文时已提示"未检测到项目上下文"
- [ ] 新增/修改/不变三类模块已显式标注
- [ ] 高风险项未跳过（有项目上下文时）
- [ ] 可扩展点仅标记位置，未做预实现
- [ ] CONTEXT-CHECK 标记已附加

## 边界与常见错误

- **不做什么**：不设计实现细节（留给 impl-guide 与代码阶段）、不拆解任务（用 task-planner）、不预实现未来需求
- **常见错误**：无 Spec 时推测性设计；多个 Spec 跳过交叉分析直接合并；不相关 Spec 强行合并；遗漏"新增/修改/不变"标注
- **输入缺失**：Spec 缺失时提示用户提供或用 spec-writer 生成，不自行回溯补齐
