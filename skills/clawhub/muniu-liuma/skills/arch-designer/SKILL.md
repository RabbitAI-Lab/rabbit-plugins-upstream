# arch-designer：Spec → 架构设计方案

## 何时使用

- 用户提供（或对话中已有）完成的 Spec，要求架构设计
- 用户要求评估架构选型、模块划分、接口风格
- 新需求接入已有项目，需要分析架构影响

## 不适用场景

- 没有 Spec 时 → 先用 spec-writer 生成 Spec（本 SKILL 不做推测性设计）
- 要求拆解任务 → 使用 task-planner
- 要求直接写代码 → 使用 impl-guide

> 以上场景下不产出架构设计；若 Spec 仅部分可用，可对可用模块做局部设计并标注缺口，不输出未经验证的完整架构。

## 输入

- **[必需] 结构化 Spec** — 六要素框架产物（功能点、验收标准、约束、已有决策），或用户直接提供的设计描述
- **[可选] 项目现有架构上下文** — 在项目目录中收集：
  - 技术栈（语言、框架、数据库、中间件）
  - 现有模块划分及职责
  - API / 接口风格
  - 关键数据流和依赖关系
  - 已有架构文档（如有）
- 用户可补充技术栈偏好

> 无项目上下文时正常设计，输出末尾提示："未检测到项目上下文，建议在项目目录中调用以获得更好的架构一致性。"

**前置依赖**：不允许在无 Spec 的情况下进行推测性设计。Spec 缺失时提示用户：

> 未检测到 Spec 输入。请提供 Spec 文本，或使用 spec-writer 先生成 Spec（本 SKILL 只负责架构设计，不执行需求解析）。

**上下文完整性检查**：Spec 来自当前对话时，检查是否包含验证标记 `<!-- CONTEXT-CHECK: ... -->`；缺失或异常时提示用户"上游 Spec 可能不完整，建议确认后继续"。

## 项目上下文收集范围

| 收集项 | 来源示例 | 收集深度 |
|---------|---------|----------|
| 技术栈 | `package.json`、`pom.xml`、`go.mod` | 直接读取配置文件 |
| 模块划分 | 项目目录结构、`src/` 子目录 | 扫描目录层级（最深 3 层） |
| 现有 API/接口 | 路由文件、Controller 类、OpenAPI | 读取路由定义，不深入实现 |
| 已有架构文档 | `ARCHITECTURE.md`、`docs/` | 仅读取文档摘要 |
| 依赖关系 | 模块间 import/引用 | 分析顶层依赖，不做递归分析 |

> 优先读取配置文件和目录结构（成本低、信息密度高），代码分析仅作补充。项目规模较大时，可主动询问用户"项目核心模块有哪些"以替代全量扫描。

## 执行流程

### 步骤 A：交叉分析

1. 读入所有 Spec，识别 Spec 数量和功能域
2. 分析 Spec 间的关系：
   - **模块重叠检测** — 是否有多个 Spec 定义了相同或相似的模块
   - **接口依赖检测** — 是否有 Spec 的输出是另一个 Spec 的输入
   - **技术栈冲突检测** — 是否有 Spec 提出了不一致的技术选型
   - **完全不相关** — 多个 Spec 分属不同的功能域
3. 如有项目上下文，分析新设计对现有架构的影响
4. 输出关系类型：强相关 / 弱相关 / 不相关

### 步骤 B：功能交互分析

识别功能点之间的跨功能影响关系，确保架构设计不遗漏隐式依赖：

1. **交互矩阵** — 构建功能点 × 功能点矩阵，标注每对功能点间的交互类型（数据流/事件/共享状态/无）
2. **级联影响分析** — 某个功能变更时，识别可能受影响的下游功能
3. **共享资源识别** — 识别多个功能共享的资源（数据库表、缓存、配置等）

**矩阵规模规则**：功能点数 ≤ 7 输出全量矩阵（7×7 已验证为可行边界）；> 7 时矩阵规模爆炸，仅选高交互对（数据流/事件/共享状态）并在输出中显式声明"仅列高交互对"。

### 步骤 C：分层设计

根据关系类型选择设计策略：

| 关系 | 策略 |
|------|------|
| **强相关** | 统一设计一套架构，所有 Spec 的需求一次覆盖 |
| **弱相关** | 各自独立设计，接口定义时对齐，标注跨 Spec 边界 |
| **不相关** | 完全独立设计，互不影响 |

- 如用户提供了技术栈偏好，优先使用
- 标识可扩展点（只标记位置，不做预实现）

### 步骤 D：架构决策记录（ADR）

为每个重大架构决策生成 ADR（Architecture Decision Record）：

- **决策**：选择了什么方案
- **背景**：面临什么问题、为什么需要做决策
- **备选方案**：考虑过哪些方案（至少 2 个）
- **理由**：为什么选择当前方案
- **后果**：这个决策带来的影响和取舍

ADR 触发条件：技术选型（框架、数据库、中间件）、架构模式（单体/微服务、同步/异步）、数据模型设计（关系型/文档型）、API 风格（REST/GraphQL/gRPC）。每个需求至少 1 个 ADR，复杂需求可多个。

### 步骤 E：风险评估

评估以下维度的技术风险：

- **技术风险**：新技术/新库的成熟度、稳定性、社区活跃度
- **实现风险**：方案复杂度是否超出团队经验
- **性能风险**：关键性能指标是否可达成
- **集成风险**：与现有系统的兼容性问题

**模糊项传导规则**（Spec 模糊项不得在架构层丢失）：

- Spec 模糊项（Q 编号）全量传导至下游产物：接口定义（参数/行为处标注"待确认"）、ADR（以策略开关/配置项承接）、风险评估（对应 R-XX）
- 安全类约束（含模糊项中的安全内容）优先识别为高风险项，纳入技术风险评估
- 被 ADR/风险承接的模糊项显式标注来源 Q 编号，便于下游（task-planner/impl-guide）追溯
- 风险缓解建议区分治标与根治：治标为缓解当前风险（约束条件/临时措施），根治为架构层消除风险来源（重新选型/结构调整）；风险评估中同时给出两者
- 风险复核机制：高风险项标注复核时点（后续架构演进/迭代评审），风险状态（已缓解/持续存在/新增）随架构更新，避免一次性评估后失联

### 步骤 F：方案输出

根据关系类型选择输出形式：统一架构 / 标注边界 / 分开输出。

## 场景模板（可选参考）

用户明确指定场景，或 Spec 特征与以下识别条件匹配时，以对应模板为**设计起点**（模块骨架与接口风格），再按 Spec 实际内容增删调整。模板为参考起点而非强制结构，不替代步骤 A–F 的执行。

| 场景 | 识别特征 |
|------|---------|
| **Web 全栈（前后端分离）** | 含 UI 页面 + 后端接口，交付目标为浏览器/桌面端 |
| **纯 API 服务** | 无 UI 页面，面向程序调用方（B 端集成/移动端/第三方） |
| **小程序** | 含小程序端页面 + 后端接口，交付目标为微信/支付宝等小程序平台 |

### Web 全栈（前后端分离）

**模块划分骨架（起点）**：

| 层 | 默认模块 | 职责 |
|----|---------|------|
| 前端 | 页面层（路由页面）、组件层（可复用 UI）、状态层（全局状态）、API 客户端 | 界面渲染与交互、服务端通信 |
| 后端 | 接口层（Controller/路由）、业务层（Service）、数据访问层（Repository/ORM）、基础设施（中间件/配置/日志） | 接口暴露、业务编排、数据持久化 |
| 共享 | 类型定义 / 接口契约 | 前后端类型与契约一致性 |

**接口风格约定（起点）**：RESTful + JSON；**双端契约先行**（接口契约/OpenAPI 定义先行，前端按契约开发）；鉴权方案（Session/JWT）须经 ADR 确认；错误响应含错误码 + 消息，前端统一处理。

### 纯 API 服务

**模块划分骨架（起点）**：

| 层 | 默认模块 | 职责 |
|----|---------|------|
| 接口层 | 路由/Controller、入参校验 | 端点暴露、参数校验 |
| 业务层 | Service、领域规则 | 业务编排、规则执行 |
| 数据层 | Repository、数据模型 | 持久化、查询封装 |
| 基础设施 | 中间件、配置、日志、限流 | 横切关注点 |

**接口风格约定（起点）**：RESTful 或 RPC（须经 ADR 确认）；统一响应包装与错误码规范；写操作幂等设计（重试安全）；列表接口统一分页约定；鉴权（API Key/OAuth2）须经 ADR 确认。

### 小程序

**模块划分骨架（起点）**：

| 层 | 默认模块 | 职责 |
|----|---------|------|
| 小程序端 | 页面层、组件层、状态层、API 封装 | 界面渲染、平台 API 调用封装 |
| 后端（如含） | 接口层、业务层、数据访问层 | 业务与数据（参考纯 API 服务骨架） |
| 平台适配 | 登录态（openid/session）、订阅消息、上传下载 | 平台能力封装 |

**接口风格约定（起点）**：与后端 RESTful 契约；登录态流程（wx.login → code → session）须经 ADR 确认；弱网/超时处理与重试策略显式设计；列表分页 + 加载态为默认交互约定。

> 场景模板与评测集复用：eval/datasets 样本按场景分类（如 Web 全栈/纯 API/小程序），模板效果可量化对照。

输出末尾附加验证标记，供下游（task-planner）检查上游产物完整性：

```markdown
<!-- CONTEXT-CHECK: M-{模块数量}, IF-{接口数量}, R-{风险评估项数}, S-{Spec数量} -->
```

**数值口径**：M/IF 计**总数**（含存量复用/修改的模块与接口），并同步在"存量影响/架构一致性检查"中单列存量处置统计（如"9 个存量接口：6 修改 + 3 兼容"），两处并存、口径一致；无项目上下文时 M/IF 即新增数。

### 格式切换（可选）

默认输出 Markdown（以上模板）。用户明确要求 JSON / CSV 时：

- **JSON**：按产物章节结构输出 JSON 对象，字段映射如下，内容与执行方法完全一致，仅改变呈现格式
- **CSV**：仅表格类产物（模块划分、接口定义、风险评估等）以 CSV 表格输出，每行一条记录，列名取表头
- **CONTEXT-CHECK 标记在任何格式下保留**（JSON 置于顶层字段 `context_check`，CSV 置于末尾注释行），供下游检查
- 格式切换不改变执行流程、判定口径与自检清单

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 交叉分析已执行（多 Spec 时未跳过步骤 A）
- [ ] 功能交互矩阵已构建（隐式依赖未遗漏）
- [ ] 每个需求至少 1 个 ADR，备选方案 ≥ 2
- [ ] 有项目上下文时已做一致性检查，不一致项已标注
- [ ] 无项目上下文时已提示"未检测到项目上下文"
- [ ] 新增/修改/不变三类模块已显式标注
- [ ] 高风险项未跳过（有项目上下文时）
- [ ] 高风险项已标注复核时点（风险状态随架构演进更新）
- [ ] 可扩展点仅标记位置，未做预实现
- [ ] 模糊项已全量传导至接口定义/ADR/风险，未在架构层丢失（Q 编号可追溯）
- [ ] 功能交互矩阵按规模规则输出（≤7 全量 / >7 高交互对并标注省略）
- [ ] CONTEXT-CHECK 标记已附加且数值口径正确（有上下文时 M/IF 为总数，存量处置统计单列）

## 边界与常见错误

- **不做什么**：不设计实现细节（留给 impl-guide 与代码阶段）、不拆解任务（用 task-planner）、不预实现未来需求
- **常见错误**：无 Spec 时推测性设计；多个 Spec 跳过交叉分析直接合并；不相关 Spec 强行合并；遗漏"新增/修改/不变"标注；Spec 模糊项在架构层静默丢失；功能点 >7 仍输出全量交互矩阵
- **输入缺失**：Spec 缺失时提示用户提供或用 spec-writer 生成，不自行回溯补齐
