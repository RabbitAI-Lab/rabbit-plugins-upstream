# impl-guide：任务+架构 → 实现指导规范

## 何时使用

- 用户提供（或对话中已有）任务清单与架构设计方案，要求生成编码阶段的实现指导
- 用户要求明确行为边界（可做/需确认/禁止）、分阶段执行计划、测试要求
- 用户准备开始编码，需要质量基准

## 不适用场景

- 没有任务清单时 → 先用 task-planner 生成（本 SKILL 不执行任务规划）
- 要求审计完成情况 → 使用 audit-trace
- 要求直接写业务代码 → 本 SKILL 只产出指导规范，不代写实现

> 以上场景下不产出实现指导；若任务清单部分可用，可对可用任务生成指导并标注缺口，不输出不完整的实现计划。

## 输入

- **[必需] 任务清单** — 任务 ID、依赖关系、验收条件、证据要求（task-planner 输出）
- **[必需] 架构设计方案** — 模块划分、接口定义、技术选型（arch-designer 输出）
- **[可选] 结构化 Spec** — 功能点、验收标准、约束条件（用于生成一致性测试要求）

**前置依赖**：不允许在无任务清单的情况下生成实现指导。任务清单缺失时提示用户：

> 未检测到任务清单。请提供任务清单文本，或使用 task-planner 基于架构方案生成（本 SKILL 只负责实现指导，不执行任务规划）。

## 执行流程

### 步骤 A：上下文完整性检查

检查上游产物是否包含验证标记 `<!-- CONTEXT-CHECK: ... -->`：

- 如验证标记存在且数值合理 → 继续生成
- 如验证标记缺失或数值异常 → 提示用户"上游产物可能不完整，建议确认后继续"

### 步骤 B：生成三层边界约束

从架构设计的约束条件和 Spec 的约束条件，派生 Agent 行为边界：

| 层级 | 含义 | 生成规则 |
|------|------|---------|
| ✅ Always | 无需询问即可做 | 运行测试、遵循命名规范、记录日志、使用已有依赖 |
| ⚠️ Ask First | 需人类确认 | 修改数据库 Schema、添加新依赖、变更 API 签名、删除文件/目录、修改配置 |
| 🚫 Never | 绝对禁止 | 提交密钥/凭证、修改 CI 配置、删除测试用例、绕过安全检查 |

**生成原则**：
- 从架构设计的约束条件中直接提取硬性约束（如"不得引入新框架"→ 🚫 Never）
- 从 Spec 约束条件中提取业务约束（如"必须支持多租户"→ ✅ Always 在每次修改时检查多租户兼容性）
- 通用安全规则始终包含在 🚫 Never 中（提交密钥、删除测试等）

**约束派生建议区分治标与根治**：治标为当前任务可执行的实施约束（如限定本次修改范围），根治为沉淀为项目级规范（如将命名/日志规则写入 Always 层，防止同类问题复发）；边界约束表中同时给出两者。

**未决项三层传导**：Spec/架构的未决项（Q-XX）在三层边界中同时出现——Ask First（标注"待确认"）+ Always（按默认策略执行）+ Never（禁止写死，需配置化承接）；未决项编号可追溯至上游产物，不得在边界层丢失。

**优先级跨产物传导**：测试要求/边界规则的优先级随所属功能点优先级传导（P0 功能点的 AC → P0；P1 功能点 → P1），不得自行升降级。

### 步骤 C：生成分阶段执行策略

将任务按开发阶段分组，形成阶段化的执行计划：

**阶段划分规则**：
1. **Setup 阶段** — 基础设施搭建（项目初始化、依赖安装、配置、数据库 Schema）
2. **Core 阶段** — 核心功能实现（P0 功能点的主路径）
3. **Advanced 阶段** — 增强功能（P1/P2 功能、错误处理、边界情况）
4. **Testing 阶段** — 测试与验证（单元测试、集成测试、性能测试）

**执行策略**：
- 阶段间**串行**：前一阶段审查门禁通过后，才进入下一阶段
- 阶段内**并行**：无依赖关系的任务可并行执行
- 每个审查门禁检查：
  - 阶段内任务是否全部完成
  - 验收条件是否达标
  - 证据是否提供（如任务清单有证据要求）
  - 是否有需要回退到上游（任务规划/架构设计/Spec）的问题

### 步骤 D：生成一致性测试要求与可执行测试骨架

从 Spec 和架构设计中派生测试要求（语言无关），并升级为**可执行测试骨架**（V-01，详见 `TEST-SKELETON-SPEC.md`）：

**派生规则**：
- Spec 验收标准（Given/When/Then） → 功能测试断言
- 架构设计 API 定义（输入/输出/状态码） → API 测试用例
- Spec 约束条件（性能指标） → 基准测试要求
- Spec 约束条件（安全要求） → 安全检查项
- 架构设计数据模型 → 数据完整性验证

**测试类型标注**：每条测试要求标注类型（功能/性能/安全/数据完整性）。

**骨架生成规则**：
- 每个 AC 至少一个测试用例，命名 `test_ac{AC-ID}_{场景}`（可回溯）
- 用例结构：Arrange（Given）→ Act（When）→ Assert（Then）
- 检测架构技术选型 → 按框架适配表输出对应语法（pytest / Vitest / JUnit / Go / Rust）；技术选型未知时输出语言无关伪代码并注明"需按目标框架适配"
- 骨架只生成断言与用例框架，不编写业务逻辑实现（桩体留空或抛占位异常）

**要求表 vs 骨架用例粒度映射**：一致性测试要求表 = 验收契约（按来源聚合，一来源一行）；测试骨架 = 执行用例（按场景拆分，用例可多于要求条目）；骨架文件按模块分文件，双端架构按端拆分（后端 API 测试 + 端上逻辑测试，端上以平台 API mock 适配）。

**前端骨架最小覆盖**：前端组件骨架至少含渲染用例 + 关键交互用例各 1（仅渲染级视为覆盖不足）。

### 步骤 E：组装输出

将三层边界约束、分阶段执行策略、一致性测试要求组装为实现指导规范。

### 格式切换（可选）

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 三层边界约束齐全（Always / Ask First / Never 均非空）
- [ ] 🚫 Never 包含安全相关硬性禁止规则
- [ ] 全部任务已归属且仅归属一个阶段
- [ ] 阶段间依赖关系保留（被依赖任务所在阶段在前）
- [ ] 每个阶段审查门禁含该阶段全部任务的验收条件检查
- [ ] 一致性测试要求已逐条从 Spec 验收标准派生，无遗漏
- [ ] 每条测试要求已标注类型（功能/性能/安全/数据完整性）
- [ ] 测试骨架已生成（每个 AC 至少 1 个用例，命名可回溯，框架语法与技术选型匹配）
- [ ] 未决项已三层传导（Ask First/Always/Never）且 Q 编号可追溯
- [ ] 测试要求/边界规则优先级随所属功能点优先级传导
- [ ] 骨架按模块/端组织文件，前端含渲染 + 关键交互用例
- [ ] CONTEXT-CHECK 标记已附加

## 边界与常见错误

- **不做什么**：不编写业务逻辑实现（只产出指导规范）、不做任务规划（用 task-planner）、不做架构设计（用 arch-designer）
- **常见错误**：无任务清单时凭 Spec 直接生成；三层边界某层缺失；任务依赖顺序在阶段划分中被破坏；测试断言遗漏 Spec 验收标准；未决项未传导至三层边界；前端骨架仅渲染级用例；测试要求表与骨架用例粒度混淆
- **输入缺失**：任务清单缺失时提示用户提供或用 task-planner 生成，不自行回溯补齐
