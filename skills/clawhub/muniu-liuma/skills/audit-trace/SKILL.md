# audit-trace：产物+代码 → 完工审计报告

## 何时使用

- 用户提供（或对话中已有）开发产物与实现代码，要求审计需求完成情况
- 用户要求判定交付状态（可交付/有条件交付/不可交付）
- 用户要求核对任务证据、无主代码、验收标准达标情况

**不适用**：没有实现代码或产物时（至少需要 Spec + 代码才能审计）；要求生成实现指导（用 impl-guide）。

## 输入

- **[必需] 结构化 Spec** — 功能点清单、验收条件（spec-writer 输出）
- **[必需] 实现代码** — 项目代码（用于代码扫描和审计）
- **[可选] 架构设计方案** — 模块划分（arch-designer 输出）
- **[可选] 任务清单** — 任务 ID 和依赖关系、证据要求（task-planner 输出）
- **[可选] 实现指导** — 三层边界约束、一致性测试要求（impl-guide 输出）
- **[可选] 实现方自评** — 实现方对各功能点/任务的完成声明（✅/⚠️/❌ + 依据），用于对抗性审查差异对照（P1-04 A-02）；缺失时跳过对照维度并标注

**输入缺失处理**（按顺序）：

1. **检查对话上下文** — 优先从当前对话中查找已有产物
2. **用户提供** — 缺失产物询问用户补充（不自动回溯调用上游 SKILL）
3. **部分审计** — 如用户明确要求"只看能查的部分"，跳过缺失维度，标注"XX 维度因缺少 XX 输入未审计"

## 执行流程

### 1. 收集输入

从对话上下文或用户提供方式获取产物，按输入缺失处理规则补齐。

### 2. 上下文完整性检查

检查上游产物是否包含验证标记 `<!-- CONTEXT-CHECK: ... -->`：

- 如验证标记存在且数值合理 → 继续审计
- 如验证标记缺失或数值异常（如 F-0 但任务清单有内容） → 提示用户"上游产物可能不完整，建议确认后继续"

### 3. 执行审计：八个维度

| 审计维度 | 检查内容 | 数据来源 |
|---------|---------|---------|
| **功能覆盖** | Spec 中每个功能点是否有对应的任务记录或代码实现 | Spec × 任务清单 × 代码 |
| **架构落地** | 架构设计中定义的每个模块是否在代码中有对应实现 | 架构设计 × 代码 |
| **无主代码** | 是否有实现了但不对应任何 Spec 功能点的代码 | 代码 × Spec（反向扫描） |
| **任务闭环** | 全部任务是否在代码中有对应实现 | 任务清单 × 代码 |
| **验收标准达标** | Spec 中 Given/When/Then 场景是否在代码逻辑中被满足 | Spec 验收标准 × 代码逻辑 |
| **实现指导对照** | 代码实现是否遵循三层边界约束、一致性测试要求是否达标 | 实现指导 × 代码 |
| **测试结果核对** | 实际测试执行结果（通过/失败、覆盖率）是否与验收标准一致（V-02，详见 TEST-SKELETON-SPEC.md） | 测试结果文件 × Spec 验收标准 |
| **证据核对** | 任务清单中的证据要求是否已提供，证据是否与实现匹配 | 任务清单 × 用户提供的证据 |

**测试结果核对规则（V-02/V-03/V-04）**：

1. 按任务清单证据要求字段定位测试结果文件（JSON 或 Markdown 报告）
2. 解析结果，按 `source.ac_ids` 关联到 Spec 功能点
3. 逐 AC 判定：

| 测试结果 | 判定 | 说明 |
|---------|------|------|
| 该 AC 全部用例 passed | ✅ 测试验证通过 | 替代纯代码阅读判定 |
| 存在 failed 用例 | ❌ 存在失败用例 | 失败清单列入报告 |
| 无结果文件/未执行 | ⚠️ 未验证（V-04 降级） | 不默认判定达标 |

**降级规则（V-04）**：任一 P0 功能点"未验证"→ 交付状态不得为"可交付"（最高 ⚠️ 有条件交付）；覆盖率 < 80% 时提示"覆盖率不足，建议补充测试"。

### 3.1 对抗性审查对照（P1-04）

**启用场景**：实现与审计由两次独立调用/独立 Agent 完成（Builder/Critic 角色分离，A-01）；或用户明确要求"对抗性审查"。

**执行规则**：
- 审计判定不采信实现方自评，仅将自评作为对照项（A-03 审计基线固定：逐条核对 Spec/任务清单，禁止"整体印象式"结论）
- 实现方自评缺失时：跳过对照维度，标注"无自评，仅输出审计方判定"

**差异对照表**（A-02）：

| 功能点/任务 | 实现方自评 | 审计方判定 | 双方依据 | 差异 |
|------------|-----------|-----------|---------|------|
| F-01 ... | ✅ 已完成 | ✅ 确认 | 自评：... / 审计：代码路径 | 无 |
| F-07 ... | ✅ 已完成 | ❌ 未实现 | 自评：... / 审计：无对应代码 | ⚠️ 差异 |

- 差异项在报告中高亮，列出双方依据，由用户裁决，审计方不强行推翻自评
- 差异项数量计入报告摘要

### 4. 代码扫描判定标准

| 判定方式 | 适用场景 | 说明 |
|---------|---------|------|
| 文件/目录存在性检查 | 模块级审计 | 检查架构定义的模块是否有对应目录/文件 |
| 函数/类名匹配 | 任务级审计 | 精确匹配 + 模糊匹配（语义相近） |
| 调用链追踪 | 功能覆盖审计 | 从入口点追踪完整功能路径 |

**语言适配**：
- 动态语言（Python/JS/TS）：侧重运行时调用分析和 import/require 分析
- 静态语言（Java/Go/Rust）：利用类型系统和编译时检查

**置信度标注**：每个判定结果标注置信度：
- ✅ **确认** — 高置信度匹配
- ⚠️ **疑似** — 模糊匹配，需用户确认
- ❌ **未实现** — 未找到对应代码

### 5. 三层审计门控（P1-05）

审计结果按三段式门控逐层把关，任一 Gate 未通过则输出缺口清单并阻止进入下一 Gate：

| 门控 | 检查内容（对应审计维度） | 通过条件 |
|------|-------------------------|---------|
| Quality Gate | 无主代码、实现指导对照（违规项）、代码质量基线 | 无 ❌ 项 |
| Review Gate | 功能覆盖、架构落地、任务闭环 | P0 全覆盖（无 P0 缺口；P0 未验证归入 Acceptance Gate 按 V-04 降级） |
| Acceptance Gate | 验收标准达标、测试结果核对、证据核对 | 全部 ✅ 或已标记例外 |

**门控流程**：

1. Quality Gate 未通过（存在 ❌ 项：无主代码/违规实现）→ 输出缺口清单，**阻止进入 Review Gate**，交付状态 ❌ 不可交付
2. Review Gate 未通过（P0 功能点未实现）→ 输出缺口清单，**阻止进入 Acceptance Gate**，交付状态 ❌ 不可交付
3. Acceptance Gate 未通过（存在未标记例外的缺口）→ 输出缺口清单，交付状态 ❌ 不可交付
4. Acceptance Gate 通过但存在已标记例外（P1/P2 缺口、P0 未验证按 V-04 强制降级）→ ⚠️ **有条件交付**
5. 三 Gate 全部通过 → ✅ **可交付**

**例外标记规则**：P0 功能点"未验证"不允许标记例外（V-04：最高 ⚠️ 有条件交付）；P1/P2 缺口可标记例外并列入交付建议。

## 自检清单

输出最终结果前逐项检查，未全部通过不得输出：

- [ ] 八个维度全部覆盖（除非输入缺失并明确标注）
- [ ] 实现指导已提供时，三层边界约束和一致性测试要求已逐条对照
- [ ] 测试结果文件存在时，已按 AC 关联核对通过/失败/未验证（V-02），P0 未验证未判"可交付"（V-04）
- [ ] 任务清单含证据要求时，已逐任务检查证据提供状态
- [ ] 证据未提供的任务已在交付建议中列出
- [ ] 每个判定结果标注了置信度（✅ 确认 / ⚠️ 疑似 / ❌ 未实现）
- [ ] P0 未实现已判定"❌ 不可交付"
- [ ] 无主代码已标注
- [ ] 验收标准逐条对照 Spec 的 Given/When/Then
- [ ] 降级审计已标注跳过维度及原因
- [ ] 对抗性审查启用时，差异对照表已输出且差异项含双方依据（A-02）
- [ ] 三 Gate 已按 Quality → Review → Acceptance 顺序执行，未通过的 Gate 已输出缺口清单并阻止进入下一 Gate（P1-05）
- [ ] P0 未验证未标记例外（V-04），例外项均已标注依据

## 边界与常见错误

- **不做什么**：不修复代码（只报告缺口）、不重新规划任务（用 task-planner）、不生成实现指导（用 impl-guide）、不代替用户裁决差异项
- **常见错误**：跳过维度且未标注原因；判定不带置信度；无主代码忽略；P0 缺口仍判定"可交付"；证据核对凭印象不对照任务清单；门控顺序颠倒或跳过失败 Gate 继续判定；P0 未验证标记例外仍判"可交付"；对抗性审查时采信自评结论
- **输入缺失**：提示用户补充缺失产物或执行部分审计，不自动回溯调用上游 SKILL
