# 边界场景与容错处理

## 入参异常

### 场景1：内容过短（<200字）

**判断**：可能是简历片段、摘要，或用户贴错了内容

**处理**：
```
检测到您提供的内容较短（约XX字）。这可能是：
A. 完整简历但内容精简 → 我可以直接处理，但优化空间有限
B. 只是部分内容 → 请发送完整简历
C. 贴错了内容 → 请重新发送简历

请确认，或直接发送完整简历。
```

### 场景2：非简历内容

**判断**：不含任何工作/项目/教育/技能相关关键词，如纯粹闲聊或长篇技术文章

**处理**：
```
这似乎不是简历内容。请发送您的简历文本，或粘贴简历内容。支持以下格式：
- 直接粘贴纯文本
- 上传 .docx/.pdf/.txt 文件
- 发送截图（我会先提取文字再处理）
```

### 场景3：图片输入

**处理**：
1. 对图片执行 OCR 提取文字
2. OCR 成功 → 展示提取结果 → 确认无误后进入正常流程
3. OCR 失败/质量差 → "图片文字提取失败，可能因为图片模糊或排版复杂。请直接发送文本版简历。"

### 场景4：加密/损坏文件

**处理**：
```
无法读取该文件。可能原因：
- PDF 设有密码保护 → 请解除密码后重新发送
- 文件已损坏 → 请重新导出或发送文本
- 使用了不支持的格式 → 请转为 .docx/.pdf/.txt
```

## JD 解析异常

### 场景5：JD 内容过短（<50字）

**处理**：
```
职位描述内容较短（约XX字），可能不是完整的JD。基于现有内容：
- 提取到的关键词：XXX（列出）
- 将仅做基础对齐，不做深度定制

是否继续？或者补充完整JD以获得更精准的优化。
```

### 场景6：JD 含大量图片/截图

**处理**：先 OCR 提取文字，提取结果可能不准确 → 请用户提供文本版JD以确保准确性

### 场景7：JD 提取不足5个有效关键词

**处理**：
```
JD关键词较少，仅提取到X个有效词：XXX
这可能是职位描述过于笼统或使用了非标准术语。

策略：降级为仅模块1（STAR基础优化），不对JD做深度定制。
如您有其他渠道的JD信息（如官网、猎头沟通），可补充后重新定向。
```

### 场景8：JD 含敏感条件

**判断**：出现年龄（35岁以下/90后等）、性别（男性优先）、籍贯、婚姻状况等

**处理**：
```
注意：JD中包含XXX条件。这些条件在劳动法中属于就业歧视范畴。
我将在优化中忽略这些条件，专注于岗位能力和经验要求。
```

## 用户交互异常

### 场景9：用户拒绝/无法提供量化数据

**处理**（遵循SKILL.md"数据补全追问协议"）：
- 先按协议发起批量追问，给用户补充真实数据的机会
- 用户说"记不清了"或明确拒绝 → 改用定性表述替代（如"覆盖全员""驱动显著提升""从手工操作变为自动化"）
- **不在终版简历保留占位符**（如 `[补充：XX]`、`[建议补充]`）
- 不做量化编造或猜测数字
- 在对话中告知用户哪些bullet用了定性表述，建议面试时准备具体数字以备追问

### 场景10：用户说"你看着改就行"

**处理**：
```
好的，我会基于STAR原则进行改写。改写过程中如发现缺失关键数据（团队规模、覆盖人数、提升幅度、项目周期等），我会汇总后一次性向您询问——能提供的提供，记不清的告诉我，我用定性表述处理。不会在简历里留占位符。
```

### 场景11：用户要求编造数据或经历

**处理**：
```
按照简历优化规范，我不能编造未经确认的数据或经历。不过：
- 如果您的某些成果有大致范围（如"大概节省了30%-40%成本"），可以使用范围值
- 如果有可验证的间接证据（如"项目被公司评为年度最佳"），可以提及作为替代
- 我可以帮您从已有描述中提取所有可能的量化线索

请选择上述任一方式，或提供真实数据。
```

### 场景12：用户中途切换需求

**示例**：正在进行STAR改写，用户说"算了，直接给我做JD优化"

**处理**：保存当前STAR改写进度（如果已完成部分），切换到模块2。在JD优化输出中标注哪些bullet已经过STAR改写、哪些仍是原始状态。

## 结果异常

### 场景13：优化后简历过长

**判断**：超过2页（A4，中文11pt行距1.5）

**处理**：
```
优化后简历约XX页，超过建议的2页上限。建议压缩：
- 5年以下经验 → 1页
- 5-10年 → 1-2页
- 10年以上 → 2页

是否需要我精简以下部分？
A. 合并早期经历（3年以前的可合并为"早期经历"）
B. 精简项目经验（保留最相关的3个）
C. 删除非核心信息（如兴趣爱好、自我评价段落）
```

### 场景14：优化后简历术语过于生硬

**判断**：自然语言流畅度下降——关键词密度过高，读起来像关键词堆砌

**处理**：回退一步，减少关键词注入量。优先保证阅读流畅度，关键词覆盖度可以适度让步。

### 场景15：用户对优化结果不满意

**处理**：
- 先确认不满意的具体方面：太夸张？太保守？不够匹配？格式问题？
- 针对性调整，优先修改用户指出的具体bullet
- 不确定时："优化后的版本与您期望的有差距。方便告诉我具体哪里不满意吗？我可以针对性调整。"

## 跨行业/特殊场景

### 场景16：应届生简历

**特殊处理**：
- 模块顺序调整：教育前置，实习/项目经验次之
- STAR改写时不过度追求量化（应届生量化空间有限）
- JD定向更侧重课程/项目/技能与岗位的对齐
- 不过度包装：只改写表述，不编造实习或项目经历

### 场景17：高管/20年+经验简历

**特殊处理**：
- 模块1：诊断重点放在"成就表述是否够高维"而非"动词是否够强"
- 早期经历允许合并为"2005-2012：XX公司/XX职位，关键成就：XXX"
- JD定向时，Summary可能比详细bullet更重要
- 关键原则：简历展示的不是"做了什么"而是"管了多大的盘、带来什么级别的商业影响"

### 场景18：自由职业/间断期

**特殊处理**：
- 如用户主动提及间断期，帮助用户用积极框架重新表述（如"Gap Year期间完成XX学习/项目"）
- 如用户未提及简历中间断期，不主动指出或质疑
- 自由职业经历按项目制组织，等效于正式工作经历

### 场景19：简历含敏感个人信息

**判断**：身份证号、家庭住址（精确到门牌号）、银行账号等

**处理**：
```
注意：简历中包含XXX等敏感个人信息。建议删除或脱敏处理：
- 家庭住址 → 改为"城市-区域"
- 身份证号 → 完全删除
- 精确出生日期 → 可选删除或仅保留年份

是否在优化版本中自动脱敏这些信息？
```

## 多语言/混合场景

### 场景20：中英文混合简历

**处理**：
- 识别简历主体语言（根据占比，>60%为判断标准）
- 英文简历 → 使用英文STAR规则（≤25词/bullet），引用英文动词库
- 中文简历中含英文技能/术语 → 保持原样（如Python、SQL），不做翻译
- 双语简历 → 默认只优化主体语言版本，如用户需要双语版本则分两次处理

### 场景21：用户要求生成双语版本

**处理**：
```
生成双语版本需要额外注意：
1. 我将先优化中文版，确认满意后再翻译为英文
2. 英文版本会使用英文STAR规则（≤25词/bullet），不是中文的逐句翻译
3. 中英文的强动词库不同，会分别匹配

是否继续？
```
