# Troubleshooting

## The skill isn't eligible / doesn't load

This skill is gated on `DANUBE_API_KEY` being set and `curl` being on `PATH`.
Check both:

```bash
test -n "$DANUBE_API_KEY" && echo "DANUBE_API_KEY is set (${#DANUBE_API_KEY} chars)"   # keys are opaque tokens, no fixed prefix
command -v curl
```

If the key lives only in `openclaw.json`, make sure it's under the skill's
entry, which is what `primaryEnv` binds to:

```json5
{ skills: { entries: { danube: { enabled: true, apiKey: "YOUR_DANUBE_API_KEY" } } } }
```

`openclaw skills list --json` shows the skill's `eligible` flag and anything `missing`.

## Danube's MCP tools don't show up in OpenClaw

```bash
openclaw mcp list                      # is "danube" saved?
openclaw mcp doctor danube --probe     # can OpenClaw connect and list tools?
openclaw mcp status
```

Common causes:

- The server was saved without `"transport":"streamable-http"` — OpenClaw then
  assumes SSE, which Danube does not serve. Re-run the `openclaw mcp set danube '{...}'`
  command from `SKILL.md`.
- The header was saved as the literal string `${DANUBE_API_KEY}` instead of
  the key value. `openclaw mcp set` stores what you type; use the actual
  key value (or switch to `"auth":"oauth"` + `openclaw mcp login danube`).
- The agent is running with the `minimal` tool profile, which hides MCP tools.
  Use `coding` or `messaging`, or check `tools.deny` for `bundle-mcp`.
- **An OAuth connection stopped working after it had been working.** Since 2026-10-04 the
  server issues one-hour access tokens (`dmcp_at_…`) and refresh tokens (`dmcp_rt_…`) that are
  spent on every use. Read the `401` before re-running sign-in: a `WWW-Authenticate` carrying
  `error="invalid_token"` means the access token simply expired or was revoked, and a refresh
  fixes it. Without that marker it is not a token problem and refreshing will not help — the
  message says which: "API key required…" (nothing reached the server) or "Invalid API key"
  (a credential arrived and was rejected). If the refresh
  itself answers `invalid_grant`, you may have presented a token you had already exchanged —
  within 30 seconds of its rotation that is forgiven as a race ("Refresh token was already
  used"), but after that it is treated as a stolen token and **the whole connection is
  revoked** — recovering means running sign-in again from the client (`openclaw mcp login
  danube`), not anything on the dashboard: https://danubeai.com/dashboard/connected-apps lists
  connections and revokes them, and has no re-approve button. Keep only the newest pair and
  never retry a refresh with an old one. A connection the user revoked can also keep answering
  for up to a minute, since the server caches the token lookup for 60 seconds.

Sanity-check the server and the key from the shell:

```bash
curl -s https://mcp.danubeai.com/health                      # server up? (no auth needed)
curl -s https://api.danubeai.com/health                      # REST backend up? (no auth needed either)
curl -s -o /dev/null -w "%{http_code}\n" "https://api.danubeai.com/v1/tools/search?query=weather" \
  -H "danube-api-key: ${DANUBE_API_KEY}"                      # 200 = key accepted, 401 = rejected
```

The second one is worth reading, not just status-checking, because it is the one place a caller
can see **how old the REST backend answering them is** — which matters whenever a note here or
in the skill file says a behaviour changed on some date and warns that an older backend may
still do the old thing. It is `/health`, not `/v1/health` (a `404`), and it answers the same with
or without a key. Live on 2026-10-10, unauthenticated, with the rest of the fields elided:

```json
{"status": "healthy", "database": "ok", "started_at": "2026-10-09T12:38:37.219276+00:00",
 "uptime_seconds": 84908, "catalogue": {"services": 517},
 "index": {"tools": 12734, "lexical_rows": 12734}}
```

`started_at` is when that backend **process** booted, so `uptime_seconds` is a floor on the age
of the code answering you and there is no ceiling: a process cannot be running code that did not
exist when it started, but a restart reboots the image it already had, so a fresh `started_at`
can still be serving old code. Read it in one direction only. A `started_at` *earlier* than a
date in one of those notes means the old behaviour is the likely one — likely rather than
certain, because those dates are when someone verified a fix, not necessarily when it shipped,
so a fix can predate the date stamped on it. A recent `started_at` tells you nothing at all.

**Two limits on that, both worth knowing before you lean on it.** It dates the REST backend and
nothing else: `api.danubeai.com` and `mcp.danubeai.com` are separate deployments with separate
images and separate process lifetimes, and the MCP server publishes no boot time anywhere —
`/health` and `/healthz` on that host return only the fixed blob above. So an MCP-layer
behaviour's date is simply not checkable from outside; the two deployments do redeploy off the
same pushes and so usually sit close together, but that is a tendency, not a guarantee, and
either build can fail or be starved on its own. And a behaviour switched by an environment
variable or fixed by a data repair has no code date to read at all.

Two fields in that body read oddly at a glance. `database` is a separate watcher's last verdict
— `ok`, `slow`, `unreachable`, or `unknown` when no probe has run yet — while `status` is always
the literal `"healthy"`, so `status: "healthy"` beside `database: "slow"` is the designed answer
rather than a contradiction: the process is up and the database is not well. That split is
deliberate, after this route's own 503s on a database stall had the container restarting about
once a minute for two hours and the reboots kept the database from recovering. The live sizes
beside them are **not** scoped alike, and the tool count is really two numbers.
`catalogue.services` counts **public** services only. `index.lexical_rows` is the
whole-catalogue population — every tool row the index holds, org-internal ones no key of yours
can see included — while `index.tools` beside it is the narrower count of rows carrying an
embedding the index can use, so a gap between the two is rows it had none for (usually ones
still waiting to be embedded) rather than a fault. They are often equal, which is what makes
the distinction easy to miss: both read 12,734 on 2026-10-10. Either way, don't read a tool
count beside `catalogue.services` as "N tools across M services" — the two are drawn from
different populations.

**Probing the MCP endpoint itself with `curl` needs the right verb, and its `401`s are easy to
misread** (all of this verified live 2026-10-03). POST is the only verb that does anything: a
`GET` of `https://mcp.danubeai.com/mcp` with a perfectly good key answers `405 Method Not
Allowed`, which says nothing about your key, and the `Allow: DELETE, POST` it sends back is not a
second route — `DELETE` answers `405` too, with `Method Not Allowed: Session termination not
supported`. A real probe is a JSON-RPC `initialize`, and the reply comes back as
`text/event-stream` (`event: message`, then a `data:` line) rather than plain JSON — so don't pipe
it to `jq`:

```bash
curl -s -X POST https://mcp.danubeai.com/mcp \
  -H "danube-api-key: ${DANUBE_API_KEY}" \
  -H 'Content-Type: application/json' \
  -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"1"}}}'
# -> event: message
#    data: {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18", ...,
#           "serverInfo":{"name":"Danube MCP Server","version":"4.0.10"}, ...}}
```

Send that `Accept` header or none at all — a *narrow* one is what fails. `Accept: application/json`
on its own answers `406` with `Not Acceptable: Client must accept both application/json and
text/event-stream`, which at least explains itself; omitting `Accept` altogether works, because
curl's default `*/*` satisfies the check.

Reading what else can come back:

- **Two different `401`s, told apart by their message.** No key at all gives
  `{"detail": "API key required. Provide 'danube-api-key' header or 'Authorization: Bearer <api_key>'."}`;
  a key the server rejects gives `{"detail":"Invalid API key"}`. Only the second one is about your key.
- **An *unauthenticated* `401` is not evidence the URL is right.** Authentication runs ahead of
  routing and short-circuits before it, so with no key — or a rejected one — a mistyped path
  answers `401` rather than `404`: `GET https://mcp.danubeai.com/sse` does, even though the server
  serves no SSE transport at all. Once a key validates, the request does reach routing, so that
  same `GET /sse` **with** a working key answers `404 Not Found`. Probe with your key and a wrong
  path looks like a wrong path. Reachable with no key: `/`, `/health`, `/healthz` and the OAuth
  routes — plus an `OPTIONS` preflight on anything, and `/v1/*` for the reason in the next bullet.
- **REST paths on this host are a `404` with a message that tells you so.**
  `https://mcp.danubeai.com/v1/tools/search?query=weather` answers
  `404 {"detail":"This endpoint is not available on the MCP server."}`, identically with and
  without a key — that reject sits ahead of the auth check. REST lives on `api.danubeai.com`; see
  `references/rest-api.md`.
- **`Authorization: Bearer <key>` works here, and misleads on the REST API.** This server accepts
  the key under either header (hence the wording of that first `401`). On `api.danubeai.com` the
  same header does one of two unhelpful things, depending on the route: one that *requires* a key
  refuses it — `/v1/tools/search` answered
  `401 {"error":{"code":"unauthorized","message":"API key required"}}`, which reads as "you sent
  no key" when the key was simply in the header REST reserves for a dashboard JWT — while one
  whose auth is *optional* ignores it without saying so: `/v1/services?limit=3` answered `200`
  with byte-for-byte the same bytes the call returns with no credentials at all (both 1,619,339 on
  2026-10-14; the figure grows with the catalogue, so read it as a floor), so
  anything the key would have unlocked is quietly absent. Keep `curl` on `danube-api-key`, and
  don't carry a Bearer header that worked against the MCP server over to a REST call.
- **Neither version number this host reports is a Danube release, and they disagree.** The
  handshake's `serverInfo.version` is `4.0.10` and `/health` says `1.0.0` (both live 2026-10-14),
  which looks like two servers and is one. `4.0.10` is the **FastMCP library's** own version — the
  server is built without declaring a version of its own, so the framework fills in its package
  version, and that number moves whenever the dependency is bumped rather than when Danube ships
  anything. It is worth seeing how fast it moves: this reference read `4.0.5` on 2026-10-04, and
  two dependency bumps landed in `mcp/requirements.txt` that same day, taking the pin to `4.0.9`
  and then to the `4.0.10` serving now — no Danube release in between. So treat whatever number
  you read as the library's, and expect it to differ from the one written here. `/health`'s
  `1.0.0` is a fixed string in that handler, wired to nothing. So don't
  report either as "the Danube MCP server version", and don't try to tell one MCP deployment from
  another with them — nothing on this host exposes its build or boot time, and the `started_at`
  above belongs to the separate REST backend. What the handshake *is* good for is proving you
  reached the real server — the `serverInfo.name` (`Danube MCP Server`), the capabilities block,
  and the `instructions` string,
  which is the same "Call get_context once at the start of a session…" line the server sends every
  client.


## Errors while executing tools

**Start with the attribution.** A failed `execute_tool` carries `error_type`, `fault` and
`retryable` — in `_meta` over MCP, at the top level of the response over REST. `fault` is
`caller` (your parameters or credentials), `upstream` (the third party failed; retrying later
may work, and this is the only class that counts against the tool's reliability score) or
`danube` (a stale catalog row or a request Danube built wrong — neither a retry nor a
`report_tool` helps). Those three fields pick the row you need below faster, and more
reliably, than matching message text.

Over MCP the text *usually* also opens with `Request error:` / `<Service> error:` / `Danube
error:` plus a line of advice, but don't match on that: `auth_required` and an insufficient
wallet balance return their own text with no prefix, and nothing is prefixed over REST. The
fields can be absent altogether when the failure never reached the execution engine — an
unresolvable `tool_id`, a `tool_name` matching nothing (no `_meta` at all over MCP), or a
refusal the REST layer turned into a real status such as `402` or `503` — so read them with
`.get()`.

| Symptom | Cause | Fix |
|---|---|---|
| A failure and you can't tell whose it is | Read `fault` before anything else: `caller`, `upstream` or `danube`, with `error_type` naming the specific class (`missing_parameters`, `auth_required`, `rate_limited`, `timeout`, `endpoint_missing`, `upstream_tool_missing`, `bad_request`, `not_found`, …) and `retryable` saying whether the identical call could succeed later | Act on the verdict rather than the prose. `retryable: false` means a bare retry cannot help — change the request, pick another tool, or tell the user. Note `error_type` is a different vocabulary from the `last_error_class` in a search result's `reliability` block, which is the reliability view's own coarser bucket |
| `fault: danube` and you want to help by filing a report | A genuine Danube-side defect is recorded for repair without you. The rest of this class isn't a defect at all: a sunset tool, a retired service and a disabled tool are deliberate catalog states | Don't `report_tool` either kind — it adds nothing in the first case and is wrong in the second. Pick another tool or tell the user what is unavailable |
| `error_type: auth_required` (`fault: caller`) | Usually the user hasn't connected that service on Danube — but read `auth_required.reason` first: `rejected` means a stored credential was refused (an upstream 401), and `org_policy` means an org credential rule left nothing to call with | Send them to the `configuration_url` in the error, or https://danubeai.com/dashboard → connect the service. For API-key services the user may hand you the key to store (confirm first) — **except** under `reason: org_policy` with `credential_policy.mode: "shared"`, where a key stored for this user is ignored and an owner or admin of the org has to add the shared one. On `rejected`, reconnect rather than re-storing the same key |
| A call takes ~30s and comes back `error_type: timeout` on a tool that legitimately does slow work (an Apify actor run, a crawl, a server-rendered report) | The default per-call ceiling is about 30 seconds | If the tool is served by an **MCP server**, re-run with `timeout_seconds` — 1 to 300 on `execute_tool`, or the same key beside `tool_input` on `POST /tools/call/{id}` — and don't `report_tool` something that simply needs longer. On an **`api`** service that parameter is accepted and ignored: the budget lives on the tool's own catalog row and a caller can't raise it, so narrow the request instead (fewer items, a tighter filter, the upstream's pagination) or `report_tool` it as `timeout`. Past 300 s the work belongs in an async flow either way: start it, keep the handle, poll the service's own status tool. On an **infrastructure connector** tool (`method: "CONNECTOR"`) neither of those applies: `timeout_seconds` is a tool *parameter*, so it goes *inside* `tool_input` (beside it, it is the budget above and never reaches the connector), its ceiling is **55 s** rather than 300 and the default is 15. The ceiling holds on every connector call even where the tool doesn't advertise the parameter — many ops don't, including nine of the thirteen write tools — and a value over it is clamped silently, so send 300 and the call runs with 55 with nothing in the response saying so |
| The call succeeded but the answer is for a different tool than you asked for | You passed `execute_tool` a `tool_name` (or a non-UUID `tool_id`, which is re-read as one) that no tool carries verbatim. Over MCP that string is resolved by search: a tool whose name or slug *is* the string is pinned first, so a correctly spelled identifier is safe — but when nothing matches, **the first result runs**, regardless of its `match` being `weak`. Live on 2026-10-09 the name `Hacker News - Get Front Page Story Titles`, which no tool carries, executed `Hacker News - Get New Stories With Content` and answered with the newest stories as an ordinary success | Read `_meta.tool_id` and `_meta.tool_name`: they name the tool that actually ran. Re-run with the UUID from `search_tools` or `describe_tool`. Nothing is broken, so don't `report_tool` it — and don't treat the payload you already have as an answer to the question you asked. REST and `batch_execute_tools` never substitute: they resolve a UUID or a slug exactly and answer `Tool not found` otherwise |
| `invalid_grant` / "token expired" | The service's OAuth grant was revoked or expired | User re-authorizes the service in the dashboard |
| `401 Unauthorized` from `api.danubeai.com` | Bad or revoked `DANUBE_API_KEY` | Regenerate at https://danubeai.com/dashboard/api-keys |
| `403` | The API key is scoped to specific services/tools (`This API key does not have permission to access this resource`), or the organization's policy blocks this tool (`Your organization does not have access to this tool`) | Tell the user what was blocked; for the organization text, an admin of the organization has to grant the tool to them, a team they are in, or their role. Don't work around it |
| `search_tools` returns tools that plainly do not fit the query | Semantic search always returns its nearest neighbours, so a capability the catalogue does not have comes back as confident-looking wrong answers — before a Postgres connector existed, "run SQL against Postgres" returned PostHog's HogQL tool and Elasticsearch's SQL endpoint ranked like real hits. Each result therefore carries **`match`**: `"strong"` when its name, description or service name hold at least 60% of the weight of the query's distinctive words (an exact name match is always strong), `"weak"` when it only resembles the query. The page is ordered by it ahead of the readiness band (full 90%+ matches, then strong, then weak), though only the two labels are ever stamped | Read `match` before committing to a tool. A page of nothing but `weak` usually means the catalogue has nothing that fits: try another phrasing once, then tell the user rather than calling the closest thing, and don't `report_tool` any of them — nothing failed. Two exceptions: searching for an exact slug or tool name is stamped `weak` (`gmail-send-email` is one token and appears nowhere in "Gmail - Send Email", so its coverage is zero) while exact-match pinning still puts that tool first, and `match` is not the final ordering either — named-service promotion, demo demotion and exact-match pinning all run after it. It is **search-only** (`search_tools`, `GET /v1/tools/search`), so `get_service_tools` and `describe_tool` never carry it, and nothing is stamped when the query reduces to no usable keywords (all stop words, or nothing over one character) or while the backend's in-process lexical index is unloaded — a missing `match` is "not judged", not `weak` |
| `search_tools` scoped with `service_id` comes back empty on a tool the service plainly has | The filter is matched for exact equality against the `service_id` each tool row carries, and that is always the UUID, so a service **slug** there scopes the search to no service at all. The page is then empty with nothing naming the filter as the cause, and an empty page is also what a service with no such tool looks like. It is easy to arrive holding a slug, because the neighbouring reads do accept one: live on 2026-10-17 `gmail` listed that service's tools through `get_service_tools` and all six of them through `GET /v1/services/gmail/tools`. Live the same minute, `service_id: "gmail"` on the query `send email` answered `[]` over MCP and over `GET /v1/tools/search`, while the service's UUID answered with `Gmail - Send Email` first | Re-run the search with the service's UUID, which every search result carries as `service_id` and every `list_services` row as `id`. An unfiltered `search_tools(query)` usually reaches the tool too, though its own `limit` of 10 and the readiness and demo re-ordering can keep one service's tool off that page. Nothing failed, so don't `report_tool` it |
| A service you just connected or published is missing from `list_services` | `list_services` (REST `GET /services` and `/services/public`) is served from a cache refreshed every 60 seconds | Wait up to a minute, or go straight to `search_tools` / `get_service_tools(service_id)`, which are not cached |
| **Every** row of a `list_services` page has `description: ""` and `url: null` | Not an empty catalogue — the compact detail level. (A single such row is a different thing: a full row renders the same way for a service that has neither a description nor a base URL on record.) `list_services` takes `detail`: `"auto"` (default), `"full"` or `"compact"`, and `auto` is full up to a `limit` of **25** and compact above it. The switch is on the `limit` you asked for, not on how many rows came back, and a compact row keeps `id`, `name` and `tool_count` while emptying the other two rather than dropping the keys (the published output schema requires them), with nothing in the answer saying the level changed. Live on 2026-10-15 the same query returned full descriptions at `limit: 25` and `description: ""` with `url: null` on every row at `limit: 26` | Keep the limit at 25 or below, or pass `detail: "full"` with the bigger one — knowing the full form is what compact exists to avoid, since it costs a backend lookup per service the listing reports with no tools. A `detail` the parameter doesn't recognise fails loudly, unlike the `?tools=` group filter: `"brief"` answers "detail must be one of auto, full, compact, got 'brief'". Nothing to `report_tool` |
| A service you searched for by name is missing from `list_services`, but REST returns it | A service the listing finds no tools for is dropped, so the page can be shorter than the `limit` you asked for while more results exist. Two conditions have to meet: the catalogue's `tool_count` must be exactly `0`, **and** below the compact threshold a live check of the service's tool list has to come back empty too — above it that check is skipped, so the same query can return a different *set* of services at `limit: 25` and `limit: 26`. A count that arrived `null` is **not** dropped; it survives reading `tool_count: 0`, un-recounted in a compact listing. Live on 2026-10-15, `GET /v1/services?query=Day AI` returned ten rows of which `Day AI`, `Read AI` and `Peec AI` carried `tool_count: 0`, and the same query over MCP returned exactly the other seven. These are usually MCP servers nobody has connected yet (`Day AI` is an `mcp_server` row with none registered) — the `needs_mcp_oauth: true` row further down this table. **The `-32602` "Invalid request parameters" failure this row used to describe is fixed**: the `null` `tool_count` that broke the MCP layer's `Service` model is coerced to `0` before the model sees it (`mcp/mcp_server.py`, 2026-09-28), and `query: "Day AI"` — the query that failed five times running on 2026-09-15 — returns normally | Don't read the absence as "no such service": `GET /v1/services?query=…` over REST returns the zero-tool rows, and the user connects the service from the dashboard, after which its tools are registered by the background first sync. If you do meet the `-32602` against an older deployment — the MCP server publishes no build date, so you cannot tell from outside — the old reading still holds: it belongs to the page rather than to the service you wanted, re-sending won't clear it, a different phrasing may, and `search_tools` and `GET /v1/services` are unaffected. Nothing to `report_tool` either way: this is Danube's own API, not a marketplace tool |
| A tool ran fine but acted as the wrong account — mail sent from a personal address, a message posted by the wrong user | `readiness: "ready"` answers whether the call will work, never as whom. For a provider that derives the actor from the OAuth grant there is no parameter to override it: `Gmail - Send Email` takes its From header from whichever Google account was connected and exposes no sender field (ten cold emails went out from a personal Gmail that way on 2026-09-03, which is why the field below exists). Nothing failed, so there is no error to read after the fact | Read **`connected_as`** beside `readiness` *before* calling: it holds the identity captured at connect time (an email address where the provider gave one, `null` where it gave nothing or the credential was stored as a plain API key), and is set only alongside `ready`. It is not always an email: the extraction prefers one, then falls back to any stable handle the provider gives (an OIDC `preferred_username`, a Notion owner name, Slack's opaque `authed_user.id`) and last of all to Slack's **workspace** name, so `"Danube HQ"` is a possible value and names the team rather than the actor. Three REST routes carry it — `GET /v1/tools/search`, `GET /v1/services/{id}/tools` and `GET /v1/services/public/{service_id}/tools` — each only for a caller sending a key, since the label is resolved against that caller's credentials. Nothing over MCP does: the MCP result model has no such field, so `search_tools` and `get_service_tools` drop it at the boundary, `detail="full"` included (verified live 2026-10-08 on a connected Gmail); `describe_tool` and `/v1/tools/{id}/describe` miss it because the describe response is built as its own dict copying only `readiness` and `configuration_url`. Over MCP alone you cannot learn the account, so read it off one of those three routes or have the user confirm the intended sender before you send. Nothing to `report_tool` |
| `get_service_tools` says `needs_configuration: false` but calls fail with `auth_required` | The flag is true only when *every* tool of the service is `needs_credential` for this account; a service mixing credential-free and credential-bearing tools reports false. Over MCP it is derived from the tools that call *returned*, i.e. the first 50 at most — see the 50-cap row below | Read the per-tool `readiness` on each entry (or on `search_tools` results); that is the answer for the tool you are about to call |
| `get_service_tools` on a service the user just connected comes back with an empty `tools` list | Possibly "not yet" rather than "none": an MCP service's tools are registered by a first sync that runs in the background (since 2026-09-13), and registering a large server's takes tens of seconds. The response says so — `tool_sync: {"status": "running"}` plus a `message`, and over REST `needs_sync: true` as well. Note the sync starts when the user connects the service in the dashboard, or on your own first read of the tool list — your `store_credential` does not start one | Read it again in a few seconds. There is nothing for you to call: the read is what starts or restarts the sync (including one a backend restart lost). Neither `"failed"` nor a `"done"` that still lists no tools is final — a read five minutes later starts a fresh attempt, and the `message` in that case explains what went wrong. It also names `POST /services/{id}/refresh-tools`, but that one needs the service **owner** signed in to the dashboard and answers `401` to an API key, so pass it on to the user rather than calling it. Read `tool_sync` defensively — it can arrive as `{}` with no `status`. Don't report the service as empty and don't `report_tool` — no tool was called |
| `get_service_tools` listed exactly 50 tools, and the one you were looking for isn't among them | Over MCP the tool's `limit` parameter defaults to **50** and the list is cut to that length, with no total, no cursor and no truncation flag to say so — the remaining tools read as tools the service doesn't have. Not an MCP-server quirk: the cut lands before anything branches on service type, and the biggest services are `api` ones (Vercel, 407 tools). Live on 2026-09-20: Higgsfield has 101 tool rows, the default call returned 50 and `limit=200` returned all 101 (nothing clamps what you pass). The REST route takes no `limit` and returns the whole list. A count of exactly 50 is a hint, not proof — a service that really has 50 looks the same — and note `needs_configuration` is derived from the sliced list, so on a larger service it describes only the first 50 | Re-read it with a big `limit` (500 covers every service in the catalog today), or use `GET /services/{id}/tools` over REST, which is already complete. Remaining today: $Y") | A limit, not an empty wallet, checked against the price Danube holds on record. The engine sets **no** `error_type` for it; the phrase "spending limit" in the prefix is what classifies it onto the same `insufficient_balance` / `caller` verdict as the credits case. A USDC balance too thin for that price is *not* a refusal here — the call falls back to the ordinary credits wallet, with no second balance check behind the fallback, and goes ahead | Tell the user which limit stopped the call; it is their setting to change, not yours. The MCP layer points at https://danubeai.com/dashboard/wallet, which redirects to the same Finances page as the credits message |
| An x402 tool refuses with "Insufficient USDC. Required: $X.XXXX. Balance: $Y.YYYY", or with "x402 payment blocked: …" carrying one of the same three limit reasons as the row above | The path where a USDC balance really can refuse you. Some x402 tools have their price re-derived at call time from the upstream's own `PAYMENT-REQUIRED` header and re-check both gates against that number, which can exceed what the earlier check cleared. **You cannot tell in advance which tools these are** — a search result carries `x402_enabled` and the price, but nothing an API key can read exposes the pricing *mode*, and `describe` carries no pricing field at all — so match on the message, not on the tool. "Insufficient USDC…" classifies correctly (`insufficient_balance` / `caller`) and over MCP carries the same numbered top-up steps as the credits case. "x402 payment blocked…" does **not**: it matches none of the engine's text rules — they look for the literal "spending limit" — so it is mis-filed as `unknown` with `fault: "danube"`, and over MCP arrives prefixed `Danube error:` with advice to wait for a repair | The rare case where the message beats the verdict. Ignore that label: it is the account's own limit, not a Danube bug. Don't retry, and don't `report_tool` it — the platform files its own row for anything it marks `danube`. Tell the user which limit to raise or how much USDC to add; note this one carries no dashboard link of its own, unlike the two rows above |
| A file-returning tool came back with `content_base64: null`, and `_meta.truncated` is `false` | Nothing failed and nothing was cut. Over MCP a base64 file is lifted out of the JSON before shaping (`Wikimedia Commons - Get File Bytes` is the live case): a displayable image — `image/jpeg`, `image/png`, `image/gif`, `image/webp`, up to 5,000,000 base64 characters — is attached as an MCP **image block** (`_meta.image_block: true`), and the text copy of `content_base64` is nulled unless your `max_response_chars` was big enough to hold the whole result. The truncation flags stay clear because this is not truncation, so the usual `_meta.truncated` check will not catch it | Read `_meta.content_base64_omitted` (with `content_base64_chars` for the real length) rather than the null, and take the image from the image block — it is already in the conversation. For the bytes themselves as text, `_meta.file_note` names the exact `max_response_chars` to pass (live 2026-10-05, the Mona Lisa file at `width=120`: 9,828 characters, `max_response_chars=10031` — per-file figures, so expect your own). Easier still, call it over REST — `POST /v1/tools/call/{tool_id}` does no lifting and returned the same 9,828-character `content_base64` whole. Ask for a smaller `width` when the file is simply too big. Nothing to `report_tool` |
| `get_agent_info` failed outright, `400` / "This endpoint is for agents only. Use /v1/users/me for human accounts." | Nothing is broken and there is nothing to `report_tool`. The tool reads the **agent** profile behind the key, and it refuses any ordinary account — every account created by signing up in the dashboard is one, so this is its normal answer, not an edge case. Over MCP it arrives as a tool error with the REST envelope flattened into the text (`validation_error` inside the message), which reads exactly like a platform fault; live 2026-10-16. The route the message names has no MCP tool of its own, and `register_agent` is not the fix — it would make a *different*, unconnected account (see *Wallet & agents* in SKILL.md) | Call `get_wallet_balance` for the balance (any account: `balance_cents`, `formatted`, `has_wallet`) and `get_spending_limits` for the caps. What a human account cannot reach this way is the *agent profile*; the USDC figures are not agent-only — `fund_agent_wallet`, in the same group, has no such check, works here, and returns the same `balance_usdc`, with `deposit_address` on `method: "crypto"` (one platform address shared by every account). Nothing here is worth retrying, and know what that other tool does before reaching for it: it starts a funding flow |

## A tool is broken or returns wrong output

Call `report_tool(tool_id, reason, description)` with `reason` one of
`broken`, `degraded`, `incorrect_output`, `timeout`, `other` — the Danube team
reads these. A rating via `submit_rating` helps other agents too.

Don't check for an existing report first: filing the same `tool_id` + `reason`
again while an earlier report is still open or acknowledged bumps that report's
occurrence count instead of creating a duplicate. Both tools also take a `source`
parameter — leave it unset. It exists to mark Danube's own internal dogfooding
traffic, and setting it on a real report tells the team to discount what you saw.

Pass the tool's UUID as `tool_id`: the MCP `report_tool` and `submit_rating`
tools reject anything else rather than guessing. Look it up with
`search_tools` — and if what you're closing out wasn't a marketplace tool call
at all, just skip the report instead of passing a tool name or a placeholder
string.

`get_my_rating` wants the UUID too, and fails one step later: it has no
client-side guard, so a slug reaches the backend and comes back as HTTP `400`.
Over REST that is the ordinary envelope, `{"error": {"code":
"validation_error", "message": "tool_id must be a tool UUID, got:
'gmail-send-email'"}}`; over MCP the same refusal is flattened into a string —
`{"error": "API request failed with status 400 (Details: {…})", "isError":
true}` — so there is no `error.code` to branch on there. Both live, 2026-09-22.

`get_recommendations` wants it as well and is the one that never complains: a
slug is queried against a UUID column inside a `try` that only logs, and the
same unresolved string is what the endpoint excludes from its own results, so
you get the generic popular list and the tool you asked about recommended back
to you. Live on 2026-09-22, `get_recommendations("supabase-execute-sql")`
returned `Supabase - Execute SQL` at the top of its own list while the UUID
call left it out. A `reason` of `Frequently used together` is a real co-usage
hit; `Popular` is what every caller gets.

Over plain REST the *report* endpoint is the one that does accept a slug —
`POST /v1/tools/{tool_id}/report` resolves either form and stores the resolved
UUID — so the same call is fine over curl and refused over MCP. Send the UUID
and both work.

## `get_tool_ratings` says `rating_count: 0`

Four different things look identical here, and only one of them is "nobody
liked it".

- **The id wasn't a tool UUID.** This endpoint never errors on the id: it
  swallows the failed lookup deliberately, so that a public endpoint never
  `500`s, and returns `{"avg_rating": null, "rating_count": 0}` for a slug, a
  tool name or a typo — byte for byte what an unrated tool returns. So a zero
  is never confirmation that your id was right.
- **You aren't allowed to see the tool.** Since 2026-09-27 a tool on a service
  hidden from you — an org-internal tool of an organization you don't belong to
  — answers that same empty body rather than a `403` or a `404`. The check is
  against the caller, so this also covers reading the route with no key at all:
  over `curl` send your API key, or your own organization's internal tools look
  unrated. Over MCP the key always rides along.
- **The ratings that exist aren't counted.** The aggregate behind this tool
  counts only ratings whose `source` is `user`; ratings left by agents
  dogfooding Danube are excluded from it. Live on 2026-09-22, `Gmail - Send
  Email` (`6f0c4361-d0cc-45df-8ee6-87b9cc1e0d37`) returned a five-star rating
  from `get_my_rating` and `rating_count: 0` from `get_tool_ratings` on the
  same UUID.
- **It hasn't caught up yet.** It reads a materialized view on a five-minute
  refresh schedule (five minutes is the floor: a run that would overlap the
  previous one is skipped), so a rating submitted moments ago — including one
  you just submitted — is not in it.

None of these is breakage and there is nothing to `report_tool`. Judge the tool
on the `reliability` block that comes free on every search result, and read the
response's real keys, `avg_rating` and `rating_count` — not the
`average_rating` / `total_ratings` the tool's own description names.
