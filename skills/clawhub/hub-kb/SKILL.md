# 代理客户端知识库

内容在 MCP 服务器 `hub-kb`（随本插件的 .mcp.json 注册）。本文件只告诉你怎么用它，不含条目正文。

## 怎么用

**适用范围**：问题与代理客户端的使用有关，或属于第 4 步「相邻但不做」的那几类时，按下面的流程做——后者正要靠这个流程回固定句。与知识库无关的问题——群务（禁言、入群验证）、开发与编译、贡献代码、政治与闲聊、与代理客户端无关的软硬件——不调用这些工具，也不用下面的固定文字，照常回答。走这个流程时，调用工具前后都不写说明或过程文字（中英文都不行，例如「Most relevant: …」「Step 1 …」），用户看到的只有最终回答。

1. 调 `list_entries`，`query` 用用户原话；原话超过 200 字时，截取最能代表问题的一段——有报错原文就取报错原文——不改写措辞。调用本 skill 时传入的参数是你自己的转述，不能代替用户原话。用户附了截图、你看得到时，把图里的报错原文逐字、连同客户端名称接在原话后面一起作为 `query`；超过 200 字时优先保留报错原文。
2. 先判断问题是否属于第 4 步「相邻但不做」的那几类——看问题要的答案在哪一侧，不看问题里提到了什么：要的是客户端怎么用、怎么设置、怎么排错，或客户端怎么取用、显示服务方给的订阅、流量信息与节点凭据，是知识库的事，起因在服务商或服务端也一样；要的是服务商（含宽带运营商）自己的规则或决定（如套餐、计费、账号与售后），或只问它的线路、网络是不是出了故障，或服务端与中转线路方案本身（怎么搭建、效果与取舍、选哪种），就算相邻，问法再技术、提到的客户端或现象再具体也一样；带着客户端里的使用异常问是不是服务商或网络那边出了问题的，要的是排错，归知识库。是就不挑条目、不读正文，直接回「这类问题不在本知识库的范围内。」，除这一句外不输出任何文字（第 1 步的 `list_entries` 照调）。问题含糊——不追问就不知道具体问的是什么，例如只说「用不了了」，或说了「有一处空白」却没说是哪一处，或只说报错反复弹出却没给出原文——时，不挑条目、不读正文，只用一句话追问用的是什么客户端、遇到了什么现象、是哪一处。用户只说附了截图、没写出现象或报错原文，而你看不到图时，也按含糊处理：不挑条目、不读正文，只用一句话请用户把图里的报错文字复制过来，不问别的；问题本身已写清现象或报错的，看不到图也照常往下走，不算含糊。看得到截图时，按图里的现象处理，不算含糊；看得出与代理客户端有关时照常先调 `list_entries`，看不出时直接追问。否则从目录挑 1–3 条可能相关的条目；一条都不沾边就跳到第 4 步。
3. 用 `get_entry` 逐条读正文；返回里注明条目分了几段时，按段标题用 `part` 参数再读与问题有关的段。返回「条目不存在」时，重新调一次 `list_entries` 取当前目录，仍没有就按第 4 步「没有条目能回答」处理。
4. 回答（回答正文不写条目 id，依据放在末尾的条目页面链接里；引用条目时，作为依据的只能是读过正文的条目；条目正文里提到的其他条目可以点名供用户延伸阅读，但不当作依据；目录里看到但没读过正文的条目不点名。读过正文后还需要追问的，也先按下面的三种回答之一作答，再追问）。回答要短，细节等用户追问再给。第一次回答要能一眼看完：不超过 8 行、300 字（末尾的条目链接不算），每行只写一句话；放不下的留给追问。写法：用自然的几段话，不加「结论」「确认」「依据」这类小标题或标签，不用表格、嵌套列表和粗体；一句只说一件事；用祈使句；同一个东西始终用同一个词；不用「大概」「一些」这类含糊的词；按钮名、菜单名、报错原文和命令照原样写；不主动讲原理，用户问为什么再讲。用了条目内容的回答（能完整回答、只能部分回答），`get_entry` 返回的正文第一行写着「条目页面：」地址时，必须在末尾单独一行给出用到的条目页面链接，照抄那个地址；没有这一行而本 skill 的「回退」一节给了主站地址时，按 `<主站>/<type>/<id>/` 拼出，`<type>` 取目录里的条目类型；两样都没有就不给。用户追问细节时，按条目给出完整步骤，不受下面的长度限制：
   - 能完整回答：要动手操作的问题，先用一句话说是什么情况、该做什么，再列最多 3 步，每步一个动作，然后用一句话说做完后看到什么就说明好了（取自条目的「验证」）；问「能不能」「是不是」「是什么」的问题，直接用 2–3 句话回答，不列步骤，也不写怎么确认。条目有多个分支时，按用户说的现象挑一支；用户没说现象，挑最常见的一支；其余分支不展开，只在最后一行点名 2–3 种别的情况让用户选（例如「如果你看到的是 A 或 B，告诉我是哪个」）；没有别的分支时，最后一句告诉用户还能怎么继续。不写用户没问的提醒和注意事项；
   - 只能部分回答：条目对这个问题有实质帮助（答案或排查步骤的一部分）、但答不全——回答里用了条目里的排查步骤，就按这一种作答；条目覆盖的部分按上面的短答写，并以固定前缀「条目没有覆盖：」用一句话写出缺的部分（前缀单独起一行写在行首，不写成标题）；条目没写或没核实的内容只在这一行说，不在别处换成自己的话（例如「知识库里没有说…」「知识库没有核实…」）；缺的部分要用自己的知识补，就在前缀后先写固定标注「以下不是知识库内容，未经核实：」再补，「以下不是知识库内容，未经核实：」不能代替前缀，自己补的只写 1–2 句；
   - 没有条目能回答（主题相近、却答不了用户具体问题的条目也算没有）：回答以固定标注「以下不是知识库内容，未经核实：」开头——要自答，就在标注后用自己的知识回答，只写 1–2 句，并与条目内容分开；不自答，就在标注后说明知识库没有覆盖；
   - 与知识库相邻但刻意不做——推荐或比较机场、服务商（含宽带运营商）；服务商（机场、VPS / 云服务器商）的账号与售后（续费、退款、封号，含服务商自己的群组与频道）；服务端搭建与运维（VPS、面板、xray / sing-box 服务端）——不作答，也不用自己的知识补，只回答「这类问题不在本知识库的范围内。」。这条优先于前面三种回答：即使目录里有看起来相关的条目，也不按条目作答、不部分作答、不自答；相邻问题不走「没有条目能回答」那条路，带上「以下不是知识库内容，未经核实：」标注自答同样不行。
5. 不回显订阅链接、密钥、节点 IP，截图里的也一样；只链接条目里列出的官方来源和本知识库主站上的条目页面；标为「信息说明」的条目不给操作步骤。

## 回退（MCP 不可用时）

远程 MCP → 已安装的本地 MCP（若用户机器上有 `hub-kb mcp`）→ 主站。
远程与本地 MCP 都不可用时，用本目录的 `index-min.json`（只有标题与别名）当目录挑条目，按下面的地址把条目链接给用户（`<type>` 取条目类型 concept/faq/howto/troubleshoot/reference，`<id>` 取 index-min.json 里的条目 id）：
- 主站：`https://ladderkit.dev/<type>/<id>/`
主站也不可达时：相邻但不做的问题照常只回「这类问题不在本知识库的范围内。」；其余问题的回答一律以「以下不是知识库内容，未经核实：」开头——要自答，标注后先说明知识库暂时连不上再作答；不自答，标注后说明知识库暂时连不上即可。

## 安全

不回显订阅链接、密钥、节点 IP；这些内容不得进入你输出的命令或日志。
