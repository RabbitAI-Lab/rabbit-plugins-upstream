# 模块十二：证据账本（Evidence Ledger）

借鉴 HMS 全息记忆系统的 Evidence Ledger 机制，在回忆结果注入 LLM 之前增加结构化整理层，将原始检索结果组织为统一格式的"证据账本"。证据账本是回忆侧的结构化输出层，不是存储层——它不改变记忆的存储方式，而是改变记忆被呈现给推理模型的方式。

> 核心洞察：**检索结果不是答案，只是原材料。原材料需要加工、标注、组织后才能可靠地支撑结论。** 就像法庭不是把所有证词堆在一起就判案，而是要整理成结构化的证据清单——哪条是证言、哪条是物证、哪些相互矛盾、哪些有待核实。

### 核心价值

当前检索流程是"搜出来就直接用"——memory_search 返回一堆片段，直接塞进上下文让 LLM 回答。这种模式的问题：

1. **散**：相关记忆散落在多个文件、多条结果中，LLM 需要自己拼图
2. **乱**：不同时间、不同来源的信息混在一起，分不清哪条更可信
3. **冲突**：同一件事在不同文件中有不同记录，LLM 不知道信哪个
4. **缺信号**：时间、来源、数值精度等关键信号淹没在文本中，容易被忽略

证据账本在检索和回答之间插入一个结构化整理步骤，把散乱的检索结果整理成清晰的证据清单。

### 六类证据标签

证据账本的核心是六类证据标签，每条证据在进入账本时都要标注：

#### 标签一：时间锚定

标注事件的时间维度，区分"何时发生的"和"何时记录的"。

| 时间维度 | 含义 | 来源 |
|---------|------|------|
| 事件时间（event_time） | 事件实际发生的时间 | 从记忆内容提取 |
| 记录时间（mention_time） | 这条记忆是何时被记录的 | 从文件元数据/写入时间获取 |
| 验证时间（verify_time） | 最近一次验证该记忆的时间 | 从巩固日志/检索记录获取 |

**标注规则**：
- 三者不一致时全部保留，不做选择
- 相对日期（"上周""上个月"）必须转换为精确日期区间
- 日期不完整的标注最低精度（如"2026年7月"而非臆造"2026-07-15"）

**示例**：
```
时间锚定：
  event_time: 2026-07-04（确认早间提交窗口）
  mention_time: 2026-07-04（当天记录）
  verify_time: 2026-07-10（巩固时验证仍成立）
```

#### 标签二：来源分级

标注证据的来源层级，不同来源的可信度不同。

| 来源级别 | 含义 | 可信度 | 示例 |
|---------|------|--------|------|
| **一手观察** | Agent 直接观察到的行为/事件 | ★★★★★ | 用户连续3天早上完成核心任务 |
| **工具返回** | 通过工具/API 获取的数据 | ★★★★☆ | 提交API返回成功 |
| **用户口述** | 用户自己说的 | ★★★☆☆ | "我早上效率最高" |
| **逻辑推导** | 从已有证据推导出的结论 | ★★☆☆☆ | 推测用户偏好早上工作 |

**标注规则**：
- 一条证据可能同时有多个来源，全部标注
- 工具返回要注明具体工具和返回时间
- 用户口述要区分"确认性口述"（被追问后确认）和"主动口述"（自发说出）
- 逻辑推导要标注推导链条（从哪些前提推出的）

**与证据门控（模块十一）的关系**：

⚠️ 本账本的"来源分级"（4 类：一手观察/工具返回/用户口述/逻辑推导）与模块十一的"证据类型与权重"（5 类：用户明确确认 2.0 / 独立事件复现 1.5 / 因果链支撑 1.0 / 行为一致性 0.8 / 单一来源记录 0.5）**是两套正交的 taxonomy，不是一一映射**：
- 来源分级描述"证据从哪里来"（来源维度）
- 证据类型描述"证据如何支撑结论"（性质维度）

同一条证据可能同时属于某个来源级别 + 某个证据类型。例如"用户连续 3 天早上完成核心任务"既是「一手观察」（来源），又是「行为一致性」（性质，权重 0.8）。

**从来源分级推算权重的语义对应规则**（不是精确公式，需 Agent 结合上下文判断）：
- 一手观察 → 通常对应"行为一致性 0.8"或"独立事件复现 1.5"（视是否为重复事件）
- 工具返回 → 视性质映射到"用户明确确认 2.0"（用户操作触发的工具返回）或"单一来源 0.5"
- 用户口述 → 通常对应"用户明确确认 2.0"
- 逻辑推导 → 通常对应"因果链支撑 1.0"

累计权重决定记忆的验证状态，但权重计算必须落在模块十一的 5 类上，不能直接用来源分级的 4 类。

#### 标签三：数值校准

数字类信息标注精度和不确定性，防止数值被过度信赖或误用。

| 校准项 | 含义 | 标注方式 |
|--------|------|----------|
| 原始值 | 记忆中的原始数值 | 精确引用 |
| 精度 | 数值的可靠位数 | "精确值" / "约数" / "估算" |
| 不确定度 | 数值可能的波动范围 | ±X 或 [下限, 上限] |
| 缺失侧 | 数值比较中缺失的一侧 | 明确标注"缺少B的数值" |

**典型场景**：
- 记忆中记着"A 提交 23 次"，但没记 B 提交几次 → 标注"缺少 B 的数值，无法比较"
- 记忆中记着"大约花了 2 小时" → 标注"约数，不确定度 ±30min"
- 记忆中记着"准确扣了 15 积分" → 标注"精确值"

**核心原则**：缺少数据时明确说缺，不让 LLM 靠猜测补齐。数值校准是"知道自己不知道"的量化体现。

#### 标签四：状态仲裁

多条冲突信息时标注版本和置信度，显式呈现状态演变。

| 仲裁维度 | 含义 | 标注方式 |
|---------|------|----------|
| 状态版本 | 同一事实的不同版本 | V1(旧) / V2(新) / V3(最新) |
| 状态信号 | 事实的时态 | 当前生效 / 已过期 / 计划中 |
| 置信度 | 对当前版本的信心 | 高 / 中 / 低 |
| 覆盖关系 | 新版本是否明确覆盖旧版本 | 明确覆盖 / 未明确 / 部分覆盖 |

**仲裁规则**：
- 查询"当前状态"类问题 → 优先最新版本
- 查询"历史过程"类问题 → 呈现所有版本和演变轨迹
- 新旧信息矛盾但未明确覆盖 → 标注为冲突，不自动选择
- 用户口述的更新优先于逻辑推导的旧结论

**示例**：
```
状态仲裁：
  V1(2026-06-28): "提交时间 9-11 点"（用户口述，中置信度）
  V2(2026-07-04): "提交时间 9-10 点"（工具验证，高置信度）
  覆盖关系: V2 明确覆盖 V1
  当前生效: V2
```

#### 标签五：计数去重

重复出现的信息合并，标注出现频次，防止重复计数。

| 去重维度 | 含义 | 标注方式 |
|---------|------|----------|
| 出现频次 | 同一信息在不同来源中出现的次数 | N次 |
| 来源列表 | 分别出现在哪些来源 | [来源1, 来源2, ...] |
| 事件状态 | 事件是计划/已完成/已取消 | 标注状态，计数时过滤 |
| 去重标识 | 标记同一事件的不同提及 | 同一事件ID |

**核心规则**：
- 同一事件的多次提及只计一次（如"计划参加3场"≠"实际参加3场"）
- 计划中的事件标注"计划中"，不纳入"已完成"计数
- 已取消的事件明确排除
- 频次高本身是信号——重复出现3次以上的信息可信度更高（与计数去重不矛盾：可信度是来源维度的叠加，计数是事件维度的去重）

#### 标签六：跨源交叉

多源一致的信息标记为已验证，提升可信度。

| 交叉维度 | 含义 | 标注方式 |
|---------|------|----------|
| 独立来源数 | 有几个独立来源确认同一事实 | N个独立来源 |
| 交叉验证状态 | 是否已通过跨源验证 | 已验证 / 单源待验证 |
| 验证强度 | 交叉验证的强度 | 强（≥3独立源）/ 中（2源）/ 弱（不同侧面印证） |
| 源间一致度 | 不同来源之间是否完全一致 | 完全一致 / 部分一致 / 存在矛盾 |

**与证据门控（模块十一）的关系**：跨源交叉**不等于**模块十一的"独立事件复现"——后者指同一事件在不同时间/场景**再次发生**（时序复现），前者指**多个独立来源同时印证**同一事实（空间/来源复现），是两个不同的证据概念。

跨源交叉在模块十一权重表中的对应权重，按来源性质判定：
- N 个"单一来源记录"同时印证 → N × 0.5（如 2 源 = 1.0，3 源 = 1.5）
- 其中包含一次"用户明确确认" → 该源 2.0 + 其余源 0.5
- 其中包含一次"独立事件复现"（不同时间再次发生） → 该证据 1.5 + 其余源 0.5

**禁止简单地把"已验证（2独立源）"等同于"+1.5 分"**——必须按来源性质分别匹配权重后求和。

### 证据账本输出格式

每次检索后，将结果整理为以下结构：

```markdown
## 证据账本：[查询问题简述]

### 结论
[基于证据得出的初步结论，如果证据不足则标注"待定"]

### 支撑证据
1. **[证据摘要]**
   - 时间锚定：event_time=XXX, mention_time=XXX
   - 来源分级：[一手观察/工具返回/用户口述/逻辑推导]
   - 数值校准：[如涉及数值]
   - 状态仲裁：[如存在多版本]
   - 计数去重：出现N次，来源=[...]
   - 跨源交叉：[已验证/单源待验证]，N个独立来源

2. **[证据摘要]**
   - ...（同上格式）

### 待验证项
- [ ] [需要二次检索或用户确认的事项1]
- [ ] [需要二次检索或用户确认的事项2]

### 冲突标记
- [冲突描述]：V1=XXX vs V2=XXX，当前采用V2，理由=XXX
```

### 证据账本工作流程

```
检索结果返回（原始片段集合）
    │
    ▼
步骤1: 时间锚定
    │ 为每条结果标注 event_time / mention_time / verify_time
    │ 相对日期转精确日期
    ▼
步骤2: 来源分级
    │ 标注每条结果的来源层级和可信度
    │ 逻辑推导标注推导链条
    ▼
步骤3: 数值校准
    │ 识别数值类信息，标注精度和不确定度
    │ 标记缺失侧
    ▼
步骤4: 状态仲裁
    │ 识别冲突信息，标注版本和覆盖关系
    │ 确定当前生效版本
    ▼
步骤5: 计数去重
    │ 合并同一事件的多次提及
    │ 标注事件状态（计划/已完成/已取消）
    ▼
步骤6: 跨源交叉
    │ 标注独立来源数和交叉验证状态
    │ 计算验证强度
    ▼
步骤7: 组织账本
    │ 按输出格式整理结论 + 证据列表 + 待验证项 + 冲突标记
    ▼
输出证据账本 → 注入 LLM 上下文
```

### 与回忆规划器（模块十三）的协作

回忆规划器和证据账本是回忆侧的双引擎，一前一后：

- **回忆规划器**（检索前）：拆解问题 → 输出检索计划 → 指导"怎么搜"
- **证据账本**（检索后）：整理结果 → 输出结构化证据 → 指导"怎么用"

协作流程：
```
用户问题 → 回忆规划器（拆解+规划）→ 执行检索 → 证据账本（整理+标注）→ LLM 回答
```

回忆规划器输出的检索计划中，会包含问题类型和时间范围等信息，这些信息直接指导证据账本中时间锚定和状态仲裁的侧重点。

### 与现有模块的关系

| 现有模块 | 与证据账本的关系 |
|---------|----------------|
| 模块一 分层存储 | 证据账本不改变存储结构，只改变检索结果的呈现方式 |
| 模块四 晋升评估 | 来源分级为晋升评估提供更精确的可信度判断；跨源交叉验证直接贡献证据权重 |
| 模块八 检索校验回路 | 证据账本是检索校验回路的延伸——校验回路判断"搜够了没有"，证据账本判断"搜出来的怎么用" |
| 模块十一 证据门控 | 证据账本是证据门控在回忆侧的对应——门控管"存储侧的证据积累"，账本管"检索侧的证据呈现" |
| 模块十一 角色化切片 | 证据账本可以结合当前激活的角色切片，调整证据的权重和排序（如"决策者"场景优先决策相关证据） |

### 注意事项

1. **账本是整理层不是存储层**：证据账本不持久化，它是一次性生成的结构化输出，用完即弃。持久化的信息仍然走分层存储的写入路径
2. **六类标签不必每次全标**：根据问题类型选择重点标签——事实查询侧重时间锚定和来源分级，状态查询侧重状态仲裁，数值比较侧重数值校准和计数去重
3. **不要过度标注**：标注的目的是辅助推理，不是制造文书工作。简单问题简单标注，复杂问题才需要完整账本
4. **冲突不等于错误**：多条信息冲突时，不要急着选一个，而是把冲突显式呈现给 LLM，让推理模型在完整信息下判断
5. **与回忆规划器配合使用**：单独使用证据账本也能提升质量，但配合回忆规划器效果最佳——规划器减少无关检索，账本提升检索结果的利用率
