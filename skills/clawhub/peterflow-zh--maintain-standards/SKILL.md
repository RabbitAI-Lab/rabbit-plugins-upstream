# 维护共享规范

## 选动作

在会话中使用 `$maintain-standards 动作 参数`，也可以直接说要做什么。按请求选下表中的一项；用户明确要求连续执行时才接续下一项。

| 参数写法（省略 Skill 名） | 自然语言示例 | 执行说明 |
| --- | --- | --- |
| `init [工作区] [--from 材料] [--scope 范围]` | “给这个工作区建一套规范目录”“把已有规范接进来” | [建立或接入规范库](references/init.md) |
| `draft [材料] [--from 来源] [--scope 范围]` | “根据这次评审起草一条候选规范” | [写候选方案](references/draft.md) |
| `apply [候选文件、文件#条目或已确认决定]` | “采纳候选里的第二项”“按这份决定更新分页规范” | [定位、核验并应用](references/apply.md) |
| `check [范围] [--from 核对依据]` | “看看这些规范有没有冲突或过时”“核对规范与代码是否一致” | [只读检查](references/check.md) |

`--from` 接受会话中的原话、本地资料、MR 或提交，可以重复给出。`--scope` 或 `check` 的范围可用文件、目录、章节或功能名。相对路径从用户指定的工作区解析，默认当前工作区。对象可从本轮或紧邻的对话中唯一确定时可以省略。单发 Skill 名且意图不明时展示四种用法。动作或所选条目有歧义时先问清，只要求审阅、预览或解释时只读。

## 规范分级与维护人

优先使用用户指定位置，其次沿工作区 AGENTS.md 或 README 的现行入口。已有根 `standards/` 就沿用，新工作区默认 `.peterflow/standards/`。多个位置并存时按现行入口选择，写入目标仍有歧义才询问。

| 层级 | 内容与默认位置 | 谁维护 |
| --- | --- | --- |
| L0 团队通则 | `general.md`，设计、实现和评审共同遵守的约定 | 团队负责人决定条款、适用范围和例外。 |
| L1 工程专题 | 顶层专题，如 `api.md`、`database.md`、`errors.md`、`testing.md` | 对应专题的负责人决定条款、适用范围和例外。 |
| L2 功能规范与候选 | `features/<功能>.md` 是现行功能规则。`candidates/<主题>.md` 放待决定的提案。 | Agent 核对依据、起草修改，负责人决定是否采纳、调整、暂缓或拒绝。采纳后由 Agent 写回生效位置。 |
| L3 索引、证据与沿革 | 总索引 `README.md`、功能索引 `features/README.md`、`evidence/`、`sources.md`、`backup/` | Agent 在授权范围内更新导航、核实证据的版本和适用范围、记录决定出处、归档旧文。 |

例如，评审提出修改数据库规范时，建议先作为 L2 候选。负责人采纳后，Agent 可按决定写回 L1 的 `database.md`，并在 L3 记录出处。已有明确决定和写入授权时，可以直接 `apply`。

## 按改动找条款

从总索引开始，只读适用的 L0 章节，再按改动类型选 L1 专题。若还涉及产品行为，沿功能索引找到生效的 L2 条款。公共代码要看实际调用方。例如，只改数据库索引时查数据库专题。如果改动也影响打开文档，就再查打开文档的功能规范。

设计和验收以现行条款、需求和契约为依据。核实事实或决定时查证据和出处，处理提案时读选定候选，追溯旧决定时查备份。日常开发、评审与默认检查均沿现行入口。

给人读的规范、候选和报告按 `shuorenhua` 的“写文档”方法写。先说读者遇到什么情况、该怎么做，写完对照原话，保住条件、例外和证据力度。单独安装也可直接使用包内模板。操作限于本次授权的规范及引用；业务代码、全局指令、用户级安装和 Git 提交另按用户请求处理。
