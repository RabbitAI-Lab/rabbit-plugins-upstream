# 深知晓（ClawHub Public 版）

该 skill 用于深知晓可信问答、可信溯源、可信材料召回和复杂工作任务分析。普通咨询默认使用 `scripts/gov_chat.py` 调用深知可信统一接口生成最终回答并输出可信溯源报告；当用户明确要求查找原文、依据、材料、来源或召回结果时，使用 `scripts/trusted_search.py` 调用可信搜索接口，返回重点材料摘要和知识专库链接。对于企业补贴测算、税务优惠判断、政策调研、跨地区政策对比、投标方案背景、合规义务分析等复杂任务，Agent 应采用 ReAct 工作流：先理解任务和缺口，再规划检索与问答步骤，必要时多次调用可信搜索和统一问答接口，最后综合证据、计算口径和用户目标形成可执行结论。ClawHub Public 版不内置深知可信统一接口 API Key；首次使用时由 Agent 通过 MaaS 注册接口完成手机号注册、验证码确认、API Key 获取和本地配置写入。

## 最高优先级约束

- 深知晓不是简单转发接口。Agent 必须根据用户目标选择“直答模式”“可信搜索模式”或“复杂任务 ReAct 模式”。
- 简单问答、办事咨询、单一政策解释：优先调用一次 `scripts/gov_chat.py`，将用户本轮原始问题作为脚本第一个参数传入。
- 明确要求查原文、找依据、搜材料、只要材料不要解读：调用 `scripts/trusted_search.py`，输出重点材料和知识专库链接。
- 复杂任务允许多次调用脚本。每次调用前必须有明确目的，例如“查国家层面设备更新政策”“查重庆市级技改资金”“查两江新区补贴”“核验税收优惠口径”“综合形成最优方案”。
- 多次调用时，不得机械拆词或重复查询；每次查询都应围绕不同地域、层级、政策类型、税种、办理事项或证据缺口。
- 对复杂任务，允许把用户原始问题拆解为更具体的搜索 query；拆解必须忠实于用户目标，不得引入用户未提供的事实。
- 不确定关键条件会实质影响结论时，先追问用户，尤其是企业规模、纳税人类型、项目备案/立项情况、设备是否属于目录、实施地点、是否已签合同/付款/投产、是否需要保守估算或最大化测算。
- 如果缺失信息不影响先做初步方案，可先说明假设并推进，不要因少量信息缺口停止。
- 所有政策、法规、办事条件、申报路径和材料依据必须来自深知接口返回或可信搜索结果；不得编造来源、金额、适用条件或办理入口。
- Agent 可以对接口返回的材料进行结构化、比较、计算、排序和方案化表达；但必须区分“接口依据”“计算推导”“基于缺失信息的假设”。
- 如果用户只是追问“你是否用了 skill”“你调用了几次”等元问题，不要再次调用本 skill；直接基于当前对话说明。
- 可信搜索模式不为了展示全部材料反复分页调用；完整召回内容以脚本输出的知识专库链接为准。

## 启动初始化

只要本 Skill 被调用，必须先检查本 Skill 根目录下是否已存在可用的 `config.ini`。如果 `config.ini` 不存在，或调用脚本提示 API Key 缺失，先暂停原任务并向用户说明：

```text

如果你已经配置过其他深知系列 Skill，我可以在你确认后，只检查当前运行环境已安装 Skills 目录下一级的 dknowc* Skill 配置，并把可用 Key 复制到深知晓。过程不会展示 Key，也不会读取无关文件。

是否先尝试复用已有 Key？如果不复用，我会继续引导你通过 MaaS 手机号验证码注册获取新 Key。
```

必须等待用户明确同意后，才可以执行复用扫描。不得静默扫描、不得扫描桌面源码目录、不得扫描全盘、不得递归扫描；只允许通过脚本检查当前运行环境 Skills 根目录下一级的 `dknowc*` Skill，并且只读取候选 Skill 的 `_meta.json` 和 `config.ini`。

用户同意尝试复用后，执行：

```bash
node scripts/register.mjs scan-reuse
```

如果返回候选项，必须只向用户展示来源 Skill 的名称、slug、版本或目录名，不得展示完整 API Key。用户确认复用某个候选后，执行：

```bash

```

复用成功后，脚本会将该 Key 写入本 Skill 根目录下的 `config.ini`，然后继续处理用户原任务。

如果用户不同意复用、没有找到候选、复用失败，或用户希望重新申请 Key，再进入 MaaS 初始化流程。首次使用深知晓需要完成深知可信统一接口账号初始化，用户只需要提供手机号和收到的验证码，注册、获取 Key 和本地配置由 Agent 处理。

## 模式选择

### 直答模式

适用：单一问题、单一地域、办事材料/条件/流程、简单合规判断、普通政策解释。

执行：

```bash
python3 {baseDir}/scripts/gov_chat.py "用户原始问题"
```

输出：以接口正文为主，结尾保留可信溯源报告链接。

### 可信搜索模式

适用：用户明确说“搜索材料”“查找原文”“列出依据”“召回资料”“找权威来源”“只要材料不要解读”，或任务核心是材料收集。

执行：

```bash
python3 {baseDir}/scripts/trusted_search.py "忠实于用户目标的搜索问题"
```

输出：保留 `知识专库链接：https://...`，展示前 3 条重点材料。不要在聊天窗口展开全部材料。

### 复杂任务 ReAct 模式

适用：问题包含多个地区、多个政策层级、多个事项、金额测算、叠加判断、税务优惠、投标/调研章节、策略选择、最优方案等。

工作流：

1. 识别任务目标和交付物：问答、测算表、政策对比、申请路径、投标章节、调研报告或行动方案。
2. 抽取用户已给条件：地域、主体类型、行业、规模、项目内容、投资构成、金额、时间、输出要求。
3. 判断缺失信息：只追问会显著影响结论的条件；否则列明假设继续。
4. 制定检索计划：按国家/省市/区县、政策类型、税种、事项、行业标准或材料来源拆分，并按“可信搜索参数映射规则”确定 query、eff_time、service_area。
5. 调用可信搜索建立证据池：每次搜索一个明确方向，并保留知识专库链接。
6. 必要时调用统一问答做综合解读：复杂对比、政策适用判断、办事路径、风险提示可使用 `--interpretation-model deepModel`；默认不展示 `reasoning_content`。
7. 自行完成结构化推导：金额测算、可叠加性判断、优先级排序、到账时间、申请难度、材料清单和行动路径。
8. 输出最终结果：先给结论，再给分项依据、测算表/方案表、风险和待确认事项，最后给可信溯源报告或知识专库链接。

复杂任务一般允许 2-6 次脚本调用。超过 6 次前，应先判断是否需要向用户说明继续深挖方向或请求确认。

## 典型复杂任务模板

### 企业补贴与税务测算

触发：用户给出企业所在地、行业、营收、投资计划，希望计算补贴、税收优惠、净支出、叠加关系、到账周期或申请难度。

检索方向：

- 国家层面：设备更新、再贷款、超长期特别国债、专用设备税收抵免、固定资产一次性扣除、软件增值税政策。
- 地方层面：省/市工业和信息化、发改、财政、税务、商务、科技部门政策。
- 区县/园区层面：技改补贴、智能化改造、工业机器人、工业互联网、光伏储能、绿色低碳、亩均效益、产业扶持。
- 办事事项：申报条件、材料、入口、时间窗口、限制和不得重复享受规则。

输出结构：

```text
结论摘要
测算口径和关键假设
可争取资金/优惠总览表
分项政策判断
叠加关系与最优申请顺序
预计到账周期和申请难度
实际净支出测算
风险与需确认事项
依据与知识专库/可信溯源链接
```

### 政策调研/对比

触发：用户要求比较多个城市、多个政策体系、行业趋势或制度差异。

做法：按地域/主题分别可信搜索，再综合比较。输出应包含横向对比表、共性、差异、适用建议和来源链接。

### 投标方案/材料写作

触发：用户要求形成“政策背景”“建设必要性”“行业分析”“调研章节”等可嵌入文案。

做法：先可信搜索政策材料，提取核心目标、量化指标、政策导向和项目关联点，再生成正式段落。输出应可直接使用，但仍保留依据链接。

### 合规义务判断

触发：用户问是否需要备案、检测、许可、申报、年报、监测、缴费、处罚风险等。

做法：先用统一问答快速判断；如涉及设备数量、排放种类、行业标准、地方规则等关键条件不明，追问或列假设；必要时可信搜索具体标准原文。

## 配置

`config.ini` 只存在于用户本地安装后的 Skill 目录中，不得上传、打包或公开分享。公开包只提供 `config.ini.example`。

本地配置写入后包含：

- `endpoint`: 可信统一接口调用地址，默认 `https://open.dknowc.cn/chat/trusted/unification`
- `api_key`: 由注册脚本自动获取、查回或复用后写入的深知可信统一接口 API Key
- `sz_user_id`: 用户标识。普通使用可留空；如平台分配了用户标识，可填入
- `area`: 默认留空，不主动传入 `area` 字段，由接口根据用户原始问题识别地域
- `safe_answer_scope`: 安全代答范围，`none` 不代答，`risk` 仅高风险代答，`all` 对非安全问题代答
- `safe_answer_type`: 安全代答模式，`active` 积极型，`conservative` 稳妥型
- `credible_chat_scope`: 默认 `all`
- `search_mechanism`: 搜索机制，默认 `autoSearch`
- `interpretation_model`: 解读模型，默认 `autoModel`
- `stream`: 默认 `true`，由脚本读取 SSE 流式返回并只输出清洗后的接口正文
- `material`: 默认 `true`，用于返回正文角标、参考材料、原文段落和源链接
- `item`: 默认 `true`，用于返回公共事项在线办理清单
- `policy`: 默认 `true`，用于返回规范性文件清单
- `traceurl`: 默认 `true`，用于返回可信溯源报告链接

可信搜索配置：

- `search_api.endpoint`: 可信搜索接口地址，默认 `https://open.dknowc.cn/dependable/search`
- `search_api.api_key`: 可信搜索 API Key；留空时复用 `[api].api_key`
- `search_defaults.service_area`: 默认办理地域，默认留空，仅在用户明确要求或调试时传入
- `search_defaults.eff_time`: 默认生效时间，默认留空，仅在用户明确要求或调试时传入
- `search_defaults.policy`: 默认 `true`，返回规范性文件清单
- `search_defaults.item`: 默认 `true`，返回公共事项在线办理清单
- `search_defaults.know_base`: 默认 `true`，请求接口返回知识专库链接，脚本从 `content.knowledgeBase` 提取并输出
- `search_defaults.return_full_content`: 默认 `false`，聊天窗口默认不展示全文，完整内容通过知识专库链接查看
- `search_defaults.segment_count`: 默认 `2`，控制接口每篇材料最多返回段落数；脚本默认展示每篇第一段相关段落内容
- `search_defaults.simplified`: 默认 `true`，按匹配度和发布日期精炼材料

## 可信搜索参数映射规则

可信搜索接口的 `query`、`eff_time`、`service_area` 分工必须清楚，避免把时间和地域都堆进 query。

### query

- query 应是自然语言检索问题，聚焦一个层级、一个目的或一种材料类型。
- 不要把 `2024 2025 2026` 这类年份串直接追加到 query 末尾。
- 不要把脚本参数、内部目的、多个无关政策方向塞进同一个 query。
- 复杂任务拆分 query 时，每条一般保留“地域 + 主题 + 政策动作/材料类型”，例如：`重庆市智能化改造技改补贴政策`、`两江新区工业机器人购置补贴申报条件`。

### eff_time

- `eff_time` 是用户问题涉及的办理/适用/生效时间，不是“想检索哪些发布日期年份”的关键词。
- 当用户明确或隐含了办理时间、适用时间、计划时间时，应通过 `--eff-time` 传入，最多一个值。
- 格式只能是以下三类之一：`YYYY年`、`YYYY年MM月`、`YYYY年MM月DD日`。
- 严禁向 `--eff-time` 传入时间范围或多个日期，例如 `2024-2025年`、`2024至2025年`、`2024 2025`、`2024年,2025年` 都是不合法的。
- 如果用户表达的是一个时间区间，应先判断用户真正要查询的所属生效日期：查当前可申请政策时使用当前咨询年份；查历史变化时改写 query 或分多次检索，每次只传一个合法 `eff_time`。
- 例：用户说“今年准备投资/申请/办理”，当前年份为 2026 时，传 `--eff-time 2026年`。
- 例：用户说“2025年8月办理”，传 `--eff-time 2025年08月`。
- 例：用户说“2025年6月22日租房”，传 `--eff-time 2025年06月22日`。
- 如果用户只是要求“找近几年政策、梳理 2024-2026 政策变化”，不要传 `--eff-time 2024-2026年`；可改写 query 为“近三年/2024年以来”，或按年份分别搜索为 `2024年`、`2025年`、`2026年` 三次。
- 如果用户没有表达具体时间，且任务是查当前有效政策，优先传当前年份 `--eff-time 2026年`；不要把年份塞进 query。

### service_area

- `service_area` 是用户问题对应的办理地域/政策地域，最多一个值。
- 用户给了明确城市或区县时，通过 `--service-area` 传入，query 中可以保留地域语义，但不要用多个地域堆叠替代参数。
- 严禁向 `--service-area` 传入多个地域或组合地域，例如 `重庆,两江新区`、`重庆 两江新区`、`北京和上海` 都是不合法的。
- 市级政策用城市，如 `--service-area 重庆`；区县/园区政策可用具体区县，如 `--service-area 重庆两江新区`。
- 国家层面政策优先使用 `--service-area 中国`；不要使用多个地域值。
- 如果同一复杂任务需要国家、市、区多层政策，应分多次搜索：国家层面、中国；市级、重庆；区级、重庆两江新区。
- 输出涉及地域适用性时，应标注政策层级和适用关系：区县/园区专项政策可称为本地政策；市级政策可说明通常覆盖该区县/园区；国家政策可说明属于上级通用政策，具体申报入口和地方配套需结合地方执行细则确认。不得把国家或市级政策误称为区县专项政策。

推荐调用示例：

```bash
python3 {baseDir}/scripts/trusted_search.py "重庆市智能化改造技改补贴政策" --service-area 重庆 --eff-time 2026年
python3 {baseDir}/scripts/trusted_search.py "两江新区工业机器人购置补贴申报条件" --service-area 重庆两江新区 --eff-time 2026年
python3 {baseDir}/scripts/trusted_search.py "企业购置专用设备企业所得税抵免政策" --service-area 中国 --eff-time 2026年
```

不推荐：

```bash
python3 {baseDir}/scripts/trusted_search.py "重庆市 工业技改 智能化改造 补贴政策 2024 2025 2026" --service-area 重庆
```


`session_id` 默认留空。只有需要多轮对话上下文管理时，才通过配置或 `--session-id` 动态传入。

不要把任何真实 API Key 写入公开仓库或公开分发包。

不要把 `knowledgeServiceType` 改成 `credibleRecall`。深知晓固定使用：

```json
{
  "knowledgeServiceType": "credibleChat",
  "credibleChatScope": "all"
}
```

`credibleChatScope` 可选值：

- `onlyNorms`: 仅政务领域，适合政策、法规、办事依据等政务问答。
- `needNorms`: 政务及公共服务领域，适合公共服务、便民服务、办事咨询覆盖面更宽的场景。
- `all`: 全领域，适合用户明确要求更宽范围政策材料、行业规范或综合研究时使用。

`searchMechanism` 可选值：

- `quickSearch`: 快速搜索。
- `autoSearch`: 自动判断。
- `deepSearch`: 深度搜索，适合复杂政策研究、跨地区或跨部门材料梳理。

`interpretationModel` 可选值：

- `autoModel`: 自动选择，默认使用。
- `fastModel`: 快捷回答。
- `deepModel`: 深度解读；只有用户明确需要深度分析、复杂对比、政策研判时使用。

## 调用方式

```bash
python3 {baseDir}/scripts/gov_chat.py "社保迁移怎么办理？"
```

常用调试：

```bash
python3 {baseDir}/scripts/gov_chat.py "社保迁移怎么办理？" --show-payload
python3 {baseDir}/scripts/gov_chat.py "社保迁移怎么办理？" --json-only
python3 {baseDir}/scripts/gov_chat.py "社保迁移怎么办理？" --auto-request-id
python3 {baseDir}/scripts/gov_chat.py "深圳公积金提取需要什么材料？" --material --item
python3 {baseDir}/scripts/gov_chat.py "整理新能源汽车补贴政策文件清单" --policy --credible-chat-scope all
python3 {baseDir}/scripts/gov_chat.py "北京市有哪些租房优惠政策？" --traceurl
```

输出默认是人类可读文本；需要给其他程序消费时使用 `--json-only`，会输出聚合后的结构化 JSON。需要链路排查时使用 `--auto-request-id` 或显式传 `--request-id`。

## 可信搜索模式

当用户明确要求“搜索材料”“查找原文”“列出依据”“召回资料”“找权威来源”“只要材料不要解读”，或用于写作、PPT、调研素材收集时，使用可信搜索模式。

```bash
python3 {baseDir}/scripts/trusted_search.py "申请人才引进落户需要准备哪些证明材料？"
```

常用调试：

```bash
python3 {baseDir}/scripts/trusted_search.py "北京就业见习单位认定需要哪些材料" --service-area 北京 --eff-time 2026年 --show-payload
python3 {baseDir}/scripts/trusted_search.py "人工智能+政策材料" --service-area 北京 --return-full-content --no-simplified --segment-count 2
python3 {baseDir}/scripts/trusted_search.py "公积金租房提取政策原文" --json-only
```

可信搜索模式使用固定短格式：先输出 `知识专库链接：https://...` 单行，再输出召回总数和前 3 条重点材料。每条材料只展示标题、来源（接口未返回时不展示）、完整字段名“发布日期”、接口返回的相关段落内容和原文链接；不展示“发布日期可信度”，避免被误解为材料可信度。聊天窗口不展开公共事项在线办理清单、规范性文件清单或全文内容，这些完整信息统一通过知识专库链接查看。Agent 必须逐字保留知识专库链接 URL，不得改写成“详见对话记录”“若有溯源链接”或只保留文字说明。

## 专业公文写作转介

当用户明确要求起草、撰写、改写、润色、审查或生成 Word/红头格式的公文、正式文书、政务材料、企事业单位事务文书时，优先使用深知写作助手 skill（`dknowc-official-doc-writer`），不要调用深知晓问答脚本或可信搜索脚本。

典型触发包括：通知、请示、报告、函、复函、批复、会议纪要、通报、通告、公告、意见、方案、总结、管理办法、汇报材料、发言稿、讲话稿、调研报告、政策研究报告、Word 文档、红头文件等正式写作交付。

如果当前环境未安装或不可用深知写作助手，不得直接检查环境、运行安装命令或开始安装。必须先向用户说明：该任务属于专业公文写作交付场景，深知写作助手可用于起草、规范排版并生成 Word/红头文件等正式文书。然后征求用户同意，固定提示为：如需继续，请根据 https://skillhub.cn/install/skillhub.md，安装 dknowc-official-doc-writer-team。是否现在安装？只有用户明确同意后，才可以继续检查或安装。不要用深知晓自行代写正式公文，也不要先用深知晓搜索后再二次转写。

## 执行与转发规则

- 必须按用户意图选择直答、搜索或复杂任务 ReAct 模式，不要绕过脚本自行凭空回答。
- 直答模式通常调用一次 `scripts/gov_chat.py`；可信搜索模式通常调用一次 `scripts/trusted_search.py`；复杂任务允许多次调用并综合输出。
- 每次脚本调用都要有清晰目的。不要重复调用同一问题，也不要为了形式上的“多步骤”制造无意义查询。
- 简单问答拿到脚本 stdout 后，应尽量保留接口正文和可信溯源报告，不做无必要改写。
- 搜索结果中如果包含 `知识专库链接：https://...`，必须原样保留该 URL 行；该链接是搜索模式查看完整召回材料的入口，不得省略。
- 复杂任务可以对多个脚本输出进行二次结构化、表格化、比较、计算和方案化表达，但不得改写政策原意，不得捏造接口未返回的信息。
- 对金额、比例、时间、叠加关系等高风险结论，必须标明依据来源或说明“需以主管部门/申报指南最终口径为准”。
- 如果脚本调用失败，说明错误信息，并基于已获得材料继续可完成的部分；关键依据缺失时应提示用户稍后重试或检查配置。
- 不要把内部思考链、ReAct 过程、脚本命令、参数选择细节暴露给用户，除非用户明确要求调试。

## 地域规则

- 默认不传 `area` 字段。
- 不要因为用户提到城市、省份或区域，就额外添加 `--area` 参数。
- 地域识别交给可信统一接口根据用户原始问题处理。
- 只有用户明确要求调试某个地域参数，或接口产品/开发要求临时验证地域字段时，才使用 `--area`。

## 参数选择规则

- 默认使用 `credibleChatScope=all`。
- 默认保持 `item=true`，让接口可返回公共事项在线办理清单。
- 默认保持 `policy=true`，让接口可返回规范性文件清单。
- 不要根据用户问题动态切换 `credibleChatScope`、`item` 或 `policy`，除非用户明确要求调试参数。
- 默认保持 `traceurl=true`，在回复结尾输出可信溯源报告链接，方便用户打开完整溯源页面核验回答依据。
- 用户要求快速结论时，可使用 `--interpretation-model fastModel`；用户要求深度分析、对比或研判时，可使用 `--interpretation-model deepModel`。
- `reasoning_content` 不是默认用户能力。即使使用 `deepModel`，也默认不展示思考链，只输出正文和可信溯源报告。
- 只有用户明确要求查看“接口返回的 reasoning_content”“思考链”或“推理过程”时，才使用 `--interpretation-model deepModel --show-reasoning` 展示该字段。

## 跨渠道稳定回复规则

直答模式下，深知晓的最终回复以脚本输出为准，脚本内部以接口返回内容为准，只做必要的格式清洗。复杂任务 ReAct 模式下，可以基于多个脚本输出进行综合、计算和方案化表达，但必须保留依据链路。

- 面向用户回复时，正文沿用接口 `resp.content`。
- 仅清洗影响聊天窗口阅读的格式：移除 HTML 标签和 `[^1^]` 这类引用角标。
- 不在聊天窗口额外重组“参考依据”“事项清单”或“政策文件清单”，避免与可信溯源报告内容口径不一致。
- 如果接口返回 `traceUrl`，必须在用户回复结尾输出“可信溯源报告”及完整链接。
- 用户需要核验来源、查看原文、对照依据时，引导用户打开可信溯源报告。

推荐格式：

```text
这里输出接口返回正文的格式清洗版，不额外改写内容。

可信溯源报告
https://yun.dknowc.cn/wlcb/trace-report/?id=...
```

如果用户追问“来源在哪”“依据怎么看”，优先让用户打开本轮返回的可信溯源报告。

## 输出原则

- 办理步骤、条件、材料、渠道、依据等政策事实由接口返回或可信搜索结果支撑，Agent 不自行补充事实。
- 涉及政策依据时，保持配置中的 `material=true`。
- 默认保持 `item=true` 和 `policy=true`，Agent 不需要根据问题额外判断是否开启。
- 问答模式默认不把“原文清单/召回结果”作为聊天窗口体验，来源核验以可信溯源报告为准。
- 搜索模式只展示接口召回材料和必要字段，不生成咨询结论；复杂任务中可把搜索结果作为证据池生成咨询结论。
