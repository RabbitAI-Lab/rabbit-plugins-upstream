# 红旗详细判定参考

本文件为 SKILL.md Step 6 双通道红旗审查提供补充判定细节。reviewer 子代理在发现相关红旗时查阅，主评估流程无需全量加载。

---

## LLM 过度依赖：确定性工作分类表

以下类型的工作应该用脚本而非 LLM 推理：

| 类别 | 典型场景 |
|------|---------|
| **数据获取与 I/O** | API 调用、分页遍历、文件读写、目录遍历 |
| **格式转换** | JSON<->CSV、markdown<->HTML、数据 reshape、编码解码（base64 / URL encode / hash） |
| **数据处理** | 排序、过滤、去重、聚合、多源合并、结构化格式解析（JSON/CSV/XML/YAML parse） |
| **数值计算** | 数学运算、统计、计数、日期时间运算（时区转换、间隔计算） |
| **规则执行** | 明确 if-else 决策树、正则匹配、schema 校验、字符串定长操作（截断/padding/case） |
| **比较** | Diff 生成、版本对比、字段级变更检测 |
| **输出格式化** | 固定模板填充、表格生成、报告布局 |

**判断标准**：如果给同样的输入，人能写出一段不需要任何"理解"就能得到正确结果的代码，那这个环节就不该让 LLM 做。

### 评估注意

- 不是所有 skill 都有可脚本化的环节——纯知识型 / 纯创作型 skill 可能全程需要 LLM，这不算红旗
- 红旗触发条件：skill **有明确的确定性环节**（如"先调 API 拿数据，再分析"）但**全部用 LLM 推理完成**，没有脚本辅助
- 严重程度看规模：一个小格式转换不值得提，但"让 LLM 逐行解析 500 行 CSV"就是明确的浪费

## Context bloat：三轴上下文影响评估

skill 对 agent 上下文的影响分三轴，本节定义**入参轴**和**响应轴**的统一评估方法（加载轴不在本文档范围内）。

### 三轴定义

| 轴 | 含义 |
|---|---|
| **加载轴** | 目标 skill 本身的文本对 agent 上下文的影响 |
| **入参轴** | agent 调用 skill 接口/脚本时，传递给接口/脚本的参数对 agent 上下文的影响 |
| **响应轴** | agent 调用 skill 接口/脚本后获得的响应内容塞回 agent 上下文的影响 |

### 统一 5 档风险表（入参轴和响应轴共用）

| 算出的上限值 | 档位 |
|---|---|
| < 2k token | **极低** |
| 2k–5k token | **低** |
| 5k–30k token | **中** |
| 30k–200k token | **高** |
| > 200k token | **极高** |

"算不出上限" → 不是极低，强制归到 **中档** 走实测验证。

### 通用评估原则（对入参轴和响应轴均适用）

1. Step 1 静态预估档位
2. **除非是极低档**，否则在 Step 6 必须实测对应轴的实际体积
3. Step 3 测试用例设计中，**非极低档必须含 1 个极限用例**（尽可能触发该轴的最大数据量）
4. 命中中档及以上未提供解决方案 → 标 🚩 Context bloat 红旗，建议改造为"暂存 + 摘要"模式

## 响应轴评估流程

### 第一步：能不能算出输出上限？

依据来源任一即可:
- skill body 显式声明输出格式（"输出一个 yes/no"、"输出 ≤5 行 markdown"、"返回固定 5 字段 JSON"）
- 调用的 API 响应 schema 已知，且有明确条数/字段上限（最多 N 条、每条 M 字段、无 long text 字段）
- 脚本输出走固定模板（reviewer 能从代码里读出来）

算不出 → 归到中档，强制实测。

### 第二步：算出来的上限值套 5 档表

简单乘算即可：条数 × 字段数 × 字段平均长度。reviewer 不需要精确，量级对就行。

### 升档反面信号（出现任一立刻不是极低）

- 输出包含**无量化约束的开放式指令**："列出所有相关 ASIN"、"详细分析"、"完整报告"——没有上限就不是先验可定
- 调用的 API **可能返回长文本字段**：商品描述、评论原文、HTML、PDF 抽取——单字段就能爆掉
- 输出含**用户决定规模的参数**：top_n、limit、深度等可调上限
- 输出**包含上游输入的转写/复述**：输入越大输出越大（即使 skill 自己没扩张数据）

### 高上下文响应的推荐解法——数据暂存 + 摘要输出模式

1. skill 应提供（或指导 agent 使用）一个数据暂存脚本，将大体量中间产物写入临时文件而非塞回对话
2. skill 的输出应只包含：数据结果摘要 + 数据结构声明（如 JSON schema / 字段说明 / 行数统计）
3. 让 agent 基于摘要自行决策是否、何时、读取暂存文件中的哪些部分

**具体实现模式**：

```
脚本获取/计算原始数据 → 写入临时文件（如 .tmp/result-{timestamp}.json）
脚本同时输出一行摘要到 stdout（行数、字段列表、Top-N 样本）
AI 只消费摘要，按需 Read 文件的特定片段
```

向 skill 作者建议的改造步骤：
1. 在 `scripts/` 中编写数据获取脚本，脚本末尾 `print` 一个 mini-report 而非全量数据
2. 脚本将完整结果写入约定路径（如 `.tmp/{skill-name}-{date}.json`）
3. SKILL.md 中指导 agent：拿到摘要后按需用 Read + offset/limit 读取结果文件的特定片段

## 入参轴评估流程

入参体积由两个独立因素决定，**两层都要看，取较差的那一层定档**。

### 层 A：接口设计

依据来源任一即可:
- 接口签名显式声明参数类型/长度（`--asin <string, max 10 chars>`、`--top-n <int>`）
- 参数是**引用语义**（文件路径 / ID / URL / 哈希），本身体积小
- 参数有明确上限约束

### 层 B：指引质量

SKILL.md 是否显式约束了 agent 调用方式:
- "把数据写到文件，传路径过来" ← 健康
- "把内容贴进来"、"完整粘贴"、"传入完整 X" ← 反面信号

接口设计健康但指引糟糕，agent 仍然会传大数据——所以两层独立评估，定档时取较差。

### 升档反面信号（出现任一立刻不是极低）

- 参数接受**无长度约束的自由文本**（`--data="$BLOB"`、`--prompt`、`--text`）
- 参数要求**完整原始数据**而非摘要/引用（`--full-html`、`--all-reviews`、`--raw-content`）
- 参数体积**由 agent 上游决定**（没有 skill 侧硬上限）
- skill 指引里出现"贴进来"、"完整粘贴"、"传入全部"等措辞

### Step 6 入参轴观测要点

reviewer 读 transcript 时观测两件事:

1. **agent 实际传了多少 token 给 skill**（命令行参数 + stdin 字节数）
2. **agent 是否走了引用路径**（传文件路径/ID）还是**直接灌内联数据**

**关键判定原则**：
- **引用类大体积参数不算 bloat**——reviewer 就该传那么多 reference（例如 100 个 ASIN 列表）
- **内联类即便小也要标注**——传了原始评论文本即便只有 3k token，也是设计反模式，要写进报告

### 高上下文入参的推荐解法

1. skill 接口改为**接受引用而非内联数据**（`--input-file <path>` 替代 `--data <content>`）
2. skill 提供"数据暂存脚本"作为标准前置步骤，让上游数据先写文件再调用主功能
3. SKILL.md 指引明确写："agent 应将上游大数据写至 `.tmp/xxx.json`，将路径传入；勿直接粘贴内容"

## 极限测试用例设计原则

非极低档的轴**必须**在 Step 3 起草至少一个极限用例。两轴可合一也可分开:

### 响应轴极限用例

让 skill 在合理使用范围内**产出最大可能的输出**——选 skill 声称支持的最大输入规模、最广覆盖的查询、最深的分析层级。

例：评论分析 skill 让它分析 1000 条评论而不是 10 条；竞品调研 skill 让它扫 50 个 ASIN 而不是 5 个。

### 入参轴极限用例

让 agent 在合理使用范围内**最大化入参体积**——把上游数据规模拉到 skill 声称支持的上限。

例：listing 优化 skill 让 agent 把整页竞品 HTML 作为参考材料传入；评论分析 skill 让 agent 把 1000 条评论原文作为输入。

### 两轴合一的场景

很多 skill 是"输入大 → 输出也大"，一个用例就能同时压两轴。但若 skill 是"输入小 → 输出大"（如根据一个 ASIN 拉全量历史数据）或"输入大 → 输出小"（如根据 1000 条评论给出一句总结），则两个用例需要分别设计。

### 如果 skill 没声明上限

按"用户合理可能传入的极端值"来定，不要硬塞荒谬规模（如 10 万条评论挑战 skill）。极限是"贴近上限的真实场景"，不是 fuzzing。
