# 流程型 skill 扩展审查

**何时加载**：仅当 Step 1a 判定 skill 为**流程型垂直 skill**（多步编排、有步骤间数据依赖、含决策点）时，reviewer 在基础双通道 + vertical.md 之上追加这些维度。

**与 vertical.md 的关系**：vertical.md 的三条维度（领域知识正确性 / 领域 silent failure / 邻近越界）对流程型 skill 仍然适用，本文件是在此基础上的**追加**，不替代。

**区分标准**：
- 知识点型 skill：一次输入 → 一次输出，无中间状态（如"写 listing"、"分析评论"）
- 流程型 skill：多步编排 → 步骤间有数据传递 → 含至少一个用户决策点（如"选品全流程"、"竞品调研工作流"、"广告投放诊断流程"）

---

## 维度 1：流程完整性与步骤依赖

### 是什么

流程型 skill 声称覆盖某个业务场景的全流程（或关键子流程）。评估该 skill 的步骤设计是否：
- 覆盖了业务场景的关键环节（不是只做了前半截就停）
- 步骤顺序符合业务逻辑（不是乱序拼接）
- 步骤间的数据依赖被正确建立（上游产出是下游的输入）

### 典型问题

- skill 声称覆盖"选品全流程"但只有市场调研，没有竞品分析和供应链环节
- 步骤顺序错误：先深入分析单品，再做市场筛选（应该反过来）
- 某步骤需要前一步的输出但没有声明依赖，跳步执行时会失败或产出垃圾

### 怎么测

- 画出 skill 声明的步骤流程图，对照业务场景的完整链路找缺口
- 刻意跳过某个中间步骤，看下游步骤是否报错 / 优雅降级 / 还是静默产出垃圾
- 对照 skill description 的承诺范围——声明了但未实现的环节标记

### 怎么看

- 有关键环节缺失但 description 声称覆盖 → 🔴（承诺与实现不符）
- 步骤可跳过但无降级提示 / 下游产出垃圾 → 🟡
- 流程完整、依赖正确、缺少的环节已在 description 里明确排除 → ✅

## 维度 2：决策点设计

### 是什么

流程型 skill 的用户需要在某些节点做决策（选哪些候选品深入、要不要切换关键词、接不接受筛选条件）。决策点的数量和位置直接影响使用体验：
- **太多**：每步都停下来问"继续吗？"→ 用户疲劳，流程变成手动逐步确认
- **太少**：agent 自行跑完全部 → 用户失去对关键决策的控制
- **放错位置**：在无关紧要的地方暂停，在关键分岔路上自动跑过

### 典型问题

- 每一步都问"是否继续"（尤其是确定性步骤——数据获取不需要用户确认）
- 用户应该选候选对象（如 ASIN）的环节被 agent 自动决定了
- 可选分支（如"要不要做供应商搜索"）被强制执行

### 怎么测

- 跑一次完整流程，记录所有暂停点，分为：
  - **必要暂停**：用户必须做选择、输入信息、或拍板方向
  - **不必要暂停**：确认型（"好的继续"）/ 已有默认值可自动跑的
- 检查关键决策节点是否有暂停——如果 agent 自己做了选品决策而不是呈现数据让用户选，那是设计缺陷

### 怎么看

- 有不必要暂停（确定性步骤让用户确认） → 🟡（体验差但不致命）
- 关键决策被 agent 自动做了（用户失去控制） → 🔴（角色越界）
- 暂停点准确在用户需要决策的地方，确定性步骤自动执行 → ✅

## 维度 3：数据依赖完整性

### 是什么

步骤间通过文件 / 变量 / 上下文传递数据。评估：
- 上游步骤的输出格式是否被下游步骤正确解析
- 中间步骤产出的文件命名是否与下游期望一致
- 上游步骤部分失败时，下游是否能处理缺失数据（而非崩溃或编造）

### 典型问题

- 步骤 A 输出 JSON 字段名为 `monthlyRevenue`，步骤 B 读 `monthly_revenue` → 静默得到 null
- 步骤 A 对某个市场不支持（返回空文件），步骤 B 假设文件非空 → 脚本崩溃
- 文件命名约定不一致：上游写 `step3_B08XXX_keywords.json`，下游找 `step3_B08XXX_keywords_raw.json`

### 怎么测

- 追踪一次完整执行的所有中间文件，验证每个文件是否被至少一个下游步骤消费
- 故意让某个上游步骤返回空 / 错误结果，看下游行为：
  - 优雅跳过 + 标记缺失 → ✅
  - 崩溃 / 脚本报错 → 🟡
  - 静默编造数据 → 🔴

### 怎么看

- 有数据链断裂但静默产出（下游编造数据填充）→ 🔴（最危险——和 silent failure 同级）
- 有数据链断裂且崩溃 → 🟡（至少没骗人）
- 数据链完整，缺失有优雅降级 → ✅

## 维度 4：降级与中断恢复

### 是什么

流程型 skill 依赖多个外部服务（API、数据源）。评估：
- 单个 API 不可用时，流程是否整体阻塞还是能跳过继续
- 用户中断后（关闭会话、网络断开），能否从断点恢复而非重头来过
- 可选步骤（如"1688 供应商搜索"）是否正确标记为可选

### 典型问题

- 一个非关键 API 超时 → 整个流程停转（应该跳过并标注"此项数据暂不可用"）
- 用户在 Step 3 中断，回来后必须从 Step 0 重新跑（已有的 Step 1-2 数据没用上）
- 所有步骤同权重，没有"必须"vs"可选"的区分

### 怎么测

- 模拟一个非关键 API 返回错误，观察流程是否继续
- 在中间步骤中断，重新启动时给出"从 Step X 继续"的指令，看 skill 是否能利用已有数据
- 检查 skill 是否区分了"强依赖步骤"（没这个数据流程无意义）和"弱依赖步骤"（没有也能出报告，只是少一个维度）

### 怎么看

- 非关键 API 失败 → 整体阻塞 → 🟡
- 无法中断恢复但有合理原因（如 API 数据有时效性）→ 标注即可
- 非关键步骤失败能跳过 + 支持从断点恢复 → ✅

## 维度 5：执行效率（并行与串行策略）

### 是什么

多步流程中，步骤之间的执行策略是否合理：
- 无依赖关系的步骤是否并行执行（节省时间和 token）
- 有依赖关系的步骤是否正确串行（避免读到不完整的上游数据）
- 批量操作（如对多个 ASIN 做同样分析）是否有合理的并行策略

### 典型问题

- 步骤 3a（Keepa 详情）和步骤 3b（关键词反查）无依赖但串行执行 → 白白等待
- 批量 ASIN 分析串行跑 10 个 → 可以并行但没做
- 依赖上游输出的步骤被并行了 → 读到空文件或旧数据

### 怎么测

- 画出步骤依赖图，标注哪些可以并行
- 对照 skill 实际执行顺序，找"不必要的串行等待"
- 验证并行步骤是否有正确的同步点（等所有并行任务完成后再进下一阶段）

### 怎么看

- 明显可并行的独立步骤被串行化 → 🟡（效率损失但不影响正确性）
- 有依赖的步骤被错误并行 → 🔴（数据完整性风险）
- 并行策略合理、有同步点 → ✅

## 维度 6：状态管理与幂等性

### 是什么

流程型 skill 通常用文件系统作为状态存储（工作目录 + 中间文件）。评估：
- 重跑单个步骤是否安全（不会产生重复数据或覆盖有价值的中间结果）
- 工作目录结构是否清晰可预测
- 同一 skill 对同一输入跑两次，结果是否一致

### 典型问题

- 重跑 Step 2 时追加而非覆盖 → 筛选结果翻倍
- 文件命名不含区分标识（如日期/批次），重跑覆盖上次有价值的数据
- 工作目录不按关键词/市场隔离 → 多次选品数据混在一起

### 怎么测

- 同一输入跑两次完整流程，对比产出目录结构和文件内容
- 重跑单个步骤（不清除历史文件），看输出是覆盖还是追加还是报错
- 检查文件命名是否含足够的上下文信息（关键词、市场、日期、ASIN）

### 怎么看

- 重跑导致数据污染（追加重复 / 混合不同批次）→ 🔴
- 重跑安全覆盖，但覆盖了可能有保留价值的历史数据 → 🟡
- 重跑幂等（覆盖或跳过已有数据）+ 目录结构清晰 → ✅

## 维度 7：步骤产出与决策目标对齐

### 是什么

流程型 skill 每个步骤都应服务于用户在当前阶段的决策需求。评估：
- 每个步骤的产出是否有明确对应的决策动作（用户看完这步数据后该做什么决策？）
- 是否存在"看了但不知道该干什么"的步骤产出
- 关键决策所需的信息是否在对应步骤中完整呈现（而不是散落在多个步骤里需要用户自己拼凑）

### 典型问题

- 某步骤输出了大量维度数据但没有对应的决策点——用户看完不知道该做什么判断
- 用户在决策点（如选 ASIN）时需要的关键指标（利润率、竞争度）散落在不同步骤的输出里
- 存在"装饰性步骤"——产出看起来专业但对后续决策没有实质贡献

### 怎么测

- 对每个步骤问："用户看完这步输出后，预期做出什么决策或判断？"——如果答不上来，这步骤的设计需要审视
- 在关键决策点，检查用户是否能仅基于当前步骤的输出（不回翻前面）做出合理决策
- 去掉某个步骤的输出，看最终决策质量是否明显下降——如果不下降，这步是冗余的

### 怎么看

- 有步骤产出与任何决策无关（纯装饰 / 信息堆砌）→ 🟡（Orphan step 的流程型变体）
- 决策点缺少关键信息（需要翻前面几步拼凑）→ 🟡
- 每步产出对应明确决策、决策点信息完整自足 → ✅
