# OPC 开发套件总览

> **版本**：v1.7.0 | **代号**：Frost Shield（霜盾）
> **定位**：AI 辅助编码的完整质量保障体系——从需求到交付，从编码到审查，从测试到改进，全链路闭环。
> **核心哲学**：不靠 AI 自觉，靠机制倒逼。不让 AI 说"测试通过"就完事——让它证明"测够了"，报告"哪里没测到"。

---

## 一、体系架构：九层防御

```
L0-R 深度调研 → L0a 需求引导 → L0b 设计引导
     ↓
  调研质量门（6项）→ 需求质量门（8项）→ 设计质量门（6项）
     ↓
L1 规格书（三维度穷举）→ L2 架构（Result模式+中间件）
     ↓
L3 编码（异常优先模板）→ L4 测试（六层框架）
     ↓
L5 审查（Ralph模式 + 🛡️12项审计）→ Audit-Ledger 交接
     ↓
L6 反馈闭环（弯路记录→分析→改进→预防）
```

| 层级 | 名称 | 核心机制 | 不通过则 |
|------|------|---------|---------|
| L0-R | 深度调研 | 5方向×4问=20步引导 | 不允许写需求 |
| L0a | 需求引导 | 七维28步引导 | 不允许进入设计 |
| L0b | 设计引导 | 五层20步引导 | 不允许进入编码 |
| L1 | 规格书层 | 三维度穷举（十大域+参数轴+状态机） | 不允许编码 |
| L2 | 架构层 | Result模式/统一中间件/降级链 | 先补基础设施 |
| L3 | 编码层 | 异常优先提示词+填空式骨架 | 代码返工 |
| L4 | 测试层 | 六层框架（用例→执行→异常→覆盖→混沌→报告） | 补充用例重测 |
| L5 | 审查层 | Ralph模式（3轮+Stall+Memory+Receipt）+ 🛡️12项审计 | 不通过审查 |
| L6 | 反馈闭环 | 四阶段：实时记录→定期分析→改进→预防 | 持续加固 |

## 三、九层防御详解

### L0-R 深度调研（前置防线）

**5方向 × 4问 = 20步引导**

| 方向 | 核心产出 | 喂给后续 |
|------|---------|---------|
| ① 同类产品 | 用户痛点清单 | → 需求维度三·失败场景 |
| ② 技术方案 | 方案对比+选定理由 | → 设计阶段 |
| ③ 标准规范 | 合规要求清单（有URL） | → 需求维度四·非功能需求 |
| ④ 失败案例 | 已知坑+事故复盘 | → 需求失败场景 + 测试混沌注入 |
| ⑤ 参考实现 | 开源/官方/现有代码参考 | → 设计·异常架构 |

**调研质量门（6项全过才允许写需求）：** R1同类产品 / R2技术方案 / R3标准规范 / R4失败案例 / R5参考实现 / 调研-需求映射

### L0a 需求引导（七维模型）

**28步引导，从"拍脑袋"到"系统化"**

| 维度 | 引导目标 | 关键检查 |
|------|---------|---------|
| ① 用户故事 | 谁+做什么+为什么 | 角色具体到画像 |
| ② 验收条件 | Given-When-Then格式 | 异常AC ≥ 正向AC |
| ③ 失败场景 | 三维度穷举 | 十大域逐个过+参数8问+状态机 |
| ④ 非功能需求 | 具体数值+验证方式 | 性能P95/安全覆盖/故障恢复 |
| ⑤ 接口契约 | 请求+响应+错误码+降级 | 每个参数有校验规则 |
| ⑥ 数据模型 | 字段+约束+索引+迁移 | 查询字段有索引 |
| ⑦ 依赖地图 | 外部+内部+降级策略 | 每个依赖挂了怎么办 |

**需求质量门（8项全过才允许进入设计）：** D1用户故事 / D2验收条件 / D3失败场景穷举 / D4非功能需求 / D5接口契约 / D6数据模型 / D7依赖地图 / 整体一致性

### L0b 设计引导（五层防御）

**20步引导，让异常处理"无法跳过"**

| 设计层 | 核心产出 | 关键检查 |
|--------|---------|---------|
| ① 异常架构 | 全局中间件+降级链 | 中间件存在？降级链4级？每个调用有超时？ |
| ② API规范 | 统一响应格式+错误码体系 | AI只需填空不需发明 |
| ③ DB设计 | 事务+索引+迁移 | 事务可回滚？迁移向后兼容？ |
| ④ 安全设计 | 认证+授权+校验+限流 | token生命周期？数据级隔离？ |
| ⑤ 测试策略 | 分层+覆盖率+来源映射 | 用例从哪来？CI怎么自动化？ |

**设计质量门（6项全过才允许进入编码）：** S1异常架构 / S2 API规范 / S3 DB设计 / S4安全设计 / S5测试策略 / 需求-设计一致性

### L1 规格书层（三维度穷举）

**不靠"灵感"想几个，靠"工具"系统化穷举**

| 维度 | 方法 | 穷举公式 | 预期场景数 |
|------|------|---------|-----------|
| 维度一·十大域 | 对10个失败域逐个检查 | 每域2-3个 × 10域 | 20-30个 |
| 维度二·参数轴 | 每个参数问8个问题 | 参数数 × 8 | 24-40个 |
| 维度三·状态机 | 列出所有非法状态转换 | 状态数×(状态数-1)-合法转换 | 5-15个 |
| **合并去重** | 三维度结果合并 | — | **15-50个** |

### L2 架构层（让异常无法跳过）

| 模式 | AI能偷懒吗？ | 效果 |
|------|-------------|------|
| 普通函数返回值 | ✅ 能，返回null不报错 | 异常被静默吞掉 |
| **Result/Either模式** | ❌ 不能，类型系统强制处理 | 不处理Error变体编译报错 |
| try-catch | ✅ 能，catch里写console.log | 异常被"假处理" |
| **统一异常中间件** | ❌ 不能，异常自动冒泡 | AI不需要手写catch |

### L3 编码层（异常优先）

**核心策略：先说异常，后说正向。利用AI注意力衰减。**

```
第一步：列出所有失败场景（至少5个）
第二步：为每个失败场景定义处理策略
第三步：先编写所有异常处理代码
第四步：最后才编写正向流程代码
```

**三条铁律：**
- 禁止空catch块
- 禁止catch中仅console.log
- 每个catch必须有明确的恢复策略或向上传播

### L4 测试层（六层自动化测试框架）

| 层 | 目标 | 核心手段 |
|----|------|---------|
| L1 用例生成 | 从规格书自动派生测试用例 | 失败场景→测试用例映射 |
| L2 自动执行 | CI/CD管线一键跑全部 | `run-all-tests.sh` + `coverage-check.js` |
| L3 异常路径 | 测"不该发生的事" | 断言四要素（状态码+错误信息+降级行为+副作用） |
| L4 覆盖率验证 | 证明"测够了" | 行>80% + 分支>80% + 异常分支>80% |
| L5 混沌注入 | 模拟"世界崩溃" | DB断连/Redis不可用/第三方超时/磁盘满 |
| L6 测试报告 | 结构化输出 | 覆盖率矩阵+未覆盖代码清单+混沌结果 |

### L5 审查层（Ralph模式 + 🛡️12项审计）

#### 🛡️ 异常处理专项审计（必做）

**A. 外部调用覆盖（4项）**
- [ ] 所有网络请求是否有try-catch？
- [ ] 所有数据库操作是否有事务和异常处理？
- [ ] 所有文件/IO操作是否有异常处理？
- [ ] 所有第三方API调用是否有异常处理+超时？

**B. catch块质量（4项）**
- [ ] 是否有空catch块？（🔴阻塞）
- [ ] 是否有仅console.log的catch？（🔴阻塞）
- [ ] 是否有catch后return null/undefined/default？（🔴阻塞）
- [ ] 每个catch是否有恢复策略或向上传播？

**C. 降级与恢复（2项）**
- [ ] 是否有降级策略（而非直接崩溃/500）？
- [ ] 可重试异常是否有重试机制（带指数退避）？

**D. 上下文与体验（2项）**
- [ ] 异常日志是否包含调试上下文？
- [ ] 用户看到的错误提示是否友好？

#### 🔄 Ralph 审查模式（循环控制）

| 控制点 | 机制 | 阈值 |
|--------|------|------|
| **轮次限制** | 最多3轮审查 | 超过→强制人工介入 |
| **Stall检测** | 连续2轮问题数相同 | 触发→停止循环 |
| **重复问题检测** | 同file:line问题第2轮仍存在 | 触发→标记"敷衍修复" |
| **Reviewer Memory** | 跨轮次怀疑追踪 | 上轮怀疑→本轮必须验证 |
| **Falsifiable Receipt** | 每条意见有file:line+修复标准+验证方式 | 模糊意见→返工 |

**Audit-Ledger 文件系统交接：**

```
.workbuddy/audit-ledger/
├── round-1/
│   ├── deliverable.md          # 编码者交付物
│   ├── review-report.md        # 审查者报告
│   ├── reviewer-memory.md      # 审查者私有记忆（编码者不可读）
│   └── fix-report.md           # 编码者修复报告
├── round-2/
│   ├── ...
├── round-3/
│   ├── ...
└── final/
    └── approved-receipt.md     # 审查通过收据
```

### L6 反馈闭环层（弯路沉淀与持续改进）

**四阶段闭环：**

```
编码调试 → 实时记录弯路 → 定期分析模式 → 改进skill/SOP → 下次编码时自动预防
   ↑                                                              |
   └──────────────── 预防规则注入 ← 改进落地 ←────────────────────┘
```

**6大弯路分类：**

| 类型 | 代号 | 典型场景 | 改进到哪个文件 |
|------|------|---------|-------------|
| 技术选型弯路 | T-SELECT | 选了库A踩坑后换库B | `requirements-design-sop.md` |
| 调试方向弯路 | D-DIRECT | 以为是前端bug实际是后端 | `coding-sop.md` |
| 实现路径弯路 | I-PATH | 先方案X后改方案Y | `coding-sop.md` |
| 异常处理弯路 | E-MISS | 漏处理某异常场景 | `templates.md` |
| 测试弯路 | T-WRONG | 测试本身有bug | `testing-sop.md` |
| 架构弯路 | A-DESIGN | 设计漏了某约束 | `requirements-design-sop.md` |

## 四、关键衔接：6条追溯链

| 追溯链 | 路径 | 说明 |
|--------|------|------|
| 调研→需求→设计 | 调研"失败案例" → 需求"失败场景清单" → 设计"异常处理架构" | 别人的坑就是你的预防清单 |
| 调研→安全→编码 | 调研"标准规范" → 需求"非功能需求" → 设计"安全设计" → 编码"安全实现" | 合规不是选做 |
| 调研→API→测试 | 调研"技术方案" → 需求"接口契约" → 设计"API规范" → 编码"参数校验" → 测试"参数轴测试" | 契约定义一次，全链路复用 |
| 调研→架构→审查 | 调研"参考实现" → 设计"异常处理架构" → 编码"实现模式" → 审查"对比参考" | 让AI"有样学样" |
| 需求→状态→测试 | 需求"状态机" → 设计"状态机设计" → 编码"状态校验" → 测试"非法转换测试" | 有状态必画状态机 |
| 弯路→改进→预防 | 弯路"E-MISS" → 改进"templates.md" → 预防"编码前加载" | 每条弯路加固一层防御 |

## 五、使用流程：从调研到交付

### 阶段一：编码前（L0-R ~ L0b）

1. **启动调研**：对功能执行5方向深度调研（WebSearch/WebFetch/Grep/Glob）
2. **通过调研质量门**（6项）→ 进入需求
3. **执行七维需求引导**（28步）→ 产出需求规格文档
4. **通过需求质量门**（8项）→ 进入设计
5. **执行五层设计引导**（20步）→ 产出技术设计文档
6. **通过设计质量门**（6项）→ 允许编码

### 阶段二：编码中（L1 ~ L3）

7. **编写规格书**：三维度穷举失败场景，定义异常AC
8. **确认架构**：Result模式/中间件/降级链就位
9. **编码**：使用"异常优先"提示词模板，先异常后正向
10. **编码后自检**：外部调用/catch质量/降级策略/上下文日志
11. **弯路记录**：编码中走的弯路实时记录到 `lessons-learned.md`

### 阶段三：测试（L4）

12. **用例生成**：从规格书失败场景→测试用例映射
13. **自动执行**：`run-all-tests.sh` 一键跑全部
14. **异常路径**：断言四要素逐个验证
15. **覆盖率验证**：`coverage-check.js` 80%阈值卡关
16. **混沌注入**：模拟DB断连/Redis不可用/第三方超时
17. **测试报告**：结构化输出（覆盖率矩阵+未覆盖清单+混沌结果）

### 阶段四：审查（L5）

18. **编码者交付**：写入 `audit-ledger/round-1/deliverable.md`
19. **审查者启动**：读取 deliverable + 执行审查
20. **审查者输出**：`review-report.md` + `reviewer-memory.md`
21. **判定**：通过（🔴=0, 🟡≤3）/ 不通过 / Stall
22. **编码者修复**：读取 review-report → 逐条修复 → `fix-report.md`
23. **循环**：最多3轮，Stall触发则人工介入
24. **审查通过**：生成 `approved-receipt.md`

### 阶段五：弯路闭环（L6）

25. **定期分析**：聚类弯路→Top3高频→重复模式→改进优先级
26. **改进闭环**：高频弯路→更新对应skill/SOP→标注来源弯路编号
27. **预防注入**：下次编码前自动加载历史弯路检查

### 步骤5：L1 规格书

```markdown
## 功能点：用户登录

### 正向流程
1. 用户输入手机号+验证码 → 校验通过 → 返回token

### 失败场景清单
| # | 场景 | 异常类型 | 处理方式 | 用户感知 | HTTP |
|---|------|---------|---------|---------|------|
| F1 | 验证码错误 | AuthError | 返回401+错误码 | "验证码错误，还剩X次" | 401 |
| F2 | 手机号格式无效 | ValidationError | 前端拦截+后端二次校验 | "请输入正确手机号" | 400 |
| F3 | 验证码超时 | TimeoutError | 要求重新获取 | "验证码已过期" | 400 |
| F4 | 连续失败5次 | RateLimitError | 锁定15分钟 | "账号已锁定" | 429 |
| F5 | 网络超时 | NetworkError | 自动重试1次 | "网络不佳，请重试" | 503 |

### 验收标准
- AC-1（正向）：正确手机号+验证码 → 200 + token ✅
- AC-2（异常）：验证码错误 → 401 + 错误码1001 ✅
- AC-3（异常）：连续5次失败 → 429 + 锁定状态 ✅
```
