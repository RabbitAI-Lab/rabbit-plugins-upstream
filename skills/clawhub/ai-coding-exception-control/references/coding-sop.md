# 编码SOP — 异常处理控制流程

> 本SOP是 `ai-coding-exception-control` skill的执行文档。
> 每次编码任务（新功能/接口/模块）必须按此SOP执行，不可跳过任何阶段。

---

## 总览

```
阶段零：深度调研→需求与设计引导（L0）→ 开发前（L1规格书）→ 架构确认（L2）→ 编码中（L3提示词）→ 编码后测试（L4）→ 交付前审查（L5）→ 弯路记录与改进（L6）
```

| 阶段 | 检查项数 | 负责人 | 产出物 |
|------|---------|--------|--------|
| 深度调研 | 6项 | 调研员 | 调研报告+参考清单 |
| 需求与设计 | 14项（8+6） | 需求/架构师 | 需求规格文档+技术设计文档 |
| 开发前 | 8项 | 规格书编写者 | 失败场景穷举清单（三维度交叉+调研坑） |
| 架构确认 | 4项 | 架构师 | 异常中间件/Result模式确认 |
| 编码中 | 6项+弯路记录 | 编码专家 | 异常优先的代码+弯路记录 |
| 编码后 | 10项 | 测试专家 | 异常用例≥正向用例 |
| 交付前 | 12项 | 审查专家 | 异常审计报告 |
| 弯路改进 | 4项 | 编码/架构师 | 弯路分析报告+skill/SOP改进 |

## 阶段零：深度调研→需求与设计检查（L0 需求与设计层）

**目标：在写规格书之前，先深度调研行业最佳实践，再用引导式流程把需求和设计想清楚。调研阶段的每一分投入，会在需求和设计阶段产生2倍回报，在后续编码测试阶段产生4倍回报。**

> **完整引导SOP见 `requirements-design-sop.md`**（深度调研5方向20步+七维需求引导28步+五层设计引导20步+三道质量门20项检查）

### 核心理念

**调研先行，引导式跟进。** 先用WebSearch/WebFetch/Grep/Glob搞清楚"别人怎么做的、最好的实践是什么、有什么坑"，再用引导式流程把需求和设计想清楚。不是空模板，是wizard式一步步引导。

### 调研质量门（6项，通过后才允许进入需求阶段）

- [ ] **R1 同类产品**：至少3个同类产品已调研？用户痛点已提取并预映射到失败场景？
- [ ] **R2 技术方案**：至少2种方案已对比？选定方案有明确理由？最新版本最佳实践已确认？
- [ ] **R3 标准规范**：行业标准/安全合规要求已明确？每条已映射到需求/设计维度？有URL来源？
- [ ] **R4 失败案例**：至少3个已知坑/反模式已收集？每个有来源+预防措施+失败场景映射？事故复盘已提取混沌测试场景？
- [ ] **R5 参考实现**：至少1个高质量参考已收集？异常处理亮点已分析？现有代码库已搜索？
- [ ] **调研-需求映射**：调研结果已标注"喂给哪个维度/层"，形成明确的映射关系？

### 需求质量门（8项，通过后才允许进入设计阶段）

- [ ] **D1 用户故事**：包含"谁+做什么+为什么"三要素？角色具体到画像？
- [ ] **D2 验收条件**：每条AC是Given-When-Then格式？异常AC >= 正向AC？
- [ ] **D3 失败场景**：三维度穷举走完？合并去重后 >= 5个？每个标注了优先级？
- [ ] **D4 非功能需求**：性能有具体数值？安全覆盖传输/校验/存储？每个指标有验证方式？
- [ ] **D5 接口契约**：每个参数有校验规则？每个失败场景有错误码？降级场景有独立格式？
- [ ] **D6 数据模型**：每个字段有约束？查询字段有索引？有迁移策略？
- [ ] **D7 依赖地图**：每个外部依赖有降级策略？内部模块有fail策略？
- [ ] **整体一致性**：失败场景清单与验收条件、接口契约、测试策略一一对应？

### 设计质量门（6项，通过后才允许进入编码阶段）

- [ ] **S1 异常架构**：全局异常中间件已规划？降级链定义了4级？每个外部调用有超时+重试策略？
- [ ] **S2 API规范**：统一响应格式已定义？错误码体系与需求一致？分页+认证已定义？
- [ ] **S3 DB设计**：事务策略已定义？索引策略已定义？迁移策略含回滚？
- [ ] **S4 安全设计**：认证方案含token生命周期？授权方案含数据级隔离？输入校验前后端分离？限流分级？
- [ ] **S5 测试策略**：测试分层已定义？覆盖率目标已定义？用例来源有映射？CI/CD已规划？
- [ ] **需求-设计一致性**：设计中的异常处理方案与需求失败场景一一对应？

### 七维需求模型速查

| 维度 | 引导目标 | 核心问题 | 调研输入 |
|------|---------|---------|---------|
| ① 用户故事 | 谁+做什么+为什么 | 服务对象具体到画像？ | ← R1同类产品用户画像 |
| ② 验收条件 | Given-When-Then | 异常AC≥正向AC？ | ← R1用户痛点 |
| ③ 失败场景 | 三维度穷举+经验维度 | 十大域+参数轴+状态机+调研坑走完？ | ← R4已知坑/反模式 |
| ④ 非功能需求 | 具体数值+验证方式 | 性能P95？安全覆盖？ | ← R3标准规范 |
| ⑤ 接口契约 | 请求+响应+错误码+降级 | 每个失败场景有错误码？ | ← R2技术方案 |
| ⑥ 数据模型 | 字段+约束+索引+迁移 | 有迁移策略？ | ← R5参考实现 |
| ⑦ 依赖地图 | 外部+内部+降级策略 | 每个依赖挂了怎么办？ | ← R2/R4降级模式 |

### 五层设计防御速查

| 设计层 | 引导目标 | 核心问题 | 调研输入 |
|--------|---------|---------|---------|
| ① 异常架构 | 框架兜底 | 降级链4级？超时+重试？ | ← R5参考实现的异常处理 |
| ② API规范 | 统一格式 | 错误码体系复用？ | ← R3行业标准 |
| ③ DB设计 | 事务+索引+迁移 | 迁移可回滚？ | ← R5参考实现 |
| ④ 安全设计 | 认证+授权+校验+限流 | 数据级隔离？限流分级？ | ← R3安全合规要求 |
| ⑤ 测试策略 | 分层+覆盖率+来源映射 | 用例从哪来？ | ← R4事故复盘→混沌场景 |

### 判定标准
- 调研质量门任一项未通过 → **不允许进入需求阶段**，回到对应调研方向补充
- 需求质量门任一项未通过 → **不允许进入设计阶段**，回到对应维度补充
- 设计质量门任一项未通过 → **不允许进入编码阶段**，回到对应设计层补充
- 某维度不适用 → 必须说明原因（不允许"不需要"三个字打发）

## 阶段一：开发前检查清单（L1 规格书层）

**目标：在写任何代码之前，先用三维度穷举法把异常场景定义清楚。**

> **穷举原则：不靠"灵感"想几个，靠"工具"穷举。** 三维度交叉 = 十大域 + 参数轴 + 状态机。

### 检查清单

- [ ] **历史弯路检查**：已查看 `lessons-learned.md` 最近10条弯路？已确认本次功能可能遇到哪些同类弯路？相关改进措施已落地到当前流程？
- [ ] **失败场景清单表**：每个功能点是否包含"失败场景清单"表格？
- [ ] **维度一·十大域**：是否对10个失败域逐个过了一遍？（每个域至少1-2个场景，**不允许跳过任何域**——即使认为"不适用"也必须说明原因）
- [ ] **维度二·参数轴**：是否对每个输入参数问了8个问题？（缺失/空值/格式错/类型错/超长/特殊字符/注入/边界值——**每个参数必须问全8问，不允许省略任何一问**）
- [ ] **维度三·状态机**：有状态流转的功能是否列出了所有非法转换？（无状态流转的功能需标注"不适用"并说明原因）
- [ ] **场景数量**：合并去重后失败场景数量 ≥ 5个？（简单接口：≥5个；复杂接口：≥15个；核心支付/安全接口：≥20个）
- [ ] **场景具体性**：每个场景是否具体到异常类型？（禁止"其他错误""未知异常"等笼统描述；禁止"等""..."等省略表述）
- [ ] **异常AC**：验收标准中异常AC数量 ≥ 正向AC数量？（**硬性约束：异常用例不得少于正向用例**）
- [ ] **用户感知**：每个失败场景是否定义了用户看到什么提示？（禁止直接返回原始错误对象/堆栈/内部路径给前端）

### 三维度穷举法

> 完整模板见 `templates.md` 第7节"失败场景穷举模板（三维度交叉）"

| 维度 | 方法 | 穷举公式 | 预期场景数 |
|------|------|---------|-----------|
| 维度一·十大域 | 对10个失败域逐个检查 | 每域2-3个 × 10域 | 20-30个 |
| 维度二·参数轴 | 每个参数问8个问题 | 参数数 × 8 | 24-40个 |
| 维度三·状态机 | 列出所有非法状态转换 | 状态数×(状态数-1) - 合法转换 | 5-15个 |
| **合并去重** | 三维度结果合并 | 去重后取唯一项 | **15-50个** |

### 十大失败域速查

| # | 域 | 核心问题 |
|---|-----|---------|
| 1 | 输入层 | 每个参数的缺失/空值/格式/类型/超长/特殊字符？ |
| 2 | 认证授权 | 无token/过期/伪造/权限不足/越权？ |
| 3 | 网络通信 | 超时/断开/部分响应/DNS失败？ |
| 4 | 数据层 | 不存在/重复键/约束违反/死锁/事务失败？ |
| 5 | 并发冲突 | 同时提交/重复提交/并发修改/连接池耗尽？ |
| 6 | 外部依赖 | 第三方宕机/超时/返回错误/格式变了？ |
| 7 | 资源耗尽 | 内存/磁盘/连接池/限流？ |
| 8 | 业务逻辑 | 状态非法/规则违反/配额超限/数据不一致？ |
| 9 | 安全攻击 | SQL注入/XSS/越权/暴力枚举/重放攻击？ |
| 10 | 环境配置 | 环境变量缺失/配置错/端口冲突/版本不兼容？ |

### 模板

```markdown
### 失败场景清单（三维度穷举，合并去重后）
| # | 来源维度 | 场景 | 异常类型 | 处理方式 | 用户感知 | HTTP状态码 | 优先级 |
|---|---------|------|---------|---------|---------|-----------|--------|
| F1 | D9安全 | SQL注入 | SecurityError | 清洗+400 | "输入不合法" | 400 | P0 |
| F2 | D2认证 | token伪造 | AuthError | 401 | "请重新登录" | 401 | P0 |
| F3 | D5并发 | 重复提交 | ConflictError | 幂等返回 | 无感知 | 200 | P0 |
| F4 | D6外部 | AI服务超时 | TimeoutError | 降级 | "分析中" | 200 | P1 |
| ... | ... | ... | ... | ... | ... | ... | ... |

### 验收标准
- AC-1（正向）：[正向验收条件]
- AC-2（异常）：[异常验收条件，对应F1]
- 异常AC数量 >= 正向AC数量
```

### AI穷举指令

```
请为接口 [HTTP方法 + 路径] 执行失败场景穷举，按三维度交叉：
1. 十大域：逐个检查10个失败域
2. 参数轴：每个参数问8个问题
3. 状态机：列出所有非法转换
输出：三维度分别列出 → 合并去重 → 按P0/P1/P2/P3标注优先级
（完整指令模板见 templates.md 第7.5节）
```

### 判定标准

> **本阶段为质量门硬约束：任一检查项未通过，不允许进入编码阶段。**

| 检查项 | 不通过标准 | 不通过后果 |
|--------|-----------|-----------|
| 十大域覆盖 | 跳过任何域且无合理说明 | 退回补充，逐个域重新检查 |
| 参数轴8问 | 任一参数未问全8个问题 | 退回补充，对该参数重新穷举 |
| 状态机 | 有状态流转但未列非法转换 | 退回补充，列出所有非法转换 |
| **场景数量** | 简单接口<5 / 复杂接口<15 / 核心接口<20 | **补充场景后重新检查** |
| 场景具体性 | 存在"其他错误""未知异常"等笼统描述 | 退回细化，每个场景具体到异常类型+HTTP状态码+用户提示 |
| 异常AC数量 | 异常AC < 正向AC | 补充异常验收条件 |
| 用户感知 | 任一失败场景未定义用户提示 | 补充用户感知列 |

- **总判定**：任一检查项未通过 → **不允许进入编码阶段**
- **失败场景数量 < 5**（简单接口）或 **< 15**（复杂接口） → **补充场景后重新检查**

## 阶段二：架构确认检查清单（L2 架构层）

**目标：确认异常处理基础设施已就位，让AI"想偷懒都做不到"。**

### 检查清单

- [ ] **统一异常中间件**：是否已有全局异常处理中间件？（AI只需抛异常，中间件兜底）
- [ ] **超时控制**：所有外部调用（DB/HTTP/Redis/第三方）是否已设置超时？
- [ ] **重试机制**：可重试异常（网络/超时/死锁）是否已有重试+指数退避机制？
- [ ] **降级策略**：关键链路是否有降级方案？（而非直接500崩溃）

### 架构约束参考
- Result/Either模式：函数返回类型强制包含错误通道
- 熔断器：失败超阈值自动熔断
- 幂等设计：重试不会产生副作用

### 判定标准
- 基础设施缺失 → 先补基础设施，再写业务代码

## 阶段三：编码中检查清单（L3 提示词层）

**目标：用"异常优先"策略对抗AI的偷懒本能。**

### 检查清单

- [ ] **异常优先顺序**：是否先写异常处理代码，后写正向流程？
- [ ] **失败场景覆盖**：规格书中的每个失败场景是否都有对应代码实现？
- [ ] **catch块质量**：每个catch是否有恢复策略或向上传播？（禁止空catch、禁止仅console.log）
- [ ] **异常日志**：是否包含请求参数、用户ID、时间戳、错误堆栈？
- [ ] **用户提示**：错误提示是否友好？（不暴露SQL/堆栈/内部路径）
- [ ] **资源释放**：异常时是否正确释放资源？（连接/文件句柄在finally中关闭）

### 编码指令模板

```
请实现[功能名称]，必须按以下顺序：
第一步：列出所有失败场景（≥5个）
第二步：为每个失败场景定义处理策略
第三步：先编写所有异常处理代码
第四步：最后才编写正向流程代码

约束：
- 禁止空catch块
- 禁止catch中仅console.log
- 每个catch必须有恢复策略或向上传播
- 异常日志包含：请求参数、用户ID、时间戳、错误堆栈
- 错误提示对用户友好，不暴露技术细节
```

### 三条铁律（不可违反）
1. **异常优先**：先列失败场景 → 先写异常代码 → 最后写正向
2. **禁止假处理**：空catch = 没处理；console.log = 没处理；return null = 没处理
3. **外部调用必包**：网络/DB/文件/第三方API → 必须try-catch + 超时

### 判定标准
- 任一铁律违反 → **代码不通过，返工**

### 弯路实时记录（编码中触发）

> **完整闭环SOP见 `lessons-feedback-loop.md`**

编码/调试过程中走了弯路时，必须立即记录到 `.workbuddy/memory/lessons-learned.md`：

- [ ] **弯路识别**：回顾编码/调试过程，识别走过的弯路（至少1条，除非真的全程顺利）

- [ ] **根因分析**：必须选一个根因类型（知识盲区/工具误用/流程缺失/AI偷懒/信息不全），不允许"粗心"
- [ ] **预防措施**：必须是具体的检查项或规则，不允许"注意"

## 阶段四：编码后测试检查清单（L4 测试层）

**目标：用测试倒逼异常处理——异常没处理，测试就过不了。**

> **完整测试SOP见 `testing-sop.md`**（六层框架30+项检查，含用例生成指令、一键测试脚本、异常用例模板、混沌注入矩阵、覆盖率验证、结构化报告）。

### AI全量自动化测试六层框架

| 层 | 检查项 | 不通过则 |
|----|--------|---------|
| L1 用例生成 | 失败场景映射+异常≥正向+边界枚举+安全用例+并发用例 | 不允许开始测试 |
| L2 自动执行 | 单元测试命令+API测试脚本+一键全量脚本+覆盖率阈值 | 补全自动脚本 |
| L3 异常路径 | 每个失败场景有测试+断言四要素+mock质量+测试隔离+负面测试 | 补充用例 |
| L4 覆盖率验证 | 行覆盖>80%+异常分支>80%+异常≥正向+未覆盖路径分析 | 补全异常分支 |
| L5 混沌注入 | 网络故障+依赖故障+资源耗尽+降级验证 | 补全降级逻辑 |
| L6 测试报告 | 用例执行结果+覆盖率矩阵+未覆盖清单+混沌结果+结论判定 | 整体不通过 |

### L4阶段检查清单（编码后必查）

- [ ] **异常用例数量**：异常测试用例数量 ≥ 正向用例？
- [ ] **场景覆盖**：规格书中的每个失败场景是否都有对应测试用例？
- [ ] **边界和安全用例**：是否包含空值/极值/SQL注入/XSS/伪造token测试？
- [ ] **混沌注入**：是否mock了网络失败、DB断连、超时等异常场景？
- [ ] **分支覆盖**：异常分支覆盖率 > 80%？
- [ ] **红绿循环**：异常测试是否先红（失败）→ 实现后转绿（通过）？
- [ ] **断言四要素**：每个异常测试是否验证了 ①状态码/错误码 ②错误信息 ③降级行为 ④副作用？
- [ ] **技术细节泄露**：异常响应是否验证了不暴露SQL/堆栈/内部路径？
- [ ] **一键测试脚本**：是否有 `run-all-tests.sh` 可一键执行全部测试？
- [ ] **结构化报告**：测试报告是否包含覆盖率矩阵+未覆盖代码清单+结论判定？

### 测试指令模板

```
请为[功能名称]编写测试：
1. 异常用例数量 >= 正向用例
2. 覆盖以下场景（必须全部通过）：
   - [F1]: 期望返回 [错误码]
   - [F2]: 期望触发 [降级策略]
   - [F3]: 期望 [重试] 后成功
3. 每个异常用例必须验证四要素：状态码 + 错误信息 + 降级行为 + 副作用
4. 混沌注入：mock DB断连/Redis不可用/第三方API超时，验证降级行为
5. 运行测试，异常用例失败则先修复异常处理代码
6. 报告异常分支覆盖率，目标 > 80%
```

### 判定标准
- 异常用例不足 → 补充用例后重新测试
- 异常分支覆盖率 < 80% → 补全异常分支后重新测试
- 混沌测试中系统崩溃 → 修复降级逻辑后重新测试
- 断言不全（只验证状态码）→ 补全四要素断言

## 阶段五：交付前审查检查清单（L5 审查层）

**目标：用第二个AI角色专做异常审计，找第一个AI写的代码中的异常漏洞。**

### 12项异常审计清单

**A. 外部调用覆盖（4项）**
- [ ] 所有网络请求是否有try-catch？
- [ ] 所有数据库操作是否有事务和异常处理？
- [ ] 所有文件/IO操作是否有异常处理？
- [ ] 所有第三方API调用是否有异常处理+超时？

**B. catch块质量（4项）**
- [ ] 是否有空catch块？（🔴阻塞）
- [ ] 是否有仅console.log的catch？（🔴阻塞）
- [ ] 是否有catch后return null/undefined/default？（🔴阻塞，静默吞异常）
- [ ] 每个catch是否有恢复策略或向上传播？

**C. 降级与恢复（2项）**
- [ ] 是否有降级策略（而非直接崩溃/500）？
- [ ] 可重试异常是否有重试机制（带指数退避、最大次数）？

**D. 上下文与体验（2项）**
- [ ] 异常日志是否包含调试上下文（请求参数、用户ID、时间戳、错误堆栈）？
- [ ] 用户看到的错误提示是否友好（非SQL/堆栈/内部路径等技术细节）？

### 审计判定标准

| 结果 | 判定 | 动作 |
|------|------|------|
| 🔴阻塞项 > 0 | **不通过** | 必须修复后重新审查 |
| 🟡建议项 > 3 | **有条件通过** | 列出修复计划后可合并，下个PR必须修 |
| 仅💭小改进 | **通过** | 建议改进，不阻塞合并 |

### 审计员提示词

```
你是一个严格的异常处理审计员。请审查以下代码，仅关注异常处理：
1. 找出所有缺少异常处理的外部调用
2. 找出所有"假处理"的catch块（空catch、仅console.log、仅return null）
3. 找出所有可能导致崩溃的未处理路径
4. 列出缺失的异常场景

输出格式：
- 🔴严重：[文件:行号] 问题描述 → 修复建议
- 🟡一般：[文件:行号] 问题描述 → 修复建议
```

## 阶段六：弯路定期分析与改进（L6 反馈闭环层）

**目标：把弯路变成资产——记录→分析→改进→预防，让同样的弯路不再走第二次。**

> **完整闭环SOP见 `lessons-feedback-loop.md`**（四阶段：实时记录+定期分析+改进闭环+预防注入）
> **分析报告模板见 `templates.md` 第11.3节**

### 触发时机

- 每完成一个功能模块后
- 每周/每两周
- 里程碑节点
- 弯路累计≥10条时

### 检查清单

- [ ] **弯路聚类**：按类型和根因聚类，统计各类占比和总浪费时长
- [ ] **Top3高频识别**：找出出现次数最多的3类弯路，分析共同根因
- [ ] **重复模式检查**：同一类弯路出现≥3次 → 说明现有skill/SOP有系统性漏洞
- [ ] **改进落地**：每条高频弯路必须映射到具体skill/SOP文件的改进（标注来源弯路编号）
- [ ] **改进验证**：已改进的项目在下次编码时验证效果（✅有效/⚠️部分有效/❌无效）

### 改进映射

| 弯路类型 | 改进到哪个文件 | 改进方式 |
|---------|-------------|---------|
| T-SELECT | `requirements-design-sop.md` 调研方向② | 增加排除清单/风险标注 |
| D-DIRECT | `coding-sop.md` 阶段三 | 增加快速定位检查项 |
| I-PATH | `coding-sop.md` 阶段一 | 增加"方案对比"检查步骤 |
| E-MISS | `templates.md` 第7节 | 增加到"经验维度"失败场景 |
| T-WRONG | `testing-sop.md` L3层 | 增加测试质量检查项 |
| A-DESIGN | `requirements-design-sop.md` 设计阶段 | 增加设计质量门检查项 |

### 判定标准
- 弯路记录为空且编码过程非全顺利 → **补记弯路**
- 高频弯路（≥3次）无改进措施 → **必须立即改进对应skill/SOP**
- 改进验证为❌无效 → **换改进方案，重新落地**

## 教训来源

本SOP基于真实项目开发实践总结，核心教训：

1. **AI编码天然偏科** — 只写happy path，异常处理敷衍（训练数据偏差+上下文压缩）
2. **catch{}静默吞没是项目级问题** — 多个模块系统性存在，非个别bug
3. **事后审查已经晚了** — 代码写完再修异常处理，成本极高
4. **一次性投入永久收益** — L1模板+L2中间件，搭一次所有功能受益
5. **不固化到skill就等于没做** — 下次专家团队该偷懒还是偷懒
6. **弯路不记录就白走了** — 走过的弯路是资产，记录→分析→改进→预防，让同样的弯路不再走第二次
