# 弯路沉淀与持续改进闭环SOP

> 本SOP是 `ai-coding-exception-control` skill的反馈闭环文档。
> **编码调试中走过的每一条弯路都是资产——不记录就白走了，不分析就还会再走，不改进就永远在原地打转。**

---

## 核心理念

**静态的教训沉淀（写死在skill里的5条）解决不了动态的问题——每次开发都会遇到新的坑。**

需要一个活的、持续运转的闭环：

```
编码调试 → 实时记录弯路 → 定期分析模式 → 改进skill/SOP → 下次编码时自动预防
   ↑                                                              |
   └──────────────── 预防规则注入 ← 改进落地 ←────────────────────┘
```

**AI同样会走弯路**（选错方案/调试方向错误/实现路径绕路/异常遗漏），而且AI走弯路的特点是：
- **不自知**：AI不会主动说"我刚才走弯路了"
- **重复走**：同一个坑不同会话里反复踩
- **不记录**：弯路信息在上下文压缩后丢失
- **不学习**：除非写进skill，否则下次还是一样

所以必须用机制倒逼：**记录→分析→改进→预防，四阶段缺一不可。**

## 本SOP的异常处理声明

> **教人游泳的教练自己必须会游泳。** 本SOP教人记录和分析弯路，自身必须处理所有可能的异常场景。

### 本SOP可能遇到的异常场景

| 场景 | 异常类型 | 处理方式 | 降级策略 |
|------|---------|---------|---------|
| lessons-learned.md 文件不可写 | FileSystemError | 检查权限，尝试写入临时目录，提示用户 | 降级到 stdout 输出 |
| 文件被误删或损坏 | DataLossError | 使用 Git 版本控制恢复，或从备份恢复 | 从 Git 历史恢复，重建文件 |
| 编码者声称"没有弯路" | DeceptionError | 强制至少记录1条，除非全程顺利 | 追问：真的没有？哪怕是最小的？ |
| 根因分析写"粗心" | InvalidRootCauseError | 拒绝，要求选择具体根因类型 | 提供根因选择清单 |
| 弯路编号不连续 | NumberingError | 检查是否有遗漏记录，补齐 | 自动检测连续性问题 |
| 定期分析时弯路不足10条 | InsufficientDataError | 延长分析周期，或缩小分析范围 | 按现有数量分析，标注样本不足 |
| 改进目标文件被占用 | FileLockError | 等待或选择其他时间改进 | 记录待改进项，延后执行 |
| 预防措施无法落地 | ImplementationError | 重新评估可行性，调整预防措施 | 改为更轻量的预防措施 |
| 编码前加载历史弯路时文件不存在 | FileNotFoundError | 自动创建 lessons-learned.md 骨架 | 使用默认骨架，提示用户首次记录 |
| 上下文压缩导致弯路记录丢失 | ContextLossError | 将记录写入文件系统而非依赖上下文 | 文件系统持久化 |

### 文件系统保护策略

1. **版本控制**：建议用 Git 跟踪 `lessons-learned.md`（`.workbuddy/memory/` 目录加入 Git）
2. **追加不修改**：任何工具不得修改历史记录，只追加新记录
3. **定期备份**：每周/里程碑时手动复制备份
4. **权限检查**：写入前检查目录权限，不可写时降级到 stdout 输出

## 弯路分类体系

### 6大类弯路

| 类型 | 代号 | 典型场景 | 分析价值 |
|------|------|---------|---------|
| 技术选型弯路 | T-SELECT | 选了库A，踩了一堆坑后换库B | 下次调研阶段直接排除A或标注风险 |
| 调试方向弯路 | D-DIRECT | 以为是前端bug，排查半天发现是后端返回格式变了 | 诊断方法论改进，增加快速定位检查项 |
| 实现路径弯路 | I-PATH | 先用方案X实现，review后发现方案Y更简洁，返工 | 编码前增加"方案对比"检查步骤 |
| 异常处理弯路 | E-MISS | 漏处理某个异常场景，测试/线上暴露后补 | 补充到失败场景穷举的"经验维度" |
| 测试弯路 | T-WRONG | 测试本身有bug（mock不对/断言不严），测了等于没测 | 加强测试质量检查（断言四要素） |
| 架构弯路 | A-DESIGN | 设计时没考虑某个约束（并发/性能/兼容），编码到一半返工 | 补充到设计质量门检查项 |

### 弯路严重度

| 级别 | 代号 | 定义 | 改进优先级 |
|------|------|------|-----------|
| 🔴 高 | S-HIGH | 浪费>1小时 或 导致线上问题 | 立即改进skill/SOP |
| 🟡 中 | S-MED | 浪费15分钟-1小时 | 下次分析周期内改进 |
| 🟢 低 | S-LOW | 浪费<15分钟 | 记录备查，模式出现3次再改进 |

## 阶段一：实时记录（Capture）

### 触发时机

- **调试中走了弯路后**：发现正确方向时，立即记录刚才的错误方向
- **编码完成自检时**：回顾编码过程，补记之前走的弯路
- **代码审查发现时**：审查发现的问题，如果是"编码时走过的弯路"也记录
- **测试暴露问题时**：测试发现bug，如果根因是"编码时的弯路"也记录

### 记录格式

每条弯路记录包含以下字段：

```markdown
### [日期] [弯路编号] [类型代号] [严重度]

- **功能模块**：[模块/功能名称]
- **弯路描述**：[一句话描述走了什么弯路]
- **错误尝试**：[具体做了什么错误的事，花了多长时间]
- **根因分析**：[为什么会走这个弯路？是知识盲区/工具误用/流程缺失/AI偷懒？]
- **正确方案**：[最终正确的做法是什么]
- **浪费时长**：[X分钟/X小时]
- **教训提炼**：[一句话可复用的教训]
- **预防措施**：[下次怎么避免？加到哪个skill/SOP/检查项？]
- **改进状态**：[待改进/已改进/已验证]
```

### 记录原则

1. **不追究责任**：记录是为了改进，不是为了追责。AI走的弯路也要记录
2. **具体不笼统**："调试了很久"不算记录，"以为是JWT过期，实际是Redis缓存了旧token，花了40分钟"才算
3. **根因必分析**：每条弯路必须有根因分析，不能只记现象不挖根因
4. **预防必落地**：每条弯路必须提出预防措施，且标注改进到哪个文件
5. **追加不修改**：已记录的弯路不删除、不修改（除非事实有误），只追加改进状态

### AI记录指令

```
在编码/调试过程中，如果你走了弯路（尝试了错误的方向、换了实现方案、漏处理了异常等），
必须立即记录到 lessons-learned.md，格式如下：

1. 弯路类型：[T-SELECT/D-DIRECT/I-PATH/E-MISS/T-WRONG/A-DESIGN]
2. 严重度：[S-HIGH/S-MED/S-LOW]
3. 弯路描述：[一句话]
4. 错误尝试：[具体做了什么，花了多久]
5. 根因分析：[为什么走弯路]
6. 正确方案：[最终正确做法]
7. 教训提炼：[可复用的一句话]
8. 预防措施：[加到哪个文件/检查项]

约束：
- 不允许"没有弯路"——除非真的全程顺利，否则至少记录1条
- 根因分析不允许写"粗心/疏忽"——必须挖到知识盲区/流程缺失/工具误用
- 预防措施不允许写"注意"——必须是具体的检查项或规则
```

## 阶段二：定期分析（Analyze）

### 分析时机

| 触发条件 | 分析范围 |
|---------|---------|
| 每完成一个功能模块 | 本模块的弯路 |
| 每周/每两周 | 近期所有弯路 |
| 里程碑节点 | 整个里程碑期间的弯路 |
| 弯路累计≥10条 | 全量弯路 |

### 分析流程

#### 步骤1：弯路聚类

按类型和根因聚类，找出高频模式：

```markdown
### 弯路聚类分析

| 类型 | 数量 | 占比 | 典型案例 | 根因模式 |
|------|------|------|---------|---------|
| E-MISS 异常遗漏 | X | XX% | [典型案例] | [根因模式] |
| D-DIRECT 调试方向 | X | XX% | [典型案例] | [根因模式] |
| I-PATH 实现路径 | X | XX% | [典型案例] | [根因模式] |
| ... | ... | ... | ... | ... |
```

#### 步骤2：Top3高频问题识别

找出出现次数最多的3类弯路，深入分析：

```markdown
### Top3 高频弯路

#### 高频1：[弯路类型+描述]（出现X次）
- **共同根因**：[为什么反复出现]
- **现有防御为什么没防住**：[当前skill/SOP哪里有漏洞]
- **改进建议**：[具体加到哪个文件/哪个步骤/什么检查项]
- **预期效果**：[改进后能防止多少%的此类弯路]

#### 高频2：...
#### 高频3：...
```

#### 步骤3：重复模式检查

识别"同一类弯路出现≥3次"的模式——这说明现有skill/SOP有系统性漏洞：

```markdown
### 重复模式检查

| 模式 | 首次出现 | 最近出现 | 出现次数 | 现有防御 | 防御漏洞 | 改进方案 |
|------|---------|---------|---------|---------|---------|---------|
| [模式描述] | [日期] | [日期] | X次 | [现有规则] | [为什么没防住] | [改进方案] |
```

#### 步骤4：改进优先级排序

```markdown
### 改进优先级矩阵

| 改进项 | 影响弯路数 | 实现难度 | 优先级 | 负责人 | 目标完成日期 |
|--------|-----------|---------|--------|--------|-------------|
| [改进1] | X条 | 低/中/高 | P0/P1/P2 | | |
| [改进2] | X条 | 低/中/高 | P0/P1/P2 | | |
```

## 阶段三：改进闭环（Improve）

### 改进映射表

分析结果必须映射到具体的skill/SOP改进：

| 弯路类型 | 改进到哪个文件 | 改进方式 |
|---------|-------------|---------|
| T-SELECT 技术选型 | `requirements-design-sop.md` 调研方向② | 增加排除清单/风险标注 |
| D-DIRECT 调试方向 | `coding-sop.md` 阶段三 | 增加快速定位检查项 |
| I-PATH 实现路径 | `coding-sop.md` 阶段一 | 增加"方案对比"检查步骤 |
| E-MISS 异常遗漏 | `templates.md` 第7节 | 增加到"经验维度"失败场景 |
| T-WRONG 测试错误 | `testing-sop.md` L3层 | 增加测试质量检查项 |
| A-DESIGN 架构弯路 | `requirements-design-sop.md` 设计阶段 | 增加设计质量门检查项 |

### 改进执行流程

```
1. 确定改进项 → 2. 打开目标文件 → 3. 添加检查项/规则/教训
→ 4. 标注来源（"来自弯路#LL-XXX"）→ 5. 更新弯路记录的"改进状态"为"已改进"
→ 6. 下次使用该skill/SOP时验证效果 → 7. 验证有效后标记"已验证"
```

### 改进验证

每次改进后，在下次编码时验证效果：

```markdown
### 改进验证记录

| 改进项 | 改进日期 | 首次验证日期 | 验证结果 | 备注 |
|--------|---------|------------|---------|------|
| [改进描述] | [日期] | [日期] | ✅有效/❌无效/⚠️部分有效 | [说明] |
```

- ✅有效：该类弯路不再出现
- ⚠️部分有效：出现频率降低但仍有发生，需要加强
- ❌无效：弯路照旧，需要换改进方案

## 阶段四：预防注入（Prevent）

### 编码前自动加载

在 `coding-sop.md` 阶段一（开发前检查）新增步骤：

```
- [ ] **历史弯路检查**：已查看 lessons-learned.md 最近10条弯路？
      已确认本次功能可能遇到哪些同类弯路？
      已查看相关改进是否已落地到当前skill/SOP？
```

### AI预防指令

```
在开始编码前，请执行以下预防检查：

1. 读取 lessons-learned.md，查看最近10条弯路记录
2. 识别本次功能可能遇到的同类弯路（基于功能相似性）
3. 对于每条可能遇到的弯路，确认预防措施已在当前流程中
4. 如果预防措施未生效，主动提醒并补充

输出：
- 最近10条弯路摘要
- 本次功能可能遇到的弯路清单
- 预防措施确认
```

## 与七层防御体系的关系

弯路沉淀闭环不是独立的第七层，而是**贯穿L0-L5全链路的反馈回路**：

```
L0 调研/需求/设计 ──→ 弯路记录（A-DESIGN/T-SELECT）
L1 规格书 ──→ 弯路记录（E-MISS 异常遗漏）
L2 架构 ──→ 弯路记录（A-DESIGN 架构约束遗漏）
L3 编码 ──→ 弯路记录（I-PATH/E-MISS/T-WRONG）
L4 测试 ──→ 弯路记录（T-WRONG 测试本身有问题）
L5 审查 ──→ 弯路记录（发现编码弯路）

         ↓ 定期分析 ↓

L0 ← 新增调研排除项/设计检查项
L1 ← 新增经验维度失败场景
L2 ← 新增架构约束检查项
L3 ← 新增编码检查项/铁律
L4 ← 新增测试质量检查项
L5 ← 新增审计检查项
```

**每次弯路改进，都是对七层防御中某一层的加固。**
