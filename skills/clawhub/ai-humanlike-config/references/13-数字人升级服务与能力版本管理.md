# 数字人升级服务与能力版本管理

> 配套 `08-能力清单与分级报价.md` / `07-交付可信与全链路可追溯.md` / `12-专业服务交付标准.md` / `04-业务流SOP.md`。
> 本文件解决两件事：① 把每个能力**做成带版本号的可演进单元**（我们出新能力 → 升版本）；② 把"升版"做成**持续收费的接口**——和月费、可追溯天然咬合，形成第二增长曲线。

---

## 0. 核心定位：能力要分版本，升版要收费

我们配的数字人不是"一锤子买卖的交付物"，而是**持续演进的能力体**：

- 我们研发了新能力（或显著改进了某项），对应能力的**版本号 +1**；
- 在月费期的客户，看板会标"有新版可升级"，我们发 release notes；
- 客户选择升级 → 付**升级费** → 我们实施 → 打新时间戳/哈希/指纹（连 `07`）→ 看板版本号刷新。

> 卖点话术：**"你买的不只是一个配置，是一路跟着我们进化、越用越强的数字人——新能力出来，你一键升版，不用重买。"**
> 这把一次性搭建收入，变成"搭建 + 月费 + 升版"的复利结构，且让客户**持续感知我们在投入研发**（信任感）。

---

## 1. 能力版本化模型（每个能力一个版本号）

每条能力（见 `08` 清单 #1–#14）用**语义化版本号 `MAJOR.MINOR.PATCH`** 管理：

| 变更类型 | 含义 | 版本号动作 | 是否单独收费 |
|----------|------|-----------|--------------|
| PATCH | 修复 / 微调 / 提示词优化 | x.y.Z+1 | 否（含月费养护） |
| MINOR | 显著增强（同能力更好用、加选项） | x.Y+1.0 | 否（含月费养护）或低价升级 |
| MAJOR | 新增能力 / 重大重构 / 跨代升级 | X+1.0.0 | **是（升级费）** |

**版本载体**

- **单能力版本**：每条能力自带版本号，如 `#6 安全加固 v1.2.0`、`#7 AI造AI v2.0.0`。
- **数字人整体版本**：每个交付实例有复合版本号 `DH-<客户ID>-v<maj>.<min>.<patch>`，记录"这一版由哪些能力、什么版本构成"。
- **版本基线**：首次交付记为 `v1.0.0`；每次升版按变更类型滚动。
- **版本与可追溯绑定**：每次升版都打**时间戳 + 数字指纹 + 哈希**（见 `07`），写入该客户的版本链：`客户 ID ↔ 版本 ↔ 时间戳 ↔ 哈希 ↔ 指纹`，可随时查证"谁、何时、从哪版升到哪版"。

---

## 2. 版本看板（在可观测看板 `08` §0 上扩展）

在 `08` 的可观测看板里，给已交付客户加一个**「能力版本」页签**：

| 列 | 内容 |
|----|------|
| 能力 | #1–#14 清单项 |
| 当前版本 | 如 `v1.2.0` |
| 最新版本 | 我们已发布的如 `v2.0.0`，未升级则标「可升级」徽标 |
| 变更说明 | 该版本 release notes 摘要（新能力/增强/修复） |
| 升级入口 | 客户点「申请升级」→ 进升级流程（§4） |

> 透明即信任：客户看得见"我的数字人在哪个版本、有没有新能力可用"，不用追着我们问"你们又更新没"。这也是续费/升版的自然钩子。

---

## 3. 升版触发（我们新能力 → 通知客户）

**内部动作**
- 我们研发/改进某能力 → 在内部将该能力版本号 +1，写 release notes（变了什么、对客户有啥用）。
- 同步更新 `08` 能力清单的版本基线（对外可展示的"最新版本"）。

**对外动作**
- 月费期客户：版本看板标"可升级" + 月度《服务月报》（`12`）附"本月新能力"摘要。
- 非月费客户（已交付未续费）：可发新版通告，邀请回归续费+升版（upsell 路径，见 `04` 阶段 6）。

**升版分级口径（决定收费）**
- **MAJOR（收费升级）**：新增能力（如清单里原本没的 #15）、或某能力跨代重构（效果质变）。
- **MINOR（月费含 / 可选低价升级）**：同能力显著增强（如 #3 主动执行加了"多触发器编排"），通常含在月费养护里；客户若想立刻用也可付费提前开通。
- **PATCH（免费，含月费）**：修复/微调，月费期内自动推送，不打扰客户。

---

## 4. 升级收费接口（升版即收费）

> 设计原则：月费覆盖"保持当前能力健康"（PATCH+MINOR 养护）；**MAJOR 升版是增量交付，单独收升级费**——既不白送研发成果，也不让客户觉得"月费啥都没干"。一律法币，严禁加密。

### 升级费定价（国内 / 国外双市场）

升级费按"版本增量"折算，低于从零搭建（因为是在已有配置上增量改，不是重搭）：

| 升版类型 | 折算基准（对标 `08` 搭建费/加购价） | 国内升级费 | 国外升级费 |
|----------|--------------------------------------|------------|------------|
| MAJOR·新增能力（清单内现有项补配，如给老客加 #11 私有化） | 该能力加购价 × 60–80% | ¥800–3k | $120–450 |
| MAJOR·跨代重构（如 #7 AI造AI v1→v2） | 该能力加购价 × 50–70% | ¥1k–2.8k | $150–400 |
| MINOR·增强（客户想立刻用，不等月费） | 该能力加购价 × 20–40% | ¥300–1.2k | $50–180 |
| PATCH·修复微调 | ¥0（含月费） | ¥0 | $0 |

> **汇率红利**：国外同档约为国内 5–7 倍（同 `08`）。
> **克制原则**：升级费只收"增量研发交付"部分，不重收已付过的搭建费；同一客户同月多能力升级可合并报价，给打包折扣（如 2 项 MAJOR 升版 9 折）。

## 5. 升级流程（SOP）

1. **通知**：版本看板标"可升级" + 月报附 release notes；客户点「申请升级」或我们主动邀约。
2. **报价**：出「升级费单」（模板 K），列明"从 vX 到 vY、变了什么、升级费多少、是否含重验"。
3. **付费**：客户付升级费（法币；国内微信/对公、国外 Stripe/Wire/托管），**升级费到账再实施**（对齐"定金→服务"闭环，不白干）。
4. **实施**：在客户现有配置上增量改（不破坏既有记忆/角色），按 `00-方法论.md` 落变更。
5. **重验**：按「模板 D 验收单」四件套 + 验人感四条复检升级部分；客户确认。
6. **留证**：打新时间戳 + 数字指纹 + SHA-256 哈希（见 `07`），刷新版本链 `客户 ID ↔ 新版本 ↔ 时间戳 ↔ 哈希 ↔ 指纹`；看板版本号更新为 vY。
7. **记录**：写「模板 K 升级确认与版本记录」，绑定客户 ID，全链路可查。

> 客户**可跳过**某次升级（不是强制消费），看板持续提示"有新版可用"；跳过不影响现有功能，只是暂不用新能力——把选择权留给客户，反而提信任。

---

## 6. 与现有模块的联动

- **↔ `08` 能力清单**：清单项是版本化对象；升级费定价直接复用 `08` 的权重/加购价折算。
- **↔ `07` 可追溯**：每次升版 = 一条新版本记录，时间戳/哈希/指纹串成"进化史"，争议/展示/续费全可查。
- **↔ `12` 服务月报**：月报体现"版本演进 + 本月新能力"，让客户持续感知研发在投入，续费/升版动力双增。
- **↔ `04` 阶段 5 月费**：升版是月费之外的收入补充，列为「阶段 5.7 升版」；与转介绍（5.5）、upsell（6）构成复利三层（月费 / 升版 / 转介）。
- **↔ `02` 报价**：升级费与搭建费/月费同源，统一报价口径，不碎片化。

---

## 7. 对外话术要点

- "你买的是会进化的数字人，不是一次性配置"——把研发持续投入讲成客户权益。
- "新能力出来你一键升版，不用重买"——降低决策门槛、强化长期关系。
- 禁绝对词（"最/第一"），用"持续进化 / 越用越强"等可验证表述（见 `09` 话术红线）。
- 升版自愿、不强制，透明展示版本与变更，避免"偷偷加价"的信任反噬。
