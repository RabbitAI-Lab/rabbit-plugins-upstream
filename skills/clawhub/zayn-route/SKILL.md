# ROUTE() Skill 路由与编排

## 1. 基本信息

```text
Skill ID: zayn-route
Display Name: ROUTE()
Chinese Name: Skill 路由与编排
Project: WorkFn
Author Prefix: zayn
Category: Skill Orchestration
Version: 0.1.2
Status: Draft for testing
```

## 2. 解决的问题

ROUTE() 用于解决以下问题：

1. 用户遇到复杂问题，不知道先调用哪个 Skill
2. 一个问题可能需要多个 Skill 串联
3. 前一个 Skill 的结果没有被正确传给下一个 Skill
4. Skill 调用顺序错误
5. 信息不足时仍然继续后续分析
6. 多个 Skill 重复分析同一问题
7. 最终输出 Skill 不明确
8. 路由过程越来越复杂，重新变成万能工具

## 3. 适用场景

适用于：

1. 用户的问题涉及多个阶段
2. 需要先理解再澄清
3. 需要先判断再报价
4. 需要先分析客诉再判断责任
5. 需要先检查订单再启动交付
6. 需要先梳理重点再汇报或决策
7. 用户不确定应该调用哪个 Skill
8. 需要明确 Skill 调用链和停止条件
9. 需要在日报、周报、月报、年中报告、年度报告之间选择正确的汇报 Skill
10. 需要在跨部门协同、内部请求、问题升级、领导决策和最终上级沟通之间选择正确路径

## 4. 不适用场景

不适用于：

1. 一个明确 Skill 已足够解决的问题
2. 用户已经明确指定要调用的 Skill
3. 只需要执行简单翻译
4. 只需要普通总结
5. 需要 ROUTE() 自己完成全部业务分析
6. 需要自动执行所有 Skill
7. 需要创建复杂多 Agent 系统

## 5. 输入参数

### 必填参数

| 参数 | 说明 |
|---|---|
| user_problem | 用户当前遇到的问题 |
| desired_outcome | 用户最终希望得到什么 |
| available_context | 当前已有上下文和材料 |

### 建议参数

| 参数 | 说明 |
|---|---|
| current_stage | 当前处于理解、澄清、判断、决策、执行、沟通、跟踪或复盘阶段 |
| known_facts | 已确认事实 |
| missing_information | 已知缺失信息 |
| existing_outputs | 已经运行过的 Skill 结果 |
| constraints | 时间、权限、风险、数据和业务限制 |
| final_output_type | 最终希望得到回复、报价、汇报、方案、计划或纪要 |
| user_selected_skill | 用户已经指定的 Skill |
| available_skills | 当前项目已有 Skill 列表 |

## 6. 参数运行要求

正式路由前必须输出参数状态表。

参数状态只使用：

```text
已命中
部分命中
缺失
冲突
待验证
```

最低运行条件：

1. 用户问题基本明确
2. 最终目标基本明确
3. 当前已有上下文可识别
4. 能判断至少一个候选 Skill
5. 能识别是否需要停止补充信息

如果用户问题和最终目标都不明确，不得生成 Skill 调用链。

## 7. 问题类型识别

ROUTE() 必须先判断当前问题属于哪一种或哪几种类型：

1. 理解
2. 澄清
3. 判断
4. 决策
5. 执行
6. 沟通
7. 跟踪
8. 复盘

示例：

```text
客户原话看不懂
```

属于：

```text
理解
```

示例：

```text
客户需求不完整，需要确认配置
```

属于：

```text
澄清
```

示例：

```text
判断是否值得报价
```

属于：

```text
判断
```

示例：

```text
确定价格后生成报价
```

属于：

```text
执行
```

## 8. 单 Skill 优先原则

ROUTE() 必须先判断：

```text
一个 Skill 是否已经足够解决问题。
```

如果一个 Skill 足够，不得为了展示能力而增加调用链。

例如：

```text
帮我检查这份报价是否完整
```

只使用：

```text
QUOTE()
```

例如：

```text
帮我整理会议结论和责任人
```

只使用：

```text
MINUTES()
```

## 9. 多 Skill 调用原则

只有在以下情况下才使用多个 Skill：

1. 当前问题包含明显的前后阶段
2. 后一个 Skill 依赖前一个 Skill 的输出
3. 直接调用后一个 Skill 会缺少关键参数
4. 不同 Skill 之间职责明确
5. 每一步都有必要性
6. 调用链长度合理

第一版建议：

```text
最多推荐 5 个 Skill。
```

超过 5 个时，应重新检查是否过度设计。

## 10. Skill 调用链设计

调用链必须说明：

1. 顺序
2. Skill 名称
3. 作用
4. 所需输入
5. 产出
6. 产出传给哪个 Skill
7. 停止条件

统一格式：

| 顺序 | Skill | 作用 | 所需输入 | 关键输出 | 输出传给 | 停止条件 |
|---|---|---|---|---|---|---|

## 11. 参数传递规则

前一个 Skill 的输出传给下一个 Skill 时，必须：

1. 只传必要字段
2. 不原样传递整段长文本
3. 保留已确认事实
4. 保留待验证信息
5. 保留冲突
6. 不把推测升级为事实
7. 标明来源 Skill

例如，INTENT_DECODE() 输出：

```text
客户明确表达
客户核心关注点
可能意图
待确认事项
```

传给 CLARIFY() 时，只保留：

```text
已确认需求
待确认事项
不可过度推断的部分
```

## 12. 停止条件

ROUTE() 必须为每个调用链设置停止条件。

常见停止条件：

1. 关键参数缺失
2. 产品身份无法确认
3. 客户需求范围不明确
4. 责任状态无法确认
5. 价格、库存或交期未确认
6. 订单尚未确认
7. 用户目标发生变化
8. 当前证据不足
9. 后续 Skill 不具备最低运行条件

停止时必须明确说明：

1. 为什么停止
2. 缺什么
3. 应该补什么
4. 补充后从哪个 Skill 继续

## 13. 正式路由触发条件

只有同时满足以下条件，才生成完整 Skill 调用链：

1. 用户问题明确
2. 最终目标明确
3. 至少一个候选 Skill 明确
4. 关键输入可识别
5. Skill 之间有真实依赖
6. 调用链没有明显重复
7. 已设置停止条件

## 14. 输出结构

ROUTE() 必须按以下结构输出：

### A. 参数完整度结论

只使用：

```text
可直接路由
需要补充关键参数
当前只适合单 Skill
存在冲突，暂不建议继续
```

### B. 参数状态表

列出：

1. 用户问题
2. 最终目标
3. 当前阶段
4. 已有材料
5. 已有 Skill 输出
6. 限制条件

### C. 问题识别

```text
当前问题类型：
核心目标：
当前阶段：
```

### D. 单 Skill 或多 Skill 判断

明确说明：

1. 一个 Skill 是否足够
2. 为什么
3. 是否需要调用链

### E. 推荐 Skill 链

使用统一表格。

### F. 当前先执行哪一步

只给一个当前动作。

例如：

```text
先调用 INTENT_DECODE()
```

### G. 参数传递说明

明确哪些结果传给下一个 Skill。

### H. 停止条件

列出必须停止的情况。

### I. 最终输出 Skill

明确最终由哪个 Skill 生成结果。

## 15. 常见路由示例

### 示例一：客户表达不清，需要回复

```text
INTENT_DECODE()
↓
CLARIFY()
↓
REPLY()
```

### 示例二：陌生产品询价并报价

```text
PRODUCT_BRIEF()
↓
CLARIFY()
↓
RFQ()
↓
PRICE()
↓
QUOTE()
↓
REPLY()
```

### 示例三：客户压价

```text
INTENT_DECODE()
↓
PRICE()
↓
NEGOTIATE()
↓
REPLY()
```

### 示例四：客户投诉并要求退款

```text
COMPLAINT()
↓
RESPONSIBILITY()
↓
RMA()
↓
SOLUTION()
↓
REPLY()
```

### 示例五：订单确认后的交付

```text
ORDER()
↓
ORDER_KICKOFF()
↓
DELIVERY()
↓
MEETING()
↓
MINUTES()
```

### 示例六：复杂项目汇报

```text
KEYPOINT()
↓
REPORT()
↓
DECISION()
```

### 示例七：周期性工作汇报

如果用户已明确周期，优先直接路由到对应专项 Skill：

```text
DAILY_REPORT() / WEEKLY_REPORT() / MONTHLY_REPORT() / MIDYEAR_REPORT() / ANNUAL_REPORT()
```

如果用户只说“写个汇报”，但周期、对象或目的不明确，先使用：

```text
REPORT()
```

### 示例八：跨部门协同后对外回复

```text
CROSS_FUNCTIONAL_COLLABORATION()
↓
REPLY()
```

如果只是向内部某部门提出明确问题且无承诺、推责或风险判断，可直接使用：

```text
REQUEST()
```

### 示例九：向经理或老板沟通

如果用户需要把已整理的事实、建议或请求转化为面向直属主管、经理、部门负责人或老板的最终沟通内容，使用：

```text
UPWARD_COMMUNICATION()
```

需要先比较方案并请领导拍板时：

```text
DECISION()
↓
UPWARD_COMMUNICATION()
```

问题超出权限或存在重大风险时：

```text
ESCALATE()
↓
UPWARD_COMMUNICATION()
```

向平级同事或职能部门提出执行请求仍使用 `REQUEST()`；信息明确的请假、调休、工作安排和普通上级沟通可直接使用 `UPWARD_COMMUNICATION()`。

以上示例只是候选路径，不得无条件套用。

## 16. 风险检查

必须检查：

1. 是否推荐过多 Skill
2. 是否存在职责重复
3. 是否跳过参数检查
4. 是否缺少停止条件
5. 是否把一个简单问题复杂化
6. 是否让 ROUTE() 自己完成业务分析
7. 是否把推测继续传给下游
8. 是否忽略用户已指定的 Skill
9. 是否忽略已有 Skill 输出
10. 是否重复询问已经提供的信息

## 17. 禁止事项

ROUTE() 不得：

1. 自动执行全部 Skill
2. 直接完成所有业务分析
3. 为简单问题创建长调用链
4. 推荐超过 5 个 Skill，除非有明确必要
5. 跳过前置 Skill 的最低运行条件
6. 把前一个 Skill 的全部长文本传给下一个
7. 删除冲突信息
8. 把待验证信息写成确定事实
9. 强行使用所有现有 Skill
10. 覆盖用户指定的合理路径
11. 在关键信息不足时继续后续流程
12. 把路由器重新做成万能工具

## 18. 人工判断边界

1. 用户可以指定或修改路由
2. 用户可以跳过某个 Skill
3. 人工确认事实优先
4. ROUTE() 只能建议，不得强制执行
5. AI 不得修改原始材料
6. AI 不得覆盖已有人工判断
7. 所有自动传递内容必须可追溯到来源 Skill

## 19. 验收标准

一个合格的 ROUTE() 输出必须满足：

1. 能识别问题类型
2. 能判断一个 Skill 是否足够
3. 不为了展示能力增加 Skill
4. 调用顺序合理
5. 参数传递清楚
6. 每一步有明确作用
7. 有停止条件
8. 明确当前先做什么
9. 明确最终输出 Skill
10. 不直接代替业务 Skill
11. 不把问题复杂化
12. 不把待验证信息传成确定事实

## 21. 通用版与行业版选择

先判断用户材料是否包含行业专属证据，再选择 Skill：

1. 服务器、存储、内存、SSD、GPU、网络设备、笔记本配件、PN、固件或硬件兼容问题使用 `zayn-product-brief`；其他实体产品、数字产品或服务使用 `zayn-general-product-brief`。
2. 涉及硬件型号、PN、配置兼容、成色、序列号、保修、锁货或二手备件时，使用 `zayn-alternative`、`zayn-availability` 或 `zayn-condition`；其他行业分别使用对应的 `zayn-general-*`。
3. 涉及硬件工程确认、固件、测试、QC、标签序列号、包装和清关时使用 `zayn-order-kickoff`；普通产品、服务合同或项目启动使用 `zayn-general-order-kickoff`。
4. 涉及硬件序列号、测试、安装兼容、保修、维修、换货、退运检测或供应商退换窗口时，使用原硬件售后 Skill；一般产品、服务、订阅或项目问题使用对应的 `zayn-general-complaint`、`zayn-general-responsibility`、`zayn-general-rma` 或 `zayn-general-solution`。
5. 行业证据不足时默认使用通用版，不得仅因用户提到“产品”“库存”“退货”就触发硬件版。
