# 报销完成监控

## 建立任务

1. 实时查询申请与流程，确定用户指向的申请 ID、申请时间、项目和当前状态。ID 只保留在本地任务配置，不放进用户通知或通用技能示例。
2. 列出现有任务，复用相同账号和申请的监控，避免重复提醒。未指定频率时可采用白天每小时检查，并在最终说明时区与时段；不要把此默认硬编码成所有用户的要求。
3. 使用确定性只读脚本查询：复用 `query_fee_requests.py --json` 或 `OAAuth`，不筛选“审批中”；日期参数带完整时分秒。使用详情接口或分页查找精确 ID，不能把“未找到”“认证失败”“空列表”当成流程完成。
4. 校验进程退出码、JSON 业务成功码和目标记录。`20` 审批中不输出；`30` 已通过输出完成消息；`40` 驳回、`-1` 撤回、`0` 作废单独通知，不称为通过。未知状态保持未确认。查询失败走错误通知，不写完成标记。
5. 采用脚本型调度：在 Hermes 中使用 `no_agent=true`，stdout 仅留需要发送的消息，日志写 stderr；正常等待期 stdout 必须为空，避免每小时打扰。失败通知和业务通知显式指定用户授权渠道，含报销信息的任务不要默认广播所有平台。
6. 注册前实际执行脚本，确认等待状态是成功退出且无 stdout。可用隔离测试状态验证终态分支，禁止改动真实 OA 状态来制造完成条件，也不要把测试数据当成真实审批结果。
7. 注册后重新读取任务，核对 enabled、schedule、deliver、script、no_agent、next_run_at。报告监控范围、频率、下一次检查与静默规则；区分“查询验证通过”“任务已启用”和“终态消息已送达”。

## 去重与投递可靠性

- 将监控状态绑定账号/地址与申请 ID，使用权限受限、原子更新的状态文件；并发运行时加锁，避免重复发送。
- 区分“观察到终态”“消息待投递”“已确认送达”。不要在打印 stdout 前写入永久 `notified=true` 并把它当成可靠投递：脚本成功后仍可能发送失败，提前标记会让以后全部静默，丢失提醒。
- 需要可靠一次提醒时，核实当前调度器的投递确认/重试机制，或使用可确认发送结果的持久待发送队列。只有读到成功投递结果后才永久抑制后续通知；没有这种能力时明确是尽力通知，不声称 exactly-once。
- 终态确认送达后可暂停后续轮询；仅在脚本内提前返回不等于调度任务已暂停。任务生命周期变化也要读回验证。

## 通知内容

金额与明确状态优先，随后分行列项目和申请时间；通过时补一句“审批通过不代表已经到账”。不展示内部 ID、凭据或原始流程 XML。用户询问耗时才增加申请创建、本轮流程与节点耗时，避免每条提醒变成长报告。
