# 工时查询、查漏与周度总结

### 查询工时列表
```bash
python scripts/query_time_entry.py 2026-04-10
```
→ 内部调用 `POST /sn/timeEntry/findEveryDayList`

### 按周查漏与多轮补填

1. 用实际当前时间和用户时区计算“本周/上周”的周一至周日范围，首次答复标明具体日期。随后用户只说“周三”等星期时，沿用正在核查的那一周，不切回本周。
2. 对范围优先调用 `python scripts/query_time_ranges.py --range <开始日期> <结束日期> --json`；单日可使用 `query_time_entry.py`。批量入口复用认证会话。先核实每个响应成功，再提取记录；非零退出、不可解析响应、业务失败或未查到的日期都不能算作“未填”。按适用的工作日历核对调休与节假日，普通周末空记录不计漏填；草稿、驳回与有效已提交记录分开说明。
3. 输出先列缺填日期，再简列其他工作日的时长和状态；不默认展开全部描述。用户紧接着问某几天的内容时，可直接使用刚获得的同批查询结果，按“日期与星期 → 工作内容 → 状态”展示，共同项目仅写一次；执行任何写入前仍须重新核对同日记录。
4. 在查漏对话里接收逐日工作描述时，先保留日期与文案的待提交清单。若用户指定的日期已有记录，指出已有内容并询问是日期说错还是确实要修改；不要自行改到空缺日，也不要新建重复记录。用户仅回复更正的星期时，只修正最近待处理条目的日期，不移动其他条目或视为撤回授权。
5. 当此前只授权查询、尚未授权填报时，集中列出待补日期、润色文案、项目和时长，统一确认一次。用户针对这份清单回复同意后，按“润色后填报与中断续办”的查询 → 预览 → 真实提交流程完成全部已确认日期，不重复索要同一授权；已有记录若需撤回重提，仍遵守独立修改授权流程。
6. 批量完成后分别核实每个日期的实际结果，不能用后一条成功掩盖前一条失败；结果简列日期与内容，共同项目、时长、状态可合并。只有此前已完整核查该周、且所有缺填日都已核实补齐时，才说“本周/上周已全部填齐”。

### 按指定区间导出与周度润色总结

1. **按用户给定的起止日期分组，并包含首尾两天。** 不擅自扩展为完整自然周，也不因某天是周末就跳过已有记录；历史记录导出与新增填报的工作日限制是不同任务。
2. **先取真实记录，再写总结。** 使用主文档的 `query_time_ranges.py` 一次传入全部区间，复用同一个认证会话。不逐日驱动模型，不重复编写查询脚本。需要核查时加 `--raw-output <新的私有JSON路径>` 保存证据；检查退出状态与完整性，失败、空记录、草稿和有效记录分开处理，不用历史聊天补造缺失数据。

3. **从保存的源数据计算指标。** 用记录 ID 去重采集结果，分别计算有记录日期数、记录条数、实际工时之和及状态分布；用十进制数求和，不按日期跨度乘固定工时。同日多条真实记录不能按描述去重。区间重叠时，各区间保留自身统计，跨区间总计按唯一记录计算。没有核对工作日历时称“填报日”，不把填报日数自动叫做应出勤工作日数。
4. **按周归并主题，而非机械复制日报。** 每段标题保留用户指定的日期区间及天数／时长；段内去掉逐日前缀日期和星期，用完整通顺的工作内容条目合并重复事项。只润色已有事实：不把研究、讨论、排查擅自写成上线、验收或已解决。保留接口、参数、数量和专有名称；相似但不同的系统名称无可靠证据时分别保留，不自行纠错统一。
5. **按需交付，不回写 OA。** 共同项目和总体审批情况在开头集中说明；仅全部源记录核实一致时才能说“全部已审批”。普通汇总直接在聊天展示；用户要求文件时沿用指定或已确认的格式，生成 Word 时加载 `docx` 技能。保持聊天与附件的分组、指标、内容一致，不在附件暴露内部 ID。导出授权不包含修改或重新提交原记录。
6. **校验后再报告完成。** 用源 JSON 断言已查询日期集合与请求相符、唯一记录数及总工时准确；读取生成附件，检查每个区间标题和所有总结条目，Word 再执行包健康检查。查询范围未覆盖整月时，不宣称整月工时已齐。

### 获取工时详情
```bash
python scripts/get_time_entry_details.py <工时ID>
```
→ 内部调用 `GET /sn/timeEntry/details/<工时ID>`

> 注意：工时提交/查询/详情/修改接口统一通过完整认证会话发起，必须同时携带 `Authorization: Bearer {token}` 和 `Admin-OA-Token: {token}` 两个请求头。
