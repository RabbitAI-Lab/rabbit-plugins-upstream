# 已有工时修改：撤回、修改原记录、重新提交

## 适用范围与授权

仅适用于用户明确指定的普通工作记录及已确认的新描述。先告知撤回会终止当前审批并触发重新提交；必须取得明确授权才使用 `--withdraw-resubmit`。用户只说“修改描述”不自动等于允许终止审批；先预览说明影响，再确认。只读查询、预览、测试、排查或发布技能均不授权修改真实记录。

```text
python scripts/update_time_entry.py <record-id> --job-desc "<new-description>" --preview
python scripts/update_time_entry.py <record-id> --job-desc "<new-description>" --withdraw-resubmit
```

## 协议证据

用户提供的页面 HAR 展示：

1. 查询当日列表，原记录为 `state=20`、未删除。
2. `POST /sn/workflow/task/stopProcess`，参数只有该记录当前 `procInsId`。
3. 再查同一天，原记录 ID 未变，状态为 `-1`。
4. `POST /sn/timeEntry/saveOrUpdate`，`timeEntryList` 保留原 `id` 与业务字段，更改 `jobDesc`，外层 `saveOrSubmit=1`；页面日期形式为 `YYYY-MM-DD(周X)`。
5. 用户页面操作后，实时只读核实同一天仍只有原记录，新描述正确、8 小时时长与项目未变、状态回到审批中。

这里记载的是协议与观察，不是一个可重放的 HAR。发布包不得包含原始抓包、认证 Cookie、token、账号、个人姓名、服务地址或真实业务标识。不能据本样本断言所有审批状态、项目或旧版系统都支持撤回重提，也不能声称该新实现已经执行过真实写入。

## 执行边界

- 预览只读：不能撤回、保存、删除或创建草稿，也不保存个人默认。
- 真实执行必须核实同日列表完整且只有指定的原记录；日期、ID、普通工作类型、未删除状态和不可变业务字段不确定时停止。
- 已审批、删除、草稿、非普通工作、其他日期、未知状态、多条记录或缺少当前流程 ID 均不能自动处理。
- ID 与业务代码不得通过去空格、补零等方式修复。日期只解析已知服务端纯日期或精确午夜形式，不能任意截断。
- 仅允许变更已授权的描述；项目、日期、时长、填报人、业务类型、阶段等不得借机更改。
- 认证必须绑定当前 OA 地址、真实账号和双认证头；每个阶段验证身份未变。写入禁用自动重登重试、HTTP 重定向与重试型 adapter。
- 修改使用独立持久日志，仍与新建提交共享账号/日期锁。不能清除、替换或绕过普通新建提交保护，也不把已有记录伪装成新记录再次提交。
- 撤回前和重新提交前先持久化相应意图；不能仅凭 HTTP 成功进入下阶段，须读回状态和业务字段验证。
- 撤回失败或结果不明时，不发送重新提交。重新提交结果不明时只读核实，不自动重复 POST；中断后不得盲目重跑整条链路。
- 如果已撤回但未完成重新提交，必须明确告知用户当前状态及未完成阶段，不能报“修改成功”。对记录的并发修改或审批变动应 fail-closed，不覆盖。
- 成功必须读回同一原 ID、精确新描述、全部不可变字段、未删除且审批中；仅 HTTP 200 不代表成功。

## 旧入口

不带新标志的描述修改仍走 `PUT /sn/timeEntry/update`；这是历史兼容入口，不保证审批中可修改。它被服务器拒绝后不能自动撤回。逻辑删除仍为独立 `--delete`，不得与 `--withdraw-resubmit` 组合，也不能用删除重建替代修改。

## 验证与发布

离线测试使用泛化假记录和注入的 HTTP fake，覆盖正常流转、原 ID 保持、无授权和预览零写入、状态/字段冲突、身份变化、持久意图、超时无重发及只读核实。全套测试须同时保留普通提交回归测试。

发布前可对用户已修改完成的记录进行授权范围内的只读查询与相同文案预览；这只能证明读取/预览与接口契约，不是新实现真实撤回/重提的 live 写入验证。需要实际写入验证时，应另选用户明确授权且确有修改必要的记录，不能制造测试工时或重复撤回已正确的记录。

本地锁不是跨机器的服务端事务。不同客户端仍可能竞争；安全保证依赖保护目录持久保留与所有调用方遵守确认边界。
