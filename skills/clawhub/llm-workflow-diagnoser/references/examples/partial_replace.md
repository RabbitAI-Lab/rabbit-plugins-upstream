# 部分改造示例：合同条款抽取 + 风险标记

> 用途：写报告前对照风格，不内嵌到主报告里。
> 注意：示例展示的是"报告原文贴在 Chat"的效果，章节标题、表格格式必须完全一致。

## 用户上下文

- 流程名：合同条款抽取 + 风险标记。
- 触发：每天 30-50 份合同。
- 输入：合同 PDF / docx（半结构化长文本）。
- 输出：抽取字段表（甲方 / 乙方 / 金额 / 履约期）+ 风险条款高亮。
- 错误成本：中（错误的金额字段会被法务复核）。
- 改造目标：把抽取字段的人工耗时砍掉，但风险条款判断保留人工。

---

## 报告原文示例（应直接复制此结构）

```text
# 诊断说明
- 一句话说明：字段抽取适合 LLM 全自动，但风险条款判断属于高合规边界，必须保留人工。
- 改造步骤：
  - 步骤 1：固化 JSON schema + prompt，做字段抽取的 LLM 化
  - 步骤 2：保留风险条款判断为人工环节，LLM 仅生成候选
  - 步骤 3：建立「抽取准确率 / 复核一次通过率」两道监控
- ROI 分数：6/10（10为满分）
- 改造关键：
  - 关键 1：字段抽取结构化强、可量化
  - 关键 2：风险条款判断属合规边界，不能交给 LLM
  - 关键 3：法务复核通道必须保留
- 下一步建议：
  - 建议 1：先抽 50 份历史合同做对照验证
  - 建议 2：把风险条款判断明确从 LLM 流程中隔离
  - 建议 3：上线前法务跑一轮 dry-run

# LLM 介入边界
- 硬护栏护住：风险条款最终判断（合规边界）
- 仅部分场景适用：风险条款候选生成 + 多版本对比；法务裁决
- 全量适用：字段抽取、字段标准化、命名规整
- AI 可护住：检索（找相似条款）、生成（候选风险描述）、数据能力边界（限定 JSON schema）

# 改造难度评级

维度	｜ 难度值（xx/10，10为满分）｜解释
输入多样性	｜ 5/10（10为满分）｜ 合同格式多样但字段稳定
输出一致性要求	｜ 7/10（10为满分）｜ 字段抽取必须严格统一
容错率	｜ 5/10（10为满分）｜ 字段抽取错会被法务复核
决策密度	｜ 4/10（10为满分）｜ 风险条款判断需要经验
可验证性	｜ 2/10（10为满分）｜ 有抽取字段表与人工复核率

# 落地 MVP 路线图
- MVP 步骤 1：固化 JSON schema + prompt，抽取字段表
- MVP 步骤 2：风险条款判断环节保留人工，LLM 仅生成候选
- MVP 步骤 3：上线后跑 4 周 A/B，统计抽取准确率与人工耗时

# 风险清单
- 风险 1：字段抽取错 → 缓解：固化 JSON schema + 校验脚本
- 风险 2：风险条款误判 → 缓解：判断环节必须人工裁决
- 风险 3：法务对 LLM 输出不信任 → 缓解：dry-run + 复核通道

# 信息缺口 / 需补充追问
- 缺口 1：未告知合同主要类型（采购 / 销售 / 服务），不同类型风险条款差异大
- 缺口 2：未告知当前人工抽取耗时基线
```
