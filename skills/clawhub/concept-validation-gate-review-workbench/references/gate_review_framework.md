## 1. Gate评审体系概述

### 1.1 5-Gate体系定义

概念验证中心采用5-Gate评审体系，与传统Stage-Gate体系的区别在于：

| 维度 | 传统Stage-Gate | 概念验证中心Gate |
|------|---------------|----------------|
| **核心目标** | 硬性通过标准 | 包容性探索 |
| **一致性要求** | 4维一致性（严格） | 3维轻一致性（方向正确即可） |
| **失败处理** | 项目终止 | 失败归档，允许Pivot |
| **资源分配** | 单路线深耕 | 多路线并行（60/30/10） |
| **决策风格** | 一票否决 | 蓝灯有条件通过 |

### 1.2 Gate体系架构

```

│                    概念验证中心5-Gate体系                                 │
│                                                                         │

│  项目筛选   探索评审   技术评审   商业评审   出站评审                    │
```

## 2. 各Gate评审要点详解

### 2.1 Gate 0：项目筛选（TRL 1）

**目标**：筛选有价值的项目进入概念验证中心

**评审角色**：老胡（主持）、验验、瞭瞭

**评审要点**：
| 维度 | 评审要点 | 评估方法 |
|------|---------|---------|
| 方向判断 | 技术方向是否有科学依据 | 文献调研、原理推导 |
| 价值初筛 | 是否有潜在商业/社会价值 | 市场分析、创新性评估 |
| 资源匹配 | 中心资源是否能支持验证 | 资源就绪评估 |

**三灯制判定标准**：

| 灯色 | 判定条件 | 说明 |
|------|---------|------|
| 🟢 绿灯 | 方向有依据 + 有潜在价值 + 资源可匹配 | 全部满足 |
| 🔵 蓝灯 | 方向有依据但需补充信息/调整方向 | 方向正确但细节待定 |
| 🔴 红灯 | 方向无科学依据/违反基本原理 | 有一票否决项 |

**一票否决项**：
- ❌ 无任何论文/专利/理论支撑
- ❌ 明确违反已知物理/化学定律
- ❌ 无知识产权保护方案
- ❌ 核心成员无法参与

**通过标准**：
- 🟢 绿灯：全部通过，直接准入
- 🔵 蓝灯：方向正确，附带条件后准入
- 🔴 红灯：终止，不准入

---

### 2.2 Gate 1：探索评审（TRL 2）

**目标**：评估原理可行性和探索价值

**评审角色**：老胡（主持）、验验、瞭瞭

**评审要点**：
| 维度 | 评审要点 | 评估方法 |
|------|---------|---------|
| 原理可行性 | 核心技术原理是否可行 | 理论分析、专家访谈 |
| 探索价值 | 技术探索是否有价值 | 创新性分析、市场潜力 |
| 团队状态 | 团队是否具备探索能力 | 团队能力评估 |

**四灯制判定标准**：

| 灯色 | 判定条件 |
|------|---------|
| 🟢 绿灯 | 原理可行 + 探索价值高 + 团队到位 |
| 🔵 蓝灯 | 原理基本可行但需补充/探索价值待验证 |
| 🟡 黄灯 | 原理存疑/探索价值不明显 |
| 🔴 红灯 | 原理不可行/无探索价值 |

**一票否决项**：
- ❌ 原理被证明不可行
- ❌ 探索价值被否定
- ❌ 团队完全不具备探索能力

---

### 2.3 Gate 2：技术评审（TRL 3）

**目标**：评估技术可行性和3维轻一致性

**评审角色**：老胡（主持）、验验、营营

**评审要点**：
| 维度 | 评审要点 | 评估方法 |
|------|---------|---------|
| 技术可行性 | 技术方案是否可行 | 验验实验数据 |
| 3维轻一致性 | 原理/可重复/对标一致性 | 三维验证报告 |
| 路线选定 | 主攻/备选/探索路线确定 | 资源分配决策 |

**四灯制判定标准**：

| 灯色 | 判定条件 |
|------|---------|
| 🟢 绿灯 | 3维轻一致性全部通过 |
| 🔵 蓝灯 | 1-2维通过但方向正确/需继续探索 |
| 🟡 黄灯 | 技术存疑，需补充验证 |
| 🔴 红灯 | 技术被否定/无可行路线 |

**必须输出**：
- ✅ 3维轻一致性验证报告
- ✅ 技术路线推荐
- ✅ 蓝灯附带条件（如有）

---

### 2.4 Gate 3：商业评审（TRL 4）

**目标**：评估商业可行性和市场需求

**评审角色**：老胡（主持）、营营、验验、闯闯

**评审要点**：
| 维度 | 评审要点 | 评估方法 |
|------|---------|---------|
| 需求真实性 | 客户需求是否真实存在 | 客户访谈（≥10次） |
| 模式可行性 | 商业模式是否可行 | 商业模式画布验证 |
| 价值假设 | 核心价值假设是否验证 | 假设验证报告 |

**四灯制判定标准**：

| 灯色 | 判定条件 |
|------|---------|
| 🟢 绿灯 | 需求真实 + 模式可行 + 价值假设验证 |
| 🔵 蓝灯 | 需求基本真实但需进一步验证/模式需调整 |
| 🟡 黄灯 | 需求存疑，需更多客户访谈 |
| 🔴 红灯 | 需求被否定/无可行商业模式 |

**参考I-Corps标准**：
- 客户访谈≥10次
- 至少1种商业模式画布完成
- 价值假设验证≥3个

---

### 2.5 Gate 4：出站评审（TRL 4-5）

**目标**：评估概念验证完整性和中试就绪度

**评审角色**：老胡（主持）、全体角色

**评审要点**：
| 维度 | 评审要点 | 评估方法 |
|------|---------|---------|
| 概念验证完整性 | 技术+商业双验证是否完成 | 验证报告审核 |
| 中试就绪度 | 是否具备进入中试条件 | 中试条件对照 |
| 交付包达标 | 8项交付物是否完整 | 交付包清单 |

**四灯制判定标准**：

| 灯色 | 判定条件 |
|------|---------|
| 🟢 绿灯毕业 | 双验证完成 + 中试就绪 + 交付包达标 |
| 🔵 蓝灯毕业 | 基本完成但需在中试初期补充（列出补充项） |
| 🟡 黄灯延期 | 需要额外验证时间 |
| 🔴 红灯终止 | 概念验证未通过，但失败经验归档 |

**毕业条件**：
- ✅ 技术验证报告v1完成
- ✅ 商业验证报告v1完成
- ✅ 概念验证整合报告完成
- ✅ 交付包8项文件全部或基本完成

## 3. 四灯制深度解读

### 3.1 灯色心理模型

| 灯色 | 心理暗示 | 适合场景 | 不适合场景 |
|------|---------|---------|-----------|
| 🟢 绿灯 | "做得好，继续" | 核心要求全部满足 | 细节不完美 |
| 🔵 蓝灯 | "方向对了，补一补" | 方向正确但有不确定性 | 方向存疑 |
| 🟡 黄灯 | "停一停，想清楚" | 存在重大疑问 | 细节问题 |
| 🔴 红灯 | "方向错了，止损" | 核心假设被否定 | 可修复问题 |

### 3.2 蓝灯的价值

蓝灯是概念验证中心最重要的创新机制，体现了"包容性"原则：

| 蓝灯价值 | 说明 |
|---------|------|
| **降低门槛** | 不要求完美，方向正确即可通过 |
| **加速迭代** | 边验证边补充，不用等完美 |
| **保留机会** | 给不确定的项目一个机会 |
| **明确条件** | 清晰的附带条件便于追踪 |

### 3.3 蓝灯条件设计原则

| 原则 | 说明 | 示例 |
|------|------|------|
| **可验证** | 条件完成状态可明确判定 | "补充实验报告" ✅ / "提高技术水平" ❌ |
| **有时限** | 条件有明确的完成期限 | "下一Stage完成" ✅ |
| **有负责人** | 每条条件有明确责任人 | "验验负责" ✅ |
| **有价值** | 条件完成能实质性推动项目 | "补充客户访谈5次" ✅ |

## 5. 蓝灯追踪机制

### 5.1 追踪台账设计

| 字段 | 说明 | 示例 |
|------|------|------|
| 条件编号 | 唯一标识 | B-01 |
| 条件内容 | 具体要求 | 补充实验数据，至少3组 |
| 条件类型 | 技术/商业/团队/资源/IP | 技术 |
| 负责人 | 角色名称 | 验验 |
| 计划完成 | 计划日期 | 2026-08-01 |
| 实际完成 | 实际日期 | 2026-08-05 |
| 完成状态 | 状态标识 | ✅已完成 |
| 证据 | 证明材料 | 实验报告v2.0.pdf |

### 5.2 追踪频率

| 追踪节点 | 触发条件 | 动作 |
|---------|---------|------|
| **Gate评审时** | 进入下一Gate | 记录新条件，更新旧条件状态 |
| **Stage中** | 里程碑节点 | 检查条件完成进度 |
| **预警提醒** | 截止前7天 | 提醒负责人 |
| **逾期提醒** | 截止日期到达 | 催促完成 |

### 5.3 条件完成判定

| 判定结果 | 证据要求 | 下一Gate处理 |
|---------|---------|-------------|
| **已完成** | 提供完整证据，经老胡审核通过 | 绿灯处理 |
| **部分完成** | 提供部分证据 | 视情况蓝灯或黄灯 |
| **未完成** | 无证据或证据不足 | 降级处理 |

## 6. 多路线资源分配

### 6.1 初始资源分配

| 路线类型 | 资源占比 | 选择标准 |
|---------|---------|---------|
| **主攻路线** | 60% | 技术可行性最高 + 团队能力匹配 |
| **备选路线** | 30% | 有一定可行性 + 可快速切换 |
| **探索路线** | 10% | 高风险高回报 + 新方向探索 |

### 6.2 资源调整触发条件

| 触发条件 | 调整动作 |
|---------|---------|
| 主攻路线成功 | 继续支持，备选可降级 |
| 主攻路线失败 | 备选升级为60%，探索可升级为30% |
| 主攻+备选均失败 | 从Gate 1重新评审，探索可作为新主攻 |
| 发现新方向 | 可新增探索路线 |

### 6.3 路线切换流程

```
路线失败识别
    │
    ▼
验验技术评估 → 新路线可行？
    │
    ├─ 是 → 资源重新分配建议
    │
    └─ 否 → 老胡决策：
            ├─ 暂停项目（黄灯）
            └─ 终止项目（红灯）
```
