# 质量关卡：来源分级 · 置信度 · 退出码 · 引导话术 · 降级链

> 这一份是**交付前的硬性质量层**，把「数字可信吗」从口号变成可执行的检查。
> 设计借鉴社区高分技能的可核验机制：**四档来源标注 + 分项置信度 + 退出码对号入座 + 强制降级链**。

---

## 一、来源四档标注（每个数字都要带档位）

任何进入报告的数字，必须标注来源档位。**未标档位 = 视为 S4 并被交付闸门拦下。**

| 档位 | 名称 | 质量分 | 含义 | 报告里怎么写 |
|---|---|---|---|---|
| **S1** | 平台原始数据 | 100 | 平台后台导出 / 用户提供的原始明细 | `客单价 128 元（S1｜生意参谋导出 2026-08）` |
| **S2** | 单方来源 | 70 | 客户口述、单一第三方工具、单一页面读数 | `退货率 8%（S2｜客户自述，待导出核验）` |
| **S3** | 公开来源 | 55 | 公开榜单 / 可检索公开数据 | `类目均价 99 元（S3｜公开榜单，抓取于 2026-09-27）` |
| **S4** | 推算值 | 20 | 模型推算 / 行业经验值，未经核验 | `类目平均转化率 3.5%（S4｜推算值，非真实数据，仅供参考）` |

**铁律**
- S4 只能作为「参考」，**不得作为决策主证据**；结论若仅由 S4 支撑，必须在报告中显式写「本结论依赖推算值，待核验」。
- 同一指标有多个来源时，取档位最高者，其余在附注列出。
- 报告末尾必须附**分项置信度块**（由脚本算出，不得手写）。

### 用脚本算置信度

```bash
PY="python3"
S="<skill-dir>/scripts"

"$PY" "$S/confidence.py" --data sources.json --json
```

输入 `sources.json`：

```json
{
  "items": [
    {"name": "支付金额", "source": "S1", "note": "生意参谋导出"},
    {"name": "竞品价格", "source": "S3", "note": "公开榜单 2026-09-27"},
    {"name": "类目转化率", "source": "S4", "note": "无数据时推算"}
  ],
  "checks": {
    "data_complete": true,
    "caliber_consistent": true,
    "recomputable": true,
    "conclusion_robust": false
  },
  "gate_min": 60
}
```

输出：来源分布 + 加权来源分 + 四维度分项得分 + S4 折损 + 综合置信度 + 是否放行。

**四个评分维度**

| 维度 | 权重 | 问的问题 |
|---|---|---|
| 数据完整性 | 30 | 关键字段齐了吗，有没有空缺？ |
| 口径一致性 | 25 | 同一指标是否同源同口径（ROAS/ROI 没混算吧）？ |
| 计算可复现 | 25 | 数值是本 Skill 脚本产出的吗，别人能复算吗？ |
| 结论稳健性 | 20 | 结论有 ≥2 条独立证据支撑吗，还是单点推测？ |

S4 占比越高，整体置信度折损越大（最高扣 30 分）。**综合分低于 `gate_min`（默认 60）拒绝交付**。

## 二、退出码 → 处理（对号入座，禁止自行判定失败）

脚本失败时按表处理，**不允许凭感觉重试或改参数掩盖错误**。

| 脚本 | 退出码 | 含义 | 处理动作 |
|---|---|---|---|
| `confidence.py` | 0 | 达到闸门，允许交付 | 正常进入关卡②③ |
| | 1 | **低于闸门 / 存在未标档位数据** | 补齐 S1–S3 数据，或把所有推算值显式标 S4 并在报告中降权；不得删掉数据蒙混 |
| | 2 | 输入文件不存在 / JSON 解析失败 | 检查 `--data` 路径与 JSON 格式，修好后重跑（**同一份输入，不得改数据**） |
| `profit_roi.py` / `selection_eval.py` / `stocking_plan.py` / `funnel_diagnose.py` | 0 | 正常 | —— |
| | 2 | 缺少必需数据 | 按 §三 引导话术一次性问清缺失字段，**不要用行业均值填补** |
| `settlement_audit.py` | 0 | 无 P0 异常 | —— |
| | 1 | **存在 P0 异常** | 这是**发现问题的正常返回**，不是失败：逐条列出金额影响，按 C1–C9 附处理建议 |
| | 2 | 缺输入 | 要结算单导出文件，引导用户提供 |
| `copy_compliance.py` | 0 | 无 P0 | 可交付 |
| | 1 | **命中 P0 违禁词** | 必须改文案直到 0 处；未清空前禁止交付（R7） |
| `data_verify.py` | 0 | 关卡①通过 | —— |
| | 1 | 关卡①未通过 | 回到 §三 ② 补数据或修口径，**不得跳过关卡①** |
| | 2 | 输入错误 | 检查 `--bundle` JSON |
| `report_pdf.py` | 0 | 生成成功 | 立即跑 `pdf_verify.py` |
| | 2 | spec 输入错误 | 按 `report-spec.md` 修 spec，**不得手改报告里的数值** |
| `pdf_verify.py` | 0 | 九项验真通过 | 可交付 |
| | 1 | 九项中有未通过项 | 看具体哪一项（页数/字体/图表数/表格数/关键词/文本层/体积），对应修 spec 重生成 |
| `run_all.py` | 0 | 全量自检通过 | —— |
| | 1 | 有自测失败 | 修脚本，直到全绿（R11） |

**通用原则**
- `settlement_audit` 退出码 1、`copy_compliance` 退出码 1 是**业务发现**，不是程序故障，别当成 bug 去"修好"。
- 任何重跑都必须**同一份输入、同一套参数**；改参数等于另一次分析，要在报告里说明。
- 连续 3 次同类失败 → **熔断**，停下来向用户报告实际情况并询问，不要继续重试。

## 三、缺失数据引导话术（一次性问清，不要挤牙膏）

用户没给数据时，用下面这种亲和中文，**一次性列全所需字段**，不要一个一个追问。

### 场景：问「这款值不值得做」但没给数据

> 可以算，但我需要几个真实数据，缺一个这结论就不成立 👇
>
> 1. **售价**和**到手价**（有没有券/满减）
> 2. **成本**：货品成本 + 物流/履约成本（元/单）
> 3. **平台佣金率**（不知道就告诉我平台和类目，我按官方费率表查）
> 4. **退货率**（近 30 天，能拿到最好）
> 5. **竞品 3–5 个**：价格 / 月销 / 评分（有竞品链接也行）
>
> 这些数据你后台都能导出（生意参谋 / 京东商智 / 抖店罗盘 / 拼多多商家后台），导出发我就行，我按脚本给你算六维评分和做不做结论。

### 场景：问「保本 ROI 多少」但缺口径

> 保本 ROI 需要先统一口径，给我这三个数就能算准：
>
> 1. **客单价**（支付金额 ÷ 支付买家数）
> 2. **真实毛利率**（扣掉佣金、支付手续费、退货损耗之后的）
> 3. **要不要把固定成本摊进去**（房租人力，摊的话结论会保守一些）
>
> 另外提醒一句：**ROAS 和 ROI 别混着用**，平台后台和广告后台的归因窗口不一样，混算出来的保本值没有意义。你要哪一版，我按那一版算。

### 场景：结算单对账但文件字段不全

> 对账要能定位到每一笔，导出时请包含这几列：
>
> **订单号 / 支付金额 / 退款金额 / 佣金 / 平台补贴 / 广告费 / 结算金额 / 下单时间**
>
> 缺「退款金额」就没法查退款大于销售额，缺「广告费」就没法查零销售额却有费用。导出发我，我按 C1–C9 九类逐条给你金额影响。

### 场景：要文案但没给产品信息

> 写之前得先知道在卖什么 🙋‍♀️
>
> 1. **产品名 + 核心卖点**（1–3 个，最打动人的那个放第一）
> 2. **目标人群**（谁买、什么场景用）
> 3. **价格 + 有没有促销机制**
> 4. **平台**（不同平台标题写法和违禁词口径不一样）
> 5. 有没有**禁用词**（比如不想提「治疗」这种）
>
> 给我这些，我写完直接过一遍违禁词检测再给你。

## 四、联网调研降级链（查不到怎么办）

需要外部数据（类目行情、竞品公开数据、平台规则）时按此链逐级降级，**每一级都要如实标注**：

```
① 用户提供的后台导出 / 已给的数据        → S1，最优
        ↓ 没有
② 本 Skill 参考文档（platform-traffic / commission-rates 等）
        ↓ 不够 / 需现势数据
③ web_search 公开检索                    → S3，须注明出处与日期
        ↓ 检索失败或不可用
④ 明确告诉用户「查不到」并给获取路径       → 记为 DATA_MISSING，**禁止用经验值填补**
```

**禁止**：为了凑齐报告而把 S4 推算值伪装成 S3/S1；检索失败后自行编造数据。

**必须**：检索类数据标注来源 URL + 抓取日期；同一数据多渠道不一致时，全部列出并说明差异，由用户裁定。

## 六、如实报告（不许粉饰）

以下情况必须**原样告知用户**，不得修改输入或重算来掩盖：

- 脚本返回错误 → 如实转述错误信息，给最小恢复步骤
- 计算结果与预期相反（比如看着能赚钱实际亏损）→ **这正是要报告的事实**，不准调整数据重算到「好看」
- 专家之间结论冲突 → 列出冲突双方与依据，走仲裁顺序（真实数据 > 脚本输出 > 平台口径 > 专家推算 > 经验值），**不删掉任一方意见**
- 数据来源不足导致某些结论无法给出 → 写 `DATA_MISSING`，并说明要什么数据才能补上

## 七、不可逆 / 对外动作确认清单（R19）

借鉴 ALITA 的审批档位设计：不管处于哪一档，以下动作**都必须先停下来问用户**，且**拒绝后不得绕道**。

### 必须先确认（任一命中即停）

| 类别 | 典型动作 |
|---|---|
| 对外发 | 发布/上架商品、改价、对外发消息或邮件、提交平台审批 |
| 花钱 | 调整投放预算、出价、充值、付坑位费 |
| 删改不可逆 | 批量删除/覆盖、清空、丢弃已完成的改动 |
| 无人值守 | 设置定时/后台自动任务、自动盯群回复 |
| 引入外部能力 | 装外部脚本/工具、交给外部代理执行 |
| 后果不清 | 任何说不清影响面的操作 |

### 确认时要说清三件事

1. **在哪、做什么** —— 「在【淘宝店 A】把【SKU-123】的价格从 129 改成 99」
2. **为什么问** —— 「这一步会改变在售商品售价，影响的订单与活动不可撤销」
3. **会影响 / 不会影响** —— 「影响：正在进行的满减活动叠加；不影响：已下单订单」

### 三条硬规矩

- **拒绝即停止**：用户点「不允许」，这一步就不做，**不许换一个法子绕过去**。
- **无人回应则跳过**：等不到回应时，这一步不做，并在收尾列出「**这几步有风险我没做，等你决定**：…」，不算用户拒绝。
- **中断期间不做副作用动作**：任务暂停/后台/中断期间，一律不执行对外、花钱、删除类步骤。

## 八、交付前回读核对（R20）

「装完回读一遍，查过了才说装好」——做完不等于做完，要回读验证。

### 报告交付前的回读清单

- [ ] 打开生成的 PDF，核对**关键数字**与 spec 里的数值一致（不是「应该一致」，是逐个看）
- [ ] 核对**图表数量**与**表格数量**达到预期（用 `pdf_verify.py` 的 `--charts` / `--tables` 卡住）
- [ ] 抽查**中文文本层可复制**（验真项已覆盖，仍建议实际选中一段确认）
- [ ] 报告里的日期、区间、口径说明与实际数据一致
- [ ] 有 `DATA_MISSING` 的项已在报告中列出，没有被数值悄悄顶替

### 核不动时怎么说

某项实在无法核实（例如用户给的是截图、数据无法复算）→ **明说「未确认」**，并写清为什么没法确认、要什么才能确认。

❌ 禁止：把「没核对」说成「已核对」，把「截图读数」说成「后台导出数据」（那会把 S2 伪装成 S1，违反 R15）。

## 九、批量变更预演（R25）

借鉴 QM-CLAW `ecommerce` 技能的店铺操作守则：**批量操作默认 dry-run，先出预览再让人确认。**

### 预演清单（执行前逐条走）

- [ ] 明确 `action`：`price_update` / `publish` / `unpublish` / `update` / `delete`
- [ ] 用 `batch_plan.py` 生成「变更前 → 变更后」对照预览
- [ ] 风险标记全部看完：**P0 清零**后才谈执行

```bash
PY="python3"
S="<skill-dir>/scripts"
"$PY" "$S/batch_plan.py" --data plan.json --csv-out preview.csv
```

### 风险规则（脚本自动标记）

| 级别 | 情形 |
|---|---|
| **P0** | 降价幅度 >30%（可能击穿成本 / 影响活动价） |
| **P0** | 有库存却要下架或删除 |
| **P0** | SKU 重复 |
| **P0** | 变更后价格 ≤ 0 |
| P1 | 涨价幅度 >50% |
| P1 | 无标题（不便人工核对） |
| 跳过 | 缺 SKU / 缺变更前后值 / 变更前=变更后 |

### 三条硬规矩

1. **绝不推断删除** —— 数据里缺一行，只当「跳过」，**不产生任何未声明的 delete**。只有 `action=delete` 才有删除语义。
2. **只出预览，不代执行** —— 不登录店铺、不点后台、不调平台 API。执行交给用户在平台后台完成，或用户明确授权后再动。
3. **留痕且可回滚** —— 保留原始导出文件；变更文件另存并带时间戳；每行记录变更前与变更后两个值，随时可回滚。

### 与 R19 的关系

R25 是 R19 在**批量场景**下的具体化：R19 管「要不要问」，R25 管「问之前先把预演做出来」——带着对照预览和风险清单去问，用户才判断得了。
