# 追问维度定义

每个场景有一套独立维度。追问过程中持续追踪当前场景的全部维度，不按顺序问，跟着对话自然走。收口前每个维度必须有实质内容或被标记为「未明确」。

---

# 场景一 · 经验萃取（K1–K5）

## [K1] 事件锚点

**要收集的内容**：一个具体发生过的事件，含时间、场合、涉及的人。

**有实质内容的判断标准**：对方说出了一件可定位的具体事，而不是一类事的概括。

```
[有效] 「去年 11 月那个客户要临时改需求，我们已经开发了一半。」
[无效] 「我平时经常处理这种客户改需求的情况。」（是一类事，不是一件事）
```

## [K2] 关键动作

**要收集的内容**：在那个事件里，本人具体做了什么，按顺序。

**有实质内容的判断标准**：出现可观察的动作，有主语有动词，不是心理活动。

```
[有效] 「我先把改动列成清单，标了工时，然后拉他们项目经理单独开了半小时会。」
[无效] 「我就是耐心沟通，稳住客户情绪。」（无具体动作）
```

## [K3] 判断依据

**要收集的内容**：当时为什么这么做，依据什么信息做的判断，有没有考虑过别的做法。

**有实质内容的判断标准**：说出了做决定时依赖的具体信息或标准。

```
[有效] 「因为看到他们项目经理才是真正拍板的人，对接人做不了主。」
[无效] 「凭经验吧。」
```

## [K4] 例外情况

**要收集的内容**：同样的做法在哪次不管用，那次和成功的那次有什么不同。

**有实质内容的判断标准**：说出了一个反例，或明确说「没遇到过失手的情况」。

```
[有效] 「有一次对方是集团采购统一定的，怎么谈都没用，那次没有能拍板的人。」
[有效] 「这套一直有效，没失手过。」
[无效] 「偶尔也有不行的时候吧。」（无具体反例）
```

## [K5] 可复用规律

**要收集的内容**：几次经历放在一起有什么共同点，什么条件下这套做法成立。

**有实质内容的判断标准**：跳出单个事件，说出了跨事件成立的做法或前提条件。

```
[有效] 「说白了就是先找到能拍板的人，找不到就别急着谈方案。」
[无效] 「就是要灵活应变。」
```

# 场景二 · 价值梳理（V1–V5）

## [V1] 服务对象

**要收集的内容**：谁在用、谁在买、谁最终受益，三者是不是同一批人。

**有实质内容的判断标准**：说出了具体的对象类型，不是「所有人」「各行各业」。

```
[有效] 「主要是本地做外贸的中小厂，二三十人规模，老板自己管财务那种。」
[无效] 「面向所有有需求的企业。」
```

## [V2] 具体交付

**要收集的内容**：对方最终拿到手的是什么，以什么形式交付。

**有实质内容的判断标准**：说出了可指认的交付物或可观察的服务动作。

```
[有效] 「每月给一份现金流预警表，超阈值当天电话通知。」
[无效] 「提供专业的一站式服务。」
```

## [V3] 差异化对照

**要收集的内容**：同样这件事别人怎么做，你们的做法哪里不一样，这个不一样是怎么形成的。

**有实质内容的判断标准**：出现了具体的参照物和可比较的差异点。

```
[有效] 「一般代账公司月底才出报表，我们是每周对一次账，所以问题当周就能发现。」
[无效] 「我们更专业、更用心。」
```

## [V4] 可验证结果

**要收集的内容**：对方用了之后发生了什么变化，有没有可指认的结果。

**有实质内容的判断标准**：出现了具体案例、数字或第三方可确认的事实。

```
[有效] 「有个客户去年靠这个提前两个月发现应收账款有问题，追回了八十多万。」
[无效] 「客户反馈都很好。」
```

## [V5] 适用边界

**要收集的内容**：什么情况下这套不适用，什么样的客户不适合。

**有实质内容的判断标准**：说出了明确的不适用条件，或明确说「没有限制」。

```
[有效] 「上市公司不行，他们有自己的审计流程，我们插不进去。」
[无效] 「基本都能做。」
```

# 场景三 · 方案生成（A–F）

## [A] 业务背景

**要收集的内容**：现在有什么问题、为什么现在要做、不做会怎样。

**有实质内容的判断标准**：说出了一个具体的现状问题，不是「想做 xxx」而是「现在 xxx 有问题」。

```
[有效] 「我们客服一天处理 1000 个工单，80% 是重复问题，人力成本太高。」
[无效] 「我想做一个 AI 系统。」（这是解决方案，不是业务背景）
```

## [B] 核心功能

**要收集的内容**：要能做什么，哪些必须有，哪些可以后做。

**有实质内容的判断标准**：说出了至少一个具体功能点，并区分了优先级。

```
[有效] 「必须能自动回复重复工单，数据分析后台后面再说。」
[无效] 「功能要全，用户体验要好。」
```

## [C] 用户群体

**要收集的内容**：谁来用、大概多少人、主要在哪个部门或场景下用。

**有实质内容的判断标准**：说出了使用对象的身份和大致规模。

```
[有效] 「内部客服团队用，大概 30 个人，还有运营偶尔看数据。」
[无效] 「用户用。」
```

## [D] 技术约束

**要收集的内容**：有没有现有系统要对接、数据在哪、有没有内部技术团队。

**有实质内容的判断标准**：说出了现有系统或数据情况，或明确说「没有任何现有系统」。

```
[有效] 「有个老的 CRM，MySQL 数据库，数据比较乱，没人整理过。」
[有效] 「没有任何现有系统，从零开始。」
[无效] 「应该有一些数据吧。」
```

## [E] 时间与预算

**要收集的内容**：什么时候要上线、预算范围。

**有实质内容的判断标准**：给出了时间或预算中任意一个的具体范围，哪怕是「大概」。

```
[有效] 「最好三个月内上线，预算 50 万以内。」
[有效] 「时间不急，但预算不能超过 30 万。」
[无效] 「尽快吧，预算看情况。」
```

## [F] 验收标准

**要收集的内容**：做到什么程度算成功、用什么指标衡量、有没有红线。

**有实质内容的判断标准**：说出了一个可以判断成败的标准，或说出了红线。

```
[有效] 「自动处理率达到 70% 以上，用户满意度不能下降，这是红线。」
[有效] 「只要客服工单量减半，我就认为成功了。」
[无效] 「做好就行，用户满意就行。」
```

# 维度覆盖规则

适用于全部三个场景：

- 对方给出实质内容 → 标记为已覆盖，填入原话概括（不超过 20 字）
- 同一维度追问 ≥ 2 次仍说不清 → 标记为「未明确」，不再追问，视为覆盖
- 当前场景全部维度覆盖（含「未明确」）→ 满足收口条件
- **已覆盖的维度不得退回 null**。维度状态只能从 null 变为有值。
