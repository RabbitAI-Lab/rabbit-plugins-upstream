# 踩坑清单

这一节全部来自真实项目的失败记录。每一条都导致过返工，按出现频率排序。

---

## 1. 用户改过的文件，绝对不要整体重建

**症状**：用户说"我改了一些内容，别覆盖"，你仍然用 build 脚本重新生成 → 用户的修改（学院名、学号、改写的句子）全部丢失。

**原因**：生成脚本里存的是你上一次写的文本，不是用户当前的文件。

**修复**：

- 先 `Copy-Item` 备份，文件名带时间戳。
- 用 `python-docx` 读**当前文件**，取出实际文本作为基准。
- 只做**精确字符串替换**，每条替换前 `assert old in text`，命中失败就中止且不保存。
- 需要调整版式时，改段落属性（字号、行距、缩进），**不要重写段落文本**。
- 只有在改动面超过一半、且用户明确同意时，才重建整个文档。

---

## 2. 控制台会把中文显示成乱码，让你误判文件坏了

**症状**：`Get-Content` 或 `print()` 输出一片 `宸ョ▼浼︾悊`，看起来文件编码坏了，于是你去"修复"一个其实没坏的文件。

**原因**：Windows 终端代码页与文件编码不一致。**文件本身可能是好的，乱码只发生在显示环节。**

**修复**：

- 不要用眼睛判断编码。用 Python 读，`print(len(s))`、`print(s[:20] == "工程伦理")` 这类**布尔断言**判断。
- 需要看内容时，写入一个 UTF-8 文件再用 `read` 工具读，不要经过终端。
- `PowerShell` 里设 `$OutputEncoding=[Console]::OutputEncoding=[Text.UTF8Encoding]::new($false)`，但仍不可靠，最终以断言为准。

---

## 3. PDF 文本层可能是"双重编码"，先诊断再重抽

**症状**：提取出的全是 `宸ョ▼` 这类生僻字，重抽一遍还是一样。

**原因**：PDF 的 ToUnicode 映射把 UTF-8 字节当 GBK 解了一次，重新提取不解决问题。

**诊断与修复**：

```python
raw = open(path, "rb").read()
try:
    s = raw.decode("utf-8")
    print("utf8 ok, chars=", len(s))
except UnicodeDecodeError as e:
    print("need fallback:", e)
```

如果 UTF-8 能解且字面是 `宸ョ▼`，说明是"UTF-8 字节被按 GBK 解释后再次存成 UTF-8"，此时 `s.encode("gbk").decode("utf-8")` 可能还原；解不动就请用户贴文本，**不要硬猜**。

---

## 4. 引用序号重排后，必须与文献表交叉核对

**症状**：正文写 `[1]`，文献表第 1 条却是另一篇。整篇引用错位。

**原因**：占位符的编号基准（写作时的临时序号）与文献表列表位置不一致；或重排用的映射表搞混了"旧号→新号"的方向。

**修复**：加一道**语义断言**，不要只看序号是否连续：

```python
expect = {1: "王健", 2: "方伟", 3: "李正风"}   # 序号 → 期望的第一作者
for n, author in expect.items():
    assert author in refs[n-1][:20], (n, refs[n-1])
```

再加一道顺序断言：

```python
seen = []          # 正文首次出现顺序
assert seen == list(range(1, len(refs) + 1))
```

两道都过，才敢交付。

## 5. "近 N 年文献占比"会被 URL 访问日期污染

**症状**：算出 68%，实际只有 52%。

**原因**：`[EB/OL]. (2021)[2026-11-10].` 里的访问日期被正则当成出版年。

**修复**：先删访问日期，再取年份（见 `docx-formatting.md` 第四节）。统计完打印**每一条的出版年列表**，肉眼扫一遍。

---

## 6. 时间线要算减法，不要凭印象

**症状**：写"两个月后评级恢复"，实际 5 月下调、6 月恢复，只有一个月。

**原因**：叙述时凭语感，没有真的减。

**修复**：凡涉及"X 个月后""X 年后"，写出两个日期再算。这类错误最容易被老师抓住，而且一抓就是硬伤。

---

## 7. 字数超限不要在最后才处理

**症状**：写完发现 5200 字，限 5000，于是反复删改，每删一处又影响论证。

**原因**：没有在动笔前分配配额。

**修复**：

- 动笔前按章节分配字数，并**预留 300–500 字余量**（因为小标题、标点、后续补引文都会加字）。
- 目标定在区间中上部（如要求 3500–5000，就写 4700 左右），既够分量又留退路。
- 需要加内容时，先想好从哪里减，**成对增删**。

---

## 8. 摘要比正文更容易超标

**症状**：要求 250–300 字，写成 343 字。

**原因**：摘要写成了"问题+方法+案例+结论"四段式全套。

**修复**：

- 摘要压到 280 字左右，留 10–20 字缓冲。
- 同时报"含标点"和"不含标点"两个数，确保两种算法都在区间内。
- 摘要末句不要写"据此，本文主张……"，改成研究结论的陈述句。

---

## 9. Word 重新保存会改变 run 结构

**症状**：用户用 Word 打开保存后，原本一个个干净的 run 被拆成很多段，部分 run 的直接格式被剥离、改为继承 Normal 样式。

**后果**：按原来的 run 索引去改格式会错位；按 `font is None` 判断"格式丢了"会误判（继承样式其实是合格的）。

**修复**：

- 改格式时**遍历段落的所有 run**，逐个设字体字号，不要只改 `runs[0]`。
- 判断格式是否合格，要看**实际渲染值**（继承 Normal 样式也算），不要只看 run 上有没有显式属性。
- 用户编辑后再验证一次，不要沿用编辑前的检查结论。

---

## 10. 参考文献里塞政府公告和网页，会被判"不像文献"

**症状**：文献表 20 条，只有 2 条是期刊论文，其余是标准、政策通知、评级机构网页。

**原因**：取证时优先找了权威源，但"权威"不等于"学术文献"。

**修复**：

- 文献表只放：期刊论文 `[J]`、学位论文 `[D]`、专著 `[M]`、标准 `[S]`。
- 政府公告、机构网页降级为**正文括注**（如"（NHTSA 召回报告 16V-344）"），保持可核验但不占文献位。
- 近 N 年占比靠新发表的期刊论文来凑，不要靠公告凑。

---

## 11. 三级标题容易名存实亡

**症状**：全文只有两处三级标题，看起来像为了凑层级硬加的。

**修复**：开题时就想清楚哪些章需要三级（通常是案例的技术细节部分），让层级分布自然。若全文只有一两处，不如把三级标题的内容并入二级，改用段落首句提示。

---

## 12. 结语写成条目＝报告体

**症状**：结语出现"第一，……。第二，……。第三，……。"或"综上所述"。

**修复**：结语用 2~3 段连贯散文，四步走：回扣问题 → 提炼判断 → 落到实践 → 一句收束。**一篇文章的最后一句话，最好是一个短判断，不是一句总结。**

---

## 13. 用户的"聚焦"要求和评分表可能冲突

**症状**：用户说"只写工程师个体，不要制度"，但课程评分表写着"建议兼顾个体与企业制度两个层面（15%）"。

**处理**：

1. **执行用户指令**（用户是决策者）。
2. **明确告知代价**：哪一项评分可能拿不满，缺口多大。
3. **给一个低成本补救方案**：比如加一小节、两百字，不动主体结构。
4. 不要自作主张替用户兼顾，也不要假装没看见冲突。

---

## 14. 交付时必须报"待核对项"

**症状**：论文交出去，里面有几条文献的译者/版次是推测的，用户不知道。

**修复**：交付时固定输出三样：

1. 文件状态（字数三档、页数、文献条数、近 N 年占比）
2. **待核对清单**（推测项逐条列出，标"请核对"）
3. 修改建议（仍显机械的地方、可再压的段落、答辩可能被追问的点）

**这一条不是可选项。** 用户拿去交的是一份要被打分的文件，不是一份草稿。
