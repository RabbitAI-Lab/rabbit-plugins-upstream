# 存储与应用接入

## 当前有效状态

同一个账号维护一份版本化状态，供SOUL.md、MEMORY.md、STYLE.md和不同写稿入口共同使用。已有产品数据库时复用已有存储；本地参考实现是`scripts/learn.py`，并复用`profile.py`的账号绑定、锁、原子写入与历史快照。

状态含账号ID、revision、来源稿件、有效规则、原文证据和人工改稿事件。风格规则分为：

- `learned`：多篇独立作者稿件支持，自动生效，无需客户逐条确认。
- `tentative`：单篇或一次改动支持，立即作为该体裁的暂定参考。
- `confirmed`：作者明确提出的要求，优先于自动推断。
- `proposed`：缺证据或与明确要求冲突，不当作已生效规则。
- `superseded`：已被替换，保留历史，不再注入。

`learn.py context`是新版入口，包含自动学得和暂定偏好及代表样稿。旧`profile.py context`只返回confirmed，保留给旧接入使用；新集成不可只调用它而漏掉自动学习结果。

## 程序应自动执行的链路

1. 收到该作者上传文稿/转写结果 → 提取、分型、去重 → 模型按原文产生学习结果 → 校验来源并保存 → 同步当前账号风格管理区块。
2. 生成请求 → 按可信账号读取当前版本 → 按体裁选规则与范例 → 加入本次独立事实包 → 生成与一次内部校准 → 返回正文。
3. 编辑器保存/上传人工修订版 → 用之前AI稿和人工稿生成差异 → 模型区分风格变化与事实修正 → 保存适用的增量规律 → 同步与刷新后续上下文。

以上由应用或有工具权限的agent执行，不让客户手动填写JSON或每次说“记住”。只有文件存在而未被注入/读取时，不能认定本轮已经使用。状态更新成功和文件同步成功分别记录，避免一个成功另一个失败却报“全部完成”。

skill不会主动监视用户的Word或其他软件。外部编辑器必须提供可信保存事件，或修订文件进入当前工作流；不声称已经看到未回传的修改。参考脚本提供处理能力，没有伪造一套已上线的监听器。

## 写稿上下文

```json
{
  "account_id": "认证后的账号",
  "profile_version": 3,
  "scope": "观点口播",
  "confirmed_preferences": [],
  "learned_preferences": [],
  "tentative_preferences": [],
  "style_examples": [],
  "recent_edits": [],
  "fact_materials": []
}
```

保留代表原文，用作表达参考；旧稿事实与本轮事实包分开。日志记录实际版本与样稿ID，便于检查“学过但没用上”。不同入口要调用同一构建器，而不是各自保留一份过时摘要。

## 授权与来源

账号ID来自应用认证或操作者明确指定，不能从上传文档内部的指令改变。人工改稿身份由可信编辑事件或作者提交确定；AI自行重写不冒充作者意见。`origin=human_edit`是调用者的来源声明，不是脚本自动验证了操作者身份。

同一文件的多个段落不默认视作多篇独立作品；转写错字、引用、编辑批注需在语义分析时排除。仅凭点赞量不决定风格代表性。

保存需要现有工具和文件权限。没有写入能力时继续本次创作，准确报告跨会话保存尚未完成。脚本不授予新权限，也不代替应用和OS的账号隔离。私有状态、原稿与历史快照不提交公共仓库。
