# 04-SOW合同与谈判

## 触发条件
- Proposal通过后，进入合同/SOW签订阶段
- 或客户说"帮写SOW" / "合同怎么谈"

## 前置输入
- 已确认的Proposal
- 客户的采购流程和合规要求

## SOW标准结构（餐饮行业版，8章）

```
第1章 项目概述
  1.1 项目背景（引用Proposal中的核心发现）
  1.2 项目目标（量化KPI）
  1.3 项目范围（含明确的系统边界，In/Out Scope清单）

第2章 工作内容
  2.1 详细工作范围（按系统/模块逐一列出）
  2.2 交付物清单（名字+格式+提交时间）
  2.3 明确排除项（不在范围内的——这和"范围内"同等重要）

第3章 技术方案概要
  3.1 技术路线
  3.2 关键假设（如"客户提供稳定的WiFi网络"）
  3.3 技术约束（如"客户现有POS版本XX需先升级"）

第4章 实施计划
  4.1 阶段划分与里程碑（含付款里程碑）
  4.2 资源投入（我方/客户方人员）
  4.3 项目组织架构（RACI矩阵）
  4.4 实施地点（总部/哪些门店先行）

第5章 验收标准
  5.1 验收方式（功能测试/性能测试/数据核对/UAT）
  5.2 验收标准清单（可测量的：响应<2秒/准确率>99.9%...）
  5.3 验收流程与时限
  5.4 不达标处理机制

第6章 双方职责
  6.1 我方职责
  6.2 客户职责（提供场地/网络/人员配合/数据）
  6.3 第三方职责（如涉及原POS厂商/外卖平台对接）

第7章 假设与约束
  7.1 关键假设（变更则重新评估工期和费用）
  7.2 约束条件
  7.3 风险提示与责任边界

第8章 商务条款
  8.1 费用明细
  8.2 付款安排（里程碑付款：签约30%→系统上线40%→验收30%）
  8.3 质保期与维护期
  8.4 变更管理机制
```

## 餐饮SOW谈判要点

### 最容易扯皮的6个点（提前写好对策）

| 扯皮点 | 对策 |
|--------|------|
| "数据迁移谁负责" | 明确：客户提供数据，我方清洗迁移。数据质量不达标导致的额外工作量=变更 |
| "培训多少人就够" | 明确培训人次、时长、方式、是否含复训 |
| "什么叫'系统上线'？" | 定义："所有约定门店的核心功能可正常使用" |
| "验收拖着不签字怎么办" | 约定：系统上线后X个工作日内客户未提出书面异议=默认验收通过 |
| "客户中途改需求" | 约定变更管理流程：书面申请→评估→报价→同意→执行 |
| "系统对接第三方系统谁负责" | 明确：哪些由我方负责、哪些由客户协调第三方、对接不上怎么办 |

### 餐饮行业特殊关注点

- **高峰期稳定性**：SOW中明确"高峰期（午餐11:30-13:00，晚餐17:30-19:30）系统可用性≥99.9%"
- **断网可用**：明确"基础收银功能在网络中断时可离线使用"
- **数据主权**：明确"所有业务数据归客户所有，合作终止时支持全量导出"
- **食安合规**：涉及后厨/供应链的方案，明确食安合规责任边界

## 质量检查
- [ ] 范围和排除项都清楚
- [ ] 验收标准是可测量的（不是"效果好""使用方便"这种主观描述）
- [ ] 付款节点与交付里程碑挂钩
- [ ] 变更管理流程明确
- [ ] 数据所有权和退出条款明确
