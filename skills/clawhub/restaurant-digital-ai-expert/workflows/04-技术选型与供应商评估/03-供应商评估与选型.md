# 03-供应商评估与选型

## 触发条件
- RFP收集完成，需要进行最终评审和选型决策

---

## Step 1: 组织评估委员会

### 委员会构成（5-7人）

| 角色 | 职责 | 是否必须 |
|------|------|:---:|
| 业务负责人（如运营总监） | 评估业务需求匹配度 | 必须 |
| 技术负责人（CTO/IT总监） | 评估技术架构和扩展性 | 必须 |
| 财务负责人 | 评估TCO和商务条款 | 必须 |
| 一线用户代表（店长/厨师长） | 评估易用性和实际适用性 | 必须 |
| CEO/老板 | 最终决策 | 大项目必须 |
| 外部顾问（可选） | 专业补充+中立视角 | 推荐 |

> 务必包含一线用户代表。多少餐饮IT项目死在"管理层觉得好，一线用不起来"。

## Step 2: 统一评分标准

### 餐饮供应商7维评分矩阵

详见 `tools/餐饮科技选型决策矩阵.md`

**核心7个维度**：

| 维度 | 权重 | 0分(差) | 1分(及格) | 2分(好) | 3分(优秀) |
|------|:---:|---------|----------|--------|----------|
| **产品功能匹配** | 25% | <50% | 50-70% | 70-90% | >90% |
| **技术架构** | 20% | 单体/老旧 | 微服务雏形 | 成熟云原生 | SaaS+多云 |
| **餐饮行业经验** | 15% | 无经验 | 1-2个客户 | 5+客户 | 同业态标杆 |
| **公司稳定性** | 15% | 初创/<10人 | A轮/20-50人 | C轮/100+人 | 上市/盈利 |
| **服务与支持** | 10% | 远程 | 区域办事处 | 本地团队 | 专属客户成功 |
| **集成与开放** | 10% | 无API | RESTful API | 开放平台 | API+ISV生态 |
| **价格与TCO** | 5% | >预算1.5倍 | 预算1-1.5倍 | 预算内 | <预算80% |

## Step 3: 各家独立评分

### 评分流程（杜绝偏见）

1. **独立评分**：每名评委独立打分，不讨论、不受影响
2. **打分标准化**：使用统一的评分卡（见 `templates/技术选型与供应商评估模板.md`）
3. **强制排名**：每人必须排出1>2>3>...，不允许并列
4. **取均值**：去掉最高分和最低分，取剩余评分的均值
5. **权重加权**：按维度权重加权计算总分

### 评分注意事项

- **不要被Demo吓到**：Demo是精心设计的最佳路径，要问"那XXX场景怎么办？"
- **不要被品牌吓到**：大品牌≠适合你（SAP餐饮版对大排档是灾难）
- **不要被低价诱惑**：看TCO不要看首年费用
- **必须打背调电话**：找3个现有客户（不是供应商指定的）问真实体验

## Step 4: 客户背调

### 背调问题清单

| # | 问题 |
|---|------|
| 1 | 你们用了多久了？多少家门店在用？ |
| 2 | 实施过程中遇到的最大坑是什么？ |
| 3 | 系统故障最严重的一次是什么情况？恢复了多久？ |
| 4 | 供应商响应速度真能达到SLA吗？（不是合同写的，是实际体验） |
| 5 | 系统有什么你当初没想到的"坑"吗？ |
| 6 | 续约时涨价了吗？涨了多少？ |
| 7 | 如果让你重新选择一次，你还会选这家吗？为什么？ |
| 8 | 有什么功能宣传得很好但实际很难用？ |

> 关键技巧：第7个问题是"杀手问题"，能过滤掉90%的"还行"回答。
> 不要问"产品好用吗"这种引导性问题。要问开放式问题，让对方说具体的经历。

## Step 5: PoC/试点验证

### 何时需要PoC？

| 情况 | 需要PoC？ |
|------|:---:|
| 合同金额>100万 | 必须 |
| 涉及核心系统（POS/会员）替换 | 必须 |
| 供应商成立<3年/第一次合作 | 必须 |
| 合同金额<10万且是辅助系统 | 可选 |
| 市场公认的成熟产品（如美团收银） | 可选 |

### PoC设计原则

```
PoC不是"试用一下"，而是"用极限条件验证关键假设"

正确做法：
- 选1-3家门店（含最忙的和最偏的）
- 真实运营2-4周
- 用真实订单量（不要"测试环境"）
- 核心场景全覆盖（高峰/断网/退款/对账...）
- 定义"通过标准"：如POS高峰并发100单/分钟不卡顿
```

### PoC通过标准模板

| 测试场景 | 通过标准 | 实测结果 | 通过？ |
|---------|---------|---------|:---:|
| 午高峰收银 | 60单/分钟持续30分钟不卡顿 | | |
| 网络中断 | 离线模式正常收银，恢复后数据不丢失 | | |
| 跨平台对账 | 美团+饿了么+堂食自动对账，差异率<0.1% | | |
| 会员数据迁移 | 10万会员数据迁移，丢失=0 | | |
| 并发登录 | 50个账号同时登录不超时 | | |
| 报表生成 | 100家门店日报5分钟内出 | | |

## Step 6: 谈判与合同

### 谈判策略

| 谈判点 | 目标 | 筹码 | 底��� |
|------|------|------|------|
| 价格 | 拿到最低价 | "我们还在看X家的方案" | 预算上限 |
| 付款节奏 | 3:3:3:1 | "先付3成，上线再付3成" | 4:3:3 |
| 服务 | 专属客户成功经理 | "你们的服务条款不如X家" | 标准服务即可 |
| SLA | 要惩罚条款 | "餐饮高峰宕机是致命的" | 无罚款的非约束SLA不可接受 |
| 数据 | 数据归我方+随时可导出 | "数据安全是我们的底线" | 不可让步 |
| 解约 | 无违约金、数据完整导出 | "我们不想被锁定" | 不可让步 |

### 合同审查重点（法务+顾问联合审查）

- [ ] 数据归属权明确（客户数据归客户，不是归供应商）
- [ ] 解约条款清晰（提前多久通知、数据如何导出、有无违约金）
- [ ] SLA有实际约束力（有监控方式+有处罚条款）
- [ ] 续约涨价有限制条款（避免"签了1年，第2年涨价50%"）
- [ ] 知识产权条款（定制开发部分的IP归属）
- [ ] 供应商被收购或倒闭时的数据迁移方案
- [ ] 争议解决地为客户所在地（不是在供应商总部）

## 特殊场景指南

### 场景1：2家供应商评分非常接近（<5%差距）

按以下决胜条件顺序：
1. 客户背调结果（最真实）
2. 餐饮行业专注度（更专注 > 更通用）
3. 服务响应速度（本地有团队 > 远程支持）
4. 公司财务健康度（活得过3年的 > 烧钱换增长的）

### 场景2：老板"关系"要指定某家供应商

处理方式：
- 不直接否决（不要挑战老板的面子）
- 做法：让"关系供应商"也走完整评估流程，和其他家一起评分
- 如果关系供应商的得分确实最高 → 没问题，选它（皆大欢喜）
- 如果关系供应商得分倒数 → 把评分矩阵摆在老板面前，用数据说话
- 经验：80%的情况下，数据会让老板自己改变主意

### 场景3：便宜的选不上，贵的选不起

处理方式：
- 扩大RFP范围，找中间带的新供应商
- 和得分最高的2家同时谈价（让它们竞争）
- 重新审视需求优先级，砍掉"锦上添花"的需求，降低总价
