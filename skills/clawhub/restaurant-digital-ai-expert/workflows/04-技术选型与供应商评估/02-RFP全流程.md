# 02-RFP全流程

## 触发条件
- 短名单确定后，需要向供应商正式发出RFP（招标需求书）

## 什么时候需要RFP？

| 情况 | 是否需要正式RFP | 替代做法 |
|------|:---:|------|
| 1-3家店买个POS | 否 | 直接找2-3家Demo对比 |
| 10-50家店买核心系统 | 简易RFP | 1页需求清单+Demo+比价 |
| 50-200家店/合同金额>50万 | 是 | 正式RFP流程 |
| 200+家店/合同金额>200万 | 是（需法务参与） | 完整RFP流程+POC |

---

## RFP文档结构（标准8章）

```
1. 项目背景与目标
2. 项目范围与技术需求
3. 实施与交付要求
4. 服务与SLA要求
5. 供应商资质要求
6. 商务条款
7. 评分标准
8. 响应格式要求
```

---

## 第1章：项目背景与目标

**撰写要点**：
- 简要说明公司/品牌基本情况（门店数/业态/当前系统/痛点）
- 明确项目目标（量化，如"将门店对账时间从30分钟降到5分钟"）
- 说明为什么现在启动这个项目

**模板**：
```
[XX品牌]目前在全国运营[XX]家[业态]门店，年营收约[XX]万元。
当前使用[XX系统]，存在[XX痛点]。
本项目旨在[XX目标]，预期实现[XX量化收益]。
```

---

## 第2章：项目范围与技术需求

**撰写要点**：
- 使用MECE方法列出所有功能需求
- 区分"必须满足(Must-have)"和"加分项(Nice-to-have)"
- 技术需求明确但不限定具体技术方案（给供应商发挥空间）

### 功能需求矩阵模板

| 需求编号 | 功能域 | 需求描述 | 优先级 | 量化标准 |
|---------|-------|---------|:---:|---------|
| F-01 | POS-点餐 | 支持扫码点餐、服务员点餐、自助点餐机 | 必须 | ≤2次点击完成下单 |
| F-02 | POS-支付 | 支持微信/支付宝/银联/会员余额 | 必须 | 支付成功率>99.5% |
| F-03 | POS-退款 | 支持原路退款、部分退款 | 必须 | 退款到账<5分钟 |
| F-04 | KDS-分屏 | 按菜品类型自动分屏到不同备餐区 | 必须 | 延迟<1秒 |
| F-05 | 会员-积分 | 消费积分+积分抵扣+积分兑换 | 必须 | 积分到账延迟<10秒 |
| ... | ... | ... | ... | ... |

### 技术需求模板

| 需求编号 | 技术域 | 需求描述 | 优先级 |
|---------|-------|---------|:---:|
| T-01 | 架构 | 支持云原生部署，支持弹性伸缩 | 必须 |
| T-02 | 容灾 | 99.9%可用性，RTO<1小时，RPO<5分钟 | 必须 |
| T-03 | API | 提供RESTful API，支持OAuth 2.0认证 | 必须 |
| T-04 | 数据 | 支持数据导出，不可锁定数据 | 必须 |
| T-05 | 安全 | 等保二级认证，数据加密传输+存储 | 必须 |

## 第3章：实施与交付要求

| 需求编号 | 实施需求 | 标准 | 备注 |
|---------|---------|------|------|
| I-01 | 实施周期 | <X个月（第X家店上线） | 从签约日起算 |
| I-02 | 培训 | 覆盖所有店长+区域经理 | 含培训手册 |
| I-03 | 数据迁移 | 将X万会员+Y万订单迁移 | 数据丢失=0 |
| I-04 | 试运行 | 先X家门店试运行X周 | 试运行通过标准见附件 |
| I-05 | 推广节奏 | 每周X家门店上线 | 必须支持分批上线 |

## 第4章：服务与SLA要求

| 服务项目 | SLA标准 | 监控方式 | 处罚机制 |
|---------|---------|---------|---------|
| 系统可用性 | ≥99.9%（午晚高峰≥99.95%） | 独立监控工具 | 低一个9扣月费5% |
| 响应时间 | 高峰期页面加载<2秒 | APM工具 | 超标每次扣月费1% |
| 故障响应 | P0故障15分钟内响应 | 工单系统 | 每超30分钟赔500元 |
| 故障恢复 | P0故障<1小时恢复 | 工单系统 | 按分钟赔偿 |
| 客服支持 | 7×12小时在线（午晚高峰必���在线） | 工单系统 | 计入季度评估 |
| 版本更新 | 提前2周通知+非高峰窗口更新 | 发布日历 | — |

### P0/P1/P2/P3分级标准

| 等级 | 定义 | 举例 | 响应 | 恢复 |
|------|------|------|:---:|:---:|
| P0 | 系统不可用/无法收银 | POS全部门店崩溃 | 15分钟 | 1小时 |
| P1 | 核心功能不可用 | 扫码点餐挂了 | 30分钟 | 4小时 |
| P2 | 部分功能异常 | 报表数据延迟 | 2小时 | 24小时 |
| P3 | 轻微问题 | 界面显示小bug | 8小时 | 下个版本 |

## 第5章：供应商资质要求

- [ ] 成立≥3年（降低倒闭风险）
- [ ] 餐饮行业客户≥50家
- [ ] 有同规模/同业态客户案例至少3个
- [ ] 可提供客户推荐（含联系方式，允许背调）
- [ ] 技术团队≥20人
- [ ] 24小时内可到达项目现场
- [ ] 提供最近年度的审计报告或同等级别的财务健康证明

---

## 第6章：商务条款

| 条款 | 要求 | 备注 |
|------|------|------|
| 定价模式 | 订阅制（按门店/按订单/混合） | 一次性买断仅限特殊情况 |
| 付款节奏 | 3:3:3:1（签约:上线:验收:维保） | 可根据项目调整 |
| 合同期限 | 1年+自动续约 | 避免被长期锁定 |
| 退出条款 | 提前3个月通知，无违约金 | 数据必须完整导出 |
| 价格保护 | 续约涨价不超过上一年CPI+3% | 防止坐地起价 |
| 知识产权 | 客户数据归客户所有 | 明确数据处理权限 |

---

## 第7章：评分标准（公开透明）

需在RFP中告知评分权重：

| 评分维度 | 权重 |
|:---:|:---:|
| 产品功能匹配度 | 30% |
| 技术架构与扩展性 | 20% |
| 实施与服务能力 | 15% |
| 供应商实力与稳定性 | 15% |
| 价格与商务条款 | 10% |
| 行业经验与案例 | 10% |

---

## 第8章：响应格式要求

- 截止时间：X年X月X日 X时（北京时间）
- 响应语言：中文
- 文件格式：PDF + PPT（演示用）
- 报价模板：使用附件中的《商务报价模板》
- 问题澄清截止时间：X年X月X日前（只接受邮件提问，统一答复）

---

## RFP全流程时间线

```
T-14天：发送RFP给短名单供应商（3-5家）
T-7天： 供应商问题收集截止、统一电话/书面澄清
T+0天： 供应商提交方案+报价（密封）
T+3天： 内部评审+打分（2-3人独立打分，取均值）
T+5天： 通知2-3家进入第二轮的供应商
T+14天：每家供应商2小时现场演示（包含Q&A）
T+15天：团队讨论+汇总评分+排名
T+16天：通知中标和未中标供应商
T+30天：合同签订
```

## 常见RFP错误 & 避免方法

| 错误 | 后果 | 避免方法 |
|------|------|---------|
| 需求写得太大太泛 | 供应商报价差异巨大，无法比较 | 需求要具体、可量化、可验证 |
| 只比价格不比TCO | 中了低价，后期被服务费宰 | TCO模型覆盖3-5年 |
| 不要求客户推荐 | 被供应商演示"骗"了 | 必填3个可联系的客户推荐 |
| RFP发给不合适的供应商 | 浪费所有人的时间 | 先筛选再发RFP |
| 评分全凭感觉 | 内部撕逼、选错供应商 | 独立打分+强迫排名+取均值 |

## 产出
- RFP正式文档（8章完整版 或 简化版）
- 供应商长名单→短名单→第二轮名单
- RFP进度时间表

## 质量检查
- [ ] RFP中每个功能需求有明确的量化标准（不是"支持XX"而是"在XX条件下XX秒"）
- [ ] SLA有处罚机制（没牙齿的SLA是废纸）
- [ ] 评分权重公开透明
- [ ] 至少要求3个可联系的客户推荐
