# 支付异常排查

保留原 request_id、X-Request-Token、请求体、商户订单号及官方工具返回的支付查询单号。不同类型的单号不可互换；支付宝命令、查询参数及停止条件以当前安装的官方支付 Skill 为准。

## PROXY_TARGET_BLOCKED

检查报错中的目标域名和解析地址。Clash 等代理的 Fake-IP 可能返回保留地址，导致官方支付组件拒绝连接；同时检查 IPv4 和 IPv6，本次真实测试曾分别遇到 `198.18.0.48` 和 `2001:2::30`。权威 DNS 未配置 IPv6 不代表本机不会返回合成的 IPv6 地址。

由环境维护者让目标域名返回真实解析结果，例如调整 Fake-IP 排除配置。仅配置 DIRECT 不一定改变 DNS 结果。不关闭支付组件的地址校验，不把请求改成裸 IP。修复后继续原任务，不重新上传或新建图片订单。

## request expired

先通过官方支付能力核对原支付状态。若曾展示支付入口、用户可能已经付款，或查询失败，不能仅凭网关的 `pending` 判定未付款，也不要自动重新发起支付。

确认未支付且官方流程允许继续时，复用原 ID、令牌和请求体重新 POST `/api/jobs` 获取当前账单，重新核对金额 CNY，再交给官方支付 Skill。保存本次工具实际返回的新链接和查询标识；不使用过期二维码，不假定刷新入口必然产生新订单号。

## 请勿重复绑定／授权页面提示稍后重试

这些提示本身不能证明钱包已经正确绑定，也不能证明 Agent 客户端缺少支付宝签约。授权码是否需要、由何处取得，以官方工具本次返回为准；不自行生成授权码，不把支付二维码当作绑定码。

已有待确认支付时，先按官方支付 Skill 处理原支付状态；只有支付流程明确转交钱包操作时才切换到钱包 Skill。不要自动解绑、反复切换扫码账号或建立新订单来尝试解决。需要用户完成支付宝侧操作时，展示当前有效入口并等待操作结果。

## 支付查询失败

`INVALID_PARAMETER` 等查询错误不能证明付款失败。保留原任务与当前支付查询标识，按官方 Skill 返回错误并停止本轮自动尝试；不要把商户订单号当作支付查询单号，也不要据此提示用户重新付款。

## 已验证行为的范围

2026-11-03，本项目在 Codex 中通过本机官方支付组件完成了媒体处理支付与交付。一次重新发起支付返回了相同支付订单号和新授权支付链接；最终查询返回资源 HTTP 200、`order_status=fulfilled`、`status=completed` 和结果链接。

这验证了该环境的成功路径，不代表所有 Agent 或账号均可直接使用，也没有确定先前授权页面报错的根因。
