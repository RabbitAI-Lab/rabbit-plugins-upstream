# 执行测试 workflow

触发词：`执行测试`、`跑测试`、`运行测试`、`验证测试`

定位：按需能力指令。只处理测试验证和测试记录，不自动补写需求、设计、代码审查或完整任务链。

## 执行步骤

1. 定位当前任务目录；如不明确，先询问任务编号。
2. 读取项目第 4 节测试命令。
3. 如存在 `test-cases.md`，读取测试场景清单；如不存在，基于用户复现步骤、变更文件、错误日志和测试命令确定最小验证范围，并在测试日志中标注“未整理测试用例”。
4. 必要时读取 `design.md`，但不因缺少设计文档自动补写设计。
5. 读取 `ai-pilot/standards/14-test-execution-log-template.md`。
6. 大型项目中优先确定与本次变更相关的最小测试集；需要全量测试时先说明原因。
7. 根据工具能力执行或引导用户执行测试命令。
8. 分析测试结果，区分环境问题、测试数据问题、测试代码问题、业务代码问题和历史遗留问题。
9. 如存在失败，提出修复方案并说明涉及文件；涉及业务规则或高风险逻辑时先提醒人工确认。
10. 自动修复最多 3 轮；超过 3 轮仍失败，停止并输出剩余失败、已尝试方案和人工介入点。
11. 更新 `test-execution-log.md`，记录命令、目录、时间、通过/失败数量、关键错误、修复轮次、未覆盖场景，以及是否存在 `test-cases.md`。
12. 仅在 `test-cases.md` 已存在或用户明确要求时，更新 `test-cases.md` 测试结论；只记录事实，不编造覆盖率。

## 约束

- 不得删除、跳过或弱化已有测试来规避失败。
- 测试日志只记录关键摘要，不粘贴超长终端输出。
- 1DAY级任务没有 `test-cases.md` 时，可以轻量执行验证，不强制补建测试用例文件。
- 单元测试可优先直接执行。
- 集成测试、E2E、数据库迁移测试、依赖外部服务的测试，执行前应说明影响范围和依赖条件。
- 涉及写数据库、调用外部系统、批量任务、消息消费、定时任务或长时间运行的测试，应先提醒人工确认或提供安全替代验证方式。
