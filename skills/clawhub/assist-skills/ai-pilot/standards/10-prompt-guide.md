# Prompt 协作指南

> 日常任务优先使用 `AGENTS.md` 第 15 节定义的快速指令，例如 `初始化项目`、`开始任务：{任务名称}`、`梳理需求`、`开始设计`、`编写测试用例`、`开始编码`、`执行测试`、`审查代码`、`完成任务`。
>
> 本文档作为复杂场景的进阶参考：当快速指令无法表达足够约束时，再使用下面的结构化 Prompt。
>
> `开始任务` 会按任务级别使用不同 context 模板：1WEEK级完整版、3DAY级精简版、1DAY级极简版，并优先由 AI 自动扫描和对话式引导补充。

> `编写测试用例` 后推荐使用 `开始编码`，再使用 `执行测试` 运行测试、分析结果并进入 `审查代码`。

本指南用于帮助使用人员向 Trae、CodeBuddy、Claude Code 和 opencode 提出更清晰、可验证、可沉淀的研发请求。

## 1. 通用结构

推荐使用以下结构：

```text
背景：说明业务场景、目标用户、当前问题。
目标：说明希望 AI 完成什么，不希望 AI 做什么。
输入：列出需求、代码路径、接口文档、日志或截图等材料。
约束：说明技术栈、兼容性、安全边界、交付格式。
输出：说明希望得到哪些文件、表格、代码或测试建议。
验证：说明如何判断结果可用。
```

## 2. 需求澄清 Prompt

```text
请基于以下背景帮我梳理需求，并先提出澄清问题，不要直接给实现方案。

背景：
{业务背景}

已知信息：
{现有需求 / 用户反馈 / 约束条件}

请输出：
1. 需求理解
2. 待澄清问题
3. 初步范围边界
4. 可能风险
```

## 3. 设计方案 Prompt

```text
请根据 requirement.md 生成技术设计草案。

项目技术栈：
{技术栈}

相关代码路径：
{路径}

请输出：
1. 方案概览
2. 影响范围
3. 数据流 / 调用链
4. 接口或数据库变更
5. 风险与回滚建议
6. 需要人工确认的问题
```

## 4. 编码 Prompt

```text
请基于 design.md 实现以下范围内的代码变更。

限制：
- 只修改以下路径：{路径}
- 不处理生产密钥、Token、连接串
- 不改变既有公共接口，除非 design.md 已明确说明

请完成后输出：
1. 修改文件列表
2. 关键实现说明
3. 测试建议
4. 风险点
```

## 5. 测试用例 Prompt

```text
请基于 requirement.md 和 design.md 生成测试用例。

请覆盖：
1. 正常流程
2. 异常流程
3. 边界条件
4. 权限和数据范围
5. 回归测试点

输出为 Markdown 表格，并标注优先级。
```

## 6. 测试执行 Prompt

```text
请执行本项目测试命令，并根据输出分析测试结果。

任务目录：
{ai-pilot/poc/TASK-xxx}

请先读取：
1. AGENTS.md 第 4 节测试命令
2. 当前任务的 test-cases.md
3. 相关测试代码

请完成：
1. 运行测试命令并保留关键输出
2. 统计通过 / 失败用例
3. 分析失败原因，区分测试代码问题和业务代码 Bug
4. 如需修复，先说明修改文件和修改点，等待确认
5. 修复后最多重新运行 3 轮，超过后提示人工介入
6. 对照 test-cases.md 检查自动化测试覆盖情况
7. 生成或更新 test-execution-log.md，记录命令、执行时间、输出摘要、失败修复记录和覆盖情况
8. 更新 test-cases.md 第 9 节“测试结论”
```

如果当前工具无法直接执行命令，可以改用：

```text
请告诉我需要运行的测试命令。我会在本地终端执行，并把输出粘贴给你，请你继续分析失败原因、覆盖情况，并更新 test-execution-log.md 和 test-cases.md 测试结论。
```

## 7. 代码审查 Prompt

```text
请对以下变更进行代码审查，优先关注 bug、回归风险、安全问题和缺失测试。

变更范围：
{文件 / diff / PR}

请按严重程度输出：
1. 问题清单（含文件位置）
2. 风险说明
3. 修改建议
4. 测试补充建议
```

## 8. 常见反模式

| 反模式 | 问题 | 改进方式 |
|---|---|---|
| “帮我做一下这个功能” | 目标、范围、验收标准都不清楚 | 补充背景、输入、约束和输出要求 |
| “直接改代码” | 容易跳过需求澄清和设计 | 先要求 AI 复述理解并列出待确认点 |
| 粘贴生产日志 | 可能泄露敏感信息 | 先脱敏，再说明字段含义 |
| 不指定路径 | AI 容易扩大修改范围 | 明确允许读取和修改的目录 |
| 不要求验证 | 结果难以评审 | 要求输出测试方式和风险点 |

## 9. 工具使用差异

| 工具 | 建议 |
|---|---|
| Trae | 自动读取项目根目录的 `.trae/rules/poc-rule.md`（由技能包 `rules/trae-poc-rule.md` 复制改名落地），推荐作为首选工具，适合结合项目规则进行交互式开发 |
| CodeBuddy | 适合结合项目规则进行代码生成、审查和改造建议 |
| Claude Code | 适合多文件修改、命令验证和长链路任务，需要保持 `CLAUDE.md` 指向 `AGENTS.md` |
| opencode | 优先读取 `AGENTS.md`，适合按项目级规则持续执行任务 |
