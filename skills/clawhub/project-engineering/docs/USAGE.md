# 使用手册

## 推荐提示词结构

```text
使用 $project-engineering。

目标：要完成什么。
模式：新项目架构 / 工程基线 / 只读分析 / 方案设计 / 直接开发 / 故障诊断 / 代码审查 / 验收交付。
范围：允许修改的模块、明确不做的内容。
验收：完成标准和必须运行的检查。
外部操作：是否允许提交、推送、建 PR、迁移或部署。
```

目标和验收通常比“请写得优雅”更有价值。没有写出的外部操作权限不会因为调用 Skill 而自动获得。

## 新项目架构与工程基线

```text
使用 $project-engineering。

这是一个全新项目，当前只做架构与工程基线设计，不创建代码。
目标：说明核心用户、首期业务结果和明确不做的内容。
约束：说明技术栈偏好、运行环境、部署、安全、团队和交付条件。

请区分已确认约束、暂定假设和待决策项，并输出：
1. 首期范围与验收边界；
2. 技术选择及理由；
3. 部署单元、模块职责和依赖方向；
4. 核心数据、API、身份权限、成功链和失败链；
5. 构建、配置、日志、测试、CI 和交付基线；
6. 第一个可运行、可验证的纵向切片。

不要虚构流量、外部协议或已经验证的环境能力；
不要创建文件、初始化 Git、配置远端或部署。
```

如果希望直接创建项目，把模式改成“创建并实现最小纵向切片”，给出目标目录和验收命令，并单独说明是否允许初始化 Git、提交、推送或部署。

## 第一次使用：5 分钟只读验证

先用一个不会修改仓库或外部系统的任务验证 Skill 是否真的在“读项目”，而不是复述 README：

```text
使用 $project-engineering。

只读验证当前仓库：选择一条真实业务入口（HTTP、CLI、消息或定时任务），
追踪到数据库写入或外部副作用。输出：
1. 入口文件与方法；
2. 完整调用链及每一步职责；
3. 身份权限、事务边界和状态权威源；
4. 一条正常路径与一条失败路径；
5. 现有测试覆盖、已经证明的能力和仍未验证的部分。

每条关键结论附文件路径、配置、命令输出或测试证据。不要修改文件，不执行会写入外部状态的命令。
```

验收时重点检查：

- 是否完整读取了当前路径适用的仓库规则，而不只是根 README；
- 是否从真实入口追到数据或外部副作用，而不是根据类名猜测；
- 是否能区分设计文档、当前代码和自动测试各自证明了什么；
- 是否明确失败、超时、权限或状态冲突路径；
- 是否保持工作区不变，并说明没有执行哪些外部操作。

这个案例可以直接用于 Spring Boot、Node.js、Python、Go、Rust、.NET 或混合技术栈仓库。若项目没有业务入口，可改为追踪一个构建、发布或数据处理入口。

## 项目梳理

```text
使用 $project-engineering。

只读理解当前仓库。基于真实代码而不是 README 猜测，输出：
1. 产品定位和项目类型；
2. 技术栈、构建与包管理；
3. 模块、产物、运行进程和部署形态；
4. 核心数据、外部系统和权限边界；
5. 一条关键正常链路和一条失败链路；
6. 设计、实现与验证之间的差异；
7. 当前主要工程风险。
不要修改任何文件。
```

## 架构方案

```text
使用 $project-engineering。

为当前项目设计“通知中心”。只做设计，不编码。
先确认现有模块和可复用接口，再给出职责归属、依赖方向、
主调用链、失败链、数据权威源、接口/事件、兼容迁移、测试和回退。
比较可行方案，但给出一个明确推荐。
```

## 直接开发

```text
使用 $project-engineering。

实现“批量导出巡检记录”。
先给出最小范围、调用链、影响文件和关键决策，然后直接编码。
保留工作区已有修改，遵循现有项目风格，运行相关模块测试。
不要提交和推送。
```

## API、消息或协议演进

```text
使用 $project-engineering。

为订单状态回调增加失败原因字段。
检查所有生产者、消费者、Schema、版本、未知字段策略、幂等、
顺序、重复、超时、重试、模拟器、契约测试和发布顺序。
兼容旧客户端，不虚构尚未确认的外部协议能力。
```

## 数据库变更

```text
使用 $project-engineering。

新增设备维护状态及审计记录。
先检查真实迁移机制、已有编号、配置、历史表以及代码和文档中的
预留引用；覆盖新安装、存量升级、约束、索引、回填、发布顺序、
测试 Schema、备份和回退。发现编号冲突时不要自行占用。
```

## 高影响功能

```text
使用 $project-engineering。

审查语音控制机器人功能，只读，不修改代码。
按 L4/L5 深度检查所有入口、服务端身份、权限、目标和状态复核、
控制权仲裁、确认、幂等、审计、结果未知、失败关闭和真实环境验收。
明确哪些结论是设计、代码事实、自动测试或真机验证。
```

## 代码审查

```text
使用 $project-engineering。

审查从 main 到当前分支的变更，只报告可操作问题，不修改代码。
分别检查需求符合性、项目规范、架构边界、数据兼容、安全可靠性、
测试证据和交付完整性。每个问题给出精确文件位置、触发条件和影响。
```

## 验收与交付

```text
使用 $project-engineering。

验收当前功能并整理交付报告。运行与风险相称的检查，分别报告：
设计完成、代码完成、自动验证、集成环境验证和真实环境验收。
列出实际文件、调用链、测试命令与结果、未验证项、风险、回退方式，
以及是否已经提交、推送或发布。
```

## 自动匹配与显式调用

支持隐式匹配的 Agent 可以根据 `description`，在新项目架构与工程基线、现有项目跨文件开发、重构、审查或交付等任务中自动选择本 Skill。对于重要任务，推荐显式写出 `$project-engineering`，这样可以避免同类 Skill 之间的路由歧义。

Skill 默认跟随用户当前使用的语言；语言选择不改变仓库规则、安全边界或验证要求。

单文件纯文案、格式调整或完全确定的机械替换不需要这套完整流程；Skill 会采用轻量路径，或由 Agent 直接处理。
