# 实现、数据与验证

## 1. 先继承项目约定

从构建清单、格式配置、相邻代码、测试和贡献规范确定：语言/运行时版本、命名、依赖注入、错误处理、DTO/实体习惯、目录、日志、注释和测试框架。不要把某一语言或框架的偏好写成通用规则。

全新项目不存在可继承约定时，依据已确认的产品目标、运行环境、组织标准和生态惯例建立最小基线，并把关键约定落实到构建清单、目录、格式/静态检查、测试入口、配置和 CI 等可执行载体。说明选择理由和待决策项，不把新决定伪装成仓库原有规范。

相邻代码只能证明现状，不能自动证明最佳实践。遇到明显的安全、兼容或维护问题时，指出证据并采用与本次范围相称的改进，不机械复制缺陷，也不借机全库重写。

## 2. 变更影响矩阵

| 变化 | 至少检查 |
|---|---|
| 新业务能力 | 职责归属、公开边界、数据、权限、配置、测试、用户文档 |
| API/CLI | 输入校验、身份、错误、兼容、文档、客户端/调用方 |
| 消息/事件/协议 | 双端模型、版本、顺序、重复、超时、重试、模拟器、契约测试 |
| 数据结构 | 权威 Schema、迁移、索引、约束、回填、回退、测试数据库 |
| 外部服务 | Adapter、密钥、限流、超时、重试、熔断/降级、审计、成本 |
| 状态机/异步流程 | 合法转换、并发、幂等、取消、补偿、结果未知、可观测性 |
| 权限/多租户 | 服务端身份、资源归属、最小权限、越权测试、审计 |
| 公共库/构建 | 所有消费者、版本收敛、可选依赖、发布与根构建 |
| UI/交互 | 正常/空/加载/错误/权限态、可访问性、后端契约、浏览器验证 |

不适用项可以排除，但要基于证据，而不是因为改动文件少。

## 3. 代码与抽象

- 入口层负责协议适配和输入边界；已有集中业务规则时，不要从入口绕过它直写数据库或调用低层副作用。
- 事务放在真正的一致性边界，避免大事务包裹慢外部调用。
- 数据传输、持久化、领域/业务值和外部厂商模型是否分离，取决于变化边界；不要为了层数重复映射同一简单对象。
- 优先不可变值和显式状态；框架要求可变对象时遵循框架生命周期。
- 错误应可分类、可观测、可映射到调用方；禁止吞异常或用模糊成功响应隐藏部分失败。
- 注释解释契约、约束、时序、安全原因和非显然取舍，不重复代码表面行为。
- 日志使用可关联但不敏感的请求/操作标识；异常日志也不能泄漏凭证或完整隐私数据。

## 4. 依赖与版本

1. 先确认依赖由哪个清单、父工程、锁文件或平台 BOM 管理。
2. 优先复用已有依赖和标准库；新增依赖需说明用途、维护性、许可证、体积和安全影响。
3. 更新依赖时同时检查运行时要求、传递依赖、锁文件、弃用 API、配置变化和消费者兼容。
4. 不手工编辑自动生成锁文件；使用项目既有包管理流程。
5. 公共依赖或运行时升级应运行所有受影响消费者的构建，而不只运行修改模块。

网络下载、安装全局工具或修改开发机配置属于额外外部状态；仅在任务需要且授权范围内执行。

## 5. 配置、密钥和环境

- 区分安全默认、开发默认和生产必填；生产不能依赖弱默认值。
- 配置应通过项目现有机制注入，密钥不得写入源码、前端、镜像层、测试资源或版本化配置。
- 可选能力应有明确开关、启动行为和禁用时的错误语义。
- 修改配置同步检查示例、部署清单、配置绑定校验、测试环境和旧配置兼容。
- 不在诊断输出中打印完整环境变量、连接串、Token、私钥或音频/文件内容。
- 发现疑似已跟踪真实凭证时只报告位置和类型，不回显值；建议撤销/轮换并清理历史。

## 6. API、权限与输入

- 先枚举所有入口：HTTP、WebSocket、消息消费者、回调、定时器、CLI、后台任务、调试端点和内部工具。不要因为 HTTP Controller 已鉴权，就假定其他入口具有相同安全过滤链。
- 所有外部输入先做结构和范围校验，再进入业务流程。
- 服务端从认证上下文获得身份、租户和资源归属，不能信任可伪造请求参数。
- 权限检查应靠近业务操作并覆盖间接入口；隐藏按钮不是权限控制。
- 高影响操作在真正执行前重新检查权限、目标和当前状态，避免确认后状态变化。
- 错误码区分无权限、不存在、冲突、非法状态、超时与结果未知，避免调用方盲目重试。
- 变更接口定义 operationId/idempotency key、重复请求返回和保留期限；只读接口也需考虑分页、限流和数据隔离。

## 7. 数据库与迁移

先发现项目使用 Flyway、Liquibase、ORM migration、手工 SQL、云迁移服务还是其他机制，按现有顺序和工具执行，不能假定编号规则。

分配新迁移版本前，必须同时检查迁移目录、构建/运行配置、迁移历史表或锁文件，以及代码和文档对尚未落库迁移的引用；不能仅用“当前最大文件号 + 1”。发现缺号、预留版本、文档引用不存在文件或不同分支迁移冲突时，先查清来源并停止占用该版本。

每次结构变化至少检查：

1. 新安装和存量升级路径。
2. 向前/向后兼容窗口，以及应用和数据库发布顺序。
3. 非空、唯一、外键/业务完整性、索引与查询计划。
4. 大表锁、回填批次、在线 DDL 和失败恢复。
5. 默认值、时区、字符集、精度和枚举扩展。
6. 迁移是否可重复、可恢复或有备份方案。
7. 测试 Schema、夹具、生成模型和文档是否同步。

测试数据库兼容模式不能完全证明生产数据库 DDL、锁和性能安全。高风险迁移要在同类数据库、代表性数据量和备份后的环境验证。

## 8. 并发、幂等与外部副作用

- 使用唯一约束、条件更新或版本列保护本地并发，而不是只靠应用层“先查询”。
- 对消息、回调、任务和命令定义稳定幂等键、重复结果和过期策略。
- 外部调用超时不代表失败；在未知结果下先查询/对账，不能直接重复扣款、发命令或创建资源。
- 自动重试只用于已证明安全的错误和操作，设置上限、退避、抖动与可观测性。
- 事务提交和消息发布之间存在窗口时，根据风险使用 Outbox、可靠队列、补偿或定期对账。
- 取消与超时应终止后续副作用，并说明已经发生的部分如何处理。

## 9. 验证选择

按变更风险从小到大组合：

- 静态检查、格式、类型检查或编译。
- 受影响纯逻辑单元测试。
- 模块/包测试和数据库集成测试。
- 契约、消息、API、浏览器或进程间测试。
- 外部依赖、迁移、故障注入和端到端测试。
- 预发布、生产同类环境或真实设备人工验收。

先从构建清单、CI 和贡献规范提取真实命令，不凭习惯发明 `mvn test`、`npm test` 或 `pytest`。测试失败时诊断根因；不得删除、跳过或弱化有效测试只为得到绿色结果。

报告实际命令、退出结果、被跳过的层次和原因。生成代码、文档或静态资产也应有适合其风险的语法、渲染或行为验证。
