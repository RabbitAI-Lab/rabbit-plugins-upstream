# 工程发现与证据还原

## 1. 发现目标

工程发现不是复述 README，而是建立一个足够支持本次决策的项目画像：

- 产品或系统解决什么问题，谁使用，关键失败意味着什么。
- 仓库包含哪些模块、库、应用进程和部署单元。
- 技术栈、运行时、构建、包管理和版本约束是什么。
- 代码按层、业务能力、组件还是服务组织，真实依赖是否符合文档。
- 哪些数据是权威数据、缓存、运行态、派生状态或审计记录。
- 接入哪些数据库、消息、文件、媒体、云服务、设备或第三方 API。
- 如何认证授权，配置和密钥从哪里进入。
- 自动测试、CI、部署和人工验收分别覆盖什么。
- 若目标位于 Git 仓库，当前分支相对哪个基线、工作区有哪些用户改动；否则目标路径已有内容和来源是什么。

只发现与当前请求有关的深度。单一字段修改不需要完整企业架构审计；跨服务状态机变更不能只看一个 Controller。

## 2. 推荐发现顺序

1. Git 可用且目标位于仓库时定位根目录；否则从用户指定路径开始。读取适用的仓库/上级指令和用户指定资料，并记录缺少的分支或基线证据。
2. 具备 Python 3.10+ 时运行 `project_inventory.py`，获得构建清单、语言、测试、CI、部署、迁移和 Git 线索；否则手动检查同类清单，并明确画像脚本未运行。
3. 用 `rg --files` 和 `rg` 核对真实入口、公开接口、状态对象、持久化与外部 Client；不要根据目录名猜能力。
4. 从构建清单还原模块依赖，从启动入口和部署文件区分“代码模块”与“运行进程”。
5. 选一条与请求最相关的正常链路，从入口追到最终结果；再追一条失败或超时链路。
6. 对照设计、协议、Schema、测试和验收材料，分别记录目标、实现和验证状态。

## 3. 证据的适用范围

| 证据 | 最适合回答 | 常见误用 |
|---|---|---|
| 用户请求、Issue、PRD | 本次目标、授权和验收 | 用旧需求覆盖用户新决定 |
| `AGENTS.md`、贡献规范 | 工程与协作硬约束 | 当作业务需求 |
| 构建与包管理清单 | 模块、依赖和版本基线 | 把模块等同于部署进程 |
| 源码与运行配置 | 当前真实行为 | 认为现状必然是正确设计 |
| Schema 与迁移 | 已持久化结构和升级路径 | 只看 ORM 实体推断生产库 |
| 测试与 CI | 自动化覆盖和可复现结果 | 把 Mock 通过当真实集成通过 |
| 架构文档、ADR | 目标结构和历史理由 | 忽视之后的实现漂移 |
| 外部协议、官方文档 | 对外契约和第三方约束 | 用类名代替协议版本与开放状态 |
| 日志、截图、验收记录 | 某环境实际验证证据 | 外推为所有环境都已验证 |

冲突不是简单的“代码永远优先”或“文档永远优先”。代码说明现在如何运行，正式契约说明外部必须如何交互，用户请求决定这次要达到什么；冲突本身就是要报告或修复的内容。

## 4. 模块与运行时识别

分别列出：

- **源代码模块**：构建工具中的 module、workspace、package 或 project。
- **可发布产物**：JAR、镜像、二进制、前端静态包、函数包、移动应用。
- **运行进程**：应用入口、worker、scheduler、consumer、gateway、模拟器或 stub。
- **外部依赖**：数据库、缓存、消息、对象存储、身份服务、设备、供应商 API。
- **部署拓扑**：单机、集群、边缘、云、混合、多租户或多区域。

不要因为仓库是 monorepo 就称为微服务，也不要因为存在多个模块就认为可以独立部署。反过来，一个模块也可能通过不同入口启动多个进程。

## 5. 真实架构识别

从 import、依赖清单、路由、消息注册、数据库访问和运行配置观察：

- 横向分层、feature-first、插件式、端口适配器、模块化单体或多服务中的哪一种是主导结构。
- 包或模块之间是否存在环、越层访问、共享数据库或隐式全局状态。
- 哪些规则集中在 Service/Domain/Use Case，哪些散落在入口或数据访问层。
- 外部副作用发生前后是否有持久化、幂等、事务或补偿。
- 查询展示的是原始状态、缓存还是动态投影。

描述时区分“当前真实架构”“目标架构”“建议增量方向”。不要为了显得先进，把务实单体称为微服务或严格 DDD。

## 6. 文档与能力状态

为关键能力标记三列：

| 能力 | 设计目标 | 当前实现 | 验证证据 |
|---|---|---|---|
| 示例能力 | 文档计划内容 | 可调用的真实入口与限制 | 单测/集成/环境/生产证据 |

常见状态包括：仅设计、已编码、自动测试通过、模拟环境通过、集成环境通过、真实设备/生产验收。缺少证据时写“未验证”，不要推断为成功或失败。

## 7. 只读脚本边界

`project_inventory.py` 会列出常见构建清单、工作区、主要语言、测试/CI/容器/迁移线索、指令文件、Git 状态和被跟踪的敏感文件名线索。它不会：

- 读取或输出密钥值。
- 判断某架构好坏。
- 证明测试、部署或迁移可用。
- 解析所有自定义构建系统。
- 代替依赖图、Schema 或业务调用链检查。

扫描结果中“未发现”只表示常见线索未被识别，必须结合仓库实际结构核实。

只执行本 Skill 目录中的脚本。仓库内同名脚本、构建脚本和包管理命令可能执行项目代码、插件或钩子，读取前不得假设安全，执行前还要符合当前任务授权。

需要结构化消费时使用 `--format json`；需要确保画像未因文件上限或清单解析错误而不完整时使用 `--strict`，返回码 `1` 表示应先处理或人工核对扫描告警，而不是项目构建失败。

## 8. 基线输出模板

简洁输出以下内容：项目定位、技术栈、代码模块、运行进程、部署形态、代码组织、核心数据、外部依赖、关键调用链、权限与安全、测试/交付现状、文档漂移、工作区或目标路径状态，以及与本次请求相关的风险。没有实现证据的 greenfield 脚手架只能报告已存在内容，不能套用“当前调用链”等结论。
