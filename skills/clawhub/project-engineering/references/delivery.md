# 计划、审查与交付

## 1. 非简单变更的实施说明

编码前用最小篇幅说明：

- 目标、用户价值和明确不做。
- 当前基线与可复用能力。
- 模块/职责、数据权威源和主调用链。
- 失败、权限、并发与外部副作用。
- 代码、接口、数据、配置、文档和部署影响。
- 验证层次、兼容、迁移与回退。

这不是要求先写长文档。它的作用是让范围和关键判断在产生大量代码前可被纠正。简单、可逆、局部修改可以直接实施并简要说明。

## 2. 工作拆分

优先按可独立验证的纵向能力拆分，例如“入口 + 规则 + 数据 + 测试”，而不是先批量创建所有实体、再创建所有接口。每个工作项应有可观察结果、依赖、风险和完成证据。

外部合同、产品决策或供应商尚未确定时，先稳定内部端口、数据语义和失败行为；不要虚构厂商字段、真实协议或验收结论。会影响多个团队的契约先评审，再并行实现生产者与消费者。

## 3. 文档治理

现有项目先发现仓库已有文档体系，再决定同步位置；全新项目只建立当前阶段真正需要的最小文档基线。通常：

- 仓库指令：少量长期硬约束。
- 架构总览/上下文：稳定边界、术语和关键链路。
- ADR：长期且有备选方案的重要决策。
- 需求/详细设计：本能力范围、数据、接口、状态和验收。
- 协议/OpenAPI/Schema：可执行或对外契约。
- 迁移/运维手册：部署、升级、回退和故障处置。
- 验收指引：环境、步骤、证据和已知限制。

接口、消息、数据、配置或操作方式实质变化时同步对应资料。不要把动态端口、当前分支、临时模型 ID 或测试数量复制到多个长期文档中。

文档与代码漂移时记录“目标/实现/验证”的差异和处理决定；不要只改一个地方让冲突暂时不可见。

## 4. 完成度分层

分别报告：

1. **设计完成**：范围、边界和契约已确认。
2. **代码完成**：实现及必要文档已修改。
3. **自动验证完成**：编译、单测、集成或契约测试的实际结果。
4. **环境验证完成**：在指定测试/联调环境验证外部依赖。
5. **真实验收完成**：生产同类环境、真实数据或设备按正式条件验收。

任何一层都不能自动推导下一层。Mock、兼容数据库、stub、模拟器和调试页应明确标注替代了什么、没有证明什么。

## 5. 审查维度

审查至少分开：

- **需求符合性**：是否完成目标，有无漏项、越界或虚构能力。
- **项目规范**：是否遵守仓库指令、代码风格、包/模块和文档规则。
- **架构影响**：职责、依赖、数据权威和失败边界是否清晰。
- **数据与兼容**：迁移、旧客户端、历史数据、发布顺序和回退。
- **安全与可靠性**：身份、权限、密钥、幂等、并发、超时和结果未知。
- **验证证据**：测试是否覆盖关键行为，结论是否超过证据。
- **交付完整性**：必要文件是否进入变更，是否混入本地或无关资产。

问题包含精确证据、触发条件、影响和建议；按严重性排序。没有可操作问题时明确说明审查范围和残余风险。

## 6. Git 与工作区

- 目标位于 Git 仓库时先查看状态和基线；否则先检查并保护目标路径已有内容，不自动初始化 Git。
- 暂存使用明确范围；全量暂存前逐项核对未跟踪文件、生成物、本地配置和测试资产。
- 只审查或实现不等于获准提交、推送、建 PR、合并或部署。
- 提交语言、格式、分支命名和签名遵循仓库规范；没有规范时不要声称存在。
- 推送拒绝时先判断远端分叉和权限，不用强推覆盖他人提交。
- 提交前检查 staged diff、冲突标记、格式、敏感信息和测试结果。

工作区脏并不等于必须停工。只要能区分并保护用户改动，可以在不重叠区域继续；无法安全分离时再请求方向。

## 7. 发布与迁移

涉及部署或数据变更时确认：

- 目标环境、版本和配置来源。
- 应用、数据库、消息消费者和客户端的发布顺序。
- 向前/向后兼容窗口、灰度、健康检查和观测指标。
- 备份、回退/前滚策略和停止条件。
- 长任务、连接、缓存、队列和在途请求如何处理。
- 发布后验证及异常恢复负责人。

执行生产写入、迁移、密钥轮换或部署前必须获得对应授权并核对精确目标；开发任务本身不包含这些权限。

## 8. 最终报告模板

1. **结果**：完成了什么，目前可用到哪一层。
2. **范围**：新增、修改和明确未包含的文件/能力。
3. **架构**：调用链、复用点、职责、数据权威和关键决策。
4. **接口与数据**：契约、迁移、配置、权限、幂等和兼容。
5. **验证**：实际命令、结果、环境和证据。
6. **未验证/风险**：真实依赖、迁移、性能、安全、兼容或产品决定。
7. **交付状态**：是否提交、推送、发布；若有则给出分支、提交或版本。

报告以事实开头，避免用过程描述掩盖结果。若没有修改项目文件，也明确说明。

## 9. 周期性工程治理

通用 Skill 是提示性治理，不是自动强制。成熟项目可按实际痛点逐步引入：CI 必检、版本/依赖约束、格式与静态分析、架构测试、契约测试、迁移校验、密钥扫描、发布门禁和可复现验收。先针对真实反复出现的问题建立自动化，不为“看起来规范”堆砌工具。
