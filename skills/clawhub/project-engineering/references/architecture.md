# 架构与边界设计

## 1. 先确定职责，再决定目录

新增能力先回答：

1. 谁拥有这个业务概念和规则？
2. 谁拥有其权威数据与状态转换？
3. 生命周期、事务、一致性和失败边界是什么？
4. 哪些调用方需要它，已有公开边界能否承载？
5. 是否需要独立发布、伸缩、故障隔离、团队所有权或跨产品复用？

然后选择最小合适边界：现有类/包、现有模块、新模块、新进程、新服务或独立仓库。目录整齐、概念听起来独立、可能未来会用，都不足以单独证明需要新边界。

## 2. 边界选择

| 选择 | 更适合的条件 | 警惕 |
|---|---|---|
| 扩展现有包/能力 | 同一职责、数据和生命周期 | 把万能包继续做大 |
| 新建同模块业务包 | 职责独立但仍共享部署与事务 | 只建空目录制造形式边界 |
| 新建构建模块 | 需要依赖隔离、复用或独立测试 | 模块循环、公共模块业务化 |
| 新建进程/服务 | 独立部署、伸缩、故障或团队边界明确 | 远程调用、数据一致性和运维成本 |
| 独立仓库 | 生命周期、权限和发布治理真正独立 | 重复基础设施和契约漂移 |

现有项目遵循仓库主导风格：分层架构中不要局部强塞完整 DDD，feature-first 项目也不要新建全局万能 Service/Util 层。全新项目没有可继承风格时，根据已确认约束选择最小一致的组织方式，并落实为可执行工程基线。若现状存在缺陷，采用可验证的增量约束，而不是顺便重构全部历史代码。

## 3. 状态与数据归属

为每个关键字段或状态标记类别：

- **配置/期望状态**：用户或管理方希望系统处于什么状态。
- **观测状态**：外部系统、设备或运行时实际报告了什么。
- **派生状态**：由多个事实和时效动态计算的投影。
- **命令/意图**：请求发生某个有副作用动作。
- **事件/事实**：已经发生且用于传播的不可变事实。
- **审计记录**：谁在何时基于什么理由执行了什么。

不要把派生状态作为可编辑真值，也不要用“命令已发送”替代“动作已完成”。配置、观测和结果冲突时，定义优先级、时效、最终权威方和对外解释。

数据归属还应回答：公开标识与内部主键、租户/组织归属、删除语义、历史快照、保留期限、隐私等级和迁移兼容。

## 4. 依赖方向

先画真实依赖，再提出目标方向。新增依赖时：

- 调用拥有规则的一方公开边界，避免复制校验或直接写入对方存储。
- 外部厂商协议通过 Client/Gateway/Adapter 隔离，核心模型不泄漏非必要厂商字段。
- 共享库只承载稳定、确实共享且不产生反向业务依赖的能力。
- 同步调用、异步事件和共享数据表各自有不同耦合，不要只看 import。
- 遇到依赖环，先识别共享概念、编排职责或错误归属；不要用全局静态对象掩盖。

“所有跨包调用都走接口”不是普遍真理。接口应隔离变化、外部系统或多实现；单实现且稳定的局部代码可以保持直接和清晰。

## 5. 调用链与失败链

对非简单变更至少描述：

```text
入口 → 身份/输入 → 业务规则 → 数据/状态 → 外部副作用
    → 结果/事件 → 状态回写 → 查询或通知出口
```

同时覆盖：校验失败、无权限、目标不存在、并发竞争、重复请求、部分成功、超时、断线、取消、重试耗尽和结果未知。对每个副作用说明：发生前是否持久化、是否可幂等重试、谁确认最终完成、如何补偿或人工恢复。

## 6. 一致性与并发

- 单事务内优先使用数据库约束和明确事务边界。
- 跨进程或外部系统操作不能伪装成原子事务；选择幂等、Outbox、Saga、补偿、对账或人工处置中的适当机制。
- “先检查再执行”存在竞态时，需要锁、版本号、条件更新、租约、fencing token 或执行点再次复核。
- 缓存不是默认权威源；定义 TTL、失效、冷启动和降级行为。
- 重试前区分只读、幂等写入和非幂等副作用；结果未知时先查状态。

机制由实际风险和现有基础设施决定，不为理论完整引入分布式组件。

## 7. 对外契约

REST、消息、事件、文件格式、CLI 和设备协议都属于契约。变化时检查：

- 请求/响应或消息方向、版本和兼容窗口。
- 必填/可选、默认值、枚举扩展和未知字段策略。
- 身份、权限、租户/归属和审计语义。
- 幂等键、顺序、重复、超时、重试和取消。
- 错误码与结果未知如何表达。
- 生产者、消费者、模拟器、SDK、文档和契约测试是否同步。

文件存在于协议目录不代表能力已发布；需确认版本状态和两端实现。

## 8. 模式选择

仅在减少变化传播或错误率时使用模式：

- 多实现或厂商切换：Strategy/Adapter。
- 稳定名称到处理器映射：Registry。
- 有副作用且需确认/排队/审计：Command/Proposal。
- 真实复杂生命周期：State Machine。
- 多来源事件到读模型：Projection。
- 跨系统可靠发布：Outbox 等可靠消息模式。

简单条件分支、单一实现或局部 CRUD 不需要抽象工厂、层层接口和形式化领域对象。

## 9. 架构决策输出

记录：背景、当前证据、目标与非目标、选择、备选方案、为什么、依赖方向、数据权威源、正常/失败链、兼容迁移、测试与回退。只有会长期影响多人决策的内容才值得形成 ADR；普通实现细节留在代码和详细设计。
