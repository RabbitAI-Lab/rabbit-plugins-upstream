# 全新项目与工程基线

## 1. 进入条件与事实边界

用户明确从零开始、目标目录不存在，或目录中尚无可分析的实现时，使用 `greenfield` 模式。已有脚手架只能证明其中实际存在的文件和配置，不能自动证明架构、业务边界或技术选型已经确认。

所有重要结论使用以下状态之一：

- **已确认约束**：来自用户、正式需求、运行环境、组织标准或必须兼容的外部契约。
- **暂定假设**：为继续推进而采用的最小、可逆假设，必须说明验证方式。
- **待决策项**：不同选择会实质改变契约、成本、安全、数据或交付方式，需要负责人决定。
- **已实现/已验证**：已经落到代码、配置或环境，并有相应检查证据。

不要把行业惯例、常见流量、团队能力或未来规模写成已知事实；也不要把拟议架构描述成当前实现。

## 2. 先收敛约束，再选择技术

设计前至少确认或显式标记以下信息：

1. 核心用户、关键场景、首期范围和明确不做的内容。
2. 核心数据、权威来源、保留要求和外部系统。
3. 运行环境、部署边界、身份权限、安全、隐私和合规要求。
4. 可用性、性能、容量、成本、可观测性和恢复目标。
5. 团队技术栈、维护能力、交付时间和运维方式。
6. 第一个可验收的端到端结果，以及由谁在什么环境验收。

缺少的信息若不影响对外契约、安全、成本或大范围返工，可以采用最小、局部、可逆的默认并记录假设；否则形成明确决策门，不通过追问清单拖延所有可并行工作。

技术选择优先成熟、可维护、与团队和部署环境匹配的最小组合。不要在约束尚未出现时预建微服务、事件总线、插件体系、多租户、跨区域容灾或复杂领域层级。

## 3. 建立最小架构基线

架构方案至少表达：

- 部署单元、模块职责、公开边界和依赖方向。
- 核心数据模型、数据权威源、事务与一致性边界。
- 一条关键成功链和一条失败链，包括超时、重试、幂等与结果未知。
- API、事件或协议契约，以及兼容和版本策略。
- 身份、权限、配置、密钥、审计和敏感数据边界。
- 日志、指标、追踪、容量假设、部署和回退方式。

只稳定当前阶段必须稳定的边界。尚未确定的云厂商、协议实现或规模策略放在适配边界之后，不提前实现完整扩展体系。

## 4. 建立最小工程基线

若用户要求创建或实现项目，将架构决策落实为可执行基线：

1. 运行时、依赖管理、构建清单、目录和模块边界。
2. 格式化、静态检查、错误处理、日志、配置和密钥规则。
3. 测试分层、测试入口，以及覆盖关键链路的第一个纵向切片。
4. 最小 CI、产物和部署边界；没有真实环境时明确模拟与验收差距。
5. 稳定入口文档和架构说明；只有长期重要且存在取舍的决策才记录 ADR。

优先完成一个可运行、可验证的纵向切片，再按证据扩展。不要一次性生成大量空目录、占位接口或没有消费者的抽象层。

## 5. 验证、交付与授权

验证从最小相关层开始，再按风险扩大：构建和静态检查、核心单元测试、模块/集成测试、契约测试、部署烟测和真实环境验收。报告每层实际证明了什么，不能把脚手架可启动等同于业务完成。

“只做设计”不授权创建脚手架或修改文件；“创建/实现项目”允许在用户指定目标内写入必要文件，但不自动授权初始化 Git、配置远端、提交、推送、创建云资源、迁移数据库或部署。目标路径已有内容时先检查并保护，不覆盖来源不明的文件。
