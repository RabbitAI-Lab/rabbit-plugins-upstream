# 产品通关六步法 — 全部检查清单汇总

> 以下清单可以在每个阶段结束时逐项核查。每一关的清单都围绕该阶段最常见的"翻车"场景设计。

---

## 第一关：探路 — 问题发现检查清单

在投入任何开发资源之前，用这个清单验证问题的真实性。

- [ ] 问题描述中是否出现了"我觉得""应该会有人""大概"等模糊词？
  - 如果出现，替换为用户原话或具体数据
- [ ] 能否用数据或用户原话证明这个问题的存在？
  - 数据来源：客服记录、用户访谈、数据分析、竞品调研
- [ ] 这个问题影响的是大多数目标用户，还是某个大客户的特殊需求？
  - 大客户需求可以列入"战略定制"，不能伪装成"产品需求"
- [ ] 用户已经在用替代方案了吗？
  - 有替代方案 = 有真实需求；没有替代方案 = 可能不是真的痛
- [ ] 如果问题不被解决，用户会继续忍受还是流失？
  - 如果用户能"继续忍受"，优先级至少降一级
- [ ] 问题的"痛苦程度"是否有三个信号支撑？（频率、强度、支付意愿）
- [ ] 能用一句话说清楚"谁、什么痛点、什么价值"吗？

---

## 第二关：画像 — 用户理解检查清单

在确定"为谁做"时，用这个清单避免自嗨式用户画像。

- [ ] 用户画像里是否包含"他们现在怎么解决"这个关键信息？
  - 没有"替代方案"的画像是不完整的
- [ ] 是否把"用户说的话"和"用户做的事"区分开了？
  - 用户说"我需要 XX 功能" ≠ 用户真的需要 XX 功能
- [ ] 目标用户群是否足够具体？
  - "白领""年轻人""中小商家"太泛 → 换成具体的角色+场景
- [ ] 有没有找到用户"愿意付费的信号"？
  - 付费信号：已在花时间/金钱解决、主动搜索方案、吐槽竞品价格
- [ ] 竞品分析是否包括"用户用 Excel/微信/纸质本子凑合"这种替代方式？
  - 用户的替代方案 > 友商的功能列表
- [ ] 是否知道用户"发现你的产品"的路径？
  - 从哪个渠道来？搜什么关键词？谁推荐的？
- [ ] 是否知道用户在什么情绪状态下会想起用你的产品？

---

## 第三关：构图 — 方案设计检查清单

在画出华丽原型图之前，用这个清单确保方案本身是合理的。

- [ ] 方案设计是否从"最小闭环"开始，而不是罗列完整功能列表？
  - 最小闭环 = 一个用户完成一次核心任务的最短路径
- [ ] 有没有方案比较过程，还是直接跳到了最喜欢的那一个？
  - 任何方案至少和"不做"以及"最简方案"做比较
- [ ] 关键假设清单写了吗？每条假设有没有验证方式？
  - 价值假设、可用假设、技术假设、商业假设
- [ ] 有没有"如果不做什么"的明确边界？
  - Out of Scope 不是可选章节，是必须写清楚的
- [ ] 核心流程是否能让一个新用户在 5 分钟内体验到价值？
  - 如果不行，说明 MVP 还不够 M
- [ ] 方案是否考虑了上线后的"撤退方案"？
  - 如果功能上线后效果不及预期，能安全下线吗？
- [ ] 最坏情况下，这个功能会搞砸什么？

---

## 第四关：落笔 — 文档质量检查清单

在把 PRD 发给开发之前，用这个清单做最后的自我审查。

- [ ] 一个完全不了解背景的人读懂全文需要超过 10 分钟吗？
  - 如果超过 10 分钟，考虑拆分或增加 TL;DR
- [ ] 有没有"优化""提升""改善"这种需要译者自行脑补的动词？
  - 替换为具体的："从 X 秒降到 Y 秒""从 N% 提升到 M%"
- [ ] "正常情况"之外的异常分支写了几个？是否覆盖了最常见的 5 个异常？
  - 未登录、数据为空、网络异常、权限不足、输入超限
- [ ] 验收标准是否足够具体，可以直接转换成测试用例？
  - 测试应该能对每条标准回答"通过"或"不通过"
- [ ] 有没有写"不做什么"？
  - 没有 scope exclusion 的 PRD 是 scope creep 的邀请函
- [ ] 每个用户可见的文案是否都已确定？
  - 空状态文案、错误提示文案、确认弹窗文案
- [ ] 埋点需求是否已在 PRD 中定义，而不是"上线后再说"？

---

## 第五关：行军 — 迭代执行检查清单

每周迭代结束时花 5 分钟过一遍。

- [ ] 当前迭代中是否混入了没有关联到任何用户故事的"顺便做"的需求？
  - 每条开发任务都应该能追溯到用户故事
- [ ] 有没有超过 3 天还没更新的阻塞项？
  - 阻塞项超过 3 天应该升级为更高级别的干预
- [ ] 需求变更时有没有同步更新验收标准和测试用例？
  - 变更只改代码不改验收 = 上线后一定被测试抓 bug
- [ ] 上一次回顾会提出的改进项，落实了吗？
  - 如果连续 2 次回顾会同一项都没落实，说明这项不重要，删掉
- [ ] 团队是否有"沉默的担忧"——那种没人说但大家都隐隐觉得不对的事？
  - 匿名投票："你对当前迭代的交付质量有多大信心？1-5 分"
- [ ] 是否有团队成员超过 3 天没有任何可演示的产出？
  - 不是催进度，是判断任务拆分是否太粗
- [ ] 产品经理本周是否至少跟用户聊了 1 次？

---

## 第六关：复盘 — 度量学习检查清单

功能上线后，确保不是"上完就完了"。

- [ ] 上线后是否设定了明确的"看数据"的时间点？
  - 建议节点：上线后第 3 天、第 7 天、第 30 天
- [ ] 有没有区分"相关性"和"因果性"？
  - 指标涨了不一定是你的功能导致的
- [ ] 失败的经验有没有被记录下来，还是只庆祝了成功？
  - 失败的功能要复盘但不追责、庆祝也不隐瞒
- [ ] 复盘产出的行动项有没有责任人 + 截止日期？
  - "下次注意"不是行动项
- [ ] 是否观察了反向指标？
  - 你希望涨的指标涨了，你不希望涨的指标有没有涨？
- [ ] 知识库是否有被团队其他人查阅的机制？
  - 知识存在某人的脑子里 = 不存在
- [ ] 有没有把成功经验提炼成"可复用的模式"？
  - "这次搜索做对了" → "后台工具类产品，搜索是最基础也是最重要的功能"
