# 三问复盘画布 — 模板与使用指南

## 核心理念

传统复盘容易变成"报喜不报忧"或"互相甩锅"。三问复盘法的核心前提是：**功能上线只是实验的开始，数据才是实验结果。** 我们复盘的不是"做得好不好"，而是"假设对不对"。

---

## 复盘画布模板

│                                                              │
│  复盘主题：[功能名称]                                        │
│  上线日期：[YYYY-MM-DD]   复盘日期：[YYYY-MM-DD]             │
│  参与人：[列出]                                              │
│                                                              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Q1: 我们对用户做了什么核心假设？                             │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ 假设 A：                                             │    │
│  │   我们假设：用户会因为 [XX] 而 [做YY]                │    │
│  │   如果假设成立，会看到的数据信号：[具体指标变化]      │    │
│  │                                                      │    │
│  │ 假设 B：                                             │    │
│  │   我们假设：解决了 [XX] 痛点后，用户会 [提升YY]       │    │
│  │   如果假设成立，会看到的数据信号：[具体指标变化]      │    │
│  │                                                      │    │
│  │ 假设 C：（如果有）                                    │    │
│  │   我们假设：...                                       │    │
│  └──────────────────────────────────────────────────────┘    │
│                                                              │
│  Q2: 数据告诉了我们什么？                                    │
│  ┌──────────────────────────────────────────────────────┐    │

## 填写示例

```
┌──────────────────────────────────────────────────────────────┐
│  复盘主题：订单搜索功能                                      │
│  上线日期：2025-03-10   复盘日期：2025-03-24                  │
│  参与人：张三(PM)、李四(DEV)、王五(DS)                       │
├──────────────────────────────────────────────────────────────┤
│  Q1: 我们对用户做了什么核心假设？                             │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ 假设 A：拣货员需要频繁搜索订单                         │    │
│  │   如果成立：搜索功能日均使用次数 ≥ 30 次/人            │    │
│  │                                                      │    │
│  │ 假设 B：搜索能显著提升拣货效率                         │    │
│  │   如果成立：单笔订单查找时间从 40s 降至 10s 以内       │    │
│  └──────────────────────────────────────────────────────┘    │
│  Q2: 数据告诉了我们什么？                                    │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  日均搜索次数：0(基线) → 58次/人(上线) → ✅ 远超预期  │    │
│  │  单笔查找时间：40s(基线) → 8s(上线) → ✅ 大幅下降    │    │
│  │  搜索无结果率：- → 12%(上线) → ⚠️ 需优化              │    │
│  │                                                      │    │
│  │  意外发现：近 40% 的搜索发生在 PC 端，与"都用扫码枪"    │    │
│  │  的假设不一致，说明仓库里 PC 使用场景被低估了          │    │
│  └──────────────────────────────────────────────────────┘    │
│  Q3: 如果重来一次，我们会怎么不同？                           │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  1. 第一天就埋无结果率的点，12% 无结果说明需要优化     │    │
│  │     模糊搜索和同义词匹配                               │    │
│  │  2. 灰度期间直接去仓库观察拣货员使用，而不是看报表      │    │
│  └──────────────────────────────────────────────────────┘    │
│  知识沉淀：                                                  │
│  ┌──────────────────────────────────────────────────────┐    │
│  │  B2B 后台工具类功能，搜索是使用频率最高的功能。        │    │
│  │  后台类搜索的容错要求比 C 端更高——用户打错字不会重试，│    │
│  │  会直接放弃搜索。应该默认开启模糊匹配。                │    │
│  └──────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────┘
```

## 复盘会议引导话术

**主持人开场（2 分钟）：**
> "今天我们复盘 [功能名]，目标不是评判谁做得好不好，而是看看我们做的假设对不对、数据告诉我们什么。这不是批斗会，是学习会。"

**Q1 引导（5 分钟）：**
> "上线前，我们觉得用户会因为什么而用这个功能？谁来帮我把当时的核心假设写下来？"

**Q2 引导（10 分钟）：**
> "对照每条假设，数据怎么说？——注意，我们只看数据不看感受。如果有数据没达到预期，这不是失败，这是我们学到的东西。"

**Q3 引导（10 分钟）：**
> "假设 Q2 的信息就是我们唯一能知道的事情——如果时光倒流到开发第一天，我们会做什么不一样的选择？每人写一条，然后贴在白板上。"

**收尾（3 分钟）：**
> "我们最后提炼一条知识，这句话应该是：未来团队遇到类似场景时，可以直接参考的经验。谁来拟第一稿？"

## 常见陷阱

| 陷阱 | 怎么办 |
|------|--------|
| 没有基线数据，上线后无从比较 | 上线前至少跑 1 周基线数据，写在 PRD 里 |
| 把相关性当因果性 | 除了你的功能，同期还有什么变化？（营销活动、节假日、竞品动态） |
| 只看"涨了"不看"为什么涨" | 拆分层：哪个用户群涨了？哪个场景涨了？ |
| 复盘完了没有行动项 | Q3 的每条必须带责任人 + deadline |
| 只复盘成功的，不复盘失败的 | 失败的功能是最便宜的学习机会，不复盘就是真亏了 |
