# Artifact Patterns

## Daily Card Contents

Each day card should include:

- Title: `Day N | date | origin → destination`
- One-sentence day strategy.
- Weather in the user’s preferred unit.
- Drive summary: time range, distance, difficulty, fatigue warning.
- Ordered stop list with map links.
- Route chooser using the same ordered stop list.
- Leg-by-leg navigation links when the day has multiple stops.
- Priority badges for optional stops when the day is flexible. Do not merge `A/B/C` into the stop name text.
- Source provenance for volatile weather, road, ticket, restaurant, and image facts when the artifact is reusable.

## Stop Detail Pattern

For each significant stop:

- `tag`: short role, such as `经典照片`, `午餐休息`, `低体力高回报`.
- `priority`: optional A/B/C label.
- `why`: why it is worth stopping compared with alternatives.
- `history`: one short background sentence when useful.
- `tip`: practical comfort/safety note.
- `links`: official venue, ticket, parking, restaurant, source, or visual reference links. Map links should be generated by the HTML template unless the user explicitly wants a provider-specific URL.
- `images`: optional swipeable gallery. Prefer 2-4 stable image objects with `src`, `alt`, `title`, `caption`, `credit`, and `link`.
- `imageQuery`: optional search query to display when a photo still needs to be filled.

## Visual Gallery Pattern

Use images to answer “what does this stop look like, and where should we stand?” rather than decorating the card.

- Attractions can include multiple “camera spot” images: classic frame, low-effort viewpoint, indoor/backup angle, or skip-if-crowded reference.
- Hotels, starts, airports, rental-car points, and overnight anchors should get photos when the user provides a name/link or asks the skill to search for them.
- Prefer user-provided image URLs/files first. When searching, use stable public or official sources, keep a source/credit/link, and avoid embedding uncertain-rights images when a visual reference link is safer.
- For real hotels, use public hotel exterior/lobby/area photos only; do not expose booking confirmations, room numbers, private addresses, or traveler names.
- If no image is available yet, set `imageQuery` and `imageNote` so the HTML shows a useful “photo to add” placeholder instead of a blank block.
- Avoid overloading a low-stamina plan with aspirational late-night or difficult “网红机位” shots; caption them as optional visual references when they are not comfort-first.

## Multi-Map Navigation Pattern

Generated navigation should not assume one map ecosystem. For every route, stop, and map marker:

- Open a map chooser instead of hard-wiring a single provider.
- Include Apple Maps, Google Maps, Amap / 高德地图, and Baidu Maps / 百度地图.
- Use Google Maps for full multi-stop routes when possible.
- Include first-to-last route links plus leg-by-leg links for providers whose web URI behavior varies by device or supports fewer waypoints.
- Keep ticket, official, restaurant, and source links separate from generated map choices.
- For mainland China trips, verify coordinate systems and local POI names; for international trips, tell users to fall back to Apple/Google if Amap/Baidu results look offset or sparse.

## HTML Route Map Pattern

For static HTML maps:

- Treat the page as the primary trip artifact unless the user asks for text-only output.
- Use one card per day with weather, drive difficulty, a mini map, route link, and calendar import.
- Draw a polyline through the main route points and numbered markers for all visible stops.
- If a point is only an after-check-in option, keep it in display details but do not make it the route destination.
- Make the whole card clickable. Open a flip-style detail panel/modal with images, why-it-matters, short background, comfort tips, ticket links, meal notes, and map chooser links.
- Stop visuals should be swipeable galleries when multiple `images` are present, with captions/credits visible on each slide.
- Follow `references/trip-data-contract.md` for structured fields such as `sourceProvenance[]`, `cutRules[]`, `tickets[]`, `parking`, and `medicalBackup[]`.
- Add per-day `.ics` downloads and, when useful, an all-trip `.ics` download.
- Verify locally after edits:
  - Number of day cards.
  - Map chooser opens for route buttons, ordered stop links, detail stop buttons, and marker popups.
  - Route links contain expected stops and exclude removed stops.
  - Leg-by-leg links exist for multi-stop days.
  - Priority labels are visible as distinct badges, not only inline text.
  - Calendar downloads contain the expected dates, titles, locations, and notes.
  - Image galleries swipe horizontally, images do not fail, and empty hotel/start anchors show a useful fill prompt.
  - `node scripts/validate-route-artifact.mjs <artifact.html>` passes when scripts are available.
  - No horizontal overflow on a narrow viewport.

## Calendar Notes Pattern

Calendar notes should be plain text, link-heavy, and useful on a phone:

```
Day N | date | route

Main strategy:
...

Weather:
...

Drive:
...

Stops:
• A keep | Stop name | reason | Apple/Google/Amap/Baidu map-choice URLs
• B optional | Stop name | reason | Apple/Google/Amap/Baidu map-choice URLs
• C skip | Stop name | reason | Apple/Google/Amap/Baidu map-choice URLs

Tickets / food:
...

Cut rules:
...

Backup medical:
...
```

Use calendar updates only when the user explicitly asks to sync or create events. If using Apple Calendar, verify the target calendar name and read back at least title/location after writing.

## Markdown Itinerary Pattern

Keep Markdown short enough to read on the road:

- One route overview.
- “Real-time attention” section with dated checks.
- Day sections with bullets.
- A/B/C priorities when the day can be shortened.
- Navigation links inline, not collected at the end.

## Privacy for Public Output

When publishing a skill or template derived from a real trip, remove:

- Home addresses.
- Hotel confirmation details.
- Personal medical status.
- Names of travelers.
- Private calendar names.

Keep generalized lessons, examples, and placeholder values.
