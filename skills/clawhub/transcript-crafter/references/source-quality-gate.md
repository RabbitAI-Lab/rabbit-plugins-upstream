# 信源质量门控（Source Quality Gate）

## 概述

本文件定义transcript-crafter技能的**信源质量硬阻断机制**。信源质量是横切关注点，贯穿Step 5（增量搜索）和Step 7（质量验证）两个阶段。未通过任一阻断点→禁止进入Step 8交付。

**核心问题背景**：聚合平台（头条/百家号/UC大鱼号/企鹅号等）转载内容多、始发信源少、可信度参差。若搜索阶段过度依赖聚合平台，会导致文章引用信源可信度不足，即使数据准确也会削弱文章权威性。

---

## 3个硬阻断点

### 阻断1：信源多样性阻断

**目的**：避免单一域名/平台主导信源结构

**检查项**：

| 检查项 | 标准 | 不通过时 |
|--------|------|---------|
| 单一域名占比 | ≤30% | 换通道重搜 |
| 独立信源总数 | ≥6个 | 补搜更多信源 |
| 引擎使用数 | ≥5个 | 补搜更多引擎 |
| 聚合平台信源占比 | ≤20% | 追溯始发信源或换权威媒体 |

**聚合平台黑名单**（默认按聚合平台计入占比）：
- 头条搜索（so.toutiao.com / m.toutiao.com）
- 百家号（baijiahao.baidu.com）
- UC大鱼号（mp.dayu.com / uc.cn）
- 企鹅号（om.qq.com）
- 网易号（www.163.com来自网易号的内容）
- 搜狐号（m.sohu.com来自搜狐号的内容）
- 36kr聚合、虎嗅聚合（当内容为转载非始发时）

**检查方式**：
1. 统计每条补充信息的来源URL域名
2. 识别聚合平台信源（通过URL域名+内容是否始发判断）
3. 计算单一域名占比和聚合平台占比
4. 未通过→识别超标域名对应的引擎/通道→换用权威媒体通道重搜

**产出**：信源多样性检查表

| 域名 | 条数 | 占比 | 是否聚合平台 | 是否通过 |
|------|------|------|------------|---------|

**阻断标准**：单一域名>30% 或 聚合平台>20% → 禁止进入Step 7

---

### 阻断2：信源分级覆盖阻断

**目的**：确保信源结构有权威性梯度，避免全部依赖Tier 4-5

**检查项**：

| 检查项 | 标准 | 不通过时 |
|--------|------|---------|
| Tier 1（官方）覆盖 | ≥1条 | 补搜官方信源（SEC/交易所/公司官网/政府文件） |
| Tier 2（权威媒体）覆盖 | ≥2条 | 补搜路透/彭博/财新/新华社等 |
| Tier 3（行业研究）覆盖 | ≥1条 | 补搜Gartner/McKinsey/IDC/行业白皮书 |
| Tier 4-5占比 | ≤50% | 提升Tier 1-3占比 |
| 聚合平台信源占比 | ≤20% | 追溯始发或换权威媒体 |

**5级采信标准**（复用tool-router.md定义）：

| 级别 | 来源类型 | 示例 |
|------|---------|------|
| **Tier 1 官方** | SEC/交易所/公司官网/政府文件/同行评审论文 | 招股书、财报原文、官方公告 |
| **Tier 2 权威媒体** | 路透/彭博/财新/WSJ/Nature/新华社 | 路透社报道、财新深度 |
| **Tier 3 行业研究** | TrendForce/Gartner/McKinsey/IDC/白皮书 | Gartner预测、McKinsey报告 |
| **Tier 4 聚合/二手** | 36kr/虎嗅/TheVerge/科技博客/聚合平台 | 36kr转载、虎嗅分析 |
| **Tier 5 社区/推断** | 知乎/微博/小红书/Agent推断 | UGC内容、AI推断 |

**检查方式**：
1. 对每条补充信息标注Tier分级
2. 统计各Tier覆盖情况
3. 计算Tier 4-5占比

**产出**：信源分级覆盖检查表

| Tier | 条数 | 占比 | 覆盖要求 | 是否通过 |
|------|------|------|---------|---------|
| Tier 1 | X | X% | ≥1条 | |
| Tier 2 | X | X% | ≥2条 | |
| Tier 3 | X | X% | ≥1条 | |
| Tier 4-5 | X | X% | ≤50% | |

**阻断标准**：任一覆盖要求不满足 → 禁止进入Step 7

---

### 阻断3：关键数据交叉验证阻断

**目的**：确保关键数据有多个独立信源支撑，避免单点失误

**强制交叉验证的数据类型**：

| 数据类型 | 交叉验证要求 | 优先信源 |
|---------|------------|---------|
| 财务数据（营收/利润/市值/融资额） | ≥2个非原文信源 | Tier 1（SEC/交易所）+ Tier 2（路透/财新） |
| 政策数据（文号/日期/核心内容） | ≥2个非原文信源 | Tier 1（政府官网）+ Tier 2（新华社/财新） |
| 行业排名/市场份额 | ≥2个非原文信源 | Tier 3（Gartner/IDC）+ Tier 2（权威媒体） |
| 技术规格（参数/性能） | ≥2个非原文信源 | Tier 1（官方博客/论文）+ Tier 2（权威媒体） |
| 人物引语/表态 | ≥1个非原文信源 | Tier 2（权威媒体）优先 |

**检查方式**：
1. 从文章中提取所有关键数据点
2. 每个数据点标注信源（原文+非原文1+非原文2）
3. 统计交叉验证率

**产出**：关键数据交叉验证表

| 关键数据 | 原文信源 | 非原文信源1 | 非原文信源2 | 是否通过 |
|---------|---------|------------|------------|---------|

**阻断标准**：任一关键数据非原文信源<2个 → 禁止进入Step 7

## 始发信源追溯规则

**核心原则**：聚合平台只能作为线索，不能作为最终信源。

### 追溯流程

```
搜索结果来自聚合平台（头条/百家号/36kr等）
    ↓
识别内容是否为始发
    ├─ 是始发（深度原创分析）→ 可作为Tier 4信源使用
    └─ 是转载/聚合 → 进入追溯流程
    ↓
从聚合内容中提取原始报道线索（机构名/媒体名/原作者）
    ↓
搜索原始信源
    ├─ 找到原始信源 → 引用原始信源，聚合平台不计入信源
    ├─ 找不到原始信源但有机构/媒体名 → 标注"据{机构/媒体}报道，原始URL待追溯" + 降级为Tier 5
    └─ 完全无法追溯 → 不使用该数据，或标注"据聚合平台报道，原始信源待核实" + 降级为Tier 5
```

### 追溯优先级

| 聚合内容线索 | 追溯目标信源 | 优先级 |
|------------|------------|-------|
| 提到"据XX公司财报" | 财报原文（SEC/交易所） | Tier 1 |
| 提到"据路透/彭博/财新报道" | 对应权威媒体原文 | Tier 2 |
| 提到"据Gartner/McKinsey报告" | 对应机构报告原文 | Tier 3 |
| 提到"据XX公司CEO表示" | CEO官方表态（官网/官方博客/社交媒体） | Tier 1 |
| 提到"据行业人士分析" | 行业分析师原始出处 | Tier 3-4 |
| 无任何线索 | 不使用或降级Tier 5 | — |

### 文章中的标注方式

| 追溯结果 | 文章标注方式 |
|---------|------------|
| 成功追溯 | `数据（[原始信源](URL)）` —— 不再提及聚合平台 |
| 部分追溯（有机构名无URL） | `数据（据{机构名}报道，原始URL待追溯）` |
| 无法追溯 | `数据（据聚合平台报道，原始信源待核实）` 或不使用 |

---

## 执行时机

### Step 5（增量搜索）阶段——实时门控

每次搜索完成后，立即执行：

1. **搜索通道选择**：按tool-router.md引擎级路由，优先Tier 1-3通道
2. **结果筛选**：对聚合平台结果执行始发追溯
3. **实时统计**：更新信源多样性+分级覆盖+交叉验证三张表
4. **实时阻断**：若某次搜索导致单一域名>30%或聚合平台>20%→换通道重搜

### Step 7（质量验证）阶段——最终门控

Step 6撰写完成后，执行3个硬阻断点的最终检查：

1. **阻断1：信源多样性** → 未通过→回到Step 5补搜
2. **阻断2：分级覆盖** → 未通过→回到Step 5补搜
3. **阻断3：交叉验证** → 未通过→回到Step 5补搜
4. 全部通过 → 进入Step 8交付

## 与tool-router.md的关系

| 文件 | 职责 | 关注点 |
|------|------|--------|
| tool-router.md | 引擎级路由（从哪搜） | 搜索通道选择 |
| source-quality-gate.md（本文件） | 信源质量门控（能用什么） | 引用结果筛选 |

**协同关系**：
- tool-router.md规定"头条作为最后兜底引擎"
- source-quality-gate.md规定"聚合平台信源占比≤20%"
- 两者共同确保：搜索阶段不过度依赖聚合平台，引用阶段不过度使用聚合信源

## 与transcript-rewriter的对比

| 维度 | transcript-crafter（本文件） | transcript-rewriter（block-rules.md） |
|------|----------------------------|--------------------------------------|
| 单一域名阈值 | ≤30% | ≤30% |
| 聚合平台阈值 | ≤20% | 无（隐含在域名控制） |
| Tier 1覆盖 | ≥1条 | 无明确要求 |
| Tier 2覆盖 | ≥2条 | 无明确要求 |
| Tier 3覆盖 | ≥1条 | 无明确要求 |
| 独立信源总数 | ≥6个 | ≥8个 |
| 交叉验证 | 关键数据≥2非原文信源 | 每论点≥2非原文信源 |
| 始发追溯 | 强制 | 无（原文降级为引子） |

**核心差异**：
- crafter以"原文为主体"，信源质量门控重点是补充信息的可信度
- rewriter以"增量为主体"，信源质量门控重点是增量信息的独立验证
- crafter更强调始发追溯（因为原文已是主体，补充必须可信）
- rewriter更强调多信源验证（因为增量是主体，必须独立验证）

## 阻断执行顺序

```
Step 5 增量搜索
  ↓ 实时门控（每次搜索后更新三张表）
Step 6 撰写
  ↓
Step 7 质量验证
  ├─ 6.4.5 素材覆盖率阻断（原文素材100%融入）
  ├─ 6.4.6 增量融入阻断（增量100%融入）
  ├─ 信源多样性阻断（本文件-阻断1）⭐ 新增
  ├─ 信源分级覆盖阻断（本文件-阻断2）⭐ 新增
  ├─ 关键数据交叉验证阻断（本文件-阻断3）⭐ 新增
  ├─ 6.8 内容审核阻断
  ↓ 全部通过
Step 8 交付
```

**阻断优先级**：6.4.5 → 6.4.6 → 信源多样性 → 信源分级 → 交叉验证 → 6.8

## 快速自查清单（撰写时使用）

撰写前快速自查，避免Step 7被阻断回炉：

- [ ] 是否过度依赖头条/百家号等聚合平台？（≤20%）
- [ ] 是否有Tier 1官方信源？（≥1条）
- [ ] 是否有Tier 2权威媒体信源？（≥2条）
- [ ] 是否有Tier 3行业研究信源？（≥1条）
- [ ] 关键财务数据是否有≥2个非原文信源？
- [ ] 聚合平台信源是否已追溯始发？
- [ ] 单一域名占比是否≤30%？
- [ ] 独立信源总数是否≥6个？
