# 7步管道详细流程

## Step 1: 输入获取 + 预处理

**1.1 输入识别**：

| 输入类型 | 识别标志 | 处理方式 |
|---------|---------|---------|
| 文本粘贴 | 用户直接发送大段文字 | 直接使用 |
| 本地文件 | `.txt`/`.md`/`.docx` 文件路径 | 用 Read 工具读取 |
| 飞书妙记链接 | URL 含 `feishu.cn` 或 `lark` 且含 `/minutes/` | 用 lark-minutes skill 获取逐字稿 |
| 微信公众号/在线文章 | 其他 URL | 用 WebFetch 工具抓取全文内容 |

**1.2 飞书妙记降级**：抓取失败 → 提示用户粘贴文本或提供本地文件

**1.3 来源验证（防幻觉）**：

WebFetch 抓取微信公众号文章时，**通常无法获取公众号名称**（页面顶部的账号名不在正文DOM中）。必须执行以下验证：

1. 检查抓取内容中是否包含公众号名称/来源标识（如"文丨XX"上方的账号名）
2. 若抓取内容中**无来源名称**：
   - 优先从用户提供的上下文中推断（用户说"这篇XX的文章"）
   - 若无法推断，用 cn-web-search 搜狗微信引擎搜索文章标题，确认公众号名称
   - **绝对禁止凭空编造来源名称**，不确定时标注"来源待确认"
3. 作者信息同理：若抓取内容中有"文丨XX"，直接使用；若无，标注"作者待确认"

**1.4 预处理**：说话人识别 → 去噪（时间戳/语气词标记）→ 段落切分 → 语言检测

**1.5 基本信息提取**：主题（必需）/ 来源名称+作者（必需，经1.3验证）/ 发言者及身份（必需）/ 行业领域（必需）/ 时间场合（可选）/ 受众预期（可选）

---

## Step 2: 信息提取 → 素材稿

**2.0 衔接**：基于 Step 1 提取的基本信息（行业领域/核心议题/发言者身份），调整提取重点：
- 行业领域 → 优先提取该领域的专业维度（如财经偏DATA/INSIGHT，科技偏HOWTO/STUNNING）
- 核心议题 → 围绕议题关键词重点标记相关素材
- 发言者身份 → CEO偏战略VIEW，技术人偏HOWTO/STORY，投资人偏CONTRA/EXPLOSIVE

详见 `extraction-guide.md`（10维度提取体系完整规范）

**确认点1**：向用户展示素材稿，确认核心观点准确、分类合理、无遗漏

---

## Step 3: 行业适配 + 人设选择

**3.1 行业特征分析**：术语密度 / 读者画像 / 信息偏好 / 表达惯例

**3.2 人设选择（混合模式）**：

基础人格（WeWrite 7套 + khazix-writer，若不存在用内置3套：行业观察者/深夜好友/锐评记者）：

| 基础人格 | 适合访谈场景 |
|---------|------------|
| `midnight-friend` | 创业者/个人经验分享 |
| `warm-editor` | 人物故事/情感类访谈 |
| `industry-observer` | 行业专家/高管访谈 |
| `sharp-journalist` | 调查性访谈/争议话题 |
| `cold-analyst` | 财经/投研访谈 |
| `humor-storyteller` | 轻松对谈/行业八卦 |
| `tech-coder` | 技术人物访谈 |
| `khazix-writer` | AI/科技领域访谈，口语化节奏，反AI味极强（详见 `anti-ai-rules.md`） |

访谈覆盖层（详见 `interview-personas.yaml`）：

| 访谈类型 | 覆盖层 | quote_handling |
|---------|--------|---------------|
| 专家独白型 | `expert-amplifier` | direct_quotes |
| 对话交锋型 | `dialogue-extractor` | mixed |
| 行业圆桌型 | `synthesis-weaver` | paraphrased |
| 实战经验型 | `practitioners-notebook` | direct_for_howto |
| AI/科技好奇型 | `curious-explorer` | mixed |

**访谈信号→persona 推荐决策矩阵**（v1.2.0 新增，基于 3 信号智能推荐，覆盖层 suitable_for/not_suitable_for 详见 `interview-personas.yaml`）：

按发言者数量 + 话题领域 + 语气特征 3 个信号查表推荐。信号从 Step 1 基本信息和 Step 2 素材稿获取。

| 发言者数 | 话题/语气信号 | 推荐覆盖层 | 推荐基础人格 |
|---------|-------------|----------|-----------|
| 1人 | AI/科技 + 好奇探索语气 | `curious-explorer` | khazix-writer |
| 1人 | 专家独白（非AI，观点密集） | `expert-amplifier` | industry-observer / cold-analyst（财经） |
| 1人 | 实操分享（参数/工具/步骤密集） | `practitioners-notebook` | tech-coder |
| 1人 | 创业者/个人经验 + 情感 | `expert-amplifier` | midnight-friend |
| 2人 | 对话交锋/辩论 | `dialogue-extractor` | sharp-journalist |
| 2人 | AI/科技好奇对谈 | `curious-explorer` | khazix-writer |
| 3人+ | 跨领域圆桌/峰会 | `synthesis-weaver` | industry-observer |
| 3人+ | 单一主题深度讨论 | `dialogue-extractor` | sharp-journalist |

**推荐流程**：
1. 从 Step 1 获取发言者数量、行业领域
2. 从 Step 2 素材稿识别语气特征（独白型/交锋型/探索型/实操型）
3. 查上表确定推荐覆盖层 + 基础人格
4. 对照覆盖层 `not_suitable_for` 二次校验，命中则换推荐
5. **确认点2**向用户展示推荐结果，用户可 override

**3.3 人设合并**：覆盖层参数覆盖基础人格同名字段，冲突时覆盖层优先

## Step 4: 框架生成

**4.1 框架类型**：

| 框架 | 适合类型 | 特点 |
|------|---------|------|
| 观点递进型 | 专家独白 | 观点→论据→推演→预判 |
| 对话提炼型 | 对话交锋 | 保留对话张力，提取交锋点 |
| 主题编织型 | 行业圆桌 | 多主题交叉编织 |
| 实战拆解型 | 实战经验 | 问题→方法→验证→避坑 |
| 故事还原型 | 人物故事 | 时间线叙事，情感弧线 |
| 洞察深挖型 | 趋势预判 | 表层→深层→未来推演 |
| 调查实验型 | 亲自下场 | 好奇→行动→发现→层层递进，核心是"我替你去做了这件事" |
| 产品体验型 | 工具/产品评测 | 场景演示→真实感受→逐一展示（升番逻辑：最弱→最强→意外），核心是"跟我一起玩" |

**英雄之旅叙事弧**（适用于调查实验型和产品体验型）：普通人被好奇心召唤→行动→踩坑→获得发现→带着变化回到日常。读者跟着走完弧线，有"我也经历了一遍"的参与感。冒险起点必须是具体的、读者能代入的困境或好奇。

**4.2 框架内容**：H1标题(来自 Step 4.3 候选，24-38字) + 开头策略 + 各H2(核心节点+支撑素材+增量需求) + 收尾策略 + 素材-框架映射 + 待补充信息清单

**4.3 标题候选生成**（v1.3.0 新增，详见 `title-strategist.md`）：

基于 Step 2 素材稿 + Step 3.2 访谈覆盖层，按 5 风格组生成最多 12 个候选标题，按 5 维度评分前 5 名，标记 6 类风险（含访谈专属"原话归属风险"），推荐 1 主标题 + 2 备选。

**硬约束**：
- 标题中的所有实体/数字/判断必须来自素材稿或 Step 5 补充信息，禁止编造
- 不得使用访谈中未出现的判断词（"首个""最强""颠覆""革命性"等）
- 任何 Critical 风险候选不得作为主标题

**确认点2**：向用户展示框架类型+人设+骨架+标题候选+待补充清单

## Step 5: 信息补充 + 事实核查

详见 `tool-router.md`（5工具路由+兜底机制+来源可信度分级完整规范）
详见 `fact-check-guide.md`（事实核查方法论）

**5.1 补充信息标准化格式**：每条补充信息必须携带来源分级+URL，传递给 Step 6：

```markdown
### [维度标记]-N: {补充信息摘要}
- **核查结果**: [VERIFIED / PARTIAL / UNVERIFIED / ...]
- **来源分级**: Tier {1-5}
- **来源标注**: {来源名称}
- **来源URL**: {URL 或 "无"}
- **文章写法**: {含链接或标注的具体写法}
- **链接位置**: 正文行内 / 文末参考来源 / 无链接
```

**5.2 来源分级采信逻辑**：
- Tier 1-2（官方/权威媒体）→ 必附URL，正文行内链接
- Tier 3（行业研究）→ 尽量附URL，无则标机构+报告名
- Tier 4（聚合/二手）→ 选择性附URL，文末参考来源
- Tier 5（社区/推断）→ 不附URL，文字标注

**5.3 信源质量门控**（搜索完成后必须执行，详见 `source-quality-gate.md`）：

实时执行3项门控检查，未通过任一项→换通道重搜：

1. **信源多样性**：单一域名占比≤30%、独立信源≥6个、聚合平台（头条/百家号/UC大鱼号/企鹅号等）占比≤20%
2. **信源分级覆盖**：Tier 1官方≥1条、Tier 2权威媒体≥2条、Tier 3行业研究≥1条、Tier 4-5占比≤50%
3. **始发信源追溯**：聚合平台内容必须追溯始发信源，追溯不到→降级Tier 5或弃用

未通过时换通道优先级：妙想mx-search → cn-web-search财经引擎（东方财富/财新）→ cn-web-search英文引擎（Brave/DDG）→ Wikipedia

记录门控结果（通过/修复后通过/仍不达标），传递给 Step 7 质量验证。

**确认点3**：向用户展示补充信息摘要+核查结果+来源分级+信源质量门控结果+新发现

**5.4 事实核查阻断**（搜索补充后必须执行，未通过禁止进入 Step 6）：

逐项检查以下内容，任何一项不通过必须修正后再继续：

| 阻断检查 | 标准 | 不通过时 |
|---------|------|---------|
| 来源URL完整性 | 每条补充信息有来源URL或"据公开报道" | 补充URL或标注 |
| 数据交叉核对 | 文中数据与来源原文一致，无张冠李戴 | 回到来源核对修正 |
| 政策文号核实 | 政策名称/文号/日期与官方原文一致 | 搜索官方原文核对 |
| 来源分级合规 | 每条信息标注Tier级别，Tier 1-2必附URL | 补充分级和URL |
| 不可核实标注 | 无法核实的数据标注"待核实"，不凭空编造 | 删除或标注 |

核查产出：核查修正记录（修正了什么、为什么修正），传递给 Step 6 和 Step 7。

## Step 6: 文章撰写

**6.0 撰写前置映射 + 入口校验**（进入6.1撰写前必须产出，无映射表禁止开始撰写）

**入口校验**——进入 Step 6 前，必须确认以下前置产出物存在且非空：

- [ ] `material-draft.md`（Step 2 素材稿）存在且非空
- [ ] `framework.md`（Step 4 框架）存在且非空
- [ ] `supplement.md`（Step 5 补充信息）存在，或 Step 5 明确标注"无补充信息"
- [ ] Step 5.4 事实核查阻断已通过（有核查修正记录）
- [ ] 用户已在确认点3确认补充信息

任一缺失 → 回到对应 Step 补做，不得直接开始撰写。

**撰写前置映射**——校验通过后，撰写文章前先产出两张映射表。这是"先列清单再写"的硬约束，避免"写完再查漏"的事后检查缺陷。

**表1：素材→段落映射**（对照素材稿逐条标记）

| 素材标记 | 传播力 | 计划写入H2 | 融入方式 | 备注 |
|---------|--------|-----------|---------|------|
| [VIEW]-1 | ⭐⭐⭐⭐⭐ | H2-1 | 引用块+展开 | — |
| [DATA]-4 | ⭐⭐⭐⭐⭐ | H2-3 | 增量数据 | — |
| [HUMOR]-3 | ⭐⭐⭐ | H2-5 | 行内点缀 | 可省略需说明理由 |

要求：每条素材都必须在映射表中出现一行，"未融入"需明确标注理由。

**表2：增量信息→段落映射**（对照 Step 5 supplement.md 逐条标记）

| 增量信息摘要 | 来源分级 | 计划写入H2 | 融入方式 | 来源标注 |
|------------|---------|-----------|---------|---------|
| Gartner 1.5万亿/2万亿 | Tier2 | H2-3 | 行内链接 | URL+机构 |
| AlexNet 2012历史 | Tier3 | H2-4 | 背景注释 | 机构+报告名 |

要求：Step 5 的每条补充信息都必须在映射表中出现一行，"评估不融入"需明确标注理由。

**映射表用途**：
1. 撰写时对照映射表逐条融入，避免靠记忆导致遗漏
2. 6.4.5 素材覆盖率阻断 和 6.4.6 增量信息融入阻断 时，直接对照映射表检查
3. 映射表作为审核修正记录的附件产出

**6.1 写作约束**：框架结构 + 素材节点必须出现 + 补充信息融入 + 人设参数 + 反AI规范（详见 `anti-ai-rules.md`，所有人格共享；curious-explorer覆盖层强制启用） + 2500-4000字

**6.2 写作原则**：
- 增量密度：纯复述≤30%，每段有增量，增量标注来源
- 观点归属：实录观点标注发言者，Agent分析与实录观点区分
- 引用处理：按覆盖层quote_handling参数（direct_quotes/paraphrased/mixed）
- 可读性：术语首次出现解释，数据场景化，每800-1000字有消化点
- 原话引用：金句/判断/颠覆性原话用 `>` 引用块+署名；简短参数/描述行内即可
- 出处链接：按来源分级（Tier 1-5）决定链接策略，Tier 1-2必附URL行内链接，Tier 3尽量附，Tier 4-5不附（详见 `tool-router.md` 来源可信度分级体系 + `wechat-format-guide.md` 第六节）
- 链接密度：正文行内链接 ≤ 8个，避免破坏阅读流

**6.3 输出**：H1标题（来自 Step 4.3 用户确认的标题，24-38字，深度访谈可放宽到 35-50 字）+H2+H3结构 + 2-3个编辑锚点 + 标准Markdown格式（引用块/加粗/斜体/列表/表格/分割线，详见6.5样式丰富度规范）

**6.4 四层自检体系**（文章写完后必须逐层检查，源自 khazix-writer + 人味儿写作心法）

文章写完后，按以下四层逐层检查。每层通过后才进入下一层，任何一层不通过则修完再检。

### 第一层：硬性规则扫描

像代码的语法检查一样，出现就一定有问题。逐条扫描全文：

| 检查项 | 标准 | 不通过时 |
|--------|------|---------|
| 禁用词 | 无"说白了""意味着什么""本质上""换句话说""不可否认" | 替换为口语化表达 |
| 禁用标点 | 无冒号"："、无破折号"——"、无双引号"" | 替换为逗号/句号/「」 |
| 结构套话 | 无"首先...其次...最后""综上所述""值得注意的是""不难发现" | 删除或重写 |
| 教科书开头 | 不是"在当今XX快速发展的时代""随着技术的不断进步" | 换为具体事件/场景切入 |
| 空泛工具名 | 无"AI工具""某个模型"，用具体名字 | 替换为具体产品名 |

### 第二层：风格一致性检查

检查文章的风格是否与人设匹配，是否像"一个人写的"：

| 检查项 | 标准 | 不通过时 |
|--------|------|---------|
| 开头切入 | 从具体事件/场景/数据切入，不是宏大叙事 | 重写开头 |
| 长短句交替 | 有节奏感，不是均匀的中等长度句子 | 打断均匀节奏，加入短句断裂 |
| 口语化表达 | 有转场词/判断词/自嘲词，不是全程书面语 | 加入人设风格的口语化词组 |
| 人设声音 | 全文有统一的分析视角和判断语气，不是"据XX报道"的搬运工 | 换用更匹配的人设，增加判断句 |
| 观点交锋 | 多空/正反观点有张力呈现，不是各说各话 | 增加交锋段落 |
| 分析推导 | 有"现象→追问→洞察"的推导链，不是数据摆完就完 | 补充"为什么"和"意味着什么" |

### 第三层：内容质量检查

检查文章的信息密度和内容深度：

| 检查项 | 标准 | 不通过时 |
|--------|------|---------|
| 素材覆盖 | ⭐⭐⭐⭐⭐素材全部入文 | 补充遗漏素材 |
| 增量密度 | 纯复述≤30%，每段有实录外增量 | 补充背景/数据/对比/注释 |
| 观点归属 | 实录观点标注发言者，Agent分析明确区分 | 修正归属标注 |
| 核查标记 | 补充信息标注来源分级和核查状态 | 补充标注 |
| 人味儿三要素 | 每段有位置（谁在说话）、代价（判断有理由）、手迹（原话保留） | 补充上下文/理由/原话 |
| AI味6组检查 | 无意义拔高/宣传腔/句式套路/格式痕迹/语气痕迹/填充对冲 | 逐条修掉（详见 `anti-ai-rules.md`） |

### 第四层：活人感终审

这一层最主观，也最重要。就一个核心问题：

**读完这篇文章，你觉得这是一个有见识的人在认真跟你聊一件打动他的事，还是一个AI在给你输出信息？**

逐段自问：
- 这段话背后，站着一个具体的人吗？
- 这段话有只有这个人才会这么说的判断吗？
- 如果把人设名字遮掉，还能认出这是谁写的吗？
- 有没有哪段读起来AI味重了？

任何一段读起来感觉AI味重了，就返工。不要凑合。

**典型问题模式**：如果文章读起来像"据A报道XX，据B报道YY，据C报道ZZ"——这就是信源搬运工，没有人设灵魂。需要回到素材，找到分析切入点，用人设的视角重新组织。

**6.4.5 素材覆盖率阻断**（四层自检后必须执行，未通过禁止进入6.5）

逐条对照 Step 2 素材稿，标记每条素材的融入状态。这是硬性阻断，不是"建议检查"。

| 素材标记 | 融入状态 | 对应段落 | 备注 |
|---------|---------|---------|------|
| [VIEW]-1 | ✅已融入 | H2-1第1段 | — |
| [DATA]-4 | ❌未融入 | — | 待补写 |

阻断标准：
- **素材覆盖率 = 已融入条数 / 素材稿总条数 ≥ 95%**（硬性）
- **⭐⭐⭐⭐⭐传播力素材覆盖率 = 100%**（硬性，零容忍）
- 任何⭐⭐⭐⭐⭐素材未融入 → 禁止进入6.5
- 覆盖率 90-95% → 列出未融入项，逐条评估是否可省略（需说明理由），不可省略则补写
- 覆盖率 < 90% → 回到 6.1 重写对应段落

产出：**素材覆盖率自检表**（附在审核修正记录中或单独记录），格式：
```
素材覆盖率：43/46 = 93.5%
⭐⭐⭐⭐⭐素材覆盖率：12/12 = 100%
未融入素材：[标记]列表 + 理由
```

**6.4.6 增量信息融入阻断**（紧接6.4.5执行，未通过禁止进入6.5）

逐条对照 Step 5 补充信息清单（supplement.md），标记每条增量的融入状态。Step 5 搜索到的增量信息必须 100% 融入文章，不得遗漏。

| 增量信息摘要 | 融入状态 | 对应段落 | 来源标注 |
|------------|---------|---------|---------|
| Gartner 1.5万亿/2万亿 | ✅已融入 | H2-3第2段 | Tier2+URL |
| AlexNet 2012历史 | ✅已融入 | H2-4第1段 | Tier3 |

阻断标准：
- **增量信息融入率 = 已融入条数 / Step5补充总数 = 100%**（硬性，零容忍）
- 任何增量信息未融入 → 禁止进入6.5，回到文章补写
- 若某条增量信息经评估不适用（如核查后推翻原数据），需明确标注"评估不融入+理由"，不计入未融入

产出：**增量信息融入清单**（附在审核修正记录中或单独记录），格式：
```
增量信息融入率：8/8 = 100%
评估不融入：[信息] + 理由
```

**6.5 格式适配 + 样式丰富度**（详见 `wechat-format-guide.md`）：

| 检查项 | 操作 |
|--------|------|
| 人设→主题推荐 | 按映射表推荐 rico-md 排版主题 |
| 标题层级 | 仅1个H1 + 3-5个H2 + H3全文3-6个，无H4-H6 |
| 加粗 | 每段2-4处，关键判断/核心数据/转折词/结论句 |
| 斜体 | 每段0-2处，概念定义/注释说明/英文术语 |
| 引用块 | 全文3-5处，原话+金句+关键数据+对比观点，署名 `—— 姓名，身份` |
| 有序列表 | 全文至少1处（方法论/排名/步骤），≤5项 |
| 无序列表 | 特征列举/数据对比要点，≤5项 |
| 表格 | 全文至少1个（数据对比/竞品分析），≤5列 |
| 分割线 | 2-3处（导语后+章节转折+文末前） |
| 图片处理 | 标准MD语法+描述性alt，无图处加占位注释 |
| 链接处理 | 重要URL正文化，来源链接集中文末 |
| 公众号兼容 | 去除HTML标签/下划线/自定义样式 |
| 文末格式 | 参考来源段落 + 增量信息声明 |
| 视觉节奏 | 不连续3段以上纯文本无任何样式变化 |

**6.6 来源导语**（详见 `wechat-format-guide.md` 第七节）：

在 H1 标题之后、第一个 H2 之前，撰写一段来源导语，让读者快速了解"这篇文章的信息从哪来、为什么值得读"。

| 来源类型 | 导语核心要素 | 字数 |
|---------|------------|------|
| 访谈/对话 | 5W1H：谁说的、什么场合、什么时候、为什么重要 | 200-400字 |
| 会议/圆桌 | 会议背景+议题+参与者分量 | 200-400字 |
| 学术论文 | 核心论点+研究价值+发表背景 | 150-300字 |
| 公众号/网页文章 | 来源+核心观点+为什么值得深读 | 100-200字 |

导语语气必须适配人设（详见 `wechat-format-guide.md` 第七节人设适配表）。

**6.7 内容审核**（写完后回看上下文，修正内容级问题）：

文章初稿完成后，**必须回到素材稿和来源**，逐项审核以下5个维度。发现问题时直接修正文章，不跳过。

| 审核维度 | 检查内容 | 常见问题 |
|---------|---------|---------|
| **归属准确性** | 每个引用块中的原话是否为来源原文？Agent总结/转述不得使用引用块+署名格式 | 把AI总结标为作者原话（最严重） |
| **结论强度匹配** | 文章结论是否与证据强度匹配？论文原文克制时，文章不得推出更强结论 | 论文说"尚未证实"，文章写成"已被否定" |
| **数据一致性** | 文中数据是否与素材稿/来源一致？有无四舍五入或转述导致的偏差 | 百分比计算错误、数据张冠李戴 |
| **来源分级合规** | 每条补充信息的来源标注是否符合5级采信标准？Tier 1-2是否附了URL？ | Tier 4来源标为"据XX报道"但实际是博客转载 |
| **遗漏检查** | 素材稿中的重要素材是否都在文章中出现？有无高传播力素材被遗漏 | ⭐⭐⭐⭐⭐素材未入文 |

**审核执行方式**：

1. 逐段扫描文章，标记所有引用块→回到素材稿/来源验证是否为原文
2. 逐段扫描文章，标记所有结论性陈述→与论文/来源原文对比强度
3. 逐段扫描文章，标记所有数据→与素材稿交叉核对
4. 逐段扫描文章，标记所有来源标注→按5级标准验证
5. 对照素材稿清单，检查是否有高传播力素材遗漏

**审核产出**：修正后的文章 + 审核修正记录（修正了什么、为什么修正）

**6.8 内容审核阻断**（审核未通过禁止进入 Step 7）：

审核必须产出"审核修正记录"。无修正记录 → 视为未执行审核 → 禁止进入 Step 7。

审核修正记录格式：
```markdown
### 审核修正记录
- [归属] 修正：XXX → YYY（原因：原话归属错误/AI总结误标为原文）
- [数据] 修正：XXX → YYY（原因：与来源不一致/四舍五入偏差）
- [结论] 修正：XXX → YYY（原因：结论强度超出证据支撑范围）
- [来源] 补充：XXX（原因：Tier 1-2来源缺少URL）
- [遗漏] 补充：XXX（原因：⭐⭐⭐⭐⭐素材未入文）
- [素材覆盖] 覆盖率 X/Y = Z%（⭐⭐⭐⭐⭐素材：A/B = C%）；未融入：[标记]列表 + 理由
- [增量融入] 融入率 X/Y = Z%；未融入：[信息]列表 + 理由；评估不融入：[信息] + 理由
- 无修正项（全文审核通过）
```

## Step 8: 桌面保存 + 飞书云盘同步

**8.1 桌面保存**：

将最终文章（`{skill_dir}/output/{date}-{slug}.md`）复制到用户桌面：

```bash
# Windows
Copy-Item "{skill_dir}/output/{date}-{slug}.md" "C:\Users\{username}\Desktop\{date}-{slug}.md"
```

**同名文件处理**：若桌面已存在同名文件（安全策略禁止覆盖），自动追加版本号：

```bash
# 方式1：追加 -v2 后缀
Copy-Item "{skill_dir}/output/{date}-{slug}.md" "C:\Users\{username}\Desktop\{date}-{slug}-v2.md"

# 方式2：使用中文描述性文件名
Copy-Item "{skill_dir}/output/{date}-{slug}.md" "C:\Users\{username}\Desktop\{主题关键词}-转写稿.md"
```

**必须反馈完整桌面路径**：`C:\Users\{username}\Desktop\{实际文件名}.md`

**8.2 飞书云盘上传**：

使用 `lark-cli drive +upload` 将最终文章上传到飞书云盘：

```bash
# 注意：lark-cli drive +upload 的 --file 参数必须是 cwd 内的相对路径
# 如果桌面路径不在 cwd 内，需要先将文件复制到 cwd 目录下再上传

# 方式1：文件已在 cwd 内
lark-cli drive +upload --file "./{date}-{slug}.md" --name "{date}-{slug}.md" --as user

# 方式2：文件在桌面，需先复制到 cwd
Copy-Item "C:\Users\{username}\Desktop\{date}-{slug}.md" "./{date}-{slug}.md"
lark-cli drive +upload --file "./{date}-{slug}.md" --name "{date}-{slug}.md" --as user
# 上传后清理 cwd 中的临时文件
```

**上传成功后反馈**：
- 飞书文件 URL
- 飞书 file_token

**8.3 降级处理**：

| 场景 | 处理方式 |
|------|---------|
| lark-cli 未配置 | 仅保存到桌面，提示用户配置 lark-cli 后手动上传 |
| lark-cli 上传失败 | 仅保存到桌面，记录错误信息，提示用户手动上传 |
| 用户未登录飞书 | 提示用户运行 `lark-cli auth login` 后重试 |
| 用户说"不用上传飞书" | 跳过8.2，仅执行8.1 |

**8.4 清理**：上传完成后，删除 cwd 中的临时副本（如有）

## 错误处理

| 步骤 | 降级 |
|------|------|
| 飞书链接抓取 | 提示用户粘贴文本或提供本地文件 |
