# 转化细则：把产品剥成可复用的能力

C 级才需要读这份。目标是把一个具体产品里的方法，抽成不依赖这个产品的可复用能力。

---

## 一、三层剥离的完整判断

先说清一件常被混淆的事：**"加功能"和"剥离能力"是反方向的两件事。**

- 加功能：产品变得更全，但更重、更难改
- 剥离：把已有的东西拆出来独立存在，产品可能变瘦

复刻做多了容易上瘾"加"，但真正的杠杆在"剥"。

| 层 | 回答的问题 | 独立后的形态 | 判断它该不该独立 |
|---|---|---|---|
| 判断层 | 谁在说话 | 专家包 / 人格设定 | 换个产品这套立场还成立吗 |
| 执行层 | 怎么算 | Skill / API / 脚本 | 参数能写成规则吗 |
| 呈现层 | 怎么长得 | 视觉规范 / 组件库 | 已经有三个以上样本了吗 |

---

## 二、执行层：Skill 的写法

### 一个 skill 好不好，看 description

description 决定它会不会被触发。三个必备要素：

1. **做什么**（一句话能力描述）
2. **什么时候用**（罗列用户的原话，不是行业黑话）
3. **不要做什么**（负面约束，防止误触发后乱做）

```yaml
description: 复刻任意应用、工具或小程序……当用户说"复刻这个""仿一个""抄一个"
"照着做一个""把这个 App 拆解""换个皮做我的产品"……时使用本技能。
输出五张结构化表格……不要在没有判定级别和承重墙结论的情况下直接开始写代码。
```

**关键**：用户的原话要写进去。用户不会说"请执行产品逆向工程"，他会说"仿一个"。

### SKILL.md 的五段结构

```markdown
## 两条铁律          ← 最硬的约束，放最前，违反就废
## 五步流程          ← 主链路，每步给产出物格式
## 输出约定          ← 不同场景给什么
## 常见错误          ← 从真实失败里来的
## 参考文件          ← 按需加载，列触发条件
```

**为什么铁律要放最前**：模型读文件的注意力是递减的。最不能违反的东西必须在开头。

**每步必须给"输出格式"**，不能只给"要做什么"。给了格式，输出才稳定；只给要求，每次长得都不一样。

### references 的拆分原则

| 拆法 | 什么时候用 |
|---|---|
| 按阶段拆（triage/extraction/restyle…） | 流程型 skill，每步独立可查 |
| 按类型拆（产品A/产品B） | 领域型 skill，不同对象不同规则 |
| 按深度拆（quick/full） | 有轻量版和完整版两种用法 |

拆完检查：**单个 reference 能不能独立读懂？** 不能说明耦合了。

给每个 reference 写"什么时候读"的触发条件，否则模型要么全读（浪费上下文），要么不读（等于没写）。

## 三、判断层：专家包的写法

### 专家包和执行 skill 的分工

| | 专家包 | Skill |
|---|---|---|
| 管 | 该不该、值不值、要不要反对 | 多少、怎么算、分几步 |
| 输出 | 有立场的判断 | 可解析的结构化结果 |
| 失败形态 | 说了正确的废话 | 算出了错的数 |
| 依赖 | 可挂载 skill | 不依赖人格 |

**一句话记法：专家决定"要不要"，skill 决定"多少"。**

### 人格要写四样东西

**① 出身**（让他有具体经验，不是万能专家）
差："十年花艺设计经验"。
好："十年从业，昆明花市起步，做过两百多场婚礼，后来只接日常瓶插"。
**具体的起点决定他的偏见方向。**

**② 信条**（三条以内，决定判断顺序）
例：形态先于品种、比例先于色彩、季节先于流行。
**信条必须是"先于"结构**，因为它表达的是顺序，不是偏好。顺序才能指导行动。

**③ 拒绝清单**（明确不做什么，比做什么更重要）
例：不做网红花束、不说"再自然一点"这类话、看不清的照片不猜、不接供应链和婚礼统筹。
**没有拒绝清单的专家，就是一个语气好一点的搜索框。**

**④ 输出习惯**（先说什么、最后说什么）
例：先排除风险 → 再算约束 → 再给方案 → 最后标不确定。
**这个顺序本身就是专业性的体现。** 通用模型会先给方案，再想起来问有没有猫。

### 反直觉的一条

**人格里要写"他看不准什么"。**

例："照片里的花看不清就不猜名字"、"价格只能给区间，各城市能差三成"。

承认不确定的专家，用户才会相信他确定的部分。全都敢答的专家，一句都不敢信。

## 四、判断"不要剥"

这一节比"怎么剥"重要。

### 只有一版样本，不要抽象

抽象需要至少三个样本才能看出真不变量。一版原型上的"规律"很可能是偶然。

**判定话术**：

> 这个我暂时不做。理由是现在只有一版样本，写下来的规范大概率两周后就要改，成本高于价值。
> 触发条件：等做到第三版，或者这个模式在第二个产品上复用了一次，那时再固化。

### 只能在原产品用，不要剥

如果剥离出来的东西换个产品就作废，那不是能力，是产品特性。产品特性不该独立存在。

### 剥了没法验收，不要剥

如果一个产物做出来，你说不清"什么样算对"，那它会变成一个永远在修改的负担。**先想清楚验收标准，再动手剥。**

## 五、自包含打包

### 专家包必须自包含

把 skill 复制进专家包的 `skills/` 目录，而不是引用用户级 skills 目录。

理由：专家包是要发给别人的。引用外部路径，别人装上就是缺件。

```
expert-name/
├── .codebuddy-plugin/plugin.json
├── agents/expert-name.md          ← 人格
├── avatars/expert.png             ← 512×512
├── skills/                        ← 复制进来，不引用
│   └── skill-name/
└── README.md
```

### 打包前必查

```
□ 专家包内的 skill 是完整副本（不是软链接、不是引用）
□ 头像 ≤ 500KB，512×512
□ plugin.json 的 plugin 字段 = name 字段
□ defaultInitPrompt 与 quickPrompts 第一条一致
□ tags 正好 3 个，quickPrompts 正好 3 个
□ 所有文件路径都是相对路径
□ 隐私：无用户名、无绝对路径、无本机目录名
```

### 交付三件套

| 件 | 内容 | 给谁 |
|---|---|---|
| 单文件原型（或成品） | 能直接打开看 | 设计师、开发、客户 |
| 可执行能力（skill/专家包） | 能装能用 | 自己长期用、发给同行 |
| 安装说明 | 怎么装、想改改哪个文件 | 任何人 |

**安装说明里必须有一张表**：想改 X，改哪个文件，影响什么。没有这张表，收到的人只能放着不用。

## 六、转化的验收

```
□ 去掉原产品的名字，这套能力还成立吗？
□ 换一个行业/场景，只改参数能跑吗？
□ 别人拿到能自己装上并用起来吗？
□ 做错了能被发现吗（有验收标准）？
□ 我明确说了哪些没做、为什么吗？
```

最后一条最容易被跳过：**没做什么，和做了什么同样重要**，因为用户会默认"你没说就是没想到"。
