# 拆解细则：五张表怎么填

SKILL.md 给了表头。这份文件给**填法、示例、和不同类型的提取重点**。

---

## 一、先分类型：承重墙在哪，取决于产品是什么

同样用五张表，但不同产品的重心完全不同。先判断类型，能省一半时间。

| 产品类型 | 承重墙通常是什么 | 拆解时最该盯的 | 最容易漏的 |
|---|---|---|---|
| **工具型**（记账、剪贴板、提醒） | 数据结构 + 一个核心算法 | ④ 数据结构 | 失败/异常状态 |
| **内容型**（课程、资讯、资料库） | 内容组织方式（分类体系/检索逻辑） | ① 信息架构 | 内容的不可复刻性 |
| **社交型**（撮合、动态、社区） | 撮合机制 / 激励设计 | ③ 状态流 | 冷启动与空状态 |
| **交易型**（电商、预约、下单） | 履约链路（谁在什么时候做什么） | ③ 状态流 + ② 机制 | 异常分支（退款/超时/缺货） |
| **创作型**（出图、写文、编曲） | 生成质量 + 可控性（能否局部改） | ② 核心机制 | 一致性（各产物对不上） |
| **效率型**（看板、协作、任务） | 信息密度 + 状态可见性 | ① 架构 + ③ 状态流 | 权限与并发 |

**读法**：先对号入座，然后重点填那一列，其余四张表填到能交接即可。

## 二、五张表的填写示例

以"AI 花艺师 App"为例（真实案例，可整体沿用思路）。

### ① 信息架构表

| # | 屏幕 | 用户想达成什么 | 界面**必须**给出的信息 | 出口 |
|---|---|---|---|---|
| 1 | 首页 | 快速开始 | 主 CTA、最近方案、次入口 | 需求输入 / 作品 |
| 2 | 需求输入 | 少填就能生成 | 场景、预算、风格、避让条件、预计耗时 | 方案结果 |
| 3 | 方案结果 | 判断值不值 | 效果图、总价、难度、一键改价 | 详情 / 改方案 |
| 4 | 详情 | 照着做 | 清单带单价与小计、替代项与差价、步骤、养护 | 作品 |
| 5 | 作品 | 记录与分享 | 上传、AI 点评、导出 | 我的 |
| 6 | 我的 | 回访 | 历史、偏好、会员 | — |

**第 4 列的填法**：问"这屏如果不给这个信息，用户会不会卡住？"会卡 → 必须给。不会卡 → 是装饰，删。

**常见错误**：第 4 列写成功能名（"显示清单"）。必须写成**信息内容**（"清单带单价与小计"）。功能名无法判断必要性，信息内容可以。

### ② 核心机制

**一句话，必须是动宾结构，必须能说"因为这样，所以用户愿意用"。**

- ✗ "AI 生成花艺方案"（这是功能，不是机制）
- ✓ "输入场景与预算，输出一份能直接照着做的结构化配方"（这是机制，含输入、输出、价值）

**进阶写法**——机制要能回答"为什么用户不用通用工具"：

> 通用出图工具能给出好看的图，但给不出花材数量、预算分配和缺货替代。所以机制不是"生成"，是"生成合法的、可执行的"。

写不出这句，说明还没看懂它为什么存在。

### ③ 状态流

用箭头串起来，**每个状态必须有出口，包括失败出口**。

```
进入
 ├→ 输入中 ──放弃──→ [空态首页，可恢复草稿]
 ├→ 生成中 ──超时──→ [重试 / 降低要求]
 ├→ 结果 ──改方案──→ 输入中（保留已填）
 │        └──确认──→ 详情 ──做完了──→ 作品
 └→ [异常：预算不足 / 无可用花材]
```

**必查三项**（复刻时最常漏）：

1. **空状态**：第一次进入，没有任何历史数据时显示什么？
2. **错误状态**：生成失败、网络断、预算不成立时说什么？
3. **中断恢复**：用户填到一半退出了，回来还在不在？

这三项不复刻，做出来的东西"能跑但不耐用"，用户一遇到异常就流失。

### ④ 数据结构

**这是中枢。必须先于其他一切产物定义。**

```json
{
  "occasion": "生日",
  "style": "自然风",
  "colors": ["粉", "白"],
  "budget_total": 200,
  "vessel": {"type": "圆形玻璃花瓶", "mouth_cm": 9, "height_cm": 18},
  "flowers": [
    {"name": "洋桔梗", "qty": 6, "unit_price": 7, "role": "主花"},
    {"name": "康乃馨", "qty": 3, "unit_price": 4, "role": "配花"},
    {"name": "肾蕨", "qty": 2, "unit": "扎", "unit_price": 9, "role": "叶材"}
  ],
  "difficulty": "新手",
  "duration_min": 35,
  "steps": [],
  "care": [],
  "derived": {
    "flower_cost": 106,
    "vessel_cost": 40,
    "total": 146,
    "image_prompt": "…"
  }
}
```

**填写规则三条**：

1. **派生字段集中在 `derived` 里**，标记为"算出来的"，不要和输入混在一起。混了以后就分不清哪个是变量。
2. **每个字段问一句"谁在读它"**。没人读的字段是垃圾，删掉。
3. **角色/类型字段（`role`）一定要有**。它是下游分组的依据，没有它，清单和视觉无法对应。

**如果数据结构定义不出来**：说明需求还没理解清楚。停下来，回去看①和③，不要往下走。

### ⑤ 视觉 token 表

见 `restyle.md`，那里有完整的浅色/深色两套模板。

拆解阶段只需抄出这几个值：底色、表面、主文字、主色、强调、圆角、字号阶梯。

## 三、承重墙的七种常见形态

判断时对照，比空想快。

| # | 形态 | 特征 | 例子 |
|---|---|---|---|
| 1 | **一份结构化数据** | 多个产物都从它派生 | 花艺配方、行程单 |
| 2 | **一个算法** | 效果好坏全在这个计算上 | 推荐排序、路径规划 |
| 3 | **一条履约链路** | 多角色按序交接 | 下单→支付→发货→售后 |
| 4 | **一个撮合机制** | 双方匹配规则 | 拼车、约饭、二手交易 |
| 5 | **内容组织方式** | 分类与检索体系 | 课程大纲、资料库标签体系 |
| 6 | **状态可见性** | 用户能否随时知道"到哪了" | 看板、审批流、物流 |
| 7 | **生成质量与可控性** | 能不能局部改而不重来 | 出图工具的局部重绘 |

**这一条尤其要注意**：形态 7 里，"可控性"常常比"质量"更是承重墙。用户能忍受 90 分的图，不能忍受改一处要重生成全部。

## 四、拆解完成的自检

五张表填完后，用这三问验一遍：

```
1. 一个没看过原产品的人，只看这五张表，能不能复现出 80% 的体验？
   └─ 不能 → 信息缺失，回去补

2. 承重墙那一项，我能不能用它解释产品 3 个以上的设计细节？
   └─ 不能 → 承重墙判断错了

3. 信息架构表里，有没有哪一屏的第 4 列我想不出来？
   └─ 有 → 那屏可能是冗余的，或者我理解得不够
```

三问全过，才进换皮阶段。**跳过这一步直接换皮，是最常见的浪费。**
