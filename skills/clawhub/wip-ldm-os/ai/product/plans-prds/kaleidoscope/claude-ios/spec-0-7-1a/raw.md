Excavated architectural gaps and prioritized critical reliability catches
Fresh read done — both docs end to end, plus a second look at my own LLM-wiki recommendation. The architecture holds up; I'm not going to relitigate anything the six review rounds settled. But reading it cold, as if I hadn't written it, I found real problems — including two the entire review chorus (and I) missed, and one place where my own last recommendation was wrong. Ordered by severity:
1. The reconciliation sweep is misphased, and on iOS it's not "redundancy" — it's the primary recovery path. The spec calls live capture primary and the sweep redundancy (Phase 5). That framing is inherited from desktop thinking. On iOS, Safari suspends the content script whenever the tab is backgrounded — and switching apps mid-generation is the normal mobile pattern. If the assistant finishes while the script is suspended, the turn-finish signal never fires, and without a sweep that turn is silently lost. That's not an edge case; it's every "ask Claude, check Messages, come back" interaction. A minimal sweep (on load/focus, rescan rendered turns against the watermark) is ~30 lines reusing T1's extraction path and T9's dedup — the cost argument for deferring it to Phase 5 is weak, and the reliability argument for Phase 0 is strong. It also makes M13–M14 testable immediately. Recommendation: pull a minimal on-focus sweep into Phase 0 (new ticket or folded into T1); keep only the exhaustive scroll-driven backfill for later.
2. §9.1's ordering claim has a hole nobody caught: parent_turn_hash is uncomputable when the parent is evicted. The cross-surface backfill section says the backfilled middle slots in via turn_index + parent_turn_hash. But in the virtualized case, the first visible turn of a backfill window has an off-DOM parent — you can't hash a turn you can't see. And turn_index itself is suspect: DOM order gives relative order of rendered turns, not absolute position, unless claude.ai exposes ordinals. So both ordering mechanisms §9.1 leans on can be unavailable exactly in the scenario §9.1 exists for. This doesn't break the design — vendor_message_id or DOM ordinals likely save it — but it means Spike 6 is load-bearing for M16, and §9.1 overstates confidence. The spike should be rephrased: "determine what absolute ordering signal exists in the DOM; parent_turn_hash is unavailable at backfill-window heads."
3. Deletion vs. immutability is an unresolved contradiction. §14 promises "user deletion/export." §7.4 makes sealed segments immutable. core.message_deleted is a tombstone — it hides content from projections, but the plaintext lives forever in sealed segments in the user's iCloud. For a privacy-first product, a "delete" that doesn't delete is a real problem (and a GDPR-adjacent one). The fix is known — a compaction operation: rewrite affected segments dropping tombstoned payloads, reseal with new manifests, emit core.segment_compacted. But it must be specified, because it's the one sanctioned exception to immutability and engineers will otherwise either refuse to delete or hand-hack segments. This needs a decision: tombstone-only (honest: "deleted from view, retained in archive") or tombstone + compaction (true erasure). I'd spec compaction as a named Core operation, even if implemented late.
4. A dropped thread from v0.2 never got answered: what happens when iCloud is off or full? The old open question "iCloud-off fallback — degraded local mode or hard requirement?" silently vanished around v0.5. The frozen spec writes canonical logs to the iCloud Drive container and never says what happens if iCloud Drive is disabled, unsigned-in, or over quota. Related and also unaddressed: writing to the ubiquity container has its own coordination semantics (NSFileCoordinator, dataless/evicted files) — "atomic rename" behaves differently there than in a local container. Cleanest answer: canonical logs write to the local app container as truth; the iCloud Drive copy is a mirrored export — which keeps Phase 0 working with iCloud off and sidesteps ubiquity-container write coordination. But that's a real architectural choice the frozen spec should state, not imply.
5. Phase 0 has a hidden read-model gap. M6 tests "delete local working DB/read model, rebuild from log" — but no Phase 0 ticket builds a local DB or read model. T7 says "render from projection," which literally means the chat UI lists conversations by globbing JSON files. That works for 10 conversations and degrades fast. Either T7 quietly needs a small conversation index (then ticket it), or M6 is testing an artifact that doesn't exist until Phase 1 (then move it). Small, but it's the kind of seam where an engineer invents an unspecified cache.
6. The onboarding funnel's weakest step isn't ticketed. Your MVP funnel is "install app, install plugin, use Claude." On iOS, "install plugin" means: enable the extension in Settings→Safari (or the Manage Extensions sheet), then grant claude.ai permission, then choose "Always Allow." This flow is notoriously where Safari-extension products die — and no ticket covers the guided walkthrough. For a product whose entire pitch is frictionless capture, T11: extension-enable onboarding (in-app guided steps, detect-enabled state, re-prompt until granted) is arguably as important as T1.
7. Smaller precision items, quickly: (a) M5's "byte-identical" needs canonical serialization specified (stable JSON key order, timestamp/float formats) or the test will flake — say "canonical-form identical." (b) Cross-session re-sends are expected behavior — after a refresh the script re-ships rendered turns and Core drops them; fine, but T1's "sent once per session" phrasing hides that the system re-sends across sessions by design; note it so nobody "fixes" it. (c) On a normalization_version bump, all old turns re-hash differently, so re-observed old turns would double-store — Core should re-derive hashes for existing turns on version bump (it has the raw text). One line prevents a real bug. (d) T3: the handler can't easily know core_epoch_seen; either it reads a shared state file or omits it and Core stamps epoch on acceptance — pick one. (e) T3 should name the Data Protection class (Complete blocks future background drain; CompleteUntilFirstUserAuthentication is the pragmatic choice).
8. And a correction to my own last post (the LLM-wiki integration): two things I'd walk back. First, I suggested adding a wiki section to the frozen spec — that violates the freeze discipline I argued for two turns earlier; it should be a separate future-layer one-pager, not an edit to a frozen doc. Second and more substantively: I called the wiki a "projection," and it can't be one — §7.5 defines projections as deterministic functions of the log, and LLM-maintained synthesis is nondeterministic. Calling it a projection would quietly corrupt the category system that makes the spec sound. The right integration is a third class: curated derivations, where the LLM's edits are themselves recorded as canonical events (wiki.page_updated with content). That restores replayability at the "replay the recorded edits" level rather than pretending you can re-run the LLM and get the same wiki — and it makes the wiki auditable through the same event log as everything else. That distinction is the difference between the wiki strengthening the architecture and quietly breaking its core invariant.
What genuinely holds up on re-read, for the record: the event-sourcing spine (inbox/canonical boundary, acceptance metadata, sealed segments, atomic writes), the commit-boundary rule, the embedding invariant and multi-space RRF model, the honest iOS-lifecycle framing, the threat model, and the ruthlessness of the Phase 0 scope. None of that needs touching.
Verdict: the spine is right; the fresh catches are #1 (sweep phasing — the one I'd fix before writing code), #2 (ordering-signal hole), #3 (deletion), and #4 (iCloud-off). The rest is ticket-level.
