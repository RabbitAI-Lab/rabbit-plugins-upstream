# LDM OS Installer Master Ticket

This is the rolling index for all LDM OS installer work. It is **append-only**: tickets get added here, status moves here, editorial notes about each ticket live here. The individual ticket files in `ai/product/bugs/installer/` are the source of truth for their own scope. This master is the source of truth for **ordering, dependencies, and rolling context** across all of them.

## Why this exists

The 2026-05-13 dogfood after alpha.27 shipped the install-prompt UX clean (zero gh release violations, zero memory grep, populated status table in 2 seconds). Then Parker investigated the "10 unavailable" rows that remained and discovered the underlying architecture problem: **the installer's update-detection model is npm-centric, while WIP Computer's extension ecosystem is largely not**. Some extensions ship bundled inside parent packages (`lesa-bridge` ships with LDM OS since v0.3.0). Some live in private GitHub repos with no npm publication. Some are forks ahead of their public source. The registry has no way to express any of this, so `ldm status` defaults to "ask public npm or give up."

Parker decided to pause Remote Control work and repair the installer foundation. This master ticket sequences all installer work in execution order so we go through it methodically.

### 2026-05-13 wind-down state

The 2026-04-24 to 2026-05-13 installer foundation repair is complete. Phase 0 (concept/design) and Phase 1 (source.npm cleanup) shipped via alpha.28 + alpha.29. The dogfood-gate rule landed in the coder playbook. Three follow-up bugs were surfaced during the 2026-05-13 dogfood and are captured but parked: dedup-reverts (P1, blocks Phase 2), full-inventory-table (P1), status-vs-dryrun (P2). Remote Control pivot is unblocked. Phase 2 source-types-migration is queued behind dedup-reverts and the promoted preview-sandbox / fixture-harness safety gap.

## Operating principles

1. **Append-only.** This file gets edited to add new tickets, move tickets between phases as they complete, and add editorial notes. Individual ticket files do not need to be rewritten to reflect what's noted here.
2. **One slice per PR.** Per the role spec. Each phase below is several PRs, not one.
3. **Honest reporting first, capability second.** Phase 1 makes `ldm status` stop lying. Phase 2 makes it actually capable.
4. **Dogfood after every alpha.** Each phase below cuts an alpha and gets a real `ldm status` + install-prompt dogfood before the next phase starts.
5. **Reviewer field is normative on every ticket.** Every installer ticket carries `reviewer: Installer CC Partner` (or whichever reviewer applies) in its YAML frontmatter. The review step is real, not implicit. Tickets without a reviewer field were filed before this rule and get the field added **when the ticket is next opened for work**, not as a separate bulk retrofit pass across the older queue.

## How to use this file

When a new installer ticket is filed: add a row in the right phase, link the file, write one line of context.

When a ticket moves through status (open → fixed → done): edit the row here. Don't rewrite the individual ticket file unless something material in its body needs updating.

When you want to know "what should I work on next?": read top-down. Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5. Skip tickets in Done.

When you want context on a ticket that's old or unclear: read its editorial note above. If the note says "verify before re-implementing," do that verification before opening a PR.

When you are acting as Installer CC Coder shipping a ticket: follow [`ldmos-bugs-operating-procedure--installer-coder.md`](ldmos-bugs-operating-procedure--installer-coder.md) for the /goal-driven execution playbook.
