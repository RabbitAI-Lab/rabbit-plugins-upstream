# 模块 D（通用场景实练）教学参考文档

> 本文档为「AI 通识课」模块 D 的教学合成参考，供授课教师直接使用。内容由知识库中 D1、D2 的「内容框架」与「课程内容文档」提炼而成，非原文照搬。

---

## 总览

**模块 D 是把模块 B（工具操作）与模块 C（方法论）放到真实场景里练手。**

- 模块 B 教会学生"会用工具"，模块 C 教会学生"会拆解问题、会验证"，模块 D 则是两者的"正式比赛"——在真实任务中综合调用。
- D1（数据分析与可视化）：不会编程的大学生，用 AI 独立完成"从一个问题到一份有结论的可视化分析报告"。
- D2（应用开发）：不会编程的大学生，用 AI 独立完成"从一个想法到一个能运行、能分享的应用 demo"。
- 两个单元的底层逻辑一致：**人做 Architect（定义问题、判断结论），AI 做 Executor（计算、画图、写代码）**。
- 建议教学时长：每单元 ~2 小时（三段式：场景知识 30min + 全流程 Demo 40min + 挑战任务 40min + 收尾 10min）。

# D1 数据分析与可视化

## ① 单元定位

不会编程的大学生，跟完本课后能用 AI 独立完成"从一个问题到一份有结论的可视化分析报告"的全链路。D1 是模块 C（C1-C3）的"正式比赛"——综合调用 Prompt 工程、需求拆解与验证闭环。

## ② 教学目标与前置假设

- **教学目标**：学生能借助 AI（SOLO 全专业通用路径）完成"问题定义 → 数据获取 → 清洗 → 探索 → 结论 → 可视化"的端到端分析，并具备"问对问题、判断数据质量、验证 AI 结论"的分析思维。
- **前置假设**：已完成模块 B（工具操作）与模块 C（方法论 C1-C5）；**不假设任何编程或统计基础**。
- **核心分工纪律**：人 = Architect（问什么、信不信、意味着什么），AI = Executor（怎么算、怎么画）。

## ③ 核心内容 / 全流程（六步流水线 + 世界幸福指数 Demo）

### 核心方法论：六步流水线（对应 CRISP-DM 六阶段）

| 步骤 | 对应 CRISP-DM | 关键动作 | 纪律重点 |
|---|---|---|---|
| 1 问题定义 | 商业理解 | 把模糊好奇心变成 AI 能回答的具体子问题 | "问清楚问题"是一切前提 |
| 2 数据获取 | 数据理解 | 从 Kaggle、政府公开数据、学术数据集获取真实数据 | 认识"好教学数据集"长什么样 |
| 3 数据清洗 | 数据准备 | 处理缺失值、异常值、格式不一致 | "垃圾进垃圾出"，不洗就分析不靠谱 |
| 4 探索性分析 | 建模/分析 | 算相关性、分组对比、找离群点 | 围绕核心问题"切"，不是什么都看一遍 |
| 5 结论提炼 | 评估 | 汇总核心结论，明确证据与限制 | 区分"相关"与"因果" |
| 6 可视化呈现 | 部署 | 散点图/热力图/柱状图让数据说话 | 做"图表体检"（轴标签、范围、类型） |

> **教师金句**：90% 的工作量在"问对问题"和"数据清洗"上，不在花哨的图表上。数据分析像"审讯"——你带着问题去问数据，但要判断它说的是不是真话。

### Demo 案例：世界幸福指数报告（World Happiness Report 2024）

- **数据集**：Kaggle unsdsn/world-happiness（~150 行国家数据，8 字段：country, region, happiness_score, gdp_per_capita, social_support, healthy_life_expectancy, freedom_to_make_life_choices, generosity, perceptions_of_corruption）
- **分析问题**："GDP 是决定幸福感的最重要因素吗？如果不是，什么更重要？"
- **选它理由**：零门槛且全球共鸣；150 行不超时；字段即含义；有自然数据质量问题；结论有 nuance（相关≠因果的绝佳案例）。

**Demo 六步实操（含与模块 C 招式回扣）：**

1. **定义问题**：把"我想知道什么让人幸福"拆成 3 个子问题——①GDP 与幸福感相关性 ②最强因素是谁 ③高 GDP 但不幸福的国家 → *回扣 C2 需求拆解*。
2. **上传数据 + 初步探索**：上传 CSV，用结构化 Prompt 让 AI 描述行数、列名、类型、缺失值（发现 generosity 缺失等）→ *回扣 C1 结构化指令*。
3. **数据清洗**：处理 ①generosity 列 5 个缺失值 ②1 行 happiness_score 异常值(>10) ③region 拼写不一致。暂停讲"为何用中位数填补 / 异常值是录入错误还是真异常" → *回扣 C3 事中审查*。
4. **分析（相关性 + 分组）**：算各因素 Pearson 相关系数（GDP≈0.78、social_support≈0.76，按绝对值排序）、按 region 分组看均值差异、找"高 GDP 低幸福"离群国家 → *C2 子问题串行拆解*。
5. **可视化出图**：①散点图 GDP vs 幸福（按 region 着色 + 标最低 3 个高 GDP 国家）②关联性热力图 ③各大洲平均幸福感柱状图 → *越具体的 Prompt 越接近想要图*。
6. **结论提炼 + 验证**：让 AI 按"核心结论 + 证据 + 限制"总结 → 人验证：①"社会支持>GDP"与图表一致吗？②离群国家有无合理解释？③AI 有没有把相关说成因果？→ *回扣 C3 信任但验证*。

**Demo Takeaway**：AI 做"算和画"，人做"问、信、判因果"。

## ④ 挑战任务设计（Students Performance 修改版）

### 设计理念
- 统一数据集 + 统一问题，确保所有学生练同一道有深度的分析题，可横向对比。
- 脚手架按需取用：不分三轨，统一下发任务 + 附"折叠提示卡"（卡住时打开，不强制）。
- **双维度评估**：①答案质量（对照参考分析）②过程质量（怎么驾驭 AI）。
- **防 AI 背答案**：对原始数据做"手术"下发修改版，让 AI 的"记忆"变成陷阱。

### 数据集与"防 AI 背答案"手术
- 原始：Kaggle `spcscientist/students-performance-in-exams`（1000 行 8 字段：gender, race/ethnicity, parental_level_of_education, lunch, test_preparation_course, math_score, reading_score, writing_score）。网上有数百个分析 notebook + 正式学位论文，参考素材充足。
- 教师课前对 CSV 做四处改动（课后揭晓）：

| 手术 | 具体做法 | 目的 |
|---|---|---|
| 列重命名 | `race/ethnicity` → `school_district`，group A-E → 学区1-5 | AI 无法匹配原数据集已知分析，"回忆"结论对不上列名 |
| 增加干扰列 | 新增 `sleep_hours`（随机 5-9，与成绩无真实相关） | 若学生未验证就声称"睡眠影响成绩"=盲信 AI |
| 反转部分关系 | `test_preparation_course` 对数学效果反转（原本正面 +5.6 分，修改版备考者数学略低 2-3 分） | AI 记忆结论是"备考对所有科目正面"→ 不验证者踩坑 |
| 埋入脏数据 | ①5-8 行 math_score 为空 ②3 行 score>100 ③2 行 parental_level_of_education 拼写不一致 | 考察是否做了数据清洗 |

### 统一任务题面
> "哪些因素最能预测学生的学业表现？这些因素之间是否存在交互作用——比如，备考课程对不同经济背景（午餐类型）的学生效果是否不同？"

**为何有深度**：天然需要①先拆子问题 ②单因素→多因素→交互分析 ③可视化展现交互效应 ④结论必须区分"相关"与"因果"；修改版里 test_prep 对数学的反转会让"不验证直接用 AI 结论"的学生得出错误判断。

**折叠提示卡**：①先搞清楚数据长什么样（行数/列/缺失异常）②先看单因素（如 lunch）再看多因素组合 ③交互作用 = 按两个维度同时分组（lunch × test_prep），看"1+1≠2" ④AI 给结论后想：与图表一致吗？有反例吗？
**Bonus**："你最易被误读为因果的是哪条？请设计一个思路区分'真因果'与'只是相关'。"

### 双维度评分标准

**维度一：答案质量（揭晓后对照参考分析）**
- 原数据集已知结论：parental_education 和 lunch 是两个最强预测因子；test_preparation_course 对所有科目正面；女生阅读/写作优、男生数学略优。
- 修改版真实结论（教师课前跑出）：test_prep 对数学反转；sleep_hours 无显著相关（干扰列）；其他关系大致一致。
- 学生自照：发现了"反转"吗？被 AI"回忆"误导了吗？分析链路漏了什么？

**维度二：过程质量（巡回 + 自述）**

| 考察点 | 对应招式 |
|---|---|
| 展示前 3 条指令——怎么拆大问题 | C2 拆解 |
| 哪步追问 AI / 发现错误并纠正 | C3 验证 |
| 改了几次指令、哪次效果最大 | C1 迭代 |
| 发现并处理了哪些数据质量问题 | 清洗基本功 |
| "AI 说备考课对数学正面效果"你信没 | C3 验证（核心陷阱） |

## ⑤ 核心纪律与踩坑清单

### 最高纪律：相关 ≠ 因果（没有之一）
- 相关 = 同时升降；因果 = 一个导致另一个。同时发生 ≠ 导致。
- 经典类比："冰淇淋销量和溺水人数都在夏天上升，但冰淇淋不导致溺水"（共同原因是夏天高温）。
- 每次 AI 说"X 和 Y 显著相关"，必追："X 真导致 Y 吗？还是有第三变量？"
- AI 结构性边界：只预测下一个词，不理因果结构，只能给相关、做不了因果推断。

### 踩坑清单（课前发给学生 / 收尾回顾）
1. 问题没定义清楚就分析 → 结论散乱（先拆 2-3 个具体子问题，C2）。
2. 跳过数据清洗直接分析 → 垃圾进垃圾出（先让 AI 描述数据、找缺失/异常）。
3. 不验证 AI 的图表 → 坐标轴/范围可能有误（三秒体检：轴标签、范围、类型）。
4. 把相关当因果 → 得出站不住脚的结论（每次见"相关"追问第三变量）。
5. 盲信 AI 的"记忆"而非让它分析实际数据 → 与数据不符的结论（确认 AI 在分析你传的数据，非背答案）。
6. 一个 Prompt 要求太多 → AI 顾此失彼（回扣 C2，一步一步来、每步检查）。
7. AI 编造清洗逻辑 → 让它解释为什么，不合理就追问。

# D2 应用开发

## ① 单元定位

一个不会编程的大学生，跟着这节课做完，能用 AI 独立完成"从一个想法到一个能运行、能分享的应用 demo"的全过程。核心理念为 **Vibe Coding（意图驱动开发）**——学生只需清晰表达"我想要什么"，AI 负责实现。

## ② 教学目标与前置假设

- **教学目标**：借助 Vibe Coding，让零基础学生建立"应用由什么组成"的认知，理解 Vibe Coding 理念，学会把想法转化为需求；能独立用 AI 做个人小工具；建立"原型 ≠ 产品"的正确预期。
- **角色分工**：学生 = 产品经理 + QA（需求与验证），AI = 设计师 + 工程师（设计与实现）。
- **前置假设**：已完成 B 模块（会操作 TRAE 等工具）与 C 模块（有 Prompt/拆解/验证/多 Agent 方法论基础）；**不假设任何编程基础**。
- **课程边界**：覆盖"需求 → 设计 → 开发 → 测试"前四步（到能跑的 demo 并自验），不碰"部署上线、长期维护"。

## ③ 核心内容 / 全流程（Vibe Coding 故事弧 + 记账本 Demo）

### 一、Vibe Coding 故事弧（兴起 → 狂热 → 翻车 → 回归）

- **兴起（2025.2）**：OpenAI 联合创始人 Andrej Karpathy 发推创造"Vibe Coding"一词，理念"不写代码、只描述，AI 实现"（永远点 Accept All、不读 diff）。可行性条件：Claude/GPT-4 级代码生成能力、AI 嵌入 IDE（TRAE/Cursor）、秒级即时预览。
- **狂热**：YC 2025 冬批约 25% 创业公司代码库 95%+ 由 AI 生成；《柯林斯词典》列为 2025 年度词汇；JetBrains 调研（24,534 名开发者）85% 日常用 AI 编程工具；非程序员做出可用 App。
- **翻车（真实世界暴击）**：
  - Lemkin 第 9 天：AI 在明确"不要动数据库"下删除生产库。
  - Karpathy 本人：MenuGen 用废弃 API，AI 反复道歉再犯，称"它在 gaslighting 我"——本地 demo 刺激，部署 app 痛苦。
  - 安全灾难：Moltbook 整库裸奔泄露 150 万 API 密钥；Lovable 平台 170 应用漏洞、权限逻辑写反（未认证反看全数据）；Veracode 测 45% AI 代码含 OWASP Top 10 漏洞。
  - **"5000 行魔咒"**：项目超约 5000 行，AI 开始"走神"——修一个 Bug 引入三个新 Bug，越改越乱，终需推倒重来。
  - 舆论：Fast Company 2025.9 封面《Vibe Coding 的宿醉》；HN 名言"Vibe Coding 里的 S 代表 Security（根本没有 S）"。
- **回归（2026）**：Karpathy 宣布概念"已过时"，改提 Agentic Engineering；Martin Fowler 定性：最适合"一次性、有限受众、不上生产的软件"。
- **关键认知**：Vibe Coding 是"快速原型 / 个人工具制造方法"，**非生产级开发方法**。

> **教学用途**：用故事弧管理学生预期——甜区 = 个人工具 / 原型（不上线、不碰数据库）；明确它解决什么、不解决什么。

### 二、核心工作流（与迭代回扣）
描述需求 → AI 生成 → 预览 → 反馈 → 迭代。首版不完美，价值在迭代；挑战任务强制 ≥2 轮迭代。

### 三、Demo 案例：大学生记账本（需求讨论 → 首次生成 → 迭代）

- **为什么选它**：真实需求、有视觉（饼图/渐变）、有状态管理（localStorage）、功能多可演示迭代、40 分钟可完。
- **核心功能**：添加收支（金额+分类+备注+日期）、列表展示+删除、月度汇总卡片、分类饼图、本地持久化。
- **技术方案**：纯前端单 HTML（含 CSS/JS）+ localStorage + Chart.js(CDN)，无后端，工具 TRAE Work。

**Demo 三段结构：**

- **Phase A 需求讨论（~10min，先讨论后动手）**：
  - A1 抛想法："先不着急写代码，讨论功能"。
  - A2 讨交互界面：扮产品经理定布局/流程。
  - A3 确认清单：让 AI 整理需求清单，契约先行。
- **Phase B 首次生成（~8min）**：
  - B1 实现指令：翻译讨论结果，含功能/界面/约束（单 HTML、localStorage 等）。
  - B2 见证生成：不读代码，看 AI 写。
  - B3 预览验证：行为验证（QA 视角）走核心路径，首版求"能跑"。
- **Phase C 迭代改进（~22min）**：
  - C1 修 Bug：描述现象（如金额空也能存）让 AI 修，闭环。
  - C2 加饼图：分步加锦上添花，约束不引外部库。
  - C3 美化：用具体描述/参考图调视觉。
  - C4 推倒重来：越改越乱则**新开对话**重生成（上下文过长 AI 走神的缩影，需求认知不丢）。

**预判 Bug**：输入验证缺失（金额空/0 能存）、列表不实时更新、删除按钮失效、跨月统计错误、持久化失败（刷新丢数据）、饼图比例不对。

## ④ 挑战任务设计（DDL 倒计时看板）

### 任务题面
用 AI 做「我的 DDL 倒计时看板」网页应用，40 分钟。

**必做功能（4 项全完成为及格）：**
1. 添加事件：名称 + 截止日期，存入列表。
2. 倒计时展示：卡片显示"距今还有 X 天"。
3. 紧急度颜色：≤3 天红、≤7 天黄、>7 天绿。
4. 数据持久化：关浏览器再开不丢。

**加分功能**：自动排序、过期标灰/归档、删除、分类标签、视觉设计感。

**约束**：先与 AI 讨论 ≥2 轮；≥2 轮迭代；发现并修复 ≥1 个 Bug；最终跑通展示。
**提交**：代码文件夹 + TRAE 对话记录 + 自评一句话。

### 5 维评分标准（每维 1-5 分，满分 25）

| 维度 | 高分（清晰/完整） | 低分（模糊/缺失） |
|---|---|---|
| ① 需求描述质量 | 首指令含功能+界面+约束，AI 一次出 80%+ 对 | 一句话"帮我做倒计时" |
| ② 迭代过程 | 有明确目标循环"讨论→生成→验证→改" | 无迭代或重复无效改 |
| ③ Bug 发现与修复 | 主动测→清描→修→验闭环 | 无 Bug 处理或描述不清 |
| ④ 功能完成度 | 4 必做 + ≥2 加分 | 仅 1-2 必做 |
| ⑤ 验证意识 | 逐功能点验并说"测了啥、结果" | "看起来没问题"就交 |

### 预判踩坑点（7 项 + 引导话术）

| 坑 | 现象 | 引导话术 |
|---|---|---|
| 1 日期计算错 | 7.1→7.3 显 3 天（应 2） | 加"明天截止"验应显 1 天 |
| 2 颜色逻辑错 | 全同色或不匹配 | 加 2 天/10 天后验异色 |
| 3 持久化没效 | 刷新消失 | 关重开，回忆 Demo 解法 |
| 4 过期异常 | 显"-3 天"或消失 | 改昨天截止看合理否 |
| 5 排序不生效 | 顺序与紧急度乱 | 验最紧急在最上 |
| 6 跳需求讨论 | 上来写码 | 先聊功能，回忆 Demo |
| 7 越改越乱 | 改一坏一 | 用推倒重来，新开对话 |

## ⑤ 核心纪律与踩坑清单

### 核心纪律（安全 + 边界）
- **安全红线**：Vibe Coding 的甜区是"个人工具 / 原型"——不上线、不碰数据库、不处理敏感数据。任何涉及生产环境、用户隐私、密钥的逻辑都必须人工审查（社区名言："Vibe Coding 里的 S 代表 Security"）。
- **5000 行魔咒认知**：项目超过约 5000 行，AI 开始走神、修 Bug 引新 Bug。策略：及时新开对话、控制规模、分步迭代。
- **原型 ≠ 产品**：Vibe Coding 是快速验证想法的方法，不是生产级开发方法。

### 通用踩坑清单（收尾五条）
1. 一次给太多需求 → 分步来（回扣 C2）。
2. 看不懂代码不知对否 → 用行为验证（QA 视角走核心路径）。
3. 越改越乱 → 推倒重来（新开对话）。
4. 说不清想要效果 → 用参考图 / 具体描述。
5. 数据没存 → 首条需求就明确说"要本地存储"。

## ⑥ 与模块 A3 / Vibe Coding / 迭代 的回扣点

## 教师教学提示（总）

- **两单元共同主线**：人做 Architect、AI 做 Executor。D1 的"问/信/判因果"与 D2 的"需求/验证"本质都是 Architect 职责。
- **D1 的灵魂步骤**是 Step6 验证（不验证 = 把 AI 的话当真理）；**D2 的灵魂步骤**是迭代闭环（首版不完美，价值在迭代）。
- **两个"防骗"设计**值得强调：D1 的"防 AI 背答案手术"（列重命名/干扰列/反转关系/埋脏数据）和 D2 的安全灾难案例，都是为了让学生体验"AI 的流畅 ≠ 正确 / 安全"。
- **模块衔接**：D1 收尾回扣 C1-C3 与 CRISP-DM，D2 收尾回扣 A3 / Vibe Coding / 迭代；讲 D 之前务必确认学生已完成 B、C 模块。
