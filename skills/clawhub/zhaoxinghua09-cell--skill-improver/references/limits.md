# 拒绝清单：工具不肯修的东西

这份清单比"能修什么"更重要。一个只会加东西的自动修复工具，最终会把评测体系变成自欺。

## 四条拒绝，逐条给理由

### 1. 不生成测试用例（`reproducible:no-golden`）

**看起来能做**：按 SKILL.md 命令反推几个输入输出，写进 `tests/golden.json`。

**为什么不做**：测试的价值在于**作者真的验过**。机器猜出来的用例只是把"没有验证"包装成"有验证"——评测器会给分，但包依旧没验过。这是本工具要防的第一号作弊。

### 2. 不生成测试执行器（`reproducible:no-runner`）

**看起来能做**：写一个 `tests/run_golden.py` 循环读用例、比较输出。

**为什么不做**：执行器必须与真实接口对齐。凭空写出来的 runner 极可能一跑就挂，或者更糟——跑通但什么都没验。**空 runner 拿到 reproducible 分，是评分体系最典型的失效点。**

### 3. 不生成 demo（`reproducible:no-demo`）

**看起来能做**：造一个能跑通的示例脚本。

**为什么不做**：demo 的意义是让人第一次用就看到真实效果。伪造的 demo 会用假数字骗过所有后来者。

### 4. 不代写安全边界（`hygiene:no-boundary`）

**看起来能做**：补一句"本技能只读文件、不联网、不执行外部命令"。

**为什么不做**：这是一句**关于行为的断言**。工具不知道这个包实际做什么，替它声明等于替它担保。如果包实际会联网而文档说不联网，这句自动生成的声明就从装饰变成了隐患。

## 一条判断标准

遇到拿不准的项，问一句：

> **改完之后，这个包是真的变好了，还是只是分数变高了？**

后者一律不做。这条标准也适用于任何"自动优化"类工具。

## 拒绝之后怎么办

不是"没修就完了"。工具会：

1. 把拒绝项**逐条列出**，带语义键和原因；
2. 明确说"仍需人工 N 项"，让使用者知道剩下的是真问题；
3. 复测报真实分数——不会因为拒绝了就不给分。

一句话：**能修的修干净，修不动的明说，剩下的才是这个包的真问题。**
