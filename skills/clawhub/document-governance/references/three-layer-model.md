# 三层记录模型（过程层 / 项目层 / 知识层）

## 为什么分层

AI 编程项目的文档最大失败模式是**混杂**：进度、决策、知识、计划写在同一处，导致
- AI 检索时无法判断哪条信息仍然有效；
- 人类无法快速定位"当前约束是什么"；
- 过时信息与有效信息不可区分，最终整篇文档失去信任。

分层模型用"记录目的"切分文档，每层有独立的读者、写入模式与生命周期，从结构上消除混杂。

## 各层定义

### 过程层（Process Layer）

- **记录什么**：事情如何发生——做了什么、当时怎么决定、遇到什么、学到什么。
- **读者**：本迭代的协作者、未来的复盘者。
- **写入模式**：**追加式（append-only）**。已写入的记录不回改；纠错用新条目，不篡改历史。
- **生命周期**：迭代级。迭代结束后归档（移入 archive 或加 `archived` 标记），不再维护。
- **质量标准**：及时 > 精美。当天的决策当天记，因为 AI 与人的记忆一样会衰减。
- **典型文档**：PROGRESS（进展日志）、RETRO（迭代复盘）。

### 项目层（Project Layer）

- **记录什么**：项目的规格与决策——要解决什么问题（PRD）、方案是什么（DESIGN）、为什么这样决策（ADR）、接下来做什么（ROADMAP）、给谁做（PERSONA）、怎么运维（RUNBOOK）。
- **读者**：所有项目参与者（人类 + AI 智能体）。这是 AI 编程时最主要的事实来源。
- **写入模式**：**维护式**。持续更新以保持与最新有效决策一致；重大变更必须留下痕迹（引用 ADR）。
- **生命周期**：项目级，版本化演进。
- **质量标准**：准确 > 全面。每一句技术事实都要经得起与代码核对。
- **典型文档**：PRD、DESIGN、ADR、ROADMAP、PERSONA、RUNBOOK。

### 知识层（Knowledge Layer）

- **记录什么**：从具体经历中提炼的、**脱离具体项目仍成立**的知识——某个坑的成因与解法、某种模式的适用条件、某类问题的排查思路。
- **读者**：跨项目、跨时间的任何人（含 AI）。
- **写入模式**：**提炼式**。一主题一篇；写之前先检索是否已有同主题笔记，有则合并更新而非新建。
- **生命周期**：长期。定期复核（`last-verified`），失效则归档。
- **质量标准**：可复用 > 详细。判断标准：删掉项目名后这篇笔记是否仍然有意义。
- **典型文档**：TECH。

## 层间流动规则

信息只允许向下沉淀（过程层 → 项目层 → 知识层），不允许向上污染：

```
过程层 ──(RETRO 行动项 / 反复操作)──▶ 项目层（ADR / ROADMAP / RUNBOOK）
过程层 ──(去项目化提炼)───────────▶ 知识层（TECH）
项目层 ──(方案抽象化)─────────────▶ 知识层（TECH）
```

具体机制：

1. **RETRO 行动项强制外发**：复盘产出的每一条改进项必须落到具体去处——
   - 是"以后要这样决策" → 新建/更新 ADR；
   - 是"以后要做这件事" → 进入 ROADMAP 待办；
   - 是"这个经验值得记住" → 写成 TECH；
   - 无处可落的行动项视为未完成，复盘不关闭。
2. **重复两次的手工操作 → RUNBOOK**：同一操作在 PROGRESS 中出现第二次，即触发建 Runbook。
3. **TECH 的提炼门槛**：同一个问题在两个以上迭代/项目里出现过，或排查成本超过 30 分钟，才值得成文；否则写在 RETRO 里即可。
4. **反向禁止**：PRD/DESIGN 里不写"这周做了什么"（那是 PROGRESS）；TECH 里不绑定具体项目路径（那会随项目死亡而失效，引用项目仅作示例）。

## 分层与 doc-class 的关系

三层模型决定文档的**归属与生命周期**，doc-class 决定文档的**事实性质**，二者正交：

| 文档 | 层 | doc-class | 说明 |
|---|---|---|---|
| PROGRESS | 过程层 | history | 不可变的历史记录 |
| RETRO | 过程层 | history | 不可变，行动项外发后关闭 |
| PRD | 项目层 | to-be | 规定目标，非现状描述 |
| DESIGN | 项目层 | to-be → as-is | 实现前是规范，实现验收后转现状并持续核对 |
| ADR | 项目层 | history | 决策当时快照，永不在原地改写内容 |
| ROADMAP | 项目层 | to-be | 纯计划性 |
| PERSONA | 项目层 | as-is | 描述真实用户 |
| RUNBOOK | 项目层 | as-is | 描述现有系统操作 |
| TECH | 知识层 | as-is | 陈述已验证事实 |

## 常见反模式

- **流水账式 DESIGN**：把进展、计划、架构混在一篇文档里按时间堆叠 → 拆为 DESIGN + PROGRESS + ROADMAP。
- **永生的 PROGRESS**：一个迭代日志文件写了一年 → 按迭代拆分并归档旧文件。
- **只流入不流出**：RETRO 写完就束之高阁，行动项没有落成 ADR/ROADMAP/TECH → 复盘关闭条件不满足。
- **知识层垃圾场**：TECH 里堆满项目专属细节 → 提炼门槛（见上）没被执行。
