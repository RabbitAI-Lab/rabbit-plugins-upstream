# 五类核心文档 + TECH 知识笔记（类型标准）

本文是全部文档类型的权威定义。任何角色在创建、评审、归档文档前，先在此确认类型归属。

## 总览表

| 类型 | 层 | doc-class | 核心问题 | 受众 | 触发时机 |
|---|---|---|---|---|---|
| PRD | 项目层 | to-be | 我们要解决什么问题？为谁？边界在哪？怎么算成功？ | 全员 | 新需求/新特性立项时，先于实现 |
| DESIGN | 项目层 | to-be→as-is | 方案是什么？为什么是这个方案？ | 工程角色 | 方案复杂度超过"单文件可自明"时 |
| ADR | 项目层 | history | 为什么选了 X 而不是 Y？ | 全员（含未来的自己） | 重大技术选型/权衡发生时，立即记录 |
| PROGRESS | 过程层 | history | 这段时间实际做了什么？ | 迭代协作者 | 迭代开始建档，随做随记 |
| RETRO | 过程层 | history | 哪里做得好/不好？下次改什么？ | 团队 | 每个迭代结束时 |
| TECH | 知识层 | as-is | 这个可复用的知识是什么？ | 跨项目任何人 | 同一问题第二次出现时 |
| PERSONA | 项目层 | as-is | 目标用户是谁？痛点与旅程如何？ | 产品/工程角色 | 用户理解出现分歧或需求定义时 |
| RUNBOOK | 项目层 | as-is | 这项操作怎么执行？出错怎么办？ | 值班/运维/执行者 | 同一手工操作第二次执行前 |
| ROADMAP | 项目层 | to-be | 现在做什么？接下来做什么？ | 全员 | 项目立项时建立，滚动维护 |

## 扩展专业系列（doc-writer 模板库，14 类）

五类核心 + TECH 之外，doc-writer 提供覆盖全交付周期的扩展专业模板（`doc-writer/templates/` 五条线分组），全部遵循同一套 frontmatter/职责头/质量门禁/红线自查/追踪链规范：

| 线 | 类型 | 层 / doc-class | 定位 |
|---|---|---|---|
| 产品 | REQ-SPEC 需求规格 | 项目层 / to-be | **需求唯一真值源**：逐 FR 的 Given/When/Then；PRD/USER-STORY/TEST-PLAN 只引用不复制 |
| 产品 | USER-STORY 用户故事 | 项目层 / to-be | 故事地图 + US/UC 转译，INVEST 自检，验收引用 GWT |
| 产品 | UI-SPEC UI 规格 | 项目层 / to-be | 五态/四全局态门禁，逐页信息架构挂 API 端点 |
| 产品 | BUSINESS-PROCESS 业务流程 | 项目层 / to-be | BP 端到端流程图与关键场景时序，异常路径强制 |
| 架构 | API-CONTRACT API 契约 | 项目层 / to-be | 冻结后为前后端与测试唯一依据；FR↔端点覆盖映射 |
| 架构 | DDD-DESIGN 领域设计 | 项目层 / to-be | 限界上下文/聚合不变量/三数据合同 |
| 架构 | DEV-STANDARDS 开发规范 | 项目层 / to-be | 仓库拓扑/工作流/规范索引/例外豁免登记 |
| 架构 | REVERSE-ANALYSIS 逆向分析 | 项目层 / as-is | ORRI：合法性门禁 + 零推测观察 + 五类场景产出 |
| 交付 | TEST-PLAN 测试计划 | 项目层 / to-be | 冒烟先行策略 + TC↔FR/端点映射 + 风险加深 |
| 交付 | TEST-REPORT 测试报告 | 过程层 / history | 执行矩阵 + FR 验收矩阵 + 脱敏缺陷清单 + 发布建议 |
| 交付 | DEPLOY-GUIDE 部署指南 | 项目层 / as-is | 新人可从零部署门禁 + 配置项清单 + 回滚三条件 |
| 交付 | CHANGELOG 变更日志 | 项目层 / history | Keep a Changelog + SemVer，每条可追溯 |
| 过程 | HANDOFF 交接单 | 过程层 / history | 总指挥跨角色委派载体，user_brief 逐字透传 |
| 过程 | PR-SUMMARY 交付摘要 | 过程层 / history | 任务收尾一页纸：交付清单 + 质量结论 + 验证命令 |

**核心真值链**（同一信息只维护一处）：

```
REQ-SPEC（需求真值）→ PRD / USER-STORY（转译）→ API-CONTRACT / DESIGN（承载）
→ TEST-PLAN / TEST-REPORT（验证）→ DEPLOY-GUIDE / RUNBOOK（运维）
→ CHANGELOG / PR-SUMMARY（交付记录）→ TECH / ADR（沉淀）
```

## PRD（产品需求文档）

**定位**：定义问题、用户、需求边界与成功指标。PRD 是规范文档（to-be）——它规定"应当做成什么"，不描述"现在是什么"。

**必须包含的四个要素**：
1. **问题定义**：用户在什么场景下遇到什么困难，现状为何不可接受。
2. **目标用户**：链接到 PERSONA 文档；无画像支撑的"所有用户"视为边界缺失。
3. **需求边界**：in-scope / out-of-scope / 明确的 non-goals。**边界缺失是 PRD 最常见缺陷**——没有 out-of-scope 的 PRD 会被无限扩张。
4. **成功指标**：每个指标必须可度量、有基线、有目标值、有测量方式。不可度量的"用户满意度提升"是愿景，不是指标。

**人机双重视角**：需求条目带稳定 ID（FR-xxx / NFR-xxx）供 DESIGN 覆盖追踪与 AI 实现时逐条核对；逐条验收标准（Given-When-Then）归 REQ-SPEC（`docs/project/req-spec.md`，唯一真值源），PRD 只保留需求摘要与链接，禁止复制。

**质量红线**：PRD 不写实现方案（那是 DESIGN 的事）；不写排期（那是 ROADMAP 的事）。

## DESIGN（设计文档）

**定位**：技术方案的结构化描述，采用 **arc42 骨架 + C4 视图**（详见 `../../doc-writer/references/format-guides.md`）。

**C4 分级**（按需取用，不必全画）：
- **L1 系统上下文**：系统与外部角色/系统的边界——必画。
- **L2 容器图**：系统内的进程/服务/存储划分——单体超过 3 个模块或多服务时必画。
- **L3 组件图**：单个容器内部的组件划分——仅对复杂容器绘制。
- **L4 代码级**：不进文档，由代码自身表达。

**与 ADR 的关系**：DESIGN 中每个重大选型必须以 `ADR-NNNN` 引用支撑；出现了没有 ADR 的重大选型，是评审 Blocker。

**生命周期**：设计定稿未实现时 doc-class 为 to-be；实现并通过验收后转为 as-is，之后每次架构变更同步更新，并接受与代码的交叉验证。

## ADR（架构决策记录）

**定位**：一条 ADR 记录一个技术决策的完整上下文——背景、决策、理由、备选、后果。它是历史文档（history），**accepted 之后内容永不在原地修改**，变更通过新 ADR 取代（superseded）。

**五种状态**（完整状态机与规则见 format-guides.md）：
`proposed（提议）→ accepted（接受） | rejected（拒绝）`；`accepted → deprecated（废弃） | superseded（被取代）`。

**不可替代的价值**：rejected 的 ADR 同样保留——记录"考虑过且被否决的方案及原因"，防止团队与 AI 重复论证已经否决的路线。

## PROGRESS（进度文档）

**定位**：迭代内的追加式工作日志，属于过程层。**记录事实，不做评价**（评价属于 RETRO）。

**格式要点**：
- 按日期/条目追加，不回改历史条目；纠错追加新条目。
- 每条记录：做了什么、相关产出（链接 commit/PR/文档）、过程中的临时决策（事后该立 ADR 的要补）。
- 结束时记录阻塞项与交接要点。

**归档**：迭代结束、RETRO 完成后即归档，不再维护。

## RETRO（复盘文档）

**定位**：对一段时间工作的结构化反思，属于过程层。**事实已留在 PROGRESS，RETRO 只负责提炼判断与改进行动**。

**结构**：目标回顾（对照迭代目标/ROADMAP 承诺）→ 做得好的 → 做得不好的 → 改进行动项。

**关闭条件**：每条行动项必须外发到具体去处（ADR / ROADMAP / TECH / RUNBOOK），否则复盘不算完成。RETRO 本体随后归档。

## TECH（知识笔记）

**定位**：知识层的单主题笔记，从具体经历中提炼、去项目化后仍然成立。

**结构**：问题 → 背景 → 方案 → 适用范围与限制 → 参考。

**成文门槛**：同一问题第二次出现，或排查/解决成本超过 30 分钟。低于门槛的发现写在当期 RETRO 里。

**复核**：frontmatter 维护 `last-verified`；知识依赖的外部版本/环境变化后须复核，失效则归档。

## PERSONA（用户画像）

**定位**：目标用户的结构化描述——背景、痛点、**四阶段使用旅程**、期望与成功标准。服务于 PRD 的用户定义与需求优先级判断。

**四阶段用户旅程分析框架**：认知（如何发现）→ 评估（如何比较决策）→ 使用（如何上手与日常使用）→ 沉淀（如何获得价值、留存与传播）。每阶段分析场景、行为、触点、情绪与机会点。详见 format-guides.md。

## RUNBOOK（运维手册）

**定位**：可执行的操作手册，描述**现有系统**（as-is）的某项操作。采用强制四段式：**前提条件 → 操作步骤 → 验证 → 故障排查**。详见 format-guides.md。

**与 ADR 的区别**：Runbook 回答"怎么做"，不回答"为什么"；操作背后的架构原因链到 DESIGN/ADR。

## ROADMAP（路线图）

**定位**：项目层计划文档（to-be），**强制分离当前迭代与待办事项**：
- **当前迭代**：已承诺事项，链接 PROGRESS 跟踪，有明确的完成标准；进入即代表承诺。
- **待办 Backlog**：按优先级排序的候选事项，每项标注来源（PRD 条目 / RETRO 行动项 / 战略目标）；进入当前迭代时移入并建立跟踪。
- **Later / 已拒绝**：暂缓与明确不做的事项（保留拒绝原因，作用同 rejected ADR）。

**红线**：待办不是承诺——向外部承诺前必须先移入当前迭代。

## 类型选择的快速判据

1. 内容是"发生的事实" → 过程层（PROGRESS/RETRO）
2. 内容是"规定的目标/计划" → 项目层 to-be（PRD/ROADMAP/规范）
3. 内容是"现存系统的描述" → 项目层 as-is（DESIGN-as-is/RUNBOOK）
4. 内容是"某个决策的来龙去脉" → ADR
5. 内容是"删掉项目名仍有价值的知识" → TECH
6. 拿不准 → 先按最接近的类型建小文档，由治理专家在巡检时归位。
