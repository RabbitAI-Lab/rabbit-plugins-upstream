# 现状文档与规范文档的强制区分（as-is / to-be）

## 问题背景

文档失信任的头号原因是**读者无法判断哪句话仍然有效**。典型症状：

- 架构文档里一半描述已实现的系统，一半描述"计划中"的架构，未加区分；
- 运维手册混着旧流程（已下线）与新流程（未推行）；
- AI 智能体读到"应当使用消息队列"（规范）与"当前使用同步调用"（现状）并存，实现时随机采信其一。

解法：每篇文档声明 `doc-class`，且**内容性质必须与声明一致**。

## 三种 doc-class

### `as-is`（现状文档）

- **定义**：描述当前实际存在的系统、流程、事实。
- **契约**：内容与现实一致。与代码/系统不符即为缺陷（漂移），必须修复文档或修复现实。
- **写作口吻**："系统当前…"、"配置为…"、"流程是…"（现在时陈述）。
- **代表文档**：实现后的 DESIGN、RUNBOOK、TECH、PERSONA。
- **附加义务**：frontmatter 必须维护 `last-verified`（最近一次与实现核对通过的时间）。

### `to-be`（规范文档）

- **定义**：规定应当达到的目标、标准、计划。允许尚未实现。
- **契约**：内容是**指令性**的；未实现不构成缺陷，但必须可辨认"已实现/未实现"。
- **写作口吻**："系统应当…"、"必须…"、"不得…"（祈使/规范语气）。
- **代表文档**：PRD、ROADMAP、实现前的 DESIGN、编码规范、流程规范。
- **附加义务**：条目应带状态标记或版本，便于追踪落地进度（进度本身记在 ROADMAP/PROGRESS，不在规范文档内展开）。

### `history`（历史记录）

- **定义**：某时间点的不可变快照。
- **契约**：内容冻结，永不改写；其价值恰恰在于"它记录了当时"。
- **代表文档**：ADR、PROGRESS、RETRO。

## 强制规则

1. **声明强制**：所有文档 frontmatter 必须含 `doc-class`；缺失视为治理缺陷。
2. **同篇共存、同章禁混**：同一文档内允许存在 as-is 章节与 to-be 章节（如 DESIGN 的"现状架构/目标架构"分章），但**同一章节内禁止混写**，且章节标题必须显式标注性质（"当前架构（as-is）" / "目标架构（to-be）"）。
3. **口吻自检**：as-is 章节出现"应当/必须/计划"字样，或 to-be 章节出现现在时事实陈述，均为混写信号。
4. **状态迁移**：规范落地后必须迁移文档状态——
   - DESIGN：实现验收通过后 `doc-class: to-be → as-is`，从此接受与代码的核对；
   - ROADMAP：待办完成进入当前迭代再转为交付事实（事实落在 PROGRESS）；
   - 迁移只改 frontmatter 与状态标记，不动历史正文，必要时附变更说明。
5. **ADR 特殊性**：ADR 是 history，**不代表当前约束**。"当前有效约束" = 全部 `accepted`/`deprecated` ADR 的聚合 + 现行 DESIGN/规范。引用 ADR 时须确认其状态。
6. **禁止"隐形规范"**：规范只能存在于声明为 to-be 的文档（或规范库）中。在 as-is 文档里夹带"建议大家以后都…"是治理缺陷——应抽出为独立规范或 ADR。

## 判别流程（遇到混淆时）

1. 这句话如果明天实现变了，它就错了 → as-is。
2. 这句话描述的是要求，实现了才对、不实现是问题 → to-be。
3. 这句话描述的是当时怎么想的，无论后来如何它都不改 → history。
4. 三者都像 → 文档本身职责混杂，触发治理专家做拆分评审。

## 典型示例

**反例（混写）**：
> 部署使用 k8s（现状）。服务间通信应当全部迁移到事件驱动（规范）。网关目前是 nginx（现状），我们计划换成自研网关（计划）。

**正例（分节）**：
> ## 当前架构（as-is）
> 部署使用 k8s；网关为 nginx。
> ## 目标架构（to-be）
> 服务间通信应全部迁移到事件驱动（依据 ADR-0012）；网关计划替换为自研网关（追踪：ROADMAP 待办 #23）。
