# Agent Skill 课程知识点速查

按"核心链路 → 结构 → 存储 → 安全 → 进阶"组织，出巩固材料时按需取用。

## 1. 触发与执行流程（核心链路）

用户请求 → 意图匹配（name / description / keywords）→ 调用 Skill 工具加载 SKILL.md → 指令注入上下文（渐进式披露）→ 按步骤执行（调用工具 / 脚本 / MCP）。

关键结论：
- 匹配对象是**用户怎么描述需求**，不是"功能叫什么名字"
- 匹配不中 → 不加载，直接用通用能力回答
- keywords 解决精确命中，description 解决语义相似，两者缺一不可

意图匹配三层递进（延伸）：
1. 精确命中：消息中出现技能名或 keywords 原词
2. 语义相似：消息与 description 语义相近
3. 主动检索：模型判断可能存在现成技能，主动搜索技能列表

## 2. SKILL.md 结构解剖

一个 skill 包 = SKILL.md（唯一必需）+ 附属资源（可选）。

- **YAML frontmatter（给系统看的）**：name（小写连字符）、description（写"何时使用"，推荐 "Use when..." / "当用户要求 X / 提到 Y 时使用" 句式）、keywords（中文别名 + 口语表达 + 场景词）、metadata（版本 / 依赖声明）
- **Markdown 正文（给模型看的）**：前置条件、工作流程（分步骤）、安全规则、输出格式

一句话总结：**frontmatter 是简历，正文是操作手册**。简历决定有没有面试机会（被触发），操作手册决定活干得好不好（执行质量）。

附属资源：
- `scripts/`：可执行脚本（重复编写的代码、需要确定性可靠性的任务）
- `references/`：详细参考文档（大文档放这里，需要时再读）
- `assets/`：输出用的静态资源（模板、图片、字体），不进上下文

## 3. 渐进式披露（三级加载）

1. 元数据（name + description）：常驻上下文，约 100 词
2. SKILL.md 正文：触发时加载（建议 <5k 词）
3. 附属资源：按需读取（脚本可直接执行不进上下文，近乎无限）

为什么不全量加载：
- token 成本：几十个 skill 全量加载会吃掉大量上下文
- 执行准确性：无关指令稀释注意力，诱发用错技能；上下文越聚焦，指令遵循越准

## 4. 两级存储

| 级别 | 路径 | 范围 | 适用 |
|------|------|------|------|
| 用户级 | `~/.workbuddy/skills/` | 所有项目 | 个人习惯、通用工作流 |
| 项目级 | `{workspace}/.workbuddy/skills/` | 当前项目，可随仓库共享 | 团队约定、项目专属流程 |

生命周期：安装前安全审计 → 使用中积累改进 → 发现问题及时修正。

## 5. 安全模型

Skill 本质是**注入到模型上下文的指令**，模型当作可信指令执行：
- 恶意正文可夹带隐匿指令（读取敏感文件并外传等）
- `scripts/` 脚本拥有本机执行权限，等同安装来路不明的软件
- 指示模型拉取远程文档再执行 = 二次注入风险

审计分级：P0 拒装、P1 警告并要求确认、P2 放行。与审查第三方依赖同一思路。

## 6. 好 Skill 的三重边界

- 任务边界：只做一类事，写清"不做什么"
- 数据边界：明确读写路径，绝不静默保存密钥（密钥落盘前必须询问并获同意）
- 动作边界：只报告不擅改；对外发送类动作必须先确认

description 反例：笼统（"一个很有用的技能"）→ 该触发触发不了，不该触发乱触发。
自检标准：两个技能的 description 放一起能否一眼分清谁管什么。

## 7. 评估方法（延伸）

- 触发率（召回）：测试话术集上该触发的触发了吗
- 误触发率（精确）：不该触发的场景有没有乱入
- 端到端成功率：触发后按流程走完并产出正确结果的比率
- 实践：为每个非玩具技能维护 10-20 条测试话术清单，改完回归——skill 的"单元测试"

## 8. Skill vs MCP（延伸）

本质区别：**指令 vs 能力**。Skill 传授方法（提示词、流程、约定），不增加新能力；MCP 提供能力（外部数据、API、执行通道），本身不含方法。
决策顺序：缺能力先上 MCP，缺方法写 skill，两者常配合使用。
