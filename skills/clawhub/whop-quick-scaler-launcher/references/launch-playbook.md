# Launch playbook

## Purpose and operating boundary

Use this playbook to release a Whop product or an independent Whop-related tool, then check its first week. All initial destinations go live on Day 1. Days 2 to 7 are for verification, useful demonstrations, corrections and review, not a staggered initial release.

The procedures below are adapted from operating workflows. The calendar is a recommended work sequence, not a promise of admission, traffic, sales or search visibility. Examples and copy templates are generic. Whop documentation was checked on 29 September 2026.

Default to local preparation and read-only inspection. A launch plan does not authorize account creation, remote edits, invitations, scheduling, sending, publication or payment tests. Obtain approval for the exact action, target and date before executing it. Whop states that its CLI has no sandbox, test or dry-run mode; CLI operations affect production. A local preview must be described as a local preview. [W1]

For an independent tool, say that it is unofficial. Separate a guidance-only assistant from a connected version that can make approved changes. Publish only capabilities exercised in the release being distributed.

## 1. Define the release before choosing the date

Assign a release owner, a builder, an independent verifier and a distribution operator. One person can cover several operational roles, but a writer or builder must not be the only person approving their own claims.

Complete this local release record:

```text
Audience and problem:
One observable task the release helps with:
Included deliverables:
Excluded capabilities:
Canonical product or project page:
Canonical release and version, if software:
Guidance-only or connected operation:
Whop purchase destination, if applicable:
Access or delivery route after signup or purchase:
Commercial terms approved by the owner:
Required initial destinations:
Optional destinations, excluded from the launch promise:
Common launch date and named time zone:
Release owner / verifier / distribution operator:
Budget and separately approved expenses:
Authorization record for each external action:
Stop conditions and recovery owner:
```

Use the returned, verified purchase URL. Do not reconstruct it from a product title or replace a redirecting checkout with a different purchase link merely because both show the same offer. Inspect the actual destination and its configuration.

For a free release, verify the whole joining flow before saying “no card required.” Whop's checkout documentation describes an “Add a waitlist” option that collects card details and charges on approval, including in the free-link section. A waitlist is therefore not automatically a no-obligation interest form. Keep that option off for a card-free interest list and verify that there is no payment mandate or unrelated paid access. [W2, W3]

### Example scope

A course creator offers a reusable lesson-planning worksheet. The launch promise is access to that worksheet and its instructions. Coaching, a private group and future course updates are excluded unless separately approved. The demonstration uses illustrative lesson content and does not present fictional customers or earnings as evidence.

## 2. Build one release pack

Prepare the following before announcing a date:

- The product or tested software package, with its version, instructions, prerequisites and known limitations.
- A canonical page with the audience, deliverable, access route, terms and one primary action.
- A short demonstration of the actual release. Use a clearly labeled local demonstration when remote execution has not been authorized.
- Channel-specific descriptions, approved media, accessibility text and the exact links to be used.
- A source-backed FAQ covering setup, access, billing where applicable, limitations and support.
- An evidence record and a recovery procedure for each publishing surface.

Keep private account data, credentials, customer details, internal notes and unapproved commercial terms out of the pack, including screenshots, video frames, file metadata and generated archives.

For a tool, use one canonical source release. Adapt its packaging to each supported client; do not create duplicate projects to manufacture popularity. Test a fresh installation and a repeat installation for every compatibility claim. Confirm that a guidance-only version never reports an account mutation it did not perform.

For a Whop product, reconcile page copy, product, pricing variant, checkout and delivered content. Preserve the approved amount, currency, billing interval, access duration, questions and redirect. A checked page is not evidence of a completed payment or delivery test.

## 3. Resolve same-day publication constraints

“Same day” means that every required destination is publicly usable within the agreed calendar date and time zone. It does not mean that every submission was sent that day.

Maintain one row per actual destination. Separate formats on the same destination when they have different review processes.

| Destination class | What must be ready | Evidence required on Day 1 |
| --- | --- | --- |
| Canonical source or product page | Frozen release, instructions, demonstration and valid access route | Exact public page and the expected version or offer |
| Conversational assistant catalog | Working conversation, accurate limits and accepted identity | Public assistant opens and completes its advertised guidance scenario |
| Installable skill catalog | Complete package, license and tested installation instructions | Public listing and a fresh installation of its served package |
| Tool-server registry | Working server, valid manifest and supported transport | Accepted entry plus successful tool discovery in the advertised client |
| Plugin catalog | Reviewed package and the exact release reference | Public catalog entry points to the reviewed version |
| General tool directory | Real product page, accurate description and accepted listing | Public listing leads to the usable product, not only a referral link |
| Whop Marketplace, when included | Product submission prerequisites and completed review | The actual offer is publicly listed, separately from direct checkout availability |

These are distribution classes, not claims about a particular catalog's rules. Check each selected destination's current rules, charges, name availability, review process and allowed referral placement.

1. Identify any destination that requires an already-public source release before review.
2. Ask whether private prereview or a coordinated release is genuinely supported. Do not invent an embargo arrangement.
3. Record whether submission itself becomes public. Early submission can violate the common launch date.
4. If a required review cannot finish within the agreed constraints, postpone the common launch or have the owner explicitly narrow its scope before launch. Do not silently spread it over several days.
5. Treat unsolicited mirrors and search indexing as later discoveries outside the controlled same-day commitment.

Whop's “Publish Product” operation submits a product for Marketplace review. Submission is not Marketplace approval, and direct checkout availability is a separate state. Do not promise a review deadline that Whop has not confirmed for the actual submission. [W4]

## 4. Pass the preflight

### Product and permissions

- [ ] The offer, inclusions, exclusions and customer-facing terms match the approved release.
- [ ] The selected Whop business and the ownership of each affected object have been verified privately. Similar display names are insufficient.
- [ ] Existing drafts are reused rather than duplicated after an interruption.
- [ ] New preparation resources are hidden and closed to entry until opening is authorized. Already-live resources outside scope are unchanged.
- [ ] The direct checkout has been checked separately. Hiding a store-page option does not disable its shared link. [W2]
- [ ] Affiliate participation and rates have been inspected explicitly, including global and member settings. Do not assume defaults suit the product. Use the affiliate procedure in [Acquisition](acquisition.md).
- [ ] Required delivery exists. A manual delivery route, if approved, is described honestly instead of being called automatic.

### Content and buyer experience

- [ ] The public page and checkout show the correct seller, offer, billing terms and access route on desktop and mobile.
- [ ] The demonstration shows the actual release and labels untested steps.
- [ ] Every CTA and asset loads at its exact intended destination. A successful HTTP response alone is insufficient.
- [ ] The package, preview images and social snippets contain no private material or invented proof.
- [ ] Any real signup, purchase, invitation or message used for testing has its own approval. Never press a payment button just to inspect it, particularly in a session with saved cards.
- [ ] Public descriptions distinguish unofficial guidance from supported connected operations.

### Distribution

- [ ] Every required destination has a feasible same-day admission path.
- [ ] The approved date includes a named time zone and an operator available to verify the release.
- [ ] Messages, recipients or audiences, media, links and expenses have been approved for their specific actions.
- [ ] The owner has accepted the recovery procedure and knows who can stop promotion.

An unchecked required item is a no-go. “Unknown” stays unknown; it must not be silently counted as a pass.

## 5. Execute Day 1 in dependency order

Publish sequentially within the common date. This avoids sending people to listings whose underlying release is still missing.

1. Confirm the go decision, the frozen version and the before-state of every surface to be changed.
2. Make the canonical release, product page and demonstration available within the authorized scope. Verify their served content immediately.
3. Release the guidance-only assistants and installable packages that depend on the canonical page. Verify access and the advertised task in each format.
4. Release the tool-server and plugin entries from the same tested version. Read back each entry and test its referenced package or endpoint.
5. Release the prepared directory listings and any approved Whop Marketplace entry once their prerequisites are met. Record review-pending entries as pending.
6. Reconcile the required destination list against public evidence. If a required destination failed after the first release, pause the broad announcement, preserve the working surfaces and report the failed same-day condition. Do not delete working resources or relabel the launch without approval.
7. After the destinations and access route pass, send the approved audience announcement. Verify each post, its media and its link or first comment. Newsletter dispatch requires its own explicit approval.
8. Save the end-of-day receipt, including everything still unverified.

After a timeout, read the exact destination before retrying. An uncertain response can hide a completed publication. Resume the same object or release rather than creating a duplicate.

If a checkout, permissions check or delivery route fails, stop new promotion of the affected offer. Use only the approved recovery action. Never erase existing memberships, alter financial terms or trigger refunds as an improvised rollback.

## 6. Ask the audience for useful actions

Choose one primary action per message. Make optional support secondary and voluntary.

| Audience | Primary request | Optional request | Avoid |
| --- | --- | --- | --- |
| Curious readers | Watch the demonstration | Share it with someone facing the same task | Asking for a purchase before explaining the deliverable |
| Intended users | Try the documented task or obtain the product | Report the first unclear step | Forcing account creation when an existing account works |
| Technical users | Install the tested release if they want to use it | Star or bookmark the canonical project if useful and supported | Paid stars, exchanged ratings, artificial accounts or scripted engagement |
| Existing customers | Use the new resource or feature available to them | Give honest feedback about actual use | Invented testimonials or a positive-review requirement |
| Potential affiliates | Read the approved product-affiliate terms | Apply voluntarily where applications are used | Automatic enrollment, undisclosed commissions or earnings promises |

A star, view, conversation, download and completed task measure different actions. None guarantees a catalog ranking, sale or product activation.

### Announcement template

Replace bracketed fields with verified facts before submitting the message for approval.

```text
[RESOURCE] helps [AUDIENCE] complete [SPECIFIC TASK].

The demonstration shows [OBSERVABLE STEPS].
Included: [DELIVERABLES].
Limit: [IMPORTANT EXCLUSION OR UNTESTED STEP].

Try it here: [VERIFIED PRODUCT OR PROJECT LINK]
If you try it, tell us which step was unclear. Remove private account and
customer information from any example you share.
```

For an independent tool, add:

```text
This is an independent, unofficial tool for Whop.
The guidance-only version prepares text and instructions. It does not change
your Whop account. A connected version makes only the changes you approve.
```

Use the connected-version sentence only when that version exists and has passed its tests.

### Optional project-support request

```text
If this project is useful, you can star or bookmark its canonical page where
that option is available. Install it only if you want to try it.
```

### Useful feedback request

```text
What task were you trying to complete?
Which release or product version did you use?
Which step failed, and what did you expect instead?
Share a sanitized reproduction if possible. Do not send credentials,
payment details or customer information.
```

Do not bundle all these requests into the launch message. Use the one appropriate to the audience and its stage.

## 7. Run the 7-day calendar

Day 1 is the common public release. The remaining days improve and verify that release without quietly adding unfinished initial destinations.

| Day | Operator action | Evidence and decision |
| --- | --- | --- |
| Day 1 | Execute the dependency order, verify the complete required destination set, then publish the approved announcement | Per-destination access, version, admission state and live links; record any missed commitment explicitly |
| Day 2 | Reinstall from the public listings or repeat the real access route; inspect the first reported blockers | Test the served artifact, not the private build; fix only authorized, reproducible defects |
| Day 3 | Inspect discovered copies and owned listings for identity, version and link drift | Correct owned surfaces within scope; label uneditable copies and unknown attribution honestly |
| Day 4 | Explain the already-live demonstration with one useful use case | Show an actual capability; use a clearly labeled hypothetical example when no real customer evidence is available |
| Day 5 | Resolve the highest-impact setup or documentation defect and repeat the affected tests | Updated version record and proof of the correction; refresh pinned catalog references where required |
| Day 6 | Read native counters and admission states; check that descriptions and links still match the product | Dated measurements with units and periods; separate visits, installs, usage and payments |
| Day 7 | Close the launch review and select one next improvement | Verified destination inventory, unresolved blockers, owner and acceptance test for the next change |

Timing should reflect the actual audience and support capacity. No specific weekday or hour is a universal best time. Do not schedule reminder messages by default; each follow-up needs a new useful angle and the applicable sending approval.

## 8. Close with evidence

Keep the launch receipt factual:

```text
Release / date / time zone:
Required destinations:
Verified publicly usable destinations:
Pending or failed destinations and exact reasons:
Served version and installation or access checks:
Product visibility:
Pricing-option visibility:
Direct checkout availability:
Marketplace state:
Post-purchase redirect configured:
Real payment tested: yes / no
Actual delivery tested: yes / no
Announcement and newsletter dispatch states:
Observed counters, source, unit and measurement period:
Unresolved risk:
Next correction / owner / acceptance test:
```

Mark irrelevant fields “not applicable,” and record tests not performed. Do not add installations to stars, infer purchases from clicks, or present a configured redirect as a verified post-payment journey. Choose the next improvement from observed friction before adding another destination or feature.
