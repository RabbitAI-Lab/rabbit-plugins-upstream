# Patching — Diff, Patch, and Merge Between Two Documents

Text diffs on JSON are noise: a reordered key or a re-indent produces a full-file diff with no semantic change. Everything here operates on the structure.

**Contents:** [Semantic Diff](#semantic-diff) · [JSON Patch (RFC 6902)](#json-patch-rfc-6902) · [JSON Merge Patch (RFC 7386)](#json-merge-patch-rfc-7386) · [Choosing Between Them](#choosing-between-them) · [The Array Identity Problem](#the-array-identity-problem) · [Three-Way Merge](#three-way-merge) · [Concurrency](#concurrency) · [Applying a Patch Safely](#applying-a-patch-safely) · [Making Diffs Readable](#making-diffs-readable)

## Semantic Diff

- Compare parsed structures, not text: objects are unordered, so key order differences are not changes; arrays are ordered, so element order differences are.
- Report differences as a list of `{op, path, from, to}` with paths as JSON Pointers (`querying.md`) — that form is both human-readable and directly convertible to a patch.
- Numbers compare by value, not by text: `1.0` and `1` are the same number and a different string. A diff tool that says they differ is comparing text.
- Before diffing files that should be identical, canonicalize both (`signing.md`); otherwise indentation and escaping style dominate the output.
- For diffing two versions of a *schema*, diff the resolved and bundled form, not the source, or a `$ref` reorganization looks like a contract change (`schema.md`).

## JSON Patch (RFC 6902)

An array of operations, media type `application/json-patch+json`, applied **atomically**: if any operation fails, the whole patch fails and the document is unchanged.

```json
[
  { "op": "test",    "path": "/version", "value": 7 },
  { "op": "replace", "path": "/status", "value": "paid" },
  { "op": "add",     "path": "/tags/-", "value": "urgent" },
  { "op": "remove",  "path": "/note" },
  { "op": "move",    "from": "/tmp/x", "path": "/x" },
  { "op": "copy",    "from": "/a", "path": "/b" }
]
```

- Every `path` is a JSON Pointer, with `~0`/`~1` escaping and `-` meaning "append" for arrays.
- `add` on an existing object key **replaces** it; on an array index it **inserts** before that index. Those are different operations sharing one name.
- `remove` on a missing path is an error, not a no-op. Patches are not idempotent: applying the same `add ... /tags/-` twice appends twice.
- `test` is the concurrency primitive: it compares by JSON equality (deep, order-insensitive for objects, order-sensitive for arrays) and fails the whole patch on mismatch.
- `move` and `copy` are conveniences; a generated patch that uses them can be correct and unreadable. For machine-to-machine use they are fine, for a human-reviewed changeset prefer explicit remove/add.

## JSON Merge Patch (RFC 7386)

A document shaped like the target, media type `application/merge-patch+json`:

```json
{ "status": "paid", "note": null, "shipping": { "carrier": "dhl" } }
```

- Objects merge recursively; `null` **deletes** the key.
- Therefore a merge patch **cannot set a value to null** — the single limitation that decides most designs (Rule 3: if your API distinguishes null from absent, merge patch cannot express one of them).
- Arrays are replaced wholesale. There is no way to append one element or change element 3.
- Idempotent: applying the same merge patch twice gives the same result. That makes retries safe, which is why it fits HTTP PATCH so well.
- Not atomic in the RFC-6902 sense — there is nothing to fail; it is a merge, so partial-looking outcomes come from your own validation, not from the format.

## Choosing Between Them

| Question | JSON Patch | Merge Patch |
|---|---|---|
| Change one array element | Yes | No — replaces the array |
| Set a field to null | Yes | No — that deletes it |
| Delete a field | Yes (`remove`) | Yes (`null`) |
| Idempotent | No | Yes |
| Atomic with a precondition (`test`) | Yes | No |
| Readable by a human | Moderate | High — it looks like the resource |
| Size on the wire for a small change | Larger | Smaller |
| Client implementation effort | Needs a library | Trivial |

Default: **merge patch** for a public API where clients send small, partial updates and null-versus-absent is not distinguished. **JSON Patch** when arrays must be edited element-wise, when a precondition must be atomic, or when the patch is generated by a machine. Document which one, in the media type, and reject the other — accepting both on one endpoint means a body that is valid under both interpretations does two different things.

## The Array Identity Problem

Patching arrays by index is safe only if nobody else can reorder them. In a concurrent system nobody can promise that:

- A patch that says `replace /items/2/qty` applied after another writer inserted an element edits the wrong record — silently, and with a plausible result.
- Fix by identity: treat arrays of entities as maps keyed by a stable id. Either the payload holds an object keyed by id (queryable, unordered) or the patch addresses elements by a `test` on the id before the change:
  `[{"op":"test","path":"/items/2/id","value":"sku-9"},{"op":"replace","path":"/items/2/qty","value":3}]`
- Ordered arrays where order is data (a playlist) need a different move: send the whole array, or an explicit reorder operation with the full id sequence.
- Diff generators frequently produce index-based array patches that look minimal and are unsafe under concurrency. Review generated array operations before shipping them to a multi-writer endpoint.

## Three-Way Merge

Base, ours, theirs — the shape for config files in version control and for offline-first clients:

1. Compute the diff base→ours and base→theirs as structural changes.
2. Non-overlapping paths merge cleanly, regardless of key order.
3. The same path changed on both sides is a conflict unless both changed it to the same value.
4. Arrays are where three-way merges fail: two inserts at different positions are not a conflict semantically but are one positionally. Key by id and merge as a map when the array is a set of entities.

Reducing merge conflicts in checked-in JSON (lockfiles, fixtures, translations):

- Sort keys deterministically when writing the file, so unrelated additions never reorder anything.
- One value per line — expanded formatting, not compact — so a line-based merge tool can do its job.
- Keep arrays sorted by a stable key when order is not data.
- These three habits turn most JSON merge conflicts into clean merges, at the cost of a larger file in the repository (`testing.md`).

## Concurrency

- **ETag + `If-Match`**: the server rejects a PATCH whose `If-Match` does not equal the current ETag with 412. This is the cheapest correct optimistic concurrency for HTTP APIs, and it needs a stable ETag — which needs canonical serialization or the stored bytes (`signing.md`).
- **`test` operations** put the precondition inside the patch, which works for transports that have no headers and lets a patch assert several preconditions at once.
- **A `version` field** in the resource, asserted by the patch and incremented by the server, is the transport-independent version of the same idea.
- Never rely on "read, modify, write the whole document": it silently discards any field another writer changed between the read and the write. That is lost-update, and it looks like data disappearing at random.

## Applying a Patch Safely

1. Reject unknown operations rather than ignoring them — an ignored `op` is a change the client believes happened.
2. Enforce the same limits you enforce on any input: patch array length, path depth, and resulting document size (`security.md`). An `add` with a huge value is an unbounded write, and a `copy` can multiply a subtree repeatedly.
3. Forbid patches that reach fields the caller may not change (`/id`, `/created_at`, `/owner`) with an allowlist of paths, not a denylist.
4. **Validate the result against the schema after applying**, before persisting. A patch is a sequence of legal operations that can produce an illegal document (`schema.md`).
5. Apply atomically: build the new document, validate, then commit. Never mutate in place operation by operation on the stored object.
6. Return the resulting resource (or 204 with an ETag), so the client does not have to guess what the merge produced.

## Making Diffs Readable

- Canonicalize both sides first: sorted keys, consistent number formatting, no insignificant whitespace (`signing.md`).
- Pretty-print with one value per line for review; compact only for transport.
- Elide unchanged subtrees in a review-facing diff and show the pointer path, not the full nesting.
- For a large structural change, show a summary first — counts of added, removed and changed paths — then the detail. A 4,000-line diff nobody reads is equivalent to no review.

**When a transformation between two shapes is worked out** — a mapping from a legacy payload to a new one, a migration patch, a merge policy — write it to `~/Clawic/data/json/artifacts/<kebab-name>.md` as a source-path → target-path table with the rules, and add its `## Boxes` line in the same turn (`memory-template.md`). Field mappings are re-derived every time they are not written down.
