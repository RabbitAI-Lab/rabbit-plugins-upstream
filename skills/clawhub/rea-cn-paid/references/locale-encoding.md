# REA-CN 环境编码参考（防中文/GBK 乱码）

> 纯英文引擎在中文 Windows / 中文 Locale 下最常见的两个坑：① 中文文件路径导致解析失败；② 终端 GBK 让引擎英文输出变乱码。
> 本文件给出强制规范。

## 1. 文件路径：优先 ASCII，避免中文目录

- REA 大量读写本地路径（如 `open_binary` 的 `path`、`export_evidence_bundle` 的输出路径）。
- **中文（或非 ASCII）路径在部分 provider / 子进程下会解析失败或静默截断。**
- 建议：
  - 把待分析目标与输出目录放在 **纯 ASCII 路径**（如 `C:/rea/work/`、`/tmp/rea/`）。
  - 避免 `桌面`、`下载`、`我的文档`、含中文的项目名等作为目标/输出根。
  - 若必须用中文路径，先做一次 ASCII 测试（`open_binary` 一个英文路径样本）确认环境 OK。

## 2. 终端/控制台编码：统一 UTF-8

- 引擎所有输出（Evidence、错误、日志）为 **UTF-8 英文**。
- 中文 Windows 默认控制台为 **GBK（代码页 936）**，直接运行会把 UTF-8 字节误读成乱码。
- 解决：
  - **PowerShell**：`chcp 65001` 切到 UTF-8 后再运行；或在终端设置中把编码设为 UTF-8。
  - **CMD**：`chcp 65001`。
  - **IDE / WorkBuddy 内置终端**：多数默认 UTF-8，无需处理；若遇乱码，确认终端编码非 GBK。
  - 把引擎输出重定向到文件（`.json` / `.md`）后再用 UTF-8 阅读器打开，可彻底避开控制台编码问题。

## 3. 输入参数：值可用中文，键必须英文

- 工具入参是 JSON 对象：**键**一律英文 `snake_case`；**值**（路径、注释文本、查询字符串）可用中文，但路径值仍建议 ASCII（见第 1 节）。
- 例（正确）：
  ```json
  { "tool": "set_comment", "address": "0x1000", "comment": "此处为登录校验分支", "document": "main" }
  ```

## 4. 中文 LLM 输出：翻译呈现即可

- 引擎返回的英文 Evidence 由 LLM **翻译为中文结论**呈现给用户；不要把英文结果改写后回灌给引擎当输入。
- 若需把分析结论/注释写入二进制元数据（`set_comment` 等），中文注释本身无害（UTF-8 存储），但请确认目标 provider 支持 UTF-8 注释。

## 5. 自查清单

- [ ] 目标与输出路径是否为 ASCII？
- [ ] 终端编码是否为 UTF-8（非 GBK）？
- [ ] 重定向到文件阅读时是否以 UTF-8 打开？
- [ ] 参数键是否英文、值是否合法 UTF-8？
