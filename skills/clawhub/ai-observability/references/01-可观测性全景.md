# 01 可观测性全景

> 适用：AI 应用上线前的监控设计——先定范围
> 核对基准日：2026-08

## 1. 为什么 AI 需要专门的可观测性

传统应用监控（CPU/内存/接口错误率）对 AI 应用远远不够：
- **模型行为不可预测**：同样的输入可能输出不同质量
- **成本随调用线性增长**：Token 费用是新增成本维度
- **质量问题隐蔽**：回答"能用但错"比"报错"更难发现
- **护栏/合规新增**：注入攻击、敏感数据泄漏是 AI 特有风险

## 2. 三大支柱 + AI 扩展

```
传统三大支柱：
├─ 日志（Logs）：事件记录
├─ 指标（Metrics）：聚合统计
└─ 追踪（Traces）：调用链
AI 扩展观测对象：
├─ 模型行为：幻觉率/拒答率/质量评分
├─ Token 成本：输入/输出 Token 消耗
├─ 护栏命中：注入拦截/敏感词拦截
└─ Prompt 状态：版本/参数/上下文长度
```

## 3. 观测对象全景（六类）

| 类别 | 观测内容 | 示例指标 |
|---|---|---|
| 质量 | 输出质量 | 幻觉率、拒答率、质量评分 |
| 行为 | 用户与交互 | 满意度、转人工率、会话长度 |
| 性能 | 响应效率 | 延迟（TTFT/TPS）、吞吐 |
| 成本 | Token 消耗 | 单次成本、日成本、成本分布 |
| 安全 | 风险拦截 | 护栏命中率、注入检测数 |
| 依赖 | 外部依赖 | 模型 API 错误率、超时、限流 |

## 4. 监控分层设计

```
L0 基础设施层：服务器/网络/存储（复用现有监控）
L1 应用层：接口/服务/错误率（传统 APM）
L2 AI 层：模型行为/质量/成本/护栏（本技能重点）
L3 业务层：满意度/转化/留存（业务指标）
```

- L0-L1 复用现有体系，**重点补 L2**
- L3 与业务团队共建

## 5. 设计原则
1. **先定 SLO**：核心指标的目标值（如幻觉率 <3%、延迟 P95 <2s）
2. **少而精**：核心指标 10-20 个，别堆百个指标没人看
3. **可行动**：每个指标都有响应动作（告警/看板/复盘）
4. **隐私合规**：监控采集要过滤敏感信息（衔接数据法规）
