# Bug修复工作流

## 目标
规范Bug修复的完整流程，确保问题快速解决且不影响系统稳定性。

## 工作流步骤

### 阶段1：问题确认与分类
**时间**：收到Bug报告时
**行动**：
1. 确认问题存在
2. 收集问题信息
3. 分类问题严重程度
4. 确定修复优先级

**问题分类标准**：
```
P0级（紧急）：
- 系统完全不可用
- 核心功能受损
- 数据丢失风险
- 需要立即处理

P1级（重要）：
- 主要功能异常
- 用户体验严重受损
- 需要尽快修复（24小时内）

P2级（一般）：
- 次要功能问题
- 用户体验受影响
- 可以计划修复（1周内）

P3级（轻微）：
- 界面显示问题
- 非核心功能异常
- 可以后续优化
```

**检查点**：
- [ ] 问题已确认
- [ ] 问题信息已收集
- [ ] 严重程度已分类
- [ ] 优先级已确定

### 阶段2：分支策略选择
**时间**：开始修复前
**行动**：
1. 根据问题类型选择分支策略
2. 创建修复分支
3. 设置分支保护规则

**分支策略选择**：
```
1. 创建热修复分支（P0/P1级问题）
   - 从main分支创建
   - 命名：hotfix/[问题描述]
   - 适合：线上紧急问题

2. 在dev分支上修复（P2级问题）
   - 从dev分支创建修复分支
   - 命令：git checkout -b fix/[问题描述]
   - 适合：非紧急问题

3. 在现有分支上修复（P3级问题）
   - 在当前功能分支上修复
   - 适合：小问题快速修复
```

**检查点**：
- [ ] 分支策略已确定
- [ ] 修复分支已创建
- [ ] 分支名符合规范

### 阶段3：问题分析与定位
**时间**：分支创建后
**行动**：
1. 分析问题原因
2. 定位问题代码
3. 确定影响范围
4. 制定修复方案

**分析工具**：
```bash
# 查看错误日志
tail -f logs/error.log

# 查看代码修改历史
git log --oneline --graph

# 查看文件修改历史
git log -p --follow [文件名]

# 查看特定提交
git show [commit-hash]
```

**检查点**：
- [ ] 问题原因已分析
- [ ] 问题代码已定位
- [ ] 影响范围已确定
- [ ] 修复方案已制定

### 阶段4：问题修复
**时间**：分析完成后
**行动**：
1. 实施修复方案
2. 编写修复代码
3. 编写测试用例
4. 本地测试验证

**修复规范**：
```bash
# 1. 修复代码
# ... 修改代码 ...

# 2. 编写测试
# ... 编写单元测试 ...

# 3. 本地测试
pnpm test

# 4. 提交修复
git add .
git commit -m "fix: 修复[问题描述]

- 问题原因：[原因分析]
- 影响范围：[影响描述]
- 修复方案：[方案描述]"
```

**检查点**：
- [ ] 修复代码已编写
- [ ] 测试用例已编写
- [ ] 本地测试通过
- [ ] 提交信息规范

### 阶段5：测试验证
**时间**：修复完成后
**行动**：
1. 在测试环境验证
2. 执行回归测试
3. 确认问题已解决
4. 确认无副作用

**测试清单**：
```markdown
## 问题修复验证
- [ ] 原问题已解决
- [ ] 相关功能正常
- [ ] 边界条件测试通过
- [ ] 异常情况处理正常

## 回归测试
- [ ] 核心功能测试通过
- [ ] 性能测试通过
- [ ] 安全测试通过
- [ ] 兼容性测试通过

## 影响评估
- [ ] 无新增问题
- [ ] 无性能下降
- [ ] 无安全风险
- [ ] 无用户体验下降
```

**检查点**：
- [ ] 问题修复已验证
- [ ] 回归测试通过
- [ ] 无副作用
- [ ] 测试报告已记录

### 阶段6：合并发布
**时间**：测试验证后
**行动**：
1. 创建Pull Request
2. 代码审查
3. 合并到相应分支
4. 部署到相应环境

**合并策略**：
```
P0/P1级问题：
1. 合并到main分支
2. 合并到dev分支
3. 立即部署到生产环境
4. 监控系统状态

P2级问题：
1. 合并到dev分支
2. 部署到测试环境
3. 验证通过后合并到main
4. 计划部署到生产环境

P3级问题：
1. 合并到dev分支
2. 随版本一起发布
3. 部署到生产环境
```

**检查点**：
- [ ] Pull Request已创建
- [ ] 代码审查已通过
- [ ] 已合并到相应分支
- [ ] 已部署到相应环境

### 阶段7：监控与确认
**时间**：部署后
**行动**：
1. 监控系统状态
2. 收集用户反馈
3. 确认问题已解决
4. 记录修复过程

**监控清单**：
```markdown
## 系统监控
- [ ] 错误日志正常
- [ ] 性能指标正常
- [ ] 系统稳定性正常

## 用户反馈
- [ ] 用户确认问题解决
- [ ] 无新的相关问题
- [ ] 用户体验正常

## 文档更新
- [ ] 问题记录已更新
- [ ] 修复方案已记录
- [ ] 知识库已更新
```

**检查点**：
- [ ] 系统状态正常
- [ ] 用户确认解决
- [ ] 文档已更新
- [ ] 修复过程已记录

## 常见问题处理

### 1. 问题定位困难
```bash
# 1. 扩大日志范围
tail -f logs/error.log | grep "相关关键词"

# 2. 使用调试工具
# 在代码中添加console.log
# 使用浏览器开发者工具

# 3. 二分法定位
git bisect start
git bisect bad [当前提交]
git bisect good [已知正常提交]
```

### 2. 修复引入新问题
```bash
# 1. 回滚修复
git revert [修复提交]

# 2. 分析新问题
# ... 分析新问题原因 ...

# 3. 重新修复
# ... 编写新的修复方案 ...
```

### 3. 多个问题同时出现
```bash
# 1. 优先处理P0/P1级问题
# 2. 为每个问题创建独立分支
git checkout -b hotfix/问题1
git checkout -b hotfix/问题2

# 3. 分别修复，独立测试
# 4. 按优先级合并发布
```

## 工具和脚本

### 热修复分支创建脚本
```bash
# 创建热修复分支
./scripts/create-hotfix-branch.sh [问题描述]

# 从最新release分支创建
./scripts/create-hotfix-branch.sh [问题描述] --from-release
```

### 问题跟踪脚本
```bash
# 记录问题修复过程
./scripts/log-bug-fix.sh [问题描述] [修复方案]

# 生成问题报告
./scripts/generate-bug-report.sh [时间范围]
```
