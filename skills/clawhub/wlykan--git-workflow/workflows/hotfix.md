# 热修复工作流

## 目标
规范紧急问题修复的完整流程，确保问题快速解决且最小化影响。

## 工作流步骤

### 阶段1：紧急问题确认
**时间**：收到紧急问题报告时
**行动**：
1. 确认问题严重程度
2. 评估影响范围
3. 确定修复优先级
4. 组建紧急响应团队

**紧急程度评估**：
```
P0级（系统瘫痪）：
- 系统完全不可用
- 核心业务中断
- 数据丢失风险
- 响应时间：立即

P1级（严重受损）：
- 主要功能异常
- 大量用户受影响
- 业务损失严重
- 响应时间：< 1小时

P2级（部分受损）：
- 次要功能异常
- 部分用户受影响
- 业务损失较轻
- 响应时间：< 4小时
```

**影响范围评估**：
```markdown
## 影响范围评估
- 用户影响：[ ] 全部用户 [ ] 部分用户 [ ] 少量用户
- 功能影响：[ ] 核心功能 [ ] 主要功能 [ ] 次要功能
- 业务影响：[ ] 严重损失 [ ] 一般损失 [ ] 轻微损失
- 时间影响：[ ] 持续中断 [ ] 间歇中断 [ ] 偶发问题
```

**检查点**：
- [ ] 问题已确认
- [ ] 影响范围已评估
- [ ] 优先级已确定
- [ ] 响应团队已组建

### 阶段2：紧急分支创建
**时间**：确认问题后立即
**行动**：
1. 从main分支创建热修复分支
2. 命名规范：hotfix/[问题描述]
3. 设置分支保护规则
4. 通知相关人员

**分支创建**：
```bash
# 1. 从main分支创建热修复分支
git checkout main
git pull origin main
git checkout -b hotfix/login-crash-fix

# 2. 推送到远程（可选）
git push origin hotfix/login-crash-fix

# 3. 通知团队
# 发送紧急修复通知
```

**分层合并流程**：
```
热修复分支 → main分支（紧急修复）
热修复分支 → dev分支（同步修复）
```

**检查点**：
- [ ] 热修复分支已创建
- [ ] 分支已推送到远程
- [ ] 相关人员已通知
- [ ] 修复团队已就位

### 阶段3：紧急问题分析
**时间**：分支创建后立即
**行动**：
1. 快速定位问题原因
2. 分析影响范围
3. 制定最小化修复方案
4. 评估修复风险

**快速定位方法**：
```bash
# 1. 查看错误日志
tail -f logs/error.log | grep "相关关键词"

# 2. 查看最近提交
git log --oneline -10

# 3. 查看代码修改
git diff HEAD~5 --name-only

# 4. 使用调试工具
# 在代码中添加console.log
# 使用浏览器开发者工具
```

**最小化修复原则**：
```markdown
## 最小化修复原则
1. 只修改必要的代码
2. 不引入新功能
3. 不进行重构
4. 不优化性能
5. 不修改配置

## 修复范围控制
- 修复文件数量：< 5个
- 代码修改行数：< 50行
- 影响模块数量：< 3个
```

**检查点**：
- [ ] 问题原因已定位
- [ ] 影响范围已确认
- [ ] 修复方案已制定
- [ ] 修复风险已评估

### 阶段4：紧急问题修复
**时间**：分析完成后立即
**行动**：
1. 实施最小化修复
2. 编写必要测试
3. 本地快速验证
4. 提交修复代码

**修复规范**：
```bash

# ... 修改代码（最小化修改）...

# 2. 编写测试（如必要）
# ... 编写关键测试用例 ...

# 3. 本地验证
pnpm test

# 4. 提交修复
git add .
git commit -m "hotfix: 紧急修复登录崩溃问题

问题原因：[简要原因]
修复方案：[简要方案]
影响范围：[影响描述]
风险评估：[风险描述]"
```

**修复验证**：
```markdown
## 修复验证清单
- [ ] 原问题已解决
- [ ] 核心功能正常
- [ ] 无新增问题
- [ ] 性能无明显下降
- [ ] 安全无风险
```

**检查点**：
- [ ] 修复代码已编写
- [ ] 测试已执行
- [ ] 本地验证通过
- [ ] 修复已提交

### 阶段6：紧急发布 ⚠️ REQUIRED
**时间**：测试验证后立即
**行动**：
1. 合并到main分支（紧急修复）
2. 创建热修复标签
3. 部署到生产环境
4. 验证发布结果
5. 合并到dev分支（同步修复）

**分层合并流程**：
```
热修复分支 → main分支（紧急修复）
热修复分支 → dev分支（同步修复）
删除热修复分支
```

**紧急发布命令**：
```bash
# 1. 合并到main分支
git checkout main
git merge --no-ff hotfix/login-crash-fix

# 2. 创建热修复标签
git tag -a v1.2.1 -m "热修复版本 1.2.1

修复内容：
- 紧急修复登录崩溃问题

影响范围：
- 所有用户

修复方案：
- [简要修复方案]"

# 3. 推送到远程
git push origin main
git push origin v1.2.1

# 4. 合并到dev分支（同步修复）
git checkout dev
git merge --no-ff hotfix/login-crash-fix
git push origin dev

# 5. 删除热修复分支
git branch -d hotfix/login-crash-fix
git push origin --delete hotfix/login-crash-fix
```

**检查点**：

**行动**：

4. 记录修复过程

```markdown
- 发布后4-24小时：每小时检查一次

## 监控指标
- 系统性能：响应时间、吞吐量、错误率

## 异常处理
- 发现异常：立即评估影响
- 严重异常：准备回滚
- 一般异常：记录并观察
```

## 常见问题处理

### 1. 修复引入新问题
```bash
# 1. 立即回滚
git checkout main
git reset --hard v1.2.0
git push origin main --force

# 2. 分析新问题
# ... 分析问题原因 ...

# 3. 重新修复
git checkout -b hotfix/new-issue
# ... 重新修复 ...

# 4. 重新发布
# ... 按照正常流程发布 ...
```

### 2. 修复时间过长
```bash
# 1. 评估是否继续修复
# 如果超过预期时间，考虑：
# - 回滚到稳定版本
# - 临时关闭问题功能
# - 发布临时解决方案

# 2. 调整修复方案
# 简化修复范围
# 聚焦核心问题
# 寻求外部帮助
```

### 3. 多个紧急问题同时出现
```bash
# 1. 评估优先级
# 按照影响范围和严重程度排序

# 2. 优先处理最高优先级问题
# 集中资源解决最关键问题

# 3. 其他问题临时处理
# 临时关闭问题功能
# 发布临时解决方案
# 计划后续修复
```
