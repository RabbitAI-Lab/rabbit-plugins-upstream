# Anti-Patterns: What NOT to Do

基于真实用户反馈的失败案例。以下每个反模式均来自实际交接文档被批评"太抽象、无法理解"。

---

## 反模式1：业务讲解太薄

### ❌ 错误做法
```
## 一句话讲清楚这个项目
这是催收实验的监控探头。

## 业务类比
你开了一家电话催收公司...

（然后立刻跳到20个表格的技术细节）
```

### ✅ 正确做法
业务讲解应占全文40%。以3-5段正式书面语阐述：
- 项目解决的业务问题
- 上游数据来源与下游消费者
- 技术方案概述
- 版本迭代说明

接手者看完此段应能向管理层汇报项目业务定位。

---

## 反模式2：用表格替代讲解

### ❌ 错误做法
用20个表格讲业务逻辑、执行流程、代码设计——每个表格5-10行，全文29KB，如同审计报告。

### ✅ 正确做法
- **正式书面语**叙述：业务逻辑、执行流程、代码设计意图
- **表格**仅用于查表：业务规则速查、环境变量列表、修改指引
- 如果一个内容是"通读理解"的，用书面语叙述；如果是"回头查阅"的，用表格

---

## 反模式3：强套4层框架

### ❌ 错误做法
项目没有 utils 模块、没有模型，但仍然硬填：
```
### 4.1 工具层 utils
（本项目没有自己的utils模块...）

### 4.3 模型核心层
（本项目不含模型训练...）
```

### ✅ 正确做法
自适应：有则讲，无则跳。只讲最重要的2-3个文件。

---

## 反模式4：风险列19条

### ❌ 错误做法
列19个风险点，分4类×3级，每个一行。读者看到第5条即失去耐心。

### ✅ 正确做法
只列Top 5，按严重程度排序（红/黄/绿）。每个风险：
1. 一句话描述问题（加粗）
2. 2-3句话分析影响与后果
3. 标注 `文件:行号`

---

## 反模式5：流程图画满屏

### ❌ 错误做法
画一个超过10个框的ASCII流程图，嵌套3层，阅读负担重。

### ✅ 正确做法
以5-8段正式书面语阐述主流程。如确需图示，使用简单缩进列表。

---

## 反模式6：文档太长

### ❌ 错误做法
HANDOVER.md 29KB，需30分钟通读，实际无人阅读。

### ✅ 正确做法
- HANDOVER.md 目标10-15KB，15分钟通读
- 超过20KB？精简技术细节，保留业务理解
- QUICKSTART.md 目标2-3KB，5分钟通读

---

## 反模式7：口语化表述

### ❌ 错误做法
使用"打个比方""蒙混过关""开后门""踩了会怎样""这东西干嘛的"等口语化词汇，降低文档专业性。

### ✅ 正确做法
全程使用正式书面语。对照参考：

| 禁止 | 推荐 |
|------|------|
| "打个比方" | "举例而言" 或直接陈述 |
| "蒙混过关" | "通过 NULL 传播规避问题" |
| "开后门" | "通过命名规则手动回捞" |
| "为什么这么写" | "设计意图" |
| "踩了会怎样" | "风险影响分析" |
| "像给同事讲" | "以专业视角阐述" |
| "这东西干嘛的" | "项目概述" / "业务背景" |

章节使用中文数字编号（一、二、三...），子节用 1.1、1.2 格式。
