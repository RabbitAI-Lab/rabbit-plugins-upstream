# Reply Polish：工作回复润色

把用户已经写好的回复润色成自然、专业、简洁的职场表达。目标是**发出去像用户自己平时说话，只是更清楚、更得体**——不是把话说"高级"。

## 硬原则（不可违背）

1. **保留原意，不擅自增加事实。** 不补充用户没说的信息、不替用户表态、不把"大概"改成"肯定"。
2. **说话方式优先保留。** 用户的口头禅、语气词（"嗯""哈""诶"）、口语短句、省略号收尾都是他的声音，不是待清除的噪声。好的润色读起来仍像同一个人。
3. **过度润色等于失败。** 一句话如果已经清楚自然，就别动它。润色以减法为主：删重复、删套话、删无意义客套，而不是逐句换词。三处关键改动好过三十处机械替换。
4. **意思第一，风格第二。** 去掉某种 AI 腔如果会改变原意或弱化用户的立场，保留原句。
5. **技术内容保持准确。** 接口名、字段名、数字、时间、因果链一个都不能动错；技术术语不为了"通俗"而失真。

## 工作流

1. **读草稿**：判断三个变量——受众是谁（领导/产品/后端/同事/客户）、场合（私聊/群聊/邮件/评论区）、意图（同步进展/求助/拒绝/催办）。草稿里看不出来且影响措辞时，先问一句再动笔。三个变量各有配套动作：
   - **受众** → 按下方语气校准表；
   - **场合** → 群聊/评论区对事不对人，需要否定或批评具体某人时建议转私聊说；
   - **意图** → 催办给明确时间点（"今天下班前"优于"尽快"）；求助先说自己已经试过什么再问；同步坏消息先给结论再给原因；拒绝给清楚理由和可行替代，不含糊拖着也不硬顶。
2. **动笔**：按硬原则做最小改动。优先砍，其次调语序，最后才是换词。
3. **输出**：默认只给一个最推荐版本，可直接复制发送，**不解释修改过程**。仅当用户要求时才给"原文 → 改后 → 理由"对照；仅当用户明示拿不准、或草稿本身是高风险内容（拒绝、坏消息、催办领导）时，才给稳妥/直接两版让他挑。

## 受众语气校准

| 受众 | 分寸 |
|---|---|
| 领导 | 说清进展和风险，不过度承诺，不铺技术细节 |
| 产品 | 需求边界说明白（能做/不能做/要多久），少用技术黑话，分歧对事不对人 |
| 后端/研发同行 | 技术准确优先，直截了当；带上下文（接口、字段、复现路径），不用铺客套 |
| 同事日常 | 自然随意，能不动就不动 |
| 客户/外部 | 礼貌但不卑不亢，避免内部术语外泄和负面信息扩散 |

拿不准受众时按"对方需要拿这条信息做什么"来定颗粒度：领导要的是判断依据，产品要的是边界，同行要的是细节。

**校准的边界（与硬原则 3 的裁决）**：受众规则只修草稿已有的问题。原稿的顺序确实让对方抓不住重点时才调语序；不为了"结论先行"而重组已经清楚的句子，更不因为对面是领导就把口语改成公文。

## 删什么：AI 腔与公文腔黑名单

黑名单是"味道样本"不是机械替换表——命中味道的才改，在语境里自然的词留着。

- **套话连接**：针对……这一情况 / 基于……的考虑 / 从而实现…… / 以达到……的效果 / 值得注意的是 / 综上所述 / 总的来说
- **公文式结构**：首先、其次、最后 / 不仅……还……（对仗句式）/ 三个一组的排比
- **机器客气**（日常 IM 场景；对外正式邮件可保留基本礼貌）：感谢您的理解与支持 / 感谢配合 / 望周知
- **虚张声势**：进一步提升……能力 / 有效保障…… / 助力…… / 赋能……
- **啰嗦前摇**：在……的过程中 / 我这边想问一下能不能就是 / 其实就是说

## 示例

**示例一：过度润色（反例，禁止产出这种）**

> 原文：嗯，之前有一些需求，还有产品经理口头提的、临时比较急的需求没地方放，所以我加了一个需求类型，后面统一录到这里。
>
> ❌ 针对此前部分需求以及产品经理临时提出的紧急需求，由于缺乏统一的归档入口，因此新增了该需求类型，用于统一记录相关事项。
>
> ✅ 嗯，之前有一些需求没地方放，还有一些是产品经理口头提的、临时比较急的，所以我加了一个需求类型，后面统一记到这里。

第一版"改好了"每句话，但说话的人没了——这就是失败。

**示例二：同一份草稿，不同受众**

> 草稿：接口文档我看了，列表页的分页参数用的 page/pageSize，但后端实际返回的是 cursor 模式，两边对不上，联调时翻页会丢数据，我看是文档没更新还是接口改了，明天碰一下？
>
> 给后端：文档和实际返回对不上。文档写的 page/pageSize 分页，接口返回 cursor 模式，联调翻页会丢数据。是文档没更新还是接口改了？明天碰一下。
>
> 给领导：发现列表翻页有个问题，接口文档和实际返回的参数模式不一致，联调时会丢数据。我在核对，明天给结论。

给后端保留全部技术细节和提问，给领导砍掉细节、只留风险和承诺的时间点——两版都还是草稿作者的口吻。（实际使用中受众不明先问一句再动笔，此处为演示受众对照。）

**示例三：黑名单命中**

> 草稿：这个方案上线后可以进一步提升系统的查询效率，从而实现用户体验的优化。
>
> ✅ 上线后查询能快一些，用起来也会更顺畅。

## 留什么：个人声音

- 语气词和口头禅（"嗯""哈""这样""OK 那个"）——除非密度高到影响专业形象
- 不完整句式和口语节奏——职场聊天不是书面语
- 用户自己的判断和态度（委婉的拒绝、保留的赞同）——润色只顺表达，不软化也不激化立场

## 发送前自检

- [ ] 以原稿未改动的语气为基准，改后的句子插回去不违和
- [ ] 事实、数字、术语与原稿一致，没多没少
- [ ] 对方扫一眼就知道说什么（需要调序才调，见"校准的边界"）
- [ ] 中英文/数字之间有空格，标点全半角跟随原稿习惯并保持统一
- [ ] 不新增破折号；原稿自带的破折号保留或换成逗号，以不打断语气为准
- [ ] 长度不比原稿明显更长——润色做减法，越改越长通常方向错了

## 与相邻技能的分工

判据：**发给具体某人/某群的双向沟通消息归本技能，无论长短；面向不特定公众、无具体收件人的成段内容归 write / humanizer-zh。**

| 需求 | 用哪个 |
|---|---|
| 改已写好的工作回复、拿不准措辞 | **reply-polish（本技能）** |
| 沟通方法论、邮件模板、会议纪要框架 | professional-communication |
| 成段文章/文案的重写与去 AI 味 | write / humanizer-zh |
| 从零起草内部通讯/邮件 | internal-comms |
| 优化给 AI 的提示词 | prompt-optimizer |
