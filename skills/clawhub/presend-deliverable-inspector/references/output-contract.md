# 输出合同

所有输出第一屏必须能看出能不能发。

## 标准版

```markdown
出街判定：[可以发送 / 快改后发送 / 暂缓发送 / 重做后再发]
我按这个上下文判：发给[对象]，目标[动作]，时间[截止]。
权重依据：优先看 [上下文导致的 1-3 个风险域]。

必须改：
1. [位置] [error_family/error_type] [发现依据] -> [修法]

可以保留：
- [结构、顺序、图表或表达里已经成立的部分]

30 分钟修复路线：
1. [0-10 分钟] [先修事实、来源、数字]
2. [10-20 分钟] [再修标题、结论、图表匹配]
3. [20-30 分钟] [最后补下一步和发送话术]

未核验项：
- [影响发送但当前材料无法确认的事项]
```

当已有 inspection JSON 时，优先运行 `scripts/render_inspection_report.py` 生成用户式报告，避免宿主自由改写导致格式漂移。

## JSON 上下文字段

`context_basis` 除基础字段外必须包含：

- `context_signals`：每条写 `field`、`value`、`source`、`impact`。
- `risk_weighting`：每条写 `risk_area`、`direction`、`reason`。

这两个字段用于证明判定读过语境，并说明为何某些风险进入前列。

`must_fix` 只承载首屏前 7 条。其余发现进入 `additional_findings`；`finding_overflow` 必须给出发现总数、首屏条数、其余条数、其余阻断数、全部其余位置和展开入口。发送判定按全部发现计算，不能按首屏截断后的数组计算。

## 快速版

用户只问“能不能发”或时间很紧时：

```markdown
判定：[判定]
上下文：[对象 + 目标 + 截止；缺失则写缺口]
先别动结构，先修：[最关键 1-3 项]
能保留：[1 句话]
现在 30 分钟：[三步动作]
```

## 位置写法

| 文件 | 位置 |
| --- | --- |
| PPT | 第 X 页、标题、图表、备注、附录 |
| Word | 第 X 页、第 X 节、段落标题、表格 |
| PDF | 第 X 页、图 X、表 X、脚注 |
| Excel | 工作表、单元格区域、图表、透视表、隐藏表 |
| 粘贴内容 | 小标题、段落序号、原句片段 |

## 问题写法

每条必须改都用同一结构：

```text
[位置] [错误族/错误类型] [发现依据] -> [修法]
```

示例：

```text
第 7 页 reasoning_gap/claim_evidence_gap：标题写“已验证可规模化”，图表只显示 1.2% 波动 -> 改成“初步验证，仍需补样本”。
```

错误族和错误类型都取自 `references/error-library.md`，不要自造分类。

## 修复路线排序

1. 先处理来源、数字、口径、版本。
2. 再处理标题、结论、图表匹配。
3. 再补老板或客户需要的下一步。
4. 最后才做美化、语气和格式。

## 上下文缺口写法

无法确认对象或目标动作时，不要装作已经确认。

```markdown
我先按保守场景判：收件人和目标动作未确认。
```

报告正文和 `未核验项` 使用中文业务标签；JSON 的 `context_basis.missing_context` 保留机器字段名，便于验收和审计。

缺口只写影响判定的内容：

- 收件对象不清，无法判断承诺边界。
- 目标动作不清，无法判断最后一页够不够。
- 没有源文件，只能按截图或粘贴内容判断。
- 没有备注、隐藏表或底层数据，数字一致性仍需复查。

## 结尾入口

给 2-3 个短入口：

- `按30分钟路线改`
- `只看必须改`
- `生成老板版修订稿`
- `生成客户版修订稿`
- `帮我做发送话术`
