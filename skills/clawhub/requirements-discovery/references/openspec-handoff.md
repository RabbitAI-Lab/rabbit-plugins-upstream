# OpenSpec 交接规则

仅在用户选择 OpenSpec 或当前项目既定流程需要它时使用。读取本参考不会授予创建或修改文件的权限。

## 复用现有上下文

先确定目标项目、已有 change 和用户授权范围。用户已指定目标时直接使用；有多个实际候选且会影响写入位置时再澄清。不重复询问已确认业务规则，不另建重复 change。

使用当前环境可用的 OpenSpec 流程。依据其实际 schema、产物依赖、模板、项目约束和解析后的输出路径生成材料，不硬编码目录或假设特定 CLI 版本。工具缺失时报告限制，保留可交接内容，不擅自安装或初始化。

## 内容映射

| 已澄清内容 | 常见产物用途 |
| --- | --- |
| 目标、范围、价值 | proposal |
| 已确认业务规则、可观察验收场景 | specs |
| 现状证据、约束、经评估的技术选择 | design |
| 实施步骤、依赖、验证安排 | tasks |

这是内容映射，不是固定产物清单；以当前项目 schema 为准。技术建议进入 design 前仍需评估，不能伪装成用户要求。新增业务冲突回到对应问题，勿重启整轮访谈。

## 唯一维护位置

澄清期间以对话草稿为准。授权落盘并完成交接后，明确具体 change 和对应产物为本次变更的维护位置；不额外保存一份长期重复的完整需求契约。

已有需求文档需要保留时，不擅自删除或覆盖：明确它是原始输入、历史快照还是项目指定的权威文档，并用引用减少重复。若权威来源相互冲突，解决冲突后再更新依赖材料。

归档后遵守项目既定的主规格维护流程，不把已归档 change 永久当成当前系统规格。

## 交接检查

- 已确认规则与验收场景完整映射，没有新增未经确认的业务行为。
- 阻塞项已解决；可建议项仍保留其技术建议属性。
- 用户改变决策后，受影响的规则、场景、设计和任务保持一致。
- 按实际流程检查产物；检查通过只能证明对应检查范围。
- 报告维护位置、材料就绪情况和仍未执行的验证。
- 已授权实施时接续实施；只授权保存方案时停留在方案范围，不额外请求重复确认。
